The Saga pattern is how you get **data consistency across multiple services/databases** without a distributed transaction. `@Transactional` gives you atomicity within *one* connection — the moment a flow spans services, each with its own DB, no single boundary can cover all of them, and Saga is what you reach for instead of 2PC.

> The one-paragraph version of this pattern already lives in [[11. Transaction Boundaries]] §8–§11 (compensation as a reversal entry, choreography vs orchestration, the "why not 2PC" table, the full payment-flow shape). This note is the **deep dive**: the eight things that actually make Saga hard in production, not just the diagram.

> - **Why 2PC is disqualified, and the two-worlds mental model** → [[11. Transaction Boundaries]] §4, §10
> - **The idempotency-key mechanics referenced everywhere below** → [[10. Distributed Concurrency]] §7

> - **Correlation-ID propagation across service/message boundaries (the observability half)** → [[3. Distributed Logging]], [[5. Observability]] §3

> [!info] The through-line of this note
> Saga trades one guarantee (atomicity) for two others (availability, throughput) — and everything below is the bill for that trade.
>
> 1. The core move (§1–§2): replace one distributed transaction with a **sequence of local transactions**, undone by **compensation** instead of rollback, coordinated by **choreography or orchestration** (§3).
> 2. That move immediately costs you **isolation** (§4) — other readers see intermediate, possibly-doomed state — and it means "undo" is really "record a new opposite fact" (§5), which some actions can't even do (§6).
> 3. Because every step can be retried (timeouts, crashes, at-least-once delivery), **idempotency stops being optional** (§7) and even the compensation itself needs to survive a crash (§8) — which is why real sagas persist their state instead of holding it in memory.
> 4. The two problems that actually page someone at 3 a.m. are **not knowing if a step landed** (§9) and **not being able to reconstruct what happened** across five services' logs (§10).
> 5. No amount of in-flight correctness logic closes every timing window, so production systems add **reconciliation** as an out-of-band safety net (§11) — the same idea NPCI itself uses for UPI settlement.
>
> One line to anchor everything: **Saga buys you availability by giving up one global commit — everything in this note is a consequence of that one missing commit.**

## Short Notes

---

### 1. The Core Problem — Why Not 2PC

A UPI transaction might need to:
1. Debit the payer (Payment service, own DB)
2. Credit the payee (Ledger service, own DB)
3. Update transaction status (Switch/Orchestrator service, own DB)
4. Send a notification

- You can't wrap all four in one `@Transactional` — separate databases, possibly separate services
- **2PC/XA** technically solves it but holds locks **across services** and makes the coordinator a single point of failure — not viable at UPI-scale volumes → full disqualification table in [[11. Transaction Boundaries]] §10
- **Saga's answer**: a sequence of **local transactions**, each committing independently; a later failure triggers **compensating transactions** on the earlier ones instead of a rollback

---

### 2. The Mechanism — Local Transactions + Compensation

```text
Forward:      Debit Payer → Credit Payee → Update Status → Notify
                                  ✗ fails
Compensate:              ← Reverse Credit ← (nothing to undo before it)
```

- Each arrow is its **own committed transaction** — there is no single rollback that spans them
- Compensation only undoes **already-committed** steps, working backward from the failure point

---

### 3. Choreography vs Orchestration

| | Choreography | Orchestration |
|---|---|---|
| Coordination | None — each service finishes its local transaction and publishes an event; the next service reacts | A central coordinator explicitly tells each service what to do next and tracks overall state |
| Coupling | Loose — services only know events | Tighter — orchestrator knows the whole flow |
| Complexity as steps grow | Hard to trace ("which service reacts to what") | Centralized — easier to visualize and debug |
| Single point of failure | None | The orchestrator itself needs to be reliable/HA |
| Good fit | Few services, simple flows | Complex flows with branching — most payment engines choose this |

- ⭐ A flow like *try PSP-A → timeout → fallback to PSP-B → reconcile → notify* has enough branching that a choreographed event-web gets hard to reason about — orchestration is the standard choice for payment orchestrators
- Real implementations: **Axon Framework**, **Eventuate Tram**, or a hand-rolled state machine — a `saga_state` table + Kafka events — which is what most UPI/PSP systems actually run, precisely because state is **persisted**, not in-memory, so a crashed orchestrator can resume

---

### 4. No Isolation Between Sagas ⭐

The property that trips people up most: sagas have **no "I" in ACID**.

**Concrete anomaly**: Saga A debits ₹500 (step 1 committed). Before Saga A's later steps run, Saga B reads that account and decides based on the *already-debited* value — even though Saga A might still fail and compensate, putting the money back. Saga B acted on transient, possibly-wrong data.

- Since each local transaction commits immediately, **other transactions can read intermediate saga state** — a payer's balance can show debited *before* the payee is credited
- This is only **eventual** consistency, never real isolation

**Mitigations (all partial):**
- **Semantic lock** — mark the resource `PENDING`/`LOCKED` for the saga's duration; others wait or reject
- **Commutative updates** — design ops so order doesn't matter (`-500` then `+500` commutes regardless of interleaving)
- **Pessimistic re-read** — dependent sagas re-verify state right before their own critical step instead of trusting an earlier read

---

### 5. Compensations Are Forward Transactions, Not Rollbacks

- "Undo" ≠ deleting a row — the money already left the account and may already be visible to other reads/reports
- The compensation for "debit ₹500" is "credit ₹500," recorded as a **new** entry, never an erasure
- ⭐ In an NPCI/RBI-style ledger, compensations must be first-class recorded events — the audit trail needs the reversal to be **visible**, not the original mistake to be **hidden**

---

### 6. Not Everything Is Compensatable

- "Send SMS" can't really be undone — you either accept it (compensate with a follow-up "transaction reversed" SMS) or design the step to run only after the saga's point of no return
- An external bank/NPCI API call that already executed with no reversal endpoint has the same problem
- **Rule**: sequence irreversible steps **last**, after the point where failure becomes vanishingly unlikely — never make "send confirmation SMS" step 2 of 7

---

### 7. Idempotency — Required at Every Single Step ⭐

Steps get retried: timeouts, orchestrator crash-and-resume, at-least-once delivery from Kafka. **Every forward step and every compensation must be idempotent**, or a retry double-executes it.

**Classic dangerous example**: orchestrator calls "credit payee ₹500," the write succeeds, the response is lost — the same in-doubt scenario as a bare `@Transactional` commit ([[Transactional]] §8). The orchestrator times out, assumes failure, retries → payee credited twice.

- **Standard fix**: every operation carries an idempotency key (the saga step's unique id), checked against a **`UNIQUE` constraint** before the effect is applied, in the **same transaction** as the effect → full pattern in [[10. Distributed Concurrency]] §7
- Without that "insert the key first" ordering, the check-then-act is itself a race between concurrent retries

---

### 8. Compensation Atomicity — Persisted Saga State

- The compensating transaction is just as vulnerable to failure as the forward one — what if *it* fails (DB down, network partition)?
- You need to **retry compensations until they succeed**, which means a durable record of "this compensation is owed" that survives a process crash
- This pushes every real implementation toward a **persisted saga-state table** — `saga_id`, `current_step`, `status`, `retry_count` — instead of holding progress in memory

---

### 9. Timeouts and the In-Doubt Problem ⭐

Each step usually calls an external service (a bank, or NPCI itself) with its own latency profile.

- The saga needs a coherent timeout policy: how long before declaring a step failed and triggering compensation, versus the chance it's just slow and will still land?
- ⚠️ Get this wrong in either direction: compensate **too early** → false failure while the real operation later succeeds (a duplicate-effect risk once it does land); wait **too long** → the whole saga hangs
- This is the exact same ambiguity as an in-doubt commit ([[Transactional]] §8) playing out at the service-call level instead of the JDBC level — you cannot locally distinguish "it failed" from "it succeeded and the ack was lost"

---

### 10. Observability Across Services

A saga that failed at step 4 of 7, three days ago, spread across five services' logs, has no single stack trace — the "transaction" is a sequence of independent events over time.

**What's needed:**
- A **persisted saga-state history** — not just current state, the full audit trail of transitions
- **Correlation IDs propagated in message headers** (a Kafka header carrying the trace/txn id) — the same MDC mechanism that breaks across thread pools breaks *worse* across service/process boundaries, because there's no shared `ThreadLocal` at all → full mechanics in [[3. Distributed Logging]], shipped implementation in [[5. Observability]] §3
- **Centralized distributed tracing** (Zipkin/Jaeger, or SigNoz if spans are properly propagated) tying the whole chain together

---

### 11. Testing, Reporting & Reconciliation — the Safety Net ⭐

- **Testing**: "did the debit happen" is trivial; "does the compensation chain correctly unwind a partial failure at step 4 of 7, under retries and concurrent sagas on the same account" is a combinatorial explosion most teams underinvest in — and find in production instead
- **Reporting**: each service owns its own DB, so no single query gives "the current true state of transaction X." Either query and reconcile across services live, or maintain a **CQRS-style read projection** updated as saga events flow through, purely for querying
- ⭐ **The pattern tying it together**: production sagas end up with a **reconciliation job** that periodically re-checks saga state against source-of-truth ledgers — because no amount of in-flight correctness logic eliminates every timing-window bug. This is exactly what NPCI does with UPI settlement/reconciliation files: the same underlying problem (distributed consistency without 2PC), solved with the same tool, at a different layer

---

**Must Know**: why 2PC/XA doesn't scale (locks across services, coordinator SPOF), local transactions + compensation as the alternative, choreography vs orchestration trade-offs, **sagas have no isolation** and the concrete stale-read anomaly, compensations are forward-recorded reversals not deletes, **idempotency is mandatory at every step** via a unique-constraint key in the same transaction as the effect, why persisted saga state (not in-memory) is required for crash recovery

# Detailed Explanation

---

## The Core Problem — Why Not 2PC

Consider a UPI transaction that needs to debit the payer's account (Payment service, own DB), credit the payee (Ledger service, own DB), update transaction status (Switch/Orchestrator service, own DB), and send a notification. Each of those lives behind its own database, possibly its own service entirely — there is no single `@Transactional` boundary that can wrap all four, because `@Transactional` atomicity stops at the edge of one connection.

Two-phase commit (XA transactions) technically solves the multi-database case: a coordinator asks every participant to *prepare*, then tells them all to *commit*. But it does so by holding locks across every participant for the duration of both round trips, and it makes the coordinator a single point of failure — if it dies between "prepare" and "commit," every participant sits **in doubt**, holding its locks, until the coordinator recovers. At UPI-scale volumes, that's not a viable trade: availability drops (every participant must be up simultaneously) and latency rises (two round trips plus forced log flushes, per participant, per transaction). The full disqualification table — blocking, availability, latency, lack of support (Kafka doesn't do XA at all) — is in [[11. Transaction Boundaries]] §10.

Saga's answer is to stop trying to make the whole operation atomic. Break it into a sequence of **local transactions**, each committing independently and immediately. If a later step fails, you don't roll back what already committed — you can't, it's already durable and possibly already visible to other readers. Instead you run **compensating transactions** that semantically undo the earlier steps by recording the opposite effect.

---

## The Mechanism — Local Transactions + Compensation

```text
Forward:      Debit Payer → Credit Payee → Update Status → Notify
                                   ✗ fails
Compensate:              ← Reverse Credit ← (nothing to undo before it)
```

Each arrow in the forward path is its own committed local transaction. When "Update Status" fails, the saga doesn't attempt a `ROLLBACK` — there is no single transaction to roll back, and even if there were, the credit to the payee has already committed and may already be visible in a report. Instead, it walks backward through the steps that *did* commit and issues a compensating action for each: here, reversing the credit. Whatever step failed and whatever came after it never happened at all, so there's nothing to compensate there.

This is the single conceptual shift the whole pattern rests on: **failure handling moves from "undo the transaction" to "record the opposite fact."** Everything else in this note is a consequence of taking that shift seriously.

---

## Choreography vs Orchestration

**Choreography** has no central coordinator. Each service completes its local transaction and publishes an event; the next service in the flow listens for that event and reacts by running its own local transaction and publishing its own event.

**Orchestration** puts a central coordinator — a saga orchestrator — in charge. It explicitly tells each service what to do next and tracks the overall state itself, rather than relying on services to know what event to listen for.

| | Choreography | Orchestration |
|---|---|---|
| Coupling | Loose — services only know events, not each other | Tighter — the orchestrator knows the whole flow |
| Complexity as steps grow | Gets hard to trace: "which service reacts to what" | Centralized and easier to visualize/debug |
| Single point of failure | None | The orchestrator itself needs to be reliable/HA |
| Good fit | Few services, simple flows | Complex flows with many steps/branches |

Most payment orchestration engines choose orchestration, and the reasoning generalizes: a flow like *try PSP-A → timeout → fallback to PSP-B → reconcile → notify* has enough branching and failure paths that a choreographed event-web becomes very hard to reason about — you'd need to trace through every service's event handlers to answer "what happens if PSP-A times out twice." A central orchestrator makes that branching explicit in one place.

In practice this is either an off-the-shelf framework (**Axon Framework**, **Eventuate Tram**) or a hand-rolled state machine — a `saga_state` table plus Kafka events for step transitions. The hand-rolled version is what most real UPI/PSP systems run, and the reason is in the next section: state has to be **persisted**, not held in the orchestrator's memory, so a crashed orchestrator process can resume exactly where it left off rather than losing track of an in-flight payment.

---

## No Isolation Between Sagas

This is the property that costs people the most in interviews and in production, because it's invisible until you go looking for it: **sagas have no "I" in ACID.**

Since each local transaction commits immediately and independently, its effects are visible to *any other transaction* the instant it commits — including other sagas still in flight. Concretely: Saga A debits ₹500 from an account and that step commits. Before Saga A's remaining steps run (and possibly before it decides to compensate because a later step failed), Saga B reads that same account's balance and makes a business decision based on the *already-debited* value. If Saga A later fails and compensates, putting the ₹500 back, Saga B already acted on state that turned out to be transient and, from a strict-isolation point of view, never should have been visible on its own.

None of the standard mitigations are perfect, which is itself worth saying out loud in an interview rather than presenting one as a full fix:

- **Semantic lock** — mark the resource `PENDING` or `LOCKED` for the saga's duration, and have other sagas either wait for it to clear or reject operations against it outright. This buys you something close to real isolation, at the cost of introducing a lock you now have to manage the lifetime of (what if the saga crashes while the resource is `PENDING`?).
- **Commutative updates** — design the operations themselves so that order doesn't matter. "Add −500" and "add +500" commute regardless of what interleaves between them, so even if Saga B reads mid-flight, the eventual final state is correct even if the *intermediate* read was momentarily surprising.
- **Pessimistic re-read** — instead of trusting a value read earlier in the saga, force a fresh read right before the step that actually depends on it being current.

The honest framing, and the one worth giving in an interview: Saga trades real isolation for availability, and every mitigation here narrows the exposure window rather than closing it.

---

## Compensations Are Forward Transactions, Not Rollbacks

"Undo" in the Saga sense does not mean deleting a row. By the time a compensation runs, the original effect may already be durable *and already visible to other reads or reports* — money has left an account, a report may have already been generated referencing it. Physically erasing that row would erase evidence that the operation was ever attempted, which is exactly what an audit trail must not do.

So the compensation for "debit ₹500" is "credit ₹500" — recorded as a brand-new ledger entry, not a correction to the old one. This matters concretely for NPCI/RBI-style systems: regulatory audit requires a full, append-only ledger history, where every attempted operation and every reversal is its own visible, timestamped fact. A compensation that silently undid the original entry would make it impossible to answer "what actually happened to this transaction, in order" — which is the entire point of a ledger.

---

## Not Everything Is Compensatable

Some actions have no possible reversal. An SMS or push notification that already reached the user's phone cannot be un-sent. A call to an external bank or NPCI API that already executed on their side, with no reversal endpoint exposed, has already had its real-world effect.

There are only two honest responses to this:

1. **Accept it and compensate downstream** — for a notification, that means sending a *follow-up* message ("this transaction was reversed") rather than pretending the first one can be recalled.
2. **Sequence the step so it can't be reached until failure is vanishingly unlikely** — put irreversible actions **last** in the saga, after every step that could plausibly still fail. "Send confirmation SMS" as step 2 of 7 guarantees you'll eventually need option 1 anyway; as step 7 of 7 it almost never triggers it.

---

## Idempotency — Required at Every Single Step

Every step in a saga can be retried — an orchestrator timing out and re-invoking a step, a crash-and-resume cycle picking up mid-saga, or Kafka's at-least-once delivery redelivering an event the consumer already processed. If any forward step or any compensation isn't idempotent, a retry re-applies its effect, not just re-attempts it.

The example that makes this concrete and dangerous: the orchestrator calls "credit payee ₹500." The database write actually succeeds, but the response never reaches the orchestrator — this is the identical in-doubt scenario a plain `@Transactional` commit can hit at the JDBC level ([[Transactional]] §8), just occurring one layer up, over a service call instead of a database connection. The orchestrator, seeing a timeout, has no way to know the credit landed. If it assumes failure and retries the same "credit ₹500" call, the payee is credited twice — and nothing about the saga's control flow caught it, because from the orchestrator's point of view it just retried a failed step like any other.

The fix is structural, not a smarter retry policy: every operation carries an **idempotency key** — typically the saga step's unique id — and the receiving service checks whether it has already processed that key *before* applying the effect. Mechanically that's a `UNIQUE` constraint on the key, with the check-and-insert happening in the **same transaction** as the effect itself, so a concurrent duplicate can't slip through between the check and the write. The full pattern, including why the insert has to come first and how to return the original response on a duplicate, is in [[10. Distributed Concurrency]] §7.

---

## Compensation Atomicity — Persisted Saga State

The compensating transaction is not somehow exempt from the failure modes the forward transaction has — a compensation can fail too, for exactly the same reasons: the database is down, the network partitions mid-call. If a compensation fails, you can't just give up; the whole point of the saga was to leave the system in a consistent state, and an unapplied compensation leaves it inconsistent indefinitely.

That means compensations must be **retried until they succeed**, which in turn means the system needs a durable record that a given compensation is still owed, one that survives the orchestrator process itself crashing mid-retry. In practice this is what pushes every serious saga implementation toward a **persisted saga-state table** — something like `saga_id`, `current_step`, `status`, `retry_count` — rather than tracking progress as in-memory orchestrator state. An in-memory saga dies with its process; a persisted one can be picked back up by any orchestrator instance after a restart, which is exactly the property a payment system can't do without.

---

## Timeouts and the In-Doubt Problem

Every step in a saga typically means calling an external system — a bank's API, or NPCI itself — each with its own, often variable, latency profile. The saga has to decide, for every step, how long to wait before declaring it failed and triggering compensation.

Get that timeout too short, and you compensate for a step that was simply slow and would have succeeded a moment later — creating a **false failure**, and worse, one that may itself later collide with the real (delayed) success once it lands, since compensating for something that hadn't actually failed can produce a duplicate-effect situation of its own. Get it too long, and a genuinely stuck step hangs the entire saga indefinitely, blocking every step downstream of it.

There is no timeout value that makes this ambiguity go away — it's the same structural problem as an in-doubt commit ([[Transactional]] §8), just occurring at the granularity of a whole service call instead of a single database round trip. You cannot locally distinguish "the step failed" from "the step succeeded and I never heard back." The only real resolution is the same one used there: a status-check call to the downstream service before deciding to compensate, rather than trusting the absence of a response as proof of failure.

---

## Observability Across Services

A saga that failed at step 4 of 7, three days ago, with its seven steps spread across five services' independent log streams, has no single stack trace to look at. The "transaction," in the traditional debugging sense, doesn't exist as one artifact — it's a sequence of independent events that happened over time, in different processes.

Reconstructing it after the fact needs three things working together. First, a **persisted saga-state history** — not just the current status, but every transition the saga went through, so you can see the sequence, not just the endpoint. Second, **correlation IDs riding in message headers** across every service call — the same MDC mechanism that already needs explicit propagation across a single service's thread-pool boundary breaks in exactly the same way, only more completely, across a service or process boundary, because there's no `ThreadLocal` to even attempt to share. A Kafka header carrying the trace or transaction id, read into MDC by each consumer before its listener runs, is what lets every service's log lines for one logical saga carry the same id — the full producer/consumer wiring for this is in [[5. Observability]] §3. Third, **centralized distributed tracing** (Zipkin, Jaeger, or SigNoz) that ties the spans from each service call into one visualizable chain, provided every hop actually propagates the trace context instead of starting a fresh span with no parent.

Without all three, a production saga failure becomes an exercise in manually grepping five services' logs for a timestamp range and hoping the pieces line up.

---

## Testing, Reporting & Reconciliation — the Safety Net

Unit-testing "did the debit happen" is trivial. Testing "does the compensation chain correctly unwind a partial failure at step 4 of 7, while a concurrent saga is touching the same account, under a retry" is a combinatorial explosion of failure-injection scenarios — which step fails, at what point in its own lifecycle, with what else running concurrently. Most teams underinvest here, not out of negligence but because the test matrix genuinely doesn't fit into normal unit-test thinking, and these bugs surface in production instead.

Reporting has a related structural problem: because each service owns its own database, there is no single query that answers "what is the current true state of transaction X?" You either query every service involved and reconcile the answer yourself, or you build and maintain a **CQRS-style read projection** — a denormalized view updated as saga events flow through, that exists purely to answer that question quickly. Building that projection and keeping it in sync with the actual saga events is its own subsystem, not a side effect you get for free.

The pattern that ties testing gaps, compensation-atomicity risk, the timeout/in-doubt ambiguity, and cross-service reporting together in practice is the same one: production saga implementations end up building a **reconciliation job** that periodically re-checks saga states against source-of-truth ledgers, independent of whatever the in-flight saga logic believes happened. This exists precisely because no amount of in-flight correctness logic closes every timing-window bug — there will always be a gap between "the saga's own bookkeeping says X" and "the ledgers actually say Y," caused by exactly the ambiguities in §9 and the concurrency in §4. This is not a coincidence with what NPCI itself does for UPI settlement and reconciliation files — it's the same underlying problem, distributed consistency without a global commit, solved with the same tool, at a different layer of the stack.

## ❓ Interview Questions

### Q1. Why can't you just use a distributed transaction (2PC/XA) across services instead of Saga?

2PC holds locks across every participant for the duration of both round trips and makes the coordinator a single point of failure — if it dies between prepare and commit, every participant is stuck in doubt, holding locks, until it recovers. That kills both availability and throughput at scale, and several common infra pieces (Kafka included) don't support XA at all.

### Q2. What replaces atomicity in a Saga?

A sequence of independently committing **local transactions**. If a later step fails, you don't roll back — you run **compensating transactions** that record the opposite effect for whatever already committed.

### Q3. Choreography or orchestration — which do you pick for a payment flow with retries and fallbacks?

Orchestration. A flow with real branching (try PSP-A, fall back to PSP-B on timeout, reconcile, notify) becomes very hard to reason about as a web of choreographed event handlers; a central orchestrator makes the branching explicit and debuggable, at the cost of needing that orchestrator itself to be highly available.

### Q4. Do sagas provide isolation?

No — that's the property people miss most. Each local transaction commits immediately and is visible to any other reader right away, including other in-flight sagas. A second saga can read and act on state a first saga later compensates away. Mitigations (semantic locks, commutative updates, forced re-reads) narrow this window; none close it.

### Q5. If a saga needs to "undo" a debit, what actually happens?

A new compensating transaction records a credit — the original debit entry is never deleted or edited. This preserves the audit trail: every attempted operation and every reversal stays visible as its own event, which is mandatory in ledger-style, regulated systems.

### Q6. What do you do about a step that genuinely can't be undone, like a sent SMS?

Either accept it and compensate downstream with a follow-up message ("this transaction was reversed"), or design the saga so irreversible steps run last, after the point where failure is vanishingly unlikely.

### Q7. Why must every saga step be idempotent?

Every step can be retried — orchestrator timeouts, crash-and-resume, at-least-once Kafka delivery. Without idempotency, a retry re-applies the effect rather than re-attempting it: the classic case is a credit that actually succeeded but whose response was lost, followed by a retry that double-credits.

### Q8. How is idempotency actually implemented?

A caller-supplied idempotency key, checked and inserted via a `UNIQUE` constraint in the **same transaction** as the effect. A duplicate call fails the insert instead of re-applying the effect, and the service returns the originally stored response.

### Q9. Why do real saga implementations persist their state instead of keeping it in memory?

Because compensations themselves can fail and must be retried until they succeed, which requires a durable record of "this compensation is still owed" that survives the orchestrator process crashing. An in-memory saga loses that record on restart; a persisted `saga_state` table lets any orchestrator instance resume exactly where it left off.

### Q10. A saga step times out — do you compensate immediately?

Not blindly. A timeout is ambiguous: the step may have failed, or it may have succeeded with the response lost — the same in-doubt problem a database commit can hit. Compensating immediately risks compensating a step that actually succeeded. The safer approach is a status check against the downstream system before deciding, and ultimately, reconciliation as a backstop for whatever slips through.

### Q11. Why do production systems still run a reconciliation job if the saga logic is correct?

Because no in-flight correctness logic closes every timing window — the isolation gaps, in-doubt timeouts, and retry races described above are structural, not bugs to be coded away. Reconciliation periodically checks saga state against source-of-truth ledgers independently, catching whatever the saga's own bookkeeping got wrong. NPCI's UPI settlement/reconciliation files solve the identical problem at a different layer.

> - Saga = **local transactions + compensation**, used because 2PC doesn't scale (cross-service locks, coordinator SPOF).
> - **Choreography** (event-driven, loosely coupled) vs **orchestration** (central coordinator, better for branching flows — usually the right call for payments).
> - ⭐ **No isolation between sagas** — intermediate, possibly-doomed state is visible to other readers. Mitigate with semantic locks, commutative updates, or forced re-reads; none fully close the gap.
> - **Compensation = a new opposite entry, never a delete** — the audit trail must show both the attempt and the reversal.
> - Some steps **aren't compensatable** (a sent SMS, an executed external call) — sequence them **last**.
> - ⭐ **Every step must be idempotent** — retries are guaranteed (timeouts, crash-resume, at-least-once delivery). Implement via a `UNIQUE`-constrained idempotency key inserted in the same transaction as the effect.
> - Compensations can fail too — need **persisted saga state** (`saga_id`, `current_step`, `status`) to survive a crash and retry until they succeed.
> - A step timeout is an **in-doubt problem**, not a clean failure signal — compensating too eagerly risks undoing a step that actually succeeded.
> - Observability needs correlation IDs in **message headers** (MDC alone doesn't cross process boundaries) plus distributed tracing.
