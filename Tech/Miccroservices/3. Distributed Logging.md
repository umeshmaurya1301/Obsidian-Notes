**MDC** (Mapped Diagnostic Context) stamps every log line on the current thread with context — a transaction ID, a user ID — without threading it through every method signature. **Distributed tracing** is the same idea solved one level up, once a request stops living on one thread in one process and starts crossing services.

> [!info] Where this fits
> - **`ThreadLocal` itself — the mechanism MDC is built on** → [[2. Java Thread Basics]] §6
> - **The identical binding pattern for a DB connection instead of a log context** → [[Transactional]] §3
> - **Why `@Async`/executor work loses this context** (briefly touched, not derived) → [[4. Executors and Thread Pools]], [[7. Async Programming]]
> - **The concrete, shipped implementation of everything in §1–§5** — real interceptor code, real MDC keys, real config → [[5. Observability]] (Kafka)
> - **The saga-observability problem this solves at the multi-service level** → [[1. Saga Design Pattern]] §10
>
> This note derives the mechanism and the failure modes; [[5. Observability]] shows the production library that already implements it for Kafka.

> [!info] The through-line of this note
> One `ThreadLocal`, then the same problem at every larger scale.
>
> 1. MDC is a **`ThreadLocal<Map<String,String>>`** (§2) — the exact same primitive behind `TransactionSynchronizationManager` ([[Transactional]] §3). Anything true of one is true of the other.
> 2. Because it's thread-local, it needs to be **set at the entry point and cleared in a `finally`** (§3) — miss the clear and a pooled thread leaks stale context into the next unrelated request.
> 3. Every thread hop loses it: a thread-pool handoff (§4) or a message crossing to a different JVM entirely (§5). Same root cause, two different fixes — a `TaskDecorator` for the first, an explicit header for the second.
> 4. Once the identifier has to travel across services anyway, formalize it: **distributed tracing** (§6–§7) is "carry an ID across a network boundary" done properly, with a parent-child span tree instead of a flat string.
> 5. The payoff (§8–§11) is that tracing and MDC aren't separate systems — the tracer **injects into MDC automatically**, so your existing log lines and a visual waterfall in SigNoz are two views of the same `trace_id`.
>
> One line to anchor everything: **every gap in this note is a `ThreadLocal` (or its network equivalent) not being where the next hop expected it to be.**

```java

```

- In a high-throughput system, thousands of transactions interleave in the log stream simultaneously

### 2. How MDC Works — `ThreadLocal<Map<String,String>>` ⭐

```java
MDC.put("txnId", "UPI2024091912345");
MDC.put("userId", "user-8821");

log.info("Processing payment");   // txnId=UPI2024091912345 userId=user-8821 Processing payment
log.info("Debiting account");     // same context, automatically included

MDC.clear();
```

- Same underlying primitive as `TransactionSynchronizationManager` for `@Transactional` → [[Transactional]] §3. Each thread gets its own isolated map; nothing here is special to logging
- The pattern in `logback.xml` reads it at format time:

```xml
<pattern>%d{HH:mm:ss} [%thread] %-5level %X{txnId} %X{userId} - %msg%n</pattern>
```

- Logback/SLF4J reads the **current thread's** MDC map at the moment each line is written — you never pass `txnId` into the log call itself

---

### 3. Setting MDC at the Entry Point

```java
public class TxnIdFilter extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String txnId = req.getHeader("X-Txn-Id");
        MDC.put("txnId", txnId != null ? txnId : UUID.randomUUID().toString());
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear();     // non-negotiable
        }
    }
}
```

- ⚠️ **The `finally { MDC.clear(); }` is not optional.** Servlet containers **reuse threads** across requests; skip the clear and the next unrelated request on that pooled thread inherits the previous request's `txnId` — logs that quietly lie about which transaction they belong to

---

### 4. The Thread-Pool Gotcha — `TaskDecorator` Fix ⭐

MDC is `ThreadLocal`, so it does **not** cross a thread-pool handoff — the exact limitation `@Transactional`'s connection binding has → [[Transactional]] §6.

```java
public class MdcTaskDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable runnable) {
        Map<String, String> contextMap = MDC.getCopyOfContextMap();   // snapshot on the CALLING thread
        return () -> {
            try {
                if (contextMap != null) MDC.setContextMap(contextMap);   // apply on the pool thread
                runnable.run();
            } finally {
                MDC.clear();   // don't leak into the next task this pooled thread picks up
            }
        };
    }
}
```

```java
@Bean(name = "taskExecutor")
public Executor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setTaskDecorator(new MdcTaskDecorator());
    executor.initialize();
    return executor;
}
```

- Full treatment of *why* `@Async` loses context in the first place → [[4. Executors and Thread Pools]], [[7. Async Programming]]

### 5. The Kafka Gotcha — a Different JVM Entirely

- MDC obviously can't survive a message going onto a topic and being picked up by a **different process**, let alone a different machine — there's no shared thread, no shared memory
- Fix: carry the correlation ID **explicitly in the message itself** — a Kafka header (`X-Txn-Id`), never in the payload — and have the consumer do `MDC.put(...)` at the start of processing, `MDC.clear()` at the end
- ⭐ **The identifier must travel as data on the wire** at every hop (HTTP header, Kafka header, gRPC metadata) — MDC only ever solves "show up in every log line, on this one thread, in this one process." A real shipped implementation of exactly this → [[5. Observability]] (Kafka) §2–§4

### 6. Distributed Tracing — Trace, Span, Context Propagation ⭐

- **Trace** — one end-to-end logical operation (one UPI transaction, initiation to settlement), identified by a single **trace ID** constant across every service it touches
- **Span** — one unit of work inside that trace ("validate request," "debit call to Issuer," "Kafka publish"). Each has its own **span ID**, a **parent span ID**, and the shared trace ID — spans form a tree, which is what lets a tool reconstruct the full call graph, not just a flat log line
- **Context propagation** — carrying `(trace_id, span_id)` across a network call, since there's no shared memory to rely on. Same limitation as MDC, one layer up: the network instead of the thread

# Detailed Explanation

---

## The Problem MDC Solves

In a high-throughput service, log lines from many concurrent transactions interleave in one stream:

```java
log.info("Processing payment");
log.info("Debiting account");
log.error("Debit failed");
```

None of these lines say *which* payment or transaction they belong to. With thousands of interleaved transactions, "what happened to txn `UPI2024...`" becomes a manual, error-prone grep across a firehose — assuming every relevant log line even mentions the ID at all, which requires every developer to remember to pass it in explicitly, everywhere, forever. MDC exists to make that automatic instead of a discipline problem.

---

## How MDC Works

MDC is backed by a `ThreadLocal<Map<String, String>>` — the same underlying primitive as `TransactionSynchronizationManager`, which binds a JDBC connection to the current thread for `@Transactional` ([[Transactional]] §3). Recognizing that the two are the same mechanism, applied to different data, is worth more than memorizing either one separately: every property true of one is true of the other, including every failure mode below.

```java
MDC.put("txnId", "UPI2024091912345");
MDC.put("userId", "user-8821");

log.info("Processing payment");   // txnId=UPI2024091912345 userId=user-8821 Processing payment
log.info("Debiting account");     // same context, automatically included

MDC.clear();
```

The logging pattern reads the map at format time, not at call time:

```xml
<pattern>%d{HH:mm:ss} [%thread] %-5level %X{txnId} %X{userId} - %msg%n</pattern>
```

`%X{key}` tells Logback/SLF4J to look up `key` in the *current thread's* MDC map at the moment each line is actually written to the appender. Your business code never passes `txnId` into `log.info(...)` — the association is entirely a side effect of what's sitting in that thread's map when the line fires.

---

## Setting MDC at the Entry Point

The natural place to populate MDC is the first point a request enters your service — a servlet filter:

```java
public class TxnIdFilter extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String txnId = req.getHeader("X-Txn-Id");
        MDC.put("txnId", txnId != null ? txnId : UUID.randomUUID().toString());
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear();
        }
    }
}
```

The `finally { MDC.clear(); }` is not defensive boilerplate — it's the entire correctness of the mechanism. Servlet containers run requests on a **pooled** thread; once this request finishes, that same thread goes back into the pool and will shortly handle a completely unrelated request. If the clear is skipped, the next request's log lines will carry the *previous* request's `txnId` — not an exception, not a crash, just log lines that quietly attribute the wrong transaction to the wrong lines. This is a nastier bug class than a missing ID, because a missing ID is obviously wrong, while a wrong-but-present ID looks correct until someone tries to actually use it to debug an incident.

---

## The Thread-Pool Gotcha

Because MDC's map lives on the `ThreadLocal` of whichever thread called `MDC.put`, it simply isn't there on any other thread — including a thread pulled from a pool to run `@Async` work, a manually submitted `Runnable`, or a `CompletableFuture` stage. This is the identical shape of problem as a `@Transactional` connection binding not following work onto a different thread ([[Transactional]] §6) — same `ThreadLocal` primitive, same "the binding lives on the thread, not the logical operation" root cause.

The fix is to capture the map on the calling thread and reapply it on the worker thread, wrapped so cleanup still happens:

```java
public class MdcTaskDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable runnable) {
        Map<String, String> contextMap = MDC.getCopyOfContextMap();
        return () -> {
            try {
                if (contextMap != null) MDC.setContextMap(contextMap);
                runnable.run();
            } finally {
                MDC.clear();
            }
        };
    }
}
```

```java
@Bean(name = "taskExecutor")
public Executor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setTaskDecorator(new MdcTaskDecorator());
    executor.initialize();
    return executor;
}
```

Note the `finally { MDC.clear(); }` inside the decorated task, not just the original filter — the worker thread is *also* pooled, so without this second clear, the next unrelated task picked up by that same pool thread inherits the first task's context, the exact same leak as §3 one layer further in. The deeper "why does `@Async` lose context at all" question — the thread-pool mechanics themselves — is covered in [[4. Executors and Thread Pools]] and [[7. Async Programming]]; this note only needs the fix.

---

## The Kafka Gotcha

A thread-pool handoff at least stays inside one JVM, where a snapshot-and-restore trick works. A Kafka message consumed by a different service entirely shares no process, no memory, nothing a `ThreadLocal` could possibly reach into. There is no snapshot to take on the producing side that a `ThreadLocal` restore could apply on the consuming side — the two sides aren't even in the same runtime.

The fix has to move the identifier onto the wire itself: carry it as a Kafka **header** (never the payload — you don't want tracing concerns coupled to your business message schema), and have the consumer explicitly read it back into MDC before its listener runs, then clear it when done. This generalizes past Kafka specifically: **the identifier has to travel as actual data at every hop** — an HTTP header, a Kafka header, gRPC metadata — because MDC's `ThreadLocal` only ever solves the single-thread, single-process version of the problem. A concrete, already-shipped version of exactly this — producer interceptor stamping `X-Correlation-Id`, consumer interceptor reading it back into MDC before the listener, clearing it in `finally` — is documented in [[5. Observability]] (Kafka) §2–§4, including the actual MDC keys used (`correlationId`, `traceId`, `kafka.topic`, `kafka.key`).

---

## Distributed Tracing — Trace, Span, Context Propagation

Once the identifier has to travel across a network boundary regardless, it's worth formalizing rather than reinventing per-protocol. Distributed tracing gives that formalization three concepts:

A **trace** represents one end-to-end logical operation — a UPI transaction from initiation through settlement — identified by a single trace ID that stays constant across every service it touches, no matter how many hops that takes.

A **span** represents one unit of work inside that trace: "validate request" in the Switch, "debit call" to the Issuer bank, "Kafka publish." Each span carries its own span ID, a reference to its parent span's ID, and the shared trace ID. Because every span (except the root) points at a parent, the full set of spans for one trace forms a tree — which is what lets a tracing UI reconstruct the actual call graph, not just a flat list of log lines in arrival order.

**Context propagation** is the mechanism that carries `(trace_id, span_id)` across a network call. There's no shared memory or thread to lean on here, which is exactly MDC's limitation from §5, just one layer up — the network instead of the thread.

---

## W3C Trace Context — the `traceparent` Header

Most modern tools, SigNoz included (it's OpenTelemetry-native), use the standardized W3C format for HTTP:

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ^^ ^------------trace_id-----------^ ^----span_id----^ ^^
          version                                                 flags
```

For gRPC, the identical context rides in **metadata**, gRPC's equivalent of headers. Kafka has no equivalent built-in standard the way HTTP does, but the convention — and what OpenTelemetry's own Kafka instrumentation does automatically — is to inject `traceparent` as a **message header**, kept separate from the payload for the same reason the correlation ID is kept separate in §5: tracing plumbing shouldn't leak into your business message schema.

---

## How Tracing and MDC Work Together

Tracing and MDC are not two competing systems solving the same problem — they compose. The tracing library (the OpenTelemetry Java agent, or manual SDK calls) does three things automatically at each service boundary:

1. Generates a new trace context if none exists yet, or extracts one from an incoming `traceparent` header/Kafka header if it does.
2. **Injects `trace_id` and `span_id` into MDC** for the duration of that request or message's processing — so a log pattern that already prints `%X{txnId}` can add `%X{trace_id}` and every existing log statement in your business logic gets correlated for free, with no code change required anywhere in that business logic.
3. Exports the span data — start/end time, tags, status — separately to the collector, which is what builds the visual waterfall/flame graph in a tool like SigNoz, distinct from the plain-text logs.

The practical result is two correlated views of the same underlying event: grep-able, human-readable logs with `trace_id=...` on every line, and a structured span timeline showing per-hop latency and error tagging — both keyed by the identical `trace_id`, so you can jump from "I see this error in the logs" straight to "here's the full distributed call graph that produced it."

## Getting Data Out — Auto vs Manual Instrumentation

**Auto-instrumentation** is the default path and needs no code changes: attach the OpenTelemetry Java agent as a JVM flag.

```bash
java -javaagent:opentelemetry-javaagent.jar \
     -Dotel.service.name=upi-switch \
     -Dotel.exporter.otlp.endpoint=http://signoz-collector:4317 \
     -jar switch.jar
```

The agent bytecode-instruments common libraries — Spring MVC, the Kafka client, JDBC drivers, gRPC, RestTemplate/WebClient — at class-load time, automatically creating spans for incoming HTTP requests, outgoing HTTP calls, Kafka produce/consume, and DB queries. It's worth noticing the family resemblance to Spring's own AOP proxies: both are "intercept the call transparently" strategies, just operating at different layers — bytecode manipulation at class-load time here, versus a generated proxy object at bean-creation time there.

**Manual instrumentation** fills the gap for a custom business-logic span the auto-instrumentation has no way to know is meaningful:

```java
Span span = tracer.spanBuilder("validate-npci-checksum").startSpan();
try (Scope scope = span.makeCurrent()) {
    // nested spans created here are automatically parented to this one
} catch (Exception e) {
    span.recordException(e);
    span.setStatus(StatusCode.ERROR);
} finally {
    span.end();
}
```

`span.makeCurrent()` is what lets any spans created inside the `try` block automatically parent themselves to this one, building the tree from §6 without you manually threading a parent reference through every nested call.

## The OpenTelemetry Pipeline

The architecture SigNoz (and most modern tracing stacks) are built on has six distinct pieces:

**1. Instrumentation libraries** — the code, or auto-attached bytecode agent, that actually creates spans for a specific integration point (Spring MVC, Kafka client, JDBC, gRPC, WebClient). Each knows how to extract or inject the `traceparent` header for its own protocol.

**2. SDK** — the in-process library managing spans in memory: starting and ending them, building the parent-child tree, attaching attributes (`http.status_code`, `db.statement`), batching before handoff. This is deliberately separate from the **API** your code calls (`tracer.spanBuilder(...)`), so a library can be instrumented against the API without depending on a specific SDK implementation underneath it.

**3. Exporter** — converts the SDK's internal span representation into a wire format and ships it. The default today is **OTLP** (OpenTelemetry Protocol) over gRPC or HTTP — the `otel.exporter.otlp.endpoint` flag from the launch command above.

**4. Collector** — a standalone process, not part of your application, sitting between your services and storage. Your application only ever talks to the Collector; it doesn't need to know or care about storage details, retries, or fan-out. Internally the Collector is its own three-stage pipeline:

- **Receiver** — accepts incoming telemetry, often on multiple protocols at once (OTLP, Jaeger, Zipkin format), which is what lets you migrate instrumentation gradually without a hard cutover.
- **Processor** — transforms data in flight. The **batch processor** groups spans before sending onward, cutting network overhead versus one request per span. The **sampling processor** decides which traces to actually keep — at high transaction volume, exporting every span for every transaction is expensive and often unnecessary (§11 covers the head-based vs tail-based choice here).
- **Exporter (collector-side)** — sends the processed batch on to one or more backends, potentially two at once if you're mid-migration between storage systems.

At higher scale, the Collector is commonly deployed in two tiers: a lightweight **agent** collector per host/pod (close to the app, handles local buffering, low added latency) feeding into a central **gateway** collector that does the heavier processing — tail-sampling in particular — before exporting to storage.

**5. Storage backend** — where processed spans land, structured for fast time-range and trace-ID lookups. SigNoz specifically uses **ClickHouse**, a columnar OLAP database, which is a deliberate fit: trace data is high-volume and append-only, and queried far more often by aggregation ("p99 latency for `debit-account` spans over the last hour") than by single-row lookup — exactly the access pattern columnar storage is built for.

**6. Query layer / UI** — what you actually interact with: takes a `trace_id` or a service/latency filter, queries the backend, and reconstructs the parent-child span tree into the flame-graph/waterfall view. Alerting rules ("page if p99 latency for the Issuer bank call exceeds 2s," "alert if error rate on the debit span exceeds 1%") live here too, as continuous queries against the same span data evaluated on a schedule — not a separate subsystem.

SigNoz bundles the Collector, ClickHouse, and the query/UI layer into one deployable stack, rather than requiring you to wire up a separate Jaeger deployment, a separate Collector, and a separate storage system by hand — the way tracing setups commonly looked before OpenTelemetry standardized the pipeline. The only pieces that stay inside *your* application are instrumentation, the SDK, and the exporter; everything from the Collector onward is shared infrastructure every service in a system points at once.

---

## Sampling — Head-Based vs Tail-Based

Exporting 100% of spans for every transaction at real production volume is expensive in storage and ingestion cost, and often unnecessary — most transactions are unremarkable. Sampling controls what fraction actually gets kept, and there are two fundamentally different ways to decide:

**Head-based sampling** decides at the very start of a trace, essentially by a random roll, whether to keep it at all. It's cheap — the decision costs nothing and needs no buffering — but it might discard exactly the rare, genuinely interesting trace you'd have wanted, since the decision is made before anything interesting has had a chance to happen.

**Tail-based sampling** waits: the collector buffers the entire trace and only decides whether to keep it after seeing how it turned out — was it slow, did it error. This is far more useful precisely because it lets you guarantee you capture every trace that actually needed investigating, at the cost of the collector needing enough memory to buffer complete traces before deciding.

For anything payments-adjacent, tail-based sampling at the gateway collector is usually worth that memory cost. The traces you actually need — the ones that timed out, that errored, that might be the in-doubt-transaction scenario from [[Transactional]] §8 — are exactly the ones a random head-based sample is most likely to miss, since they're rare by definition. Guaranteeing you keep 100% of error/high-latency traces while sampling down the unremarkable majority gets you both the cost control and the debugging guarantee.

## ❓ Interview Questions

### Q1. What data structure backs MDC?

A `ThreadLocal<Map<String, String>>` — the same primitive Spring uses in `TransactionSynchronizationManager` to bind a JDBC connection to a thread for `@Transactional`.

### Q2. Why must you call `MDC.clear()` in a `finally` block?

Servlet containers and thread pools reuse threads across requests/tasks. Without clearing, the next unrelated request or task handled by that same pooled thread inherits the previous one's MDC values — logs that silently attribute the wrong context, not an error you'd notice.

### Q3. Does MDC automatically propagate to an `@Async` method or a submitted task?

No. MDC is thread-local, and the worker thread from the pool is a different thread than the one that set it — same limitation as `@Transactional`'s connection binding. Fix it with a `TaskDecorator` that captures `MDC.getCopyOfContextMap()` before submission and applies it (then clears it) inside the task.

### Q4. Does MDC survive a message crossing to a consumer in a different service via Kafka?

No — different JVM, different process, no shared thread or memory at all. The correlation ID has to be carried explicitly as a Kafka message header, and the consumer must read it back into MDC before its listener runs.

### Q5. What's the difference between a trace and a span?

A trace is one end-to-end logical operation, identified by one trace ID constant across every service it touches. A span is one unit of work within that trace, with its own span ID and a reference to its parent span ID — the set of spans for a trace forms a tree, reconstructing the actual call graph.

### Q6. How does trace context actually cross an HTTP call?

Via the standardized W3C `traceparent` header, carrying a version, the trace ID, the parent span ID, and flags. gRPC carries the same context in metadata; Kafka carries it as a message header by convention.

### Q7. How do distributed tracing and MDC-based logging relate?

They compose. The tracing library automatically injects `trace_id`/`span_id` into MDC at each service boundary, so existing log statements get correlated with zero code changes, while also exporting the same trace data as structured spans for a visual waterfall view — two views of one `trace_id`.

### Q8. What does the OpenTelemetry Collector do, and why isn't it just built into each service?

It's a standalone process that receives telemetry from every service (via a Receiver), batches and samples it (Processor), and exports it to storage (Exporter). Keeping it out of the application means services don't need to know about storage details, retries, or fan-out — they just send data and move on.

### Q9. Why does SigNoz use ClickHouse for span storage?

Trace data is high-volume, append-only, and queried mostly by aggregation (p99 latency over a time window) rather than single-row lookup — the access pattern a columnar OLAP store like ClickHouse is optimized for.

### Q10. Head-based vs tail-based sampling — which would you pick for a payments pipeline, and why?

Tail-based, despite its higher collector memory cost, because it decides after seeing whether a trace was slow or errored — letting you guarantee you keep every problematic trace instead of risking a random head-based sample missing the one transaction that actually needed investigating.

> [!tip] ⚡ Quick Recall
> - MDC = `ThreadLocal<Map<String,String>>` — same primitive as `TransactionSynchronizationManager`. Set at the entry point, **always clear in `finally`**.
> - **Thread-pool hop** loses MDC → fix with a `TaskDecorator` that snapshots/restores the context map.
> - **Process/service hop** (Kafka, HTTP) loses MDC entirely → the ID must ride as an explicit header, re-populated into MDC by the receiver.
> - **Trace** = one logical operation, one trace ID. **Span** = one unit of work, its own span ID + parent span ID — spans form a tree.
> - **`traceparent`** (W3C) is the standard HTTP propagation header; gRPC uses metadata; Kafka uses a convention header.
> - The tracer **auto-injects `trace_id`/`span_id` into MDC** — logs and the visual trace waterfall are two views of the same ID.
> - OTel pipeline: **instrumentation → SDK → exporter (OTLP) → Collector (receive/process/export) → storage (ClickHouse in SigNoz) → query/UI**.
> - **Auto-instrumentation** (`-javaagent`) needs zero code changes for common libraries; **manual spans** cover custom business logic.
> - **Tail-based sampling** buffers a full trace before deciding to keep it — worth the memory cost when you can't afford to randomly miss an error/in-doubt trace.
