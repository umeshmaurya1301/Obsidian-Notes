# Types of Design Patterns

---

## Short Notes

---

### 1. What Is a Design Pattern (And What It Isn't)

- A **named, reusable solution** to a recurring design problem — not a finished piece of code, a template for structuring classes and their collaboration
- Comes from the **Gang of Four (GoF)** book, *Design Patterns: Elements of Reusable Object-Oriented Software* (1994) — 23 original patterns
- A pattern is **language-agnostic shape**, not a library you import — you re-implement it each time in the context you're in
- Not the same as an **algorithm** (a pattern is about object structure/collaboration, not a computational procedure) or a **framework** (a framework is a concrete reusable implementation; a pattern is just the blueprint)
- Interviewers care whether you can **recognize the shape in a requirement** and justify the trade-off — not recite the GoF definition

---

### 2. The GoF Classification

| Category | Answers | Count (GoF) |
| --- | --- | --- |
| **Creational** | How is an object *created*? | 5 |
| **Structural** | How are objects/classes *composed* into larger structures? | 7 |
| **Behavioral** | How do objects *communicate and distribute responsibility*? | 11 |

- Creational patterns hide `new` and construction complexity behind an abstraction
- Structural patterns focus on **composition** — building bigger things from smaller ones without tangling their internals
- Behavioral patterns focus on **communication** — who talks to whom, and who owns an algorithm
- Almost every LLD interview question is really "which 2–3 patterns compose to solve this"

---

### 3. Creational Patterns

- **Singleton**: exactly one instance, global access point — `ConnectionPool`, `ConfigManager`
- **Factory Method**: subclass decides which concrete class to instantiate — one creation method, overridden per type
- **Abstract Factory**: a **factory of factories** — creates families of related objects without naming concrete classes
- **Builder**: constructs a complex object **step by step**, separating construction from representation — kills telescoping constructors
- **Prototype**: creates new objects by **cloning** an existing instance instead of `new` + re-initializing

---

### 4. Structural Patterns

- **Adapter**: converts one interface into another the client expects — wraps an incompatible legacy/third-party API
- **Decorator**: attaches new behaviour to an object **at runtime** by wrapping it, without touching its class
- **Proxy**: a stand-in that controls access to the real object — caching, lazy-init, access control, remote calls
- **Facade**: one simple interface in front of a **complicated subsystem** of many classes
- **Composite**: treats a group of objects and a single object **uniformly** via a shared interface — tree structures
- **Bridge**: splits an **abstraction** from its **implementation** so both can vary independently
- **Flyweight**: shares immutable state across many objects to cut memory — fine-grained object reuse

---

### 5. Behavioral Patterns

- **Strategy**: interchangeable algorithms behind one interface, picked at runtime — see [[12. SOLID And Design Principles]] for the `PaymentStrategy` example
- **Observer**: one-to-many — subscribers get notified automatically when subject state changes
- **Command**: wraps a request as an object — enables queuing, logging, undo/retry
- **Template Method**: base class fixes the **algorithm's skeleton**, subclasses fill in specific steps
- **Chain of Responsibility**: a request passes along a chain of handlers until one handles it
- **State**: an object changes its behaviour when its **internal state** changes — looks like it changed class
- **Iterator**: sequential access to a collection's elements without exposing its internal structure
- **Mediator**: centralizes chaotic many-to-many object communication into one coordinator
- **Memento**: capture and restore an object's internal state — undo functionality
- **Visitor**: adds a new operation to a class hierarchy without modifying the classes
- **Interpreter**: rarely asked in interviews — defines a grammar and an evaluator for it

---

### 6. The Patterns That Actually Show Up in MAANG LLD Interviews

- **Tier 1 (near-guaranteed)**: Singleton, Factory Method, Builder, Strategy, Observer, Decorator, Adapter, Proxy, Facade
- **Tier 2 (common in specific problems)**: Abstract Factory, Command, Template Method, Chain of Responsibility, State
- **Tier 3 (rare, mostly framework-internals trivia)**: Composite, Bridge, Flyweight, Prototype, Mediator, Memento, Visitor, Iterator, Interpreter
- Machine coding rounds (Parking Lot, BookMyShow, Splitwise, Elevator) test whether you **reach for the right pattern unprompted**, not whether you can name all 23

---

### 7. Design Patterns vs SOLID Principles

- SOLID are **principles** (goals); patterns are **concrete shapes** that satisfy them
- Strategy is OCP made concrete; Observer is DIP + loose coupling made concrete; Decorator is OCP without touching the wrapped class
- A pattern applied where the principle doesn't call for it is **overengineering**, not good design — see [[12. SOLID And Design Principles]] on KISS/YAGNI tension

---

### 8. Symptom → Pattern Cheatsheet

| Symptom in the requirement | Reach for |
| --- | --- |
| "Only one X should exist app-wide" | Singleton |
| "Which subclass to build depends on a type/config" | Factory Method / Abstract Factory |
| "This object has 6+ optional constructor params" | Builder |
| "Same operation, different algorithm per case, switch at runtime" | Strategy |
| "Notify N listeners when something changes" | Observer |
| "Add behaviour to an object without touching its class" | Decorator |
| "Wrap a class that has the wrong interface" | Adapter |
| "Control/lazy-init/cache access to an expensive object" | Proxy |
| "Hide a messy subsystem behind one clean call" | Facade |
| "An object's behaviour depends on a lifecycle state" | State |
| "Request should be queued, logged, retried, or undone" | Command |
| "Same steps every time, one step varies by subclass" | Template Method |
| "Request should pass through validators/handlers until one fits" | Chain of Responsibility |

---

### 9. When Not to Use a Pattern

- A pattern is a **cost**: an extra interface, an extra class, an extra layer of indirection to read through
- Applying Strategy to an `if (x % 2 == 0)` check is the textbook KISS violation — not every branch is a "family of algorithms"
- Rule of thumb: introduce the pattern when the **variation point is real and known**, not speculative (YAGNI)
- In an interview, **narrate the trade-off** — "I could use Abstract Factory here for families of related objects, but since we only have one family right now, plain Factory Method is enough" reads senior; silently over-patterning a toy problem does not

---

### SDE-2 Interview Priority

**Must Know**: Singleton, Factory Method, Builder, Strategy, Observer, Decorator, Adapter, Proxy, Facade, Creational/Structural/Behavioral split, pattern vs principle relationship

**Nice To Know**: Abstract Factory, Command, Template Method, Chain of Responsibility, State, symptom→pattern mapping, when a pattern is overkill

**Advanced**: Composite, Bridge, Flyweight, Prototype, Mediator, Memento, Visitor, Iterator, where each shows up inside the JDK/Spring internals

# Detailed Explanation

---

## What Is a Design Pattern (And What It Isn't)

A design pattern is a **named solution to a problem that recurs across unrelated codebases** — not because the code is copy-pasted, but because the underlying forces (multiple implementations of one concept, one-to-many notification, controlled object creation) show up again and again in object-oriented systems. The Gang of Four catalogued 23 of these in 1994, and the vocabulary stuck because it gives engineers a **shared name** for a shape: saying "this needs a Strategy" communicates an entire structure in two words instead of a paragraph.

Three things a pattern is *not*:

- **Not code you import.** A pattern is a shape you re-implement in your own classes, in your own language, adapted to your own constraints. There's no `import Singleton`.
- **Not an algorithm.** Patterns are about the *arrangement of objects and their responsibilities*, not about computing something. Quicksort is an algorithm; Strategy is what you'd use to let quicksort and mergesort be swapped at runtime.
- **Not a silver bullet.** Every pattern trades simplicity for flexibility along one specific axis. Using one where that axis of flexibility isn't needed is pure cost — see [[#When Not to Use a Pattern]].

> 💡 **Interview**: "What's the difference between a design pattern and a framework?" → A framework is a reusable, opinionated piece of software you build *inside* (it calls your code). A pattern is a reusable idea you implement *with* your own code — there's no shared runtime, just a shared shape.

---

## The GoF Classification

The 23 GoF patterns split into three categories by **what question they answer**:

```text
Creational   → "How does this object get MADE?"
Structural   → "How do these objects/classes fit TOGETHER?"
Behavioral   → "How do these objects TALK to each other, and who owns the algorithm?"
```

This split isn't academic trivia — it's the fastest way to narrow down which pattern fits a requirement. If the pain point is "constructing this object is getting complicated," you're in Creational territory. If it's "these two components don't fit together" or "I need to compose small pieces into a bigger thing," you're in Structural. If it's "who decides what happens next, and how do parts communicate," you're in Behavioral.

Almost no real LLD problem uses exactly one pattern — a parking lot system typically combines Factory Method (creating the right `Vehicle`/`Spot` type), Strategy (fee calculation per vehicle type), Observer (notifying on a spot becoming free), and sometimes Singleton (the lot manager itself).

## Creational Patterns

### Singleton

Ensures a class has **exactly one instance** and provides a global access point to it. Classic uses: a `ConnectionPool`, a `ConfigManager`, a logging registry — anything where having two instances would mean two sources of truth or wasted resources.

```java
public class ConnectionPool {
    private static volatile ConnectionPool instance;
    private ConnectionPool() { /* expensive setup */ }

    public static ConnectionPool getInstance() {
        if (instance == null) {                    // first check — avoids locking on the hot path
            synchronized (ConnectionPool.class) {
                if (instance == null) {             // second check — only one thread actually constructs
                    instance = new ConnectionPool();
                }
            }
        }
        return instance;
    }
}
```

This is the **double-checked locking** form — `volatile` is required, otherwise another thread can observe a partially-constructed object due to instruction reordering. The simpler and generally preferred Java idiom is an `enum` singleton (serialization-safe, reflection-safe, thread-safe for free) or Spring's default singleton-scoped bean, which sidesteps hand-rolling this entirely.

**The honest downside**: Singleton is also the most *overused* pattern — it's effectively a global variable, makes unit testing harder (hidden shared state), and hides a dependency that should have been passed in explicitly. In an interview, naming this downside unprompted is a good signal.

### Factory Method vs Abstract Factory

**Factory Method** — one creation method, overridden by subclasses to decide the concrete type:

```java
interface PaymentMethod { void pay(long amountPaise); }
class UpiPayment implements PaymentMethod { public void pay(long p) { /* ... */ } }
class CardPayment implements PaymentMethod { public void pay(long p) { /* ... */ } }

class PaymentMethodFactory {
    static PaymentMethod create(String type) {
        return switch (type) {
            case "UPI"  -> new UpiPayment();
            case "CARD" -> new CardPayment();
            default -> throw new IllegalArgumentException("Unknown: " + type);
        };
    }
}
```

**Abstract Factory** — a factory that produces a **family** of related objects, without the client naming any concrete class:

```java
interface UIFactory {
    Button createButton();
    Checkbox createCheckbox();
}
class DarkThemeFactory implements UIFactory {
    public Button createButton()     { return new DarkButton(); }
    public Checkbox createCheckbox() { return new DarkCheckbox(); }
}
class LightThemeFactory implements UIFactory {
    public Button createButton()     { return new LightButton(); }
    public Checkbox createCheckbox() { return new LightCheckbox(); }
}
```

The distinction that gets tested: Factory Method creates **one product**; Abstract Factory creates a **consistent family** of products (you'd never want a `DarkButton` paired with a `LightCheckbox`) — Abstract Factory is literally "a factory of factory methods."

### Builder

Separates the **construction** of a complex object from its **representation**, replacing telescoping constructors and long parameter lists with a fluent, readable chain.

```java
// ❌ telescoping constructor — which boolean is which at the call site?
new TransactionRequest("txn123", 50000L, "INR", true, false, null, 3);

// ✅ Builder
TransactionRequest req = TransactionRequest.builder()
    .transactionId("txn123")
    .amountPaise(50_000L)
    .currency("INR")
    .idempotent(true)
    .retryCount(3)
    .build();
```

Builder is the pattern behind Java's `StringBuilder`, `Stream.Builder`, and Lombok's `@Builder`. It shines exactly when a class has several optional fields and you want compile-time-readable, order-independent construction.

### Prototype

Creates new objects by **cloning** an existing "prototype" instance rather than constructing from scratch — useful when construction is expensive (e.g., loaded from a DB or computed) and a copy-with-tweaks is cheaper. Java's `Object.clone()` and `Cloneable` are the built-in (if clunky) version; most modern code prefers a copy constructor or a `toBuilder()` instead. Rare in interviews but occasionally shows up in "duplicate this configuration/document with small edits" prompts.

## Structural Patterns

### Adapter

Converts the interface a class exposes into the interface a client expects — the classic use is wrapping a **legacy or third-party API** you can't modify.

```java
interface PaymentGateway { void charge(long amountPaise); }        // interface our system expects

class LegacyBankApi {                                              // third-party, can't touch
    void makePaymentInRupees(double rupees) { /* ... */ }
}

class LegacyBankAdapter implements PaymentGateway {
    private final LegacyBankApi legacy;
    LegacyBankAdapter(LegacyBankApi legacy) { this.legacy = legacy; }

    public void charge(long amountPaise) {
        legacy.makePaymentInRupees(amountPaise / 100.0);            // bridges paise ↔ rupees, interface ↔ interface
    }
}
```

### Decorator

Attaches responsibilities to an object **at runtime** by wrapping it in another object that implements the same interface — an alternative to subclassing for every combination of behaviour.

```java
interface PaymentService { void process(long amountPaise); }

class BasicPaymentService implements PaymentService {
    public void process(long amountPaise) { System.out.println("Processing " + amountPaise); }
}

class LoggingDecorator implements PaymentService {
    private final PaymentService wrapped;
    LoggingDecorator(PaymentService wrapped) { this.wrapped = wrapped; }
    public void process(long amountPaise) {
        System.out.println("Before: " + amountPaise);
        wrapped.process(amountPaise);
        System.out.println("After: " + amountPaise);
    }
}

class RetryDecorator implements PaymentService {
    private final PaymentService wrapped;
    RetryDecorator(PaymentService wrapped) { this.wrapped = wrapped; }
    public void process(long amountPaise) {
        try { wrapped.process(amountPaise); }
        catch (Exception e) { wrapped.process(amountPaise); }        // one retry
    }
}

PaymentService service = new RetryDecorator(new LoggingDecorator(new BasicPaymentService()));
```

Each decorator adds one concern and can be **stacked in any order**, without touching `BasicPaymentService` — this is OCP in structural form. Java I/O (`BufferedInputStream` wrapping a `FileInputStream`) is Decorator in the standard library.

### Proxy

A stand-in object that **controls access** to the real one — same interface as the real subject, but interposes logic before/after delegating.

```java
interface AccountBalance { long getBalance(String accountId); }

class RealAccountBalance implements AccountBalance {
    public long getBalance(String id) { /* expensive DB call */ return 100_000L; }
}

class CachingProxy implements AccountBalance {
    private final AccountBalance real;
    private final Map<String, Long> cache = new HashMap<>();
    CachingProxy(AccountBalance real) { this.real = real; }

    public long getBalance(String id) {
        return cache.computeIfAbsent(id, real::getBalance);          // caches on first access
    }
}
```

**Proxy vs Decorator** is a frequent mix-up: both wrap the same interface, but Decorator's *intent* is adding behaviour the client asked for (logging, retry), while Proxy's *intent* is controlling access the client doesn't need to know about (caching, lazy loading, permission checks, remote calls). Structurally near-identical; intent differs.

### Facade

One simplified interface in front of a **complex subsystem** of many interacting classes.

```java
class PaymentFacade {
    private final FraudCheckService fraud;
    private final LedgerService ledger;
    private final NotificationService notify;

    void processPayment(String txnId, long amountPaise) {
        if (!fraud.isSafe(txnId)) throw new SecurityException("Blocked");
        ledger.debit(txnId, amountPaise);
        notify.sendReceipt(txnId);
    }
}
```

The caller doesn't need to know fraud checks, ledger writes, and notifications are three separate subsystems with their own APIs — Facade doesn't add new capability, it removes required knowledge.

### Composite, Bridge, Flyweight

- **Composite**: a `Menu` containing `MenuItem`s and other `Menu`s, both implementing a shared `MenuComponent` — client code calls `render()` uniformly whether it's a leaf or a whole subtree. Any "tree of things, some of which contain more things" problem (file systems, org charts, UI containers).
- **Bridge**: splits an abstraction (`Shape`) from its implementation (`DrawingAPI`) so each can vary independently — e.g. `Shape` subtypes (Circle, Square) times rendering engines (OpenGL, SVG) without an `N × M` class explosion.
- **Flyweight**: shares immutable, reusable state across many logical objects to cut memory — e.g. representing millions of characters in a text editor by sharing one glyph object per distinct character, keeping only position as per-instance state.

These three are asked rarely at SDE-2 level — know the one-line intent, not full implementations.

## Behavioral Patterns

### Strategy

Already covered in depth in [[12. SOLID And Design Principles]] as the concrete mechanism behind OCP — interchangeable algorithms behind one interface, selected at runtime instead of an `if/else` or `switch` on type.

### Observer

Defines a one-to-many dependency: when the **subject's** state changes, all registered **observers** are notified automatically.

```java
interface TransactionListener { void onStatusChanged(String txnId, String status); }

class Transaction {
    private final List<TransactionListener> listeners = new ArrayList<>();
    private String status = "INITIATED";

    void addListener(TransactionListener l) { listeners.add(l); }

    void setStatus(String newStatus) {
        this.status = newStatus;
        listeners.forEach(l -> l.onStatusChanged("txn123", newStatus));   // fan-out on state change
    }
}
```

This is the shape behind pub/sub, Java's (deprecated) `Observable`, Spring's `ApplicationEventPublisher`, and webhook-style notifications in a payments system (notify merchant + ledger + analytics when a transaction settles) without the `Transaction` class knowing any of them exist.

### Command

Encapsulates a request as an object, so it can be **queued, logged, retried, or undone** — decoupling the invoker from the thing that executes the request.

```java
interface Command { void execute(); }

class ChargeCommand implements Command {
    private final PaymentService service;
    private final long amountPaise;
    ChargeCommand(PaymentService s, long amt) { service = s; amountPaise = amt; }
    public void execute() { service.process(amountPaise); }
}

Queue<Command> retryQueue = new LinkedList<>();
retryQueue.add(new ChargeCommand(service, 50_000L));   // the request now exists as data, not a live call
```

Useful whenever "run this later / run this again / run this in order" is a requirement — a transaction retry queue, a job scheduler, or undo/redo in an editor.

### Template Method

The base class fixes the **skeleton of an algorithm**; subclasses override only the steps that vary.

```java
abstract class ReconciliationJob {
    final void run() {                          // the algorithm's shape — never overridden
        fetchRecords();
        validate();
        reportDiscrepancies();
    }
    abstract void fetchRecords();
    abstract void validate();
    void reportDiscrepancies() { System.out.println("Standard report"); }   // default step, overridable
}

class BankReconciliationJob extends ReconciliationJob {
    void fetchRecords() { /* pull from bank statement API */ }
    void validate()     { /* compare against ledger */ }
}
```

The `final` on `run()` is the point — it guarantees every subclass follows the same sequence, only the marked steps differ.

### Chain of Responsibility

A request passes along a **chain of handlers**; each either handles it or forwards it to the next.

```java
abstract class FraudCheckHandler {
    protected FraudCheckHandler next;
    FraudCheckHandler setNext(FraudCheckHandler next) { this.next = next; return next; }
    abstract void check(Transaction txn);
}

class VelocityCheck extends FraudCheckHandler {
    void check(Transaction t) {
        if (t.exceedsVelocityLimit()) throw new SecurityException("Blocked: velocity");
        if (next != null) next.check(t);
    }
}
```

Used for validation pipelines, middleware/filter chains (Servlet `Filter`, Spring `HandlerInterceptor`), and fraud/compliance checks where each rule is independent and the set of rules changes often.

### State

An object appears to **change its class** as its internal state changes — behaviour is delegated to a state object instead of branching on an enum everywhere.

```java
interface TransactionState { void next(TransactionContext ctx); }

class InitiatedState implements TransactionState {
    public void next(TransactionContext ctx) { ctx.setState(new ProcessingState()); }
}
class ProcessingState implements TransactionState {
    public void next(TransactionContext ctx) { ctx.setState(new SuccessState()); }
}
class SuccessState implements TransactionState {
    public void next(TransactionContext ctx) { /* terminal */ }
}
```

This is how a payment lifecycle (`INITIATED → PROCESSING → SUCCESS/FAILED`) is modeled without a giant `switch(status)` scattered across the codebase — each state owns its own valid transitions.

### Iterator, Mediator, Memento, Visitor

- **Iterator**: sequential access to a collection without exposing its internal structure — Java's `Iterator`/`Iterable` *is* this pattern, already used every time you write a for-each loop.
- **Mediator**: centralizes many-to-many communication between components into one coordinator object, so components talk to the mediator instead of each other directly — an air traffic control tower is the canonical analogy; a chat room server relaying between clients is the software one.
- **Memento**: captures an object's internal state externally so it can be restored later, without violating encapsulation — the mechanism behind undo/redo and snapshotting.
- **Visitor**: lets you add a new operation across a class hierarchy without modifying the classes themselves — an external `Visitor` object implements one method per concrete type; useful when the hierarchy is stable but the set of operations on it keeps growing (e.g. a fixed AST visited by a type-checker, then a code-generator, then a formatter).

These four are low-frequency at SDE-2 level — know the one-liner, don't over-invest in implementations.

## Design Patterns vs SOLID Principles

SOLID principles (see [[12. SOLID And Design Principles]]) are the **goals** — high cohesion, low coupling, safe extension. Design patterns are **known-good shapes that achieve those goals** in specific situations:

| Pattern | Principle it embodies |
| --- | --- |
| Strategy | OCP — new algorithm = new class, zero edits to existing code |
| Observer | DIP — subject depends on an abstraction (`Listener`), not concrete subscribers |
| Decorator | OCP — new behaviour without touching the wrapped class |
| Factory Method | DIP — client depends on the product interface, not `new ConcreteClass()` |
| Adapter | ISP/DIP — client's expected interface stays clean regardless of the vendor behind it |

The relationship also explains why patterns can be *misapplied*: a pattern introduced where the corresponding principle wasn't actually under threat is pure overhead — see below.

---

## Symptom → Pattern Cheatsheet

The table in Short Notes is the quick-reference version; the underlying method is: identify **which axis is expected to vary**, then pick the pattern whose entire purpose is isolating that one axis.

- Varies: *which concrete type to construct* → Creational (Factory Method/Abstract Factory/Builder)
- Varies: *how two existing pieces fit together* → Structural (Adapter/Facade/Bridge)
- Varies: *what happens next, or who's listening* → Behavioral (Strategy/Observer/State/Chain of Responsibility)

If nothing is expected to vary, no pattern is needed — that's not a gap in the cheatsheet, that's the correct answer.

---

## When Not to Use a Pattern

Every pattern buys flexibility along one axis at the cost of an extra interface and an extra layer of indirection **on every read**. The interview mistake isn't failing to know a pattern — it's reaching for one where the corresponding principle isn't actually threatened:

```java
// ❌ Strategy for a binary, permanent decision
interface EvenOddChecker { boolean check(int n); }
class EvenChecker implements EvenOddChecker { public boolean check(int n) { return n % 2 == 0; } }
// three files and an interface to express `n % 2 == 0`

// ✅
boolean isEven = n % 2 == 0;
```

The tell that a pattern is earning its place: you can name the **future case** that would otherwise force editing tested code (a new payment rail, a new notification channel, a new fraud rule) — not a hypothetical one, an expected one. This is exactly the OCP/YAGNI tension already covered in [[12. SOLID And Design Principles]]: structural readiness for a *known* variation is good design; speculative machinery for an *imagined* one is waste.

> 💡 **Interview**: "How do you decide whether to introduce a design pattern?" → Name the axis of variation, confirm it's real (not speculative), and check the pattern's cost (extra classes/indirection) is smaller than the cost of the `if/else` chain or constructor explosion it replaces. If a problem has no real variation point, the correct design has no pattern in it.

## SDE-2 Interview Priority Checklist

### Must Know (100%)

- Creational / Structural / Behavioral split and what question each answers
- Singleton (with the double-checked-locking + `volatile` reasoning, and its testability downside)
- Factory Method vs Abstract Factory — one product vs a consistent family
- Builder — telescoping constructor problem it solves
- Strategy, Observer, Decorator, Adapter, Proxy, Facade — one working code example each
- Proxy vs Decorator — same structure, different intent (access control vs added behaviour)
- Pattern as a concrete instance of a SOLID principle (Strategy→OCP, Observer→DIP)

### Nice To Know

- Abstract Factory family-consistency guarantee
- Command, Template Method, Chain of Responsibility, State — one example each
- Symptom → Pattern mapping as a live design-interview technique
- When a pattern is overkill (KISS/YAGNI applied to pattern selection)

### Advanced

- Composite, Bridge, Flyweight — intent and one real-world example each
- Prototype, Mediator, Memento, Visitor, Iterator — one-line intent
- Where these show up inside the JDK/Spring (`Iterator`, I/O Decorator stack, `ApplicationEventPublisher` as Observer, BeanFactory as Abstract Factory)
- Combining multiple patterns in one LLD answer (Parking Lot: Factory Method + Strategy + Observer + Singleton)
