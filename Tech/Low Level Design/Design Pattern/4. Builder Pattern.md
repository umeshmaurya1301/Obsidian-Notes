# Builder Pattern

---

## Short Notes

---

### 1. The Problem — Telescoping Constructors

- An object with **many fields**, especially a mix of required and optional, breaks plain constructors fast
- **Telescoping constructor anti-pattern**: a new constructor overload for every combination of optional fields you might need
- Call sites become positional and ambiguous — `new Transaction("txn123", 500, "user@upi", null, "INR", false, null, "device456")` — which `null` means what?
- No compile-time protection against swapping two same-typed args (`merchantId` vs `currency`)

---

### 2. The Failed Alternative — JavaBean Setters

- `new Transaction(); t.setTxnId(...); t.setAmount(...);` — readable, but three real problems
- **Mutable** — can be changed at any point after construction
- **Inconsistent intermediate state** — between `new` and the last setter, the object is partially built; other code reading it mid-construction sees incomplete data
- **No enforcement** that required fields were actually set — forgetting `setAmount()` compiles fine

---

### 3. The Builder Solution — Structure

- `Transaction` gets a **private constructor** taking only a `Builder`, and exposes **getters only — no setters**
- **Static nested `Builder` class**: required fields go in the `Builder`'s own constructor; optional fields get chainable `fieldName(value)` methods returning `this`
- `build()` calls the private `Transaction` constructor and returns the finished object — whether that object is actually immutable depends on how `Transaction` itself is written, not on Builder (see §4)
- Usage: `new Transaction.Builder("txn123", 500, "user@upi").merchantId("m789").currency("USD").build()` — every field named at the call site

---

### 4. Two Precision Corrections — Read Before The Rest

- **Compile-time vs runtime is not "Builder = compile-time safe"**: only the **required-field structure** is compile-time enforced (missing a required constructor arg won't compile). **Values** — `amount = -500`, cross-field rules — are only checked if you write an explicit `if` inside `build()`, and that check fires at **runtime**
- `new Transaction.Builder("txn123", -500, "user@upi").build()` **compiles fine**; it's rejected only when `build()` executes and throws `IllegalArgumentException`
- **Immutability is NOT a property of Builder itself** — Builder only guarantees clean, staged construction with no half-built object visible mid-assembly. Whether the *result* can be mutated afterward is decided entirely by the target class: `final` fields + no setters → immutable; non-final fields + setters → mutable, Builder or not
- Lombok corollary: `@Builder` alone does **not** imply immutability — `@Builder` + `@Setter` (or non-final fields) is mutable. Genuine immutability needs `@Builder` + `@Value` (private final fields, no setters, final class)

---

### 5. Benefits — Readability, Optional Fields, Required-Field Enforcement

- **Readable**: each chained method name documents exactly what it sets — no need to check a constructor signature
- **No overload explosion**: only call the builder methods for fields you actually want to set, in any order
- **Compile-time required-field enforcement**: required params live in the `Builder`'s constructor, so `new Transaction.Builder().build()` (missing required args) is a compile error — this checks **structure** (argument count/type), never **values**

---

### 6. Benefits — Immutability (If You Choose It), No Intermediate State, Centralized Validation

- **Enables immutability, doesn't force it**: pair `final` fields + no setters on the target class with Builder and the result can never mutate after `build()` returns — all the mutability lives in the disposable `Builder`. Swap in non-final fields + setters and the identical Builder code produces a mutable object
- **No inconsistent intermediate state**: no `Transaction` object exists at all until `build()` returns — unlike JavaBean setters, there's no window where a half-built one is visible
- **Cross-field validation, centralized, at runtime**: `build()` is the natural place to check invariants spanning multiple fields (e.g. "amount cannot be negative", "recurring transactions require a discount code") — a single setter can't see the whole picture, and these checks only run when `build()` executes

---

### 7. Benefits — Fluent Chaining, Decoupled Construction

- `return this;` in every chainable method (see [[3. Static And Dynamic Binding]] or the `this` keyword topic) is what enables `.size(...).extraCheese(...).addTopping(...)` reading like a sentence
- Splits **construction concerns** (defaults, derived fields, validation) from **representation concerns** (the plain, data-holding target class) — a mild SRP application, see [[12. SOLID And Design Principles]]

---

### 8. Real-World / JDK Examples

- `StringBuilder` — a simpler streaming variant, not the full pattern
- `Stream.Builder<String>` — genuine Builder pattern in the JDK: `.add("a").add("b").build()`
- **Lombok `@Builder`** generates the entire static nested `Builder` class, chainable methods, and `build()` from one annotation — this is what you actually use day-to-day in Spring Boot
- `@Builder` alone → mutable if fields aren't final/have setters; `@Builder` + `@Value` → genuinely immutable — the piece responsible for immutability is `@Value`, not `@Builder`
- Knowing the hand-rolled mechanics is exactly what lets you answer "you use `@Builder` — do you know what it generates, and why `@Value` matters?"

---

### 9. When Builder Is Overkill

- A `Point(int x, int y)` with 2 required fields and no validation needs nothing more than a plain constructor (or a `record`)
- **Use Builder when**: 4+ fields, several optional, or validation spanning multiple fields — add immutability separately via `final`/no setters if that's also wanted
- **Skip Builder when**: object is simple, mostly-required fields, no complex validation — don't reach for it reflexively just because it's a "known good pattern" (KISS/YAGNI, see [[12. SOLID And Design Principles]])

---

### 10. Quick Comparison — All Three Construction Approaches

| | Telescoping Constructor | JavaBean Setters | Builder |
| --- | --- | --- | --- |
| Readability at call site | Poor — positional, ambiguous | Good — named setters | Good — named, chainable |
| Immutability | Yes (typically) | No | **Optional** — depends on target class (`final` + no setters), not on Builder itself |
| Required-field enforcement | Yes, but unwieldy | No | Yes, via `Builder`'s own constructor — structure only, not values |
| Handles many optional fields | Poorly — overload explosion | Well | Well |
| Inconsistent intermediate state risk | No | Yes | No |
| Cross-field validation | Awkward | Awkward, scattered | Clean — centralized in `build()`, at runtime |

---

**Must Know**: telescoping constructor problem, JavaBean setter problems (mutability, intermediate state, no enforcement), Builder structure (private constructor, static nested Builder, chainable `this`-returning setters, `build()`), compile-time enforces required-field *structure* only while value/business validation is runtime inside `build()`, immutability comes from the target class (`final` + no setters) not from Builder itself, Lombok `@Builder` generating this automatically

**Nice To Know**: centralized cross-field validation in `build()`, `@Builder` + `@Value` as the Lombok combination for genuine immutability, `Stream.Builder` as a real JDK example

**Advanced**: Builder as a mild SRP split (construction vs representation concerns), when Builder is overkill vs a plain constructor/record, the full comparison table across all three construction approaches

# Detailed Explanation

---

## The Problem — Telescoping Constructors

An object with many fields — especially a mix of required and optional — breaks down plain constructors quickly.

```java
class Transaction {
    String txnId;
    double amount;
    String upiId;
    String merchantId;
    String currency;
    boolean isRecurring;
    String discountCode;
    String deviceId;

    // a constructor overload for every combination you might need...
    Transaction(String txnId, double amount, String upiId) { ... }
    Transaction(String txnId, double amount, String upiId, String merchantId) { ... }
    Transaction(String txnId, double amount, String upiId, String merchantId, String currency) { ... }
    Transaction(String txnId, double amount, String upiId, String merchantId, String currency, boolean isRecurring) { ... }
    // ...and so on, for every combination of optional fields
}
```

```java
Transaction t = new Transaction("txn123", 500, "user@upi", null, "INR", false, null, "device456");
// Which parameter is which?? What does 'null' mean here? What does 'false' mean?
// Easy to swap two same-typed parameters (merchantId vs currency) with NO compile error
```

This is the **telescoping constructor anti-pattern** — every new optional field theoretically doubles the number of constructor overloads needed, and call sites become unreadable, positional, and easy to get subtly wrong: the compiler cannot catch two `String` arguments swapped in position.

---

## The Failed Alternative — JavaBean Setters

```java
Transaction t = new Transaction();
t.setTxnId("txn123");
t.setAmount(500);
t.setUpiId("user@upi");
// readable, but...
```

This fixes the readability problem but introduces three new ones:

- **Mutable** — the object can be changed at any point after construction, breaking immutability.
- **Inconsistent intermediate state** — between `new Transaction()` and the last setter call, the object exists in a partially-constructed state. If some other code reads `t` in that window (e.g. a validation check running mid-construction), it sees incomplete data.
- **No enforcement of required fields** — nothing stops you from forgetting `setAmount()` entirely; it compiles fine and fails, if at all, only at runtime.

---

## The Builder Solution — Structure

```java
class Transaction {
    private final String txnId;        // required
    private final double amount;       // required
    private final String upiId;        // required
    private final String merchantId;   // optional
    private final String currency;     // optional
    private final boolean isRecurring; // optional
    private final String discountCode; // optional

    private Transaction(Builder builder) {   // private — ONLY the Builder can call this
        this.txnId = builder.txnId;
        this.amount = builder.amount;
        this.upiId = builder.upiId;
        this.merchantId = builder.merchantId;
        this.currency = builder.currency;
        this.isRecurring = builder.isRecurring;
        this.discountCode = builder.discountCode;
    }

    static class Builder {                    // static nested class
        private final String txnId;             // required — passed to Builder's own constructor
        private final double amount;
        private final String upiId;

        private String merchantId;              // optional — chainable setter-style methods, defaults if unset
        private String currency = "INR";        // sensible default
        private boolean isRecurring = false;
        private String discountCode;

        Builder(String txnId, double amount, String upiId) {   // required fields enforced HERE
            this.txnId = txnId;
            this.amount = amount;
            this.upiId = upiId;
        }

        Builder merchantId(String merchantId) { this.merchantId = merchantId; return this; }   // chaining
        Builder currency(String currency)     { this.currency = currency; return this; }
        Builder isRecurring(boolean r)        { this.isRecurring = r; return this; }
        Builder discountCode(String code)     { this.discountCode = code; return this; }

        Transaction build() {
            if (amount < 0) {                     // RUNTIME check — see precision points below
                throw new IllegalArgumentException("Amount cannot be negative");
            }
            return new Transaction(this);       // constructs the final object
        }
    }

    // getters only on Transaction — NO setters. This is what actually makes it immutable, not Builder itself.
}
```

```java
Transaction t = new Transaction.Builder("txn123", 500, "user@upi")
        .merchantId("merchant789")
        .currency("USD")
        .isRecurring(true)
        .build();
```

Compare directly to the telescoping-constructor call from earlier — **every field is named at the call site**. There's no ambiguity about which value means what, and only the optional fields actually needed get specified, in any order, with the rest skipped entirely.

---

## Two Precision Corrections — Read Before The Rest

These two points get glossed over in a first pass at Builder and are worth stating precisely, because they're exactly the kind of thing an interviewer probes on follow-up.

### 1. Only required-field *structure* is compile-time. Value validation is runtime.

```java
new Transaction.Builder("txn123", "user@upi");
// ❌ COMPILE ERROR — missing 'amount' argument. Caught before the program even runs.

new Transaction.Builder("txn123", -500, "user@upi").build();
// ✅ COMPILES FINE. The -500 is only rejected when build() actually EXECUTES,
// via the `if (amount < 0)` check — which throws an unchecked IllegalArgumentException at runtime.
```

The compiler can only check **structure** — the right number and type of arguments — it can never check **values**, i.e. whether `500` (or `-500`) is a sensible, non-negative amount. That distinction is exactly why:

- Required fields → enforced by the `Builder`'s own constructor signature → **compile-time**.
- Business-rule validation (non-negative amounts, cross-field rules, etc.) → written explicitly inside `build()` → **runtime**, and only as good as the checks actually written.

### 2. Immutability is not a property of Builder — it depends entirely on the target class

Builder only guarantees **clean, staged construction**: no half-built object visible mid-assembly, readable chained calls. Whether the final object can be changed afterward is decided purely by how `Transaction` itself is written:

```java
// Immutable version — what's shown above
private final double amount;   // final, no setter → CANNOT be changed after build()

// Mutable version — identical Builder pattern, different target class
private double amount;                                          // not final
public void setAmount(double amount) { this.amount = amount; }   // setter exists

Transaction t = new Transaction.Builder(...).build();
t.setAmount(999);   // legal — Builder did nothing to prevent this
```

The accurate claim: *"Builder + `final` fields + no setters on the target class → immutable result. Builder + non-final fields + setters → mutable result, Builder pattern or not."* Builder and immutability are commonly paired, but they're independent design choices — Builder is about **how** construction happens, immutability is about **whether the target class allows mutation after** construction.

**Lombok corollary**: `@Builder` alone doesn't imply immutability. `@Builder` + `@Setter` (or plain non-final fields) gives a mutable object. For genuine immutability with Lombok, pair `@Builder` with `@Value`, which makes fields `private final`, generates no setters, and makes the class itself `final`.

> 💡 **Interview**: "Does the Builder pattern make an object immutable?" → No — Builder only controls *how* the object is assembled. Immutability comes from the target class having `final` fields and no setters. The two are usually paired, but Builder alone guarantees neither immutability nor value validation beyond what you explicitly code into `build()`.

---

## Benefits — Readability, Optional Fields, Required-Field Enforcement

### Readable, self-documenting construction

```java
// Telescoping constructor — what do these mean?
new Transaction("txn123", 500, "user@upi", null, "INR", false, null, "device456");

// Builder — self-explanatory
new Transaction.Builder("txn123", 500, "user@upi")
    .currency("INR")
    .isRecurring(false)
    .build();
```

Each method name tells you exactly what field it sets — no need to check the constructor signature or documentation to understand a call site.

### Optional parameters without overload explosion

Only the builder methods for fields actually wanted get called — no need for a dozen constructor overloads covering every combination of present/absent optional fields.

### Required fields enforced at compile time

```java
new Transaction.Builder("txn123", 500, "user@upi")   // txnId, amount, upiId are constructor params — MUST be provided
    .build();                                          // compiles fine — optional fields use their defaults

// new Transaction.Builder().build();   // ❌ COMPILE ERROR — required params missing from Builder's constructor
```

By putting required fields in the `Builder`'s own constructor — not as chainable methods — required fields are provably never skipped, while optional fields remain genuinely optional via chainable setter-style methods. This is a **structural** guarantee only: the compiler verifies argument count and type, never the value inside them (a missing `amount` won't compile; a `-500` amount compiles just fine).

---

## Benefits — Immutability (If You Choose It), No Intermediate State, Centralized Validation

### Enables immutability — doesn't force it

If `Transaction`'s fields are all `final` and it exposes getters with no setters, once `build()` returns the object can never be mutated — all the standard benefits of immutability (thread safety, safe sharing, safe as a map key) apply directly, and the mutability lives entirely in the temporary `Builder` object, typically discarded right after `build()` is called. But this is a property of `Transaction`'s own design, not of Builder — as the precision section above shows, the identical `Builder` code paired with non-final fields and setters on `Transaction` produces a fully mutable object.

### Avoids inconsistent intermediate states

With JavaBean setters, code holding a reference to a `Transaction` mid-construction could observe a half-built object. With Builder, **no `Transaction` object exists at all** until `build()` is called — there's no window where an incomplete `Transaction` is visible to any other code. The `Builder` is a separate, temporary staging object; the real `Transaction` comes into existence fully formed. This guarantee holds regardless of whether the target class ends up mutable or immutable.

### Enables validation at the point of construction — at runtime

```java
Transaction build() {
    if (amount <= 0) {
        throw new IllegalArgumentException("Amount must be positive");
    }
    if (isRecurring && discountCode == null) {
        throw new IllegalArgumentException("Recurring transactions require a discount code");
    }
    return new Transaction(this);
}
```

`build()` is a natural, centralized place to validate **cross-field invariants** — rules involving multiple fields together — something that's awkward to do cleanly with scattered setter calls, since each individual setter only ever sees the one field it's setting. These checks are ordinary Java code inside `build()`, so — unlike the required-field check — they run and fail only at **runtime**, and only for the invariants actually written.

---

## Benefits — Fluent Chaining, Decoupled Construction

### Fluent method chaining reads like a sentence

```java
Pizza pizza = new Pizza.Builder()
    .size("Large")
    .extraCheese(true)
    .addTopping("Mushroom")
    .addTopping("Olives")
    .build();
```

Every `return this;` in a builder method is what enables this chaining — a classic use of the `this` reference. It reads almost like natural language describing what's being built, step by step.

### Decouples construction logic from the object's representation

The `Builder` can hold complex assembly logic — conditional defaults, derived fields, validation — entirely separate from `Transaction` itself, which stays a clean, simple, purely data-holding class. This is a mild application of SRP (see [[12. SOLID And Design Principles]]): object-construction concerns and object-representation concerns split into two classes.

---

## Real-World / JDK Examples

```java
StringBuilder sb = new StringBuilder();          // named "Builder", but a simpler streaming variant
sb.append("Hello").append(" ").append("World");

// Full Builder pattern in the JDK:
Stream.Builder<String> builder = Stream.builder();
builder.add("a").add("b").add("c");
Stream<String> stream = builder.build();
```

In a Spring Boot codebase, hand-writing the full Builder boilerplate above is rare — **Lombok's `@Builder` annotation generates the entire static nested `Builder` class, the chainable methods, and `build()` automatically** from one annotation:

```java
@Builder
class TransactionRequest {
    String upiId;
    double amount;
    String merchantId;
}

TransactionRequest req = TransactionRequest.builder()
    .upiId("user@upi")
    .amount(500)
    .merchantId("merchant789")
    .build();
```

**`@Builder` alone does not imply immutability** — with plain, non-final fields and no `@Value`/`@Getter`-only setup, Lombok still generates setters unless told not to, so the object above can be mutated after `build()` just like any other JavaBean. For genuine immutability, pair it with `@Value`:

```java
@Builder
@Value   // makes fields private final, generates no setters, makes the class final — genuinely immutable
class TransactionRequest {
    String upiId;
    double amount;
    String merchantId;
}
```

The piece responsible for immutability here is `@Value`, not `@Builder` — the same separation of concerns as the hand-rolled version above. Knowing the underlying pattern is exactly what lets you answer, precisely, what Lombok is generating under the hood and why `@Value` — not `@Builder` — is the annotation doing the immutability work, a question that comes up directly when an interviewer notices `@Builder` on your resume or in your code sample.

---

## When Builder Is Overkill

```java
// Overkill — only 2 simple required fields, no optional fields, no complex validation
class Point {
    int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }   // a plain constructor is perfectly fine here
}
```

**Use Builder when**: an object has 4+ fields (especially with several optional ones), needs immutability, or needs validation spanning multiple fields.

**Skip Builder when**: the object is simple — 2–3 fields, mostly required, no complex validation — a plain constructor, or even a `record`, is simpler and equally clear. This is the same KISS/YAGNI tension covered in [[12. SOLID And Design Principles]]: added structure should earn its complexity, not get applied reflexively because it's a "known good pattern."

## Quick Comparison — All Three Construction Approaches

| | Telescoping Constructor | JavaBean Setters | Builder |
| --- | --- | --- | --- |
| Readability at call site | Poor — positional, ambiguous | Good — named setters | Good — named, chainable |
| Immutability | Yes (typically) | No — mutable after construction | **Optional** — depends on the target class (`final` fields, no setters), not on Builder itself |
| Required field enforcement | Yes, but unwieldy with many overloads | No | Yes, via `Builder`'s own constructor — structure only, never values |
| Handles many optional fields | Poorly — overload explosion | Well | Well |
| Risk of inconsistent intermediate state | No | Yes | No |
| Cross-field validation | Awkward | Awkward, scattered | Clean — centralized in `build()`, checked at runtime |

> 💡 **Interview**: "Walk me through why you'd reach for Builder over a constructor." → Telescoping constructors give positional, ambiguous, error-prone call sites; JavaBean setters fix readability but sacrifice immutability and allow inconsistent intermediate states. Builder gets compile-time enforcement that required fields are present, readable named optional parameters, and one centralized runtime place — `build()` — to validate values and cross-field invariants. Immutability of the result is a separate, deliberate choice in how the target class is written, not something Builder gives you automatically.

**Interview-ready summary line**: *"Builder solves telescoping constructors and inconsistent mutable state during construction — required fields are enforced at compile time via the Builder's own constructor, while value validation like non-negative checks happens at runtime inside `build()`. Immutability of the final object isn't something Builder provides automatically — it comes from making the target class's fields `final` with no setters; Builder just gives you a clean way to assemble that object step by step before it's created. In practice I mostly get this via Lombok's `@Builder` (paired with `@Value` for immutability) rather than hand-writing the nested class, but the underlying mechanics are exactly what this walkthrough covers."*
