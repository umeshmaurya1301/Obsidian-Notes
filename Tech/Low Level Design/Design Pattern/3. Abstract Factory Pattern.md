# Abstract Factory Pattern

---

## Short Notes

---

### 1. The Core Idea

- **Definition**: provides an interface for creating **families of related objects**, without specifying their concrete classes
- One-line distinction from Factory Method (see [[1. Types of Design Patterns]]): Factory Method creates **one product**; Abstract Factory creates a **whole family** and guarantees they're all from the same family
- "Family" = a set of objects that must always be used **together, consistently** — e.g. every UPI-related object, or every Card-related object, never a mix

---

### 2. The Problem It Solves

- A payment rail (UPI, Card) needs its own `Validator` + `Processor` + `Notifier`, and the three **must travel together per rail**
- Without a family abstraction: `new UpiValidator()` paired with `new CardProcessor()` compiles fine — nothing in the type system stops the mismatch
- The bug gets easier to introduce as the number of rails and object types grows — pure programmer discipline is the only guard

---

### 3. Building The Solution

- **Step 1 — product interfaces**: `Validator`, `Processor`, `Notifier`
- **Step 2 — concrete products, grouped by family**: `UpiValidator`/`UpiProcessor`/`UpiNotifier`, `CardValidator`/`CardProcessor`/`CardNotifier`
- **Step 3 — the abstract factory interface**: `PaymentRailFactory` with one creation method per product type (`createValidator()`, `createProcessor()`, `createNotifier()`)
- **Step 4 — concrete factories**: `UpiRailFactory`, `CardRailFactory` — each produces exactly **one** consistent family
- **Step 5 — client**: `TransactionHandler` takes a single `PaymentRailFactory` in its constructor and asks it for all three products — never names a concrete class

---

### 4. The Key Guarantee

- Mixing families is now **structurally impossible**, not just discouraged — `TransactionHandler` only ever asks **one** factory for all three objects
- Each concrete factory only ever produces its own family, so the design itself — not programmer discipline — prevents the mismatch bug from §2
- Picking the family becomes **one decision** (`new UpiRailFactory()`), not three independent ones that could drift out of sync

---

### 5. Factory Method vs Abstract Factory — Side By Side

| | Factory Method | Abstract Factory |
| --- | --- | --- |
| Produces | One product | A family of related products |
| Structure | One creation method | An interface with multiple creation methods, one per product type |
| Guarantees | "You get *some* implementation of X" | "You get a **consistent set** of X, Y, Z that belong together" |
| Example | `ShapeFactory.createShape("circle")` → `Shape` | `UpiRailFactory` → matching `Validator` + `Processor` + `Notifier` |

- Mnemonic: Abstract Factory is **"a factory of factories"** — each `createX()` on the interface is individually just a Factory Method; Abstract Factory bundles several of them into one interface so they're always used as a matched set

---

### 6. Real JDK Example

- `DocumentBuilderFactory.newInstance()` is a genuine Abstract Factory
- Depending on the XML parser implementation on the classpath, it produces a whole family of matching objects (`DocumentBuilder`, and internally consistent `Document`/`Node` implementations)
- Caller never references a specific parser vendor's classes directly

---

### 7. Mapping To Spring

- `@Profile`-scoped `@Configuration` classes (`UpiRailConfig`, `CardRailConfig`) each declaring `Validator`/`Processor`/`Notifier` beans express the same guarantee declaratively
- Only one `@Profile` is active at a time → Spring's container **is** the Abstract Factory here, injecting the whole consistent family with zero hand-written factory interface
- Good interview line: *"I've used Abstract-Factory-like guarantees via Spring profiles grouping related beans, rather than hand-writing the classic GoF interface"*

---

### 8. When To Actually Use It

- **Good fit**: multiple families of related objects (payment rails, cloud provider SDK wrappers, UI themes) that must always be used together, and you want to swap the **entire family** in one place
- **Overkill**: only one type of object needs creating — that's plain Factory Method; adding a family interface for a single product is unnecessary layering (KISS/YAGNI, see [[12. SOLID And Design Principles]])

---

### SDE-2 Interview Priority

**Must Know**: Factory Method vs Abstract Factory distinction, the mismatch bug it structurally prevents, the 5-step construction (product interfaces → concrete products → abstract factory interface → concrete factories → client depending only on the interface)

**Nice To Know**: "factory of factories" framing, `DocumentBuilderFactory` as a real JDK example, when it's overkill vs a plain Factory Method

**Advanced**: Spring `@Profile`-based config classes as an implicit Abstract Factory, swapping an entire family via one factory/profile selection instead of N independent factory calls

# Detailed Explanation

---

## The Core Idea

Abstract Factory provides an interface for creating **families of related objects**, without the client ever naming their concrete classes. The distinction from plain Factory Method (see [[1. Types of Design Patterns]]) is the one line worth memorizing: Factory Method produces **one product**; Abstract Factory produces a **whole family of related products** and guarantees they all come from the same family — never an accidental mix of a UPI object with a Card object.

"Family" here means: a set of objects that must always be used **together, consistently**. The pattern's entire value proposition is turning "please remember to keep these three in sync" into "it is impossible to get these three out of sync."

---

## The Problem It Solves

Consider a UPI Switch supporting multiple payment rails — UPI and Card — where each rail needs its own `Validator`, `Processor`, and `Notifier`, and the three must always be used together, per rail.

```java
class UpiValidator implements Validator { }
class UpiProcessor implements Processor { }
class UpiNotifier  implements Notifier  { }

class CardValidator implements Validator { }
class CardProcessor implements Processor { }
class CardNotifier  implements Notifier  { }
```

```java
void handleTransaction(String rail) {
    Validator validator = rail.equals("UPI") ? new UpiValidator() : new CardValidator();
    Processor processor = new CardProcessor();   // ❌ BUG — should've been UpiProcessor when rail == "UPI"
    Notifier notifier = rail.equals("UPI") ? new UpiNotifier() : new CardNotifier();
    // nothing stops mixing a UpiValidator with a CardProcessor — pure programmer discipline required
}
```

Nothing in the type system prevents combining a `UpiValidator` with a `CardProcessor`. This is a real, easy-to-introduce bug, and it only gets more likely as the number of rails and object types grows — three independent `equals()` checks that are supposed to agree, but aren't enforced to.

---

## Building The Solution

**Step 1 — define the family of products as interfaces:**

```java
interface Validator { void validate(double amount); }
interface Processor { void process(double amount); }
interface Notifier  { void notify(String message); }
```

**Step 2 — concrete products, grouped by family:**

```java
// UPI family
class UpiValidator implements Validator {
    public void validate(double amount) { System.out.println("UPI validation: " + amount); }
}
class UpiProcessor implements Processor {
    public void process(double amount) { System.out.println("UPI processing: " + amount); }
}
class UpiNotifier implements Notifier {
    public void notify(String message) { System.out.println("UPI SMS: " + message); }
}

// Card family
class CardValidator implements Validator {
    public void validate(double amount) { System.out.println("Card validation: " + amount); }
}
class CardProcessor implements Processor {
    public void process(double amount) { System.out.println("Card processing: " + amount); }
}
class CardNotifier implements Notifier {
    public void notify(String message) { System.out.println("Card email: " + message); }
}
```

**Step 3 — the Abstract Factory interface, one creation method per product type in the family:**

```java
interface PaymentRailFactory {
    Validator createValidator();
    Processor createProcessor();
    Notifier createNotifier();
}
```

**Step 4 — concrete factories, each producing exactly one consistent family:**

```java
class UpiRailFactory implements PaymentRailFactory {
    public Validator createValidator() { return new UpiValidator(); }
    public Processor createProcessor() { return new UpiProcessor(); }
    public Notifier createNotifier()   { return new UpiNotifier();  }
}

class CardRailFactory implements PaymentRailFactory {
    public Validator createValidator() { return new CardValidator(); }
    public Processor createProcessor() { return new CardProcessor(); }
    public Notifier createNotifier()   { return new CardNotifier();  }
}
```

**Step 5 — client code depends only on the abstract factory, never on a concrete class:**

```java
class TransactionHandler {
    private final Validator validator;
    private final Processor processor;
    private final Notifier notifier;

    TransactionHandler(PaymentRailFactory factory) {   // gets a FAMILY, guaranteed consistent
        this.validator = factory.createValidator();
        this.processor = factory.createProcessor();
        this.notifier  = factory.createNotifier();
    }

    void handle(double amount) {
        validator.validate(amount);
        processor.process(amount);
        notifier.notify("Transaction of " + amount + " completed");
    }
}
```

```java
PaymentRailFactory factory = new UpiRailFactory();   // pick ONE factory — the whole family arrives together
TransactionHandler handler = new TransactionHandler(factory);
handler.handle(500);

// Output:
// UPI validation: 500.0
// UPI processing: 500.0
// UPI SMS: Transaction of 500.0 completed
```

---

## The Key Guarantee

It is now **structurally impossible** to mix a `UpiValidator` with a `CardProcessor`, because `TransactionHandler` only ever asks **one** factory for all three objects, and each concrete factory only ever produces its own family. The design itself — not programmer discipline — prevents the mismatch bug from the previous section. Choosing the rail becomes one decision (which factory to instantiate), rather than three independent `equals()` checks that have to happen to agree.

---

## Factory Method vs Abstract Factory — Side By Side

| | Factory Method | Abstract Factory |
| --- | --- | --- |
| Produces | One product | A family of related products |
| Structure | One factory method, often on a single factory class or an overridable method in a base class | An interface with **multiple** creation methods, one per product type in the family |
| Guarantees | Just "you get some implementation of X" | "You get a **consistent set** of X, Y, Z that belong together" |
| Example | `ShapeFactory.createShape("circle")` → returns a `Shape` | `UpiRailFactory` → returns matching `Validator` + `Processor` + `Notifier`, all UPI-specific |

A useful way to remember it: Abstract Factory is often described as **"a factory of factories"**, or more precisely, a factory whose products are individually just Factory Method results — each `createX()` on the abstract factory interface is, on its own, a Factory Method. Abstract Factory is the pattern of **bundling several Factory Methods together** into one cohesive interface so they're always used as a matched set.

---

## Real JDK Example

```java
DocumentBuilderFactory factory = DocumentBuilderFactory.newInstance();   // Abstract Factory
DocumentBuilder builder = factory.newDocumentBuilder();                 // consistent with the chosen XML implementation
```

`DocumentBuilderFactory` is a genuine Abstract Factory in the JDK: depending on which XML parser implementation is on the classpath, it produces a whole family of matching, compatible XML-processing objects (`DocumentBuilder`, and internally consistent `Document`/`Node` implementations) without the caller ever referencing a specific parser vendor's classes.

---

## Mapping To Spring

Spring's `@Profile`-based bean families express the same guarantee declaratively, without hand-writing a factory interface at all:

```java
@Configuration
@Profile("upi")
class UpiRailConfig {
    @Bean Validator validator() { return new UpiValidator(); }
    @Bean Processor processor() { return new UpiProcessor(); }
    @Bean Notifier notifier()   { return new UpiNotifier();  }
}

@Configuration
@Profile("card")
class CardRailConfig {
    @Bean Validator validator() { return new CardValidator(); }
    @Bean Processor processor() { return new CardProcessor(); }
    @Bean Notifier notifier()   { return new CardNotifier();  }
}
```

```java
@Service
class TransactionHandler {
    private final Validator validator;   // Spring injects the CONSISTENT family based on the active profile
    private final Processor processor;
    private final Notifier notifier;

    TransactionHandler(Validator validator, Processor processor, Notifier notifier) {
        this.validator = validator;
        this.processor = processor;
        this.notifier = notifier;
    }
}
```

Spring's container **is** the Abstract Factory here — activating the `"upi"` profile guarantees the entire UPI-consistent family gets injected together, with zero risk of wiring a `CardProcessor` alongside a `UpiValidator`, since only one `@Profile` config class is active at a time.

> 💡 **Interview**: "Have you used Abstract Factory in real work?" → Implicitly, via Spring profiles and `@Configuration` classes that group related beans — rather than hand-writing the classic GoF interface. Activating one profile is the equivalent of selecting one concrete factory.

---

## When To Actually Use Abstract Factory

**Good fit when:**

- There are **multiple families** of related objects (different payment rails, different cloud provider SDK wrappers, different UI themes/toolkits) that must always be used together as a consistent set.
- You want to swap the **entire family** in one place — one factory selection — rather than juggling multiple independent factory calls that could drift out of sync.

**Overkill when:**

- Only **one** type of object ever needs creating — that's a plain Factory Method; adding the family-interface layer for a single product is unnecessary complexity. This is the same KISS/YAGNI judgment call from [[12. SOLID And Design Principles]]: don't build the "family" abstraction until there's actually more than one related product that needs to travel together.

**Interview-ready summary line**: *"Abstract Factory extends the basic Factory idea from producing one object to producing a whole family of related objects, guaranteeing they're always compatible with each other — like a Validator, Processor, and Notifier that must all belong to the same payment rail. It trades a bit of extra structure for eliminating an entire class of 'mismatched object' bugs that plain factories can't prevent."*
