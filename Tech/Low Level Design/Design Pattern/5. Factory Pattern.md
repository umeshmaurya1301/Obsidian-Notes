# Factory Pattern

---

## Short Notes

---

### 1. The Problem It Solves

- Object creation sometimes involves **decision logic** — which concrete class to instantiate depends on an input/condition
- Without a factory, that `if-else`/`switch` creation logic lives directly in client code, which then references **every** concrete class
- Violates **DIP**: a high-level class (`TransactionHandler`) depends on low-level details (`UpiPayment`, `CardPayment`, ...) — see [[12. SOLID And Design Principles]]
- Violates **DRY**: the same creation `if-else` tends to get duplicated wherever a `PaymentMethod` is needed
- Violates **OCP**: adding a new payment type means **editing** the existing creation method

---

### 2. The Factory Solution

- **Definition**: encapsulate object-creation logic in one dedicated class/method — client code asks for an object **by intent**, without knowing which concrete class gets instantiated
- `PaymentMethodFactory.create("UPI")` — one static method, one `switch`, returns the `PaymentMethod` interface
- Client (`TransactionHandler`) now references only the `PaymentMethod` interface and the factory — never a concrete class → DIP restored
- Creation logic lives in **exactly one place** — a new type or a changed creation rule (e.g. a config lookup) means editing the factory only, not every call site

---

### 3. Two Common Flavors Of "Factory"

- **Simple Factory** (what most people mean casually): one class, one static/instance method, `if-else`/`switch` on input — **not** one of the 23 official GoF patterns, but the most commonly used in practice
- **Factory Method** (the actual GoF pattern): each subclass **overrides a creation method** to decide what gets created — polymorphism replaces the conditional entirely
- Factory Method reuses the **Template Method** shape: a fixed skeleton method (`execute()`) calls an abstract "factory method" (`createPayment()`) that subclasses fill in
- Adding a type under Factory Method = **new subclass**, zero edits to existing code — true OCP; Simple Factory still requires editing the `switch`

---

### 4. Simple Factory vs Factory Method — Side By Side

| | Simple Factory | Factory Method |
| --- | --- | --- |
| Mechanism | One method, `if-else`/`switch` on a parameter | Abstract method, overridden per subclass |
| Adding a new type | Edit the existing factory method (mild OCP violation) | Add a new subclass (true OCP — no existing code touched) |
| Structure | One factory class | A class hierarchy, each with its own creation logic |
| Complexity | Simple, minimal boilerplate | More classes, more structure |
| When to use | Small, stable set of types; simplicity matters more than strict OCP | Growing/plugin-style set of types; strict OCP compliance matters |

- **In practice**: most real codebases reach for **Simple Factory** far more often — a `switch` over a handful of known payment types is perfectly reasonable
- Factory Method's extra class hierarchy earns its cost mainly in genuine plugin architectures — new types added frequently by different teams without touching shared code

---

### 5. Real JDK Examples

- `Calendar.getInstance()` — Simple Factory, returns a `GregorianCalendar` or locale-specific subclass internally
- `NumberFormat.getInstance()` — returns a different concrete formatter based on locale/config
- `List.of("a", "b")` — returns an internal, unnamed `List` implementation the caller never needs to know
- The pattern in one line: **program to the interface, let the factory pick the implementation**

---

### 6. Factory vs Abstract Factory — Quick Recap

| | Factory | Abstract Factory |
| --- | --- | --- |
| Produces | One product | A family of related products, guaranteed consistent |
| Example | `PaymentMethodFactory.create("UPI")` → one `PaymentMethod` | `UpiRailFactory` → matching `Validator` + `Processor` + `Notifier` |

- Abstract Factory (see [[3. Abstract Factory Pattern]]) is "several Factory Methods bundled into one interface" — same mental model, one level up

---

### 7. Connection To Spring Boot

- `context.getBean(PaymentMethod.class)` — `ApplicationContext` itself **is a Factory**: you ask by type/name, the container decides the concrete implementation via `@Profile`/`@Qualifier`/config
- A `@Bean`-annotated method inside `@Configuration` **is, structurally, a Factory Method** — Spring calls it to create the bean, exactly like `createPayment()` above
- Day-to-day Spring work uses Factory constantly without ever hand-rolling the classic GoF static-method class

---

### 8. When To Use Factory

- **Good fit**: object creation involves conditional logic on input/config, you want to hide concrete classes from clients (DIP), or creation logic might grow/change and needs one place to live
- **Skip it**: only one concrete implementation ever exists, or `new SomeClass()` directly is already clear and unlikely to vary — a Factory here is unnecessary indirection (KISS/YAGNI, see [[12. SOLID And Design Principles]])

---

### SDE-2 Interview Priority

**Must Know**: the DIP/DRY/OCP violations plain conditional creation causes, Simple Factory structure, Factory Method structure (abstract creation method overridden per subclass), the OCP distinction between the two flavors

**Nice To Know**: Factory Method as a special case of Template Method, `Calendar.getInstance()`/`List.of()` as JDK examples, Spring `@Bean` methods and `ApplicationContext.getBean()` as Factory mechanisms

**Advanced**: when Factory Method's extra class hierarchy is actually worth it (plugin architectures) vs when Simple Factory is the pragmatic choice, Factory vs Abstract Factory distinction, when a Factory is unneeded indirection (KISS/YAGNI)

# Detailed Explanation

---

## The Problem It Solves

Object creation sometimes involves decision logic — which concrete class to instantiate depends on some input or condition. Left unmanaged, that decision logic scatters across the codebase and tightly couples client code to every concrete class it might need.

```java
interface PaymentMethod {
    void process(double amount);
}

class UpiPayment implements PaymentMethod {
    public void process(double amount) { System.out.println("Processing UPI: " + amount); }
}

class CardPayment implements PaymentMethod {
    public void process(double amount) { System.out.println("Processing Card: " + amount); }
}

class NetBankingPayment implements PaymentMethod {
    public void process(double amount) { System.out.println("Processing NetBanking: " + amount); }
}
```

```java
class TransactionHandler {
    void handle(String type, double amount) {
        PaymentMethod payment;
        if (type.equals("UPI")) {
            payment = new UpiPayment();
        } else if (type.equals("CARD")) {
            payment = new CardPayment();
        } else if (type.equals("NETBANKING")) {
            payment = new NetBankingPayment();
        } else {
            throw new IllegalArgumentException("Unknown type");
        }
        payment.process(amount);
    }
}
```

Three concrete problems with this:

- **DIP violation** — `TransactionHandler`, a high-level module, directly depends on every low-level concrete class (`UpiPayment`, `CardPayment`, `NetBankingPayment`). See [[12. SOLID And Design Principles]].
- **DRY violation** — this same `if-else` creation logic is likely to get duplicated wherever else a `PaymentMethod` needs to be built.
- **OCP violation** — adding a new payment type means *modifying* this method, touching code that's already tested and in production.

---

## The Factory Solution

**Definition**: encapsulate object-creation logic in a single dedicated class or method, so client code asks the factory for an object **by intent**, without knowing or caring which concrete class actually gets instantiated.

```java
class PaymentMethodFactory {
    static PaymentMethod create(String type) {
        return switch (type) {
            case "UPI" -> new UpiPayment();
            case "CARD" -> new CardPayment();
            case "NETBANKING" -> new NetBankingPayment();
            default -> throw new IllegalArgumentException("Unknown payment type: " + type);
        };
    }
}
```

```java
class TransactionHandler {
    void handle(String type, double amount) {
        PaymentMethod payment = PaymentMethodFactory.create(type);   // just ASKS for what it needs
        payment.process(amount);
    }
}
```

What improved:

- `TransactionHandler` no longer references `UpiPayment`, `CardPayment`, or `NetBankingPayment` at all — it only knows the `PaymentMethod` interface and the factory. This is DIP in action.
- The creation logic exists in **exactly one place** — a new payment type, or a change to how creation works (e.g. needing a config lookup), means editing `PaymentMethodFactory` only, never every call site.
- Every other class that needs a `PaymentMethod` reuses the same factory — no duplicated `if-else` chains anywhere else.

---

## Two Common Flavors Of "Factory"

### a) Simple Factory (what's shown above)

A single class with a static (or instance) method that returns different concrete types based on input. Technically not one of the 23 official GoF patterns — it's a widely-used simplification — but it's what most people mean when they casually say "Factory pattern."

### b) Factory Method (the actual GoF pattern)

Instead of one static method with an `if-else`/`switch`, each subclass **overrides a creation method** to decide what gets created — polymorphism does the branching instead of conditionals.

```java
abstract class PaymentProcessorTemplate {
    void execute(double amount) {
        PaymentMethod payment = createPayment();   // Factory Method — subclasses decide WHAT gets created
        payment.process(amount);
    }

    abstract PaymentMethod createPayment();          // the "factory method"
}

class UpiProcessorTemplate extends PaymentProcessorTemplate {
    PaymentMethod createPayment() { return new UpiPayment(); }
}

class CardProcessorTemplate extends PaymentProcessorTemplate {
    PaymentMethod createPayment() { return new CardPayment(); }
}
```

```java
PaymentProcessorTemplate processor = new UpiProcessorTemplate();
processor.execute(500);   // internally calls createPayment() → gets a UpiPayment, polymorphically
```

**Key difference from Simple Factory**: no `if-else`/`switch` anywhere. Adding a new payment type means adding a **new subclass** (`NetBankingProcessorTemplate`) — zero changes to any existing class. This is pure OCP: extension via new subclasses, no modification of existing code at all.

Notice this also directly reuses the **Template Method** pattern structure: `execute()` is the fixed skeleton, `createPayment()` is the customizable step. Factory Method is very often implemented as a special case of Template Method — the "template" here just happens to be a single step whose entire job is object creation.

---

## Simple Factory vs Factory Method — Side By Side

| | Simple Factory | Factory Method |
| --- | --- | --- |
| Mechanism | One method, `if-else`/`switch` on a parameter | Abstract method, overridden per subclass |
| Adding a new type | Edit the existing factory method (violates OCP, mildly) | Add a new subclass (true OCP — no existing code touched) |
| Structure | One factory class | A class hierarchy, each with its own creation logic |
| Complexity | Simple, minimal boilerplate | More classes, more structure |
| When to use | Small, stable set of types; simplicity matters more than strict OCP | Growing/plugin-style set of types; strict OCP compliance matters |

In practice, most real codebases use **Simple Factory** far more often — it's simpler, and a `switch` statement over a handful of known payment types is perfectly reasonable. Factory Method's extra class hierarchy tends to be worth it only when new types are added *frequently*, by *different teams/modules*, without touching shared code — a genuine plugin architecture.

> 💡 **Interview**: "When would you pick Factory Method over Simple Factory?" → When new types are added often enough, by different owners, that editing a shared `switch` every time becomes the actual bottleneck — Factory Method turns "add a case" into "add a class," touching zero existing code. For a small, stable set of types, Simple Factory's `switch` is simpler and equally correct.

---

## Real JDK Examples

```java
Calendar cal = Calendar.getInstance();          // Simple Factory — returns a GregorianCalendar (or locale-specific subclass) internally
NumberFormat nf = NumberFormat.getInstance();   // returns a different concrete formatter based on locale/config
List<String> list = List.of("a", "b");          // returns an internal, unnamed List implementation — caller doesn't know/care which
```

The caller never knows — or needs to know — the exact concrete class `Calendar.getInstance()` returns; it just gets back something that satisfies the `Calendar` contract. That's the entire point of Factory: **program to the interface, let the factory pick the implementation.**

---

## Factory vs Abstract Factory — Quick Recap

| | Factory | Abstract Factory |
| --- | --- | --- |
| Produces | One product | A family of related products, guaranteed consistent |
| Example | `PaymentMethodFactory.create("UPI")` → one `PaymentMethod` | `UpiRailFactory` → matching `Validator` + `Processor` + `Notifier` |

Abstract Factory (see [[3. Abstract Factory Pattern]]) is essentially "several Factory Methods bundled into one interface" — the same mental model as this note, extended to a whole family of products that must arrive together.

---

## Connection To Spring Boot

Spring's `ApplicationContext.getBean()` is itself a Factory — you ask for a bean by type/name, and the container decides which concrete implementation to hand back, based on configuration (`@Profile`, `@Qualifier`, XML/Java config):

```java
PaymentMethod payment = context.getBean(PaymentMethod.class);   // Factory — caller doesn't know/care which concrete bean it is
```

This is also why `@Configuration` classes with `@Bean` methods are, structurally, Factory Methods:

```java
@Configuration
class PaymentConfig {
    @Bean
    PaymentMethod paymentMethod() {   // this IS a factory method — Spring calls it to CREATE the bean
        return new UpiPayment();
    }
}
```

## When To Use Factory

**Good fit when:**

- Object creation involves conditional logic based on input/config.
- You want to hide concrete implementation classes from client code (DIP).
- Creation logic might change or grow over time, and a single place to manage it is valuable.

**Skip it when:**

- There's only ever one concrete implementation, or `new SomeClass()` directly is already clear and unlikely to need to vary — adding a Factory here is unnecessary indirection (KISS/YAGNI, see [[12. SOLID And Design Principles]]).

**Interview-ready summary line**: *"Factory encapsulates object-creation decisions in one place, so client code depends on an interface rather than concrete classes — that's DIP in practice. Simple Factory uses a conditional inside one method; Factory Method pushes that decision into subclasses via polymorphism for stricter OCP compliance. In Spring, `@Bean` methods and `ApplicationContext.getBean()` are factory mechanisms I use constantly without necessarily hand-rolling the classic GoF structure myself."*
