# Singleton Pattern

---

## Short Notes

---

### 1. What It Is And Why

- **Definition**: ensures a class has **exactly one instance** for the app's lifetime, with a **global access point** to it
- Genuine use cases: `ConfigManager`, connection pool, logging registry, cache manager — things where a second instance means wasted resources or inconsistent shared state
- Classic failure mode it prevents: two separate connection pools independently fighting over the same limited DB connections
- Three requirements for any Singleton: **private constructor**, a **static field** holding the instance, a **static `getInstance()`** that returns/creates it

---

### 2. Approach 1 — Eager Initialization

- Instance created **at class-loading time**, via `private static final ConfigManager instance = new ConfigManager();`
- Thread-safe **for free** — JVM class loading is itself guaranteed thread-safe
- Downside: instance is built **whether or not it's ever used** — wasteful if construction is expensive and some runs never touch it

---

### 3. Approach 2 — Naive Lazy Initialization (Broken)

- `if (instance == null) instance = new ConfigManager();` — only builds on first actual use
- **Broken under concurrency**: two threads can both pass the `null` check before either finishes assigning — **two instances get created**, singleton contract violated
- Classic textbook race condition — never acceptable in any multi-threaded code (i.e. essentially all backend/Spring Boot code)

---

### 4. Approach 3 — Synchronized Method (Correct, Slow)

- Marks `getInstance()` itself `synchronized` — only one thread can execute it at a time
- Fixes the race correctly, but pays **lock overhead on every single call, forever** — including call #1,000,000, long after the instance already exists
- Wasteful in a hot path (e.g. `getInstance()` on every incoming transaction in a UPI switch)

---

### 5. Approach 4 — Double-Checked Locking (Correct AND Fast)

- Two `null` checks: an outer one **without** a lock (fast path once initialized), an inner one **inside** `synchronized` (closes the race)
- `volatile` on the instance field is **mandatory**, not optional — without it, another thread can observe a **partially-constructed object** due to JMM instruction reordering (see [[3. Synchronization]] on `volatile`/happens-before)
- Pre-Java-5 double-checked locking (before `volatile` semantics were strengthened) is a documented historically-broken pattern — a frequently tested subtlety

---

### 6. Approach 5 — Bill Pugh (Static Holder)

- Instance lives inside a `private static class Holder`, which the JVM doesn't load until `Holder.INSTANCE` is first referenced
- Lazy **and** thread-safe with **zero explicit `synchronized`/`volatile`** — relies on the JVM's guarantee that class initialization happens exactly once
- Zero ongoing lock cost after the first call — considered the best classic (pre-enum) Singleton implementation

---

### 7. Approach 6 — Enum Singleton (Joshua Bloch's Pick)

- `enum ConfigManager { INSTANCE; ... }` — thread-safe the same way Bill Pugh is, with far less boilerplate
- **Serialization-safe automatically**: a normal class's deserialization bypasses the private constructor via reflection and silently creates a second instance; enum deserialization always returns the existing constant
- **Reflection-attack-proof automatically**: `constructor.setAccessible(true)` can force-instantiate a normal private constructor; the JVM explicitly forbids reflective instantiation of enums
- Trade-off: an enum can't `extend` another class — rarely matters for config/cache/registry use cases

---

### 8. Comparison Of Approaches

| Approach | Lazy? | Thread-safe? | Perf after 1st call | Serialization-safe? | Reflection-safe? |
| --- | --- | --- | --- | --- | --- |
| Eager | No | Yes (class loading) | Best | No | No |
| Naive lazy | Yes | **No — broken** | N/A | No | No |
| Synchronized method | Yes | Yes | Poor (lock every call) | No | No |
| Double-checked locking | Yes | Yes (needs `volatile`) | Good | No | No |
| Bill Pugh (holder) | Yes | Yes | Best | No | No |
| **Enum** | Yes | Yes | Best | **Yes** | **Yes** |

---

### 9. Singleton In Spring Boot

- `@Service`/`@Component` beans are **singleton-scoped by default** — the IoC container creates exactly one instance and injects that same instance everywhere it's `@Autowired`
- This is Spring's own container-managed implementation of the pattern — same guarantee, no hand-written `getInstance()`
- Interview-honest answer to "have you used Singleton?": *rely on Spring's default singleton bean scope; hand-rolled singletons are for cases outside DI-framework control* (a static utility/cache in a non-Spring context, or an LLD exercise testing the pattern itself)

---

### 10. When To Use It, And The Anti-Pattern Criticism

- Good fits: logging frameworks, config/settings objects, connection pool managers, cache managers — shared cross-cutting state/resources that should genuinely be singular
- Overuse criticism: introduces **global mutable state**, harder to reason about and test — shared instance can leak state between tests
- Hides dependencies: `ConfigManager.getInstance()` inside a class is an invisible dependency, not declared in its constructor — unlike DIP-style constructor injection (see [[12. SOLID And Design Principles]]) which is explicit and mockable
- This is exactly why Spring's DI-managed singleton beans beat hand-rolled ones: same "one shared instance" benefit, dependencies stay explicit and swappable for mocks

---

# Detailed Explanation

---

## What It Is And Why

Singleton ensures a class has **exactly one instance** for the entire application lifetime, with a global access point to reach it. The motivating cases are things that genuinely should exist only once: a `ConfigManager`, a connection pool, a logging registry, a cache manager. Creating a second instance of any of these isn't just wasteful — it's actively wrong: two separate connection pools would independently compete over the same limited set of database connections, each unaware the other exists, and two configuration managers could disagree about a setting depending on which one a given class happened to receive.

Every Singleton implementation, regardless of approach, rests on the same three mechanical requirements:

1. A **private constructor** — blocks `new ConfigManager()` from outside the class.
2. A **static field** holding the one instance.
3. A **static accessor** (conventionally `getInstance()`) that returns that instance, creating it on demand if needed.

Everything that follows is really six different answers to one question: *when and how safely does step 3 create the instance?*

---

## Approach 1 — Eager Initialization

```java
class ConfigManager {
    private static final ConfigManager instance = new ConfigManager(); // created at class-loading time

    private ConfigManager() {
        System.out.println("ConfigManager created");
    }

    public static ConfigManager getInstance() {
        return instance;
    }
}
```

```java
ConfigManager c1 = ConfigManager.getInstance();
ConfigManager c2 = ConfigManager.getInstance();
System.out.println(c1 == c2);      // ✅ true — same object
// new ConfigManager();            // ❌ compile error — constructor is private
```

The instance is built the moment the JVM loads the class — static field initialization happens during class loading, and the JVM guarantees class loading is thread-safe, so this approach is correct with zero locking code. The cost is that the instance is created **unconditionally**, even in a run of the application that never calls `getInstance()` at all — wasteful if construction does real work (opens a file, makes a network call).

---

## Approach 2 — Naive Lazy Initialization (Not Thread-Safe)

```java
class ConfigManager {
    private static ConfigManager instance;

    private ConfigManager() { }

    public static ConfigManager getInstance() {
        if (instance == null) {
            instance = new ConfigManager();   // only created on first actual use
        }
        return instance;
    }
}
```

This defers construction until first use — better, in principle. But it is **broken the moment two threads call it concurrently**:

```text
Thread A: checks "instance == null" → true → about to create
Thread B: checks "instance == null" → ALSO true (A hasn't finished yet) → about to create
Both threads construct a ConfigManager — TWO instances now exist. Singleton contract broken.
```

This is the textbook race condition: both threads can pass the `null` check before either finishes the assignment. Since virtually all backend/Spring Boot code is multi-threaded (a servlet container handles concurrent requests), this version should never appear in real code — it exists in the progression purely to motivate the next three approaches.

---

## Approach 3 — Synchronized Method (Correct, Slow)

```java
class ConfigManager {
    private static ConfigManager instance;

    private ConfigManager() { }

    public static synchronized ConfigManager getInstance() {   // only one thread at a time
        if (instance == null) {
            instance = new ConfigManager();
        }
        return instance;
    }
}
```

`synchronized` on the method serializes every call, so the null-check-then-create sequence can never be interleaved between two threads — the race is fully closed.

The cost is that **every** call acquires the lock, forever — call #1 and call #1,000,000 pay identical locking overhead, even though the instance has existed since call #1 finished and there is zero remaining race to protect against. In a hot path — `getInstance()` invoked on every incoming transaction in a payment switch — that's contention and context-switching overhead paid for no benefit after the very first call.

---

## Approach 4 — Double-Checked Locking (Correct AND Fast)

```java
class ConfigManager {
    private static volatile ConfigManager instance;   // volatile is CRITICAL — see below

    private ConfigManager() { }

    public static ConfigManager getInstance() {
        if (instance == null) {                            // outer check — no lock, fast path
            synchronized (ConfigManager.class) {
                if (instance == null) {                      // inner check — inside the lock, closes the race
                    instance = new ConfigManager();
                }
            }
        }
        return instance;
    }
}
```

**Why two checks:**

- **Outer check (no lock)** — once the instance exists, every subsequent call sees `instance != null` and returns immediately without ever touching `synchronized`. This is the performance win over Approach 3 for the overwhelming majority of calls.
- **Inner check (locked)** — if two threads both pass the outer check simultaneously (both observed `null` before either finished creating), only one can enter the `synchronized` block at a time. The first to enter creates the instance; the second, now inside the lock, re-checks and sees `instance` is no longer `null`, so it skips creation entirely.

**Why `volatile` is not optional here.** Object construction is not a single atomic step from another thread's point of view — conceptually it's (1) allocate memory, (2) run the constructor to initialize fields, (3) assign the reference to `instance`. The Java Memory Model permits the compiler/JVM to **reorder** these steps for optimization, and specifically allows step 3 to become visible to another thread before step 2 has finished:

```java
// Without volatile — a second thread could observe:
if (instance == null) {      // false — instance already looks non-null!
    // skips creation
}
return instance;              // returns a reference to a PARTIALLY CONSTRUCTED object
```

`volatile` establishes a **happens-before** relationship (see [[3. Synchronization]]) that forbids exactly this reordering — it guarantees that by the time any thread observes `instance` as non-null, the object it points to is fully and correctly constructed. This is one of the most subtle, most frequently tested concurrency details in Java: the original pre-Java-5 double-checked-locking idiom, written *without* `volatile`, is a documented **broken pattern** in Java literature — `volatile`'s semantics were specifically strengthened in Java 5 to make this idiom correct.

> 💡 **Interview**: "Why does double-checked locking need `volatile`?" → Without it, the JVM can reorder the constructor call and the reference assignment, letting a second thread see a non-null but partially-constructed instance. `volatile` forbids that reordering via a happens-before edge.

---

## Approach 5 — Bill Pugh Singleton (Static Holder Idiom)

```java
class ConfigManager {
    private ConfigManager() { }

    private static class Holder {                       // NOT loaded until first referenced
        private static final ConfigManager INSTANCE = new ConfigManager();
    }

    public static ConfigManager getInstance() {
        return Holder.INSTANCE;                          // triggers Holder's class loading HERE
    }
}
```

This gets lazy initialization **and** thread safety with no explicit `synchronized` or `volatile` at all, by leaning entirely on a JVM guarantee: a class is initialized exactly once, and if multiple threads trigger that initialization concurrently, the JVM handles the necessary synchronization internally. Because `Holder` is a separate static nested class, it isn't loaded — and `INSTANCE` isn't created — until `getInstance()` is called for the first time, giving true laziness. After that first call, there is no lock check at all on the return path, unlike even the outer check in Approach 4.

This is generally regarded as the best classic (pre-enum) Java Singleton implementation — lazy, correct under concurrency, and zero ongoing synchronization cost.

---

## Approach 6 — Enum Singleton (Effective Java's Recommendation)

```java
enum ConfigManager {
    INSTANCE;

    private Map<String, String> settings = new HashMap<>();

    public void set(String key, String value) { settings.put(key, value); }
    public String get(String key) { return settings.get(key); }
}
```

```java
ConfigManager.INSTANCE.set("env", "production");
System.out.println(ConfigManager.INSTANCE.get("env"));   // "production"
```

*Effective Java* recommends this as the single best approach overall, for three reasons:

1. **Thread safety** — same JVM class-loading guarantee as Bill Pugh, with far less code.
2. **Serialization-safety, automatically.** A normal Singleton class that implements `Serializable` has a hidden hole: deserialization creates a **brand-new object**, bypassing the private constructor entirely via reflection-based object creation — silently producing a second instance and breaking the singleton guarantee. Enums have special JVM-level serialization handling built specifically to prevent this: deserializing an enum constant always returns the **existing** constant, never a new one.
3. **Reflection-attack-proof, automatically.** For a normal class, a private constructor is not actually un-callable:

```java
Constructor<ConfigManager> constructor = ConfigManager.class.getDeclaredConstructor();
constructor.setAccessible(true);                    // bypasses the 'private' restriction
ConfigManager hacked = constructor.newInstance();   // a SECOND instance — singleton broken
```

Enums are immune — the JVM explicitly forbids reflective instantiation of enum types and throws at the attempt.

**The trade-off**: an enum implicitly extends `java.lang.Enum`, and Java has no multiple class inheritance, so an enum Singleton can't `extend` some other base class. This limitation is rarely a real constraint for config managers, caches, and registries.

---

## Comparison Of Approaches

| Approach | Lazy? | Thread-safe? | Perf after 1st call | Serialization-safe? | Reflection-safe? |
| --- | --- | --- | --- | --- | --- |
| Eager | No | Yes (class loading) | Best | No (needs extra work) | No |
| Naive lazy | Yes | **No — broken** | N/A | No | No |
| Synchronized method | Yes | Yes | Poor (lock every call) | No | No |
| Double-checked locking | Yes | Yes (with `volatile`) | Good | No | No |
| Bill Pugh (static holder) | Yes | Yes | Best | No (needs extra work) | No |
| **Enum** | Yes | Yes | Best | **Yes, automatically** | **Yes, automatically** |

The progression from Approach 2 through 6 is really the same story told three times: naive code is broken under concurrency → a lock fixes correctness but costs performance → a smarter check (double-checked locking, or leaning on JVM class-loading guarantees) recovers the performance without losing correctness.

## Singleton In Spring Boot

```java
@Service                              // Spring beans are SINGLETON-scoped by default
class TransactionValidator {
    // the IoC container creates exactly ONE instance of this,
    // and injects the SAME instance everywhere it's @Autowired
}
```

Spring's default bean scope (`singleton`) is Spring's own container-managed implementation of this pattern: one instance, shared everywhere it's injected — but the mechanism is the IoC container's bean lifecycle, not a hand-written private-constructor/static-field class.

This matters for interviews specifically: asked "have you used Singleton in your work," the accurate answer for most Spring Boot engineers is that they rarely hand-write classic Singleton code — they rely on Spring's default singleton bean scope for the same guarantee, managed by the container. Hand-rolled singletons in modern backend Java are mostly reserved for cases **outside** a DI framework's control: a static utility/cache class in a non-Spring-managed context, or an LLD interview exercise specifically testing the pattern itself.

---

## When To Use It, And The Anti-Pattern Criticism

**Good fits**: logging frameworks, configuration/settings objects, connection pool managers, cache managers — anything holding genuinely shared, cross-cutting state or resources where a second instance would be wrong, not just redundant.

**The common criticism** — Singleton is sometimes called an anti-pattern when overused, for two concrete reasons:

- **Global mutable state.** It makes code harder to reason about and test — a shared singleton instance can leak state between unrelated tests if they aren't careful to reset it.
- **Hidden dependencies.** A class that internally calls `ConfigManager.getInstance()` has a dependency that is invisible in its constructor signature — the opposite of the DIP-driven, constructor-injected dependencies covered in [[12. SOLID And Design Principles]], which are explicit and trivially mockable in tests.

This is precisely why Spring's DI-managed singleton beans are considered better engineering practice than hand-rolled `getInstance()` singletons: you keep the "exactly one shared instance" benefit, but the dependency stays explicit — passed through the constructor — and easily swapped for a mock in a unit test, instead of hidden behind a static method call baked into the class's implementation.

> 💡 **Interview**: "Is Singleton an anti-pattern?" → Not inherently — it's correct when a resource genuinely must be singular. It becomes an anti-pattern when it's used as a substitute for dependency injection, hiding a dependency that should have been passed in explicitly and made mockable.
