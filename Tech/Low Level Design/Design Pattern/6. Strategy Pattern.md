# Strategy Pattern

---

## Short Notes

---

### 1. The Core Idea

- **Definition**: define a **family of interchangeable algorithms**, encapsulate each in its own class, make them **swappable at runtime** through a common interface
- **Behavioral** pattern (unlike Singleton/Factory/Builder/Abstract Factory, which are creational, see [[1. Types of Design Patterns]]) — not about *how objects get created*, about **how behavior is selected and varied**
- Already seen twice without the name attached: the `PaymentStrategy` example in [[10. Object Relationships]] (Composition vs Inheritance), and the OCP fix in [[12. SOLID And Design Principles]]

---

### 2. The Problem It Solves

- Conditional dispatch on a type/string baked into one method: `if (method.equals("UPI")) {...} else if (method.equals("CARD")) {...}`
- Violates **OCP** — every new payment method means editing this already-tested method
- Algorithm choice is fixed at compile time in one place — can't be swapped dynamically, configured externally, or unit-tested in isolation
- If the same logic is needed elsewhere (checkout, refunds, recurring billing), the `if-else` chain gets duplicated — violates DRY

---

### 3. Building The Solution

- **Step 1 — strategy interface**: `PaymentStrategy { void pay(double amount); }`
- **Step 2 — one class per algorithm**: `UpiPayment`, `CardPayment`, `WalletPayment`, each implementing `PaymentStrategy`
- **Step 3 — context holds the strategy by composition, not hardcoded**: `Checkout` stores a `PaymentStrategy` field, takes it via constructor, and exposes `setStrategy(...)` to swap it **at runtime**
- `checkout.setStrategy(new CardPayment())` mid-execution — something a compiled-in `if-else` could never do

---

### 4. The Three Participants

| Role | In this example | Responsibility |
| --- | --- | --- |
| **Strategy** (interface) | `PaymentStrategy` | Declares the algorithm's contract |
| **ConcreteStrategy** | `UpiPayment`, `CardPayment`, `WalletPayment` | Each implements one specific algorithm |
| **Context** | `Checkout` | Holds a reference to a `Strategy`, delegates to it, implements none of the algorithm itself |

- Signature to recognize: a class holds an **interface-typed field** and **delegates** one piece of behavior to it, with multiple interchangeable implementations available

---

### 5. Strategy vs Plain `if-else` — When It's Worth It

- **Stick with `if-else`/`switch`**: option set is small and genuinely stable; each branch is a couple of lines, not a real "algorithm"
- **Reach for Strategy**: variant count likely to **grow** (new rails, tiers, discount rules); each variant has enough distinct logic to warrant its own class/tests; behavior needs to swap **at runtime** off config/feature flags; multiple places need the same conditional (Strategy centralizes it once)
- Same KISS/YAGNI judgment as everywhere else — see [[12. SOLID And Design Principles]]

---

### 6. Real JDK Examples

- `Comparator<T>` — textbook Strategy interface; `List.sort()`/`Collections.sort()` is the **Context**, delegating comparison logic to whatever `Comparator` is handed in
- `names.sort(Comparator.reverseOrder())` then `names.sort(String::compareToIgnoreCase)` — swapping strategies on the same context, one a static factory, one a method reference
- Strategy interfaces are usually **functional interfaces** (single abstract method) — Java 8+ lambdas let you skip a named class entirely: `new Checkout(amount -> System.out.println("Paying via UPI: " + amount))`
- Other JDK strategies: `Runnable` ("what code to run"), `ThreadFactory` ("how to create threads"), `FileFilter`/`FilenameFilter` ("which files count")

---

### 7. Real-World Relevance — Fee Calculation

- `FeeCalculationStrategy { double calculateFee(double amount); }` with `UpiFeeStrategy` (0%) and `CardFeeStrategy` (2.5%) as concrete strategies, injected into `TransactionProcessor`
- Any "calculation/validation/routing differs by payment rail, overall flow stays the same" spot — retry logic per rail, validation rules per rail, acquiring-bank routing — is a natural Strategy fit

---

### 8. Strategy + Spring

- Spring can autowire **`Map<String, FeeCalculationStrategy>`** — every bean implementing the interface, keyed by bean name — with zero hand-written `if-else`/`switch` and zero separate factory class
- `strategies.get(rail + "Fee")` picks the strategy dynamically at runtime from the injected map
- A genuinely common, practical interview point: Strategy + DI collapsing into one map lookup

---

### 9. Strategy vs Other Patterns — Disambiguation

| Pattern | Purpose | Key difference from Strategy |
| --- | --- | --- |
| **Strategy** | Swap interchangeable algorithms, same interface, at runtime | — |
| **Template Method** | Fix the algorithm's skeleton, subclasses customize specific steps | Uses **inheritance** (override a step); Strategy uses **composition** (inject a different object) |
| **Factory** | Decide which object to create | Answers "which object do I build?"; Strategy answers "which behavior do I run?" — a Factory is often used *to construct* the right Strategy, see §10 |
| **State** | Swap behavior based on internal state changes over a lifecycle | Structurally similar, but State manages its own transitions (`PENDING → PROCESSING → COMPLETED`); Strategy is usually chosen once by the client and doesn't self-transition |

---

### 10. Strategy + Factory — Why They're Paired

- Strategy answers "which algorithm do I run?"; Factory answers "which object do I construct?" — genuinely different concerns
- But *creating* a Strategy can itself need a conditional (`if UPI, new UpiFeeStrategy()`) — that just relocates the exact `if-else` Strategy was meant to remove
- **Without a Factory**: the conditional creeps back into `TransactionProcessor`, which now does two jobs — deciding *and* processing — a mild SRP violation, duplicated if needed in multiple services
- **Fix**: a Factory constructs the right Strategy; the client that *uses* the Strategy never sees any conditional, for selection or for creation

---

### 11. Factory Handling Creation, Strategy Handling Behavior

- `FeeStrategyFactory.getStrategy(rail)` — the **only** place in the codebase with an `if-else`/`switch` on `rail`
- `TransactionProcessor` becomes one line: `strategy = FeeStrategyFactory.getStrategy(rail)` — no branching visible
- Adding a rail means editing **exactly one place** (the factory); every consumer stays untouched
- Even cleaner variant: factory backed by a pre-built `Map<String, FeeCalculationStrategy>` — no `if-else` at all, just a lookup; safe to share single instances since these strategies are typically stateless

---

### 12. Spring — Factory + Strategy, Container-Managed

- Injecting `Map<String, FeeCalculationStrategy>` (from §8) makes Spring's IoC container **both** the Factory (constructs each `@Component` bean) and the strategy-selection mechanism (map lookup)
- No hand-written `FeeStrategyFactory` class needed at all — the container absorbed that job entirely
- **General principle**: whenever *choosing* which Strategy to use itself needs conditional logic, that logic belongs in a Factory — never inline in the Strategy's consumer

---

### 13. Quick Mental Model

| Question you're answering | Pattern responsible |
| --- | --- |
| "Which class should I instantiate?" | **Factory** |
| "What behavior should run once I have an object?" | **Strategy** |
| "Both, and I don't want conditional logic duplicated" | **Factory constructs the Strategy; client only sees the Strategy interface** |

- Same combination shape recurs elsewhere: `ComparatorFactory.getComparator("byPrice")`, `NotifierFactory.getNotifier("SMS")`, `DiscountStrategyFactory.getStrategy(customerTier)`

---

### SDE-2 Interview Priority

**Must Know**: the OCP/DRY problem plain conditional dispatch causes, the 3-step Strategy build (interface → concrete strategies → context via composition), the 3 participants (Strategy/ConcreteStrategy/Context), `Comparator` as the canonical JDK example, Strategy vs Template Method (composition vs inheritance)

**Nice To Know**: Strategy + Spring via `Map<String, StrategyInterface>` injection, when a plain `if-else` is still fine (KISS/YAGNI), Strategy vs Factory vs State disambiguation

**Advanced**: why pairing Strategy with a Factory prevents the conditional from just relocating, the map-based Factory variant with shared stateless instances, Spring's container acting as both Factory and strategy-selector with zero hand-written factory class

# Detailed Explanation

---

## The Core Idea

Strategy defines a **family of interchangeable algorithms**, encapsulates each one in its own class, and makes them swappable at runtime through a common interface — the client using the algorithm doesn't need to know which specific implementation it's currently working with.

This is a **behavioral** pattern, distinct from the creational patterns already covered ([[2. Singleton Pattern]], [[3. Abstract Factory Pattern]], [[4. Builder Pattern]], [[5. Factory Pattern]]) — it isn't concerned with *how objects get created*, only with *how behavior is selected and varied*. It's also not actually new material: the `PaymentStrategy` example from [[10. Object Relationships]] (Composition vs Inheritance) and the OCP violation-fix in [[12. SOLID And Design Principles]] were both this exact pattern, just not named as such at the time.

---

## The Problem It Solves

```java
class Checkout {
    void processPayment(String method, double amount) {
        if (method.equals("UPI")) {
            System.out.println("Deducting via UPI: " + amount);
            // UPI-specific logic
        } else if (method.equals("CARD")) {
            System.out.println("Charging card: " + amount);
            // Card-specific logic, EMI checks, etc.
        } else if (method.equals("WALLET")) {
            System.out.println("Deducting from wallet: " + amount);
        }
        // adding a new method = editing this method, growing this if-else forever
    }
}
```

Three concrete problems:

- **OCP violation** — every new payment method requires modifying this existing, tested method.
- **Compile-time-fixed choice** — the algorithm selection (`if-else` on a string) is baked into one place; it can't be swapped dynamically, configured externally, or tested in isolation easily.
- **DRY violation** — if this logic is needed in multiple places (checkout, refunds, recurring billing), the same `if-else` chain gets duplicated.

---

## Building The Solution

**Step 1 — define the strategy interface:**

```java
interface PaymentStrategy {
    void pay(double amount);
}
```

**Step 2 — encapsulate each algorithm in its own class:**

```java
class UpiPayment implements PaymentStrategy {
    public void pay(double amount) {
        System.out.println("Deducting via UPI: " + amount);
    }
}

class CardPayment implements PaymentStrategy {
    public void pay(double amount) {
        System.out.println("Charging card: " + amount);
    }
}

class WalletPayment implements PaymentStrategy {
    public void pay(double amount) {
        System.out.println("Deducting from wallet: " + amount);
    }
}
```

**Step 3 — the context class holds a reference to a strategy, composed rather than hardcoded:**

```java
class Checkout {
    private PaymentStrategy strategy;   // composition — the KEY structural element of this pattern

    Checkout(PaymentStrategy strategy) {
        this.strategy = strategy;
    }

    void setStrategy(PaymentStrategy strategy) {   // allows SWAPPING at runtime
        this.strategy = strategy;
    }

    void processPayment(double amount) {
        strategy.pay(amount);   // delegates to whichever strategy is currently set
    }
}
```

```java
Checkout checkout = new Checkout(new UpiPayment());
checkout.processPayment(500);          // "Deducting via UPI: 500.0"

checkout.setStrategy(new CardPayment());   // swap the algorithm AT RUNTIME
checkout.processPayment(1000);         // "Charging card: 1000.0"
```

What improved:

- Adding `NetBankingPayment` requires **zero changes** to `Checkout` or any existing strategy class — just a new class implementing `PaymentStrategy`. Pure OCP.
- Each algorithm lives in its own focused class — easy to test **in isolation** (unit test `UpiPayment` directly, no need to exercise the whole `Checkout` flow).
- `Checkout` doesn't care *how* payment happens, only *that* it happens, via the interface contract — DIP in direct application.
- The strategy can be swapped dynamically **at runtime** — something an `if-else` baked into one method could never do; here the object's behavior changes mid-execution, not just on the next call with a different string.

---

## The Three Participants

| Role | In this example | Responsibility |
| --- | --- | --- |
| **Strategy** (interface) | `PaymentStrategy` | Declares the algorithm's contract |
| **ConcreteStrategy** | `UpiPayment`, `CardPayment`, `WalletPayment` | Each implements one specific algorithm |
| **Context** | `Checkout` | Holds a reference to a `Strategy`, delegates work to it, doesn't implement the algorithm itself |

This three-part shape is the signature of Strategy: if a class holds an interface-typed field and delegates a specific piece of behavior to it, with multiple interchangeable implementations available, that's Strategy — regardless of what it's named in the code.

---

## Strategy vs Plain `if-else` — When The Extra Structure Is Worth It

Not every conditional needs to become Strategy — this connects directly back to KISS/YAGNI.

**Stick with `if-else`/`switch` when:**

- The set of options is small and genuinely stable (unlikely to grow).
- Each branch is a couple of lines, not a meaningfully separate "algorithm."

**Reach for Strategy when:**

- The number of variants is likely to **grow** over time (new payment rails, new pricing tiers, new discount rules).
- Each variant has **enough distinct logic** to warrant its own class and tests.
- The behavior needs to **swap at runtime** based on configuration, user choice, or feature flags — not just at compile time.
- Multiple places in the codebase need the same conditional logic — Strategy centralizes it once, reusably.

---

## Real JDK Examples

```java
List<String> names = new ArrayList<>(List.of("Umesh", "Aarav", "Zara"));

names.sort(new Comparator<String>() {   // Comparator IS a Strategy interface
    public int compare(String a, String b) { return a.length() - b.length(); }
});

names.sort(Comparator.reverseOrder());        // swap in a DIFFERENT strategy, same sort() context
names.sort(String::compareToIgnoreCase);      // yet another strategy, via method reference
```

`Comparator<T>` is a textbook Strategy interface — `Collections.sort()`/`List.sort()` is the **Context**, and it delegates the actual comparison logic to whatever `Comparator` implementation is handed to it. This is exactly why lambdas work so naturally for Strategy: since Strategy interfaces are usually **functional interfaces** (a single abstract method), Java 8+ lets you skip writing a full named class for simple strategies:

```java
Checkout checkout = new Checkout(amount -> System.out.println("Paying via UPI: " + amount));   // lambda AS a strategy
```

Other JDK examples: `Runnable` (a strategy for "what code to run"), `ThreadFactory` (a strategy for "how to create threads"), `FileFilter`/`FilenameFilter` (a strategy for "which files count").

> 💡 **Interview**: "Give a JDK example of Strategy." → `Comparator<T>`: `List.sort()` is the Context, `Comparator` is the Strategy interface, and any custom comparator, `Comparator.reverseOrder()`, or a lambda is a ConcreteStrategy — all interchangeable through the same `sort()` call.

## Real-World Relevance — Fee Calculation

```java
interface FeeCalculationStrategy {
    double calculateFee(double amount);
}

class UpiFeeStrategy implements FeeCalculationStrategy {
    public double calculateFee(double amount) { return 0.0; }              // UPI — typically fee-free
}

class CardFeeStrategy implements FeeCalculationStrategy {
    public double calculateFee(double amount) { return amount * 0.025; }   // 2.5% card fee
}

class TransactionProcessor {
    private final FeeCalculationStrategy feeStrategy;

    TransactionProcessor(FeeCalculationStrategy feeStrategy) {
        this.feeStrategy = feeStrategy;
    }

    double processAndCharge(double amount) {
        double fee = feeStrategy.calculateFee(amount);
        return amount + fee;
    }
}
```

Anywhere "the calculation/validation/routing logic differs based on payment rail, but the overall flow is the same" — retry logic per rail, validation rules per rail, routing logic to different acquiring banks — Strategy is the natural fit.

## Strategy + Spring

```java
interface FeeCalculationStrategy {
    double calculateFee(double amount);
}

@Component("upiFee")
class UpiFeeStrategy implements FeeCalculationStrategy {
    public double calculateFee(double amount) { return 0.0; }
}

@Component("cardFee")
class CardFeeStrategy implements FeeCalculationStrategy {
    public double calculateFee(double amount) { return amount * 0.025; }
}

@Service
class TransactionProcessor {
    private final Map<String, FeeCalculationStrategy> strategies;   // Spring injects ALL implementations, keyed by bean name

    TransactionProcessor(Map<String, FeeCalculationStrategy> strategies) {
        this.strategies = strategies;
    }

    double process(String rail, double amount) {
        FeeCalculationStrategy strategy = strategies.get(rail + "Fee");   // pick strategy dynamically at runtime
        return amount + strategy.calculateFee(amount);
    }
}
```

Spring can autowire a `Map<String, FeeCalculationStrategy>` of every bean implementing that interface, keyed by bean name — a clean, idiomatic way to implement Strategy in a Spring codebase without a manual `if-else`/`switch` anywhere, and without a separate factory class either. This is a genuinely common, practical pattern worth knowing for interviews specifically because it demonstrates Strategy and DI working together elegantly.

---

## Strategy vs Other Patterns — Disambiguation

| Pattern | Purpose | Key difference from Strategy |
| --- | --- | --- |
| **Strategy** | Swap interchangeable algorithms, same interface, chosen/changed at runtime | — |
| **Template Method** | Fix the overall algorithm skeleton, let subclasses customize specific steps | Uses **inheritance** — a subclass overrides steps; Strategy uses **composition** — inject a different implementation |
| **Factory** | Decide which object to create | Factory answers "which object do I build?"; Strategy answers "which behavior do I run?" — a Factory is often used *to construct* the right Strategy object, so they frequently appear together |
| **State** | Swap behavior based on internal state changes over an object's lifecycle | Structurally very similar to Strategy, but State typically manages its own transitions internally (a transaction moving `PENDING → PROCESSING → COMPLETED`, each state having different allowed operations); Strategy is usually chosen once by the client and doesn't self-transition |

---

## Strategy + Factory — Why They're Often Paired

Strategy answers **"which algorithm do I run?"**; Factory answers **"which object do I construct?"** These are genuinely different concerns. But to *use* a Strategy, something has to *create* it first — and if that creation itself involves conditional logic ("if UPI, create `UpiFeeStrategy`; if Card, create `CardFeeStrategy`"), the exact `if-else` problem Strategy was meant to eliminate has simply moved to a different spot.

**The combination**: use a Factory to construct the right Strategy object, so the client code doing the *actual work* never sees any conditional logic at all — not for selecting the algorithm, and not for creating it.

### Without combining them — the conditional creeps back in

```java
class TransactionProcessor {
    double process(String rail, double amount) {
        FeeCalculationStrategy strategy;
        if (rail.equals("UPI")) {              // the if-else is BACK, just relocated here
            strategy = new UpiFeeStrategy();
        } else if (rail.equals("CARD")) {
            strategy = new CardFeeStrategy();
        } else {
            throw new IllegalArgumentException("Unknown rail");
        }
        return amount + strategy.calculateFee(amount);
    }
}
```

`TransactionProcessor` is now doing **two jobs** — deciding which strategy to construct, and doing the actual fee-processing work. That's a mild SRP violation, and if this rail-selection logic is needed in three different services, it gets duplicated three times.

---

## Factory Handling Creation, Strategy Handling Behavior

**Step 1 — the Factory's only job: pick and construct the right Strategy:**

```java
class FeeStrategyFactory {
    static FeeCalculationStrategy getStrategy(String rail) {
        return switch (rail) {
            case "UPI" -> new UpiFeeStrategy();
            case "CARD" -> new CardFeeStrategy();
            case "NETBANKING" -> new NetBankingFeeStrategy();
            default -> throw new IllegalArgumentException("Unknown rail: " + rail);
        };
    }
}
```

**Step 2 — the Context (client) never sees the conditional at all:**

```java
class TransactionProcessor {
    double process(String rail, double amount) {
        FeeCalculationStrategy strategy = FeeStrategyFactory.getStrategy(rail);   // ONE line, no branching visible here
        return amount + strategy.calculateFee(amount);
    }
}
```

What each pattern is doing, precisely:

- **Factory** (`FeeStrategyFactory`) owns the *creation decision* — the only place in the entire codebase with an `if-else`/`switch` on `rail`.
- **Strategy** (`FeeCalculationStrategy` + implementations) owns the *behavior* — each class knows how to calculate its own fee, nothing else.
- **`TransactionProcessor`** does neither — it just asks the factory for a strategy and uses it. Clean separation of "which," "how," and "do."

If a new rail is added, exactly **one place** gets edited (the factory's `switch`) — every `TransactionProcessor`-style consumer stays untouched.

### An even cleaner variant — factory returns based on a lookup, not string comparison

```java
class FeeStrategyFactory {
    private static final Map<String, FeeCalculationStrategy> strategies = Map.of(
        "UPI", new UpiFeeStrategy(),
        "CARD", new CardFeeStrategy(),
        "NETBANKING", new NetBankingFeeStrategy()
    );

    static FeeCalculationStrategy getStrategy(String rail) {
        FeeCalculationStrategy strategy = strategies.get(rail);
        if (strategy == null) throw new IllegalArgumentException("Unknown rail: " + rail);
        return strategy;
    }
}
```

Here the factory isn't doing `if-else` at all — it's a lookup in a pre-built map. Adding a new rail means adding one map entry, not touching a `switch` statement. Since these strategy objects are typically stateless, sharing single instances via the map like this is safe and avoids constructing a new object on every call.

## Spring — Factory + Strategy, Container-Managed

This connects directly to the `Map<String, FeeCalculationStrategy>` injection pattern from earlier — Spring's container effectively acts as **both** the Factory (it constructs each `@Component` bean) and the strategy-selection mechanism (via the map lookup), so a `FeeStrategyFactory` class doesn't need to be hand-written at all:

```java
@Component("UPI")
class UpiFeeStrategy implements FeeCalculationStrategy {
    public double calculateFee(double amount) { return 0.0; }
}

@Component("CARD")
class CardFeeStrategy implements FeeCalculationStrategy {
    public double calculateFee(double amount) { return amount * 0.025; }
}

@Service
class TransactionProcessor {
    private final Map<String, FeeCalculationStrategy> strategies;   // Spring constructs + supplies ALL of them

    TransactionProcessor(Map<String, FeeCalculationStrategy> strategies) {
        this.strategies = strategies;
    }

    double process(String rail, double amount) {
        FeeCalculationStrategy strategy = strategies.get(rail);   // selection logic ONLY — no creation logic anywhere
        return amount + strategy.calculateFee(amount);
    }
}
```

Spring's IoC container has absorbed the Factory's job entirely — constructing each `UpiFeeStrategy`/`CardFeeStrategy` instance at startup — leaving the application code with pure Strategy selection and no explicit Factory class. This is a genuinely elegant, idiomatic way the two patterns fuse in a DI-based codebase.

**The general principle behind this pairing**, worth internalizing:

> Whenever "choosing which Strategy to use" itself requires conditional logic, that conditional logic belongs in a Factory — never inline in the class that consumes the Strategy.

The same combination shape applies well beyond payments:

- **Sorting**: a `ComparatorFactory.getComparator("byPrice")` returning different `Comparator` strategies.
- **Notification systems**: a `NotifierFactory.getNotifier("SMS")` returning `SmsNotifier`, `EmailNotifier`, etc. — each a Strategy for "how to notify."
- **Discount engines**: a `DiscountStrategyFactory.getStrategy(customerTier)` returning tier-specific discount calculation strategies.

## Quick Mental Model

| Question you're answering | Pattern responsible |
| --- | --- |
| "Which class should I instantiate?" | **Factory** |
| "What behavior should run once I have an object?" | **Strategy** |
| "Both, and I don't want conditional logic duplicated for each" | **Factory constructs the Strategy; client only sees the Strategy interface** |

> 💡 **Interview**: "How do Strategy and Factory work together?" → Factory centralizes the one place where a conditional decides which concrete Strategy to build; every consumer of that Strategy only ever sees the interface, with zero branching logic of its own. In Spring, injecting a `Map<String, StrategyInterface>` of all beans often collapses this further, letting the container act as the factory.

**Interview-ready summary line**: *"Strategy lets me swap an algorithm's implementation without touching the class that uses it — the context holds a reference to an interface, not a concrete class, so new algorithms are added via new classes, not by editing existing conditional logic. That's OCP and DIP working together through composition. When creating the right Strategy itself needs a conditional, that decision belongs in a Factory, not inline in the consumer — and in Spring, injecting a `Map` of all beans implementing the strategy interface often replaces both the switch and the hand-written factory class entirely."*
