# Kafka Intro

These notes are written around **`infra-kafka`** — a reusable, opinionated Spring Boot library (`org.infra:infra-kafka:1.0.0`, Java 21, Spring Boot 3.4.2) that a microservice pulls in as a JAR to get production-ready Kafka producers, consumers, retry/DLQ, serialization, security, and observability with **zero boilerplate**. You add the dependency, set `infra.kafka.*` in `application.yml`, and start producing/consuming.

The topics that follow (Producer, Consumer, Retry & DLQ, Observability, Serialization, Security, Transactions, Admin) each map to a delivery phase of the library. This note lays the conceptual foundation they all build on.

---

## 1. What is Kafka?

Apache Kafka is a **distributed, append-only commit log** used as a durable, high-throughput event backbone. The mental model:

- **Producers** publish **records** (key + value + headers) to **topics**.
- A topic is split into **partitions** — the unit of parallelism and ordering.
- **Consumers** (grouped into **consumer groups**) pull records and track their position via **offsets**.
- **Brokers** store partitions on disk and replicate them for fault tolerance.

Kafka's power comes from three properties: records are **persisted** (not deleted on read, unlike a queue), **ordered within a partition**, and **replayable** (a consumer can rewind to any offset within the retention window).

> [!info] Log vs Queue
> A traditional queue deletes a message once it is consumed. Kafka keeps the record until the **retention policy** (time or size based, default ~7 days) expires. Multiple independent consumer groups can therefore read the same topic at their own pace — this is what makes Kafka a *streaming platform*, not just a message broker.

## 2. KRaft — Kafka without ZooKeeper

Historically Kafka needed **ZooKeeper** to store cluster metadata (topics, partitions, ACLs, controller election). Modern Kafka (the library targets Kafka 3.7 / KRaft mode) replaces ZooKeeper with **KRaft** — a **Raft-based quorum** of controller nodes that manage metadata internally.

```
Controller Quorum (KRaft)
  Controller 1 ← Active Controller (Leader)
  Controller 2 ← Voter
  Controller 3 ← Voter
  Majority needed: 2 out of 3  (⌊N/2⌋ + 1)
```

Why it matters for interviews: KRaft removes an entire external system, **simplifies operations**, speeds up controller failover and metadata propagation, and scales to many more partitions. From the **client's** point of view nothing changes — the bootstrap protocol is identical, so `infra-kafka` works against both KRaft and legacy ZooKeeper clusters.

## 3. Core concepts

### 3.1 Partitions & ordering

A topic is divided into **N partitions**. Ordering is guaranteed **only within a single partition**, never across partitions. Which partition a record lands in is decided by the **partitioning strategy**:

| Strategy | Rule | Effect |
|----------|------|--------|
| **Key-based** (default) | `hash(key) % numPartitions` | All records with the same key → same partition → **ordering per key** |
| **Round-robin** | used when key is `null` | Even spread → maximum throughput, no ordering |
| **Custom** | implement `Partitioner` | Business routing (e.g. by region) |

This is why `infra-kafka`'s `publisher.send("order-events", order.getId(), order)` passes the **order ID as the key** — all events for one order stay ordered.

### 3.2 Replication, Leader/Follower, ISR

Every partition is replicated across `replication.factor` brokers for durability.

```
Topic: order-events, Partition 0
  Replica 0 (Broker 1) ← Leader     (handles ALL reads & writes)
  Replica 1 (Broker 2) ← Follower (ISR)
  Replica 2 (Broker 3) ← Follower (ISR)
```

- **Leader** — the single replica that serves all produce/consume requests for that partition.
- **Followers** — passively replicate from the leader.
- **ISR (In-Sync Replicas)** — the set of replicas fully caught up with the leader (governed by `replica.lag.time.max.ms`). **Only ISR members are eligible to be elected leader** if the current leader dies.

**Fault tolerance formula:** `tolerated broker failures = replication.factor − 1`.

| Environment | `replication.factor` | Tolerated failures |
|-------------|----------------------|--------------------|
| Dev | 1 | 0 |
| Staging | 2 | 1 |
| Production | 3 | 2 |

`min.insync.replicas` (typically `replication.factor − 1`) sets the **minimum ISR count** a write needs when `acks=all`; if the ISR shrinks below it, the producer gets an error instead of silently risking data loss.

### 3.3 Durability — the `acks` setting

The single most important producer knob (covered in depth in [[2. Producer]]):

| `acks` | Behaviour | Durability | Latency |
|--------|-----------|-----------|---------|
| `0` | Fire-and-forget | ❌ None | ⚡ Lowest |
| `1` | Leader acknowledges | ⚠️ Partial | 🔵 Medium |
| `all` (`-1`) | All ISR acknowledge | ✅ Full | 🔴 Highest |

`infra-kafka` defaults to **`acks=all`**.

### 3.4 Idempotent producer

Network retries can cause a producer to write the same record twice. With `enable.idempotence=true` (requires `acks=all`, `retries>0`, `max.in.flight ≤ 5`), the broker assigns each producer a **Producer ID (PID)** and a **per-partition sequence number**, and silently drops duplicates. This gives **exactly-once *delivery* to the log** for producer retries. It is **ON by default** in the library.

> [!warning] Idempotence ≠ consumer dedup
> Producer idempotence only stops the *producer* from double-writing during retries. It does **not** stop a *consumer* from reprocessing a record (e.g. after an offset reset or rebalance). Consumer-side idempotency (DB upserts on a unique key) is a separate concern — see [[3. Consumer]].

### 3.5 Exactly-Once Semantics (EOS v2)

Builds on the idempotent producer by adding **transactions**: a consume→transform→produce pipeline atomically commits both the **output records** and the **input offsets**. Requires a `transactional.id` and consumers reading with `isolation.level=read_committed`. Off by default (performance cost) — see [[8. Transactions (EOS)]].

### 3.6 Consumer groups & rebalancing

Each partition is read by **exactly one consumer within a group** at a time — this is how Kafka parallelises consumption. When members join/leave, partitions are redistributed (**rebalance**):

| Assignor | Behaviour |
|----------|-----------|
| `RangeAssignor` | Contiguous partitions per topic |
| `RoundRobinAssignor` | Round-robin across topics |
| `StickyAssignor` | Minimises movement |
| **`CooperativeStickyAssignor`** | **Incremental** rebalance — consumers keep reading unaffected partitions instead of a stop-the-world pause |

The library defaults to **`CooperativeStickyAssignor`** to minimise disruption during deploys and scaling. Detail in [[3. Consumer]].

## 4. How `infra-kafka` is wired (Spring Boot auto-configuration)

The library is delivered as a **Spring Boot auto-configuration**, *not* a component-scanned package. A single entry class, `InfraKafkaAutoConfiguration`, is listed in `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` so Spring Boot loads it automatically. It:

1. Is gated by `@ConditionalOnClass(KafkaTemplate.class)` (spring-kafka must be present) and `@ConditionalOnProperty(infra.kafka.enabled, matchIfMissing=true)`.
2. Binds all `infra.kafka.*` properties via `@EnableConfigurationProperties(InfraKafkaProperties.class)`.
3. `@Import`s every `@Configuration` the library owns (because there is no component scan).

Each phase is a `@Configuration` class, and **opt-in features gate themselves** with their own `@ConditionalOnProperty` / `@ConditionalOnClass`, so importing them unconditionally is safe — they simply back off when disabled:

| Phase | Config class | Default | Activation |
|-------|--------------|---------|-----------|
| 1 Producer | `KafkaProducerConfig` | ✅ on | always |
| 2 Consumer | `KafkaConsumerConfig` | ✅ on | always |
| 3 Retry/DLQ | `RetryTopicConfig` / `NonBlockingRetryConfig` | ✅ on | `infra.kafka.retry.*` |
| 4 Observability | `ObservabilityConfig` | ✅ on | `infra.kafka.logging/metrics` |
| 5 Avro | `AvroSerializerConfig` | ❌ off | `serialization.type=avro` + Confluent on classpath |
| 6 Security | `KafkaSecurityConfig`, `SaslConfigProvider` | ✅ present (no-op on PLAINTEXT) | always |
| 7 Transactions | `KafkaTransactionConfig` | ❌ off | `transaction.enabled=true` |
| 8 Admin | `KafkaAdminConfig` | ❌ off | `admin.auto-create=true` |

> [!tip] `@ConditionalOnMissingBean` everywhere
> Every library bean (`KafkaTemplate`, `ConsumerFactory`, error handlers, …) is guarded with `@ConditionalOnMissingBean`. This means a consuming service can **override any single bean** by simply declaring its own — the library backs off gracefully. Sensible defaults, full escape hatch.

The public surface a service actually touches is tiny:

- **Produce:** inject `KafkaMessagePublisher` → `publisher.send(topic, key, payload)`.
- **Consume:** annotate a method with `@InfraKafkaListener(topics = "...", groupId = "...")`.

Everything else (idempotence, retry, DLQ routing, logging, metrics, security) is configured by properties.

## 5. The `infra.kafka.*` configuration surface

All settings live under the `infra.kafka` prefix, bound by `InfraKafkaProperties`. The nested groups:

```yaml
infra:
  kafka:
    bootstrap-servers: localhost:9092,localhost:9093
    producer:        { acks, retries, batch-size, linger-ms, compression-type, idempotent, ... }
    consumer:        { group-id, auto-offset-reset, enable-auto-commit, max-poll-records, concurrency, trusted-packages, ... }
    retry:           { enabled, mode: blocking|non-blocking, max-attempts, backoff-*, ... }
    dlq:             { enabled, suffix: "-dlq" }
    serialization:   { type: json|avro, schema-registry-url, ... }
    security:        { protocol, sasl: {...}, ssl: {...} }
    transaction:     { enabled, id-prefix }
    admin:           { auto-create, topics: [...] }
    logging:         { enabled, log-payload }
    metrics:         { enabled }
    shutdown:        { timeout: 30s }
    circuit-breaker: { enabled }
```
