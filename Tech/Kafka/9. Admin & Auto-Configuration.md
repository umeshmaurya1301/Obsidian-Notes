# Admin & Auto-Configuration

This note ties the library together: how **topics get created** (Phase 8 admin), how **Spring Boot auto-wires everything** with zero `@Configuration` in the consuming service, and the **graceful-shutdown** and override mechanics that make it production-safe.

---

## 1. Topic auto-creation — `KafkaAdminConfig`

**Off by default** (`admin.auto-create=false`), gated by `@ConditionalOnProperty(infra.kafka.admin.auto-create=true)`. When on, it:

1. Registers a `KafkaAdmin` bean pointed at `bootstrap-servers`, **with security applied** (so it works on secured clusters).
2. For each declared topic, builds a `NewTopic` via `TopicBuilder` and calls `admin.createOrModifyTopics(...)`.

```yaml
infra:
  kafka:
    admin:
      auto-create: true          # keep FALSE in prod
      topics:
        - { name: order-events,   partitions: 6, replication-factor: 3 }
        - { name: payment-events, partitions: 3, replication-factor: 3 }
```

```java
NewTopic t = TopicBuilder.name(td.getName())
        .partitions(td.getPartitions())
        .replicas(td.getReplicationFactor())
        .build();
admin.createOrModifyTopics(t);
```

If `auto-create=true` but no topics are declared, it logs a warning and no-ops.

> [!warning] Disable auto-create in production
> Auto-creation is a **dev convenience**. In prod a typo silently creates a junk topic with default (usually wrong) partition/replication settings, and you lose control over the cluster's topic inventory. Manage topics via **IaC** (Terraform/Ansible) and keep `auto-create=false`. Partition count especially is effectively immutable — you can add partitions but never remove them, and adding them breaks key-based ordering.

`createOrModifyTopics` can **grow** partition count or add configs but **won't shrink** partitions or reduce replication — Kafka doesn't allow that online.

## 2. How auto-configuration works (no `@Configuration` needed)

The library is a **Spring Boot auto-configuration**, delivered as a JAR. The consuming service writes **zero** Kafka config classes. The mechanics:

```
src/main/resources/META-INF/spring/
  org.springframework.boot.autoconfigure.AutoConfiguration.imports   ← lists InfraKafkaAutoConfiguration
```

Spring Boot reads that file at startup and loads `InfraKafkaAutoConfiguration`, which:

```java
@AutoConfiguration
@ConditionalOnClass(KafkaTemplate.class)                                  // spring-kafka present?
@ConditionalOnProperty(prefix="infra.kafka", name="enabled",
                       havingValue="true", matchIfMissing=true)           // kill-switch
@EnableConfigurationProperties(InfraKafkaProperties.class)                // bind infra.kafka.*
@Import({ SaslConfigProvider, KafkaSecurityConfig,   // security first (others depend on it)
          KafkaProducerConfig, KafkaConsumerConfig,
          RetryTopicConfig, NonBlockingRetryConfig, ObservabilityConfig,
          AvroSerializerConfig, SchemaRegistryHealthIndicator,
          KafkaTransactionConfig, KafkaAdminConfig })
public class InfraKafkaAutoConfiguration { }
```

> [!info] Auto-configuration ≠ component scan
> Because the library ships as an auto-config (not scanned via `@ComponentScan`), **every** `@Configuration`/`@Component` it owns must be listed in `@Import`. Component scanning wouldn't reach `org.infra.kafka.*` from a consumer app in `com.acme.*` anyway. This is *the* reason the imports are explicit.

**Ordering matters:** `SaslConfigProvider` + `KafkaSecurityConfig` are imported *first* because the producer, consumer, Avro and admin configs all take `KafkaSecurityConfig` as a constructor dependency (`applySecurity(...)`).

## 3. The two conditional patterns

The whole library is built on two Spring Boot conditions:

### `@ConditionalOnMissingBean` — sensible defaults, full override

Every library bean (`KafkaTemplate`, `ProducerFactory`, `ConsumerFactory`, error handlers, `DlqHandler`, container factories…) carries `@ConditionalOnMissingBean`. So a service can **override any one bean** by declaring its own — the library backs off for just that bean and keeps the rest.

```java
// In the consuming service — take over the template, keep everything else from infra-kafka
@Bean
public KafkaTemplate<String, Object> kafkaTemplate(ProducerFactory<String, Object> pf) {
    return new KafkaTemplate<>(pf);   // infra-kafka's infraKafkaTemplate now backs off
}
```

### `@ConditionalOnProperty` / `@ConditionalOnClass` — self-gating opt-ins

Opt-in phases activate themselves, so importing them unconditionally is safe:

| Feature | Gate |
|---------|------|
| Avro | `serialization.type=avro` **+** `@ConditionalOnClass(KafkaAvroSerializer)` |
| Non-blocking retry | `retry.mode=non-blocking` |
| Transactions | `transaction.enabled=true` |
| Admin auto-create | `admin.auto-create=true` |
| Metrics | `metrics.enabled=true` **+** `@ConditionalOnClass(MeterRegistry)` |
| Circuit breaker | `circuit-breaker.enabled=true` |

`matchIfMissing=true` on the always-on features (logging, retry) means they're active unless explicitly disabled.

## 4. Graceful shutdown

Configured in `KafkaConsumerConfig.buildBaseFactory()` from `shutdown.timeout` (default `30s`):

```java
factory.getContainerProperties().setShutdownTimeout(timeout.toMillis());
```

On SIGTERM (deploy/rollout), the listener container:
1. **Stops polling** for new records,
2. **finishes in-flight** records (up to the timeout),
3. **commits offsets** (AckMode.RECORD commits after each record anyway),
4. then shuts down.

Combined with **`CooperativeStickyAssignor`** (incremental rebalance, see [[3. Consumer]]), a rolling deploy causes minimal disruption — unaffected partitions keep flowing instead of a stop-the-world pause.

```yaml
infra:
  kafka:
    shutdown:
      timeout: 30s
```

> [!info] Why this prevents message loss
> Without draining, in-flight records could be interrupted mid-processing on shutdown. Because AckMode is `RECORD` (offset committed only **after** successful processing), an interrupted record simply isn't committed and gets redelivered to another instance — at-least-once is preserved across deploys.

## 5. Overriding & extending — FAQ

| Question | Answer |
|----------|--------|
| Need any `@Configuration` in my service? | **No** — add the dep, set `application.yml`. |
| Override the producer/consumer beans? | Yes — declare your own; `@ConditionalOnMissingBean` backs off. |
| Consume multiple topics in one listener? | `@InfraKafkaListener(topics = {"a","b"})`. |
| Different serialization per service? | Yes — each service sets its own `serialization.type`. |
| Kill the whole library? | `infra.kafka.enabled=false`. |
| Hook producer success/failure? | Register a `ProducerCallback` bean (see [[2. Producer]]). |

## 6. Circuit breaker (planned hardening)

`CircuitBreakerProperties` (`circuit-breaker.enabled`, default false) reserves the flag for **Resilience4j**-based circuit breaking on consumer downstream failures — pausing consumption when a downstream dependency is failing hard, to avoid hammering it and flooding the DLQ. Off by default so consumption is never paused unexpectedly.

## 8. Interview soundbites

- **"How does a Spring Boot library auto-configure without being component-scanned?"** → an `@AutoConfiguration` class listed in `META-INF/spring/...AutoConfiguration.imports`, that `@Import`s all its config classes and binds `@ConfigurationProperties`.
- **"How do you let users override defaults?"** → `@ConditionalOnMissingBean` on every bean; user beans win.
- **"How do you make opt-in features safe to always import?"** → each is self-gated with `@ConditionalOnProperty`/`@ConditionalOnClass` and backs off when disabled.
- **"Why not auto-create topics in prod?"** → typos create junk topics with default partitioning; manage via IaC. Partition count is practically immutable.
- **"Graceful shutdown during a deploy?"** → stop polling → drain in-flight (bounded by timeout) → commit → exit; `CooperativeStickyAssignor` keeps unaffected partitions flowing.
