# Serialization (Avro & Schema Registry)

Kafka moves **bytes** — it has no idea what a record *means*. Serialization is the contract between producer and consumer, and getting it wrong is how you break every consumer of a topic at once. `infra-kafka` defaults to **JSON** (zero setup) and offers opt-in **Avro + Confluent Schema Registry** (`serialization.type=avro`) for strongly-typed, space-efficient, schema-governed messaging.

This is **Phase 5** (`org.infra.kafka.serialization`).

---

## 1. JSON vs Avro at a glance

| | **JSON** (default) | **Avro** (opt-in) |
|---|---|---|
| Setup | none | Schema Registry + `kafka-avro-serializer` dep |
| Payload size | large (field names repeated) | compact (binary, schema by reference) |
| Schema enforcement | none (convention only) | **registry-enforced** compatibility |
| Human-readable | ✅ yes | ❌ binary |
| Evolution safety | manual (`@JsonIgnoreProperties`) | automatic (compatibility modes) |
| Cross-language | good | excellent (schema is language-neutral) |
| Best for | internal services, fast iteration | high-volume / many teams / strict contracts |

Switch with one property — **no code change** in the service, because the Avro factories are marked `@Primary` and override the JSON ones:

```yaml
infra:
  kafka:
    serialization:
      type: avro
      schema-registry-url: http://localhost:8081
```

## 2. JSON serialization (the default path)

- **Producer** (`KafkaProducerConfig`): key = `StringSerializer`, value = Spring's `JsonSerializer`. Type headers are **disabled** (`spring.json.add.type.headers=false`) to keep payloads clean and portable across services/languages.
- **Consumer** (`KafkaConsumerConfig`): value = `JsonDeserializer`, wrapped in `ErrorHandlingDeserializer` (see [[4. Retry and DLQ]]). `USE_TYPE_INFO_HEADERS=false`, so the target type comes from the **listener method signature**.

### Trusted packages — security, not ceremony

`JsonDeserializer` can instantiate arbitrary classes from the wire — a **deserialization-attack vector**. So it's gated by a package allow-list:

```yaml
infra.kafka.consumer.trusted-packages: "com.acme.orders.events"
```

- **Blank (default, secure):** nothing is blanket-trusted; the type is taken from the listener signature, so legitimate typed payloads still deserialize.
- **`"*"` :** trusts *every* package — dev only. The library logs a loud **SECURITY** warning when it sees `"*"`.

> [!warning] Never ship `trusted-packages: "*"`
> It lets a malicious message name any class on your classpath as the deserialization target. Scope it to your event-model package(s) in production.

### JSON schema evolution rules

| Change | Compatible? | Note |
|--------|-------------|------|
| Add optional field (with default) | ✅ | old consumers ignore it |
| Remove optional field | ✅ | new consumers handle absence |
| Rename field | ❌ | use `@JsonAlias` during migration |
| Change field type | ❌ | make a new event version |
| Add **required** field (no default) | ❌ | breaks old consumers |

**Golden rule:** always annotate event DTOs with `@JsonIgnoreProperties(ignoreUnknown = true)` and add fields as optional-with-defaults.

```java
@JsonIgnoreProperties(ignoreUnknown = true)
public record OrderCreatedEvent(
    String orderId, String customerId, BigDecimal total, Instant timestamp,
    @JsonProperty(defaultValue = "UNKNOWN") String source   // safe additive change
) {}
```

## 3. Avro & the Schema Registry

**Avro** stores data in a compact binary form described by a **schema** (a JSON document: field names, types, defaults). Instead of shipping the schema with every message, the **Confluent Schema Registry** stores schemas centrally and assigns each a numeric **schema ID**; the message carries only that ID (a few bytes) plus the binary payload.

```
Producer                         Schema Registry                 Consumer
  │ serialize with schema v3  ───▶ register / lookup → ID=42        │
  │ write [magic][ID=42][avro bytes] ──────▶ topic ──────────▶ read │
  │                                          fetch schema ID=42 ◀────┤
  │                                          deserialize with it     │
```

Benefits: **small payloads**, **enforced compatibility** at write time, one source of truth for the contract.

### What `AvroSerializerConfig` wires

Activated by `@ConditionalOnProperty(serialization.type=avro)` **and** `@ConditionalOnClass(KafkaAvroSerializer)` (Confluent dep present). It builds `@Primary` producer & consumer factories:

- Value serializer → `KafkaAvroSerializer`; deserializer → `KafkaAvroDeserializer` (keys stay `String`).
- `schema.registry.url` from `serialization.schema-registry-url`.
- Reapplies the same reliability defaults (idempotence, acks, batching, timeouts) and Phase 6 security.

Key Avro-specific properties (`SerializationProperties`):

| Property | Default | Meaning |
|----------|---------|---------|
| `auto-register-schemas` | `false` | **Off in prod** — register via CI/CD, not accidentally at runtime |
| `use-latest-version` | `true` | use the latest registered schema for the subject vs the writer schema |
| `specific-avro-reader` | `true` | deserialize into generated Avro POJOs (vs `GenericRecord`) |
| `subject-naming-strategy` | `TopicNameStrategy` | how subjects are named (see below) |
| `schema-registry-auth` | `""` | `username:password` Basic Auth (use env vars!) |

> [!warning] `auto-register-schemas=false` in production
> Auto-registration lets any producer mutate the shared contract at runtime — a subtle way to ship a breaking schema. Register schemas through CI/CD with an explicit compatibility check; keep runtime registration off.

### Subject naming strategy

The **subject** is the registry key a schema is stored under:

| Strategy | Subject | Use |
|----------|---------|-----|
| `TopicNameStrategy` (default) | `<topic>-value` | one schema type per topic |
| `RecordNameStrategy` | Avro record FQN | same record type across many topics |
| `TopicRecordNameStrategy` | `<topic>-<record>` | multiple event types on one topic |

### Avro compatibility modes (registry-enforced)

| Mode | Allowed change | Who upgrades first |
|------|----------------|--------------------|
| `BACKWARD` (library default) | delete fields, add optional fields | **consumers** first |
| `FORWARD` | add fields, delete optional fields | **producers** first |
| `FULL` | add/delete optional only | either |
| `NONE` | anything (unsafe) | — |

`BACKWARD` means a **new consumer** can read data written by an **old producer** — the safest default for rolling upgrades where you deploy consumers ahead of producers.

### Schema Registry Basic Auth

```yaml
infra.kafka.serialization.schema-registry-auth: "${SR_USER}:${SR_PASS}"
```
→ the library sets `basic.auth.credentials.source=USER_INFO` + `user.info`. **Never hardcode** — use env vars.

## 4. Schema Registry health check

`SchemaRegistryHealthIndicator` (a `HealthIndicator` named `schemaRegistry`, active only in Avro mode) does a lightweight `GET <url>/subjects` on each health poll:

```json
GET /actuator/health
{ "components": { "schemaRegistry": {
    "status": "UP", "details": { "url": "http://localhost:8081", "httpStatus": 200 } } } }
```

**2xx → UP**, otherwise **DOWN** with a reason. Crucially it is **fail-soft**: if the registry is unreachable at startup the app still boots (health shows DOWN), so a slow-starting registry doesn't crash your service. Timeouts are 3s connect / 3s read.

## 5. Versioned topics — for genuinely breaking changes

When a change can't be made compatible, don't fight the schema — **version the topic**:

```
order-events-v1   ← existing consumers
order-events-v2   ← new consumers, breaking schema
```

Migration: deploy v2 consumers → producers **dual-write** v1+v2 → migrate remaining consumers → deprecate & delete v1.

## 6. Interview soundbites

- **"Why Avro over JSON?"** → compact binary + a central registry that *enforces* compatibility, so one team can't silently break every consumer.
- **"How does the consumer know the schema?"** → the message carries a schema **ID**; the consumer fetches that schema from the registry and caches it.
- **"BACKWARD vs FORWARD compatibility?"** → BACKWARD: new consumer reads old data (upgrade consumers first). FORWARD: old consumer reads new data (upgrade producers first).
- **"Biggest JSON footgun?"** → no schema enforcement + `trusted-packages: "*"` (RCE risk) + non-additive changes breaking consumers.

## 7. Avro vs Protobuf — when to use which

Both solve **efficient binary serialization with strict schema enforcement**, but differ in how they store schemas, identify fields, and evolve.

| Aspect | **Avro** (Kafka ecosystem) | **Protobuf** (gRPC ecosystem) |
|--------|--------------------------|-------------------------------|
| Field identification | By **name** (schema resolution) | By **numeric field tag** (`= 1`, `= 2`) |
| Wire format | Raw binary values, **zero field tags or type markers** | `[Tag ID \| Wire Type \| Value]` per field |
| Schema delivery | 5-byte header (1 magic + 4-byte Schema ID from Registry) | Compiled into client/server code at build time |
| Decoding without schema | ❌ Impossible — binary is meaningless without writer's schema | ✅ Partially self-describing via tag+wire type |
| Evolution mechanism | Schema Resolution (writer schema vs reader schema) | Field tags are stable; unknown tags skipped |
| Best fit | Kafka (schema by reference = tiny payloads) | gRPC / service-to-service RPC |

> [!info] Why Kafka Uses Avro Over Protobuf
> Avro's design — where the schema is stored **externally** and only a 5-byte reference is sent per message — is ideal for high-volume Kafka topics where the same schema applies to millions of messages. Protobuf encodes field metadata into every message, which is fine for RPC but wastes bytes at Kafka scale.

## 8. How Avro Schema Resolution works (deep dive)

Avro handles evolution through **Schema Resolution**: the deserializer reconciles the **Writer's Schema** (used when producing) with the **Reader's Schema** (the consumer currently expects). Fields are matched by **name**, and compatibility depends entirely on **default values**.

### Backward Compatibility (consumer upgrades first)

A **new consumer** can read data produced by an **old producer**.

| Change | Allowed? | Rule |
|--------|:--------:|------|
| Add a new field | ✅ | Must have a `default` value — Avro fills it in for old messages |
| Delete a field | ✅ | New consumer simply stops looking for it |
| Rename a field | ❌ | Breaking (unless using `aliases`) |

### Forward Compatibility (producer upgrades first)

An **old consumer** can read data produced by a **new producer**.

| Change | Allowed? | Rule |
|--------|:--------:|------|
| Add a new field | ✅ | Old consumer ignores unknown fields |
| Delete a field | ✅ | Must have had a `default` in the old consumer schema |
| Change field type | ❌ | Breaking |

### Full Compatibility (safe for arbitrary deployment order)

Producer and consumer can be upgraded **in any order**.

| Change | Allowed? | Rule |
|--------|:--------:|------|
| Add field with default | ✅ | Safe both directions |
| Delete field with default | ✅ | Safe both directions |
| Add/delete without default | ❌ | Breaks one direction |
| Rename a field | ❌ | Breaking (unless `aliases`) |

> [!important] The Golden Rule
> You can **only add or delete fields that define a default value** under Full Compatibility. This is why Avro schemas should always provide defaults for every non-required field.
