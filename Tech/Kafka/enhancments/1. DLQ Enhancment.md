# Future Enhancement: Kafka DLQ Replay Architecture

This document describes a **production-grade Dead Letter Queue (DLQ) replay architecture** for the Infra Kafka library.  
The goal is to enable **safe, observable, and controlled replay of failed Kafka messages** without creating retry storms or infinite loops.

---

# 1. Problem With Simple DLQ Replay

A naive implementation replays messages directly from DLQ:

```
DLQ
 │
 ▼
Replay
 │
 ▼
Original Topic
 │
 ▼
Consumer
 │
 ├─ Success
 └─ Failure → DLQ again
```

If the underlying issue is not resolved, this creates an **infinite retry loop**:

```
DLQ → Replay → Fail → DLQ → Replay → Fail → DLQ
```

Problems caused by this approach:

- Kafka traffic storms
    
- Consumer overload
    
- Log flooding
    
- Hidden production failures
    
- Lack of operational control
    

A more robust architecture is required.

---

# 2. Production DLQ Replay Architecture

A safer architecture introduces **processing, storage, and controlled replay services**.

```
                ┌──────────────────┐
                │  Original Topic  │
                └─────────┬────────┘
                          │
                          ▼
                    Kafka Consumer
                          │
                   Processing Failure
                          │
                          ▼
                ┌──────────────────┐
                │        DLQ       │
                └─────────┬────────┘
                          │
                          ▼
                 DLQ Processing Service
                          │
          ┌───────────────┼───────────────┐
          │               │               │
          ▼               ▼               ▼
        Logging        Metrics        Storage
                                             │
                                             ▼
                                      DLQ Database
                                             │
                                             ▼
                                       Replay Service
                                             │
                                             ▼
                                      Original Topic
```

This architecture ensures:

- Controlled retries
    
- Safe replay
    
- Observability
    
- Operational visibility

# 4. Replay Service

Replay service controls when and how DLQ messages are retried.

Instead of:

```
DLQ → Immediate Replay
```

The workflow becomes:

```
DLQ → Store → Inspect → Replay
```

Example service:

```java
@Service
public class DlqReplayService {

    private final KafkaTemplate<String, Object> kafkaTemplate;
    private final DlqRepository repository;

    public void replay(Long dlqId) {

        DlqMessage msg = repository.findById(dlqId);

        if (msg.getRetryCount() >= 3) {
            throw new IllegalStateException("Retry limit exceeded");
        }

        kafkaTemplate.send(
            msg.getOriginalTopic(),
            msg.getKey(),
            msg.getPayload()
        );

        msg.incrementRetry();
        repository.save(msg);
    }
}
```

---

# 5. Retry Limits

Each DLQ message must track the number of replay attempts.

Example:

```
retry_count = 0
max_retries = 3
```

Replay condition:

```
retry_count < max_retries
```

If retry limit is exceeded:

```
status = PERMANENT_FAILURE
```

This prevents infinite replay loops.

# 7. Replay Rate Limiting

Replaying thousands of messages instantly can overload consumers.

Bad example:

```
10,000 DLQ messages → replay immediately
```

Recommended approach:

```
Replay rate = 50 messages / second
```

Example implementation:

```java
RateLimiter limiter = RateLimiter.create(50);

for (DlqMessage msg : messages) {

    limiter.acquire();

    kafkaTemplate.send(
        msg.getOriginalTopic(),
        msg.getKey(),
        msg.getPayload()
    );
}
```

This protects downstream services.

# 9. Infinite Loop Protection

Introduce a replay header:

```
X-DLQ-REPLAY-COUNT
```

Each replay increments this value.

If:

```
replay_count > max_retries
```

Then do not send to DLQ again.

Instead route to a **Permanent DLQ**.

```
Original Topic
      │
      ▼
Consumer
      │
      ▼
DLQ
      │
      ▼
Replay Service
      │
      ▼
Original Topic
      │
      ▼
Failure Again
      │
      ▼
Permanent DLQ
```

Permanent DLQ is used for messages that cannot be processed even after retries.
