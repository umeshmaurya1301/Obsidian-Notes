# Distributed Locks & Concurrency in Kafka

When 50 consumers are listening and a transaction for a given account/card must be processed by **only one** consumer, you need concurrency control. This note covers Redis distributed locks, Kafka partitioning strategies, and database-level locking — and when to use each.

---

## 1. The Problem: Concurrent Consumer Processing

Without any locking:

```text
Consumer-1 reads TXN1 (Account A) → balance = ₹10,000
Consumer-2 reads TXN2 (Account A) → balance = ₹10,000

TXN1 debits ₹8,000 → balance = ₹2,000
TXN2 debits ₹5,000 → balance = ₹5,000  ← WRONG (should fail!)
```

Both consumers read the same stale balance → inconsistent state.

---

## 2. Redis Distributed Lock Approach

### Basic Pattern

```java
// Acquire lock — Set if Not Exists, with 30s TTL
SET lock:account:A consumer-1 NX EX 30
```

| Consumer | Lock Result | Action |
|----------|------------|--------|
| Consumer-1 | `OK` ✅ | Processes transaction |
| Consumer-2 | `NULL` ❌ | Retries later / moves to delayed queue |

After completion:
```java
DEL lock:account:A
```

### Lock Key Design (by Business Entity)

| Entity | Lock Key | Scope |
|--------|----------|-------|
| Account | `lock:account:123` | One transaction per account |
| Card | `lock:card:9876` | One card operation at a time |
| UPI Mandate | `lock:mandate:M123` | One mandate update |
| Settlement | `lock:settlement:20260820` | One settlement job per day |

---

## 3. Redis Lock Failure Modes

### Problem 1: JVM Crash → Lock Stuck Forever

If the consumer acquires the lock then crashes, the lock remains indefinitely.

**Solution:** TTL (`EX 30`) is mandatory. Redis auto-releases after 30 seconds.

### Problem 2: Processing Exceeds TTL

```text
Lock TTL = 30 sec
Processing takes = 45 sec
    → Lock expires at 30s
    → Another consumer acquires lock
    → BOTH process the same transaction!
```

**Solution:** Lock renewal (heartbeat) — extend the lock periodically:

```java
// Every 10 seconds, extend the lock
PEXPIRE lock:account:A 30000
```

Libraries like **Redisson** handle this automatically with a watchdog thread.

### Problem 3: Unsafe Lock Release

```text
C1 acquires lock (owner=A)
    → TTL expires
C2 acquires lock (owner=B)
C1 finishes and calls DEL lock:key
    → C1 deletes C2's lock!
```

**Solution:** Only release if you are still the owner (Lua script for atomicity):

```lua
if redis.call("GET", KEYS[1]) == ARGV[1]
then return redis.call("DEL", KEYS[1])
else return 0
end
```

## 4. Redis High Availability Concerns

### Single Redis Instance = SPOF

Not acceptable for critical systems. If Redis crashes, locks disappear and mutual exclusion is lost.

### Redis Sentinel

```text
Master → Replica → Replica (auto-failover)
```

**Problem:** Replication is **asynchronous**. If the master crashes before replication completes, the lock vanishes. Another consumer acquires a fresh lock → two processors exist. Classic distributed lock problem.

### Redis Cluster

Same issue — improves availability, does **NOT** guarantee lock correctness.

### Redlock (Redis Creator's Proposal)

```text
5 independent Redis nodes
Acquire lock on majority (≥ 3/5)
```

Reduces risk, but many distributed systems experts debate whether Redlock provides sufficient guarantees for critical financial operations (Martin Kleppmann's criticism — clock assumptions, network partitions, split-brain).

> [!warning] Redlock Controversy
> Even just saying *"Redlock improves availability but many teams still rely on DB constraints for financial correctness"* is enough to impress an interviewer.

## 5. The Better Approach: Kafka Partitioning by Key

Instead of Redis locks, many fintech systems use **partitioning by business key**:

```text
Producer sends: key = accountId
    → Kafka: same key → same partition
    → One partition → one consumer (within a consumer group)
```

```text
Account A → Partition 3 → Consumer-7 (only this one processes)
```

All transactions for Account A go to Partition 3 → **sequential processing** by a single consumer → **no lock required**.

### Partition Count Change Caveat

```java
partition = hash(key) % numPartitions
```

If partitions change: `hash(accountA) % 8 = 3` but `hash(accountA) % 16 = 11`

- Old messages remain in Partition 3.
- New messages go to Partition 11.
- **Ordering across old and new messages is affected.**

Because of this, payment systems typically:
- **Pre-create enough partitions** upfront
- Avoid increasing partitions frequently
- Use **custom partitioners** for critical ordered streams

## 6. Rebalance & Duplicate Processing

During a Kafka rebalance (partition increase, consumer crash, scaling):

```text
1. Kafka revokes partitions from Consumer-1
2. Consumer-1 is expected to stop processing
3. Partition reassigned to Consumer-2
4. Consumer-2 starts from LAST COMMITTED OFFSET
```

The real risk:
```text
Consumer-1 processed the transaction
    → Offset NOT committed
    → Rebalance happens
    → Consumer-2 reads the SAME message
    → DUPLICATE PROCESSING
```

**Solution:** Idempotency key (`txn_id` with `UNIQUE` constraint in the DB). If Consumer-2 replays, the insert fails → transaction is safely ignored.

> [!important] Key Insight
> Kafka = At-Least-Once delivery. Business layer = Exactly-Once execution (via idempotency).

## 7. Database Locking (The Source of Truth)

For **monetary correctness**, the database — not Redis — is the primary mechanism.

### Pessimistic Locking (`SELECT ... FOR UPDATE`)

```sql
SELECT balance FROM account WHERE id = 123 FOR UPDATE;
-- Txn-1 gets the row lock
-- Txn-2 WAITS until Txn-1 commits/rollbacks
```

| Pros | Cons |
|------|------|
| Strong consistency | Blocking — reduced throughput |
| Simple to reason about | Potential deadlocks |

### Optimistic Locking (Version Column)

```sql
-- Read: version = 5
UPDATE account
SET balance = ?, version = 6
WHERE id = 123 AND version = 5;
```

If another transaction already updated → `0 rows affected` → retry.

| Pros | Cons |
|------|------|
| High throughput (no blocking) | Requires retry logic |
| No deadlocks | Contention under high write volume |

## 8. The Complete Fintech Production Pattern

```text
Transaction Arrives
        ↓
Kafka key = accountId            ← Partition-level ordering
        ↓
Single consumer processes        ← No concurrent access
        ↓
Redis lock (optional guard)      ← Coordination / duplicate prevention
        ↓
SELECT ... FOR UPDATE            ← DB-level correctness
        ↓
Balance update + idempotency check
        ↓
COMMIT
```

Even if Kafka replays the message, `idempotency_key = txnId` prevents double debit.

### Role of Each Component

| Component | Role | Is it Sufficient Alone? |
|-----------|------|:-----------------------:|
| Kafka partitioning | Ordering + single consumer per key | ❌ (rebalance → replay) |
| Redis distributed lock | Coordination, duplicate-work prevention | ❌ (TTL edge cases, Redis failure) |
| DB row locking | Monetary correctness (source of truth) | ✅ (ACID guarantees) |
| Idempotency key | Prevents double execution on replay | ✅ (works even without Redis) |

> [!tip] Senior-Level Takeaway
> **Redis = optimization / coordination. Database = correctness.** If Redis goes down completely, DB locking + idempotency keys still protect you. This distinction is what interviewers are looking for.

---

## 9. Distributed Locking Without Redis

If Redis is unavailable, alternatives exist:

| Technology | Mechanism |
|------------|-----------|
| DB row locks | `SELECT ... FOR UPDATE` |
| ZooKeeper | Ephemeral sequential nodes |
| etcd | Lease-based locks |
| Consul | Session-based locks |
| PostgreSQL | Advisory locks (`pg_advisory_lock`) |

> [!tip] Interview Follow-up
> *"Why choose Redis over ZooKeeper?"* — Redis is faster (in-memory, sub-ms), simpler to operate, and sufficient for coordination. ZooKeeper provides stronger consensus guarantees but is heavier to run and slower.
