## 1. What is a Kafka Consumer?

If a Kafka Producer publishes data, the **Kafka Consumer** is the client application that subscribes to Kafka topics and reads those messages. While producers _push_ data to brokers, consumers **pull** data from brokers. This pull-based model allows consumers to process messages at their own pace without being overwhelmed by sudden spikes in traffic.

> [!info] Context
> These settings map to the `infra-kafka` `KafkaConsumerConfig` / `ConsumerProperties` (Phase 2). In practice you annotate a method with `@InfraKafkaListener(topics = "...", groupId = "...")` and the library wires the container factory for you. See [[2. Producer]] for the publishing side and [[1. Kafka Intro]] for foundational concepts.

## 2. Core Concepts

Understanding how a consumer operates requires understanding three fundamental mechanisms:

- **Consumer Groups:** Kafka is designed for massive scale. A Consumer Group is a collection of consumers working together to read from a topic. **The Golden Rule:** Each partition in a topic can only be read by _one_ consumer within a specific Consumer Group at any given time. This allows for parallel processing.
    
- **The Polling Loop:** Consumers run a continuous loop, asking the broker: _"Do you have any new data for me?"_ by calling `poll()`. If a consumer stops polling (e.g., it crashes or takes too long to process a batch), the broker assumes it has died and reassigns its partitions to other consumers in the group.
    
- **Offsets and Committing:** To remember what it has already read, a consumer tracks the **offset** (a sequential ID for each message in a partition). Periodically, the consumer sends a message back to Kafka saying, _"I have successfully processed all messages up to this offset."_ This is called **committing**.

## 3. The `auto.offset.reset` Strategy and Missing Bookmarks

Sometimes, a consumer asks Kafka for its last committed offset, and Kafka has no record of it. This usually happens because:

1. It is a brand new Consumer Group that has never read from the topic.
    
2. The consumer was offline for so long that Kafka deleted the offset record to save disk space (default is usually 7 days).
    
3. The data the offset pointed to has been deleted due to topic retention policies.
    

When the offset is missing, the `auto.offset.reset` property tells the consumer where to start reading.

- **`latest`:** The consumer ignores historical data and only reads _new_ messages that arrive after it connects.
    
- **`earliest`:** The consumer goes to the very beginning of the partition and reads every single piece of available historical data.
    
- **`none`:** The consumer throws an exception and crashes (used in strict environments where a missing offset indicates a critical error).
    

---

## 4. The Idempotency Misconception

A common pitfall is assuming that configuring `idempotent = true` on the **Producer** will protect the **Consumer** from processing duplicate messages if its offset is lost.

**This is false.** Producer idempotence only ensures the producer doesn't write the same message to Kafka twice during a network retry. If a consumer's offset is lost and it resets to `earliest`, Kafka will feed it historical messages it has already seen.

To prevent processing the same message twice, you must implement **Consumer-Side Idempotence** in your application code. This is typically done using:

- **Database Upserts / Unique Keys:** Using a unique identifier (like an `order_id`) to ensure that processing the message a second time results in a safe database "update" or is rejected as a duplicate key.

> [!tip] When strict exactly-once is required
> Consumer-side idempotency (upserts) is the pragmatic default. For a genuinely atomic *consume → transform → produce* pipeline (offset commit + output send in one unit), the library offers opt-in Kafka transactions — see [[8. Transactions (EOS)]].

## 5. Consumer Properties Breakdown

Here is an explanation of the specific configurations in your `ConsumerProperties` class and how they dictate the consumer's behavior.

### Identity & Grouping

- **`groupId` ("${spring.application.name:default-group}"):** The unique identifier for the Consumer Group. If you change this, Kafka treats your application as a brand new group, and it will trigger the `autoOffsetReset` strategy.
    

### Offset Management

- **`autoOffsetReset` ("earliest"):** If this consumer loses its offset, it will start reading from the oldest available message in the partition, ensuring no historical data is missed.
    
- **`enableAutoCommit` (false):** This is highly recommended for enterprise apps. By setting this to `false`, you are telling Kafka _not_ to commit offsets automatically in the background. Instead, your Spring Kafka framework (or your custom code) will manually commit the offset _after_ the message has been successfully processed. This prevents data loss if the application crashes mid-processing. In the library this pairs with `AckMode.RECORD` (commit after each record) and graceful shutdown draining — see [[9. Admin & Auto-Configuration]]. When processing throws, the record flows into retry → DLQ instead of being lost, see [[4. Retry and DLQ]].
    

### Polling & Concurrency

- **`maxPollRecords` (500):** When the consumer calls `poll()`, it will fetch a maximum of 500 messages at once. If your processing logic is slow, you should lower this number to ensure the consumer finishes the batch before the broker assumes it has died.
    
- **`concurrency` (3):** In a Spring Boot context, this creates 3 separate consumer threads running in parallel within your application instance. **Crucial note:** This number should never exceed the number of partitions in your topic. If you have 2 partitions and a concurrency of 3, one thread will sit completely idle.
    

### Deserialization & Security

- **`keyDeserializer` & `valueDeserializer`:** These do the exact opposite of the Producer. They take the raw byte arrays from the network and convert the Key back into a `String` and the Value back into a JSON object. In the library both are wrapped in an `ErrorHandlingDeserializer`, so a corrupt/poison-pill message is routed to the DLQ instead of wedging the partition — see [[4. Retry and DLQ]]. For the Avro alternative, see [[6. Serialization (Avro & Schema Registry)]].
    
- **`trustedPackages` ("*"):** Spring's `JsonDeserializer` is strict about security to prevent malicious code execution. It requires you to whitelist the Java packages it is allowed to deserialize into. Using `"*"` allows all packages, which is fine for local development but should be restricted to your specific model packages (e.g., `"com.mycompany.events.*"`) in production. (The library is secure-by-default — blank trusts nothing and takes the type from the listener signature — and logs a loud warning if it sees `"*"`; details in [[6. Serialization (Avro & Schema Registry)]].)
    

### Partition Assignment

- **`partitionAssignmentStrategy` ("...CooperativeStickyAssignor"):** This is an advanced and excellent configuration. When a new consumer joins or leaves the group, Kafka must reassign partitions (a "rebalance"). Older assignors caused a "stop-the-world" event where _all_ consumers stopped reading during the rebalance. The `CooperativeStickyAssignor` allows consumers to keep reading from their current partitions while only reassigning the ones that actually need to move, drastically reducing processing latency during deployments or scaling events.
