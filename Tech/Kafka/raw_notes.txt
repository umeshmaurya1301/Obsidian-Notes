**Exactly-Once Semantics (EOS)** means that across a distributed data pipeline (producer $\rightarrow$ broker $\rightarrow$ consumer), a message is processed and reflected in downstream state **precisely once**, even in the presence of producer retries, network failures, broker crashes, or consumer rebalances.

In distributed systems, the three primary delivery guarantees are:

* **At-most-once:** Messages may be lost, but never duplicated ($0 \le \text{deliveries} \le 1$).
* **At-least-once:** Messages are never lost, but may be duplicated ($1 \le \text{deliveries}$).
* **Exactly-once:** Messages are neither lost nor duplicated ($\text{deliveries} = 1$).

---

**How Kafka Achieves EOS Internally**

True EOS in Kafka is built on two core components: **Idempotent Producers** and the **Transactional Coordinator**.

**1. Producer Idempotency (`enable.idempotence=true`)**

* Prevents duplicates introduced by network retries between producer and broker.
* **Mechanism:**
* The broker assigns each producer a unique **Producer ID (PID)**.
* Every message sent by the producer carries an incrementing **Sequence Number** per topic-partition.
* If a broker receives a batch with a sequence number it has already committed (e.g., if an ACK was dropped and the producer retried), the broker discards the duplicate write while still returning an ACK to the producer.



**2. Transactional Processing (Read-Process-Write)**

* Used when consuming from Kafka, transforming data, and producing back to Kafka.
* **Mechanism:**
* Coordinates writes across multiple topic-partitions and consumer offset commits using a **Transaction Coordinator** and an internal `__transaction_state` topic.
* It follows a **Two-Phase Commit (2PC)**: writes are marked with commit markers.
* Downstream consumers configured with `isolation.level=read_committed` buffer messages and only expose records to the application once the commit marker is received. If a transaction aborts, those records are skipped.



---

**The Critical Nuance: End-to-End vs Within-Kafka**

Kafka's native EOS only applies to the boundary of Kafka itself (**Kafka-in $\rightarrow$ Kafka-out**).

If a consumer reads from Kafka and writes to an external storage system (e.g., MySQL, PostgreSQL, MongoDB), Kafka’s transactional coordinator cannot guarantee atomic commits across both systems without a distributed 2PC or external coordination.

To achieve true end-to-end exactly-once processing with external systems:

* **Idempotent Consumer Writes:** Store the Kafka message offset/unique business ID in the destination database within the same database transaction (e.g., via unique keys, upserts, or an Outbox table).
* **Distributed Locks / Deduplication Keys:** Deduplicate incoming events in Redis or the DB before executing side effects (like calling external 3rd-party APIs).

Here is a detailed breakdown of message delivery guarantees, idempotency configurations, and the exact failure scenario you mentioned. This is a classic SDE 2 interview discussion.

### 1. What are Delivery Guarantees?

In distributed systems, failures are inevitable (network drops, broker crashes, consumer restarts). A **delivery guarantee** defines the contract between the system and the application regarding how these failures are handled and whether a message might be lost or duplicated.

There are three strict categories:

* **At-most-once (Fire and Forget):**
* The producer sends a message and never retries, regardless of whether it receives an acknowledgment (ACK).
* **Result:** Messages might be lost, but they will never be duplicated.


* **At-least-once (Safe but Duplicative):**
* The producer expects an ACK. If it doesn't get one (due to a timeout or error), it retries sending the message.
* **Result:** Messages are never lost, but they can be duplicated if the retry was unnecessary.


* **Exactly-once Semantics (EOS):**
* A combination of mechanisms ensures that even if the producer retries, the broker only commits the message once, and the consumer processes it once.
* **Result:** No data loss, no duplicates.



---

### 2. How Idempotency is Configured

Idempotency in Kafka is a producer-side feature. You enable it in the producer properties when initializing your Kafka client.

In Java (Spring Boot or vanilla Kafka client), it looks like this:

```java
Properties props = new Properties();
// Other configs like bootstrap servers...
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, "true");
props.put(ProducerConfig.ACKS_CONFIG, "all"); // Required for idempotency

```

#### What is `enable.idempotence=true`?

When you set this to true, Kafka guarantees that producer retries will not introduce duplicate records into the Kafka topic.

* **How it works:** When the producer starts, the broker assigns it a unique **Producer ID (PID)**. Every message the producer sends is stamped with this PID and an incrementing **Sequence Number** (per topic-partition). The broker keeps track of the largest sequence number it has successfully committed for that PID.
* *Note for interviews: Starting from Kafka 3.0, `enable.idempotence` is `true` by default.*

#### What if `enable.idempotence=false`?

If disabled, the producer operates in standard **At-least-once** mode.

* It does not track sequence numbers.
* If the producer retries a message, the broker treats it as a brand-new message and appends it to the log again.
* Furthermore, if you have `max.in.flight.requests.per.connection > 1`, a retry can cause messages to be written out of order.

---

### 3. The Interview Scenario: The Network Glitch (Lost ACK)

* **The setup:** The producer publishes a message. The broker successfully writes it to the disk/partition and sends an ACK back to the producer.
* **The failure:** Before the ACK reaches the producer, a network glitch occurs. The ACK is dropped.

Here is exactly what happens next, depending on your configuration:

#### Scenario A: `enable.idempotence=false`

1. The producer waits for the ACK. Its `request.timeout.ms` timer expires.
2. The producer assumes the message failed and **retries** sending the exact same payload.
3. The broker receives the payload. Because idempotency is off, the broker has no idea this is a retry. It treats it as a new message.
4. The broker writes the duplicate message to the partition and sends a new ACK.
5. **Result:** Your topic now contains two identical messages. You have achieved **At-least-once** delivery, resulting in a duplicate downstream.

#### Scenario B: `enable.idempotence=true`

1. The producer waits for the ACK, times out, and **retries** sending the message.
2. Crucially, this retry carries the **exact same PID and Sequence Number** as the original attempt.
3. The broker receives the request, inspects the PID and Sequence Number, and checks its cache.
4. The broker realizes: *"Wait, I already committed Sequence Number 5 for this PID."*
5. The broker **silently drops the duplicate write** (it does not append it to the log again), but it **returns a success ACK** back to the producer.
6. **Result:** The producer receives the ACK and moves on. The topic contains only one copy of the message. You have successfully handled a network failure with **Exactly-once** guarantees at the producer level.

These are two very different concepts that often get confused in interviews. Let's break them down clearly.

### 1. Broker Write Commit vs. Consumer Offset Commit

When you hear the word "commit" in Kafka, you have to ask: *Who is doing the committing?*

**The Broker Commit (Producer Idempotency)**

* **What it is:** This happens when the producer sends a message to the broker. The broker writes the message to the physical topic partition log on disk.
* **The "Sequence Number" Check:** As mentioned in the previous scenario, the broker keeps a small in-memory cache of the latest Sequence Number it received for a specific Producer ID (PID). If the producer retries Sequence Number 5, the broker checks this cache, sees it already has 5, and drops the duplicate.
* **Purpose:** To protect the topic from getting duplicate messages caused by **producer retries** during network blips.

**The Consumer Offset Commit**

* **What it is:** This happens on the other end of the pipeline. A consumer pulls a message, processes it (e.g., updates a database), and then tells Kafka, "I have successfully processed up to offset 1045."
* **How it works:** The consumer doesn't update the actual topic. Instead, it writes a message to a hidden internal Kafka topic called `__consumer_offsets`.
* **Purpose:** To act as a "bookmark." If the consumer application crashes and restarts, it reads `__consumer_offsets` to figure out where to resume processing, ensuring it doesn't process old messages again.

---

### 2. Production Fintech: What Semantics Are Preferred?

You might assume that because fintech systems (like UPI payment switches, core banking ledgers, or payment gateways) deal with money, they strictly use Kafka's internal **Exactly-Once Semantics (EOS)**.

**This is a trap. In reality, the industry standard is At-Least-Once delivery paired with rigorous Consumer-Side Idempotency.**

Here is why:

#### Option A: Kafka's Exactly-Once Semantics (Transactions)

Kafka's EOS relies on the Transaction Coordinator and a Two-Phase Commit (2PC) protocol to group messages.

* **The Fatal Flaw for Fintech:** Kafka's EOS is only guaranteed **Kafka-in to Kafka-out**. If your consumer reads an event from a topic, processes a payment, and writes the updated balance to a PostgreSQL database, Kafka's transaction coordinator cannot control PostgreSQL. If the consumer dies after updating the DB but before committing the Kafka offset, Kafka will replay the message on restart. You will process the payment twice.
* **Pros:** Perfect for pure stream processing (e.g., Kafka Streams or Flink reading from Topic A, aggregating fraud metrics, and writing to Topic B).
* **Cons:** Introduces latency and performance overhead due to transaction markers. It does not solve the end-to-end database write problem.

#### Option B: At-Least-Once + Idempotent Database Writes (The Standard)

Because Kafka cannot guarantee EOS when external databases are involved, large distributed systems embrace **At-Least-Once** delivery and handle deduplication at the destination.

* **How it works:** The system accepts that Kafka might deliver the same payment event twice. To fix this, the consumer logic is built to be strictly idempotent.
* **Implementation:** You include a unique idempotency key (like a `transaction_id` or `retrieval_reference_number`) in the Kafka message. When the consumer processes the message, it uses an `INSERT ... ON CONFLICT DO NOTHING` (upsert) in the database, or checks a distributed Redis lock.
* **Pros:**
* Massive throughput and lower latency because you aren't waiting on Kafka's transaction coordinator.
* Absolute guarantee of financial consistency, because the source of truth (the database) enforces the idempotency.


* **Cons:** Requires rigorous discipline from the engineering team. Every single downstream consumer must be explicitly designed to handle duplicates safely.

**The Takeaway:** Do not rely on Kafka to magically solve end-to-end exactly-once delivery when external systems are involved. Accept duplicates from Kafka (At-Least-Once), but neutralize them in your database.

### 1. When is At-Most-Once (`acks=0`) used?

At-most-once is used strictly when **throughput and ultra-low latency are the highest priority, and occasional data loss is completely acceptable.** The producer fires the message into the network buffer and moves on, without waiting for the broker to acknowledge it.

In a UPI payment system, you would never use this for an Acquirer or Issuer switch transaction payload—if a message drops, money is lost or a transaction hangs.

However, you **would** use it for:

* **High-volume telemetry & metrics:** Streaming CPU, memory, or thread-count stats from your microservices.
* **Non-critical logging:** Shipping debug or trace logs to a centralized logging system (like ELK).
* **Analytics and Clickstreams:** Tracking user navigation events. If you lose 20 out of 50,000 "button click" events, the analytics dashboard is fundamentally unaffected, but your system saved massive network and I/O overhead by not waiting for ACKs.

You are **incorrect** on a crucial detail here. There is a logical contradiction in your statement: *"broker was not able to commit... realizes message already produced"*.

If the broker failed to commit the message initially, it cannot possibly realize it was already produced during the retry!

2. Broker fails to write it to the partition log. It returns an error (or times out).
3. Producer retries sending the exact same message (PID: A, Seq: 5).
4. Broker receives it. It checks its cache and says, *"I do not have Seq 5 committed."*
5. Broker successfully writes it to the log now, and returns a success ACK.

**Scenario B: The broker committed successfully, but the network dropped the ACK**

1. Producer sends message (PID: A, Seq: 5).
2. Broker writes it to the partition log successfully.
3. Broker sends the ACK, but a network glitch destroys the ACK before it reaches the producer.
4. Producer times out and retries sending (PID: A, Seq: 5).
5. Broker receives it. It checks its cache and says, *"Wait, I already committed Seq 5 for PID A."*
6. Broker **silently drops the duplicate** (does not write to disk again) but returns a success ACK to the producer to resolve the retry loop.

### 3. Clarifying At-Least-Once

You are **completely incorrect** here.

If you are operating in standard At-Least-Once semantics, `enable.idempotence` is set to `false`.

Because idempotency is off, **there is no PID and no Sequence Number.** The producer doesn't generate them, and the broker doesn't track them.

Here is what actually happens:

1. Producer sends a raw payload.
2. Broker commits it and sends an ACK, but the ACK is lost in the network.
3. Producer times out and resends the exact same raw payload.
4. The broker has no memory of previous requests. It treats this as a brand-new, completely independent message.
5. The broker writes it to the partition again. You now have a duplicate in your topic.

**A critical note on Sequence Numbers:**
Even if you had idempotency enabled, a retry **never** increments the sequence number. If a producer retried with an incremented sequence number, the broker would think it's a brand-new message and write it, defeating the entire purpose of idempotency. Sequence numbers only increment for brand-new, unique messages in the application code.

In production distributed systems—especially fintech, payment gateways, and core banking—the architecture relies on **At-Least-Once delivery coupled with strict consumer-side idempotency** rather than relying on broker-level transactions.

Here is the operational breakdown of why this architectural pattern is standard and how each layer functions:

**1. The Dual-System Boundary Problem**
Kafka’s built-in Exactly-Once Semantics (via the Transaction Coordinator and 2PC) only guarantees atomicity **Kafka-in to Kafka-out** (e.g., reading from Topic A and producing to Topic B via Kafka Streams).

In fintech, consumer side-effects almost always cross network and storage boundaries:

* Writing ledger entries to an RDBMS (PostgreSQL, MySQL, Oracle).
* Calling downstream third-party APIs (payment switches, clearing houses, card networks).
* Mutating distributed caches (Redis).

Kafka cannot coordinate a distributed transaction across external databases or third-party HTTP endpoints without massive latency overhead, distributed deadlocks, and failure points.

**2. The End-to-End Production Pattern**
To achieve absolute consistency, high-throughput systems split the responsibility across three distinct stages:

* **Producer Layer (Guaranteed Publishing):**
Producers run with `enable.idempotence=true` and `acks=all` (often paired with the **Transactional Outbox Pattern** to prevent the dual-write problem between the local DB and Kafka).
* **Transport Layer (At-Least-Once Delivery):**
Kafka guarantees that no message is lost. If a consumer crashes mid-processing or a rebalance occurs before an offset is committed, the message is redelivered.
* **Consumer Layer (Deterministic Deduplication):**
The consumer treats every incoming payload as potentially duplicated and enforces deduplication natively at the persistence layer using:
* **Unique Constraints / Upserts:** Enforcing a unique database index on a natural business key (e.g., `transaction_id`, `reference_number`).
* **Idempotency Keys & Status Checks:** Querying an `idempotency_keys` table inside the same ACID database transaction before applying state mutations.
* **Distributed Locks (Redis/Redlock):** Preventing race conditions when identical events land concurrently across different consumer threads.



Because external side-effects and cross-system state changes cannot be rolled back by Kafka, large-scale fintech systems universally adopt this model: **accept at-least-once delivery over the wire, and enforce exactly-once execution at the database boundary.**

These three concepts are the backbone of distributed consistency. In an SDE 2 interview, it is not enough to define them; you must understand their failure modes and when to use which.

Let's break them down using a high-throughput fintech context, like an Acquirer Switch processing UPI transactions.

### 1. Database Unique Constraints (Upsert)

This is your first line of defense and the most robust way to ensure exactly-once processing when your **only side effect is updating a database.**

* **What it is:** You rely on the ACID properties of your relational database (like PostgreSQL or MySQL) to reject duplicate processing.
* **How it works:** Every Kafka message must contain a unique business identifier (e.g., an RRN - Retrieval Reference Number, or a `transaction_id`). You place a `UNIQUE` index on this column in your database table.
* **Execution:** When the consumer pulls a message, it executes an "Upsert" (Insert or Update):
```sql
INSERT INTO upi_transactions (rrn, amount, status)
VALUES ('123456789012', 500, 'SUCCESS')
ON CONFLICT (rrn) DO NOTHING;

```


* **The SDE 2 Catch:** If the Kafka message is a duplicate, the database effortlessly ignores it. However, this **only** works if you aren't doing anything else. If your consumer also makes an HTTP call to NPCI or a core banking system before writing to the database, the DB constraint will not prevent that HTTP call from happening twice.

### 2. Distributed Locks (Redis)

You use distributed locks when you have **external side effects** that cannot be rolled back by a database transaction (like calling a 3rd-party API).

* **What it is:** A mutual exclusion mechanism. Since you might have 50 consumer instances running, you need a centralized place to say, "I am currently processing transaction 12345, nobody else touch it."
* **How it works:**
1. Consumer receives RRN `12345`.
2. It calls Redis: `SET rrn:12345 "processing" NX EX 30` (Set Not Exists, with a 30-second Time-To-Live).
3. If Redis returns `OK`, this consumer has the lock. It calls the external API, updates the DB, and then updates the Redis key to "completed".
4. If Redis returns `NULL`, another consumer is already handling it (or already finished it), so this consumer skips the message.


* **The SDE 2 Catch (Pushback):** Relying solely on Redis locks for financial consistency is a massive red flag. What happens if the consumer acquires the lock, takes 35 seconds to process, and the lock's TTL expires at 30 seconds? Another consumer will pick up the duplicate message, acquire a fresh lock, and you now have a race condition leading to double-processing. **Always use locks for efficiency (to prevent concurrent duplicate API calls), but use the Database Unique Constraint as the ultimate source of truth.**

### 3. The Outbox (and Inbox) Pattern

There is a slight misconception in your premise here. The **Outbox Pattern** is primarily used to guarantee idempotency and consistency on the *Producer* side (solving the "Dual-Write Problem"). To solve consumer-side idempotency, you use its sibling: the **Inbox Pattern** (or Idempotency Table).

**The Dual-Write Problem:**
You need to update a wallet balance in Postgres AND publish a "WalletUpdated" event to Kafka. You cannot wrap Postgres and Kafka in a single transaction. If Postgres commits but Kafka crashes, you have an inconsistent system.

**The Solution (Outbox for Producers):**

1. You create an `outbox_events` table in the same Postgres database.
2. In a single DB transaction, you update the wallet balance AND insert the Kafka payload into `outbox_events`. If either fails, the DB rolls back.
3. A separate asynchronous process (like Debezium via Kafka Connect) reads the `outbox_events` table and guarantees it gets pushed to Kafka.

**The Solution (Inbox/Idempotency Table for Consumers):**
When consuming, you want to guarantee you don't process the same message twice.

1. You create an `idempotency_keys` table in your consumer's database.
2. When a Kafka message arrives, you open a DB transaction.
3. You attempt to `INSERT INTO idempotency_keys (message_id) VALUES (...)`.
4. If it fails (due to a unique constraint violation), it means you already processed this message. You abort the transaction and commit the Kafka offset.
5. If it succeeds, you execute your business logic (update balances, etc.) and commit the DB transaction.

### Summary: How to Architect It

If you are asked to design a fault-tolerant payment consumer, you do not choose just one of these. You combine them:

1. Use **Redis Distributed Locks** to prevent two concurrent threads from processing the same duplicate message at the exact same millisecond.
2. Use an **Inbox/Idempotency Table** (or DB Unique Constraints) within a single ACID transaction to guarantee the state is only mutated once.

## Q1. What happens if partitions are increased while a message is being processed?

Suppose:

```text
Account A -> Partition 3 -> Consumer 1
```

Consumer 1 has already polled the message but has not committed the offset yet.

Now partitions increase:

```text
8 partitions -> 16 partitions
```

Kafka triggers a **rebalance**.

Your concern:

```text
Consumer 1 processing message
Consumer 2 gets same partition
Consumer 2 processes same message
```

### What actually happens?

During rebalance:

1. Kafka revokes partitions from Consumer 1.
2. Consumer 1 is expected to stop processing and release ownership.
3. Partition gets assigned to Consumer 2.
4. Consumer 2 starts from the **last committed offset**.

The real issue is not two consumers owning the partition simultaneously.

The real issue is:

```text
Consumer 1 processed txn
Offset not committed
Rebalance happens
Consumer 2 reads same message again
```

Result:

```text
Duplicate processing
```

This can happen.

### How fintech systems handle it

Never rely solely on Kafka for exactly-once business processing.

Use:

```text
txn_id (idempotency key)
```

Example:

```sql
INSERT INTO processed_txn(txn_id)
```

with

```sql
UNIQUE(txn_id)
```

If Consumer 2 replays:

```text
txn_id already exists
```

Transaction is ignored.

So:

```text
Kafka = At least once
Business layer = Exactly once
```

---

### What about partition count increase?

Another subtle issue:

Kafka partition selection:

```java
partition = hash(key) % numPartitions
```

If partitions change:

```text
hash(accountA)%8 = 3
hash(accountA)%16 = 11
```

Future messages may go to Partition 11.

Old messages remain in Partition 3.

New messages go to Partition 11.

Therefore ordering across old and new messages can be affected.

Because of this, many payment systems:

```text
Avoid increasing partitions frequently
```

or

```text
Pre-create enough partitions
```

or

```text
Use custom partitioners
```

for critical ordered streams.

---

# Q2. What if Redis fails?

Excellent question.

Suppose:

```text
Consumer 1 acquires lock
Redis crashes
```

Now lock disappears.

Consumer 2 may acquire lock.

You lose mutual exclusion.

### Single Redis Instance

```text
Redis
  ↑
SPOF
```

Not acceptable for critical systems.

---

### Option 1: Redis Sentinel

```text
Master
  ↓
Replica
  ↓
Replica
```

Failover occurs automatically.

Problem:

Replication is asynchronous.

Scenario:

```text
Lock written on Master
Master crashes
Replication not completed
```

Replica becomes Master.

Lock vanished.

Another consumer acquires lock.

Now two processors exist.

This is a classic distributed lock problem.

---

### Option 2: Redis Cluster

Same issue.

Cluster improves availability.

It does NOT guarantee lock correctness.

---

### Option 3: Redlock

Redis creator proposed:

```text
5 Redis nodes
Acquire lock on majority
```

Example:

```text
Node1 ✓
Node2 ✓
Node3 ✓
Node4 ✗
Node5 ✗
```

3/5 majority => lock acquired.

This reduces risk.

But many distributed systems experts still debate whether Redlock provides sufficient guarantees for critical financial operations.

---

# Then why use Redis lock at all?

Because Redis locks are usually for:

```text
coordination
```

not

```text
money correctness
```

Examples:

### Good Use Cases

```text
Run settlement job once
Generate statement once
Run scheduler once
Prevent duplicate notification
Prevent duplicate webhook processing
```

For these, Redis is great.

---

### Bad Use Case

```text
Account balance correctness depends solely on Redis lock
```

Dangerous.

If Redis fails:

```text
double debit
double credit
```

can occur.

---

# What do fintech systems use for correctness?

Usually the database.

Example:

```sql
SELECT balance
FROM account
WHERE id=123
FOR UPDATE;
```

Now:

```text
Txn-1 gets row lock
Txn-2 waits
```

DB becomes the source of truth.

Or optimistic locking:

```sql
version = 5
```

Update:

```sql
UPDATE account
SET balance=?, version=6
WHERE version=5
```

If another transaction already updated:

```text
0 rows updated
```

Retry.

# Senior-Level Takeaway

For monetary transactions:

```text
Kafka partitioning
        +
Idempotency
        +
DB row locking / optimistic locking
```

is the primary correctness mechanism.

Redis distributed locks are typically:

```text
Performance optimization
Coordination mechanism
Duplicate-work prevention
```

but should not be the only thing preventing financial inconsistencies. That's the distinction interviewers are usually looking for.
