# Retry & DLQ

When a consumer's business logic throws, the record must not be silently lost, nor should it block the partition forever, nor be retried infinitely. `infra-kafka` gives every listener **automatic retry with exponential backoff → Dead Letter Queue (DLQ)** out of the box, with two retry strategies and a per-listener opt-out.

This is **Phase 3** of the library (`org.infra.kafka.retry` + `org.infra.kafka.error`).

---

## 1. The big picture

```
 record consumed
      │
      ▼
 deserialize ──fail──▶ DeserializationErrorHandler ──▶ DLQ  (no retry — corrupt bytes never fix themselves)
      │ ok
      ▼
 @InfraKafkaListener body
      │ throws
      ▼
 DefaultKafkaErrorHandler
      ├─ non-retryable exception? ──────────▶ DLQ immediately
      └─ retryable? → retry w/ backoff → exhausted ──▶ DLQ
```

Two distinct failure classes are handled by two distinct components:

| Failure | Handler | Behaviour |
|---------|---------|-----------|
| **Deserialization** (corrupt / schema mismatch / poison pill) | `DeserializationErrorHandler` | Straight to DLQ — retrying is pointless |
| **Business logic exception** | `DefaultKafkaErrorHandler` | Classify → retry with backoff → DLQ |

---

## 2. Why deserialization errors are special

If the raw bytes can't be turned into your object, **no number of retries will help** — the bytes are the same every time. Worse, a naive consumer would crash on the record, re-poll, get the *same* record, and crash again forever (the classic **poison pill** that halts a partition).

The library prevents this in `KafkaConsumerConfig` by wrapping the real deserializer in Spring Kafka's **`ErrorHandlingDeserializer`**:

```java
config.put(KEY_DESERIALIZER_CLASS_CONFIG,   ErrorHandlingDeserializer.class);
config.put(VALUE_DESERIALIZER_CLASS_CONFIG, ErrorHandlingDeserializer.class);
config.put(ErrorHandlingDeserializer.VALUE_DESERIALIZER_CLASS, JsonDeserializer.class);
```

Instead of throwing during the poll, a failed deserialization is captured as a `DeserializationException` *inside the record value*. `DeserializationErrorHandler` detects it and routes the raw record to `<topic><dlq-suffix>`, stamping diagnostic headers:

- `X-Infra-DLQ-Reason = DESERIALIZATION_ERROR`
- `X-Infra-Original-Topic`
- `X-Infra-Exception-Message`

> [!info] Why this matters
> Without `ErrorHandlingDeserializer`, one malformed message can wedge an entire partition indefinitely. This wrapping is the single most important resilience default in the consumer config.

## 3. Blocking vs Non-blocking retry

The retry strategy is selected by **`infra.kafka.retry.mode`** (`RetryProperties.RetryMode` enum):

| | **BLOCKING** (default) | **NON_BLOCKING** |
|---|---|---|
| Where retries happen | In place, on the consuming container (in-memory backoff) | Records forwarded to dedicated **retry topics** |
| Property | `retry.mode: blocking` | `retry.mode: non-blocking` |
| Ordering | ✅ Preserves per-partition order | ⚠️ Retried records may be processed **out of order** |
| Throughput | ⚠️ Partition is **paused** during a record's backoff | ✅ Original partition never blocks |
| Topics needed | Just the DLQ | `<topic>-retry-0`, `-retry-1`, … + DLT |
| Built on | `DefaultErrorHandler` + `ExponentialBackOff` | Spring Kafka `@RetryableTopic` infra |
| Per-listener opt-out | ✅ supported | ❌ global config governs all listeners |

**Rule of thumb:** choose **BLOCKING** when strict per-key ordering matters more than throughput; choose **NON_BLOCKING** when availability/throughput matters and a downstream dependency (DB, API) may be transiently down for seconds.

### 3.1 Blocking mode — `DefaultKafkaErrorHandler`

Wraps Spring Kafka's `DefaultErrorHandler` with an `ExponentialBackOff` and a `DeadLetterPublishingRecoverer`:

```java
ExponentialBackOff backOff = new ExponentialBackOff(initialIntervalMs, backoffMultiplier);
backOff.setMaxInterval(maxIntervalMs);
backOff.setMaxAttempts(maxAttempts - 1);   // maxAttempts counts the first delivery
DefaultErrorHandler delegate = new DefaultErrorHandler(recoverer, backOff);
```

Retry sequence with defaults (`max-attempts=3`, `initial=1000ms`, `multiplier=2.0`, `cap=10000ms`):

```
Attempt 1 (original) → fail
Attempt 2 → wait 1s  → fail
Attempt 3 → wait 2s  → fail
exhausted → DLQ (order-events-dlq)
```

During each backoff the **partition is paused** — that is the cost of preserving ordering.

### 3.2 Non-blocking mode — `NonBlockingRetryConfig`

Activated by `@ConditionalOnProperty(retry.mode=non-blocking)`. It declares a global `RetryTopicConfiguration` bean, which bootstraps Spring Kafka's retry-topic feature for **every** listener:

```java
RetryTopicConfigurationBuilder.newInstance()
    .maxAttempts(retry.getMaxAttempts())
    .exponentialBackoff(initial, multiplier, maxInterval)
    .retryTopicSuffix(retry.getRetryTopicSuffix())   // "-retry"
    .dltSuffix(dlq.getSuffix())                        // "-dlq"
    .notRetryOn(IllegalArgumentException.class)        // mirrors blocking classification
    .notRetryOn(IllegalStateException.class)
    .notRetryOn(NullPointerException.class)
    .doNotRetryOnDltFailure();
```

A failing record is **forwarded** to a delayed retry topic and re-consumed later, so the source partition keeps flowing.

```
order-events ─fail─▶ order-events-retry-0 (1s) ─fail─▶ order-events-retry-1 (2s) ─fail─▶ order-events-dlq
```

**Topic creation:** retry/DLT topics must exist. When `retry.auto-create-retry-topics=true` (default), the config supplies a dedicated `KafkaAdmin` (pointed at `infra.kafka.bootstrap-servers`, with security applied) so Spring Kafka can create them — controllable via `retry-topic-partitions` / `retry-topic-replication-factor`.

> [!warning] Ordering trade-off
> Non-blocking retry trades **strict per-key ordering during failures** for availability: a retried record (delayed on a retry topic) can be processed *after* later records from the same source partition. If your consumer relies on ordering, stay on BLOCKING.

## 4. Two container factories — retry vs no-retry

Retry behaviour is a property of the **listener container factory**, so it's selected *per listener* (`InfraKafkaListener` exposes two factory bean-name constants):

| Constant | Bean name | Behaviour |
|----------|-----------|-----------|
| `RETRYING_CONTAINER_FACTORY` (default) | `infraKafkaListenerContainerFactory` | retry w/ backoff → DLQ |
| `NON_RETRYING_CONTAINER_FACTORY` | `infraKafkaNoRetryListenerContainerFactory` | straight to DLQ on **first** failure |

```java
// default — retries then DLQs
@InfraKafkaListener(topics = "inventory-events", groupId = "inventory-service")
public void handleInventory(@Payload InventoryEvent e) { inventoryService.reserve(e); }

// opt OUT of retries — non-transient event types
@InfraKafkaListener(
    topics = "audit-events",
    groupId = "inventory-service",
    containerFactory = InfraKafkaListener.NON_RETRYING_CONTAINER_FACTORY)
public void handleAudit(@Payload AuditEvent e) { auditService.record(e); }
```

The no-retry factory is backed by `infraKafkaNoRetryErrorHandler` — a `DefaultKafkaErrorHandler` constructed with **`maxAttempts=1`** (zero retries → immediate DLQ).

> [!note] This replaces the old `retryable` flag
> An earlier version had a `retryable` attribute on the annotation that had **no effect** (retry is a factory concern, not an annotation concern). It was replaced by explicit, verifiable container-factory selection.
>
> **Non-blocking caveat:** the per-listener opt-out is a **blocking-mode** feature. In non-blocking mode the global `RetryTopicConfiguration` governs every listener — `KafkaConsumerConfig` deliberately skips wiring a blocking error handler (`isBlockingRetry()` is false) so the two don't conflict.

## 5. Exception classification (non-retryable)

Some exceptions should **never** be retried — a validation failure or a null field will fail identically every time. `DefaultKafkaErrorHandler` seeds a non-retryable list:

```java
IllegalArgumentException.class
IllegalStateException.class
NullPointerException.class
```

Add your own (e.g. `InvalidSchemaException`, `JsonParseException`) via `addNotRetryable(Class)`. These skip retries and go straight to the DLQ. The non-blocking config mirrors the same three via `.notRetryOn(...)` for consistent behaviour across modes.

| Error type | Example | Strategy |
|-----------|---------|----------|
| **Transient** | network timeout, broker unavailable | retry with backoff |
| **Deserialization** | corrupt message, schema mismatch | DLQ immediately |
| **Business logic** | validation failure, null field | non-retryable → DLQ (or retry if idempotent) |
| **Fatal** | OOM, config error | stop container, alert |

---

## 6. DLQ topic naming & headers

**Naming:** `<original-topic>` + `infra.kafka.dlq.suffix` (default `-dlq`). So `order-events` → `order-events-dlq`.

The `DeadLetterPublishingRecoverer` **preserves the original partition** and appends diagnostic headers to every DLQ message:

| Header | Meaning |
|--------|---------|
| `kafka_dlt-original-topic` | source topic |
| `kafka_dlt-original-partition` | source partition |
| `kafka_dlt-original-offset` | source offset |
| `kafka_dlt-exception-fqcn` | exception class |
| `kafka_dlt-exception-message` | error text |
| `X-Infra-DLQ-Reason` | library classification (e.g. `DESERIALIZATION_ERROR`) |

## 7. Consuming & replaying the DLQ — `DlqHandler`

`DlqHandler` is a utility bean (it does **not** auto-subscribe). A service wires its own listener on the `*-dlq` topic and delegates:

```java
@Component
public class OrderDlqConsumer {
    private final DlqHandler dlqHandler;

    @InfraKafkaListener(topics = "order-events-dlq", groupId = "order-service-dlq")
    public void handleDlq(ConsumerRecord<String, Object> record) {
        dlqHandler.handle(record);          // structured ERROR log with all diagnostic headers
        // dlqHandler.replay(record);       // republish to the original topic (only after the bug is fixed!)
    }
}
```

- **`handle(record)`** — logs the DLQ message at ERROR with every diagnostic header extracted, for searchability in log aggregation.
- **`replay(record)`** — reads `kafka_dlt-original-topic` and republishes `key`+`value` back to the source topic. Guards against a missing original-topic header.

> [!warning] Replay only after the fix
> Replaying a DLQ message before resolving the root cause just cycles it back into the DLQ. For a robust, loop-safe, rate-limited, persisted replay pipeline, see the design in [[enhancments/1. DLQ Enhancment]] (replay service, retry-count headers, Permanent DLQ, replay rate limiting).

## 8. Configuration reference

```yaml
infra:
  kafka:
    retry:
      enabled: true
      mode: blocking                 # blocking (default) | non-blocking
      max-attempts: 3                # total attempts incl. first (3 = 1 original + 2 retries)
      backoff-initial-interval: 1000 # ms
      backoff-multiplier: 2.0
      backoff-max-interval: 10000    # ms (cap)
      # non-blocking only:
      retry-topic-suffix: "-retry"
      auto-create-retry-topics: true
      retry-topic-partitions: 1
      retry-topic-replication-factor: 1
    dlq:
      enabled: true
      suffix: "-dlq"
```

## 9. Interview soundbites

- **"How do you stop a poison pill from wedging a partition?"** → `ErrorHandlingDeserializer` turns a deserialization failure into a value you can route to the DLQ instead of an exception on every poll.
- **"Blocking vs non-blocking retry?"** → blocking = in-memory backoff, preserves order, pauses the partition; non-blocking = retry topics, keeps the partition flowing but loses strict ordering.
- **"Why not retry a validation error?"** → deterministic failures fail identically every time; retrying wastes throughput. Classify them non-retryable → DLQ.
- **"How do you avoid infinite retry loops?"** → capped `max-attempts` → DLQ, and (for replay) a retry-count header + Permanent DLQ.

## 10. What actually happens to DLQ messages in production

Not every DLQ message can (or should) be replayed. The DLQ is not just a "replay buffer" — it exists to **protect partition throughput**, **preserve auditability**, and **trigger operational workflows**.

### Core purposes

| Purpose | Why It Matters |
|---------|---------------|
| **Prevent head-of-line blocking** | A poison pill would otherwise stall the entire partition, creating massive consumer lag for valid messages behind it |
| **Audit trail & compliance** | In regulated systems (fintech, healthcare), silently dropping a message is a critical violation. The DLQ is a 100% durable record |
| **Alerting & anomaly detection** | DLQ traffic should normally be zero. Any message triggers real-time alerts (Datadog / Prometheus / PagerDuty) |
| **Isolated root-cause analysis** | Preserves the exact payload + contextual error headers for debugging without live production memory dumps |

### Handling by failure category

Every DLQ message is enriched with diagnostic headers (original topic, partition, offset, exception name, stack trace). Downstream action depends on **why** it failed:

**1. Schema Mismatches / Serialization Errors (Poison Pills)**

- **Problem:** Producer deployed a new field format that broke consumer deserialization.
- **Action:** Cannot process now. Once the consumer is patched and deployed, an ops tool (or Kafka replay consumer) reads from the DLQ, re-deserializes, and feeds it back into the main pipeline.

**2. Expired / Time-Sensitive Payloads (e.g., Stale Payment Requests)**

- **Problem:** A payment request timed out while sitting in retry topics — executing the debit now would violate business rules.
- **Action:** The system **does not replay**. An automated DLQ consumer triggers a **compensating transaction** (marks the transaction as `FAILED_EXPIRED`, notifies the merchant/user, or cancels the reservation).

**3. Irreparable Data / Invalid Business Data**

- **Problem:** Negative transaction amount, invalid foreign key reference, or corrupt user ID.
- **Action:** Archived to cold storage (S3/GCS or an audit ledger DB) for compliance retention and **discarded** from active processing queues.

> [!tip] Interview Tip
> When asked *"What do you do with DLQ messages?"*, don't just say "replay them." Show you understand that different failure categories require different operational responses — some get replayed, some trigger compensating actions, and some are archived and discarded.
