# Transactions (EOS)

Idempotent producing (see [[2. Producer]]) gives **exactly-once *delivery to a single partition*** during producer retries. But real pipelines are **consume → transform → produce**: read from topic A, do work, write to topic B, commit the offset on A. If the service crashes between the write and the offset commit, you either **reprocess** (duplicate output) or **lose** the offset. **Transactions** make that whole unit atomic — this is **Exactly-Once Semantics (EOS v2)**.

`infra-kafka` **Phase 7** (`org.infra.kafka.transaction`). **Off by default** because it has a real throughput cost.

---

## 1. The problem EOS solves

```
Consumer.poll(topic-A) → transform → Producer.send(topic-B) → commit offset(A)
```

Without transactions, those are separate operations. A crash between `send` and `commit` breaks atomicity:

| Order of ops | Crash effect |
|--------------|--------------|
| commit offset **then** send | offset advanced but output never written → **message lost** |
| send **then** commit offset | output written but offset not advanced → **duplicate output on reprocess** |

EOS wraps the `send`(s) **and** the offset commit in **one Kafka transaction**: either all of it commits, or none of it does. Consumers reading topic B with `isolation.level=read_committed` never see the output of an aborted transaction.

---

## 2. How transactions work (the mechanics)

Three ingredients:

1. **`transactional.id`** — a stable, unique ID per producer instance. On restart, the broker uses it to **fence** the previous (possibly zombie) producer with the same ID via an epoch, so a hung old instance can't commit stale writes. Built on the idempotent producer (PID + sequence numbers).
2. **Transaction coordinator** — a broker-side component backed by the internal `__transaction_state` topic that tracks each transaction's state (Ongoing / PrepareCommit / Complete).
3. **`isolation.level=read_committed`** on consumers — so they skip records from aborted or in-flight transactions.

```
producer.beginTransaction()
   send(topic-B, ...)                     // buffered, marked uncommitted
   sendOffsetsToTransaction(offsets, groupMeta)  // offset commit joins the txn
producer.commitTransaction()              // atomically visible  ── OR ── abort → nothing visible
```

> [!info] EOS v2
> "v2" (Kafka ≥ 2.5) made EOS scale: one producer can commit offsets for a consumer group efficiently, so the consume-transform-produce pattern is practical at throughput. The library targets this.

## 3. What `infra-kafka` wires

Enable it:

```yaml
infra:
  kafka:
    transaction:
      enabled: true
      id-prefix: "txn-order-service-"   # a unique transactional.id prefix per app
```

When `transaction.enabled=true`, three things change across the library:

**a) Producer factory gets a transactional ID prefix** (`KafkaProducerConfig` / `AvroSerializerConfig`):
```java
if (properties.getTransaction().isEnabled())
    factory.setTransactionIdPrefix(properties.getTransaction().getIdPrefix());
```
This flips the `KafkaTemplate` into transactional mode.

**b) Consumers read only committed data** (`KafkaConsumerConfig` / Avro consumer):
```java
config.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed");
```

**c) A `KafkaTransactionManager` bean is registered** (`KafkaTransactionConfig`, gated by `@ConditionalOnProperty(transaction.enabled=true)`):
```java
@Bean
public KafkaTransactionManager<String,Object> kafkaTransactionManager(ProducerFactory<String,Object> pf) {
    return new KafkaTransactionManager<>(pf);
}
```
This integrates Kafka transactions with Spring's `@Transactional`, so a listener method's sends + offset commit run in one transaction.

## 4. Using it — `@Transactional` consume-transform-produce

```java
@Component
public class OrderProcessor {

    private final KafkaMessagePublisher publisher;

    @Transactional("kafkaTransactionManager")
    @InfraKafkaListener(topics = "order-events", groupId = "order-processor")
    public void process(@Payload OrderEvent event) {
        var enriched = enrich(event);
        publisher.send("enriched-orders", event.orderId(), enriched);
        // send + consumed-offset commit are ONE atomic Kafka transaction.
        // Throw anywhere here → transaction aborts, nothing on enriched-orders becomes visible,
        // the offset is NOT advanced, and the record is redelivered.
    }
}
```

The prefix must be **stable per deployment** so fencing works across restarts; Spring appends per-instance suffixes to keep each producer's `transactional.id` unique.

## 5. Cost & when to use it

| | Idempotent producer only | Transactions (EOS) |
|---|---|---|
| Default | ✅ ON | ❌ OFF |
| Guarantee | no dup writes on retry (per partition) | atomic multi-partition write + offset commit |
| Throughput | high | **lower** (coordinator round-trips, commit markers) |
| Latency | low | **higher** (read_committed adds visibility delay) |
| Use when | most services | money movement, no-dup-or-loss pipelines |

> [!warning] Don't turn it on reflexively
> Transactions add latency (commit markers, coordinator round-trips) and consumers pay a visibility delay under `read_committed`. Enable EOS only for pipelines that genuinely need atomic consume-transform-produce (e.g. financial/ledger flows). For most services, `acks=all` + idempotent producer + consumer-side idempotency (DB upserts) is enough. Requires Kafka ≥ 2.5 and, in local KRaft dev, a `transaction.state.log` with enough replicas.

---

## 6. Interview soundbites

- **"Idempotence vs transactions?"** → idempotence stops duplicate *writes* on producer retry (one partition). Transactions make *multiple sends + the offset commit* atomic across partitions — that's exactly-once *processing*.
- **"What's `transactional.id` for?"** → stable identity so the broker can **fence** a zombie producer after restart (epoch bump), preventing stale commits.
- **"What does `read_committed` do?"** → consumers skip records from aborted/in-flight transactions, so they never see rolled-back output.
- **"Why off by default?"** → throughput/latency cost; only worth it for no-dup-no-loss pipelines.
