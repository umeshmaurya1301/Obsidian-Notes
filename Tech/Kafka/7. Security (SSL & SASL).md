# Security (SSL & SASL)

Kafka security answers two orthogonal questions: **"Is the traffic encrypted?"** (SSL/TLS) and **"Who are you?"** (SASL authentication). `infra-kafka` **Phase 6** (`org.infra.kafka.security`) makes both plug-and-play via properties — no client code changes.

Two beans do the work: `KafkaSecurityConfig` (applies protocol + SSL/SASL to any client config map) and `SaslConfigProvider` (builds the JAAS login string).

> [!info] Always present, no-op by default
> Unlike other opt-in phases, the security beans are registered **unconditionally** and imported *first* in the auto-config, because the producer, consumer, Avro, and admin configs all depend on them. When `protocol=PLAINTEXT` (the default) `applySecurity()` returns immediately — it's a fast no-op, so there's zero cost until you turn security on.

---

## 1. The four protocols

`SECURITY_PROTOCOL_CONFIG` = one of:

| Protocol | Encryption (TLS) | Authentication | Use case |
|----------|:---:|:---:|----------|
| `PLAINTEXT` | ❌ | ❌ | local dev only |
| `SSL` | ✅ | ✅ (mutual TLS) | encryption + cert-based auth |
| `SASL_PLAINTEXT` | ❌ | ✅ | auth **without** encryption (trusted network) |
| `SASL_SSL` | ✅ | ✅ | **production recommended** |

The library keys off the string: if it **contains `SSL`** → apply SSL settings; if it **contains `SASL`** → apply SASL settings. So `SASL_SSL` triggers both.

```java
if (protocol == null || "PLAINTEXT".equalsIgnoreCase(protocol)) return; // no-op
config.put(SECURITY_PROTOCOL_CONFIG, protocol.toUpperCase());
if (protocol.contains("SSL"))  applySsl(config, ssl);
if (protocol.contains("SASL")) applySasl(config, sasl);
```

## 2. SASL — authentication

SASL is a pluggable **authentication framework**. Kafka commonly uses:

| Mechanism | How | Notes |
|-----------|-----|-------|
| `PLAIN` | username/password sent to broker | **cleartext** — only safe over `SASL_SSL` |
| `SCRAM-SHA-256` | salted challenge-response | password never sent in the clear |
| `SCRAM-SHA-512` | stronger hash | **preferred** |

### JAAS config generation — `SaslConfigProvider`

Kafka needs a `sasl.jaas.config` string naming a **LoginModule**. `SaslConfigProvider.getJaasConfig()` builds it from the mechanism:

```java
// SCRAM-*  → ScramLoginModule
org.apache.kafka.common.security.scram.ScramLoginModule required
    username="..." password="...";

// PLAIN    → PlainLoginModule
org.apache.kafka.common.security.plain.PlainLoginModule required
    username="..." password="...";
```

`KafkaSecurityConfig.applySasl()` then sets `sasl.mechanism` + `sasl.jaas.config` on the client map.

```yaml
infra:
  kafka:
    security:
      protocol: SASL_SSL
      sasl:
        mechanism: SCRAM-SHA-512
        username: ${KAFKA_USERNAME}      # from env / Vault — never hardcode
        password: ${KAFKA_PASSWORD}
      ssl:
        truststore-location: classpath:kafka-truststore.jks
        truststore-password: ${KAFKA_TRUSTSTORE_PASS}
```

> [!warning] `PLAIN` leaks credentials without TLS
> `SASL_PLAINTEXT` + `PLAIN` sends the password in the clear over the wire. Prefer **SCRAM-SHA-512**, and always pair SASL with SSL (`SASL_SSL`) in production.

## 3. SSL/TLS — encryption & mutual auth

Two stores, two roles:

- **Truststore** — the CA certs the client *trusts*. Needed to verify the **broker's** identity (server auth). This is the minimum for encryption.
- **Keystore** — the client's own cert + private key. Needed only for **mutual TLS (mTLS)**, where the broker also verifies the *client's* identity.

`applySsl()` sets whichever are provided:

```java
if (truststoreLocation) → SSL_TRUSTSTORE_LOCATION_CONFIG + password   // server auth
if (keystoreLocation)   → SSL_KEYSTORE_LOCATION_CONFIG   + password   // client auth (mTLS)
                          + optional SSL_KEY_PASSWORD_CONFIG
```

### mTLS example (protocol `SSL`, no SASL)

```yaml
infra:
  kafka:
    security:
      protocol: SSL
      ssl:
        truststore-location: /certs/truststore.jks
        truststore-password: ${TRUSTSTORE_PASS}
        keystore-location: /certs/keystore.jks     # presence of a keystore ⇒ mTLS
        keystore-password: ${KEYSTORE_PASS}
        key-password: ${KEY_PASS}
```

Supports **JKS** and **PKCS12** store formats.

### Classpath vs filesystem cert resolution

A neat detail: `resolveResource()` accepts Spring locations (`classpath:...`, `file:...`). It tries `resource.getFile()`; if that throws (the cert is **inside a fat JAR** and has no real file path), it **extracts the resource to a temp file** (`deleteOnExit()`) and hands the Kafka client that absolute path — because the native client needs a real filesystem path, not a JAR URL.

```java
try { return resource.getFile().getAbsolutePath(); }      // IDE / unpacked
catch (IOException ex) { return extractToTempFile(resource).getAbsolutePath(); } // fat JAR
```

## 4. Where security gets applied

`KafkaSecurityConfig.applySecurity(config)` is called from **every** client-building path, so security is uniform across the whole library:

| Caller | Client |
|--------|--------|
| `KafkaProducerConfig` | producer |
| `KafkaConsumerConfig` | consumer |
| `AvroSerializerConfig` | Avro producer + consumer |
| `KafkaAdminConfig` | admin (topic auto-create) |
| `NonBlockingRetryConfig` | retry-topic admin |

That last two matter: **admin operations** (creating topics) also need credentials on a secured cluster — a common thing to forget.

---

## 5. Best practices

- **Never hardcode credentials** — inject via env vars / Vault (`${KAFKA_PASSWORD}`), never commit to `application.yml`.
- **Prefer `SASL_SSL` + `SCRAM-SHA-512`** in production.
- **Enable ACLs** on the cluster so each service can only touch its own topics (authorization, the layer *after* authentication).
- **Rotate certificates** on a schedule; JKS/PKCS12 both supported.
- Encrypt in transit (TLS) **and** consider at-rest encryption at the storage layer.

> [!note] AuthN vs AuthZ
> SASL/SSL handle **authentication** (proving identity) and **encryption**. **Authorization** (what an identity may do) is enforced separately by broker-side **ACLs** — the library configures the client credentials; ACLs are a cluster-admin concern.

---

## 6. Interview soundbites

- **"SSL vs SASL?"** → SSL = encryption (+ optional client cert auth); SASL = authentication framework (PLAIN/SCRAM). `SASL_SSL` = both.
- **"Truststore vs keystore?"** → truststore verifies the *broker* (server auth, minimum for TLS); keystore proves the *client* (needed for mTLS).
- **"Why SCRAM over PLAIN?"** → SCRAM is challenge-response; the password never crosses the wire in cleartext.
- **"Certs inside a JAR?"** → the native Kafka client needs a real file path, so the library extracts classpath certs to a temp file at startup.
