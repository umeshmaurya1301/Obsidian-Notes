# Consumer-Side Idempotency & Patterns

Kafka's native EOS only applies to the boundary of **Kafka-in → Kafka-out**. When a consumer writes to an external system (RDBMS, Redis, 3rd-party API), Kafka's Transaction Coordinator **cannot** guarantee atomic commits across both systems. This note covers the patterns that solve this.

---

## 1. The Dual-System Boundary Problem

In fintech, consumer side-effects almost always cross network and storage boundaries:

- Writing ledger entries to an RDBMS (PostgreSQL, MySQL, Oracle)
- Calling downstream 3rd-party APIs (payment switches, clearing houses, card networks)
- Mutating distributed caches (Redis)

Kafka cannot coordinate a distributed transaction across external databases or HTTP endpoints without massive latency overhead, distributed deadlocks, and failure points.

> [!important] Production Standard
> **At-Least-Once delivery + rigorous Consumer-Side Idempotency** is the industry standard for fintech — not Kafka's internal EOS transactions.

---

## 2. Why Not Kafka EOS for External Systems?

| Aspect | Kafka EOS (Transactions) | At-Least-Once + Consumer Idempotency |
|--------|--------------------------|--------------------------------------|
| **Scope** | Kafka-in → Kafka-out only | End-to-end (Kafka → DB / API) |
| **External DB writes** | ❌ Cannot control PostgreSQL | ✅ DB enforces idempotency |
| **Latency** | Higher (transaction markers) | Lower (no coordinator overhead) |
| **Throughput** | Reduced | Massive throughput |
| **Best for** | Pure stream processing (Kafka Streams, Flink) | Payment processing, ledger updates |

**The fatal flaw:** If the consumer dies after updating the DB but before committing the Kafka offset, Kafka replays the message on restart → **double processing**.

---

## 3. The Three Idempotency Mechanisms

### 3.1 Database Unique Constraints (Upsert)

**First line of defense** — the most robust method when the only side effect is a database write.

Every Kafka message must contain a unique business identifier (e.g., RRN, `transaction_id`). Place a `UNIQUE` index on this column:

```sql
INSERT INTO upi_transactions (rrn, amount, status)
VALUES ('123456789012', 500, 'SUCCESS')
ON CONFLICT (rrn) DO NOTHING;
```

- If the message is a duplicate, the database silently ignores it.
- **Limitation:** Only protects database writes. If the consumer also makes an HTTP call to NPCI or a core banking system, the DB constraint won't prevent that call from happening twice.

### 3.2 Distributed Locks (Redis)

Used when there are **external side effects** that cannot be rolled back by a database transaction.

```java
// Acquire lock — Set if Not Exists, with 30s TTL
SET lock:rrn:12345 "consumer-1" NX EX 30
```

**Flow:**
1. Consumer receives RRN `12345`.
2. Calls Redis `SET ... NX EX 30`.
3. If `OK` → acquired lock → process → update Redis to "completed".
4. If `NULL` → another consumer is handling it → skip.
5. After completion → `DEL lock:rrn:12345`.

> [!warning] Redis Locks Are Not Sufficient Alone
> If the consumer holds the lock, takes 35 seconds to process, and the TTL expires at 30 seconds — another consumer acquires a fresh lock → **race condition → double processing**. Always use DB unique constraints as the ultimate source of truth; Redis locks are for **coordination efficiency**, not correctness.

### 3.3 The Outbox & Inbox Patterns

#### Outbox Pattern (Producer Side — Solves the Dual-Write Problem)

**Problem:** You need to update a wallet balance in Postgres **AND** publish a "WalletUpdated" event to Kafka. You cannot wrap Postgres and Kafka in a single transaction.

**Solution:**
1. Create an `outbox_events` table in the same Postgres database.
2. In a **single DB transaction**: update the wallet balance AND insert the Kafka payload into `outbox_events`.
3. A separate async process (e.g., **Debezium** via Kafka Connect) reads `outbox_events` and pushes to Kafka.

#### Inbox Pattern (Consumer Side — Idempotency Table)

**Problem:** Guarantee you don't process the same message twice.

**Solution:**
```sql
CREATE TABLE idempotency_keys (
    message_id VARCHAR(50) PRIMARY KEY,
    processed_at TIMESTAMP DEFAULT NOW()
);
```

1. Message arrives → open a DB transaction.
2. `INSERT INTO idempotency_keys (message_id) VALUES (...)`.
3. If it **fails** (unique constraint violation) → already processed → abort and commit Kafka offset.
4. If it **succeeds** → execute business logic → commit DB transaction.

## 4. The Production Architecture (Combining All Three)

For a fault-tolerant payment consumer, you don't choose just one — you **layer** them:

```text
Kafka Message Arrives
        │
        ▼
┌─────────────────────────┐
│  Redis Distributed Lock │  ← Prevents concurrent duplicate processing
│  SET lock:txn:X NX EX   │    across 50 consumer instances
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│  Inbox/Idempotency Table│  ← DB unique constraint guarantees
│  INSERT ... ON CONFLICT │    state is mutated EXACTLY ONCE
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│  Business Logic         │  ← Update balance, call APIs
│  + DB Row Locking       │
└───────────┬─────────────┘
            ▼
      Commit Kafka Offset
```

**The end-to-end production pattern:**

| Layer | Mechanism | Purpose |
|-------|-----------|---------|
| **Producer** | `enable.idempotence=true` + `acks=all` + Outbox Pattern | Guaranteed, deduplicated publishing |
| **Transport (Kafka)** | At-Least-Once delivery | No message loss; replays on crash/rebalance |
| **Consumer** | Unique constraints + Redis locks + Idempotency table | Deterministic deduplication at persistence layer |

> [!tip] The Takeaway
> Accept duplicates from Kafka (At-Least-Once), but **neutralize them in your database**. Don't rely on Kafka to magically solve end-to-end exactly-once delivery when external systems are involved.
