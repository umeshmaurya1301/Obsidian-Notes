# Delivery Guarantees & Idempotency

In distributed systems, failures are inevitable — network drops, broker crashes, consumer restarts. A **delivery guarantee** defines the contract between the system and the application regarding how these failures are handled and whether a message might be lost or duplicated.

---

## 1. The Three Delivery Guarantees

| Guarantee | Behaviour | Data Loss? | Duplicates? |
|-----------|-----------|:----------:|:-----------:|
| **At-Most-Once** (fire & forget) | Producer sends and never retries | ✅ Possible | ❌ Never |
| **At-Least-Once** (safe but duplicative) | Producer retries on missing ACK | ❌ Never | ✅ Possible |
| **Exactly-Once (EOS)** | Idempotent producer + transactional coordinator | ❌ Never | ❌ Never |

> [!tip] Interview Framing
> Don't just list these — tie them to `acks` and `enable.idempotence` configs. Interviewers want you to connect the guarantee to the mechanism.

---

## 2. At-Most-Once (`acks=0`)

The producer fires the message into the network buffer and moves on **without waiting** for any broker acknowledgment.

**When to use** — only when throughput and ultra-low latency are the highest priority and occasional data loss is completely acceptable:

- **High-volume telemetry & metrics** — streaming CPU, memory, thread-count stats from microservices.
- **Non-critical logging** — shipping debug / trace logs to a centralized logging system (ELK).
- **Analytics & clickstreams** — tracking user navigation events. Losing 20 out of 50,000 "button click" events doesn't affect the dashboard, but the system saves massive I/O overhead.

> [!warning] Never for Payments
> In a UPI/payment system you would **never** use `acks=0` for transaction payloads — a dropped message means money is lost or a transaction hangs.

---

## 3. At-Least-Once (Default without Idempotency)

The producer expects an ACK. If it doesn't get one (timeout / error), it **retries**. Messages are never lost, but can be duplicated if the retry was unnecessary.

When `enable.idempotence=false`:
- No PID, no sequence numbers — the broker has no memory of previous requests.
- A retry is treated as a brand-new message → **duplicate in the topic**.
- With `max.in.flight.requests.per.connection > 1`, a retry can also cause **out-of-order** writes.

---

## 4. Exactly-Once Semantics (EOS)

True EOS in Kafka is built on two core components: **Idempotent Producers** and the **Transaction Coordinator**.

### 4.1 Idempotent Producer (`enable.idempotence=true`)

Prevents duplicates introduced by network retries between producer and broker.

```java
Properties props = new Properties();
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, "true");
props.put(ProducerConfig.ACKS_CONFIG, "all"); // Required for idempotency
```

**Mechanism:**
1. Broker assigns each producer a unique **Producer ID (PID)**.
2. Every message carries an incrementing **Sequence Number** per topic-partition.
3. If the broker receives a batch with an already-committed sequence number (e.g., ACK was dropped and the producer retried), it **discards the duplicate write** but still returns a success ACK.

> [!info] Default Since Kafka 3.0
> `enable.idempotence` is `true` by default starting from Kafka 3.0.

### 4.2 Transactional Processing (Read-Process-Write)

Used when consuming from Kafka, transforming data, and producing back to Kafka (see [[8. Transactions (EOS)]]).

- Coordinates writes across multiple topic-partitions and consumer offset commits using a **Transaction Coordinator** and the internal `__transaction_state` topic.
- Follows a **Two-Phase Commit (2PC)**: writes are marked with commit markers.
- Downstream consumers with `isolation.level=read_committed` buffer messages and only expose records once the commit marker is received. Aborted transactions are skipped.

## 5. The Lost-ACK Scenario (Classic Interview Question)

**Setup:** Producer publishes a message → broker writes it to disk → broker sends ACK → **network glitch drops the ACK** before it reaches the producer.

### Without Idempotency (`enable.idempotence=false`)

```text
1. Producer waits → request.timeout.ms expires
2. Producer retries (raw payload, no PID/SeqNum)
3. Broker treats it as a new message → writes duplicate
4. Result: TWO identical messages in the partition
```

### With Idempotency (`enable.idempotence=true`)

```text
1. Producer waits → timeout → retries with SAME PID + Seq#5
2. Broker checks cache: "Seq#5 for this PID already committed"
3. Broker DROPS the duplicate write (no disk append)
4. Broker returns success ACK to resolve the retry loop
5. Result: ONE message in the partition ✓
```

### When the Broker Actually Failed to Commit

```text
1. Producer sends (PID: A, Seq: 5)
2. Broker fails to write (disk full, partition offline) → returns error
3. Producer retries (PID: A, Seq: 5)
4. Broker checks cache: "I do NOT have Seq#5 committed"
5. Broker writes successfully → returns ACK
6. Result: ONE message in the partition ✓
```

> [!important] Sequence Numbers Never Increment on Retry
> A retry **never** increments the sequence number. If it did, the broker would treat it as a brand-new message — defeating the purpose of idempotency entirely. Sequence numbers only increment for genuinely new messages.

---

## 6. Broker Commit vs Consumer Offset Commit

Two completely different operations that use the same word "commit":

| Aspect | Broker Write Commit | Consumer Offset Commit |
|--------|-------------------|----------------------|
| **Who** | Broker (on message arrival) | Consumer (after processing) |
| **What** | Appends message to partition log on disk | Writes position to `__consumer_offsets` topic |
| **Purpose** | Protect topic from producer-retry duplicates (via PID + Seq#) | Bookmark — so a restarted consumer knows where to resume |
| **Scope** | Producer → Broker boundary | Consumer → Broker boundary |

> [!tip] Interview Tip
> When you hear "commit" in a Kafka interview, always clarify **which** commit. This distinction is a strong differentiator.

## 7. Kafka Offset Limits & Retention

### Are Offsets Bounded?

Yes, but the limit is practically unreachable. Offsets are stored as a **64-bit signed long (`int64`)**:

```text
Max value: 9,223,372,036,854,775,807 ≈ 9.2 quintillion
```

| Throughput | Time to Exhaust |
|------------|----------------|
| 1 million msg/sec | ~292,000 years |
| 10 million msg/sec | ~29,000 years |

For practical purposes, you'll never hit the limit. Before that could happen, the topic would be recreated, the cluster migrated, and retention would have removed old data millions of times over.

### Why Are Offsets Never Reused?

Offsets are used for consumer position tracking, ordering guarantees, replication, recovery, and rebalancing. Reusing them would create ambiguity:

```text
Offset 500 → Which message is it?
  • The original one?
  • A new one written after retention deleted the old one?
```

Kafka avoids this entirely by **never reusing offsets** — they are a strictly monotonic sequence per partition.

### Log Start Offset & Log End Offset

After retention deletes old messages, Kafka tracks the valid range:

```text
Retention removed offsets 0–799

Log Start Offset = 800   (earliest available message)
Log End Offset   = 1501  (next offset to be written)
```

If a consumer tries to read `offset = 100`, Kafka responds with an **`OffsetOutOfRangeException`**.

The `auto.offset.reset` config then decides where to start:

| Setting | Behaviour |
|---------|-----------|
| `earliest` | Start from Log Start Offset (800) |
| `latest` | Start from Log End Offset (1501) |
| `none` | Throw exception — consumer must handle it |

> [!tip] Interview Note
> *"If old messages are deleted, how does Kafka know where a consumer can start?"* — this Log Start / End Offset question is asked more often than offset overflow. Know both.
