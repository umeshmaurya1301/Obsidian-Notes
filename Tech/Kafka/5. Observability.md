# Observability

A message bus you can't see into is a liability. `infra-kafka` **Phase 4** (`org.infra.kafka.observability`) gives every produced and consumed message **structured logging**, **correlation-ID propagation via MDC**, and **Micrometer metrics** — with zero code in the consuming service. All of it is wired by `ObservabilityConfig`.

Three pillars: **Logs** (what happened), **Metrics** (how much / how fast), **Traces/Correlation** (tying a request chain together).

---

## 1. What gets wired

`ObservabilityConfig` creates three beans, each guarded by `@ConditionalOnMissingBean`:

| Bean | Side | Enabled when | Purpose |
|------|------|--------------|---------|
| `KafkaLoggingInterceptor` | Producer | `infra.kafka.logging.enabled=true` (default) | pre-send / post-ack logging + MDC |
| `infraKafkaConsumerInterceptor` (`RecordInterceptor`) | Consumer | `infra.kafka.logging.enabled=true` | MDC before processing, metrics + clear after |
| `KafkaMetricsConfig` | Both | `infra.kafka.metrics.enabled=true` **and** Micrometer on classpath | Micrometer counters/timers |

The metrics bean is additionally `@ConditionalOnClass(MeterRegistry)` — it only activates if the service has Actuator/Micrometer, so the library never forces that dependency.

---

## 2. Producer-side logging — `KafkaLoggingInterceptor`

Implements Kafka's native `ProducerInterceptor`. It's registered on the producer factory in `KafkaProducerConfig` via `interceptor.classes`, and the `log-payload` flag is passed through the producer config map so `configure()` can pick it up.

Lifecycle hooks:

| Hook | When | Log level |
|------|------|-----------|
| `onSend(record)` | before serialization/send | `DEBUG` (`PRE-SEND topic key [payload]`) |
| `onAcknowledgement(meta, ex)` | after broker ack **or** failure | `INFO` on ack (`topic partition offset`), `ERROR` on failure |

On `onSend` it **populates the MDC** so downstream log lines carry the context; on `onAcknowledgement` it **clears the MDC** (in a `finally`, so it's cleared even on failure).

> [!note] Two logging layers
> `KafkaMessagePublisher` itself also logs `SEND` / `SEND OK` / `SEND FAILED` at INFO around the `send()` call. The interceptor logs at the lower-level Kafka client boundary (`PRE-SEND` / `SEND ACK`). Both respect `logging.log-payload`.

---

## 3. Correlation via MDC — the whole point of tracing

**MDC** (Mapped Diagnostic Context, SLF4J) is a per-thread key/value map that your logging pattern can print on **every** log line. By copying correlation IDs from message headers into MDC, all logs for one logical request chain share the same IDs across services.

Keys set by both interceptors (consistent producer↔consumer):

| MDC key | Source |
|---------|--------|
| `kafka.topic` | record topic |
| `kafka.key` | record key |
| `correlationId` | `X-Correlation-Id` header |
| `traceId` | `X-Trace-Id` header |

**Flow:** upstream stamps `X-Correlation-Id` when producing → the producer interceptor puts it in MDC → the consumer's `RecordInterceptor.intercept()` reads it back from the header into MDC *before* the listener runs → your business logs automatically carry it → cleared in `success()`/`failure()`.

```java
// producer side — stamp the correlation id as a header
publisher.send("order-events", order.getId(), event, headers ->
    headers.add("X-Correlation-Id", correlationId.getBytes()));
```

To see it, include MDC in the log pattern, e.g. Logback:
```
%d %-5level [%X{correlationId}] [%X{kafka.topic}] %logger - %msg%n
```

> [!warning] Always clear MDC
> MDC is thread-local and Kafka listener threads are pooled/reused. If you don't clear it, a stale `correlationId` leaks into the next record's logs. The library's interceptors clear MDC in a `finally` block for exactly this reason — a good pattern to remember for interviews.

## 4. Consumer-side interceptor — `InfraConsumerRecordInterceptor`

A named `RecordInterceptor<String,Object>` (named class, not a lambda, so Spring Kafka's generics resolve unambiguously). It's attached to **both** container factories (retrying + no-retry) in `KafkaConsumerConfig.buildBaseFactory()`.

| Hook | Action |
|------|--------|
| `intercept(record)` | before listener — populate MDC (topic, key, correlation, trace), DEBUG `CONSUME BEGIN` |
| `success(record)` | after listener returns OK — `recordConsumerSuccess`, DEBUG `CONSUME OK`, clear MDC |
| `failure(record, ex)` | listener threw — `recordConsumerFailure(topic, group, exName)`, WARN `CONSUME FAILED`, clear MDC |

It calls the metrics bean only `ifAvailable` — so it degrades gracefully when Micrometer isn't present.

---

## 5. Metrics — `KafkaMetricsConfig` (Micrometer)

Wraps a `MeterRegistry` and **lazily creates + caches** meters per `topic` (and `groupId`) in `ConcurrentHashMap`s, so the hot path avoids repeated registry lookups.

### Producer metrics

| Metric | Type | Tags | Meaning |
|--------|------|------|---------|
| `infra.kafka.producer.send.success` | Counter | `topic` | acked sends |
| `infra.kafka.producer.send.failure` | Counter | `topic`, `exception` | failed sends |
| `infra.kafka.producer.send.duration` | Timer | `topic` | send latency (p50/p95/p99) |

### Consumer metrics

| Metric | Type | Tags | Meaning |
|--------|------|------|---------|
| `infra.kafka.consumer.record.success` | Counter | `topic`, `groupId` | processed OK |
| `infra.kafka.consumer.record.failure` | Counter | `topic`, `groupId`, `exception` | listener threw |
| `infra.kafka.consumer.record.dlq` | Counter | `topic`, `groupId` | routed to DLQ after exhausted retries |
| `infra.kafka.consumer.record.duration` | Timer | `topic`, `groupId` | processing latency (p50/p95/p99) |

Timers publish **percentiles** `0.5, 0.95, 0.99` — so you get tail latency, not just averages (averages hide the p99 pain).

> [!info] Metric naming: dots → underscores
> Micrometer registers `infra.kafka.producer.send.success`; Prometheus scrapes it as `infra_kafka_producer_send_success_total` (counters get a `_total` suffix, dots become underscores). Timers expose `..._seconds_bucket/_count/_sum`.

### Grafana / PromQL examples

```promql
# produce rate per topic
sum(rate(infra_kafka_producer_send_success_total[1m])) by (topic)

# consumer error rate
sum(rate(infra_kafka_consumer_record_failure_total[1m])) by (topic, groupId)

# DLQ rate — alert when > 0 sustained
sum(rate(infra_kafka_consumer_record_dlq_total[1m])) by (topic)

# p99 send latency
histogram_quantile(0.99, rate(infra_kafka_producer_send_duration_seconds_bucket[5m]))
```

**Consumer lag** (records behind the log end) is the other must-watch signal; expose it via Actuator + the Kafka client's built-in `kafka.consumer.*` metrics and alert on sustained growth.

## 6. Configuration

```yaml
infra:
  kafka:
    logging:
      enabled: true         # producer + consumer interceptors, MDC
      log-payload: false    # true only in dev — never log PII/payloads in prod
    metrics:
      enabled: true         # requires Micrometer + Actuator on the classpath
```

Expose metrics with Actuator:
```yaml
management:
  endpoints.web.exposure.include: health,prometheus,metrics
```
→ scrape `GET /actuator/prometheus`.

> [!warning] `log-payload` in production
> Logging full payloads leaks PII/secrets and blows up log volume/cost. Keep `log-payload=false` in prod (the default); enable only locally when debugging.

## 7. Log levels & lifecycle at a glance

| Event | Where | Level |
|-------|-------|-------|
| pre-send | producer interceptor | DEBUG |
| send ack (partition/offset) | producer interceptor / publisher | INFO |
| send failed | producer | ERROR |
| consume begin | consumer interceptor | DEBUG |
| consume ok | consumer interceptor | DEBUG |
| consume failed (will retry) | consumer interceptor | WARN |
| routed to DLQ | error handler | ERROR |

This ladder — INFO on success, WARN on retry, ERROR on DLQ — makes an alerting rule as simple as "page on ERROR-rate spike + DLQ counter > 0".
