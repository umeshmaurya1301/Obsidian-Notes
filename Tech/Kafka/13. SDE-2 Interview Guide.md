## 2. Most Common Deep-Dive Questions

### Exactly-Once Semantics

> **Q: Kafka supports EOS. Why do you still need consumer-side idempotency?**

Kafka EOS guarantees atomicity for `Producer → Kafka` and `Kafka → Kafka` transactions. It does **NOT** guarantee `Kafka → Database` exactly-once. If the consumer updates the DB but crashes before committing the offset, the message replays → double processing.

→ Detailed notes: [[10. Delivery Guarantees & Idempotency]]

### Consumer Crash Scenario

> **Q: Consumer updated DB but crashed before offset commit. How do you prevent double debit?**

```text
Read Message → Update DB → CRASH → Offset not committed → Message replays
```

**Answer:** Idempotency key (`txn_id`) with a `UNIQUE` constraint in the database. On replay, the `INSERT ... ON CONFLICT DO NOTHING` silently drops the duplicate.

→ Detailed notes: [[11. Consumer-Side Idempotency & Patterns]]

### Redis Lock Sufficiency

> **Q: Why is a Redis lock not sufficient for monetary correctness?**

Redis locks can fail due to: TTL expiration during long processing, async replication loss on master failover, or complete Redis outage. For monetary transactions, the **database** (row locking + idempotency keys) is the source of truth. Redis locks are a **coordination optimization**, not a correctness mechanism.

→ Detailed notes: [[12. Distributed Locks & Concurrency]]

## 3. Common Follow-Up Chains

### Chain 1: Locking Deep-Dive

| # | Question | Expected Answer |
|---|----------|----------------|
| 1 | Why not simply use DB locking instead of Redis? | Redis reduces contention before hitting DB; coordinates across services. DB remains source of truth. |
| 2 | Redis lock acquired, consumer crashes before releasing? | TTL auto-expires the lock. |
| 3 | What if processing takes longer than TTL? | Lock renewal / heartbeat (Redisson watchdog). |
| 4 | How do you safely release a Redis lock? | Lua script: only `DEL` if `owner == currentConsumer`. |
| 5 | Why is Redlock controversial? | Clock assumptions, network partitions, Martin Kleppmann's criticism. DB constraints still needed. |

### Chain 2: Partitioning & Ordering

| # | Question | Expected Answer |
|---|----------|----------------|
| 1 | Is Kafka partitioning enough for exactly-once? | No — rebalance/crash → replay → duplicate. Idempotency still needed. |
| 2 | How do you maintain ordering when increasing partitions? | `hash(key) % N` changes → ordering breaks. Pre-create partitions / custom partitioner. |
| 3 | Why not use one partition? | Throughput bottleneck, single consumer, no horizontal scaling. Trade-off: ordering vs parallelism. |
| 4 | How do you handle hot partitions? | Key redesign, sharding strategy, compound keys, load-balanced sub-partitioning. |

### Chain 3: Idempotency Design

| # | Question | Expected Answer |
|---|----------|----------------|
| 1 | How would you design an idempotency table? | `CREATE TABLE processed_txn (txn_id VARCHAR PRIMARY KEY, processed_at TIMESTAMP)` |
| 2 | What if the table grows to billions of records? | Partitioning, archival, TTL-based cleanup. |
| 3 | Why not use `accountId` as idempotency key? | One account can have millions of txns. Need `txnId` / `requestId` — unique per business operation. |
| 4 | How do banks prevent double debit? | Idempotency + ledger + DB transaction + unique business reference. Not Redis. |

## 4. Kafka Rebalance (Step-by-Step)

> **Q: Explain what happens during a Kafka rebalance.**

```text
1. Partition revoked from current consumer
2. Consumer stops processing (onPartitionsRevoked callback)
3. Partition reassigned to another consumer
4. New consumer resumes from last committed offset
```

**Risk:** Potential message replay → duplicate processing → must have idempotency.

### Can Two Consumers Process the Same Message Simultaneously?

**This is a trap question.** Most candidates say "No."

**Correct answer: Yes** — during:
- Consumer crash + offset replay
- Rebalance (partition reassignment)
- Network issues (session timeout)

**Hence:** Idempotency is mandatory, not optional.

## 5. Pessimistic vs Optimistic Locking for Payments

| Aspect | Pessimistic (`SELECT ... FOR UPDATE`) | Optimistic (version column) |
|--------|---------------------------------------|----------------------------|
| Mechanism | Row-level lock, others wait | Check version on update, retry on conflict |
| Consistency | Strong | Eventual (with retries) |
| Throughput | Lower (blocking) | Higher (non-blocking) |
| Deadlock risk | Yes | No |
| Best for | High-contention accounts | Low-contention, high-throughput |
