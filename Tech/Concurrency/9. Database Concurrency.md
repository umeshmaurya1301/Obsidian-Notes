Covers Roadmap section 9. In-process locks (`synchronized`, `ReentrantLock`) only protect one JVM. The moment you run two pods, the database becomes the only shared source of truth — so correctness moves into the DB layer.

> [!info] The through-line of this note
> Everything here follows one chain of cause and effect. Read it in order:
>
> 1. A database gives you **ACID** (§1) — of which only **Isolation** is tunable.
> 2. Isolation is tunable because the engine **interleaves** transactions for throughput (§2). Interleaving is where all the performance comes from — and all the bugs.
> 3. A bad interleaving has a name: an **anomaly** (§3). There are five, and they fall out of a simple conflict taxonomy rather than needing memorisation.
> 4. **Isolation levels** (§4) are just cumulative cut-offs on that anomaly list — each blocks one more, and costs more.
> 5. One anomaly — **lost update** — can't be fixed by raising the level, because it happens in your application's memory where the DB can't see it. That's why **locks** exist (§5–§8).
> 6. §9 is how all of it looks in Spring Boot; §10 is what it looks like when it goes wrong in a payments system.

### 1. ACID — and Why Locking Exists

A **transaction** is a group of statements that must behave as a single unit. ACID is the set of four guarantees a database gives you about that unit. In Spring, the boundary is simply `@Transactional` — method entry begins the transaction, a clean return commits, a `RuntimeException` rolls back.

#### 1.1 The Four Guarantees

**A — Atomicity: all or nothing.**
Every statement in the transaction succeeds, or none of them do. There is no partial state.

```
BEGIN;
  UPDATE wallet SET balance = balance - 500 WHERE id = 1;   -- debit sender
  UPDATE wallet SET balance = balance + 500 WHERE id = 2;   -- credit receiver
COMMIT;
```

If the second statement fails, the first is undone. Without atomicity, ₹500 vanishes from the system. The engine implements this with an **undo log** — every change records how to reverse itself, and `ROLLBACK` replays those in reverse.

> [!warning] Spring gotcha
> `@Transactional` rolls back on **unchecked** exceptions only. A checked exception commits the partial work silently. If you throw checked exceptions, declare `@Transactional(rollbackFor = Exception.class)`.

**C — Consistency: the database moves from one valid state to another valid state.**
"Valid" means every declared rule still holds after commit: primary keys, foreign keys, `NOT NULL`, `CHECK`, and unique constraints.

```sql
ALTER TABLE wallet ADD CONSTRAINT chk_non_negative CHECK (balance >= 0);
```

Now no transaction can leave a wallet negative — the commit is rejected outright.

> [!info] The nuance interviewers look for
> C is the odd one out. A, I, and D are enforced *by the database*. Consistency is really a **shared responsibility**: the DB enforces the constraints you declared, but *business* invariants ("a refund can't exceed the original payment") are only guaranteed if you encode them — as a constraint, or in your application logic. Many people argue C was included mostly to make the acronym pronounceable.
>
> Also note this is a *different* "consistency" from the C in **CAP**, which is about replicas agreeing. Don't conflate them.

**I — Isolation: concurrent transactions don't corrupt each other.**
The one this whole note is about, and the only one that's *tunable* — see §1.2.

**D — Durability: once committed, it survives.**
After `COMMIT` returns, the data persists through a crash, power loss, or process kill. Implemented via a **write-ahead log (WAL)**: changes are `fsync`'d to the log *before* the commit is acknowledged, so recovery can replay them even if the data pages never made it to disk.

> [!warning] Durability is a dial, not a boolean
> MySQL's `innodb_flush_log_at_trx_commit=2` and Postgres's `synchronous_commit=off` trade durability for throughput — a commit is acknowledged before it's truly on disk, so a crash can lose the last ~1s of transactions. Fine for analytics. **Never for payments.** Similarly, in a replicated setup a commit durable on the primary may not be on the replica yet — that's why financial systems use synchronous replication.

#### 1.2 Which Ones Concurrency Actually Threatens

Atomicity and durability are essentially free — you get them by using transactions at all, and there are no levels to choose. Consistency is mostly your constraints doing their job. **Isolation is the only property you configure**, and every weakening of it is a deliberate trade of correctness for throughput.

So the rest of this note is about the I.

### 2. Where Anomalies Come From

Before naming the anomalies, it's worth being clear on *why they exist at all* — otherwise the list in §3 is just vocabulary to memorise.

#### 2.1 Why the database runs transactions concurrently

The obvious way to guarantee perfect isolation is to run transactions **one at a time**. Nothing overlaps, so nothing can interfere. Databases don't do this, for a simple reason:

A transaction spends the overwhelming majority of its life **waiting** — for disk reads, for the WAL `fsync`, for network round trips back to your Spring app between statements. Actual CPU work is a sliver of it.

```
One transaction, serial execution:

|--wait for disk--|-cpu-|----wait for app's next statement----|--fsync--|
 ~5ms               0.1ms  ~2ms                                 ~1ms

≈ 8ms wall clock, of which ~0.1ms is real work.
Serial execution ⇒ ~125 transactions/second for the whole database. Unusable.
```

So the engine **interleaves** them: while T1 waits on disk, the CPU runs a piece of T2, then a piece of T3. The hardware stays busy and throughput goes up by orders of magnitude.

> [!info] The trade in one line
> **Interleaving is the source of all the performance, and the source of all the bugs.** Every anomaly in §3 is a specific interleaving that produces a result no serial order could have produced.

#### 2.2 Schedules — serial vs interleaved

A **schedule** is the actual order in which the database ends up executing the individual reads and writes of concurrent transactions.

A **serial schedule** runs them back-to-back. Two transactions each adding ₹100 to a ₹1000 balance:

```
Serial (T1 then T2):
T1: read 1000 → write 1100
T2: read 1100 → write 1200        ✅ final = 1200
```

An **interleaved schedule** mixes their steps. Most interleavings are perfectly fine — but some aren't:

```
Interleaved (bad):
T1: read 1000
T2: read 1000            ← reads before T1 wrote
T1: write 1100
T2: write 1100           ❌ final = 1100. One ₹100 credit vanished.
```

Same two transactions, same starting data. **Only the interleaving differs**, and it silently destroyed money.

#### 2.3 The correctness criterion: serializability

This gives us the definition everything else hangs off:

> An interleaved schedule is **correct** if it produces the same result as *some* serial ordering of those transactions.

Note "**some**" — the database doesn't have to match the order you'd have guessed. `T1→T2` and `T2→T1` are both acceptable outcomes (1200 either way). What's unacceptable is 1100, which matches *neither*.

A schedule with that property is **serializable**. A schedule without it exhibits an **anomaly**.

> [!info] So: an "isolation anomaly" is simply a *named, commonly-occurring bad interleaving*
> They aren't exotic edge cases or database bugs. They're the handful of interleaving patterns that (a) show up constantly in real workloads and (b) each require a different, increasingly expensive mechanism to prevent — which is exactly why the SQL standard defines isolation *levels* around them.

#### 2.4 Why there are exactly these anomalies — the conflict taxonomy

You can derive the list rather than memorise it. Two operations from different transactions can only interfere if they touch **the same data** *and* **at least one of them is a write**:

|Operation pair|Conflict?|Why|
|---|---|---|
|Read – Read|✅ Safe|Neither changes anything. Reads never need to be isolated from each other.|
|**Write – Read**|❌ Conflict|A reader may see a write that later gets rolled back|
|**Read – Write**|❌ Conflict|A writer changes data someone already read and will act on|
|**Write – Write**|❌ Conflict|One write silently overwrites the other|

Three conflict types, and each one generates its anomalies directly:

| Conflict | Anomaly it produces | The question it raises |
|---|---|---|
| **W → R** | **Dirty read** (§3.1) | Should I be allowed to see *uncommitted* data? |
| **R → W** | **Non-repeatable read** (§3.2) — a row I read changed | Should data I already read be allowed to change under me? |
| **R → W** | **Phantom read** (§3.3) — the row *set* I read changed | …including rows *appearing*, not just changing? |
| **W → W** | **Lost update** (§3.4) | Should my write be allowed to clobber one I never saw? |
| **R → W** across *different* rows | **Write skew** (§3.5) | Can two individually-valid writes break a rule *together*? |

That's the whole list, and it explains its own ordering: dirty read is the crudest (visible uncommitted data), and each subsequent one requires the engine to track more — a stable snapshot, then a stable *range*, then relationships between rows it never wrote.

#### 2.5 Why not just always be serializable?

Because preventing all of them is expensive. To guarantee serializability the engine must either hold locks on everything you read until commit (so transactions queue up behind each other — you've partly undone §2.1's throughput win), or track every read-set and abort transactions on conflict (so your app must handle retries).

Hence the deal every database offers:

> **A menu of isolation levels.** Each level blocks a specific prefix of the anomaly list, and costs more than the one below it. You pick the cheapest level whose *remaining* anomalies your business logic can actually tolerate.

Choosing well is the skill. A product-catalogue read tolerates almost anything. A wallet debit tolerates none of it.

#### 2.6 The two mechanisms engines use

Everything in this note is built from two primitives, usually combined:

- **Locking** — a transaction blocks others from touching a row. Pessimistic, prevents the bad interleaving from ever occurring.
- **MVCC (Multi-Version Concurrency Control)** — writers don't overwrite; they create a *new version* of the row, and each transaction reads from a consistent **snapshot** as of a point in time. This is why in both Postgres and InnoDB **readers never block writers, and writers never block readers** — the reader is served an older version instead of waiting.

> [!info] Key mental model, worth holding onto
> **MVCC handles reads. Locking handles writes.**
>
> That split explains where the dangerous gap is: MVCC gives your `SELECT` a consistent snapshot, but the moment you pull that value into Java, compute on it, and write it back, you've stepped *outside* what the snapshot protects. The database sees an independent `UPDATE`, not a continuation of your read. **That gap is where lost update (§3.4) lives, and it's the single most common real-world data bug in payments.**

### 3. Isolation Anomalies

The five named interleavings from §2.4, in increasing order of subtlety. For each: what it is, why the engine allows it, and where it hurts.

#### 3.1 Dirty Read

**Conflict type:** W → R (a read sees an uncommitted write)

T1 writes but hasn't committed; T2 reads that uncommitted value; T1 then rolls back. T2 acted on data that **never existed** in any committed state.

```
T1: UPDATE wallet SET balance = 5000 WHERE id = 1;   -- not committed yet
T2: SELECT balance FROM wallet WHERE id = 1;         -- reads 5000  ← dirty
T1: ROLLBACK;                                        -- 5000 never existed

T2 has now approved a ₹4000 withdrawal against a balance that was never real.
```

**Why an engine would ever allow it:** because *not* allowing it costs something. To avoid dirty reads the reader must either wait for the writer to finish, or be served the previous committed version. The first costs latency; the second costs version storage. READ UNCOMMITTED skips both — it just hands you whatever bytes are currently in the page.

**Why you'll never actually see it:** MVCC makes the "previous committed version" almost free, since old versions are retained anyway for rollback. Postgres therefore **never** produces dirty reads, at any level — `READ UNCOMMITTED` silently behaves as `READ COMMITTED`. InnoDB only does it if you explicitly ask.

**Prevented by:** `READ COMMITTED` and above — i.e. everything you'd realistically run.

#### 3.2 Non-Repeatable Read

**Conflict type:** R → W (data you read is changed underneath you)

T1 reads a row twice and gets **different values**, because T2 committed an `UPDATE` in between.

```
T1: SELECT balance FROM wallet WHERE id = 1;        -- 1000
T2: UPDATE wallet SET balance = 500 WHERE id = 1; COMMIT;
T1: SELECT balance FROM wallet WHERE id = 1;        -- 500  ← same query, different answer
```

**Why the engine allows it:** at `READ COMMITTED`, each **statement** gets a *fresh* snapshot. That's a deliberate design choice with a real upside — every statement sees the most current committed data, and the engine can discard old row versions as soon as no statement needs them. Preventing this means pinning **one snapshot for the whole transaction**, which forces the engine to retain every row version created during your transaction's lifetime (Postgres bloat, InnoDB undo-log growth). A long-running transaction at REPEATABLE READ is a genuine operational problem.

**Where it hurts:** any multi-query business operation. You compute a settlement total in one query and its line-item breakdown in another — and they don't reconcile, because a payment committed between the two. The report is internally inconsistent and nothing errored.

**Prevented by:** `REPEATABLE READ` and above.

#### 3.3 Phantom Read

**Conflict type:** R → W, but on a **range** rather than a row

T1 runs a **range query** twice and gets a **different number of rows**, because T2 `INSERT`ed (or deleted) something matching the predicate.

```
T1: SELECT COUNT(*) FROM txn WHERE user_id=1 AND created_at::date = CURRENT_DATE;  -- 4
T2: INSERT INTO txn (user_id, amount) VALUES (1, 2000); COMMIT;
T1: SELECT COUNT(*) FROM txn WHERE user_id=1 AND created_at::date = CURRENT_DATE;  -- 5  ← phantom
```

> [!info] The distinction interviewers probe
> Non-repeatable read = **an existing row's value changed.**
> Phantom read = **the set of rows matching your predicate changed.**
>
> They're both R→W conflicts, so why separate names? Because preventing them requires *different machinery*. Protecting a row you read is easy — you already know its identity, so you can lock or version it. Protecting rows that **don't exist yet** is fundamentally harder: you must lock a *predicate* — a region of key space — to stop someone inserting into it.

**Why the engine allows it:** that predicate machinery is expensive. InnoDB implements it with **gap locks / next-key locks** (§5.3), which block inserts into an index range and therefore reduce write concurrency for everyone touching that range. Postgres implements it under SSI with **predicate locks** and read-set tracking, paying in memory and aborted transactions.

**Where it hurts:** enforcing any "at most N" rule. *"A user may have at most 3 active payment methods"* — two concurrent inserts both count 2, both proceed, and now there are 4.

**Prevented by:** `SERIALIZABLE` per the SQL standard — but in practice both InnoDB and Postgres already prevent it at `REPEATABLE READ` (§4).

#### 3.4 Lost Update

**Conflict type:** W → W

Two transactions read the same value, each computes a new value from it, and both write. One update silently vanishes. **This is the single most common real-world payments bug.**

```
Balance = 1000

T1: SELECT balance → 1000            T2: SELECT balance → 1000
T1: 1000 - 200 = 800   (in Java)     T2: 1000 - 300 = 700   (in Java)
T1: UPDATE SET balance = 800         T2: UPDATE SET balance = 700

Final = 700. Should be 500. ₹200 created out of thin air.
```

**Why the engine allows it — and this is the important part:** *the database never saw a conflict.* Look at what it actually received from T2: a `SELECT`, then, some milliseconds later, an `UPDATE` setting a column to the literal `700`. Both are perfectly legal. Nothing in that sequence tells the engine that `700` was **derived from** the earlier read.

The conflict exists only in your application's *intent* — "subtract 300 from whatever I read" — and intent is not something you transmitted. The read-modify-write happened in **JVM memory**, in the gap between two independent database round trips.

> [!warning] This is why no isolation level saves you by default
> Isolation levels govern what a transaction is allowed to *see*. Lost update is not a visibility failure — both transactions saw perfectly valid data. It's an **intent** failure. So `REPEATABLE READ` does not help in MySQL/InnoDB.
>
> Postgres RR is stricter and aborts T2 with a `40001` serialization error, but you still have to catch and retry it. Fixing lost update requires you to *communicate the intent* to the database, in one of exactly three ways:
> 1. **Pessimistic** — `SELECT ... FOR UPDATE` (§6): "nobody else may read this for update until I'm done."
> 2. **Optimistic** — a `version` check (§7): "only apply this if nothing changed since my read."
> 3. **Atomic update** (§9.4): `SET balance = balance - 300` — never pull the value into Java at all, so there's no gap.

**Where it hurts:** wallet debits, stock/inventory decrements, counters, loyalty points — anything of the form *read a number, change it, write it back*.

#### 3.5 Write Skew

**Conflict type:** R → W across **different rows** — the reason snapshot isolation isn't enough

The subtlest one. Two transactions read an **overlapping set**, each verifies an invariant, then each writes to a **different row**. Each transaction is individually valid; together they break the rule.

```
Rule: a high-value payout must always have ≥ 1 active approver.
Currently: Alice and Bob are both active.

T1: SELECT COUNT(*) active approvers → 2.  Fine, Alice may go inactive.
T2: SELECT COUNT(*) active approvers → 2.  Fine, Bob may go inactive.
T1: UPDATE approver SET active=false WHERE name='Alice';   COMMIT;
T2: UPDATE approver SET active=false WHERE name='Bob';     COMMIT;

→ 0 active approvers. The invariant is broken and no row was written twice.
```

**Why the engine allows it:** snapshot isolation detects **write-write conflicts on the same row** — that's its whole conflict-detection strategy. Here T1 and T2 write to *different rows*, so by that test there is **no conflict at all**. The real conflict is that each transaction *read* data the other *invalidated*, and catching that requires tracking full read-sets and checking them at commit — which is exactly what Postgres's SSI does, and why `SERIALIZABLE` costs more.

**Where it hurts:** any invariant spanning multiple rows — maker-checker approval rules, "at least one admin," doctor on-call rotas, seat/inventory allocation, and **refunds against a shared parent total** (§10.3).

> [!example] The practical fix, if you can't afford SERIALIZABLE
> **Materialize the conflict onto a single row.** If the rule is about the *payment*, lock the `payment` row (`SELECT ... FOR UPDATE`) before validating its refunds. You've converted an undetectable cross-row R→W conflict into an ordinary W→W conflict on one row — which every isolation level can handle.

**Prevented by:** `SERIALIZABLE` only.

#### Summary — the five, and what each one costs to prevent

| Anomaly | Conflict | Root cause | Prevented by | Payments impact |
|---|---|---|---|---|
| **Dirty read** | W→R | Reading uncommitted bytes | `READ COMMITTED` | Acting on a rolled-back balance |
| **Non-repeatable read** | R→W (row) | Per-statement snapshots | `REPEATABLE READ` | Reports that don't reconcile |
| **Phantom read** | R→W (range) | Can't lock rows that don't exist yet | `SERIALIZABLE`* | "At most N" rules breached |
| **Lost update** | W→W | Read-modify-write gap **in your app** | Explicit locking / atomic update | **Money created or destroyed** |
| **Write skew** | R→W (cross-row) | No same-row write conflict to detect | `SERIALIZABLE` | Multi-row invariants breached |

\* in practice both InnoDB and Postgres block phantoms at `REPEATABLE READ` — see §4.

> [!warning] The one that isn't on the isolation menu
> Notice that **lost update is the only row whose fix isn't "raise the isolation level."** Every other anomaly is something the database can prevent for you, because it can see the conflict. Lost update happens in the gap between two round trips, where the database isn't looking — which is precisely why §6–§9 (pessimistic, optimistic, atomic updates) exist, and why they occupy most of this note.

### 4. Isolation Levels

Now the menu from §2.5 makes sense. The four standard levels are simply **cumulative cut-off points on the anomaly list** — each one blocks everything the level below blocks, plus one more, and charges you for it:

```
READ UNCOMMITTED  →  blocks nothing                       (cheapest, useless)
READ COMMITTED    →  + no dirty reads                     (fresh snapshot per statement)
REPEATABLE READ   →  + no non-repeatable reads            (one snapshot per transaction)
SERIALIZABLE      →  + no phantoms, no write skew         (read-set tracking / range locks)
```

That's the entire concept: **pick the lowest level whose remaining anomalies your business logic tolerates.** Note where lost update sits — mostly outside this ladder, per §3.4.

|Level|Dirty Read|Non-Repeatable|Phantom|Lost Update|Write Skew|
|---|---|---|---|---|---|
|**READ UNCOMMITTED**|❌ allowed|❌|❌|❌|❌|
|**READ COMMITTED**|✅ prevented|❌|❌|❌|❌|
|**REPEATABLE READ**|✅|✅|⚠️ see below|⚠️ engine-specific|❌|
|**SERIALIZABLE**|✅|✅|✅|✅|✅|

**Engine-specific reality (this is what gets asked):**

|                       | MySQL / InnoDB                                                                            | PostgreSQL                                                                                |
| --------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **Default level**     | `REPEATABLE READ`                                                                         | `READ COMMITTED`                                                                           |
| **Phantoms at RR**    | Prevented — MVCC snapshot for plain reads, **next-key locks** for locking reads            | Prevented — RR is true snapshot isolation                                                  |
| **Lost update at RR** | **Still possible** via app-side read-modify-write                                          | T2 aborts with `40001` serialization failure                                               |
| **SERIALIZABLE**      | Implemented with heavy locking (turns reads into `FOR SHARE`)                              | **SSI** — optimistic, detects conflicts and aborts one txn                                  |

> [!example] Practical default for payments
> Stay on the engine default (`READ COMMITTED` on Postgres) and use **explicit locking on the specific rows that need it**. Globally raising the isolation level to SERIALIZABLE to fix one endpoint is a blunt instrument that tanks throughput across the whole service.

### 5. Types of Locks

#### 5.1 By Mode — what it lets others do

|Lock|Also called|Blocks|Acquired by|
|---|---|---|---|
|**Shared (S)**|Read lock|Other writers, not other readers|`SELECT ... FOR SHARE` / `LOCK IN SHARE MODE`|
|**Exclusive (X)**|Write lock|Everyone (readers-for-update and writers)|`UPDATE`, `DELETE`, `SELECT ... FOR UPDATE`|
|**Update (U)**|—|Other U and X, but not S|SQL Server; intermediate state to avoid conversion deadlocks|

Compatibility matrix — the whole thing in one grid:

```
        S      X
  S    ✅     ❌
  X    ❌     ❌
```

Many readers coexist. One writer excludes everyone. Same semantics as Java's `ReadWriteLock`, just distributed.

#### 5.2 By Granularity — how much it covers

From cheapest-to-hold to most-blocking:

- **Row lock** — one row. What you want 99% of the time.
- **Page lock** — a disk page (several rows). SQL Server; InnoDB doesn't do this.
- **Table lock** — the whole table. DDL, or InnoDB falling back when there's no usable index on the `WHERE` clause.
- **Intent locks (IS / IX)** — a *flag* on the table saying "someone holds row locks below." Lets the engine check "can I lock this whole table?" in O(1) instead of scanning every row lock. You never request these directly.

> [!warning] The classic production incident
> `UPDATE txn SET status='DONE' WHERE reference_no = 'X'` with **no index on `reference_no`** makes InnoDB scan and lock **every row it examines** — effectively a table lock. Under load the whole payments table serializes and connections pile up. **Lock granularity is decided by your indexes.**

#### 5.3 By What Is Locked — InnoDB specifics

- **Record lock** — the index record itself.
- **Gap lock** — the *empty space between* index records. Blocks `INSERT` into that gap. This is how InnoDB kills phantoms.
- **Next-key lock** — record lock + gap before it. **InnoDB's default at REPEATABLE READ.**
- **Insert intent lock** — a gap lock variant that lets multiple inserts into the same gap proceed if they don't collide.

Postgres's equivalent for phantom prevention is **predicate locks** under SSI (`SERIALIZABLE`) — tracked read-sets rather than physical gaps.

#### 5.4 Advisory Locks

Application-defined locks with **no relation to any row** — you lock an arbitrary number/string. Postgres only.

```sql
-- Serialize a nightly settlement job across all pods
SELECT pg_try_advisory_lock(42);   -- returns true/false, non-blocking
-- ... do work ...
SELECT pg_advisory_unlock(42);
```

Cheap, effective distributed mutex if you already have Postgres and don't want to introduce Redis. Session-scoped, so it dies with the connection — beware of connection pools handing you a different session.

### 6. Pessimistic Locking

**Assume conflict will happen. Lock the row up front; everyone else waits.**

```sql
BEGIN;
SELECT balance FROM wallet WHERE id = 1 FOR UPDATE;  -- X lock, others block here
-- compute in Java
UPDATE wallet SET balance = 800 WHERE id = 1;
COMMIT;                                               -- lock released
```

Important variants:

|Clause|Behaviour|Use when|
|---|---|---|
|`FOR UPDATE`|Wait for the lock (until `lock_timeout`)|Default; genuine contention on hot rows|
|`FOR SHARE`|S lock — read it, stop others writing|You need a stable read but aren't writing that row|
|`FOR UPDATE NOWAIT`|Fail immediately if locked|Interactive API — fail fast, return `409`, don't hold a thread|
|`FOR UPDATE SKIP LOCKED`|**Skip** locked rows, return the rest|**Job queues** — see §9.5|

**Costs:** holds a lock for the whole transaction (including any slow work you foolishly do inside it), risks deadlocks, and blocked threads occupy connection-pool slots. A 2s external call inside a `FOR UPDATE` transaction will exhaust HikariCP under load.

---

### 7. Optimistic Locking

**Assume conflict is rare. Don't lock — detect the collision at write time and retry.**

Implemented with a `version` column. The `UPDATE` is conditional on the version you read:

```sql
-- read
SELECT balance, version FROM wallet WHERE id = 1;    -- balance=1000, version=7

-- write, guarded
UPDATE wallet
   SET balance = 800, version = 8
 WHERE id = 1 AND version = 7;
```

If another transaction already bumped it to 8, this updates **0 rows** → conflict detected → the app retries the whole read-compute-write cycle. No lock was ever held.

Variants: a monotonic `version` integer (standard), or a `updated_at` timestamp (avoid — clock resolution collisions), or comparing the old value itself (`WHERE balance = 1000`, a compare-and-swap).

> [!info] This is exactly `AtomicInteger.compareAndSet()`, one layer down
> Same CAS idea as [[1. Core Fundamentals]] — read, compute, swap only if unchanged, retry on failure.

> [!warning] Optimistic locking is a *bet* that conflicts are rare
> When that bet is wrong it doesn't degrade gracefully — it collapses. See §8.4 (retry storms) before using this on a hot row.

### 8. Optimistic vs Pessimistic — Choosing

#### 8.1 The comparison

|                     | Optimistic                                             | Pessimistic                                   |
| ------------------- | ------------------------------------------------------ | --------------------------------------------- |
| **Assumption**      | Conflicts are rare                                     | Conflicts are likely                          |
| **Mechanism**       | `version` column + conditional update                  | `SELECT ... FOR UPDATE`                       |
| **Blocking**        | Never blocks                                            | Blocks other transactions                     |
| **Failure mode**    | Fails at commit → **you must retry**                    | Waits, then lock timeout / deadlock           |
| **Deadlock risk**   | None                                                    | Real                                          |
| **Throughput**      | High under low contention; **collapses** under high (retry storms) | Steady under high contention                  |
| **Wasted work**     | Real — you compute, *then* get rejected                 | None — you wait, then compute once            |
| **Fairness**        | None; a transaction can starve indefinitely             | Roughly FIFO queue                            |
| **Long think-time** | ✅ Good — nothing held while user thinks                | ❌ Bad — never hold a lock across user input  |

**The decision rule is one question:** *how often do two requests hit the **same row** concurrently?* Not how busy the system is overall — a 10,000 TPS system spread across a million rows has near-zero contention per row.

#### 8.2 Where each is actually used

**Optimistic — low contention, and/or long-lived edits:**

| Case | Why optimistic wins |
|---|---|
| User edits profile / address / KYC details | Two concurrent edits to the *same* user are vanishingly rare |
| Admin editing merchant configuration | Human-speed, single-editor |
| A multi-screen wizard or a "edit and save" form | The read-to-write gap spans **user think time** — you must not hold a DB lock for 30 seconds |
| Order/cart edits before checkout | One owner per cart |
| Any entity behind a REST `PUT` with an `If-Match`/ETag | Optimistic locking *is* the HTTP conditional-request model |
| Batch jobs over disjoint row sets | Rows rarely overlap between workers |

**Pessimistic — genuine contention, or logic too complex for one statement:**

| Case | Why pessimistic wins |
|---|---|
| Debiting a hot merchant/settlement wallet | Hundreds of writers on one row; retries would storm |
| Seat / ticket / inventory allocation on a popular item | Everyone wants the same rows at the same instant |
| Multi-step debit: load wallet → check freeze → check KYC/AML → check limits → debit → write ledger → write audit | **Can't be expressed as one SQL statement**, so you need the row pinned across all of it |
| Claiming a job from a queue table | `FOR UPDATE SKIP LOCKED` (§9.5) |
| Anything where a failed retry is worse than a wait | Payments — a queued 40ms is fine, a 500 is not |

> [!info] The third option that's usually the right one
> Neither — **an atomic conditional `UPDATE`** (§9.4). If the whole operation is expressible in one statement, `UPDATE wallet SET balance = balance - :amt WHERE id = :id AND balance >= :amt` beats both: the engine holds a row lock for microseconds, there's no version column, no retry loop, and no deadlock window. Reach for optimistic/pessimistic only when the logic genuinely doesn't fit in one statement.

#### 8.3 What the databases themselves prefer internally

Worth knowing, because it explains why the same JPA code behaves differently across engines.

| Database | Internal concurrency model | Reads | Writes | Notes |
|---|---|---|---|---|
| **PostgreSQL** | MVCC | Snapshot — **never blocked** | Row lock, recorded in the tuple header (`xmax`) | No central lock table for row locks, so **no lock escalation** — millions of row locks are fine. `SERIALIZABLE` is **SSI**: genuinely optimistic, tracks read-sets and aborts on conflict. Default `READ COMMITTED`. |
| **MySQL / InnoDB** | MVCC + locking | Snapshot via undo log | Row locks in an **in-memory lock table**, plus **gap/next-key locks** at RR | Noticeably **more pessimistic** than Postgres by default — gap locks block inserts into ranges. Default `REPEATABLE READ`. |
| **MongoDB (WiredTiger)** | **Optimistic** at document level | Snapshot | Write conflict detected at commit | Single-document writes that conflict are **retried transparently by the server**. Multi-document transactions surface `TransientTransactionError` and **your app must retry**. Idiomatic path is atomic operators (`$inc`, `findAndModify`) — the direct analogue of §9.4. |
| **Oracle** | MVCC | Never blocked | Row locks | `SELECT ... FOR UPDATE` is idiomatic; readers never block writers. |
| **SQL Server** | **Pessimistic by default** | Takes **shared locks** — readers *do* block writers | Row locks with **escalation** to page/table | The outlier. Turn on `READ_COMMITTED_SNAPSHOT` to get Postgres-like MVCC behaviour — most modern deployments do. |
| **Spanner** | Pessimistic 2PL | Lock-free snapshot reads | Two-phase locking for read-write txns | Plus TrueTime for external consistency. |
| **CockroachDB** | Was optimistic → added pessimistic | Snapshot | Locking for contended keys | They moved *toward* pessimistic precisely because of retry storms. |

> [!info] The pattern across all of them
> Almost every engine is **optimistic for reads (MVCC snapshots) and pessimistic for writes (row locks)** — which is exactly the "MVCC handles reads, locking handles writes" model from §2.6. The genuinely optimistic outliers are Postgres SSI and MongoDB/WiredTiger, and both handle it by **aborting and retrying**, which is the cost you inherit.
>
> Separately: **Hibernate/JPA defaults to optimistic** (`@Version`). That's an application-layer choice, not a database one — an ORM can't hold a DB lock across a detached session, so optimistic is the only thing it can offer by default.

#### 8.4 Why optimistic locking breaks down at scale — retry storms

This is the most important practical limit, and it's a favourite senior-level question.

Take a merchant settlement account during a sale — one row, balance ₹50 Cr, ~500 TPS of debits. Under optimistic locking:

```
500 concurrent transactions all read version = 105
  → all 500 compute their new balance
  → all 500 issue UPDATE ... WHERE version = 105
  →   1 succeeds (version → 106)
  → 499 update 0 rows, throw, and retry

Next round: 499 read version = 106 → 1 succeeds → 498 retry
Next round: 498 ...
```

The cost is **quadratic**. To push N transactions through one hot row you perform roughly `N + (N-1) + … + 1 = N(N+1)/2` attempts — for N=500 that's ~125,000 attempted transactions to commit 500. And the wasted work is *worse than idle*: each failed attempt burned a connection, a snapshot, and the CPU to compute a balance it then threw away.

> [!warning] Three compounding failure modes
> 1. **Throughput collapse** — the DB spends most of its capacity on transactions that will be rolled back.
> 2. **Starvation** — optimistic retry has no fairness. A transaction can lose the race repeatedly and never commit, while pessimistic locking queues writers roughly FIFO.
> 3. **Retry amplification** — retries add load, which slows things down, which causes more conflicts, which causes more retries. Without jitter and a strict `maxAttempts`, this is a self-sustaining outage.

Under pessimistic locking the same 500 transactions simply **queue**: total work is linear, each transaction succeeds on its first attempt, and latency degrades gracefully instead of the system melting down.

#### 8.5 What high-throughput payment systems actually do

Rarely "pick optimistic or pessimistic." They apply a **ladder**, in this order:

**1. Idempotency first — before you ever reach the balance.**
Deduplicate on RRN / UTR / transaction ID / idempotency key (§10.2). A large fraction of duplicate traffic is retries, and this eliminates them before they can contend for anything.

**2. Atomic SQL updates.** ⭐ The workhorse.
```sql
UPDATE wallet SET balance = balance - :amount
 WHERE id = :id AND balance >= :amount;
```
One statement, row locked for microseconds, invariant enforced by the `WHERE`. No version column, no retry loop.

**3. Pessimistic locking — when the business logic won't fit in one statement.**
Load wallet → check freeze status → check KYC → check AML → check velocity limits → debit → write ledger → write audit → commit. That can't be one `UPDATE`, so you pin the row with `SELECT ... FOR UPDATE` for the duration.

**4. Ledger-first architecture.** ⭐ What large systems evolve toward.
Stop updating a hot balance row at all. Append immutable entries and *derive* the balance (§10.5):
```
ledger:  +1000   -200   -300   +500   -100
balance: SUM(...) — with periodic snapshot rows to keep it fast
```
`INSERT`s don't contend with each other the way repeated `UPDATE`s on one row do. This converts a contention problem into a storage problem, which is a much better trade.

**5. Partitioning / serialization by key.**
Route every transaction for a given account to the same Kafka partition ([[3. Consumer]]); one consumer processes that account's events sequentially. **No two threads ever touch that account concurrently**, so the locking question disappears entirely — the ordering guarantee does the work.

> [!warning] On what NPCI / Visa / Mastercard "actually do"
> Their internals aren't public, so state this carefully — claiming specific knowledge is a bad look in an interview. What's safe and accurate: systems at that scale are *typically* built from append-only financial records, atomic operations, partitioning/sharding so same-account operations serialize, stream processing for ordering, idempotency on RRN/UTR, and **very short** lock durations where locks are used at all.
>
> What you *can* assert confidently: plain optimistic locking on a hot shared account at thousands of TPS would be a poor fit, for the retry-storm reasons in §8.4.

> [!example] Where a UPI switch sits in this
> Worth being precise about, because it's a common interview follow-up: a **switch is usually not the system of record for customer balances.** The issuer bank's **Core Banking System owns the balance** and applies the debit safely.
>
> The switch's job is routing, validation, orchestration, timeout/reversal handling, and **idempotency on RRN/UTR** — so it typically isn't running 20 instances contending on one balance row at all. Knowing which component owns the money is half of answering "how do you handle concurrency here?"

#### 8.6 The interview answer

> **Q: Would you use optimistic locking for a merchant account receiving thousands of transactions per second?**
>
> "No. Optimistic locking is the right default when conflicts are *rare* — user profiles, configuration, anything with a single logical editor — because it never blocks and has no deadlock risk. But it's a bet, and on a hot merchant account you lose that bet on nearly every transaction: hundreds of writers read the same version, one commits, the rest roll back and retry. That's a retry storm, the work is quadratic in the contention, and there's no fairness so transactions can starve.
>
> For high-contention financial updates I'd prefer, in order: an **atomic conditional `UPDATE`** so the read-modify-write never leaves the database; **pessimistic locking** when the business logic is too complex for one statement; and at real scale a **ledger-based design** where balances are derived from append-only entries, combined with **partitioning by account** so operations on the same account are serialized by the queue rather than by a lock. Idempotency on the transaction reference sits in front of all of it."

### 9. Spring Boot — How This Actually Looks

#### 9.1 `@Transactional` — the Foundation

Everything below depends on this annotation being correctly applied, and it's the single most misunderstood piece of Spring.

**What it actually does.** Spring creates a **proxy** around your bean. When an outside caller invokes an annotated method, the proxy runs the transaction lifecycle around your code:

```
proxy intercepts call
  → PlatformTransactionManager.getTransaction()   →  BEGIN  (connection bound to the thread)
  → your method body runs
  → normal return   →  flush + COMMIT
  → RuntimeException →  ROLLBACK
  → connection released back to the pool
```

The connection is bound to the current thread (via `TransactionSynchronizationManager`), which is how a repository call three layers down joins *your* transaction without you passing anything.

##### How it maps to ACID

| ACID | What `@Transactional` gives you |
|---|---|
| **Atomicity** | The method *is* the unit. Return → `COMMIT`, unchecked exception → `ROLLBACK`. This is the annotation's primary job. |
| **Consistency** | Indirect — it defers constraint checking to commit time, so your invariants are evaluated once against the final state, not mid-way. |
| **Isolation** | `@Transactional(isolation = ...)` sets the level *for this transaction only* — the precise, surgical alternative to changing the server default (§3). |
| **Durability** | Free once `COMMIT` returns — that's the WAL `fsync`. `@Transactional` just decides *when* commit happens. |

##### The attributes that matter

```java
@Transactional(
    propagation = Propagation.REQUIRED,        // default
    isolation   = Isolation.READ_COMMITTED,    // default = DEFAULT (uses the DB's setting)
    timeout     = 5,                           // seconds; caps lock-hold duration
    readOnly    = false,
    rollbackFor = Exception.class              // include checked exceptions
)
```

**Propagation** — what happens when an already-transactional method calls another:

| Value | Behaviour | Payments use |
|---|---|---|
| `REQUIRED` | Join the existing transaction, or start one. **Default.** | Almost everything |
| `REQUIRES_NEW` | **Suspend** the caller's transaction, run in a genuinely separate one | Audit/log rows that must survive even if the payment rolls back |
| `NESTED` | Savepoint inside the current transaction; can roll back partially | Retrying one leg of a batch |
| `MANDATORY` | Throw if there's no existing transaction | Enforcing "this must be called inside a transaction" |
| `SUPPORTS` | Join if present, else run non-transactionally | Reads |
| `NOT_SUPPORTED` | Suspend and run without a transaction | A slow report you don't want holding a connection |
| `NEVER` | Throw if a transaction exists | Rare |

> [!warning] `REQUIRES_NEW` uses a *second* connection
> The outer transaction is suspended but still holds its connection and its locks. If the inner transaction needs a row the outer one locked, you deadlock **against yourself** — and with a pool size of N, N concurrent `REQUIRES_NEW` calls can exhaust the pool with every thread waiting for a second connection.

**`readOnly = true`** — sets the Hibernate flush mode to `MANUAL` (skips dirty-checking, a real win on large result sets), marks the JDBC connection read-only so the driver/DB can optimize, and lets routing datasources send the query to a **read replica**. Use it on every query method.

**`timeout`** — the safety net for §9.3. Caps how long the transaction (and therefore every lock it holds) can live.

##### The four ways it silently does nothing

> [!warning] All four fail *silently* — no transaction, no error, no log
> **1. Self-invocation.** Calling `this.debit()` from another method in the same class bypasses the proxy entirely.
> ```java
> public void process() {
>     this.debit(id, amt);   // ❌ no transaction — the proxy was never involved
> }
> @Transactional public void debit(...) { }
> ```
> Fix: inject the bean into itself, split into two beans (preferred), or use `TransactionTemplate`.
>
> **2. Non-public methods.** Spring's default proxying ignores `private`, `protected`, and package-private methods.
>
> **3. Checked exceptions.** The default rollback rule is `RuntimeException` and `Error` **only**. A checked exception **commits**. Use `rollbackFor = Exception.class`.
>
> **4. Swallowed exceptions.** A `try/catch` inside the method that doesn't rethrow means Spring sees a normal return and commits the partial work.

Also: once *any* participant marks the transaction rollback-only, the whole thing is doomed. Catching an exception from an inner `REQUIRED` method and continuing gets you `UnexpectedRollbackException` at commit — the classic "but I handled it!" bug.

##### Programmatic alternative

When you need a transaction boundary narrower than a method — a common need with locking, to keep the locked window tiny:

```java
private final TransactionTemplate txTemplate;

public void process(Long id) {
    callExternalPsp();                                  // outside any transaction ✅
    txTemplate.execute(status -> walletRepo.debitIfSufficient(id, amt));   // tiny window
}
```

#### 9.2 Optimistic — `@Version`

JPA does all the work. Just add the field:

```java
@Entity
public class Wallet {
    @Id
    private Long id;

    private BigDecimal balance;

    @Version                       // jakarta.persistence.Version
    private Long version;          // Hibernate manages this — never set it manually
}
```

Hibernate now generates `UPDATE wallet SET balance=?, version=8 WHERE id=? AND version=7` automatically on flush. If 0 rows are affected it throws `ObjectOptimisticLockingFailureException`.

Handle the retry — **the retry must be outside the transaction**, because a failed transaction is already marked rollback-only:

```java
@Service
public class WalletService {

    @Retryable(
        retryFor = ObjectOptimisticLockingFailureException.class,
        maxAttempts = 3,
        backoff = @Backoff(delay = 50, multiplier = 2, random = true)  // jitter
    )
    @Transactional
    public void debit(Long walletId, BigDecimal amount) {
        Wallet w = walletRepo.findById(walletId).orElseThrow();
        if (w.getBalance().compareTo(amount) < 0) {
            throw new InsufficientBalanceException();
        }
        w.setBalance(w.getBalance().subtract(amount));
        // no save() needed — dirty checking flushes at commit
    }

    @Recover
    public void debitFailed(ObjectOptimisticLockingFailureException e, Long id, BigDecimal amt) {
        throw new PaymentBusyException("Too many concurrent operations on wallet " + id);
    }
}
```

> [!warning] Ordering matters
> `@Retryable` must sit **outside** `@Transactional` so each attempt gets a fresh transaction. Since both are proxy-based and Spring orders `@Retryable` first by default, putting them on the same public method works — but calling `debit()` from another method *in the same class* bypasses both proxies entirely.

#### 9.3 Pessimistic — `@Lock`

```java
public interface WalletRepository extends JpaRepository<Wallet, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)                  // → SELECT ... FOR UPDATE
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
    @Query("select w from Wallet w where w.id = :id")
    Optional<Wallet> findByIdForUpdate(@Param("id") Long id);
}
```

```java
@Transactional
public void debit(Long walletId, BigDecimal amount) {
    Wallet w = walletRepo.findByIdForUpdate(walletId).orElseThrow();   // blocks here
    if (w.getBalance().compareTo(amount) < 0) throw new InsufficientBalanceException();
    w.setBalance(w.getBalance().subtract(amount));
}   // lock released at commit
```

`LockModeType` values worth knowing:

|Mode|SQL|Meaning|
|---|---|---|
|`PESSIMISTIC_READ`|`FOR SHARE`|Shared lock|
|`PESSIMISTIC_WRITE`|`FOR UPDATE`|Exclusive lock — the one you'll use|
|`PESSIMISTIC_FORCE_INCREMENT`|`FOR UPDATE` + version bump|Lock *and* signal a change to optimistic readers|
|`OPTIMISTIC`|—|Version-check a row you only *read*|
|`OPTIMISTIC_FORCE_INCREMENT`|—|Bump parent version when a child changes (e.g. edit a `TxnLine`, version the `Txn`)|

Always set a **lock timeout**. Without it, a stuck transaction blocks every subsequent request on that row until the connection dies.

#### 9.4 Skip JPA entirely — the atomic update

The fastest and safest fix for lost update is often to **not read into Java at all**. Let the database do the arithmetic and enforce the invariant in the `WHERE` clause:

```java
@Modifying
@Query("""
    update Wallet w
       set w.balance = w.balance - :amount
     where w.id = :id
       and w.balance >= :amount
    """)
int debitIfSufficient(@Param("id") Long id, @Param("amount") BigDecimal amount);
```

```java
int rows = walletRepo.debitIfSufficient(id, amount);
if (rows == 0) throw new InsufficientBalanceException();
```

One statement, one row lock held for microseconds, no version column, no retry loop, no deadlock window. **Mention this in interviews** — reaching straight for `FOR UPDATE` when an atomic conditional update would do is a common mistake.

Caveat: it bypasses the persistence context, so add `@Modifying(clearAutomatically = true, flushAutomatically = true)` if you touch that entity elsewhere in the same transaction.

#### 9.5 `SKIP LOCKED` — the payout worker queue

Ten pods poll a `payout_job` table. Without `SKIP LOCKED`, they all block on the same first row and you get zero parallelism. With it, each pod grabs a *different* batch:

```java
public interface PayoutJobRepository extends JpaRepository<PayoutJob, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout",
                           value = "-2"))     // -2 = SKIP LOCKED in Hibernate
    @Query("""
        select j from PayoutJob j
         where j.status = 'PENDING'
         order by j.createdAt
        """)
    List<PayoutJob> claimBatch(Pageable pageable);
}
```

This gives you a competing-consumers queue with no Kafka, no Redis, and exactly-once-per-row claiming — the same role `BlockingQueue` plays in a single JVM.

#### 9.6 Transaction hygiene

Non-negotiable rules once locks are involved:

- **Never make an HTTP call inside a locked transaction.** Calling a PSP (Razorpay/Stripe) while holding `FOR UPDATE` means their p99 latency becomes *your* lock duration. Pattern: lock → write intent row → commit → call PSP → new transaction to record result.
- **Keep transactions short.** Lock duration = transaction duration, always.
- **`@Transactional(readOnly = true)`** on reads — skips Hibernate dirty checking and routes to replicas.
- **Set `spring.jpa.properties.jakarta.persistence.lock.timeout`** and Postgres `lock_timeout` globally as a safety net.
- **Self-invocation doesn't work.** `this.debit()` skips the proxy, so no transaction and no retry.

### 10. Real-World Payments Scenarios

#### 10.1 Double-spend on a wallet

The §3.4 lost update, in production. Two concurrent debits of ₹200 and ₹300 on a ₹1000 balance leave ₹700 instead of ₹500 — the system minted money.

**Fix:** atomic conditional update (§9.4), or `FOR UPDATE`. Optimistic works too but a hot wallet will thrash on retries.

#### 10.2 Double charge from a retry (idempotency)

The client times out and retries; the request is genuinely processed twice. **No isolation level fixes this** — they're two legitimately distinct transactions. This is an *application* concern.

**Fix — let a unique constraint be the lock:**

```sql
CREATE UNIQUE INDEX ux_payment_idem ON payment (idempotency_key);
```

```java
@Transactional
public PaymentResult charge(ChargeRequest req) {
    try {
        paymentRepo.saveAndFlush(Payment.pending(req));   // flush forces the constraint check now
    } catch (DataIntegrityViolationException e) {
        return paymentRepo.findByIdempotencyKey(req.key())   // already processed — return the original
                          .map(PaymentResult::from)
                          .orElseThrow();
    }
    // ... proceed to charge
}
```

Insert-first is better than check-then-insert: the check-then-insert has a race window between the `SELECT` and the `INSERT`, and the unique index closes it atomically at the storage layer.

#### 10.3 Refund exceeding the original amount

Two partial refunds of ₹600 each against an ₹1000 payment. Both read `refunded_total = 0`, both pass validation, both write. Total refunded = ₹1200.

**Fix:** either lock the parent `payment` row with `PESSIMISTIC_WRITE` before summing refunds, or push the invariant into SQL:

```sql
UPDATE payment
   SET refunded_total = refunded_total + :amt
 WHERE id = :id AND refunded_total + :amt <= amount;
```

Zero rows affected → reject. Same shape as §9.4.

#### 10.4 Deadlock in a fund transfer

The textbook case. Two transfers in opposite directions:

```
T1 (A→B): lock A ... then wants B
T2 (B→A): lock B ... then wants A
→ circular wait. MySQL error 1213, Postgres SQLSTATE 40P01.
```

Identical to Java's dining-philosophers deadlock in [[1. Core Fundamentals]], and the fix is identical: **impose a global lock ordering.**

```java
Long first  = Math.min(fromId, toId);
Long second = Math.max(fromId, toId);
walletRepo.findByIdForUpdate(first);
walletRepo.findByIdForUpdate(second);   // every transaction locks in ascending ID order
```

Databases *detect* deadlocks and kill a victim, unlike the JVM which just hangs — but a killed transaction is still a failed payment. Order your locks, and retry on `CannotAcquireLockException`.

#### 10.5 Ledger design — sidestepping locks entirely

The strongest answer to "how do real payment systems handle this?" is that they **avoid the hot-row update.** A double-entry ledger is **append-only**:

```
ledger_entry (id, account_id, txn_id, direction, amount, created_at)
```

Debits and credits are pure `INSERT`s — no contention, since inserts don't fight over an existing row. Balance is `SUM(...)`, kept fast with a periodic snapshot/rollup row.

Adjacent patterns worth naming:

- **Reserve-then-capture (holds).** Authorization creates a `HOLD` row; `available_balance = balance - SUM(active holds)`. Shortens the locked window to just the reservation.
- **Transactional outbox.** Write the state change and an `outbox` row in *one* transaction, publish to Kafka after commit. Removes the "DB committed but event lost" gap — no distributed transaction needed.
- **Partition by key.** Route all operations for a wallet to one Kafka partition (see [[3. Consumer]]) so they're processed serially by construction. Contention disappears because concurrency does.

#### 10.6 When the database isn't enough

Everything above works because the lock and the data live in the **same transaction** — that's what makes DB locking genuinely safe. Once the thing you're protecting is *outside* the database (a nightly job that must run on one pod, a PSP API you mustn't call twice, a cross-service counter), you lose that property and need a distributed lock.

That's a materially weaker guarantee, and it's covered in [[10. Distributed Concurrency]] — Redis locks, why a lease-based lock can be held by two clients at once, what happens when Redis fails over, and fencing tokens.

There's a second, separate way the database stops being enough: when a single operation has effects **outside** the transaction — a Kafka publish, a PSP call, work handed to another thread. A rollback can't reach any of those, no matter how correct your locking is. That's [[11. Transaction Boundaries]] — outbox, sagas, idempotent consumers, and why 2PC isn't the answer.

> [!info] The rule that connects the two notes
> **If the resource is in your database, lock it in your database.** Reach for Redis only when it isn't.
