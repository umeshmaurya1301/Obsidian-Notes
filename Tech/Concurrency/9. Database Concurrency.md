Covers Roadmap section 9. Notes 1–8 were about concurrency **inside one JVM** — threads, locks, atomics, pools. This note moves the shared mutable state **into the database**, where it's shared across every instance of your service. The problems rhyme (lost updates, stale reads, deadlocks) but the tools are completely different: no `synchronized` here, only isolation levels, MVCC snapshots, and row locks.

> [!info] The through-line of this note
> One chain, read in order:
>
> 1. **ACID exists because four things went wrong** (§1) — partial updates, invalid data, concurrent users, crashes. Four failures, four properties (§2).
> 2. Of those four, **only Isolation is yours to think about.** Atomicity, Consistency and Durability the database handles for you; Isolation is where *your* code and *your* SQL decide whether you're correct.
> 3. Isolation is defined by what it **forbids**, so learn the **anomalies first** (§3) — dirty read, non-repeatable read, phantom, lost update. **Isolation levels** (§4) are just named packages of "which of these four can still happen."
> 4. Databases deliver those guarantees two ways: **locks** (§5) — old, simple, and readers block writers — and **MVCC** (§6), which keeps multiple row versions so a reader gets a consistent **snapshot** and never blocks anyone.
> 5. MVCC covers **reads only**. Writes still take **exclusive row locks**, which is where **deadlocks** (§7) come from, and what actually happens when two transactions update the same row (§8) is the single most misunderstood part of this topic.
> 6. Then the practical half: the **toolkit for a correct balance update** (§9), **MVCC vs optimistic vs pessimistic** (§10) — a guaranteed interview question — **PostgreSQL vs MySQL** (§11), and the end-to-end model (§12).
>
> One line to anchor everything: **MVCC makes reads cheap; it does nothing for writes. Two transactions updating the same row still serialise on a row lock.**

## Short Notes

---

### 1. Why ACID Exists — the Four Failures

Four concrete failures, each answered by one property:

| Failure | What happens | Property |
|---|---|---|
| **Partial update** | Debit Alice ₹300, crash before crediting Bob → ₹300 vanishes | **Atomicity** |
| **Invalid data** | `balance = -500`, unknown account type, duplicate PK | **Consistency** |
| **Concurrent users** | Two txns read `1000`, one writes `700`, other writes `500` → final `500`, should be `200` | **Isolation** |
| **Crash after commit** | DB says "commit successful", power dies, transaction is gone | **Durability** |

- Every one of these is a *real* production incident shape, not a textbook exercise
- The concurrency failure (row 3) is the **lost update** — it comes back in §3, §8 and §9

---

### 2. ACID — and Why Interviews Only Ask About Isolation

| Property | Guarantee |
|---|---|
| **Atomicity** | All or nothing |
| **Consistency** | Valid state → valid state (constraints, FKs, triggers hold) |
| **Isolation** | Concurrent transactions behave as if alone |
| **Durability** | Committed data survives a crash |

- **A, C and D are the database's job** — WAL, redo/undo logs, constraint checking. You rarely tune them
- **Isolation is yours** — it's where your isolation level, your SQL shape, and your retry policy decide correctness
- Isolation means: a transaction behaves **as if executing alone**, even with hundreds running together
- Running everything serially would be correct but far too slow — isolation is the **correctness/concurrency trade-off**

> Backend engineers deal with concurrent users, race conditions, locking, deadlocks and throughput. That's why the interview lives here.

---

### 3. The Four Isolation Anomalies

The anomalies came **first**; isolation levels were designed later to forbid them.

| Anomaly | What T1 sees | Root cause |
|---|---|---|
| **Dirty Read** | Reads T2's **uncommitted** `500`; T2 rolls back → the value never existed | Reading uncommitted data |
| **Non-Repeatable Read** | Reads `1000`, T2 updates + commits, T1 re-reads → `1500` | **Same row** changed mid-transaction |
| **Phantom Read** | `WHERE salary > 5000` returns 5 rows, T2 inserts, re-run → 6 rows | **New rows** matched the same predicate |
| **Lost Update** | T1 and T2 both read `1000`, both write → last writer wins | Read-modify-write with no guard |

- **Non-repeatable vs phantom** is the classic follow-up: non-repeatable = **an existing row changed**; phantom = **the row set changed**
- **Lost update** is the odd one out — it's not in the original SQL standard list, and it's the one *your application code* usually causes

---

### 4. Isolation Levels

Levels are named packages of "which anomalies can still happen":

| Level | Dirty Read | Non-Repeatable | Phantom | Lost Update |
|---|---|---|---|---|
| **Read Uncommitted** | Possible | Possible | Possible | Possible |
| **Read Committed** | Prevented | Possible | Possible | Possible |
| **Repeatable Read** | Prevented | Prevented | DB-dependent | Usually prevented |
| **Serializable** | Prevented | Prevented | Prevented | Prevented |

- **Read Committed** — each *statement* sees a fresh snapshot. **PostgreSQL's default**
- **Repeatable Read** — the *transaction* sees one snapshot throughout; the same row always returns the same value. **MySQL InnoDB's default**
- **Serializable** — the result must match *some* serial order. Highest correctness, lowest concurrency, **may abort your transaction**
- ⚠️ **Levels are not portable.** PostgreSQL's Repeatable Read is snapshot isolation and blocks phantoms; InnoDB blocks them with **next-key (gap) locks**; PostgreSQL treats Read Uncommitted as Read Committed (it never gives dirty reads)
- Higher level ⇒ more correctness, less concurrency, **more aborts you must retry**

---

### 5. Locks — Shared, Exclusive, and Their Cost

| Lock | Used by | Rule |
|---|---|---|
| **Shared (S)** | Reads | Many readers at once |
| **Exclusive (X)** | Writes | Exactly one writer, no readers |

| Existing lock | New read | New write |
|---|---|---|
| **Shared** | ✅ allowed | ❌ blocked |
| **Exclusive** | ❌ blocked | ❌ blocked |

- The oldest mechanism, and correct — but **readers block writers and writers block readers**
- Consequences: waiting, deadlocks, and throughput that collapses under load
- That cost is exactly what **MVCC** was invented to remove (§6)

---

### 6. MVCC — Multi-Version Concurrency Control

- **Never overwrite in place** — an update creates a **new version** of the row, the old one stays readable
- A transaction takes a **snapshot** — a photograph of which versions are visible to it. Later commits don't alter your photograph

```text
10:00  T1 starts → snapshot: balance = 1000
10:01  T2 updates balance = 300, COMMIT   → version 2 created
10:02  T1 reads  → still sees 1000        (its snapshot is unchanged)
```

- Payoff: **readers never block writers, writers never block readers**
- ⭐ **MVCC applies to READS only.** Writes still take exclusive row locks — the single most misunderstood point in this topic
- Snapshot *scope* is set by the isolation level: per-statement (Read Committed) vs per-transaction (Repeatable Read)

---

### 7. Deadlocks in the Database

- Same cycle as in-JVM deadlock (see [[3. Synchronization]] §1's shared-state framing), but the resources are **rows**
- Classic trigger: two transfers grabbing the same two accounts in **opposite order**

```text
T1: lock row A ──wants──► row B
T2: lock row B ──wants──► row A     → cycle, neither proceeds
```

- The DB **detects the cycle and aborts one transaction** — you get an error, not a hang (`deadlock detected` in PostgreSQL, error 1213 in InnoDB)
- **Lock-wait timeout is a different thing** — no cycle, just waiting too long (`innodb_lock_wait_timeout`)
- **Prevention**: consistent lock ordering (always touch accounts in ascending id), keep transactions short, touch fewer rows, avoid user-think-time inside a transaction
- ⚠️ **Deadlocks are normal under load, not a bug to eliminate** — your app must **catch and retry** them idempotently

---

### 8. What Actually Happens on a Concurrent Write

Three transactions, `balance = 1000`, each withdrawing `700`:

```text
T1, T2, T3 all READ 1000        ← MVCC, nobody blocks
T2 reaches UPDATE → takes the exclusive row lock
T1, T3 → WAIT
T2 commits, balance = 300
T1 wakes up …
```

- **Naive expectation**: T1 applies `1000 - 700` from its stale snapshot → three withdrawals, balance still `300`. **Wrong**
- **What really happens (PostgreSQL, Read Committed)**: the waiting UPDATE **rechecks the latest row version** (`EvalPlanQual`), re-evaluates its `WHERE`, and computes from `300`, not `1000`
- **Under Repeatable Read** PostgreSQL refuses instead: `could not serialize access due to concurrent update` — your app must retry
- ⚠️ The recheck only protects `SET balance = balance - 700` (computed **in the database**). It cannot save `SELECT` → compute in Java → `SET balance = 300` — that's a genuine lost update

---

### 9. Protecting a Balance Update in Production

Layer these; they're complementary, not alternatives:

| # | Mechanism | Shape |
|---|---|---|
| 1 | **Condition in the `WHERE`** ⭐ | `SET balance = balance - 700 WHERE id = 1 AND balance >= 700` → **0 rows** = insufficient funds |
| 2 | **`CHECK` constraint** | `CHECK (balance >= 0)` — the database refuses `-400` no matter which code path |
| 3 | **`SELECT … FOR UPDATE`** | Pessimistic — lock the row up front, others queue |
| 4 | **Serializable + retry** | DB raises a serialization failure; the app retries |
| 5 | **Optimistic version column** | `SET version = version + 1 WHERE version = 5` → 0 rows = someone beat you, retry |

- ⭐ **Do the arithmetic in SQL, not in your application** — `balance = balance - ?` beats `SET balance = <value computed in Java>`
- **0 rows updated is a signal, not a no-op.** Always check the affected-row count and branch on it
- Constraints are the last line of defence — they hold even when a new code path forgets the rule
- Every retry path must be **idempotent** ([[10. Distributed Concurrency]])

---

### 10. MVCC vs Optimistic vs Pessimistic Locking

The guaranteed interview question. They solve **three different problems**:

| | **MVCC** | **Optimistic Locking** | **Pessimistic Locking** |
|---|---|---|---|
| Purpose | Consistent **reads** | **Detect** write conflicts | **Prevent** write conflicts |
| Where it lives | Inside the database | Application layer (version column) | Database (`FOR UPDATE`) |
| Waiting | None | None | Others block |
| On conflict | N/A | Fail, then **retry** | Never happens — you waited |
| Best for | Everything (it's automatic) | Profiles, CMS, product details — **low contention** | Wallet, ledger, inventory, ticket booking — **high contention** |

```text
MVCC                → makes reads fast
Optimistic Locking  → detects conflicts after the fact
Pessimistic Locking → prevents conflicts up front
```

- They are **complementary, not competitors** — a payments system uses all three
- Rule of thumb: **conflicts rare ⇒ optimistic** (retries are cheap); **conflicts common ⇒ pessimistic** (retry storms are worse than waiting)

---

### 11. PostgreSQL vs MySQL InnoDB

- **"Does MySQL use MVCC?"** → Yes, but the precise answer is *"**InnoDB** does"* — MySQL has pluggable **storage engines** (InnoDB, MyISAM, Memory) and not all support it
- The storage engine owns storage, indexes, locks, transactions and crash recovery
- **InnoDB** (the default) provides ACID, MVCC, row locks, foreign keys, crash recovery, undo logs and redo logs

| | **PostgreSQL** | **MySQL InnoDB** |
|---|---|---|
| Old versions | Stored **in the table** as extra row versions | Reconstructed from **undo logs** |
| Cleanup | `VACUUM` reclaims dead tuples | Purge thread trims undo |
| Cost shape | Table bloat if VACUUM lags | Long transactions grow undo history |
| Default level | **Read Committed** | **Repeatable Read** |
| Phantoms at RR | Prevented (snapshot isolation) | Prevented via **next-key / gap locks** |

| Database | MVCC | Row locks |
|---|---|---|
| PostgreSQL | ✅ | ✅ |
| MySQL InnoDB | ✅ | ✅ |
| Oracle | ✅ | ✅ |
| SQL Server | Optional (snapshot isolation) | ✅ |

> **Do both still use locks?** Yes. Reads → MVCC. Writes → exclusive row locks. MVCC never eliminated locking.

### 12. The End-to-End Mental Model

```text
                    Client Request
                          │
                 BEGIN TRANSACTION
                          │
                   Read Operations
                          │
                  Uses MVCC Snapshot
                          │
            Readers Don't Block Writers
                          │
                   UPDATE / DELETE
                          │
             Acquire Exclusive Row Lock
                          │
           Waiting Transactions Queue Here
                          │
         Recheck Latest Row Version (if needed)
                          │

                          │
                   COMMIT / ROLLBACK
                          │
             Redo Logs Persist Changes
             Undo Logs Support Rollback / MVCC
```

- **Reads take the MVCC path; writes take the lock path.** Everything in this note hangs off that split
- Learn **anomalies → levels → mechanisms**, in that order
- Production financial systems combine **transactions + row locks + a SQL condition + constraints + retries**. No single one is sufficient

# Detailed Explanation

## Why ACID Exists — the Four Failures

ACID isn't an academic acronym someone invented top-down. Each letter is the answer to a specific way early databases lost data.

### 1. Partial updates → Atomicity

Transfer ₹300 from Alice to Bob:

```sql
UPDATE accounts SET balance = balance - 300 WHERE id = 'Alice';
-- 💥 crash here
UPDATE accounts SET balance = balance + 300 WHERE id = 'Bob';
```

Result: `Alice = 700`, `Bob = 500`. **₹300 has simply disappeared.** The money left one account and never arrived at the other, and no error was raised — the first statement succeeded.

**Atomicity** says the pair is indivisible: all of it, or none of it.

### 2. Invalid data → Consistency

Nothing stops a bad write from producing states that make no business sense:

```text
balance = -500
account_type = 'Unknown'
duplicate primary keys
```

**Consistency** means the database moves from one *valid* state to another — constraints, foreign keys, uniqueness and triggers all hold at commit. Note the distinction that gets asked: consistency is about **your declared rules**, not about concurrency. If you never declared `CHECK (balance >= 0)`, the database will happily store `-500` and still call itself consistent.

### 3. Concurrent users → Isolation

Two users update the same account at the same time. Both read `1000`; one writes `700`, the other writes `500`. Final balance: `500`. Correct answer: `200`.

One withdrawal vanished. This is the **lost update**, and it is the single most important failure in this note — it reappears in §3, §8 and §9.

**Isolation** is the property that makes concurrent transactions behave correctly.

### 4. Crash after commit → Durability

The database returns `Commit Successful`, the power fails a millisecond later, and after restart the transaction is gone. **Durability** says that once commit returns, the change survives — which is what the write-ahead log (redo log) is for.

## ACID — and Why Interviews Only Ask About Isolation

| Property | Purpose |
|---|---|
| **Atomicity** | All or nothing |
| **Consistency** | Valid state → valid state |
| **Isolation** | Concurrent transactions behave correctly |
| **Durability** | Committed data survives a crash |

**Three of the four are handled for you.** Atomicity and Durability come from the WAL and undo/redo logs; Consistency comes from the constraints you declare. You almost never tune these, and interviewers know it.

**Isolation is the one you own.** It is the property where your choices — isolation level, the shape of your SQL, whether you retry — determine whether the system is correct. Backend engineers spend their incidents on concurrent users, race conditions, locking, deadlocks and throughput. All of that is Isolation.

**What isolation actually promises:**

> A transaction should behave *as if it were executing alone*, even when hundreds are executing together.

**Why not just run them one at a time?** Because that's correct and useless:

```text
10,000 users → T1 → T2 → T3 → …   serial, correct, far too slow
```

You need **correctness *and* concurrency**. Isolation levels are the dial between them — and every step toward correctness costs throughput and adds transactions you must retry.

## The Four Isolation Anomalies

Learn these **before** the levels, because the levels are defined purely in terms of which anomalies they forbid. Get the anomalies right and the levels table becomes something you can derive rather than memorise.

### Dirty Read — reading uncommitted data

```text
T1: UPDATE balance = 500        (not committed)
T2: SELECT balance     → 500    ← reads uncommitted data
T1: ROLLBACK                     → actual balance is 1000
```

T2 acted on a value that **never existed** in any committed state of the database. Everything it computed from that read is wrong.

### Non-Repeatable Read — the same row changed

```text
T1: SELECT salary → 1000
T2: UPDATE salary = 1500; COMMIT
T1: SELECT salary → 1500        ← same query, same row, different answer
```

T1 is a single transaction that saw two different values for one row. Any logic that reads a value twice — validate then apply — is now inconsistent with itself.

### Phantom Read — the row *set* changed

```text
T1: SELECT * FROM employees WHERE salary > 5000  → 5 rows
T2: INSERT INTO employees (salary) VALUES (8000); COMMIT
T1: SELECT * FROM employees WHERE salary > 5000  → 6 rows   ← a phantom appeared
```

No existing row changed. A **new row** started matching the predicate.

> 💡 **Interview**: non-repeatable read vs phantom read? → Non-repeatable = an **existing row's value** changed. Phantom = the **set of rows matching your predicate** changed. That's why a row lock fixes the first but you need a range/predicate lock for the second.

### Lost Update — the one your code causes

```text
T1: read 1000                    T2: read 1000
T1: write 1000 - 300 = 700       T2: write 1000 - 500 = 500
                                 → final 500, one update lost
```

Last writer wins, silently. This is the same read-modify-write race as `count++` from [[3. Synchronization]] §1 — the shared state just happens to live in a database row instead of the heap.

It's worth calling out that lost update is **not** in the original SQL-standard anomaly list, which is why it doesn't map neatly onto the levels table. It's largely an artefact of how the *application* writes its SQL, which is exactly why §9 exists.

## Isolation Levels

Isolation levels are standardised packages of "which anomalies are still allowed."

| Level | Dirty Read | Non-Repeatable | Phantom | Lost Update |
|---|---|---|---|---|
| **Read Uncommitted** | Possible | Possible | Possible | Possible |
| **Read Committed** | Prevented | Possible | Possible | Possible |
| **Repeatable Read** | Prevented | Prevented | DB-dependent | Usually prevented |
| **Serializable** | Prevented | Prevented | Prevented | Prevented |

**Read Uncommitted** — you can see other transactions' uncommitted writes. Almost never useful. PostgreSQL accepts the syntax but silently treats it as Read Committed; it never produces dirty reads at all.

**Read Committed** — you only see committed data, but each *statement* gets a **fresh snapshot**. So two `SELECT`s in one transaction can legitimately disagree. **PostgreSQL's default**, and the right default for most OLTP work.

**Repeatable Read** — the whole *transaction* runs against one snapshot:

```text
balance = 1000
T1: SELECT balance → 1000
T2: UPDATE balance = 300; COMMIT
T1: SELECT balance → 1000        ← still 1000, T1's snapshot is fixed
```

The same row always returns the same value inside one transaction. **MySQL InnoDB's default.**

**Serializable** — the outcome must be equivalent to *some* serial order of the transactions:

```text
Behaves as:   T1 → T2 → T3
Even though the DB runs them concurrently
```

Highest correctness, lowest concurrency, and critically: **it may abort your transaction** with a serialization failure. Serializable is not a free upgrade — adopting it means adopting a retry loop.

> [!warning] Isolation levels are not portable between databases
> The SQL standard defines levels by *which anomalies are forbidden*, not by *how*. Vendors differ in ways that matter:
> - **PostgreSQL Repeatable Read** is snapshot isolation — it **does** prevent phantoms, despite the standard permitting them at this level.
> - **MySQL InnoDB Repeatable Read** prevents phantoms too, but through **next-key (gap) locks** — locking the *gaps between* index entries so no one can insert into your range. Different mechanism, different locking behaviour, different deadlock profile.
> - **PostgreSQL Read Uncommitted** behaves as Read Committed.
> - **PostgreSQL Serializable** uses SSI (serializable snapshot isolation) and aborts conflicting transactions; **InnoDB Serializable** instead turns plain `SELECT`s into locking reads.
>
> "We use Repeatable Read" tells you almost nothing until you say which database.

**The trade-off, stated plainly:** every step up the table buys correctness with concurrency, and hands you more aborted transactions to retry.

## Locks — Shared, Exclusive, and Their Cost

The oldest way to implement isolation, and the easiest to reason about.

**Shared lock (S)** — taken for reads. Many transactions can hold one on the same row at once:

```text
T1 read ─┐
T2 read ─┼── all proceed simultaneously
T3 read ─┘
```

**Exclusive lock (X)** — taken for writes. Exactly one holder, and no shared locks alongside it:

```text
T1 UPDATE → holds X lock
T2        → WAIT
T3        → WAIT
```

| Existing lock | New read | New write |
|---|---|---|
| **Shared** | ✅ allowed | ❌ blocked |
| **Exclusive** | ❌ blocked | ❌ blocked |

**The problem with a purely lock-based design** is the top-right and bottom-left of that table: **readers block writers and writers block readers.** In a read-heavy system — which almost every OLTP system is — a single long-running report can stall every write touching the same rows. Add deadlocks and the throughput collapse under load, and you have the motivation for the next section.

## MVCC — Multi-Version Concurrency Control

The core idea is one sentence: **never overwrite a row in place.**

An update creates a **new version** of the row and leaves the old one readable:

```text
Version 1: balance = 1000
      │  UPDATE balance = 300
      ▼
Version 2: balance = 300        ← Version 1 still exists and is still readable
```

### Snapshots

When a transaction starts (or, at Read Committed, when each statement starts) the database records **which versions are visible to it** — a snapshot. Think of it as taking a photograph. Other transactions committing afterwards don't retouch your photograph.

```text
10:00   T1 starts
        snapshot: balance = 1000
────────────────────────────────────
10:01   T2 UPDATE balance = 300
        COMMIT
────────────────────────────────────
10:02   T1 SELECT balance
        → still 1000
```

T1 isn't reading stale data by accident — it's reading a **consistent** view, deliberately. That's the whole point: T1 sees the database as it was at a single instant, rather than a smear of other people's half-finished work.

**The payoff:** readers never block writers, and writers never block readers. The two worst cells in the lock-compatibility table are gone.

> [!warning] MVCC is for READS only — this is the most misunderstood point in the topic
> MVCC gives you consistent, non-blocking **reads**. It does **nothing** for two transactions writing the same row. Those still serialise on an **exclusive row lock**, exactly as in §5.
>
> If you take one thing from this note: *"MVCC removed read-write blocking. It did not remove write-write blocking."* §8 is what that looks like in practice.

The isolation level controls the snapshot's **scope**: a new snapshot per statement (Read Committed) versus one snapshot for the whole transaction (Repeatable Read). That single knob is the entire difference between those two levels.

## Deadlocks in the Database

The same cycle you know from in-JVM concurrency, with **rows** as the contended resource instead of monitors.

```text
T1: UPDATE accounts WHERE id = A   → holds X lock on A
T2: UPDATE accounts WHERE id = B   → holds X lock on B
T1: UPDATE accounts WHERE id = B   → waits for T2
T2: UPDATE accounts WHERE id = A   → waits for T1
                                     → cycle
```

The classic trigger is a transfer, because the row order depends on the caller: `transfer(A → B)` and `transfer(B → A)` running concurrently grab the same two rows in opposite orders.

**The database resolves it for you.** Unlike a JVM deadlock, which just hangs, the database runs a deadlock detector, picks a **victim**, and aborts it:

```text
PostgreSQL:  ERROR: deadlock detected
MySQL InnoDB: ERROR 1213: Deadlock found when trying to get lock; try restarting transaction
```

Note what that means: **you get an exception, not a hang**, and the fix is in your application.

> [!info] Deadlock vs lock-wait timeout — different errors, different causes
> A **deadlock** is a genuine cycle; the DB detects it fast and kills one transaction. A **lock-wait timeout** (`innodb_lock_wait_timeout`, default 50 s) means there was *no* cycle — one transaction simply held a lock longer than the waiter was willing to wait. The second usually points at a long transaction or a slow external call inside one, not at lock ordering.

**Prevention** — the same playbook as JVM locks:

- **Consistent lock ordering** — always touch accounts in ascending id. Both `A→B` and `B→A` transfers then lock `A` first, and no cycle can form.
- **Keep transactions short.** The window for a cycle is the time you hold locks.
- **Touch fewer rows**, and take locks as late as possible.
- **Never wait on anything external inside a transaction** — no HTTP call, no user think-time, no queue publish. This is the database version of "never hold a lock during I/O."

> [!warning] Deadlocks are normal under load — plan to retry
> Under real concurrency you will get deadlocks, and that isn't a defect to engineer away entirely. What *is* a defect is not handling them. Catch the deadlock error, back off briefly with jitter, and retry the transaction — and make sure the retry is **idempotent** so a partially-applied effect isn't duplicated ([[10. Distributed Concurrency]]).

## What Actually Happens on a Concurrent Write

This is the section that separates people who have read about MVCC from people who understand it.

Three transactions, `balance = 1000`, each withdrawing `700`:

```text
T1 reads 1000
T2 reads 1000     ← all three succeed instantly, MVCC, nobody blocks
T3 reads 1000
```

**The naive (wrong) conclusion.** Everyone computed `1000 - 700 = 300`, so everyone writes `300`:

```text
writes: 300, 300, 300
final balance: 300
```

Three withdrawals of ₹700 happened and the balance dropped by ₹700. ₹1,400 conjured from nothing. If MVCC really worked this way, no bank could use it.

**What PostgreSQL actually does.** The reads are fine — snapshots, no blocking. The divergence is at the `UPDATE`:

```text
T2 reaches UPDATE → acquires EXCLUSIVE ROW LOCK
T1 → WAIT
T3 → WAIT

T2 commits → balance = 300, lock released

T1 wakes up …
```

And here is the key behaviour: **the database does not blindly apply T1's update against its stale snapshot.** Before proceeding, the waiting statement **rechecks the latest committed version of the row** — PostgreSQL calls this **EvalPlanQual** — and re-evaluates the statement against it:

```text
Not:  1000 - 700   (T1's snapshot value)
But:   300 - 700   (the current committed row)
```

So `balance = balance - 700` is computed from `300`, and the `WHERE` clause is re-checked against the new version too. The lost update is prevented **by the database**, for this shape of statement.

**Under Repeatable Read, PostgreSQL refuses instead.** Rechecking would break the promise that T1 sees one consistent snapshot, so rather than silently changing what T1 sees, it aborts:

```text
ERROR: could not serialize access due to concurrent update
```

Your application must catch that and retry. This is the trade-off from §4 made concrete: the stricter level converts a silent behaviour into an explicit failure you have to handle.

> [!warning] The recheck only saves *database-computed* updates
> This protection applies to `SET balance = balance - 700`, where the arithmetic happens **inside the database** against the current row. It cannot help you here:
> ```java
> // ❌ genuine lost update — no database recheck can save this
> long balance = jdbc.queryForObject("SELECT balance FROM account WHERE id = ?", ...); // 1000
> long updated = balance - 700;                                                        // computed in Java
> jdbc.update("UPDATE account SET balance = ? WHERE id = ?", updated, id);              // writes 300
> ```
> ```java
> // ✅ the database computes from the current row, and rechecks it
> jdbc.update("UPDATE account SET balance = balance - ? WHERE id = ? AND balance >= ?", 700, id, 700);
> ```
> The first version sends a **literal value** the database has no way to recognise as stale. Read-modify-write across a network round trip is the same bug as `count++`, and the database cannot fix it for you. That's what §9 is for.

## Protecting a Balance Update in Production

No single mechanism is sufficient. Real financial systems layer these.

### 1. Put the business condition in the `WHERE` ⭐

The highest-value line in this whole note:

```sql
UPDATE account
SET balance = balance - 700
WHERE id = 1
  AND balance >= 700;      -- the guard travels WITH the write
```

Two things happen at once: the arithmetic is done by the database against the current row, and the precondition is checked **atomically with the update**. There is no window between the check and the write for anyone to slip into.

If the balance is only `300`, the row doesn't match and you get:

```text
rows updated = 0
```

```java
int rows = jdbc.update(sql, amount, id, amount);
if (rows == 0) throw new InsufficientBalanceException();   // 0 rows is a SIGNAL, not a no-op
```

**Always check the affected-row count.** Silently ignoring a 0-row update is how "the payment said success but nothing moved" incidents happen.

### 2. `CHECK` constraint — the last line of defence

```sql
ALTER TABLE account ADD CONSTRAINT positive_balance CHECK (balance >= 0);
```

The database rejects `-400` no matter which service, script, or hand-run SQL statement attempted it. Application guards protect the paths you remembered; a constraint protects the ones you didn't.

### 3. `SELECT … FOR UPDATE` — pessimistic

```sql
BEGIN;
SELECT balance FROM account WHERE id = 1 FOR UPDATE;   -- X lock taken NOW
-- other transactions touching this row queue here
UPDATE account SET balance = ... WHERE id = 1;
COMMIT;
```

Locks the row immediately, so the read-then-write sequence is safe even with logic in between. This is what you use when the decision genuinely can't be expressed as one SQL statement. The cost is that everyone else waits — keep the transaction very short.

### 4. Serializable + retry

Let the database detect the conflict and raise a serialization failure, then retry in the application. Correct and simple to reason about, but it converts contention into aborted transactions, so it needs a real retry policy with backoff.

### 5. Optimistic locking with a version column

```sql
UPDATE account
SET balance = ?, version = version + 1
WHERE id = ? AND version = 5;
```

If someone else updated the row since you read it, the version no longer matches, `0 rows` come back, and you re-read and retry. This is application-level and portable — it's exactly what JPA's `@Version` does.

> [!tip] The production recipe
> For a wallet debit: **one statement**, arithmetic in SQL, the business rule in the `WHERE`, a `CHECK` constraint underneath, the affected-row count checked, and an idempotency key so a retry can't double-debit ([[10. Distributed Concurrency]], [[12. Lost Updates & High-Contention Architectures]]). Reach for `FOR UPDATE` only when the logic genuinely cannot be one statement.

## MVCC vs Optimistic vs Pessimistic Locking

A near-guaranteed interview question, and one people fumble because they treat the three as competing options. They aren't — they solve **three different problems**.

**MVCC** — *consistent reads.* Built into the database, always on, requires nothing from you. Readers never wait. It does **not** address write conflicts.

**Optimistic locking** — *detect* write conflicts. Assume conflicts are rare; proceed without locking; check at write time (version column) and retry if you lost. Nobody ever waits, but a conflict costs you a retry.

**Pessimistic locking** — *prevent* write conflicts. Assume conflicts are likely; take the lock first (`FOR UPDATE`); everyone else queues. Nobody ever retries, but everybody might wait.

| | **MVCC** | **Optimistic** | **Pessimistic** |
|---|---|---|---|
| Purpose | Consistent reads | **Detect** conflicts | **Prevent** conflicts |
| Layer | Database engine | Application (version column) | Database (`FOR UPDATE`) |
| Waiting | None | None | Yes |
| On conflict | N/A | Fail → retry | Doesn't arise |
| Cost under contention | — | Retry storms | Queueing, deadlock risk |
| Best for | Everything | Profiles, CMS, product details | Wallet, ledger, inventory, ticket booking |

```text
MVCC                → makes reads fast
        ─────────────────────────────
Optimistic Locking  → detects conflicts after the fact
        ─────────────────────────────
Pessimistic Locking → prevents conflicts up front
```

**They are complementary, not competitors.** A payments service uses MVCC for every read without thinking about it, optimistic locking on low-contention entities like merchant config, and pessimistic locking on the hot wallet row.

**How to choose, in one rule:** estimate the conflict rate. **Rare conflicts ⇒ optimistic** — retries are cheap and you never block. **Frequent conflicts ⇒ pessimistic** — under real contention, optimistic locking degenerates into a retry storm where most work is thrown away, and waiting in an orderly queue is strictly better.

## PostgreSQL vs MySQL InnoDB

**"Does MySQL use MVCC?"** Yes — but the precise answer, and the one that shows you know how MySQL is built, is:

> **MySQL's InnoDB storage engine uses MVCC.** Not every MySQL storage engine does.

MySQL is unusual in having pluggable **storage engines** — `InnoDB`, `MyISAM`, `Memory` and others. The engine, not the SQL layer, is responsible for storing data, indexes, locks, transactions and crash recovery. `MyISAM`, for instance, has table-level locking and no transactions at all.

**InnoDB** is the default and the only one you should be using for OLTP. It provides ACID, MVCC, row-level locks, foreign keys, crash recovery, undo logs and redo logs.

### How each stores old versions

The two databases reach the same guarantee by opposite routes:

**PostgreSQL** keeps old row versions **in the table itself**. An update writes a new tuple and marks the old one dead. Dead tuples stay until `VACUUM` reclaims them — which is why a lagging autovacuum, or a very long-running transaction that keeps old versions visible, shows up as **table bloat**.

**MySQL InnoDB** keeps the **current** row in place and pushes the previous image into the **undo log**. An older transaction that needs the earlier value reconstructs it by walking undo records backwards. The cost lands differently: a long transaction grows the **undo history**, which slows reads that must walk it.

| | **PostgreSQL** | **MySQL InnoDB** |
|---|---|---|
| Old versions | Extra row versions in the table | Reconstructed from undo logs |
| Cleanup | `VACUUM` | Purge thread |
| Long-transaction cost | Table bloat, VACUUM can't advance | Long undo chains slow reads |
| Default isolation | **Read Committed** | **Repeatable Read** |
| Phantoms at Repeatable Read | Prevented (snapshot isolation) | Prevented (next-key / gap locks) |

### Do both still use locks?

Yes — and this is the summary sentence for the whole note:

```text
Reads   → MVCC            (no blocking)
Writes  → Exclusive row locks   (serialised)
```

**MVCC did not eliminate locking.** It eliminated *read-write* blocking. Write-write conflicts are still resolved the old way.

| Database | MVCC | Row locks |
|---|---|---|
| PostgreSQL | ✅ | ✅ |
| MySQL InnoDB | ✅ | ✅ |
| Oracle | ✅ | ✅ |
| SQL Server | Optional snapshot isolation | ✅ |

## The End-to-End Mental Model

```text
                    Client Request
                          │
                          ▼
                 BEGIN TRANSACTION
                          │
                          ▼
                   Read Operations
                          │
                  Uses MVCC Snapshot
                          │
            Readers Don't Block Writers
                          │
                          ▼
                   UPDATE / DELETE
                          │
             Acquire Exclusive Row Lock
                          │
                          ▼
           Waiting Transactions Queue Here
                          │
                          ▼
         Recheck Latest Row Version (if needed)
                          │
                          ▼
         Business Rules / Constraints Evaluated
                          │
                          ▼
                   COMMIT / ROLLBACK
                          │
                          ▼
             Redo Logs Persist Changes
             Undo Logs Support Rollback / MVCC
```

**Read the diagram as two lanes.** Everything above `UPDATE / DELETE` is the **MVCC lane** — snapshots, no blocking, no locks. Everything below is the **lock lane** — serialised, queued, rechecked. Almost every confusion about database concurrency comes from applying one lane's rules to the other.

**If you remember only eight things:**

1. **ACID** exists to fix four concrete failures: partial updates, invalid data, concurrent users, crashes.
2. **Isolation** is the only ACID property you actively design for.
3. Learn **anomalies first**, then isolation levels — the levels are defined by what they forbid.
4. **Non-repeatable read** = an existing row changed. **Phantom** = the row set changed.
5. Isolation levels are **not portable** — PostgreSQL defaults to Read Committed, InnoDB to Repeatable Read, and they prevent phantoms by different mechanisms.
6. **MVCC is a read mechanism.** Writes still take exclusive row locks.
7. Do the arithmetic **in SQL** and put the business rule **in the `WHERE`** — then check the affected-row count.
8. **Optimistic** detects conflicts (rare conflicts); **pessimistic** prevents them (frequent conflicts); **MVCC** is neither — it's about reads.

## Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| What is MVCC? | Multiple versions of a row are kept, so readers get a consistent snapshot without blocking writers and without being blocked by them. |
| Does MVCC eliminate locks? | No. It removes read-write blocking. Conflicting **writes** still take exclusive row locks. |
| What is a snapshot? | The consistent view of the database a transaction sees; its scope (per statement vs per transaction) is set by the isolation level. |
| Which ACID property do interviews care about, and why? | Isolation — A, C and D are handled internally by the engine, while Isolation is where your level, SQL shape and retry policy decide correctness. |
| Is Consistency about concurrency? | No — it's about your declared rules (constraints, FKs, triggers) holding at commit. Concurrency is Isolation's job. |
| The four anomalies? | Dirty read, non-repeatable read, phantom read, lost update. |
| Non-repeatable read vs phantom? | Non-repeatable = an existing **row's value** changed. Phantom = the **set of rows** matching a predicate changed. |
| Which anomaly does the application usually cause? | Lost update — read-modify-write across a round trip, with no guard in the `WHERE`. |
| Default isolation level? | PostgreSQL: **Read Committed**. MySQL InnoDB: **Repeatable Read**. Always name the database. |
| Read Committed vs Repeatable Read? | Read Committed takes a fresh snapshot **per statement**; Repeatable Read uses **one snapshot for the transaction**. |
| Does Repeatable Read prevent phantoms? | Per the SQL standard, no. In practice PostgreSQL does (snapshot isolation) and InnoDB does (next-key/gap locks). |
| What does Serializable cost you? | Concurrency, plus **aborted transactions** — adopting it means adopting a retry loop. |
| Shared vs exclusive lock? | Shared = many readers; exclusive = one writer, no readers. Shared blocks writes; exclusive blocks everything. |
| Why was MVCC invented? | Pure locking makes readers block writers and vice versa, which destroys throughput in read-heavy OLTP. |
| Three transactions read 1000 and each withdraw 700 — what happens? | Reads are concurrent via MVCC; the updates serialise on the row lock. Each waiting update **rechecks the current row** and computes from it, so the balance decreases correctly. |
| What is `EvalPlanQual`? | PostgreSQL's row recheck: a blocked `UPDATE` re-reads the latest committed version and re-evaluates its `WHERE` before applying. |
| What happens instead under Repeatable Read? | PostgreSQL raises `could not serialize access due to concurrent update` — the app must retry. |
| Can the database prevent every lost update? | No. It can protect `SET balance = balance - ?`. It cannot protect a value you computed in Java from a stale read. |
| Best way to make a balance debit safe? | One statement: arithmetic in SQL, business rule in the `WHERE` (`AND balance >= ?`), then check the affected-row count. |
| What does "0 rows updated" mean? | Your precondition failed — insufficient balance, or someone else won the version race. It's a signal to branch on, never to ignore. |
| What does `SELECT … FOR UPDATE` do? | Takes the exclusive row lock immediately, so a read-then-write sequence is safe. Others queue — keep the transaction short. |
| Optimistic vs pessimistic locking? | Optimistic **detects** conflicts at write time via a version column and retries; pessimistic **prevents** them by locking first and making others wait. |
| When would you choose each? | Rare conflicts ⇒ optimistic (no waiting, cheap retries). Frequent conflicts ⇒ pessimistic (retry storms are worse than queueing). |
| MVCC vs optimistic locking? | MVCC gives consistent **reads** inside the engine; optimistic locking is an **application** strategy for detecting concurrent **writes**. |
| Does MySQL use MVCC? | Yes — **InnoDB** does. MySQL has pluggable storage engines and not all of them support MVCC or transactions. |
| What is InnoDB? | MySQL's default transactional storage engine: ACID, MVCC, row locks, foreign keys, crash recovery, undo and redo logs. |
| How do PostgreSQL and InnoDB differ in storing old versions? | PostgreSQL keeps extra row versions in the table (cleaned by `VACUUM`); InnoDB keeps the current row and reconstructs old ones from **undo logs**. |
| Why do long-running transactions hurt? | They hold old versions visible — PostgreSQL can't VACUUM (bloat), InnoDB grows undo history (slower reads). |
| What causes a database deadlock? | Two transactions locking the same rows in **opposite order** — classically two transfers between the same pair of accounts. |
| How does the database handle a deadlock? | It detects the cycle, aborts a victim, and returns an error (`deadlock detected` / error 1213). You retry — it doesn't hang. |
| Deadlock vs lock-wait timeout? | Deadlock = a real cycle, detected fast. Lock-wait timeout = no cycle, just a lock held too long — usually a long transaction. |
| How do you prevent DB deadlocks? | Consistent lock ordering (e.g. ascending account id), short transactions, fewer rows touched, and never wait on I/O inside a transaction. |
