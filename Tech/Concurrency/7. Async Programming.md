Covers Roadmap section 7. [[2. Java Thread Basics]] §2 left you with a `Future` you can only *block on*. This note is the fix: `CompletableFuture` lets you say "when this finishes, do that" without a thread ever sitting on `get()`.

> [!info] The through-line of this note
> One limitation drives the whole design:
>
> 1. A plain `Future` is a dead end — the only way to use its result is `get()`, which **blocks a thread** (§1). For a payment handler calling three downstreams, that's three threads parked doing nothing.
> 2. `CompletableFuture` makes the result a **callback**: attach work that runs *when* the value arrives (§2). This is the pivot from pull to push.
> 3. From that one idea everything follows — **chaining** dependent steps (§3), **combining** independent results (§4), fanning out over many (§5).
> 4. Async code fails async, so **exception handling** needs its own operators (§6) — the most-skipped, most-asked part.
> 5. Every async op runs on *some* thread pool; **which pool** is a correctness decision (§7), and it links straight back to the `ForkJoinPool` warning in [[4. Executors and Thread Pools]].
>
> Anchor: **`Future` = a handle you block on; `CompletableFuture` = a pipeline you attach to.**

---

### 1. Why `Future` Isn't Enough

`Future` (from [[2. Java Thread Basics]]) can start async work, but to *use* the result you're stuck:

```java
Future<Balance> f = pool.submit(() -> cbs.fetchBalance(acct));
Balance b = f.get();   // BLOCKS this thread until done — the only option
```

Three things it can't do:
- **React without blocking** — no "run X when it completes"; a thread must wait.
- **Chain** — no way to feed the result into the next async step without blocking in between.
- **Combine** — no way to say "when *these two* finish, merge them."

`CompletableFuture<T>` (Java 8+) is a `Future` that also implements `CompletionStage` — it adds ~50 methods for exactly those three gaps. You describe a *pipeline of stages*; each stage runs when its input is ready, on a pool, without anyone blocking.

---

### 2. Creating and Attaching — the Core Shift

Start async work with the static factories:

```java
// returns a value -> supplyAsync
CompletableFuture<Balance> cf = CompletableFuture.supplyAsync(() -> cbs.fetchBalance(acct));

// no return value -> runAsync
CompletableFuture<Void> logged = CompletableFuture.runAsync(() -> audit.write(txn));

// already have the value
CompletableFuture<String> done = CompletableFuture.completedFuture("RRN123");
```

Now attach a callback instead of blocking:

```java
CompletableFuture.supplyAsync(() -> cbs.fetchBalance(acct))
    .thenAccept(balance -> log.info("balance = {}", balance));   // runs WHEN ready
// the calling thread moves on immediately — nothing blocks
```

> [!info] `thenApply` vs `thenAccept` vs `thenRun`
> The naming is regular across the whole API:
> - **`thenApply(fn)`** — takes the result, **returns a new value** (transform). `Balance → BigDecimal`.
> - **`thenAccept(consumer)`** — takes the result, **returns nothing** (side effect, e.g. log it).
> - **`thenRun(runnable)`** — ignores the result, just runs after (e.g. "mark done").
>
> Same triple appears with `Async` suffixes (§7) and in the combine methods (§4).

### 3. Chaining Dependent Steps

When step B needs step A's result, and B is *itself* async, `thenApply` would give you a nested `CompletableFuture<CompletableFuture<T>>`. **`thenCompose` flattens it** — it's the `flatMap` of async.

```java
// A payment flow: validate -> fetch balance -> post debit. Each step is async & depends on the prior.
CompletableFuture<Receipt> flow =
    CompletableFuture.supplyAsync(() -> validate(txn))          // CF<ValidatedTxn>
        .thenCompose(v -> supplyAsync(() -> cbs.fetchBalance(v.acct())))  // CF<Balance>, flattened
        .thenApply(balance -> checkSufficient(balance, txn))    // sync transform -> CF<Debit>
        .thenCompose(debit -> supplyAsync(() -> ledger.post(debit)));     // CF<Receipt>
```

> [!warning] `thenApply` vs `thenCompose` — the classic mix-up
> - Use **`thenApply`** when your function returns a **plain value** (`T → U`).
> - Use **`thenCompose`** when your function returns **another `CompletableFuture`** (`T → CF<U>`).
>
> Get it wrong and you end up with `CompletableFuture<CompletableFuture<Receipt>>` and a compile-time headache — or worse, you block inside a `thenApply` to unwrap it, defeating the whole point. `thenApply` = `map`, `thenCompose` = `flatMap`.

### 4. Combining Independent Results

When two futures are **independent**, run them in parallel and merge:

```java
CompletableFuture<Balance>   bal  = supplyAsync(() -> cbs.fetchBalance(acct));
CompletableFuture<RiskScore> risk = supplyAsync(() -> riskEngine.score(txn));

// thenCombine: wait for BOTH, merge the two results
CompletableFuture<Decision> decision =
    bal.thenCombine(risk, (b, r) -> decide(b, r));   // runs when both are ready
```

- **`thenCombine(other, fn)`** — both results, produce a merged value.
- **`thenAcceptBoth`** — both results, side effect only.
- **`applyToEither(other, fn)`** — whichever finishes **first** wins (hedged requests, primary/replica).

> [!info] Why this beats sequential `get()`s
> Calling `bal.get()` then `risk.get()` runs them back-to-back — total latency = sum. `thenCombine` lets both run concurrently — total latency = max(the two). For a payment authorising against balance *and* risk in parallel, that's often halving the response time.

### 5. Fan-Out Over Many — `allOf` / `anyOf`

For a *collection* of futures:

```java
List<CompletableFuture<Balance>> futures = accounts.stream()
        .map(a -> supplyAsync(() -> cbs.fetchBalance(a)))
        .toList();

// wait for ALL, then collect results
CompletableFuture<List<Balance>> all =
    CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]))
        .thenApply(v -> futures.stream().map(CompletableFuture::join).toList());
```

> [!warning] `allOf` returns `CompletableFuture<Void>`
> It completes when everything's done but hands you **no results** — you re-collect them from the original futures with `.join()` (safe here because they're already complete). `join()` is like `get()` but throws an unchecked `CompletionException`, so it works cleanly inside lambdas. `anyOf` completes when the **first** of the batch finishes.

### 6. Exception Handling — the Part Everyone Skips

A blocking `try/catch` can't catch a failure that happens on another thread later. Async errors propagate *down the pipeline* and you handle them with dedicated stages:

```java
CompletableFuture<Receipt> flow =
    supplyAsync(() -> cbs.fetchBalance(acct))
        .thenApply(this::postDebit)
        .exceptionally(ex -> {                       // catch: supply a fallback value
            log.error("debit failed", ex);
            return Receipt.failed(txn);
        });
```

The three recovery operators:

| Operator | Sees | Can change result? | Use for |
|---|---|---|---|
| `exceptionally(fn)` | Exception only (on failure) | Yes — returns a fallback value | Simple fallback on error |
| `handle(fn)` | (result, exception) — **always runs** | Yes | Branch on success *or* failure in one place |
| `whenComplete(fn)` | (result, exception) — **always runs** | No — observe only, re-throws | Logging/cleanup without altering the outcome |

```java
// handle: one place, both paths
.handle((receipt, ex) -> ex == null ? receipt : Receipt.failed(txn));
```

> [!warning] An exception skips the "happy path" stages
> If a stage throws, every downstream `thenApply`/`thenCompose` is **skipped** until a handler stage — the exception short-circuits straight to the next `exceptionally`/`handle`. So place a handler at the end of the chain (or at each point you can meaningfully recover). And a `CompletableFuture` whose exception you never handle is a **silently swallowed failure** — same trap as an ungot `Future` in [[2. Java Thread Basics]] §2. Always terminate a chain with error handling.

> [!info] Timeouts (Java 9+)
> `orTimeout(500, MILLISECONDS)` fails the future with `TimeoutException` if it isn't done in time; `completeOnTimeout(fallback, ...)` completes it with a default instead. Essential for payments — you never wait unboundedly on a downstream. This is the `CompletableFuture` equivalent of `future.get(timeout, unit)`.

### 7. Which Thread Runs It — the `Async` Suffix

Every operator has two forms, and the difference is a real correctness issue:

- **`thenApply(fn)`** (no suffix) — may run on the thread that *completed the previous stage*, or even the calling thread. You don't control it.
- **`thenApplyAsync(fn)`** — runs on the **common `ForkJoinPool`**.
- **`thenApplyAsync(fn, myExecutor)`** — runs on **your** pool. Prefer this in servers.

> [!warning] Don't do blocking I/O on the default pool
> With no executor argument, async stages run on the shared common `ForkJoinPool` — the same one `parallelStream` uses ([[4. Executors and Thread Pools]] §7). Blocking it (a DB call, an HTTP call to NPCI/CBS) starves every other parallel task in the JVM. **Always pass your own bounded `ExecutorService`** for blocking work:
> ```java
> ExecutorService io = new ThreadPoolExecutor(...);   // bounded, named
> supplyAsync(() -> cbs.fetchBalance(acct), io)        // <-- your pool
>     .thenApplyAsync(this::postDebit, io);
> ```
> This ties the whole chapter together: `CompletableFuture` is *what* you compose, but the pool from note 4 is *where* it runs — and the where is where systems fall over.

> [!info] Boundary caveat — async leaves your transaction
> Work handed to `supplyAsync` runs on a **different thread**, so it's outside the caller's `@Transactional` scope (transactions are thread-bound — [[11. Transaction Boundaries]]). The async stage gets its own connection/transaction or none at all. Don't split a single atomic DB unit across `CompletableFuture` stages expecting one rollback to cover them.

### 8. Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| `Future` vs `CompletableFuture`? | `Future` you can only block on (`get()`); `CompletableFuture` lets you attach non-blocking callbacks, chain, and combine. |
| `thenApply` vs `thenCompose`? | `thenApply` = `map` (fn returns a value); `thenCompose` = `flatMap` (fn returns another future). |
| `thenApply` vs `thenAccept` vs `thenRun`? | Transform-and-return / consume-result / ignore-result-run-after. |
| Combine two independent futures? | `thenCombine` — both run in parallel, latency = max not sum. |
| `allOf` gotcha? | Returns `CompletableFuture<Void>`; re-collect results via `.join()` on the originals. |
| `exceptionally` vs `handle` vs `whenComplete`? | Fallback-on-error / always-runs-and-can-change-result / always-runs-observe-only. |
| What happens to downstream stages on an exception? | Skipped until a handler stage — the error short-circuits to the next `exceptionally`/`handle`. |
| `thenApply` vs `thenApplyAsync`? | Async form runs on a pool (common FJP or your executor); plain form may run on the completing/calling thread. |
| Why pass your own executor? | Default is the common `ForkJoinPool`; blocking I/O on it starves all parallel work in the JVM. |
| Does async code stay in the transaction? | No — different thread, so outside the `@Transactional` boundary. |
