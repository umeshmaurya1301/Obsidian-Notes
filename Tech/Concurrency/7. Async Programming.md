Covers Roadmap section 7. [[2. Java Thread Basics]] §2 left you with a `Future` you can only *block on*. [[4. Executors and Thread Pools]] gave you pools to run work on. This note is the composition layer: `CompletableFuture` lets you say "when this finishes, do that" without a thread ever sitting on `get()`. It's the most-used async API in Spring Boot services — REST aggregation, parallel downstream calls, dashboard endpoints.

> [!info] The through-line of this note
> One limitation drives the whole design:
>
> 1. A plain `Future` is a dead end — the only way to use its result is `get()`, which **blocks a thread** (§1). For a handler calling three downstreams sequentially, that's 2+3+2 = 7 seconds of mostly waiting.
> 2. `CompletableFuture` makes the result a **callback**: attach work that runs *when* the value arrives (§2). This is the pivot from **pull** to **push**, and everything else follows from it.
> 3. But async work runs on *some* pool, and **which pool** is a correctness decision (§3) — get this wrong and you starve the JVM.
> 4. `join()`/`get()` still exist (§4) — they're the boundary where you re-enter blocking code. *Where* you put them decides whether you got any benefit at all.
> 5. Then the three composition shapes: **chain** dependent steps (§5–§6), **combine** two independent ones (§7), **fan out** over many (§8).
> 6. Async code fails async, so **exception handling** needs its own operators (§9) — the most-skipped, most-asked part — plus **timeouts** (§10), which are non-negotiable in production.
>
> Anchor: **`Future` = a handle you block on; `CompletableFuture` = a pipeline you attach to.**

> [!tip] Interview weight: ⭐⭐⭐⭐⭐
> The recurring questions: *Future vs CompletableFuture · supplyAsync vs runAsync · join vs get · **thenApply vs thenCompose** · thenCompose vs thenCombine · what allOf returns · **exceptionally vs handle vs whenComplete** · which thread runs a stage.* The two bolded pairs come up most often.

### 1. Why `Future` Isn't Enough

> [!example] Ordering food
> **Synchronous:** place the order, then stand at the counter until it's ready. Your time is wasted waiting.
> **Asynchronous:** place the order, go shopping, collect it when notified. You do useful work while the kitchen works.
>
> `Future` gets you the order token. `CompletableFuture` gets you the notification.

`Future` (from [[2. Java Thread Basics]] §2) can *start* async work, but to *use* the result you're stuck:

```java
Future<Balance> f = pool.submit(() -> cbs.fetchBalance(acct));
Balance b = f.get();   // BLOCKS this thread until done — the only option
```

Worse when steps are sequential — a `get()` between every stage:

```java
User u    = userFuture.get();          // block 2s
Order o   = orderFuture.get();         // block 3s
Payment p = paymentFuture.get();       // block 2s     → total 7s
```

Four things `Future` can't do:

- **React without blocking** — there's no "run X when it completes"; a thread must wait.
- **Chain** — no way to feed the result into the next async step without blocking in between.
- **Combine** — no way to say "when *these two* finish, merge them."
- **Handle errors well** — exceptions surface only when you call `get()`, wrapped, at a place far from the failure.

**`CompletableFuture<T>`** (Java 8, `java.util.concurrent`) implements both `Future` **and `CompletionStage`**:

```text
CompletableFuture  =  Future  +  callbacks  +  pipelines  +  error handling
```

You describe a *graph of stages*; each runs when its input is ready, on a pool, with nobody blocking in between.

### 2. Creating a `CompletableFuture`

Two factories cover almost everything:

```java
// returns a value → supplyAsync (takes a Supplier<T>)
CompletableFuture<Balance> cf = CompletableFuture.supplyAsync(() -> cbs.fetchBalance(acct));

// no return value → runAsync (takes a Runnable)
CompletableFuture<Void> logged = CompletableFuture.runAsync(() -> audit.write(txn));

// already have the value — completes immediately
CompletableFuture<String> done = CompletableFuture.completedFuture("RRN123");

// manual control — you complete it yourself later (§9)
CompletableFuture<String> manual = new CompletableFuture<>();
```

| `supplyAsync()` | `runAsync()` |
|---|---|
| Takes a `Supplier<T>` | Takes a `Runnable` |
| **Returns a value** | No return value |
| → `CompletableFuture<T>` | → `CompletableFuture<Void>` |
| Fetch a balance, score a risk | Send an email, write an audit row |

**What actually happens on `supplyAsync`:**

```text
Main thread                          Worker thread (pool)
──────────────────────────           ────────────────────────────
creates the CompletableFuture
submits the task            ────────► runs the supplier
returns IMMEDIATELY                   stores the result in the CF
continues its own work                marks the CF COMPLETED
                                              │
                                      any attached stages now fire
```

The calling thread does **not** wait. That's the entire point — and it's why the print order in a toy example looks "wrong":

```java
CompletableFuture<String> f = CompletableFuture.supplyAsync(() -> {
    System.out.println("worker");
    return "done";
});
System.out.println("main");
System.out.println(f.join());
```

```text
main            ← main thread didn't wait for the task to even start
worker
done
```

### 3. Where It Runs — the Default Pool Is a Trap

Every async stage runs on *some* pool. If you don't say which, you get **`ForkJoinPool.commonPool()`**:

```java
CompletableFuture.supplyAsync(() -> fetch());              // → commonPool
CompletableFuture.supplyAsync(() -> fetch(), myExecutor);  // → your pool
```

> [!warning] Never do blocking I/O on the common pool
> The common `ForkJoinPool` is shared JVM-wide, sized `cores - 1`, and is the same pool `parallelStream()` and `Arrays.parallelSort` use ([[4. Executors and Thread Pools]] §11). Park its workers on a DB query or an HTTP call to CBS/NPCI and you starve **every** parallel task in the process — including code you didn't write. On an 8-core box that's 7 threads total; three slow downstream calls can wedge the whole application.
>
> **Always pass your own bounded, named executor for blocking work:**
> ```java
> private final ExecutorService io = new ThreadPoolExecutor(
>         16, 32, 60, TimeUnit.SECONDS,
>         new ArrayBlockingQueue<>(500),
>         new NamedThreadFactory("cbs-io"),
>         new ThreadPoolExecutor.CallerRunsPolicy());
>
> supplyAsync(() -> cbs.fetchBalance(acct), io)
>     .thenApplyAsync(this::postDebit, io);
> ```
> This is where the whole series ties together: `CompletableFuture` is *what* you compose; the pool from note 4 is *where* it runs — and the *where* is what falls over in production. Rule of thumb: **common pool for CPU work, your own pool for anything that blocks.**

**The `Async` suffix — every operator has three forms:**

| Form | Runs on |
|---|---|
| `thenApply(fn)` | The thread that **completed the previous stage** — or the **calling thread** if the stage is already complete. You don't control it. |
| `thenApplyAsync(fn)` | The **common `ForkJoinPool`** |
| `thenApplyAsync(fn, executor)` | **Your** executor ✅ |

So the non-`Async` form is *not* "synchronous" — it's "whichever thread happens to be available", which for a cheap transform (`User → String`) is exactly right and avoids a pool handoff. Use the plain form for trivial CPU-bound mapping; use `...Async(fn, myPool)` the moment the stage blocks or does real work.

### 4. Getting the Result — `get()` vs `join()`

Both **block** until the future completes. The difference is exception style:

| `get()` | `join()` |
|---|---|
| Blocks | Blocks |
| Throws **checked** `InterruptedException`, `ExecutionException` | Throws **unchecked** `CompletionException` |
| Forces a `try/catch` | No mandatory `try/catch` |
| Inherited from `Future` | Native to `CompletableFuture` |
| `get(timeout, unit)` available | No timed variant (use `orTimeout`, §10) |

Because `join()` is unchecked, it composes cleanly inside lambdas and streams — which is why it's the idiomatic choice in `CompletableFuture` code. Use `get(timeout, unit)` when you specifically want a bounded blocking wait.

**If the future is already complete, neither blocks** — the value is returned immediately.

> [!example] `join()` is a parcel pickup
> **Bad:** order the parcel, then sit outside your door until it arrives.
> **Good:** order the parcel, go to the gym, study, cook — then collect it.
>
> `join()` means *"I need it now: if it's here, hand it over; otherwise I'll wait."* The skill is **putting the `join()` as late as possible.**

**This is the part people get wrong.** `join()` immediately after creating the future gives you nothing:

```java
// ❌ Effectively synchronous — main thread creates the future and instantly waits
CompletableFuture<User> f = supplyAsync(this::fetchUser);
User user = f.join();
```

```java
// ✅ The overlap is the whole benefit
CompletableFuture<User> f = supplyAsync(this::fetchUser);   // starts in background
validateJwt();                                             // main thread does real work
readConfiguration();
prepareResponseHeaders();
User user = f.join();                                      // likely already done → no wait
```

> [!tip] "Does `join()` make async code synchronous?"
> A common trap question. The answer: *"`join()` blocks only at the point where the result is actually needed. Before that, the calling thread does other work while the task runs in parallel. If you call `join()` immediately after creating the future, you lose most of the benefit — the work still happens on another thread, but the caller just waits."*
>
> The better answer for real code: **don't `join()` at all** in the middle of a pipeline — chain (§5) so nothing blocks, and only block at the outermost boundary (or return the `CompletableFuture` to the framework and let Spring/servlet async handle it).

### 5. Chaining Dependent Steps — `thenApply` / `thenAccept` / `thenRun`

When each step needs the previous one's result, the manual version is a ladder of blocking calls:

```java
User user = userFuture.join();                     // ❌ blocks
Orders orders = fetchOrders(user);
Discount d = calculateDiscount(orders);
Invoice inv = createInvoice(d);
```

Chaining expresses the same workflow as a pipeline, with **no `join()` between steps**:

```java
future.thenApply(user -> process(user));   // "when this completes, run that"
```

**Three operators, answering three questions:**

| Method | Receives previous result? | Returns a value? | Use when |
|---|---|---|---|
| `thenApply(fn)` | ✅ | ✅ → `CF<R>` | Transform: `User → String` |
| `thenAccept(consumer)` | ✅ | ❌ → `CF<Void>` | Consume it: log, audit, publish |
| `thenRun(runnable)` | ❌ | ❌ → `CF<Void>` | Just run after: "mark done" |

```java
// thenApply — transform
supplyAsync(() -> 10).thenApply(x -> x * 2);                    // → 20

// chained transforms, each feeding the next
supplyAsync(() -> 5)
    .thenApply(x -> x + 5)      //  10
    .thenApply(x -> x * 10)     // 100
    .thenApply(x -> x - 20);    //  80

// thenAccept — consume, produce nothing
supplyAsync(this::fetchUser).thenAccept(user -> auditService.log(user));

// thenRun — ignores the result entirely
supplyAsync(this::savePayment).thenRun(() -> log.info("audit finished"));
```

> [!tip] It's the Streams API, one value at a time
> | Streams | `CompletableFuture` |
> |---|---|
> | `map()` | `thenApply()` |
> | `flatMap()` | `thenCompose()` (§6) |
> | `forEach()` | `thenAccept()` |
>
> If you know `map` vs `flatMap`, you already know `thenApply` vs `thenCompose`. That analogy answers the single most-asked question in this note.

### 6. `thenCompose` — `flatMap` for Futures ⭐

The problem: step B depends on A's result, **and B is itself async**. Using `thenApply` gives you a future inside a future:

```java
// ❌ nested — CompletableFuture<CompletableFuture<String>>
supplyAsync(() -> 10)
    .thenApply(id -> supplyAsync(() -> "User " + id));
```

Now you'd have to `join()` inside a stage to unwrap it — blocking a pool thread and defeating the whole design. **`thenCompose` flattens it:**

```java
// ✅ flat — CompletableFuture<String>
supplyAsync(() -> 10)
    .thenCompose(id -> supplyAsync(() -> "User " + id))
    .join();                                              // "User 10"
```

```text
thenApply:    Future A → (fn returns Future B) → Future<Future<T>>   ❌
thenCompose:  Future A → (fn returns Future B) → flatten → Future<T> ✅
```

> [!warning] The rule, and the tell
> - Your lambda returns a **plain value** (`T → U`) → **`thenApply`**
> - Your lambda returns **another `CompletableFuture`** (`T → CF<U>`) → **`thenCompose`**
>
> The tell that you picked wrong: your type is `CompletableFuture<CompletableFuture<X>>`, or you find yourself calling `.join()` inside a `thenApply` to unwrap. Both mean "should have been `thenCompose`."

A real dependent pipeline — each step async, each needing the last:

```java
CompletableFuture<Receipt> flow =
    supplyAsync(() -> validate(txn), io)                                   // CF<ValidatedTxn>
        .thenCompose(v -> supplyAsync(() -> cbs.fetchBalance(v.acct()), io))  // CF<Balance>
        .thenApply(bal -> checkSufficient(bal, txn))                        // sync transform
        .thenCompose(debit -> supplyAsync(() -> ledger.post(debit), io));    // CF<Receipt>
```

### 7. Combining Two Independent Futures

Chaining is for *dependent* steps. When two futures **don't depend on each other**, run them in parallel and merge:

```java
CompletableFuture<User>        userF  = fetchUser();
CompletableFuture<List<Order>> orderF = fetchOrders();

CompletableFuture<UserDashboard> dashboard =
    userF.thenCombine(orderF, (user, orders) -> new UserDashboard(user, orders));
```

Both start immediately; the merge function runs only once **both** have completed.

| Method | Uses both results? | Returns a value? |
|---|---|---|
| `thenCombine(other, fn)` | ✅ | ✅ |
| `thenAcceptBoth(other, consumer)` | ✅ | ❌ → `CF<Void>` |
| `runAfterBoth(other, runnable)` | ❌ | ❌ → `CF<Void>` |

And the "first one wins" family:

| Method | Behaviour |
|---|---|
| `applyToEither(other, fn)` | Whichever completes **first**, transform it |
| `acceptEither(other, consumer)` | First result, consume it |
| `runAfterEither(other, runnable)` | Run once either completes |

`applyToEither` is how you hedge a request across a primary and a replica — issue both, take whichever answers first.

> [!info] Latency becomes max, not sum
> Sequential `userF.join()` then `orderF.join()` runs them back to back — **total = sum**. `thenCombine` lets both run concurrently — **total = max**. For a 2 s balance lookup and a 3 s risk score, that's 5 s → 3 s.
>
> `thenCompose` vs `thenCombine` — the distinction interviewers probe:
> - **`thenCompose`** = *dependent*. B needs A's result, so B **cannot start** until A finishes. Sequential by necessity.
> - **`thenCombine`** = *independent*. Both already running in parallel; you're just merging the two results.

### 8. Fan-Out Over Many — `allOf` and `anyOf`

For a *collection* of futures — the dashboard-aggregation shape:

```java
CompletableFuture<Void> all = CompletableFuture.allOf(userF, orderF, walletF, couponF);
all.join();                       // returns when ALL four are done

User user = userF.join();         // already complete → returns instantly
Wallet w  = walletF.join();
```

```text
Future A ──────────┐
Future B ──────────┤──► allOf() ──► continue (total ≈ slowest, not sum)
Future C ──────────┘
```

> [!warning] `allOf` returns `CompletableFuture<Void>` — it does not collect results
> This surprises everyone. `allOf` only *signals* completion; you re-collect each value from its original future. The idiomatic pattern:
> ```java
> List<CompletableFuture<Balance>> futures = accounts.stream()
>         .map(a -> supplyAsync(() -> cbs.fetchBalance(a), io))
>         .toList();
>
> CompletableFuture<List<Balance>> all =
>     CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]))
>         .thenApply(v -> futures.stream().map(CompletableFuture::join).toList());
> ```
> The inner `join()` calls are safe and non-blocking **because `allOf` already guarantees every future is complete.** Note it must be `thenApply` on the `allOf` result — not a bare `join()` — to keep the whole thing non-blocking.

**`anyOf`** completes as soon as the **first** of the batch finishes — three cache replicas, take whoever answers:

```java
CompletableFuture<Object> fastest = CompletableFuture.anyOf(redis1, redis2, redis3);
System.out.println(fastest.join());
```

| `allOf()` | `anyOf()` |
|---|---|
| Waits for **all** | Waits for the **first** |
| Returns `CompletableFuture<Void>` | Returns `CompletableFuture<Object>` (untyped!) |
| Dashboard aggregation, batch fan-out | Fastest-response wins, hedged requests |

> [!warning] Three gotchas in this pair
> 1. **`anyOf` does not cancel the losers.** They keep running to completion, still consuming pool threads and still hitting downstreams. Cancel them yourself if that matters.
> 2. **`anyOf` returns `Object`**, since the inputs may have different types — you cast. If they're all the same type, `applyToEither` (§7) keeps type safety for two, and there's no typed n-ary equivalent in the JDK.
> 3. **`allOf` fails if *any* input fails.** `all.join()` then throws, and so does the `join()` inside your collect — you lose the results that *did* succeed. For partial-failure tolerance, attach a per-future fallback **before** `allOf`:
>    ```java
>    .map(a -> supplyAsync(() -> cbs.fetchBalance(a), io)
>                  .exceptionally(ex -> Balance.unavailable(a)))   // ← each one survives
>    ```
>    This is the single most useful production detail in this section.

### 9. Exception Handling — the Part Everyone Skips ⭐

A `try/catch` around the *submission* cannot catch a failure that happens on another thread later:

```java
try {
    CompletableFuture.supplyAsync(() -> riskyOperation());   // throws on a worker thread
} catch (Exception e) {
    // ❌ never reached — nothing has failed yet when this line runs
}
```

So the API brings its own operators. Start with a failing future:

```java
CompletableFuture<Integer> f = supplyAsync(() -> 10 / 0);   // ArithmeticException
f.join();
```

```text
CompletionException
  Caused by: java.lang.ArithmeticException: / by zero
```

**The original exception is wrapped** — `join()` throws `CompletionException`, `get()` throws `ExecutionException`. Both keep the real cause in `getCause()`. That "which exception does `join()` throw?" question is asked specifically to see whether you know it's `CompletionException`, not `ExecutionException`.

**The four operators:**

| Method | Runs on success | Runs on failure | Can change the result | Typical use |
|---|---|---|---|---|
| `exceptionally(fn)` | ❌ | ✅ | ✅ | Fallback value on error |
| `handle(fn)` | ✅ | ✅ | ✅ | Branch on both paths in one place |
| `whenComplete(fn)` | ✅ | ✅ | ❌ (observes, re-throws) | Logging, metrics, cleanup |
| `completeExceptionally(ex)` | — | forces failure | — | Manually fail a future you own |

**`exceptionally`** — the workhorse. On failure, supply a fallback and the pipeline continues as if it had succeeded:

```java
CompletableFuture<List<Product>> recs =
    fetchRecommendations()
        .exceptionally(ex -> {
            log.warn("recommendations unavailable", ex);
            return List.of();                       // degrade, don't fail the page
        });
```

**`handle`** — always runs, sees `(result, exception)`, returns a new value. One place for both paths:

```java
.handle((receipt, ex) -> ex == null ? receipt : Receipt.failed(txn));
```

**`whenComplete`** — the `finally` of the async world. Sees both, **cannot change either**; the exception still propagates downstream:

```java
.whenComplete((result, ex) -> {
    timer.stop();                                    // cleanup / metrics
    if (ex != null) log.error("txn failed", ex);      // observe only
});                                                  // ← exception continues down the chain
```

**`completeExceptionally`** — for a future you created manually (a callback bridge, say):

```java
CompletableFuture<String> f = new CompletableFuture<>();
// ... later, from a callback:
f.completeExceptionally(new PaymentDeclinedException("insufficient funds"));
```

> [!warning] An exception short-circuits every downstream happy-path stage
> If a stage fails, all following `thenApply`/`thenCompose`/`thenAccept` stages are **skipped** — the failure jumps straight to the next `exceptionally`/`handle`. After recovery, the pipeline resumes normally:
> ```java
> supplyAsync(() -> { throw new RuntimeException(); })
>     .exceptionally(ex -> "default value")     // recovers
>     .thenApply(String::toUpperCase)           // runs — on "default value"
>     .join();                                  // → "DEFAULT VALUE"
> ```
> Placement matters: a handler at the **end** catches everything; a handler **mid-chain** lets later stages proceed with a fallback. Choose deliberately.

> [!warning] An unhandled failure is a silently swallowed one
> A `CompletableFuture` that completes exceptionally and is never `join()`ed, never inspected, and has no `exceptionally`/`handle` **logs nothing and throws nowhere**. Exactly the same trap as an un-`get()` `Future` ([[4. Executors and Thread Pools]] §8) — fire-and-forget async work fails invisibly. **Always terminate a chain with error handling**, even if it's only `.whenComplete((r, ex) -> { if (ex != null) log.error(...); })`.

> [!tip] Which one do I pick?
> - Fallback only when something fails → **`exceptionally`**
> - Need to handle success *and* failure, possibly transforming → **`handle`**
> - Log / metrics / cleanup without altering the outcome → **`whenComplete`**
> - Manually mark a future you own as failed → **`completeExceptionally`**
>
> (Java 12+ adds `exceptionallyAsync` and `exceptionallyCompose` — the async and flat-mapping variants, for when your *recovery* is itself async.)

### 10. Timeouts

Nothing above bounds how long a stage may take. In a payments path that's unacceptable — a hung downstream must not hold a request thread forever.

```java
// Java 9+
cf.orTimeout(500, TimeUnit.MILLISECONDS);                  // fail with TimeoutException
cf.completeOnTimeout(Balance.unknown(), 500, MILLISECONDS); // complete with a default instead
```

```java
CompletableFuture<Balance> bal =
    supplyAsync(() -> cbs.fetchBalance(acct), io)
        .orTimeout(800, TimeUnit.MILLISECONDS)
        .exceptionally(ex -> Balance.unavailable(acct));     // covers timeout AND real errors
```

On Java 8 the equivalent is `get(timeout, unit)` at the blocking boundary, or `applyToEither` against a future you complete on a timer.

> [!warning] A timeout does not stop the work
> `orTimeout` completes the *future* exceptionally; the underlying task **keeps running** on its pool thread. Same for `cancel()`:
>
> **`CompletableFuture.cancel(mayInterruptIfRunning)` ignores its argument and does not interrupt anything.** It completes the future with `CancellationException` while the supplier runs to completion. This differs from `Future.cancel(true)` on an executor-submitted task, which *does* interrupt. So a `CompletableFuture` you time out or cancel still consumes a thread and still hits the downstream — bound the work itself with client-level read timeouts (HTTP, JDBC), not just the future.

### 11. Production Concerns

Beyond the API, four things that bite in real services:

**1. Async leaves your transaction behind.** A stage runs on a different thread, so it's outside the caller's `@Transactional` scope — transactions are thread-bound ([[11. Transaction Boundaries]]). The stage gets its own transaction or none. Never split one atomic DB unit across stages expecting a single rollback to cover it, and don't pass lazily-loaded entities into a stage — pass IDs and reload.

**2. `ThreadLocal` context doesn't follow.** MDC trace IDs, security context, tenant — all lost across the pool handoff ([[2. Java Thread Basics]] §6). Your async stages log without correlation IDs, exactly where you most need them. Capture the context before submitting and restore it inside the task (or use a context-propagating executor wrapper).

**3. Don't block inside a stage.** `join()` inside a `thenApply`, or a bare `Thread.sleep`, occupies a pool thread doing nothing. If a stage needs another async result, that's `thenCompose` (§6), not `join()`.

**4. Spring integration.** An `@Async` method can return `CompletableFuture<T>` and Spring will manage the pool — configure it explicitly ([[4. Executors and Thread Pools]] §15). A controller returning `CompletableFuture` lets the servlet container release the request thread while the work runs, which is the actual throughput win; returning `.join()` throws that away.

### 12. Cheat Sheet

| Need | Use |
|---|---|
| Start async work returning a value | `supplyAsync(supplier, executor)` |
| Start async work returning nothing | `runAsync(runnable, executor)` |
| Transform the result | `thenApply` |
| Consume the result | `thenAccept` |
| Run something after, ignoring the result | `thenRun` |
| Next step is **async and dependent** | `thenCompose` ← *flatMap* |
| Two **independent** futures, merge results | `thenCombine` |
| Whichever of two finishes first | `applyToEither` |
| Wait for **all** of many | `allOf` (+ collect via `join`) |
| Take the **first** of many | `anyOf` |
| Fallback on failure | `exceptionally` |
| Handle success and failure together | `handle` |
| Log/cleanup either way | `whenComplete` |
| Bound the wait | `orTimeout` / `completeOnTimeout` |
| Get the value (blocking boundary only) | `join()` |

```text
                       supplyAsync / runAsync
                                 │
              ┌──────────────────┼──────────────────┐
              ▼                  ▼                  ▼
      thenApply / Accept    thenCompose        thenCombine
      transform / consume   dependent async    independent, merge
              │                  │                  │
              └──────────────────┼──────────────────┘
                                 ▼
                        allOf / anyOf
                        fan-in / first-wins
                                 │
                                 ▼
                 exceptionally / handle / whenComplete
                                 │
                                 ▼
                        orTimeout → join()
```

### 13. Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| `Future` vs `CompletableFuture`? | `Future` can only be blocked on with `get()`. `CompletableFuture` adds non-blocking callbacks, chaining, combining, and real exception handling — it implements `Future` **and** `CompletionStage`. |
| Why was `CompletableFuture` introduced? | `Future` can't react without blocking, can't chain, can't combine, and has poor error handling. |
| `supplyAsync` vs `runAsync`? | `supplyAsync` takes a `Supplier` and returns `CF<T>`; `runAsync` takes a `Runnable` and returns `CF<Void>`. |
| Which pool runs an async stage by default? | `ForkJoinPool.commonPool()`. Pass your own executor for anything that blocks. |
| Why is the common pool dangerous? | It's shared JVM-wide and sized `cores - 1`; blocking it starves every `parallelStream` and async stage in the process. |
| `thenApply` vs `thenApplyAsync`? | Plain form runs on the thread that completed the previous stage (or the caller if already complete); `Async` runs on the common pool, or on your executor if you pass one. |
| `get()` vs `join()`? | Both block. `get()` throws checked `InterruptedException`/`ExecutionException`; `join()` throws unchecked `CompletionException` — so it composes in lambdas. |
| Which exception does `join()` throw? | **`CompletionException`** (not `ExecutionException`), wrapping the original cause. |
| Does `join()` make async code synchronous? | Only from the point you call it. Called immediately after creating the future, you gain nothing — the benefit comes from doing other work first, or from not blocking at all. |
| Does `join()` block if the future is already complete? | No — it returns immediately. |
| `thenApply` vs `thenAccept` vs `thenRun`? | Transform-and-return / consume-the-result / ignore-the-result-and-run. |
| `thenApply` vs `thenCompose`? | `thenApply` = `map` (fn returns a value); `thenCompose` = `flatMap` (fn returns another future). Using `thenApply` for an async fn gives `CF<CF<T>>`. |
| `thenCompose` vs `thenCombine`? | `thenCompose` = **dependent** (B needs A's result, so B starts after A). `thenCombine` = **independent** (both already running in parallel; merge the two results). |
| How do you run three independent calls in parallel? | Start all three futures, then `thenCombine`/`allOf`. Latency = the slowest, not the sum. |
| What does `allOf` return? | `CompletableFuture<Void>` — it signals completion but **collects nothing**. Re-collect with `.join()` on the originals inside a `thenApply`. |
| What happens if one future in `allOf` fails? | The `allOf` completes exceptionally and you lose the successful results too. Attach a per-future `exceptionally` **before** `allOf` for partial-failure tolerance. |
| Does `anyOf` cancel the losers? | No — they run to completion unless you cancel them explicitly. |
| Why does `anyOf` return `CompletableFuture<Object>`? | Its inputs may have different types, so it can't be typed. Use `applyToEither` for two same-typed futures. |
| `exceptionally` vs `handle` vs `whenComplete`? | `exceptionally`: failure only, can supply a fallback. `handle`: always runs, sees both, can change the result. `whenComplete`: always runs, sees both, **cannot** change the result — logging/cleanup. |
| What happens to downstream stages when a stage throws? | They're **skipped** until an `exceptionally`/`handle`; after recovery the chain resumes normally. |
| What if you never handle an async exception? | It's silently swallowed — no log, no throw. Always terminate a chain with error handling. |
| What is `completeExceptionally` for? | Manually failing a `CompletableFuture` you created yourself — typically when bridging a callback API. |
| How do you bound an async call? | `orTimeout(t, unit)` (fail) or `completeOnTimeout(default, t, unit)` (fall back). Java 9+. |
| Does `cancel()` stop the running task? | **No** — `CompletableFuture.cancel` ignores `mayInterruptIfRunning`, completes the future with `CancellationException`, and lets the task run on. Bound the work with client-level timeouts. |
| Is async work inside the caller's transaction? | No — different thread, so outside the `@Transactional` boundary, and `ThreadLocal` context (MDC, security) doesn't propagate. |
