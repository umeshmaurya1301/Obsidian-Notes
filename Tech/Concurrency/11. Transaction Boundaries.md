Covers Roadmap section 11. [[9. Database Concurrency]] was about *contention* — two writers on one row. [[10. Distributed Concurrency]] was about *coordination* — locking something outside the DB. This note is about **boundaries**: what a rollback can and cannot undo, and what to do about everything it can't.

> [!info] The through-line of this note
> One question governs every design decision here:
>
> > **Is this operation inside my database transaction, or outside it?**
>
> 1. Inside the transaction, failure is *free* — the engine erases every table you touched, in any order, and a retry starts clean (§1–§3).
> 2. The moment you cross the boundary — an HTTP call, a Kafka publish, another thread — **rollback loses its power** (§4–§5). Those effects have already happened and no `ROLLBACK` can reach them.
> 3. So you never try to roll back across the boundary. You restructure so the boundary is only crossed **after commit** (§6–§7), and make the far side safe to repeat (§9).
> 4. Where no shared transaction exists at all, you stop undoing and start **compensating** (§8) — and you don't reach for 2PC, for reasons worth being able to list (§10).
>
> Once this distinction is internalised, Outbox and Saga stop being patterns to memorise and become the obvious consequences.

## Short Notes

---

### 1. The Scenario: Three Tables, One Exception

- Three saves in one `@Transactional` method; the third throws. **Do you undo the first two?** → **No, and there is nothing to undo**
- Executing SQL ≠ committing it — until `COMMIT` the rows live in the **undo log**, visible to nobody else
- Spring marks the transaction **rollback-only**; the retry is a **brand-new transaction** that re-runs all three
- ⚠️ **Optimistic locking never fires on a fresh `INSERT`** — only on `UPDATE`/`DELETE` of an existing versioned row. The insert-time analogue is a unique-constraint violation
- ⚠️ **The exception rarely fires on the line you think** — Hibernate batches and **reorders** DML, and flushes at **commit**, so `save()` returning means almost nothing

> A transaction marked rollback-only is dead — you cannot "continue" it. The retry must live **outside** the transaction.

---

### 2. Rollback Rules — What Actually Triggers It

| Situation | Rolls back? |
|---|---|
| `RuntimeException` / `Error` escapes | ✅ Yes — the default rule |
| **Checked** exception escapes | ❌ **No — it commits.** Need `rollbackFor = Exception.class` |
| You caught it and returned normally | ❌ No — Spring sees success and commits partial work |
| Inner `REQUIRED` threw, outer caught and continued | ⚠️ Already rollback-only → outer commit throws `UnexpectedRollbackException` |
| Inner `REQUIRES_NEW` threw, outer caught | ✅ Only the inner one rolled back — separate transaction |

- **`REQUIRES_NEW`** = a genuinely separate transaction on a **second connection** — use it when an audit row must survive the failure
- ⚠️ It holds a second pool connection while the outer is suspended, and **can deadlock against your own outer transaction** if it needs a row that one locked
- **`NESTED`** = a **savepoint**, not a new transaction — undo one step, keep the rest. Needs JDBC savepoints; doesn't work over JTA

---

### 3. Making the Retry Itself Safe

- ⚠️ **Never reuse an entity object across attempts.** After rollback it's **detached and poisoned** — the `@Id` was assigned but no row exists, so Hibernate issues `UPDATE`, hits 0 rows, and the retry loop can *never* succeed
- **Rule**: pass immutable request/DTO data in, construct entities **inside** the retried method
- **Bound the retry** (`maxAttempts`) and **add jitter** (`@Backoff(random = true)`) — without jitter, contending threads retry in lockstep and collide again
- Always define a `@Recover` so exhaustion becomes a clean `409`, not a stack trace
- `@Retryable` must wrap `@Transactional`, on **different beans**, so each attempt gets a fresh transaction

---

### 4. The Two Worlds ⭐

| | **World 1 — inside the transaction** | **World 2 — outside it** |
|---|---|---|
| **Examples** | Inserts/updates across any number of tables in the same DB | HTTP/PSP calls, Kafka publishes, emails, SMS, cache writes, another thread, another service, another database |
| **On failure** | `ROLLBACK` — silently and completely undone | **Already happened. Permanently.** |
| **Consistency** | Free, guaranteed by the engine | Your problem, by design |
| **Tool** | `@Transactional` | Outbox, Saga, idempotency, compensation |

- ⭐ **The one-line rule**: a database rollback can only undo **database writes, in that database, in that transaction**
- The *number of tables is irrelevant* — three or thirty, one transaction rolls them all back
- **Crossing into World 2 even once** is what changes the problem

---

### 5. What Breaks When You Cross the Boundary

- **External API call** — the card is charged and your DB says the payment never existed. If `@Retryable` wraps it, attempt 2 charges again
- **Kafka publish** — Kafka cannot un-send; a consumer may already have acted on an event for a payment that doesn't exist

```text
Publish inside the txn  → event published, DB rolled back  → phantom event
Publish after the txn   → DB committed, crash before publish → lost event
```

- ⭐ That's the **dual-write problem**: two systems, no shared transaction, and **neither ordering is safe**
- **Another thread** — Spring binds the transaction and its connection to the thread via `ThreadLocal`, so rollback can't reach it, *and* it can't see your uncommitted rows (`EntityNotFoundException` for a row you "just saved")
- Applies equally to `@Async`, `CompletableFuture`, parallel streams, `@Scheduled`. **A transaction never propagates across a thread boundary**
- Kafka's transactional producer gives exactly-once for **Kafka→Kafka** only — it cannot make a Kafka write atomic with a Postgres write

---

### 6. Transactional Outbox ⭐ — the Industry Standard

- Stop writing to two systems. Write **both** to the one system that has transactions — your DB — and publish separately

```java
@Transactional
void processPayment(req) {
    paymentRepo.save(...);
    outboxRepo.save(OutboxEvent.of("PaymentCreated", ...));  // just another row
}   // COMMIT — data and intent-to-publish commit together, or neither does
```

```text
Transaction fails   → payment ❌ AND outbox row ❌ → nothing is ever published
Transaction commits → payment ✅ AND outbox row ✅ → relay publishes, retrying until it succeeds
```

- **The dual write is gone because there is no longer a dual write**
- Relay options: **polling** (simple, no new infra, adds poll-interval latency) vs **CDC/Debezium** (low latency, another moving piece)
- ⚠️ **Outbox is at-least-once, never exactly-once** — the relay can publish then crash before marking `published_at`. Consumers **must** be idempotent (§9)

---

### 7. `@TransactionalEventListener` — the Lightweight Middle Ground

- `AFTER_COMMIT` phase — the handler runs **only if the transaction committed**
- Solves the **ordering** problem (never fires on rollback) but **not the durability** problem
- ⚠️ Process dies between commit and listener → **event lost forever**
- ✅ Right for: cache invalidation, nice-to-have notifications
- ❌ **Not for money.** Use the outbox when losing the event is unacceptable

---

### 8. Saga & Compensating Transactions

- Across services with separate databases, **no transaction spans the flow**
- A saga is a sequence of **local** transactions; on failure you **don't roll back, you compensate**

```text
Forward:   Create Payment → Reserve Inventory → Debit Wallet → Notify User
                                                     ✗ fails
Compensate:            ← Release Inventory ← Cancel Payment
```

| Style | How | Trade-off |
|---|---|---|
| **Choreography** | Each service listens and reacts | No central component; flow is implicit, hard to trace |
| **Orchestration** | A coordinator drives each step | Explicit and debuggable; one more component to own |

- ⭐ **In payments, compensation is a reversal entry, never a delete** — ledgers are append-only and auditable
- ⚠️ **Sagas are not atomic** — there's a real window where inventory is reserved but the wallet isn't debited. You get *eventual* consistency, and the business must accept that window

---

### 9. Idempotent Consumers — the Non-Negotiable Backstop

- Everything above delivers **at-least-once**, so every consumer must tolerate duplicates
- Mechanism: a **`UNIQUE` constraint**, checked by **inserting first** ([[10. Distributed Concurrency]] §7)
- ⭐ Mark-as-processed and the work itself must be in **one transaction** — otherwise you can mark it done and then fail
- Protects against Kafka **consumer-group rebalances** replaying uncommitted offsets, which happen routinely — not just on failure

---

### 10. Why Not 2PC / XA?

| Problem | Why it's disqualifying |
|---|---|
| **Blocking** | Coordinator dies after "prepare" → participants sit **in doubt**, holding locks, until it recovers |
| **Availability** | Every participant must be up; availability multiplies *down*: 3 × 99.9% ≈ 99.7% |
| **Latency** | Two round trips plus forced log flushes, per participant, per transaction |
| **Support** | **Kafka doesn't support XA at all** — nor do most modern datastores or any HTTP API |
| **Operations** | Recovering in-doubt transactions is manual, rare, and always at 3 a.m. |

- It also buys less than it looks: 2PC gives atomicity, but a **payment gateway call still isn't transactional**
- The industry trades *atomicity* for **eventual consistency + retries** — outbox + saga + idempotency

---

### 11. Putting It Together — a Payment Flow

```text
1.  Idempotency check on RRN / UTR         ← dedupe retries before any work
        ↓
2.  BEGIN
      INSERT txn            (state = PENDING)
      INSERT outbox_event   (TxnCreated)
    COMMIT                                  ← one atomic unit, all in World 1
        ↓
3.  Outbox relay → Kafka                    ← World 2, only after commit
        ↓
4.  Consumers (idempotent) → ledger, notifications, reconciliation
        ↓
5.  External call (bank/PSP) outside any transaction, with its own idempotency key
        ↓
6.  BEGIN  UPDATE txn SET state='SUCCESS' WHERE id=? AND state='PENDING'  COMMIT
                                            ← conditional update: safe to repeat
```

- **Every boundary crossing happens after a commit**, and every step past it is safe to repeat
- Step 6's conditional update means a duplicate callback updates **0 rows** instead of double-applying

> **Three rules**: never call out or publish inside a transaction · assume at-least-once everywhere · know which side of the boundary each operation is on.

# Detailed Explanation

---

## The Scenario: Three Tables, One Exception

The question that makes all of this concrete.

```java
@Transactional
public void processPayment(PaymentRequest req) {
    paymentRepo.save(payment);          // Table 1  ✅ looks fine
    ledgerRepo.save(ledger);            // Table 2  ✅ looks fine
    txnLogRepo.save(log);               // Table 3  💥 ObjectOptimisticLockingFailureException
}
```

**The question:** rows went into the first two tables. The third failed. On retry, do I have to undo the first two myself?

**The answer: no — and there is nothing to undo.** All three are in one transaction, so the failure rolls back *everything*, and the retry re-executes all three from scratch.

### What actually happens

```text
BEGIN
  INSERT INTO payment ...          -- written, but only visible to THIS transaction
  INSERT INTO ledger  ...          -- same
  UPDATE txn_log SET version=8 WHERE id=10 AND version=7
                                   -- 0 rows → Hibernate throws
  ↓
  Spring marks the transaction ROLLBACK-ONLY
  ↓
ROLLBACK

Final state:  payment      → gone
              ledger       → gone
              txn_log      → unchanged
```

It is as if the method was never called. **That's Atomicity — the A in ACID** ([[9. Database Concurrency]] §1) doing exactly its job.

### Why the first two inserts don't survive

This trips people up: *"but the insert already executed — I saw the SQL in the logs."*

Executing SQL is not the same as committing it. Until `COMMIT`:

- The rows exist only in your transaction's view, backed by the **undo log**.
- **No other transaction can see them** at any sane isolation level — that's precisely the dirty-read guarantee from [[9. Database Concurrency]] §3.
- `ROLLBACK` replays the undo log and they're gone, with no trace beyond some WAL churn.

So there is no "partial state" to clean up. The database never let anyone observe one.

### The retry is a brand-new transaction

```text
Attempt 1                      Attempt 2
─────────                      ─────────
BEGIN                          BEGIN
INSERT payment                 INSERT payment
INSERT ledger                  INSERT ledger
✗ OptimisticLockException      INSERT txn_log
ROLLBACK                       COMMIT ✅
(nothing survives)
```

The retry re-reads the now-current version, recomputes, and writes all three again. Nothing from attempt 1 is reused or left behind.

> [!warning] The retry must live *outside* the transaction
> A transaction marked rollback-only is dead — you cannot "continue" it. `@Retryable` has to wrap `@Transactional` so each attempt gets a **fresh** transaction, and the two must be on different beans or the proxy ordering bites you — the same proxy mechanics as [[10. Distributed Concurrency]] §9.

### The scoping question: is `txn_log` inserted or updated?

Worth being precise, because it changes the diagnosis:

**Optimistic locking is checked on `UPDATE` and `DELETE` of an existing versioned row — never on a fresh `INSERT`.** A brand-new row has no prior version to compare against; Hibernate just writes `version = 0`.

So if you're genuinely seeing `ObjectOptimisticLockingFailureException` on what you believe is an insert, it's one of:

| Actual cause | How to tell |
|---|---|
| It's really a **merge/update** — the entity was detached with an ID set, so Hibernate issues `UPDATE`, not `INSERT` | Check for a non-null `@Id` on the entity you passed to `save()` |
| A **different** versioned entity in the same persistence context failed at flush | Read the exception's entity name — it may not be `TxnLog` at all |
| A `@Version` bump on a **parent** (`OPTIMISTIC_FORCE_INCREMENT`) triggered by editing a child | Look for cascade/lock-mode config on the parent |
| It's actually a **unique constraint violation**, which is the insert-time analogue | That surfaces as `DataIntegrityViolationException` instead |

> [!warning] The exception rarely fires on the line you think
> Hibernate batches and **reorders** DML at flush time — inserts, then updates, then deletes — and flush usually happens at **commit**, not at your `save()` call. So `save()` returning normally means almost nothing. Blaming "the third save" is usually wrong; the failure surfaced when the whole unit of work was flushed.

## Rollback Rules — What Actually Triggers It

Since the whole model rests on rollback working, know exactly when it does.

| Situation | Rolls back? |
|---|---|
| `RuntimeException` / `Error` escapes | ✅ Yes — the default rule |
| **Checked** exception escapes | ❌ **No — it commits.** Need `rollbackFor = Exception.class` |
| You caught the exception and returned normally | ❌ No — Spring sees success and commits partial work |
| Inner `REQUIRED` method threw, outer caught it and continued | ⚠️ Transaction is already **rollback-only** → outer commit throws `UnexpectedRollbackException` |
| Inner `REQUIRES_NEW` method threw, outer caught it | ✅ Only the inner one rolled back — it was a separate transaction |

The second and third rows are where real bugs live. A checked exception that escapes a `@Transactional` method **commits the partial work** — which is almost never what the author intended, and produces exactly the "half-written state" that this whole note claims is impossible.

### When you *want* something to survive the rollback

Occasionally a row must persist even though the business transaction failed — a failed-attempt audit record, a fraud signal:

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void recordAttempt(AuditEntry e) { auditRepo.save(e); }
```

This runs in a genuinely separate transaction on a **second connection**, so it commits independently. Two cautions: it holds a second pool connection while the outer transaction is suspended, and if it needs a row the outer transaction locked, **you deadlock against yourself** — a real cycle, which the database will resolve by killing one of your own transactions ([[9. Database Concurrency]] §7).

### Partial rollback with savepoints

`Propagation.NESTED` creates a **savepoint** rather than a new transaction, letting you undo one step while keeping the rest:

```java
@Transactional(propagation = Propagation.NESTED)
public void applyOptionalDiscount(...) { ... }   // failure rolls back to the savepoint only
```

Useful for batch processing where one bad item shouldn't kill the batch. Note it needs JDBC savepoint support and doesn't work over JTA.

## Making the Retry Itself Safe

The retry re-executes your method body. That's fine for pure DB work — but two things bite.

### Don't reuse entity objects across attempts

After a rollback the persistence context is discarded, and your entity objects are left **detached and poisoned**:

- A sequence-generated `@Id` was already assigned, but the row no longer exists.
- The `@Version` field holds a value that was never committed.

Re-saving that same instance on attempt 2 makes Hibernate see a non-null ID and issue an `UPDATE` against a row that isn't there — 0 rows, another optimistic failure, and a retry loop that **can never succeed**. This is a genuinely nasty bug because it looks like contention (repeated optimistic failures) when it's actually a self-inflicted permanent failure.

```java
@Retryable(retryFor = ObjectOptimisticLockingFailureException.class, maxAttempts = 3)
@Transactional
public void processPayment(PaymentRequest req) {
    // ✅ Build entities from the request INSIDE the method, fresh every attempt
    Payment payment = Payment.from(req);
    Ledger  ledger  = Ledger.from(req);
    ...
}
```

**Rule: pass immutable request/DTO data into the retried method, and construct entities inside it.** Never hand it a pre-built entity from the caller.

### Bound the retry, and add jitter

```java
@Retryable(
    retryFor = ObjectOptimisticLockingFailureException.class,
    maxAttempts = 3,
    backoff = @Backoff(delay = 50, multiplier = 2, random = true)   // jitter is not optional
)
```

Without jitter, contending threads retry in lockstep and collide again — the **retry storm** that makes optimistic locking degrade badly under real contention ([[9. Database Concurrency]] §10). Without `maxAttempts`, a hot row turns retries into a self-sustaining outage. And always define a `@Recover` so exhaustion becomes a clean `409`, not a stack trace.

## The Two Worlds

Here is the whole mental model:

| | **World 1 — inside the transaction** | **World 2 — outside it** |
|---|---|---|
| **Examples** | Inserts/updates across any number of tables in the same DB | HTTP/PSP calls, Kafka publishes, emails, SMS, cache writes, another thread, another service, another database |
| **On failure** | `ROLLBACK` — silently and completely undone | **Already happened. Permanently.** |
| **Consistency** | Free, guaranteed by the engine | Your problem, by design |
| **Tool** | `@Transactional` | Outbox, Saga, idempotency, compensation |

> [!warning] The one-line rule
> **A database rollback can only undo database writes, in that database, in that transaction.** Everything else you did has already escaped.

The number of tables is irrelevant — three tables or thirty, one transaction rolls them all back. **Crossing into World 2 even once is what changes the problem.**

## What Breaks When You Cross the Boundary

### An external API call

```java
@Transactional
public void processPayment(...) {
    paymentRepo.save(payment);
    stripeClient.charge(req);        // 💥 the customer's card is now charged
    ledgerRepo.save(ledger);         // optimistic lock failure here
}                                    // ROLLBACK
```

Result: **the customer was charged and your database says the payment never existed.** Stripe has no idea your transaction rolled back, and no rollback can reach it.

Worse, if `@Retryable` wraps this, attempt 2 charges them *again*.

> [!warning] Never call an external service inside a database transaction
> Two independent reasons, both sufficient:
> 1. **Correctness** — the call can't be rolled back (this section).
> 2. **Availability** — you're holding DB locks and a pooled connection for the duration of someone else's p99 latency ([[9. Database Concurrency]] §7).

### Publishing to Kafka

```java
@Transactional
public void processPayment(...) {
    paymentRepo.save(payment);
    kafkaTemplate.send("ledger-topic", event);   // gone the instant it's sent
    txnLogRepo.save(log);                        // 💥
}                                                // ROLLBACK
```

Kafka cannot un-send. A consumer may **already have processed the event** and created a downstream ledger entry — for a payment that, in the source of truth, does not exist.

This is the **dual-write problem**: two systems, no shared transaction. It fails in both directions:

```text
Publish inside the txn  → event published, DB rolled back  → phantom event, downstream invents data
Publish after the txn   → DB committed, app crashes before publish → lost event, downstream never learns
```

Neither ordering is safe on its own. That's what the outbox solves.

> [!info] "Can't I just use Kafka transactions?"
> Kafka's transactional producer gives exactly-once semantics for **Kafka→Kafka** flows (consume, process, produce, commit offsets atomically) — see [[8. Transactions (EOS)]]. It does **not** make a Kafka write atomic with a Postgres write — they're separate systems with separate commit protocols. Spring's old `ChainedKafkaTransactionManager` synchronised the two commits but was explicitly best-effort (a crash between them still breaks you), and it's been removed in Spring Kafka 3.x. **Use the outbox.**

### Another thread

```java
@Transactional
public void processPayment(...) {
    paymentRepo.save(payment);
    executor.submit(() -> ledgerRepo.save(ledger));   // different thread
    txnLogRepo.save(log);                             // 💥
}                                                     // ROLLBACK
```

The main transaction rolls back. The executor thread **had no transaction at all** (or its own, already committed). The ledger row survives; the payment doesn't.

**Why:** Spring binds the transaction — and its JDBC connection — to the current thread via `TransactionSynchronizationManager`, which is a `ThreadLocal`. That's the same mechanism that lets a repository three layers down silently join your transaction, and the same `ThreadLocal`-doesn't-follow-the-thread problem as `@Async` ([[4. Executors and Thread Pools]] §15).

```text
Thread A  →  ThreadLocal  →  Transaction A, Connection 1
Thread B  →  ThreadLocal  →  (empty) — no transaction

Rollback on Thread A cannot reach Thread B. Different connection, different transaction.
```

The same applies to `@Async` methods, `CompletableFuture.supplyAsync(...)`, parallel streams, and `@Scheduled` tasks. **A transaction never propagates across a thread boundary.**

> [!warning] The read-your-own-writes trap
> Even without failure, spawning a thread mid-transaction is broken: the new thread uses a *different connection*, so it **cannot see your uncommitted rows**. It'll get `EntityNotFoundException` for a row you "just saved." If you must fan out, do it **after** commit — that's what `@TransactionalEventListener` is for.

## Transactional Outbox ⭐ the industry standard

Stop trying to write to two systems atomically. Instead, write **both** to the one system that has transactions — your database — and let a separate process do the publishing.

```java
@Transactional
public void processPayment(PaymentRequest req) {
    paymentRepo.save(Payment.from(req));
    txnLogRepo.save(TxnLog.from(req));
    outboxRepo.save(OutboxEvent.of("PaymentCreated", req.id(), payload));  // just another row
}   // COMMIT — the payment and its intent-to-publish commit together, or neither does
```

```sql
CREATE TABLE outbox_event (
    id             BIGSERIAL PRIMARY KEY,
    aggregate_id   VARCHAR(64)  NOT NULL,
    event_type     VARCHAR(64)  NOT NULL,
    payload        JSONB        NOT NULL,
    created_at     TIMESTAMPTZ  NOT NULL DEFAULT now(),
    published_at   TIMESTAMPTZ                            -- NULL = not yet published
);
CREATE INDEX ix_outbox_unpublished ON outbox_event (id) WHERE published_at IS NULL;
```

A relay then publishes committed events:

```java
@Scheduled(fixedDelay = 500)
public void publishOutbox() {
    // SKIP LOCKED so multiple pods can relay in parallel
    // — see [[10. Distributed Concurrency]] §8, "design the lock away"
    for (OutboxEvent e : outboxRepo.claimUnpublished(100)) {
        kafkaTemplate.send(topicFor(e), e.getAggregateId(), e.getPayload());
        e.setPublishedAt(Instant.now());
    }
}
```

Why it works:

```text
Transaction fails  → payment ❌ AND outbox row ❌  → nothing is ever published
Transaction commits → payment ✅ AND outbox row ✅  → relay publishes, retrying until it succeeds
```

The dual-write problem is gone because **there is no longer a dual write.**

| Relay approach | Trade-off |
|---|---|
| **Polling** (above) | Simple, no extra infra; adds up to one poll-interval of latency and constant DB queries |
| **CDC** (Debezium tailing the WAL) | No polling, very low latency, scales well; another moving piece to operate |

> [!warning] Outbox gives *at-least-once*, never exactly-once
> The relay can publish and then crash before marking `published_at`, so the event goes out twice. That is unavoidable and fine — **consumers must be idempotent**. Anyone claiming exactly-once delivery across systems is describing at-least-once plus deduplication.

---

## `@TransactionalEventListener` — the Lightweight Middle Ground

When you just need "do X after this commits" and durability isn't critical:

```java
// inside the transaction
publisher.publishEvent(new PaymentCreated(payment.getId()));

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onPaymentCreated(PaymentCreated e) {
    kafkaTemplate.send("payments", e);      // runs only if the transaction committed
}
```

This solves the *ordering* problem (never fires on rollback) but **not the durability problem** — if the process dies between commit and the listener running, the event is lost forever.

The distinction is worth stating precisely, because the two look interchangeable in a code review: the outbox makes the *intent to publish* durable by committing it with the data; the listener only makes the *timing* correct. It's the right tool for cache invalidation or a nice-to-have notification; **it is not the right tool for money.**

## Saga & Compensating Transactions

Across services with separate databases, no transaction spans the flow. A saga is a sequence of local transactions, each publishing an event that triggers the next — and if a step fails, you **don't roll back, you compensate**:

```text
Forward:   Create Payment → Reserve Inventory → Debit Wallet → Notify User
                                                     ✗ fails
Compensate:            ← Release Inventory ← Cancel Payment
```

| Style | How it works | Trade-off |
|---|---|---|
| **Choreography** | Each service listens for events and reacts | No central component; flow is implicit and hard to trace |
| **Orchestration** | A coordinator explicitly drives each step | Flow is explicit and debuggable; the orchestrator is a component to own |

> [!example] Compensation in payments is a *new entry*, never a delete
> A saga's compensating action for a debit is **not** `DELETE FROM ledger`. Financial records are append-only and auditable — you post a **reversal entry**:
> ```text
> ledger:  txn_123  DEBIT   ₹500   (original)
>          txn_123  CREDIT  ₹500   (reversal, references the original)
> ```
> The balance nets to zero, and the audit trail shows what happened *and* that it was reversed. An append-only ledger composes far better with sagas than a mutable balance column, because compensation becomes an ordinary write rather than a destructive one.

Also note: sagas are **not atomic**. There's a real window where inventory is reserved but the wallet isn't debited. You get *eventual* consistency, and the business has to accept that window.

## Idempotent Consumers — the Non-Negotiable Backstop

Everything above delivers at-least-once, so **every consumer must tolerate duplicates**. Same mechanism as the idempotency key in [[10. Distributed Concurrency]] §7: a unique constraint, checked by inserting first.

```java
@KafkaListener(topics = "payments")
@Transactional
public void onPayment(PaymentEvent e) {
    try {
        processedRepo.saveAndFlush(new Processed(e.eventId()));   // UNIQUE(event_id)
    } catch (DataIntegrityViolationException dup) {
        return;                                                    // already handled — ack and move on
    }
    ledgerService.apply(e);
}
```

Marking-processed and doing the work are in **one transaction**, so you can't mark it done and then fail. Note this also protects against Kafka consumer-group rebalances replaying uncommitted offsets — which happen routinely, not just on failure.

> 💡 **Interview**: how do you get exactly-once across services? → You don't. You get at-least-once delivery plus idempotent consumers, and that combination is what everyone means when they say exactly-once.

## Why Not 2PC / XA?

You *can* make a DB and a broker commit atomically with two-phase commit (JTA, Atomikos/Narayana). Large-scale systems almost universally don't:

| Problem | Why it's disqualifying |
|---|---|
| **Blocking** | If the coordinator dies after "prepare," participants sit **in doubt** — holding locks — until it recovers. A hot row can be frozen indefinitely. |
| **Availability** | Every participant must be up to commit anything. Availability multiplies *downward*: 3 × 99.9% ≈ 99.7%. |
| **Latency** | Two network round trips plus forced log flushes per participant, per transaction. |
| **Support** | **Kafka doesn't support XA at all.** Neither do most modern datastores or any HTTP API. |
| **Operations** | Recovering in-doubt transactions is manual, rare, and always at 3 a.m. |

It also buys less than it appears: 2PC gives atomicity, but a payment gateway call still isn't transactional. Netflix, Uber, Amazon and Stripe overwhelmingly use outbox + saga + idempotency instead — trading *atomicity* for *eventual consistency plus retries*, which is the trade that actually scales.

## Putting It Together — a Payment Flow

The unsafe version, and why:

```java
@Transactional
public void handleDebit(DebitRequest req) {
    txnRepo.save(txn);
    kafkaTemplate.send("txn-events", event);   // ❌ published before commit
    riskClient.evaluate(req);                  // ❌ external call holding locks
}
```

If the transaction rolls back after that publish, downstream services believe a transaction exists that the source of truth says never happened — and a switch that has already responded to the network can't take it back.

The safe shape:

```text
1.  Idempotency check on RRN / UTR         ← dedupe retries before any work
        ↓
2.  BEGIN
      INSERT txn            (state = PENDING)
      INSERT outbox_event   (TxnCreated)
    COMMIT                                  ← one atomic unit, all in World 1
        ↓
3.  Outbox relay → Kafka                    ← World 2, only after commit
        ↓
4.  Consumers (idempotent) → ledger, notifications, reconciliation
        ↓
5.  External call (bank/PSP) outside any transaction, with its own idempotency key
        ↓
6.  BEGIN  UPDATE txn SET state = 'SUCCESS' WHERE id = ? AND state = 'PENDING'  COMMIT
                                            ← conditional update: safe to repeat
```

Every boundary crossing happens **after** a commit, and every step past it is safe to repeat. The `PENDING → SUCCESS` conditional update in step 6 means a duplicate callback updates 0 rows instead of double-applying — the atomic conditional update from [[9. Database Concurrency]] §9 again.

> [!info] Which component owns the money?
> In a UPI switch this matters: the switch orchestrates, validates, and enforces idempotency, but the **issuer bank's Core Banking System owns the balance**. Most of the switch's consistency problems are therefore boundary problems — outbox, idempotency, reversal handling — rather than row-contention problems.

> [!warning] Three rules
> 1. **Never** call an external service or publish an event inside a transaction.
> 2. Assume **at-least-once** everywhere; make every consumer and every retry idempotent.
> 3. Know which side of the boundary each operation is on — that single question determines whether you need `@Transactional`, an outbox, or a saga.

## Interview Quick-Fire

| Question | The answer they want |
|---|---|
| Two tables inserted, third throws — do I undo the first two? | No — one transaction, so `ROLLBACK` erases all of it. The retry re-runs everything. |
| Why don't the first two inserts survive? | They were never committed; no other transaction could even see them. |
| Does optimistic locking fire on an `INSERT`? | No — only on `UPDATE`/`DELETE` of an existing versioned row. The insert-time analogue is a unique-constraint violation. |
| Where does the exception actually get thrown? | At **flush/commit**, not at your `save()` — Hibernate batches and reorders DML. |
| Does a checked exception roll back? | **No** — it commits. You need `rollbackFor = Exception.class`. |
| What if I catch the exception and return normally? | Spring sees success and commits the partial work. |
| What is `UnexpectedRollbackException`? | An inner `REQUIRED` method failed and marked the transaction rollback-only; the outer one caught the error and tried to commit anyway. |
| `REQUIRES_NEW` vs `NESTED`? | `REQUIRES_NEW` is a separate transaction on a second connection; `NESTED` is a savepoint inside the current one. |
| Risk of `REQUIRES_NEW`? | It holds a second pooled connection, and it can deadlock against a row your own outer transaction locked. |
| Why can't I reuse the entity object on retry? | It's detached with an ID already assigned but no row — Hibernate then issues `UPDATE` and fails forever. Rebuild from the DTO. |
| Retry only the failed statement? | No — the transaction is rollback-only. A retry is a whole new transaction. |
| Why does retry backoff need jitter? | Without it, contending threads retry in lockstep and collide again — a retry storm. |
| What if a Kafka publish is in the transaction? | It can't be un-sent — a phantom event for a payment that doesn't exist. **Dual-write problem.** |
| Why isn't publishing *after* commit safe either? | The process can die between commit and publish — the event is lost and downstream never learns. |
| What if work happens on another thread? | Transactions are thread-bound (`ThreadLocal`); rollback can't reach it, and it can't see your uncommitted rows. |
| How do you fix the dual write? | **Transactional outbox** — the event row commits with the data; a relay publishes after commit. |
| Outbox delivery guarantee? | At-least-once. Consumers **must** be idempotent. |
| Polling relay vs CDC? | Polling is simple with no new infra but adds latency; CDC (Debezium) is low-latency but another component to operate. |
| `@TransactionalEventListener` vs outbox? | Both fire only after commit; the listener isn't durable (crash = lost event). Outbox for money. |
| Can Kafka transactions solve this? | Only Kafka→Kafka. They can't make a Kafka write atomic with a Postgres write. |
| Rollback across services? | You don't — **saga with compensating transactions**. |
| What does compensation look like in payments? | A **reversal entry**, not a delete — ledgers are append-only and auditable. |
| Are sagas atomic? | No. There's a real window of inconsistency; you get eventual consistency and the business accepts it. |
| Choreography vs orchestration? | Choreography = services react to events, no central piece, hard to trace. Orchestration = a coordinator drives the flow, explicit and debuggable. |
| How do you make a consumer idempotent? | Insert the event id against a `UNIQUE` constraint **in the same transaction** as the work; on conflict, ack and return. |
| Why not 2PC? | Blocking on coordinator failure, availability multiplies down, high latency, and Kafka doesn't support XA. |
| The one rule? | **A rollback undoes database writes and nothing else.** Cross the boundary only after commit. |
