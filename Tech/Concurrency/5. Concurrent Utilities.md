Covers Roadmap section 5. Note 3 gave you locks — correct, but blocking. Note 4 gave you pools to run work on. This note is the layer in between: the `java.util.concurrent` toolkit that replaces hand-rolled `synchronized` and `wait`/`notify` with **lock-free counters** and **purpose-built coordination primitives**. In production these are what you actually reach for.

> [!info] The through-line of this note
> Two families, one insight each.
>
> **Family 1 — atomics (§2–§5): do it without locking.** A lock is not the only way to get atomicity. **CAS** (compare-and-swap, §2) is a single CPU instruction that says *"change X to Y, but only if X is still what I last read."* Build a retry loop on top and you get **`AtomicInteger`/`AtomicLong`/`AtomicBoolean`** (§3) and **`AtomicReference`** (§4) — atomic without ever blocking a thread. Under *heavy* contention that retry loop becomes the bottleneck, which is why **`LongAdder`** (§5) splits one counter into many.
>
> **Family 2 — coordination (§6–§10): wait for the right thing.** Each solves a different shape of "wait":
> - **`CountDownLatch`** (§6) — *wait until N things finish.* One-shot.
> - **`CyclicBarrier`** (§7) — *wait until N threads all arrive.* Reusable.
> - **`Semaphore`** (§8) — *wait until a permit is free.* Limits how many at once.
> - **`Phaser`** (§9) — a barrier where the party count can change.
> - **`Condition`** (§10) — *wait until a predicate is true.* (Covered in [[3. Synchronization]] §10.)
>
> The framing question that unlocks §1: **`volatile` gives visibility, locks give atomicity — atomics give both, without blocking.**

> | `AtomicInteger` / CAS | ⭐⭐⭐⭐⭐ | Very frequently |

### 1. Visibility vs Atomicity — Why `volatile` Isn't Enough

This is *the* most commonly asked question in this area, usually phrased as: **"if `volatile` makes a variable thread-safe, why do we need `AtomicInteger`?"** The answer is that they solve different problems.

Recall the three problems from [[1. Core Fundamentals]]: **visibility**, **atomicity**, **ordering**. `volatile` solves visibility and ordering. It does **nothing** for atomicity.

**`volatile` fixes visibility.** Each core has its own cache, so a thread can read a stale value forever:

```text
                 RAM:  flag = false → true
                  │
        ┌─────────┴─────────┐
   Core 1 cache        Core 2 cache
   flag = true         flag = false   ← Thread B still reads this
   (Thread A wrote)    (never refreshed)
```

```java
volatile boolean running = true;              // ✅ correct use of volatile
void worker() { while (running) { } }         // now exits promptly
void stop()   { running = false; }
```

**`volatile` does not fix atomicity.** `count++` is three operations — read, add, write:

```java
volatile int count = 0;
count++;                    // ❌ still broken
```

`count = 5`. Thread A reads `5`, Thread B reads `5`, both add 1, both write `6`. Expected `7`, got `6`. Every read *was* fresh — that was never the problem. The problem is that nothing stopped the two read-modify-write sequences from **interleaving**.

Run it: 100 threads × 1,000 increments should give `100000`. With `volatile int` you get `98121`, `99210`, `95672` — a different wrong answer every run. With `AtomicInteger` you get `100000`, every time.

> [!example] The whiteboard analogy
> A whiteboard everyone can see.
>
> **`volatile`** = everyone immediately sees what's written. But two people can erase and rewrite at the same time: both read `100`, both write `101`. Final value `101`, should be `102`. Visible ≠ safe.
>
> **`AtomicInteger`** = you may only write if the board *still says* what you last read. Person B's write fails, so B re-reads (`101`), recomputes, writes `102`. Correct every time.

| Feature | `volatile` | `AtomicInteger` | `synchronized` |
|---|---|---|---|
| Visibility | ✅ | ✅ | ✅ |
| Atomicity of compound ops | ❌ | ✅ (single variable) | ✅ (any block) |
| Prevents race conditions | ❌ | ✅ | ✅ |
| Uses locks | ❌ | ❌ (CAS) | ✅ (monitor) |
| Blocks threads | Never | Never (retries) | Yes |
| Protects **multiple** variables together | ❌ | ❌ | ✅ |
| Best for | Flags, status, config refs | Counters, single shared value | Multi-variable invariants |

> [!warning] `volatile AtomicInteger` is pointless
> `AtomicInteger` already guarantees visibility *and* atomicity — its internal value field is `volatile`. Adding the keyword on top of the reference adds nothing (unless you're reassigning the reference itself, which you shouldn't be — make it `final`).

> [!info] The dividing line, in one rule
> One variable, simple update ⇒ **atomic**. One variable, read-only publication ⇒ **`volatile`**. Two or more variables that must change together ⇒ **lock**. Atomics can't span fields: `if (a.get() > 0) b.decrementAndGet();` is *two* atomic operations and therefore not atomic. That check-then-act still needs a lock.

### 2. CAS — the Engine Under Every Atomic ⭐

**Compare-and-swap** is a single hardware instruction (`lock cmpxchg` on x86) that atomically does:

> *"Set this memory location to `newValue`, but **only if** it currently holds `expectedValue`. Tell me whether you succeeded."*

```java
AtomicInteger a = new AtomicInteger(5);

a.compareAndSet(5, 10);   // → true,  value is now 10
a.compareAndSet(5, 20);   // → false, value is 10, not 5 — nothing changed
```

The `false` return is the whole point: it means *somebody else changed this since I read it*, so my update would have silently destroyed their work. Instead of overwriting, I'm told to try again.

**Every atomic increment is a retry loop over CAS.** `incrementAndGet()` is conceptually:

```java
while (true) {
    int current = get();                       // read
    int next = current + 1;                    // compute
    if (compareAndSet(current, next))          // publish, only if unchanged
        return next;                           // success
    // else: someone beat us — loop and retry with the fresh value
}
```

Worked through: `count = 5`. Thread A CASes `5→6`, succeeds. Thread B tries CAS with expected `5`, but the value is `6` — **fails**, so B re-reads `6`, computes `7`, CASes `6→7`, succeeds. Final: `7`. Correct, and **no thread ever blocked**.

**Why it's fast:**

| Lock | CAS |
|---|---|
| Acquire monitor → maybe **block** → context switch → modify → release → wake a waiter | One CPU instruction; retry in userspace on failure |
| A losing thread is descheduled (expensive) | A losing thread keeps its core and immediately retries |

This is **lock-free**, not wait-free: no thread can be blocked *by another thread holding something*, but an unlucky thread can retry several times. Under low-to-moderate contention that's a huge win. Under *heavy* contention the retries themselves become waste — see §5.

Modern JDKs implement this through **`VarHandle`** (Java 9+; `sun.misc.Unsafe` historically), and the JIT compiles it down to the native compare-exchange instruction. And note: **a successful CAS establishes a happens-before edge** just like a volatile write ([[3. Synchronization]] §5), so atomics publish safely too.

> [!warning] The ABA problem — the classic CAS follow-up question
> CAS compares **values**, not history. If a value goes `A → B → A` while you were computing, your `compareAndSet(A, ...)` **succeeds** — even though the world changed underneath you.
>
> For a counter this is harmless (you only care about the number). It bites when the value is a **reference** whose identity carries meaning — a lock-free stack where a node was popped, reused, and pushed back would let you link into a stale node.
>
> **Fix:** attach a version stamp, so identity includes "how many times it has changed."
> ```java
> AtomicStampedReference<Node> top = new AtomicStampedReference<>(node, 0);
> int[] stampHolder = new int[1];
> Node current = top.get(stampHolder);
> top.compareAndSet(current, next, stampHolder[0], stampHolder[0] + 1);  // stamp must match too
> ```
> `AtomicMarkableReference` is the cheap variant — a single boolean instead of a counter. Knowing the name of the problem and that `AtomicStampedReference` exists is usually enough.

### 3. `AtomicInteger`, `AtomicLong`, `AtomicBoolean`

Package: `java.util.concurrent.atomic`. Same API shape across all three.

```java
AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet();
System.out.println(count.get());   // 1 — no synchronization anywhere
```

**The methods, and the naming rule that trips people up:**

| Method | Returns | Java equivalent |
|---|---|---|
| `get()` / `set(v)` | value / void | read / write (volatile semantics) |
| `incrementAndGet()` | the **new** value | `++count` (pre-increment) |
| `getAndIncrement()` | the **old** value | `count++` (post-increment) |
| `decrementAndGet()` / `getAndDecrement()` | new / old | `--count` / `count--` |
| `addAndGet(d)` / `getAndAdd(d)` | new / old | `count += d` |
| `getAndSet(v)` | the old value | atomic swap |
| `compareAndSet(exp, new)` | `boolean` | the CAS primitive (§2) |
| `updateAndGet(fn)` / `getAndUpdate(fn)` | new / old | CAS retry loop over a lambda |
| `accumulateAndGet(x, fn)` | new value | CAS loop combining current with `x` |

> [!tip] `getAndX` returns the OLD value; `xAndGet` returns the NEW one
> Read it left-to-right: `getAndIncrement` = "get, *then* increment" → you receive the pre-increment value.
> ```java
> AtomicInteger a = new AtomicInteger(5);
> a.getAndIncrement();   // returns 5, a is now 6
> a.incrementAndGet();   // returns 7, a is now 7
> ```
> An off-by-one from picking the wrong one is a real bug — sequence generators and array indices care.

**`updateAndGet` is the general-purpose escape hatch** — any pure function of the current value, atomically, without writing the retry loop yourself:

```java
AtomicInteger cap = new AtomicInteger(100);
cap.updateAndGet(v -> Math.max(0, v - 10));           // clamped decrement
AtomicLong max = new AtomicLong();
max.accumulateAndGet(latencyMs, Math::max);            // running maximum
```

> [!warning] The lambda may run more than once
> `updateAndGet` / `accumulateAndGet` retry on CAS failure, which means **your function can be invoked several times for one successful update**. It must be **pure**: no logging, no I/O, no mutation, no counters of its own. A side effect in there fires an unpredictable number of times.

**`AtomicLong`** is the same for 64-bit values — sequence generators, request IDs, transaction numbers, Kafka offsets, byte counters. (It also makes 64-bit reads/writes atomic, which plain non-volatile `long` isn't guaranteed to be on some 32-bit JVMs.)

**`AtomicBoolean`** shines for **one-shot guards** — the idiom is worth memorising:

```java
private final AtomicBoolean initialised = new AtomicBoolean(false);

void init() {
    if (initialised.compareAndSet(false, true)) {   // exactly one thread wins
        loadConfiguration();
    }
}
```

Exactly one thread can flip `false → true`, so exactly one runs the block — no lock, no double-checked locking. The same pattern guards "shut down only once," "publish this event only once," and idempotent callbacks.

> [!info] Also in the package, worth knowing by name
> - **`AtomicIntegerArray` / `AtomicLongArray` / `AtomicReferenceArray`** — per-element atomics. Better than an array of `AtomicInteger` (one object, no boxing per slot).
> - **`AtomicIntegerFieldUpdater`** and friends — atomic updates to a `volatile` field of an existing class without adding an object per instance. A memory optimisation for millions of instances; rare in application code.
> - **`lazySet(v)`** — a `set` without the full store barrier. A micro-optimisation; ignore unless profiling says otherwise.

### 4. `AtomicReference` — Atomic Object Swaps

`AtomicInteger` covers numbers. When the shared thing is an **object**, use `AtomicReference<T>`:

```java
AtomicReference<String> ref = new AtomicReference<>("A");
ref.compareAndSet("A", "B");      // atomic reference swap
```

Note what's atomic: **the reference**, not the object's contents. Mutating the referenced object is not protected at all. Which leads to the pattern that makes this class genuinely useful:

> [!tip] `AtomicReference` + immutable object = lock-free shared state
> Don't mutate — **replace**. Build a fresh immutable snapshot and CAS the reference in. Readers get either the whole old state or the whole new state, never a half-updated one:
> ```java
> // Immutable snapshot of the FX table
> record RateTable(Map<String, BigDecimal> rates) {
>     RateTable { rates = Map.copyOf(rates); }
> }
>
> private final AtomicReference<RateTable> current = new AtomicReference<>(new RateTable(Map.of()));
>
> BigDecimal rate(String pair)      { return current.get().rates().get(pair); }   // no lock, no blocking
> void publish(Map<String, BigDecimal> fresh) { current.set(new RateTable(fresh)); }
> ```
> Compare this with the `ReadWriteLock` version in [[3. Synchronization]] §9: same job, but readers never touch a lock at all. This is the **safe publication** pattern from [[3. Synchronization]] §13, and it's the right shape for read-heavy, write-rare config: rate tables, feature flags, routing tables, cached catalogues.

For read-modify-write on the object, `updateAndGet` keeps it atomic:

```java
AtomicReference<Balance> balance = new AtomicReference<>(new Balance(1000));
balance.updateAndGet(b -> b.debit(100));    // b.debit() must return a NEW Balance
```

Again: the lambda can run multiple times, so `debit` must be pure and return a new instance rather than mutating.

Other uses: the current cache object, the latest published config, and lock-free data structures (where you must think about ABA — §2).

### 5. `LongAdder` and `DoubleAdder` — Striped Counters for Hot Paths

Take 500 threads all calling `atomicLong.incrementAndGet()`. Every one of them CASes **the same memory word**. Most fail, retry, fail again — and that single cache line ping-pongs between cores (false sharing). CAS was supposed to avoid blocking, but under this much contention the retry loop *is* the bottleneck.

`LongAdder` fixes it by removing the single hot spot: it keeps an **array of cells** and steers different threads to different cells, so their increments don't collide. When you want the total, it sums the cells.

```text
AtomicLong:   500 threads ──────────► [ one value ]        ← everyone fights
LongAdder:    500 threads ──┬───────► [ cell 0 ]
                            ├───────► [ cell 1 ]           ← contention spread out
                            ├───────► [ cell 2 ]
                            └───────► [ cell N ]
                                          │
                                     sum() = Σ cells
```

```java
LongAdder requests = new LongAdder();

requests.increment();          // hot path — called from every request thread
requests.add(5);
requests.decrement();

long total = requests.sum();   // cold path — called by the metrics exporter
requests.reset();
```

`DoubleAdder` is the same for `double` (accumulating latencies, amounts).

| `AtomicLong` | `LongAdder` |
|---|---|
| One value | Multiple internal cells |
| Faster under **low** contention | Much faster under **high** contention |
| Supports `compareAndSet`, `getAndSet`, `updateAndGet` | **No CAS API** — only add/increment/sum |
| `get()` is an exact instantaneous value | `sum()` aggregates cells — not an atomic snapshot |
| Use when you need the value *and* conditional updates | Use for write-heavy counters you read rarely |

> [!warning] `sum()` is not a consistent snapshot
> `sum()` walks the cells while other threads are still updating them, so the result is approximate — it isn't a point-in-time total, and it can miss increments that land mid-traversal. For **metrics that's fine** (nobody cares if the request counter is off by three for a microsecond). For anything you make a decision on — a rate limit threshold, an inventory count, a balance — use `AtomicLong` or a lock. And there is no `compareAndSet`, so "increment only if below the cap" is impossible with `LongAdder`.

**Use `LongAdder` for:** HTTP request counts, Kafka messages processed, total API hits, cache hits/misses, bytes transferred — write-often, read-occasionally statistics. This is exactly what Micrometer counters use internally (§14 of [[4. Executors and Thread Pools]]).

### 6. `CountDownLatch` — Wait Until N Things Finish

The shape: **one or more threads wait until a count reaches zero.** A one-way gate.

A payment can't proceed until fraud check, balance check and KYC all come back — and all three should run in parallel:

```java
CountDownLatch latch = new CountDownLatch(3);

pool.execute(() -> { try { fraudCheck(txn); }   finally { latch.countDown(); } });
pool.execute(() -> { try { balanceCheck(txn); } finally { latch.countDown(); } });
pool.execute(() -> { try { kycCheck(txn); }     finally { latch.countDown(); } });

if (!latch.await(2, TimeUnit.SECONDS))          // bounded wait — see the warning
    throw new TimeoutException("pre-checks did not complete");

authorise(txn);
```

| Method | Does |
|---|---|
| `countDown()` | Decrement by one. No-op once already zero. |
| `await()` | Block until the count hits zero |
| `await(t, unit)` | Same, bounded — returns `false` on timeout |
| `getCount()` | Current count (diagnostics only) |

**Characteristics:** the count only ever **decreases**, it **cannot be reset**, and once it hits zero the latch stays open forever — every subsequent `await()` returns immediately. It is **one-shot**. Need it again? Create a new one.

> [!warning] A missed `countDown()` hangs the waiter forever
> If a task throws before reaching `countDown()`, the count never reaches zero and `await()` blocks **indefinitely**. Two defences, use both:
> 1. **`countDown()` in a `finally`** — exactly as above. This is not optional.
> 2. **Always prefer the timed `await(t, unit)`** in server code. An unbounded `await()` on a request thread is a hang waiting to happen.
>
> Also remember `await()` throws `InterruptedException` — restore the flag or rethrow ([[2. Java Thread Basics]] §4).

> [!info] Two other uses of the same primitive
> - **A start gate:** initialise a latch at `1`, have N worker threads `await()` on it, then `countDown()` once to release them all simultaneously. Standard trick for benchmarking and for reproducing race conditions in tests.
> - **Readiness signalling:** a service `await()`s a latch that its initialisation thread counts down — a bootstrapping barrier.
>
> In everyday code, `invokeAll` or `CompletableFuture.allOf` ([[4. Executors and Thread Pools]] §2, [[7. Async Programming]]) express fan-in more cleanly and give you the *results*. `CountDownLatch` is the primitive underneath — know it, but reach for the higher-level tool.

### 7. `CyclicBarrier` — Wait Until N Threads All Arrive

Different shape from a latch: here the waiting threads *are* the counted parties. Everyone stops at the barrier until the last one arrives, then all proceed together — and the barrier **resets** for the next round.

```java
CyclicBarrier barrier = new CyclicBarrier(5, () -> log.info("phase complete"));  // optional action

Runnable worker = () -> {
    computePhaseOne();
    barrier.await();          // wait for all 5
    computePhaseTwo();        // nobody starts phase two until everyone finished phase one
    barrier.await();
};
```

The optional **barrier action** runs once, on the last thread to arrive, *before* any of them are released — the natural place to merge partial results or roll the simulation forward one step.

| `CountDownLatch` | `CyclicBarrier` |
|---|---|
| **One-shot** — cannot be reset | **Reusable** — resets automatically each cycle |
| Waiters and counters are **different** threads | The waiting threads are the parties |
| `countDown()` doesn't block | `await()` blocks the caller |
| "Wait until N tasks are done" | "Wait until N threads meet here" |
| Count is fixed and only decreases | Trip count restored every cycle |

Use it for iterative, phased computation: multi-pass simulations, parallel matrix work, batch jobs where every partition must finish stage N before anyone starts stage N+1.

> [!warning] `BrokenBarrierException` — one failure breaks it for everyone
> This is the gotcha, and it's why barriers are harder to use safely than latches. If **any** waiting thread is interrupted, times out, or the barrier action throws, the barrier is **broken**: every other waiting thread gets a `BrokenBarrierException`, and all *future* `await()` calls fail too until someone calls `reset()`.
>
> That's deliberate — a barrier with a missing party can never trip, so failing everyone loudly beats hanging silently. But it means you must handle `BrokenBarrierException` as a real path, not a formality:
> ```java
> try { barrier.await(); }
> catch (BrokenBarrierException e) { abortComputation(e); }      // the phase is unrecoverable
> catch (InterruptedException e)   { Thread.currentThread().interrupt(); return; }
> ```
> Also: if fewer than N threads ever arrive, everyone waits forever. The party count must match reality exactly — a worker that dies early deadlocks the barrier.

### 8. `Semaphore` — Limit How Many at Once

A semaphore holds **N permits**. `acquire()` takes one (blocking if none are left), `release()` gives one back. It's the tool for "at most N threads in here at a time."

```java
private final Semaphore connections = new Semaphore(10);   // pool of 10

void query(String sql) throws InterruptedException {
    connections.acquire();
    try {
        runOnConnection(sql);
    } finally {
        connections.release();        // MANDATORY — and must be in finally
    }
}
```

| Method | Does |
|---|---|
| `acquire()` / `acquire(n)` | Take permit(s), blocking. Throws `InterruptedException` |
| `tryAcquire()` | Take one **or return `false` immediately** |
| `tryAcquire(t, unit)` | Bounded wait — the production-friendly form |
| `release()` / `release(n)` | Return permit(s) |
| `availablePermits()` | Diagnostics / metrics |
| `drainPermits()` | Take everything available |
| `new Semaphore(n, true)` | **Fair** mode — FIFO, prevents starvation, costs throughput |

**Real uses:** connection pools, capping concurrent uploads/downloads, bounding how many threads hit one flaky downstream (a bulkhead — [[4. Executors and Thread Pools]] §16), guarding an expensive resource, throttling parallelism inside a batch job.

`Lock` vs `Semaphore`, the one-liner: a lock has **one** permit and an **owner**; a semaphore has **N** permits and **no owner**.

> [!warning] A semaphore has no ownership — and that's a real hazard
> Unlike a lock, **any** thread can call `release()`, including one that never acquired. There's no "you don't hold this" check. Two consequences:
> - A stray or double `release()` **inflates the permit count above the initial value** — permanently. Your pool of 10 silently becomes a pool of 12, and the invariant you were protecting is gone. There is no exception to tell you.
> - Forgetting `release()` **leaks a permit**, and enough leaks deadlock everything. `try { } finally { release(); }` is as mandatory here as `unlock()` in [[3. Synchronization]] §7.
>
> Since it isn't reentrant either, a thread that acquires twice needs two permits — recursion through a semaphore-guarded method will deadlock itself.

> [!info] A semaphore limits concurrency, not rate
> "10 permits" means *ten at a time*, not *ten per second*. If each task takes 10 ms you're allowing ~1,000/sec; if each takes a second, ~10/sec. For true rate limiting you need a token bucket that refills on a schedule (Guava's `RateLimiter`, Resilience4j, or a `ScheduledExecutorService` that `release()`s permits periodically). Calling a semaphore a rate limiter in an interview is a common slip.

### 9. `Phaser` — a Barrier Whose Party Count Can Change

`CyclicBarrier` needs its party count fixed up front. `Phaser` doesn't: threads can **register** and **deregister** as the computation proceeds, and it tracks a phase number across many rounds.

```java
Phaser phaser = new Phaser(3);         // start with 3 parties

phaser.arriveAndAwaitAdvance();        // ≈ CyclicBarrier.await() — arrive, wait for the phase to advance

phaser.register();                     // a new participant joins mid-flight
phaser.arriveAndDeregister();          // "I'm done, don't wait for me again"
int phase = phaser.getPhase();         // which round we're on
```

Reach for it when the number of participants genuinely varies — recursive task decomposition where subtasks spawn subtasks, or a pipeline where workers retire as their partition finishes. It also supports **tiering** (parent/child phasers) to reduce contention with many parties.

> [!info] Interview depth: shallow
> `Phaser` is rated ⭐⭐ for a reason. You're expected to know **what it is** ("a reusable barrier that supports dynamic registration and multiple phases") and **when it beats `CyclicBarrier`** ("when the party count isn't fixed"). Deep internals are essentially never asked. Don't spend revision time here — spend it on `Semaphore` and `CountDownLatch`.

### 10. `Condition` — Wait Until a Predicate Is True

Roadmap §5 lists `Condition` here, but it belongs to the lock family and is covered in full in **[[3. Synchronization]] §10**. The short version:

`Condition` is `wait`/`notify` for the `Lock` API — and its advantage is **multiple named wait-sets on one lock**, where an intrinsic monitor has only one.

```java
Lock lock = new ReentrantLock();
Condition notFull  = lock.newCondition();
Condition notEmpty = lock.newCondition();
```

| `wait()` / `notify()` | `Condition` |
|---|---|
| Belongs to `Object` | Created from a `Lock` |
| Requires `synchronized` | Requires the `Lock` held |
| `wait()` / `notify()` / `notifyAll()` | `await()` / `signal()` / `signalAll()` |
| **One** wait-set per object | **Many** per lock — signal exactly the right group |

Same rules carry over: `await()` releases the lock and reacquires before returning, and you **must** loop on the predicate (`while (!ready) condition.await();`) because of spurious wakeups. The canonical use is a bounded buffer with separate `notFull`/`notEmpty` queues — which is precisely how `ArrayBlockingQueue` is built ([[4. Executors and Thread Pools]] §6).

### 11. Choosing the Right Utility

Match the **shape of the wait** to the tool:

| You need to… | Use |
|---|---|
| Increment a shared counter safely | `AtomicInteger` / `AtomicLong` |
| Increment a *very hot* counter (metrics) | `LongAdder` |
| Flip a one-shot guard ("initialise once") | `AtomicBoolean.compareAndSet(false, true)` |
| Atomically swap an immutable object (config, rate table) | `AtomicReference` |
| Wait for N parallel tasks to finish | `CountDownLatch` (or `invokeAll` / `allOf`) |
| Make N threads rendezvous each round | `CyclicBarrier` |
| Same, but the party count changes | `Phaser` |
| Cap how many threads use a resource at once | `Semaphore` |
| Wait until a condition/predicate becomes true | `Condition` + `Lock` |
| Hand work between producers and consumers | `BlockingQueue` ([[6. Concurrent Collections]]) |
| Guard a multi-variable invariant | `synchronized` / `ReentrantLock` ([[3. Synchronization]]) |

> [!info] They're all built on the same machinery
> `CountDownLatch`, `Semaphore`, `ReentrantLock` and `ReentrantReadWriteLock` are all thin layers over **`AbstractQueuedSynchronizer` (AQS)** — an `int` state word manipulated by CAS, plus a queue of parked threads. A latch's state is its count; a semaphore's is its permit count; a lock's is its hold count. (`CyclicBarrier` is built one level up, on `ReentrantLock` + `Condition`; `Phaser` has its own CAS-based implementation.)
>
> Two payoffs from knowing this: it explains why they all behave consistently around **interruption** and **timeouts**, and "they're all AQS + CAS" is a strong answer to *"how are these implemented?"*

> [!warning] Every blocking call here throws `InterruptedException`
> `await()`, `acquire()`, `arriveAndAwaitAdvance()` — all of them. That's deliberate: it's what makes `shutdownNow()` and request cancellation work ([[4. Executors and Thread Pools]] §13). Never swallow it. Restore the flag or rethrow, and prefer the **timed** variant (`await(t, unit)`, `tryAcquire(t, unit)`) anywhere on a request path — an unbounded wait in a server is a hang in waiting.

### 12. Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| Why can't `volatile` replace `AtomicInteger`? | `volatile` gives visibility and ordering only. `count++` is read-modify-write, so it still races. Atomics add atomicity via CAS. |
| What is CAS? | A single CPU instruction: set the location to `newValue` only if it still holds `expectedValue`; report success. Failure means someone else changed it, so retry. |
| How does `AtomicInteger.incrementAndGet()` work internally? | A retry loop: read the current value, compute value+1, `compareAndSet`; on failure re-read and repeat. Compiled to a native compare-exchange via `VarHandle`. |
| Why is `AtomicInteger` faster than `synchronized` for a counter? | No lock acquisition, no blocking, no context switches — a losing thread keeps its core and retries in userspace. |
| Is CAS lock-free or wait-free? | Lock-free — no thread blocks on another, but an unlucky thread may retry repeatedly. |
| `getAndIncrement()` vs `incrementAndGet()`? | `getAndIncrement` returns the **old** value (`count++`); `incrementAndGet` returns the **new** one (`++count`). |
| What is the ABA problem? | A value changes `A→B→A`, so CAS succeeds even though state changed. Fix with `AtomicStampedReference` (adds a version stamp) or `AtomicMarkableReference`. |
| Can `updateAndGet`'s lambda run twice? | Yes — it retries on CAS failure, so the function must be pure with no side effects. |
| When would you use `AtomicReference`? | To atomically swap an **immutable** object: config snapshots, FX/rate tables, feature flags, cached state. Lock-free reads. |
| Does `AtomicReference` protect the object's fields? | No — only the reference. That's why the referenced object should be immutable. |
| `AtomicLong` vs `LongAdder`? | `AtomicLong` = one value, exact reads, supports CAS, best at low contention. `LongAdder` = striped cells, far better at high contention, no CAS, `sum()` is approximate. |
| When would you *not* use `LongAdder`? | When you need an exact instantaneous value or a conditional update — no `compareAndSet`, and `sum()` isn't a consistent snapshot. So: metrics yes, rate-limit thresholds and balances no. |
| Can atomics replace locks entirely? | No. They're per-variable. Any invariant spanning two or more fields (or a check-then-act across them) still needs a lock. |
| Is `volatile AtomicInteger` useful? | No — `AtomicInteger` already provides visibility and atomicity. Make the reference `final` instead. |
| `CountDownLatch` vs `CyclicBarrier`? | Latch: one-shot, count only decreases, waiters ≠ counters. Barrier: reusable, resets each cycle, the waiting threads are the parties. |
| Can a `CountDownLatch` be reused? | No. Once it reaches zero it stays open; create a new one. |
| What if `countDown()` is never called? | `await()` blocks forever. Always `countDown()` in a `finally` and prefer the timed `await`. |
| What is `BrokenBarrierException`? | If any party is interrupted/times out or the barrier action throws, the barrier breaks — all waiters and all future `await()`s fail until `reset()`. Fail loud instead of hanging forever. |
| What does the `CyclicBarrier` barrier action do? | Runs once on the last arriving thread, before any are released — used to merge results between phases. |
| What problems does `Semaphore` solve? | Bounding concurrency: connection pools, concurrent uploads, per-downstream bulkheads, throttling parallelism. |
| `Lock` vs `Semaphore`? | A lock has one permit and an owner; a semaphore has N permits and **no owner** — any thread may release. |
| Biggest `Semaphore` hazard? | No ownership check: a stray `release()` permanently inflates the permit count, and a missed one leaks a permit. Always `release()` in `finally`. |
| Is a `Semaphore` a rate limiter? | No — it limits *concurrent* holders, not requests per second. Use a token bucket for rate. |
| What does `Phaser` add over `CyclicBarrier`? | Dynamic registration (`register` / `arriveAndDeregister`) and explicit phase numbers, so the party count can change. |
| `Condition` vs `wait()`/`notify()`? | `Condition` works with a `Lock` and gives **multiple** named wait-sets; a monitor has one. `await`/`signal`/`signalAll` map to `wait`/`notify`/`notifyAll`. |
| How are these implemented? | Mostly `AbstractQueuedSynchronizer`: a CAS-updated `int` state plus a park/unpark queue. Latch state = count, semaphore state = permits, lock state = hold count. |
| What do all their blocking methods have in common? | They throw `InterruptedException` — so cancellation and `shutdownNow()` work. Never swallow it; prefer timed variants on request paths. |
