# Index & Lock Internals

---

Extends §9 ([[9. Database Concurrency]]) and §12 ([[12. Lost Updates & High-Contention Architectures]]). Those notes stop at "the second transaction waits on a row lock." This note opens that box: **what the index physically looks like, what the engine actually latches, and what exactly the second thread is suspended on.** It's the layer below isolation levels — the one interviewers reach for when you answer the isolation-level question too well.

> [!info] The through-line of this note
> One chain, read in order:
>
> 1. **An index is a B+-tree** (§1) — internal nodes navigate, leaves hold data and are linked. InnoDB says so; Postgres says "B-tree" but is structurally the same thing (§2).
> 2. Where the **row data lives** is the real difference: InnoDB's table *is* the primary-key tree (**clustered**), Postgres keeps an unordered **heap** and indexes point into it with a TID (§3). That single choice explains the double lookup (§4) and both engines' index-maintenance costs (§5).
> 3. Writing into that tree needs two *different* protections, and conflating them is the classic mistake: a **latch** guards the physical page for microseconds; a **lock** guards logical data until commit (§6).
> 4. Trace a concurrent insert on a unique key: InnoDB leaves an **implicit lock** on the fresh row (its `trx_id`) and only materialises a real lock entry when someone actually waits (§7, §8). Postgres has no implicit lock — the waiter blocks **directly on the inserter's XID** (§9). Different plumbing, identical outcome (§10).
> 5. Two threads on the **same page with different keys** also wait — but on the latch, always microseconds, unrelated to uniqueness (§11).
> 6. **Non-unique** indexes skip conflict checking entirely; duplicates are ordered by a hidden tiebreaker (§12) — and when one key owns most of the rows, the index stops earning its keep (§13).
> 7. Then the correctness layer: what isolation level actually changes about an MVCC snapshot (§14), first-committer-wins vs last-writer-wins (§15), **Redis in front of the DB lock** as a resource guard rather than a correctness fix (§16), and where optimistic locking really lives (§17, §18).
>
> One line to anchor everything: **the second thread inserting a duplicate key doesn't fail fast — it queues, waiting on the first transaction's commit, because the fresh row already carries an ownership stamp.**

## Short Notes

---

### 1. B-tree vs B+-tree

| | B-tree (classic) | B+-tree |
|---|---|---|
| Data location | **Any** node — internal or leaf | **Leaves only**; internal nodes are keys + child pointers |
| Search | Can terminate **early** at an internal node | Always walks **all the way down** to a leaf |
| Leaf links | None | **Leaves linked** (sibling pointers) |
| Range scan | Re-traverse the tree per step | **Walk the leaf chain** — cheap |

- The two B+-tree properties that matter: **all data in leaves** + **linked leaves**
- That combination is why every serious DB index is a B+-tree — `BETWEEN`, `ORDER BY` and full index scans become a linear walk
- Fanout is huge (hundreds of keys per page), so real indexes are **3–4 levels deep** even at billions of rows

> "Binary tree" is never the answer for a DB index — a node is a **page** holding hundreds of keys, sized to one buffer-pool page.

---

### 2. What the Engines Actually Use

- **MySQL InnoDB**: documented as a **B+-tree**, explicitly — no ambiguity
- **PostgreSQL**: `USING btree` is **historical naming**; the structure is a B+-tree (internal nodes navigation-only, leaves hold `key + TID`)
- Postgres specifically implements the **Lehman & Yao B-link tree** — a high-concurrency B+-tree variant with **right-sibling pointers at every level**, so a traversal that lands on a page mid-split just **moves right** instead of latching upward
- Practical effect: Postgres avoids some of InnoDB's upward-latching pain during concurrent splits

> The wrong takeaway from blog posts: "MySQL = B+-tree, Postgres = B-tree." Both are B+-trees; only the *name* differs.

---

### 3. Clustered Index vs Heap Storage

| | InnoDB | PostgreSQL |
|---|---|---|
| Table storage | **Clustered** — the table *is* the PK B+-tree | **Heap** — unordered pages, separate from every index |
| PK index leaf holds | The **entire row** | `key + TID` |
| Secondary index leaf holds | Indexed column(s) + **PK value** | `key + TID` |
| Row address | Logical (the PK) | Physical — **TID** = `(page_number, offset)` |

- InnoDB has **no heap**: there is nowhere for a row to live except a clustered-index leaf
- No PK declared? InnoDB uses the first non-null unique index, else a hidden 6-byte `row_id` — it **always** has one internally
- Postgres has **no clustered index at all** (`CLUSTER` is a one-off physical re-sort, not maintained)

---

### 4. Secondary Index Lookup — the Double Lookup

`SELECT * FROM payments WHERE upi_ref_id = 'UPI700';`

```text
InnoDB                                  PostgreSQL
──────                                  ──────────
1. traverse idx_upi_ref                 1. traverse idx_upi_ref
   → ('UPI700', id=102)                    → ('UPI700', TID=(3,2))
2. traverse CLUSTERED index for id=102  2. jump straight to heap page 3, off 2
   → full row                              → full row
= 2 tree traversals                     = 1 traversal + 1 direct fetch
```

- InnoDB's step 2 is the **double lookup** (bookmark lookup) — unavoidable unless the index **covers** the query
- **Covering index**: if every selected column lives in the secondary index, InnoDB stops at step 1
- Postgres's equivalent shortcut is an **index-only scan** — needs the visibility map to say the page is all-visible, otherwise it must touch the heap anyway to check MVCC visibility

---

### 5. What Each Layout Costs You

- **InnoDB — keep the PK short and sequential**: every secondary-index leaf stores a **copy of the PK**, so a UUID PK bloats *every* index; a random PK also scatters inserts across leaf pages instead of appending near the rightmost one
- **Postgres — pay in MVCC bloat**: an `UPDATE` writes a **new tuple** at a new TID and marks the old one dead; index entries pointing at dead tuples linger until `VACUUM`
- Postgres softens this with **HOT** (heap-only tuple) updates — if **no indexed column changed** and the new tuple fits on the same page, no index entry is written at all
- "Which is faster for a secondary-key point lookup?" → **it depends**; one hop via TID sounds cheaper, but InnoDB's second traversal is a warm in-memory tree walk, and Postgres pays vacuum/bloat costs InnoDB doesn't

---

### 6. Latch vs Lock — the Core Distinction

| | **Latch** | **Lock** |
|---|---|---|
| Protects | Physical in-memory structure (a **page**) | Logical data — transaction isolation |
| Granularity | **Page**-level | **Row** / index-record level |
| Duration | **Microseconds** — the write itself | Until **commit / rollback** |
| Transaction-aware | **No** | **Yes** |
| Deadlocks | Avoided by protocol; **not detected** | **Detected**, victim rolled back |
| Analogy | Mutex / spinlock | Classic DB row lock |
| Postgres name | **Buffer lock** (+ lightweight locks) | Row lock / XID wait |

- **S-latch** allows concurrent readers and traversals; only a **write** needs the **X-latch**
- The latch is released **the instant the page write finishes** — long waits are *never* latch waits
- So: "what is the second thread waiting on?" → **the lock**, essentially always

---

### 7. Concurrent Insert on a Unique Key — InnoDB

Two threads insert the same `upi_ref_id`, microseconds apart.

```text
T1  traverse B+-tree → target leaf page
    X-latch the leaf → write row → release latch      (µs)
    row header now carries T1's trx_id  ← implicit lock
T2  brief latch on the same page just to read it
    sees a row for that key, trx_id still ACTIVE
    duplicate check requests a lock on that record
    → InnoDB converts T1's implicit lock into an EXPLICIT one
    → T2 registered as a waiter, physically suspended
    ─────────────── waits for T1 to resolve ───────────────
    T1 COMMIT   → T2 wakes, re-checks → DUPLICATE KEY ERROR
    T1 ROLLBACK → row gone → T2 wakes → INSERT SUCCEEDS
```

- T2 is **not polling and not choosing** to wait — the engine suspends the thread
- The wait is bounded by **T1's transaction length**, not by the insert — a long transaction holds the duplicate check hostage for its whole life
- `SHOW ENGINE INNODB STATUS` and `sys.innodb_lock_waits` are where this surfaces; `innodb_lock_wait_timeout` (default 50s) ends it

---

### 8. Implicit Locks — What They Actually Are

- Still a **pessimistic exclusive** lock — same category as a normal row lock, *not* an optimistic scheme
- "Implicit" describes **when the lock-table entry is created**, nothing else:
  - **Normal path**: entry created eagerly the moment a row is locked
  - **Fresh insert**: **no entry at all** — the row's `trx_id` alone implies "this transaction owns me"
  - Entry is **materialised on demand**, only when a second transaction actually needs to wait
- Why the optimisation exists: the overwhelming majority of inserted rows are **never contended**, so allocating a lock object per insert would be pure waste
- What it explains: a plain `INSERT` hitting an *uncommitted* duplicate **queues** instead of failing instantly

---

### 9. Concurrent Insert on a Unique Key — PostgreSQL

- Postgres has **no implicit-lock concept** — every tuple carries `xmin` / `xmax` (creating / deleting XIDs), and both visibility *and* waiting key off those

```text
T1  traverse B-tree → target leaf
    brief BUFFER LOCK on the page → insert heap tuple + index entry → release
    tuple tagged xmin = T1
T2  traverses to the same slot, buffer-locks to read
    finds T1's entry, xmin belongs to a STILL-ACTIVE transaction
    → XactLockTableWait(T1)   ← blocks on the TRANSACTION ID, not the row
    ─────────────── waits for T1 to resolve ───────────────
    T1 COMMIT   → ERROR: duplicate key value violates unique constraint
    T1 ROLLBACK → tuple dead → re-check → INSERT SUCCEEDS
```

- The wait object is literally *"tell me when XID 12345 finishes"* — visible as `wait_event_type = 'Lock'`, `wait_event = 'transactionid'` in `pg_stat_activity`
- ⚠️ **Terminology precision**: *speculative insertion* (with its speculative token and `SpeculativeInsertionWait`) is the **`INSERT … ON CONFLICT`** machinery. A **plain** `INSERT` doesn't use it — `_bt_check_unique` simply waits on the conflicting XID

---

### 10. InnoDB vs PostgreSQL — Same Outcome, Different Plumbing

| | InnoDB | PostgreSQL |
|---|---|---|
| Physical write protection | Page **latch** | **Buffer lock** (same idea) |
| What T1 holds after insert | **Implicit lock** via `trx_id` on the row | Nothing extra — just `xmin` on the tuple |
| What T2 waits on | Implicit lock **converted to explicit** record lock | T1's **XID**, via `XactLockTableWait` |
| Upsert primitive | `INSERT … ON DUPLICATE KEY UPDATE`, `INSERT IGNORE` | `INSERT … ON CONFLICT` (first-class) |
| Outcome | Wait → duplicate error **or** success | **Identical** |

> **One-liner**: "The outcome is identical — the second thread waits for the first transaction to resolve. InnoDB gets there by converting an implicit row lock into an explicit one; Postgres gets there by blocking directly on the inserting transaction's XID. Same guarantee, different internal plumbing."

---

### 11. Same Page, Different Key — Pure Latch Contention

- Latches are **page-level, not row-level** — the whole leaf page is the unit of protection
- T1 inserts key `A`, T2 inserts key `B`, **same leaf page** → T2 **does** wait, but only for the **X-latch**
- That wait is nano/microsecond scale, **unrelated to uniqueness or transaction length** — pure "two threads can't write the same memory page at once"
- **Page split** (leaf full): the split must latch the **parent** too, briefly widening the contention window — rare, and exactly where Postgres's right-links pay off
- Same mechanism explains **rightmost-page contention** on a monotonic PK: every insert lands on the last page and serialises on its latch

| Scenario | Waits on | Duration |
|---|---|---|
| Same key, T1 uncommitted | **Lock** | Length of T1's transaction — unbounded |
| Same page, different key | **Latch** | Microseconds |
| Different page | Nothing | — |

---

### 12. Non-Unique Indexes — How Duplicates Are Ordered

- A B+-tree needs a **total order**; equal keys need a **tiebreaker** to be positioned and uniquely located
- **InnoDB** silently appends the **PK** to every secondary-index entry — so entries are unique internally whether or not the index is declared `UNIQUE`
- **Postgres** uses the **TID**, which is unique by construction (page + offset)

```text
idx_status ON payments(status)      -- non-unique

InnoDB leaves            Postgres leaves
('PENDING', pk=102)      ('PENDING', TID=(3,2))
('PENDING', pk=108)      ('SUCCESS', TID=(3,1))
('SUCCESS', pk=101)      ('SUCCESS', TID=(3,4))
('SUCCESS', pk=105)      ('SUCCESS', TID=(7,2))
```

- Equal keys **cluster together**; a lookup finds the first match and **walks right along the linked leaves** until the key changes
- **No conflict check, no duplicate-related waiting** — that step exists only for `UNIQUE` indexes
- Any locking you see on a non-unique index is **ordinary** row locking (`SELECT … FOR UPDATE`, `UPDATE`), never a consequence of duplication

---

### 13. Low Cardinality — When the Index Stops Helping

- If one value owns most rows (`status = 'SUCCESS'` on 90% of a payments table), its duplicate cluster spans **many leaf pages**
- The scan must walk all of them — and in InnoDB pay the **double lookup once per matching row**
- The planner will often **skip the index** and full-scan instead: random per-row fetches cost far more per row than a sequential scan
- Fixes: index **selective** columns; use a low-cardinality column only as the **leading column of a composite** index (`(status, created_at)`), or a **partial index** (Postgres: `WHERE status = 'PENDING'`)
- Payments shape: `status` alone is useless; `(status, created_at)` serves the pending-worklist query, and a partial index on `PENDING` keeps the hot set tiny

---

### 14. MVCC Snapshots — What Isolation Level Actually Changes

- Every row has **multiple versions** tagged by transaction ID — Postgres stores old versions **in the heap** (`xmin`/`xmax`); InnoDB **reconstructs** them on demand from the **undo log**
- A reader gets the version visible **as of its snapshot** — and *when the snapshot is taken* is the isolation level's job:

| | READ COMMITTED | REPEATABLE READ / SERIALIZABLE |
|---|---|---|
| Snapshot taken | **Per statement** | **Once per transaction** |
| Re-read after another txn commits | Sees the **new** value | Sees the **old** value |

- ⚠️ "T1 still sees 1000 after T2 commits" is true **only** under RR/SERIALIZABLE — under READ COMMITTED the very next statement sees 300
- **Writes never use the snapshot.** `UPDATE` / `DELETE` / `SELECT … FOR UPDATE` do a **current read**: latest committed version + X lock
- Defaults differ and it matters: **MySQL = REPEATABLE READ**, **PostgreSQL = READ COMMITTED**

---

### 15. First Committer Wins vs Last Writer Wins

- **Postgres, RR/SERIALIZABLE**: T1 updating a row committed by another txn **after** T1's snapshot → `ERROR: could not serialize access due to concurrent update`. The engine **aborts** T1; the app retries → **first committer wins**
- **Postgres SERIALIZABLE (SSI)** additionally catches **read/write dependency cycles** via predicate (SIREAD) locks → `could not serialize access due to read/write dependencies among transactions`
- **InnoDB, REPEATABLE READ**: the `UPDATE` blocks, then proceeds against the **latest committed** row. **No error, no abort** → **last writer wins**, which is precisely why MySQL's RR still permits the lost update ([[12. Lost Updates & High-Contention Architectures]])
- ⚠️ Engine-specific — never say "the DB aborts the second writer" without naming the engine *and* the level
- *Semi-consistent read* is a narrower InnoDB `UPDATE` optimisation (don't wait on rows that won't match the `WHERE`), tied to READ COMMITTED — not the mechanism behind any of the above

---

### 16. Redis Lock in Front of the DB Lock

**Rule: a Redis lock is always *in addition to* the DB lock, never instead of it.**

```text
SET lock:account:123 <uuid> NX EX 5
  ├── acquired     → SELECT … FOR UPDATE → txn → COMMIT → release (Lua CAS-delete)
  └── not acquired → fail fast, never touch the DB, retry with backoff
```

- What it buys: **DB connections**. Without it, 1000 requests for one hot account each occupy a pooled connection while blocked on the row lock — exhausting the pool and degrading **unrelated** accounts
- With it, only **one** request per account reaches the DB; the rest are turned away by a microsecond in-memory op
- Two non-negotiables: **TTL** (`EX`) so a crashed holder can't wedge the account forever, and a **unique value + compare-and-delete in Lua** so you never release a lock that TTL'd out and was re-acquired by someone else
- It is a **resource-protection** mechanism, not a correctness one — the DB was already correct. See [[10. Distributed Concurrency]] for fencing tokens and why Redlock isn't a safety guarantee

---

### 17. Optimistic Locking — Application-Level vs Engine-Level

Two genuinely different mechanisms, one philosophy: *don't block, detect late.*

| | **A. Version column (app-level)** | **B. SERIALIZABLE (engine-level)** |
|---|---|---|
| Who detects | **Your code** — `rowsAffected == 0` | **The engine** — predicate/SIREAD tracking |
| DB awareness | None — it's just a conditional `UPDATE` | Native to the isolation level |
| Schema change | Needs `version` / `updated_at` | None |
| Portability | Any DB | Postgres SSI; MySQL SERIALIZABLE is lock-based instead |
| Cost | Near zero | Full SSI overhead across the whole transaction |
| App's job | Retry from the read | Catch the serialization error, retry |

- **When optimistic wins**: high read / low write, conflicts genuinely **rare** — you almost always succeed first try with no blocking at all
- **When it loses**: a contended hot row — every attempt fails and retries, converting contention into wasted work and tail latency. Use pessimistic there, or change the shape (§12 architectures)
- The version column dominates in practice: simple, portable, and it doesn't buy SERIALIZABLE's blanket cost

---

### 18. Where Optimistic Locking Is Actually Used

| System | The conflict detector | Why optimistic fits |
|---|---|---|
| **E-commerce stock** | `WHERE id = ? AND version = 12` | Millions browse; same-item simultaneous checkout is rare |
| **JPA / Hibernate `@Version`** | `OptimisticLockException` on 0 rows | The default enterprise-Java pattern, often unnamed |
| **Reconciliation / retry jobs** | `AND status = 'PENDING'` — state as the guard | Two workers must not double-credit or double-webhook |
| **Collaborative docs** | Version divergence → **OT / CRDT merge** | Locking a document makes co-editing unusable |
| **Ticket / seat booking** | **Hybrid** — optimistic while browsing, pessimistic at payment | Double-booking a paid seat costs more than 200 ms of waiting |

- The lightest real form needs **no version column at all** — the **business state** is the guard:
  `UPDATE payments SET status='SUCCESS' WHERE txn_id=? AND status='PENDING'`
- The app's job is always identical: **check `rowsAffected`, retry or surface a conflict on 0**
- Real systems choose **per operation**, not per system

### 19. The End-to-End Mental Model

```text
INSERT INTO payments(upi_ref_id, …)   -- unique index on upi_ref_id
   │
   ├─ traverse B+-tree (S-latches, released as you descend)
   │
   ├─ X-LATCH target leaf page ─────── µs, physical ──────► other writers on this
   │     write entry; split if full (parent latched too)     page wait here, briefly
   │     release latch
   │
   ├─ UNIQUE index? ── no ──► done. duplicates just cluster by PK/TID tiebreaker
   │        │
   │       yes
   │        ▼
   │   existing entry for this key?
   │        ├─ committed     ──► duplicate key error, immediately
   │        ├─ uncommitted   ──► WAIT  (InnoDB: implicit→explicit lock
   │        │                          Postgres: XactLockTableWait on XID)
   │        │                    bounded by the OTHER TXN's lifetime
   │        │                      → it commits   = duplicate error
   │        │                      → it rolls back = success
   │        └─ none          ──► insert proceeds
   │
   └─ row now carries trx_id / xmin = me  ► implicit ownership until I resolve
```

- **Latch = physical, µs, page.  Lock = logical, until commit, row.** Every long wait is a lock wait
- **Uniqueness is what creates waiting on insert** — non-unique indexes never wait on "sameness"
- **Keep transactions short.** A duplicate-key check on a contended key is hostage to the other transaction's length
- **Remove contention structurally**: an idempotency key with `ON CONFLICT DO NOTHING` / `INSERT … ON DUPLICATE KEY UPDATE` instead of check-then-insert; avoid a random PK in InnoDB; watch the rightmost page when the PK is purely monotonic

# Detailed Explanation

---

## B-tree vs B+-tree

The naming is used loosely everywhere, and the distinction is small but real.

A **classic B-tree** allows *any* node — internal or leaf — to carry payload. A search can therefore terminate early, at an internal node, if the key happens to live there. Leaves have no relationship to each other.

A **B+-tree** makes two changes:

1. **Internal nodes hold keys only** — they are pure routing tables. All payload lives in the leaves. Every search walks the full height of the tree, with no early exit.
2. **Leaves are linked** to their siblings.

Losing early termination sounds like a regression, and in isolation it is. But it buys two things a database cares about far more:

- **Range scans become a linear walk.** `WHERE created_at BETWEEN a AND b` descends once, then follows the leaf chain. In a classic B-tree, each successive key requires re-navigating from wherever you are.
- **Predictable I/O.** Every lookup costs exactly the height of the tree, and internal nodes are tiny (keys only), so more of them fit in memory. In practice the upper levels stay permanently cached in the buffer pool.

```text
B+-tree, height 3

                    [ 500 | 900 ]              internal: keys only
                   /      |      \
        [100|300]     [600|750]    [950]       internal: keys only
        /   |   \      /  |  \      /  \
      L1 ↔ L2 ↔ L3 ↔ L4 ↔ L5 ↔ L6 ↔ L7 ↔ L8   leaves: DATA + sibling links
```

Nothing here is a binary tree. A node is a **page** (16 KB in InnoDB, 8 KB in Postgres) holding hundreds of keys, so fanout is in the hundreds and even a billion-row table is 3–4 levels deep. That's why a point lookup is "3 page reads," most of which are cache hits — and why answering "binary search tree" to an index question is an immediate red flag.

---

## What the Engines Actually Use

**MySQL InnoDB** calls it a B+-tree in its own documentation. No interpretation required.

**PostgreSQL** ships `CREATE INDEX … USING btree` and calls the access method `btree` — but that name is historical and generic, not a structural claim. Structurally:

- internal nodes hold **keys + child pointers only**;
- leaves hold `(key, TID)` pairs, where the TID points at the heap row.

Data-bearing leaves, navigation-only internal nodes — that is a B+-tree.

Postgres goes further and implements the **Lehman & Yao B-link tree**, a B+-tree variant designed specifically for high concurrency. Its defining feature is **right-sibling pointers at every level, not just the leaves**. Why that matters: if a concurrent insert splits a page while you are descending, the key you want may have moved to the new right-hand page. In a plain B+-tree the descending thread would need to back up and re-latch the parent. With right-links it simply **moves right** until it finds the page that now covers its key. Traversal never needs to hold a latch upward, which is a large part of why Postgres suffers less page-latching pain than InnoDB during concurrent modification.

> 💡 **Interview**: "MySQL uses a B+-tree and Postgres uses a B-tree, right?" → "Both are B+-trees. Postgres's default access method is *named* `btree` for historical reasons, but internal nodes are navigation-only and leaves hold key+TID — a B+-tree shape, specifically the Lehman & Yao B-link variant for concurrency. The real difference between the engines isn't the tree, it's clustered storage vs heap storage."

---

## Clustered Index vs Heap Storage

This is the difference that actually changes how you design a schema.

**InnoDB is clustered.** The table *is* the primary key's B+-tree. Leaf pages of that tree contain the **complete rows**, in primary-key order. There is no separate table storage — no heap — for a row to live in. Consequences:

- A primary key is **mandatory internally**. If you don't declare one, InnoDB picks the first non-null `UNIQUE` index; failing that, it generates a hidden 6-byte `row_id`.
- **Secondary index leaves store the indexed columns + the PK value**, because the PK is the only address a row has.

**Postgres is heap-based.** The table is a set of unordered pages. Every index — primary key included — is a separate B+-tree whose leaves hold `(key, TID)`. A **TID** is a physical address: `(page_number, offset_within_page)`.

```text
InnoDB                                  PostgreSQL

  PK tree (= the table)                   HEAP (unordered pages)
  ┌────────────────────────┐              ┌──────────────────────┐
  │ leaf: id=102 | UPI700  │              │ page 3, off 2:       │
  │       | SUCCESS | 400  │  ← full row  │  102|UPI700|SUCCESS  │
  └────────────────────────┘              └──────────────────────┘
            ▲                                        ▲
            │ PK value                               │ TID
  ┌─────────┴──────────┐                  ┌──────────┴───────────┐
  │ idx_upi_ref leaf:  │                  │ idx_upi_ref leaf:    │
  │  ('UPI700', 102)   │                  │  ('UPI700', (3,2))   │
  └────────────────────┘                  └──────────────────────┘
```

Postgres has **no clustered index** at all. `CLUSTER table USING index` does a one-time physical re-sort of the heap; nothing maintains that order afterwards, so it drifts as soon as you write.

## Secondary Index Lookup — the Double Lookup

One table, one query, traced physically in both engines.

```sql
CREATE TABLE payments (
    id         INT PRIMARY KEY,          -- InnoDB: this becomes the clustered index
    upi_ref_id VARCHAR(50),
    status     VARCHAR(20),
    amount     DECIMAL(10,2)
);
CREATE UNIQUE INDEX idx_upi_ref ON payments(upi_ref_id);

-- id=101, 'UPI500', SUCCESS, 250.00
-- id=102, 'UPI700', SUCCESS, 400.00

SELECT * FROM payments WHERE upi_ref_id = 'UPI700';
```

**InnoDB — two tree traversals:**

```text
1. Traverse idx_upi_ref for 'UPI700'
   → leaf entry ('UPI700', id=102)
     ↑ this leaf has NO status and NO amount — only the PK value

2. Take id=102 and traverse the CLUSTERED index (the PK tree)
   → leaf entry: (102, 'UPI700', 'SUCCESS', 400.00)   ← the full row

3. Return the row
```

**PostgreSQL — one traversal plus a direct fetch:**

```text
1. Traverse idx_upi_ref for 'UPI700'
   → leaf entry ('UPI700', TID=(page 3, offset 2))

2. Jump straight to heap page 3, offset 2
   → (102, 'UPI700', 'SUCCESS', 400.00)

3. Return the row
```

| Step | InnoDB | Postgres |
|---|---|---|
| 1 | Traverse secondary B+-tree | Traverse B-tree |
| 2 | Get **PK value** from leaf | Get **TID** from leaf |
| 3 | **Traverse the clustered index again** | **Jump directly** to page/offset |
| Total | 2 tree traversals | 1 traversal + 1 direct fetch |

InnoDB's step 2 is the **double lookup** (or bookmark lookup). The escape hatch is a **covering index** — if every column the query needs is already in the secondary index, step 1 is the whole story:

```sql
-- Covered: InnoDB answers entirely from idx_ref_status, no clustered-index visit
CREATE INDEX idx_ref_status ON payments(upi_ref_id, status);
SELECT status FROM payments WHERE upi_ref_id = 'UPI700';   -- ✅ index-only
SELECT * FROM payments WHERE upi_ref_id = 'UPI700';        -- ❌ needs the row
```

Postgres's counterpart is the **index-only scan**, and it has an extra condition: because MVCC visibility information lives in the **heap tuple**, not the index entry, Postgres can skip the heap only when the **visibility map** marks the page all-visible. On a page written recently, an "index-only scan" still touches the heap. This is one reason a stale `VACUUM` quietly degrades read plans.

## What Each Layout Costs You

Each design pays a maintenance bill, and they are different bills.

**InnoDB: keep the primary key short and, ideally, sequential.**

- Every secondary index leaf carries a **copy of the PK**. A 16-byte random UUID PK inflates *every* secondary index on the table, permanently.
- A random PK also **scatters inserts** across the clustered index: each insert lands on an arbitrary leaf page, so the working set is the whole index rather than the tail, and page splits are frequent. A sequential PK appends near the rightmost page instead — far fewer splits and better cache behaviour.
- Trade-off worth knowing: a purely monotonic PK concentrates *all* inserts on that one rightmost page, which is where **latch** contention shows up (§ Same Page, Different Key). The usual answer at high insert rates is neither a pure UUID nor a pure counter but something like a time-ordered ULID/UUIDv7.

**Postgres: pay in MVCC bloat.**

- An `UPDATE` does not modify the row in place. It writes a **new tuple** (new TID) and marks the old one dead via `xmax`. Index entries then point at dead tuples until `VACUUM` reclaims them.
- Mitigation is **HOT** — heap-only tuple — updates: when **no indexed column changed** and the new version fits on the same heap page, Postgres links the new tuple from the old one and writes **no index entries at all**. This is why "don't index columns you update constantly" is real advice on Postgres.
- InnoDB has no direct analogue because updates modify the clustered-index row roughly in place and push the old version into the **undo log**, which is discarded once no snapshot needs it.

So "which is faster for a point lookup on a secondary key?" is honestly **it depends**. One TID hop sounds cheaper than a second tree traversal, but InnoDB's PK tree is almost certainly warm in the buffer pool, and Postgres carries vacuum/bloat costs InnoDB doesn't. Have the nuance ready rather than declaring a winner.

## Latch vs Lock — the Core Distinction

Two threads writing to a B+-tree need protection at two entirely separate levels, and conflating them is the single most common error in this whole topic.

A **latch** protects a **physical structure in memory** — one page in the buffer pool. It exists so that two threads don't corrupt the page's internal layout (slot directory, free-space pointers) while both writing bytes into it. It is exactly a mutex: no transaction identity, no isolation semantics, no deadlock detection (correctness comes from a fixed acquisition protocol), and a lifetime measured in **microseconds** — the duration of the write itself.

A **lock** protects **logical data** for the sake of transaction isolation. It is transaction-aware, it lives in a lock table, it is held **until commit or rollback**, it is subject to **deadlock detection with a rolled-back victim**, and its lifetime is entirely up to your application's transaction boundaries.

| | **Latch** | **Lock** |
|---|---|---|
| Protects | A page (physical, in-memory) | A row / index record (logical) |
| Purpose | Structural integrity | ACID isolation |
| Held for | Microseconds | Until commit/rollback |
| Transaction-aware | No | Yes |
| Deadlock | Avoided by protocol, not detected | Detected; victim rolled back |
| Postgres term | Buffer lock / LWLock | Row lock, XID wait |

Traversal takes **shared (S) latches** and releases them as it descends, so any number of readers can walk the tree concurrently. Only the actual page **write** requires the **exclusive (X) latch**.

The practical takeaway for debugging: **if a query is waiting for a long time, it is waiting on a lock, not a latch.** Latch waits are invisible at application timescales. Latch contention shows up as *CPU/throughput ceiling* on a hot page, never as a multi-second stall.

## Concurrent Insert on a Unique Key — InnoDB

The scenario: two threads insert the same `upi_ref_id`, microseconds apart. This is the real shape of a duplicate UPI reference arriving twice — a client retry, or two pods handling the same callback.

**Step 1 — both threads navigate.** Each descends the unique index's B+-tree and arrives at the same **target leaf page**. So far nothing conflicts; traversal only takes S-latches.

**Step 2 — T1 writes.**

- Acquires the **X-latch** on the leaf page.
- Writes the entry (and the clustered-index row).
- **Releases the latch immediately** — microseconds later.
- The new row's hidden header now carries T1's **`trx_id`**. That stamp *is* an **implicit exclusive lock** on the row. No lock-table entry has been created.

**Step 3 — T2 arrives.**

- Briefly latches the same page just to read it. (The latch is free by now; if not, it waits microseconds.)
- Finds an entry for that exact key whose `trx_id` belongs to a **still-active transaction**.
- The unique-key duplicate check now needs a lock on that record — InnoDB's documented behaviour is that an `INSERT` hitting a duplicate takes a **shared lock on the conflicting index record**, and under REPEATABLE READ that is a next-key lock. Because T1 owns the record exclusively (implicitly), that request conflicts.
- InnoDB performs **implicit → explicit lock conversion**: it *materialises* a real lock-table entry representing T1's ownership, then queues T2 as a **waiter** on it.
- T2 is **physically suspended by the engine**. This is not a retry loop and not an application choice.

**Step 4 — resolution, decided entirely by T1.**

| T1 does | T2's outcome |
|---|---|
| `COMMIT` | Wakes, re-checks, finds a **committed** duplicate → `ERROR 1062 Duplicate entry` |
| `ROLLBACK` | Wakes, row is gone, no conflict → **insert succeeds** |

```java
// Two pods handling the same UPI callback, ~µs apart
// Pod A
tx.begin();
jdbc.update("INSERT INTO payments(upi_ref_id, status, amount) VALUES (?,?,?)",
            "UPI700", "PENDING", amount);
callBankApi();          // ❌ 400 ms of network INSIDE the transaction
tx.commit();            //    Pod B has been suspended this entire time

// Pod B — blocked on the duplicate check for the full 400 ms,
// then gets DuplicateKeyException the instant Pod A commits
```

The lesson embedded in that snippet: the wait is bounded by **T1's transaction length**, not by the insert. Any I/O you do between the insert and the commit is time a duplicate-key waiter spends suspended. `innodb_lock_wait_timeout` (default 50 s) is the only backstop, and `SHOW ENGINE INNODB STATUS` / `sys.innodb_lock_waits` is where you see it.

> 💡 **Interview**: "Two threads insert the same unique key at the same time — does the second fail immediately?" → "No. It blocks. The first thread's fresh row already carries its `trx_id`, which acts as an implicit exclusive lock; the second thread's duplicate check converts that into an explicit lock and queues behind it. It only learns its fate when the first transaction resolves — duplicate-key error on commit, success on rollback. The wait is as long as the first transaction, which is why you never do network I/O between an insert and its commit."

---

## Implicit Locks — What They Actually Are

The word "implicit" misleads people into thinking this is an optimistic mechanism. It isn't.

An implicit lock is a **pessimistic exclusive** lock — the same category as any ordinary InnoDB row lock. "Implicit" describes exactly one thing: **when InnoDB bothers to create the lock-table entry.**

- **The normal path** is eager. Touch a row in a locking read or a write, and a lock-table entry is allocated immediately.
- **For a freshly inserted row**, InnoDB creates **nothing**. The row's `trx_id` in its hidden header already identifies the owner, and no other transaction can even see the row as committed. So ownership is *derivable* rather than *recorded*.
- The entry is **materialised on demand** — only at the moment a second transaction genuinely needs to wait on that row.

The reason is pure economics: the overwhelming majority of inserted rows are never contended by anyone. A bulk load of a million rows would otherwise allocate a million lock objects that nobody ever queries. Deriving ownership from a field already in the row header makes the common case free.

What this design *explains* is the behaviour that surprises people: a plain `INSERT` colliding with an **uncommitted** duplicate **queues** rather than failing fast. There is a real exclusive lock there — it just hadn't been written down yet.

| | Implicit lock | Optimistic locking |
|---|---|---|
| Philosophy | **Pessimistic** — block the conflicting writer | Proceed, detect the conflict at the end |
| Who implements | The **engine**, invisibly | **You**, via a version column (or SSI) |
| On conflict | Waiter **suspended** | Writer **fails** and retries |
| What's deferred | Only the lock-table **bookkeeping** | The **conflict check** itself |

## Concurrent Insert on a Unique Key — PostgreSQL

Postgres reaches the same end state with different machinery. There is **no implicit-lock concept**: every tuple carries `xmin` (creating XID) and `xmax` (deleting XID) inline, and both visibility *and* waiting are derived from those.

**T1:**

1. Traverses the B-tree to the slot where the key belongs.
2. Takes a brief **buffer lock** on the page — Postgres's latch equivalent — inserts the heap tuple and the index entry, and releases it.
3. The tuple is physically present, tagged `xmin = T1`, and invisible to everyone else because T1 hasn't committed.

**T2:**

1. Traverses to the same slot and buffer-locks the page to read it.
2. Finds T1's entry for that key, with an `xmin` belonging to a **still-active** transaction.
3. `_bt_check_unique` cannot decide the outcome yet — it depends on whether T1 commits. So it calls **`XactLockTableWait(T1)`**: block until XID T1 finishes.

The crucial framing: T2 is **not** locking the row in any traditional sense. It is blocking on *"tell me when transaction 12345 ends."* In `pg_stat_activity` this shows as `wait_event_type = 'Lock'`, `wait_event = 'transactionid'`.

**Resolution:**

| T1 does | T2's outcome |
|---|---|
| `COMMIT` | `ERROR: duplicate key value violates unique constraint "idx_upi_ref"` |
| `ROLLBACK` | Tuple is dead → re-check passes → **insert succeeds** |

⚠️ **A precision worth carrying, because it's commonly mis-stated:** *speculative insertion* — with its speculative token and the separate `SpeculativeInsertionWait` event — is the machinery behind **`INSERT … ON CONFLICT`**. A **plain** `INSERT` does not use it; it inserts, then waits on the conflicting transaction's XID. The distinction matters if an interviewer pushes on how upsert avoids spurious errors.

Which is also why Postgres has a genuinely first-class upsert, and it's the right tool for an idempotency key:

```sql
-- ✅ Idempotent insert, no duplicate-key exception to catch
INSERT INTO payments(upi_ref_id, status, amount)
VALUES ('UPI700', 'PENDING', 400.00)
ON CONFLICT (upi_ref_id) DO NOTHING;

-- ❌ Check-then-insert: the gap between the two statements is the race
SELECT 1 FROM payments WHERE upi_ref_id = 'UPI700';
INSERT INTO payments … ;
```

## InnoDB vs PostgreSQL — Same Outcome, Different Plumbing

| | InnoDB | PostgreSQL |
|---|---|---|
| Physical write protection | Page **latch** | **Buffer lock** — same idea |
| What T1 holds after inserting | **Implicit lock** via `trx_id` in the row header | Nothing extra — just `xmin` on the tuple |
| What T2 waits on | The implicit lock, **converted to an explicit** record lock | T1's **XID**, directly, via `XactLockTableWait` |
| Old row versions live in | **Undo log** (reconstructed on demand) | **The heap** (old tuples, until `VACUUM`) |
| Upsert primitive | `INSERT … ON DUPLICATE KEY UPDATE`, `INSERT IGNORE` | `INSERT … ON CONFLICT` |
| Observability | `SHOW ENGINE INNODB STATUS`, `sys.innodb_lock_waits` | `pg_stat_activity` (`wait_event = 'transactionid'`), `pg_locks` |
| Net result | Wait → duplicate error or success, by commit/rollback | **Identical** |

> **The one-liner if asked "what's the actual difference then?"**
> "The outcome is identical — the second thread waits for the first transaction to resolve. InnoDB gets there by converting an implicit row lock into an explicit one; Postgres gets there by having the waiter block directly on the inserting transaction's XID. Same guarantee, different internal plumbing."

## Same Page, Different Key — Pure Latch Contention

A separate scenario that people conflate with the duplicate-key case, and the distinction is exactly what "latch vs lock" buys you.

Latches are **page-level, not row-level**. So if T1 inserts key `A` and T2 inserts key `B`, and both keys belong on the **same leaf page**, T2 **does** wait — but only for the **X-latch**, and only for as long as T1's physical page write takes. Nanoseconds to microseconds. It has nothing to do with uniqueness, transaction length, or isolation level: it is purely "two threads cannot write the same memory page at once."

```text
Same key, T1 uncommitted        →  LOCK wait   →  as long as T1's transaction (unbounded)
Same page, different keys       →  LATCH wait  →  microseconds
Different pages                 →  no wait
```

Two refinements worth having ready:

**Page splits.** If the target leaf is full, the insert must split it — allocate a new page, redistribute entries, and **insert a new separator key into the parent**, which means latching the parent too (and recursively, if the parent is also full). The contention window widens briefly and covers more of the tree. This is rare per-insert but is precisely the case Postgres's B-link right-links were designed for: a concurrent reader that lands on a split page just moves right instead of blocking.

**Rightmost-page contention.** With a monotonically increasing PK (`AUTO_INCREMENT`, a sequence, a timestamp prefix), *every* insert targets the same last leaf page. Every concurrent inserter therefore serialises on that one page's X-latch. This is the real, measurable ceiling behind "insert hot spot" at high write rates — and note that it is a **latch** ceiling, so it caps throughput rather than producing visible multi-second stalls. It's the counterweight to "always use a sequential PK": sequential is great for the buffer pool and terrible for page-latch parallelism at extreme rates.

## Non-Unique Indexes — How Duplicates Are Ordered

A **non-unique** index — a plain `CREATE INDEX` — explicitly permits many rows to share a key. But a B+-tree is a **totally ordered** structure: for equal keys it still needs a tiebreaker, both to decide relative position and to be able to locate one specific entry (to delete it, for instance).

**InnoDB appends the primary key** to every secondary-index entry, whether or not you asked for it. Every entry is therefore internally unique:

```text
CREATE INDEX idx_status ON payments(status);   -- non-unique, many duplicates

leaf entries (conceptually):
('PENDING', pk=102)
('PENDING', pk=108)
('SUCCESS', pk=101)
('SUCCESS', pk=105)
('SUCCESS', pk=110)
```

All `'SUCCESS'` entries sit together, ordered internally by the hidden PK tiebreaker. This is another reason InnoDB *needs* a primary key concept even when you never declare one — it is the universal disambiguator baked into every index.

**Postgres uses the TID**, which is unique by construction, so duplicates are naturally distinguishable with nothing PK-related involved:

```text
('PENDING', TID=(3,2))
('SUCCESS', TID=(3,1))
('SUCCESS', TID=(3,4))
('SUCCESS', TID=(7,2))
```

Either way, `WHERE status = 'SUCCESS'` finds the **first** matching leaf entry, then **walks right along the linked leaves**, collecting matches until the key changes. In InnoDB, fetching the full row costs the double lookup **once per matching row**.

**And this is where the contrast with the unique index lands.** For a `UNIQUE` index, insertion does:

1. Traverse to the target leaf.
2. **Check whether an entry with this exact key already exists** — committed or in-flight.
3. If in-flight → the wait we traced above (implicit lock in InnoDB, XID wait in Postgres). If committed → immediate duplicate error.
4. If absent → insert.

For a **non-unique** index, **step 2 does not exist.** There is no conflict check, so there is no duplicate-related waiting at all — the entry just joins its duplicate cluster. Any locking you observe on a non-unique index is ordinary transactional row locking for whatever the statement is doing (`SELECT … FOR UPDATE`, `UPDATE`, `DELETE`), never a consequence of sameness.

> **One-liner**: "Non-unique indexes handle duplicates with an internal tiebreaker — InnoDB silently appends the PK to every secondary entry, Postgres uses the TID — so equal keys still have a well-defined total order and can be walked via the linked leaves. No conflict check and no locking happens *because of* duplication; that only applies to unique indexes."

## Low Cardinality — When the Index Stops Helping

The duplicate cluster has a failure mode. If one value owns most of the table — `status = 'SUCCESS'` on 90% of a payments table — that cluster of leaf entries spans a very large number of pages. A lookup for it must walk all of them, and on InnoDB pay the double lookup for every row it returns.

At that point the index is worse than useless: it's a **random-access** path over most of the table, while a sequential scan reads the same data in physical order at a fraction of the per-row cost. The planner knows this and will typically **abandon the index** and full-scan — which is the real content behind the folklore "indexes don't work on low-cardinality columns."

What actually works:

```sql
-- ❌ Useless on its own: two or three distinct values across millions of rows
CREATE INDEX idx_status ON payments(status);

-- ✅ Composite, low-cardinality column leading, selective column second
CREATE INDEX idx_status_created ON payments(status, created_at);
SELECT * FROM payments
 WHERE status = 'PENDING' AND created_at < now() - interval '5 minutes'
 ORDER BY created_at LIMIT 500;      -- the reconciliation worklist query

-- ✅ Postgres partial index: indexes ONLY the tiny hot set
CREATE INDEX idx_pending ON payments(created_at) WHERE status = 'PENDING';
```

The payments shape makes the point cleanly. `status` has three values, and `SUCCESS` dominates — so an index on `status` alone never earns its keep. But `PENDING` is a tiny, permanently hot set that a reconciliation worker polls constantly. Either put `status` first in a composite index so the second column adds selectivity within the cluster, or index the predicate itself with a partial index so the index stays small enough to remain fully cached. MySQL has no partial indexes; the composite is the portable answer.

## MVCC Snapshots — What Isolation Level Actually Changes

[[9. Database Concurrency]] covers MVCC's mechanics. What belongs here is the part that is regularly stated too strongly, because the interviewer's follow-up is always "under which isolation level?"

Every row keeps **multiple versions**, tagged with the transaction that created or deleted it. The storage differs:

- **Postgres** keeps old versions **in the heap** — literally extra tuples with `xmin` / `xmax` set — which is why it needs `VACUUM`.
- **InnoDB** does *not* keep old row copies in the table. It stores the change in the **undo log** and **reconstructs** the older version on demand.

A reader is handed the version visible **as of its snapshot**. The isolation level decides *when the snapshot is taken*, and that single fact drives everything:

| | READ COMMITTED | REPEATABLE READ / SERIALIZABLE |
|---|---|---|
| Snapshot | **Fresh per statement** | **Fixed once per transaction** |
| Re-read after another txn commits | Sees the **new** value | Still sees the **old** value |
| Default in | **PostgreSQL**, Oracle | **MySQL / InnoDB** |

```sql
-- T1                                  -- T2
BEGIN;                                 BEGIN;
SELECT balance;   -- 1000
                                       UPDATE account SET balance = 300;
SELECT balance;   -- 1000  (T2 uncommitted: invisible at ANY level)
                                       COMMIT;
SELECT balance;   -- REPEATABLE READ  → 1000   ← the RR guarantee
                  -- READ COMMITTED   →  300   ← fresh snapshot per statement
```

So the common claim "T1 still sees 1000 after T2 commits" is true **only** under RR/SERIALIZABLE, and only for the rest of T1's transaction. Under READ COMMITTED — the default in Postgres — the next statement sees 300.

The second half is more important and more often missed: **writes never use the snapshot.** `UPDATE`, `DELETE`, and `SELECT … FOR UPDATE` perform a **current read** — they read the **latest committed** version and take an exclusive lock, regardless of what the transaction's snapshot says. That's why `UPDATE account SET balance = balance - 500` is safe: the engine recomputes from the current row, not from your stale read. The vulnerable pattern is always the one where **your application** computed the new absolute value from an earlier `SELECT`.

## First Committer Wins vs Last Writer Wins

Now the part that is genuinely engine-specific, and where "the DB aborts the second writer" is stated far too confidently.

**PostgreSQL at REPEATABLE READ or SERIALIZABLE.** T1 tries to update a row that another transaction modified and committed **after** T1's snapshot was taken. Postgres will not silently apply a write derived from a version T1 can no longer legally see, so it aborts:

```text
ERROR: could not serialize access due to concurrent update
```

The application must catch this and **retry the whole transaction from the read**. This is **first committer wins**.

**PostgreSQL at SERIALIZABLE** adds a second, broader detector: **SSI** (Serializable Snapshot Isolation) tracks read/write dependencies with predicate (SIREAD) locks and aborts a transaction when the dependency graph would admit a cycle — catching anomalies like write skew that no row-level conflict would reveal:

```text
ERROR: could not serialize access due to read/write dependencies among transactions
```

**InnoDB at REPEATABLE READ.** No such abort. T1's `UPDATE` performs a current read: it **blocks** on T2's row lock, and once T2 commits, it proceeds against the **latest committed** row. No error is raised. This is **last writer wins**, and it is exactly why MySQL's confidently-named REPEATABLE READ still permits the lost update while Postgres's REPEATABLE READ does not — the full treatment is in [[12. Lost Updates & High-Contention Architectures]].

| | Postgres RR / SERIALIZABLE | InnoDB RR | Either engine, READ COMMITTED |
|---|---|---|---|
| Conflicting write | **Aborted** with a serialization error | **Blocks**, then applies | Proceeds against latest committed |
| Winner | **First committer** | **Last writer** | **Last writer** |
| App must | Catch and **retry** | Guard it yourself | Guard it yourself |

One term to keep in its lane: **semi-consistent read** is a narrow InnoDB optimisation for `UPDATE` — it lets the statement look at the latest committed version of a row to decide the row won't match the `WHERE` anyway and skip waiting on it — and it applies at READ COMMITTED (or with the old `innodb_locks_unsafe_for_binlog`). It is **not** the mechanism behind any of the above, and citing it as such is the kind of detail an interviewer will catch.

## Redis Lock in Front of the DB Lock

A distributed lock in Redis is frequently proposed as a *replacement* for a database lock. That is wrong, and it's a correctness error, not a style preference.

**The rule: the Redis lock is always in *addition* to the DB lock, never instead of it.**

```java
String token = UUID.randomUUID().toString();
// NX = only if absent, EX 5 = auto-expire after 5s
boolean got = redis.set("lock:account:123", token, SetParams.setParams().nx().ex(5));

if (!got) {
    // Someone else owns this account right now — do NOT touch the DB
    throw new RetryableException("account busy, retry");   // ✅ fail fast, no connection burned
}
try {
    tx.begin();
    // The DB lock is STILL the correctness guarantee
    var acct = jdbc.query("SELECT * FROM account WHERE id = ? FOR UPDATE", 123);
    jdbc.update("UPDATE account SET balance = balance - ? WHERE id = ? AND balance >= ?", …);
    tx.commit();
} finally {
    releaseIfMine("lock:account:123", token);   // Lua compare-and-delete
}
```

```lua
-- Release safely: only delete a lock that is still MINE (atomic in Redis)
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
end
return 0
```

**What it actually buys you: database connections.**

Without it, every concurrent request for a hot account reaches the DB and queues on the row lock. Each waiting request **holds an open, idle, pooled connection** for the entire wait. A thousand requests for one hot merchant account can exhaust a 50-connection pool — and then **unrelated** accounts' requests start failing too. The hot row's contention has become a whole-service outage.

With Redis in front, exactly **one** request per account reaches the DB. Everyone else is rejected by a single in-memory operation costing microseconds, long before a connection is checked out. Redis is a bouncer deciding who may walk up to the DB; the DB lock is still the thing keeping the data correct.

**Two things you must not skip:**

1. **TTL (`EX`).** If the process holding the lock crashes, a TTL-less lock is stuck forever and that account is permanently unprocessable. TTL is the safety net — set it comfortably above your worst-case transaction time.
2. **Unique token + compare-and-delete.** If your TTL expires mid-work, someone else legitimately acquires the lock. A blind `DEL` on the way out would release *their* lock. Compare the token first, atomically in Lua.

And the honest framing, which is the actual interview point: **this is resource protection, not correctness.** The DB was already correct on its own. Redis makes the system cheaper and more resilient under contention; it adds no safety guarantee — a process can be paused past its TTL and still believe it holds the lock, which is why safety needs **fencing tokens** at the resource, not a lock in Redis. See [[10. Distributed Concurrency]].

> 💡 **Interview**: "Why not just use a Redis distributed lock instead of `SELECT … FOR UPDATE`?" → "Because a Redis lock can't guarantee mutual exclusion — a GC pause past the TTL and two holders both think they own it. It's a cheap admission gate that stops requests from piling onto DB connections while blocked, which is a real and valuable win at high contention. The database lock stays underneath as the correctness guarantee."

## Optimistic Locking — Application-Level vs Engine-Level

Two distinct mechanisms share one philosophy — *don't block, detect the conflict late* — and they are not the same technique layered twice.

### A. Version column — application-level, and by far the most common

You implement it with nothing more than a conditional `UPDATE`:

```sql
-- You READ version 5 earlier, computed a new balance in application code
UPDATE account
   SET balance = 300, version = version + 1
 WHERE id = 123 AND version = 5;      -- ← the version you read

-- rowsAffected == 1 → success, nobody touched it since your read
-- rowsAffected == 0 → someone did (version moved) → YOUR CODE retries
```

The conflict detection is literally `rowsAffected == 0`. The database has **no idea** this is "optimistic locking" — to the engine it's an ordinary conditional update that matched no rows. The whole concept lives in how you shaped the query and how your application reacts. An `updated_at` timestamp works the same way.

In Java this is almost always Hibernate doing it for you:

```java
@Entity
public class Account {
    @Id private Long id;
    private BigDecimal balance;

    @Version                      // Hibernate manages this column itself
    private Long version;
}
// Every UPDATE Hibernate generates becomes:
//   UPDATE account SET balance = ?, version = version + 1 WHERE id = ? AND version = ?
// 0 rows affected → OptimisticLockException, thrown for you
```

### B. SERIALIZABLE isolation — engine-level

Here the **engine** detects the conflict with no version column and no cooperation from your query. Postgres SERIALIZABLE (SSI) tracks read/write dependencies between concurrent transactions and, at commit time, aborts one with `could not serialize access due to read/write dependencies among transactions`. This is optimistic in spirit — transactions never block each other, conflicts surface only at the end — but the machinery is inside the database and your app's only job is to catch the error and retry.

| | Version column | SERIALIZABLE |
|---|---|---|
| Detector | Your code, on `rowsAffected` | The engine |
| Scope | The specific rows you guard | Every statement in the transaction |
| Schema | Needs a `version` / `updated_at` column | None |
| Portability | Any database | Postgres SSI; MySQL's SERIALIZABLE is lock-based, not SSI |
| Cost | ~zero | Significant, transaction-wide; plus retries everywhere |

The version-column pattern dominates real systems because it's simple, portable, and scoped to exactly the rows that need it. SERIALIZABLE is what you reach for when you need airtight correctness across complex multi-statement transactions (write skew, invariants spanning rows) and are willing to implement retry handling everywhere.

**And the choice of optimistic vs pessimistic is entirely about contention, not preference:**

- **High read, low write, conflicts rare** → **optimistic**. Pessimistic locking makes every would-be updater block even though 99% of the time there was no conflict to avoid. Optimistic pays nothing in the common case.
- **Same hot row contended constantly** → **pessimistic**, or stop doing read-modify-write at all. Under heavy contention optimistic degenerates: attempts fail, retry, collide again, and you've converted contention into wasted work plus a fat latency tail. That's the hot-wallet case, and the answer there isn't a better lock — it's a different shape (see [[12. Lost Updates & High-Contention Architectures]]).

> **One-liner**: "Optimistic locking is a philosophy — don't block, detect conflicts late. It's usually implemented at the application level with a version or timestamp column and a conditional `UPDATE`, but some databases offer it natively at the isolation level, like Postgres SERIALIZABLE, where the engine detects the conflict instead of your code checking a version."

## Where Optimistic Locking Is Actually Used

Concrete systems, including one from the payments domain.

**1. E-commerce inventory.** Thousands of users view a product page constantly; two people checking out the *same* item in the same instant is comparatively rare.

```sql
-- Product: stock = 5, version = 12. Users A and B both read that.
-- A checks out
UPDATE products SET stock = 4, version = 13 WHERE id = 'case_1' AND version = 12;  -- 1 row → ✅
-- B checks out moments later, still holding version 12
UPDATE products SET stock = 4, version = 13 WHERE id = 'case_1' AND version = 12;  -- 0 rows → ❌
-- → app re-reads (stock is now 4) and retries or tells B "stock changed"
```

Row-locking every product on every page view would be absurd; optimistic locking costs something only when a real conflict occurs.

**2. JPA / Hibernate `@Version`.** Genuinely everywhere in enterprise Java. Most codebases using it don't call it "optimistic locking" — but that's exactly what it is, and it's probably the single most common real-world implementation in backend Java systems.

**3. Reconciliation / retry jobs — the payments case.** A background worker polls NPCI or the bank and moves local `status` from `PENDING` to `SUCCESS`/`FAILED`. Multiple workers may run concurrently, or the same job may be retried while the first attempt is still in flight:

```sql
UPDATE payments
   SET status = 'SUCCESS', settled_at = now()
 WHERE txn_id = 'UPI700' AND status = 'PENDING';    -- ✅ state IS the guard

-- rowsAffected == 1 → I own this transition; safe to credit the merchant + fire the webhook
-- rowsAffected == 0 → another worker already transitioned it; do nothing, don't double-credit
```

This is optimistic locking **with no version column at all** — the **business state** is the conflict check. It's the lightest and most common form of the pattern in payments, and it's what stops a duplicate reconciliation run from double-crediting a merchant or sending two webhooks.

**4. Collaborative editing (Google Docs / Notion, conceptually).** Nobody can lock the document while one person types — that would make co-editing unusable. Edits apply optimistically against the client's last-known version, and when versions diverge, real systems **merge** via Operational Transformation or CRDTs rather than rejecting. Fancier conflict resolution, same root philosophy: don't lock, detect divergence, reconcile.

**5. Ticket / seat booking (IRCTC, BookMyShow) — a hybrid, and the best example to raise.** Seat browsing and temporary holds are optimistic or short-TTL Redis holds, because many people must be able to look at once. **Final payment confirmation** frequently switches to **pessimistic** — a row lock or a distributed lock on that seat for a few seconds — because double-booking a *paid* seat and having to cancel someone's booking is far worse than making a user wait 200 ms. It shows you understand this is chosen **per operation**, not per system.

**The pattern across all five:** optimistic locking fits wherever the same record being written by two writers at once is the **exception**, while reads of it are frequent. The detector is either an explicit version column or an implicit state guard (`WHERE status = 'PENDING'`), and the application's job never changes: **check `rowsAffected`, retry or surface a conflict on 0.**

## The End-to-End Mental Model

One insert, all the way down. This is the diagram to reproduce on a whiteboard when someone asks what happens when two requests insert the same idempotency key.

```text
INSERT INTO payments(upi_ref_id, …)   -- unique index on upi_ref_id
   │
   ├─ traverse B+-tree (S-latches, released as you descend)
   │
   ├─ X-LATCH target leaf page ─────── µs, physical ──────► other writers on this
   │     write entry; split if full (parent latched too)     page wait here, briefly
   │     release latch
   │
   ├─ UNIQUE index? ── no ──► done. duplicates just cluster by PK/TID tiebreaker
   │        │
   │       yes
   │        ▼
   │   existing entry for this key?
   │        ├─ committed     ──► duplicate key error, immediately
   │        ├─ uncommitted   ──► WAIT  (InnoDB: implicit→explicit lock
   │        │                          Postgres: XactLockTableWait on XID)
   │        │                    bounded by the OTHER TXN's lifetime
   │        │                      → it commits    = duplicate error
   │        │                      → it rolls back = success
   │        └─ none          ──► insert proceeds
   │
   └─ row now carries trx_id / xmin = me  ► implicit ownership until I resolve
```

Four things fall out of it, in the order they matter:

**1. Classify the wait before you tune anything.** *Latch = physical, microseconds, page-scoped. Lock = logical, until commit, row-scoped.* Every wait you can actually observe from the application is a lock wait. A latch problem never looks like a slow query — it looks like a throughput ceiling that won't move no matter how many threads you add.

**2. Uniqueness is what creates waiting on insert.** A non-unique index has no conflict check, so two inserts of the same value never wait on each other. The moment you declare `UNIQUE`, every insert of an already-in-flight key becomes a queue behind someone else's transaction.

**3. Transaction length is the variable you control.** The engine's part of the duplicate-key wait is microseconds. Everything else is *your* transaction — the bank call, the retry, the log flush you left between the insert and the commit. Shorten the transaction and the contention mostly evaporates.

```java
// ❌ Duplicate-key waiters are suspended for the whole bank call
tx.begin();  insert(payment);  callBankApi();  tx.commit();

// ✅ Commit the row first; do the slow, external work outside the transaction
tx.begin();  insert(payment);  tx.commit();
callBankApi();          // now nobody is blocked on my trx_id
```

**4. When contention is real, remove it structurally rather than locking better.** Use the engine's upsert as the idempotency primitive instead of check-then-insert (`ON CONFLICT DO NOTHING` / `INSERT … ON DUPLICATE KEY UPDATE`) — one statement, no race window, no exception to catch. Avoid a fully random PK in InnoDB because every secondary index carries a copy of it; but watch the rightmost leaf page if the PK is purely monotonic and insert rates are extreme. And once contention lands on a single *entity* rather than a single statement, you're out of index-internals territory and into the architectures in [[12. Lost Updates & High-Contention Architectures]] — append-only ledgers, partitioned queues, sharded balances. **The fix is never a better lock.**

## Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| Is a DB index a binary tree? | No — a **B+-tree**. Each node is a page holding hundreds of keys, so even a billion rows is 3–4 levels deep. |
| B-tree vs B+-tree? | B-tree can store data in internal nodes and allows early termination. B+-tree stores data **only in leaves** and **links the leaves**, making range scans a linear walk. |
| Which does Postgres use? | A B+-tree, despite the `btree` name — specifically the **Lehman & Yao B-link** variant with right-sibling pointers at every level for high-concurrency traversal. |
| Real difference between InnoDB and Postgres indexes? | Not the tree — the **table storage**. InnoDB is **clustered** (the table *is* the PK tree, rows in the leaves); Postgres is a **heap** with indexes holding `key + TID`. |
| What is the double lookup? | InnoDB secondary index → PK value → **second traversal** of the clustered index to fetch the row. Avoided by a **covering index**. |
| Postgres equivalent shortcut? | **Index-only scan** — but only when the visibility map says the page is all-visible, since MVCC info lives in the heap tuple. |
| Why must an InnoDB PK be short? | Every secondary-index leaf stores a **copy of the PK**, so a large PK bloats every index. Random PKs also scatter inserts and cause splits. |
| Postgres's equivalent cost? | **MVCC bloat** — every `UPDATE` writes a new tuple and leaves a dead one, until `VACUUM`. Mitigated by **HOT** updates when no indexed column changed. |
| Latch vs lock? | **Latch** = page-level, physical, µs, not transaction-aware, no deadlock detection. **Lock** = row-level, logical, held until commit, deadlock-detected. |
| Two threads insert the same unique key — does the second fail instantly? | **No, it blocks.** It waits for the first transaction to commit or roll back. |
| What is it waiting on, exactly? | InnoDB: the first txn's **implicit lock**, materialised into an **explicit** record lock. Postgres: the first txn's **XID**, via `XactLockTableWait`. |
| Is InnoDB's implicit lock optimistic? | **No — pessimistic.** "Implicit" only describes *when the lock-table entry is created*; the lock itself is a normal exclusive row lock. |
| Why defer the lock entry at all? | Most inserted rows are never contended, so the row's `trx_id` implying ownership makes the common case free. |
| Outcome when the first txn commits? | Duplicate key error for the waiter. On rollback → the insert **succeeds**. |
| How long can that wait be? | As long as the **first transaction**, not the insert — which is why you never do network I/O between an insert and its commit. |
| Same page, different keys — is there a wait? | Yes, but only for the **X-latch** — microseconds, unrelated to uniqueness or transaction length. |
| What makes a page split more expensive? | It must latch the **parent** too, to insert the separator key — briefly widening the contention window. |
| Why is a monotonic PK a contention risk? | Every insert targets the same **rightmost leaf page**, so they all serialise on its latch. A throughput ceiling, not a stall. |
| How do non-unique indexes order duplicates? | With a hidden tiebreaker — InnoDB appends the **PK**, Postgres uses the **TID**. |
| Do non-unique index inserts ever wait on each other? | **No** — there's no conflict check at all. Any locking is ordinary row locking, not caused by duplication. |
| Why are indexes useless on low-cardinality columns? | The duplicate cluster spans most of the table, so the index becomes random access over nearly everything — the planner prefers a sequential scan. |
| Fix for a low-cardinality predicate? | Lead a **composite** index with it (`(status, created_at)`), or a Postgres **partial index** (`WHERE status = 'PENDING'`). |
| Does a transaction always keep seeing its original snapshot? | Only under **REPEATABLE READ / SERIALIZABLE**. READ COMMITTED takes a **fresh snapshot per statement**. |
| Do writes use the snapshot? | **Never.** `UPDATE`/`DELETE`/`FOR UPDATE` do a **current read** — latest committed version + X lock. |
| Does the DB abort a conflicting writer? | Engine-specific. **Postgres RR/SERIALIZABLE**: yes — `could not serialize access due to concurrent update` (first committer wins). **InnoDB RR**: no — it blocks then applies (last writer wins). |
| What extra thing does Postgres SERIALIZABLE catch? | Read/write **dependency cycles** via predicate/SIREAD locks — e.g. write skew that no row conflict would reveal. |
| Redis lock instead of a DB lock? | Never *instead* — always **in addition**. Redis is an admission gate that saves DB connections; the DB lock is the correctness guarantee. |
| What does Redis in front actually save? | Connection-pool exhaustion. Blocked requests each hold an idle pooled connection; failing fast in Redis keeps a hot row from taking down unrelated traffic. |
| Two mandatory parts of a Redis lock? | A **TTL** (so a crashed holder doesn't wedge the key forever) and a **unique token + Lua compare-and-delete** (so you never release someone else's lock). |
| Is optimistic locking app-level or DB-level? | Both, as two different mechanisms: a **version column** where your code checks `rowsAffected`, or **SERIALIZABLE** where the engine detects the conflict. |
| Most common real-world implementation? | Hibernate `@Version` → `OptimisticLockException` on 0 rows affected. |
| Optimistic locking without a version column? | Use the **business state** as the guard: `WHERE txn_id = ? AND status = 'PENDING'`. Standard in reconciliation jobs. |
| When is optimistic the wrong choice? | On a constantly contended hot row — every attempt fails and retries, turning contention into wasted work and tail latency. |

## SDE-2 Interview Priority Checklist

### Must Know (100%)

- A DB index is a **B+-tree**, not a binary tree; page-sized nodes, 3–4 levels deep, linked leaves
- **B-tree vs B+-tree** — data in leaves only, linked leaves, no early termination
- **Clustered (InnoDB) vs heap (Postgres)** storage, and that this is the real difference between the engines
- The **double lookup** on an InnoDB secondary index, and how a **covering index** eliminates it
- Why an InnoDB primary key should be **short and roughly sequential**
- **Latch vs lock**: physical/µs/page vs logical/until-commit/row — and that every long wait is a lock wait
- Two threads inserting the same unique key: the second **blocks** until the first commits or rolls back, then gets a duplicate error or succeeds
- Keeping transactions short, because a duplicate-key waiter is hostage to the other transaction's length
- **Unique vs non-unique** index behaviour: only unique indexes do a conflict check, so only they wait on "sameness"
- Why indexes are ineffective on **low-cardinality** columns, and the composite/partial-index fixes
- **Per-statement vs per-transaction snapshots**, and that writes always do a **current read**
- **First committer wins (Postgres RR)** vs **last writer wins (InnoDB RR)** — never state it without naming the engine
- Choosing **optimistic vs pessimistic** by contention level, and the `rowsAffected == 0` retry contract
- A **Redis lock is additive**, never a replacement — plus TTL and Lua compare-and-delete

### Nice To Know

- **Implicit → explicit** lock conversion in InnoDB, and why the lock entry is created lazily
- `XactLockTableWait`, and reading `wait_event = 'transactionid'` in `pg_stat_activity`
- InnoDB storing a **PK copy** in every secondary-index entry — the mechanism behind PK-size bloat *and* duplicate ordering
- Postgres **MVCC bloat**, `VACUUM`, and **HOT** updates avoiding index writes
- **Index-only scans** and their dependence on the visibility map
- InnoDB rebuilding old versions from the **undo log** vs Postgres keeping old tuples in the heap
- **Composite** vs **partial** indexes, and that MySQL has no partial indexes
- Hibernate `@Version` / `OptimisticLockException`, and **state-as-guard** optimistic updates
- Upsert primitives as the correct idempotency tool: `ON CONFLICT DO NOTHING` vs check-then-insert

### Advanced

- **Lehman & Yao B-link tree** right-sibling pointers at every level, and moving right instead of latching upward
- **Page splits** latching the parent, and the recursive case
- **Rightmost-page insert contention** under a monotonic PK — a latch-level throughput ceiling
- **Speculative insertion** (`ON CONFLICT`, `SpeculativeInsertionWait`) vs a plain insert's XID wait
- **SSI** predicate/SIREAD locks and `could not serialize access due to read/write dependencies among transactions`
- **Semi-consistent reads** in InnoDB, and why they are *not* the lost-update mechanism
- The **shared (next-key) lock** a duplicate-key `INSERT` takes on the conflicting index record
- Why a Redis lock can't provide mutual exclusion, and **fencing tokens** at the resource
