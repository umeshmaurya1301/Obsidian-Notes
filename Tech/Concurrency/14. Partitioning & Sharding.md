# Partitioning & Sharding

---

Continues the database thread: §9 ([[9. Database Concurrency]]) → §12 ([[12. Lost Updates & High-Contention Architectures]]) → §13 ([[13. Index & Lock Internals]]). Those notes make **one table on one node** correct and fast. This one is about what you do when that table stops fitting — splitting it **within** a node (partitioning) or **across** nodes (sharding), and the read-model pattern that avoids having to choose.

> [!info] The through-line of this note
> One chain, read in order:
>
> 1. **Partitioning ≠ sharding** (§1). Partitioning splits one table into sub-tables **on one node**, transparently. Sharding splits rows across **many nodes** and your app must route. One reorganises files; the other adds hardware.
> 2. Partitioning is fast because of **partition pruning** (§2) — the optimizer eliminates partitions the predicate can't match. The wins, ranked honestly: fewer pages, better buffer-pool residency, and only *modestly* shallower trees (§3).
> 3. The trap: indexes are **local per partition** (§4). Any query without the partition key searches **every** partition and is **slower than unpartitioned**. And in MySQL/Postgres every unique key **must include the partition column** — which can silently destroy an idempotency guarantee (§5).
> 4. The reason people actually partition is often **retention** (§6): `DROP PARTITION` is a file unlink; the equivalent `DELETE` is hours of undo, locks and replication lag. What partitioning does *not* fix is **write contention** (§7) — date partitioning concentrates it.
> 5. So **partition by the column your dominant query filters on** (§8), and when that conflicts, pick from four real alternatives (§9) — or don't partition at all (§10).
> 6. When two access patterns genuinely conflict, stop forcing one table to serve both: a **CQRS read model** (§11), synced by **CDC** (§12), with strict discipline about eventual consistency and lag (§13).
> 7. Then sharding: what it buys (§14), the six cases where it's right (§15), the six where it's actively wrong (§16), shard-key schemes and rebalancing (§17), and the cost you can't avoid — **cross-shard transactions** (§18). Applied to the payments domain (§19), and the escalation ladder that tells you when you've earned it (§20).
>
> One line to anchor everything: **partitioning and sharding both help exactly one query pattern — the one that filters on the key you chose — and make every other pattern worse.**

---

## Short Notes

---

### 1. Partitioning vs Sharding

| | **Partitioning** | **Sharding** |
|---|---|---|
| Scope | One database node | **Multiple** nodes |
| Managed by | The DB engine, **transparently** | Your **app** or a routing layer |
| Query view | One logical table | App must route to the right node |
| Solves | Table size, scan cost, maintenance | **Total capacity**, cross-node scale |
| Adds | Almost no ops burden | Routing, rebalancing, N× ops |

- Partitioning splits **one table into N physical sub-tables** on the same server — the app still queries `ledger_entries` and never sees them
- Sharding adds **machines**: more total CPU, RAM and disk I/O. Partitioning only reorganises files on the hardware you already have
- Partitioning is a **query-optimisation and maintenance** tool; sharding is a **capacity** tool
- They compose: a shard can itself be partitioned by date

---

### 2. Partition Pruning — the Mechanism

```sql
PARTITION BY RANGE (TO_DAYS(created_at)) (
    PARTITION p2026_08 VALUES LESS THAN (TO_DAYS('2026-09-01')),
    PARTITION p2026_09 VALUES LESS THAN (TO_DAYS('2026-10-01')),
    PARTITION pmax     VALUES LESS THAN MAXVALUE
);

SELECT * FROM ledger_entries
 WHERE created_at >= '2026-08-01' AND created_at < '2026-09-01'
   AND account_id = 'POOL_001';
```

- The optimizer compares the `created_at` predicate against each partition's **range boundaries** and opens only the ones that can match
- `EXPLAIN` shows it directly — MySQL prints a `partitions:` column: `partitions: p2026_08` ← one, not five
- Pruning happens **before** any index work: ~80% of the table eliminated for free
- Postgres prunes at **plan time**, and also at **execution time** (PG 11+) for prepared/parameterised queries where the value isn't known until runtime

---

### 3. Why Partitioning Is Actually Faster

Three benefits, and they are **not** equally important:

1. **Fewer pages scanned** (biggest win, range queries) — one contiguous ~83M-row partition instead of scattered pages across a 1B-row structure
2. **Smaller indexes stay in the buffer pool** (the underrated win) — each partition has its **own** B+ tree, so only recent months' index pages stay hot; one giant index makes all history compete for cache
3. **Shallower trees** (real, but modest) — at ~500 entries/16 KB page: `log₅₀₀(10⁹) ≈ 3.4` → **4 levels**; `log₅₀₀(8.3×10⁷) ≈ 2.9` → **3 levels**. One level = ~25% fewer I/Os per point lookup

> Lead with buffer-pool residency and page-scan reduction, not tree height — blog posts overstate the tree-depth win, and knowing the numbers is the differentiator.

---

### 4. Local Indexes — the Trap

- MySQL and Postgres both use **local indexes**: every partition has its **own independent index**. There is **no global index** spanning partitions
- A query with no partition-key predicate **cannot prune** and must search **every partition's index**:

```sql
SELECT * FROM ledger_entries WHERE txn_id = 'UPI700';   -- no created_at filter
-- EXPLAIN partitions: p2026_06,p2026_07,p2026_08,p2026_09,pmax   ← all of them
```

- 24 months of partitions = **24 index traversals** instead of 1 — **slower than the unpartitioned table**
- **The rule**: partitioning helps only queries that filter on the partition key; everything else pays an N-partition penalty

---

### 5. Unique Keys Must Include the Partition Key

- **MySQL**: every unique index — **including the primary key** — must contain **all columns of the partitioning expression**. Postgres declarative partitioning has the same restriction
- So on a table partitioned by `created_at`, `UNIQUE KEY uk_idem (idem_key)` is **rejected**; you're forced into `UNIQUE KEY uk_idem (idem_key, created_at)`
- That no longer guarantees `idem_key` is **globally** unique — the same key on a different date lands in a different partition and **will not conflict**
- ⚠️ Your duplicate-key protection ([[13. Index & Lock Internals]]) silently stops protecting you — no error, just a second row
- **Never date-partition an `idempotency_keys` table.** Leave it unpartitioned with a cleanup job, or partition by `HASH(idem_key)` so the unique constraint can legitimately include the partition column

---

### 6. Retention & Archival — the Real Reason to Partition

```sql
ALTER TABLE ledger_entries DROP PARTITION p2025_09;              -- ✅ milliseconds
DELETE FROM ledger_entries WHERE created_at < '2025-10-01';      -- ❌ hours
```

- The `DELETE` scans and deletes millions of rows, generates enormous **undo/WAL** volume, holds locks, blows out **replica lag**, and leaves the table bloated → then needs `OPTIMIZE TABLE` / `VACUUM FULL`
- `DROP PARTITION` is a **file unlink + catalog update**. Postgres: `DETACH PARTITION` (`CONCURRENTLY` in PG 14+) then drop or archive
- Archival works in reverse: **detach** an old partition, move it to cold storage — no row-by-row export
- In payments ("retain 7 years, purge beyond") this **alone** often justifies partitioning, before any query-speed argument

---

### 7. What Partitioning Does NOT Solve

- **Write contention.** All new inserts go to the **newest partition**, so a hot spot moves from "the whole table" to "the current partition" — if anything it **concentrates** it
- Same for a hot row: partitioning never splits one logical row ([[12. Lost Updates & High-Contention Architectures]])
- If write concurrency is the problem, you need `PARTITION BY HASH(account_id)`, intra-account bucketing, or a single-writer queue — **not** date ranges
- Also doesn't help: cross-partition aggregates, joins on non-partition keys, or any query that has to touch everything

> Don't let "would partitioning help here?" pull you into agreeing when the answer is no.

---

### 8. Choosing the Partition Key

- **Partition by the column your most frequent/critical queries actually filter on** — not by whatever column "feels natural", like a date
- If 90% of traffic is point lookups by `txn_id` and 10% is date-range reporting, date partitioning optimises the **minority** pattern and penalises the majority
- Test the key against three questions: does the **dominant** query filter on it? is it **evenly distributed**? does it let unique constraints stay meaningful (§5)?
- Retention is a legitimate reason to pick a date key — but then say out loud that you're accepting slower point lookups for it

---

### 9. Alternatives When the Partition Key Doesn't Fit

| Option | What it does | Cost |
|---|---|---|
| **1. Don't partition** | One well-tuned index on `txn_id` beats any partitioning scheme for point lookups | No retention trick |
| **2. `PARTITION BY HASH(txn_id)`** | Optimizer hashes the value, prunes to **exactly one** of N partitions | Loses date-based `DROP PARTITION` |
| **3. Derive the date from the ID** | If the ID embeds a timestamp (many UPI RRNs do), extract it in app code and pass it as an extra predicate so pruning works | App must own that logic |
| **4. Global lookup table** | Tiny unpartitioned `txn_id_index(txn_id PK, created_at)`; look up the date, then query the big table with **both** predicates | Extra hop; two writes to keep in sync |

- Option 4 is **manually building the global index** the engines don't give you — it keeps date retention *and* fast point lookups
- "Big table → must partition" is a false reflex; option 1 is a real answer

---

### 10. When Not to Partition

- Table under roughly **50–100 million rows** — the overhead rarely pays for itself
- No single natural key that your dominant queries filter on
- **Too many partitions**: each costs planning time and open file handles; hundreds-to-thousands can make the **optimizer itself** slow (MySQL caps at 8192 including subpartitions)
- **MySQL limitation**: partitioned tables don't support **foreign keys** — in or out
- You need a **globally** unique constraint on a column that isn't the partition key (§5)

---

### 11. CQRS Read Model — Two Tables, Two Access Patterns

When point lookups and date-range reporting genuinely conflict, stop forcing one schema to serve both:

- **`txn_log`** (OLTP, source of truth) — **unpartitioned**, tuned for `txn_id` point lookups, serves live processing
- **`txn_log_reporting`** (derived) — **date-partitioned**, tuned for "all of August", dashboards, batch reconciliation, admin views
- Each table fully optimised for its own job, instead of one doing both badly
- This is a **CQRS read model** / materialised reshaped view — *not* a read replica (§13)

---

### 12. Syncing the Read Model

| Approach | Freshness | Verdict |
|---|---|---|
| **CDC** — binlog/WAL → Debezium → Kafka → consumer | Sub-second to seconds | ✅ **Production answer** |
| **Dual write** in app code | Immediate | ❌ **No atomicity** between the two writes |
| **Batch ETL** on a watermark | Minutes | ⚠️ Fine only for a non-urgent dashboard |

- **CDC** adds no load to the primary beyond what replication already costs, and needs no app cooperation
- **Dual write's** failure mode: crash between the two writes → the derived table silently drifts from the source of truth. Name this weakness even if you'd never pick it
- If you must write from the app, use the **transactional outbox**: insert the event into an `outbox` table **in the same transaction**, then relay it — that restores atomicity
- Consumers must be **idempotent** — CDC delivery is at-least-once, so replays happen

---

### 13. Read-Model Discipline

- **It is eventually consistent, on purpose** — acceptable precisely because nothing on the write path or balance-check path may read it
- **Never let it become a correctness dependency.** "Let's reconcile off the reporting table, it's easier to query" is a bug: CDC lag or a dead consumer means it's most stale during the incident where accuracy matters most
- **Lag monitoring is mandatory** — track `MAX(created_at)` in the derived table vs the source, alert past a threshold. Otherwise staleness is invisible
- **Not a read replica**: a replica is schema-identical, so it inherits the primary's *unpartitioned* layout and gets no pruning. This is a **purpose-built reshaped table**
- Even here, add `KEY idx_txn (txn_id, created_at)` — an admin drilling into one transaction still pays the all-partitions penalty without a date

---

### 14. What Sharding Actually Is

- Splitting one logical table's rows across **multiple independent DB instances**, each with its own CPU, memory and storage

```text
account_id % 4 == 0 → Node A      account_id % 4 == 2 → Node C
account_id % 4 == 1 → Node B      account_id % 4 == 3 → Node D
```

- What it buys that partitioning **cannot**: **more total CPU, RAM and disk I/O**, because you're adding machines
- The cost: your **application or a routing layer** must know which node holds which row — nothing is transparent any more
- Tooling exists to hide some of it: **Vitess** (MySQL), **Citus** (Postgres) — worth naming, but they don't remove the cross-shard problems

---

### 15. When Sharding Is Useful

1. **Data volume exceeds one machine** — 500M rows whose working set no longer fits any single server's buffer pool. No index or partition fixes that
2. **Write throughput exceeds one node's ceiling** *and* writes spread across **many independent keys** — millions of customers, each occasional
3. **A natural, stable, evenly-distributed key** — `customer_id`, `merchant_id`, `tenant_id`. The single strongest predictor that sharding will work cleanly
4. **Read scale beyond replicas** — every replica still applies **every** write, so replicas are bounded by single-primary write throughput; shards have independent write capacity
5. **Data residency / compliance** — EU data in the EU, Indian data in India (real for UPI-adjacent systems). Not a performance reason at all
6. **Blast-radius isolation** — one merchant spiking 50× during a sale degrades only their shard. Underrated: this is about **fault isolation**, not throughput

---

### 16. When Sharding Is the Wrong Answer

1. **A single hot row/entity** — one logical account always maps to exactly one shard. Sharding does **nothing**; use intra-entity bucketing or single-writer batching
2. **Cross-shard joins/aggregates** — `SELECT SUM(balance) … WHERE region='APAC'` becomes **scatter-gather**: hit every shard, merge in app code. Every former `JOIN` becomes application-level stitching
3. **Data fits comfortably on one node** — premature sharding is one of the most common real mistakes. **Exhaust vertical scaling, replicas, indexing and partitioning first**
4. **Cross-entity ACID requirements** — an atomic transfer between accounts on different shards needs **2PC** (slow, fragile) or a **saga** (eventual, harder to debug)
5. **Skewed key distribution** — shard by `merchant_id` when one merchant is 40% of volume and you've just moved the hot spot up a level
6. **Naive `hash % N`** — adding a node reshuffles nearly all data. Decide the scheme **upfront** (§17)

> Sharding should be closer to a **last resort** than a first instinct — the operational cost is permanent.

---

### 17. Shard Key Schemes & Rebalancing

| Scheme | Routing | Rebalance | Watch out for |
|---|---|---|---|
| **Range** | `account_id < X → shard 1` | Split a range | Sequential keys → all writes hit the newest shard |
| **Hash (modulo)** | `hash(key) % N` | ❌ Reshuffles ~everything | Never use if N will change |
| **Consistent hashing** | Ring + virtual nodes | Only `1/N` of keys move | The default choice ([[10. Distributed Concurrency]]) |
| **Directory** | Lookup table: key → shard | Update a row | Extra hop; the directory becomes critical infra |

- **Virtual nodes** are what make consistent hashing distribute evenly and let you weight heterogeneous hardware
- **Directory-based** is the most flexible — it lets you pin one whale tenant to a dedicated shard, which no hash scheme can express
- Hot-shard fixes: **split** the shard, **salt** the key, or move the offender to its own node

---

### 18. Cross-Shard Transactions — the Cost You Can't Avoid

- A local ACID transaction is **free**; the moment it spans two shards, that guarantee is gone

| | **2PC** | **Saga** |
|---|---|---|
| Consistency | Atomic across shards | **Eventual**, with compensating actions |
| Failure mode | Coordinator dies → participants **blocked** holding locks | Compensation itself can fail → needs retries + DLQ |
| Latency | Two round trips, locks held across both | No cross-shard locks |
| In practice | Rarely used at scale | The common answer |

- A saga replaces "debit A, credit B, atomically" with "debit A → emit event → credit B → on failure, **compensating credit** back to A"
- Compensation is not a rollback: the debit really happened and is really visible in between
- Requires **idempotent** steps and a durable state machine — see [[11. Transaction Boundaries]]

---

### 19. The Payments Domain — What to Shard

| Table | Shard? | Why |
|---|---|---|
| `customer_accounts` (millions) | **Yes** — by `customer_id` | Naturally distributed, high volume, customers independent |
| `pool_account` (one row, high TPS) | **No** | It's one entity — bucketing + single-writer, not sharding |
| `ledger_entries` | **Maybe** — by `account_id` | Date-partitioning one large node is usually enough first |
| `idempotency_keys` | **Not by date** | Uniqueness must stay global (§5) — hash the key if anything |
| Customer → pool transfer | **Sharding makes it worse** | Now spans two shards → saga instead of a local transaction |

- Raise that last row **proactively**: "if I shard customers by `customer_id`, every debit-customer/credit-pool transaction may span shards, so I'd need a saga rather than a local ACID transaction"

---

### 20. The Escalation Ladder

```text
1. Index / query tuning      ← always first; often the whole answer
2. Vertical scaling          ← boring, cheap, buys years
3. Read replicas             ← offload reads; write ceiling unchanged
4. Partitioning              ← pruning + instant retention, ONE node
5. CQRS read model           ← two access patterns, two schemas
6. Sharding                  ← more machines; permanent ops + consistency cost
```

- Each rung costs more operationally than the one below — **never skip rungs to look sophisticated**
- Rungs 1–4 keep single-node ACID. Rung 6 gives it up for anything cross-shard
- Diagnose the **actual** bottleneck first: total volume → shard; scan cost → partition; contention on one row → neither ([[12. Lost Updates & High-Contention Architectures]])

# Detailed Explanation

---

## Partitioning vs Sharding

Keep these strictly separate — interviewers conflate them deliberately to see whether you will.

**Partitioning** splits **one table into N physical sub-tables on the same server**. The database engine manages it, and the application is oblivious: it still queries `ledger_entries` and never names a partition. It's a reorganisation of files on the hardware you already have.

**Sharding** splits rows across **multiple independent database instances**, each with its own CPU, memory and disk. Nothing is transparent: your application or a routing layer must know which node holds which row.

| | Partitioning | Sharding |
|---|---|---|
| Scope | One node | Multiple nodes |
| Managed by | The DB engine, transparently | Your app / a proxy |
| Query view | One logical table | Route to the right node first |
| Solves | Table size, scan cost, maintenance | Total capacity |
| Transactions | Normal, local, ACID | Cross-shard needs 2PC or saga |
| Ops cost | Near zero | Permanent and large |

The distinction that matters: **partitioning optimises access patterns on fixed hardware; sharding scales the hardware itself.** If your bottleneck is "this query reads too many pages," partition. If it's "this machine has no more RAM/CPU/IOPS to give," shard. Answering "shard it" to a scan-cost problem is a wrong answer that sounds impressive, and vice versa.

They compose fine: a shard can itself be date-partitioned. That's a normal end state for a large ledger.

---

## Partition Pruning — the Mechanism

Everything good about partitioning flows from one optimizer behaviour.

```sql
CREATE TABLE ledger_entries (
    entry_id    BIGINT AUTO_INCREMENT,
    txn_id      VARCHAR(64)    NOT NULL,
    account_id  VARCHAR(50)    NOT NULL,
    amount      DECIMAL(20,4)  NOT NULL,
    created_at  DATETIME       NOT NULL,
    PRIMARY KEY (entry_id, created_at),          -- partition col forced in, see below
    KEY idx_account_time (account_id, created_at)
)
PARTITION BY RANGE (TO_DAYS(created_at)) (
    PARTITION p2026_06 VALUES LESS THAN (TO_DAYS('2026-07-01')),
    PARTITION p2026_07 VALUES LESS THAN (TO_DAYS('2026-08-01')),
    PARTITION p2026_08 VALUES LESS THAN (TO_DAYS('2026-09-01')),
    PARTITION p2026_09 VALUES LESS THAN (TO_DAYS('2026-10-01')),
    PARTITION pmax     VALUES LESS THAN MAXVALUE
);
```

Now run a month-scoped query:

```sql
SELECT * FROM ledger_entries
 WHERE created_at >= '2026-08-01' AND created_at < '2026-09-01'
   AND account_id = 'POOL_001';
```

The optimizer reads the `created_at` predicate, compares it against each partition's declared range boundaries, and concludes that **only `p2026_08` can possibly contain matching rows**. It never opens the others.

```text
EXPLAIN output:
partitions: p2026_08          ← one partition, not five
```

That's **partition pruning**, and note *when* it happens: **before any index work**. Roughly 80% of the table is eliminated for free, then the surviving partition's local index does the real search.

The `partitions:` column in MySQL's `EXPLAIN` is the single most useful diagnostic here — if it lists every partition, your pruning isn't working and you're about to be slower than an unpartitioned table.

Postgres prunes at **plan time** the same way, and since **PG 11** also at **execution time**, which matters for prepared statements and parameterised queries where the actual value isn't known when the plan is built. Worth mentioning if an interviewer pushes on prepared statements.

```sql
-- Postgres declarative partitioning
CREATE TABLE ledger_entries (
    entry_id    BIGSERIAL,
    txn_id      VARCHAR(64)   NOT NULL,
    account_id  VARCHAR(50)   NOT NULL,
    amount      NUMERIC(20,4) NOT NULL,
    created_at  TIMESTAMPTZ   NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE ledger_2026_08 PARTITION OF ledger_entries
    FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');
```

## Why Partitioning Is Actually Faster

Three separate benefits, and the ranking is the part most people get wrong.

**1. Fewer pages to scan — the biggest win for range queries.**
"Give me all of August" on an unpartitioned 1-billion-row table walks the index and reads pages scattered across the entire structure. On a partitioned table it reads one contiguous ~83-million-row partition. Dramatically fewer pages touched, and they're physically clustered.

**2. Smaller indexes fit in the buffer pool — the underrated win.**
Each partition has its **own** B+ tree. If your traffic is mostly recent data — which for a payments ledger it overwhelmingly is — only the last month or two of index pages need to stay resident. On an unpartitioned table, one giant index means all historical data competes for the same buffer pool, and your cache hit rate on hot data is worse for no benefit.

**3. Shallower trees — real, but smaller than people claim.**
With a typical fanout of ~500 entries per 16 KB page:

```text
1 billion rows   → log₅₀₀(10⁹)      ≈ 3.4  → 4 levels
83 million rows  → log₅₀₀(8.3×10⁷)  ≈ 2.9  → 3 levels
```

One fewer level, so roughly **25% fewer I/Os per point lookup**. Genuinely real, but modest — and the top levels of any B+ tree are permanently cached anyway ([[13. Index & Lock Internals]]), so the saved level is often the cheapest one.

> 💡 **Interview**: "Why is a partitioned index faster?" → "Mostly two things: pruning eliminates most of the table before any index work, and each partition's smaller index means recent data actually stays resident in the buffer pool. Tree depth does drop — about four levels to three at a billion rows — but that's a ~25% I/O win on point lookups, not the main effect. Blog posts lead with tree height; the buffer-pool and page-scan effects are bigger."

---

## Local Indexes — the Trap

This is what an interviewer is usually testing when they ask "does partitioning make search faster?"

**MySQL and Postgres both use local indexes.** Each partition carries its own independent index structure. **There is no global index spanning all partitions** — neither engine supports one. (In Postgres, `CREATE INDEX` on the parent since PG 11 creates a matching index on every partition; it's still N separate indexes, not one.)

The consequence is immediate:

```sql
SELECT * FROM ledger_entries WHERE txn_id = 'UPI700';   -- no created_at predicate
```

There is nothing to prune on, so the optimizer must search **every partition's index separately**:

```text
EXPLAIN output:
partitions: p2026_06,p2026_07,p2026_08,p2026_09,pmax    ← all of them
```

Five index lookups instead of one — and with 24 months of retention, **24 index traversals** instead of one. That is **strictly slower than the same query on an unpartitioned table**, which would have done a single traversal of one large index.

```sql
-- ❌ 24 partitions searched: slower than unpartitioned
SELECT * FROM txn_log WHERE txn_id = 'UPI700';

-- ✅ pruned to one partition: fast
SELECT * FROM txn_log WHERE txn_id = 'UPI700' AND created_at >= '2026-08-01'
                                              AND created_at <  '2026-09-01';
```

**The rule, stated cleanly:**

> Partitioning helps only queries that filter on the partition key. Queries that don't include it pay an N-partition penalty. So you partition by the column your dominant query pattern actually filters on, and you accept that secondary access paths get worse.

---

## Unique Keys Must Include the Partition Key

This one connects straight back to the idempotency work in [[13. Index & Lock Internals]], and raising it unprompted is a strong signal.

**MySQL requires every unique index — including the primary key — to contain all columns of the partitioning expression.** Postgres declarative partitioning has the same restriction: a unique constraint or primary key on a partitioned table must include the partition key columns.

The reason is structural, not arbitrary: with only local indexes, enforcing global uniqueness would require checking every partition on every insert. The engines refuse to make that promise, so they force the constraint into a shape they *can* enforce locally.

```sql
-- Table partitioned by created_at

UNIQUE KEY uk_idem (idem_key)                 -- ❌ ERROR: partition column not included
UNIQUE KEY uk_idem (idem_key, created_at)     -- ✅ accepted... and now nearly useless
```

That second constraint does **not** guarantee `idem_key` is globally unique. The same key submitted on a different date lands in a different partition and **will not conflict**. The whole mechanism traced in §13 — implicit lock, waiter, duplicate-key error on commit — never fires, because from the index's point of view these are two different keys.

```java
// A client retries a payment the next day with the same idempotency key.
// Unpartitioned:            DuplicateKeyException  → you return the original result. ✅
// Partitioned by date:      insert succeeds        → the customer is charged twice.  ❌
```

No error is raised, nothing appears in the logs, and you find out during reconciliation.

**Practical rules:**

- **Do not date-partition `idempotency_keys`.** Keep it unpartitioned with a scheduled cleanup job, or partition by `HASH(idem_key)` — then the partition column *is* the unique column and the constraint stays honest.
- **Do** date-partition the ledger. Ledger uniqueness is naturally scoped by `entry_id`/`txn_id` semantics rather than by a cross-time global constraint, and the retention benefit is the point.

---

## Retention & Archival — the Real Reason to Partition

For a ledger or audit table under a retention policy, this benefit frequently dwarfs the query-speed argument.

```sql
-- ✅ Partitioned: a metadata operation
ALTER TABLE ledger_entries DROP PARTITION p2025_09;

-- ❌ Unpartitioned: hours of work
DELETE FROM ledger_entries WHERE created_at < '2025-10-01';
```

That `DELETE` scans and deletes millions of rows. It generates enormous undo-log / WAL volume, holds locks for its duration, blows out replication lag on every replica, and leaves the table physically bloated — so you then need `OPTIMIZE TABLE` (MySQL) or `VACUUM FULL` (Postgres) to reclaim the space, which is itself a heavyweight operation. In practice teams end up chunking it into batched deletes with sleeps, running for days.

`DROP PARTITION` is a **file unlink and a catalog update**. Milliseconds, no undo volume, no replica lag, no bloat.

Archival is the same trick in reverse: **detach** the old partition, move the file to cold storage, done — no row-by-row export. Postgres has `ALTER TABLE … DETACH PARTITION`, and since **PG 14** a `CONCURRENTLY` variant that avoids taking an `ACCESS EXCLUSIVE` lock on the parent.

In payments — "retain 7 years, purge beyond" is a compliance requirement, not a preference — this alone routinely justifies partitioning before anyone measures a query.

---

## What Partitioning Does NOT Solve

**Date partitioning does not help write contention.** Every new insert goes into the newest partition, so a write hot spot doesn't disappear — it moves from "the whole table" to "the current partition," which is *smaller*, so if anything the contention concentrates. The rightmost-page latch contention from [[13. Index & Lock Internals]] is exactly as bad, now on a smaller tree.

Nor does partitioning ever split a single logical row. If your bottleneck is one pool account taking thousands of writes per second, partitioning the table it lives in changes nothing — that row is in exactly one partition, and every writer still serialises on it ([[12. Lost Updates & High-Contention Architectures]]).

If **write concurrency** is the actual problem, the tools are different: `PARTITION BY HASH(account_id)` so concurrent writers land on different partitions, intra-account bucketing, a single-writer queue, or an append-only ledger. Date ranges are the wrong instrument entirely.

Also on the "doesn't help" list: cross-partition aggregates, joins on anything other than the partition key, and any query that legitimately has to touch all the data.

> Don't let an interviewer's "would partitioning help here?" pull you into agreeing when the answer is no. Saying "no, and here's what would" is the stronger answer.

---

## Choosing the Partition Key

The single decision that determines whether partitioning helps or hurts.

> **Partition by the column your most frequent and most critical queries actually filter on — not by whatever column feels natural, like a date.**

Consider a `txn_log` where `txn_id` point lookups are the dominant pattern:

```sql
SELECT * FROM txn_log WHERE txn_id = 'UPI700';
```

- Unpartitioned: **1** index traversal, 3–4 B+ tree levels.
- Partitioned by month, 24 months retained: **24** index traversals, because each partition has its own local index and nothing can be pruned without a value on the partition key.

So date partitioning would make your **most frequent** query pattern ~24× more expensive, to gain a benefit (pruning on date ranges) that only helps a pattern you said isn't dominant. That's a bad trade for that table — and being able to say so is the difference between reciting "partitioning improves performance" and actually reasoning about it.

Three questions to run any candidate key through:

1. **Does the dominant query filter on it?** If not, stop.
2. **Is it evenly distributed?** A key that puts 40% of rows in one partition gives you one giant partition and a lot of empty ones.
3. **Do unique constraints survive?** Check §5 before committing — a key that forces `UNIQUE (idem_key, created_at)` may silently break a guarantee you depend on.

Retention is a legitimate reason to pick a date key even when it hurts point lookups. Just say that out loud as a trade you're making, rather than pretending it's free.

---

## Alternatives When the Partition Key Doesn't Fit

Four real options when the dominant query and the retention requirement want different keys.

**Option 1 — Don't partition at all.**
If it's a hot, well-indexed `txn_id` lookup table, a single well-tuned index will outperform any partitioning scheme. Partitioning is not mandatory just because a table is large. A lot of candidates assume "big table → must partition"; saying "I wouldn't partition this one" is often the senior answer.

**Option 2 — Partition by `HASH` of the lookup key.**

```sql
PARTITION BY HASH(txn_id) PARTITIONS 32;
```

Now `WHERE txn_id = 'UPI700'` hashes the value, and the optimizer computes exactly which of the 32 partitions it lives in and prunes to **that single partition**. You get the smaller-index and buffer-pool-residency benefits *for the query pattern you actually have*. The cost: hash partitions don't correspond to time ranges — old and new rows are mixed in every partition — so you lose the `DROP PARTITION` retention trick entirely.

**Option 3 — Derive the pruning key from the ID.**
If you must keep date partitioning for retention, you can often still prune. Many real payment reference IDs embed a timestamp component (a UPI RRN is typically time-derived). Extract the date from the ID in application code and pass it as an additional predicate, so the optimizer can prune even though the caller only "asked for" a `txn_id`:

```java
// Caller only has the txn_id — the app supplies the pruning key
LocalDate d = RrnCodec.dateOf(txnId);           // ID embeds its own date
jdbc.query("SELECT * FROM txn_log WHERE txn_id = ? AND created_at >= ? AND created_at < ?",
           txnId, d.atStartOfDay(), d.plusDays(1).atStartOfDay());   // ✅ prunes to 1 partition
```

The application now owns that logic, and it breaks the day your ID format changes — document it.

**Option 4 — Build the global index yourself.**
Keep a small, unpartitioned lookup table: `txn_id_index(txn_id PRIMARY KEY, created_at)`. Tiny rows, one index, stays fully cached. Point lookups hit it first to get `created_at`, then query the big partitioned table with **both** predicates, pruning to one partition.

```text
app → txn_id_index (unpartitioned, tiny)  → created_at
    → txn_log (partitioned) WHERE txn_id = ? AND created_at = ?   → 1 partition
```

This is manually building the global index the engines don't provide. Two hops and two writes to keep in sync (put the second write in the same transaction, or derive it via CDC), but it preserves date-based retention **and** fast point lookups.

> **The honest tradeoff statement**: "If the dominant pattern is a point lookup by `txn_id` with no date component, month partitioning hurts it, because local indexes mean every partition gets searched. I'd either not partition, partition by `HASH(txn_id)` if lookups matter most, or — if I need date retention for compliance — add a small unpartitioned `txn_id → created_at` lookup table so the app can supply the pruning key even when the caller only has the transaction id."

---

## When Not to Partition

- **Under roughly 50–100 million rows.** The overhead usually isn't worth it; a good index does the job.
- **No single natural key** that your dominant queries filter on. Partitioning by a column nobody filters on is pure downside.
- **Too many partitions.** Each costs planning time and open file handles. Hundreds to thousands can make the **optimizer itself** slow — you've moved the cost from execution to planning. MySQL caps at **8192** partitions including subpartitions; Postgres has no hard cap but planning degrades well before that.
- **MySQL: no foreign keys.** Partitioned InnoDB tables can't participate in foreign key relationships in either direction. If your schema depends on them, partitioning is off the table (or the FKs are).
- **You need a genuinely global unique constraint** on a column that can't be the partition key (§5).

## CQRS Read Model — Two Tables, Two Access Patterns

When the point-lookup and date-range patterns genuinely conflict and none of the four options above is clean, stop forcing one schema to serve both jobs. Maintain two tables, each fully optimised for its own access pattern:

- **`txn_log` (OLTP, source of truth)** — unpartitioned, tuned for `txn_id` point lookups, serves live transaction processing. No compromise for reporting.
- **`txn_log_reporting` (derived)** — date-partitioned, tuned for "all transactions in August", sum-by-day dashboards, batch reconciliation, admin views. No compromise for point lookups.

```text
     writes                          CDC                    reads
  ──────────►  txn_log  ──────────────────────────►  txn_log_reporting  ──────────►
               (unpartitioned,                        (date-partitioned,
                txn_id lookups,                        range scans, retention,
                source of truth)                       eventually consistent)
```

This is a **CQRS read model** — a materialised, *reshaped* view of the same data. Recognising "one table, one job" instead of forcing a single schema to serve two conflicting access patterns is the actual design instinct being tested.

The reporting table's dominant pattern really *is* date-driven — "this month's report", "last quarter's reconciliation", "purge beyond 7 years" — so date-range partitioning is now unambiguously the right choice, exactly where it was the wrong choice on `txn_log`:

```sql
CREATE TABLE txn_log_reporting (
    entry_id     BIGINT,
    txn_id       VARCHAR(64)   NOT NULL,
    account_id   VARCHAR(50)   NOT NULL,
    amount       DECIMAL(20,4) NOT NULL,
    status       VARCHAR(20)   NOT NULL,
    created_at   DATETIME      NOT NULL,
    PRIMARY KEY (entry_id, created_at),
    KEY idx_txn (txn_id, created_at)     -- see the note below
)
PARTITION BY RANGE (TO_DAYS(created_at)) (
    PARTITION p2026_07 VALUES LESS THAN (TO_DAYS('2026-08-01')),
    PARTITION p2026_08 VALUES LESS THAN (TO_DAYS('2026-09-01')),
    PARTITION pmax     VALUES LESS THAN MAXVALUE
);
```

`idx_txn` deliberately includes `created_at` as well: an admin drilling into a single transaction from a report still pays the all-partitions penalty unless they also supply a date. That's usually acceptable here precisely because this table is not the hot path — but know that it's true rather than being surprised by it.

## Syncing the Read Model

Three approaches, in typical order of preference.

**1. CDC (Change Data Capture) — the production-grade answer.**

```text
txn_log (MySQL) → binlog → Debezium → Kafka topic → consumer → txn_log_reporting
```

Debezium tails MySQL's binlog (or Postgres's WAL) and emits an event for every insert, update and delete, typically with sub-second to few-second lag. A consumer applies those events to the partitioned reporting table.

Why it's usually right: it adds **no load to the primary** beyond what replication already costs, it requires **no cooperation from application code** (nobody can forget to "also write the reporting table"), and it drops straight into an existing Kafka stack.

**2. Application-level dual write — simplest, with a real correctness problem.**

```java
saveToTxnLog(txn);
saveToReportingTable(txn);   // ❌ separate write, no atomicity with the first
```

If the process crashes between the two writes, the reporting table silently drifts from the source of truth. (If both tables live in the *same* database you can wrap them in one transaction and the problem vanishes — but a derived table on a separate node can't.) Name this failure mode even when you wouldn't choose the approach; understanding it is the point.

The fix if you must write from the app is the **transactional outbox**: insert the event row into an `outbox` table **inside the same local transaction** as the business write, then have a relay (or CDC on the outbox table) publish it. Atomicity is restored because there is only ever one transaction.

```java
// ✅ Outbox: one transaction, so the event can't be lost or orphaned
tx.begin();
insertTxnLog(txn);
insertOutboxEvent(txn);     // same DB, same transaction
tx.commit();
// a relay/CDC process publishes outbox rows and marks them sent
```

**3. Periodic batch ETL — simplest to build, highest staleness.**

```sql
INSERT INTO txn_log_reporting
SELECT * FROM txn_log WHERE updated_at > :last_sync_watermark;
```

Easy, but "periodically" is an explicit acceptance of minutes of lag. Fine for an admin dashboard nobody expects to be live. **Not** fine if "reporting" quietly means "reconciliation that must match NPCI within seconds" — which in payments it often does.

Whichever you pick, the consumer must be **idempotent**: CDC and message queues deliver at-least-once, so the same event will be replayed. Upsert on the natural key rather than blind-inserting.

For a payments system specifically, CDC is usually the right call, because freshness expectations for reconciliation and admin visibility turn out tighter than people initially state, and CDC gets you near-real-time without polling the primary every N minutes.

---

## Read-Model Discipline

Three rules that separate a working read model from an outage.

**1. It is eventually consistent, and that's the correct trade — for this table.**
Say it explicitly: "the reporting table is intentionally eventually consistent, and that's acceptable because it is never on the write path or the balance-check path." The trade is only defensible while that sentence stays true.

**2. Never let it become a dependency for correctness.**
The moment someone says "let's reconcile off the reporting table, it's easier to query," you have a latent incident. CDC lag or a stuck consumer means the derived table is most stale during exactly the incident where accuracy matters most. **Reconciliation against NPCI must hit the ledger**, not the derived copy. Enforce it socially and, ideally, with separate credentials that only grant read access to reporting consumers.

**3. Lag monitoring is mandatory, not optional.**
Track `MAX(created_at)` in the reporting table against the source and alert past a threshold. Without it, an admin looking at a "report" has no way to know whether they're seeing data from two seconds or two hours ago, because a dead consumer looks exactly like a quiet period.

**And the distinction to draw if asked "isn't this just a read replica?"**
A plain read replica already solves "don't load the primary with reporting queries" — but it is **schema-identical** to the primary, so it inherits the primary's *unpartitioned* structure and gives you no pruning. What this is, is a **purpose-built derived table**: same replication *idea*, but with a schema and partitioning scheme chosen for the reporting query shape. A materialised, reshaped view — not a byte-for-byte copy.

> 💡 **Interview**: "How do you make one table fast for both `txn_id` lookups and monthly reports?" → "I wouldn't. Those want opposite partition keys, so I'd keep the OLTP table unpartitioned and tuned for point lookups, and maintain a separate date-partitioned reporting table synced by CDC — a CQRS read model. The discipline is that the derived table is strictly read-only, eventually consistent, never in the path of a balance check or reconciliation-for-correctness, and monitored for lag so staleness is visible rather than silent."

## What Sharding Actually Is

Splitting one logical table's rows across **multiple independent database instances**, each with its own compute, memory and storage.

```text
Shard 1: account_id % 4 == 0  → DB Node A
Shard 2: account_id % 4 == 1  → DB Node B
Shard 3: account_id % 4 == 2  → DB Node C
Shard 4: account_id % 4 == 3  → DB Node D
```

The fundamental thing sharding buys that partitioning cannot: **more total CPU, memory and disk I/O**, because you are adding machines rather than reorganising files on one.

The fundamental thing it costs: **transparency**. The application or a routing layer must resolve every query to a node before issuing it, and any operation spanning two nodes loses the single-node ACID guarantee you've had for free through notes 9–13.

Middleware can hide part of this — **Vitess** for MySQL (what YouTube built), **Citus** for Postgres — and they're worth naming. But they hide the *routing*, not the *physics*: cross-shard joins are still scatter-gather, and cross-shard transactions are still hard.

---

## When Sharding Is Useful

**1. Total data volume exceeds one machine's capacity.**
500 million rows whose working set no longer fits in any single server's RAM/buffer pool. No amount of indexing or partitioning fixes that — you need more machines. The textbook case.

**2. Write throughput exceeds one machine's ceiling, and writes are spread across many independent keys.**
This is the nuance that matters. Sharding helps when contention is spread across **many different rows**, not concentrated on one. Millions of customers each making occasional transactions → shard by `customer_id`, and each shard handles only its slice. Each customer's own transactions still serialise correctly on their shard; different customers stop competing entirely.

**3. A natural, stable, evenly-distributed key exists.**
`customer_id`, `merchant_id`, `tenant_id` in multi-tenant SaaS — anything where rows genuinely belong to independent owners who rarely interact. This is the **single strongest predictor** that sharding will work cleanly. If your data has an obvious ownership key, shard on it; if it doesn't, expect pain.

**4. Read scale beyond what replicas provide.**
Replicas help, but every replica must still apply **every** write, so total capacity is still bounded by single-primary write throughput and, under heavy write load, by replica lag. Shards have **independent write capacity**, which indirectly raises total read capacity too.

**5. Regulatory / data-residency requirements.**
Real and common in fintech: EU customer data stays in the EU, Indian data in India — data localisation is a genuine constraint for UPI-adjacent systems. Sharding by geography here isn't about performance at all; it's a hard compliance requirement. Naming it as a **different kind of reason** shows range.

**6. Blast-radius isolation.**
If one large merchant's traffic spikes 50× during a sale, on a shared unsharded DB that degrades everyone. Sharding contains it to their shard(s). This is about **fault isolation**, not throughput, and it's consistently underrated.

---

## When Sharding Is the Wrong Answer

**1. A single hot row or entity.**
One logical account always maps to exactly one shard, so sharding does **nothing** for it. The fix is intra-entity bucketing, single-writer plus batching, or a reservation pattern — see [[12. Lost Updates & High-Contention Architectures]]. Recognising this instantly is the fastest way to show you understand what sharding is *for*.

**2. Queries that join or aggregate across shards.**

```sql
SELECT SUM(balance) FROM accounts WHERE region = 'APAC';
```

Sharded by `account_id`, this must hit **every shard**, gather partial results, and merge them in application code — **scatter-gather**. Latency becomes the slowest shard's latency, and every `JOIN` that used to be one line of SQL becomes application-level stitching. If broad aggregates and joins dominate your workload, sharding actively makes things worse: it's the same "wrong key, wrong query pattern" trap as partitioning, at far higher operational cost.

**3. The data fits comfortably on one node.**
A few million rows that fit in RAM with years of headroom. Sharding adds a routing layer, cross-shard transaction handling, rebalancing machinery, and N× the ops/monitoring/backup burden for zero benefit. **Premature sharding is one of the most common real-world mistakes** — "we might need scale eventually" is not a reason. Exhaust vertical scaling, replicas, indexing and partitioning first.

**4. Strong cross-entity transactional consistency.**
If business logic frequently needs an atomic transaction spanning two entities that could land on different shards — a transfer from Account A on Shard 1 to Account B on Shard 3 — you lose the simple local transaction. You get **2PC** (slow, fragile, rarely used at scale) or a **saga** (eventual consistency with compensating actions — more common, genuinely harder to reason about and debug). If your domain is full of these, sharding introduces a categorically harder correctness problem than anything in notes 9–13.

**5. Uneven or unpredictable key distribution.**
Shard by `merchant_id` when one merchant is 40% of platform volume, and that shard is a hotspot no better than the original hot-row problem — you've moved it up a level and added a routing layer. Even distribution has to be true **in practice**, not just in theory.

**6. A rebalancing scheme chosen carelessly.**
Plain `hash(key) % N` means adding or removing a node reshuffles almost all your data — exactly the problem consistent hashing exists to solve. Decide upfront whether assignment is range-based, hash-based with consistent hashing, or directory-based; getting it wrong makes every future rebalance an operational nightmare.

---

## Shard Key Schemes & Rebalancing

| Scheme | Routing | Rebalance cost | Watch out for |
|---|---|---|---|
| **Range** | `id < X → shard 1` | Split a hot range | Sequential keys send all new writes to the last shard |
| **Hash (modulo)** | `hash(key) % N` | ❌ Nearly all keys move | Only safe if N never changes |
| **Consistent hashing** | Position on a ring | Only ~`1/N` of keys move | Needs virtual nodes for even spread |
| **Directory** | Lookup table: key → shard | Update one row | Extra hop; the directory is now critical infra |

**Range** partitioning of shards gives you clean range scans within a shard, but a monotonically increasing key (a timestamp, an auto-increment) sends every new write to the newest shard — you've built a hot shard by construction.

**Consistent hashing** is the default answer, and **virtual nodes** are what make it work: each physical node owns many points on the ring, which evens out distribution and lets you weight heterogeneous hardware by giving bigger machines more virtual nodes. Covered in [[10. Distributed Concurrency]].

**Directory-based** is the most flexible and the most underrated. Because assignment is data, not a formula, you can express things no hash can: pinning one whale tenant to a dedicated shard, migrating a single customer, or keeping EU tenants on EU nodes. The price is a lookup on every request (cache it) and a directory service that must not go down.

When a shard does run hot, the fixes are: **split** it, **salt** the key to spread one heavy tenant, or **move** the offender to its own dedicated node — the last being the reason many teams end up with a directory scheme eventually.

## Cross-Shard Transactions — the Cost You Can't Avoid

This is the price of sharding, and it is not optional.

Within one shard, everything from notes 9–13 still applies: row locks, MVCC, isolation levels, a local `BEGIN … COMMIT`. Across shards, none of it does.

| | **2PC (two-phase commit)** | **Saga** |
|---|---|---|
| Guarantee | Atomic across shards | **Eventual**, via compensating actions |
| Mechanism | Prepare → all vote → commit | Local txn per step + compensations on failure |
| Failure mode | Coordinator dies after prepare → participants **blocked** holding locks | A compensation can itself fail → retries + DLQ |
| Latency | Two round trips, locks held across both | No cross-shard locks held |
| Intermediate state | Invisible | **Visible** — the debit really happened |
| In practice | Rare at scale | The common answer |

A saga replaces "debit A and credit B atomically" with a sequence: debit A → emit event → credit B → and on failure, a **compensating credit** back to A. The critical thing to be precise about: **compensation is not a rollback.** The debit genuinely happened, was genuinely visible to anyone reading account A, and is undone by a *second* forward transaction. In a ledger this is correct and auditable — you have both entries — but in the customer's app it can mean money visibly leaving and returning.

That means every step must be **idempotent** (retries will happen) and the whole flow needs a durable state machine so a crashed orchestrator can resume. See [[11. Transaction Boundaries]].

```text
Saga: customer → pool transfer across shards

  Shard 1                       Shard 3
  ───────                       ───────
  debit customer  ──event──►    credit pool
       ▲                             │
       └────── compensating ─────────┘  (on failure: credit customer back)
                 credit
```

## The Payments Domain — What to Shard

Applying all of it to the domain:

| Table | Shard? | Why / why not |
|---|---|---|
| `customer_accounts` (millions of customers) | **Yes** — by `customer_id` | Naturally distributed, high total volume, customers largely independent |
| `pool_account` (one entity, high TPS) | **No** | It's one row. Sharding doesn't touch it — use intra-account bucketing + single-writer |
| `ledger_entries` | **Maybe** — by `account_id` if volume is enormous | Date-partitioning on one large node is often enough first; depends whether the bottleneck is volume or write concurrency |
| `idempotency_keys` | **Not by date**; hash the key if anything | Uniqueness must remain global — see the partition-key constraint above |
| Customer → pool transfer | **Sharding makes this harder** | Customer and pool may sit on different shards → saga instead of a local ACID transaction |

That last row is the one to raise **proactively**: "if I shard customer accounts by `customer_id`, every debit-from-customer / credit-to-pool transaction potentially spans two shards, so I'd handle it with a saga rather than a local ACID transaction." Volunteering the consequence of your own design decision — before being asked — is exactly the forward-looking tradeoff awareness these interviews are fishing for.

## The Escalation Ladder

The synthesis, and the thing to say when someone opens with "the table is huge, what do you do?"

```text
1. Index / query tuning   ← always first; frequently the entire answer
2. Vertical scaling       ← boring, cheap, buys years of headroom
3. Read replicas          ← offload reads; write ceiling unchanged
4. Partitioning           ← pruning + instant retention, still ONE node, still ACID
5. CQRS read model        ← two conflicting access patterns → two schemas
6. Sharding               ← more machines; permanent ops + consistency cost
```

Three rules for using it:

**Never skip rungs to sound sophisticated.** Jumping to "shard it" for a problem that a composite index solves is the most common way to fail this question. Each rung costs meaningfully more operationally than the one below.

**Rungs 1–4 preserve single-node ACID.** Everything you know from notes 9–13 keeps working. Rung 6 gives that up for anything spanning shards, permanently, and there's no path back.

**Diagnose the bottleneck before picking a rung.** They are not interchangeable:

| Symptom | Right tool |
|---|---|
| Query reads too many pages | Index, then partitioning |
| Working set exceeds RAM on the biggest machine available | Sharding |
| Read load saturating the primary | Read replicas |
| Two query patterns want opposite layouts | CQRS read model |
| Purging old data takes hours | Date partitioning |
| Thousands of writers on **one row** | **None of these** — bucketing, queueing, or an append-only ledger ([[12. Lost Updates & High-Contention Architectures]]) |

That last row is the trap the whole database thread has been building toward: partitioning and sharding both distribute **across** keys. Neither one can help when the contention is **on a single key**. The fix is never a better distribution scheme — it's not doing synchronous read-modify-write on one row.

## Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| Partitioning vs sharding? | Partitioning splits one table into sub-tables **on one node**, transparently, managed by the engine. Sharding splits rows across **multiple nodes**, and the app must route. One optimises access patterns on fixed hardware; the other adds hardware. |
| What makes a partitioned search fast? | **Partition pruning** — the optimizer compares the predicate against partition boundaries and never opens the ones that can't match, before any index work. |
| How do you verify pruning is happening? | MySQL `EXPLAIN` prints a `partitions:` column. If it lists every partition, pruning failed and you're slower than unpartitioned. |
| Rank the benefits of partitioning honestly. | 1) fewer pages scanned, 2) smaller per-partition indexes stay resident in the buffer pool, 3) one less B+ tree level (~25% fewer I/Os). Blog posts lead with #3; it's the smallest. |
| Does partitioning make *every* query faster? | **No.** Indexes are **local per partition**, so a query without the partition key must search every partition — strictly slower than an unpartitioned table. |
| 24 monthly partitions, point lookup by `txn_id`? | 24 index traversals instead of 1. If that's your dominant pattern, date partitioning is the wrong choice. |
| What constraint does partitioning force on unique keys? | Every unique index, **including the PK**, must contain all columns of the partitioning expression — in both MySQL and Postgres. |
| Why is that dangerous? | `UNIQUE (idem_key, created_at)` isn't globally unique. The same idempotency key on a different date lands in another partition and **won't conflict** — silent double-charge. |
| So how do you partition an idempotency table? | Don't partition it by date. Leave it unpartitioned with a cleanup job, or `PARTITION BY HASH(idem_key)` so the unique constraint can honestly include the partition column. |
| Why do teams really partition a ledger? | **Retention.** `DROP PARTITION` is a file unlink; the equivalent `DELETE` is hours of undo/WAL, locks, replica lag, and bloat needing `OPTIMIZE`/`VACUUM FULL`. |
| Does date partitioning help write contention? | **No — it concentrates it.** All inserts go to the newest partition. Use `HASH(account_id)`, bucketing, or a single-writer queue instead. |
| How do you choose the partition key? | By the column your **dominant, most critical** queries filter on. Then check it's evenly distributed and that unique constraints survive. |
| Dominant query has no date, but you need date retention? | Four options: don't partition; `HASH(txn_id)`; derive the date from an ID that embeds a timestamp; or a small unpartitioned `txn_id → created_at` lookup table (a hand-built global index). |
| When should you not partition at all? | Under ~50–100M rows, no natural key your queries filter on, or so many partitions that planning time and file handles become the cost. MySQL also loses foreign keys on partitioned tables. |
| One table, two conflicting access patterns? | Don't force it. **CQRS read model**: unpartitioned OLTP table for point lookups, separate date-partitioned derived table for reporting. |
| How do you sync the derived table? | **CDC** (binlog/WAL → Debezium → Kafka → consumer) — near real time, no extra load on the primary, no app cooperation needed. |
| What's wrong with dual writes? | No atomicity between the two writes — a crash in between makes the derived table silently drift. Fix it with a **transactional outbox** in the same local transaction. |
| Non-negotiables for a derived table? | It is **eventually consistent** and read-only; it must **never** be in a balance-check or reconciliation-for-correctness path; and lag must be monitored so staleness is visible. |
| Isn't that just a read replica? | No — a replica is schema-identical and inherits the primary's unpartitioned layout, so it gets no pruning. This is a **reshaped, purpose-built** derived table. |
| What does sharding buy that partitioning can't? | **More total CPU, RAM and disk I/O** — you're adding machines, not reorganising files. |
| When is sharding clearly right? | Data exceeds one machine; write throughput spread over many independent keys; a stable evenly-distributed ownership key; read scale past replicas; data-residency compliance; blast-radius isolation. |
| When is sharding clearly wrong? | A single hot row; workloads dominated by cross-shard joins/aggregates; data that fits one node; frequent cross-entity ACID needs; a skewed key; a naive `hash % N` scheme. |
| Does sharding fix a hot pool account? | **No.** One logical account maps to exactly one shard. Use intra-account bucketing or a single-writer queue. |
| What happens to `SUM()` across shards? | **Scatter-gather** — every shard queried, partial results merged in app code. Latency becomes the slowest shard's; former `JOIN`s become application stitching. |
| Which shard-assignment scheme, and why? | **Consistent hashing with virtual nodes** by default (only ~1/N of keys move on a rebalance). **Directory-based** when you need to pin or migrate individual tenants. Never plain `hash % N` if N will change. |
| Cross-shard transfer — how? | **2PC** (atomic, but a dead coordinator blocks participants holding locks — rare at scale) or a **saga** (local transactions plus compensating actions — the common answer). |
| Is a saga compensation a rollback? | **No.** The debit really happened and was really visible; compensation is a *second forward transaction* undoing it. Every step must be idempotent. |
| The order to escalate in? | Index/query tuning → vertical scaling → read replicas → partitioning → CQRS read model → sharding. Never skip rungs; rungs 1–4 keep single-node ACID. |
| One line to close on? | Partitioning and sharding both distribute **across** keys — neither helps when the contention is **on one key**. |

## SDE-2 Interview Priority Checklist

### Must Know (100%)

- **Partitioning vs sharding** — one node vs many, transparent vs app-routed, access-pattern optimisation vs capacity
- **Partition pruning**: the optimizer eliminates partitions the predicate can't match, before any index work
- Why partitioning is faster, **ranked honestly**: page-scan reduction, buffer-pool residency, then tree depth
- **Local indexes**: no global index exists, so a query without the partition key searches every partition and is **slower than unpartitioned**
- **Unique keys must include the partition column** — and how that silently breaks a date-partitioned idempotency table
- `DROP PARTITION` vs `DELETE` for retention — the reason many teams partition at all
- **Partitioning does not fix write contention**; date partitioning concentrates it
- Choose the partition key by the **dominant query pattern**, not by what feels natural
- When **not** to partition, and when **not** to shard (single hot row, cross-shard aggregates, data that fits one node)
- The **CQRS read model** + **CDC**, and why the derived table must never be a correctness dependency
- Cross-shard transactions require **2PC or a saga**, and compensation is not a rollback
- The **escalation ladder**: index → vertical → replicas → partition → read model → shard

### Nice To Know

- `EXPLAIN`'s `partitions:` column as the pruning diagnostic
- Postgres **runtime pruning** (PG 11+) for prepared/parameterised queries
- `DETACH PARTITION CONCURRENTLY` (PG 14+) and detach-to-cold-storage archival
- **Hash vs range vs directory** shard assignment, and consistent hashing with **virtual nodes**
- **Transactional outbox** as the fix for dual-write atomicity
- **Idempotent consumers** — CDC and queues are at-least-once
- **Lag/watermark monitoring** on any derived table
- MySQL: no **foreign keys** on partitioned tables; 8192-partition cap
- **Vitess** (MySQL) and **Citus** (Postgres) as sharding middleware
- Read replica vs purpose-built reshaped table

### Advanced

- The fanout/tree-depth math (`log₅₀₀`) and why buffer-pool residency dominates it
- **Partition-wise joins** when both sides share a partition key
- **Scatter-gather** cost: latency equals the slowest shard, plus app-side merge
- **2PC coordinator failure** leaving participants blocked while holding locks
- **Saga compensation failure** handling — retries, DLQs, durable state machines
- **Hot-shard remediation**: splitting, key salting, pinning a whale tenant via a directory
- Deriving a pruning predicate from a **timestamp embedded in the ID** (UPI RRN)
- Hand-building a **global index table** to keep both retention and point-lookup speed
