Covers Roadmap section 10. [[9. Database Concurrency]] solved contention *inside* one database — rows, locks, MVCC. This note is about coordination when the resource **isn't a row**: a payment gateway, a nightly job, a counter too hot for the database. Every guarantee you relied on gets weaker, and the failure modes stop throwing exceptions.

> [!info] The through-line of this note
> One idea drives everything: **as the lock moves further from the data, it stops being a correctness mechanism.**
>
> 1. Scaling one JVM → many pods **silently deletes** the shared memory `synchronized` depended on (§1). Move the lock to the database and you're safe again — because lock and data commit together.
> 2. The moment the resource lives *outside* the database, you need a **referee** (Redis, etcd, ZooKeeper) — and you hit the one impossibility that shapes this whole note: **you cannot tell a crashed process from a slow one** (§2). Both are silence.
> 3. That forces the referee to expire locks on a timer. Locks become **leases** — and a lease expiring **does not stop the holder** (§5). Two clients can genuinely be inside the critical section, with no bug anywhere.
> 4. So the honest framing: a distributed lock is a **performance optimization** (avoid duplicate work), not a correctness guarantee. Correctness has to live **at the resource** — via **fencing tokens** (§5) or **idempotency** (§7).
> 5. Redis makes it worse in a specific way: it's an **AP** system, so a failover can hand the same lock to two clients while everything looks healthy (§6).
> 6. Then the practical half: which lock service to pick, failing closed, bounding everything, designing the lock away (§8), and getting the Spring wiring right (§9).
>
> One line to anchor everything: **a lease only guarantees that one client *believes* it holds the lock.**

## Short Notes

---

### 1. From One JVM to Many — Why This Note Exists

The requirement never changes — *two operations must not run at once* — but the machinery evaporates as you scale:

| Stage | Situation | Mutual exclusion |
|---|---|---|
| 1 | One JVM, one thread | Nothing is concurrent — no problem |
| 2 | One JVM, many threads | `synchronized (wallet)` — a memory operation, nanoseconds, **absolute** |
| 3 | Many JVMs, one DB | `synchronized` still compiles, still runs, **does nothing** |
| 4 | Resource isn't in the DB | No row to lock → separate lock service, **much weaker** guarantee |

- ⚠️ **Stage 3 is the most common distributed bug in Spring services** — code correct on one instance goes silently wrong when someone sets `replicas: 3`. Nothing throws, nothing logs, tests still pass (they run in one JVM)
- **Stage 3's fix**: move the lock to the one thing all pods share — the database (`FOR UPDATE`, `@Version`, conditional `UPDATE`)

| | `synchronized` | DB row lock | Redis lock |
|---|---|---|---|
| Shared state lives in | Process memory | The database | A separate service |
| If the holder dies | JVM exits, lock gone — **atomic** | Transaction rolls back — **atomic** | Lock **remains held** until TTL |
| Lock and data together? | Yes | **Yes** — same txn | **No** — two systems |
| Can two holders exist? | No | No | **Yes** |

> The decisive property is **"lock and data together."** Once the lock is in Redis and the data is in Postgres, nothing makes those two atomic.

---

### 2. What Makes Distributed Mutual Exclusion Hard

- **No shared memory** — "who holds the lock?" stops being a memory address and becomes a **message**, and messages get delayed, reordered, duplicated, lost
- So you need a **referee** (Redis / ZooKeeper / etcd / DB) — which is a **new dependency** and a **network call** on every acquire
- ⚠️ **A timeout tells you nothing** — your `SET NX` may have succeeded with the response lost in transit. You genuinely don't know if you hold the lock
- ⭐ **The core impossibility**: you **cannot distinguish a crashed process from a slow one**. Both send nothing — a 40 s GC pause, CPU starvation and a dead pod are byte-for-byte identical. This is the practical face of **FLP**

| If a holder goes silent | Consequence |
|---|---|
| **Wait forever** | One crashed pod deadlocks the resource permanently |
| **Reclaim after TTL** | Progress preserved, but the holder **may still be running** |

- Every practical system picks the second → locks become **leases**
- **Why DB locks escape this**: a DB lock is held by a **connection**, not a lease. Client dies → TCP drops → engine rolls back. Lock released **and** work undone in one atomic act

---

### 3. When You Actually Need a Distributed Lock

> **Most of the time, you don't.**

| Scenario | Why the DB can't help |
|---|---|
| Only one pod runs the 2 AM settlement | No row to lock — it's a **process** |
| Rate-limit a merchant to 100 TPS across pods | Counter is too **hot** for a DB row |
| Don't call the PSP refund API twice concurrently | Resource is a **third party** |
| Coordinate cache rebuild / prevent stampede | Nothing in the DB to lock |

- **Rule of thumb**: data in the DB → lock in the DB. Side effects outside the DB → distributed lock **plus** an idempotency key
- If the resource lives in your database, a row lock or conditional `UPDATE` is strictly safer *and* cheaper

---

### 4. Redis Lock Basics

```text
SET lock:payout:123  <random-uuid>  NX  PX 30000
```

| Part | Purpose |
|---|---|
| `NX` | Set only if absent — **this is the mutex** |
| `PX 30000` | TTL — without it, a crash means deadlock forever |
| `<random-uuid>` | **Ownership token** for safe release |

- **Release must be atomic** — check-then-delete in two round trips is a race. Use a Lua compare-and-delete
- ❌ **Broken 1 — `SETNX` + `EXPIRE`**: not atomic. Crash between them → key with **no TTL** → deadlock forever
- ❌ **Broken 2 — blind `DEL`**: no ownership check. If your work overran the TTL you delete *someone else's* lock

---

### 5. TTLs Are Not Safe — the Section That Matters ⭐

```text
What you think you bought:  "only one client is in the critical section"
What you actually bought:   "only one client BELIEVES it is in the critical section"
```

```text
t=0   Client A acquires lock (TTL 30s)
t=0   Client A hits a 40-second stop-the-world GC pause
t=30  Lock expires in Redis
t=31  Client B acquires it ✅ legitimately — it's free
t=40  Client A wakes, BELIEVES it still holds the lock, writes
      → two clients in the critical section. No bug in Redis.
```

- **Lease expiry does not stop the holder** — that's the whole problem
- ⚠️ **Auto-renewal (Redisson watchdog) does NOT fix it** — a paused client can't renew *and* can't be stopped. Rarer, not absent
- ⭐ **Fencing tokens are the actual fix**: issue a **monotonically increasing** token per grant; the **resource** rejects stale ones

```sql
UPDATE payout SET status = 'SENT', fence_token = :token
 WHERE id = :id AND fence_token < :token;   -- stale holder writes 0 rows
```

- Token sources: Redis `INCR`, or ZooKeeper's znode `zxid` (free)
- **Enforcement lives at the resource, not the lock service**

---

### 6. Redis as a Single Point of Failure

Two failure modes, opposite consequences:

**6a — Redis is down.** Every `SET NX` fails, and you must choose:

| Strategy | Behaviour | Consequence |
|---|---|---|
| **Fail-closed** | Refuse the operation | Availability outage. **Correct** |
| **Fail-open** | Proceed unprotected | Full availability. **No mutex** |

- ⚠️ A `try/catch` that logs a warning and continues **is** fail-open — it converts a dependency failure into a financial incident
- For payments → **always fail closed**

**6b — Redis fails over.** Worse, because nothing looks broken:

```text
t0  A: SET lock NX PX → primary says OK ✅
t1  Primary crashes — the lock was NEVER replicated (async!)
t2  Sentinel promotes the replica — no lock key there
t3  B: SET lock NX PX → OK ✅        → two holders, silently
```

- This isn't a misconfiguration — **Redis is AP**, so it can't offer the linearizable register a correct lock needs. `WAIT` narrows the window, it isn't consensus
- **Redlock** (5 independent primaries, majority acquire) raises the bar but stays timing-dependent — Kleppmann vs antirez. At 5 deployments, **etcd or ZooKeeper gives genuinely correct locks**

---

### 7. Idempotency — Correctness Without the Lock

- **Definition**: applying the same request twice has the same effect as applying it once
- **Why it's unavoidable**: a timeout never tells you whether the work happened, so callers **must** retry — and networks, queues and Kafka consumers are all **at-least-once**
- ⭐ "Exactly-once processing" in practice = **at-least-once delivery + an idempotent handler**. There is no other kind

| Operation | Idempotent? |
|---|---|
| `SET status = 'SENT'` | ✅ Yes — same result every time |
| `balance = balance - 100` | ❌ **No** — runs twice, debits twice |
| `INSERT … ON CONFLICT DO NOTHING` | ✅ Yes |
| `UPDATE … WHERE status = 'PENDING'` | ✅ Yes — second call updates 0 rows |

- **Idempotency key**: a caller-generated unique id, stored with a **`UNIQUE` constraint**, written **in the same transaction as the effect**
- A duplicate key violation means *already done* → return the **stored original response**, not just "duplicate"
- **Lock vs idempotency**: a lock stops **concurrent** duplicates; idempotency stops **sequential** ones (retries). Money paths need both
- PSPs expose this directly — Stripe/Razorpay `Idempotency-Key` header makes a double call charge once

---

### 8. Prevention and Mitigation

Layered — no single one is sufficient.

**Choose the right lock service:**

| System | Model | Lock safety | Cost |
|---|---|---|---|
| Redis (single) | AP | Weak — lost on failover | Fastest, ~1 ms |
| Redlock (5 nodes) | AP | Better, still timing-dependent | 5 nodes, 5 RTTs |
| ZooKeeper | CP | Strong — ephemeral znodes | Slower, JVM ops burden |
| etcd | CP | Strong — leases + revisions | Already in k8s |
| Postgres advisory lock | CP | Strong — dies with the connection | Uses existing DB |
| DB row lock | CP | **Strongest** — same transaction | Only for DB resources |

- **Fail closed, explicitly** — plus a circuit breaker and a bulkhead so lock-waiters don't eat the pool
- **Bound everything**: never `lock()`, always `tryLock(wait, lease)`; lease > p99 work time; **never hold a lock across an unbounded network call**
- **Make the critical section safe without the lock**: fencing tokens (§5), idempotency keys (§7), conditional state transitions
- **Design the lock away** — the best option:

| Pattern | How it removes the lock |
|---|---|
| **Partition by key** | All events for a wallet → one Kafka partition → serial by construction |
| **Single-writer / leader** | Elect one instance (etcd lease) to own a shard |
| **Transactional outbox** | State + event in one DB txn → no cross-system coordination |
| **`SKIP LOCKED`** | `SELECT … FOR UPDATE SKIP LOCKED` → the DB does distributed claiming |

---

### 9. Spring Boot — Redisson

- `spring-boot-starter-data-redis` gives you a **client, not a lock** — use **Redisson** (Lua release, watchdog, reentrancy)
- Always `tryLock(waitTime, leaseTime, unit)`; release in a `finally` guarded by `isHeldByCurrentThread()`
- ⚠️ **Lock/transaction ordering is a real bug**:

```text
✅  acquire lock → BEGIN → work → COMMIT → release lock
❌  BEGIN → acquire lock → work → release lock → COMMIT
```

- In the broken order the lock is free **before the writes are visible** → the next node reads stale data → both do the work
- Putting `@Transactional` on the *same method* that acquires the lock produces exactly this — **keep them in separate beans**
- Alternatives: Spring `LockRegistry` (`RedisLockRegistry`, `JdbcLockRegistry`), and **ShedLock** for "run this `@Scheduled` job on one node only"

# Detailed Explanation

---

## From One JVM to Many — Why This Note Exists

The problem never changes:

> Two operations must not run at once.

What changes is whether the machinery you're relying on still exists. Watch it disappear.

### Stage 1 — One JVM, one thread

No problem exists. Nothing is concurrent.

### Stage 2 — One JVM, many threads

Threads share heap memory, so mutual exclusion is a **memory operation**:

```java
synchronized (wallet) { wallet.debit(200); }
```

Every thread sees the same lock object at the same memory address, and the CPU guarantees only one wins the CAS.

```text
Cost:   nanoseconds
Safety: absolute
```

See [[1. Core Fundamentals]].

### Stage 3 — Many JVMs, one database

You scale to 3 pods for availability. `synchronized` still compiles. It still runs. It **does nothing useful.**

Each pod locks its own heap object, so three threads — one per pod — enter the critical section simultaneously.

> [!warning] This is the most common distributed-systems bug in Spring services
> Code that was correct on one instance becomes silently wrong the moment someone sets `replicas: 3`. Nothing throws. Nothing logs. Tests still pass, because they run in one JVM. The only symptom is duplicated work in production — a double payout, a double email, two settlement runs.

**The fix:** move the lock to the one thing all pods share — the database. `SELECT … FOR UPDATE`, a `@Version` column, or an atomic conditional `UPDATE`. See [[9. Database Concurrency]] §9.

This is genuinely safe, and it's worth being precise about *why*: **lock and data are in the same transaction.** If the transaction dies, the lock dies with it, atomically.

### Stage 4 — The resource isn't in the database

Now you need to stop two pods calling a payment gateway simultaneously, or ensure only one pod runs the 2 AM settlement. **There is no row to lock.** So you introduce a separate lock service — and inherit a far weaker guarantee.

### What you lose at each step

| | `synchronized` | DB row lock | Redis lock |
|---|---|---|---|
| Shared state lives in | Process memory | The database | A separate service |
| If the holder dies | JVM exits, lock gone — **atomic** | Transaction rolls back — **atomic** | Lock **remains held** until TTL |
| Lock and data together? | Yes | **Yes** — same txn | **No** — two systems |
| Can two holders exist? | No | No | **Yes** |
| Cost | ~nanoseconds | ~1 ms, in-transaction | ~1 ms + network + a new dependency |

> The decisive property is **"lock and data together."** A DB lock is safe because releasing the lock and committing the data are the *same event*. Once the lock lives in Redis and the data lives in Postgres, nothing makes those two atomic — and every problem in the rest of this note follows from that gap.

---

## What Makes Distributed Mutual Exclusion Hard

### No shared memory — you need a referee

In one JVM:

```text
"Who holds the lock?" = a value at a memory address
```

Across machines:

```text
No such address — only messages
```

And messages can be delayed, reordered, duplicated, or lost. So mutual exclusion needs a **referee**: Redis, ZooKeeper, etcd, or a database.

That introduces two new properties, both of which cause outages:

1. The referee is a **new dependency** — if it's unreachable, nobody makes progress.
2. Every lock operation is a **network call** — which can time out.

> [!warning] A timeout tells you nothing
> Your `SET NX` may have **succeeded on the server**, with only the response lost in transit. From the client's side, "it worked and I didn't hear back" and "it never arrived" are indistinguishable. You genuinely do not know whether you hold the lock — which means the retry path has to assume you might.

### The core impossibility

> **You cannot distinguish a process that has crashed from one that is merely slow.**

From the referee's point of view:

```text
Client A crashed                 Client A is alive but stalled
  → sends nothing                  → sends nothing
                                     (40 s GC pause, CPU starvation,
                                      swap thrashing, network partition)
```

Byte-for-byte identical: **silence**. And no timeout reliably separates the two — pick it short and you evict healthy clients, pick it long and a crashed client blocks everyone. This is the practical face of the **FLP impossibility result**.

### This forces leases — and reintroduces the problem

The referee has to choose what to do when a holder goes silent:

| Choice | Consequence |
|---|---|
| **Wait forever** | One crashed pod deadlocks the resource permanently |
| **Reclaim after a TTL** | Progress is preserved, but the holder **may still be running** |

Every practical system chooses the second. Locks stop being locks and become **leases** — granted for a bounded time.

> **Expiring the lease does not stop the holder.** The referee can revoke its *record* of the lock. It cannot reach into a paused JVM and stop the work. That single sentence is §5.

### Why DB locks escaped this

A database lock isn't a lease — it's held by a **connection**.

If the client dies, the TCP connection drops, and the engine rolls the transaction back:

```text
Lock released + work undone = one atomic act
```

There is **no window** in which the lock is free but the work is still in flight. That is exactly the guarantee you give up when the lock moves out of the database, and no amount of Redis tuning buys it back.

---

## When You Actually Need a Distributed Lock

> **Most of the time, you don't.**

If the resource lives in your database, use a row lock or a conditional `UPDATE`. It is strictly safer *and* cheaper — no new dependency, no new failure mode. You reach for Redis only when the resource is genuinely **outside** the database:

| Scenario | Why the DB can't help |
|---|---|
| Only one pod runs the 2 AM settlement job | No row to lock — it's a **process**, not data |
| Rate-limit a merchant to 100 TPS across pods | The counter is far too hot for a DB row |
| Don't call the PSP refund API twice concurrently | The resource is a **third-party system** |
| Coordinate a cache rebuild / prevent a stampede | There's nothing in the DB to lock |

> **Rule of thumb:** Data in the DB → lock in the DB. Side effects outside the DB → distributed lock **plus** an idempotency key (§7). The lock reduces duplicate work; the idempotency key is what actually makes it correct.

---

## Redis Lock Basics

### The correct implementation

```text
SET lock:payout:123  <random-uuid>  NX  PX 30000
```

Three parts, all mandatory:

| Part | Purpose |
|---|---|
| `NX` | Set only if absent — **this is the mutex** |
| `PX 30000` | TTL — without it, a crashed holder deadlocks the key forever |
| `<random-uuid>` | Ownership token, so you can release **only your own** lock |

### Release must be atomic

Check-then-delete over two round trips is a race — the lock can expire and be re-acquired between your `GET` and your `DEL`. Do it in a Lua script, which Redis executes atomically:

```lua
-- compare-and-delete, executed atomically by Redis
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

### Two classic broken versions

**Broken 1 — non-atomic set + expire:**

```text
❌  SETNX lock 1
    EXPIRE lock 30
```

Two commands, not atomic. Crash between them and the key exists with **no TTL** — a deadlock that lasts until a human notices.

**Broken 2 — blind delete:**

```text
❌  DEL lock
```

No ownership check. If your work overran the TTL, your lock already expired and someone else acquired it — and you have just deleted **their** lock. Now a third client can acquire it too, and three clients are in the critical section. This is why the random UUID exists.

---

## TTLs Are Not Safe — the Section That Matters ⭐

This is what senior interviews actually probe, and the point where most people's mental model breaks.

### The guarantee is weaker than you think

```text
What you think you bought:  "only one client is in the critical section"
What you actually bought:   "only one client BELIEVES it is in the critical section"
```

### The scenario

```text
t=0   Client A acquires the lock (TTL 30 s)
t=0   Client A hits a 40-second stop-the-world GC pause
t=30  The lock expires in Redis
t=31  Client B acquires the same lock ✅ (legitimately — it's free)
t=31  Client B starts processing payout 123
t=40  Client A wakes up, BELIEVES it still holds the lock
t=40  Client A writes to payout 123

→ Two clients in the critical section. No bug in Redis.
```

Read that last line again — **nothing malfunctioned**. Redis did exactly what it promised, A did exactly what it was told, B acquired a genuinely free lock. The mutual exclusion still broke.

> A lock with a timeout **cannot guarantee mutual exclusion**, because the lock expiring does not stop the holder from working.

A GC pause is the textbook trigger, but it's far from the only one: CPU starvation on a noisy node, swap thrashing, a hypervisor stealing time, a network partition that heals, or simply a debugger breakpoint. Any of them produce the same shape.

### Auto-renewal does not fix this

Redisson's watchdog renews the lease every 10 s while the holder is alive. That's genuinely useful — it stops a long-but-healthy job from losing its lock. But think about what fails:

```text
A paused client can't renew  AND  can't be stopped
```

The renewal thread is inside the same JVM that's paused. It makes the window **rarer, not absent** — and a race you've made rare is a race that now fails at 3 AM once a quarter instead of in your integration tests.

### Fencing tokens — the actual fix

Issue a **monotonically increasing token** with every lock grant, and make the **protected resource** reject stale ones:

```text
Client A acquires → token 33
Client A pauses
Client B acquires → token 34
Client B writes with token 34   → accepted, resource records 34
Client A wakes,  writes token 33 → REJECTED (33 < 34)
```

The critical design point: **enforcement lives at the resource, not the lock service.** The lock service can't help — it already believes A's lease is gone. Only the thing being written to can adjudicate.

With a database resource that's just a `WHERE` clause — the same conditional-update trick from [[9. Database Concurrency]] §9:

```sql
UPDATE payout
   SET status = 'SENT', fence_token = :token
 WHERE id = :id
   AND fence_token < :token;      -- stale holder writes 0 rows
```

Where the token comes from:

| Source | Token |
|---|---|
| Redis | `INCR` on a counter key |
| ZooKeeper | The znode `zxid` — monotonic, free |
| Database | A sequence |

> 💡 **Interview**: are Redis locks safe? → A distributed lock is a **performance optimization** — it avoids duplicate work in the common case. It is **not** a correctness guarantee, because a lease expiring can't stop a paused holder. Correctness has to come from the resource: a fencing token, or idempotency.

---

## Redis as a Single Point of Failure

Two distinct failure modes with opposite consequences — and the dangerous one is not the obvious one.

### Redis is down

Every `SET NX` fails. Your code must choose, and *not choosing* is itself a choice:

| Strategy | Behaviour | Consequence |
|---|---|---|
| **Fail-closed** | Lock unavailable → refuse the operation | Availability outage. **Correct.** |
| **Fail-open** | Lock unavailable → proceed unprotected | Full availability. **No mutex.** |

> [!warning] A `try/catch` that logs and continues *is* fail-open
> ```java
> try { lock.tryLock(...); } catch (Exception e) { log.warn("lock failed", e); }
> doTheWork();   // ❌ runs unprotected on every pod, during a Redis outage
> ```
> This is the single most common way a Redis outage becomes a **financial** incident rather than an availability one. For payments, always **fail closed**.

### Redis fails over — the dangerous one

Worse than an outage, because **nothing looks broken**. Redis replication is asynchronous:

```text
t0  Client A: SET lock NX PX 30000 → primary says OK ✅
t1  Primary crashes — the lock was NEVER replicated
t2  Sentinel promotes the replica. The new primary has no lock key.
t3  Client B: SET lock NX PX 30000 → OK ✅

→ A and B both hold "the" lock. Both believe they're exclusive.
```

No error is raised anywhere. Both clients got a successful acquire. Your metrics look fine.

> This is not a misconfiguration you can tune away. Redis is an **AP** system — it chose availability under partition, so it cannot promise the **linearizable register** that a correct lock requires. `WAIT numreplicas timeout` narrows the window, but waiting for replicas is not consensus.

### Redlock — and why it's contested

Redis's own answer: run **5 independent primaries** (no replication between them), acquire on a **majority (3)**, and only consider the lock held if acquisition took less than the TTL.

| Side | Argument |
|---|---|
| **Martin Kleppmann** | Depends on bounded clock drift and bounded pauses. A GC pause or NTP jump breaks it. Use fencing tokens. |
| **Salvatore (antirez)** | The timing assumptions are reasonable in practice, and it's meaningfully stronger than single-node Redis. |

> **The interview position:** Redlock raises the bar but doesn't remove the need for fencing. And it costs **five** Redis deployments — at which point etcd or ZooKeeper gives you genuinely correct locks for comparable operational effort. Say that and you've answered the question and the follow-up.

---

## Idempotency — Correctness Without the Lock

Fencing tokens (§5) are one way to push correctness down to the resource. **Idempotency** is the other, and it's the one you'll use far more often — because it also solves a problem locks never touch.

> **Idempotent**: applying the same request twice has the same effect as applying it once.

### Why retries are not optional

Go back to §2: a timeout tells you nothing. The caller cannot know whether the work happened, so the caller **must** retry — and every layer between you and it is **at-least-once** by design:

- HTTP clients retry on timeout and 5xx.
- Message queues redeliver on missing ack.
- Kafka consumers replay from the last committed offset after a rebalance or restart.
- Your own scheduler reruns a job that appeared to fail.

You cannot switch this off, because the alternative — at-most-once — silently drops work.

> ⭐ **"Exactly-once processing" is at-least-once delivery plus an idempotent handler.** There is no other implementation of it. When someone claims exactly-once, that's what they've built.

### Which operations are already idempotent

| Operation | Idempotent? | Why |
|---|---|---|
| `SET status = 'SENT'` | ✅ | Absolute assignment — same result every time |
| `balance = balance - 100` | ❌ | **Relative** — runs twice, debits twice |
| `INSERT … ON CONFLICT DO NOTHING` | ✅ | The second insert is a no-op |
| `UPDATE … WHERE status = 'PENDING'` | ✅ | The second call matches 0 rows |
| `POST /payments` (no key) | ❌ | Creates a second payment |

The pattern: **absolute assignments and guarded transitions are idempotent; relative arithmetic is not.** This is the same distinction as [[9. Database Concurrency]] §9 — except there the guard protected against *concurrent* writers, and here it protects against *the same writer twice*.

### The idempotency key pattern

For anything that isn't naturally idempotent, make it so with a caller-supplied key:

```sql
CREATE TABLE idempotency (
    key         VARCHAR(64) PRIMARY KEY,   -- UNIQUE is doing the work
    response    JSONB,
    created_at  TIMESTAMPTZ NOT NULL
);
```

```java
@Transactional                                  // key + effect commit together
public PayoutResponse payout(String idempotencyKey, PayoutRequest req) {
    try {
        idempotencyRepo.insert(idempotencyKey);      // UNIQUE violation = already done
    } catch (DuplicateKeyException e) {
        return idempotencyRepo.findResponse(idempotencyKey);  // ✅ return the ORIGINAL response
    }
    PayoutResponse res = doTheActualPayout(req);
    idempotencyRepo.saveResponse(idempotencyKey, res);
    return res;
}
```

Three details that matter:

1. **The key insert and the effect must be in the same transaction.** If they aren't, a crash between them leaves you with a key recorded and no work done — permanently blocking a legitimate retry.
2. **Store the response, not just the key.** A retry should get the *same answer* ("payout `p_123` succeeded"), not a bare "duplicate" the caller can't act on.
3. **Expire old keys** on a TTL or a nightly sweep, or the table grows forever.

This is exactly what payment providers expose — Stripe's and Razorpay's `Idempotency-Key` header means a double-submitted charge bills once.

### How idempotency and locks divide the work

They cover **different** failure modes, which is why money paths need both:

| | Prevents | Failure mode |
|---|---|---|
| **Distributed lock** | Two workers acting **at the same time** | Concurrent duplicates |
| **Idempotency key** | The same work being applied **twice over time** | Retries, redelivery, replays |

A lock does nothing about a retry that arrives ten seconds after the first attempt completed and released. An idempotency key does nothing to stop two pods entering the critical section simultaneously — though if the key insert is the *first* thing in the transaction, the database's unique index will serialise them for you.

> 💡 **Interview**: how do you guarantee a payment isn't processed twice? → An idempotency key with a unique constraint, written in the **same transaction** as the effect, returning the stored original response on conflict. The distributed lock is an optimization on top to avoid wasted concurrent work — the unique constraint is what makes it correct.

## Prevention and Mitigation

Layered. No single one of these is sufficient.

### Choose the right lock service

| System | Model | Lock safety | Cost |
|---|---|---|---|
| Redis (single) | AP | Weak — lost on failover | Fastest, ~1 ms |
| Redlock (5 nodes) | AP | Better, still timing-dependent | 5 nodes, 5 RTTs |
| ZooKeeper | CP | Strong — ephemeral znodes | Slower, JVM ops burden |
| etcd | CP | Strong — leases + revisions | Already in k8s |
| Postgres advisory lock | CP | Strong — dies with the connection | Uses existing DB |
| DB row lock | CP | **Strongest** — same transaction | Only for DB resources |

> **The pragmatic path:** don't introduce ZooKeeper for one nightly job. If you already run Postgres, `pg_try_advisory_lock` is a **correct** distributed lock with **zero new infrastructure** — it's connection-scoped, so it dies with the client exactly like a row lock.

### Fail closed, explicitly

```java
boolean acquired;
try {
    acquired = lock.tryLock(2, 30, TimeUnit.SECONDS);
} catch (RedisConnectionFailureException e) {
    // Redis is down. Do NOT proceed.
    throw new ServiceUnavailableException("Lock service unavailable", e);
}
if (!acquired) {
    throw new ResourceBusyException("Operation already in progress");
}
```

Pair it with a **circuit breaker** (Resilience4j) so you stop hammering a dead Redis, and a **bulkhead** so threads waiting on locks can't consume the whole pool ([[4. Executors and Thread Pools]] §16).

### Bound everything

| Parameter | Rule |
|---|---|
| Acquire timeout | Never `lock()`, always `tryLock(wait, lease)` |
| Lease time | Must exceed worst-case work duration (p99) |
| Network calls | **Never hold a lock across an unbounded call** |

> An unbounded wait turns one slow holder into cascading thread-pool exhaustion — the distributed version of the "no I/O under a lock" rule from [[3. Synchronization]] §2.

### Make the critical section safe WITHOUT the lock

Assume the lock will fail, and ensure the outcome is still correct:

| Technique | How it works |
|---|---|
| **Fencing tokens** (§5) | Monotonic number with the lock; the resource rejects stale tokens |
| **Idempotency keys** (§7) | Unique constraint on the key → a duplicate inserts nothing |
| **Conditional state transitions** | `UPDATE SET status='SENT' WHERE status='PENDING'` → 0 rows means you were beaten |
| **PSP idempotency** | Stripe/Razorpay `Idempotency-Key` header → a double call charges once |

### Design the lock away

The best distributed lock is the one you never take:

| Pattern | How it eliminates the lock |
|---|---|
| **Partition by key** | Route all events for a wallet to one Kafka partition → serial **by construction**, no lock at all |
| **Single-writer / leader** | Elect one instance (etcd lease) to own a shard |
| **Transactional outbox** | State + event in one DB transaction → no cross-system coordination. See [[11. Transaction Boundaries]] |
| **`SKIP LOCKED`** | `SELECT … FOR UPDATE SKIP LOCKED` → the database handles distributed claiming. No Redis at all |

Partition-by-key is the one worth internalising: it converts a **concurrency** problem into a **routing** problem, and routing problems don't have GC pauses.

## Spring Boot — Redisson

`spring-boot-starter-data-redis` gives you a **client**, not a lock. Use **Redisson** for a correct implementation — it handles the Lua release, the watchdog, and reentrancy for you.

```java
@Service
@RequiredArgsConstructor
public class SettlementService {

    private final RedissonClient redisson;
    private final PayoutService payoutService;

    public void runSettlement(String merchantId) {
        RLock lock = redisson.getLock("settlement:" + merchantId);
        boolean acquired = false;
        try {
            // waitTime=5s (fail fast), leaseTime=120s (> p99 work time)
            acquired = lock.tryLock(5, 120, TimeUnit.SECONDS);
            if (!acquired) {
                throw new ResourceBusyException(
                    "Settlement already running for " + merchantId);
            }
            payoutService.settle(merchantId);  // @Transactional lives HERE, in another bean
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException(e);
        } finally {
            if (acquired && lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

### Lock/transaction ordering — a critical bug

The lock must be acquired **outside** the transaction and released **after** commit:

```text
✅  acquire lock → BEGIN → work → COMMIT → release lock
❌  BEGIN → acquire lock → work → release lock → COMMIT
```

In the second ordering there's a window where:

```text
The lock is free, but the writes aren't visible yet
→ the next node acquires the lock and reads stale data
→ both nodes do the work
```

You've paid for a distributed lock and still got duplicate execution.

> [!warning] `@Transactional` on the locking method causes exactly this
> Spring's transaction proxy wraps the **whole method**, so `BEGIN` happens before your first line — including `tryLock`. The transaction then commits after `unlock()` in the `finally`. That's the broken ordering, produced by an annotation that looks harmless.
>
> **Fix:** keep them in separate beans — the lock in the outer service, `@Transactional` on the inner one, exactly as in the snippet above. (Same proxy mechanics as `@Async` self-invocation — [[4. Executors and Thread Pools]] §15.)

### Alternatives

| Library | Use case |
|---|---|
| Spring `LockRegistry` | Swap Redis for DB without touching your code |
| `RedisLockRegistry` | Redis-backed distributed locks |
| `JdbcLockRegistry` | DB-backed distributed locks |
| **ShedLock** | Run a `@Scheduled` job on only one node — the single most common real need |

## Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| Why doesn't `synchronized` work across pods? | Each JVM locks its own heap object — no shared memory, no shared lock. |
| Why is a DB lock safer than Redis? | Lock and data live in the **same transaction** — the holder dying releases both atomically. |
| Why does a distributed lock need a TTL? | A crashed holder can't release, and you can't tell crashed from slow, so the lock must self-expire. |
| What's the core impossibility? | You cannot distinguish a crashed process from a slow one — both are silence. (FLP.) |
| What does a lease actually guarantee? | Only that one client *believes* it holds the lock. |
| How do you implement a Redis lock correctly? | `SET key <uuid> NX PX <ttl>`, plus a Lua compare-and-delete to release. |
| Why the random UUID? | Ownership — without it you can delete a lock someone else has since acquired. |
| Why is `SETNX` + `EXPIRE` wrong? | Not atomic — a crash between them leaves a key with no TTL, i.e. a permanent deadlock. |
| Walk me through the GC-pause scenario. | A holds the lock, pauses 40 s, the 30 s TTL expires, B acquires legitimately, A wakes believing it still holds it — two writers, no bug anywhere. |
| Does Redisson's watchdog fix that? | No. A paused client can't renew and can't be stopped — it makes the window rarer, not absent. |
| What's a fencing token? | A monotonic number issued with the lock; the **resource** rejects any write carrying a lower token. |
| Where must fencing be enforced? | At the resource, not the lock service — the lock service already thinks the stale lease is gone. |
| Redis goes down — what happens? | You choose: fail-closed (outage, correct) or fail-open (no mutex). For money paths, fail closed. |
| Is a try/catch-and-continue fail-open? | Yes — and it converts a Redis outage into a financial incident. |
| Redis fails over — what happens? | Replication is async, so the lock may not have replicated; the new primary hands it out again. Two holders, silently, with no error. |
| Why can't Redis give a correct lock? | It's an **AP** system — it can't provide the linearizable register a correct lock requires. |
| Is Redlock safe? | Stronger than single-node, but it assumes bounded clock drift and pauses. Kleppmann says that's unsafe; fence regardless. At 5 nodes, use etcd/ZooKeeper. |
| Redis vs ZooKeeper for locks? | Redis = AP, fast, unsafe on failover. ZK/etcd = CP, correct, slower and heavier to operate. |
| Cheapest *correct* distributed lock? | `pg_try_advisory_lock`, or `SELECT … FOR UPDATE SKIP LOCKED` — no new infrastructure. |
| What is idempotency? | Applying the same request twice has the same effect as applying it once. |
| Why is idempotency mandatory in distributed systems? | Timeouts are ambiguous, so callers retry, and queues/Kafka are at-least-once. Duplicates are guaranteed. |
| Is "exactly-once" real? | Only as at-least-once delivery **plus** an idempotent handler. There's no other implementation. |
| Is `balance = balance - 100` idempotent? | No — it's relative. `SET status = 'SENT'` is, because it's an absolute assignment. |
| How do you implement an idempotency key? | Unique constraint on the key, inserted in the **same transaction** as the effect; on conflict return the stored original response. |
| Lock vs idempotency key — which do you need? | Both. The lock prevents **concurrent** duplicates; the key prevents duplicates **over time** (retries, redelivery). |
| How do you avoid needing a lock at all? | Partition by key (Kafka), single-writer/leader election, conditional state transitions, transactional outbox, `SKIP LOCKED`. |
| Where does the lock go relative to the transaction? | Acquire **before** `BEGIN`, release **after** `COMMIT`. The reverse frees the lock before writes are visible. |
| What breaks if `@Transactional` is on the locking method? | Spring's proxy starts the transaction before `tryLock` and commits after `unlock` — the broken ordering. Split into two beans. |
