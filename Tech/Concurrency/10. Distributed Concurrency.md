# Distributed Concurrency

Covers Roadmap section 10. [[9. Database Concurrency]] solved contention *inside* one database. This note is about coordination when the resource isn't a row.

---

# Quick Reference Summary

## The Core Truth

> A distributed lock is a **performance optimization**, not a correctness mechanism.

> You cannot distinguish a crashed process from a slow one. Both are just silence.

## Lock Safety Comparison

| Lock Type       | Where It Lives  | If Holder Dies                     | Two Holders Possible? |
| --------------- | --------------- | ---------------------------------- | --------------------- |
| `synchronized`  | Process memory  | JVM exits → lock gone (atomic)     | No                    |
| DB row lock     | Database        | Transaction rolls back (atomic)    | No                    |
| Redis lock      | Separate service| Lock remains held until TTL expires| **Yes**               |

## When to Use What

| Resource Location               | Lock Strategy                            |
| -------------------------------- | ---------------------------------------- |
| Data in the database             | DB lock (`FOR UPDATE`, version column)   |
| Process coordination (cron jobs) | Distributed lock (Redis / etcd)          |
| Third-party API (payment gateway)| Distributed lock + idempotency key       |
| Hot counter / rate limiter       | Redis atomic ops                         |

## Lock Service Comparison

| System                 | Model | Lock Safety                    | Cost                  |
| ---------------------- | ----- | ------------------------------ | --------------------- |
| Redis (single)         | AP    | Weak — lost on failover        | Fastest, ~1ms         |
| Redlock (5 nodes)      | AP    | Better, still timing-dependent | 5 nodes, 5 RTTs       |
| ZooKeeper              | CP    | Strong — ephemeral znodes      | Slower, JVM ops burden|
| etcd                   | CP    | Strong — leases + revisions    | Already in k8s        |
| Postgres advisory lock | CP    | Strong — dies with connection  | Uses existing DB      |
| DB row lock            | CP    | Strongest — same transaction   | Only for DB resources |

## The Three Rules

> 1. **Never fail open** on a lock service outage in a money path.
> 2. **Never rely on a distributed lock for correctness** — fence it or make the operation idempotent.
> 3. **If the resource is in your database, lock it in your database.**

## One-Liner Answers

> **Why not `synchronized` across pods?** — Each JVM locks its own heap object. No shared memory = no shared lock.

> **Why DB lock is safer than Redis?** — Lock and data are in the same transaction. Holder dying releases both atomically.

> **Why TTL?** — Crashed holder can't release. Can't tell crashed from slow. Must self-expire.

> **Redis failover danger?** — Async replication. Lock may not have replicated. Two holders, silently.

> **Real correctness?** — Fencing tokens, idempotency keys, conditional state transitions at the resource.

# 1. From One JVM to Many — Why This Note Exists

The problem

> Two operations must not run at once.

Watch what happens as the system grows.

---

## Stage 1 — One JVM, One Thread

No problem exists.

Nothing is concurrent.

---

## Stage 2 — One JVM, Many Threads

Threads share heap memory.

Mutual exclusion is a memory operation.

```java
synchronized (wallet) { wallet.debit(200); }
```

Every thread sees the same lock object at the same memory address.

CPU guarantees only one wins the CAS.

```
Cost: nanoseconds
Safety: absolute
```

See [[1. Core Fundamentals]].

---

## Stage 3 — Many JVMs, One Database

Scale to 3 pods for availability.

`synchronized` still compiles.

Still runs.

**Does nothing useful.**

Each pod locks its own heap object.

Three threads, one per pod, enter the critical section simultaneously.

> This is the most common distributed-systems bug in Spring services. Code that was correct on one instance becomes silently wrong when someone sets `replicas: 3`. Nothing throws. Nothing logs. Tests still pass (they run in one JVM).

### The Fix

Move the lock to the one thing all pods share — the database.

`SELECT ... FOR UPDATE`, `@Version` column, or atomic `UPDATE`.

See [[9. Database Concurrency]].

> This is genuinely safe because lock and data are in the same transaction. If the transaction dies, the lock dies with it — atomically.

---

## Stage 4 — The Resource Isn't in the Database

Now you need to

* Stop two pods calling a payment gateway simultaneously
* Ensure only one pod runs the 2 AM settlement

There is no row to lock.

> You introduce a separate lock service (Redis) and inherit a much weaker guarantee.

---

## What You Lose at Each Step

|                           | `synchronized`  | DB Row Lock         | Redis Lock               |
| ------------------------- | --------------- | ------------------- | ------------------------ |
| Shared state lives in     | Process memory  | The database        | A separate service       |
| If the holder dies        | JVM exits, lock gone — **atomic** | Transaction rolls back — **atomic** | Lock **remains held** until TTL |
| Lock and data together?   | Yes             | **Yes** — same txn  | **No** — two systems     |
| Can two holders exist?    | No              | No                  | **Yes**                  |
| Cost                      | ~nanoseconds    | ~1ms, in-transaction| ~1ms + network + new dep |

> The decisive property is **"lock and data together."** A DB lock is safe because releasing the lock and committing the data are the *same event*. Once the lock lives in Redis and the data lives in Postgres, nothing makes those two atomic.

---

# 2. What Makes Distributed Mutual Exclusion Hard

---

## 2.1 No Shared Memory — Need a Referee

In one JVM

```
"Who holds the lock?" = value at a memory address
```

Across machines

```
No such address — only messages
```

Messages can be delayed, reordered, duplicated, or lost.

So mutual exclusion needs a **referee**.

```
Redis / ZooKeeper / etcd / Database
```

This creates two new properties

1. The referee is a **new dependency** — if unreachable, no progress
2. Every lock operation is a **network call** — can time out

> A timeout tells you nothing. Your `SET NX` may have succeeded on the server with the response lost in transit. You genuinely don't know whether you hold the lock.

---

## 2.2 The Core Impossibility

> **You cannot distinguish a process that has crashed from one that is merely slow.**

From the referee's point of view

```
Client A crashed                Client A is alive but stalled
  → sends nothing                 → sends nothing
                                    (40s GC pause, CPU starvation,
                                     swap thrashing, network partition)
```

Byte-for-byte identical — silence.

No timeout reliably separates the two cases.

This is the practical face of the **FLP impossibility result**.

---

## 2.3 This Forces Leases — And Reintroduces the Problem

The referee must choose

| If a holder goes silent | Consequence                                         |
| ----------------------- | --------------------------------------------------- |
| **Wait forever**        | One crashed pod deadlocks the resource permanently  |
| **Reclaim after TTL**   | Progress preserved, but holder may still be running |

Every practical system chooses the second.

Locks become **leases** — granted for a bounded time.

> Expiring the lease does not stop the holder.

### Why DB Locks Escaped This

A database lock is held by a **connection**, not a lease.

If the client dies → TCP connection drops → engine rolls back.

```
Lock released + work undone = one atomic act
```

No window where lock is free but work is still in flight.

> That's the guarantee you give up when the lock moves out of the database. No amount of Redis tuning buys it back.

---

# 3. When You Actually Need a Distributed Lock

> **Most of the time, you don't.**

If the resource lives in your database → use a row lock or conditional UPDATE.

You reach for Redis only when the resource is **outside** the database.

| Scenario                                      | Why the DB Can't Help            |
| --------------------------------------------- | -------------------------------- |
| Only one pod runs the 2 AM settlement job     | No row to lock — it's a process  |
| Rate-limit a merchant to 100 TPS across pods  | Counter is too hot for a DB row  |
| Don't call PSP refund API twice concurrently  | Resource is a third party system |
| Coordinate cache rebuild / prevent stampede   | Nothing in the DB to lock        |

> **Rule of thumb:** Data in DB → lock in DB. Side effects outside DB → distributed lock **plus** idempotency key.

# 4. Redis Lock Basics

---

## 4.1 The Correct Implementation

```
SET lock:payout:123  <random-uuid>  NX  PX 30000
```

Three parts, all mandatory

| Part             | Purpose                                   |
| ---------------- | ----------------------------------------- |
| `NX`             | Set only if absent — this IS the mutex    |
| `PX 30000`       | TTL — without it, crash = deadlock forever|
| `<random-uuid>`  | Ownership token for safe release          |

### Release Must Be Atomic

Check-then-delete in two round trips is a race.

Use Lua script

```lua
-- compare-and-delete, executed atomically by Redis
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

---

## 4.2 Two Classic Broken Versions

### Broken Version 1 — Non-Atomic Set + Expire

```
❌  SETNX lock 1
    EXPIRE lock 30
```

Not atomic.

Crash between the two commands → key has **no TTL** → deadlock forever.

---

### Broken Version 2 — Blind Delete

```
❌  DEL lock
```

No ownership check.

If your work overran the TTL

```
Your lock expired → someone else owns it → you deleted THEIR lock
```

Now three clients are in the critical section.

---

# 5. The Fundamental Problem — TTLs Are Not Safe

This is the most important section. What senior interviews actually probe.

---

## The Guarantee Weakens

```
What you think you bought:  "only one client is in the critical section"
What you actually bought:   "only one client BELIEVES it is in the critical section"
```

---

## The Scenario

```
t=0   Client A acquires lock (TTL 30s)
t=0   Client A hits 40-second stop-the-world GC pause
t=30  Lock expires in Redis
t=31  Client B acquires the same lock ✅ (legitimately — it's free)
t=31  Client B starts processing payout 123
t=40  Client A wakes, BELIEVES it still holds the lock
t=40  Client A writes to payout 123

→ Two clients in the critical section. No bug in Redis.
```

> A lock with a timeout **cannot guarantee mutual exclusion** because the lock expiring does not stop the holder from working.

---

## Auto-Renewal Does NOT Fix This

Redisson's watchdog renews the lease every 10s.

Reduces the frequency.

But a paused client

```
Can't renew AND can't be stopped
```

> Makes the window rarer, not absent.

---

## 5.1 Fencing Tokens — The Actual Fix

Issue a **monotonically increasing token** with every lock grant.

Make the **protected resource** reject stale tokens.

```
Client A acquires → token 33
Client A pauses
Client B acquires → token 34
Client B writes with token 34   → accepted, resource records 34
Client A wakes,  writes token 33 → REJECTED (33 < 34)
```

Enforcement lives at the resource, not the lock service.

With a DB resource

```sql
UPDATE payout
   SET status = 'SENT', fence_token = :token
 WHERE id = :id
   AND fence_token < :token;      -- stale holder writes 0 rows
```

How to get the token

| Source     | Token              |
| ---------- | ------------------ |
| Redis      | `INCR` counter     |
| ZooKeeper  | znode `zxid` (free)|

> A distributed lock is a **performance optimization** (avoid duplicate work), not a **correctness guarantee**. Correctness must come from the resource.

# 6. Redis as a Single Point of Failure

Two distinct failure modes with opposite consequences.

---

## 6.1 Redis is Down

Every `SET NX` fails.

Your code must choose

| Strategy         | Behaviour                               | Consequence                        |
| ---------------- | --------------------------------------- | ---------------------------------- |
| **Fail-closed**  | Lock unavailable → refuse the operation | Availability outage. **Correct.**  |
| **Fail-open**    | Lock unavailable → proceed unprotected  | Full availability. **No mutex.**   |

> A `try/catch` around lock acquisition that logs a warning and continues **IS** fail-open. Under a Redis outage this converts a dependency failure into a financial incident.

For payments → **always fail closed**.

---

## 6.2 Redis Fails Over — The Dangerous One

Worse than an outage because **nothing looks broken**.

Redis replication is asynchronous.

```
t0  Client A: SET lock NX PX 30000 → primary says OK ✅
t1  Primary crashes — the lock was NEVER replicated
t2  Sentinel promotes the replica. New primary has no lock key.
t3  Client B: SET lock NX PX 30000 → OK ✅

→ A and B both hold "the" lock. Both believe they're exclusive.
```

> This is not a misconfiguration. Redis is an **AP** system — it chose availability, so it cannot promise the linearizable register a correct lock requires.

`WAIT numreplicas timeout` narrows the window but is still not consensus.

---

## 6.3 Redlock — And Why It's Contested

Redis's own answer

Run **5 independent primaries** (no replication between them).

Acquire on a **majority (3)**.

Only consider lock held if acquisition took less than the TTL.

### The Debate

| Side                        | Argument                                                            |
| --------------------------- | ------------------------------------------------------------------- |
| **Martin Kleppmann**        | Depends on bounded clock drift and pauses. GC/NTP breaks it. Use fencing. |
| **Salvatore (antirez)**     | Timing assumptions are reasonable. Meaningfully stronger than single-node. |

> **Interview position:** Redlock raises the bar but doesn't remove the need for fencing. It also costs 5 deployments — at that point etcd or ZooKeeper gives genuinely correct locks.

---

# 7. Prevention and Mitigation

Layered — no single one is sufficient.

---

## 7.1 Choose the Right Lock Service

| System                 | Model | Lock Safety                    | Cost                  |
| ---------------------- | ----- | ------------------------------ | --------------------- |
| Redis (single)         | AP    | Weak — lost on failover        | Fastest, ~1ms         |
| Redlock (5 nodes)      | AP    | Better, still timing-dependent | 5 nodes, 5 RTTs       |
| ZooKeeper              | CP    | Strong — ephemeral znodes      | Slower, JVM ops burden|
| etcd                   | CP    | Strong — leases + revisions    | Already in k8s        |
| Postgres advisory lock | CP    | Strong — dies with connection  | Uses existing DB      |
| DB row lock            | CP    | Strongest — same transaction   | Only for DB resources |

> **Pragmatic path:** Don't introduce ZooKeeper for one nightly job. If you already run Postgres, `pg_try_advisory_lock` is a correct, zero-new-infrastructure distributed lock.

---

## 7.2 Fail Closed, Explicitly

```java
boolean acquired;
try {
    acquired = lock.tryLock(2, 30, TimeUnit.SECONDS);
} catch (RedisConnectionFailureException e) {
    // Redis is down. Do NOT proceed.
    throw new ServiceUnavailableException("Lock service unavailable", e);
}
if (!acquired) {
    throw new ResourceBusyException("Operation already in progress");
}
```

Pair with

* **Circuit breaker** (Resilience4j) — stop hammering dead Redis
* **Bulkhead** — prevent lock-waiting threads from consuming the pool

---

## 7.3 Bound Everything

| Parameter        | Rule                                          |
| ---------------- | --------------------------------------------- |
| Acquire timeout  | Never `lock()`, always `tryLock(wait, lease)`  |
| Lease time       | Must exceed worst-case work duration (p99)     |
| Network calls    | Never hold a lock across unbounded calls       |

> Unbounded wait turns one slow holder into cascading thread-pool exhaustion.

---

## 7.4 Make the Critical Section Safe WITHOUT the Lock

Assume the lock will fail. Ensure the outcome is still correct.

| Technique                     | How It Works                                                    |
| ----------------------------- | --------------------------------------------------------------- |
| **Fencing tokens**            | Monotonic number with lock, resource rejects stale tokens       |
| **Idempotency keys**          | Unique constraint on key → duplicate inserts nothing            |
| **Conditional state transitions** | `UPDATE SET status='SENT' WHERE status='PENDING'` → 0 rows = beaten |
| **PSP idempotency**           | Stripe/Razorpay `Idempotency-Key` header → double-call charges once |

---

## 7.5 Design the Lock Away

| Pattern                    | How It Eliminates the Lock                                |
| -------------------------- | --------------------------------------------------------- |
| **Partition by key**       | Route all events for a wallet to one Kafka partition → serial by construction |
| **Single-writer / leader** | Elect one instance (etcd lease) to own a shard            |
| **Transactional outbox**   | State + event in one DB transaction → no cross-system coordination. See [[11. Transaction Boundaries]] |
| **SKIP LOCKED**            | `SELECT ... FOR UPDATE SKIP LOCKED` → DB handles distributed claiming. No Redis. |

---

# 8. Spring Boot — Redisson

`spring-boot-starter-data-redis` gives you a client, not a lock.

Use **Redisson** for correct implementation (Lua release, watchdog, reentrancy).

```java
@Service
@RequiredArgsConstructor
public class SettlementService {

    private final RedissonClient redisson;
    private final PayoutService payoutService;

    public void runSettlement(String merchantId) {
        RLock lock = redisson.getLock("settlement:" + merchantId);
        boolean acquired = false;
        try {
            // waitTime=5s (fail fast), leaseTime=120s (> p99 work time)
            acquired = lock.tryLock(5, 120, TimeUnit.SECONDS);
            if (!acquired) {
                throw new ResourceBusyException(
                    "Settlement already running for " + merchantId);
            }
            payoutService.settle(merchantId);  // @Transactional lives here
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException(e);
        } finally {
            if (acquired && lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

---

## Lock/Transaction Ordering — Critical Bug

The lock must be acquired **outside** the transaction.

Released **after** commit.

```
✅  acquire lock → BEGIN → work → COMMIT → release lock
❌  BEGIN → acquire lock → work → release lock → COMMIT
```

In the second ordering

```
Lock is free but writes aren't visible yet
→ next node reads stale data
→ both do the work
```

> Putting `@Transactional` on the same method that acquires the lock produces exactly this bug. Spring's transaction proxy wraps the lock code. Keep them in separate beans.

---

## Alternatives

| Library                   | Use Case                                 |
| ------------------------- | ---------------------------------------- |
| Spring `LockRegistry`    | Swap Redis for DB without touching code  |
| `RedisLockRegistry`      | Redis-backed distributed locks           |
| `JdbcLockRegistry`       | DB-backed distributed locks              |
| **ShedLock**              | Run `@Scheduled` job on only one node    |

# Key Takeaways

1. Scaling from one JVM to many **silently removes** the shared memory that `synchronized` relied on.
2. A DB lock is safe because **lock and data are in the same transaction**.
3. A distributed lock needs a **referee** (Redis, ZK, etcd) — which is a new dependency.
4. **You cannot distinguish crashed from slow** — this forces TTL-based leases.
5. TTL expiry **does not stop the holder** — so two holders can genuinely exist.
6. **Fencing tokens** are the actual fix — enforcement lives at the resource, not the lock.
7. Redis is an **AP** system — async replication means locks are lost on failover.
8. **Redlock** is stronger but still timing-dependent — use fencing regardless.
9. **Fail closed** on lock service outage in any money path.
10. Best strategy is to **design the lock away** — partition by key, transactional outbox, SKIP LOCKED.
