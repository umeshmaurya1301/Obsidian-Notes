Covers Roadmap section 10. [[9. Database Concurrency]] solved contention *inside* one database. This note is about coordination when the thing you're protecting isn't a row — and about the uncomfortable truth that **a distributed lock is never as safe as a database lock.**

> [!info] The through-line of this note
> One physical fact drives everything here: **you cannot tell a crashed process apart from a slow one.** Read it in order:
>
> 1. Scaling from one JVM to many pods **silently removes** the shared memory that `synchronized` relied on (§1).
> 2. With no shared memory, mutual exclusion needs a **third party** — and that third party can crash, lag, or be partitioned away (§2).
> 3. Because a dead holder can't tell you it died, every lock needs a **TTL** — and a TTL means the lock can expire while its holder is still working (§5).
> 4. So a distributed lock can genuinely be held by **two clients at once**. Redis being down (§6.1) or failing over (§6.2) makes this worse, not different.
> 5. Therefore the lock cannot be your correctness guarantee. Correctness has to live at the **resource** — fencing tokens, idempotency keys, conditional writes (§5.1, §7.4).
>
> If you take one thing: **a distributed lock is a performance optimisation, not a correctness mechanism.**

### 1. From One JVM to Many — Why This Note Exists

Follow the same problem — *two operations must not run at once* — as a system grows. Each step silently removes a guarantee the previous step depended on.

#### 1.1 The progression

**Stage 1 — one JVM, one thread.** No problem exists. Nothing is concurrent.

**Stage 2 — one JVM, many threads.** Threads share heap memory, so mutual exclusion is a memory operation:

```java
synchronized (wallet) { wallet.debit(200); }
```

This works because every thread sees the *same* lock object at the *same* memory address, and the CPU guarantees only one wins the CAS on it. Cheap (nanoseconds) and **absolutely reliable** — see [[1. Core Fundamentals]].

**Stage 3 — many JVMs, one database.** You scale to 3 pods for availability. `synchronized` still compiles, still runs, still **does nothing useful** — each pod locks its *own* heap object. Three threads, one per pod, enter the "critical section" simultaneously.

> [!warning] The failure that gets shipped
> This is the single most common distributed-systems bug in a Spring service: code that was correct on one instance becomes silently wrong the day someone sets `replicas: 3`. Nothing throws. Nothing logs. The tests still pass, because they run in one JVM.

The fix is [[9. Database Concurrency]]: move the lock to the one thing all pods share — the database. `SELECT ... FOR UPDATE`, a `@Version` column, or an atomic `UPDATE`. This works **and is genuinely safe**, because the lock and the data it protects are in the same transaction: if the transaction dies, the lock dies with it, atomically.

**Stage 4 — the resource isn't in the database.** Now you need to stop two pods calling a payment gateway simultaneously, or ensure only one pod runs the 2 AM settlement. There is no row to lock. The shared, transactional arbiter you'd been leaning on **doesn't cover this resource** — so you introduce a separate lock service (Redis), and inherit a much weaker guarantee.

#### 1.2 What you lose at each step

|                          | `synchronized` | DB row lock | Redis lock |
| --- | --- | --- | --- |
| **Shared state lives in** | Process memory | The database | A separate service |
| **If the holder dies** | JVM exits, lock gone — **atomic** | Transaction rolls back, lock released — **atomic** | Lock **remains held** until a TTL expires |
| **Lock and data together?** | Yes | **Yes** — same transaction | **No** — two independent systems |
| **Can two holders exist?** | No, ever | No | **Yes** (§5, §6.2) |
| **Cost** | ~nanoseconds | ~1ms, in-transaction | ~1ms + network + a new dependency |

The decisive row is **"lock and data together."** A DB lock is safe because releasing the lock and committing the data are the *same event*. Once the lock lives in Redis and the data lives in Postgres, nothing makes those two atomic — and every problem in this note flows from that gap.

### 2. What Makes Distributed Mutual Exclusion Hard

#### 2.1 There is no shared memory, so someone must be the referee

In one JVM, "who holds the lock?" is a value at a memory address that all threads can read directly. Across machines there is no such address — only messages, which can be **delayed, reordered, duplicated, or lost**.

So mutual exclusion needs a **referee**: some external service that everyone agrees to ask. That's Redis, ZooKeeper, etcd, or your database. This immediately creates two properties you didn't have before:

1. The referee is a **new dependency** — if it's unreachable, you can't make progress (§6.1).
2. Every lock operation is a **network call** — it can time out, and *a timeout tells you nothing*. Your `SET NX` may have succeeded on the server with the response lost in transit. You genuinely don't know whether you hold the lock.

#### 2.2 The impossibility at the heart of it

Here is the fact that generates the rest of the note:

> **You cannot distinguish a process that has crashed from one that is merely slow.**

From the referee's point of view, these two situations are **byte-for-byte identical** — silence:

```
Client A crashed                    Client A is alive but stalled
  → sends nothing                     → sends nothing
                                        (40s GC pause, CPU starvation,
                                         swap thrashing, network partition)
```

Waiting longer doesn't help: a slow client might respond in 1 more second, or never. There is no timeout that reliably separates the two cases — this is the practical face of the FLP impossibility result, and it holds regardless of which lock service you pick.

#### 2.3 Which forces leases — and reintroduces the problem

The referee has to make a choice, and both options are bad:

| If a holder goes silent… | Consequence |
|---|---|
| **Wait forever** | A single crashed pod deadlocks that resource **permanently**. One `kill -9` during a deploy takes out settlement until someone manually clears the key. |
| **Reclaim after a timeout (TTL)** | Progress is preserved — but if the holder was only *slow*, it's still running while someone else holds the lock. |

Every practical system chooses the second: locks are **leases**, granted for a bounded time. That choice is correct, and it is also precisely why §5 exists — a lease can expire while its holder is still working, because *expiring the lease does not stop the holder*.

> [!info] Why the DB lock escaped this
> A database lock is held by a **connection**, not a lease. If the client dies, the TCP connection drops and the engine rolls the transaction back — releasing the lock and undoing the work as one atomic act. There's no window where the lock is free but the work is still in flight. **That's the guarantee you give up when the lock moves out of the database**, and no amount of Redis tuning buys it back.

### 3. When You Actually Need a Distributed Lock

First, the honest answer: **most of the time, you don't.** If the resource lives in your database, a row lock or a conditional `UPDATE` (§9.4 of [[9. Database Concurrency]]) is strictly safer, because the lock and the data are guarded by the same transaction.

You reach for Redis only when the resource is **outside** the database:

|Scenario|Why the DB can't help|
|---|---|
|Only one pod should run the 2 AM settlement job|No row to lock; it's a *process*, not data|
|Rate-limit a merchant to 100 TPS across 20 pods|Counter is too hot for a DB row|
|Don't call the PSP refund API twice concurrently|The resource is a third party's system|
|Coordinate a cache rebuild / prevent stampede|Nothing in the DB to lock|

> [!info] Rule of thumb
> Data in the DB → lock in the DB. Side effects outside the DB → distributed lock, **plus** an idempotency key so the lock isn't your only defence.

### 4. Redis Lock Basics — Getting It Right

#### 4.1 The correct minimal implementation

```
SET lock:payout:123  <random-uuid>  NX  PX 30000
```

Three parts, all mandatory:

- **`NX`** — set only if absent. This *is* the mutual exclusion.
- **`PX 30000`** — TTL. Without it, a crashed holder deadlocks the resource forever.
- **`<random-uuid>`** — an **ownership token**, so you can prove the lock is still yours at release time.

Release **must** be atomic — check-then-delete in two round trips is a race:

```lua
-- compare-and-delete, executed atomically by Redis
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

#### 4.2 The two classic broken versions

```
❌  SETNX lock 1        ❌  DEL lock
    EXPIRE lock 30
```

Left: not atomic — crash between the two commands and the key has **no TTL**, deadlocking the resource permanently.

Right: no ownership check. If your work overran the TTL, the lock already expired and **someone else owns it now** — you just deleted *their* lock, and now three clients are in the critical section.

### 5. The Fundamental Problem: TTLs Are Not Safe

This is §2.3 coming due, and it matters far more than the syntax in §4 — it's what senior interviews actually probe.

Recall the bind: the referee can't tell *crashed* from *slow*, so it must reclaim a lock after a TTL or risk deadlocking forever. But reclaiming is a decision made **entirely on the referee's side**. Redis expires a key; it has no way to reach into a stalled JVM and stop it.

So the guarantee quietly weakens from what you assumed to what you actually have:

```
What you think you bought:  "only one client is in the critical section"
What you actually bought:   "only one client believes it is in the critical section"
```

A lock with a timeout **cannot guarantee mutual exclusion**, because the lock expiring does not stop the holder from working:

```
Client A: acquires lock (TTL 30s)
Client A: ⏸ 40-second stop-the-world GC pause  (or CPU starvation, or a network stall)
          → lock expires in Redis at t=30
Client B: acquires the same lock at t=31 ✅  (legitimately — it's free)
Client B: starts processing payout 123
Client A: ⏵ wakes at t=40, believes it still holds the lock, writes to payout 123

→ Two clients in the critical section. No bug in Redis. No network partition.
```

Redis did nothing wrong. **The flaw is inherent to lease-based locking in an asynchronous system** — you cannot distinguish "the holder is dead" from "the holder is slow."

> [!warning] Auto-renewal does not fix this
> Redisson's watchdog renews the lease every 10s while work is in progress. It reduces the *frequency* of the above, but a paused client can't renew *and* can't be stopped. Renewal makes the window rarer, not absent.

#### 5.1 Fencing tokens — the actual fix

Issue a **monotonically increasing token** with every lock grant, and make the *protected resource* reject stale tokens.

```
Client A acquires → token 33
Client A pauses
Client B acquires → token 34
Client B writes with token 34   → accepted, resource records 34
Client A wakes,  writes token 33 → REJECTED (33 < 34)
```

The enforcement has to live at the resource, not the lock service. With a DB resource, that's just a conditional update — the same pattern as optimistic locking:

```sql
UPDATE payout
   SET status = 'SENT', fence_token = :token
 WHERE id = :id
   AND fence_token < :token;      -- stale holder writes 0 rows
```

`INCR` gives you the token from Redis. ZooKeeper gives it for free as the znode `zxid`.

> [!info] The takeaway
> A distributed lock is a **performance optimization** (avoid duplicate work), not a **correctness guarantee**. Correctness must come from the resource: a fencing token, a unique constraint, or an idempotency key.

### 6. Redis as a Single Point of Failure

§5 showed the lock can fail **while Redis is working perfectly.** This section is the other half: what happens when Redis itself misbehaves.

That's the cost §2.1 warned about. By moving mutual exclusion to a referee, you made Redis a hard dependency of your write path — every operation that needs the lock now needs Redis to be up *and* correct. Two distinct failure modes, with opposite consequences:

- **§6.1 Redis is down** — you know immediately. The damage depends entirely on what your code does next.
- **§6.2 Redis fails over** — you *don't* know. Everything looks healthy while mutual exclusion is silently gone. This is the worse one.

#### 6.1 Redis is simply *down*

Every `SET NX` fails. Now your code has to choose, and **the default choice is usually the wrong one**:

|Strategy|Behaviour|Consequence|
|---|---|---|
|**Fail-closed** (reject)|Lock unavailable → refuse the operation|Availability outage. Payments decline. **Correct for money.**|
|**Fail-open** (proceed)|Lock unavailable → carry on unprotected|Full availability, **zero mutual exclusion**. Every pod processes every payout. Mass double-spend.|

> [!warning] The silent killer
> A `try/catch` around lock acquisition that logs a warning and continues **is** fail-open. Under a Redis outage that converts a dependency failure into a *financial* incident — which is far worse than downtime. If you can't get the lock, you must not enter the critical section.

The mitigation for the outage itself isn't cleverness in the lock code — it's **not needing the lock to be correct** (§5.1, §7.4).

#### 6.2 Redis fails *over* — the dangerous one

Worse than an outage, because nothing looks broken.

**Redis replication is asynchronous.** The primary acknowledges your write before replicating it:

```
t0  Client A: SET lock NX PX 30000 → primary says OK ✅
t1  Primary crashes — the lock was never replicated
t2  Sentinel promotes the replica. The new primary has no lock key.
t3  Client B: SET lock NX PX 30000 → OK ✅

→ A and B both hold "the" lock. Both believe they're exclusive.
```

This is not a misconfiguration you can tune away. It's the direct consequence of Redis being an **AP** system: it chose availability, so it cannot also promise the linearizable, never-lost register that a correct lock requires. Sentinel and Cluster give you *failover*, not *consensus* — they improve uptime and do nothing for lock safety.

`WAIT numreplicas timeout` forces acknowledgement from N replicas and narrows the window, but it still isn't consensus (an acked replica can itself be lost) and it costs you a round trip per lock.

#### 6.3 Redlock, and why it's contested

Redis's own answer: run **N=5 independent primaries** (no replication between them), acquire on a **majority (3)**, and only consider the lock held if that took substantially less than the TTL.

The debate is worth knowing by name:

- **Martin Kleppmann's critique:** Redlock depends on bounded clock drift and bounded pauses. A GC pause or an NTP jump breaks it, so it's neither a good efficiency lock (too costly) nor a good correctness lock (unsafe). If you need correctness, use fencing tokens.
- **Salvatore Sanfilippo's (antirez) reply:** the timing assumptions are reasonable in practice, and Redlock is meaningfully stronger than single-node Redis.

**Position to take in an interview:** Redlock raises the bar but doesn't remove the need for fencing. It also costs 5 deployments and 5 round trips — at which point etcd or ZooKeeper gives you a genuinely correct lock for comparable operational effort.

### 7. Prevention and Mitigation

Layered — no single one is sufficient.

#### 7.1 Choose a lock service that matches the guarantee you need

|System|Model|Lock safety|Cost|
|---|---|---|---|
|**Redis (single)**|AP|Weak — lost on failover|Fastest, ~1ms|
|**Redlock**|AP|Better, still timing-dependent|5 nodes, 5 RTTs|
|**ZooKeeper**|CP (Zab)|Strong — ephemeral znodes tied to session, `zxid` = free fencing token|Slower, JVM ops burden|
|**etcd**|CP (Raft)|Strong — leases + revision numbers as fencing tokens|Slower; already in your k8s cluster|
|**Postgres advisory lock**|CP|Strong, dies with the connection|Uses your existing DB|
|**DB row lock**|CP|Strongest — same transaction as the data|Only for DB-resident resources|

> [!example] The pragmatic path
> Don't introduce ZooKeeper for one nightly job. If you already run Postgres, `pg_try_advisory_lock` (§5.4 of [[9. Database Concurrency]]) is a correct, transactional, zero-new-infrastructure distributed lock. Reach for Redis when you need the throughput; reach for etcd/ZK when a split lock is unacceptable *and* you can't fence.

#### 7.2 Fail closed, explicitly

```java
boolean acquired;
try {
    acquired = lock.tryLock(2, 30, TimeUnit.SECONDS);
} catch (RedisConnectionFailureException e) {
    // Redis is down. Do NOT proceed. Shed load and let the retry/DLQ handle it.
    throw new ServiceUnavailableException("Lock service unavailable", e);
}
if (!acquired) {
    throw new ResourceBusyException("Operation already in progress");
}
```

Pair it with a **circuit breaker** (Resilience4j) so you stop hammering a dead Redis, and a **bulkhead** so lock-waiting threads can't consume the whole pool.

#### 7.3 Bound everything

- **Acquire timeout** — never `lock()`, always `tryLock(waitTime, leaseTime, unit)`. An unbounded wait turns one slow holder into a cascading thread-pool exhaustion.
- **Lease time** — must exceed worst-case work duration, or you guarantee the §3 double-holder scenario. Measure p99, don't guess.
- **Never hold a lock across an unbounded network call** — same rule as DB locks.

#### 7.4 Make the critical section safe *without* the lock

This is the real answer, and the one that impresses. Assume the lock will fail, and ensure the outcome is still correct:

- **Fencing tokens** (§5.1) — the general mechanism.
- **Idempotency keys** — a unique constraint on `idempotency_key` (§10.2 of [[9. Database Concurrency]]) means a duplicate execution *inserts nothing and returns the original result*. The DB is the arbiter, and it's CP.
- **Conditional state transitions** — `UPDATE payout SET status='SENT' WHERE id=:id AND status='PENDING'`. Rows-affected = 0 means someone beat you. This alone prevents double-payout even with no lock at all.
- **Idempotency at the PSP** — Stripe/Razorpay accept an `Idempotency-Key` header. Use it; then even a genuine double-call charges once.

#### 7.5 Design the lock away

- **Partition by key.** Route all events for a wallet to one Kafka partition ([[3. Consumer]]) — one consumer owns that key, so operations on it are serial by construction. No lock needed; contention becomes a routing property.
- **Single-writer / leader election.** Elect one instance (via etcd lease or a k8s `Lease`) to own a whole shard, rather than locking per-item.
- **Transactional outbox.** Write state + event in one DB transaction, publish after commit — removes the cross-system coordination that tempted you into a lock. Covered fully in [[11. Transaction Boundaries]].
- **`SELECT ... FOR UPDATE SKIP LOCKED`.** For "N workers, one job table," the DB already gives you safe distributed claiming (§9.5 of [[9. Database Concurrency]]). No Redis at all.

### 8. Spring Boot — Redisson

`spring-boot-starter-data-redis` gives you a client, not a lock. Use **Redisson** for a correct implementation (Lua release, watchdog renewal, reentrancy):

```java
@Service
@RequiredArgsConstructor
public class SettlementService {

    private final RedissonClient redisson;
    private final PayoutService payoutService;

    public void runSettlement(String merchantId) {
        RLock lock = redisson.getLock("settlement:" + merchantId);
        boolean acquired = false;
        try {
            //          waitTime=5s (fail fast), leaseTime=120s (> p99 work time)
            acquired = lock.tryLock(5, 120, TimeUnit.SECONDS);
            if (!acquired) {
                throw new ResourceBusyException("Settlement already running for " + merchantId);
            }
            payoutService.settle(merchantId);      // @Transactional lives in here
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException(e);
        } finally {
            if (acquired && lock.isHeldByCurrentThread()) {
                lock.unlock();                     // isHeldByCurrentThread avoids releasing a re-acquired lock
            }
        }
    }
}
```

> [!warning] Lock/transaction ordering — the bug everyone ships once
> The lock must be acquired **outside** the transaction and released **after commit**.
>
> ```
> ✅  acquire lock → BEGIN → work → COMMIT → release lock
> ❌  BEGIN → acquire lock → work → release lock → COMMIT
> ```
>
> In the second ordering there's a window where the lock is free but your writes aren't visible yet — the next node reads stale data and both do the work. Putting `@Transactional` on the *same method* that acquires the lock produces exactly this bug, because Spring's transaction proxy wraps the lock code. Keep them in separate beans, as above.

Alternatives: Spring Integration's `LockRegistry` abstraction gives you `RedisLockRegistry` and `JdbcLockRegistry` behind one interface — useful if you want to swap Redis for the DB without touching call sites. ShedLock is purpose-built for the narrower "run this `@Scheduled` job on only one node" case.

### 9. Interview Quick-Fire

|Question|The answer they want|
|---|---|
|Why doesn't `synchronized` work across pods?|Each JVM locks its own heap object — no shared memory, so no shared lock|
|Why is a DB lock safer than a Redis lock?|Lock and data are in the **same transaction** — the holder dying releases both atomically|
|Why does a distributed lock need a TTL?|A crashed holder can't release it, and you can't tell crashed from slow — so it must self-expire|
|What's the core impossibility?|You cannot distinguish a crashed process from a slow one; both are just silence|
|What does a lease actually guarantee?|Only that one client *believes* it holds the lock — not that one client is running|
|How do you implement a Redis lock?|`SET key <uuid> NX PX <ttl>`; release via Lua compare-and-delete|
|Why the random UUID?|Ownership — otherwise you delete a lock that expired and was re-acquired by someone else|
|Why is `SETNX` + `EXPIRE` wrong?|Not atomic — a crash between them leaves a key with no TTL, deadlocked forever|
|Redis goes down — what happens?|Depends on your choice: fail-closed = outage, fail-open = no mutual exclusion. For payments, fail closed.|
|Redis fails *over* — what happens?|Async replication means the lock may not have replicated → **two holders**, silently|
|So Redis locks are unsafe?|They're an *efficiency* optimization. Correctness needs fencing tokens or idempotency at the resource.|
|What's a fencing token?|Monotonic number issued with the lock; the resource rejects any write with a lower token|
|Redlock — safe?|Better than single-node; Kleppmann's critique is that it assumes bounded clocks/pauses. Still fence.|
|Redis vs ZooKeeper for locks?|Redis = AP, fast, unsafe on failover. ZK/etcd = CP, correct, slower. Pick by CAP need.|
|Cheapest correct distributed lock?|`pg_advisory_lock` or `SELECT ... FOR UPDATE SKIP LOCKED` — if you already run Postgres|
|How do you avoid needing a lock?|Partition by key, single-writer, conditional state transition, idempotency key|

> [!warning] The three rules
> 1. **Never fail open** on a lock service outage in a money path.
> 2. **Never rely on a distributed lock for correctness** — fence it or make the operation idempotent.
> 3. **If the resource is in your database, lock it in your database.**
