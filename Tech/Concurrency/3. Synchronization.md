Covers Roadmap section 3. Note 1 told you *what* goes wrong when threads share state — races, lost updates, stale reads from CPU caches. Note 2 gave you threads to run. This note is the toolbox for making shared state safe: mutual exclusion (`synchronized`, `Lock`) and visibility (`volatile`).

> [!info] The through-line of this note
> Two distinct problems hide under the word "synchronization" — keep them apart:
>
> 1. **Visibility** — will thread B ever *see* thread A's write? Fixed by `volatile` (§3) — the cheap tool, no mutual exclusion.
> 2. **Atomicity / mutual exclusion** — will a check-then-act (`balance -= amount`) run without another thread interleaving? Fixed by `synchronized` (§1) and `Lock` (§5).
>
> The chain: `synchronized` is built on the **intrinsic monitor lock** every object carries (§2). That monitor also powers **`wait`/`notify`** for threads to *signal* each other (§4). `synchronized` is simple but rigid, so Java adds the explicit **`Lock`** interface (§5) → **`ReentrantLock`** (its main implementation, §6) → **`ReadWriteLock`** for read-heavy state (§7). Each step buys flexibility at the cost of "you must now `unlock()` yourself."
>
> One line to anchor everything: **`volatile` guarantees visibility but not atomicity; `synchronized` guarantees both.** (You saw this table in [[1. Core Fundamentals]] — this note is the *why*.)

### 1. `synchronized` — Mutual Exclusion via the Monitor

`synchronized` guarantees that only **one thread at a time** executes a block guarded by a given lock object. It solves the race condition from note 1's `i++` example.

The problem it fixes:

```java
class Wallet {
    private long balance;
    void debit(long amt) { balance -= amt; }   // NOT atomic: read, subtract, write
}
```

`balance -= amt` is three steps. Two threads can both read `100`, both write `50`, and one debit vanishes — a **lost update**. `synchronized` serialises the whole read-modify-write:

```java
class Wallet {
    private long balance;
    synchronized void debit(long amt) { balance -= amt; }   // one thread at a time
}
```

Two forms:

```java
// Synchronized METHOD — locks on 'this' (instance method) or the Class object (static)
synchronized void debit(long amt) { ... }

// Synchronized BLOCK — you choose the lock object; narrower critical section
private final Object lock = new Object();
void debit(long amt) {
    synchronized (lock) { balance -= amt; }   // only this line is guarded
}
```

> [!info] Prefer the block, prefer a private lock
> A synchronized *method* locks on `this` — anyone with a reference to your object can also `synchronized(walletInstance)` and interfere with (or deadlock) your locking. A **private final lock object** can't be seen from outside, so no external code can grab it. Blocks also keep the critical section small, which means less contention. Rule: hold the lock for the shortest span that keeps the invariant.

> [!info] Synchronization gives you both visibility AND atomicity
> Entering a `synchronized` block establishes a *happens-before* edge (from [[1. Core Fundamentals]]): everything a thread did before releasing the monitor is visible to the next thread that acquires it. So `synchronized` doesn't just serialise — it also flushes caches to main memory. That's why you rarely need `volatile` *and* `synchronized` on the same field.

### 2. The Intrinsic Lock (Monitor) — What `synchronized` Actually Uses

Every Java object has a hidden **monitor lock** (a.k.a. intrinsic lock) built into its header. `synchronized(obj)` acquires `obj`'s monitor on entry and releases it on exit — including if an exception is thrown, which is why you never "forget to unlock" with `synchronized`.

Key properties:

- **One monitor per object.** Two threads synchronizing on *different* objects don't block each other.
- **Reentrant.** A thread that holds a monitor can re-acquire it (e.g. one synchronized method calling another on the same object) without deadlocking itself. It tracks a hold count.
- **Automatically released** on block exit / exception. No leak possible.

> [!warning] Locking on the wrong object = no locking at all
> `synchronized(new Object())` in a method locks a *fresh* object every call — every thread gets its own monitor, so nothing is mutually excluded. Same trap: locking on a `Long`/`String` that gets reassigned, or an autoboxed value that isn't the same instance. The lock object must be **final** and **shared** by exactly the threads you want to exclude.

### 3. `volatile` — Visibility Without Locking

`volatile` solves *only* the visibility half. A write to a `volatile` field is immediately flushed to main memory and every read goes to main memory — no thread reads a stale cached copy. It also prevents the compiler/CPU from reordering across it.

The canonical use — a stop flag:

```java
class Worker implements Runnable {
    private volatile boolean running = true;   // without volatile, the loop may spin forever
    public void run() {
        while (running) { doWork(); }
    }
    public void stop() { running = false; }    // seen by the worker thread promptly
}
```

Without `volatile`, the worker thread may cache `running = true` and never see the update — an infinite loop that "shouldn't be possible."

> [!warning] `volatile` does NOT make compound actions atomic
> `volatile int count; count++;` is still broken — `++` is read-modify-write, and `volatile` only guarantees each *individual* read and write is fresh, not that the trio is indivisible. For a counter use `AtomicInteger` (Roadmap §5); for anything more, use a lock. **`volatile` is for visibility of a single field, not mutual exclusion.**

| | `volatile` | `synchronized` |
|---|---|---|
| Visibility | ✅ | ✅ |
| Atomicity of compound ops | ❌ | ✅ |
| Mutual exclusion | ❌ | ✅ |
| Blocks threads | Never | Yes (contention) |
| Cost | Very cheap | Heavier (contention, context switches) |
| Use for | One flag/reference read across threads | Any check-then-act on shared state |

### 4. `wait()` / `notify()` / `notifyAll()` — Threads Signalling Each Other

`synchronized` stops threads from *colliding*. `wait`/`notify` let them *coordinate* — one thread waits until another says "condition's ready." This is how a bounded queue, a producer/consumer, or a connection pool is built by hand.

The three methods live on `Object` and **must be called while holding that object's monitor** (inside a `synchronized` block on it):

- `wait()` — **releases the monitor** and parks the thread until notified. (Contrast `sleep()`, which keeps the lock — see [[2. Java Thread Basics]].)
- `notify()` — wakes **one** waiting thread.
- `notifyAll()` — wakes **all** waiters; they re-contend for the lock.

Bounded buffer, done right:

```java
class BoundedBuffer<T> {
    private final Queue<T> q = new LinkedList<>();
    private final int cap;
    BoundedBuffer(int cap) { this.cap = cap; }

    synchronized void put(T item) throws InterruptedException {
        while (q.size() == cap) wait();      // WHILE, not if — see below
        q.add(item);
        notifyAll();                          // wake any waiting consumers
    }

    synchronized T take() throws InterruptedException {
        while (q.isEmpty()) wait();
        T item = q.remove();
        notifyAll();                          // wake any waiting producers
        return item;
    }
}
```

> [!warning] Always `wait()` in a `while` loop, never an `if`
> Two reasons. **(1) Spurious wakeups:** a thread can wake from `wait()` without being notified — the JVM permits it. **(2) The condition can be stolen:** after `notifyAll()`, several threads wake and race for the lock; by the time this one acquires it, another may have already consumed the item. Re-checking the condition in a `while` covers both. An `if` here is a real, subtle bug.

> [!info] Prefer `notifyAll()` unless you can prove `notify()` is safe
> `notify()` wakes one *arbitrary* waiter — if it's waiting on a different condition than the one you satisfied, it goes back to sleep and the right thread never wakes (a lost-wakeup deadlock). `notifyAll()` is safe by default. In practice, reach for higher-level tools (`BlockingQueue`, `Condition`, `Semaphore` — Roadmap §5–§6) instead of hand-rolling `wait`/`notify`; know the primitive, use the library.

### 5. The `Lock` Interface — Explicit Locking

`synchronized` is convenient but rigid: you can't try-and-give-up, can't time out, can't interrupt a thread waiting for the lock, and the lock must release in the same block it was acquired. `java.util.concurrent.locks.Lock` makes locking an explicit object with none of those limits.

```java
Lock lock = new ReentrantLock();
lock.lock();
try {
    // critical section
} finally {
    lock.unlock();   // MANDATORY — and must be in finally
}
```

What you gain over `synchronized`:

| Capability | `synchronized` | `Lock` |
|---|---|---|
| Try without blocking | ❌ | `tryLock()` |
| Time-boxed wait | ❌ | `tryLock(timeout, unit)` |
| Interruptible wait | ❌ | `lockInterruptibly()` |
| Fairness (FIFO) option | ❌ | `new ReentrantLock(true)` |
| Multiple condition queues | ❌ (one wait-set) | `lock.newCondition()` |
| Release outside the block | ❌ | ✅ (you own it) |

> [!warning] The cost of explicit locks: you must `unlock()` yourself
> `synchronized` releases automatically, even on exception. A `Lock` does not. Forgetting `unlock()` — or putting it outside `finally` so an exception skips it — leaves the lock held forever and every other thread blocks. **The `try { } finally { unlock() }` shape is not optional.** This is the tradeoff: more power, more rope.

`tryLock` is the killer feature for deadlock avoidance and responsiveness:

```java
if (lock.tryLock(200, TimeUnit.MILLISECONDS)) {
    try { transfer(); } finally { lock.unlock(); }
} else {
    // couldn't get the lock in time — fail fast instead of hanging the request
    throw new ResourceBusyException();
}
```

> [!info] This is the in-JVM cousin of a distributed lock
> Timeouts, try-acquire, fencing — the same concerns scale up to Redis/ZooKeeper locks when you have multiple pods. In one JVM, `ReentrantLock` is the tool; across JVMs, the database or a distributed lock is (see [[10. Distributed Concurrency]]). The failure modes rhyme.

### 6. `ReentrantLock` — The Workhorse `Lock`

`ReentrantLock` is the standard `Lock` implementation. "Reentrant" means the holding thread can re-acquire it (hold count, like the intrinsic monitor). It adds everything in the §5 table.

```java
class Account {
    private final ReentrantLock lock = new ReentrantLock();
    private long balance;

    void debit(long amt) {
        lock.lock();
        try {
            if (balance < amt) throw new InsufficientFundsException();
            balance -= amt;
        } finally { lock.unlock(); }
    }
}
```

**Fairness.** `new ReentrantLock(true)` grants the lock in FIFO order — the longest waiter goes next, preventing starvation (the problem from [[1. Core Fundamentals]] §9). The default (unfair) is faster because it allows barging, but a thread can theoretically wait indefinitely. Use fair only when starvation is a demonstrated problem — it has real throughput cost.

`Condition` replaces `wait`/`notify` with *named* wait-sets on a `Lock` — you can have separate "not full" and "not empty" queues and notify exactly the right one, avoiding the wake-the-wrong-thread problem from §4.

```java
Lock lock = new ReentrantLock();
Condition notFull  = lock.newCondition();
Condition notEmpty = lock.newCondition();
// notFull.await() / notEmpty.signal() — targeted signalling
```

> [!info] When to pick `ReentrantLock` over `synchronized`
> Default to `synchronized` — it's simpler, auto-released, and the JVM optimises it well. Reach for `ReentrantLock` only when you need a specific feature: `tryLock`/timeout, interruptible acquisition, fairness, or multiple `Condition`s. Extra power you don't need is just extra rope to hang on (a forgotten `unlock`).

### 7. `ReadWriteLock` — Many Readers or One Writer

A plain lock serialises *everything*, even concurrent reads that don't conflict. But reads don't corrupt each other (from [[9. Database Concurrency]]: R-R is always safe). `ReadWriteLock` exploits that:

- **Read lock:** many threads hold it simultaneously.
- **Write lock:** exclusive — blocks all readers and other writers.

```java
class RateTable {
    private final ReadWriteLock rw = new ReentrantReadWriteLock();
    private Map<String, BigDecimal> fx = new HashMap<>();

    BigDecimal rate(String pair) {          // hot path — thousands of reads/sec
        rw.readLock().lock();
        try { return fx.get(pair); }
        finally { rw.readLock().unlock(); }
    }

    void reload(Map<String, BigDecimal> fresh) {   // rare — a few times a day
        rw.writeLock().lock();
        try { fx = fresh; }
        finally { rw.writeLock().unlock(); }
    }
}
```

> [!info] Only a win when reads massively outnumber writes
> A `ReadWriteLock` has more bookkeeping overhead than a plain lock, and heavy writes can *starve readers* (or vice versa). It pays off only for read-dominated, relatively-stable state: FX/rate tables, feature-flag config, routing tables in a payment switch. For write-heavy or tiny critical sections, a plain `ReentrantLock` is faster. And for a shared map specifically, `ConcurrentHashMap` (Roadmap §6) usually beats hand-rolling a `ReadWriteLock`.

> [!warning] No lock upgrade
> You cannot hold the read lock and then acquire the write lock — that deadlocks (the writer waits for readers to release, but you're a reader who won't). Release the read lock first, then take the write lock, then re-check state (it may have changed in the gap). `StampedLock` (Roadmap "basics") offers optimistic reads and a controlled upgrade path, but it's non-reentrant and easy to misuse — know it exists, reach for it rarely.

### 8. Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| `volatile` vs `synchronized`? | `volatile` = visibility only, no blocking; `synchronized` = visibility + atomicity + mutual exclusion. |
| Is `count++` safe if `count` is `volatile`? | No — `++` is read-modify-write; `volatile` doesn't make it atomic. Use `AtomicInteger` or a lock. |
| What does `synchronized` lock on? | The object's intrinsic monitor — `this` for instance methods, the `Class` for static, or the named object for a block. |
| Why is `synchronized` reentrant? | The monitor tracks a hold count, so the holding thread can re-acquire it without deadlocking itself. |
| `sleep()` vs `wait()`? | `sleep()` holds the lock, time-based; `wait()` releases the monitor and waits for `notify()`. |
| Why `wait()` in a `while`, not `if`? | Spurious wakeups + the condition can be consumed by another thread before you re-acquire the lock. |
| `notify()` vs `notifyAll()`? | `notify()` wakes one arbitrary waiter (risk: wrong thread → lost wakeup); `notifyAll()` wakes all — safer default. |
| Why choose `ReentrantLock` over `synchronized`? | `tryLock`, timeouts, interruptible acquire, fairness, multiple `Condition`s. Otherwise prefer `synchronized`. |
| Biggest risk with `Lock`? | Forgetting `unlock()` — must be in `finally`, or the lock is held forever. |
| When does `ReadWriteLock` help? | Read-heavy, write-rare shared state. Watch out: no lock upgrade; writes can starve. |
| How avoid deadlock with locks? | Consistent lock ordering, `tryLock` with timeout, keep critical sections small, hold fewer locks. |
