Covers Roadmap section 3. Note 1 told you *what* goes wrong when threads share state — races, lost updates, stale reads from CPU caches. Note 2 gave you threads to run. This note is the toolbox for making shared state safe, and the mental models to pick the right tool.

> [!info] The through-line of this note
> Synchronization is **not a Java feature** — it's the answer to one problem: **concurrent access to shared mutable state** (§1). Everything here is a different-priced answer to that problem.
>
> Two distinct guarantees hide under the word "synchronization" — keep them apart:
>
> 1. **Visibility / ordering** — will thread B ever *see* thread A's write, and in the right order? Fixed by `volatile` (§4) — cheap, no mutual exclusion.
> 2. **Atomicity / mutual exclusion** — will a read-modify-write (`balance -= amt`) run without another thread interleaving? Fixed by `synchronized` (§2).
>
> The chain: `synchronized` is built on the **intrinsic monitor** every object carries (§3). Both it and `volatile` are just ways of buying **happens-before edges** (§5) — the one rule the whole Java Memory Model reduces to. That same monitor powers **`wait`/`notify`** so threads can *signal* each other (§6).
>
> Then the design half: the cheapest lock is the one you never take — **thread-safety patterns** that remove the need to synchronize at all (§7), and a **decision matrix** for when you can't (§8).
>
> One line to anchor everything: **`volatile` guarantees visibility but not atomicity; `synchronized` guarantees both.** (You saw the table in [[1. Core Fundamentals]] — this note is the *why*.)

## Short Notes

---

### 1. Why Synchronization Exists — Shared Mutable State

- Needed **only when all three are true**: multiple threads **+** shared data **+** at least one thread mutates it
- **Shared** = reachable by 2+ threads · **Mutable** = value can change · **State** = the data an object holds
- Local variables (private stack) and immutable objects (`final String`) need **nothing**
- `balance -= amt` is **read → modify → write** — three steps, interleavable → **lost update**
- `count++` is therefore **not atomic** — the flat answer to a very common question
- Three problems solved: **atomicity**, **visibility**, **ordering**

| Problem | Meaning | Broken example |
|---|---|---|
| **Atomicity** | Completes as one indivisible unit | `count++`, `balance -= amt` |
| **Visibility** | Other threads see the latest value | `while (running)` that never exits |
| **Ordering** | Writes become visible in a JMM-guaranteed order | seeing `ready == true` but `data == 0` |

> **Mutual exclusion** is the mechanism for atomicity. **Thread safety** is the property you're aiming for.

---

### 2. `synchronized` — Mutual Exclusion via the Monitor

- Gives **three** guarantees, not one: mutual exclusion **+** visibility **+** happens-before ordering
- **Method form** locks `this`; **`static synchronized`** locks the `Class` object — *different locks, they don't exclude each other*
- **Block form** lets you choose the lock object and keep the critical section narrow
- **Reentrant** — the owning thread can re-enter its own monitor without deadlocking
- Prefer a `private final Object lock` over `this` — outside code can't grab what it can't see
- **Never hold the lock across I/O** — microseconds of real work, hundreds of ms of waiting for everyone else

> Releasing a monitor publishes everything done before it — that's why you rarely need `volatile` **and** `synchronized` on the same field.

---

### 3. The Intrinsic Monitor — What Actually Gets Locked

- Every Java object carries a hidden **monitor** (intrinsic lock) in its header — only the JVM can touch it
- `synchronized` locks an **object**. Never a variable, never code
- **Auto-released** on normal exit *and* on exception — you cannot forget to unlock
- **Reentrant via a hold count**: enter → `1`, nested → `2`, released only at `0`
- **No fairness promise** — the JVM picks *a* waiting thread, not the first one. Never rely on order
- Threads on **different** objects never block each other → the seed of splitting locks per state

| You write | Monitor acquired | Verdict |
|---|---|---|
| `synchronized (this)` | the current object | Works, but public-ish |
| `synchronized (lock)`, `private final Object lock` | that object | ✅ Best practice |
| `synchronized (Counter.class)` | the `Class` object | Class-wide lock |
| `synchronized ("LOCK")` | the interned literal | ❌ JVM-wide — unrelated code collides |
| `synchronized (boxedInteger)` | the `Integer` | ❌ Cached/shared, and reassignment moves the lock |
| `synchronized (new Object())` | a fresh monitor each call | ❌ Excludes nobody |
| `synchronized (x)` where `int x` | — | ❌ Compile error |

> A lock protects a **critical section**, not a field. Every access must use the **same** lock — a field guarded on one path and not another is not guarded at all.

---

### 4. `volatile` — Visibility and Ordering Without Mutual Exclusion

- Guarantees **visibility** + **ordering**. Provides **no mutual exclusion** — it is *not* a lightweight `synchronized`
- Every read sees the latest write from any thread; no stale core-cache copy, and the JIT can't hoist the read out of a loop
- `volatile count++` is **still broken** — compound read-modify-write is not made indivisible
- A single read or write **is** atomic, **including `long` and `double`** (the one 64-bit tearing case)
- **Use for**: stop/shutdown flags, feature toggles, status flags, config reference swaps, safe publication
- **Don't use for**: counters, balances, inventory → `AtomicInteger`/`AtomicLong` ([[5. Concurrent Utilities]])

| | `volatile` | `synchronized` |
|---|---|---|
| Visibility | ✅ | ✅ |
| Ordering | ✅ | ✅ |
| Mutual exclusion | ❌ | ✅ |
| Atomicity of compound ops | ❌ | ✅ |
| Blocks threads | Never | Yes (contention) |
| Cost | Very cheap | Heavier |

---

### 5. Happens-Before — the Rule Everything Else Reduces To ⭐

- **Definition**: if A happens-before B, everything A did is **visible** to B, and B can't be reordered before A
- **Not** wall-clock order. **Not** "thread A finishes before thread B starts." It's about **memory effects**
- Every tool in this note is just a way of **buying a happens-before edge**

| # | Rule | The edge |
|---|---|---|
| 1 | **Program order** | Each statement happens-before the next, within one thread |
| 2 | **Monitor** | Releasing a monitor → next acquisition of **the same** monitor |
| 3 | **Volatile** | A write → every subsequent read of **that same** field |
| 4 | **`Thread.start()`** | Everything before `start()` → anything the new thread does |
| 5 | **`Thread.join()`** | Everything the thread did → `join()` returning |
| 6 | **Transitivity** | A → B and B → C implies A → C |

- **Same** monitor / **same** volatile field, or there is no edge at all
- A volatile write publishes **the past, not the future** — writes after it get no guarantee
- The reader must actually **read** the volatile field; skipping the flag buys nothing

---

### 6. `wait()` / `notify()` / `notifyAll()` — Threads Signalling Each Other

- Declared on **`Object`**, not `Thread` — every object can be a coordination point
- Must be called **while holding that object's monitor**, else `IllegalMonitorStateException`
- `wait()` **releases** the monitor and parks; reacquires it before returning
- Always `wait()` in a **`while`**, never an `if` — spurious wakeups **+** the condition can be stolen
- `notify()` wakes **one arbitrary** waiter; `notifyAll()` is the safe default
- `notify()` **doesn't hand over the lock** — the waiter moves WAITING → BLOCKED and runs only after the notifier exits the block
- One monitor = **one wait-set** for producers and consumers together → the lost-wakeup trap

| | `wait()` | `sleep()` |
|---|---|---|
| Declared on | `Object` | `Thread` |
| Releases the monitor | ✅ Yes | ❌ No |
| Must hold a monitor | ✅ Yes | ❌ No |
| Wakes on | `notify()`/`notifyAll()`/timeout/interrupt | timeout / interrupt |
| Purpose | Thread **communication** | **Delaying** execution |

> Know the primitive, ship the library — `BlockingQueue`, `CountDownLatch`, `Semaphore` ([[5. Concurrent Utilities]]) instead of hand-rolled `wait`/`notify`.

---

### 7. Thread-Safety Patterns — Designing So You Don't Need to Synchronize

- **Immutability** ⭐ — `final` class, all fields `final`, no leaked internals → nothing to protect. This is *why* `String` is thread-safe
- **Thread confinement** — locals live on the thread's own stack; each HTTP request is its own thread. `ThreadLocal` is the explicit form
- **Statelessness** — the real reason a Spring singleton bean is usually safe. **Not** because it's a singleton
- **Safe publication** — a reference handed to another thread needs an edge: `volatile`, `AtomicReference`, the same lock readers use, a concurrent collection, or `final` fields set in the constructor
- **Defensive copying** — returning your internal mutable collection hands callers a way around your locks
- **Minimise shared mutable state** — every shared field is a thing to protect and a place to get it wrong

```text
Is the data shared across threads?      No  → done, nothing to do
        │ Yes
Can it be immutable?                    Yes → make it immutable
        │ No
Can it be thread-confined (local)?      Yes → keep it local
        │ No
Is it a counter / single field?         Yes → AtomicInteger / volatile
        │ No
                                            → synchronized
```

> "I used `synchronized`, so my code is thread-safe" — not necessarily. Thread safety is a property of **design**, not a keyword.

---

### 8. Choosing the Right Tool — Best Practices

- **Synchronize only what's necessary** — the smallest block that preserves the invariant
- **Never hold a lock during slow operations** — DB, REST, Kafka, Redis, file I/O
- Prefer **immutable** > **stateless** > **confined** > **atomic** > `synchronized`
- Keep lock objects **`private final`**; never a `String` literal (interned) or a boxed primitive (cached)
- Prefer the library: `BlockingQueue` over `wait`/`notify`, `AtomicInteger` over `volatile int`, `ConcurrentHashMap` over a synchronized `HashMap`
- **Don't over-synchronize** — `synchronized int add(int a, int b)` guards nothing
- **Document the lock**: `// guarded by balanceLock` next to the field

| Problem | Reach for |
|---|---|
| Protect an object's shared mutable state | `synchronized` (private final lock) |
| A visibility-only flag (shutdown, toggle) | `volatile boolean` |
| A counter / accumulator | `AtomicInteger` / `AtomicLong` / `LongAdder` |
| Shared map | `ConcurrentHashMap` ([[6. Concurrent Collections]]) |
| Producer–consumer / work handoff | `BlockingQueue` ([[5. Concurrent Utilities]]) |
| Async pipelines, chaining, combining | `CompletableFuture` ([[7. Async Programming]]) |
| Coordination across JVMs / pods | DB row lock, or a distributed lock ([[10. Distributed Concurrency]]) |

# Detailed Explanation

## Why Synchronization Exists — Shared Mutable State

Synchronization is only ever needed for **shared mutable state**. Three words, each doing work:

- **Shared** — more than one thread can reach it (an instance field of an object two threads hold, a static field, an object in a cache).
- **Mutable** — its value can change. `final String NAME = "JAVA"` can't, so it needs nothing.
- **State** — the data an object currently holds. `balance` is the state of an `Account`.

**You need synchronization only when all three are true:**

```text
Multiple threads   +   shared data   +   at least one thread mutates it
```

If any one is false, you need nothing:

| Case | Why it's safe |
|---|---|
| `int x = 10;` inside a method | Local — lives on each thread's private stack (thread confinement) |
| `final String NAME = "JAVA";` | Immutable — nothing can change |
| Only one thread ever touches it | No concurrency at all |
| Shared + mutable + multi-threaded | ❌ **Synchronization required** |

**The bug this prevents — the lost update.** Wallet balance is `1000`, two threads each debit `100`:

```java
class Wallet {
    private long balance = 1000;
    void debit(long amt) { balance -= amt; }   // NOT atomic: read, subtract, write
}
```

| Expected | What can actually happen |
|---|---|
| `1000 → 900 → 800` | A reads `1000` · B reads `1000` · A writes `900` · B writes `900` → **final `900`** |

One debit vanished. In a wallet that's real money leaking. The cause: `balance -= amt` *looks* like one instruction but is three.

**Read-modify-write.** `count++` compiles to:

```text
read count   →   add 1   →   write back
```

Any thread can be scheduled out between those steps. So the interview answer to *"is `count++` atomic?"* is a flat **no**.

**The three problems synchronization solves** — almost every topic in this note comes back to this table:

| Problem | Meaning | Broken example |
|---|---|---|
| **Atomicity** | The operation completes as one indivisible unit | `count++`, `balance -= amt` |
| **Visibility** | Other threads actually see the latest value | a `while (running)` loop that never exits |
| **Ordering** | Writes become visible in an order the JMM guarantees | seeing `ready == true` but `data == 0` |

**Mutual exclusion** is the mechanism for atomicity: only one thread at a time inside the critical section.

```java
synchronized (lock) { balance += 100; }   // Thread A inside → Thread B waits
```

And **thread safety** is the property you're aiming for: *a class is thread-safe if it behaves correctly when multiple threads use it simultaneously, with no extra coordination from the caller.* `ConcurrentHashMap` is; `HashMap` is not.

> [!tip] The interview framing
> "Is synchronization always needed?" — No. Only for shared *mutable* state. Local variables are thread-safe because each thread has its own stack. Immutable objects (including `String`) are thread-safe because there is nothing to change. Say that and you've answered four questions at once.

## `synchronized` — Mutual Exclusion via the Monitor

`synchronized` is a JVM-supported keyword that gives you **three** things. Most people remember only the first:

1. **Mutual exclusion** — one thread at a time.
2. **Memory visibility** — the next thread to acquire the same lock sees everything the previous one did.
3. **Happens-before guarantees** — no harmful reordering across the boundary.

Fixing the wallet:

```java
class Wallet {
    private long balance;
    synchronized void debit(long amt) { balance -= amt; }   // one thread at a time
}
```

Two forms:

```java
// Synchronized METHOD — locks 'this' (instance) or the Class object (static)
synchronized void debit(long amt) { ... }

// Synchronized BLOCK — you choose the lock object; narrower critical section
private final Object lock = new Object();
void debit(long amt) {
    synchronized (lock) { balance -= amt; }   // only this line is guarded
}
```

A synchronized *method* is (near enough) sugar for a block on `this`:

```java
public synchronized void deposit() { ... }
// ≡
public void deposit() { synchronized (this) { ... } }
```

And a **`static synchronized`** method locks the `Class` object, not any instance:

```java
public static synchronized void process() { ... }
// ≡  synchronized (Counter.class) { ... }
```

That's **one lock for the whole class** — there is exactly one `Counter.class` per class loader, so all instances contend for it. An instance-level and a static-level synchronized method therefore do *not* exclude each other: different locks.

> [!warning] Prefer the block, prefer a private lock
> A synchronized *method* locks on `this` — anyone holding a reference to your object can write `synchronized (walletInstance) { ... }` and interfere with (or deadlock) your locking. A **`private final Object lock`** is invisible from outside, so no external code can grab it. Blocks also keep the critical section small. Rule: hold the lock for the shortest span that still preserves the invariant.

**Why small blocks matter, concretely:**

```java
// ❌ Bad — the lock is held across three network calls
public synchronized void save() {
    callDatabase();      // 500 ms
    callRedis();         // 50 ms
    callExternalApi();   // 300 ms
}

// ✅ Good — I/O outside, lock only around the shared state
public void save() {
    callDatabase();
    callRedis();
    callExternalApi();
    synchronized (lock) { balance++; }   // ~microseconds
}
```

In the bad version every other thread waits ~850 ms for work that needed the lock for microseconds. This is the single most common cause of a "the app is slow but the CPU is idle" incident: p99 latency climbing while the CPU sits idle, because most threads are `BLOCKED` rather than working. Confirm it with a thread dump (`jstack`) — many threads `- waiting to lock <0x...>` on the same monitor.

**Reentrancy.** Java locks are reentrant, so this does *not* deadlock:

```java
public synchronized void a() { b(); }   // holds the monitor
public synchronized void b() { }        // same thread, same monitor → allowed
```

**Different objects don't block each other:**

```java
Counter c1 = new Counter(), c2 = new Counter();
// Thread A: c1.increment();   Thread B: c2.increment();   → no blocking, different monitors
```

> [!info] `synchronized` gives you visibility *as well as* atomicity
> Releasing a monitor publishes everything the thread did before it; acquiring the *same* monitor makes those writes visible. So `synchronized` doesn't just serialise — it flushes. That's why you almost never need `volatile` **and** `synchronized` on the same field.

## The Intrinsic Monitor — What Actually Gets Locked

Every Java object carries a hidden **monitor** (a.k.a. intrinsic lock) in its header. You can't touch it directly; only the JVM can.

```text
+---------------------+
|      Object         |
+---------------------+
| Data (fields)       |
| Metadata            |
| Monitor  ← the lock |
+---------------------+
```

`synchronized (obj)` acquires `obj`'s monitor on entry and releases it on exit — **including when an exception is thrown**, which is why you can never "forget to unlock" with `synchronized`.

**The most important sentence in this section:** `synchronized` never locks a *variable*, and never locks *code*. **It locks an object.**

```java
class Counter {
    private int count = 0;
    public synchronized void increment() { count++; }
}
```

`count` is not locked — it's a primitive, it has no monitor. The JVM acquires the monitor of the **`Counter` object (`this`)**. The primitive is protected *indirectly*: every path that touches it is serialised by the same monitor.

> [!example] The locker analogy
> A bank locker holds cash, documents, jewellery. The **cash isn't locked** — the *locker* is. Everything inside becomes protected because the only way in is through the one door. The object is the locker; its fields are the contents; the monitor is the door.

**So which monitor does a block acquire?** Whatever the expression evaluates to — and it must be an object reference:

| You write | Monitor acquired | Verdict |
|---|---|---|
| `synchronized (this)` | the current object | Works, but public-ish |
| `synchronized (lock)` where `private final Object lock` | that object | ✅ Best practice |
| `synchronized (Counter.class)` | the `Class` object | Class-wide lock (static state) |
| `synchronized ("LOCK")` | the interned `String` literal | ❌ Shared JVM-wide — unrelated code can collide |
| `synchronized (boxedInteger)` | the `Integer` object | ❌ Boxed values are cached/shared, and reassigning changes the lock |
| `synchronized (new Object())` | a **fresh** monitor every call | ❌ Excludes nobody |
| `synchronized (x)` where `int x` | — | ❌ **Compile error** — primitives have no monitor |

**Key properties of the monitor:**

- **One per object.** Threads synchronizing on *different* objects never block each other.
- **Reentrant, via a hold count.** Enter → `1`, nested enter → `2`, return → `1`, return → `0` and only *then* is it released. Another thread waiting must wait for the count to reach `0`.
- **Automatically released** on normal exit *and* on exception. No leak possible.
- **Entry queue with no fairness promise.** When the owner leaves, the JVM picks *a* waiting thread according to JVM/OS scheduling policy — **not FIFO**. Never write code that relies on the order.

> [!warning] A lock protects a critical section, not a variable
> The monitor has **no idea** which fields you meant to protect:
> ```java
> class Account {
>     int balance, rewardPoints;
>     private final Object lock = new Object();
>     void updateBalance() { synchronized (lock) { balance++; } }
>     void bumpPoints()    { rewardPoints++; }            // ❌ unprotected — still racy
> }
> ```
> It only guarantees one thread at a time inside the block. **You** are responsible for making *every* access to that state use *the same* lock. A field guarded on one path and not another is not guarded at all. (Document it: `// guarded by lock`.)

**The flip side of "one lock per object" — you can split state deliberately:**

```java
private final Object balanceLock = new Object();
private final Object orderLock   = new Object();

synchronized (balanceLock) { balance++; }   // these two no longer block each other
synchronized (orderLock)   { orders++;  }
```

Two unrelated pieces of state, two locks, no false contention. Taken all the way down to a data structure this becomes **lock striping** — partition the data and lock per partition, so threads touching different keys never contend. That's the idea behind `ConcurrentHashMap` ([[6. Concurrent Collections]]), and it's worth knowing by name.

## `volatile` — Visibility and Ordering Without Mutual Exclusion

`volatile` is the most misunderstood keyword in Java. It is **not** "a lightweight `synchronized`" — it provides **no mutual exclusion at all**. It gives you exactly two of the three guarantees: **visibility** and **ordering**.

**The problem it solves.** Each CPU core has its own caches:

```text
Main memory:   running = true
Thread A core cache:  running = true     ← keeps reading this
Thread B writes:      running = false    → main memory
Thread A still sees:  running = true     ← forever
```

```java
class Worker implements Runnable {
    private volatile boolean running = true;   // without volatile the loop may spin forever
    public void run() { while (running) { doWork(); } }
    public void stop() { running = false; }    // seen by the worker promptly
}
```

Without `volatile`, the JIT is even allowed to hoist the read out of the loop entirely — an infinite loop that "shouldn't be possible" and that never reproduces on your laptop.

**What it guarantees:**

1. **Visibility** — every read of a `volatile` sees the most recent write, from any thread. No stale cached copy.
2. **Ordering** — a `volatile` write publishes everything written before it; a `volatile` read of the *same* field sees all of it.

**What it does NOT guarantee — atomicity of compound actions:**

```java
volatile int count = 0;
count++;                  // ❌ still broken
```

`count = 5`; A reads `5`, B reads `5`, A writes `6`, B writes `6`. Expected `7`, got `6` — the same lost update as before. `volatile` makes each individual read and write fresh; it does not make the read-modify-write **trio** indivisible.

| | `volatile` | `synchronized` |
|---|---|---|
| Visibility | ✅ | ✅ |
| Ordering | ✅ | ✅ |
| Mutual exclusion | ❌ | ✅ |
| Atomicity of compound ops | ❌ | ✅ |
| Blocks threads | Never | Yes (contention) |
| Cost | Very cheap | Heavier (contention, context switches) |

**Use `volatile` for:** shutdown/stop flags, feature toggles, status flags, occasionally-updated config references, and **safe publication of an immutable object** (swap the whole reference — see the thread-safety patterns below).

**Don't use it for:** counters, balances, inventory, wallet amounts — anything read-modify-write. Use `AtomicInteger`/`AtomicLong` ([[5. Concurrent Utilities]]) or `synchronized`.

> [!info] How the JVM enforces it — memory barriers
> The compiler inserts **memory barriers** (fences) around volatile accesses:
> ```text
> Writer:  write normal fields → [BARRIER] → write volatile
> Reader:  read volatile       → [BARRIER] → read normal fields
> ```
> Nothing may be reordered across a barrier, and the barrier forces the cache traffic. You don't need the specific fence names (LoadLoad, StoreStore…) for SDE-2 unless you're interviewing for JVM/low-level roles — knowing "volatile ⇒ barriers ⇒ no harmful reordering + visibility" is the level that's expected.

> [!tip] Is reading a `volatile` atomic?
> Yes — a single read or write of a `volatile` field is atomic, *including* `long` and `double` (which are the one case where non-volatile 64-bit access could tear on some 32-bit JVMs). It's only **compound** operations that aren't.

## Happens-Before — the Rule Everything Else Reduces To ⭐

This is the concept to nail, because `synchronized`, `volatile`, `start()`, `join()` and atomics are all just **different ways of buying the same thing: a happens-before edge.**

**Why it had to exist.** Without rules, this question has no answer:

```java
// Thread A            // Thread B
x = 10;                print(x);
y = 20;                print(y);
```

Can B see `x` but not `y`? Stale values? Nobody knows — the compiler, JIT and CPU all reorder and cache freely (see [[1. Core Fundamentals]] §10). The JMM needed a formal answer to *"when is one thread guaranteed to see another thread's changes?"* That answer is happens-before.

> **Definition:** if action **A happens-before** action **B**, then everything A did is guaranteed **visible** to B, and B cannot be reordered to appear before A.

Two crucial clarifications, both commonly asked:

- It is **not** about wall-clock time. "A ran earlier" means nothing without an edge.
- It does **not** mean thread A finishes before thread B starts. It's a statement about **memory effects**, not scheduling.

> [!example] The bell analogy — the one to remember
> A teacher writes answers on a whiteboard, then rings a bell. Students wait for the bell, then read the board.
> ```text
> Teacher:  write answers  →  ring bell        (bell = volatile write)
> Student:  hear bell      →  read whiteboard  (bell = volatile read)
> ```
> If you heard the bell, **everything written before the bell is complete and visible**. The bell itself carries no information — its whole job is to establish the ordering. That is exactly what a volatile write/read pair, or a monitor release/acquire pair, does.

**The six rules:**

| # | Rule | The edge |
|---|---|---|
| 1 | **Program order** | Within one thread, each statement happens-before the next |
| 2 | **Monitor lock** | Releasing a monitor happens-before the next acquisition of **the same** monitor |
| 3 | **Volatile** | A write to a `volatile` happens-before every subsequent read of **that same** field |
| 4 | **`Thread.start()`** | Everything before `t.start()` happens-before anything the new thread does |
| 5 | **`Thread.join()`** | Everything the thread did happens-before `t.join()` returns |
| 6 | **Transitivity** | A → B and B → C implies A → C |

**Rule 2 in code** — the reason `synchronized` publishes data:

```java
// Thread A                          // Thread B
synchronized (lock) {                synchronized (lock) {     // SAME lock
    balance = 500;                       print(balance);       // ✅ guaranteed 500
}                                    }
```

**Rules 4 and 5** — free edges you get without any lock:

```java
value = 100;
t.start();                 // rule 4: the new thread is guaranteed to see value == 100

Thread t = new Thread(() -> result = 500);
t.start();
t.join();                  // rule 5
print(result);             // ✅ guaranteed 500 — without join(), no guarantee at all
```

**Rule 6 is what makes it usable** — one volatile write can publish a whole object graph:

```java
// Thread A                    // Thread B
data = loadFromDb();  // 1     if (ready) {        // 3  volatile read
ready = true;         // 2         use(data);      // 4  ✅ sees the data
                      //   volatile write          }
```

`1 → 2` (program order), `2 → 3` (volatile rule), `3 → 4` (program order), therefore **`1 → 4`** — even though `data` itself is not volatile. This is the mechanism behind safe publication.

Now the three details that separate "memorised it" from "understood it":

> [!warning] Detail 1 — it must be the *same* lock / the *same* volatile field
> ```java
> synchronized (lock1) { balance = 500; }     // Thread A
> synchronized (lock2) { print(balance); }    // Thread B → ❌ NO edge. Different monitors.
> ```
> Same for volatile: if the reader never reads **that** volatile field, no edge exists. "I added `synchronized`" is not automatically a fix — the question is always *"on which lock, and does every accessor use it?"*

> [!warning] Detail 2 — the guarantee only covers what came *before* the write
> ```java
> data = 100;
> ready = true;   // volatile write
> x = 50;         // AFTER the barrier
> ```
> A reader that sees `ready == true` is guaranteed to see `data == 100`, but **not** `x == 50`. The volatile write is a publish point: it publishes the past, not the future.

> [!warning] Detail 3 — the reader must actually read the volatile field
> The edge is created by the *pair* (volatile write, subsequent volatile read of the same field). A reader that skips the flag and reads `data` directly gets nothing. Both halves are required — same as needing both threads to use the same monitor.

**Everything that creates an edge:**

| Operation | Edge? |
|---|---|
| Program order within a thread | ✅ |
| `synchronized` release → acquire (same monitor) | ✅ |
| `volatile` write → read (same field) | ✅ |
| `Thread.start()` / `Thread.join()` | ✅ |
| `Atomic*` operations | ✅ (on that variable) |
| `final` field frozen in a constructor | ✅ (safe publication) |
| Two threads on *different* locks | ❌ |
| "It ran earlier in wall-clock time" | ❌ |

> [!tip] The one-sentence interview answer
> "A write to a volatile variable happens-before every subsequent read of **that same** variable, which guarantees that all writes made before the volatile write are visible to the reading thread." The examiner is listening for **"that same variable"** and for the word **guarantee** (not "immediately" or "faster").

## `wait()` / `notify()` / `notifyAll()` — Threads Signalling Each Other

`synchronized` stops threads from *colliding*. `wait`/`notify` let them *coordinate* — one thread waits until another says "the condition you need is now true." This is how a bounded queue, a producer/consumer, or a connection pool is built by hand.

The alternative is busy-waiting, which is simply wrong at scale:

```java
while (queue.isEmpty()) { }   // ❌ burns a whole core doing nothing
```

The three methods live on **`Object`**, not `Thread` — every object can be a coordination point — and **must be called while holding that object's monitor**, else you get `IllegalMonitorStateException`.

- `wait()` — **releases the monitor** and parks the thread until notified. (Contrast `sleep()`, which keeps the lock — see [[2. Java Thread Basics]].)
- `notify()` — wakes **one** arbitrary waiting thread.
- `notifyAll()` — wakes **all** waiters; they re-contend for the lock.

Bounded buffer, done right:

```java
class BoundedBuffer<T> {
    private final Queue<T> q = new LinkedList<>();
    private final int cap;
    BoundedBuffer(int cap) { this.cap = cap; }

    synchronized void put(T item) throws InterruptedException {
        while (q.size() == cap) wait();      // WHILE, not if — see below
        q.add(item);
        notifyAll();                          // wake any waiting consumers
    }

    synchronized T take() throws InterruptedException {
        while (q.isEmpty()) wait();
        T item = q.remove();
        notifyAll();                          // wake any waiting producers
        return item;
    }
}
```

**Why `wait()` must release the monitor** — if it didn't:

```text
Consumer: owns monitor → waits forever
Producer: needs monitor to add an item → can never acquire it
                         → deadlock
```

Releasing is what lets the other side make the condition true. On wake-up, `wait()` **reacquires** the monitor before returning, so the code after it is still inside the critical section.

> [!warning] Always `wait()` in a `while` loop, never an `if`
> Two reasons. **(1) Spurious wakeups:** a thread may return from `wait()` without being notified — the JVM explicitly permits it. **(2) The condition can be stolen:** after `notifyAll()`, several threads wake and race for the lock; by the time this one reacquires it, another may have consumed the item. Re-checking in a `while` covers both. An `if` here is a real, subtle, production-only bug.

> [!info] `notify()` doesn't hand over the lock
> `notify()` only moves a thread from **WAITING** to **BLOCKED**. The notified thread still can't run until the notifier *exits the synchronized block* and releases the monitor. Calling `notify()` early in a long block wakes nobody early.

> [!info] Prefer `notifyAll()` unless you can prove `notify()` is safe
> With one monitor there is **one wait-set** holding *all* waiters — producers blocked on "full" and consumers blocked on "empty" queue together. `notify()` may wake a producer when you satisfied the consumers' condition; it rechecks, goes back to sleep, and the thread that *should* have woken never does — a lost-wakeup hang. `notifyAll()` is the safe default; the cost is spurious wake-ups. The proper fix for the "one wait-set" problem is a `Condition` — see [[5. Concurrent Utilities]] §11.

`wait()` vs `sleep()` — asked constantly:

| | `wait()` | `sleep()` |
|---|---|---|
| Declared on | `Object` | `Thread` |
| Releases the monitor | ✅ Yes | ❌ No |
| Must hold a monitor | ✅ Yes | ❌ No |
| Wakes on | `notify()` / `notifyAll()` / timeout / interrupt | timeout / interrupt |
| Purpose | Thread **communication** | **Delaying** execution |

> [!tip] Know the primitive, use the library
> In real code reach for `BlockingQueue`, `CountDownLatch`, `Semaphore` ([[5. Concurrent Utilities]]), or `CompletableFuture` ([[7. Async Programming]]) instead of hand-rolling `wait`/`notify`. Interviewers still ask for it because it proves you understand monitors — but shipping it is rarely the right call.

## Thread-Safety Patterns — Designing So You Don't Need to Synchronize

> "I used `synchronized`, so my code is thread-safe."

Not necessarily. Thread safety is a property of *design*, not a keyword. The cheapest lock is the one you never take. Six patterns, roughly in order of preference:

**Pattern 1 — Immutability.** ⭐ The best synchronization is none.

```java
public final class Money {                 // final class
    private final long amountMinor;        // final fields
    private final String currency;
    public Money(long amountMinor, String currency) { ... }
    // getters only; any "change" returns a NEW Money
}
```

Nothing can change after construction, so there is nothing to protect and no lock, no contention, no deadlock. This is *why* `String` is thread-safe: `s = s + "21"` creates a new `String`; the old one never mutates. (Requirements: `final` class or no overridable methods, all fields `final`, no leaked references to internal mutable state.)

**Pattern 2 — Thread confinement.** A variable only one thread can reach needs no synchronization. Local variables live on the thread's private stack — that's why they're automatically safe. In Spring, each HTTP request runs on its own thread, so locals in a controller/service method are confined by construction. (`ThreadLocal` is the explicit form — and its pooled-thread hazards are in [[2. Java Thread Basics]] §6.)

**Pattern 3 — Statelessness.** No mutable instance fields ⇒ nothing shared.

```java
@Service
public class TaxCalculator {
    public BigDecimal gst(BigDecimal amount) { return amount.multiply(RATE); }  // params only
}
```

This is the actual reason a Spring singleton bean is usually safe: **not** because it's a singleton, but because it's stateless. Add one mutable field and you've created a race shared by every request:

```java
@Service
public class PaymentService {
    private int totalPayments;   // ❌ singleton bean + mutable field = race condition
}
```

**Pattern 4 — Safe publication.** Thread A builds an object; thread B gets the reference. How does B know it sees a *fully constructed* object? Only a happens-before edge guarantees it. Safe ways to publish:

- Assign to a `volatile` field, or an `AtomicReference`.
- Assign inside a `synchronized` block that readers also use.
- Store it in a concurrent collection (`ConcurrentHashMap.put`).
- Make it reachable only through `final` fields set in a constructor (final-field freeze).
- Hand it off via a static initializer.

A plain `sharedRef = new Employee("John", 25)` with an unsynchronized reader can expose a **partially-initialised object**. Object creation is three steps — allocate memory, run the constructor, publish the reference — and without an ordering guarantee another thread can observe the published reference *before* the constructor has finished.

**Pattern 5 — Defensive copying.** Returning your internal mutable collection hands callers a way around your locks:

```java
private final List<String> subjects = new ArrayList<>();

public List<String> getSubjects() { return subjects; }                  // ❌ caller can mutate
public List<String> getSubjects() { return new ArrayList<>(subjects); } // ✅ copy
public List<String> getSubjects() { return List.copyOf(subjects); }     // ✅ immutable view
```

(Copy on the way **in** too, if a constructor takes a mutable collection.)

**Pattern 6 — Minimise shared mutable state.** Every shared field is a thing to protect and a place to get it wrong. Share only what genuinely must be shared; keep everything else local.

**The decision checklist** — walk it top-down before writing a single `synchronized`:

```text
Is the data shared across threads?      No  → done, nothing to do
        │ Yes
Can it be immutable?                    Yes → make it immutable
        │ No
Can it be thread-confined (local)?      Yes → keep it local
        │ No
Is it a counter / single field?         Yes → AtomicInteger / volatile
        │ No
                                            → synchronized
```

> [!tip] Three answers worth memorising
> **Best way to achieve thread safety?** Immutability — no locks, no contention, no deadlocks. **Are Spring singleton beans thread-safe?** Only if stateless or properly synchronized; being a singleton guarantees nothing. **Why are local variables thread-safe?** Each thread has its own stack.

## Choosing the Right Tool — Best Practices and Decision Matrix

The question every interviewer eventually asks: *"which one would you use?"*

**Best practices, condensed:**

1. **Synchronize only what's necessary** — the smallest block that preserves the invariant.
2. **Never hold a lock during slow operations** — DB, REST, Kafka publish, Redis, file I/O. One slow network call can block hundreds of threads.
3. **Prefer immutable objects** over locking mutable ones.
4. **Prefer stateless services** — especially Spring singleton beans.
5. **Keep lock objects `private final`.** A public lock lets outside code control your synchronization.
6. **Never synchronize on `String` literals** (interned, JVM-wide) or boxed primitives (cached, reassignable).
7. **Prefer higher-level utilities** — `BlockingQueue` over `wait`/`notify`, `AtomicInteger` over `volatile int`, `ConcurrentHashMap` over a synchronized `HashMap`.
8. **Don't over-synchronize.** `public synchronized int add(int a, int b) { return a + b; }` guards nothing — no shared state, no lock needed.
9. **Document the lock.** `// guarded by balanceLock` next to the field it protects. A lock is a convention; conventions need writing down.

**Feature comparison:**

| Feature | `synchronized` | `volatile` | `AtomicInteger`* |
|---|---|---|---|
| Mutual exclusion | ✅ | ❌ | ❌ (but atomic ops) |
| Visibility | ✅ | ✅ | ✅ |
| Ordering | ✅ | ✅ | ✅ |
| Atomic compound ops | ✅ | ❌ | ✅ (single var, via CAS) |
| Automatic release | ✅ | — | — |
| Blocks threads | Yes | Never | Never (CAS retry) |
| Cost | Heavier under contention | Very cheap | Cheap; degrades under heavy contention |

*`AtomicInteger`/CAS in detail: [[5. Concurrent Utilities]].

**Problem → tool:**

| Problem | Reach for |
|---|---|
| Protect an object's shared mutable state | `synchronized` (private final lock) |
| A visibility-only flag (shutdown, feature toggle) | `volatile boolean` |
| A counter / accumulator | `AtomicInteger` / `AtomicLong` / `LongAdder` |
| Shared map | `ConcurrentHashMap` ([[6. Concurrent Collections]]) |
| Producer–consumer / work handoff | `BlockingQueue` ([[5. Concurrent Utilities]]) |
| Async pipelines, chaining, combining | `CompletableFuture` ([[7. Async Programming]]) |
| Coordination across JVMs / pods | DB row lock, or a distributed lock ([[10. Distributed Concurrency]]) |

**Common production mistakes** (all seen in real codebases):

- Wrapping a `HashMap` in `synchronized` blocks instead of using `ConcurrentHashMap`.
- `volatile int count; count++;` instead of `AtomicInteger`.
- Holding a lock across an HTTP or DB call.
- `new Thread()` per request instead of a pool ([[4. Executors and Thread Pools]]).
- Swallowing `InterruptedException`. At minimum restore the flag:
  ```java
  catch (InterruptedException e) { Thread.currentThread().interrupt(); }
  ```
- Synchronizing the *write* path but not the *read* path — a half-guarded field is unguarded.

**If you remember only eight things from this note:**

1. Shared **mutable** state is the whole problem; remove any of the three words and the problem disappears.
2. `synchronized` locks an **object's monitor** — never a variable, never code.
3. Every Java object has an intrinsic monitor; it's reentrant and auto-released, even on exception.
4. `volatile` = visibility + ordering, **not** mutual exclusion, and `count++` is still broken.
5. **Happens-before** is the single rule; every tool here is a way to buy an edge — and it must be the **same** lock or the **same** volatile field.
6. A volatile write publishes the **past**, not the future — and the reader must read that same field.
7. `wait()` releases the monitor; `sleep()` does not. Always `wait()` in a `while`, and prefer `notifyAll()`.
8. The best synchronization is none — immutability, confinement, statelessness, then atomics, then `synchronized`.

## Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| Is `count++` atomic? | No — read, modify, write. Three steps, interleavable. |
| The three problems synchronization solves? | Atomicity, visibility, ordering. |
| When do you need synchronization? | Multiple threads + shared data + at least one mutation. Any one missing ⇒ not needed. |
| `volatile` vs `synchronized`? | `volatile` = visibility + ordering, non-blocking; `synchronized` = those **plus** atomicity and mutual exclusion. |
| Is `count++` safe if `count` is `volatile`? | No — `volatile` doesn't make read-modify-write indivisible. Use `AtomicInteger` or `synchronized`. |
| What does `synchronized` actually lock? | The object's intrinsic monitor — `this` for instance methods, the `Class` object for static, the named object for a block. |
| Can you synchronize on a primitive? | No — compile error. `synchronized` needs an object reference; create a `private final Object lock`. |
| Do an instance and a static synchronized method exclude each other? | No — different monitors (`this` vs the `Class` object). |
| Why is `synchronized` reentrant? | The monitor tracks the owning thread and a hold count, so the owner can re-acquire it. |
| Do threads acquire a contended monitor in FIFO order? | No — JVM/OS scheduling decides. Never rely on order. |
| Why is synchronizing on a `String` literal bad? | Literals are interned and JVM-wide, so unrelated code can accidentally share your lock. |
| Is a `synchronized` block released if an exception is thrown? | Yes — always, which is why you can't leak an intrinsic monitor. |
| What does happens-before actually guarantee? | Visibility **and** ordering of memory effects — not scheduling, not wall-clock order. |
| Can happens-before exist without `synchronized`? | Yes — `volatile`, `start()`, `join()`, atomics, `final`-field publication. |
| After a volatile write, is everything visible? | Only what was written **before** it. Writes after the volatile write get no guarantee. |
| Is a `long` write atomic? | Only if it's `volatile` (or otherwise guarded) — non-volatile 64-bit writes could tear on some 32-bit JVMs. |
| `sleep()` vs `wait()`? | `sleep()` keeps the lock, time-based; `wait()` releases the monitor and waits for `notify()`. |
| Why `wait()` in a `while`, not an `if`? | Spurious wakeups, plus another thread can consume the condition before you reacquire the lock. |
| `notify()` vs `notifyAll()`? | `notify()` wakes one arbitrary waiter (risk: wrong thread ⇒ lost wakeup); `notifyAll()` is the safe default. |
| Does `notify()` release the lock? | No — the waiter moves WAITING→BLOCKED and runs only after the notifier exits the block. |
| Why must `wait()` be called inside `synchronized`? | It operates on that object's monitor and must release it — without owning it you get `IllegalMonitorStateException`. |
| What is lock striping? | Partitioning data so each partition has its own lock — the `ConcurrentHashMap` idea. |
| Best way to achieve thread safety? | Immutability. No locks, no contention, no deadlocks. |
| Are Spring singleton beans thread-safe? | Only if stateless or properly synchronized. Singleton ≠ thread-safe. |
| Why are local variables thread-safe? | Each thread has its own stack — they're thread-confined. |
| Safe ways to publish an object? | `volatile`/`AtomicReference`, inside the same lock readers use, a concurrent collection, `final` fields set in the constructor, or a static initializer. |
| What can go wrong publishing without an edge? | A reader can see the reference before the constructor finished — a partially-initialised object. |
