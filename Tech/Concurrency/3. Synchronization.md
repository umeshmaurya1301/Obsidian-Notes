Covers Roadmap section 3. Note 1 told you *what* goes wrong when threads share state — races, lost updates, stale reads from CPU caches. Note 2 gave you threads to run. This note is the toolbox for making shared state safe, and the mental models to pick the right tool.

> [!info] The through-line of this note
> Synchronization is **not a Java feature** — it's the answer to one problem: **concurrent access to shared mutable state** (§1). Everything here is a different-priced answer to that problem.
>
> Two distinct guarantees hide under the word "synchronization" — keep them apart:
>
> 1. **Visibility / ordering** — will thread B ever *see* thread A's write, and in the right order? Fixed by `volatile` (§4) — cheap, no mutual exclusion.
> 2. **Atomicity / mutual exclusion** — will a read-modify-write (`balance -= amt`) run without another thread interleaving? Fixed by `synchronized` (§2) and `Lock` (§7).
>
> The chain: `synchronized` is built on the **intrinsic monitor** every object carries (§3). Both it and `volatile` are just ways of buying **happens-before edges** (§5) — the one rule the whole Java Memory Model reduces to. That same monitor powers **`wait`/`notify`** so threads can *signal* each other (§6). `synchronized` is simple but rigid, so Java adds the explicit **`Lock`** interface (§7) → **`ReentrantLock`** (§8) → **`ReadWriteLock`** for read-heavy state (§9) → **`Condition`** for targeted signalling (§10). Each step buys flexibility at the cost of "you must now `unlock()` yourself."
>
> Then the production half: contention (§11), deadlock prevention (§12), designing classes that need no locks at all (§13), the singleton question (§14), and a decision matrix (§15).
>
> One line to anchor everything: **`volatile` guarantees visibility but not atomicity; `synchronized` guarantees both.** (You saw the table in [[1. Core Fundamentals]] — this note is the *why*.)

### 1. Why Synchronization Exists — Shared Mutable State

Synchronization is only ever needed for **shared mutable state**. Three words, each doing work:

- **Shared** — more than one thread can reach it (an instance field of an object two threads hold, a static field, an object in a cache).
- **Mutable** — its value can change. `final String NAME = "JAVA"` can't, so it needs nothing.
- **State** — the data an object currently holds. `balance` is the state of an `Account`.

**You need synchronization only when all three are true:**

```text
Multiple threads   +   shared data   +   at least one thread mutates it
```

If any one is false, you need nothing:

| Case | Why it's safe |
|---|---|
| `int x = 10;` inside a method | Local — lives on each thread's private stack (thread confinement, §13) |
| `final String NAME = "JAVA";` | Immutable — nothing can change |
| Only one thread ever touches it | No concurrency at all |
| Shared + mutable + multi-threaded | ❌ **Synchronization required** |

**The bug this prevents — the lost update.** Wallet balance is `1000`, two threads each debit `100`:

```java
class Wallet {
    private long balance = 1000;
    void debit(long amt) { balance -= amt; }   // NOT atomic: read, subtract, write
}
```

| Expected | What can actually happen |
|---|---|
| `1000 → 900 → 800` | A reads `1000` · B reads `1000` · A writes `900` · B writes `900` → **final `900`** |

One debit vanished. In a wallet that's real money leaking. The cause: `balance -= amt` *looks* like one instruction but is three.

**Read-modify-write.** `count++` compiles to:

```text
read count   →   add 1   →   write back
```

Any thread can be scheduled out between those steps. So the interview answer to *"is `count++` atomic?"* is a flat **no**.

**The three problems synchronization solves** — almost every topic in this note comes back to this table:

| Problem | Meaning | Broken example |
|---|---|---|
| **Atomicity** | The operation completes as one indivisible unit | `count++`, `balance -= amt` |
| **Visibility** | Other threads actually see the latest value | a `while (running)` loop that never exits |
| **Ordering** | Writes become visible in an order the JMM guarantees | seeing `ready == true` but `data == 0` |

**Mutual exclusion** is the mechanism for atomicity: only one thread at a time inside the critical section.

```java
synchronized (lock) { balance += 100; }   // Thread A inside → Thread B waits
```

And **thread safety** is the property you're aiming for: *a class is thread-safe if it behaves correctly when multiple threads use it simultaneously, with no extra coordination from the caller.* `ConcurrentHashMap` is; `HashMap` is not.

> [!tip] The interview framing
> "Is synchronization always needed?" — No. Only for shared *mutable* state. Local variables are thread-safe because each thread has its own stack. Immutable objects (including `String`) are thread-safe because there is nothing to change. Say that and you've answered four questions at once.

### 2. `synchronized` — Mutual Exclusion via the Monitor

`synchronized` is a JVM-supported keyword that gives you **three** things. Most people remember only the first:

1. **Mutual exclusion** — one thread at a time.
2. **Memory visibility** — the next thread to acquire the same lock sees everything the previous one did.
3. **Happens-before guarantees** — no harmful reordering across the boundary (§5).

Fixing §1's wallet:

```java
class Wallet {
    private long balance;
    synchronized void debit(long amt) { balance -= amt; }   // one thread at a time
}
```

Two forms:

```java
// Synchronized METHOD — locks 'this' (instance) or the Class object (static)
synchronized void debit(long amt) { ... }

// Synchronized BLOCK — you choose the lock object; narrower critical section
private final Object lock = new Object();
void debit(long amt) {
    synchronized (lock) { balance -= amt; }   // only this line is guarded
}
```

A synchronized *method* is (near enough) sugar for a block on `this`:

```java
public synchronized void deposit() { ... }
// ≡
public void deposit() { synchronized (this) { ... } }
```

And a **`static synchronized`** method locks the `Class` object, not any instance:

```java
public static synchronized void process() { ... }
// ≡  synchronized (Counter.class) { ... }
```

That's **one lock for the whole class** — there is exactly one `Counter.class` per class loader, so all instances contend for it. An instance-level and a static-level synchronized method therefore do *not* exclude each other: different locks.

> [!warning] Prefer the block, prefer a private lock
> A synchronized *method* locks on `this` — anyone holding a reference to your object can write `synchronized (walletInstance) { ... }` and interfere with (or deadlock) your locking. A **`private final Object lock`** is invisible from outside, so no external code can grab it. Blocks also keep the critical section small. Rule: hold the lock for the shortest span that still preserves the invariant.

**Why small blocks matter, concretely:**

```java
// ❌ Bad — the lock is held across three network calls
public synchronized void save() {
    callDatabase();      // 500 ms
    callRedis();         // 50 ms
    callExternalApi();   // 300 ms
}

// ✅ Good — I/O outside, lock only around the shared state
public void save() {
    callDatabase();
    callRedis();
    callExternalApi();
    synchronized (lock) { balance++; }   // ~microseconds
}
```

In the bad version every other thread waits ~850 ms for work that needed the lock for microseconds. This is the single most common cause of a "the app is slow but the CPU is idle" incident (§11).

**Reentrancy.** Java locks are reentrant, so this does *not* deadlock:

```java
public synchronized void a() { b(); }   // holds the monitor
public synchronized void b() { }        // same thread, same monitor → allowed
```

**Different objects don't block each other:**

```java
Counter c1 = new Counter(), c2 = new Counter();
// Thread A: c1.increment();   Thread B: c2.increment();   → no blocking, different monitors
```

> [!info] `synchronized` gives you visibility *as well as* atomicity
> Releasing a monitor publishes everything the thread did before it; acquiring the *same* monitor makes those writes visible. So `synchronized` doesn't just serialise — it flushes. That's why you almost never need `volatile` **and** `synchronized` on the same field.

### 3. The Intrinsic Monitor — What Actually Gets Locked

Every Java object carries a hidden **monitor** (a.k.a. intrinsic lock) in its header. You can't touch it directly; only the JVM can.

```text
+---------------------+
|      Object         |
+---------------------+
| Data (fields)       |
| Metadata            |
| Monitor  ← the lock |
+---------------------+
```

`synchronized (obj)` acquires `obj`'s monitor on entry and releases it on exit — **including when an exception is thrown**, which is why you can never "forget to unlock" with `synchronized`.

**The most important sentence in this section:** `synchronized` never locks a *variable*, and never locks *code*. **It locks an object.**

```java
class Counter {
    private int count = 0;
    public synchronized void increment() { count++; }
}
```

`count` is not locked — it's a primitive, it has no monitor. The JVM acquires the monitor of the **`Counter` object (`this`)**. The primitive is protected *indirectly*: every path that touches it is serialised by the same monitor.

> [!example] The locker analogy
> A bank locker holds cash, documents, jewellery. The **cash isn't locked** — the *locker* is. Everything inside becomes protected because the only way in is through the one door. The object is the locker; its fields are the contents; the monitor is the door.

**So which monitor does a block acquire?** Whatever the expression evaluates to — and it must be an object reference:

| You write | Monitor acquired | Verdict |
|---|---|---|
| `synchronized (this)` | the current object | Works, but public-ish (§2) |
| `synchronized (lock)` where `private final Object lock` | that object | ✅ Best practice |
| `synchronized (Counter.class)` | the `Class` object | Class-wide lock (static state) |
| `synchronized ("LOCK")` | the interned `String` literal | ❌ Shared JVM-wide — unrelated code can collide |
| `synchronized (boxedInteger)` | the `Integer` object | ❌ Boxed values are cached/shared, and reassigning changes the lock |
| `synchronized (new Object())` | a **fresh** monitor every call | ❌ Excludes nobody |
| `synchronized (x)` where `int x` | — | ❌ **Compile error** — primitives have no monitor |

**Key properties of the monitor:**

- **One per object.** Threads synchronizing on *different* objects never block each other.
- **Reentrant, via a hold count.** Enter → `1`, nested enter → `2`, return → `1`, return → `0` and only *then* is it released. Another thread waiting must wait for the count to reach `0`.
- **Automatically released** on normal exit *and* on exception. No leak possible.
- **Entry queue with no fairness promise.** When the owner leaves, the JVM picks *a* waiting thread according to JVM/OS scheduling policy — **not FIFO**. Never write code that relies on the order.

> [!warning] A lock protects a critical section, not a variable
> The monitor has **no idea** which fields you meant to protect:
> ```java
> class Account {
>     int balance, rewardPoints;
>     private final Object lock = new Object();
>     void updateBalance() { synchronized (lock) { balance++; } }
>     void bumpPoints()    { rewardPoints++; }            // ❌ unprotected — still racy
> }
> ```
> It only guarantees one thread at a time inside the block. **You** are responsible for making *every* access to that state use *the same* lock. A field guarded on one path and not another is not guarded at all. (Document it: `// guarded by lock`.)

**The flip side of "one lock per object" — you can split state deliberately:**

```java
private final Object balanceLock = new Object();
private final Object orderLock   = new Object();

synchronized (balanceLock) { balance++; }   // these two no longer block each other
synchronized (orderLock)   { orders++;  }
```

Two unrelated pieces of state, two locks, no false contention. This is the seed of **lock granularity** (§11).

**Monitor vs `Lock`** — not the same thing:

| Monitor (intrinsic) | `Lock` (explicit) |
|---|---|
| Built into every Java object | A separate interface, `java.util.concurrent.locks.Lock` |
| Used by `synchronized` | Used by `ReentrantLock` and friends |
| Automatic acquire/release | Manual `lock()` / `unlock()` |
| Simpler, JVM-optimised | More flexible (§7) |

### 4. `volatile` — Visibility and Ordering Without Locking

`volatile` is the most misunderstood keyword in Java. It is **not** "a lightweight `synchronized`" — it provides **no mutual exclusion at all**. It gives you exactly two of the three guarantees from §1: **visibility** and **ordering**.

**The problem it solves.** Each CPU core has its own caches:

```text
Main memory:   running = true
Thread A core cache:  running = true     ← keeps reading this
Thread B writes:      running = false    → main memory
Thread A still sees:  running = true     ← forever
```

```java
class Worker implements Runnable {
    private volatile boolean running = true;   // without volatile the loop may spin forever
    public void run() { while (running) { doWork(); } }
    public void stop() { running = false; }    // seen by the worker promptly
}
```

Without `volatile`, the JIT is even allowed to hoist the read out of the loop entirely — an infinite loop that "shouldn't be possible" and that never reproduces on your laptop.

**What it guarantees:**

1. **Visibility** — every read of a `volatile` sees the most recent write, from any thread. No stale cached copy.
2. **Ordering** — a `volatile` write publishes everything written before it; a `volatile` read of the *same* field sees all of it (§5).

**What it does NOT guarantee — atomicity of compound actions:**

```java
volatile int count = 0;
count++;                  // ❌ still broken
```

`count = 5`; A reads `5`, B reads `5`, A writes `6`, B writes `6`. Expected `7`, got `6` — the same lost update as §1. `volatile` makes each individual read and write fresh; it does not make the read-modify-write **trio** indivisible.

| | `volatile` | `synchronized` |
|---|---|---|
| Visibility | ✅ | ✅ |
| Ordering | ✅ | ✅ |
| Mutual exclusion | ❌ | ✅ |
| Atomicity of compound ops | ❌ | ✅ |
| Blocks threads | Never | Yes (contention) |
| Cost | Very cheap | Heavier (contention, context switches) |

**Use `volatile` for:** shutdown/stop flags, feature toggles, status flags, occasionally-updated config references, and **safe publication of an immutable object** (swap the whole reference — see §13).

**Don't use it for:** counters, balances, inventory, wallet amounts — anything read-modify-write. Use `AtomicInteger`/`AtomicLong` ([[5. Concurrent Utilities]]) or a lock.

> [!info] How the JVM enforces it — memory barriers
> The compiler inserts **memory barriers** (fences) around volatile accesses:
> ```text
> Writer:  write normal fields → [BARRIER] → write volatile
> Reader:  read volatile       → [BARRIER] → read normal fields
> ```
> Nothing may be reordered across a barrier, and the barrier forces the cache traffic. You don't need the specific fence names (LoadLoad, StoreStore…) for SDE-2 unless you're interviewing for JVM/low-level roles — knowing "volatile ⇒ barriers ⇒ no harmful reordering + visibility" is the level that's expected.

> [!tip] Is reading a `volatile` atomic?
> Yes — a single read or write of a `volatile` field is atomic, *including* `long` and `double` (which are the one case where non-volatile 64-bit access could tear on some 32-bit JVMs). It's only **compound** operations that aren't.

### 5. Happens-Before — the Rule Everything Else Reduces To ⭐

This is the concept to nail, because `synchronized`, `volatile`, `start()`, `join()`, locks and atomics are all just **different ways of buying the same thing: a happens-before edge.**

**Why it had to exist.** Without rules, this question has no answer:

```java
// Thread A            // Thread B
x = 10;                print(x);
y = 20;                print(y);
```

Can B see `x` but not `y`? Stale values? Nobody knows — the compiler, JIT and CPU all reorder and cache freely (see [[1. Core Fundamentals]] §10). The JMM needed a formal answer to *"when is one thread guaranteed to see another thread's changes?"* That answer is happens-before.

> **Definition:** if action **A happens-before** action **B**, then everything A did is guaranteed **visible** to B, and B cannot be reordered to appear before A.

Two crucial clarifications, both commonly asked:

- It is **not** about wall-clock time. "A ran earlier" means nothing without an edge.
- It does **not** mean thread A finishes before thread B starts. It's a statement about **memory effects**, not scheduling.

> [!example] The bell analogy — the one to remember
> A teacher writes answers on a whiteboard, then rings a bell. Students wait for the bell, then read the board.
> ```text
> Teacher:  write answers  →  ring bell        (bell = volatile write)
> Student:  hear bell      →  read whiteboard  (bell = volatile read)
> ```
> If you heard the bell, **everything written before the bell is complete and visible**. The bell itself carries no information — its whole job is to establish the ordering. That is exactly what a volatile write/read pair, or a monitor release/acquire pair, does.

**The six rules:**

| # | Rule | The edge |
|---|---|---|
| 1 | **Program order** | Within one thread, each statement happens-before the next |
| 2 | **Monitor lock** | Releasing a monitor happens-before the next acquisition of **the same** monitor |
| 3 | **Volatile** | A write to a `volatile` happens-before every subsequent read of **that same** field |
| 4 | **`Thread.start()`** | Everything before `t.start()` happens-before anything the new thread does |
| 5 | **`Thread.join()`** | Everything the thread did happens-before `t.join()` returns |
| 6 | **Transitivity** | A → B and B → C implies A → C |

**Rule 2 in code** — the reason `synchronized` publishes data:

```java
// Thread A                          // Thread B
synchronized (lock) {                synchronized (lock) {     // SAME lock
    balance = 500;                       print(balance);       // ✅ guaranteed 500
}                                    }
```

**Rules 4 and 5** — free edges you get without any lock:

```java
value = 100;
t.start();                 // rule 4: the new thread is guaranteed to see value == 100

Thread t = new Thread(() -> result = 500);
t.start();
t.join();                  // rule 5
print(result);             // ✅ guaranteed 500 — without join(), no guarantee at all
```

**Rule 6 is what makes it usable** — one volatile write can publish a whole object graph:

```java
// Thread A                    // Thread B
data = loadFromDb();  // 1     if (ready) {        // 3  volatile read
ready = true;         // 2         use(data);      // 4  ✅ sees the data
                      //   volatile write          }
```

`1 → 2` (program order), `2 → 3` (volatile rule), `3 → 4` (program order), therefore **`1 → 4`** — even though `data` itself is not volatile. This is the mechanism behind safe publication (§13) and behind DCL (§14).

Now the three details that separate "memorised it" from "understood it":

> [!warning] Detail 1 — it must be the *same* lock / the *same* volatile field
> ```java
> synchronized (lock1) { balance = 500; }     // Thread A
> synchronized (lock2) { print(balance); }    // Thread B → ❌ NO edge. Different monitors.
> ```
> Same for volatile: if the reader never reads **that** volatile field, no edge exists. "I added `synchronized`" is not automatically a fix — the question is always *"on which lock, and does every accessor use it?"*

> [!warning] Detail 2 — the guarantee only covers what came *before* the write
> ```java
> data = 100;
> ready = true;   // volatile write
> x = 50;         // AFTER the barrier
> ```
> A reader that sees `ready == true` is guaranteed to see `data == 100`, but **not** `x == 50`. The volatile write is a publish point: it publishes the past, not the future.

> [!warning] Detail 3 — the reader must actually read the volatile field
> The edge is created by the *pair* (volatile write, subsequent volatile read of the same field). A reader that skips the flag and reads `data` directly gets nothing. Both halves are required — same as needing both threads to use the same monitor.

**Everything that creates an edge:**

| Operation | Edge? |
|---|---|
| Program order within a thread | ✅ |
| `synchronized` release → acquire (same monitor) | ✅ |
| `volatile` write → read (same field) | ✅ |
| `Thread.start()` / `Thread.join()` | ✅ |
| `Lock.unlock()` → `Lock.lock()` (same lock) | ✅ |
| `Atomic*` operations | ✅ (on that variable) |
| `final` field frozen in a constructor | ✅ (safe publication) |
| Two threads on *different* locks | ❌ |
| "It ran earlier in wall-clock time" | ❌ |

> [!tip] The one-sentence interview answer
> "A write to a volatile variable happens-before every subsequent read of **that same** variable, which guarantees that all writes made before the volatile write are visible to the reading thread." The examiner is listening for **"that same variable"** and for the word **guarantee** (not "immediately" or "faster").

### 6. `wait()` / `notify()` / `notifyAll()` — Threads Signalling Each Other

`synchronized` stops threads from *colliding*. `wait`/`notify` let them *coordinate* — one thread waits until another says "the condition you need is now true." This is how a bounded queue, a producer/consumer, or a connection pool is built by hand.

The alternative is busy-waiting, which is simply wrong at scale:

```java
while (queue.isEmpty()) { }   // ❌ burns a whole core doing nothing
```

The three methods live on **`Object`**, not `Thread` — every object can be a coordination point — and **must be called while holding that object's monitor**, else you get `IllegalMonitorStateException`.

- `wait()` — **releases the monitor** and parks the thread until notified. (Contrast `sleep()`, which keeps the lock — see [[2. Java Thread Basics]].)
- `notify()` — wakes **one** arbitrary waiting thread.
- `notifyAll()` — wakes **all** waiters; they re-contend for the lock.

Bounded buffer, done right:

```java
class BoundedBuffer<T> {
    private final Queue<T> q = new LinkedList<>();
    private final int cap;
    BoundedBuffer(int cap) { this.cap = cap; }

    synchronized void put(T item) throws InterruptedException {
        while (q.size() == cap) wait();      // WHILE, not if — see below
        q.add(item);
        notifyAll();                          // wake any waiting consumers
    }

    synchronized T take() throws InterruptedException {
        while (q.isEmpty()) wait();
        T item = q.remove();
        notifyAll();                          // wake any waiting producers
        return item;
    }
}
```

**Why `wait()` must release the monitor** — if it didn't:

```text
Consumer: owns monitor → waits forever
Producer: needs monitor to add an item → can never acquire it
                         → deadlock
```

Releasing is what lets the other side make the condition true. On wake-up, `wait()` **reacquires** the monitor before returning, so the code after it is still inside the critical section.

> [!warning] Always `wait()` in a `while` loop, never an `if`
> Two reasons. **(1) Spurious wakeups:** a thread may return from `wait()` without being notified — the JVM explicitly permits it. **(2) The condition can be stolen:** after `notifyAll()`, several threads wake and race for the lock; by the time this one reacquires it, another may have consumed the item. Re-checking in a `while` covers both. An `if` here is a real, subtle, production-only bug.

> [!info] `notify()` doesn't hand over the lock
> `notify()` only moves a thread from **WAITING** to **BLOCKED**. The notified thread still can't run until the notifier *exits the synchronized block* and releases the monitor. Calling `notify()` early in a long block wakes nobody early.

> [!info] Prefer `notifyAll()` unless you can prove `notify()` is safe
> With one monitor there is **one wait-set** holding *all* waiters — producers blocked on "full" and consumers blocked on "empty" queue together. `notify()` may wake a producer when you satisfied the consumers' condition; it rechecks, goes back to sleep, and the thread that *should* have woken never does — a lost-wakeup hang. `notifyAll()` is the safe default; the cost is spurious wake-ups. The real fix for the "one wait-set" problem is `Condition` (§10).

`wait()` vs `sleep()` — asked constantly:

| | `wait()` | `sleep()` |
|---|---|---|
| Declared on | `Object` | `Thread` |
| Releases the monitor | ✅ Yes | ❌ No |
| Must hold a monitor | ✅ Yes | ❌ No |
| Wakes on | `notify()` / `notifyAll()` / timeout / interrupt | timeout / interrupt |
| Purpose | Thread **communication** | **Delaying** execution |

> [!tip] Know the primitive, use the library
> In real code reach for `BlockingQueue`, `CountDownLatch`, `Semaphore`, `Condition` ([[5. Concurrent Utilities]]), or `CompletableFuture` ([[7. Async Programming]]) instead of hand-rolling `wait`/`notify`. Interviewers still ask for it because it proves you understand monitors — but shipping it is rarely the right call.

### 7. The `Lock` Interface — Explicit Locking

`synchronized` is convenient but rigid. Four questions it cannot answer *at all*:

- Can I try to acquire and give up immediately if it's taken?
- Can I wait only 200 ms?
- Can I be interrupted (cancelled) while waiting?
- Can I have more than one wait-set on the same lock?

`java.util.concurrent.locks.Lock` (Java 5) makes the lock an ordinary object and answers all four.

```java
Lock lock = new ReentrantLock();
lock.lock();
try {
    // critical section
} finally {
    lock.unlock();   // MANDATORY — and must be in finally
}
```

The four methods that matter:

| Method | Behaviour |
|---|---|
| `lock()` | Acquire, blocking indefinitely. Closest to `synchronized`. |
| `unlock()` | Release. Always in `finally`. |
| `tryLock()` | Acquire **or return `false` immediately**. No waiting. |
| `tryLock(t, unit)` | Wait up to `t`, then return `false`. Impossible with `synchronized`. |
| `lockInterruptibly()` | Blocks, but throws `InterruptedException` if the waiting thread is interrupted. |

What you gain over `synchronized`:

| Capability | `synchronized` | `Lock` |
|---|---|---|
| Try without blocking | ❌ | `tryLock()` |
| Time-boxed wait | ❌ | `tryLock(timeout, unit)` |
| Interruptible wait | ❌ | `lockInterruptibly()` |
| Fairness (FIFO) option | ❌ | `new ReentrantLock(true)` |
| Multiple condition queues | ❌ (one wait-set) | `lock.newCondition()` |
| Acquire and release in different scopes | ❌ | ✅ (you own it) |
| Automatic release on exception | ✅ | ❌ **you own it** |

> [!warning] The cost of explicit locks: you must `unlock()` yourself
> ```java
> lock.lock();
> balance++;
> throw new RuntimeException();   // ❌ unlock() never runs — lock held forever
> ```
> Every other thread now blocks permanently. `synchronized` releases even on exception; a `Lock` does not. **The `try { } finally { unlock(); }` shape is not optional.** This is the trade-off: more power, more rope.

`tryLock` is the killer feature — for responsiveness and for deadlock avoidance:

```java
if (lock.tryLock(200, TimeUnit.MILLISECONDS)) {
    try { transfer(); } finally { lock.unlock(); }
} else {
    // couldn't get the lock in time — fail fast instead of hanging the request
    throw new ResourceBusyException();
}
```

`lockInterruptibly()` is the other one worth remembering: if an HTTP client disconnects and the request thread is interrupted, a thread parked in `synchronized` keeps waiting regardless, while `lockInterruptibly()` unwinds immediately.

> [!info] Is `Lock` faster than `synchronized`?
> Not inherently. It often was on older JVMs; modern JVMs optimise `synchronized` heavily (biased/thin locks, lock coarsening, escape-analysis elision). **Choose on features, not on assumed speed** — and default to `synchronized` because it can't leak a lock.

> [!info] This is the in-JVM cousin of a distributed lock
> Timeouts, try-acquire, fencing — the same concerns scale up to Redis/ZooKeeper locks when you have multiple pods. In one JVM, `ReentrantLock` is the tool; across JVMs, the database or a distributed lock is (see [[10. Distributed Concurrency]]). The failure modes rhyme.

### 8. `ReentrantLock` — The Workhorse `Lock`

`Lock` is only an interface; `ReentrantLock` is the standard implementation. It gives the same mutual exclusion as `synchronized` plus everything in the §7 table.

```java
class Account {
    private final ReentrantLock lock = new ReentrantLock();
    private long balance;

    void debit(long amt) {
        lock.lock();
        try {
            if (balance < amt) throw new InsufficientFundsException();
            balance -= amt;
        } finally { lock.unlock(); }
    }
}
```

**"Reentrant" = a hold count**, exactly like the intrinsic monitor:

```text
lock()            → hold count 1
lock() (nested)   → hold count 2
unlock()          → hold count 1
unlock()          → hold count 0   → now another thread may acquire
```

So `lock()` and `unlock()` must be balanced. One missing `unlock()` leaves the count at `1` forever and every other thread blocks — again, hence `finally`.

**Fairness** — a favourite interview topic:

| | `new ReentrantLock()` (default, **unfair**) | `new ReentrantLock(true)` (**fair**) |
|---|---|---|
| Who gets the lock next | Usually the head of the queue, but a brand-new thread may **barge** in ahead of it | Roughly arrival order (FIFO) |
| Throughput | Higher (barging avoids context switches) | Lower — stricter handoff |
| Starvation | Theoretically possible | Prevented |

Use the default. Reach for fair mode only when starvation (from [[1. Core Fundamentals]] §9) is a *demonstrated* problem — it has real throughput cost.

**`tryLock` for deadlock avoidance** — the transfer pattern:

```java
if (from.tryLock()) {
    try {
        if (to.tryLock()) {
            try { transfer(); } finally { to.unlock(); }
        }   // couldn't get the second lock → back off, release the first, retry later
    } finally { from.unlock(); }
}
```

Because the thread never *waits* while holding a lock, the circular-wait condition can't form. (Lock ordering, §12, is still the primary strategy.)

> [!info] Does `ReentrantLock` use monitors?
> No — and this trips people up. `synchronized` uses the JVM's intrinsic monitor built into the object header. `ReentrantLock` is an ordinary Java class in `java.util.concurrent.locks`, built on `AbstractQueuedSynchronizer` (an `int` state + a CAS + `LockSupport.park/unpark`). Different machinery, same happens-before guarantees.

> [!info] When to pick `ReentrantLock` over `synchronized`
> Default to `synchronized` — simpler, auto-released, well optimised. Reach for `ReentrantLock` only when you need a named feature: `tryLock`/timeout, interruptible acquisition, fairness, or multiple `Condition`s. Extra power you don't need is just extra rope (a forgotten `unlock`).

### 9. `ReadWriteLock` — Many Readers or One Writer

A plain lock serialises *everything*, even concurrent reads that can't conflict. But reads don't corrupt each other (from [[9. Database Concurrency]]: R-R is always safe). `ReadWriteLock` exploits that.

The compatibility matrix — the whole idea in four rows:

| Holder → / Arriving ↓ | Reader | Writer |
|---|---|---|
| **Reader** | ✅ allowed (parallel) | ❌ waits |
| **Writer** | ❌ waits | ❌ waits |

So: **many readers, or exactly one writer, never both.** Writers need exclusivity because a reader landing mid-update (`balance = balance - 500` half-applied) would see torn, inconsistent state.

```java
class RateTable {
    private final ReadWriteLock rw = new ReentrantReadWriteLock();
    private Map<String, BigDecimal> fx = new HashMap<>();

    BigDecimal rate(String pair) {          // hot path — thousands of reads/sec
        rw.readLock().lock();
        try { return fx.get(pair); }
        finally { rw.readLock().unlock(); }
    }

    void reload(Map<String, BigDecimal> fresh) {   // rare — a few times a day
        rw.writeLock().lock();
        try { fx = fresh; }
        finally { rw.writeLock().unlock(); }
    }
}
```

Good fits: FX/rate tables, product catalogues, feature-flag and app config, routing tables in a payment switch, in-memory caches, dictionaries — **read-dominated, write-rare, relatively stable state.**

> [!info] Only a win when reads massively outnumber writes
> A `ReadWriteLock` has more bookkeeping than a plain lock, and heavy writes can *starve readers* (or vice versa). At 90% writes it gives almost nothing — every write blocks everyone, and you've paid the overhead for nothing. For write-heavy or tiny critical sections a plain `ReentrantLock` is faster. And for a shared map specifically, `ConcurrentHashMap` ([[6. Concurrent Collections]]) usually beats hand-rolling this.

> [!warning] No lock upgrade
> You cannot hold the read lock and then acquire the write lock — that self-deadlocks (the writer waits for all readers to release, but you *are* a reader who won't). Release the read lock, take the write lock, then **re-check state** — it may have changed in the gap. `StampedLock` offers optimistic reads and a controlled upgrade path, but it's non-reentrant and easy to misuse: know it exists, reach for it rarely.

### 10. `Condition` — Multiple Wait-Sets on One Lock

§6 left a real problem: an intrinsic monitor has **exactly one wait-set**. Producers blocked on "buffer full" and consumers blocked on "buffer empty" queue up together, so `notify()` can wake the wrong kind of thread and `notifyAll()` wakes everyone to make one of them proceed.

`Condition` (Java 5, part of the `Lock` API) fixes it:

> Think of a `Condition` as **one of several named waiting rooms attached to a single lock.**

```java
Lock lock = new ReentrantLock();
Condition notFull  = lock.newCondition();
Condition notEmpty = lock.newCondition();
```

```java
// Producer
lock.lock();
try {
    while (queue.size() == cap) notFull.await();   // parks in the notFull room only
    queue.add(item);
    notEmpty.signal();                              // wakes exactly one consumer
} finally { lock.unlock(); }

// Consumer
lock.lock();
try {
    while (queue.isEmpty()) notEmpty.await();
    T item = queue.remove();
    notFull.signal();                               // wakes exactly one producer
} finally { lock.unlock(); }
```

Direct one-to-one mapping with the monitor methods:

| Monitor (`synchronized`) | `Condition` (`Lock`) |
|---|---|
| `Object` | `Condition` from `lock.newCondition()` |
| requires `synchronized` | requires the owning `Lock` held |
| `wait()` | `await()` |
| `notify()` | `signal()` |
| `notifyAll()` | `signalAll()` |
| **One** wait-set per object | **Many** wait-sets per lock |

`await()` behaves exactly like `wait()`: it **releases the lock**, parks, and **reacquires** before returning — so the `while (condition) await();` rule from §6 applies unchanged (spurious wakeups exist here too).

> [!example] This is how `ArrayBlockingQueue` is built
> Internally: one `ReentrantLock` plus two `Condition`s named `notEmpty` and `notFull` — exactly the code above. When you use a `BlockingQueue` instead of hand-rolling producer/consumer, this is the implementation you're getting for free.

> [!warning] `Condition` cannot be used with `synchronized`
> It belongs to the `Lock` API. `Condition` works only with a `Lock` implementation you hold — there's no way to attach one to an intrinsic monitor. If you want multiple wait-sets, you must move off `synchronized`.

> [!tip] The interview progression
> Interviewers walk this ladder because each rung fixes a limitation of the previous one:
> ```text
> synchronized → monitor → wait/notify → Lock → ReentrantLock → Condition
> ```
> If you can name *what limitation* each step removes (rigid → one wait-set → no timeout → no fairness → one wait-set again), you're answering the question behind the question.

### 11. Lock Contention and Performance

Everything so far was about **correctness**. This section is about **throughput**.

> **Lock contention** = multiple threads competing for the same lock.

One ATM, 100 people: one person transacts, 99 queue. If each holds the lock 10 ms, the last thread waits ~1 second. CPU utilisation *falls* while latency climbs, because most threads are BLOCKED, not working.

**Production symptoms:**

- p99 latency climbing while **CPU sits idle** — the giveaway.
- Many threads in `BLOCKED` state in a thread dump, all on the same monitor.
- Throughput flat or *falling* as you add threads.

**Tools:** `jstack` (thread dump — shows `- waiting to lock <0x...>` and who owns it), Java Flight Recorder (JFR has dedicated `JavaMonitorEnter` events), VisualVM, Mission Control.

**Cause 1 — the critical section is too big.**

```java
// ❌ everyone waits ~805 ms
public synchronized void processOrder() {
    validate(); callDatabase(); callExternalApi(); updateInventory();
}

// ✅ lock held ~5 ms
public void processOrder() {
    validate(); callDatabase(); callExternalApi();
    synchronized (lock) { updateInventory(); }
}
```

**Cause 2 — one lock protecting unrelated state.** `balance` and `orders` have nothing to do with each other, but a single `lock` makes every balance update block every order update. Split them (§3):

```java
private final Object balanceLock = new Object();
private final Object orderLock   = new Object();
```

**Lock granularity** — the trade-off to name in interviews:

| Coarse-grained (one lock for the object) | Fine-grained (one lock per piece of state) |
|---|---|
| Simple, easy to reason about | More concurrency, less waiting |
| More contention | More complex; more locks ⇒ more deadlock risk (§12) |
| Easier to maintain | Needs a documented lock order |

**Lock striping** is fine-grained locking taken to a data structure: instead of one lock for a whole map, partition it and lock per partition, so threads touching different keys never contend. That's the core idea behind `ConcurrentHashMap` ([[6. Concurrent Collections]] §2) — historically explicit segment locks, now per-bin CAS + node locking. Same principle, and worth knowing by name.

**Then stop locking where you can:** `AtomicInteger` and friends use **CAS (compare-and-swap)** — a lock-free retry loop rather than blocking. For simple counters under moderate contention they beat locks comfortably (`LongAdder` beats them both under *heavy* contention). CAS in detail: [[5. Concurrent Utilities]] §2.

**Checklist to reduce contention:**

- Keep critical sections small — hold the lock only around the state mutation.
- **Never** do I/O (DB, REST, Kafka, Redis, file) while holding a lock.
- Separate locks for unrelated state.
- `ReadWriteLock` for read-dominated state (§9).
- `AtomicInteger`/`LongAdder` for counters; `ConcurrentHashMap` for shared maps.
- Best of all: **reduce shared mutable state** so there's nothing to lock (§13).

### 12. Deadlock Prevention

Recap from [[1. Core Fundamentals]] §7: Thread A holds lock 1 and waits for lock 2; Thread B holds lock 2 and waits for lock 1. Neither ever moves. The classic trigger is a transfer:

```java
// Thread A: transfer(acctX → acctY)      // Thread B: transfer(acctY → acctX)
lock(acctX); lock(acctY);                 lock(acctY); lock(acctX);
```

Under load this deadlocks — and only under load, which is why it reaches production.

**Strategy 1 — consistent lock ordering. ⭐ The primary answer.**

If every thread acquires locks in the same global order, a cycle is *impossible*. For transfers, don't order by "from → to" (caller-dependent); order by something intrinsic and total:

```java
Account first  = (a.id() < b.id()) ? a : b;      // always smaller id first
Account second = (a.id() < b.id()) ? b : a;
synchronized (first) { synchronized (second) { transfer(a, b, amt); } }
```

Now the `X→Y` and `Y→X` threads both take `X` then `Y`. One waits; nobody cycles. (Watch for equal ids — self-transfer — and use a tiebreaker like `System.identityHashCode` if ids can collide.)

**Strategy 2 — `tryLock` and back off.** §8's nested-`tryLock` pattern: if you can't get all the locks you need, release what you hold and retry (with jitter). No thread ever waits while holding, so no circular wait.

**Strategy 3 — timeouts.** `lock.tryLock(5, TimeUnit.SECONDS)` converts "hang forever" into a failed request you can log, retry, or surface. `synchronized` cannot do this at all — a good reason to reach for `Lock` on a multi-lock path.

**Strategy 4 — fewer nested locks.** Each additional lock held simultaneously multiplies the risk. Where the invariant allows: acquire → finish → release → acquire the next, rather than nesting.

**Strategy 5 — never hold a lock during I/O.** A 2-second DB call inside a lock isn't just slow (§11) — it widens the window in which a second thread can grab the other lock and complete a cycle. Do the I/O first, lock only to mutate.

**Detecting one in production:** take a thread dump (`jstack <pid>`). The JVM detects monitor deadlocks itself and prints:

```text
Found one Java-level deadlock:
=============================
"thread-A" waiting to lock monitor 0x… which is held by "thread-B"
"thread-B" waiting to lock monitor 0x… which is held by "thread-A"
```

It names both threads, both locks, and both stacks. Note the limitation: the JVM reliably detects **intrinsic monitor** deadlocks (and `AbstractQueuedSynchronizer`-based `Lock` deadlocks in modern JVMs), but a deadlock via a semaphore, a latch, or a full thread pool won't show up as "Found one Java-level deadlock" — it just looks like a hang.

> [!tip] The sharp answer
> "Deadlocks are far easier to prevent than to debug. The primary prevention is **consistent global lock ordering**; `tryLock` with timeout and back-off is the fallback where a total order isn't available. Then: keep critical sections small, hold as few locks as possible, and never block on I/O while holding one." `tryLock` *helps avoid* deadlock — it isn't a guarantee (you can still livelock retrying), so don't overclaim it.

### 13. Thread-Safety Patterns — Designing So You Don't Need Locks

> "I used `synchronized`, so my code is thread-safe."

Not necessarily. Thread safety is a property of *design*, not a keyword. The cheapest lock is the one you never take. Six patterns, roughly in order of preference:

**Pattern 1 — Immutability.** ⭐ The best synchronization is none.

```java
public final class Money {                 // final class
    private final long amountMinor;        // final fields
    private final String currency;
    public Money(long amountMinor, String currency) { ... }
    // getters only; any "change" returns a NEW Money
}
```

Nothing can change after construction, so there is nothing to protect and no lock, no contention, no deadlock. This is *why* `String` is thread-safe: `s = s + "21"` creates a new `String`; the old one never mutates. (Requirements: `final` class or no overridable methods, all fields `final`, no leaked references to internal mutable state.)

**Pattern 2 — Thread confinement.** A variable only one thread can reach needs no synchronization. Local variables live on the thread's private stack — that's why they're automatically safe. In Spring, each HTTP request runs on its own thread, so locals in a controller/service method are confined by construction. (`ThreadLocal` is the explicit form — and its pooled-thread hazards are in [[2. Java Thread Basics]] §6.)

**Pattern 3 — Statelessness.** No mutable instance fields ⇒ nothing shared.

```java
@Service
public class TaxCalculator {
    public BigDecimal gst(BigDecimal amount) { return amount.multiply(RATE); }  // params only
}
```

This is the actual reason a Spring singleton bean is usually safe: **not** because it's a singleton, but because it's stateless. Add one mutable field and you've created a race shared by every request:

```java
@Service
public class PaymentService {
    private int totalPayments;   // ❌ singleton bean + mutable field = race condition
}
```

**Pattern 4 — Safe publication.** Thread A builds an object; thread B gets the reference. How does B know it sees a *fully constructed* object? Only a happens-before edge (§5) guarantees it. Safe ways to publish:

- Assign to a `volatile` field, or an `AtomicReference`.
- Assign inside a `synchronized`/`Lock` block that readers also use.
- Store it in a concurrent collection (`ConcurrentHashMap.put`).
- Make it reachable only through `final` fields set in a constructor (final-field freeze).
- Hand it off via a static initializer.

A plain `sharedRef = new Employee("John", 25)` with an unsynchronized reader can expose a partially-initialised object — the same hazard that breaks naive DCL (§14).

**Pattern 5 — Defensive copying.** Returning your internal mutable collection hands callers a way around your locks:

```java
private final List<String> subjects = new ArrayList<>();

public List<String> getSubjects() { return subjects; }                  // ❌ caller can mutate
public List<String> getSubjects() { return new ArrayList<>(subjects); } // ✅ copy
public List<String> getSubjects() { return List.copyOf(subjects); }     // ✅ immutable view
```

(Copy on the way **in** too, if a constructor takes a mutable collection.)

**Pattern 6 — Minimise shared mutable state.** Every shared field is a thing to protect and a place to get it wrong. Share only what genuinely must be shared; keep everything else local.

**The decision checklist** — walk it top-down before writing a single `synchronized`:

```text
Is the data shared across threads?      No  → done, nothing to do
        │ Yes
Can it be immutable?                    Yes → make it immutable
        │ No
Can it be thread-confined (local)?      Yes → keep it local
        │ No
Is it a counter / single field?         Yes → AtomicInteger / volatile
        │ No
                                            → synchronized / Lock
```

> [!tip] Three answers worth memorising
> **Best way to achieve thread safety?** Immutability — no locks, no contention, no deadlocks. **Are Spring singleton beans thread-safe?** Only if stateless or properly synchronized; being a singleton guarantees nothing. **Why are local variables thread-safe?** Each thread has its own stack.

### 14. Double-Checked Locking — the Singleton Question

The most-asked singleton question, and a perfect test of §5.

**The broken version:**

```java
public static Singleton getInstance() {
    if (instance == null)              // two threads can both see null
        instance = new Singleton();    // → two instances, singleton broken
    return instance;
}
```

**Fix 1 — synchronize the method.** Correct, and honestly fine for most code:

```java
public static synchronized Singleton getInstance() { ... }
```

The objection: *every* call takes the lock, forever, even though the write happens once. Under heavy read traffic that's pure contention.

**Fix 2 — double-checked locking:**

```java
public class Singleton {
    private static volatile Singleton instance;      // volatile is MANDATORY

    public static Singleton getInstance() {
        if (instance == null) {                      // 1st check — no lock, fast path
            synchronized (Singleton.class) {
                if (instance == null) {              // 2nd check — under the lock
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

**Why two checks?** The first is the fast path — once initialised, no thread ever takes the lock again. The second is the correctness check: several threads can pass the first check before any of them enters the block, so whoever gets in must re-verify that nobody else already built it.

**Why `volatile` is mandatory** — this is the real question, and it's a §5 question. `instance = new Singleton()` is not one step:

```text
1. allocate memory
2. run the constructor
3. publish the reference into `instance`
```

Without ordering guarantees, another thread can observe **3 before 2**:

```java
if (instance != null)   // ✅ true — reference published
    instance.use();     // ❌ but the constructor hasn't finished → partially built object
```

The second thread never enters the synchronized block (its first check passed), so it gets **no happens-before edge** and no guarantee. `volatile` supplies both halves: the write publishes everything before it, and the reader's volatile read sees it. Without `volatile`, DCL is a genuinely broken idiom — this was a real Java bug class for years.

**In real projects, prefer these.** Lazy, thread-safe, no explicit synchronization, no `volatile` to forget:

```java
// Initialization-on-demand holder idiom — the JVM guarantees class init happens once
public class Singleton {
    private Singleton() {}
    private static class Holder { private static final Singleton INSTANCE = new Singleton(); }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}
```

```java
// Enum singleton — simplest, and serialization/reflection-safe
public enum Singleton { INSTANCE; public void doWork() { ... } }
```

Both lean on a happens-before edge you get for free: **class initialization is guaranteed to complete exactly once, before any thread can see the class's static fields.** The holder class isn't initialised until `getInstance()` first touches it — that's where the laziness comes from.

> [!tip] What the interviewer is checking
> Not whether you can type DCL — whether you can explain **why `volatile`**. Answer with the three-step object creation and "the fast-path reader gets no happens-before edge, so it can see a published-but-unconstructed reference." Then add that in production you'd use the holder idiom or an enum, and that in Spring you'd just let the container manage the singleton. That last sentence is what separates SDE-2 from SDE-1.

### 15. Choosing the Right Tool — Best Practices and Decision Matrix

The question every interviewer eventually asks: *"which one would you use?"*

**Best practices, condensed:**

1. **Synchronize only what's necessary** — the smallest block that preserves the invariant.
2. **Never hold a lock during slow operations** — DB, REST, Kafka publish, Redis, file I/O. One slow network call can block hundreds of threads.
3. **Prefer immutable objects** (§13) over locking mutable ones.
4. **Prefer stateless services** — especially Spring singleton beans.
5. **Keep lock objects `private final`.** A public lock lets outside code control your synchronization.
6. **Never synchronize on `String` literals** (interned, JVM-wide) or boxed primitives (cached, reassignable).
7. **Avoid nested locks**; where unavoidable, define and document a global lock order (§12).
8. **Prefer higher-level utilities** — `BlockingQueue` over `wait`/`notify`, `AtomicInteger` over `volatile int`, `ConcurrentHashMap` over a synchronized `HashMap`.
9. **Don't over-synchronize.** `public synchronized int add(int a, int b) { return a + b; }` guards nothing — no shared state, no lock needed.
10. **Document the lock.** `// guarded by balanceLock` next to the field it protects. A lock is a convention; conventions need writing down (§3).

**Feature comparison:**

| Feature | `synchronized` | `ReentrantLock` | `ReadWriteLock` | `volatile` | `AtomicInteger`* |
|---|---|---|---|---|---|
| Mutual exclusion | ✅ | ✅ | ✅ (write side) | ❌ | ❌ (but atomic ops) |
| Visibility | ✅ | ✅ | ✅ | ✅ | ✅ |
| Ordering | ✅ | ✅ | ✅ | ✅ | ✅ |
| Atomic compound ops | ✅ | ✅ | ✅ | ❌ | ✅ (single var, via CAS) |
| `tryLock` / timeout | ❌ | ✅ | ✅ | — | — |
| Interruptible acquire | ❌ | ✅ | ✅ | — | — |
| Fair mode | ❌ | ✅ | ✅ | — | — |
| Multiple readers | ❌ | ❌ | ✅ | — | — |
| Automatic release | ✅ | ❌ | ❌ | — | — |
| Blocks threads | Yes | Yes | Yes | Never | Never (CAS retry) |

*`AtomicInteger`/CAS in detail: [[5. Concurrent Utilities]].

**Problem → tool:**

| Problem | Reach for |
|---|---|
| Protect an object's shared mutable state | `synchronized` (private final lock) |
| Need timeout / non-blocking try / interruptible acquire / fairness | `ReentrantLock` |
| Read-heavy, write-rare shared state (config, rate table) | `ReadWriteLock` |
| A visibility-only flag (shutdown, feature toggle) | `volatile boolean` |
| A counter / accumulator | `AtomicInteger` / `AtomicLong` / `LongAdder` |
| Shared map | `ConcurrentHashMap` |
| Producer–consumer / work handoff | `BlockingQueue` |
| Complex multi-condition coordination | `Lock` + `Condition` |
| Async pipelines, chaining, combining | `CompletableFuture` (see [[7. Async Programming]]) |
| Coordination across JVMs / pods | DB row lock, or a distributed lock ([[10. Distributed Concurrency]]) |

**Common production mistakes** (all seen in real codebases):

- Wrapping a `HashMap` in `synchronized` blocks instead of using `ConcurrentHashMap`.
- `volatile int count; count++;` instead of `AtomicInteger`.
- Holding a lock across an HTTP or DB call.
- `new Thread()` per request instead of a pool ([[4. Executors and Thread Pools]]).
- Swallowing `InterruptedException`. At minimum restore the flag:
  ```java
  catch (InterruptedException e) { Thread.currentThread().interrupt(); }
  ```
- Synchronizing the *write* path but not the *read* path — a half-guarded field is unguarded (§3).

**If you remember only ten things from this note:**

1. Shared **mutable** state is the whole problem; remove any of the three words and the problem disappears.
2. `synchronized` locks an **object's monitor** — never a variable, never code.
3. Every Java object has an intrinsic monitor; it's reentrant and auto-released.
4. `volatile` = visibility + ordering, **not** mutual exclusion, and `count++` is still broken.
5. **Happens-before** is the single rule; every tool here is a way to buy an edge — and it must be the **same** lock or the **same** volatile field.
6. `wait()` releases the monitor; `sleep()` does not. Always `wait()` in a `while`.
7. `ReentrantLock` buys `tryLock`, timeout, interruptibility, fairness — at the price of `finally { unlock(); }`.
8. `ReadWriteLock` only pays off when reads massively outnumber writes; there is no lock upgrade.
9. `Condition` gives one lock many named wait-sets — that's how `ArrayBlockingQueue` works.
10. Prevent deadlock with **consistent lock ordering**; prevent contention with **small critical sections** and no I/O under lock.

### 16. Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| Is `count++` atomic? | No — read, modify, write. Three steps, interleavable. |
| The three problems synchronization solves? | Atomicity, visibility, ordering. |
| When do you need synchronization? | Multiple threads + shared data + at least one mutation. Any one missing ⇒ not needed. |
| `volatile` vs `synchronized`? | `volatile` = visibility + ordering, non-blocking; `synchronized` = those **plus** atomicity and mutual exclusion. |
| Is `count++` safe if `count` is `volatile`? | No — `volatile` doesn't make read-modify-write indivisible. Use `AtomicInteger` or a lock. |
| What does `synchronized` actually lock? | The object's intrinsic monitor — `this` for instance methods, the `Class` object for static, the named object for a block. |
| Can you synchronize on a primitive? | No — compile error. `synchronized` needs an object reference; create a `private final Object lock`. |
| Why is `synchronized` reentrant? | The monitor tracks the owning thread and a hold count, so the owner can re-acquire it. |
| Do threads acquire a contended monitor in FIFO order? | No — JVM/OS scheduling decides. Never rely on order. Use `new ReentrantLock(true)` if you need fairness. |
| Why is synchronizing on a `String` literal bad? | Literals are interned and JVM-wide, so unrelated code can accidentally share your lock. |
| What does happens-before actually guarantee? | Visibility **and** ordering of memory effects — not scheduling, not wall-clock order. |
| Can happens-before exist without `synchronized`? | Yes — `volatile`, `start()`, `join()`, `Lock`, atomics, `final`-field publication. |
| After a volatile write, is everything visible? | Only what was written **before** it. Writes after the volatile write get no guarantee. |
| `sleep()` vs `wait()`? | `sleep()` keeps the lock, time-based; `wait()` releases the monitor and waits for `notify()`. |
| Why `wait()` in a `while`, not an `if`? | Spurious wakeups, plus another thread can consume the condition before you reacquire the lock. |
| `notify()` vs `notifyAll()`? | `notify()` wakes one arbitrary waiter (risk: wrong thread ⇒ lost wakeup); `notifyAll()` is the safe default. |
| Does `notify()` release the lock? | No — the waiter moves WAITING→BLOCKED and runs only after the notifier exits the block. |
| Why choose `ReentrantLock` over `synchronized`? | `tryLock`, timeouts, interruptible acquire, fairness, multiple `Condition`s. Otherwise prefer `synchronized`. |
| Is `ReentrantLock` faster? | Not inherently — modern JVMs optimise `synchronized` well. Choose on features. |
| Biggest risk with `Lock`? | Forgetting `unlock()` — must be in `finally`, or the lock is held forever. |
| Does `ReentrantLock` use the object monitor? | No — it's a Java class built on AQS (state + CAS + park/unpark). |
| When does `ReadWriteLock` help? | Read-heavy, write-rare state. Caveats: no lock upgrade, writes can starve readers. |
| Why `Condition` over `wait`/`notify`? | A monitor has one wait-set; a `Lock` can have many, so you signal exactly the right group. |
| Can `Condition` be used with `synchronized`? | No — it's part of the `Lock` API. |
| What is lock contention, and how do you spot it? | Threads competing for one lock. Symptom: rising latency with idle CPU; confirm with `jstack`/JFR (many BLOCKED on one monitor). |
| How do you reduce contention? | Smaller critical sections, no I/O under lock, split locks per state, `ReadWriteLock`, atomics, less shared state. |
| What is lock striping? | Partitioning data so each partition has its own lock — the `ConcurrentHashMap` idea. |
| Best deadlock prevention? | Consistent global lock ordering (e.g. always lock the smaller account id first); `tryLock` + timeout as fallback. |
| Can `synchronized` time out? | No. Only `Lock` supports timed acquisition — a reason to use `Lock` on multi-lock paths. |
| How do you diagnose a deadlock in prod? | `jstack` — the JVM prints "Found one Java-level deadlock" with both threads, locks and stacks. |
| Best way to achieve thread safety? | Immutability. No locks, no contention, no deadlocks. |
| Are Spring singleton beans thread-safe? | Only if stateless or properly synchronized. Singleton ≠ thread-safe. |
| Why are local variables thread-safe? | Each thread has its own stack — they're thread-confined. |
| Why is `volatile` mandatory in DCL? | Object creation is allocate → construct → publish; without ordering, the fast-path reader (which takes no lock, so gets no happens-before edge) can see a published-but-unconstructed reference. |
| Better singleton than DCL? | Initialization-on-demand holder idiom, or an `enum` — lazy, thread-safe, no explicit synchronization. |
| Safe ways to publish an object? | `volatile`/`AtomicReference`, inside the same lock readers use, a concurrent collection, `final` fields set in the constructor, or a static initializer. |
