Covers Roadmap section 8 — Project Loom. Notes 1–7 taught you to work *around* the cost of a thread: pool them (§4), never block them, compose callbacks instead ([[7. Async Programming]]). This note is Java 21 removing the constraint that made all of that necessary. Threads become cheap, so `thread-per-request` becomes viable again — and simple blocking code becomes the *scalable* option.

> [!info] The through-line of this note
> One economic fact drove twenty years of Java concurrency design: **a thread costs ~1 MB and an OS handle**, so you can't have many. Every workaround in notes 4–7 exists because of it.
>
> 1. Most backend work is **I/O-bound** — the thread sits blocked on a DB or HTTP call, holding an expensive OS resource to do nothing (§1).
> 2. The industry's answer was async/reactive: don't block, use callbacks. It works, but you pay in **readability, debuggability and stack traces**.
> 3. **Virtual threads** (§2–§6) take the other road: keep the simple blocking style, make the thread cheap. The JVM **unmounts** a blocked virtual thread from its carrier so the OS thread goes back to work (§4). Millions of threads become possible.
> 4. That's a *scalability* win, not a speed win (§5) — and it leaks if a thread gets **pinned** (§6) or if you keep treating threads as scarce (§7).
> 5. Cheap threads then expose a second gap: nobody *owns* your concurrent tasks. **Structured concurrency** (§9–§11) gives them a parent-child scope with automatic cancellation.
> 6. And cheap threads break `ThreadLocal`'s economics, so **scoped values** (§12) replace it for request context.
>
> Anchor: **virtual threads change *how tasks run*; structured concurrency changes *how tasks are organised*; scoped values change *how context flows*.**

> [!warning] Version status — check before you write this in code
> - **Virtual threads** — **final** in Java 21 (JEP 444). Safe to use.
> - **Scoped values** — previewed 21–24, **final in Java 25** (JEP 506). The `where(...).run(...)` form below is the final shape.
> - **Structured concurrency** — still **preview** as of Java 25, and **the API changed**: the `ShutdownOnFailure` / `ShutdownOnSuccess` subclasses shown in §10 are the Java 21–24 preview form, while Java 25 (JEP 505) moves to `StructuredTaskScope.open(Joiner…)`. Learn the *concepts* — they're stable and that's what interviews test — but expect the exact API to differ by JDK. Requires `--enable-preview`.

### 1. Why — Thread-per-Request Stopped Scaling

100,000 concurrent requests, each spending 500 ms in a database call. Classic Java:

```text
Request 1 → Thread 1 → send SQL → WAIT 500ms → respond
Request 2 → Thread 2 → send SQL → WAIT 500ms → respond
...
Request 100,000 → Thread 100,000
```

```text
100,000 threads × ~1 MB stack  ≈  100 GB
```

Not happening. And that's before context-switch thrashing across 8 cores ([[1. Core Fundamentals]] §4).

**But look at what the thread is actually doing:**

```java
public User getUser() {
    return repository.findById(1);   // send query → WAIT → continue
}
```

```text
Thread: ──send SQL──[ idle, 500 ms ]──receive──continue
CPU:                 doing nothing at all
```

The expensive OS thread is occupied purely to *remember where we were*. Multiply across every DB query, Redis call, Kafka poll, REST call, and file read — most backend threads spend most of their life blocked.

**The industry's answer was to stop blocking:** `CompletableFuture`, Project Reactor, RxJava. Effective, but the cost is real:

```java
fetchUser()
    .thenCompose(this::fetchOrders)
    .thenCompose(this::fetchWallet)
    .thenApply(this::buildDashboard)
    .exceptionally(this::fallback);
```

You rewrote the program to fit the runtime: control flow becomes a callback graph, stack traces stop being meaningful, debuggers stop helping, and every library in the path must also be non-blocking or the whole thing collapses.

> [!tip] The Loom bet, in one sentence
> *Don't change how programmers write code — change what a thread costs.* Virtual threads keep `User u = repo.findById(id);` exactly as it is, and make blocking it nearly free.

### 2. What Is a Virtual Thread?

> A **virtual thread** is a lightweight thread managed by the **JVM** rather than the operating system.

```text
Platform thread:   Java Thread ──1:1──► OS Thread ──► kernel scheduler

Virtual thread:    VT A  VT B  VT C ... VT 1,000,000
                          │
                    JVM scheduler (a ForkJoinPool)
                          │
                   a handful of platform threads ("carriers")
                          │
                     operating system
```

100,000 virtual threads may run on ~8 platform threads. They're **multiplexed**, and the JVM — not the kernel — decides who runs.

> [!example] The restaurant
> **Platform threads:** one dedicated waiter per customer. A waiter standing idle while their customer reads the menu is a waiter you're still paying for. 100 customers = 100 waiters.
> **Virtual threads:** 10 waiters for 100 customers. When a customer is deciding (waiting on I/O), the waiter serves someone else and comes back. Same food, same speed per dish — vastly more customers served.

| Platform thread | Virtual thread |
|---|---|
| Managed by the **OS** | Managed by the **JVM** |
| 1 Java thread ↔ 1 OS thread | Many share a few platform threads |
| ~1 MB fixed native stack | Small, **grows on demand** on the heap |
| Expensive to create — you pool them | Cheap to create — you **don't** pool them |
| Thousands, at most | **Millions** |
| Right for CPU-bound work | Right for **I/O-bound** work |
| Kernel context switch | JVM-level park/unpark |

> [!info] They're still `java.lang.Thread`
> A virtual thread *is* a `Thread` — same API, same `try/catch`, same stack traces, works with debuggers and profilers, shows up in thread dumps. Nothing about your code needs to know. Two behavioural differences worth knowing: virtual threads are **always daemon threads** (you cannot make one non-daemon — `setDaemon(false)` throws), and they always have normal priority (`setPriority` is a no-op).

### 3. Creating Them

```java
// 1. Simplest — fire one off
Thread.startVirtualThread(() -> processPayment(txn));

// 2. Builder, when you want a name (do name them — §10 of note 4 applies here too)
Thread t = Thread.ofVirtual().name("settle-", 1).start(() -> settle(batch));
t.join();

// 3. Executor — the common enterprise form
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Txn txn : batch) {
        executor.submit(() -> process(txn));      // one NEW virtual thread per task
    }
}   // close() waits for all submitted tasks — AutoCloseable
```

```java
Thread.startVirtualThread(() -> System.out.println(Thread.currentThread()));
// VirtualThread[#21]/runnable@ForkJoinPool-1-worker-1
```

Note the name: `VirtualThread[#21]`, not `Thread-0` — and it tells you which carrier it's mounted on.

> [!warning] `newVirtualThreadPerTaskExecutor()` is not a pool
> It creates a **brand-new virtual thread for every task** and never reuses one. That's deliberate — see §7. It's an `ExecutorService` only so it drops into existing code that expects one.

### 4. Mounting and Unmounting — How It Actually Works ⭐

This is the mechanism, and the thing interviews probe.

A virtual thread runs by being **mounted** on a platform thread — its **carrier**. When it hits a blocking operation, the JVM **unmounts** it: the virtual thread's stack is stashed on the heap, and the carrier is handed to another virtual thread.

```text
Platform thread 1  ──runs──► VT A
                              │  VT A calls repository.findById()  (blocks on I/O)
                              ▼
                    JVM UNMOUNTS VT A  (its stack → heap)
                              │
Platform thread 1  ──runs──► VT B        ← carrier immediately reused, not idle
                    ...
                    database responds
                              │
                    JVM MOUNTS VT A back onto some carrier
                              ▼
                    VT A continues from exactly where it stopped
```

Compare directly:

| | Platform thread blocked on a 2 s query | Virtual thread blocked on a 2 s query |
|---|---|---|
| OS thread | **Occupied, idle, for 2 s** | Released after ~microseconds |
| During the wait | Nothing else can use it | Runs other virtual threads |
| Memory held | Full 1 MB stack | Small heap-resident stack |

Two things make this work:

1. **The JDK was rewritten.** Blocking operations throughout `java.net`, `java.nio`, `java.io`, `Socket`, `synchronized`-free locks, `Thread.sleep`, and `BlockingQueue` were retrofitted to park the virtual thread rather than block the carrier. That's why JDBC drivers, HTTP clients and Hibernate get the benefit **with no code change** — they block on sockets, and socket blocking is now unmount-aware.
2. **The scheduler is a dedicated `ForkJoinPool`** in FIFO mode, with parallelism defaulting to `availableProcessors()`. So the carrier count is small and fixed; the virtual thread count is not. (Tunable via `jdk.virtualThreadScheduler.parallelism`, but you rarely should.)

> [!info] The continuation, if you want the deeper answer
> Under the hood a virtual thread is a **continuation** plus a scheduler. Unmounting captures the continuation (copying the stack frames to the heap); mounting restores it. That's why the stack can grow on demand instead of pre-reserving 1 MB, and why "millions of threads" is a memory question rather than an OS-handle question.

### 5. "Are Virtual Threads Faster?" — No ⭐

Classic trick question. Most people say yes. The correct answer:

> **Virtual threads do not make code run faster. They improve scalability — throughput and concurrency, not latency.**

A 3-second database query takes 3 seconds on a platform thread and 3 seconds on a virtual thread. The database is the bottleneck either way. What changes is that you can have **100,000 requests waiting** on 3-second queries without 100,000 OS threads.

| | Improves? |
|---|---|
| Latency of one operation | ❌ No |
| Requests served concurrently | ✅ Dramatically |
| Memory per in-flight request | ✅ Much lower |
| Context-switching overhead | ✅ Lower (JVM park/unpark, not kernel) |
| CPU-bound throughput | ❌ No — you still only have N cores |

> [!warning] Virtual threads move the bottleneck; they don't delete it
> This is the production insight the tutorials skip. Enable virtual threads on a Spring Boot service and suddenly 10,000 requests reach your **10-connection HikariCP pool** at once. 9,990 of them queue on the connection pool instead of on the Tomcat thread pool. You replaced one queue with another — and possibly a worse one, since connection-pool waits are less visible and more likely to time out.
>
> When you adopt virtual threads, **re-examine every downstream limit**: connection pool size, per-host HTTP connection caps, downstream service rate limits, and your own semaphores (§7). Unbounded concurrency against a bounded resource is just a different failure.

### 6. Pinning — When You Lose the Benefit ⭐

A virtual thread is **pinned** when the JVM cannot unmount it. It blocks, and its **carrier platform thread blocks with it** — you're back to the old cost model, silently.

```text
VT A holds a pinned frame ──► blocks on I/O ──► carrier ALSO blocked
                                                (no other VT can use it)
```

**The two causes:**

1. **Blocking inside a `synchronized` block or method** — the monitor is tied to the carrier thread, so the JVM can't move the virtual thread out.
   ```java
   synchronized (lock) {
       jdbcTemplate.query(...);     // ❌ pins the carrier for the whole query
   }
   ```
2. **A native frame on the stack** — a JNI call, or a blocking operation inside native code.

**The fix for case 1 — use a `Lock` instead of `synchronized`:**

```java
private final ReentrantLock lock = new ReentrantLock();

lock.lock();
try {
    jdbcTemplate.query(...);      // ✅ ReentrantLock parks the VT properly; carrier is freed
} finally {
    lock.unlock();
}
```

`ReentrantLock` (and everything else in `java.util.concurrent` — [[5. Concurrent Utilities]]) is built on `LockSupport.park`, which the JVM taught to unmount virtual threads. Intrinsic monitors weren't, originally.

Better still: **don't hold any lock across I/O.** That was already the rule in [[3. Synchronization]] §11 for contention reasons; with virtual threads it's also a scalability rule.

> [!info] Diagnosing it, and the version caveat
> Pinning is invisible until you look for it — the app just doesn't scale as expected. Detect it with the JFR event **`jdk.VirtualThreadPinned`** (older JDKs: the `jdk.tracePinnedThreads` system property).
>
> **Version note:** `synchronized` pinning was substantially fixed in **Java 24** (JEP 491) — monitors became unmount-aware, so a blocking call inside `synchronized` no longer pins. On Java 21–23 it does. Since Java 21 is the LTS most shops are on, **know pinning and the `ReentrantLock` workaround** — it's still the expected interview answer — and know that it's a solved problem on newer JDKs.

### 7. Stop Treating Threads as Scarce

Cheap threads invalidate habits built around expensive ones.

**Don't pool virtual threads.** A pool exists to amortise creation cost. Virtual threads have almost none, so pooling adds queueing, contention and a concurrency ceiling for nothing:

```java
// ❌ Pointless — a fixed pool of virtual threads is just a fixed pool
ExecutorService bad = Executors.newFixedThreadPool(200, Thread.ofVirtual().factory());

// ✅ One virtual thread per task
ExecutorService good = Executors.newVirtualThreadPerTaskExecutor();
```

**But still bound access to scarce resources** — with a semaphore, not a thread pool:

```java
private final Semaphore dbPermits = new Semaphore(20);   // protect the DB, not the threads

dbPermits.acquire();
try { return repository.findById(id); }
finally { dbPermits.release(); }
```

This is the conceptual shift: **you no longer limit concurrency by limiting threads; you limit it at the resource** ([[5. Concurrent Utilities]] §8). Ten thousand virtual threads can queue harmlessly on a semaphore; ten thousand platform threads could not exist to begin with.

**Reconsider `ThreadLocal`.** It still works, but with a million threads a million copies of a cached `SimpleDateFormat` is real memory, and the pooled-thread cleanup discipline from [[2. Java Thread Basics]] §6 no longer applies (threads aren't reused, so there's no leak *between tasks* — but also no reuse benefit). For request context, use scoped values (§12).

**Don't chase virtual threads for CPU-bound work:**

```java
while (true) { calculatePrimes(); }    // never blocks → never unmounts → no benefit
```

There's nothing to overlap. Use a bounded platform-thread pool sized to your cores ([[4. Executors and Thread Pools]] §12), or a `ForkJoinPool`.

| Great fit (I/O-bound) | Wrong fit (CPU-bound) |
|---|---|
| REST endpoints, microservice calls | Encryption, compression, hashing |
| JDBC / Hibernate queries | Image and video processing |
| Redis, Kafka consumers, S3 | Large in-memory computation |
| File and network I/O | Tight numeric loops |

### 8. Spring Boot — What Actually Changes

The question everyone asks: *do I rewrite my repositories?* **No.**

```properties
# Spring Boot 3.2+ on Java 21+
spring.threads.virtual.enabled=true
```

That's the whole change. Spring configures the embedded server (Tomcat/Jetty) to serve each request on a **new virtual thread**, and everything downstream inherits it:

```text
HTTP request → Virtual thread → Controller → Service → Repository → Hibernate → JDBC → DB
                    └──────────── all on the same virtual thread ─────────────┘
```

Your code is untouched:

```java
@GetMapping("/user/{id}")
public User getUser(@PathVariable Long id) {
    return userRepository.findById(id).orElseThrow();   // unchanged. Still blocking. Now cheap.
}
```

`findById` has no idea which kind of thread it's on — it just runs on the current one. When the JDBC driver blocks on the socket, the JVM parks the virtual thread and frees the carrier.

**Three follow-ons:**

- **You don't need `@Async` for ordinary request handling.** The request is already on its own virtual thread. `@Async` remains useful for genuine fire-and-forget work — and if you use it, back it with `newVirtualThreadPerTaskExecutor()` rather than a fixed pool.
- **Blocking JDBC is the point, not a problem.** Virtual threads were designed *for* blocking APIs. This is the whole reason Loom is attractive over reactive: no R2DBC rewrite, no reactive Hibernate, no library ecosystem migration.
- **Your own executors are your choice** — `newFixedThreadPool(10)` still gives platform threads; `newVirtualThreadPerTaskExecutor()` gives virtual ones. Switch deliberately, per workload type.

> [!warning] Then immediately go check your connection pool
> Per §5: with virtual threads the web tier stops being the limit, so the next-narrowest resource becomes it — usually HikariCP. Size it deliberately, keep timeouts tight, and add a semaphore in front of anything that must not be hammered. Also audit for `synchronized` around I/O (§6), which now costs you scalability rather than just latency.

### 9. Structured Concurrency — the Problem It Solves

Cheap threads make it easy to *start* concurrent work. Nothing makes it easy to *own* it.

A dashboard needs three independent calls. With `CompletableFuture`:

```java
CompletableFuture<User>        user   = supplyAsync(this::fetchUser);
CompletableFuture<List<Order>> orders = supplyAsync(this::fetchOrders);
CompletableFuture<Wallet>      wallet = supplyAsync(this::fetchWallet);

CompletableFuture.allOf(user, orders, wallet).join();
return new Dashboard(user.join(), orders.join(), wallet.join());
```

Correct on the happy path. Now the order service fails:

- Should the user and wallet calls keep running? (They will.)
- Who cancels them? (Nobody, unless you write it.)
- What if one hangs forever? (You wait forever, unless you wrote a timeout.)
- What if the client disconnects and the parent request is abandoned? (The children carry on, still consuming threads and still hitting downstreams.)

**There is no parent-child relationship.** Three futures are three independent things that happen to be referenced by the same method. When the method returns — normally or by exception — the tasks it started can outlive it. That's a **leak**, and you must hand-write every piece of the cleanup.

> [!example] Compare with ordinary method calls
> ```java
> void process() { step1(); step2(); step3(); }
> ```
> When `process()` returns you *know* all three finished. Control flow and lifetime are the same thing — that's what makes sequential code easy to reason about. Structured concurrency restores that property for concurrent tasks:
>
> > **Child tasks belong to a parent scope, and cannot outlive it.**

### 10. `StructuredTaskScope` ⭐

```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {

    Subtask<User>        user   = scope.fork(this::fetchUser);     // start child tasks
    Subtask<List<Order>> orders = scope.fork(this::fetchOrders);
    Subtask<Wallet>      wallet = scope.fork(this::fetchWallet);

    scope.join();              // wait for all children
    scope.throwIfFailed();     // propagate the first failure

    return new Dashboard(user.get(), orders.get(), wallet.get());

}   // close() GUARANTEES no child is still running
```

No executor, no `allOf`, no `CompletableFuture`, no manual cancellation. And the `try`-with-resources block is the enforcement mechanism: **you cannot leave this block with a child still alive.**

| Operation | Does |
|---|---|
| `fork(task)` | Starts the task in a **new virtual thread**, attached to this scope; returns a `Subtask` |
| `join()` | Blocks until all children complete (or the scope's policy triggers) |
| `throwIfFailed()` | Rethrows the first child failure (`ShutdownOnFailure`) |
| `subtask.get()` | The result — only valid **after** `join()` |
| `close()` | Cancels any survivors and waits; automatic via try-with-resources |

**`ShutdownOnFailure` — all-or-nothing.** The first child to throw cancels the siblings:

```text
User    ──running────────✂ cancelled
Orders  ──✗ throws
Wallet  ──running────────✂ cancelled     → exception propagates to the parent
```

With plain `CompletableFuture`, `User` and `Wallet` would run to completion, pointlessly, and you'd have written the cancellation yourself.

**`ShutdownOnSuccess` — first one wins.** For hedged requests across replicas:

```java
try (var scope = new StructuredTaskScope.ShutdownOnSuccess<String>()) {
    scope.fork(() -> query(redis1));
    scope.fork(() -> query(redis2));
    scope.fork(() -> query(redis3));
    scope.join();
    return scope.result();      // first success; the other two are cancelled
}
```

Like `CompletableFuture.anyOf()` — except `anyOf` **doesn't cancel the losers** ([[7. Async Programming]] §8) and this does.

**Timeouts and parent cancellation come free.** `scope.joinUntil(deadline)` bounds the whole group. And if the thread running the scope is interrupted — client disconnected, request timed out — **every child is cancelled**, because cancellation propagates down the hierarchy. That's the piece you'd otherwise write by hand and get wrong.

> [!info] It pairs with virtual threads but doesn't require them
> `fork()` creates a virtual thread per child, so forking ten subtasks is trivially cheap — which is what makes fine-grained structured concurrency practical. But the model itself works with any threads; the parent-child discipline is independent of thread weight.
>
> The intended shape of a modern request:
> ```text
> HTTP request → 1 virtual thread (parent)
>                     └── StructuredTaskScope
>                           ├── virtual thread (profile)
>                           ├── virtual thread (orders)
>                           └── virtual thread (wallet)
>                     join → build response
> ```
> Plain sequential-looking code, real parallelism, guaranteed cleanup.

### 11. Structured Concurrency vs `CompletableFuture`

| `CompletableFuture` | Structured concurrency |
|---|---|
| Independent futures | **Parent-child** hierarchy |
| Manual cancellation | **Automatic** on failure / success / parent cancel |
| Easy to leak background work | Scope **guarantees** cleanup |
| Callback / pipeline style | Sequential, blocking style |
| Result is a value you compose | Result is read after `join()` |
| Errors flow through `exceptionally`/`handle` | Errors propagate like normal exceptions |

**Use structured concurrency for** request-scoped parallel work where the tasks are siblings serving one goal: dashboard aggregation, calling several microservices, parallel queries, API composition.

**`CompletableFuture` is still better for** anything that isn't a neat parent-child fan-out:

- **Dependent pipelines** — `thenCompose` chains where B needs A's result ([[7. Async Programming]] §6).
- **Fire-and-forget** work that intentionally outlives the caller (structured concurrency forbids exactly this).
- **APIs that return futures** — a library handing you a `CompletableFuture`, or a controller returning one so the servlet thread is released.
- **Callback-driven** composition, `orTimeout`, `handle`, and everything else in the `CompletionStage` vocabulary.

> [!tip] Virtual threads vs structured concurrency — the question they'll ask
> They solve **different problems** and are often confused:
> - **Virtual threads** answer *"how are tasks executed?"* → lightweight, JVM-scheduled threads.
> - **Structured concurrency** answers *"how are tasks organised and managed?"* → scoped parent-child lifetimes, cancellation, error propagation.
>
> Neither replaces the other; they were designed to be used together.

### 12. Scoped Values — Replacing `ThreadLocal`

Every layer of a request needs the current user, tenant and trace ID. Threading them through every signature is noise, so we used `ThreadLocal`:

```java
static final ThreadLocal<User> CURRENT_USER = new ThreadLocal<>();
CURRENT_USER.set(user);       // in a filter
CURRENT_USER.get();           // anywhere downstream
```

**Three problems** ([[2. Java Thread Basics]] §6 covers the first):

1. **Leaks and cross-request bleed.** Pool threads are reused. Forget `remove()` and request B reads request A's user — in payments, one customer's context on another's transaction.
2. **Unbounded mutability.** Anyone, anywhere, can `set()` it. There's no way to know who changed it or when, which is the opposite of what you want from "request context".
3. **It doesn't fit a million threads.** Per-thread mutable state was designed for hundreds of threads, not millions, and it doesn't propagate cleanly to child tasks.

**A `ScopedValue` is an immutable value bound only for a bounded execution scope:**

```java
static final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();

ScopedValue.where(CURRENT_USER, authenticatedUser)
           .run(() -> handleRequest(req));      // bound for exactly this call tree

// inside handleRequest, at any depth:
User u = CURRENT_USER.get();
```

Note what's missing: **no `set()`, no `remove()`.** You can't mutate a binding, and you can't forget to clean up — when `run()` returns, the binding is gone. Calling `get()` outside the scope throws `NoSuchElementException`. Use `.call(...)` instead of `.run(...)` when the body returns a value.

```text
ScopedValue.where(USER, u).run(() -> {
    ┌─ binding active ────────────────────┐
    │ controller → service → repository   │  all see USER.get()
    └─────────────────────────────────────┘
});                                            binding gone — automatically
```

**Child tasks inherit bindings**, which is why this pairs so well with §10:

```java
ScopedValue.where(CURRENT_USER, user).run(() -> {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        scope.fork(this::fetchOrders);      // both children can call CURRENT_USER.get()
        scope.fork(this::fetchWallet);      // no copying, no propagation code
        scope.join();
    }
});
```

That inheritance is cheap because the binding is immutable — children share it rather than copying it. It's also the piece that makes structured concurrency usable in Spring, where security context and MDC would otherwise be lost across the thread hop.

| `ThreadLocal` | `ScopedValue` |
|---|---|
| **Mutable** — `set()` anywhere | **Immutable** once bound |
| Manual `remove()` in a `finally` | **Automatic** — unbound when the scope exits |
| Leaks across pooled tasks | Scope-bound; cannot leak |
| `set()` / `get()` / `remove()` | `where(k, v).run(...)` / `get()` |
| Inheritance needs `InheritableThreadLocal` | Child tasks inherit naturally |
| Fine for legacy / genuinely mutable state | The right default with virtual threads |

**Use scoped values for** read-only request context: authenticated user, tenant ID, correlation/trace ID, locale, request ID.

**Don't use them for** counters, mutable caches, or session state that changes during the request — they're immutable contextual data, not shared mutable state. For that, pass a mutable holder explicitly or use the tools in [[5. Concurrent Utilities]]. And they don't fully replace `ThreadLocal` — keep it where you genuinely need mutable per-thread state.

### 13. The Modern Stack, Together

```text
        Virtual Threads          →  run millions of cheap, blocking tasks
                │                   (changes HOW tasks execute)
                ▼
    Structured Concurrency       →  organise them into parent-child scopes
                │                   with cancellation and error propagation
                ▼                   (changes HOW tasks are organised)
         Scoped Values           →  share immutable request context safely
                                    (changes HOW context flows)
```

One request, all three:

```java
ScopedValue.where(CURRENT_USER, user).run(() -> {          // context
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {   // structure
        var profile = scope.fork(this::fetchProfile);       // each on a virtual thread
        var orders  = scope.fork(this::fetchOrders);
        var wallet  = scope.fork(this::fetchWallet);
        scope.join();
        scope.throwIfFailed();
        return new Dashboard(profile.get(), orders.get(), wallet.get());
    }
});
```

Blocking code that reads top-to-bottom, real parallelism, automatic cancellation, no context plumbing, and a stack trace that means something. That's the Project Loom endgame — and the argument for choosing it over a reactive rewrite.

### 14. Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| What problem do virtual threads solve? | One OS thread per Java thread makes thread-per-request unaffordable when threads spend their lives blocked on I/O. Virtual threads are JVM-managed threads that unmount while blocked, so a few carriers serve millions of tasks. |
| Platform vs virtual thread? | Platform = 1:1 with an OS thread, ~1 MB stack, expensive, pool it. Virtual = JVM-scheduled, heap stack that grows on demand, cheap, one per task. |
| **Are virtual threads faster?** | **No.** They improve *scalability* (throughput, concurrency, memory), not the latency of any individual operation. A 3 s query still takes 3 s. |
| How are they implemented? | As continuations plus a scheduler. A blocked virtual thread's stack is stashed on the heap (unmount), freeing the carrier platform thread; it's remounted when ready. |
| What is a carrier thread? | The platform thread a virtual thread is currently mounted on. |
| What schedules virtual threads? | A dedicated `ForkJoinPool` in FIFO mode, parallelism = `availableProcessors()` by default. |
| Why do JDBC/Hibernate benefit with no code change? | The JDK's blocking operations (sockets, `java.io`/`nio`, `sleep`, `j.u.c` locks) were retrofitted to park the virtual thread instead of the carrier. |
| What is pinning? | A virtual thread that can't be unmounted, so its carrier blocks too. Caused by blocking inside `synchronized`, or a native/JNI frame on the stack. |
| How do you avoid pinning? | Use `ReentrantLock` instead of `synchronized` around blocking calls — better still, don't hold a lock across I/O. Detect via the `jdk.VirtualThreadPinned` JFR event. (Largely fixed for `synchronized` in Java 24.) |
| Should you pool virtual threads? | **No** — pooling exists to amortise creation cost, which they don't have. Use `newVirtualThreadPerTaskExecutor()`; bound scarce *resources* with a `Semaphore` instead. |
| Are virtual threads asynchronous? | No. Your code stays synchronous and blocking. The concurrency comes from the JVM scheduler, not callbacks. |
| Do they replace `CompletableFuture`? | Not entirely. They remove the need for async *just to avoid blocking*, but composing independent tasks, pipelines, and future-returning APIs is still `CompletableFuture`'s job. |
| Do they replace thread pools? | For I/O-bound thread-per-task work, yes. For CPU-bound work, a bounded platform-thread pool is still correct. |
| Are virtual threads daemon threads? | **Yes, always** — and you can't change it; `setDaemon(false)` throws. Priority is fixed at normal too. |
| When are virtual threads the wrong tool? | CPU-bound work — nothing blocks, so nothing unmounts, and you still only have N cores. |
| How do you enable them in Spring Boot? | `spring.threads.virtual.enabled=true` on Boot 3.2+ / Java 21+. Repository and service code is unchanged. |
| Do you need `@Async` with virtual threads? | Not for normal request handling — the request already has its own virtual thread. |
| What becomes the bottleneck after adopting them? | Whatever is still bounded — usually the DB connection pool. Virtual threads move the queue, they don't remove it. |
| What is structured concurrency? | A model where concurrent child tasks belong to a parent scope and cannot outlive it, giving automatic cancellation, error propagation and lifetime management — the concurrency equivalent of a method call's guarantees. |
| Why "structured"? | Task lifetimes follow lexical scope, exactly like nested method calls. Children can't escape the block that created them. |
| What does `fork()` do? | Starts a child task on a new virtual thread, attached to the scope. It cannot outlive the scope. |
| `ShutdownOnFailure` vs `ShutdownOnSuccess`? | First failure cancels the siblings and propagates (all-or-nothing) vs first success cancels the rest and returns (hedging). |
| How does it differ from `allOf`/`anyOf`? | `allOf` doesn't cancel on failure and `anyOf` doesn't cancel the losers; a scope cancels automatically and guarantees nothing survives the block. |
| Does structured concurrency need virtual threads? | No — it works with platform threads, but it's most useful with virtual threads because forking many children is then cheap. |
| Virtual threads vs structured concurrency? | Virtual threads = *how tasks execute*. Structured concurrency = *how tasks are organised and managed*. Complementary, not alternatives. |
| Why were scoped values introduced? | To replace `ThreadLocal` for request context: immutable, scope-bound, automatically cleaned up, and cheaply inherited by child tasks — a better fit for millions of threads. |
| `ThreadLocal` vs `ScopedValue`? | Mutable + manual `remove()` + leaks across pooled threads, vs immutable + automatic unbinding + natural inheritance by child tasks. |
| Can child tasks read a scoped value? | Yes — bindings are inherited by tasks forked inside the scope, which is why it pairs with `StructuredTaskScope`. |
| When should you *not* use scoped values? | Anything mutable — counters, caches, changing session state. They're for immutable contextual data. |
| Which of the three are production-ready? | Virtual threads: final in 21. Scoped values: final in 25. Structured concurrency: still preview, and the API changed in 25. |
