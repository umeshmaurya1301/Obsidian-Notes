# Lost Updates & High-Contention Architectures

---

# Quick Reference Summary

## The Core Problem — Lost Update

Two transactions read the same balance → both compute new values in application memory → last writer silently overwrites the first → money disappears.

> MVCC provides snapshot reads but does **NOT** protect against lost writes.

## MySQL vs PostgreSQL Behavior

| Database   | Default Isolation | Lost Update Protection        |
| ---------- | ----------------- | ----------------------------- |
| MySQL      | REPEATABLE READ   | ❌ Silently allows overwrite   |
| PostgreSQL | READ COMMITTED    | ❌ At READ COMMITTED           |
| PostgreSQL | REPEATABLE READ   | ✅ Detects conflict, aborts T1 |

## Developer Intervention — Three Solutions

| Approach                            | Mechanism                                    | When to Use                 |
| ----------------------------------- | -------------------------------------------- | --------------------------- |
| **Pessimistic** (`FOR UPDATE`)      | Lock row on SELECT, others wait              | High contention, financial  |
| **Optimistic** (version column)     | Detect stale version at UPDATE, retry        | Rare conflicts              |
| **Atomic Update** (relative update) | `SET balance = balance - amount` in SQL      | No pre-read needed          |

## High-Contention Architectures (When Locking Fails)

| Architecture                    | Key Idea                                          | Throughput   |
| ------------------------------- | ------------------------------------------------- | ------------ |
| **Append-Only Ledger**          | INSERT instead of UPDATE, snapshot for reads       | High         |
| **Kafka Partitioned Queues**    | Serialize by account_id, single consumer per partition | Very High |
| **Redis Lua + Write-Behind**    | Atomic in-memory execution, async DB persistence   | Extreme (>50k TPS) |
| **Balance Sharding**            | Split 1 balance row into N slots, hash to distribute | Very High |

## Decision Flowchart

```
Low traffic?
 └── YES → Pessimistic Locking (FOR UPDATE)

Conflicts rare?
 └── YES → Optimistic Locking (version column)

High traffic + frequent conflicts?
 └── YES → Append-Only Ledger + Snapshots

Extreme contention on single entity (hot wallet)?
 └── YES → Balance Sharding or Redis Lua Execution
```

## One-Liner Answers

> **Lost Update?** — Last writer silently overwrites previous writer's committed changes.

> **Why MVCC doesn't help?** — MVCC is for reads. Writes still use row-level locks, but the app calculates stale values.

> **Best production pattern for debits?** — `UPDATE SET balance = balance - amount WHERE balance >= amount` (atomic, no app-side read needed).

> **Why not Redis as a distributed lock?** — Relocates the bottleneck, doesn't solve it. Still serializing access.

> **Snapshotting?** — Avoid full ledger SUM. Query = snapshot balance + SUM of recent entries after snapshot.

# The Lost Update Problem

Classic concurrency anomaly in financial systems.

---

## The Scenario

Organization balance

```
10 Lakh
```

T1 reads

```
10 Lakh
```

T2 reads

```
10 Lakh
```

T2 debits 2 Lakh

```
Balance = 8 Lakh
```

T2 commits.

T1 debits 9 Lakh using its stale read

```
10 - 9 = 1 Lakh
```

T1 writes

```
Balance = 1 Lakh
```

T2's deduction is entirely lost.

> The bank bleeds money.

---

# How the Database Inherently Behaves (MVCC & Locking)

Both MySQL (InnoDB) and PostgreSQL use **MVCC**.

> Readers do not block writers. Writers do not block readers.

Default Isolation Levels

| Database   | Default Isolation  |
| ---------- | ------------------ |
| MySQL      | REPEATABLE READ    |
| PostgreSQL | READ COMMITTED     |

---

## Phase 1 — The Read (MVCC)

T1 reads balance

```
10 Lakh (snapshot)
```

T2 reads balance

```
10 Lakh (snapshot)
```

MVCC provides each transaction its own consistent snapshot.

---

## Phase 2 — The First Write (Row-Level Locking)

T2 issues UPDATE

```
Balance = 8 Lakh
```

Database acquires

```
Exclusive Lock (X-Lock) on the row
```

T2 commits.

Lock released.

---

## Phase 3 — The Second Write (The Collision)

T1 issues UPDATE

```
Balance = 1 Lakh
```

If T2 was still running

```
T1 blocked — waiting for X-Lock
```

Once T2 commits

```
T1 proceeds
```

T1 overwrites the row.

Final balance

```
1 Lakh
```

> T2's update is destroyed.

---

## PostgreSQL vs MySQL Behavior

### PostgreSQL REPEATABLE READ

If elevated to REPEATABLE READ

T1 tries to update a row that T2 already modified.

PostgreSQL detects this conflict.

```
ERROR: could not serialize access due to concurrent update
```

T1 is aborted.

---

### MySQL REPEATABLE READ

Does **not** detect this conflict.

Simply allows the write to proceed based on the most recently committed version.

> T2's update is silently lost.

# Is Developer Intervention Needed?

**Yes. Absolutely.**

> You cannot trust standard `SELECT` statements for financial transactions.

If you calculate the new balance in application memory and issue an UPDATE

```
App: newBalance = readBalance - deduction
App: UPDATE SET balance = newBalance
```

The database does not know your application logic is flawed.

Three approaches to fix this.

---

## 1. Pessimistic Locking (`SELECT ... FOR UPDATE`)

Most robust approach for payment systems with high contention.

> Force the database to treat a `SELECT` like a write operation.

### The Flow

T1 executes

```sql
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
```

T1 acquires Exclusive Lock on the row.

T2 executes same query.

```
T2 instantly blocked — must wait
```

T1 computes new balance

```
10 - 9 = 1 Lakh
```

T1 updates and commits.

Lock released.

T2 unblocked.

T2 reads the **new** balance

```
1 Lakh
```

T2 realizes

```
1 - 2 = negative → insufficient funds
```

Transaction fails correctly.

---

## 2. Optimistic Locking (Versioning)

Best when collisions are rare.

Avoids database locks until the last moment.

> Add a `version` column to the table.

### The Flow

T1 reads

```
balance = 10 Lakh, version = 1
```

T2 reads

```
balance = 10 Lakh, version = 1
```

T2 updates

```sql
UPDATE accounts
SET balance = 8, version = 2
WHERE id = 1 AND version = 1;
```

Success

```
1 row affected
```

T1 updates

```sql
UPDATE accounts
SET balance = 1, version = 2
WHERE id = 1 AND version = 1;
```

Fails

```
0 rows affected — version already changed
```

Application detects 0 rows.

Throws `OptimisticLockException`.

> Developer logic must retry the entire transaction from step 1.

In Hibernate use `@Version` annotation.

---

## 3. Atomic Database Updates (Relative Updates)

Push the math down to the database engine.

> Do not calculate the absolute value in the application. Update relative to current state.

### The Flow

T2 fires

```sql
UPDATE accounts
SET balance = balance - 200000
WHERE id = 1 AND balance >= 200000;
```

T1 fires

```sql
UPDATE accounts
SET balance = balance - 900000
WHERE id = 1 AND balance >= 900000;
```

Database acquires Exclusive Lock sequentially.

When T1 gets its turn after T2

```
Current balance = 8 Lakh
```

WHERE clause evaluates

```
8 Lakh >= 9 Lakh → FALSE
```

Result

```
0 rows affected
```

Application handles insufficient funds.

---

## The Verdict

For financial systems processing debits and credits

> Do not rely on MVCC alone.

**Pessimistic Locking (`FOR UPDATE`)** or **Atomic Database Updates** are mandatory.

---

# When Pessimistic Locking is Not Enough

## The Problem

If conflicts are frequent

```
Pessimistic locking → threads waiting in lock queue
```

Throughput drops.

If you move the lock to Redis (like Redlock)

```
Transactions waiting in network I/O + Redis lock queue
```

> You are not solving the throughput problem. You are relocating the bottleneck.

Still serializing access.

Max throughput capped by

```
Acquire Redis Lock → Execute DB Query → Release Lock
```

---

## When This Happens

Massive concurrent writes on a single entity

* Centralized merchant acquirer account
* High-traffic nodal account
* Hot wallet

> You must abandon the synchronous read-modify-write cycle.

---

# High-Contention Architectures

---

## 1. Append-Only Ledger (Event Sourcing)

Databases struggle with concurrent UPDATEs on one row.

Databases are incredibly fast at concurrent INSERTs.

### How It Works

Stop updating a central balance column.

Write every debit and credit as a new immutable row.

```sql
INSERT INTO transactions (account_id, amount, transaction_type)
VALUES (:accountId, :amount, :type);
```

### Calculating Balance

Actual balance

```sql
SELECT SUM(amount) FROM transactions WHERE account_id = :id;
```

Use a background process to periodically roll up inserts into a snapshot.

> Eliminates row-level locking entirely at the cost of eventual consistency on reads.

---

### Problem with Raw SUM

Organization account can have millions of transactions.

Calculating balance from raw ledger at request time

```
SUM() over millions of rows → destroys performance
```

> Not feasible in production.

---

### Solution: Periodic Snapshotting (Checkpoint Ledger)

Never calculate from genesis (row 0).

Calculate from the latest verified checkpoint plus un-checkpointed entries.

#### Data Model

**`account_snapshots`**

```
account_id | balance | last_transaction_id | as_of_timestamp
```

**`transactions` (Ledger)**

```
id | account_id | amount | type
```

#### Live Balance Query

```sql
SELECT
    s.balance + COALESCE(SUM(t.amount), 0) AS current_balance
FROM account_snapshots s
LEFT JOIN transactions t
    ON t.account_id = s.account_id
    AND t.id > s.last_transaction_id
WHERE s.account_id = :accountId
GROUP BY s.balance;
```

Instead of scanning 10,000,000 rows

```
Scans at most a few dozen recent rows
```

Indexed by ID.

```
Sub-millisecond execution
```

Background job writes snapshots

```
Daily / Hourly / Every 10,000 transactions
```

---

## 2. Asynchronous Event Processing (Partitioned Queues)

Serialize operations before they reach the database.

### How It Works

Push all debit/credit requests into an event stream.

```
Apache Kafka — partitioned by account_id
```

Kafka guarantees strict ordering within a partition.

Single consumer reads the stream for that account.

Applies updates sequentially.

```
Only one consumer writing to that specific DB row
```

> Contention drops to zero.

Can batch events in memory

```
50 debit events → single UPDATE
```

```sql
UPDATE account
SET balance = balance - total_batched_amount
WHERE id = :accountId;
```

Drastically reduces DB load.

---

## 3. In-Memory Execution with Write-Behind (Redis as the Engine)

For synchronous ultra-low latency responses.

> Do not use Redis for locking. Use it for execution.

### How It Works

Keep hot account balance in Redis.

When a transaction comes in

```
Execute Redis Lua script
    → Check current balance
    → Deduct amount if sufficient
    → Return result
```

### Why It Works

Redis is single-threaded.

Lua script executes atomically.

> Inherently thread-safe. Tens of thousands of operations per second.

### Persistence

Once the transaction succeeds in Redis

Push event to update PostgreSQL asynchronously.

```
Write-behind cache strategy
```

Must implement

* Retry mechanisms
* Dead-letter queues

> Ensure the async DB write eventually succeeds for compliance (PCI-DSS).

---

## 4. Balance Sharding (Distributed Counters)

For extreme write contention on a single entity.

A single balance row cannot handle the write IOPS.

> Split the single account balance across N physical rows.

### The Model

```
Organization Account (Total Balance: 10 Lakh)
 ├── Slot 1: 2.5 Lakh
 ├── Slot 2: 2.5 Lakh
 ├── Slot 3: 2.5 Lakh
 └── Slot 4: 2.5 Lakh
```

### Debits / Credits

Incoming write picks a slot

```
slot_id = hash(txn_id) % N
```

Updates that specific row using atomic update

```sql
UPDATE account_slots
SET balance = balance - :amount
WHERE account_id = :id
AND slot_id = :slotId
AND balance >= :amount;
```

### Concurrency

Contention reduced by factor of N.

Multiple threads debit different slots concurrently.

No blocking.

### Reads

```sql
SELECT SUM(balance)
FROM account_slots
WHERE account_id = :accountId;
```

Reads only N rows (e.g., 4 or 8).

Aggregation is negligible.

# Architecture Decision Matrix

| Approach                        | Read Latency       | Write Contention Limit         | Complexity | Best For                                |
| ------------------------------- | ------------------ | ------------------------------ | ---------- | --------------------------------------- |
| Pessimistic (`FOR UPDATE`)      | Instant            | Low (Row serializes)           | Lowest     | Low-traffic, multi-step validations     |
| Optimistic (`version`)          | Instant            | Low–Medium (Fails on collision)| Low        | High-read, low-write accounts           |
| Append-Only + Snapshots         | Fast (O(Δ))        | High (Append is fast)          | Medium     | Core accounting & audit ledgers         |
| Sharded Balance                 | Instant            | Very High (Distributed slots)  | High       | Massive concurrent debits on one wallet |
| In-Memory Lua (Redis) + Queue   | Sub-millisecond    | Extreme (>50k TPS)             | High       | Real-time flash sales / instant switches|

---

# When to Use What

1. **Load is low** → Pessimistic Locking (`SELECT ... FOR UPDATE`)
2. **Conflicts are rare** → Optimistic Locking (version column)
3. **Load is high and conflicts are frequent** → Append-Only Ledger with Snapshots
4. **Extreme contention on a single entity** → Balance Sharding or In-Memory Redis Execution

---

# Key Takeaways

1. The **Lost Update** anomaly is not prevented by default database isolation levels in MySQL.
2. **MVCC** provides snapshot reads but does **not** protect against lost writes.
3. **Developer intervention** is mandatory for financial correctness.
4. **Pessimistic locking** serializes access — safe but limits throughput.
5. **Optimistic locking** avoids locks but requires retry logic on conflict.
6. **Atomic database updates** (`balance = balance - amount`) push logic to the DB engine.
7. For **high-contention hot accounts**, abandon read-modify-write entirely.
8. **Append-only ledgers** with periodic snapshots avoid row-level lock contention.
9. **Kafka partitioned by account_id** serializes writes with zero DB contention.
10. **Redis Lua scripts** provide atomic, single-threaded execution for ultra-low latency.
11. **Balance sharding** distributes write IOPS across N slots.
