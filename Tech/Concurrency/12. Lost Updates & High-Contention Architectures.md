Covers Roadmap section 12. [[9. Database Concurrency]] introduced the lost update as one of four anomalies; [[11. Transaction Boundaries]] showed what a rollback can't reach. This note takes the single worst case — **one row that everybody writes to** — and follows it from "add `FOR UPDATE`" all the way to architectures where the hot row no longer exists.

> [!info] The through-line of this note
> One row, escalating pressure. Each section is what you do when the previous answer stops working.
>
> 1. **The bug** (§1): two transactions read the same balance, both compute a new value **in application memory**, and the last writer silently erases the first. Money disappears with no error anywhere.
> 2. **Why the database doesn't save you** (§2–§3): MVCC gives each transaction a clean snapshot — that's the *cause*, not the cure. MVCC is a **read** mechanism; the write still lands. PostgreSQL at Repeatable Read is the only default that even notices.
> 3. **Three developer fixes** (§4–§6), in ascending order of how much you should like them: pessimistic locking, optimistic locking, and — the one to reach for — **atomic relative updates** that never read into application memory at all.
> 4. **Where all three break** (§7): when the contention is on *one* entity, every one of them serialises on that row. Moving the lock to Redis just relocates the bottleneck.
> 5. **So you change the shape of the problem** (§8–§11): stop updating a row. Append instead, serialise upstream, execute in memory, or split the row into N.
>
> One line to anchor everything: **the fix is never a better lock — it's not doing read-modify-write in application memory.**

## Short Notes

---

### 1. The Lost Update Problem

```text
Balance = 10 Lakh
T1 reads 10L                    T2 reads 10L
                                T2 debits 2L → writes 8L, COMMIT
T1 debits 9L using its stale read: 10 - 9 = 1L
T1 writes 1L
                                → T2's 2L deduction is entirely gone
```

- Both reads were **correct and committed**. Both writes **succeeded**. No error, no exception, no log line
- The damage: the account was debited 11L in total and the balance says 1L — **the bank bleeds money**
- ⭐ The root cause is not the database — it's **computing the new value in application memory** from a value that went stale in transit

---

### 2. How the Database Inherently Behaves

Three phases, and MVCC is complicit in the first one:

| Phase | What happens |
|---|---|
| **1. The read** | MVCC gives T1 and T2 their **own consistent snapshot** — both legitimately see 10L, neither blocks |
| **2. First write** | T2's `UPDATE` takes an **exclusive row lock**, commits, releases |
| **3. The collision** | T1's `UPDATE` waits, then proceeds — and **overwrites** with its stale-derived absolute value |

- ⚠️ **MVCC provides snapshot reads but does NOT protect against lost writes** — it's a read mechanism ([[9. Database Concurrency]] §6)
- The row lock worked perfectly. It serialised the two writes. It just can't know that T1's *number* was computed from a value that's no longer true
- The database has no idea your application logic is flawed — you handed it a literal

---

### 3. PostgreSQL vs MySQL — Who Detects It

| Database | Default isolation | Lost update protection |
|---|---|---|
| **MySQL InnoDB** | REPEATABLE READ | ❌ Silently allows the overwrite |
| **PostgreSQL** | READ COMMITTED | ❌ At the default level |
| **PostgreSQL** | REPEATABLE READ | ✅ **Detects it** — `could not serialize access due to concurrent update`, T1 aborts |

- PostgreSQL at Repeatable Read is the **only** common default that turns this into a visible failure you can retry
- ⚠️ **MySQL's Repeatable Read does not detect it** — despite the stricter-sounding name, it takes the most recently committed version and lets the write through
- ⚠️ This table is about **app-computed absolute values**. `SET balance = balance - 200000` is safe on both, because the database recomputes from the current row ([[9. Database Concurrency]] §8)

---

### 4. Pessimistic Locking — `SELECT … FOR UPDATE`

- Force the database to treat a `SELECT` like a write: **take the exclusive lock at read time**

```sql
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- T2 blocks here
```

- T1 reads 10L under the lock, computes, updates, commits → T2 unblocks and reads the **new** 1L, correctly fails on insufficient funds
- ✅ Most robust when the decision genuinely needs multiple steps between read and write
- ⚠️ Fully **serialises** the row — throughput is capped at `1 / (lock hold time)`
- Keep the transaction tiny; never hold it across an external call ([[11. Transaction Boundaries]] §5)

---

### 5. Optimistic Locking — Versioning

- Add a `version` column; make the version part of the `WHERE`

```sql
UPDATE accounts SET balance = 1, version = 2
 WHERE id = 1 AND version = 1;      -- 0 rows if someone else already bumped it
```

- **0 rows affected** = you lost the race → `OptimisticLockException` → **retry the whole transaction from the read**
- Hibernate does this for you with `@Version`
- ✅ No locks held; best when **collisions are rare**
- ⚠️ Under real contention it degrades into a **retry storm** — needs bounded attempts and jitter ([[11. Transaction Boundaries]] §3)
- ⚠️ The retry must rebuild entities; a detached entity re-saved will fail forever

---

### 6. Atomic Database Updates — Relative Updates ⭐

- Push the arithmetic **into the database**. Never read the balance into application memory at all

```sql
UPDATE accounts
   SET balance = balance - 900000
 WHERE id = 1 AND balance >= 900000;
```

- The row lock serialises the two statements, and T1's `WHERE` is **re-evaluated against the current row**: `8L >= 9L` is false → **0 rows affected** → insufficient funds
- ✅ No pre-read, no version column, no lock held across application logic, **one round trip**
- ⭐ **The default choice for debits and credits.** The guard travels *with* the write, so there is no window between check and update
- **0 rows is a signal, not a no-op** — always branch on the affected-row count

> **The verdict**: for financial debits, `FOR UPDATE` or an atomic relative update are mandatory. Never trust a plain `SELECT` plus app-side math.

---

### 7. When Pessimistic Locking Is Not Enough

- Under frequent conflicts, `FOR UPDATE` puts every thread in a **lock queue** — throughput collapses to serial
- ⚠️ **Moving the lock to Redis does not help** — you've added network I/O to the same serial section:

```text
Acquire Redis lock → execute DB query → release lock
```

- ⭐ **You are not solving the throughput problem, you are relocating the bottleneck.** Still one writer at a time ([[10. Distributed Concurrency]] §3)
- **When this bites**: a centralised merchant acquirer account, a high-traffic nodal account, a hot wallet — massive concurrent writes on **one entity**
- The escape: **abandon the synchronous read-modify-write cycle** entirely (§8–§11)

---

### 8. Append-Only Ledger + Snapshots

- Databases are slow at concurrent `UPDATE`s on one row and **very fast at concurrent `INSERT`s**
- So stop updating a balance column — write every debit and credit as a **new immutable row**
- ⚠️ **`SUM()` over the whole ledger is not viable** — millions of rows per account destroys read performance
- ✅ Fix: **periodic snapshotting**. Never compute from genesis; compute from the last checkpoint forward

```text
balance = snapshot.balance + SUM(entries after snapshot.last_transaction_id)
        = a few dozen indexed rows, not 10,000,000
```

- Background job writes snapshots daily / hourly / every 10,000 transactions
- Eliminates row-lock contention **at the cost of eventual consistency on reads**
- Composes naturally with saga compensation, where a reversal is just another entry ([[11. Transaction Boundaries]] §8)

---

### 9. Partitioned Queues — Serialise Upstream

- Push every debit/credit into Kafka, **partitioned by `account_id`**
- Kafka guarantees **strict ordering within a partition**, and one consumer owns that partition
- → Only one writer ever touches that DB row. **Contention drops to zero — by construction, not by locking**
- ✅ Lets you **batch**: 50 debit events → one `UPDATE balance = balance - total`
- This is the "design the lock away" pattern — it converts a **concurrency** problem into a **routing** problem ([[10. Distributed Concurrency]] §8)
- ⚠️ The trade is asynchrony: the caller no longer gets a synchronous success/failure

---

### 10. In-Memory Execution with Write-Behind (Redis Lua)

> **Don't use Redis for locking. Use it for execution.**

- Keep the hot balance **in Redis**; run the whole check-and-deduct as a **Lua script**
- Redis is **single-threaded** and executes a Lua script **atomically** — inherently thread-safe, no lock needed
- Tens of thousands of ops/sec, sub-millisecond, **synchronous** response to the caller
- Persistence is **write-behind**: push an event to update PostgreSQL asynchronously
- ⚠️ Mandatory: retries and a **dead-letter queue** — the async DB write must eventually succeed for compliance (PCI-DSS)
- ⚠️ Redis is now the source of truth for the balance; durability config and failover become a correctness concern ([[10. Distributed Concurrency]] §6)

---

### 11. Balance Sharding — Distributed Counters

- For extreme write IOPS on one entity: **split one balance row into N slots**

```text
Organization Account (10 Lakh)
 ├── Slot 1: 2.5L    ├── Slot 3: 2.5L
 ├── Slot 2: 2.5L    └── Slot 4: 2.5L
```

- Writes pick a slot — `slot_id = hash(txn_id) % N` — and use an atomic relative update on **that row only**
- **Contention reduced by a factor of N**; threads on different slots never block each other
- Reads are `SELECT SUM(balance) … WHERE account_id = ?` over just N rows — negligible
- ⭐ This is exactly **`LongAdder`'s cell striping** ([[5. Concurrent Utilities]] §6) applied to a database row: spread the hot spot, aggregate on read
- ⚠️ Same caveat as `LongAdder`: a per-slot `balance >= amount` check can reject a debit the *total* balance could cover — slot rebalancing is the hard part

---

### 12. Choosing an Architecture

| Approach | Read latency | Write contention limit | Complexity | Best for |
|---|---|---|---|---|
| Pessimistic (`FOR UPDATE`) | Instant | Low (row serialises) | Lowest | Low traffic, multi-step validation |
| Optimistic (`version`) | Instant | Low–Medium (fails on collision) | Low | High-read, low-write accounts |
| Append-only + snapshots | Fast (O(Δ)) | High (appends are fast) | Medium | Core accounting & audit ledgers |
| Sharded balance | Instant | Very High (N slots) | High | Massive concurrent debits on one wallet |
| Redis Lua + write-behind | Sub-ms | Extreme (>50k TPS) | High | Real-time flash sales, instant switches |

```text
Low traffic?                         → Pessimistic locking (FOR UPDATE)
Conflicts rare?                      → Optimistic locking (version column)
High traffic + frequent conflicts?   → Append-only ledger + snapshots
Extreme contention on one entity?    → Balance sharding or Redis Lua execution
```

# Detailed Explanation

---

## The Lost Update Problem

The classic concurrency anomaly in financial systems, and the reason the rest of this note exists.

Organization balance: **10 Lakh**.

```text
T1 reads  → 10 Lakh
T2 reads  → 10 Lakh

T2 debits 2 Lakh   →  10 - 2 = 8 Lakh   →  writes 8L, COMMIT

T1 debits 9 Lakh using its stale read
                   →  10 - 9 = 1 Lakh   →  writes 1L, COMMIT

Final balance: 1 Lakh
```

T2's deduction of 2 Lakh has been **entirely destroyed**. The account was debited 11 Lakh in total, and the balance reflects only 9 of it.

> The bank bleeds money — and nothing anywhere reported a problem.

That last point is what makes this dangerous. Both reads returned committed data. Both updates affected 1 row. Both transactions committed successfully. There is no exception to catch, no constraint violated, no log line to alert on. You find out during reconciliation, days later.

**The root cause, stated precisely:** the new balance was computed **in application memory** from a value that became stale between the read and the write. Everything downstream in this note is a way of removing that gap.

---

## How the Database Inherently Behaves — MVCC and the Three Phases

Both MySQL (InnoDB) and PostgreSQL use **MVCC**: readers don't block writers, writers don't block readers ([[9. Database Concurrency]] §6). Walk through what each engine actually did, because none of it was a malfunction.

### Phase 1 — the read (MVCC)

```text
T1 reads balance → 10 Lakh (its snapshot)
T2 reads balance → 10 Lakh (its snapshot)
```

MVCC gives each transaction its own consistent snapshot. Both values are correct as of each transaction's start. Neither blocks. **This is MVCC working exactly as designed** — and it's why the problem exists at all: the whole point of a snapshot is that it doesn't change under you, which also means it can go stale.

### Phase 2 — the first write (row-level locking)

```text
T2: UPDATE balance = 8 Lakh
    → database acquires an EXCLUSIVE (X) lock on the row
    → T2 commits, lock released
```

### Phase 3 — the second write (the collision)

```text
T1: UPDATE balance = 1 Lakh
    → if T2 still running: T1 BLOCKS waiting for the X lock
    → once T2 commits: T1 proceeds and OVERWRITES

Final balance: 1 Lakh
```

The lock did its job perfectly — the two writes were serialised, one after the other. What the lock cannot do is notice that T1's **number** was derived from a value that is no longer true. T1 handed the database the literal `1`, and the database has no way to know that `1` was arrived at by subtracting from a stale `10`.

> [!warning] MVCC is a read mechanism — it does not protect against lost writes
> This is the sentence to carry out of the section. MVCC gave both transactions a clean, consistent, non-blocking read. It has nothing to say about what you then compute from that read and write back. Contrast this with [[9. Database Concurrency]] §8, where `SET balance = balance - 700` **is** protected — because there the database recomputes from the current row rather than accepting your literal.

---

## PostgreSQL vs MySQL — Who Detects It

The two major engines behave differently here, and the difference is worth knowing precisely because the naming is misleading.

| Database | Default isolation | Lost update protection |
|---|---|---|
| **MySQL InnoDB** | REPEATABLE READ | ❌ Silently allows the overwrite |
| **PostgreSQL** | READ COMMITTED | ❌ At the default level |
| **PostgreSQL** | REPEATABLE READ | ✅ Detects the conflict and aborts T1 |

### PostgreSQL at REPEATABLE READ

If you elevate the isolation level, T1 tries to update a row that T2 has already modified since T1's snapshot was taken. PostgreSQL refuses rather than silently proceeding:

```text
ERROR: could not serialize access due to concurrent update
```

T1 is aborted, and your application retries. This is the same behaviour described in [[9. Database Concurrency]] §8 — and it's the trade-off from isolation levels made concrete: **a stricter level converts a silent corruption into an explicit failure you must handle.**

### MySQL at REPEATABLE READ

Despite the identical name, InnoDB does **not** detect this conflict. It allows the write to proceed based on the most recently committed version, and T2's update is silently lost.

> [!warning] The table above is about *app-computed absolute values*
> This is the qualification that keeps the comparison honest. `UPDATE … SET balance = 8` (a literal you computed) is lost-update-prone on both engines. `UPDATE … SET balance = balance - 200000` is **safe on both**, because InnoDB performs a "current read" for the update and PostgreSQL rechecks the row — in each case the engine recomputes from the live value rather than trusting yours.
>
> So "MySQL doesn't protect you" is precise only for the read-into-memory-then-write pattern. That pattern is the bug; the engine difference is secondary.

---

## Is Developer Intervention Needed?

**Yes. Absolutely.**

> You cannot trust a plain `SELECT` followed by application-side arithmetic for financial transactions.

```text
App: newBalance = readBalance - deduction
App: UPDATE SET balance = newBalance
```

The database does not know your application logic is flawed. It received a valid `UPDATE` with a literal value and applied it. Three approaches fix this, and they are not equally good.

---

## Pessimistic Locking — `SELECT … FOR UPDATE`

The most robust approach when the decision genuinely requires multiple steps between the read and the write.

> Force the database to treat a `SELECT` like a write operation.

```sql
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
```

```text
T1 executes SELECT ... FOR UPDATE  → acquires the exclusive row lock
T2 executes the same query          → INSTANTLY BLOCKED, must wait

T1 computes 10 - 9 = 1 Lakh, updates, commits → lock released

T2 unblocks and reads the NEW balance → 1 Lakh
T2 computes 1 - 2 = negative          → insufficient funds
T2 fails CORRECTLY
```

The critical difference from the broken version: T2's read happens **after** T1's commit, so T2 never holds a stale value at all. The window between read and write has been closed by holding the lock across it.

**The cost:** the row is fully serialised. Throughput is capped at roughly `1 / (lock hold time)`, so everything depends on keeping that transaction short. Never hold it across an external call — that's the availability failure from [[11. Transaction Boundaries]] §5, and here it directly multiplies into a throughput ceiling.

---

## Optimistic Locking — Versioning

Best when collisions are **rare**. It avoids taking any lock until the last moment.

Add a `version` column, and make the version part of the update's `WHERE`:

```text
T1 reads: balance = 10 Lakh, version = 1
T2 reads: balance = 10 Lakh, version = 1
```

```sql
-- T2 wins the race
UPDATE accounts SET balance = 8, version = 2
 WHERE id = 1 AND version = 1;          -- 1 row affected ✅

-- T1 arrives with a stale version
UPDATE accounts SET balance = 1, version = 2
 WHERE id = 1 AND version = 1;          -- 0 rows affected ❌ — version already bumped
```

The application detects **0 rows affected** and throws `OptimisticLockException`. In Hibernate the `@Version` annotation generates all of this for you.

> **The retry must restart from the read.** Re-issuing the same `UPDATE` will fail identically forever — you have to go back, re-read the current balance and version, recompute, and try again. And per [[11. Transaction Boundaries]] §3, rebuild your entities from the request rather than reusing detached ones, or the retry can never succeed.

**The cost:** under real contention this degrades badly. Every loser does its work, discovers it lost, and repeats — a retry storm where most of the CPU is spent on discarded attempts. Bound the attempts and add jitter, or contention turns into a self-sustaining outage.

---

## Atomic Database Updates — Relative Updates ⭐

Push the math down to the database engine. **Never read the balance into application memory at all.**

> Do not calculate the absolute value in the application. Update relative to the current state.

```sql
-- T2
UPDATE accounts SET balance = balance - 200000
 WHERE id = 1 AND balance >= 200000;

-- T1
UPDATE accounts SET balance = balance - 900000
 WHERE id = 1 AND balance >= 900000;
```

The database acquires the exclusive lock sequentially, so when T1 gets its turn after T2:

```text
Current balance = 8 Lakh
WHERE clause: 8 Lakh >= 9 Lakh  →  FALSE
Result: 0 rows affected
```

The application sees 0 rows and handles insufficient funds. No stale value ever existed, because the application never held one.

**Why this is the default choice:**

| | `FOR UPDATE` | Version column | Relative update |
|---|---|---|---|
| Round trips | 2 (select + update) | 2 (select + update) | **1** |
| Lock held across app logic | **Yes** | No | No |
| Extra schema | No | `version` column | No |
| Retry needed | No | **Yes** | No |
| Guard and write atomic | Separate statements | Separate statements | **Same statement** |

That last row is the real argument. The `AND balance >= :amount` guard travels **with** the write, so there is no window between checking the precondition and acting on it. With the other two you're closing that window with a lock or detecting afterwards that you lost.

```java
int rows = jdbc.update(sql, amount, id, amount);
if (rows == 0) throw new InsufficientBalanceException();   // 0 rows is a SIGNAL
```

> [!warning] The verdict
> For financial systems processing debits and credits, **do not rely on MVCC alone.** Pessimistic locking or atomic relative updates are mandatory — and prefer the relative update unless your logic genuinely can't be expressed in one statement.

---

## When Pessimistic Locking Is Not Enough

All three fixes above share a property: they resolve contention **on the row**. That's fine until the contention *is* the row.

If conflicts are frequent, `FOR UPDATE` puts every thread into a lock queue and throughput drops to serial. The obvious instinct is to reach for a distributed lock — and it doesn't help:

```text
Acquire Redis lock → Execute DB query → Release Lock
```

> You are not solving the throughput problem. **You are relocating the bottleneck** — and adding two network round trips to the serial section while you're at it.

The maximum throughput is still one writer at a time; you've just moved where they queue, from the database's lock manager into Redis plus network I/O. This is the point [[10. Distributed Concurrency]] §3 makes from the other direction: a distributed lock is for coordinating things *outside* the database, not for speeding up contention *inside* it.

**When this actually happens:**

- A centralised **merchant acquirer** account
- A high-traffic **nodal** account
- A **hot wallet** taking thousands of debits per second

> You must abandon the synchronous read-modify-write cycle entirely. The remaining sections all do that, in different ways: stop updating (§8), serialise before the database (§9), execute somewhere faster (§10), or stop having one row (§11).

---

## Append-Only Ledger (Event Sourcing)

Databases struggle with concurrent `UPDATE`s on a single row. They are **incredibly fast at concurrent `INSERT`s** — different rows, no shared lock, no contention.

So stop updating a central balance column. Write every debit and credit as a new immutable row:

```sql
INSERT INTO transactions (account_id, amount, transaction_type)
VALUES (:accountId, :amount, :type);
```

The balance becomes a derived value:

```sql
SELECT SUM(amount) FROM transactions WHERE account_id = :id;
```

This eliminates row-level lock contention entirely, at the cost of **eventual consistency on reads**.

### The problem with a raw `SUM()`

An organization account can accumulate millions of transactions. Computing the balance from the raw ledger at request time means `SUM()` over millions of rows on every read.

> Not feasible in production. You've traded a write bottleneck for a read bottleneck.

### The fix: periodic snapshotting (checkpoint ledger)

Never calculate from genesis. Calculate from the **latest verified checkpoint** plus the entries after it.

**`account_snapshots`**

```text
account_id | balance | last_transaction_id | as_of_timestamp
```

**`transactions`** (the ledger)

```text
id | account_id | amount | type
```

```sql
SELECT s.balance + COALESCE(SUM(t.amount), 0) AS current_balance
FROM account_snapshots s
LEFT JOIN transactions t
       ON t.account_id = s.account_id
      AND t.id > s.last_transaction_id          -- only entries after the checkpoint
WHERE s.account_id = :accountId
GROUP BY s.balance;
```

```text
Instead of scanning 10,000,000 rows
        → scans at most a few dozen recent rows, indexed by id
        → sub-millisecond execution
```

A background job writes snapshots daily, hourly, or every 10,000 transactions — whichever keeps the delta small.

> [!info] This is the design that composes with everything else
> An append-only ledger is also what makes saga compensation clean ([[11. Transaction Boundaries]] §8): a reversal is just another entry, never a delete. And it gives you the audit trail financial systems need anyway — so in payments you're often adopting it for compliance reasons and getting the contention win for free.

---

## Asynchronous Event Processing (Partitioned Queues)

Serialise the operations **before** they ever reach the database.

Push all debit/credit requests into an event stream — Apache Kafka, **partitioned by `account_id`**. Kafka guarantees strict ordering **within a partition**, and one consumer owns that partition.

```text
requests ──► Kafka (partition = hash(account_id))
                   │
                   ▼
          single consumer for that partition
                   │
                   ▼
          applies updates sequentially
          → only ONE writer ever touches that DB row
```

**Contention drops to zero** — not because you locked better, but because concurrent access no longer exists. This is the "design the lock away" pattern from [[10. Distributed Concurrency]] §8: it converts a **concurrency** problem into a **routing** problem, and routing problems don't have lock queues.

You also unlock **batching**, which is where the real throughput comes from:

```sql
-- 50 debit events accumulated in memory, applied as one statement
UPDATE account SET balance = balance - :total_batched_amount WHERE id = :accountId;
```

Fifty round trips and fifty lock acquisitions become one.

**The trade:** the caller no longer gets a synchronous answer. The request is accepted, not completed — so the API has to return something like `PENDING`, and the client needs a callback or a status poll. For a UPI switch that's often unacceptable on the authorization path but perfectly fine for settlement and reconciliation.

---

## In-Memory Execution with Write-Behind (Redis as the Engine)

For cases that need an ultra-low-latency **synchronous** response.

> Do not use Redis for **locking**. Use it for **execution**.

Keep the hot account balance in Redis. When a transaction arrives, run the entire check-and-deduct as a **Lua script**:

```lua
-- executed atomically by Redis; no lock required
local balance = tonumber(redis.call('GET', KEYS[1]))
local amount  = tonumber(ARGV[1])
if balance >= amount then
    redis.call('DECRBY', KEYS[1], amount)
    return 1            -- success
end
return 0                -- insufficient funds
```

**Why it works:** Redis is **single-threaded**, and a Lua script runs to completion atomically. There is no interleaving to protect against, so the read-modify-write is inherently safe — the same reason a single-threaded event loop needs no locks. Tens of thousands of operations per second, sub-millisecond.

**Persistence** is **write-behind**: once the transaction succeeds in Redis, push an event to update PostgreSQL asynchronously.

> [!warning] Write-behind makes Redis the source of truth — treat it that way
> Two obligations follow, and neither is optional in a financial system:
> - **Retries and a dead-letter queue** on the async DB write. If that write is silently lost, your durable record and your live balance permanently disagree — and for PCI-DSS/audit purposes the durable record is the one that counts.
> - **Durability and failover config.** The balance now lives in a system that, by default, can lose recent writes on failover ([[10. Distributed Concurrency]] §6). That was an availability concern for locks; here it's a correctness concern for money.

---

## Balance Sharding (Distributed Counters)

For extreme write contention on a single entity, where one balance row simply cannot absorb the write IOPS.

> Split the single account balance across **N physical rows**.

```text
Organization Account (Total Balance: 10 Lakh)
 ├── Slot 1: 2.5 Lakh
 ├── Slot 2: 2.5 Lakh
 ├── Slot 3: 2.5 Lakh
 └── Slot 4: 2.5 Lakh
```

An incoming write picks a slot and uses an atomic relative update against **that row only**:

```sql
-- slot_id = hash(txn_id) % N
UPDATE account_slots
   SET balance = balance - :amount
 WHERE account_id = :id
   AND slot_id    = :slotId
   AND balance   >= :amount;
```

Contention is reduced by a factor of **N** — threads hitting different slots never block each other. Reads aggregate the slots:

```sql
SELECT SUM(balance) FROM account_slots WHERE account_id = :accountId;
```

That's N rows (4, 8, 16), so the aggregation cost is negligible.

> [!tip] You have seen this exact idea before
> This is **`LongAdder`'s cell striping** ([[5. Concurrent Utilities]] §6) applied to a database row. Identical reasoning: one hot location is the bottleneck, so spread writes across many locations and aggregate on read. Same benefit (writes scale with N), same cost (**no single consistent instantaneous value** — the sum is assembled from slots that are still moving).

> [!warning] The hard part is slot rebalancing
> Each slot enforces `balance >= :amount` **locally**. So a debit can be rejected because *its* slot is drained, even though the account's total balance is more than sufficient — the `LongAdder` "no `compareAndSet`" limitation in a new costume. You need a rebalancing strategy: retry against another slot, periodically redistribute funds across slots, or route by amount. Don't present sharding in an interview without naming this.

## Choosing an Architecture

| Approach | Read latency | Write contention limit | Complexity | Best for |
|---|---|---|---|---|
| Pessimistic (`FOR UPDATE`) | Instant | Low (row serialises) | Lowest | Low-traffic, multi-step validations |
| Optimistic (`version`) | Instant | Low–Medium (fails on collision) | Low | High-read, low-write accounts |
| Append-only + snapshots | Fast (O(Δ)) | High (append is fast) | Medium | Core accounting & audit ledgers |
| Sharded balance | Instant | Very High (distributed slots) | High | Massive concurrent debits on one wallet |
| In-memory Lua (Redis) + queue | Sub-millisecond | Extreme (>50k TPS) | High | Real-time flash sales / instant switches |

```text
Low traffic?
 └── YES → Pessimistic locking (SELECT ... FOR UPDATE)

Conflicts rare?
 └── YES → Optimistic locking (version column)

High traffic + frequent conflicts?
 └── YES → Append-only ledger + snapshots

Extreme contention on a single entity (hot wallet)?
 └── YES → Balance sharding or Redis Lua execution
```

**The progression to say out loud in an interview:** start with the atomic relative update, because it's one statement and costs nothing. Add `FOR UPDATE` only when the decision needs multiple steps. When the row itself becomes the ceiling, stop trying to lock it better and change the shape — append instead of update, serialise upstream, or shard the row. **The fix is never a better lock.**

## Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| What is a lost update? | Two transactions read the same value, both compute from it in memory, and the last writer silently overwrites the first. No error is raised. |
| Why doesn't MVCC prevent it? | MVCC is a **read** mechanism — it gives each transaction a consistent snapshot. The write still lands; the row lock serialises it but can't tell the value was derived from stale data. |
| Does the row lock fail here? | No — it works perfectly. It serialises the writes. It just can't know your literal was computed from a stale read. |
| Does MySQL's Repeatable Read prevent it? | **No** — it silently allows the overwrite despite the stricter-sounding name. |
| Does PostgreSQL? | Only at REPEATABLE READ, where it raises `could not serialize access due to concurrent update` and aborts. Its default (READ COMMITTED) does not. |
| Is `balance = balance - 100` also vulnerable? | No — the engine recomputes from the current row on both MySQL and PostgreSQL. Only app-computed absolute values are vulnerable. |
| The three developer fixes? | Pessimistic (`FOR UPDATE`), optimistic (version column + retry), atomic relative update. |
| How does `FOR UPDATE` fix it? | It takes the exclusive lock at read time, so the second transaction reads only after the first commits — it never holds a stale value. |
| How does optimistic locking detect it? | The version is in the `WHERE`; a stale version matches 0 rows, which you turn into an exception and retry from the read. |
| Best production pattern for a debit? | `UPDATE SET balance = balance - :amt WHERE id = ? AND balance >= :amt` — one round trip, guard and write in the same statement, no stale value ever in memory. |
| Why is the relative update better than `FOR UPDATE`? | One round trip instead of two, no lock held across application logic, and the precondition is atomic with the write. |
| What does 0 rows affected mean? | Your precondition failed — insufficient funds, or you lost the version race. It's a signal to branch on, never to ignore. |
| Why not just use a Redis distributed lock? | It relocates the bottleneck rather than removing it — still one writer at a time, now with network round trips added to the serial section. |
| When do all three fixes stop working? | When the contention is on **one entity** — a nodal account, merchant acquirer, or hot wallet. Everything serialises on that row. |
| What do you do then? | Abandon synchronous read-modify-write: append-only ledger, partitioned queues, in-memory execution, or balance sharding. |
| Why is an append-only ledger faster? | Databases are slow at concurrent `UPDATE`s on one row and very fast at concurrent `INSERT`s of different rows. |
| What breaks in a naive append-only design? | Reads — `SUM()` over millions of ledger rows per request is not viable. |
| How do you fix that? | **Periodic snapshots**: balance = last checkpoint + `SUM` of entries after it. Scans a few dozen indexed rows, not millions. |
| How do partitioned queues remove contention? | Partition Kafka by `account_id`; ordering is guaranteed within a partition and one consumer owns it, so only one writer ever touches the row. |
| Extra benefit of the queue approach? | Batching — 50 debit events become one `UPDATE balance = balance - total`. |
| Cost of the queue approach? | The caller loses a synchronous answer; the API returns `PENDING` and needs a callback or status poll. |
| Why is Redis Lua safe without a lock? | Redis is single-threaded and executes a Lua script atomically — there's no interleaving to protect against. |
| What must you add with write-behind? | Retries and a dead-letter queue, so the async DB write eventually succeeds — and durability/failover config, since Redis now holds the authoritative balance. |
| What is balance sharding? | Split one balance row into N slots, route writes by `hash(txn_id) % N`, and `SUM` the N rows on read. Contention drops by a factor of N. |
| What does balance sharding resemble? | `LongAdder` cell striping — spread the hot spot, aggregate on read, and give up a single instantaneous consistent value. |
| Biggest problem with sharding? | Each slot checks `balance >= amount` locally, so a debit can be rejected even though the total balance covers it. You need slot rebalancing. |
| The one-line summary? | The fix is never a better lock — it's not doing read-modify-write in application memory. |

## SDE-2 Interview Priority Checklist

### Must Know (100%)

- The lost-update trace, end to end, with numbers
- Why MVCC does not prevent it — read mechanism vs write
- That the row lock worked and still didn't save you
- MySQL vs PostgreSQL detection behaviour, and that PG only detects at REPEATABLE READ
- That relative updates (`balance = balance - ?`) are safe on both engines
- The three developer fixes, and how each closes the read-write window
- ⭐ Why the atomic relative update is the default: one round trip, guard atomic with the write
- That 0 rows affected is the signal for insufficient funds / lost race
- Why a Redis lock only relocates the bottleneck
- When single-row fixes stop working — hot wallet, nodal, acquirer accounts
- Append-only ledger, why raw `SUM()` fails, and the snapshot fix
- Kafka partitioning by `account_id` as concurrency elimination
- Balance sharding: the model, the routing, and the read aggregation

### Nice To Know

- The snapshot + delta query shape (`t.id > s.last_transaction_id`)
- Batching many events into one `UPDATE`
- Redis being single-threaded, so Lua scripts are atomic by construction
- Write-behind requiring retries and a DLQ for compliance
- The balance-sharding ↔ `LongAdder` striping parallel
- Retry storms and jitter under optimistic locking
- That an append-only ledger is also the right shape for saga compensation and audit

### Advanced

- Slot rebalancing when one shard is drained but the total covers the debit
- Snapshot consistency while appends are landing concurrently
- PCI-DSS / audit implications of a Redis-authoritative balance
- Ordering guarantees when a Kafka partition is reassigned mid-flight
- Reconciling a write-behind balance against the durable ledger
- Choosing N for sharding, and how it interacts with read amplification
