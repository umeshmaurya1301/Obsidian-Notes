Covers Roadmap section 4. This is the one that matters most in real backend systems. Notes 2–3 gave you raw threads and locks; nobody writes `new Thread()` per request in production. Server code hands **tasks** to a **managed pool** — and every incident-worthy concurrency bug (thread exhaustion, unbounded queues, silent OOMs, tasks that vanish without a stack trace) lives here.

> [!info] The through-line of this note
> One idea drives everything: **decouple the task from the thread, then bound the threads.**
>
> 1. Raw threads don't scale — a thread costs the OS real money, and one per request is unbounded (§1). So you pool and reuse.
> 2. Java's answer is a hierarchy: **`Executor` → `ExecutorService` → `ScheduledExecutorService`** (§2). You stop saying "create a thread" and start saying "run this."
> 3. The `Executors` factory methods are convenient **presets** (§3) — and two of them are dangerous defaults.
> 4. Under every one of them sits a single real class: **`ThreadPoolExecutor`** (§4). Its seven parameters decide all behaviour, and its **submission algorithm** (§5) is the most-asked question in this module.
> 5. The pool's spine is a **`BlockingQueue`** (§6) — the producer/consumer handoff from [[3. Synchronization]] §6, now doing real work. What happens when it's full is the **rejection policy** (§7): a design decision, not an error.
> 6. To get *results* back you need **`Callable` → `Future`**, glued together by **`FutureTask`** (§8). `Future` is passive, which is exactly why `CompletableFuture` exists.
> 7. Then the production half: scheduling (§9), naming threads (§10), `ForkJoinPool` (§11), **tuning** (§12), **graceful shutdown** (§13), **monitoring** (§14), Spring's `@Async` (§15), and the mistakes that cause outages (§16).
>
> One line to anchor everything: **an unbounded queue turns your `maximumPoolSize` into dead config and your heap into a time bomb.**

### 1. Why Pools Exist — the Real Cost of a Thread

`new Thread(task).start()` looks harmless. It isn't — a thread is not a Java object, it's an **OS resource**:

```text
new Thread(task).start()
        ↓
JVM creates the Thread object
        ↓
JVM asks the OS for a native thread
        ↓
OS allocates a thread stack
        ↓
OS initialises scheduler metadata + registers the thread
        ↓
Execution begins
```

**What each thread consumes:** a stack (commonly ~1 MB, JVM/OS dependent), a native OS thread, scheduler metadata, thread-local storage, and a share of CPU scheduling time.

Do the arithmetic: **1,000 threads × 1 MB ≈ 1 GB of stack** — before your app stores a single business object.

**Then context switching makes it worse.** With 8 cores and 500 runnable threads, only 8 execute at any instant. The OS constantly saves registers and program counters, loads another thread, and updates the scheduler. Past a point, adding threads *reduces* throughput — the CPU spends its time switching instead of working (see [[1. Core Fundamentals]] §4).

**And short-lived threads are pure waste:**

```text
receive request → create thread → run 20 ms → destroy thread     × 10,000
```

Most of that time goes to creating and destroying, not to the work.

> [!example] The delivery-company analogy
> Hiring a delivery person for one order, then firing them, then hiring another for the next order — absurd. You keep a **crew on staff** and assign them deliveries as they come in. That's a thread pool: a fixed set of **worker threads** pulling **tasks** from a **queue**.

Instead of one thread per task, you get:

```text
Task 1 → Worker 1        Worker 1 finishes → picks up Task 4
Task 2 → Worker 2        Worker 2 finishes → picks up Task 5
Task 3 → Worker 3        ...
Task 4+ → queue
```

**Five benefits, in interview order:** thread **reuse** (no repeated creation cost) · lower **memory** (10 workers, not 1,000 threads) · less **context switching** · better **throughput** · and most importantly **controlled concurrency** — you can say "at most 20 workers" instead of "unlimited."

That last one is why this works at all. It's the payoff of the task/worker split from [[2. Java Thread Basics]] §1: because a `Runnable`/`Callable` doesn't own a thread, N tasks can share a small pool.

> [!info] You're already using one — Tomcat
> A Spring Boot app receiving 500 concurrent HTTP requests does **not** create 500 threads. Embedded Tomcat has a pool (~200 workers by default): the first 200 requests execute, the remaining 300 wait in a queue, and each worker picks up a new request as it frees up. That's the only reason the server survives a spike. Your own `@Async` and Kafka-consumer pools should be configured with the same discipline (§15).

### 2. The Executor Framework — Decoupling Submission From Execution

Before Java 5, your business code did thread management:

```java
Thread t = new Thread(task);
t.start();          // your code decides: create, start, manage
```

Business logic and thread lifecycle were welded together. Java 5 flipped the sentence. Instead of *"create a thread and run this,"* you say *"please execute this task"* — and something else decides **which** thread, **when**, and **how**.

The whole idea fits in one interface:

```java
public interface Executor {
    void execute(Runnable command);
}
```

```text
Old:  Task → Thread → Execution
New:  Task → Executor → Worker Thread → Execution
```

The task no longer knows who runs it. That's **decoupling task submission from task execution**, and it's the sentence to say in an interview.

**The three-level hierarchy:**

```text
Executor                          → execute(Runnable)                  fire-and-forget
  └─ ExecutorService              → submit(...) → Future, shutdown()    results + lifecycle
       └─ ScheduledExecutorService → schedule(...), scheduleAtFixedRate(...)  delays + repeats
```

**`Executor`** — one method. No result, no lifecycle. (It's so minimal you can implement it inline: `command -> command.run()` runs tasks on the *calling* thread — technically a valid `Executor`, and a useful thing to know for tests.)

**`ExecutorService`** — the one you actually use. It adds:

| Method | Does |
|---|---|
| `submit(Callable/Runnable)` | Returns a `Future` — results and exceptions (§8) |
| `invokeAll(tasks)` | Runs a batch, **blocks until all finish**, returns `List<Future>` |
| `invokeAny(tasks)` | Returns the first successful result, cancels the rest |
| `shutdown()` / `shutdownNow()` | Lifecycle (§13) |
| `awaitTermination(t, unit)` | Block until drained |

```java
ExecutorService pool = Executors.newFixedThreadPool(8);

Future<BigDecimal> score = pool.submit(() -> riskEngine.score(txn));  // Callable → result
pool.execute(() -> auditLog.write(txn));                              // Runnable → fire-and-forget

// fan-out / fan-in over a batch of accounts
List<Callable<Balance>> lookups = accounts.stream()
        .map(a -> (Callable<Balance>) () -> cbs.fetchBalance(a))
        .toList();
List<Future<Balance>> results = pool.invokeAll(lookups);   // waits for all
```

**`ScheduledExecutorService`** — delayed and periodic execution, and the correct replacement for the legacy `Timer`/`TimerTask` (§9).

> [!info] Where this shows up in your own code
> A file-upload endpoint that must save the file, generate a thumbnail, and send an email doesn't need to do all three before responding. Save synchronously; hand the thumbnail and the email to an executor; return. The HTTP request gets shorter and the slow work still happens. (Just don't assume it happened — see the exception-swallowing trap in §8 and the transaction caveat in §15.)

### 3. The `Executors` Factory Presets

Constructing a `ThreadPoolExecutor` by hand is verbose, so Java ships a factory class. Each method is just a **preset** of the §4 parameters — know what each one actually configures, because that's the interview question:

| Factory | core / max | Queue | Behaviour |
|---|---|---|---|
| `newFixedThreadPool(n)` | n / n | **Unbounded** `LinkedBlockingQueue` | N workers, infinite queue |
| `newCachedThreadPool()` | 0 / **`Integer.MAX_VALUE`** | `SynchronousQueue` (capacity 0) | New thread per task if none free; idle threads die after 60 s |
| `newSingleThreadExecutor()` | 1 / 1 | **Unbounded** | Serial execution, submission order preserved |
| `newScheduledThreadPool(n)` | n / MAX | `DelayedWorkQueue` (unbounded) | Delays and periodic tasks (§9) |
| `newWorkStealingPool()` | = `availableProcessors()` | per-worker deques | A `ForkJoinPool`; work stealing (§11) |
| `newVirtualThreadPerTaskExecutor()` | — | — | One virtual thread per task, not a pool (Java 21+; [[8. Modern Java Concurrency]]) |

**Fixed** — the default choice. N workers; extra tasks queue. Ordering across the N workers is *not* guaranteed. Good for stable workloads: web handlers, DB work.

**Cached** — reuses an idle thread if one exists, otherwise creates a new one, with effectively **no upper limit**. Fine for many short-lived bursty tasks; dangerous under sustained load (§16).

**Single** — one worker, so tasks run **strictly in submission order**. This is the tool for per-key serialization: all events for one account processed in sequence, sequential logging, ordered event handling.

**Work-stealing** — a `ForkJoinPool` in disguise (§11).

> [!info] Fixed pools don't pre-create their threads
> `newFixedThreadPool(10)` doesn't spawn 10 threads immediately — workers are created **on demand** as tasks arrive, up to the core size. (If you *want* them warm, `ThreadPoolExecutor.prestartAllCoreThreads()` exists.)

> [!warning] Why "don't use `Executors` in production" is common advice
> Two of these presets hide an **unbounded** resource:
> - `newFixedThreadPool` and `newSingleThreadExecutor` use an **unbounded queue**. Tasks arriving faster than they're processed pile up in the heap forever → memory climbs → `OutOfMemoryError`, and **no rejection ever fires** to warn you.
> - `newCachedThreadPool` has **`maximumPoolSize = Integer.MAX_VALUE`**. A burst spawns effectively unlimited threads → OOM from thread count instead.
>
> Neither degrades — both fall off a cliff. §5 explains the mechanism and §16 shows the production-safe alternative.

### 4. `ThreadPoolExecutor` — the Engine and Its Seven Parameters

Every pool above *is* a `ThreadPoolExecutor`. Understanding its constructor is understanding thread pools:

```java
new ThreadPoolExecutor(
    int corePoolSize,                   // threads kept alive even when idle
    int maximumPoolSize,                // hard ceiling on threads
    long keepAliveTime,                 // how long ABOVE-CORE idle threads survive
    TimeUnit unit,
    BlockingQueue<Runnable> workQueue,  // where tasks wait — THE critical choice
    ThreadFactory threadFactory,        // name your threads (§10)
    RejectedExecutionHandler handler    // what to do when full (§7)
);
```

> [!example] It's a restaurant
> Permanent staff (**core threads**), extra staff you call in on a busy night (**maximum pool size**), how long you keep the extras on before sending them home (**keep-alive**), the waiting area (**queue**), how you hire (**thread factory**), and what you tell customers when both the tables and the waiting area are full (**rejection policy**).

The six moving parts:

1. **`corePoolSize`** — your permanent workers. Created on demand, then kept alive even when idle. (`allowCoreThreadTimeOut(true)` lets even these expire — useful for a pool that's idle most of the day.)
2. **`maximumPoolSize`** — the hard ceiling. Extra workers above core are created **only under specific conditions** (§5 — this is where people go wrong). Must be ≥ `corePoolSize`.
3. **`keepAliveTime`** — idle above-core workers are destroyed after this, releasing memory once the spike passes.
4. **`workQueue`** — where tasks wait when all core workers are busy. Its **type and capacity change the pool's entire behaviour** (§6).
5. **`threadFactory`** — creates the worker threads. Default names are `pool-1-thread-3`; a custom one gives you `payment-worker-3` (§10).
6. **`handler`** — invoked when the pool is saturated (§7).

### 5. Internal Working — What Happens on `execute()` ⭐

This is the single most-asked question in the module. **Memorise the order:**

1. Fewer than `corePoolSize` threads running? → **create a new core thread** for this task.
2. Core is full? → **queue** the task in `workQueue`.
3. Queue is full too? → **create threads up to `maximumPoolSize`**.
4. Max threads *and* queue both full? → **reject** via the `RejectedExecutionHandler`.

```text
Task arrives
     │
     ▼
Core threads full?
     │
 ┌───┴───┐
 No     Yes
 │       │
 ▼       ▼
Create   Queue the task
core         │
thread       ▼
         Queue full?
             │
        ┌────┴────┐
        No       Yes
        │         │
        ▼         ▼
      Wait    Below maximumPoolSize?
                  │
             ┌────┴────┐
            Yes        No
             │          │
             ▼          ▼
        Create extra   REJECT
        worker
```

**Worked example** — `core = 2`, `max = 4`, `queue capacity = 2`, seven tasks arriving at once:

| Task | Where it goes | Why |
|---|---|---|
| 1 | Worker 1 (new) | below core |
| 2 | Worker 2 (new) | below core |
| 3 | Queue | core full |
| 4 | Queue | core full — **queue now full** |
| 5 | Worker 3 (new) | queue full, below max |
| 6 | Worker 4 (new) | queue full, below max — **max reached** |
| 7 | ❌ **Rejected** | max threads *and* queue both full |

**Worker thread lifecycle** — this is what makes pools cheap:

```text
Worker created → take() a task (blocks if queue empty) → execute it
      ↑                                                      │
      └──────────────── look for the next task ◄─────────────┘
                                │
                     idle past keepAliveTime?
                                │
                   destroyed (only if above core size)
```

Workers **don't die after each task** — they loop, pulling the next one. One worker handles hundreds of tasks. No creation cost per task, no destruction cost.

> [!warning] The counter-intuitive trap: an unbounded queue makes `maximumPoolSize` a lie
> Look at the order again. Step 2 (**queue**) comes *before* step 3 (**grow the pool**). So if your `workQueue` is unbounded — a `LinkedBlockingQueue` with no capacity, i.e. what `newFixedThreadPool` gives you — the queue **never fills**, step 3 **never triggers**, and the pool **never grows past `corePoolSize`**. Your `maximumPoolSize` is dead configuration.
>
> Worse: the queue grows without limit. Incoming 500 tasks/sec, processing 100/sec → the backlog goes 400 → 1,200 → 50,000 → 500,000 → `OutOfMemoryError`. And because the queue never fills, the rejection handler **never fires**, so nothing warns you. Memory just climbs until the JVM dies.
>
> **A bounded queue is what gives you real backpressure.** This is the single most important thing to understand about thread pools. In payments it's non-negotiable: an unbounded queue means a CBS latency spike silently buffers thousands of in-flight transactions in the heap until the process dies — the worst possible failure mode, because you don't know which ones were lost.

### 6. `BlockingQueue` — the Handoff Between Submitters and Workers

Without a `BlockingQueue` there is no `ThreadPoolExecutor`. It's the bridge between task submission and worker threads — and it's the producer/consumer problem from [[3. Synchronization]] §6, solved once, in the library.

**Why not a plain `Queue`?** Because a worker with an empty queue would have to spin:

```java
while (queue.isEmpty()) { }   // ❌ busy waiting — burns a core doing nothing
```

A `BlockingQueue` parks the consumer instead: when the queue is empty the worker **sleeps** (`take()` blocks), and when a task arrives it **wakes**. Zero CPU while idle. Symmetrically, a full bounded queue **blocks the producer** — which is precisely how backpressure propagates.

**The four methods, and which one blocks:**

| | Insert | Remove |
|---|---|---|
| **Blocks** | `put(e)` — waits while full | `take()` — waits while empty |
| **Returns a signal** | `offer(e)` → `false` if full | `poll()` → `null` if empty |
| **Times out** | `offer(e, t, unit)` | `poll(t, unit)` |

`ThreadPoolExecutor` uses `offer()` on submission (so a full bounded queue triggers step 3, not a block) and `take()`/`poll(keepAlive)` in the worker loop (so idle workers park, and above-core ones expire).

**The implementations worth knowing:**

| Implementation | Shape | Use for |
|---|---|---|
| `ArrayBlockingQueue(n)` | Fixed array, **always bounded** | The safe default for a production pool — a hard memory ceiling |
| `LinkedBlockingQueue` | Linked nodes; bounded **only if** you pass a capacity | Default in `newFixedThreadPool` — **unbounded when you don't** (§5) |
| `PriorityBlockingQueue` | Unbounded heap, ordered by comparator | Higher-priority tasks first (critical > high > low) |
| `DelayQueue` | Elements emerge only once their delay expires | Cache expiry, retry-after-backoff, scheduling |
| `SynchronousQueue` | **Capacity 0** — no storage at all | Direct handoff; the queue behind `newCachedThreadPool` |
| `LinkedTransferQueue` | Unbounded, `transfer()` waits for a consumer | High-throughput handoff |

> [!info] `SynchronousQueue` is the interview favourite
> It stores **nothing**. A submitter's task must be handed **directly** to a waiting worker; if none is free, the insert fails immediately. Feed that into the §5 algorithm: step 2 (queue) always fails instantly, so step 3 (create a thread up to max) fires on *every* task that has no idle worker. That's exactly how `newCachedThreadPool` grows a thread per concurrent task — and, with `max = Integer.MAX_VALUE`, exactly why it can spawn without limit.

> [!tip] Queue choice *is* pool behaviour
> Same core and max, three queues, three completely different pools: `SynchronousQueue` → grows aggressively to max (direct handoff). Bounded `ArrayBlockingQueue` → grows only after the buffer fills, then rejects. Unbounded `LinkedBlockingQueue` → never grows past core, never rejects, OOMs. If you remember one thing from §5–§6, remember that the queue is the real configuration knob.

### 7. Rejection Policies — What Happens When You're Full

Rejection fires only when **all three** are true: core threads busy, queue full, and `maximumPoolSize` reached. It is not an error condition — it's the overload behaviour *you chose*.

> [!example] The restaurant, again
> 20 tables, all occupied, waiting area full, 50 more customers arrive. You must pick a policy: turn them away, make them wait, kick someone out, or hand them an apron.

| Policy | Behaviour | Use when |
|---|---|---|
| **`AbortPolicy`** *(default)* | Throws `RejectedExecutionException` | Losing a task is unacceptable and you want overload to be **loud** — payments, transactions |
| **`CallerRunsPolicy`** | Runs the task **on the submitting thread** | You want natural backpressure without dropping work |
| **`DiscardPolicy`** | Silently drops it — no exception, no log | The task is genuinely optional: metrics, debug telemetry |
| **`DiscardOldestPolicy`** | Drops the **oldest queued** task, enqueues the new one | Freshest data wins — a live price feed |

> [!info] `CallerRunsPolicy` is the quiet hero
> It creates a feedback loop. When the pool is saturated, the thread that *submitted* the work is forced to execute it — so it **cannot submit anything else** until it finishes. The producer is automatically throttled to the pool's real throughput. No work is dropped, no exception is thrown, and the system self-stabilises instead of collapsing. For most server workloads (web handlers, message processing, Kafka producers) it's the safest default.
>
> The caveat: your submitting thread is now doing worker duty. If that's a Tomcat request thread, that request gets slower — which is the point, but size it knowing that.

> [!warning] Never `DiscardPolicy` for anything that matters
> A silently dropped task is the hardest bug in this note to diagnose: no exception, no log line, no metric — just a payment that never happened. For business-critical work use `AbortPolicy` and let the caller retry **idempotently** ([[10. Distributed Concurrency]]).

**Custom handlers** are common in production — rejection is a great place to add a durable fallback:

```java
class OverflowToOutbox implements RejectedExecutionHandler {
    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
        rejectedCounter.increment();       // make it visible on the dashboard (§14)
        outboxRepository.save(r);          // persist to DB/Kafka and replay later
        log.warn("pool saturated: queue={} active={}",
                 executor.getQueue().size(), executor.getActiveCount());
    }
}
```

That's the transactional-outbox idea from [[11. Transaction Boundaries]] applied to an in-JVM queue: when you can't process now, **durably record it** rather than dropping or exploding.

### 8. `Callable`, `Future`, and `FutureTask` — Getting Results Back

`execute(task)` tells you nothing: did it finish? did it succeed? what did it return? You can't know. That's what this trio fixes.

**`Runnable` can't express a result.** `run()` returns `void` and can't throw checked exceptions. So Java 5 added:

```java
public interface Callable<V> { V call() throws Exception; }
```

| `Runnable` | `Callable<V>` |
|---|---|
| `run()` | `call()` |
| Returns nothing | Returns `V` |
| Cannot throw checked exceptions | Can throw checked exceptions |
| Used with `execute()` (or `submit()`) | Requires `submit()` |

**Why can't `execute()` take a `Callable`?** Because `execute()` returns `void` — there'd be nowhere to put the result. A `Callable` needs a return channel, and that channel is a `Future`.

> [!example] The restaurant token
> You order food and get **token #42**. Not the food — a *claim* on food that doesn't exist yet. Later you present the token and either collect your order or wait at the counter. `Future` is token #42.

```java
Future<Integer> future = executor.submit(() -> { Thread.sleep(2000); return 100; });

System.out.println("main thread does other work...");   // not blocked

Integer value = future.get();                            // blocks here until ready
```

**The `Future` API:**

| Method | Behaviour |
|---|---|
| `get()` | **Blocks** until done; rethrows the task's exception wrapped in `ExecutionException` |
| `get(timeout, unit)` | Blocks up to a bound, then throws `TimeoutException` — **use this in production** |
| `cancel(mayInterrupt)` | If not started, prevents it; if running and `true`, **interrupts** the thread |
| `isDone()` | Non-blocking completion check (true for success, failure *and* cancellation) |
| `isCancelled()` | Was it cancelled |

**`execute()` vs `submit()`** — a favourite question, and the exception row is the one that bites:

| | `execute(Runnable)` | `submit(Runnable/Callable)` |
|---|---|---|
| Returns | `void` | `Future` |
| Accepts | `Runnable` only | `Runnable` **or** `Callable` |
| On exception | Propagates to the thread's **uncaught exception handler** (visible, thread replaced) | **Captured in the `Future`** — surfaces only when you call `get()` |
| Intent | Fire-and-forget | Track lifecycle, retrieve result |

> [!warning] `submit()` silently swallows exceptions
> This is the #1 reason a task "did nothing" with no stack trace anywhere in the logs. `submit()` catches the throwable and stores it in the `Future`. **A `Future` you never `get()` is a lost exception.** If you're using `submit()` for fire-and-forget work, either check the `Future`, or wrap the task body in try/catch and log it yourself. `execute()` is actually *safer* for fire-and-forget precisely because failures reach the uncaught handler.

**The payoff — parallel fan-out.** A checkout page needing user, cart and coupon data:

```java
Future<User>         user    = executor.submit(() -> userClient.load(id));
Future<Cart>         cart    = executor.submit(() -> cartClient.load(id));
Future<List<Coupon>> coupons = executor.submit(() -> couponClient.load(id));

render(user.get(), cart.get(), coupons.get());
```

Sequentially: 2 s + 2 s + 2 s = **6 s**. In parallel: **≈2 s** (the slowest call), assuming the calls are independent and the pool has capacity.

> [!info] `get()` order controls when you see results, not when work happens
> Submit three tasks taking 2 s, 1 s and 3 s, then `get()` them in that order. All three *start* immediately and run concurrently, but nothing prints until the 2 s task completes — because that's the first `get()`. The 1 s result was ready long before you asked for it. `Future` gives you no "tell me when the first one finishes" — that's `invokeAny`, or `CompletableFuture`.

**`FutureTask` — the glue.** A `Thread` can only run a `Runnable`; internally it calls `runnable.run()`. There is no `callable.call()` anywhere in `Thread`. So this doesn't compile:

```java
Callable<Integer> task = () -> 100;
Thread t = new Thread(task);          // ❌ Thread expects Runnable
```

`FutureTask` is the **adapter** — like a plug adapter between an Indian plug and a US socket:

```text
Callable  →  FutureTask (implements Runnable)  →  Thread / Executor
                   │
             stores the result (implements Future)
```

It implements **`RunnableFuture`** = `Runnable` + `Future`, so it has two jobs: run the `Callable`, and hold the result. Its `run()` is essentially `result = callable.call();`.

```java
FutureTask<Integer> ft = new FutureTask<>(() -> { Thread.sleep(2000); return 500; });
new Thread(ft).start();          // no ExecutorService needed
System.out.println(ft.get());    // 500
```

And this is exactly what `submit()` does for you under the hood:

```java
// executor.submit(callable) is roughly:
FutureTask<Integer> ft = new FutureTask<>(callable);
executor.execute(ft);
return ft;
```

So `FutureTask` is to `Future` what `ArrayList` is to `List` — the concrete implementation. Internally it moves through `NEW → COMPLETING → NORMAL` (or `EXCEPTIONAL` / `CANCELLED` / `INTERRUPTED`), and it runs **exactly once**: calling `run()` on a completed `FutureTask` does nothing.

> [!info] Why `CompletableFuture` had to exist
> `Future` is **passive**. It can only say *"come back later and ask me"* — it cannot say *"when I'm done, do this."* The only way to react to completion is a thread sitting on `get()`, blocked. Pizza-shop version: `Future` is a token you keep asking about; `CompletableFuture` is *"we'll text you when it's ready."*
> ```java
> CompletableFuture.supplyAsync(() -> loadUser())
>                  .thenApply(User::getName)
>                  .thenAccept(System.out::println);   // nobody blocks
> ```
> Chaining, combining, and error handling without blocking — full treatment in [[7. Async Programming]].

| Type | Purpose |
|---|---|
| `Runnable` | Task with no return value |
| `Callable<V>` | Task that returns `V` and may throw checked exceptions |
| `Future<V>` | Handle to a not-yet-available result |
| `FutureTask<V>` | Concrete `Future`; adapts `Callable` → `Runnable` and stores the result |
| `CompletableFuture<V>` | Non-blocking composition — chaining, combining, callbacks, timeouts |

You will rarely instantiate `FutureTask` yourself. Know it because it explains *how* `submit()` works, and because "how would you run a `Callable` on a bare `Thread`?" is a real interview question.

### 9. `ScheduledExecutorService` — Delayed and Periodic Work

For "email after 5 minutes," "refresh the cache every minute," "sweep stale reversals at midnight," the wrong answer is:

```java
while (true) { Thread.sleep(60_000); refreshCache(); }   // ❌ hand-rolled, unmanaged, fragile
```

```java
ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(2);
```

**Three methods:**

```java
// 1. once, after a delay
scheduler.schedule(this::sendReminder, 5, TimeUnit.SECONDS);

// 2. periodic, measured from each scheduled START time
scheduler.scheduleAtFixedRate(this::emitHeartbeat, 2, 5, TimeUnit.SECONDS);

// 3. periodic, measured from each COMPLETION
scheduler.scheduleWithFixedDelay(this::sweepStaleReversals, 2, 5, TimeUnit.SECONDS);
```

**Fixed rate vs fixed delay** — with a 5 s period and a task that takes **3 s**:

| | `scheduleAtFixedRate` | `scheduleWithFixedDelay` |
|---|---|---|
| Measured from | The scheduled **start** time | The **end** of the previous run |
| Starts at | 2, 7, 12, 17… (by the clock) | 2, 10, 18… (finish at 5, +5 delay → 10) |
| If a run overruns the period | Next run starts **immediately** — runs can pile up | Never overlaps; the period stretches |
| Good for | Heartbeats, metrics, health checks — cadence matters | Cleanup, cache refresh, log processing — duration varies |

> [!warning] An uncaught exception silently kills the schedule — forever
> If a periodic task throws, the JDK **cancels all future executions**. No further runs, no error in your logs (the throwable goes into a `Future` nobody holds — the §8 trap). Your cache-refresh job just stops, and you find out days later from stale data. **Always wrap the body of a scheduled task in try/catch:**
> ```java
> scheduler.scheduleWithFixedDelay(() -> {
>     try { sweepStaleReversals(); }
>     catch (Exception e) { log.error("sweep failed, will retry next cycle", e); }
> }, 0, 30, TimeUnit.SECONDS);
> ```
> This is the highest-value gotcha in the whole section.

> [!info] Two more scheduler details
> - `ScheduledThreadPoolExecutor` uses an **unbounded** `DelayedWorkQueue`, so `maximumPoolSize` is effectively ignored (per §5, an unbounded queue means the pool never grows past core). Size `corePoolSize` for your peak concurrent job count — a single-thread scheduler means a long job delays every other job.
> - For cron-style scheduling in Spring, `@Scheduled` sits on top of this. It defaults to a **single-threaded** scheduler, so one slow job blocks the rest — configure a `TaskScheduler` with a real pool size.

Always `scheduler.shutdown()` — its threads are non-daemon and will keep the JVM alive (§13).

### 10. `ThreadFactory` — Name Your Threads

Your production logs show `pool-1-thread-7`. Which subsystem is that — payments, the Kafka consumer, the email worker? **You cannot tell.** During an incident, with a thread dump in front of you, that's the difference between a five-minute diagnosis and an hour.

A `ThreadFactory` controls how worker threads are created: **names**, daemon flag, priority, and uncaught exception handler.

```java
class NamedThreadFactory implements ThreadFactory {
    private final String prefix;
    private final AtomicInteger count = new AtomicInteger(1);

    NamedThreadFactory(String prefix) { this.prefix = prefix; }

    @Override public Thread newThread(Runnable r) {
        Thread t = new Thread(r, prefix + "-" + count.getAndIncrement());
        t.setDaemon(false);                        // pool work should block JVM exit
        t.setUncaughtExceptionHandler(
            (thread, ex) -> log.error("uncaught in {}", thread.getName(), ex));
        return t;
    }
}
```

```java
ExecutorService pool = new ThreadPoolExecutor(
        8, 16, 60, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(1000),
        new NamedThreadFactory("payment-worker"),
        new ThreadPoolExecutor.CallerRunsPolicy());
```

Now your dump reads `payment-worker-3`, `kafka-consumer-1`, `email-worker-2` — and you can see at a glance which pool is saturated.

> [!info] What to set, and what not to
> - **Name** — always. It's the single highest-value line of code in this section.
> - **Daemon** — usually `false` for a pool doing real work, so the JVM waits for it. `true` only for genuinely disposable background chores (see the daemon warning in [[2. Java Thread Basics]] §5).
> - **Uncaught exception handler** — worth setting, but remember it only fires for `execute()`; `submit()` failures go into the `Future` instead (§8).
> - **Priority** — effectively pointless in server apps; the OS scheduler largely ignores it. Skip it.
>
> Note the counter must be thread-safe — `newThread` can be called concurrently, so use `AtomicInteger`, not `count++` (the exact race from [[3. Synchronization]] §1).

### 11. `ForkJoinPool` — Divide-and-Conquer and Work Stealing

A specialised pool for **CPU-bound tasks that recursively split** into subtasks: parallel sort, large aggregations, tree/graph traversal. Its trick is **work stealing** — each worker owns a deque, and an idle worker **steals** from the tail of a busy worker's deque, keeping all cores busy with minimal contention.

```text
Worker A: [deque A] ──── empty ────► steals from tail of ──► [deque B] :Worker B
```

```java
class SumTask extends RecursiveTask<Long> {
    private final long[] arr; private final int lo, hi;
    protected Long compute() {
        if (hi - lo <= 1000) return directSum();       // base case
        int mid = (lo + hi) >>> 1;
        SumTask left  = new SumTask(arr, lo, mid);
        SumTask right = new SumTask(arr, mid, hi);
        left.fork();                                    // schedule left asynchronously
        return right.compute() + left.join();           // compute right here, then wait
    }
}
```

`Executors.newWorkStealingPool()` gives you one sized to `availableProcessors()`.

> [!warning] You use the common `ForkJoinPool` more than you think — don't block on it
> `Arrays.parallelSort`, `Collection.parallelStream()`, and `CompletableFuture`'s default `*Async` methods all run on the shared **common pool**, sized `cores - 1`. Two consequences:
> 1. **Never do blocking I/O on it.** A blocked worker can't be stolen from, so a few slow HTTP calls inside a `parallelStream` can starve *every* parallel stream in the JVM.
> 2. For blocking work, use your own bounded `ThreadPoolExecutor` — or pass an explicit executor to `CompletableFuture.supplyAsync(task, myPool)` ([[7. Async Programming]]).
>
> Rule of thumb: `ForkJoinPool` for **CPU**, `ThreadPoolExecutor` for **I/O**.

### 12. Tuning — Sizing the Pool and the Queue ⭐

`Executors.newFixedThreadPool(10)` — why 10? Not 5, 50, or 500? "Because it looked reasonable" is the wrong answer, and interviewers know it. The goal is to keep the CPU busy while avoiding context-switch thrash and memory waste.

**Everything starts with one question: is the work CPU-bound or I/O-bound?**

| | **CPU-bound** | **I/O-bound** |
|---|---|---|
| Examples | Hashing, encryption, compression, image processing, serialization | DB queries, REST calls to NPCI/CBS, Kafka, Redis, S3, file reads |
| Where the time goes | Executing on a core | **Blocked**, waiting for a response |
| Threads to use | ≈ **number of cores** | **Many more** than cores |
| Why | Only `cores` threads can run at once; extras just add switching | A blocked thread uses no CPU, so more threads = more in-flight work |

On 8 cores, a CPU-bound pool of 100 threads is *slower* than one of 8: only 8 run, the other 92 wait, and the OS burns time switching between them. But an I/O-bound pool of 40 on the same box is entirely reasonable.

**The formula** (Brian Goetz's, and the one to quote):

```text
threads = cores × (1 + waitTime / computeTime)
```

Worked: 8 cores, tasks that spend **90%** waiting and **10%** computing →
`8 × (1 + 90/10)` = `8 × 10` = **80 threads**.

Sanity-check both ends: CPU-bound means `wait ≈ 0` → `threads ≈ cores`. Pure waiting means the number grows large — at which point you should be asking whether virtual threads ([[8. Modern Java Concurrency]]) or a non-blocking client is the better answer. **Treat the formula as a starting point, then measure** (§14).

**Core vs maximum** — think steady state vs spike:

```text
Normal traffic  20 req/s  →  core = 20 threads
Sale starts    500 req/s  →  grows to max = 100 threads
Traffic drops             →  extras expire after keepAlive, back to 20
```

**Queue sizing** is the other half, and it's a latency/memory trade-off:

| Small queue (e.g. 10–100) | Large queue (e.g. 100,000) |
|---|---|
| Lower latency — tasks don't sit around | Fewer rejections |
| Fails fast, backpressure kicks in early | High memory use |
| More rejections under load | Long waits → latency climbs, work may be stale by the time it runs |

A queued task is a task **not being worked on**. A huge queue doesn't add capacity — it just hides the fact that you're under-provisioned, and converts a fast, visible rejection into a slow, invisible timeout. Prefer a modest bounded queue plus `CallerRunsPolicy` (§7).

> [!info] The three numbers, in practice
> For an I/O-bound payment handler on an 8-core box: `core` = your steady-state concurrency (from measured throughput × latency), `max` = core × 2–5 for spikes, `queue` = enough to absorb a few seconds of arrival rate — not minutes. Then watch `getQueue().size()` and rejection count (§14) and adjust. **Never** pick these from intuition alone; never copy them from a blog without checking your core count and workload type.

### 13. Graceful Shutdown

Your app is stopping while tasks are mid-flight. Should the JVM kill those threads instantly? No — you'd lose transactions, half-written files, uncommitted DB work.

```java
executor.shutdown();       // stop accepting NEW tasks; queued + running ones finish
executor.shutdownNow();    // stop accepting; INTERRUPT running tasks; return the un-run queue
executor.awaitTermination(10, TimeUnit.SECONDS);   // block until drained or timeout
```

| | `shutdown()` | `shutdownNow()` |
|---|---|---|
| New submissions | Rejected | Rejected |
| Queued tasks | **Run to completion** | **Dropped** (returned to you as a `List<Runnable>`) |
| Running tasks | Finish normally | **Interrupted** |
| Style | Graceful | Best-effort immediate |

Neither call blocks. `shutdown()` returns instantly — it only flips a flag. To actually wait, you need `awaitTermination`.

**The canonical pattern** — memorise this shape:

```java
pool.shutdown();                                     // 1. stop intake
try {
    if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
        pool.shutdownNow();                          // 2. escalate: interrupt stragglers
        if (!pool.awaitTermination(10, TimeUnit.SECONDS))
            log.error("pool did not terminate");
    }
} catch (InterruptedException e) {
    pool.shutdownNow();
    Thread.currentThread().interrupt();              // 3. RESTORE the flag
}
```

Three things are happening: ask nicely, escalate if it takes too long, and — if *we* get interrupted while waiting — restore the interrupt flag so our own callers know ([[2. Java Thread Basics]] §4).

> [!warning] Forgetting shutdown = a hang; swallowing interrupts = shutdownNow does nothing
> Two failure modes that tie this note back to note 2:
> - Pool threads are **non-daemon by default**, so an un-shut-down `ExecutorService` keeps the JVM alive forever — the classic "why won't my app exit?" bug. In Spring, a `@Bean ExecutorService` gets shut down automatically via its inferred `destroyMethod`; a hand-rolled one is yours to close.
> - `shutdownNow()` works **only through interruption**. A task that catches `InterruptedException` and does nothing (the note-2 sin) will happily ignore the shutdown and keep running. Cooperative cancellation requires cooperation.

### 14. Monitoring — You Cannot Tune What You Cannot See

Production questions you must be able to answer: are workers busy? is the queue growing? are tasks being rejected? Cast to the concrete type and ask:

```java
ThreadPoolExecutor pool = (ThreadPoolExecutor) Executors.newFixedThreadPool(8);
```

| Metric | Meaning | What it tells you |
|---|---|---|
| `getActiveCount()` | Threads currently executing tasks | Utilisation — pinned at max means saturated |
| `getPoolSize()` | Current worker count | Whether you've grown past core |
| `getLargestPoolSize()` | High-water mark of threads ever alive | Capacity planning — did you ever hit max? |
| `getCompletedTaskCount()` | Tasks finished | Throughput, when sampled over time |
| `getQueue().size()` | Tasks waiting | **The most important one** |
| Rejection count | (Track it yourself in the handler — §7) | Overload is actually happening |

**How to read them:**

- **Queue size steadily growing** → workers can't keep up. Either the pool is too small, or tasks got slower (a downstream is degrading). This is your early warning *before* the OOM.
- **`activeCount` == max, queue full, rejections > 0** → genuinely saturated. Scale out or shed load.
- **`activeCount` low but latency high** → the threads are *blocked*, not busy. Look for I/O under a lock ([[3. Synchronization]] §11) or a slow downstream.
- **`largestPoolSize` never reached max** → either you're over-provisioned, or (much more likely) you have an unbounded queue and the pool *can't* grow (§5).

In practice, export these to **Micrometer → Prometheus → Grafana** rather than printing them. A typical dashboard row:

```text
active threads   18      queue size   4      completed  2,500,000      rejected  0
```

Spring Boot's `ThreadPoolTaskExecutor` is instrumented by Micrometer out of the box (`executor.*` metrics) once you name the bean — one more reason to configure your own (§15).

### 15. Spring Boot `@Async`

In a Spring app you rarely build pools by hand. You annotate:

```java
@Configuration
@EnableAsync                       // required — without it @Async is silently ignored
public class AsyncConfig { }
```

```java
@Service
public class NotificationService {
    @Async
    public void sendReceipt(Payment p) { mailer.send(p); }          // caller returns immediately

    @Async
    public CompletableFuture<Invoice> generateInvoice(Payment p) {
        return CompletableFuture.completedFuture(pdf.render(p));    // when you need the result
    }
}
```

The call goes through a Spring AOP proxy, which hands the invocation to a `TaskExecutor` and returns to the caller at once. Prefer returning **`CompletableFuture`** over `Future` — Spring supports it and you get composition for free ([[7. Async Programming]]).

**Always configure your own executor:**

```java
@Bean("paymentExecutor")
public Executor paymentExecutor() {
    ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
    ex.setCorePoolSize(10);
    ex.setMaxPoolSize(50);
    ex.setQueueCapacity(500);                       // BOUNDED — the whole point
    ex.setThreadNamePrefix("payment-worker-");       // §10
    ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    ex.setWaitForTasksToCompleteOnShutdown(true);    // §13
    ex.setAwaitTerminationSeconds(30);
    ex.initialize();
    return ex;
}
```

```java
@Async("paymentExecutor")        // name it, or you get the default pool
public void settle(Payment p) { ... }
```

> [!warning] Spring's defaults carry the same unbounded traps
> `ThreadPoolTaskExecutor` defaults to **core = 8, max = `Integer.MAX_VALUE`, queue capacity = `Integer.MAX_VALUE`**. Per §5, that unbounded queue means the pool never grows past 8 *and* the backlog grows until OOM. (Historically, plain `@Async` without any executor bean fell back to a `SimpleAsyncTaskExecutor`, which is worse — it creates a **new thread per call**, no pooling at all.) Configure `corePoolSize`, `maxPoolSize`, and `queueCapacity` explicitly. Every time.

> [!warning] Self-invocation silently defeats `@Async`
> ```java
> @Service
> class PaymentService {
>     @Async public void sendMail() { }
>     public void process() { sendMail(); }   // ❌ runs SYNCHRONOUSLY
> }
> ```
> `@Async` works via a **proxy**. An internal call goes straight to `this`, bypassing the proxy entirely, so the annotation does nothing — and nothing warns you. Same reason `private` and `static` methods can't be `@Async`. Fixes: call it from a *different* bean, inject self, or extract the async method into its own component. (Identical mechanics to `@Transactional` self-invocation — see [[11. Transaction Boundaries]].)

> [!warning] `@Async` leaves your transaction and your request context behind
> The work now runs on a **different thread**, so:
> - It is **outside** the caller's `@Transactional` boundary. A rollback in the caller will not undo it, and lazy-loading an entity you passed in will blow up — pass IDs and reload, or commit first and hand off after ([[11. Transaction Boundaries]]).
> - `ThreadLocal`-based context is gone: security context, MDC trace IDs, tenant. You'll lose your correlation IDs in the logs of exactly the async work you most need to trace ([[2. Java Thread Basics]] §6).
> - A `void` `@Async` method that throws sends the exception **nowhere** by default. Register an `AsyncUncaughtExceptionHandler`, or return `CompletableFuture` so the failure is capturable.

### 16. Common Mistakes and the Production Checklist

Nearly every concurrency-related outage is one of these eight.

| # | Mistake | Why it hurts | Fix |
|---|---|---|---|
| 1 | `new Thread()` per request | 1,000 req/s = 1,000 threads/s → memory, switching, instability | One shared, bounded pool |
| 2 | Forgetting `shutdown()` | Non-daemon workers keep the JVM alive — app won't exit | The §13 pattern |
| 3 | **Unbounded queue** | Backlog grows silently → OOM, and `max` never applies | `new ArrayBlockingQueue<>(1000)` |
| 4 | Too many threads | 500 threads on 8 cores = context-switch thrash, *slower* | Size by workload (§12) |
| 5 | Blocking inside the pool | One 40 s HTTP call ties up a worker for 40 s; enough of them exhaust the pool | Timeouts on every client; separate pools per downstream |
| 6 | Ignoring exceptions | `submit()` hides the throwable in the `Future`; nobody looks | try/catch in the task, or check the `Future` (§8) |
| 7 | Wrong pool size for the workload | 500 threads for CPU work; 2 for DB work | CPU ≈ cores; I/O = formula (§12) |
| 8 | No monitoring | "The app is slow" with no queue depth, no active count → undiagnosable | Export the §14 metrics |

> [!warning] Mistake 5 deserves its own paragraph — bulkheading
> A pool shared across downstreams couples their failures. If the invoice-PDF service goes slow, its tasks occupy every worker, and payments — which share the pool — start queueing behind them. One slow dependency takes down an unrelated feature. **Use separate bounded pools per downstream** (the bulkhead pattern) so a slowdown is contained. And put a timeout on every blocking call: `future.get(2, SECONDS)`, HTTP read timeouts, DB query timeouts. A blocking call with no timeout is a thread leak with extra steps.

**The checklist — run it on every pool you create:**

```text
✓ Pool size justified by workload type (CPU vs I/O), not guessed?
✓ Queue BOUNDED?
✓ Rejection policy chosen deliberately?
✓ Threads named via a ThreadFactory?
✓ Exceptions handled (or Futures actually checked)?
✓ Timeouts on every blocking call inside a task?
✓ Graceful shutdown wired up?
✓ Metrics exported (active, queue depth, completed, rejected)?
```

**The complete picture, end to end:**

```text
                        Task
                          │
              ┌───────────┴───────────┐
          Runnable                Callable
              └───────────┬───────────┘
                          ▼
                  ExecutorService
                 execute() / submit()
                          ▼
                  ThreadPoolExecutor
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
    Core threads    BlockingQueue    Extra threads (→ max)
                          │                   │
                          ▼                   ▼
                   Worker threads         (all full → Rejection policy)
                          │
                   executes task
              ┌───────────┴───────────┐
          execute()                submit()
              ▼                        ▼
          no result              Future ← FutureTask stores result
```

**Pick the right tool:**

| Need | Use |
|---|---|
| Fire-and-forget background work | `Runnable` + `execute()` |
| A return value | `Callable` + `submit()` → `Future` |
| Run a `Callable` on a bare `Thread` | `FutureTask` |
| A managed pool | `ExecutorService` / `ThreadPoolExecutor` |
| Delayed or periodic work | `ScheduledExecutorService` |
| Recursive CPU-bound splitting | `ForkJoinPool` / `RecursiveTask` |
| Spring background method | `@Async` + a configured `ThreadPoolTaskExecutor` |
| Non-blocking async pipelines | `CompletableFuture` ([[7. Async Programming]]) |

### 17. Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| Why not `new Thread()` per request? | Threads cost ~1 MB of stack plus an OS thread; per-request creation is unbounded and expensive → context-switch thrash and OOM. Pools cap and reuse. |
| What problem do thread pools solve? | Reuse a bounded set of workers to run many tasks — cheap, capped, queued, manageable. |
| Order of the `ThreadPoolExecutor` submission logic? | Core threads → queue → grow to max → reject. |
| Why can an unbounded queue break the pool? | The queue is tried *before* growing the pool. Unbounded ⇒ never fills ⇒ pool never exceeds core, rejection never fires, memory grows until OOM. |
| Why avoid `Executors.newFixedThreadPool` in prod? | Unbounded `LinkedBlockingQueue` → the trap above. Build a `ThreadPoolExecutor` with a bounded queue + explicit rejection policy. |
| Why avoid `newCachedThreadPool`? | `max = Integer.MAX_VALUE` with a `SynchronousQueue` → a burst spawns effectively unlimited threads → OOM. |
| Fixed vs cached vs single? | Fixed = N workers + queue; cached = grow/shrink per task for bursts; single = one worker, strict submission order. |
| Does a fixed pool create its threads up front? | No — on demand up to core size (`prestartAllCoreThreads()` if you want them warm). |
| Can `maximumPoolSize` be less than `corePoolSize`? | No. |
| What does `keepAliveTime` apply to? | Idle threads **above** core size (unless `allowCoreThreadTimeOut(true)`). |
| Why a `BlockingQueue` and not a `Queue`? | It parks the worker when empty and the producer when full — no busy waiting, and backpressure for free. |
| `put`/`take` vs `offer`/`poll`? | `put`/`take` block; `offer`/`poll` return `false`/`null` immediately (timed variants exist). |
| What's special about `SynchronousQueue`? | Capacity 0 — direct handoff. Insert fails unless a worker is waiting, which is why cached pools grow a thread per concurrent task. |
| When does rejection happen? | Only when core threads are busy **and** the queue is full **and** max threads is reached. |
| Default rejection policy? | `AbortPolicy` — throws `RejectedExecutionException`. |
| Which policy gives backpressure, and how? | `CallerRunsPolicy` — the submitter executes the task, so it can't submit more until done; throughput self-limits without dropping work. |
| `execute()` vs `submit()`? | `submit()` takes `Runnable` or `Callable` and returns a `Future`; `execute()` takes `Runnable` and returns void. Exceptions: `submit()` captures them in the `Future`, `execute()` sends them to the uncaught handler. |
| Where does an exception in a `submit()`ed task go? | Into the `Future` — surfaced as `ExecutionException` only when you call `get()`. Never call `get()` and it's lost silently. |
| `Runnable` vs `Callable`? | `Callable.call()` returns a value and may throw checked exceptions; `Runnable.run()` does neither. |
| Why can't `execute()` take a `Callable`? | `execute()` returns void — there's no channel for the result. |
| Does `Future` make code asynchronous? | No. The **executor** runs the task asynchronously; `Future` is just a handle to observe or fetch the result. |
| What is `FutureTask` and why does it exist? | `Runnable` + `Future`. It adapts a `Callable` into something a `Thread` can run, and stores the result. `submit()` creates one internally. |
| How do you run a `Callable` without an `ExecutorService`? | Wrap it in a `FutureTask` and pass that to `new Thread(...)`. |
| `Future` vs `CompletableFuture`? | `Future` is passive — you block on `get()`. `CompletableFuture` supports callbacks, chaining, combining and timeouts without blocking. |
| `scheduleAtFixedRate` vs `scheduleWithFixedDelay`? | Fixed rate measures from each scheduled **start** (runs can pile up if one overruns); fixed delay measures from each **completion** (never overlaps). |
| What happens if a periodic task throws? | All future executions are **silently cancelled**. Always try/catch inside the task body. |
| Why a custom `ThreadFactory`? | Thread **names** — `pool-1-thread-7` tells you nothing in a thread dump; `payment-worker-7` tells you everything. Also daemon flag and uncaught handler. |
| What is work stealing? | Idle `ForkJoinPool` workers steal tasks from the tail of busy workers' deques, keeping all cores busy with low contention. |
| Gotcha with `parallelStream`? | It runs on the shared common `ForkJoinPool`; blocking I/O there starves every parallel stream in the JVM. |
| How do you size a pool? | CPU-bound ≈ #cores; I/O-bound ≈ `cores × (1 + wait/compute)`. Starting point only — then measure. |
| Why is a huge queue not "more capacity"? | Queued work isn't being done. It converts fast visible rejections into slow invisible timeouts, and burns heap. |
| `shutdown()` vs `shutdownNow()`? | `shutdown()` stops intake and lets queued + running tasks finish; `shutdownNow()` interrupts running tasks and returns the un-run queue. |
| Does `shutdown()` kill threads or block? | Neither — it stops new submissions and returns immediately. Use `awaitTermination` to wait. |
| Why does my JVM not exit? | Pool threads are non-daemon; you never called `shutdown()`. |
| What breaks `shutdownNow()`? | Tasks that swallow `InterruptedException` — cancellation is cooperative. |
| Which pool metric matters most? | Queue depth over time — a steadily growing queue is the early warning before saturation and OOM. |
| Does `@Async` create a new thread per call? | No, it uses a `TaskExecutor` — but configure it; the defaults are unbounded (and the historical no-bean fallback did create a thread per call). |
| Why didn't my `@Async` method run asynchronously? | Self-invocation (bypasses the proxy), a `private`/`static` method, or a missing `@EnableAsync`. |
| Is `@Async` work inside the caller's transaction? | No — different thread, so it's outside the `@Transactional` boundary, and `ThreadLocal` context (security, MDC) doesn't follow. |

This closes out the JVM-side fundamentals (Roadmap §1–§4). Next: [[5. Concurrent Utilities]] — atomics, CAS, and the coordination primitives that replace hand-rolled locking. Then [[6. Concurrent Collections]], `CompletableFuture` ([[7. Async Programming]]), and the backend layer: [[9. Database Concurrency]], [[10. Distributed Concurrency]], [[11. Transaction Boundaries]].
