Covers Roadmap section 4. This is the one that matters most in real backend systems. Notes 2–3 gave you raw threads and locks; nobody writes `new Thread()` per request in production. Server code hands **tasks** to a **managed pool** — and every incident-worthy concurrency bug (thread exhaustion, unbounded queues, silent OOMs) lives here.

> [!info] The through-line of this note
> One idea drives everything: **decouple the task from the thread, then bound the threads.**
>
> 1. Raw threads don't scale — creating one per request is unbounded and expensive (§1). So you pool and reuse them.
> 2. The API is a three-level hierarchy: **`Executor` → `ExecutorService` → `ScheduledExecutorService`** (§2), each adding capability.
> 3. Under every pool sits one real class: **`ThreadPoolExecutor`** (§3). Its five knobs — core size, max size, keep-alive, **the queue**, and the **rejection policy** — decide all behaviour. The queue is where most people get burned.
> 4. The `Executors` factory methods (fixed / cached / single) are just **presets** of those knobs (§4) — and two of them are dangerous defaults (§5).
> 5. **Rejection policies** (§6) are what happens when you're full — a design decision, not an error.
> 6. **`ForkJoinPool`** (§7) is a different beast for divide-and-conquer CPU work.
> 7. Shutting down cleanly (§8) is where correctness meets the daemon/interrupt rules from [[2. Java Thread Basics]].

### 1. Why Pools — the Problem With Raw Threads

`new Thread(task).start()` per unit of work has three fatal flaws in a server:

1. **Cost.** Each thread maps to an OS thread with ~1 MB of stack. Creating and destroying them constantly is expensive.
2. **Unbounded.** A traffic spike of 10,000 requests spawns 10,000 threads → context-switch thrashing → OOM. There's no ceiling.
3. **No management.** No reuse, no queueing, no backpressure, no lifecycle control.

A **thread pool** fixes all three: a fixed set of **worker threads** pull **tasks** from a **queue**. Threads are reused (cheap), the pool size is capped (bounded), and the queue absorbs bursts (backpressure). This is the payoff of the task/worker split from [[2. Java Thread Basics]] §1 — because a `Runnable`/`Callable` doesn't own a thread, N tasks can share a small pool.

### 2. The Executor Hierarchy

Three interfaces, increasing capability:

```
Executor                    -> execute(Runnable)                fire-and-forget
  └─ ExecutorService        -> submit(...) -> Future, shutdown() results + lifecycle
       └─ ScheduledExecutorService -> schedule(...), scheduleAtFixedRate(...)  delays/repeats
```

**`Executor`** — one method, `execute(Runnable)`. Just "run this somewhere."

**`ExecutorService`** — the one you actually use. Adds:
- `submit(Callable/Runnable)` → returns a `Future` (results + exceptions, from [[2. Java Thread Basics]] §2).
- `invokeAll(tasks)` → run a batch, block until all finish, return `List<Future>`.
- `invokeAny(tasks)` → return the first successful result, cancel the rest.
- `shutdown()` / `shutdownNow()` → lifecycle (§8).

```java
ExecutorService pool = Executors.newFixedThreadPool(8);

Future<BigDecimal> score = pool.submit(() -> riskEngine.score(txn));  // Callable
pool.execute(() -> auditLog.write(txn));                              // Runnable, fire-and-forget

// fan-out / fan-in over a batch of accounts
List<Callable<Balance>> lookups = accounts.stream()
        .map(a -> (Callable<Balance>) () -> cbs.fetchBalance(a))
        .toList();
List<Future<Balance>> results = pool.invokeAll(lookups);   // waits for all
```

**`ScheduledExecutorService`** — delayed and periodic execution; the correct replacement for `Timer`/`TimerTask`.

```java
ScheduledExecutorService sched = Executors.newScheduledThreadPool(2);
sched.scheduleAtFixedRate(this::sweepStaleReversals, 0, 30, TimeUnit.SECONDS);
```

> [!info] `scheduleAtFixedRate` vs `scheduleWithFixedDelay`
> `atFixedRate` fires every N seconds *by the clock* — if a run overshoots N, the next starts immediately (runs can pile up). `withFixedDelay` waits N seconds *after the previous finishes* — no pile-up. For a job whose duration varies (a reconciliation sweep), `withFixedDelay` is usually the safer choice.

### 3. `ThreadPoolExecutor` — the Engine, and Its Five Knobs

Every pool from the `Executors` factory is really a `ThreadPoolExecutor`. Understanding its constructor is understanding thread pools:

```java
new ThreadPoolExecutor(
    int corePoolSize,        // threads kept alive even when idle
    int maximumPoolSize,     // hard ceiling on threads
    long keepAliveTime,      // how long extra (above-core) idle threads live
    TimeUnit unit,
    BlockingQueue<Runnable> workQueue,      // where tasks wait — THE critical choice
    ThreadFactory threadFactory,            // name threads! (huge for debugging)
    RejectedExecutionHandler handler        // what to do when full (§6)
);
```

**The submission algorithm — memorise this order, it's the #1 interview question here:**

1. Fewer than `corePoolSize` threads running? → **create a new thread** for the task.
2. Core is full? → **queue the task** in `workQueue`.
3. Queue is full too? → create threads up to `maximumPoolSize`.
4. Max threads *and* queue both full? → **reject** via the rejection handler.

> [!warning] The counter-intuitive trap: an unbounded queue makes `maximumPoolSize` a lie
> Step 2 queues before step 3 grows the pool. If your `workQueue` is *unbounded* (`LinkedBlockingQueue` with no capacity), the queue **never fills**, so step 3 never triggers and the pool never grows past `corePoolSize`. Your `maximumPoolSize` is dead config. Worse, the queue grows without limit → memory climbs → OOM under sustained load, with no rejection ever firing. **A bounded queue is what gives you real backpressure.** This is the single most important thing to understand about pools.

> [!info] Sizing the pool
> - **CPU-bound** work (hashing, serialization): ~`number of cores` threads. More just adds context-switch overhead.
> - **I/O-bound** work (DB calls, HTTP to NPCI/CBS, S3): threads spend most time *blocked*, so you want many more — roughly `cores × (1 + wait_time/compute_time)`. A payment handler calling three downstreams is heavily I/O-bound.
>
> Always name your threads via a `ThreadFactory` (`payment-worker-%d`). When you're staring at a thread dump during an incident, unnamed `pool-1-thread-7` tells you nothing.

### 4. The `Executors` Factory Presets

`Executors` is a convenience factory that pre-fills the `ThreadPoolExecutor` knobs. Know what each *actually* configures:

| Factory | core / max | Queue | Behaviour |
|---|---|---|---|
| `newFixedThreadPool(n)` | n / n | **Unbounded** `LinkedBlockingQueue` | N threads, infinite queue |
| `newCachedThreadPool()` | 0 / **`Integer.MAX_VALUE`** | `SynchronousQueue` (no capacity) | New thread per task if none free; idle threads die after 60s |
| `newSingleThreadExecutor()` | 1 / 1 | **Unbounded** | Serial execution, ordering guaranteed |
| `newScheduledThreadPool(n)` | n / MAX | `DelayedWorkQueue` | Delays and periodic tasks |
| `newVirtualThreadPerTaskExecutor()` | — | — | One virtual thread per task (Java 21+; see Roadmap §8) |

**Fixed** — most common. N workers, tasks queue up. Ordering not guaranteed across the N.
**Cached** — grows unboundedly; good for many short-lived bursty tasks, dangerous for sustained load.
**Single** — one thread, so tasks run **strictly in order** — useful when you need per-key serialization (e.g. all events for one account processed in sequence).

---

### 5. Why "Never Use `Executors` in Production" Is Common Advice

Two of those presets carry hidden unbounded resources:

- **`newFixedThreadPool`** and **`newSingleThreadExecutor`** use an **unbounded queue** → the OOM-under-load trap from §3. Tasks pile up in memory forever instead of applying backpressure.
- **`newCachedThreadPool`** has **`maximumPoolSize = Integer.MAX_VALUE`** → under a burst it spawns effectively unlimited threads → OOM from thread count instead.

> [!warning] The production-safe pattern
> Construct `ThreadPoolExecutor` directly with a **bounded** queue and an explicit **rejection policy**, so overload degrades predictably instead of crashing:
> ```java
> ExecutorService pool = new ThreadPoolExecutor(
>     8, 16, 60, TimeUnit.SECONDS,
>     new ArrayBlockingQueue<>(1000),                 // bounded — real backpressure
>     new ThreadFactoryBuilder().setNameFormat("pay-worker-%d").build(),
>     new ThreadPoolExecutor.CallerRunsPolicy());     // throttle the submitter
> ```
> In payments this is not optional: an unbounded queue means a downstream slowdown (CBS latency spike) silently buffers thousands of in-flight transactions in heap until the JVM dies — the worst possible failure mode. A bounded queue + `CallerRunsPolicy` makes the pressure visible and self-limiting.

> [!info] Spring's `@Async` uses a pool too
> Spring Boot's `ThreadPoolTaskExecutor` (behind `@Async`) defaults to core=8, max=Integer.MAX_VALUE, queue=Integer.MAX_VALUE — the same unbounded traps. Always configure `corePoolSize`, `maxPoolSize`, and `queueCapacity` explicitly. And remember: work moved onto an `@Async` thread has **left your `@Transactional` boundary** — see [[11. Transaction Boundaries]].

### 6. Rejection Policies — What Happens When You're Full

When both pool and queue are saturated, the `RejectedExecutionHandler` decides the fate of the new task. Four built-ins:

| Policy | Behaviour | Use when |
|---|---|---|
| `AbortPolicy` (default) | Throws `RejectedExecutionException` | You want to fail fast and surface overload |
| `CallerRunsPolicy` | Runs the task **on the submitting thread** | You want natural backpressure — the submitter slows down, which throttles intake |
| `DiscardPolicy` | Silently drops the task | The task is truly optional (best-effort metrics) |
| `DiscardOldestPolicy` | Drops the oldest queued task, enqueues the new one | Freshest data matters most (live price feed) |

> [!info] `CallerRunsPolicy` is the quiet hero
> It creates a feedback loop: when the pool is full, the thread *submitting* work is forced to execute it, so it can't submit more until it finishes. That naturally slows the producer to the pool's actual throughput — self-regulating backpressure without dropping work. For most server workloads it's the safest default. Never `DiscardPolicy` for anything you can't afford to lose (a payment must never be silently dropped — fail loud with `AbortPolicy` and let the caller retry idempotently, per [[9. Database Concurrency]] §10).

### 7. `ForkJoinPool` — Divide-and-Conquer

A specialised pool for **CPU-bound tasks that recursively split** into subtasks (parallel sort, big aggregations). Its trick is **work-stealing**: each worker has its own deque, and an idle worker *steals* tasks from the tail of a busy worker's deque — keeping all cores busy with minimal contention.

```java
class SumTask extends RecursiveTask<Long> {
    private final long[] arr; private final int lo, hi;
    protected Long compute() {
        if (hi - lo <= 1000) { /* base case: sum directly */ return directSum(); }
        int mid = (lo + hi) >>> 1;
        SumTask left  = new SumTask(arr, lo, mid);
        SumTask right = new SumTask(arr, mid, hi);
        left.fork();                       // schedule left async
        return right.compute() + left.join();   // compute right here, wait for left
    }
}
```

> [!info] You use `ForkJoinPool` more than you think
> `Arrays.parallelSort`, `Collection.parallelStream()`, and `CompletableFuture`'s default async run on the **common `ForkJoinPool`**. Two consequences: (1) it's sized to `cores - 1` by default, and (2) **never do blocking I/O on it** — a blocked worker can't be stolen from, and you starve every parallel stream in the JVM. For blocking work, use your own bounded `ThreadPoolExecutor`, not `parallelStream`.

### 8. Shutting Down Cleanly

A pool holds **non-daemon threads by default**, so the JVM won't exit until you shut it down (or those threads finish). Graceful shutdown ties together interruption ([[2. Java Thread Basics]] §4):

```java
pool.shutdown();                    // stop accepting new tasks; let queued ones finish
if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
    pool.shutdownNow();             // interrupt running tasks, drop the queue
    pool.awaitTermination(10, TimeUnit.SECONDS);
}
```

- `shutdown()` — polite: no new tasks, existing ones complete.
- `shutdownNow()` — **interrupts** running threads (so your tasks must honour interruption — the cooperative model from note 2) and returns the un-run queue.
- `awaitTermination(...)` — block until the pool drains or the timeout hits.

> [!warning] Forgetting to shut down = a hang or a leak
> An un-shut-down `ExecutorService` keeps non-daemon threads alive → the JVM never exits (a "why won't my app stop?" bug). In Spring, a `@Bean` `ExecutorService` gets `shutdown()` called automatically via `destroyMethod`; a hand-created one you own. And because `shutdownNow()` relies on interruption, a task that swallows `InterruptedException` (the note-2 sin) will ignore the shutdown and run on — tying the two topics together.

### 9. Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| Why not `new Thread()` per request? | Unbounded + expensive → context-switch thrash and OOM under load. Pools cap and reuse. |
| Order of the `ThreadPoolExecutor` submission logic? | Core threads → queue → grow to max → reject. |
| Why can an unbounded queue break the pool? | Queue fills before max grows; unbounded queue never fills, so pool never exceeds core and memory grows until OOM. |
| Why avoid `Executors.newFixedThreadPool` in prod? | Unbounded queue → OOM under load. Use `ThreadPoolExecutor` with a bounded queue + rejection policy. |
| Why avoid `newCachedThreadPool`? | `maxPoolSize = Integer.MAX_VALUE` → unlimited threads under a burst → OOM. |
| Fixed vs cached vs single? | Fixed = N workers + queue; cached = grow/shrink for bursts; single = serial, ordered execution. |
| What does `CallerRunsPolicy` do and why care? | Runs the task on the submitter → backpressure that throttles intake without dropping work. |
| How size a pool? | CPU-bound ≈ #cores; I/O-bound ≈ cores × (1 + wait/compute) — more, since threads block. |
| `submit()` vs `execute()`? | `submit()` returns a `Future` (result + exception); `execute()` is fire-and-forget, exceptions go to the uncaught handler. |
| What is work-stealing? | `ForkJoinPool` idle workers steal tasks from busy workers' deques to keep all cores busy. |
| `shutdown()` vs `shutdownNow()`? | `shutdown()` drains gracefully; `shutdownNow()` interrupts running tasks and drops the queue. |
| Gotcha with `parallelStream`? | Runs on the shared common `ForkJoinPool`; blocking I/O on it starves every parallel stream in the JVM. |
