Covers Roadmap section 6. Note 5 gave you CAS and the atomics built on it. This note is where those same ideas — CAS for the cheap path, fine-grained locking for the expensive one, striping to spread contention — get baked into **data structures**. In practice this is the most-used part of `java.util.concurrent`: almost every backend service has a `ConcurrentHashMap` and a `BlockingQueue` in it.

> [!info] The through-line of this note
> `HashMap` isn't thread-safe, and the old fix (`Collections.synchronizedMap`) puts **one lock around everything** — correct but serial (§1). Every collection here is an answer to "how do we keep it safe *without* one big lock?", and each picks a different trick:
>
> | Collection | The trick |
> |---|---|
> | **`ConcurrentHashMap`** (§2–§6) | Independent buckets: **CAS** on empty ones, **lock one bin** on occupied ones |
> | **`BlockingQueue`** (§7) | Blocking handoff — parks producers when full, consumers when empty |
> | **`ConcurrentLinkedQueue`** (§8) | Pure CAS, never blocks, unbounded |
> | **`CopyOnWrite*`** (§9) | Writers copy the whole array; readers never synchronise at all |
> | **`ConcurrentSkipList*`** (§10) | Lock-free skip list — the *sorted* option |
>
> The recurring theme: **each one buys cheap reads by making some other operation more expensive**, and knowing which trade you're making is the whole skill. The trap that catches everyone is that thread-safe *operations* don't give you thread-safe *sequences* — `containsKey` then `put` is still a race (§5).

### 1. Why These Exist — What Actually Breaks

**`HashMap` is not thread-safe.** Concurrent writes can:

- **Lose updates** — two threads inserting into the same bucket, one link overwritten.
- **Corrupt `size`** — `size++` is read-modify-write ([[3. Synchronization]] §1), so the count drifts from reality.
- **Lose entries during resize** — two threads rehashing simultaneously can drop buckets. (On Java 7 this famously produced a **circular linked list** and an *infinite loop* in `get()` — a pegged CPU core with no exception. Java 8's resize preserves order and no longer spins that way, but it's still unsafe: you get lost data and a wrong size instead of a hang. "It doesn't infinite-loop any more" is not "it's safe.")
- **Throw `ConcurrentModificationException`** — `HashMap`'s iterators are **fail-fast**: they carry a modification counter and throw the moment anyone else structurally changes the map mid-iteration.

**The old fix, and why it's not good enough:**

```java
Map<String, Long> m = Collections.synchronizedMap(new HashMap<>());
```

Every method now acquires **one shared mutex**. Three problems:

1. **Zero concurrency.** A reader on key `"A"` blocks a writer on key `"Z"`. All threads serialise through one lock, so throughput doesn't improve with cores.
2. **Compound operations are still racy.** Each *method* is atomic; a *sequence* of them isn't:
   ```java
   if (!m.containsKey(k)) m.put(k, v);   // ❌ two atomic calls, one race
   m.put(k, m.get(k) + 1);              // ❌ classic lost update
   ```
3. **Iteration needs external synchronisation anyway** — you must wrap the whole loop in `synchronized (m) { ... }`, or you get a `ConcurrentModificationException`.

`ConcurrentHashMap` fixes all three: real concurrency, atomic compound methods (§5), and iterators that never throw (§4).

### 2. `ConcurrentHashMap` — the Design

Start from how any hash map stores data — an array of **buckets** (bins), each holding a linked list (or a red-black tree once it gets long):

```text
index
  0 → null
  1 → (A=10)
  2 → (B=20) → (F=60)      ← collision: linked list
  3 → null
  4 → (C=30)
  5 → null
  6 → null
  7 → (D=40)
```

**The key insight: buckets are independent.** If `Apple` hashes to bucket 2 and `Banana` to bucket 7, two threads writing them touch **completely disjoint memory**. There is nothing to coordinate — no lock needed between them at all.

```text
Thread A: put("Apple", 100)   → bucket 2 ─┐
Thread B: put("Banana", 200)  → bucket 7 ─┴─ fully parallel, zero contention
```

That's the whole basis of `ConcurrentHashMap`'s scalability: **contention is per-bucket, not per-map.** Two threads only interfere when they land in the *same* bucket — which, with a decent hash spread, is rare.

> [!info] Two generations, and interviewers ask about both
> - **Java 7:** the map was split into 16 **segments**, each guarded by its own `ReentrantLock` (an explicit form of the **lock striping** from [[3. Synchronization]] §11). Concurrency was capped at the segment count, and every segment carried a lock object.
> - **Java 8+:** segments were **removed**. Locking is now **per bin** — the map `synchronized`s on the *first node of that bucket*, so the granularity is one bucket instead of one-sixteenth of the map. Empty buckets are filled by **CAS** with no lock at all (§3). Bins also **treeify** into a red-black tree once they exceed ~8 nodes, so a pathological hash degrades to O(log n) rather than O(n).
>
> If asked "how does CHM achieve concurrency?", the modern answer is **"CAS for empty bins, one lock per occupied bin"** — not "16 segments" and definitely not "it locks the map."

### 3. Inside `put()` — Where CAS Ends and Locking Begins ⭐

The biggest misconception is *"`ConcurrentHashMap` uses CAS everywhere."* **It doesn't.** It uses **both**, and which one depends on whether the target bucket is empty.

**Case 1 — the bucket is empty → CAS, no lock.**

Installing the first node is a **single reference write**, which is exactly what CAS can do atomically:

```text
Bucket 5:  null  ──CAS(expected = null, new = Node(Apple))──►  Node(Apple)
```

Conceptually `if (bucket == null) bucket = newNode;` — but as one indivisible instruction. No lock, no blocking. This is the fast path, and in a well-spread map it's the common one.

**What if two threads race for the same empty bucket?** Both read `null`, both attempt CAS:

```text
Thread A: CAS(null → Apple)     ✅ succeeds
Thread B: CAS(null → Banana)    ❌ fails — expected null, found Apple
```

Only one CAS can win ([[5. Concurrent Utilities]] §2). Thread B's failure isn't an error — it's information: *the bucket is no longer empty*. So B re-reads and takes the other path.

**Case 2 — the bucket is occupied → lock that one bin.**

Now Thread B must **append to a linked list**, not replace a reference:

```text
Bucket 2:  A → B → C        insert D:
             1. traverse to the tail
             2. allocate the new node
             3. update C.next
```

That's **three operations**, not one CPU instruction. CAS cannot express it. If two threads did it unsynchronised, both could write `C.next` and one insertion would silently vanish. So the map takes a lock — **on that bucket's head node only**:

```text
Bucket 2:  A → B → C → D     (locked for the duration of the pointer surgery)
```

The map is untouched. Every other bucket stays fully available.

**Put it together — four buckets, three threads, all concurrent:**

```text
Bucket 1   LOCKED by Thread B     Apple → Grapes        (occupied → lock)
Bucket 2   untouched              Orange
Bucket 3   CAS only, no lock      Mango                 (was empty → CAS)
Bucket 4   LOCKED by Thread C     Banana → Kiwi         (occupied → lock)
```

Thread B and Thread C hold **different** locks, so neither waits for the other. Thread A never took a lock at all. This is what "fine-grained locking" buys you, and it's why CHM scales where `synchronizedMap` flatlines.

**The complete flow:**

```text
put(key, value)
      │
      ▼
compute hash → locate bucket
      │
      ▼
Is the bucket empty?
     /        \
   Yes         No
    │           │
    ▼           ▼
 CAS install   synchronized (bucket head)
 the node          │
    │              ▼
 success?      walk the list/tree:
    │          replace value if key exists,
   yes         else append; treeify if long
    │              │
    └──────┬───────┘
           ▼
      count++ (striped, §6) → maybe resize
```

(A failed CAS just loops back to the top and re-evaluates — by then the bucket is occupied, so it goes down the lock path.)

> [!tip] The 30-second interview answer
> "`ConcurrentHashMap` hashes the key to find its bucket. If the bucket is **empty**, it installs the node with a **CAS** — no lock. If the bucket already has nodes (or the CAS loses a race), it takes a lock on **that bucket's head node only** and does the list/tree update there. Buckets are independent, so threads hitting different buckets never contend, and `get()` is lock-free. CAS for the cheap single-pointer case, fine-grained locking for the multi-pointer case — that's how it beats synchronizing the whole map."
>
> The follow-up is almost always **"why not CAS for everything?"** → because appending to a linked list is several pointer updates, and CAS is atomic for exactly one word.

### 4. Reads Are (Almost) Lock-Free

`get()` takes **no lock**:

```text
get(key) → compute hash → find bucket → walk the list/tree → return
```

It works because the node fields are designed for safe concurrent reading: `key` and `hash` are `final` (immutable once published), and `val` and `next` are **`volatile`**. So a reader either sees the old value or the new one — never a half-written node — courtesy of the happens-before rules in [[3. Synchronization]] §5. No locking, no barriers beyond the volatile reads.

That's why CHM is exceptional in **read-heavy** workloads, which is most caches, config lookups, and routing tables.

**Iterators are weakly consistent** — and this is a genuine behavioural difference from `HashMap`:

| | `HashMap` | `ConcurrentHashMap` |
|---|---|---|
| Iterator style | **Fail-fast** | **Weakly consistent** |
| Concurrent modification | Throws `ConcurrentModificationException` | Never throws |
| What you see | — | Every element present at creation; changes made *after* may or may not appear |
| Traverses | — | Each element exactly once |

```java
for (Map.Entry<String, Long> e : chm.entrySet()) {   // safe — no CME, no external lock
    ...
}
```

> [!info] "Weakly consistent" is a feature, not a hedge
> You get a **safe** traversal without locking the map, at the cost of not getting a **point-in-time snapshot**. For iterating a live cache or dumping metrics, that's exactly the right trade. When you truly need a consistent snapshot, CHM cannot give you one — copy under external coordination, or hold an immutable map behind an `AtomicReference` ([[5. Concurrent Utilities]] §4) and swap it.

### 5. The Atomic Compound Operations — Use These, Not Check-Then-Act

This is where most `ConcurrentHashMap` bugs live. **Each method is atomic; a sequence of methods is not.**

```java
// ❌ ALL of these are races, even on a ConcurrentHashMap
if (!map.containsKey(k)) map.put(k, newList());     // two threads → two lists, one lost
map.put(k, map.get(k) + 1);                          // lost update
Long v = map.get(k); if (v == null) map.put(k, 1L);  // same bug, spelled differently
```

The map guarantees each call is safe *individually*. Between two calls, anything can happen. CHM's answer is a family of **atomic compound methods** — each performs the whole read-decide-write under the bin's lock:

| Method | Does, atomically |
|---|---|
| `putIfAbsent(k, v)` | Insert only if absent; returns the existing value (or `null` if it inserted) |
| `computeIfAbsent(k, fn)` | Insert `fn(k)` only if absent; **`fn` runs at most once** even under a race |
| `computeIfPresent(k, fn)` | Update only if present; remove the entry if `fn` returns `null` |
| `compute(k, fn)` | Insert / update / remove, whatever `fn` decides |
| `merge(k, v, fn)` | If absent, put `v`; else put `fn(old, v)` — **the counter idiom** |
| `replace(k, old, new)` | CAS on the value — succeeds only if it still equals `old` |
| `remove(k, v)` | Remove only if currently mapped to `v` |
| `getOrDefault(k, d)` | Read with a fallback, no mutation |

The two that cover most real code:

```java
// Concurrent counter — correct, atomic, no lock in your code
map.merge(key, 1L, Long::sum);

// Lazily initialise a per-key value exactly once
List<Txn> bucket = map.computeIfAbsent(accountId, id -> new CopyOnWriteArrayList<>());
```

`merge` replaces the whole broken `get`/`+1`/`put` dance. `computeIfAbsent` replaces `containsKey`/`put` — and crucially, if 50 threads call it for a new key at once, the mapping function runs **once** and all 50 get the same value. (`putIfAbsent` would have all 50 *construct* a value and 49 throw theirs away — fine for cheap values, wasteful for expensive ones.)

> [!warning] The mapping function runs while holding the bin's lock
> `computeIfAbsent` / `compute` / `merge` invoke your lambda **inside the synchronized block for that bucket**. Three rules follow, and they're documented hazards:
> 1. **Never block in it** — no I/O, no DB call, no HTTP, no waiting on another lock. You're holding a lock that every other thread on that bucket needs (the "no I/O under a lock" rule from [[3. Synchronization]] §11, now inside a library call). A slow loader here stalls the bucket.
> 2. **Never touch the same map in it.** A recursive update — `computeIfAbsent` whose function calls `map.put`/`computeIfAbsent` on the *same* map — can throw `IllegalStateException("Recursive update")` or **deadlock**. Compute the value from inputs you already have.
> 3. **Keep it short and side-effect-free.** Same reasoning as `updateAndGet` in [[5. Concurrent Utilities]] §3.
>
> If loading is expensive or blocking, store a `CompletableFuture`/memoized holder as the value instead (`computeIfAbsent` installs the *future* cheaply, and callers await it outside the lock), or use a real cache library.

### 6. What `ConcurrentHashMap` Does *Not* Give You

Four limits worth knowing before you rely on it:

**1. `size()` is an estimate.** Java 8+ tracks the count with a striped `baseCount` + counter cells — the same design as `LongAdder` ([[5. Concurrent Utilities]] §5). Summing them while other threads mutate gives an **approximation**, not a snapshot. Prefer `mappingCount()` (returns `long`, avoids `int` overflow on huge maps). Never use `size()` in a correctness decision — no `if (map.size() < limit) map.put(...)`, which is a check-then-act race on top of an approximate number.

**2. No atomicity across keys.** Every guarantee is scoped to **one key's bucket**. Moving a value from key A to key B, or maintaining an invariant between two entries, needs your own lock. CHM gives you per-entry atomicity, not transactions.

**3. `null` keys and values are forbidden** — unlike `HashMap`, which allows both. `map.put(k, null)` throws `NullPointerException`. The reason is a real ambiguity: `get(k)` returning `null` would mean either "absent" or "present, mapped to null", and in a concurrent map you **cannot** disambiguate with a follow-up `containsKey` — the answer may change between the two calls. Banning null removes the ambiguity. (Use a sentinel or `Optional` as the value if you need "known to be empty.")

**4. Iteration is weakly consistent** (§4) — safe, but not a snapshot.

### 7. `BlockingQueue` — the Handoff Collection

You already met this as the spine of `ThreadPoolExecutor` ([[4. Executors and Thread Pools]] §6). As a collection in its own right, it's the standard **producer/consumer** channel: the `wait`/`notify` bounded buffer from [[3. Synchronization]] §6, correct and done for you.

The defining feature is that it **blocks** instead of failing:

| | Insert | Remove |
|---|---|---|
| **Blocks** | `put(e)` — waits while full | `take()` — waits while empty |
| **Returns a signal** | `offer(e)` → `false` | `poll()` → `null` |
| **Times out** | `offer(e, t, unit)` | `poll(t, unit)` |
| **Throws** | `add(e)` → `IllegalStateException` | `remove()` → `NoSuchElementException` |

| Implementation | Shape | Use for |
|---|---|---|
| `ArrayBlockingQueue(n)` | Fixed array, **always bounded**, single lock | A hard memory ceiling; the safe default for backpressure |
| `LinkedBlockingQueue` | Linked; bounded **only if** you pass a capacity | Higher throughput — **separate put/take locks**, so producers and consumers don't contend |
| `PriorityBlockingQueue` | Unbounded heap, comparator order | Priority work (critical before bulk) |
| `DelayQueue` | Elements emerge when their delay expires | Retry-after-backoff, cache expiry, scheduling |
| `SynchronousQueue` | **Capacity 0** — direct handoff | Rendezvous; the queue behind `newCachedThreadPool` |
| `LinkedTransferQueue` | Unbounded; `transfer()` waits for a consumer | High-throughput handoff |

```java
BlockingQueue<Txn> queue = new ArrayBlockingQueue<>(1000);   // BOUNDED — deliberate

// producer
queue.put(txn);                       // blocks if full → backpressure reaches the caller

// consumer
while (running) {
    Txn t = queue.poll(1, TimeUnit.SECONDS);   // timed, so shutdown is responsive
    if (t != null) process(t);
}
```

> [!warning] Bounded, or it isn't backpressure
> An unbounded `LinkedBlockingQueue` never blocks the producer, so a slow consumer just grows the heap until OOM — the exact trap from [[4. Executors and Thread Pools]] §5, now in your own code rather than a pool's. If you want the producer to feel the pressure, the queue must have a capacity **and** you must use `put` (not `offer`, which silently returns `false` and drops the item if you ignore the result).

### 8. `ConcurrentLinkedQueue` — Non-Blocking and Unbounded

A CAS-based, **lock-free** FIFO queue (the Michael–Scott algorithm). No locks anywhere, and it **never blocks**: if it's empty, `poll()` returns `null` immediately rather than waiting.

```java
Queue<Event> q = new ConcurrentLinkedQueue<>();
q.offer(event);                  // always succeeds — unbounded
Event e = q.poll();              // null if empty, never blocks
```

**`ConcurrentLinkedQueue` vs `BlockingQueue`** — pick by what you want to happen when the queue is empty:

| | `ConcurrentLinkedQueue` | `LinkedBlockingQueue` |
|---|---|---|
| Empty `poll()` | Returns `null` immediately | `take()` **waits** |
| Bounded | ❌ Never | ✅ Optional |
| Locks | None (CAS) | Yes (two locks) |
| Consumer style | You must poll in a loop — usually **busy-waiting** | Park until work arrives, zero CPU idle |
| Best for | Handing work off where a consumer is already polling for other reasons (an event loop) | Dedicated consumer threads — almost all worker patterns |

> [!info] Default to `BlockingQueue` for worker patterns
> Lock-free sounds strictly better, but if your consumer's only job is to drain the queue, `ConcurrentLinkedQueue` forces you to spin (`while ((e = q.poll()) == null) {}`) — burning a core to avoid a lock you actually *wanted*. `take()` parking the thread is the correct behaviour. Reach for `ConcurrentLinkedQueue` when the consumer is already in a loop doing other work, or when you genuinely must never block a producer.
>
> Also: **`size()` is O(n)** and weakly consistent — it walks the whole queue. Never call it on a hot path, and never use `isEmpty()`-then-`poll()` as a pair (check-then-act again — just `poll()` and null-check). `ConcurrentLinkedDeque` is the double-ended version.

### 9. `CopyOnWriteArrayList` and `CopyOnWriteArraySet`

A radically different trade: **every mutation copies the entire backing array** (under a lock), then swaps the reference in. Readers touch an immutable array and therefore **never synchronise at all**.

```text
write:  [A, B, C]  →  allocate [A, B, C, D]  →  volatile swap of the array reference
read:   grab the current array reference and walk it — no lock, no CAS, no volatile-per-element
```

| Operation | Cost |
|---|---|
| `get(i)`, iteration | **Free** — plain array access, zero contention |
| `add`, `remove`, `set` | **O(n)** — full array copy + allocation, serialised by a lock |

```java
private final List<PaymentListener> listeners = new CopyOnWriteArrayList<>();

void register(PaymentListener l) { listeners.add(l); }       // rare — startup only

void onSettled(Payment p) {
    for (PaymentListener l : listeners) l.handle(p);          // hot path — zero overhead
}
```

**Use it for:** listener/observer registries, rarely-changing config lists, small whitelists, routing tables — anything written a handful of times at startup and read constantly. `CopyOnWriteArraySet` is the same thing with set semantics (backed by the same array, so `contains` is O(n) — fine for small sets, wrong for large ones; use `ConcurrentHashMap.newKeySet()` for a real concurrent set).

> [!warning] Catastrophic for write-heavy use
> Adding N elements one at a time is **O(n²)** in copies and allocates N arrays — GC pressure plus latency spikes. A `CopyOnWriteArrayList` that grows on a request path is a performance incident waiting to happen. If writes are anything but rare, use a `BlockingQueue`, a synchronized list, or a `ConcurrentHashMap`-backed structure instead.

> [!info] Iterators are true snapshots — the opposite trade from CHM
> An iterator captures the array reference at creation, so it sees a **consistent point-in-time snapshot**, never throws `ConcurrentModificationException`, and **will not reflect writes made after it started**. That's genuinely useful (safe iteration of a listener list while a listener registers), but two consequences: a long-lived iterator can hold a stale view indefinitely, and mutating methods on the iterator (`remove`, `set`, `add`) throw `UnsupportedOperationException` — you can't modify through it.
>
> Contrast with §4: CHM iterators are *weakly consistent* (may see later writes); COW iterators are *snapshot* (never see later writes). Both never throw. Know which you're holding.

### 10. `ConcurrentSkipListMap` and `ConcurrentSkipListSet` — the Sorted Option

`ConcurrentHashMap` is unordered. When you need **sorted** concurrent access — the thread-safe counterpart of `TreeMap` — the answer is a lock-free **skip list**:

```java
ConcurrentNavigableMap<Instant, Txn> byTime = new ConcurrentSkipListMap<>();

byTime.put(txn.timestamp(), txn);
Map.Entry<Instant, Txn> oldest = byTime.firstEntry();
ConcurrentNavigableMap<Instant, Txn> window = byTime.subMap(from, to);   // range query
byTime.headMap(cutoff).clear();                                          // evict everything older
```

| | `ConcurrentHashMap` | `ConcurrentSkipListMap` |
|---|---|---|
| Ordering | None | **Sorted** by key / comparator |
| `get` / `put` | O(1) average | O(log n) |
| Range queries, first/last, ceiling/floor | ❌ | ✅ (`NavigableMap`) |
| Implementation | CAS + per-bin locks | Lock-free skip list |
| `size()` | Approximate | O(n) — walks the list |

Use it for time-ordered data: expiry/eviction by timestamp, sliding windows, leaderboards, priority indexes, anything needing "give me everything between X and Y." Otherwise `ConcurrentHashMap` is faster.

### 11. Choosing the Right Collection

| You need… | Use | Not |
|---|---|---|
| A thread-safe map | `ConcurrentHashMap` | `Collections.synchronizedMap` (one global lock) |
| A thread-safe **sorted** map | `ConcurrentSkipListMap` | `Collections.synchronizedSortedMap` |
| A thread-safe set | `ConcurrentHashMap.newKeySet()` | `CopyOnWriteArraySet` unless tiny + read-only |
| An atomic per-key counter | `map.merge(k, 1L, Long::sum)` | `get` then `put` |
| Lazy per-key initialisation | `map.computeIfAbsent(k, fn)` | `containsKey` then `put` |
| Producer → consumer handoff | `BlockingQueue` (**bounded**) | Hand-rolled `wait`/`notify` |
| A queue that must never block a producer | `ConcurrentLinkedQueue` | `BlockingQueue` with `put` |
| A read-mostly listener/config list | `CopyOnWriteArrayList` | Any write-heavy use |
| A consistent snapshot of shared state | Immutable object behind `AtomicReference` ([[5. Concurrent Utilities]] §4) | Any collection here — none give snapshots except COW iterators |
| An invariant spanning several keys/entries | Your own `Lock` ([[3. Synchronization]]) | Any concurrent collection alone |

> [!tip] The two rules that prevent most bugs
> 1. **Don't wrap — replace.** `Collections.synchronizedX` is a legacy adapter: it serialises everything *and* still leaves your compound operations racy. Reach for the purpose-built class.
> 2. **Thread-safe methods ≠ thread-safe logic.** Any `if (map.…) then map.…` is a race no matter how safe the collection is. If you can't express it as a *single* call (`merge`, `computeIfAbsent`, `putIfAbsent`, `replace(k, old, new)`, `remove(k, v)`), you need a lock. This one sentence catches more real bugs than anything else in this note.

### 12. Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| What actually breaks with a `HashMap` under concurrency? | Lost updates, a corrupted `size`, entries lost during resize, and `ConcurrentModificationException` on iteration. (Java 7 could also infinite-loop on a circular list during resize.) |
| Why not `Collections.synchronizedMap`? | One global lock ⇒ no concurrency; compound operations are still racy; iteration needs external synchronisation. |
| How does `ConcurrentHashMap` achieve concurrency? | Buckets are independent: **CAS** installs the first node in an empty bucket with no lock; an occupied bucket is **locked at its head node only**. Different buckets never contend. |
| Where exactly is CAS used in CHM? | Installing the **first node into an empty bin** (a single reference write). Not for list/tree updates. |
| Why not use CAS for everything? | Appending to a linked list is traverse + allocate + update `next` — several operations. CAS is atomic for one word only, so concurrent appends could lose an insertion. |
| What does CHM lock, and how much? | The **head node of one bin**, for the duration of that bin's update. Not the map, not a segment. |
| Java 7 vs Java 8 CHM? | Java 7: 16 lock-striped **segments**. Java 8+: **no segments** — per-bin CAS + `synchronized` on the bin head, plus treeification of long bins. |
| Does `get()` lock? | No. `key`/`hash` are final and `val`/`next` are `volatile`, so reads are safe and lock-free — which is why CHM excels at read-heavy work. |
| Fail-fast vs weakly consistent iterators? | `HashMap` iterators throw `ConcurrentModificationException`; CHM iterators never throw, see everything present at creation, and may or may not see later writes. |
| Is `if (!map.containsKey(k)) map.put(k, v)` safe on a CHM? | **No** — two atomic calls, one race. Use `putIfAbsent` or `computeIfAbsent`. |
| How do you increment a counter in a CHM correctly? | `map.merge(key, 1L, Long::sum)` — a single atomic operation. |
| `putIfAbsent` vs `computeIfAbsent`? | `putIfAbsent` needs the value constructed up front (racing threads discard duplicates); `computeIfAbsent` runs the mapping function **at most once** and only when absent — better for expensive values. |
| What must you never do inside `computeIfAbsent`? | Block (I/O, another lock) or touch the same map — you hold the bin's lock; recursive updates can throw `IllegalStateException` or deadlock. |
| Is `ConcurrentHashMap.size()` exact? | No — it's summed from striped counter cells (like `LongAdder`), so it's an estimate. Prefer `mappingCount()`, and never gate logic on it. |
| Why does CHM reject `null` keys and values? | A `null` from `get()` would be ambiguous between "absent" and "mapped to null", and you can't safely disambiguate with `containsKey` in a concurrent map. |
| Can CHM make an update across two keys atomic? | No — atomicity is per key/bin. Spanning keys needs your own lock. |
| `ArrayBlockingQueue` vs `LinkedBlockingQueue`? | Array: fixed capacity, one lock. Linked: optionally bounded, **separate put/take locks** so producers and consumers don't contend. |
| `BlockingQueue` vs `ConcurrentLinkedQueue`? | `take()` **parks** the consumer when empty; `poll()` returns `null` immediately. Use blocking for dedicated consumers; lock-free only when you must never block or are already polling. |
| Gotcha with `ConcurrentLinkedQueue.size()`? | It's **O(n)** and weakly consistent — it walks the queue. Don't call it on a hot path. |
| How does `CopyOnWriteArrayList` work? | Every mutation copies the whole backing array under a lock and swaps the reference; readers use an immutable array with **no synchronisation**. |
| When is `CopyOnWriteArrayList` wrong? | Any write-heavy use — each write is O(n) with a fresh allocation, so building it up is O(n²) plus GC pressure. |
| COW iterator vs CHM iterator? | COW = **snapshot** (never sees later writes, no mutation through it). CHM = **weakly consistent** (may see later writes). Neither ever throws CME. |
| What gives you a sorted concurrent map? | `ConcurrentSkipListMap` — a lock-free skip list, O(log n), with `NavigableMap` range queries. Use it for time-ordered/windowed data. |
| Best concurrent `Set`? | `ConcurrentHashMap.newKeySet()`. `CopyOnWriteArraySet` only for tiny, read-only sets (`contains` is O(n)). |
| The one rule that prevents most concurrency bugs with collections? | Thread-safe *methods* don't make a thread-safe *sequence*. If it isn't a single call, it needs a lock. |
