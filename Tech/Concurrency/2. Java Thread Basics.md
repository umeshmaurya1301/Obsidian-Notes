Covers Roadmap section 2. Note 1 explained *why* concurrency is hard — visibility, reordering, the JMM. This note is the mechanical layer under all of that: how you actually create, hand work to, wait on, and stop a thread in Java.

> [!info] The through-line of this note
> One chain, read in order:
>
> 1. A **task** is just code (`Runnable`/`Callable`); a **thread** is the worker that runs it (§1). Keeping those two ideas separate is the whole reason modern Java uses pools instead of raw threads.
> 2. If the task returns a value or throws, `Runnable` can't express that — that's why **`Callable` + `Future`** exist (§2).
> 3. Once a thread is running you need to **coordinate** with it: wait for it (`join`), pause it (`sleep`), hint the scheduler (`yield`) — §3.
> 4. You can't *stop* a Java thread by force. You can only **ask** it, via interruption (§4). Getting this right is the single most-failed part of thread basics.
> 5. **Daemon vs user** threads (§5) decide whether the JVM waits for your thread on shutdown.
> 6. **`ThreadLocal`** (§6) is per-thread storage — and the source of subtle leaks in exactly the pooled world §1 pushes you toward.
>
> Everything past this note (`synchronized`, executors, futures) assumes you're fluent here.

### 1. Thread vs Runnable — Worker vs Job

`java.lang.Thread` represents an independent path of execution — a worker mapped (in the classic model) 1:1 to an OS thread. `java.lang.Runnable` is a functional interface with a single `run()` method — it represents *the job*, not the worker.

The core discipline: **separate the task from the thing that runs it.** A task should not know or care whether it runs on a new thread, a pooled thread, or the calling thread.

**Approach A — extend `Thread` (rarely used):**

```java
class MyThread extends Thread {
    @Override public void run() {
        System.out.println("Running on: " + Thread.currentThread().getName());
    }
}
new MyThread().start();   // start() spawns the OS thread; run() would NOT
```

**Approach B — implement `Runnable` (preferred):**

```java
Runnable job = () -> System.out.println("Job on: " + Thread.currentThread().getName());
Thread worker = new Thread(job);
worker.start();
```

> [!warning] `start()` vs `run()` — the classic trap
> Calling `run()` directly executes the code **on the current thread** — no new thread, no concurrency. Only `start()` spawns a thread and *then* invokes `run()` on it. Interviewers ask this to check you understand a `Thread` object is not the thread.

**Why `Runnable` wins:**

| | `extends Thread` | `implements Runnable` |
|---|---|---|
| Inheritance | Burns your one superclass slot | Class stays free to extend something |
| Coupling | Task welded to the worker | Task decoupled — reusable |
| Reuse | A `Thread` can't be restarted after it finishes | One `Runnable` can be handed to many threads / a pool |
| Modern Java | Almost never used directly | What you pass to `ExecutorService` (see [[4. Executors and Thread Pools]]) |

> [!info] Why this matters beyond style
> Because a `Runnable` doesn't own a thread, an executor can run thousands of them on a small pool of reused threads. That decoupling is the foundation the entire executor framework is built on. Raw `new Thread()` per task is an anti-pattern in server code — it's unbounded, so a traffic spike spawns thousands of OS threads and OOMs the box.

### 2. `Callable` and `Future` — Tasks That Return or Throw

`Runnable.run()` returns `void` and cannot throw checked exceptions. That's fine for fire-and-forget, but most real work produces a result — a balance lookup, a risk score, an NPCI response — and can fail.

`Callable<V>` fixes both: it returns `V` and is allowed to throw.

```java
interface Callable<V> { V call() throws Exception; }
```

You can't hand a `Callable` to `new Thread(...)` — only to an executor. Submitting one gives you a **`Future<V>`**: a handle to a result that doesn't exist *yet*.

```java
ExecutorService pool = Executors.newFixedThreadPool(4);

Future<BigDecimal> f = pool.submit(() -> riskEngine.score(txnId));  // Callable

// ... do other work while it computes ...

BigDecimal score = f.get();   // BLOCKS until the result is ready
```

`Future` is the join point between "I started async work" and "I need the answer now":

| Method | Does |
|---|---|
| `get()` | Blocks until done; **rethrows** the task's exception wrapped in `ExecutionException` |
| `get(timeout, unit)` | Blocks up to a bound, then throws `TimeoutException` — essential for payments, where you never wait forever on a downstream |
| `cancel(mayInterrupt)` | Attempts to stop; interrupts the running thread if `true` |
| `isDone()` / `isCancelled()` | Non-blocking status checks |

> [!warning] `Future.get()` swallows nothing but hides everything
> If the task threw, you only find out when you call `get()` — it comes back as `ExecutionException` with the real cause inside `getCause()`. A `Future` you never `get()` is a silently-lost exception. This is the #1 reason a submitted task "did nothing" with no stack trace in the logs.

> [!info] `Future` is the primitive; `CompletableFuture` is the upgrade
> A plain `Future` can only be *blocked on* — you can't say "when this finishes, do X" without a thread sitting on `get()`. `CompletableFuture` (Roadmap §7) adds non-blocking chaining, combining, and error handling. Know `Future` as the foundation; reach for `CompletableFuture` in real code.

### 3. Coordinating With a Running Thread — `sleep`, `yield`, `join`

Once threads are running, these three control timing and ordering. All are about *cooperation*, not force.

**`Thread.sleep(ms)` — pause this thread.**
Suspends the *current* thread for at least the given time. It does **not** release any lock it holds (contrast with `wait()` in [[3. Synchronization]]). Throws `InterruptedException`.

```java
Thread.sleep(200);   // back off before retrying a downstream call
```

**`Thread.yield()` — a hint, not a guarantee.**
Suggests the scheduler give other runnable threads a turn. The JVM is free to ignore it entirely. Almost never correct to rely on in production — treat it as a testing/benchmarking curiosity.

**`join()` — wait for another thread to finish.**
The most useful of the three. `t.join()` blocks the *caller* until thread `t` completes. This is how you fan out work and then wait for all of it.

```java
Thread settlement = new Thread(() -> reconcile(batch));
settlement.start();

// main thread does other prep...

settlement.join();          // wait until reconciliation is done
System.out.println("Batch reconciled, safe to proceed");
```

> [!example] `join()` = the poor man's fan-out/fan-in
> Start N threads, then `join()` each one — now you've waited for all N. It works, but it's manual and you get no results back (they're `Runnable`s). In real code you'd use `invokeAll` on an executor or `CompletableFuture.allOf`. `join()` is the primitive those are built on. See [[4. Executors and Thread Pools]].

### 4. Interruption — You *Ask* a Thread to Stop, You Can't Force It

Java has **no safe way to forcibly kill a thread.** `Thread.stop()` is deprecated and dangerous — it can release locks mid-update and leave shared state corrupt (imagine killing a thread halfway through a two-line debit/credit). So Java uses a **cooperative** model: interruption is a *request* the target thread must choose to honour.

Interruption sets a boolean flag on the thread. Well-behaved code checks that flag and winds down.

```java
Thread worker = new Thread(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        try {
            process(queue.take());      // blocking call
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();  // RESTORE the flag — see below
            break;                                // stop cleanly
        }
    }
    log.info("Worker shutting down gracefully");
});
worker.start();
// ... later ...
worker.interrupt();   // ask it to stop
```

Two ways a thread notices interruption:

1. **It's running CPU code** → the interrupt flag is set; your loop must poll `isInterrupted()`.
2. **It's blocked** in `sleep()`, `wait()`, `join()`, or a blocking I/O/queue call → that method throws `InterruptedException` immediately and **clears the flag**.

> [!warning] The single most-broken idiom in Java concurrency
> When you catch `InterruptedException`, the flag has been **cleared**. If you just swallow it (`catch (InterruptedException e) {}`), the interruption is *lost* — outer code (like a pool shutting down) will never know the thread was asked to stop, and it may hang forever. **Always** either:
> - rethrow it, or
> - restore the flag with `Thread.currentThread().interrupt()` before handling it.
>
> Never `catch` it and do nothing. Interviewers specifically probe this.

> [!info] Why cooperative and not forced?
> Forced termination can't guarantee invariants. If you kill a thread between the debit and the credit, atomicity is gone and you've lost money. Cooperative interruption lets the thread reach a *safe point* — finish the unit, release locks, roll back — before exiting. This is the same "reach a consistent state before stopping" principle as transaction rollback in [[9. Database Concurrency]].

### 5. Daemon vs User Threads — Does the JVM Wait for You?

Every thread is either a **user thread** or a **daemon thread**. The rule that matters:

> The JVM exits when the last **user** thread finishes. It does **not** wait for daemon threads — they're killed abruptly on shutdown.

```java
Thread heartbeat = new Thread(this::emitMetrics);
heartbeat.setDaemon(true);   // must be set BEFORE start()
heartbeat.start();
```

- **User thread (default):** keeps the JVM alive. Use for work that *must complete* — processing a payment, flushing a batch.
- **Daemon thread:** background chores that should die with the app — metrics emitters, cache-eviction sweepers, heartbeat pingers.

> [!warning] Never do critical work on a daemon thread
> A daemon is killed mid-execution at shutdown with no chance to finish or clean up. If your settlement writer runs on a daemon and the JVM exits, you can get a half-written batch. Anything with correctness or durability implications belongs on a user thread (or, better, a properly shut-down executor — see [[4. Executors and Thread Pools]]).

### 6. `ThreadLocal` — Per-Thread Storage

A `ThreadLocal<T>` gives *each thread its own independent copy* of a variable. Same field, different value per thread — no sharing, so no synchronization needed.

```java
private static final ThreadLocal<SimpleDateFormat> FMT =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

String today = FMT.get().format(new Date());   // each thread gets its own SDF
```

Classic uses:
- Wrapping **non-thread-safe** objects (`SimpleDateFormat`, `SimpleDateFormat` is the canonical example) so each thread has a private one.
- Carrying **request context** without threading it through every method — trace IDs, the authenticated user, the current tenant. Spring's `SecurityContextHolder` and `TransactionSynchronizationManager` (the thing that binds your DB connection to the thread — see [[11. Transaction Boundaries]]) are both `ThreadLocal` under the hood.

> [!warning] `ThreadLocal` + thread pools = leaks and dirty reads
> This is the trap that ties §6 back to §1. Pool threads are **reused** across thousands of tasks. A value you set in one task is still there when the next task lands on that same thread. Two failure modes:
> - **Stale data leak:** task B reads the trace ID / user that task A left behind → wrong data attributed to the wrong request. In payments that's a *catastrophic* mix-up (one customer's context bleeding into another's transaction).
> - **Memory leak:** the value is never garbage-collected because the pool thread lives forever.
>
> **Rule:** if you set a `ThreadLocal` on a pooled thread, clear it in a `finally`:
> ```java
> try {
>     CONTEXT.set(requestCtx);
>     handle(request);
> } finally {
>     CONTEXT.remove();   // mandatory on pooled threads
> }
> ```
> Frameworks do this for you at request boundaries; if you add your own `ThreadLocal`, *you* own the cleanup.

### 7. Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| `start()` vs `run()`? | `run()` runs on the current thread (no concurrency); `start()` spawns a new thread then calls `run()`. |
| Why prefer `Runnable` over extending `Thread`? | Decouples task from worker, keeps your superclass slot, and lets the task go to a pool. |
| `Runnable` vs `Callable`? | `Callable` returns a value and can throw checked exceptions; `Runnable` returns void and can't. |
| What does `submit()` give you? | A `Future` — a handle to a not-yet-computed result; `get()` blocks and rethrows task exceptions. |
| Can you kill a thread in Java? | No. You *interrupt* it — a cooperative request. `Thread.stop()` is deprecated (corrupts state). |
| What must you do when catching `InterruptedException`? | Restore the flag (`Thread.currentThread().interrupt()`) or rethrow — never swallow it. |
| `sleep()` vs `wait()`? | `sleep()` keeps any held lock and is time-based; `wait()` releases the monitor and waits for `notify()`. (See [[3. Synchronization]].) |
| Daemon vs user thread? | JVM waits for user threads to finish; daemons are killed on shutdown. Never run critical work on a daemon. |
| When does `ThreadLocal` bite you? | On pooled threads — stale values leak between tasks and memory leaks unless you `remove()` in `finally`. |
