## ⚡ Quick Revision Summary
> - **Concurrency vs. Parallelism:** Concurrency is a program structure that interleaves task execution on a single processor, whereas parallelism achieves true simultaneous execution across multiple CPU cores.
    
- **Memory Visibility:** This dictates whether one thread can see another's updates to shared RAM, as updates can be obscured by local CPU caches unless explicit synchronization tools are used.
    
- **Instruction Reordering:** Compilers and CPUs may silently rearrange code for performance; while safe for single-threaded tasks, it can break multithreaded logic without proper memory barriers.
    
- **Java Memory Model (JMM):** The JMM provides the formal contract dictating how threads interact through shared memory, specifically defining the behavior of `volatile`, `synchronized`, and `final` variables.
    
- **Happens-Before Relationship:** This establishes a strict execution sequence (like unlocking a monitor before another thread locks it), ensuring memory changes from the first action are visible to the second.
    
- **JMM Guarantees:** The model formally ensures atomicity (indivisible operations), visibility (cross-thread awareness of changes), and ordering (preventing unexpected instruction shifts).
    
- **Keyword Comparison:** Both `volatile` and `synchronized` ensure visibility and ordering, but only `synchronized` (or tools like `AtomicInteger` via CAS) can guarantee atomicity.
    
- **CPU Cache Mechanism:** To bypass slow main RAM, CPUs load variables into fast local caches (L1/L2/L3), which directly causes the memory visibility traps in multithreading.
    
- **Starvation:** This system failure occurs when low-priority tasks (like low-fee transactions) are indefinitely blocked from shared resources by a constant flood of higher-priority tasks.

## 📖 Detailed Concepts
### 1. Concurrency vs. Parallelism

- **Concurrency:**
    - **Definition:** The composition of independently executing tasks. It is a program design structure.
    - **Execution:** Tasks make overlapping progress. The CPU scheduler multiplexes execution time across multiple tasks (time-slicing).
    - **Purpose:** To improve the responsiveness and throughput of applications by allowing them to perform multiple operations at once, even if they are executed on a single processor.

- **Parallelism:**
    - **Definition:** Simultaneous execution of multiple tasks on multiple processors.
    - **Execution:** Tasks run truly in parallel across different CPU cores or machines.
    - **Purpose:** To achieve significant performance improvements by utilizing the full processing power available in multi-core systems.

### 2. Memory Visibility

- **Definition:** Memory visibility refers to whether one thread can see the changes made to shared data by another thread.
- **Mechanism:** 
    - Thread A runs on CPU Core 1 and reads a `counter` variable from RAM into Core 1's local cache, then increments it.
    - Thread B runs on CPU Core 2 and reads the same `counter` variable directly from RAM.
- **Trap:** If Thread A only updates its local cache and hasn't flushed that data back to main RAM yet, Thread B will read the stale value from RAM. Thread A's modification is invisible to Thread B.
- **Fix:** Using the `volatile` keyword or synchronization blocks forces the CPU to bypass the local cache, writing directly to (and reading from) the main shared memory, ensuring visibility.

### 3. Instruction Reordering

- **Definition:** The compiler, JVM (Just-In-Time compiler), and physical CPU are allowed to silently rearrange the order of your code instructions to optimize performance.
- **Rule:** They will only reorder instructions if doing so does not change the outcome of a single-threaded execution.
- **Trap:** While reordering is safe for one thread, it can cause issues in multithreading.
    - _Code:_ `a = 1;` `flag = true;`
    - _Reordered by CPU:_ `flag = true;` `a = 1;`
    - If Thread B reads `flag == true`, it assumes that `a` has been initialized, but due to reordering, it might read the stale value of `a`.

### 4. The Memory Model (e.g., Java Memory Model - JMM)

- **Definition:** A formal set of rules and guarantees provided by the language specification.
- **Purpose:** Defines how threads interact through memory, ensuring that optimizations do not violate expected behavior.
- **Scope:** Specifies behaviors of `volatile`, `synchronized`, and `final` keywords in Java.

### 5. Happens-Before Relationship

- **Definition:** A guarantee that if Action A happens-before Action B, all memory changes made by A will be visible to B, and B will not execute before A.
- **Establishment:** Created by specific Java keywords:
    - **Monitor Lock Rule:** Unlocking a `synchronized` block happens-before another thread locking the same monitor.
    - **Volatile Variable Rule:** Writing to a `volatile` variable happens-before any subsequent read of that variable.
    - **Thread Start Rule:** Calling `Thread.start()` happens-before the actual code inside the thread's `run()` method executes.
- **Impact:** Ensures hardware-level barriers, preventing instruction reordering and synchronizing CPU caches with main memory.

### 6. Guarantees (The JMM Contract)

- **Atomicity:** Operations happen all at once or not at all.
    - **What is Atomic in Java:**
        - Reading or writing reference variables.
        - Reading or writing primitive variables except `long` and `double` on some older 32-bit JVMs.
    - **What is NOT Atomic in Java:**
        - The increment operator (`i++`).
        - Check-Then-Act operations like `if (a == 1) { a = 2; }`.

- **Visibility:** Changes made by one thread are seen by others.
    - **Java Tools:** `volatile`, `synchronized`, `Lock`.

- **Ordering:** The sequence of events is preserved as intended.
    - **Java Tools:** `volatile` (prevents some reordering), `synchronized` (prevents code from moving in/out of the block).

### 7. Practical Comparison Table

|**Feature**|**volatile**|**synchronized**|**AtomicInteger**|
|---|---|---|---|
|**Visibility**|✅ Yes|✅ Yes|✅ Yes|
|**Ordering**|✅ Yes|✅ Yes|✅ Yes|
|**Atomicity**|❌ No|✅ Yes|✅ Yes (via CAS)|

### 8. CPU Cache

- **Problem:** Main memory (RAM) is slow compared to the speed of the CPU.
- **Solution:** Modern CPUs have built-in caches (L1, L2, and L3) that store copies of frequently accessed data, significantly reducing access times.
- **How it Works:** When a thread needs a variable, the CPU loads it from RAM into its local cache and performs calculations using the cached copy.

### 9. Starvation

- **Definition:** A situation where a low-priority task waits indefinitely for access to shared resources because higher-priority tasks are constantly being scheduled first.
- **Mechanism:** Usually results from unfair thread scheduling policies or priority inversion.
- **System Impact:** The system remains functional, but specific low-priority tasks never complete.

### 10. Starvation in a Fintech System

- **Scenario:** Payment Gateway Processing Priorities.
- **Setup:** High-value transactions (high fee revenue) are prioritized over low-value transactions (low fee revenue).
- **Starvation Occurrence:**
    - On payroll day, the system is flooded with high-value transfers.
    - Worker threads constantly handle high-priority tasks, leaving low-priority tasks in a queue.

### 11. Memory Visibility Issues

- **Example:** 
    - Thread A updates a variable `counter` and stores it in its local cache.
    - Thread B reads the same variable from main memory before Thread A flushes its cache.
- **Solution:** Use `volatile` or synchronization to ensure that changes made by one thread are visible to others.

### 12. Instruction Reordering Issues

- **Example:** 
    - Code: `a = 1; flag = true;`
    - CPU reorders to: `flag = true; a = 1;`
- **Impact:** Thread B might read `flag == true` but see the stale value of `a`.
- **Solution:** Use `volatile` or synchronization to prevent unwanted reordering.

### 13. Java Memory Model (JMM)

- **Definition:** A set of rules and guarantees for thread interactions through memory in Java.
- **Purpose:** Ensures that optimizations do not violate expected behavior, particularly in multithreaded environments.
- **Key Concepts:**
    - Atomicity
    - Visibility
    - Ordering

### 14. Happens-Before Rules

- **Monitor Lock Rule:** Unlocking a `synchronized` block happens-before another thread locking the same monitor.
- **Volatile Variable Rule:** Writing to a `volatile` variable happens-before any subsequent read of that variable.
- **Thread Start Rule:** Calling `Thread.start()` happens-before the actual code inside the thread's `run()` method executes.

### 15. Guarantees in JMM

- **Atomicity:** Ensures operations are indivisible.
    - **Atomic Operations in Java:**
        - Reading or writing reference variables.
        - Reading or writing primitive variables except `long` and `double`.
- **Visibility:** Ensures changes made by one thread are visible to others.
    - **Tools:** `volatile`, `synchronized`, `Lock`.
- **Ordering:** Ensures instructions stay in the intended sequence.
    - **Tools:** `volatile`, `synchronized`.
