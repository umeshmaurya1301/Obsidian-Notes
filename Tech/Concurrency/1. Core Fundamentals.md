Covers Roadmap section 1. This is the vocabulary note — every term the rest of the roadmap assumes you already own. Nothing here is about *writing* concurrent code; it's about knowing exactly **what goes wrong** when threads share state, and why.

> [!info] The through-line of this note
> Three separate stories that people keep mixing up:
>
> 1. **Structure** (§1–§4) — what a thread *is* and how the OS runs many of them on few cores. Concurrency vs parallelism, process vs thread, lifecycle, context switching.
> 2. **Correctness failures** (§5–§8) — what breaks when threads share mutable state. Race conditions and critical sections, then the three ways progress dies: deadlock, livelock, starvation.
> 3. **The machine underneath** (§9–§12) — why a correct-looking program still fails. CPU caches hide your writes (visibility), compilers reorder your code (ordering), and the **JMM** is the contract that tells you when you're safe (happens-before).
>
> One line to anchor everything: **a concurrency bug is either two threads interleaving where they shouldn't (§5), or one thread never seeing what another wrote (§9).** Every tool in [[3. Synchronization]] exists to fix one of those two.

### 1. Concurrency vs Parallelism

**Concurrency** means handling multiple tasks by allowing each to **make progress**, even if only one is actually running at any given instant.

A single CPU core achieves this by **switching rapidly between tasks**. The switching is so fast it looks simultaneous.

```text
Task A
   ↓
Task B
   ↓
Task C
   ↓
Task A
```

Only one task runs at a time, but all of them advance.

**Parallelism** means executing multiple tasks **at exactly the same instant**. This needs multiple cores.

```text
Core 1 → Request A
Core 2 → Request B
Core 3 → Request C
```

| Concurrency | Parallelism |
|---|---|
| Multiple tasks make progress | Multiple tasks execute simultaneously |
| Works on a single core | Requires multiple cores |
| Improves resource utilisation | Improves speed of CPU-bound work |
| A **design** property | An **execution** property |

**Real backend example.** Your payment service receives hundreds of HTTP requests. While request A waits on the database, the CPU starts processing request B instead of sitting idle. That's concurrency — and it's where nearly all of your throughput comes from, because a typical backend request spends most of its life *waiting* (DB, Redis, the bank's API), not computing.

> [!info] Interview points
> - Concurrency can exist **without** parallelism (one core, many tasks).
> - Parallelism is built **on top of** concurrency by adding execution units.
> - Backend apps benefit mostly from **concurrency**, because they're I/O-bound. Data processing and encoding benefit from **parallelism**, because they're CPU-bound.
> - Rob Pike's line, worth quoting: *"Concurrency is about dealing with lots of things at once. Parallelism is about doing lots of things at once."*

### 2. Process vs Thread

A **process** is an independent running program — Chrome, IntelliJ, MySQL, your Spring Boot app. Each has its own memory space and OS resources. If one crashes, the others keep running.

A **thread** is the smallest unit of execution **inside** a process. One process can hold many.

```text
Spring Boot Process
├── Main Thread
├── Tomcat Request Threads (×200)
├── Scheduler Thread
├── Kafka Consumer Threads
└── HikariCP housekeeping Thread
```

All of these live in the same process, and that's the whole point — and the whole danger.

**What threads share:**

- Heap memory (all your objects)
- Static variables
- Open files and sockets
- The database connection pool

**What each thread owns privately:**

- Its own **stack**
- Its own **program counter**
- Its **local variables**

> [!tip] The single most useful consequence
> **Local variables are automatically thread-safe.** They live on the thread's own stack, so no other thread can even reach them. Every concurrency bug you will ever write involves something on the **heap** — a field, a static, a shared collection. When debugging, ask first: *what is shared?*

| Process | Thread |
|---|---|
| Independent execution unit | Execution unit inside a process |
| Separate memory | Shared process memory |
| Expensive to create | Lightweight |
| Strong isolation | Almost no isolation |

> [!info] Interview points
> - Threads are cheaper than processes precisely **because** they share memory — no separate address space to set up.
> - Inter-thread communication is fast (shared heap); inter-process communication needs pipes, sockets or shared-memory segments.
> - A platform thread still isn't free: roughly **1 MB of stack** each, plus OS scheduling cost. That's why we pool them ([[4. Executors and Thread Pools]]) and why **virtual threads** exist.

### 3. Thread Lifecycle — the six states

Java models a thread's life with six states (`Thread.State`):

```text
      NEW
       ↓  start()
   RUNNABLE  ←──────────────┐
       ↓                    │
BLOCKED / WAITING / TIMED_WAITING
       ↓
   TERMINATED
```

| State | Meaning | How you get there |
|---|---|---|
| `NEW` | Created, not started | `new Thread()` |
| `RUNNABLE` | Ready to run or running | `start()` |
| `BLOCKED` | Waiting for a **monitor lock** | hit a `synchronized` block someone else holds |
| `WAITING` | Waiting **indefinitely** for a signal | `wait()`, `join()`, `LockSupport.park()` |
| `TIMED_WAITING` | Waiting **with a deadline** | `sleep()`, `wait(t)`, `join(t)` |
| `TERMINATED` | Finished (returned or threw) | — |

> [!warning] Two details interviewers probe
> - Java has **no `RUNNING` state**. `RUNNABLE` covers both "on the CPU right now" and "ready and queued". Java deliberately doesn't distinguish — that's the OS scheduler's business.
> - `BLOCKED` means one specific thing: **waiting for a monitor lock** (`synchronized`). A thread waiting on a `ReentrantLock` shows as `WAITING`, not `BLOCKED`, because `Lock` is built on `LockSupport.park()`, not the monitor. This trips people up when reading thread dumps.
>
> Also: a terminated thread **cannot be restarted**. Calling `start()` twice throws `IllegalThreadStateException`.

Reading this in production: `jstack <pid>` prints every thread's state. Lots of threads `BLOCKED` on the same lock → contention. Lots `WAITING` on a pool queue → you're starved of work or of connections ([[11. Transaction Boundaries]]).

Full mechanics of starting and coordinating threads are in [[2. Java Thread Basics]].

### 4. Context Switching

A core executes one thread at a time. To run many, the OS switches between them:

```text
Thread A
   ↓
Thread B
   ↓
Thread C
   ↓
Thread A
```

On each switch the OS **saves** the current thread's state (registers, program counter, stack pointer) and **restores** another's, so execution resumes exactly where it paused.

This buys responsiveness and CPU utilisation — but it is **not free**:

- Direct cost: kernel-mode transition, saving/restoring registers (~1–10 µs)
- Indirect cost, usually bigger: the new thread's data isn't in the **CPU cache**, so it stalls on memory. Cache and TLB pollution.

> [!warning] More threads ≠ more speed
> This is the mistake behind half of all bad thread-pool configs. Past the point where the CPU is saturated, adding threads only adds switching overhead and cache misses — throughput goes **down** while latency goes up.
>
> Rough sizing: **CPU-bound work** → threads ≈ number of cores. **I/O-bound work** → more threads help, because they're blocked (not switching) most of the time. Same reasoning as connection-pool sizing.

> [!info] Interview points
> - Excessive context switching makes an application slower, not faster.
> - `vmstat` (`cs` column) or `pidstat -w` shows switch rate; a spike with no throughput gain means you're thrashing.
> - This is exactly the problem **virtual threads** solve: parking a virtual thread is a cheap JVM-level operation, not an OS context switch.

### 5. Race Condition

A race condition happens when multiple threads access and modify shared data without synchronisation, and **the result depends on the order in which they happen to run**.

The canonical example:

```java
count++;
```

One line of Java, but three operations:

```text
Read
  ↓
Increment
  ↓
Write
```

Two threads can interleave inside those three steps.

**Wallet debit, two concurrent requests of 100 each on a balance of 1000:**

Expected:

```text
1000
  ↓
 900
  ↓
 800
```

Actual:

```text
1000
  ↓
 900
```

Both threads read `1000`, both computed `900`, both wrote `900`. One debit **vanished** — and in a payments system, that's real money. This is the **lost update**, and you'll meet it again at the database level in [[9. Database Concurrency]].

**Fixes:** `synchronized` · `Lock` · `AtomicInteger` (all in [[3. Synchronization]]).

> [!info] Interview points
> - `count++` is **not atomic**. Neither is `count += 1`, nor `count = count + 1`.
> - Making it `volatile` does **not** fix it — `volatile` gives visibility, not atomicity (§11).
> - Nearly every concurrency bug reduces to **shared mutable state**. Remove the sharing (locals, `ThreadLocal`, copies) or remove the mutability (immutable objects) and the bug cannot exist.
> - The other shape of race is **check-then-act**: `if (!map.containsKey(k)) map.put(k, v);` — correct-looking, still broken.

### 6. Critical Section

The **critical section** is the region of code that touches shared mutable data. Only one thread may be inside it at a time.

```java
synchronized (lock) {
    balance -= amount;
}
```

**Keep critical sections small, fast, and focused only on the shared data.**

> [!warning] Never put slow work inside a lock
> ```java
> synchronized (lock) {
>     balance -= amount;
>     bankApi.notifyDebit(txn);   // ❌ 2-second HTTP call, lock held throughout
> }
> ```
> Every other thread that needs this lock is now blocked for two seconds. Do the external call **outside** the lock. This is the same rule as "no network calls inside `@Transactional`" ([[11. Transaction Boundaries]]) — a held lock is a held lock, whether it's a JVM monitor or a database row.

Large critical sections increase lock contention, increase waiting time, and reduce throughput — they turn your concurrent program back into a sequential one. **Amdahl's law** is the formal version: the serial fraction of your program caps your maximum speedup, no matter how many cores you add.

### 7. Deadlock

Two or more threads wait for each other forever. Nobody proceeds.

```text
Thread A
holds Lock 1
   ↓
waiting for Lock 2

------------------

Thread B
holds Lock 2
   ↓
waiting for Lock 1
```

**All four Coffman conditions must hold** for a deadlock to be possible:

| Condition | Meaning |
|---|---|
| **Mutual exclusion** | A resource can be held by only one thread |
| **Hold and wait** | A thread holds one resource while waiting for another |
| **No preemption** | A resource can't be forcibly taken away |
| **Circular wait** | A cycle exists in the wait-for graph |

Break **any one** of them and deadlock becomes impossible. In practice you break the last one.

**Prevention:**

- **Acquire locks in a consistent global order** — the simplest and most effective fix
- Keep lock duration short
- Use `tryLock()` with a timeout so you fail instead of hanging
- Hold fewer locks; better, hold one

```java
// wallet-to-wallet transfer — always lock the lower id first
Object first  = fromId < toId ? fromLock : toLock;
Object second = fromId < toId ? toLock   : fromLock;

synchronized (first) {
    synchronized (second) {
        // transfer
    }
}
```

Without that ordering, `transfer(A→B)` and `transfer(B→A)` running concurrently deadlock roughly whenever they overlap.

> [!info] Interview points
> - The JVM will **not** detect or break a deadlock for you — the threads just hang forever. (A database *will* detect it and kill one transaction — see [[9. Database Concurrency]].)
> - Diagnose with `jstack`: it prints "Found one Java-level deadlock" with both threads and both locks.
> - Consistent lock ordering is the answer interviewers want first; `tryLock` with timeout is the good follow-up.

### 8. Livelock and Starvation

**Livelock** — threads are *active* and constantly reacting to each other, but no useful work completes.

```text
Thread A retries
   ↓
Thread B retries
   ↓
Both retry again
   ↓
Repeat forever
```

Unlike deadlock, nothing is blocked. CPU sits at 100% and throughput is zero. The classic real-world version: two people stepping aside in a corridor, in sync, forever.

The realistic backend version is **two threads that both `tryLock`, both fail, both release and retry at the same instant** — over and over.

**Fix:** randomised backoff (**jitter**). Same fix as retry storms in [[11. Transaction Boundaries]].

**Starvation** — a thread waits indefinitely because other threads keep getting the resource first.

```text
High priority thread
   ↓
High priority thread
   ↓
High priority thread
   ↓
Low priority thread never runs
```

**Fintech example.** Your payment gateway prioritises high-value transfers (higher fee revenue) over low-value ones. On payroll day, the system floods with high-value transactions. Worker threads handle them continuously, and low-value transactions sit in the queue for hours. The system looks perfectly healthy — CPU fine, no errors, no deadlock — but a subset of customers is simply never served.

**Fixes:** fair locks (`new ReentrantLock(true)`), aging (raise priority the longer something waits), or separate pools per priority class so one class can't monopolise the other's threads.

| Problem | What's happening | Progress |
|---|---|---|
| **Deadlock** | Everyone blocked, waiting in a cycle | Nobody progresses |
| **Livelock** | Everyone active, reacting to each other | Nobody progresses |
| **Starvation** | Resource always given to others | Some progress, one waits forever |

### 9. CPU Cache and Memory Visibility

Now the part that makes correct-looking code fail.

**The problem:** main memory (RAM) is slow compared to the CPU. So every core has its own **L1/L2 cache** (and a shared L3), holding copies of frequently used data. A thread reads a variable into its core's cache and works on the **cached copy**.

```text
Core 1                     Core 2
  L1: running = true         L1: running = true
       ↓ writes false             ↓ still reads true
  L1: running = false        L1: running = true    ← stale!
       ↓ (not yet flushed)
        RAM: running = true
```

**Memory visibility** is the question: *when thread A writes a shared variable, is thread B guaranteed to see it?*

Without synchronisation, **no**. Thread B may keep reading a stale cached value indefinitely.

The classic bug:

```java
private boolean running = true;      // ❌ not volatile

public void run() {
    while (running) { process(); }   // may never see the update — infinite loop
}

public void stop() {
    running = false;                 // written by another thread
}
```

The JIT compiler is even allowed to hoist the read out of the loop entirely, turning it into `while (true)`.

**Fix:**

```java
private volatile boolean running = true;   // ✅
```

`volatile` forces the write to go to main memory and the read to come from it, bypassing the stale cache.

> [!warning] `volatile` gives you visibility and ordering — **not** atomicity
> ```java
> private volatile int count;
> count++;    // ❌ still broken — read-modify-write is three steps
> ```
> For a flag, `volatile` is exactly right. For a counter, you need `AtomicInteger` or a lock. Full treatment in [[3. Synchronization]].

### 10. Instruction Reordering

The compiler, the JIT, and the CPU itself are all allowed to **silently rearrange your instructions** for performance.

The only rule they must obey: *the reordering must not change the result of a **single-threaded** execution.* Nobody promises anything about other threads.

```java
a = 1;            // your code
flag = true;
```

```java
flag = true;      // what the CPU may actually execute
a = 1;
```

Single-threaded, identical outcome. But if thread B does:

```java
if (flag) {
    use(a);       // ❌ may see a == 0
}
```

then B can observe `flag == true` while `a` is still stale. This is exactly how the naive double-checked-locking singleton was broken for years — the reference was published before the constructor finished.

**Fix:** `volatile` or `synchronized`. Both insert **memory barriers** that forbid the reordering across them.

> [!tip] Visibility and ordering are two halves of one problem
> §9 is "did the write get out?" §10 is "did the writes get out **in the order I wrote them**?" Both are invisible in testing on your laptop (x86 has a fairly strong memory model), and both show up under load on a different CPU architecture. That's why we don't reason about caches directly — we reason about the **JMM**.

### 11. The Java Memory Model (JMM)

The JMM is the **formal contract** defining how threads interact through memory. It's what lets you write portable concurrent code without knowing whether you're on x86 or ARM — it specifies the behaviour of `volatile`, `synchronized` and `final`, and the JVM implements it with whatever barriers that particular CPU needs.

It gives three distinct guarantees. **Keep them separate — this is the most common interview confusion.**

**Atomicity** — an operation happens completely or not at all.

| Atomic in Java | Not atomic |
|---|---|
| Reading/writing a reference | `i++` (read-modify-write) |
| Reading/writing any primitive **except** `long`/`double` on some 32-bit JVMs | Check-then-act: `if (a == 1) a = 2;` |
| Reading/writing any `volatile`, including `long`/`double` | Anything compound |

**Visibility** — a change made by one thread becomes observable to others.
Tools: `volatile` · `synchronized` · `Lock` · `final` (safe publication)

**Ordering** — operations are not reordered across a barrier.
Tools: `volatile` · `synchronized`

**The comparison table** (memorise this one — it's asked constantly):

| Feature | `volatile` | `synchronized` | `AtomicInteger` |
|---|---|---|---|
| **Visibility** | ✅ Yes | ✅ Yes | ✅ Yes |
| **Ordering** | ✅ Yes | ✅ Yes | ✅ Yes |
| **Atomicity** | ❌ **No** | ✅ Yes | ✅ Yes (via CAS) |
| **Blocking** | Never | Yes | Never (lock-free retry) |

Read the table as one sentence: **everything gives you visibility; only locks and atomics give you atomicity.**

### 12. Happens-Before

The happens-before relationship is how the JMM lets you reason about visibility **without** thinking about caches or barriers at all.

> If **A happens-before B**, then everything A did is guaranteed visible to B, and B cannot be reordered to run first.

It's a *guarantee*, not a description of timing — "A happened earlier on the clock" means nothing without a happens-before edge.

**The rules you must know:**

| Rule | Edge it creates |
|---|---|
| **Program order** | Within one thread, each statement happens-before the next |
| **Monitor lock** | Releasing a lock happens-before the next acquisition of **the same** lock |
| **Volatile** | A write to a `volatile` happens-before every subsequent read of it |
| **Thread start** | Everything before `t.start()` happens-before anything inside the thread |
| **Thread join** | Everything in the thread happens-before `t.join()` returns |
| **Transitivity** | A → B and B → C implies A → C |

The monitor and volatile rules are the load-bearing ones — and note that the monitor rule only applies **on the same lock**. Two threads synchronising on different objects create no edge at all, which is why "I added `synchronized`" is not automatically a fix.

Transitivity is what makes it usable in practice:

```java
// Thread A
data = loadFromDb();      // 1
ready = true;             // 2  (volatile write)

// Thread B
if (ready) {              // 3  (volatile read)
    use(data);            // 4  ✅ guaranteed to see the data
}
```

`1 → 2` (program order), `2 → 3` (volatile rule), `3 → 4` (program order), therefore `1 → 4`. Thread B sees `data` even though `data` itself isn't volatile. **One volatile write can safely publish a whole object graph** — that's the trick behind safe publication.

### 13. Interview Quick-Fire

| Question | Sharp answer |
|---|---|
| Concurrency vs parallelism? | Concurrency = many tasks make progress (works on one core); parallelism = many tasks run at the same instant (needs many cores). |
| Process vs thread? | Process = own memory, strong isolation, expensive. Thread = shares the process heap, owns only its stack, cheap. |
| Why are local variables thread-safe? | They live on the thread's own stack — unreachable by any other thread. |
| Is `count++` atomic? | No — read, increment, write. Two threads can interleave and lose an update. |
| Does `volatile` fix `count++`? | No. `volatile` gives visibility and ordering, not atomicity. Use `AtomicInteger` or a lock. |
| Java thread states? | NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED. There is no RUNNING state. |
| `BLOCKED` vs `WAITING`? | `BLOCKED` = waiting for a monitor lock (`synchronized`). `WAITING` = waiting for a signal (`wait`, `join`, `park`) — including `ReentrantLock`. |
| Can you restart a terminated thread? | No — `start()` twice throws `IllegalThreadStateException`. |
| Is more threads always faster? | No. Past CPU saturation, context switching and cache misses reduce throughput. CPU-bound ≈ cores; I/O-bound can go higher. |
| What is a race condition? | Unsynchronised access to shared mutable state where the outcome depends on thread interleaving. |
| Four conditions for deadlock? | Mutual exclusion, hold-and-wait, no preemption, circular wait — break any one. |
| How do you prevent deadlock? | Consistent global lock ordering; short lock hold times; `tryLock` with timeout; hold fewer locks. |
| How do you detect a deadlock in production? | `jstack` — it explicitly reports "Found one Java-level deadlock". The JVM won't resolve it for you. |
| Deadlock vs livelock vs starvation? | Deadlock: all blocked, no progress. Livelock: all active, no progress. Starvation: others progress, one waits forever. |
| What is memory visibility? | Whether thread B is guaranteed to see thread A's write — CPU caches can hide it indefinitely. |
| What is instruction reordering? | The compiler/JIT/CPU rearranging instructions; legal if single-threaded output is unchanged, but it can break multithreaded assumptions. |
| What is the JMM? | The formal contract defining how threads interact via memory — atomicity, visibility, ordering, and the semantics of `volatile`/`synchronized`/`final`. |
| What is happens-before? | A guarantee that if A happens-before B, all of A's memory effects are visible to B and B can't be reordered ahead of it. |
| Name three happens-before rules. | Unlock → subsequent lock of the same monitor; volatile write → subsequent read; `t.start()` → code in the thread (also `join()`, program order, transitivity). |
| `volatile` vs `synchronized` vs `AtomicInteger`? | All three give visibility and ordering. Only `synchronized` and `AtomicInteger` give atomicity — `synchronized` by blocking, `AtomicInteger` lock-free via CAS. |
