### **1. Concurrency vs. Parallelism**

- **Concurrency:**
    
    - **Definition:** The composition of independently executing tasks. It is a program design structure.
        
    - **Execution:** Tasks make overlapping progress. The CPU scheduler multiplexes execution time across multiple tasks (time-slicing).
        
    - **Goal:** Maximize CPU utilization and responsiveness by masking latency (e.g., doing other work while waiting for I/O).
        
- **Parallelism:**
    
    - **Definition:** The simultaneous execution of multiple computations. It is a hardware execution property.
        
    - **Execution:** Tasks run at the exact same physical time on distinct processing units (multi-core CPUs or GPUs).
        
    - **Goal:** Increase raw computational throughput and decrease execution time for CPU-bound tasks.
        

---

### **2. Process vs. Thread**

- **Process:**
    
    - **Architecture:** An independent execution environment managed by the OS.
        
    - **Memory:** Highly isolated. Each process has its own private virtual address space (code, data, heap, and stack).
        
    - **Overhead:** Heavyweight. Creation, termination, and context switching are resource-intensive due to memory page table setups.
        
    - **Communication:** Inter-Process Communication (IPC) is complex and relatively slow (requires pipes, sockets, or OS-managed shared memory).
        
- **Thread:**
    
    - **Architecture:** The smallest sequence of programmed instructions managed by an OS scheduler. Exists _within_ a process.
        
    - **Memory:** Shared. Threads within the same process share the heap, data segment, and code segment. Each thread maintains its own private Program Counter (PC), CPU registers, and Stack.
        
    - **Overhead:** Lightweight. Faster to create, destroy, and switch because memory mapping remains the same.
        
    - **Communication:** Extremely fast via shared memory, but requires strict synchronization mechanisms (mutexes, locks) to prevent race conditions and data corruption.
        

---

### **3. Thread Lifecycle (OS Level)**

- **NEW:** The Thread Control Block (TCB) is allocated in memory, but the thread has not been submitted to the OS scheduler yet.
    
- **READY (Runnable):** The thread is loaded into the OS's Ready Queue. It has all required resources except for CPU time and is waiting for the scheduler to dispatch it.
    
- **RUNNING:** The scheduler has assigned a CPU core to the thread. The CPU is actively fetching and executing its instructions.
    
- **BLOCKED (Waiting):** The thread is suspended and removed from the CPU. This occurs when it requests an I/O operation, waits on a synchronization primitive (like a blocked lock), or is explicitly put to sleep. It cannot consume CPU cycles in this state.
    
- **TERMINATED:** The thread has completed its execution path or was forcefully killed. The OS reclaims its allocated resources (stack and TCB).

### **4. Context Switching**

- **Definition:** The OS procedure of storing the state of an active thread/process and restoring the state of a different one, allowing multiple threads to share a single CPU.
    
- **The Mechanism:**
    
    1. A hardware interrupt or system call triggers the OS scheduler.
        
    2. The OS saves the active thread's context (Program Counter, CPU registers, stack pointer) into its Thread Control Block (TCB).
        
    3. The scheduler selects the next thread from the Ready Queue.
        
    4. The OS loads the saved context from the new thread's TCB back into the physical CPU registers.
        
    5. Execution resumes for the new thread.
        
- **Performance Impact:** Context switching is pure overhead; the CPU does no productive application work while switching. Frequent switching (thrashing) degrades performance severely due to CPU cache invalidation (TLB misses and cache misses when the new thread accesses its memory).



### **5. Race Condition**

- **Definition:** A defect where a system's output becomes non-deterministic, meaning the result depends on the unpredictable order in which the operating system schedules threads to run.
    
- **Root Cause:** Occurs when multiple threads concurrently access shared, mutable state (memory), and at least one of the threads alters that state without proper synchronization.
    
- **Non-Atomic Operations:** They frequently occur during "Read-Modify-Write" cycles (like incrementing a counter: `x = x + 1`). Because this involves three distinct CPU instructions, a context switch can happen in the middle, causing threads to read stale data and overwrite each other's progress.


### **6. Critical Section**

- **Definition:** A specific, identifiable block of code within a program where shared resources (variables, data structures, files, or connections) are actively accessed or modified.
    
- **Mutual Exclusion:** To prevent race conditions, a critical section must enforce mutual exclusion. This guarantees that only one thread can execute within that boundary at any given time.
    
- **Synchronization:** This is typically implemented using concurrency primitives like Locks, Mutexes, or Semaphores. Once a thread enters the critical section, it acquires the lock; other threads attempting to enter are blocked until the lock is released.



### **7. Deadlock**

- **Definition:** A terminal state where two or more threads are permanently blocked, unable to proceed, because they are trapped in a cycle of dependencies.
    
- **Mechanism (Circular Wait):** Thread A acquires Resource 1 and waits for Resource 2. Simultaneously, Thread B acquires Resource 2 and waits for Resource 1. Neither thread will release its current resource until it gets the next one.
    
- **System Impact:** The deadlocked threads remain indefinitely in a blocked state, consuming zero CPU cycles but holding onto memory and locks, effectively freezing that part of the application.
- ### **Deadlock in a Fintech System**

- **The Scenario:** Peer-to-Peer (P2P) Money Transfer.
    
- **The Setup:** A backend service uses pessimistic database locking (`SELECT ... FOR UPDATE`) to prevent race conditions when updating account balances.
    
- **How the Deadlock Happens:**
    
    - **Transaction 1:** User A initiates a $50 transfer to User B. The system locks User A's database row to deduct funds.
        
    - **Transaction 2:** At the exact same millisecond, User B initiates a $20 transfer to User A. The system locks User B's database row to deduct funds.
        
    - **The Crash:** Transaction 1 attempts to lock User B's row to deposit the $50, but it's blocked by Transaction 2. Transaction 2 attempts to lock User A's row to deposit the $20, but it's blocked by Transaction 1.
        
- **The Result:** Both database connections are locked in a circular wait forever. The system freezes those specific threads, the database throws a `DeadlockFoundException`, and both users see a "Transaction Failed/Timeout" error.



### **8. Livelock**

- **Definition:** A concurrency failure where threads are not blocked, but are trapped in a continuous loop of changing states without making any functional progress.
    
- **Mechanism:** It often occurs when threads are programmed to be overly "polite" to avoid deadlocks. If two threads detect a conflict, they both back off and retry. If their retry timing is identical, they will continuously collide, back off, and retry infinitely.
    
- **System Impact:** Unlike a deadlock, livelocked threads are actively running. This leads to high CPU utilization (busy-waiting or thrashing) while yielding zero productive output.
- ### **Livelock in a Fintech System**

- **The Scenario:** High-Frequency Trading or Flash Sales (Optimistic Locking).
    
- **The Setup:** Instead of locking the database rows (which slows things down), a wallet service uses Optimistic Locking with a "version" column. If a thread reads version 1, does some math, and tries to save, it only succeeds if the database is still at version 1. If it fails, the application is programmed to politely catch the `OptimisticLockException`, reload the fresh data, and retry.
    
- **How the Livelock Happens:**
    
    - Thousands of micro-transactions (e.g., automated dividend payouts or cashback rewards) try to update the exact same corporate master wallet simultaneously.
        
    - Thread A reads the balance (version 10). Thread B reads the balance (version 10).
        
    - Thread A updates the balance to version 11.
        
    - Thread B tries to update, sees version 11, fails, reloads the new balance, and tries again.
        
    - Before Thread B can save, Thread C sneaks in and updates it to version 12. Thread B fails again.
        
- **The Result:** The threads are never blocked—they are working furiously, consuming 100% CPU, constantly reading data, doing math, and throwing/catching exceptions. However, because of the constant collisions, no actual database commits are successfully making progress.
    



### **9. Starvation**

- **Definition:** A state where a runnable thread is perpetually bypassed and denied the resources it needs (such as CPU time or access to a lock) to execute its critical section.
    
- **Mechanism:** This is usually the result of an unfair thread scheduling policy or priority inversion. If a system constantly prioritizes incoming high-priority tasks, a low-priority background thread may wait indefinitely in the queue.
    
- **System Impact:** The system as a whole remains functional and active, but the specific starved thread or task will never complete.
- ### **Starvation in a Fintech System**

- **The Scenario:** Payment Gateway Processing Priorities.
    
- **The Setup:** A payment processor handles both large corporate wire transfers (high fee revenue) and small merchant transactions like coffee purchases (low fee revenue). To maximize efficiency, the system routes tasks to a Thread Pool where high-value transactions are placed in a high-priority queue, and low-value transactions are placed in a low-priority queue.
    
- **How the Starvation Happens:**
    
    - It is the last Friday of the month (payroll day). The system is absolutely flooded with millions of high-value corporate salary transfers.
        
    - The worker threads constantly pull from the high-priority queue because it is never empty.
        
    - Meanwhile, thousands of regular users buying their morning coffee are placed in the low-priority queue.
