# Special Classes And Modifiers

---

## Short Notes

---

### 1. `final` Class

- Cannot be subclassed — the end of that inheritance branch
- Reasons: enforce immutability, protect security-sensitive logic, signal "complete by design"
- Minor JIT benefit — no override possible, so calls devirtualise and inline
- JDK examples: `String`, every wrapper class, `Math`

---

### 2. `final` Method

- Cannot be overridden; the implementation is locked at that point in the hierarchy
- Use to protect an **invariant sequence** — the Template Method pattern
- Also the safe way to call a method from a constructor (an override can't hijack it)
- No vtable override possible → effectively statically resolved

---

### 3. Template Method With `final`

```java
abstract class PaymentTemplate {
    final void execute(long amount) {   // the FLOW is fixed
        validate(amount);
        process(amount);
        log(amount);
    }
    abstract void validate(long amount);   // the STEPS are customisable
    abstract void process(long amount);
    void log(long amount) { ... }
}
```

---

### 4. `final` Variable — Primitive

- Assigned exactly once, then never reassigned
- `final int MAX_RETRIES = 3;` → reassignment is a compile error
- A `static final` primitive with a literal initialiser is a **compile-time constant** (inlined)

---

### 5. `final` Variable — Reference (The Big Trap)

```java
final List<String> names = new ArrayList<>();
names.add("Umesh");            // ✅ mutating the OBJECT is fine
names = new ArrayList<>();     // ❌ reassigning the REFERENCE is not
```

- `final` locks the **reference**, never the object
- Necessary but **not sufficient** for immutability

---

### 6. `final` Field

- Must be **definitely assigned exactly once** — at declaration or in every constructor path
- Miss one path, or assign twice → compile error
- This is the mechanism guaranteeing the field never changes post-construction
- JMM bonus: `final` fields set in a constructor are **safely published** to other threads

---

### 7. `final` Local / Parameter, and Effectively Final

- `final` parameter can't be reassigned inside the method
- A local captured by a lambda or anonymous class must be `final` or **effectively final**
- Effectively final = never reassigned after initialisation, even without the keyword
- Reason: the lambda may outlive the method, so it captures a **frozen value**, not a live variable

---

### 8. Enums — The Basics

- A type-safe fixed set of constants; each constant is a **singleton instance**
- `==` comparison is safe and idiomatic (one object per constant)
- Beats `public static final int`: type safety, behaviour, `switch`, readable `toString()`
- `PaymentStatus status = 5;` can't even be written

---

### 9. Enums Are Full Classes

```java
enum PaymentMethod {
    UPI(0.0, "Instant"), CARD(2.5, "1-2 business days");

    private final double feePercent;
    PaymentMethod(double fee, String settlement) { ... }   // implicitly private
    long feeOn(long amount) { ... }
}
```

- Fields, constructors, methods, interfaces — all allowed
- Constant-specific bodies (`SUCCESS { ... }`) compile to anonymous subclasses

---

### 10. Enum Built-ins

- `values()` — all constants in declaration order (returns a **clone** each call)
- `valueOf("SUCCESS")` — parse by exact name; throws `IllegalArgumentException`
- `name()` — the declared name | `ordinal()` — the position, **don't build logic on it**
- `EnumMap` / `EnumSet` — array-backed, far faster than `HashMap`/`HashSet`

---

### 11. Enum Singleton

```java
enum ConfigManager {
    INSTANCE;
    private final Map<String, String> config = new HashMap<>();
}
```

- The JVM guarantees one instance — serialization-safe and reflection-safe for free
- *Effective Java*'s recommended Singleton implementation

---

### 12. Records (Java 16+)

- One line replaces a whole immutable data class
- Auto-generates: canonical constructor, accessors, `equals`, `hashCode`, `toString`
- Accessors are `x()`, **not** `getX()` — a common trap
- Implicitly `final`, implicitly extends `Record`, **can** implement interfaces

---

### 13. Record Compact Constructor

```java
public record Money(long amountPaise, String currency) {
    public Money {                                   // no parameter list, no assignments
        if (amountPaise < 0) throw new IllegalArgumentException();
        currency = currency.toUpperCase();           // normalise before implicit assignment
    }
}
```

- Validation and normalisation; the implicit `this.x = x` runs **after** your body

---

### 14. Records vs Classes

| Use a record when | Use a class when |
| --- | --- |
| Fixed snapshot: DTO, API payload, event | State evolves over the object's lifetime |
| Value-based identity | Identity-based, accumulating state |
| No behaviour beyond the data | JPA `@Entity`, needs inheritance |

- A record models a **value**; a class models **evolving state**

---

### 15. Sealed Classes (Java 17+)

```java
public sealed class PaymentMethod permits UpiPayment, CardPayment, NetBankingPayment { }
```

- Explicitly whitelists who may extend — a **closed** hierarchy
- Every permitted subclass must be `final`, `sealed`, or `non-sealed`
- `non-sealed` reopens that branch to anyone

---

### 16. Sealed + Pattern Switch = Exhaustiveness

```java
double area(Shape s) {
    return switch (s) {
        case Circle c -> Math.PI * c.radius() * c.radius();
        case Square q -> q.side() * q.side();
        // no default needed — the compiler knows the full set
    };
}
```

- Add a permitted subtype and forget a `switch` → **compile error**, not a production surprise

---

### 17. Feature Summary

| Feature | Since | Purpose |
| --- | --- | --- |
| `final` class/method/variable | Java 1 | Lock a class, a method, a binding |
| Enums | Java 5 | Type-safe fixed set of instances |
| Records | Java 16 | Boilerplate-free immutable data carriers |
| Sealed | Java 17 | Closed hierarchy, exhaustive `switch` |

---

# Detailed Explanation

---

## `final` Class

A `final` class cannot be extended.

```java
final class PasswordHasher {
    String hash(String password) { /* secure hashing */ }
}

class WeakHasher extends PasswordHasher { }   // ❌ cannot inherit from final class
```

Four reasons to reach for it:

**1. Enforce immutability.** A subclass could add mutable state or override a method to break an invariant, and callers holding a base-typed reference would never know. `final` closes that door — it's rule one of the immutability checklist in [[11. Immutability]].

**2. Security.** Without `final`, someone can subclass `PasswordHasher`, override `hash()` with a weaker algorithm, and pass their instance anywhere a `PasswordHasher` is expected — the type check still succeeds. `final` makes the implementation the only implementation.

**3. Design intent.** Utility classes and value objects where no meaningful subclass exists. Saying so in the type system is better than saying so in a comment.

**4. Performance (minor).** The JIT knows no override can exist, so calls devirtualise and inline more aggressively. A real effect, but a secondary reason — modern JITs speculate well even without it.

The JDK's own examples — `String`, every wrapper class, `Math` — are final for exactly reasons 1 and 2.

---

## `final` Method

A `final` method cannot be overridden. Use it when the whole class needn't be closed, but one method must be.

```java
class Vehicle {
    final void startEngine() {          // locked
        System.out.println("Standard engine start sequence");
    }

    void accelerate() {                 // open
        System.out.println("Accelerating");
    }
}

class Car extends Vehicle {
    void startEngine() { }              // ❌ cannot override a final method
    @Override void accelerate() { }     // ✅
}
```

### The Template Method pattern

The most common legitimate use: fix the **algorithm's shape** while leaving the **steps** open.

```java
abstract class PaymentTemplate {

    final void executePayment(long amountPaise) {   // ← final: the SEQUENCE is a business invariant
        validate(amountPaise);
        process(amountPaise);
        logTransaction(amountPaise);
    }

    abstract void validate(long amountPaise);       // subclasses fill these in
    abstract void process(long amountPaise);

    void logTransaction(long amountPaise) {         // overridable default
        System.out.println("Logged: " + amountPaise);
    }
}
```

A subclass can define what validation and processing mean for its rail, but it cannot reorder the steps, skip validation, or drop the audit log. In a payment flow those aren't implementation details — they're compliance requirements, and `final` is how you state that in code rather than in a wiki page.

### Constructors calling overridable methods

`final` also defuses the constructor trap from [[2. Classes And Objects]]:

```java
class Processor {
    Processor() { init(); }        // ⚠ if init() is overridable, the subclass's version
    void init() { }                //    runs before the subclass's fields are initialised
}
```

Marking `init()` `final` (or `private`, or `static`) means the constructor calls exactly what it thinks it's calling. Better still, don't call overridable methods from constructors at all.

### Binding

Since no override can exist, the compiler and JIT can resolve a `final` method's target with certainty — no virtual dispatch needed. It still lives in the vtable, but the slot's content is provably constant, which is what enables inlining. See [[3. Static And Dynamic Binding]].

## `final` Variable

`final` means **assigned exactly once**. What that protects depends on what's being assigned.

### Primitives

```java
final int MAX_RETRIES = 3;
MAX_RETRIES = 5;              // ❌ cannot assign a value to final variable
```

A `static final` primitive or `String` initialised with a compile-time constant is inlined at every use site — which is why changing such a constant in a library requires recompiling every caller, not just relinking.

### References — the crucial trap

```java
final List<String> names = new ArrayList<>();
names.add("Umesh");            // ✅ perfectly legal
names.add("Priya");            // ✅
names = new ArrayList<>();     // ❌ cannot reassign the reference
```

```java
final Employee e = new Employee("Umesh");
e.setSalary(50_000);           // ✅ the object is mutable
e = new Employee("Priya");     // ❌ the reference is not
```

```text
final Employee e ──────▶ ┌──────────────────┐
   ↑ locked              │ Employee object  │  ← contents freely mutable
   (can't point          │ name, salary     │
    somewhere else)      └──────────────────┘
```

**`final` locks the reference, never the object it points to.** This is why `final` alone doesn't produce an immutable class — you also need the class to have no mutating methods, and defensive copies for mutable fields. `final` is necessary but not sufficient.

### `final` fields

A `final` instance field must be **definitely assigned exactly once**, either at declaration or in every constructor path:

```java
class Employee {
    final String employeeId;

    Employee(String id) { this.employeeId = id; }        // ✅
    Employee() { }                                       // ❌ "variable employeeId might not have been initialized"
}
```

Assigning twice is equally an error. This "exactly once" rule is the mechanism that guarantees the field genuinely never changes after construction — it isn't a convention, the compiler proves it.

There's a concurrency payoff too: under the Java Memory Model, `final` fields written in a constructor are guaranteed visible to any thread that later sees the object, with no synchronization. That's **safe publication**, and it's why immutable objects can be shared across threads freely.

### Locals, parameters, and effectively final

```java
void process(final long amountPaise) {
    amountPaise = amountPaise + 1;   // ❌ cannot assign to a final parameter
}
```

The rule that actually matters day to day: a local variable captured by a **lambda or anonymous class** must be `final` or **effectively final** — never reassigned after initialisation, even without the keyword.

```java
int counter = 0;                                        // effectively final — never reassigned
Runnable r = () -> System.out.println(counter);         // ✅

int total = 0;
for (int i = 0; i < 5; i++) total += i;                 // reassigned → not effectively final
Runnable r2 = () -> System.out.println(total);          // ❌ "must be final or effectively final"
```

**Why the restriction exists**: a lambda can outlive the method that created it — handed to an executor, stored in a field, returned. Local variables live on the stack frame, which is gone by then, so the lambda captures a **copy of the value**. If the variable could still change afterwards, the lambda's copy and the original would silently diverge, and nobody could say which value the lambda "should" see. Java removes the ambiguity by forbidding the change.

The standard workaround when you genuinely need mutation is to move the state onto the heap:

```java
AtomicLong total = new AtomicLong();
list.forEach(x -> total.addAndGet(x));   // ✅ the reference is effectively final; the object mutates
```

## Enums

An enum is a type-safe fixed set of constants. Unlike C's enum — which is just named ints — a Java enum is a full class, and each constant is a **singleton instance** of it.

```java
enum PaymentStatus { PENDING, SUCCESS, FAILED, REFUNDED }

PaymentStatus status = PaymentStatus.SUCCESS;
if (status == PaymentStatus.SUCCESS) { ... }   // == is safe: exactly one object per constant
```

### Enums are classes

```java
enum PaymentMethod {
    UPI(0.0, "Instant"),
    CARD(2.5, "1-2 business days"),
    NETBANKING(1.0, "Same day");

    private final double feePercent;
    private final String settlementTime;

    PaymentMethod(double feePercent, String settlementTime) {   // implicitly private
        this.feePercent = feePercent;
        this.settlementTime = settlementTime;
    }

    long feeOn(long amountPaise) { return (long) (amountPaise * feePercent / 100); }
    String settlementTime() { return settlementTime; }
}
```

```java
PaymentMethod.CARD.feeOn(1_000_00);      // 2500 paise
PaymentMethod.CARD.settlementTime();     // "1-2 business days"
```

Putting the fee logic *on* the enum rather than in a `switch` elsewhere is the OCP win: adding a rail adds a constant, and no existing code changes.

### Constant-specific behaviour

```java
interface Describable { String describe(); }

enum PaymentStatus implements Describable {
    SUCCESS { public String describe() { return "Transaction completed successfully"; } },
    FAILED  { public String describe() { return "Transaction could not be processed"; } };
}
```

Each constant with a body compiles to an **anonymous subclass** of the enum — which is why an enum with constant bodies isn't literally `final` in the bytecode, even though you still can't extend it yourself.

### The built-in methods

```java
PaymentStatus.values();              // all constants, declaration order — a fresh clone each call
PaymentStatus.valueOf("SUCCESS");    // parse by exact name; IllegalArgumentException if unknown
status.name();                       // "SUCCESS" — the declared name, never override this meaning
status.ordinal();                    // 1 — position, 0-indexed
```

**Don't build logic on `ordinal()`.** It changes the moment someone reorders or inserts a constant, and nothing will fail loudly — persisted ordinals silently start meaning something else. Store `name()`, and if you need a stable numeric code, declare it as a field.

Also worth knowing: `values()` clones its backing array on every call, so calling it inside a hot loop allocates. Cache it in a `private static final` array if it matters. And prefer `EnumMap`/`EnumSet` over `HashMap`/`HashSet` for enum keys — they're array-backed and dramatically faster.

### Why enums beat `public static final int`

```java
// the pre-Java-5 pattern
class PaymentStatus {
    static final int PENDING = 0, SUCCESS = 1, FAILED = 2;
}

void process(int status) {
    if (status == 5) { }         // compiles fine — 5 isn't a valid status, and nothing says so
}
```

Enums give you compile-time type safety (an invalid value can't be expressed), attached behaviour and state, safe `==`, a readable `toString()`, `switch` support, and exhaustiveness help. There is no reason to use int constants in new code.

### The enum singleton

```java
enum ConfigManager {
    INSTANCE;

    private final Map<String, String> config = new HashMap<>();

    void set(String key, String value) { config.put(key, value); }
    String get(String key) { return config.get(key); }
}

ConfigManager.INSTANCE.set("env", "prod");
```

The JVM guarantees a single instance, and — unlike a hand-written singleton — it's **serialization-safe and reflection-safe for free**. `Enum`'s `readResolve` prevents deserialization from creating a second instance, and the reflection API explicitly refuses to instantiate enum types. *Effective Java* calls this the best way to implement a singleton.

> 💡 **Interview**: Why is an enum the safest singleton? → The JVM guarantees one instance per constant, and it's inherently protected against the two standard attacks on singletons: deserialization creating a second instance, and reflection calling the private constructor.

## Records (Java 16+)

A record is a condensed declaration for an immutable data carrier.

### Before

```java
public final class Point {
    private final int x, y;

    public Point(int x, int y) { this.x = x; this.y = y; }
    public int getX() { return x; }
    public int getY() { return y; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        Point p = (Point) o;
        return x == p.x && y == p.y;
    }
    @Override public int hashCode() { return Objects.hash(x, y); }
    @Override public String toString() { return "Point[x=" + x + ", y=" + y + "]"; }
}
```

### After

```java
public record Point(int x, int y) { }
```

```java
Point p1 = new Point(1, 2);
Point p2 = new Point(1, 2);

p1.x();            // 1 — accessor is x(), NOT getX()
p1.equals(p2);     // true
p1;                // Point[x=1, y=2]
```

The compiler generates:

- A **canonical constructor** taking all components in order
- **Accessors named after the components** — `x()`, `y()`. Frameworks expecting JavaBean `getX()` need configuration (Jackson handles records natively; older reflection-based tools may not)
- `equals()` and `hashCode()` over **all** components
- `toString()` as `Name[a=1, b=2]`
- All component fields as `private final`

Records are implicitly `final`, implicitly extend `java.lang.Record` (so they cannot extend anything else), and **can** implement interfaces:

```java
interface Shape { double area(); }
record Circle(double radius) implements Shape {
    public double area() { return Math.PI * radius * radius; }
}
```

### Compact constructors

```java
public record Money(long amountPaise, String currency) {
    public Money {                                     // no parameter list, no explicit assignment
        if (amountPaise < 0) throw new IllegalArgumentException("amount cannot be negative");
        currency = currency.toUpperCase();             // normalise the parameter
    }
}
```

Your body runs first; the implicit `this.amountPaise = amountPaise` assignments happen **after** it. That's why reassigning the *parameter* inside the body works as normalisation.

A record whose component is a mutable type still needs a defensive copy here:

```java
public record Payment(String txnId, List<LedgerEntry> entries) {
    public Payment { entries = List.copyOf(entries); }
}
```

### Adding behaviour

```java
public record Money(long amountPaise, String currency) {
    public Money add(Money other) {
        if (!currency.equals(other.currency)) throw new IllegalArgumentException("currency mismatch");
        return new Money(amountPaise + other.amountPaise, currency);   // a NEW record
    }
}
```

## Records vs Classes — the decision

Use a **record** for a fixed snapshot: DTOs, API request/response payloads, value objects, events, data passed between layers. `TransactionRequest`, `PaymentResponse`, `SettlementEvent`.

Use a **regular class** when the object's state evolves over its own lifetime.

### Why a record breaks on evolving state

```java
public record TransactionRewards(String txnId, double earnedRewards) { }

TransactionRewards rewards = new TransactionRewards("txn123", 0.0);
rewards.earnedRewards += 5;    // ❌ the field is private final, and there's no setter to write
```

The only record-shaped option is to rebuild the object each time:

```java
public record TransactionRewards(String txnId, double earnedRewards) {
    public TransactionRewards addReward(double amount) {
        return new TransactionRewards(txnId, earnedRewards + amount);   // a new object every phase
    }
}

rewards = rewards.addReward(5.0);
rewards = rewards.addReward(10.0);
rewards = rewards.addReward(2.5);   // 17.5
```

That works, and for a two-field object it's cheap. But across many phases and high transaction volume, you're allocating a throwaway object per phase for what is conceptually "increment a counter".

The deeper issue is modelling, not allocation. **A record says "this object *is* these component values, permanently."** Two `Money(100, "INR")` records are interchangeable — that's exactly right for a payload. Rewards accumulating across a transaction's phases is not a value; it's **mutable state tied to an identity over time** — the same transaction, changing as it progresses. That's what a normal class is for:

```java
public class TransactionRewards {
    private final String txnId;
    private double earnedRewards;              // deliberately not final

    public TransactionRewards(String txnId) {
        this.txnId = txnId;
        this.earnedRewards = 0.0;
    }

    public void addReward(double amount) {
        if (amount < 0) throw new IllegalArgumentException("reward cannot be negative");
        earnedRewards += amount;               // mutate in place
    }

    public double getEarnedRewards() { return earnedRewards; }
}
```

### The decision table

| Question | Yes → |
| --- | --- |
| Is this a fixed snapshot — a request, a response, a finalised value? | **Record** |
| Does it change over its own lifetime — in-progress state, an accumulator? | **Class** |
| Does it need JPA/Hibernate entity behaviour (dirty checking, lazy loading, proxies)? | **Class** (`@Entity`) |
| Is it just data crossing a layer boundary, with no behaviour? | **Record** |

### The middle-ground pattern

Use a mutable accumulator during processing, then freeze it into a record at the boundary:

```java
class TransactionRewardsAccumulator {          // mutable, during the phases
    private final String txnId;
    private double earnedRewards = 0.0;

    void addReward(double amount) { earnedRewards += amount; }

    TransactionRewardsSnapshot snapshot() {    // immutable, once done
        return new TransactionRewardsSnapshot(txnId, earnedRewards);
    }
}

record TransactionRewardsSnapshot(String txnId, double totalRewards) { }
```

Cheap in-place mutation while the transaction is in flight; a safe, thread-shareable, immutable value once it's final — ready to publish to Kafka, return in a response, or log, with no risk of a downstream consumer mutating it.

## Sealed Classes (Java 17+)

A sealed type explicitly restricts who may extend or implement it.

### The problem

```java
abstract class PaymentMethod { }        // "meant" to be UPI / card / netbanking only
class UpiPayment  extends PaymentMethod { }
class CardPayment extends PaymentMethod { }

// anyone, in any file, in any module:
class CryptoPayment extends PaymentMethod { }   // the "closed set" was never actually closed
```

Every `switch` and `instanceof` chain you wrote assuming three subtypes is now silently wrong.

### The fix

```java
public sealed class PaymentMethod
        permits UpiPayment, CardPayment, NetBankingPayment { }

public final class UpiPayment        extends PaymentMethod { }
public final class CardPayment       extends PaymentMethod { }
public final class NetBankingPayment extends PaymentMethod { }

class CryptoPayment extends PaymentMethod { }   // ❌ not listed in permits
```

### Rules for permitted subtypes

Every class in the `permits` list must be exactly one of:

- **`final`** — closed, no further extension
- **`sealed`** — extendable, but only by its own permitted list (nested sealing)
- **`non-sealed`** — deliberately reopened; anyone may extend from there down

```java
public sealed class PaymentMethod permits UpiPayment, CardPayment, LegacyPayment { }

public final      class UpiPayment    extends PaymentMethod { }
public final      class CardPayment   extends PaymentMethod { }
public non-sealed class LegacyPayment extends PaymentMethod { }

class OldBankTransfer extends LegacyPayment { }   // ✅ LegacyPayment reopened the branch
```

Permitted subclasses must also be in the same module (or the same package, for unnamed modules) — the compiler has to see the whole set.

### The real payoff — exhaustive switch

```java
sealed interface Shape permits Circle, Square, Triangle { }

record Circle(double radius) implements Shape { }
record Square(double side) implements Shape { }
record Triangle(double base, double height) implements Shape { }

double area(Shape shape) {
    return switch (shape) {
        case Circle c   -> Math.PI * c.radius() * c.radius();
        case Square s   -> s.side() * s.side();
        case Triangle t -> 0.5 * t.base() * t.height();
        // no default needed — the compiler knows these are the only three
    };
}
```

Without sealing, the compiler can never prove a `switch` covers every subtype, so you're forced into a defensive `default -> throw new IllegalStateException("unreachable")` — which is a runtime failure waiting to happen. With sealing, adding `Hexagon` to the `permits` list turns every non-exhaustive `switch` in the codebase into a **compile error**, immediately, with file and line.

Sealed interfaces work identically:

```java
public sealed interface PaymentEvent
        permits PaymentInitiated, PaymentCompleted, PaymentFailed { }
```

This is the combination worth reaching for in fintech domain modelling. A `TransactionStatus`, `PaymentEvent` or `SwitchResponseCode` with a genuinely finite set of variants gets compile-time proof that every handler is exhaustive — a missing case becomes a build failure instead of a production incident.

Sealed types plus records is also the closest Java gets to algebraic data types: a sealed interface is the "or", a record is the "and".

## What Enum and Record Desugar To

Both are syntactic sugar. Knowing what the compiler emits explains exactly what's locked and why.

### Enum

```java
enum PaymentMethod {
    UPI(0.0, "Instant"),
    CARD(2.5, "1-2 business days");

    private final double feePercent;
    PaymentMethod(double fee, String settlement) { ... }
}
```

compiles to roughly:

```java
final class PaymentMethod extends Enum<PaymentMethod> {

    public static final PaymentMethod UPI  = new PaymentMethod("UPI",  0, 0.0, "Instant");
    public static final PaymentMethod CARD = new PaymentMethod("CARD", 1, 2.5, "1-2 business days");

    private final double feePercent;
    private final String settlementTime;

    private PaymentMethod(String name, int ordinal, double fee, String settlement) {
        super(name, ordinal);                  // Enum's constructor sets name() and ordinal()
        this.feePercent = fee;
        this.settlementTime = settlement;
    }

    private static final PaymentMethod[] $VALUES = { UPI, CARD };

    public static PaymentMethod[] values() { return $VALUES.clone(); }   // a copy, so callers can't corrupt it
    public static PaymentMethod valueOf(String name) { ... }
}
```

| Element | Final? | Why |
| --- | --- | --- |
| The enum class | Implicitly `final` | Nobody can add instances outside the declared constants. (Constant-specific bodies compile to anonymous subclasses internally — but *you* still can't extend it.) |
| Each constant | Implicitly `public static final` | One object per constant, created once. This is why `==` is safe. |
| The constructor | Implicitly `private` | The actual mechanism closing the set — `new PaymentMethod(...)` is unwritable. |
| Your own fields | `final` **only if you write it** | Not automatic. Mutable enum fields are legal and a bad idea — they're global mutable state. |
| The `$VALUES` array | Protected by cloning | `values()` returns a copy so external code can't rewrite the constant list. |

**Enum's final-ness is about restricting how many instances exist.**

### Record

```java
public record Money(double amount, String currency) {
    public Money {
        if (amount < 0) throw new IllegalArgumentException("Amount cannot be negative");
        currency = currency.toUpperCase();
    }
}
```

compiles to roughly:

```java
public final class Money extends Record {

    private final double amount;                 // every component: private final, no choice
    private final String currency;

    public Money(double amount, String currency) {
        if (amount < 0) throw new IllegalArgumentException("Amount cannot be negative");
        currency = currency.toUpperCase();       // ← your compact constructor body
        this.amount = amount;                    // ← implicit assignments, AFTER your body
        this.currency = currency;
    }

    public double amount()   { return amount; }     // named amount(), not getAmount()
    public String currency() { return currency; }

    @Override public boolean equals(Object o) { /* compares all components */ }
    @Override public int hashCode()           { return Objects.hash(amount, currency); }
    @Override public String toString()        { return "Money[amount=" + amount + ", currency=" + currency + "]"; }
}
```

| Element | Final? | Why |
| --- | --- | --- |
| The record class | Implicitly `final` | A subclass could add hidden state, breaking the "this object *is* exactly these components" guarantee that makes the generated `equals`/`hashCode` trustworthy |
| Every component field | Implicitly `private final` — **no choice** | The defining feature: immutability of every component, compiler-enforced |
| The canonical constructor | N/A (constructors are never `final`) | Auto-generated unless you supply a compact or full one |
| Accessors | **Not** final | You may override one to add logic |
| `equals`/`hashCode`/`toString` | **Not** final | Generated as defaults; you can supply your own |

Overriding an accessor is legal:

```java
public record Money(double amount, String currency) {
    public String currency() { return currency.trim().toUpperCase(); }
}
```

The **field** is unconditionally locked; the accessor is not.

**Record's final-ness is about guaranteeing each instance's state never changes** — which is why fields are forced final but you can create unlimited instances.

### Side by side

| | Enum | Record |
| --- | --- | --- |
| Class | `final` (implicit) | `final` (implicit) |
| Constructor | `private` (implicit, always) | Whatever you declare |
| Your fields | `final` only if you write it | `final` always, no choice |
| Instances | A fixed set — only the declared constants | Unlimited, each immutable |
| Core guarantee | "Only these N objects exist, ever" — **identity** | "Every instance is defined entirely by its components" — **value** |
