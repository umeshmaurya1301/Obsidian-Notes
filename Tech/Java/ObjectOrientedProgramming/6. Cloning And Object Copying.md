# Cloning And Object Copying

---

## Short Notes

---

### 1. What Cloning Is

- Produce a copy of an existing object **without calling a constructor**
- `Object.clone()` does a field-by-field **shallow** copy at the memory level
- `Cloneable` is a **marker interface** that merely unlocks it
- Asked in interviews far more for its design flaws than for its use

---

### 2. `Cloneable` Declares Nothing

```java
public interface Cloneable { }   // empty
```

- The real method lives on `Object`: `protected native Object clone()`
- `Object.clone()` checks `instanceof Cloneable`, else throws `CloneNotSupportedException`
- An interface controlling a method it doesn't declare — the core design flaw

---

### 3. Two Things Are Required

- **Implement `Cloneable`** — or `super.clone()` throws at runtime
- **Override `clone()` as `public`** — `Object.clone()` is `protected`, so callers can't reach it
- Doing one without the other fails, in two different ways

---

### 4. The Three Setup Traps

| Mistake | Result |
| --- | --- |
| Calling `clone()` on `Cloneable` reference | Compile error — no such method on the interface |
| Implementing `Cloneable`, not overriding `clone()` | Compile error — `protected` at the call site |
| Overriding `clone()`, not implementing `Cloneable` | Runtime `CloneNotSupportedException` |

---

### 5. Shallow Copy — The Big Trap

- `super.clone()` copies **references**, not the objects behind them
- Original and clone share every mutable nested object
- Mutating `clone.address.city` changes `original.address.city`
- Primitives and immutables (`String`) are safe; mutable references are not

---

### 6. Deep Copy

- Clone the object, then **explicitly copy each mutable field**
- `copy.scores = this.scores.clone();` for arrays; recurse for object graphs
- Nested deep copy must go all the way down — one shallow level ruins it
- Serialize→deserialize (`SerializationUtils.clone`) deep-copies generically but is slow

---

### 7. Constructors Are Not Called

- `clone()` allocates and copies memory directly — **no constructor runs**
- So constructor validation and invariants are silently skipped
- A class that guarantees state via its constructor can be cloned into an invalid state

---

### 8. `final` Fields Break Deep Copy

- Deep copy needs `copy.address = new Address(...)` — illegal on a `final` field
- `final` fields can only be assigned in a constructor, and `clone()` isn't one
- So `Cloneable` and immutability are fundamentally at odds

---

### 9. Why `Cloneable` Is Considered Broken

1. The interface declares no `clone()` method
2. `clone()` throws a **checked** exception you almost always swallow
3. Shallow by default — a footgun
4. Constructors are bypassed → invariants skipped
5. Hard to get right through an inheritance hierarchy
6. Incompatible with `final` fields

---

### 10. What To Use Instead

- **Copy constructor**: `new Employee(other)` — explicit, validating, `final`-friendly
- **Static factory**: `Employee.copyOf(other)` — can return a subtype or a cached instance
- **`List.copyOf` / `Map.copyOf`** for collections; `Arrays.copyOf` for arrays
- Best answer of all: make the class **immutable** and skip copying entirely

---

### 11. Shallow vs Deep vs Reference Copy

| | Reference copy | Shallow copy | Deep copy |
| --- | --- | --- | --- |
| New object? | No | Yes | Yes |
| Nested objects | Shared | Shared | Duplicated |
| `a == b` | `true` | `false` | `false` |
| Mutating nested affects other | Yes | Yes | No |

---

### SDE-2 Interview Priority

**Must Know**: `Cloneable` is a marker, Shallow vs deep copy, Constructors aren't called, Why copy constructors are preferred, Reference vs shallow vs deep

**Nice To Know**: `final` fields blocking deep copy, Covariant return on `clone()`, Serialization-based deep copy

**Advanced**: `clone()` in inheritance hierarchies, Immutability as the real answer, `clone()` and the security implications of constructor bypass

# Detailed Explanation

---

## What Cloning Is Meant To Solve

The original idea was to copy an object without naming every field at the call site:

```java
// without cloning
Employee e2 = new Employee(e1.getName(), e1.getSalary(), e1.getAddress());

// with cloning
Employee e2 = e1.clone();
```

Attractive for objects with many fields, and for frameworks that must copy an object whose concrete type isn't known at compile time. The execution, however, went wrong in almost every way it could, and the modern answer is to not use it.

---

## `Cloneable` Declares Nothing

```java
public interface Cloneable { }   // that's the whole file
```

The method that actually copies lives on `Object`:

```java
protected native Object clone() throws CloneNotSupportedException;
```

and it begins, conceptually:

```java
if (!(this instanceof Cloneable)) {
    throw new CloneNotSupportedException();
}
// native field-by-field memory copy
```

So `Cloneable` does not define cloning — it **unlocks** a method defined elsewhere. That inversion is the design flaw everything else follows from: the interface that supposedly governs cloning cannot be used to call it, cannot be used to type a parameter usefully, and imposes no obligation the compiler can check.

```java
Cloneable c = someObject;
c.clone();      // ❌ compile error — Cloneable has no clone() method
```

---

## The Two Requirements

Cloning only works if you do **both** of these.

### 1. Implement `Cloneable`

Otherwise `super.clone()` throws at runtime:

```java
class Employee {                                   // ⚠ no Cloneable
    @Override
    public Employee clone() throws CloneNotSupportedException {
        return (Employee) super.clone();
    }
}

new Employee().clone();   // ❌ CloneNotSupportedException at runtime
```

### 2. Override `clone()` and widen it to `public`

`Object.clone()` is `protected`, so an outside caller cannot reach it:

```java
class Employee implements Cloneable { }            // ⚠ no override

Employee e = new Employee();
e.clone();   // ❌ compile error — clone() has protected access in Object
```

Both together:

```java
class Employee implements Cloneable {
    String name;
    long salaryPaise;

    @Override
    public Employee clone() {                       // public + covariant return type
        try {
            return (Employee) super.clone();        // the native copy
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);            // unreachable — we do implement Cloneable
        }
    }
}
```

Two details worth keeping in that snippet. The return type is narrowed to `Employee` (covariant returns, Java 5+) so callers don't downcast. And the checked `CloneNotSupportedException` is caught and rethrown as an `AssertionError` — it can never fire here, and forcing every caller into a try/catch for an impossible exception is exactly the clumsiness the API is criticised for.

| Mistake | Where it fails |
| --- | --- |
| `clone()` on a `Cloneable`-typed reference | Compile time — no such method |
| `Cloneable` without overriding `clone()` | Compile time — `protected` access |
| Overriding `clone()` without `Cloneable` | Runtime — `CloneNotSupportedException` |

---

## The Biggest Trap: Shallow Copy

`super.clone()` copies the object's fields **bit for bit**. For a reference field, that copies the *reference*, not the object it points to.

```java
class Address {
    String city;
}

class Employee implements Cloneable {
    String name;
    Address address;          // mutable reference type

    @Override
    public Employee clone() throws CloneNotSupportedException {
        return (Employee) super.clone();       // shallow
    }
}
```

```java
Employee e1 = new Employee();
e1.address = new Address();
e1.address.city = "Mumbai";

Employee e2 = e1.clone();
e2.address.city = "Delhi";

System.out.println(e1.address.city);   // "Delhi" — e1 changed too
```

```text
e1 ──▶ ┌──────────────┐
       │ name         │
       │ address ─────┼──┐
       └──────────────┘  │
                         ▼
                    ┌─────────┐
                    │ Address │   ← ONE object, shared
                    │ city    │
                    └─────────┘
                         ▲
e2 ──▶ ┌──────────────┐  │
       │ name         │  │
       │ address ─────┼──┘
       └──────────────┘
```

Two `Employee` objects, one `Address`. Primitives and immutable references (`String`, boxed types) are unaffected — reassigning `e2.name` cannot touch `e1.name` — but any **mutable** nested object is shared, and the aliasing is invisible until something writes through it. In a payments codebase this is how a cloned `Payment` ends up sharing a mutable `Money` or `List<LedgerEntry>` with the original, and a "copy" silently corrupts the source.

---

## Deep Copy

A deep copy duplicates the nested objects too. There is no automatic way to do it — you clone, then fix up every mutable field by hand:

```java
class Employee implements Cloneable {
    String name;
    Address address;
    int[] scores;

    @Override
    public Employee clone() throws CloneNotSupportedException {
        Employee copy = (Employee) super.clone();   // shallow first
        copy.address = new Address(this.address.city);  // then duplicate each mutable field
        copy.scores  = this.scores.clone();             // arrays have their own clone()
        return copy;
    }
}
```

```java
Employee e2 = e1.clone();
e2.address.city = "Delhi";
System.out.println(e1.address.city);   // "Mumbai" — independent now ✅
```

The rule is that it must go **all the way down**. If `Address` itself held a mutable `GeoPoint`, `new Address(this.address.city)` would not be enough — `Address` needs its own deep copy, and so on through the graph. One shallow level anywhere makes the whole thing shallow.

A generic alternative is to round-trip through serialization:

```java
Employee copy = SerializationUtils.clone(original);   // Apache Commons Lang
```

It deep-copies an arbitrary graph without hand-written code, but every class in the graph must be `Serializable`, it is an order of magnitude slower than field copying, and it silently reproduces the constructor-bypass problem below.

---

## Constructors Are Not Called

```java
class Employee implements Cloneable {
    Employee() { System.out.println("Constructor"); }

    @Override
    public Employee clone() throws CloneNotSupportedException {
        return (Employee) super.clone();
    }
}
```

```java
Employee e1 = new Employee();
Employee e2 = e1.clone();
```

```text
Constructor        ← printed once, for `new` only
```

`clone()` allocates memory and copies bytes; it never invokes a constructor. That is efficient, and it is also the deepest problem with the whole mechanism: **every guarantee your constructor enforces is skipped.**

```java
class Wallet implements Cloneable {
    private final String walletId;
    private long balancePaise;

    Wallet(String walletId, long opening) {
        if (opening < 0) throw new IllegalArgumentException();   // never runs on clone()
        this.walletId = walletId;
        this.balancePaise = opening;
    }
}
```

Validation, registration in a cache, ID generation, invariant checks — none of it happens. If the object being cloned is already valid the copy usually is too, but any per-instance work the constructor did (assigning a unique id, incrementing a counter, registering a listener) is silently omitted.

> 💡 **Interview**: Does cloning call the constructor? → No. `clone()` performs a native memory copy, so all constructor logic — validation, id generation, registration — is bypassed. It's the main reason copy constructors are preferred.

---

## `final` Fields Break Deep Copy

Deep copying requires reassigning fields on the clone. A `final` field cannot be reassigned outside a constructor:

```java
class Employee implements Cloneable {
    private final Address address;      // final

    @Override
    public Employee clone() throws CloneNotSupportedException {
        Employee copy = (Employee) super.clone();
        copy.address = new Address(...);   // ❌ cannot assign a value to final variable
        return copy;
    }
}
```

There is no workaround short of reflection. So the moment you make fields `final` — which is the standard advice for safe, immutable, thread-friendly design — deep cloning becomes impossible. `Cloneable` pushes you away from immutability, which is precisely backwards.

---

## Why `Cloneable` Is Considered Broken

Joshua Bloch devotes an *Effective Java* item to avoiding it. The charges:

1. **The interface declares no `clone()`** — it modifies the behaviour of a `protected` method on `Object` instead, so it cannot be used as a type.
2. **Checked exception for an impossible case** — every correct implementation catches `CloneNotSupportedException` and rethrows it as unreachable.
3. **Shallow by default** — the safe-looking one-liner is the wrong one for any class with mutable fields.
4. **Constructors bypassed** — invariants and validation silently skipped.
5. **Hard in hierarchies** — every class in the chain must call `super.clone()` and fix up its own fields; one class using `new` instead breaks cloning for every subclass.
6. **Incompatible with `final` fields** — it penalises immutable design.

**The line to say**: *"`Cloneable` is a broken design — I use copy constructors instead. `clone()` bypasses the constructor so validation is skipped, it's shallow by default, the checked exception is noise, and it doesn't work with `final` fields."*

---

## What To Use Instead

### Copy constructor

```java
class Employee {
    private final String name;
    private final Address address;

    Employee(String name, Address address) {
        if (name == null || name.isBlank()) throw new IllegalArgumentException("name required");
        this.name = name;
        this.address = address;
    }

    Employee(Employee other) {                        // copy constructor
        this(other.name, new Address(other.address)); // validation runs, deep copy explicit
    }
}

Employee copy = new Employee(original);
```

Everything the clone mechanism gets wrong, this gets right: the constructor runs so invariants hold, `final` fields work, the depth of the copy is explicit and visible, there is no checked exception, and there's no cast.

### Static factory

```java
static Employee copyOf(Employee other) { return new Employee(other); }
```

Same benefits, plus a name at the call site, freedom to return a subtype, and the option to return the same instance when the type is immutable — which is exactly what `List.copyOf` does.

### Built-ins

```java
int[] copy         = Arrays.copyOf(scores, scores.length);
List<String> snap  = List.copyOf(handles);      // immutable shallow copy
Map<String, Long> m = Map.copyOf(balances);
List<String> mutable = new ArrayList<>(handles); // copy constructor on collections
```

Note all of these are **shallow** — `List.copyOf` gives a new list holding the same element references. That is fine when the elements are immutable, which is the point of the next item.

### Best answer: don't copy at all

```java
record Money(long amountPaise, String currency) { }   // immutable — sharing is safe
```

If an object cannot be mutated, there is no reason to copy it. Aliasing is only dangerous because of mutation. Making value types immutable — `record`s, `final` fields, no setters, defensive copies at the boundary — removes the entire class of problem that cloning exists to solve.

---

## Shallow vs Deep vs Reference Copy

```java
Employee a = new Employee("Umesh", new Address("Mumbai"));

Employee r = a;                       // reference copy — one object, two variables
Employee s = a.clone();               // shallow copy — two Employees, one Address
Employee d = new Employee(a);         // deep copy — two Employees, two Addresses
```

| | Reference copy | Shallow copy | Deep copy |
| --- | --- | --- | --- |
| New object created | No | Yes | Yes |
| Top-level fields | Shared (same object) | Copied | Copied |
| Nested mutable objects | Shared | **Shared** | Duplicated |
| `a == b` | `true` | `false` | `false` |
| Mutating nested affects the other | Yes | **Yes** | No |
| Cost | Free | Cheap | Proportional to the graph |

The middle column is where bugs live: it *looks* like an independent object, and for primitives and `String` fields it behaves like one, so the aliasing stays hidden until something mutates a nested object in production.
