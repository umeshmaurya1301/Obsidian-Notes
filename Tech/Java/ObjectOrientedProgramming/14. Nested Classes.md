# Nested Classes

---

## Short Notes

---

### 1. The Four Types

```java
class Outer {
    static class StaticNested { }          // 1. static nested

    class Inner { }                        // 2. inner (non-static)

    void m() {
        class Local { }                    // 3. local — inside a method
        Runnable r = new Runnable() {      // 4. anonymous — no name
            public void run() { }
        };
    }
}
```

- The split that matters: **static** (no outer instance) vs **everything else** (holds one)

---

### 2. Static Nested Class

- Behaves like a top-level class, just **namespaced** inside `Outer`
- **No** implicit reference to any outer instance
- Can access only the outer class's **static** members
- Created without an `Outer`: `new Outer.StaticNested()`

---

### 3. Static Nested — Use Cases

- **Builder pattern** — the canonical use; the builder must exist *before* the object does
- `Map.Entry` — logically scoped to `Map`, needs no `Map` instance
- Config/DTO/helper types that belong to one class and need no outer state

---

### 4. Inner Class (Non-Static)

- Every instance is bound to **exactly one** outer instance, for life
- Holds a hidden reference — `Outer.this`
- Can access **all** outer members, including `private` instance fields
- Cannot declare `static` members (pre-Java 16; constants aside)

---

### 5. Inner Class — Instantiation

```java
Outer outer = new Outer();
Outer.Inner inner = outer.new Inner();   // the unusual syntax
```

- Usually hidden behind a factory method on the outer class
- Inside the outer class, plain `new Inner()` works — `this` is implicit

---

### 6. `Outer.this`

```java
class Outer {
    int value = 10;
    class Inner {
        int value = 20;
        void show() {
            System.out.println(value);            // 20 — inner's
            System.out.println(Outer.this.value); // 10 — outer's
        }
    }
}
```

---

### 7. Inner Class — Use Case

- **Iterators**: an iterator needs the *specific* collection instance it walks
- A static nested class would need the collection passed in explicitly
- Inner classes get that link automatically — that's why they exist
- Common in data structures and Android; rarer in backend service code

---

### 8. Local Class

- Declared inside a method, constructor or block — invisible outside it
- Can access the enclosing class's members **plus** the method's locals
- Captured locals must be `final` or **effectively final**
- Mostly superseded by lambdas; still useful for multi-method, stateful, method-local logic

---

### 9. Anonymous Class

- No name — declared and instantiated in one expression
- Compiles to a real class file: `Outer$1.class`
- Exactly **one** instance ever, created at the point of definition
- Can implement an interface **or** extend a (possibly abstract) class

---

### 10. Anonymous vs Lambda

Use an anonymous class when a lambda can't do it:

- The type has **more than one** abstract method
- You're **extending a class**, not implementing an interface
- You need **extra fields or helper methods** beyond the one override
- Otherwise, since Java 8, prefer the lambda

---

### 11. Cheat Sheet

| | Static Nested | Inner | Local | Anonymous |
| --- | --- | --- | --- | --- |
| Needs outer instance | No | **Yes** | No | If in a non-static context |
| Outer instance members | Static only | All, incl. `private` | Yes | Yes |
| Enclosing method locals | N/A | N/A | Final/effectively final | Final/effectively final |
| Has a name | Yes | Yes | Yes | **No** |
| Can declare constructors | Yes | Yes | Yes | **No** |
| Can declare `static` members | Yes | No | No | No |

---

### 12. The Memory Leak Trap

- An inner / local / anonymous class holds a **strong reference** to its outer instance
- A long-lived listener or callback keeps the whole outer object alive
- Symptom: a "small" object retaining a large graph in a heap dump
- Fix: make it `static` nested and pass in only what it needs

---

### 13. What You'll Actually Use

- **Static nested** — common: builders, nested config/DTOs
- **Inner** — uncommon in backend code; custom data structures, Android
- **Local** — rare; lambdas or a real class win almost always
- **Anonymous** — for the lambda exceptions above; otherwise legacy

---

**Must Know**: The four types and their differences, Static nested vs inner, `outer.new Inner()`, Builder as the static-nested use case, When an anonymous class beats a lambda, Effectively-final capture

# Detailed Explanation

---

## The Four Types, and the Line Between Them

Java lets a class be declared inside another class in four ways:

```java
class Outer {
    static class StaticNested { }          // 1
    class Inner { }                        // 2

    void someMethod() {
        class LocalClass { }               // 3
    }

    void anotherMethod() {
        Runnable r = new Runnable() {      // 4
            public void run() { }
        };
    }
}
```

Terminology worth getting right: all four are **nested classes**. Only the non-static ones are **inner classes** — "static inner class" is a contradiction people say all the time.

The distinction that drives every rule below is whether the nested class holds a **hidden reference to an enclosing instance**. A static nested class doesn't. The other three do (when declared in an instance context), and that one fact explains what they can access, how they're created, and how they leak memory.

---

## Static Nested Class

A `static` class inside another class. It behaves almost exactly like a top-level class — it's simply **namespaced** under `Outer` for organisation.

```java
class Outer {
    private static int staticField = 100;
    private int instanceField = 200;

    static class StaticNested {
        void show() {
            System.out.println(staticField);     // ✅ outer's static members — including private
            System.out.println(instanceField);   // ❌ no outer instance exists to read it from
        }
    }
}
```

```java
Outer.StaticNested nested = new Outer.StaticNested();   // no Outer object needed
```

Characteristics:

- Accesses only the outer class's **static** members — there is no specific outer instance to consult.
- Can have its own static and instance members, its own constructors — a fully independent class.
- Instantiated as `Outer.StaticNested`, with no enclosing instance.
- It *can* still reach the outer class's `private` static members: nesting grants access, an enclosing instance is a separate matter.

### The Builder pattern — the canonical use

```java
class Pizza {
    private final String size;
    private final boolean extraCheese;

    private Pizza(Builder builder) {                // private — construction goes through the builder
        this.size = builder.size;
        this.extraCheese = builder.extraCheese;
    }

    static class Builder {                          // static: must work BEFORE a Pizza exists
        private String size;
        private boolean extraCheese;

        Builder size(String size)          { this.size = size; return this; }
        Builder extraCheese(boolean value) { this.extraCheese = value; return this; }
        Pizza build()                      { return new Pizza(this); }
    }
}

Pizza pizza = new Pizza.Builder().size("Large").extraCheese(true).build();
```

The `static` is not stylistic. A builder's entire job is to accumulate state *before* the object exists — an inner class would require a `Pizza` instance to create the builder that creates the `Pizza`. Nesting it inside `Pizza` is what lets the builder reach `Pizza`'s private constructor.

### `Map.Entry`

```java
for (Map.Entry<String, Long> e : walletBalances.entrySet()) {
    System.out.println(e.getKey() + " = " + e.getValue());
}
```

An entry has no meaning outside a map's vocabulary, but it doesn't need a specific `Map` instance to exist as a type — so it's nested and static. Same reasoning as the nested interfaces in [[5. Interfaces And Abstraction]].

---

## Inner Class (Non-Static)

A non-static nested class. Every instance is **permanently bound to one instance of the outer class**, through a hidden field the compiler adds.

```java
class Outer {
    private int instanceField = 200;

    class Inner {
        void show() {
            System.out.println(instanceField);   // ✅ reads the outer instance's private field
        }
    }
}
```

```java
Outer outer = new Outer();
Outer.Inner inner = outer.new Inner();   // created THROUGH an outer instance
```

That `outer.new Inner()` syntax is the giveaway: an inner class cannot exist without an outer object to attach to. Inside `Outer`'s own instance methods you just write `new Inner()`, and the compiler supplies `this` as the enclosing instance.

Characteristics:

- Accesses **both static and instance** members of the outer class, including `private` ones.
- Cannot declare `static` members. Before Java 16 that included static constants other than compile-time ones; Java 16 relaxed the restriction and static members are now allowed.
- Each `Inner` is tied to exactly one `Outer` for its whole lifetime.

### `Outer.this`

```java
class Outer {
    int value = 10;

    class Inner {
        int value = 20;

        void show() {
            System.out.println(value);              // 20 — Inner's own field
            System.out.println(this.value);         // 20 — same thing, explicit
            System.out.println(Outer.this.value);   // 10 — the enclosing instance
        }
    }
}
```

`Outer.this` is the name of that hidden reference. It's the only way to disambiguate when both classes declare the same member.

### The motivating use case — iterators

```java
class MyCollection<T> {
    private T[] items;
    private int size;

    class MyIterator implements Iterator<T> {
        private int index = 0;

        public boolean hasNext() { return index < size; }    // reads the outer instance directly
        public T next()          { return items[index++]; }
    }

    Iterator<T> iterator() { return new MyIterator(); }       // hides the outer.new syntax
}
```

This is why inner classes exist. An iterator is meaningless without knowing *which specific collection* it's walking. A static nested class could do the job, but only by taking the collection as a constructor parameter and storing it — the inner class gets that link automatically, and gets private access to the collection's internals for free.

Note the factory method: exposing `iterator()` rather than making callers write `collection.new MyIterator()` is standard practice.

---

## Local Class

A class declared inside a method, constructor or block. Its scope is that block and nothing else.

```java
class Outer {
    void process() {
        int threshold = 50;                 // must be final or effectively final

        class Validator {
            void validate(long amount) {
                if (amount < threshold) {   // captures the enclosing method's local
                    throw new IllegalArgumentException("below threshold");
                }
            }
        }

        Validator v = new Validator();
        v.validate(100);
    }
    // Validator does not exist outside process()
}
```

It can access the enclosing class's members like an inner class, **plus** the enclosing method's locals and parameters — but only if those are `final` or **effectively final**, exactly the lambda-capture rule from [[13. Special Classes And Modifiers]]. The reason is the same: the local class instance can outlive the stack frame, so it captures a copy of the value, and a value that could still change would be ambiguous.

### Why it's rare

```java
void process() {
    class Validator { void validate() { System.out.println("Validating"); } }
    new Validator().validate();
}

// what almost everyone writes instead today:
void process() {
    Runnable validator = () -> System.out.println("Validating");
    validator.run();
}
```

Lambdas cover the single-method case with far less ceremony, and anything more complex is usually worth extracting into a real nested or top-level class. Local classes still earn their place when you need **multiple methods and/or state** scoped tightly to one method, where a lambda's single abstract method isn't enough but a full class would be over-exposure.

---

## Anonymous Class

A class with no name, declared and instantiated in a single expression.

```java
interface Greeting { void greet(); }

Greeting g = new Greeting() {
    @Override
    public void greet() { System.out.println("Hello!"); }
};
g.greet();
```

The compiler generates a real class file for this — `Outer$1.class`, then `Outer$2.class`, and so on. It's an ordinary class; you just have no name to refer to it by, and you can create exactly **one** instance, right where it's defined.

It can also extend a class rather than implement an interface:

```java
abstract class Animal { abstract void sound(); }

Animal dog = new Animal() {
    @Override void sound() { System.out.println("Bark"); }
};
```

The classic pre-Java-8 use was callbacks and listeners:

```java
button.setOnClickListener(new OnClickListener() {
    @Override public void onClick() { System.out.println("Clicked"); }
});
```

### Lambdas replaced most of this

```java
// anonymous class
Runnable r1 = new Runnable() {
    @Override public void run() { System.out.println("Running"); }
};

// lambda — same thing
Runnable r2 = () -> System.out.println("Running");
```

### When you still need an anonymous class

**1. More than one abstract method.** Lambdas only target functional interfaces; anonymous classes work with anything.

**2. Extending a class.** A lambda can only implement a functional interface — it can never extend an abstract or concrete class.

**3. Extra state or helper methods.** A lambda body is just the one method's logic; there's nowhere to put a field.

```java
Comparator<String> byLength = new Comparator<String>() {
    private int compareCount = 0;                 // extra state — impossible in a lambda

    @Override
    public int compare(String a, String b) {
        compareCount++;
        return a.length() - b.length();
    }
};
```

There's also a semantic difference worth knowing: inside an anonymous class, `this` refers to the anonymous instance. Inside a lambda, `this` refers to the **enclosing** instance — lambdas introduce no new scope for `this`.

Capture rules are the same as local classes: enclosing locals must be final or effectively final.

## The Cheat Sheet

| | Static Nested | Inner (non-static) | Local | Anonymous |
| --- | --- | --- | --- | --- |
| Needs an outer instance to create | No | **Yes** (`outer.new Inner()`) | No, but scoped to the method | Yes, if in an instance context |
| Access to outer's instance members | No — static only | Yes, including `private` | Yes | Yes |
| Access to enclosing method's locals | N/A | N/A | Yes — final/effectively final | Yes — final/effectively final |
| Has a name | Yes | Yes | Yes | **No** |
| Can declare constructors | Yes | Yes | Yes | **No** — only an initialiser block |
| Can declare `static` members | Yes | No (until Java 16) | No | No |
| Multiple methods / extra state | Yes | Yes | Yes | Yes |
| Typical use | Builder, `Map.Entry`, helpers | Iterators, outer-state helpers | Rare — method-local logic | One-off impls lambdas can't express |

## The Memory Leak Trap

An inner, local or anonymous class holds a **strong reference to its enclosing instance**. That's invisible in the source and very visible in a heap dump.

```java
class ReportService {
    private final byte[] largeCache = new byte[50_000_000];

    Runnable buildTask() {
        return new Runnable() {                  // ⚠ captures ReportService.this
            public void run() { System.out.println("done"); }
        };
    }
}

scheduler.scheduleAtFixedRate(service.buildTask(), ...);   // the task keeps the whole service alive
```

The `Runnable` looks tiny and does nothing with the outer object, but it pins the entire `ReportService` — including the 50 MB array — for as long as the scheduler holds it. Any long-lived listener, callback, cache entry or scheduled task built this way retains its enclosing object.

The fix is to remove the link:

```java
static class ReportTask implements Runnable {    // static — no outer reference
    private final String reportId;               // takes only what it needs
    ReportTask(String reportId) { this.reportId = reportId; }
    public void run() { ... }
}
```

The same reasoning applies to the double-brace initialisation idiom from [[2. Classes And Objects]] — `new ArrayList<>() {{ add("x"); }}` creates an anonymous subclass that holds the enclosing instance.

> 💡 **Interview**: Why prefer a static nested class over an inner class by default? → An inner class holds a hidden reference to its enclosing instance, which costs memory and can retain a large object graph if the inner instance outlives the outer one's usefulness. Make it non-static only when it genuinely needs the enclosing instance.

---

## What You'll Actually Use

- **Static nested** — common. Builders, nested config or DTO types, helper classes scoped to one outer class. This should be your default when nesting.
- **Inner (non-static)** — uncommon in backend and Spring code. Shows up in custom data structures (iterators) and heavily in Android, where adapters and listeners need the enclosing Activity's state.
- **Local** — rare. Occasionally in older code; almost always better as a lambda or an extracted class today.
- **Anonymous** — for the three lambda exceptions above, and in pre-Java-8 code everywhere. For a plain `Runnable` or `Comparator`, use a lambda.
