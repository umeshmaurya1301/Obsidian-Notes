# Object Relationships

---

## Short Notes

---

### 1. The Three Relationships

```text
Association   → "uses"                    weakest, no ownership
  └ Aggregation → "has-a", lives apart     weak ownership, independent lifecycle
  └ Composition → "has-a", dies with it    strong ownership, dependent lifecycle
```

- Aggregation and composition are **specialised forms of association**
- The distinguishing question is always **lifecycle**, not syntax

---

### 2. Association

- One class **uses or interacts with** another; neither owns the other's lifecycle
- Cardinality: one-to-one, one-to-many, many-to-many
- Directionality: unidirectional (one side knows) or bidirectional (both do)
- `Driver` and `Car` — each exists perfectly well without the other

---

### 3. Aggregation

- **Has-a with independent lifecycles** — weak ownership
- The contained object is created **outside** and passed in
- Destroy the container → the contained object survives
- `University` has `Department`s; `Team` has `Player`s
- UML: **hollow diamond ◇** on the container side

---

### 4. Composition

- **Has-a with dependent lifecycles** — strong ownership
- The contained object is created **inside** the owner and dies with it
- No external reference exists, so it can't outlive the container
- `Car` has an `Engine`; `House` has `Room`s; `Order` has `OrderLine`s
- UML: **filled diamond ◆**

---

### 5. The Code-Level Signal

```java
// COMPOSITION — created inside, never injected
class Car { private final Engine engine = new Engine(); }

// AGGREGATION — created outside, passed in
class University { void addDepartment(Department d) { departments.add(d); } }
```

- **Who calls `new`, and where** is the clearest tell

---

### 6. Side-by-Side

| | Association | Aggregation | Composition |
| --- | --- | --- | --- |
| Strength | Weakest — "uses" | Weak "has-a" | Strong "has-a" (owns) |
| Lifecycle | Independent | Independent | Dependent |
| Created | Externally, unrelated | Externally, then linked | Internally, by the owner |
| Survives owner? | Yes | Yes | No |
| Example | `Driver` ↔ `Car` | `University` ↔ `Department` | `Car` ↔ `Engine` |
| UML | Plain line | Hollow ◇ | Filled ◆ |

---

### 7. Composition vs Inheritance

| | Inheritance (is-a) | Composition (has-a) |
| --- | --- | --- |
| Coupling | Tight — to the parent's implementation | Loose — to a public interface |
| Bound at | Compile time, permanently | Runtime, swappable |
| Encapsulation | Leaks the parent's whole API | Exposes only what you delegate |
| Multiple sources | One superclass only | As many collaborators as you like |
| Testing | Must build the hierarchy | Inject mocks |

---

### 8. The Fragile Base Class Problem

```java
class Stack<T> extends ArrayList<T> { ... }
s.add(0, 99);   // inherited — the LIFO invariant is broken from outside
```

- Inheriting exposes every parent method, wanted or not
- `java.util.Stack extends Vector` is the JDK's own example of this mistake
- Composition fix: hold a `List` privately, expose only `push`/`pop`

---

### 9. Why Favour Composition

1. **No fragile base class** — you depend on a contract, not internals
2. **No deep rigid hierarchies** — assemble small focused pieces
3. **Runtime flexibility** — swap the collaborator; this *is* the Strategy pattern
4. **Sidesteps single inheritance** — compose as many objects as needed
5. **Testability** — inject mocks trivially

---

### 10. When Inheritance Is Still Right

- A genuine, stable **is-a** where the subtype is substitutable everywhere (LSP holds)
- Modelling a real hierarchy, not scavenging for code reuse
- `Shape` → `Circle` / `Square`; exception hierarchies; framework template methods
- The parent was **designed** for extension: documented, `final` where it matters

---

### 11. Spring DI Is Composition at Scale

- `@Service` classes **compose** dependencies; they don't extend framework base classes
- **IoC** = the container assembles the object graph instead of your code calling `new`
- Depend on the **interface**; the container picks the implementation
- `@Profile` / `@Qualifier` = Strategy pattern, wired declaratively
- **Trap**: in the strict UML sense DI is **association/aggregation**, not composition — the container creates the dependency separately, it can be shared, and the consumer doesn't own its lifecycle. "Composition" here means the *design* sense (composition over inheritance)

---

### 12. Constructor vs Field Injection

- **Constructor** ✅ — fields can be `final`, dependencies explicit, testable with plain `new`
- **Field** `@Autowired` ❌ — hidden dependencies, no `final`, needs reflection to test
- `@RequiredArgsConstructor` generates the constructor form
- A constructor with 8 parameters is the SRP smell doing its job

---

### 13. AOP Proxies

- `@Transactional` / `@Cacheable` wrap your bean in a **proxy** — composition, not inheritance
- Your class inherits nothing transaction-related; behaviour is layered around it
- JDK dynamic proxies (interface) or CGLIB subclass proxies under the hood
- Consequence: self-invocation inside the bean bypasses the proxy

---

### SDE-2 Interview Priority

**Must Know**: Association vs aggregation vs composition, The lifecycle test, Composition vs inheritance table, Fragile base class + `Stack` example, Why favour composition, When inheritance is still right

**Nice To Know**: UML diamonds, Strategy pattern as runtime composition, Spring DI as composition, Constructor vs field injection

**Advanced**: `java.util.Stack extends Vector` as a JDK mistake, AOP proxies and self-invocation, Aggregation vs composition in JPA cascade/orphan-removal terms

# Detailed Explanation

---

## Association

The umbrella term: one class **uses or interacts with** another, with neither owning the other's lifecycle.

```java
class Driver {
    private String name;
}

class Car {
    private Driver driver;      // Car knows about Driver — association
}
```

A `Driver` exists without a `Car`; a `Car` exists without a driver assigned. Neither creates or destroys the other. They are simply connected.

Associations are described along two axes:

**Cardinality**
- One-to-one — a `Person` has one `Passport`
- One-to-many — a `Teacher` teaches many `Student`s
- Many-to-many — `Student`s enrol in many `Course`s, each with many students

**Directionality**
- Unidirectional — only `Car` holds a `Driver` reference
- Bidirectional — both hold references to each other (and both must be kept in sync, which is where JPA bugs come from)

Aggregation and composition are both **stronger, more specific forms of association** — specifically the "has-a" cases where one object holds another as a field. So every aggregation is an association; not every association is an aggregation.

---

## Aggregation

A **has-a relationship with independent lifecycles** — weak ownership.

```java
class Department {
    private final String name;
    Department(String name) { this.name = name; }
}

class University {
    private final List<Department> departments = new ArrayList<>();

    void addDepartment(Department d) { departments.add(d); }   // just holds a reference
}
```

```java
Department cs = new Department("Computer Science");   // created independently
University u = new University();
u.addDepartment(cs);                                  // linked, not owned

// u goes out of scope and is collected — cs is still perfectly alive
Department stillValid = cs;
```

The `Department` was not created by the `University` and does not die with it. It could be moved to another university, or exist on its own.

**Analogies**: a `Library` has `Book`s — close the library and the books still exist, they move elsewhere. An `Orchestra` has `Musician`s — musicians join and leave, they aren't created by the orchestra.

**UML**: hollow diamond ◇ on the container side.

---

## Composition

A **has-a relationship with dependent lifecycles** — strong ownership. The contained object is created by the owner and cannot meaningfully outlive it.

```java
class Engine {
    private final int horsepower;
    Engine(int horsepower) { this.horsepower = horsepower; }
}

class Car {
    private final Engine engine;

    Car(int hp) {
        this.engine = new Engine(hp);   // created INSIDE — never passed in
    }
}
```

Once the `Car` is unreachable, so is its `Engine` — nothing else ever held a reference to it, so it is collected along with the car.

**Analogies**: a `House` has `Room`s — demolish the house and the rooms stop existing as entities. An `Order` has `OrderLine`s — a line item has no meaning outside its order.

**UML**: filled diamond ◆.

### The code-level signal

The clearest distinguisher is **who calls `new`, and where**:

```java
// COMPOSITION — the owner constructs it, nothing outside can hold it
class Car {
    private final Engine engine = new Engine();
}

// AGGREGATION — constructed elsewhere and handed in
class University {
    private final List<Department> departments = new ArrayList<>();
    void addDepartment(Department d) { departments.add(d); }
}
```

If the object arrives through a constructor parameter or setter, someone outside holds a reference — that's aggregation. If it's created internally and never leaks out, that's composition. A composition that leaks its part through a getter (without a defensive copy) has quietly become an aggregation.

If you work with JPA, the same distinction is what `cascade = ALL, orphanRemoval = true` expresses: delete the parent, delete the children. That's composition, spelled in ORM.

---

## Association vs Aggregation vs Composition

| | Association | Aggregation | Composition |
| --- | --- | --- | --- |
| Relationship strength | Weakest — general "uses" | Weak "has-a" | Strong "has-a" (owns) |
| Lifecycle dependency | Independent | Independent | Dependent — child dies with parent |
| Object creation | External, unrelated | External, then linked | Internal, by the owner |
| Can exist without the other? | Yes | Yes | Not meaningfully |
| Example | `Driver` and `Car` | `University` and `Department` | `Car` and `Engine` |
| UML | Plain line | Hollow diamond ◇ | Filled diamond ◆ |

**The mental shortcut:**

- **Association** = "uses" — a `Driver` uses a `Car`
- **Aggregation** = "has, but can live apart" — a `Team` has `Player`s; players transfer to other teams
- **Composition** = "has, and can't live apart" — a `Car` has an `Engine`; that engine exists only as part of that car

In LLD interviews (parking lot, library system, BookMyShow) this is the vocabulary you're expected to use while drawing the class diagram — say "the `ParkingLot` composes its `ParkingFloor`s, but aggregates `Vehicle`s" and you've answered the design question before writing a line of code.

## Composition vs Inheritance

Both reuse code; they differ in how much they couple you to what you reuse.

| | Inheritance ("is-a") | Composition ("has-a") |
| --- | --- | --- |
| Relationship | `Dog` **is-a** `Animal` | `Car` **has-a** `Engine` |
| Coupling | Tight — depends on the parent's internals | Loose — depends on a public interface |
| Bound at | Compile time; the parent can never change | Runtime; the collaborator can be swapped |
| Encapsulation | Leaks — the subclass inherits the parent's entire API | Preserved — the internal object is hidden |
| Multiple behaviours | One superclass only | Compose as many objects as needed |
| Testing | Hard — tied to a concrete parent | Easy — inject stubs and mocks |

### The fragile base class problem

```java
class Stack<T> extends ArrayList<T> {      // ❌ inheritance
    void push(T item) { add(item); }
    T pop() { return remove(size() - 1); }
}

Stack<Integer> s = new Stack<>();
s.push(1);
s.push(2);
s.add(0, 99);      // inherited from ArrayList — the LIFO invariant is broken from outside
s.remove(0);       // so is this
s.set(1, 42);      // and this
```

A `Stack` is not an `ArrayList`. By inheriting, you inherited **every** `ArrayList` method — including all the ones that let a caller bypass `push`/`pop` and corrupt the ordering. You can't remove them, and you can't stop anyone from calling them.

This isn't hypothetical: `java.util.Stack extends Vector` in the JDK itself, with exactly this flaw, and is now a standing example of what not to do. (`ArrayDeque` is the modern replacement.)

### The composition fix

```java
class Stack<T> {
    private final List<T> items = new ArrayList<>();   // ✅ HAS a list

    void push(T item) { items.add(item); }
    T pop() { return items.remove(items.size() - 1); }
    boolean isEmpty() { return items.isEmpty(); }
}

Stack<Integer> s = new Stack<>();
s.push(1);
s.add(0, 99);      // ❌ compile error — no such method
```

`Stack` now controls its entire public contract. The `ArrayList` is an implementation detail — it can be swapped for an `ArrayDeque` or a linked structure without any caller noticing. That is what encapsulation is supposed to look like.

---

## Why Favour Composition Over Inheritance

The advice comes from both *Design Patterns* (Gang of Four) and *Effective Java* (Bloch). Five concrete reasons:

### 1. It avoids the fragile base class problem

With inheritance, a subclass depends on the parent's **internal implementation**, not just its public contract — so a change inside the parent can break descendants that never changed:

```java
class CountingList<E> extends ArrayList<E> {
    private int addCount = 0;

    @Override public boolean add(E e) { addCount++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);      // ⚠ ArrayList.addAll internally calls add()
    }                                //    → every element counted twice
}
```

Nothing here is wrong on its face. The bug is that `addAll` happens to be implemented in terms of `add` — an internal detail the subclass had no right to know, and one a future JDK could change in either direction. With composition you'd delegate to a `List` and count in one place.

### 2. It avoids deep, rigid hierarchies

`Animal → Mammal → Carnivore → Dog → Puppy` looks tidy until a requirement doesn't fit the tree. Every new axis of variation (diet, habitat, legality as a pet) either multiplies the hierarchy or forces an awkward placement. Composition builds behaviour by assembling small, focused pieces along whatever axes you actually need.

### 3. It gives runtime flexibility — the Strategy pattern

```java
interface PaymentStrategy { void pay(long amountPaise); }

class UpiPayment implements PaymentStrategy {
    public void pay(long amountPaise) { System.out.println("Paid via UPI: " + amountPaise); }
}
class CardPayment implements PaymentStrategy {
    public void pay(long amountPaise) { System.out.println("Paid via card: " + amountPaise); }
}

class Checkout {
    private PaymentStrategy strategy;                        // composed

    Checkout(PaymentStrategy strategy) { this.strategy = strategy; }
    void setStrategy(PaymentStrategy strategy) { this.strategy = strategy; }   // swappable

    void process(long amountPaise) { strategy.pay(amountPaise); }
}
```

```java
Checkout c = new Checkout(new UpiPayment());
c.process(10_000);
c.setStrategy(new CardPayment());    // behaviour changed while running
c.process(20_000);
```

With inheritance, the "strategy" is decided by which class you extended — fixed at compile time, unchangeable per request or per environment. Composition makes it a field, and a field can be reassigned. **The Strategy pattern is nothing more than composition plus an interface.**

### 4. It sidesteps single inheritance

A class can extend one class but compose as many objects as it likes:

```java
class Car {
    private final Engine engine;
    private final Gps gps;
    private final SoundSystem sound;
    // behaviour from three sources, no diamond problem, no hierarchy
}
```

### 5. It makes testing easy

```java
Checkout c = new Checkout(mockPaymentStrategy);   // that's the whole setup
```

Composed dependencies — especially behind interfaces — can be replaced with mocks or fakes in one line. An inherited dependency baked into a base class has no seam to substitute at.

### When inheritance is still the right call

Inheritance is right when there is a genuine, stable **is-a** relationship, the subtype is substitutable everywhere the parent is used (Liskov holds cleanly), and you are modelling a real hierarchy rather than scavenging for reuse:

```java
abstract class Shape { abstract double area(); }
class Circle extends Shape { ... }
class Square extends Shape { ... }
```

Every `Circle` genuinely *is* a `Shape` and works anywhere a `Shape` is expected. Exception hierarchies, framework template methods and sealed type families are the other legitimate cases. The extra condition: the parent must be **designed** for extension — documented self-use, `final` on everything that must not be overridden.

**The line for an interview**: *"I use inheritance when there's a genuine, stable is-a relationship with substitutability — a `Shape` hierarchy. I use composition when I want to reuse behaviour, swap implementations at runtime, or avoid coupling to a parent's internals — which is most real service and business-logic design, and is why Spring's DI model is built entirely on composition."*

## Composition at Scale — Spring Dependency Injection

Spring's entire DI model is "favour composition over inheritance" applied to a whole application. A `@Service` doesn't extend a framework base class to gain behaviour — it declares the objects it depends on, and the container supplies them.

```java
@Service
public class TransactionService {
    private final ValidationEngine validationEngine;   // composed
    private final KafkaProducer kafkaProducer;         // composed
    private final RedisCache redisCache;               // composed

    public TransactionService(ValidationEngine validationEngine,
                              KafkaProducer kafkaProducer,
                              RedisCache redisCache) {
        this.validationEngine = validationEngine;
        this.kafkaProducer = kafkaProducer;
        this.redisCache = redisCache;
    }

    public void processTransaction(Transaction txn) {
        validationEngine.validate(txn);
        redisCache.checkIdempotency(txn.getId());
        kafkaProducer.publish(txn);
    }
}
```

`TransactionService` **has-a** validator, **has-a** producer, **has-a** cache. It extends nothing. The only difference from hand-written composition is who assembles the graph.

### But is Spring DI *strictly* composition? — the trap

"Composition" is used in two senses, and an interviewer can pin you on the difference.

- **Design sense** ("favour composition over inheritance"): build behaviour by holding references instead of extending. Spring DI is 100% this — the section above.
- **UML sense** (association / aggregation / composition from the top of this note): composition means **lifecycle ownership** — the part is created inside the whole and dies with it.

Measured against the UML definition, Spring DI is **not** composition:

```java
@Service
class OrderService {
    private final PaymentService paymentService;

    OrderService(PaymentService paymentService) {      // handed in, not created here
        this.paymentService = paymentService;
    }
}
```

```text
Spring container
   ├──▶ PaymentService bean          (created first, on its own)
   └──▶ OrderService bean
            └── reference to PaymentService
```

- `PaymentService` exists **independently** — the container creates it as its own bean
- It is typically a singleton **shared** by many consumers, not owned by one
- Spring, not `OrderService`, manages both lifecycles
- Destroying `OrderService` does nothing to `PaymentService`

Apply the code-level signal from earlier — *who calls `new`, and where* — and the answer is "the container, elsewhere". That is the aggregation/association shape, not the composition shape. Most developers simply say `OrderService` **is associated with** `PaymentService`, because all it holds is a reference; the ownership semantics of true composition are absent.

Same class, two wirings, two different relationships:

```java
// UML composition — Car creates and owns its Engine; Engine has no life of its own
class Car {
    private final Engine engine = new Engine();
}

// Spring DI — Engine is a bean, may be shared, exists without any Car → association/aggregation
@Component
class Car {
    private final Engine engine;
    Car(Engine engine) { this.engine = engine; }
}
```

> 💡 **Interview**: *Does Spring Boot use composition?* → "Spring uses dependency injection, which creates **associations** between beans. The container manages each bean's lifecycle independently and a dependency can exist without — and be shared beyond — the bean consuming it, so in UML terms it's association or aggregation, not strict composition, which implies lifecycle ownership. In the *design* sense — composition over inheritance — DI is exactly that: a `@Service` holds references instead of extending a framework class."

### What "Inversion of Control" actually inverts

```java
// Manual composition — your code controls assembly
ValidationEngine validator = new UpiValidationEngine();
KafkaProducer producer = new KafkaProducer(kafkaConfig);
RedisCache cache = new RedisCache(redisConfig);
TransactionService service = new TransactionService(validator, producer, cache);
```

```java
// IoC — the container controls assembly
@Service
public class TransactionService {
    public TransactionService(ValidationEngine v, KafkaProducer k, RedisCache c) { ... }
}
```

The composition is identical. What's **inverted** is the *responsibility for assembly*: instead of your class deciding how to obtain its dependencies (`new` scattered through the codebase), the container constructs the graph and hands you a finished object. That's why DI is described as composition promoted to an architectural principle.

### Program to interfaces

```java
public interface ValidationEngine { void validate(Transaction txn); }

@Component
public class UpiValidationEngine implements ValidationEngine { ... }
```

`TransactionService` depends on the **interface**. Swapping in a `CardValidationEngine` changes nothing in `TransactionService` — which is exactly the loose coupling composition promises, and exactly what inheritance cannot give you, since the parent class is fixed at compile time.

### Profiles and qualifiers = Strategy, declared

```java
@Component @Profile("upi")  class UpiValidationEngine  implements ValidationEngine { ... }
@Component @Profile("card") class CardValidationEngine implements ValidationEngine { ... }
```

Same runtime swap as `setStrategy()`, moved into configuration.

### Testability

```java
@Test
void processesTransaction() {
    ValidationEngine validator = mock(ValidationEngine.class);
    KafkaProducer producer = mock(KafkaProducer.class);
    RedisCache cache = mock(RedisCache.class);

    TransactionService service = new TransactionService(validator, producer, cache);
    service.processTransaction(new Transaction(...));

    verify(validator).validate(any());
}
```

No Spring context, no Kafka broker, no Redis. If `TransactionService` had instead *inherited* from an `AbstractTransactionProcessor` with Kafka and Redis logic baked in, there'd be no seam to substitute at — you'd be testing against the real thing or not at all.

### No fragile base class across the framework boundary

Older frameworks did require inheritance — Struts made you extend `Action`. Every internal change to that base class could break your business logic. Because Spring composes instead, your `@Service` depends only on interfaces it was handed; Spring's internals can evolve freely as long as the contracts hold.

## Constructor vs Field Injection

```java
// ❌ field injection
@Service
public class TransactionService {
    @Autowired private ValidationEngine validationEngine;
}

// ✅ constructor injection
@Service
public class TransactionService {
    private final ValidationEngine validationEngine;

    public TransactionService(ValidationEngine validationEngine) {
        this.validationEngine = validationEngine;
    }
}
```

Constructor injection wins for reasons that are all composition discipline:

- **Fields can be `final`** — the collaborator is fixed at construction and can't be swapped by accident.
- **Dependencies are explicit** — the constructor signature is the honest list of what this class needs. You cannot construct the object in an invalid state.
- **No reflection needed in tests** — `new TransactionService(mock)` just works; field injection needs Spring or `ReflectionTestUtils`.
- **No circular-dependency surprises** — a cycle fails loudly at startup rather than half-initialising.

Since Spring 4.3 the `@Autowired` annotation is optional on a single constructor, and Lombok's `@RequiredArgsConstructor` generates the whole thing from the `final` fields.

A useful side effect: a constructor that grows to eight parameters is uncomfortable to read — which is the Single Responsibility Principle telling you the class does too much. Field injection hides that signal.

## AOP Proxies — Composition at the Framework Level

When Spring injects a `@Transactional` or `@Cacheable` bean, it usually injects a **proxy** wrapping your real object:

```java
@Service
public class TransactionService {
    @Transactional
    public void processTransaction(Transaction txn) { ... }
}
```

```text
caller ──▶ Proxy ──▶ begin transaction
                     TransactionService.processTransaction(txn)   ← your real bean
                     commit / rollback
```

Your class inherits nothing transaction-related. The cross-cutting behaviour is **layered around** it at runtime — a JDK dynamic proxy when the bean implements an interface, a CGLIB subclass proxy otherwise. Composition applied to framework concerns, not just your own object graph.

Two consequences worth knowing:

- **Self-invocation bypasses the proxy.** Calling `this.processTransaction(...)` from another method of the same bean goes straight to the real object, so `@Transactional` never fires. Fix by injecting the bean into itself, or by moving the method to a separate bean.
- **`getClass()` reports the proxy**, not your class — relevant to the `getClass()` discussion in [[9. The Object Class]].

> 💡 **Interview**: How does Spring apply `@Transactional` without your class inheriting anything? → It wraps the bean in a proxy that composes transaction management around the real object. It's runtime composition, which is why self-invocation inside the bean skips it entirely.

## The Direct Mapping

| Composition principle | Spring equivalent |
| --- | --- |
| "Has-a", not "is-a" | `@Service` composes collaborators; extends no framework class |
| Program to an interface | Constructor params typed as interfaces; container picks the impl |
| Swap behaviour at runtime | `@Profile`, `@Qualifier`, multiple implementations |
| Testability through injection | `new Service(mocks)` in a plain unit test |
| Avoid the fragile base class | Business logic never inherits framework internals |
| Assemble small focused pieces | The IoC container builds the whole graph from small beans |
