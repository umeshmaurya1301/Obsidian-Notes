# Exception Handling

---

## Short Notes

---

### 1. Exceptions Are Just Classes

- No special language machinery — **inheritance and polymorphism applied to failures**
- `catch (PaymentException e)` catches every subtype, by dynamic dispatch
- A custom exception is an object carrying state, not a decorated string
- Everything below follows from that one fact

---

### 2. The Hierarchy

```text
              Throwable
             ╱         ╲
        Error           Exception
          │            ╱         ╲
  OutOfMemoryError  RuntimeException   IOException
  StackOverflowError    │              SQLException
                   NullPointerException  ClassNotFoundException
                   IllegalArgumentException
                   ClassCastException
```

- `Throwable` has exactly two direct subclasses: `Error` and `Exception`
- It supplies `getMessage()`, `getCause()`, `printStackTrace()`, the stack trace

---

### 3. `Error`

- Serious problems **outside the application's control** — JVM-level
- `OutOfMemoryError`, `StackOverflowError`, `NoClassDefFoundError`
- Convention: **don't catch them** — the process is usually unrecoverable
- Catching broadly here masks real failures instead of fixing them

---

### 4. Checked Exceptions

- Extends `Exception` but **not** `RuntimeException`
- The compiler forces you to **catch or declare** — hence "checked"
- `IOException`, `SQLException`, `ClassNotFoundException`
- Intent: expected external conditions with a real recovery path

---

### 5. Unchecked Exceptions

- Extends `RuntimeException`
- No compiler enforcement — propagates freely until something catches it
- `NullPointerException`, `IllegalArgumentException`, `ClassCastException`
- Intent: **programming errors** — fix the code, don't catch the bug

---

### 6. Checked vs Unchecked

| | Checked | Unchecked |
| --- | --- | --- |
| Extends | `Exception` (not `RuntimeException`) | `RuntimeException` |
| Compiler | Must catch or declare | No enforcement |
| Represents | Expected external condition | Programming bug |
| Handling | Real recovery, or deliberate propagation | Fix the cause; catch at a boundary |
| Override rule | Can't broaden or add checked types | No restriction |

---

### 7. The Checked-Exception Controversy

- A genuinely contested design choice — C#, Kotlin and Python have no equivalent
- Forces `throws` boilerplate through layers that can't act on the failure
- Encourages the worst anti-pattern of all: `catch (IOException e) { }`
- Spring's own `DataAccessException` hierarchy is **entirely unchecked**, on purpose

---

### 8. Common Unchecked Exceptions

| Exception | Cause |
| --- | --- |
| `NullPointerException` | Dereferencing `null` |
| `ArrayIndexOutOfBoundsException` | Index outside the array |
| `ArithmeticException` | Integer divide by zero |
| `ClassCastException` | Invalid downcast |
| `IllegalArgumentException` | Argument violates the method's contract |
| `IllegalStateException` | Called at the wrong time / wrong object state |
| `NumberFormatException` | `Integer.parseInt("abc")` — extends `IllegalArgumentException` |
| `ConcurrentModificationException` | Mutating a collection while iterating it |
| `UnsupportedOperationException` | Operation deliberately not supported |

---

### 9. Custom Exceptions

```java
class InsufficientBalanceException extends Exception {   // checked
    private final long shortfallPaise;
    public InsufficientBalanceException(String msg, long shortfall) {
        super(msg);
        this.shortfallPaise = shortfall;
    }
    public long getShortfallPaise() { return shortfallPaise; }
}
```

- Extend `Exception` → checked; extend `RuntimeException` → unchecked
- That choice is a **design decision**, not a default

---

### 10. Choosing Checked vs Unchecked

**Checked when**: the failure is a normal outcome of calling the method, and the caller has a real, distinct recovery action.

**Unchecked when**: it signals an invalid state or bug, or it's handled centrally and `throws` clutter through every layer buys nothing.

---

### 11. Domain Exception Hierarchy

```java
abstract class PaymentException extends RuntimeException {
    private final String errorCode;
}
class InsufficientBalanceException extends PaymentException { }
class InvalidUpiIdException        extends PaymentException { }
class TransactionTimeoutException  extends PaymentException { }
```

- One base type → one `@ExceptionHandler(PaymentException.class)` catches all
- Add a subtype a year later → handled automatically. **OCP via polymorphism**

---

### 12. Always Preserve the Cause

```java
throw new PaymentException("routing failed", e);   // ✅ chained
throw new PaymentException("routing failed");      // ❌ original stack trace lost
```

- `getCause()` is what makes a wrapped exception debuggable
- Never log-and-rethrow the same exception — you get the same trace twice

---

### 13. The OOP Principles At Work

- **Inheritance** — the hierarchy is an ordinary class hierarchy, nothing special
- **Polymorphism** — one `catch` on the base type handles every subtype
- **Encapsulation** — the exception carries structured context (`errorCode`, `shortfall`)
- **OCP + LSP** — new exception types need no change to existing handlers

# Detailed Explanation

---

## Exceptions Are Just Classes

The key insight, and the reason this topic sits in an OOP note at all: **exception handling isn't a bolted-on language mechanism — it's inheritance and polymorphism applied to error conditions.**

`catch (PaymentException e)` matches any subtype of `PaymentException` through the same runtime type check that drives `instanceof`. A custom exception is a class with fields, constructors and getters. Designing an exception hierarchy is designing a class hierarchy, with the same trade-offs.

---

## The Hierarchy

```text
                        Throwable
                       ╱          ╲
                  Error            Exception
                 ╱     ╲          ╱          ╲
  OutOfMemoryError  StackOverflow  RuntimeException   IOException
                                    │                 SQLException
                          NullPointerException        ClassNotFoundException
                          ArithmeticException          ← CHECKED
                          IllegalArgumentException
                          ClassCastException
                             ← UNCHECKED
```

`Throwable` is the root — the only type that can appear in a `throw` or a `catch`. It supplies the shared machinery: a message, an optional **cause** for chaining, and a stack trace captured at construction time.

It has exactly two direct subclasses.

### `Error` — don't catch these

```java
class OutOfMemoryError   extends VirtualMachineError { }   // → Error
class StackOverflowError extends VirtualMachineError { }   // → Error
```

Serious problems outside the application's control: the JVM out of heap, a stack blown by infinite recursion, a class-loading failure. By convention you **don't catch them** — the process is usually in an unrecoverable state, and a broad `catch (Throwable t)` that swallows an `OutOfMemoryError` turns a clear crash into a mysterious, half-working service.

The narrow exception is a top-level handler that logs and then deliberately shuts down, which some frameworks do.

### `Exception` — conditions the application can handle

This splits into two categories, and the split is defined **by inheritance path, not by naming**. That is the mechanism, and it's the most-tested part of this topic.

---

## Checked Exceptions

An exception is **checked** if it extends `Exception` but **not** `RuntimeException`. The compiler forces every caller to either catch it or declare it.

```java
void readFile(String path) throws IOException {         // must declare
    FileReader fr = new FileReader(path);               // constructor declares FileNotFoundException
}
```

```java
void process() {
    readFile("data.txt");        // ❌ unreported exception IOException; must be caught or declared
}

void process() throws IOException {      // fix 1 — propagate deliberately
    readFile("data.txt");
}

void process() {                         // fix 2 — handle here
    try {
        readFile("data.txt");
    } catch (IOException e) {
        log.warn("could not read data.txt", e);
    }
}
```

### The design intent

Checked exceptions were meant to represent **expected, recoverable external conditions**: a file might not exist, a network call might time out, a database might be unreachable. These aren't bugs — they're realities the code must acknowledge. Forcing acknowledgement at compile time was meant to stop you forgetting.

### The controversy

This is a genuinely contested design decision, and worth being able to discuss. C#, Kotlin and Python deliberately have no equivalent. The criticisms:

**Boilerplate through layers that can't act.** A `throws SQLException` on a DAO propagates up through the service and controller, each of which must declare it while having no meaningful recovery.

**They're trivially "handled" badly.**

```java
try {
    readFile("data.txt");
} catch (IOException e) { }      // ❌ compiles, satisfies the compiler, hides the failure entirely
```

The empty catch block is the single worst pattern in Java, and checked exceptions are what motivate it.

**The ecosystem moved away from them.** Spring's entire `DataAccessException` hierarchy is unchecked, deliberately — it wraps `SQLException` so that no method up the stack needs a `throws` clause for something handled centrally. Most modern Java libraries follow suit.

The balanced position: checked exceptions are right when the caller genuinely has a distinct recovery path at that call site. They're wrong when the answer is always "log it and fail the request", which is most of the time in a web service.

---

## Unchecked Exceptions

An exception is **unchecked** if it extends `RuntimeException`. The compiler doesn't check anything — no `throws`, no `try`, no complaint.

```java
void process(int[] arr) {
    System.out.println(arr[10]);    // may throw ArrayIndexOutOfBoundsException — compiles fine
}
```

### The design intent

Unchecked exceptions represent **programming errors** — things that shouldn't happen in a correct program. An NPE means a missing null check. An `ArrayIndexOutOfBoundsException` means the loop bounds are wrong. An `IllegalArgumentException` means the caller broke the contract.

The philosophy: you shouldn't be forced to defensively catch bugs at every call site. You should **fix the code**, and let a bug fail loudly with a clear stack trace during development.

### The ones worth knowing by name

| Exception | Typical cause |
| --- | --- |
| `NullPointerException` | Calling a method or reading a field on `null` |
| `ArrayIndexOutOfBoundsException` | Index outside the array bounds |
| `ArithmeticException` | Integer division by zero (`1/0`; note `1.0/0` gives `Infinity`) |
| `ClassCastException` | Invalid downcast — see [[7. Polymorphism Deep Dive]] |
| `IllegalArgumentException` | Argument violates the method's contract |
| `IllegalStateException` | Method called at an inappropriate time |
| `NumberFormatException` | `Integer.parseInt("abc")` — a subclass of `IllegalArgumentException` |
| `ConcurrentModificationException` | Structurally modifying a collection while iterating |
| `UnsupportedOperationException` | An operation the implementation deliberately refuses |

Since Java 14, **helpful NullPointerExceptions** are on by default: the message names the exact expression that was null (`Cannot invoke "Payment.getAmount()" because "payment" is null`), which removes most of the guesswork on a chained call.

---

## Checked vs Unchecked

| | Checked | Unchecked |
| --- | --- | --- |
| Extends | `Exception`, not `RuntimeException` | `RuntimeException` |
| Compiler enforcement | Must catch or declare | None |
| Represents | Expected external condition | Programming bug / logic error |
| Examples | `IOException`, `SQLException` | `NullPointerException`, `IllegalArgumentException` |
| Typical handling | Real recovery logic, or deliberate propagation | Fix the cause; catch at a boundary for logging |
| Overriding rule | Cannot throw broader or new checked types | No restriction at all |

That last row connects back to [[4. Inheritance]] — the reason an override can't broaden a checked exception is that callers holding a parent-typed reference only handle what the parent declared. Unchecked exceptions carry no such promise, so they're unrestricted.

---

## Custom Exceptions

You define one by extending `Exception` (checked) or `RuntimeException` (unchecked). **That choice is the design decision**, and the interviewer's follow-up.

### Checked

```java
class InsufficientBalanceException extends Exception {
    private final long shortfallPaise;

    public InsufficientBalanceException(String message, long shortfallPaise) {
        super(message);                       // hand the message to Throwable
        this.shortfallPaise = shortfallPaise;
    }

    public long getShortfallPaise() { return shortfallPaise; }
}
```

```java
void withdraw(long amountPaise, long balancePaise) throws InsufficientBalanceException {
    if (amountPaise > balancePaise) {
        throw new InsufficientBalanceException("insufficient funds", amountPaise - balancePaise);
    }
}

try {
    withdraw(1000_00, 500_00);
} catch (InsufficientBalanceException e) {
    log.info("{} short by {}", e.getMessage(), e.getShortfallPaise());
}
```

Note the `shortfallPaise` field — this is encapsulation doing real work. The exception carries **structured context** the handler can act on, not just a string a human has to parse.

### Unchecked

```java
class InvalidTransactionException extends RuntimeException {
    public InvalidTransactionException(String message) { super(message); }
}

void validate(Transaction txn) {
    if (txn.getAmountPaise() <= 0) {
        throw new InvalidTransactionException("amount must be positive");   // no throws anywhere
    }
}
```

### How to decide

**Make it checked when:**

- The failure is a **normal, expected outcome** of calling the method, and callers should be made to think about it.
- There's a **real, distinct recovery action** at the call site — retry, fall back, show a specific message.
- `InsufficientBalanceException` fits: "the user doesn't have enough money" is core business logic with a defined path, not a bug.

**Make it unchecked when:**

- It represents an **invalid state or a programming error** that callers can't sensibly recover from at each call site.
- It will be **handled centrally anyway**, so `throws` clutter through service → controller → filter buys nothing.
- `InvalidTransactionException` fits: a malformed transaction means bad upstream validation or hostile input, best handled once.

## A Domain Exception Hierarchy

The pattern worth being able to draw:

```java
abstract class PaymentException extends RuntimeException {
    private final String errorCode;

    protected PaymentException(String message, String errorCode) {
        super(message);
        this.errorCode = errorCode;
    }

    protected PaymentException(String message, String errorCode, Throwable cause) {
        super(message, cause);                          // preserve the original
        this.errorCode = errorCode;
    }

    public String getErrorCode() { return errorCode; }
}

class InsufficientBalanceException extends PaymentException {
    public InsufficientBalanceException(String m) { super(m, "ERR_INSUFFICIENT_BALANCE"); }
}
class InvalidUpiIdException extends PaymentException {
    public InvalidUpiIdException(String m) { super(m, "ERR_INVALID_UPI_ID"); }
}
class TransactionTimeoutException extends PaymentException {
    public TransactionTimeoutException(String m, Throwable cause) { super(m, "ERR_TXN_TIMEOUT", cause); }
}
```

```java
@RestControllerAdvice
class GlobalExceptionHandler {

    @ExceptionHandler(PaymentException.class)          // catches EVERY subtype
    ResponseEntity<ErrorResponse> handle(PaymentException e) {
        return ResponseEntity.badRequest()
                             .body(new ErrorResponse(e.getErrorCode(), e.getMessage()));
    }
}
```

Three things are working at once here:

- The exceptions are **unchecked**, so business logic stays free of `throws` clauses all the way up.
- One handler catches the **base type**, and every subtype is dispatched to it polymorphically.
- Adding `SettlementMismatchException` next quarter requires **no change** to the handler — that's OCP, enforced by LSP.

The `errorCode` field is what lets the handler produce a machine-readable response without a `switch` on exception types.

---

## Always Preserve the Cause

```java
try {
    switchClient.route(payment);
} catch (SocketTimeoutException e) {
    throw new TransactionTimeoutException("switch timed out", e);   // ✅ chained
}
```

```java
    throw new TransactionTimeoutException("switch timed out");      // ❌ original trace gone
```

`Throwable(String, Throwable)` stores the cause, and `getCause()` retrieves it. A stack trace prints the whole chain as `Caused by: ...`, which is usually the only thing that tells you *where* the failure actually started. Wrapping without chaining throws away the only useful diagnostic.

Two related habits:

- **Don't log and rethrow the same exception** — you get the same stack trace twice in the logs, from different places, and it looks like two failures. Either handle it or propagate it, not both.
- **Don't catch what you can't handle.** `catch (Exception e)` in the middle of a call stack usually converts a clear failure into a confusing one.

> 💡 **Interview**: When would you make a custom exception checked? → When the caller has a genuinely distinct recovery path at the call site, like insufficient balance. If the answer at every layer is "log it and fail the request", make it unchecked and handle it centrally — that's why Spring's own `DataAccessException` hierarchy is unchecked.

---

## The OOP Principles At Work

- **Inheritance** — `Throwable → Exception → RuntimeException → PaymentException → InvalidUpiIdException` is an ordinary class hierarchy. Nothing about it is special-cased by the language.
- **Polymorphism** — `catch (PaymentException e)` resolves against the thrown object's runtime type. That's the same dynamic type check as `instanceof`, applied to control flow.
- **Encapsulation** — a custom exception bundles the failure's context as private fields with accessors. It's an object carrying state, not a formatted string.
- **OCP and LSP** — a new subtype slots into every existing handler without modification, precisely because every subtype honours the base type's contract.

**The summary line**: *"Exceptions are just a class hierarchy, so the OOP principles apply directly. I make domain exceptions unchecked under a common base class, so business logic stays free of `throws` clutter and a single `@RestControllerAdvice` handler catches every subtype — new exception types are handled automatically, which is polymorphism and OCP together. I reserve checked exceptions for cases with a genuinely different recovery path at the call site."*
