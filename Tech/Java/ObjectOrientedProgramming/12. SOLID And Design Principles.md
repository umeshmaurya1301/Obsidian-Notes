# SOLID And Design Principles

---

## Short Notes

---

### 1. The Five, In One Line Each

| | Principle | One line |
| --- | --- | --- |
| **S** | Single Responsibility | One reason to change |
| **O** | Open/Closed | Open for extension, closed for modification |
| **L** | Liskov Substitution | A subtype must be usable wherever the parent is |
| **I** | Interface Segregation | Many small interfaces beat one fat one |
| **D** | Dependency Inversion | Depend on abstractions, not concretions |

> Interviewers test whether you can **spot a violation in code** and fix it — not recite definitions.

---

### 2. SRP — Single Responsibility

- One class, one **reason to change** — one axis of change, not one method
- Violation smell: a class touching business rules **and** DB **and** email **and** PDFs
- Fix: split into `SalaryCalculator`, `EmployeeRepository`, `EmailService`, `PayslipGenerator`
- Controller / Service / Repository layering **is** SRP at the architecture level

---

### 3. OCP — Open/Closed

- Add new behaviour **without editing existing, tested code**
- Violation smell: an `if/else` or `switch` on a type that grows with every feature
- Fix: an interface + one implementation per case — new case = new class, zero edits
- Achieved almost entirely through **abstraction + polymorphism**

---

### 4. LSP — Liskov Substitution

- A subtype must honour the **behavioural contract** the parent's callers rely on
- Violations: `Square extends Rectangle`; `Penguin.fly()` throwing
- Rule: overriding to throw or to change the caller's expected outcome means the **hierarchy is wrong**
- Compiler-enforced parts: can't narrow access, can't broaden checked exceptions — both exist **because of LSP**: a child must not make the parent's contract stricter
- Narrower exception (`FileNotFoundException` for `IOException`) and covariant return are allowed — the caller's existing code still works
- Behavioural half is on you: don't strengthen preconditions, don't weaken postconditions

---

### 5. ISP — Interface Segregation

- No client should be forced to depend on methods it doesn't use
- Violation smell: `UnsupportedOperationException` stubs in an implementation
- Fix: split `Worker` into `Workable` / `Eatable` / `Sleepable`
- The JDK does this: `Comparable`, `Runnable`, `Serializable` are all tiny

---

### 6. DIP — Dependency Inversion

- High-level modules and low-level modules **both** depend on an abstraction
- Violation: `private MySQLDatabase db = new MySQLDatabase();` inside `UserService`
- Fix: depend on a `Database` interface; inject the implementation
- Inverts the arrow: the detail now points at the abstraction

---

### 7. DIP ≠ DI

- **DIP** = the design principle (depend on abstractions)
- **DI** = one technique to achieve it (pass dependencies in, don't `new` them)
- You can do DI badly — injecting a **concrete** class honours DI, not DIP
- You can honour DIP with no framework at all — just pass interface-typed objects

---

### 8. DRY — Don't Repeat Yourself

- Every piece of knowledge has **one unambiguous representation**
- The cost of duplication is drift: fix it in three places, miss the fourth
- Extract to a shared validator / helper / constant
- Careful: two pieces of code that merely *look* alike aren't duplication

---

### 9. KISS — Keep It Simple

- Prefer the simplest solution that actually solves the problem
- A factory + interface hierarchy for `n % 2 == 0` is not "good OOP", it's noise
- Often in **tension with over-applied SOLID** — sometimes an `if` is correct
- Readability is a feature

---

### 10. YAGNI — You Aren't Gonna Need It

- Don't build for hypothetical future requirements
- Speculative parameters and hooks add test surface and bug surface for nothing
- Tension with OCP, resolved: OCP is **structural** openness, YAGNI forbids **speculative features**
- Use an interface instead of a switch ✅ | add six unused parameters ❌

---

### 11. Coupling

- How much one module depends on another's internals
- **Tight**: `new MySQLDatabase()` inside the service — a swap forces edits
- **Loose**: depends on a `Database` interface — implementation changes don't ripple
- Goal: **low coupling**; DIP, composition and interfaces all aim at it

---

### 12. Cohesion

- How closely related one class's responsibilities are
- **Low**: `Employee` doing salary + DB + email + PDF
- **High**: `SalaryCalculator` where every method is about computing salary
- Goal: **high cohesion**; SRP and ISP produce it directly

---

### 13. How They Connect

| Principle | Primarily improves |
| --- | --- |
| SRP | Cohesion |
| OCP | Extensibility without touching tested code |
| LSP | Correctness of polymorphic substitution |
| ISP | Interface cohesion, avoids irrelevant dependencies |
| DIP | Coupling |
| DRY | Maintainability |
| KISS | Readability |
| YAGNI | Avoided waste |

> All of it converges on: **high cohesion within, low coupling between.**

---

### SDE-2 Interview Priority

**Must Know**: All five SOLID with a violation→fix example each, LSP violations (Square/Rectangle, Penguin), DIP vs DI, Coupling vs cohesion, OCP via polymorphism

**Nice To Know**: DRY/KISS/YAGNI and the tensions between them, ISP mirrored in the JDK's tiny interfaces, SRP as the layered architecture rationale

**Advanced**: OCP vs YAGNI trade-off, LSP preconditions/postconditions/invariants formally, When to deliberately violate a principle

# Detailed Explanation

---

## S — Single Responsibility Principle

**A class should have only one reason to change.**

The common misreading is "a class should do one thing", which people take to mean one method. The real unit is an **axis of change**: if two different business events would each force you to edit this class, it has two responsibilities.

### Violation

```java
class Employee {
    String name;
    long salaryPaise;

    void calculateSalary()      { /* payroll rules        */ }   // changes when payroll policy changes
    void saveToDatabase()       { /* JDBC / JPA           */ }   // changes when the DB changes
    void sendEmail(String msg)  { /* SMTP                 */ }   // changes when the mail provider changes
    void generatePayslipPdf()   { /* iText / PDFBox       */ }   // changes when the report format changes
}
```

Four unrelated reasons to edit one file. Migrating from MySQL to Postgres now means touching a class that is conceptually about *an employee*. Worse, everyone who touches any of those four concerns touches the same file — merge conflicts, and a test suite where a PDF change can break payroll.

### Fix

```java
class Employee {                       // pure state
    String name;
    long salaryPaise;
}

class SalaryCalculator   { long calculate(Employee e)      { ... } }
class EmployeeRepository { void save(Employee e)           { ... } }
class EmailService       { void send(String to, String m)  { ... } }
class PayslipGenerator   { byte[] generatePdf(Employee e)  { ... } }
```

Each class now has exactly one axis of change. This is also precisely why a Spring service splits into `Controller` / `Service` / `Repository` — that layering *is* SRP applied at the architecture level, with the HTTP concern, the business rules and the persistence concern each free to change independently.

**Soundbite**: *"SRP isn't about a class having one method — it's about one axis of change. If I can name two different business reasons this class would need modifying, it's violating SRP."*

The counterweight: taken to extremes, SRP produces a hundred single-method classes and a codebase you can't navigate. The test is whether the reasons to change are genuinely *different*, not whether the class has more than one method.

## O — Open/Closed Principle

**Open for extension, closed for modification** — you should be able to add behaviour without editing existing, tested code.

### Violation

```java
class PaymentProcessor {
    void process(String type, long amountPaise) {
        if (type.equals("UPI")) {
            System.out.println("Processing UPI: " + amountPaise);
        } else if (type.equals("CARD")) {
            System.out.println("Processing card: " + amountPaise);
        }
        // every new rail edits THIS method
    }
}
```

Adding net banking means modifying a class that is already tested and already in production. The `if/else` chain grows without bound, the method's cyclomatic complexity climbs, and every change risks the branches that already worked.

### Fix — abstraction plus polymorphism

```java
interface PaymentStrategy {
    void process(long amountPaise);
}

class UpiPayment  implements PaymentStrategy {
    public void process(long amountPaise) { System.out.println("Processing UPI: " + amountPaise); }
}
class CardPayment implements PaymentStrategy {
    public void process(long amountPaise) { System.out.println("Processing card: " + amountPaise); }
}

// new rail — a new class, and nothing else changes
class NetBankingPayment implements PaymentStrategy {
    public void process(long amountPaise) { System.out.println("Processing netbanking: " + amountPaise); }
}

class PaymentProcessor {
    void process(PaymentStrategy strategy, long amountPaise) {
        strategy.process(amountPaise);      // closed — this never changes again
    }
}
```

`NetBankingPayment` required **zero edits** to `PaymentProcessor` or to any existing rail. That is the Strategy pattern, and it is how a payment switch adds rails without regression-testing the ones already live.

**The mechanism is always the same**: code against an abstraction, and let new behaviour arrive as new implementations rather than new branches. In Spring, injecting a `Map<String, PaymentStrategy>` or a `List<PaymentStrategy>` lets the container collect every implementation automatically, so even the wiring stops changing.

The honest caveat: you cannot make code open to *every* axis of future change, and trying to is the YAGNI trap below. OCP is applied where you already know variation exists — here, "there will be more payment rails" is a certainty, not a guess.

## L — Liskov Substitution Principle

**If `S` is a subtype of `T`, then a `T` can be replaced by an `S` without breaking the program.**

The key word is *behavioural*. The compiler already enforces the syntactic half (signatures, access, checked exceptions). LSP is about the part the compiler can't see: what callers reasonably expect.

### Violation 1 — Square/Rectangle

```java
class Rectangle {
    protected double width, height;
    void setWidth(double w)  { width = w; }
    void setHeight(double h) { height = h; }
    double area() { return width * height; }
}

class Square extends Rectangle {
    @Override void setWidth(double w)  { width = w; height = w; }    // forces both
    @Override void setHeight(double h) { width = h; height = h; }    // forces both
}
```

```java
void testRectangle(Rectangle r) {
    r.setWidth(5);
    r.setHeight(10);
    assert r.area() == 50;          // a reasonable expectation for ANY Rectangle
}

testRectangle(new Rectangle());     // ✅ area = 50
testRectangle(new Square());        // ❌ area = 100 — setHeight() also changed the width
```

Mathematically a square *is* a rectangle. Behaviourally, `Rectangle`'s contract includes "width and height are independent", and `Square` cannot honour it. The is-a relationship is real; the substitutability is not.

**Fix** — stop forcing the inheritance:

```java
interface Shape { double area(); }

class Rectangle implements Shape {
    private final double width, height;
    Rectangle(double w, double h) { width = w; height = h; }
    public double area() { return width * height; }
}

class Square implements Shape {
    private final double side;
    Square(double side) { this.side = side; }
    public double area() { return side * side; }
}
```

Note that making them immutable dissolves the problem too — the violation lived entirely in the setters. An immutable `Square extends Rectangle` would be substitutable.

### Violation 2 — throwing in an override

```java
class Bird {
    void fly() { System.out.println("Flying"); }
}

class Penguin extends Bird {
    @Override
    void fly() { throw new UnsupportedOperationException("Penguins can't fly"); }
}
```

```java
for (Bird b : birds) b.fly();   // crashes the moment a Penguin is in the list
```

A `Penguin` is-a `Bird` in the world, but it cannot honour `Bird`'s contract. Fix by moving the capability to where it's true:

```java
class Bird { void eat() { } }
interface Flyable { void fly(); }

class Eagle   extends Bird implements Flyable { public void fly() { ... } }
class Penguin extends Bird { /* no fly() to fake */ }
```

### The formal rules

A subtype may:
- **Weaken preconditions** — accept everything the parent accepted, and possibly more
- **Strengthen postconditions** — guarantee everything the parent guaranteed, and possibly more
- **Preserve invariants** — never break something the parent's callers relied on

The compiler enforces the mechanical corollaries: an override can't narrow access and can't broaden checked exceptions (see [[4. Inheritance]]). Everything else is on you.

### Why Java's overriding rules exist — LSP enforced by the compiler

The overriding restrictions in [[4. Inheritance]] are not arbitrary syntax rules. Each one stops a subclass from making the parent's contract **stricter**, which is exactly what would break substitution.

**1. Access modifier cannot be reduced**

```java
class Parent {
    public void process() { }
}

class Child extends Parent {
    private void process() { }     // compile error
}
```

```java
Parent p = new Child();
p.process();                        // caller was promised a public method
```

The caller expects `process()` to be reachable because the parent declared it `public`. If the child could hide it, the child would no longer be a drop-in replacement. So the child must offer **at least** the parent's visibility — widening (`protected` → `public`) is fine, narrowing is not.

**2. Checked exceptions cannot be broadened**

```java
class Parent {
    void read() throws IOException { }
}
```

```java
try {
    parent.read();
} catch (IOException e) { }         // caller prepared for exactly this
```

If the child could declare `void read() throws Exception`, then `Parent p = new Child(); p.read();` could throw something the caller never prepared for. The parent's promise — "you only need to handle `IOException`" — would be broken. Java rejects it at compile time.

What *is* allowed is a **narrower** exception, because the caller's existing handler still covers it:

```java
class Child extends Parent {
    void read() throws FileNotFoundException { }   // FileNotFoundException IS-A IOException ✔
}
```

The child cannot force the caller to handle **more cases** than the parent promised — it may only promise fewer.

**3. Preconditions and postconditions — the part the compiler can't check**

The same idea applies to behaviour, but here it's on you:

- **Don't strengthen preconditions.** `Parent.withdraw(amount)` accepts `amount > 0`; a child that only accepts `amount > 1000` will reject inputs the parent accepted. Code written against `Parent` now fails with `Child`.
- **Don't weaken postconditions.** `Parent.withdraw` guarantees the balance is updated; a child that sometimes skips the update breaks every caller that relied on that guarantee.

**Summary**

| Overriding rule | Why it exists | LSP relation |
| --- | --- | --- |
| Access level cannot decrease | Caller expects the same visibility | Child must stay usable as Parent |
| Checked exceptions cannot broaden | Caller only handles Parent's exceptions | Child can't demand extra handling |
| Return type may be more specific (covariant) | Still satisfies Parent's contract | Safe substitution |
| Method signature must match | Caller expects the same operation | Consistent behaviour |

> 💡 **Interview answer**: *"Java's overriding rules enforce the Liskov Substitution Principle. A subclass must not make the parent's contract stricter. Reducing visibility would make the method less accessible, and broadening checked exceptions would force callers to handle failures they never signed up for. Both break substitutability, so the compiler rejects them."*

**Soundbite**: *"LSP says inheritance must model behavioural substitutability, not just conceptual is-a. If an override has to throw, or changes what the caller expects, the hierarchy is wrong — that's not a case for a workaround."*

## I — Interface Segregation Principle

**No client should be forced to depend on methods it does not use.**

### Violation

```java
interface Worker {
    void work();
    void eat();
    void sleep();
}

class HumanWorker implements Worker {
    public void work()  { System.out.println("Working"); }
    public void eat()   { System.out.println("Eating"); }
    public void sleep() { System.out.println("Sleeping"); }
}

class RobotWorker implements Worker {
    public void work()  { System.out.println("Working"); }
    public void eat()   { throw new UnsupportedOperationException(); }   // ❌ forced
    public void sleep() { throw new UnsupportedOperationException(); }   // ❌ forced
}
```

The stubs are the smell. `RobotWorker` is dragged into depending on two methods that make no sense for it — and the exceptions it throws also break LSP, since substituting a `RobotWorker` where a `Worker` is expected can now blow up.

### Fix

```java
interface Workable  { void work();  }
interface Eatable   { void eat();   }
interface Sleepable { void sleep(); }

class HumanWorker implements Workable, Eatable, Sleepable { ... }
class RobotWorker implements Workable { public void work() { ... } }
```

Each class implements only what genuinely applies, and each *caller* depends only on the narrow role it needs — a method taking `Workable` doesn't care whether the argument eats.

The JDK is built this way: `Comparable`, `Runnable`, `Callable`, `Serializable`, `AutoCloseable` are all one-method interfaces rather than one giant capability interface. That's also what makes them usable as lambda targets.

**Soundbite**: *"ISP is about role-specific interfaces. If implementing one forces a class to write dummy or exception-throwing methods, the interface is too fat."*

## D — Dependency Inversion Principle

**High-level modules should not depend on low-level modules; both should depend on abstractions. Abstractions should not depend on details; details should depend on abstractions.**

### Violation

```java
class MySQLDatabase {                                    // low-level detail
    void save(String data) { System.out.println("Saving to MySQL: " + data); }
}

class UserService {                                      // high-level policy
    private final MySQLDatabase db = new MySQLDatabase();  // ❌ depends on the concrete class

    void createUser(String name) { db.save(name); }
}
```

Business logic is welded to a database technology. Switching to Mongo means editing `UserService` — a class that has nothing to do with storage engines. And there is no seam to test against: any unit test of `createUser` needs a real MySQL.

### Fix

```java
interface Database { void save(String data); }                   // the abstraction

class MySQLDatabase implements Database { public void save(String d) { ... } }
class MongoDatabase implements Database { public void save(String d) { ... } }

class UserService {
    private final Database db;                                    // depends on the abstraction

    UserService(Database db) { this.db = db; }                    // injected

    void createUser(String name) { db.save(name); }
}
```

```java
new UserService(new MySQLDatabase());
new UserService(new MongoDatabase());     // zero changes to UserService
new UserService(mock(Database.class));    // and the test seam comes free
```

### What actually gets "inverted"

```text
Before:   UserService ──────▶ MySQLDatabase
          (high-level)        (low-level)      ← policy depends on detail

After:    UserService ──────▶ «Database»  ◀────── MySQLDatabase
          (high-level)        (abstraction)       (low-level)
                                                  ↑ the arrow flipped
```

The dependency arrow from the low-level module now points *up* at the abstraction. Crucially, the interface belongs to the high-level module — it is defined in terms of what `UserService` needs, not what MySQL offers.

This is exactly Spring's constructor-injection pattern. DIP is the principle; the IoC container is a framework-scale implementation of it. Every time you inject a `ValidationEngine` interface instead of a `UpiValidationEngine` class, you're practising DIP — see [[10. Object Relationships]] for the full mapping.

### DIP ≠ DI — the distinction that gets tested

- **Dependency Inversion Principle** — a *design principle*: depend on abstractions.
- **Dependency Injection** — a *technique*: receive your dependencies instead of constructing them.

They're independent:

```java
class UserService {
    private final MySQLDatabase db;
    UserService(MySQLDatabase db) { this.db = db; }   // DI ✅ (injected) but DIP ❌ (concrete type)
}
```

```java
UserService s = new UserService(new MySQLDatabase());  // DIP ✅ (interface-typed field), no framework
```

Injecting a concrete class is DI without DIP. Manually passing an interface-typed object is DIP without a container. Spring gives you both at once, which is why the two get conflated.

> 💡 **Interview**: What's the difference between Dependency Inversion and Dependency Injection? → DIP is the principle — high-level code depends on an abstraction it owns. DI is one mechanism for supplying that dependency. Injecting a concrete class satisfies DI but violates DIP.

## DRY — Don't Repeat Yourself

**Every piece of knowledge should have a single, unambiguous representation.**

```java
// ❌ the same rule, twice
class UserService {
    void createUser(String email) {
        if (!email.contains("@") || !email.contains(".")) throw new IllegalArgumentException("Invalid email");
    }
}
class NewsletterService {
    void subscribe(String email) {
        if (!email.contains("@") || !email.contains(".")) throw new IllegalArgumentException("Invalid email");
    }
}
```

```java
// ✅ one source of truth
final class EmailValidator {
    static void validate(String email) {
        if (!email.contains("@") || !email.contains("."))
            throw new IllegalArgumentException("Invalid email");
    }
}
```

The cost of duplication isn't the extra lines — it's **drift**. When the rule changes to a proper regex, you fix it in three places and miss the fourth, and now two parts of the system disagree about what a valid email is.

The important qualification: DRY is about duplicated **knowledge**, not duplicated **text**. Two validation methods that happen to look identical today but encode two different business rules should stay separate — merging them couples two things that will diverge. Premature deduplication creates worse coupling than the duplication it removed.

## KISS — Keep It Simple

**Prefer the simplest solution that correctly solves the problem.**

```java
// ❌ over-engineered
interface NumberChecker { boolean check(int n); }
class EvenNumberChecker implements NumberChecker {
    public boolean check(int n) { return n % 2 == 0; }
}
class NumberCheckerFactory {
    static NumberChecker getChecker(String type) {
        if (type.equals("even")) return new EvenNumberChecker();
        throw new IllegalArgumentException();
    }
}
boolean isEven = NumberCheckerFactory.getChecker("even").check(4);
```

```java
// ✅
boolean isEven = n % 2 == 0;
```

A factory and an interface hierarchy for an even check is *technically* flexible OOP and *actually* three files to read instead of one expression. **KISS is frequently in tension with over-applied SOLID**, and knowing when a plain `if` beats a Strategy pattern is a senior signal, not a junior one. Readability is a feature; every layer of indirection is paid for by every future reader.

## YAGNI — You Aren't Gonna Need It

**Don't build for requirements that haven't been asked for.**

```java
// ❌ built for imagined futures
class PaymentProcessor {
    void process(long amountPaise, String currency, String region,
                 boolean isRecurring, String discountCode,
                 Map<String, Object> futureMetadata) {
        // only amountPaise is used anywhere in the codebase today
    }
}
```

Every speculative parameter is more surface to test, more to document, more to keep working, and more to migrate when the real requirement arrives and turns out not to match the guess.

### The OCP/YAGNI tension, resolved

They sound contradictory — OCP says design for extension, YAGNI says don't. The distinction is **structural openness vs speculative features**:

- ✅ **OCP** — use an interface instead of a `switch`, so a future case is a new class. Costs nothing today.
- ❌ **YAGNI violation** — add six unused parameters and a plugin registry for cases nobody has asked for.

OCP shapes the code you're writing anyway. YAGNI forbids writing code you don't need yet.

## Coupling

**How much one module depends on another's internals.**

```java
// tight
class UserService {
    private final MySQLDatabase db = new MySQLDatabase();
}

// loose
class UserService {
    private final Database db;
    UserService(Database db) { this.db = db; }
}
```

With tight coupling, changes inside `MySQLDatabase` — or replacing it — ripple straight into `UserService`. With loose coupling, `UserService` depends only on a contract, and anything behind that contract can change freely.

Coupling is the property that determines whether a codebase stays modifiable. Low coupling means you can understand, change and test one module in isolation. It's the *outcome* that DIP, composition-over-inheritance and interface-based design are all working toward — they're mechanisms; low coupling is the goal.

## Cohesion

**How closely related the responsibilities inside one class are.**

```java
// ❌ low cohesion — nothing in common but the word "Employee"
class Employee {
    void calculateSalary()    { }
    void saveToDatabase()     { }
    void sendEmail()          { }
    void generatePayslipPdf() { }
}

// ✅ high cohesion — every method is about one thing
class SalaryCalculator {
    long calculateBaseSalary(Employee e) { ... }
    long calculateBonus(Employee e)      { ... }
    long calculateDeductions(Employee e) { ... }
}
```

High cohesion means a class's methods and fields genuinely belong together — they operate on the same state toward the same purpose. A class you can only describe with "and" ("it calculates salary **and** saves to the database") has low cohesion.

### The pairing

The two are the standard interview pair, and they reinforce each other: **high cohesion within modules, low coupling between them.** When each class has one well-defined responsibility, it naturally needs fewer connections to do its job — so raising cohesion tends to lower coupling for free. SRP and ISP produce cohesion; DIP and OCP produce loose coupling.

---

## How It All Connects

| Principle | Primarily improves |
| --- | --- |
| SRP | Cohesion — one focused purpose per class |
| OCP | Extensibility without touching tested code |
| LSP | Correctness of polymorphic substitution |
| ISP | Interface cohesion; no forced irrelevant dependencies |
| DIP | Coupling — depend on abstractions, not details |
| DRY | Maintainability — one source of truth |
| KISS | Readability — no unearned complexity |
| YAGNI | Avoided waste — no speculative features |

**The summary answer to "what's the point of all this":** *"SOLID collectively pushes a system toward high cohesion and low coupling — classes that do one thing well (SRP, ISP) and depend on abstractions rather than concrete details (DIP, OCP). That's what keeps a large codebase like a payment switch testable and safely extensible, instead of a tangle where every change risks breaking something unrelated."*

And the mature follow-up: these are **principles, not laws**. KISS and YAGNI exist precisely to stop the other five from being applied everywhere by reflex. Knowing when *not* to introduce an abstraction is as much a part of the skill as knowing how.
