# Inheritance

---

## Short Notes

---

### 1. `extends`

- Establishes an **is-a** relationship — the subclass acquires the parent's fields and methods
- `class Car extends Vehicle` → `Car` **is-a** `Vehicle`
- One `extends` only; no `extends` written → implicitly `extends Object`
- `private` members are inherited into the object's memory but not into the child's scope

---

### 2. What Is and Isn't Inherited

| Inherited | Not inherited |
| --------- | ------------- |
| `public` / `protected` members | Constructors |
| Package-private members (same package only) | `private` members (not in scope) |
| `static` members (shared, not copied) | Initializer blocks |

---

### 3. `super` Keyword

- **Field**: `super.x` reaches the parent's shadowed field
- **Method**: `super.m()` calls the parent's version from inside an override
- **Constructor**: `super(...)` invokes the parent's constructor, **first statement only**
- Compiled as `invokespecial` → never virtually dispatched, so `super.m()` can't recurse

---

### 4. Implicit `super()`

- If a constructor starts with neither `this()` nor `super()`, the compiler inserts `super()`
- So the parent **must** have a no-arg constructor, or you must chain explicitly
- Parent with only a parameterized constructor → child must call `super(args)` or fail to compile

---

### 5. Types of Inheritance

```text
Single          Multilevel        Hierarchical      Multiple (classes)
  A                 A                  A                A   B
  │                 │                 ╱ ╲                ╲ ╱
  B                 B                B   C                C   ❌ not allowed
                    │
                    C
```

- Java supports **single**, **multilevel**, **hierarchical** with classes
- **Multiple** and **hybrid** only via interfaces

---

### 6. Method Overriding Rules

- Same signature; return type same or **covariant**
- Access modifier cannot narrow; checked exceptions cannot broaden
- `private`, `static`, `final` methods cannot be overridden
- `static` redefinition = hiding; field redefinition = shadowing
- Always annotate with `@Override` — turns a typo into a compile error

---

### 7. Covariant Return Types

- Since Java 5, an override may return a **subtype** of the parent's return type
- Saves the caller a downcast — used by `clone()` overrides and fluent builders
- One-directional: narrow only, never widen

```java
class Animal { Animal reproduce() { ... } }
class Dog extends Animal { @Override Dog reproduce() { ... } }
```

---

### 8. Why No Multiple Inheritance With Classes

- `class C extends A, B` → compile error
- Avoids the **Diamond Problem**: two inherited implementations of the same method, no rule to pick
- Also avoids ambiguous state layout and constructor ordering
- Java's trade: unambiguous hierarchy over C++-style flexibility

---

### 9. Diamond Problem

```text
      A
     ╱ ╲
    B   C     B and C override A.show() differently
     ╲ ╱
      D       which show() does D inherit?
```

- **Classes**: sidestepped entirely — multiple class inheritance is illegal
- **Interfaces (Java 8+ defaults)**: the conflict is legal to create but **must be resolved explicitly**
- Compiler error: *"inherits unrelated defaults for show() from types B and C"*
- Resolve with `B.super.show()` or a fresh implementation

---

### 10. Interface Multiple Inheritance

- A class may `implements` any number of interfaces — multiple inheritance of **type**
- Pre-Java 8: no bodies, so nothing could conflict
- Java 8+: `default` methods add implementation → mini diamond, resolved by the programmer
- Java's principle: **the compiler never silently guesses**

---

### 11. Resolution Order for Defaults

1. **Class wins** — a concrete method in the class (or inherited from a superclass) beats any `default`
2. **Most specific interface wins** — a sub-interface's `default` beats its super-interface's
3. **Otherwise ambiguous** — the class must override and pick with `X.super.m()`

---

### 12. Inheritance vs Composition

- Inheritance = compile-time, permanent, exposes the parent's API and internals
- Composition = runtime, swappable, exposes only what you delegate
- **Fragile base class**: a parent change silently breaks descendants
- Default to composition; use inheritance when is-a is permanent and LSP holds

---

### SDE-2 Interview Priority

**Must Know**: `extends` semantics, all three uses of `super`, Implicit `super()`, Types of inheritance, Overriding rules, Why no multiple class inheritance, Diamond problem in both forms

**Nice To Know**: Covariant return types, Default-method resolution order, What is and isn't inherited, `Interface.super.method()` syntax

**Advanced**: Fragile base class problem, LSP violations in real hierarchies, Constructor leaking `this` during the super chain

# Detailed Explanation

---

## `extends`

`extends` makes a subclass acquire the members of a superclass and declares an **is-a** relationship the compiler will then enforce everywhere.

```java
class Vehicle {
    protected int speed;
    void move() { System.out.println("Vehicle moving"); }
}

class Car extends Vehicle {
    int doors;
}
```

`Car` is-a `Vehicle`: it inherits `speed` and `move()`, adds `doors`, and — crucially — is now usable anywhere a `Vehicle` is expected:

```java
Vehicle v = new Car();               // ✅ upcasting, always safe
List<Vehicle> fleet = List.of(new Car(), new Truck());
```

### The rules

- **One superclass only.** `class C extends A, B` does not compile.
- **`private` members are not accessible** in the subclass. The bytes are there in the object's layout — a `Car` object physically contains every `Vehicle` field — but the name is not in scope, so the child must go through a `protected` or `public` accessor.
- **Every class implicitly extends `Object`** when nothing else is named, which is why `equals()`, `hashCode()` and `toString()` are always available.
- `final` classes cannot be extended at all (`String`, `Integer`, all the boxed types).

### What is and isn't inherited

| Inherited | Not inherited |
| --- | --- |
| `public` and `protected` members | **Constructors** — they aren't members |
| Package-private members, if the child is in the same package | `private` members — present in memory, absent from scope |
| `static` members (shared, not copied per class) | Static and instance initializer blocks |

The constructor point is the one interviewers probe: a subclass never inherits a constructor, it *invokes* one via `super(...)`.

---

## `super` Keyword

`super` is a reference to the immediate parent, and it has exactly three uses.

### a) Reach a shadowed field

```java
class Parent { int x = 10; }

class Child extends Parent {
    int x = 20;
    void show() {
        System.out.println(x);        // 20 — the child's own
        System.out.println(super.x);  // 10 — the parent's
        System.out.println(this.x);   // 20
    }
}
```

Both fields exist inside the one object (see the field-hiding section in the binding note). `super.x` is how you reach the other slot.

### b) Call the parent's overridden method

```java
class Vehicle {
    void move() { System.out.println("Vehicle moving"); }
}

class Car extends Vehicle {
    @Override
    void move() {
        super.move();                          // run the parent's behaviour first
        System.out.println("Car moving fast"); // then extend it
    }
}
```

This is the "extend, don't replace" pattern, and it is why `super.move()` compiles to `invokespecial` rather than `invokevirtual` — the call is nailed to `Vehicle.move()` at compile time. If it were dispatched virtually it would resolve back to `Car.move()` and recurse until the stack blew up.

### c) Invoke the parent's constructor

```java
class Vehicle {
    protected final int speed;
    Vehicle(int speed) { this.speed = speed; }
}

class Car extends Vehicle {
    private final int doors;
    Car(int speed, int doors) {
        super(speed);        // must be the FIRST statement
        this.doors = doors;
    }
}
```

The parent must be fully constructed before the child touches anything, which is why `super(...)` takes the first slot — and why a constructor can contain `super()` **or** `this()`, never both.

---

## Implicit `super()`

If a constructor's first statement is neither `this(...)` nor `super(...)`, the compiler silently inserts a no-arg `super()`.

```java
class Car extends Vehicle {
    Car() {
        doors = 4;
    }
}
// compiles as:
// Car() { super(); doors = 4; }
```

The consequence catches people out constantly: **the parent must have an accessible no-arg constructor**, or the child fails to compile.

```java
class Vehicle {
    Vehicle(int speed) { }          // only a parameterized constructor
}

class Car extends Vehicle {
    Car() { }                       // ❌ "constructor Vehicle in class Vehicle
}                                   //     cannot be applied to given types"

class Bike extends Vehicle {
    Bike() { super(50); }           // ✅ chain explicitly
}
```

Note also that writing *any* constructor in `Vehicle` removes its free default one — so adding a parameterized constructor to a base class can break every subclass that relied on the implicit `super()`.

The full chain always terminates at `Object()`:

```text
new Car(120, 4)
  → Car(int, int)
      → super(120)  → Vehicle(int)
                        → super()  → Object()
                        ← Vehicle's instance blocks + body
      ← Car's instance blocks + body
```

## Types of Inheritance

### Single

One class, one parent.

```java
class Animal { }
class Dog extends Animal { }
```

### Multilevel

A chain — each class inherits everything from all its ancestors.

```java
class Animal { void breathe() { } }
class Mammal extends Animal { void feedMilk() { } }
class Dog extends Mammal { void bark() { } }
// Dog has bark(), feedMilk(), breathe(), and Object's methods
```

Deep chains are a smell: by level four, a change at the top can break behaviour three levels down in ways nobody predicts.

### Hierarchical

Several classes share one parent — the most common and most useful shape.

```java
abstract class PaymentProcessor { abstract PaymentResult process(Payment p); }
class UpiProcessor  extends PaymentProcessor { ... }
class CardProcessor extends PaymentProcessor { ... }
class WalletProcessor extends PaymentProcessor { ... }
```

This is the shape that runtime polymorphism is built for: one loop over `List<PaymentProcessor>`, three behaviours.

### Multiple and hybrid — not with classes

```text
Single          Multilevel        Hierarchical        Multiple
  A                 A                  A                A   B
  │                 │                 ╱ ╲                ╲ ╱
  B                 B                B   C                C    ❌
                    │
                    C
```

`class C extends A, B` is a compile error, and hybrid (any combination that produces a diamond through classes) is unreachable as a result. Both are available through interfaces.

## Method Overriding Rules

For a subclass method to actually override:

1. **Identical signature** — same name and parameter types in the same order.
2. **Return type** identical or **covariant**.
3. **Access cannot narrow** — `protected` → `public` is fine, the reverse is not.
4. **Checked exceptions cannot broaden** — same, narrower, fewer, or none. Unchecked exceptions are unrestricted.
5. **`private`, `static`, `final` cannot be overridden** — a same-named `private` method is unrelated, a `static` one is *hidden*, a `final` one is locked.
6. **Constructors are never overridden.**

```java
class BaseProcessor {
    protected Number settle(Payment p) throws IOException { return 0L; }
}

class UpiProcessor extends BaseProcessor {
    @Override
    public Long settle(Payment p) throws FileNotFoundException {   // ✅ wider access,
        return 1L;                                                 //    covariant return,
    }                                                              //    narrower checked exception
}
```

Rules 3 and 4 exist for the same reason. A caller holding a `BaseProcessor` reference is promised `protected` access and only `IOException`; if the override could narrow visibility or throw something broader, that promise would break at runtime through a parent-typed reference. Substitutability has to survive the override — that is Liskov, enforced by the compiler.

**Always write `@Override`.** It costs nothing and converts the most common inheritance bug — a typo or a mismatched parameter type that silently creates an *overload* instead of an override — into a compile error.

```java
class Child extends Parent {
    @Override
    void proccess(Payment p) { }    // ❌ caught immediately: nothing to override
}
```

## Covariant Return Types

Since Java 5, an override may return a **subtype** of the parent's declared return type.

```java
class Animal {
    Animal reproduce() { return new Animal(); }
}

class Dog extends Animal {
    @Override
    Dog reproduce() { return new Dog(); }   // narrowed from Animal to Dog — legal
}
```

```java
Animal a = new Dog().reproduce();   // ✅ Dog is-a Animal
Dog puppy = new Dog().reproduce();  // ✅ no cast needed — this is the win
```

Without covariance the second line would need `(Dog) new Dog().reproduce()`, and every caller would pay a downcast for information the compiler already had. It is why `clone()` overrides can return the concrete type, and why fluent builders can return `this` typed precisely.

The rule is one-directional — the new return type must be assignable **to** the old one:

```java
class Cat extends Animal {
    @Override
    Object reproduce() { return new Cat(); }   // ❌ Object is wider than Animal
}
```

Primitives have no subtype relationship, so `int` cannot be covariantly returned where `long` was declared.

## Why Java Does Not Support Multiple Inheritance With Classes

`class C extends A, B` is a compile error. The headline reason is the **Diamond Problem** — genuine ambiguity when two parents supply conflicting implementations of the same method — but there are two more that are worth having ready:

- **State layout.** If `A` and `B` both extend a common ancestor, does `C` contain one copy of the ancestor's fields or two? C++ needs `virtual` inheritance to answer that; Java refuses the question.
- **Constructor ordering.** With two parents, which `super()` runs first, and what happens to a shared ancestor's constructor? There is no answer that is both intuitive and safe.

C++ allows multiple inheritance with rules to disambiguate. Java's designers deliberately traded that flexibility for a hierarchy that is always unambiguous — and offered interfaces as the escape hatch.

---

## Diamond Problem

```text
      A
     ╱ ╲
    B   C     B and C each override A.show() differently
     ╲ ╱
      D       D inherits two conflicting show() implementations
```

### With classes — sidestepped entirely

```java
class A { void show() { System.out.println("A"); } }
class B extends A { @Override void show() { System.out.println("B"); } }
class C extends A { @Override void show() { System.out.println("C"); } }

class D extends B, C { }   // ❌ compile error — Java never lets the diamond form
// if it were legal: new D().show() → B's version or C's? No principled answer.
```

Java prevents the ambiguity by preventing the shape.

### With interfaces — legal to form, mandatory to resolve

Before Java 8 interfaces had no bodies, so implementing two of them could never conflict: whatever the signatures, the class supplied the single implementation. `default` methods reintroduced implementation inheritance, and with it a real diamond:

```java
interface B { default void show() { System.out.println("B"); } }
interface C { default void show() { System.out.println("C"); } }

class D implements B, C {
    // ❌ without this override:
    //    "class D inherits unrelated defaults for show() from types B and C"
    @Override
    public void show() {
        B.super.show();          // explicitly pick one…
        // C.super.show();       // …or both, in your chosen order…
        // System.out.println("D"); // …or write something entirely new
    }
}
```

The `X.super.m()` syntax is only valid inside a class that directly implements `X`, and only for a `default` method.

This is Java's actual design principle, and the sentence worth memorising: **ambiguity must be resolved explicitly by the programmer; the compiler never guesses.** Java did not avoid the diamond problem — it made silent ambiguity impossible.

> 💡 **Interview**: Does Java support multiple inheritance? → Of **type**, yes, through interfaces. Of **state**, no. Of **implementation**, partially since Java 8 via `default` methods — but any conflict is a compile error until the class resolves it explicitly with `Interface.super.method()`.

---

## Resolution Order for Default Methods

When a method could come from several places, the compiler applies three rules in order:

**1. Class wins.** A concrete method in the class, or inherited from a superclass, always beats any interface `default`.

```java
interface Greeter { default String greet() { return "interface"; } }
class Base { public String greet() { return "class"; } }

class Impl extends Base implements Greeter { }
new Impl().greet();   // "class" — the superclass method wins, no ambiguity error
```

**2. The most specific interface wins.** If one candidate interface extends another, the sub-interface's `default` beats the super-interface's.

```java
interface A { default String id() { return "A"; } }
interface B extends A { @Override default String id() { return "B"; } }

class Impl implements A, B { }
new Impl().id();      // "B" — B is more specific than A
```

**3. Otherwise it's ambiguous** and the class must override, resolving with `X.super.m()` or supplying fresh logic.

Rule 1 has a real consequence: adding a `default` method to a widely implemented interface is source-compatible with classes that already have such a method — the class's version simply keeps winning. That is exactly why `default` was added in Java 8: it let `Collection` gain `stream()` and `forEach()` without breaking every implementation in existence.

## Inheritance vs Composition

Inheritance is the tightest coupling Java offers. The subclass depends on the parent's *implementation*, not merely its interface, and it inherits the parent's entire public API whether or not that API makes sense for the subtype.

```java
class Stack extends ArrayList<String> {     // ❌ a Stack is not an ArrayList
    void push(String s) { add(s); }
    String pop() { return remove(size() - 1); }
}

Stack s = new Stack();
s.push("a");
s.add(0, "sneaky");     // inherited — the LIFO invariant is now broken from outside
```

```java
class Stack {                                // ✅ composition
    private final List<String> items = new ArrayList<>();
    void push(String s) { items.add(s); }
    String pop() { return items.remove(items.size() - 1); }
    // only push/pop are visible — the invariant is safe
}
```

### The fragile base class problem

Because the subclass sees the parent's implementation, a change inside the parent can break descendants that never changed:

```java
class CountingList<E> extends ArrayList<E> {
    private int addCount = 0;

    @Override public boolean add(E e) { addCount++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);      // ⚠ ArrayList.addAll internally calls add()
    }                                //    → every element counted twice
}
```

Nothing here is wrong on its face. The bug is that `addAll` happens to be implemented in terms of `add` — an internal detail the subclass had no right to know, and that a future JDK release could change in either direction.

| | Inheritance | Composition |
| --- | --- | --- |
| Relationship | is-a | has-a / uses-a |
| Bound at | Compile time, permanently | Runtime, swappable |
| Exposes | The parent's whole API | Only what you delegate |
| Coupling | Tight — to implementation | Loose — to interface |
| Testability | Must construct the hierarchy | Inject a fake collaborator |

**Default to composition.** Reach for inheritance when the is-a relationship is permanent, the subtype is substitutable everywhere the parent is used (Liskov), and the parent was *designed* for extension — documented, with `final` on everything that must not be overridden.
