# Interfaces And Abstraction

---

## Short Notes

---

### 1. Abstract Classes

- Declared `abstract` → **cannot be instantiated**, exists to be extended
- Can mix **abstract methods** (no body) and **concrete methods** (with body)
- Can have fields (any modifier), constructors, static/instance blocks
- A subclass must implement **all** abstract methods, or be declared `abstract` itself
- Can have **zero** abstract methods — enough to block direct instantiation

---

### 2. Interfaces

- A pure contract: what a type can do, with no state to back it
- Methods implicitly `public abstract` (unless `default`, `static`, or `private`)
- Fields implicitly `public static final` — constants only, **no instance state**
- No constructors; a class may `implements` many, an interface may `extends` many

---

### 3. Abstract Class vs Interface

| Aspect | Abstract Class | Interface |
| --- | --- | --- |
| Methods | Abstract + concrete | Abstract, `default`, `static`, `private` |
| Fields | Any — instance, static, mutable | Only `public static final` |
| Constructors | Yes | No |
| Inheritance | `extends` — exactly one | `implements` — many |
| Relationship | **is-a**, with shared code | **can-do**, a capability |
| State | Can hold it | Cannot |

- Abstract class → related types sharing **state + implementation**
- Interface → unrelated types sharing a **capability** (`Comparable`, `Runnable`)

---

### 4. Default Methods (Java 8)

- An interface method **with a body**: `default void honk() { ... }`
- Motivation: add methods to an interface without breaking every implementer
- That's how `Collection` gained `stream()` and `forEach()` in Java 8
- Implementers may override it; conflicting defaults **must** be resolved explicitly
- A default is a **fallback**: override it if you want different behaviour; if it doesn't apply at all, the interface is too broad → split it (ISP), don't throw

---

### 5. Static Methods in Interfaces (Java 8)

- Utility methods that belong to the interface itself
- Called as `MathOps.square(5)` — **not inherited** by implementers
- `Calc.square(5)` on an implementing class is a **compile error**
- Replaces the old companion-class pattern (`Collections`, `Arrays`)
- Introduced for **organisation**, not backward compatibility — that was default methods

---

### 6. Private Methods in Interfaces (Java 9)

- `private` / `private static` helper methods inside an interface
- Purpose: share code **between** `default` / `static` methods without exposing it
- Not part of the contract, not inherited, not visible to implementers

---

### 7. Functional Interfaces

- Exactly **one abstract method** (SAM) — any number of `default` / `static` / `private`
- Enables lambdas and method references: `Calculator add = (a, b) -> a + b;`
- `@FunctionalInterface` is optional but makes the SAM rule a **compile error** to break
- `public` methods of `Object` (e.g. `equals`) don't count toward the SAM limit

---

### 8. Built-in Functional Interfaces

| Interface | Method | Shape |
| --- | --- | --- |
| `Function<T,R>` | `R apply(T)` | in → out |
| `Supplier<T>` | `T get()` | nothing → out |
| `Consumer<T>` | `void accept(T)` | in → nothing |
| `Predicate<T>` | `boolean test(T)` | in → boolean |
| `BiFunction<T,U,R>` | `R apply(T,U)` | two in → out |
| `UnaryOperator<T>` | `T apply(T)` | `Function<T,T>` |

---

### 9. Marker Interfaces

- An interface with **no methods** — a tag attached to a class's type
- Consumers check `instanceof` and change behaviour; nothing is ever called on it
- Canonical three: `Serializable`, `Cloneable`, `Remote`
- Pre-annotation-era pattern — new designs use **annotations** instead

---

### 10. `Serializable`

- Flags "this object's fields may be written as bytes"
- `ObjectOutputStream` checks the tag → else `NotSerializableException`
- `transient` fields and `static` fields are excluded
- Always declare `serialVersionUID` or class changes break deserialization

---

### 11. `Cloneable` and `Remote`

- `Cloneable` → unlocks `Object.clone()`; without it, `CloneNotSupportedException`
- `Remote` (RMI) → methods callable from another JVM; every method throws `RemoteException`
- RMI is legacy; gRPC/REST solve the same problem today
- See [[6. Cloning And Object Copying]] for why `Cloneable` is considered broken

---

### 12. Nested Interfaces

- An interface declared inside a class or interface — implicitly `static`
- Referenced as `Outer.Inner`: `class Car implements Vehicle.Serviceable`
- Canonical example: **`Map.Entry`** — meaningless outside `Map`'s context
- Purpose: namespacing and keeping tightly coupled types together

---

### 13. Feature Timeline

| Feature | Since | Purpose |
| --- | --- | --- |
| Abstract classes, interfaces | Java 1 | Partial implementation / pure contract |
| Marker, nested interfaces | Java 1 | Tagging / namespacing |
| `default`, `static` methods | Java 8 | Evolve interfaces, utility methods |
| Functional interfaces | Java 8 | Enable lambdas |
| `private` interface methods | Java 9 | Reuse inside defaults, unexposed |

---

**Must Know**: Abstract class vs interface and when to pick each, Default methods and why they exist, Static interface methods aren't inherited, Functional interfaces + SAM, Marker interfaces and how `instanceof` drives them

**Nice To Know**: Private interface methods, Nested interfaces / `Map.Entry`, `serialVersionUID` and `transient`, Built-in `java.util.function` types

**Advanced**: Marker interfaces vs annotations trade-off, Interface evolution and binary compatibility, Deserialization bypassing constructors

# Detailed Explanation

---

## Abstract Classes

An `abstract` class cannot be instantiated. It exists to be extended, and it can carry both a contract (abstract methods) and shared machinery (fields, constructors, concrete methods).

```java
abstract class PaymentProcessor {
    protected final String merchantId;        // shared state
    protected long processedCount;

    PaymentProcessor(String merchantId) {     // constructor — runs via super()
        this.merchantId = merchantId;
    }

    abstract PaymentResult process(Payment p);       // the contract — no body

    final PaymentResult processAndCount(Payment p) { // shared template, locked
        processedCount++;
        return process(p);
    }
}

class UpiProcessor extends PaymentProcessor {
    UpiProcessor(String merchantId) { super(merchantId); }

    @Override
    PaymentResult process(Payment p) { return switchClient.route(p); }
}
```

```java
new PaymentProcessor("M1");   // ❌ compile error — abstract class
new UpiProcessor("M1");       // ✅
```

Points that get probed:

- **It can have a constructor**, even though it can't be instantiated. The constructor runs through `super()` when a concrete subclass is created — that is how `merchantId` gets initialised.
- **It can have zero abstract methods.** Sometimes the only reason to mark a class abstract is to forbid direct instantiation while still sharing code.
- A subclass that doesn't implement every inherited abstract method **must itself be `abstract`**.
- Single inheritance still applies — a class can extend exactly one abstract class.

The `processAndCount` method above shows the real reason abstract classes survive alongside interfaces: it holds mutable state (`processedCount`) and a `final` template method that subclasses cannot break. An interface can do neither.

---

## Interfaces

An interface declares what a type can do, with nothing to back it.

```java
interface Refundable {
    void refund(String txnId, long amountPaise);      // implicitly public abstract
}

interface Reconcilable {
    void reconcile(LocalDate settlementDate);
}

class UpiProcessor implements Refundable, Reconcilable {   // multiple — allowed
    public void refund(String txnId, long amountPaise) { ... }
    public void reconcile(LocalDate settlementDate) { ... }
}

interface FullRail extends Refundable, Reconcilable { }    // interface extending many — allowed
```

The implicit modifiers matter:

- **Methods are `public abstract`** by default. This is why an implementing class must declare the method `public` — anything less would narrow the access, which overriding forbids:

```java
class Car implements Drivable {
    void drive() { }          // ❌ "attempting to assign weaker access privileges"
    public void drive() { }   // ✅
}
```

- **Fields are `public static final`.** An interface cannot hold instance state, which is the single deepest difference from an abstract class:

```java
interface Limits {
    long MAX_TXN_PAISE = 100_000_00;   // implicitly public static final
    // long counter = 0;               // still a constant — can never be mutated
}
```

- **No constructors**, because there is no state to initialise and no instance to create.

---

## Abstract Class vs Interface

| Aspect | Abstract Class | Interface |
| --- | --- | --- |
| Keyword | `abstract class` | `interface` |
| Methods | Abstract + concrete | Abstract, `default`, `static`, `private` |
| Fields | Any kind, mutable, any modifier | Only `public static final` |
| Constructors | Yes | No |
| Inherit via | `extends`, exactly one | `implements`, any number |
| Multiple inheritance | No | Of type, yes |
| Models | **is-a** with shared implementation | **can-do**, a capability |

The decision rule:

- **Abstract class** when subclasses genuinely share **state and implementation** and sit in one is-a hierarchy. `Animal` with `name` and `age`, extended by `Dog` and `Cat`.
- **Interface** when you are naming a **capability** that otherwise unrelated types can offer. `Flyable` implemented by both `Bird` and `Airplane` — two types with nothing else in common. `Comparable`, `Runnable`, `Serializable` are all of this shape.

Since Java 8 blurred the line (interfaces can carry behaviour now), the sharpest remaining distinction is **state**: an interface can never hold instance fields. If your shared code needs to read or mutate per-object state, you need an abstract class.

> 💡 **Interview**: Now that interfaces have default methods, why keep abstract classes? → Interfaces still cannot hold instance state or constructors. Anything requiring shared mutable fields, constructor-enforced invariants, or a `final` template method needs an abstract class.

## Default Methods

Java 8 let an interface supply a method body:

```java
interface Vehicle {
    void start();

    default void honk() {                      // has a body
        System.out.println("Beep beep!");
    }
}

class Car implements Vehicle {
    public void start() { System.out.println("Car starting"); }
    // honk() not implemented — inherits the default
}

new Car().honk();   // "Beep beep!"
```

The motivation was **interface evolution**. Before Java 8, adding a method to a published interface broke every implementation in existence. That made `Collection` frozen — and the Stream API needed `stream()` on it. `default` solved exactly this: `Collection.stream()`, `Iterable.forEach()`, `Comparator.reversed()` were all added without breaking a single existing implementer.

An implementing class may override a default freely. And when two interfaces supply conflicting defaults, the class **must** resolve it explicitly — the diamond problem, covered in [[4. Inheritance]]:

```java
interface A { default void show() { System.out.println("A"); } }
interface B { default void show() { System.out.println("B"); } }

class C implements A, B {
    @Override public void show() { A.super.show(); }   // ❌ compile error without this
}
```

### When an implementer doesn't want the default

A default is only a **fallback**. Most implementers are happy with it; the ones that aren't simply override it:

```java
interface Vehicle {
    default void stop() { System.out.println("Stopping"); }
}

class Car implements Vehicle { }                       // happy with the default

class Airplane implements Vehicle {
    @Override
    public void stop() { System.out.println("Deploy landing brakes"); }
}

new Car().stop();                 // "Stopping"
Vehicle v = new Airplane();
v.stop();                         // "Deploy landing brakes"  — normal dynamic dispatch
```

The harder case is when the method **doesn't make sense at all** for some implementer:

```java
interface Bird {
    default void fly() { System.out.println("Flying"); }
}

class Ostrich implements Bird { }

new Ostrich().fly();              // compiles, runs, and is conceptually wrong
```

The problem here is not the default method — it's the **interface design**. `fly()` was never a capability of every `Bird`. Split it out so only the birds that can fly promise it:

```java
interface Bird { }
interface Flyable { void fly(); }

class Sparrow implements Bird, Flyable { public void fly() { System.out.println("Flying"); } }
class Ostrich implements Bird { }                      // nothing to fake
```

That is the Interface Segregation Principle from [[12. SOLID And Design Principles]] — and the same fix as the `Penguin.fly()` LSP violation there.

The JDK follows the same judgement call. `Collection.removeIf(...)` is a default because almost every collection can support it; an implementation with a faster path overrides it; an unmodifiable collection throws `UnsupportedOperationException`. Defaults are added only when the behaviour makes sense for *most* implementers.

> 💡 **Interview**: *"If an implementation doesn't want the default behaviour it overrides the method. If the method doesn't conceptually apply to some implementers, that's a sign the interface is too broad — it violates ISP and the hierarchy should be split, not patched with a throwing override."*

## Static and Private Interface Methods

### Static (Java 8)

Utility logic that belongs with the interface, callable on the interface itself:

```java
interface MathOps {
    static int square(int x) { return x * x; }
}

MathOps.square(5);   // ✅ called via the interface name
```

The rule that gets tested: **static interface methods are not inherited.**

```java
class Calc implements MathOps { }

Calc.square(5);      // ❌ compile error — not inherited
new Calc().square(5) // ❌ compile error either way
```

This is deliberate. Before Java 8 such helpers lived in a companion class — `Collections` for `Collection`, `Arrays` for arrays. Static interface methods let the logic live where it belongs: `Comparator.comparing(...)`, `Stream.of(...)`, `List.of(...)`, `Map.entry(...)`.

They also cannot be overridden or hidden by implementers — they belong strictly to the interface.

### Private (Java 9)

Once interfaces had default and static methods, those methods started duplicating logic — and there was no way to factor it out without exposing a new public method. Java 9 added private interface methods:

```java
interface AuditLog {
    default void logSuccess(String txnId) { write("OK", txnId); }
    default void logFailure(String txnId) { write("FAIL", txnId); }

    private void write(String status, String txnId) {         // helper, not part of the contract
        System.out.println(Instant.now() + " " + status + " " + txnId);
    }

    private static String format(String s) { return s.trim(); }   // for static methods
}
```

`write` is invisible to implementers and to callers — it exists purely to deduplicate the defaults.

### Why each was introduced — don't mix them up

A common interview slip is to say static interface methods were added for backward compatibility. That's **default** methods. Static methods had a different, much smaller motive.

- **Default methods → backward compatibility / interface evolution.** Suppose millions of classes implement `Vehicle { void start(); }`. Adding `void stop();` breaks all of them. Adding `default void stop() { ... }` breaks none — old implementations keep compiling and inherit the new behaviour.
- **Static methods → organisation.** Helpers that used to sit in a companion utility class (`Collections.sort`, a hand-rolled `CollectionsUtil`) can now live next to the interface they serve: `Comparator.reverseOrder()`, `Comparator.comparing(...)`. Nothing about evolution — purely keeping related code together.
- **Private methods (Java 9) → deduplication.** Once defaults and statics exist, they share logic; private methods let you factor it out without adding to the public contract.

| Feature | Why introduced |
| --- | --- |
| **Default methods** (Java 8) | Add new behaviour to a published interface without breaking existing implementers |
| **Static methods** (Java 8) | Keep utility/helper methods inside the interface instead of a separate utility class |
| **Private methods** (Java 9) | Avoid duplicating code between default/static methods |

> 💡 **Interview**: *Why were default methods introduced?* → "To support interface evolution and backward compatibility while still letting implementing classes inherit the behaviour." Static methods were added for organisation and convenience, not compatibility.

## Functional Interfaces

An interface with **exactly one abstract method** (SAM — Single Abstract Method). It can carry any number of `default`, `static` and `private` methods without breaking the rule.

```java
@FunctionalInterface
interface FeeRule {
    long feeFor(long amountPaise);          // the single abstract method

    default FeeRule capped(long capPaise) { // defaults don't count
        return amount -> Math.min(feeFor(amount), capPaise);
    }
}
```

```java
FeeRule flat     = amount -> 200;
FeeRule bps      = amount -> amount * 30 / 10_000;
FeeRule cappedBps = bps.capped(1000);

cappedBps.feeFor(1_000_00);   // 300 → capped at 1000 only if it exceeded
```

Because there is exactly one abstract method, the compiler knows what a lambda is implementing — that is the entire mechanism behind lambdas and method references.

`@FunctionalInterface` is optional but worth writing: it makes the SAM rule a **compile error** to violate, so a teammate adding a second abstract method finds out immediately rather than breaking every lambda downstream.

One nuance: `public` methods of `Object` don't count against the SAM limit, which is why `Comparator` is a functional interface despite declaring `equals`:

```java
@FunctionalInterface
interface Comparator<T> {
    int compare(T o1, T o2);
    boolean equals(Object obj);   // redeclared from Object — doesn't count
}
```

### The built-ins worth knowing

| Interface | Method | Shape | Typical use |
| --- | --- | --- | --- |
| `Function<T,R>` | `R apply(T)` | in → out | `map(...)` |
| `Supplier<T>` | `T get()` | nothing → out | lazy values, `orElseGet` |
| `Consumer<T>` | `void accept(T)` | in → nothing | `forEach(...)` |
| `Predicate<T>` | `boolean test(T)` | in → boolean | `filter(...)` |
| `BiFunction<T,U,R>` | `R apply(T,U)` | two in → out | `merge(...)` |
| `UnaryOperator<T>` | `T apply(T)` | T → T | `replaceAll(...)` |
| `BinaryOperator<T>` | `T apply(T,T)` | T,T → T | `reduce(...)` |

## Marker Interfaces

A marker interface declares **nothing**:

```java
public interface Serializable { }   // literally empty
public interface Cloneable    { }
public interface Remote       { }
```

Its only job is to attach a fact to a class's *type*, which other code checks with `instanceof` and then behaves differently. The compiler enforces nothing — the "contract" is upheld by convention plus a runtime check in whoever consumes the object.

```java
class Employee implements Serializable {
    private String name;
}
```

Nothing is ever called on `Serializable`. The presence of the type in the hierarchy is the whole signal.

### `Serializable` — the real mechanism

Serialization turns an object into a byte stream (for a file, a socket, a cache) and back. `ObjectOutputStream.writeObject(obj)` does, conceptually:

```java
if (!(obj instanceof Serializable)) {
    throw new NotSerializableException(obj.getClass().getName());
}
// then walks the object's fields reflectively and writes them
```

That check is the entire magic.

```java
class Employee implements Serializable {
    private static final long serialVersionUID = 1L;

    private String name;
    private int age;
    private transient String password;   // excluded from the byte stream
}

try (ObjectOutputStream oos = new ObjectOutputStream(new FileOutputStream("emp.ser"))) {
    oos.writeObject(new Employee("Umesh", 25, "secret"));
}

try (ObjectInputStream ois = new ObjectInputStream(new FileInputStream("emp.ser"))) {
    Employee e = (Employee) ois.readObject();   // password comes back null
}
```

Where it actually shows up: caching (Redis/Ehcache/Hazelcast object payloads), HTTP session replication in a Tomcat cluster, RMI arguments, older JMS message payloads, and the serialize-then-deserialize deep-copy trick.

The details interviewers probe:

- **`transient`** excludes a field — passwords, derived values, or anything non-serializable like a `Socket` or `Thread`.
- **`static` fields are never serialized** — they belong to the class, not the object.
- **`serialVersionUID`** identifies the class version. If you don't declare it, the JVM derives one from the class structure, so almost any change to the class breaks deserialization of old bytes with `InvalidClassException`. Always declare it explicitly so *you* decide what is compatible.
- **Inheritance**: if a superclass is `Serializable`, every subclass is too. If the parent is *not* serializable, the parent's fields are not restored from the stream — instead its **no-arg constructor is invoked** during deserialization, so one must exist and be accessible.
- Deserialization **does not call the class's own constructor**, which is why it can produce objects that violate constructor invariants — a real security concern, not just trivia.

### `Cloneable`

`Object` holds the actual method:

```java
protected native Object clone() throws CloneNotSupportedException;
```

and it begins, conceptually, with `if (!(this instanceof Cloneable)) throw new CloneNotSupportedException();`. So `Cloneable` unlocks a method it does not itself declare — the design flaw that makes it the standard example of how *not* to use a marker interface. Full treatment in [[6. Cloning And Object Copying]].

### `Remote`

RMI lets a method on an object in one JVM be invoked from another, over the network — Java's pre-REST answer to distributed calls.

```java
interface PaymentService extends Remote {
    double getBalance(String accountId) throws RemoteException;   // every method must declare it
}
```

The server registers an implementation with the RMI registry; a client in another JVM looks it up by name and calls it. Arguments are serialized out, the call executes remotely, the result is serialized back. The `Remote` tag tells the RMI runtime to generate the stub/proxy machinery. Every method must declare `RemoteException` because a network call can fail in ways a local one cannot.

RMI is effectively legacy — gRPC, REST and message queues occupy that space now. It stays in interviews as the third canonical marker, to check whether you understand the *pattern*.

### The pattern behind all three

| Marker | Flags | Checked by | Missing it gives |
| --- | --- | --- | --- |
| `Serializable` | Convertible to bytes | `ObjectOutputStream` | `NotSerializableException` |
| `Cloneable` | Shallow-copyable via native `clone()` | `Object.clone()` | `CloneNotSupportedException` |
| `Remote` | Invocable from another JVM | RMI runtime / stub generation | Unusable in the RMI registry |

### Markers vs annotations

Markers are a **pre-annotation-era** pattern. Since Java 5, annotations are the better tool for tagging:

- An annotation can **carry data** — `@Column(name = "txn_id")`, `@Retention(RUNTIME)`. A marker interface carries only its own presence.
- An annotation doesn't **pollute the type hierarchy**. A marker adds a supertype that shows up in every `instanceof`, every generic bound, every API signature.

The counter-argument, and the reason markers aren't dead: a marker is **compile-time checkable**. `void save(Serializable s)` refuses non-serializable arguments at compile time; an annotation can only be checked reflectively at runtime.

`Serializable` and `Cloneable` survive because they date to Java 1 and removing them would break the world. New designs should reach for annotations — `@FunctionalInterface`, `@Entity`, `@Deprecated`.

## Nested Interfaces

An interface declared inside a class or another interface. It is implicitly `static` — writing `static` is legal but redundant — and is referenced through its enclosing type.

```java
class Vehicle {
    interface Serviceable {          // implicitly static
        void service();
    }
}

class Car implements Vehicle.Serviceable {
    public void service() { System.out.println("Servicing car"); }
}
```

The canonical example is `Map.Entry`, which has no meaning outside a `Map`:

```java
for (Map.Entry<String, Long> e : walletBalances.entrySet()) {
    System.out.println(e.getKey() + " = " + e.getValue());
}
```

The value is namespacing: a type that only makes sense in one context stays scoped to it, instead of adding noise to the package. A nested interface inside a *class* may be `private` or `protected` — an interface nested in an interface is always implicitly `public`.
