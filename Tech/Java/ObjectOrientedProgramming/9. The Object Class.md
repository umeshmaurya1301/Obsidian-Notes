# The Object Class

---

## Short Notes

---

### 1. What Every Class Inherits

```java
public class Object {
    public boolean equals(Object obj)
    public int hashCode()
    public String toString()
    protected Object clone() throws CloneNotSupportedException
    public final Class<?> getClass()
    protected void finalize()          // deprecated since Java 9, removed in 18+
    // wait(), notify(), notifyAll()   // final — thread coordination
}
```

- Every class extends `Object` directly or transitively
- `getClass()`, `wait()`, `notify()`, `notifyAll()` are `final` — never overridable

---

### 2. `equals()` — Default

- `Object.equals()` is literally `return this == obj;` — **reference identity**
- Two objects with identical fields are **not** equal by default
- Override to define **logical / value equality**

---

### 3. The `equals()` Recipe

1. `if (this == obj) return true;` — fast path
2. `if (obj == null || getClass() != obj.getClass()) return false;`
3. Cast to the concrete type
4. Compare the fields that define identity

- `getClass()` for strict type match; `instanceof` allows subclasses but can break symmetry

---

### 4. `equals()` Contract

- **Reflexive**: `x.equals(x)` is `true`
- **Symmetric**: `x.equals(y) == y.equals(x)`
- **Transitive**: `x=y` and `y=z` → `x=z`
- **Consistent**: same answer on repeated calls if nothing changed
- **Null**: `x.equals(null)` returns `false`, never throws

---

### 5. `hashCode()`

- Default: an int derived from the object's identity (address-ish, JVM-dependent)
- Used by `HashMap` / `HashSet` to pick a **bucket** before `equals()` is ever called
- Standard idiom: `return Objects.hash(x, y);`
- Manual form: `result = 31 * result + field` starting from `17`

---

### 6. Why 31

- Odd **prime** → preserves information better on multiplication overflow
- `31 * i` compiles to `(i << 5) - i` — a shift and a subtract, not a multiply

---

### 7. The `equals`/`hashCode` Contract

- `x.equals(y)` **must** imply `x.hashCode() == y.hashCode()`
- The reverse is **not** required — equal hashes with unequal objects is a legal **collision**
- Override `equals()` without `hashCode()` → hash collections break **silently**

---

### 8. What Breaks Concretely

```java
Set<Point> set = new HashSet<>();
set.add(new Point(1, 2));
set.contains(new Point(1, 2));   // false — different default hashes → wrong bucket
```

- `contains()` hashes first, jumps to a bucket, and never even calls `equals()`

---

### 9. The Symmetry Trap

- `Point.equals` using `instanceof` + `ColorPoint` adding a field breaks symmetry
- `p.equals(cp)` → `true`, `cp.equals(p)` → `false`
- Fix: use `getClass()` comparison, or make the subclass not add value fields
- Cost: a `Point` is then never equal to a `ColorPoint`, even with matching coordinates

---

### 10. `toString()`

- Default: `ClassName@hexHashCode` — useless in logs
- Called implicitly by `println(obj)`, string concatenation, and collection printing
- Override on every domain/entity class; `@ToString` or the IDE can generate it
- `record` gives you a good one free

---

### 11. `clone()`

- `protected native` shallow copy; throws unless the class implements `Cloneable`
- Bypasses constructors, shallow by default, hostile to `final` fields
- Prefer copy constructors — full treatment in [[6. Cloning And Object Copying]]

---

### 12. `getClass()`

- Returns the **runtime** class as `Class<?>` — object type, not reference type
- `final` — cannot be overridden by anyone
- Uses: reflection (Spring, Jackson, Hibernate), exact-type checks in `equals()`, loggers

```java
Animal a = new Dog();
a.getClass();              // class Dog
a.getClass() == Dog.class; // true — exact match only, ignores inheritance
a instanceof Animal;       // true — walks the hierarchy
```

---

### 13. `==` vs `equals()`

| | `==` | `.equals()` |
| --- | --- | --- |
| Compares | References (values for primitives) | Whatever the class defines |
| Overridable | No — it's an operator | Yes |
| On objects, by default | Reference identity | Reference identity |
| On `String`, wrappers | **Still reference identity** | Value equality |

---

### 14. The String Pool Trap

```java
String s1 = "hello";
String s2 = "hello";
String s3 = new String("hello");

s1 == s2;       // true  — both interned in the String Pool
s1 == s3;       // false — new String() bypasses the pool
s1.equals(s3);  // true  — String overrides equals()
s1 == s3.intern(); // true — intern() pulls it into the pool
```

---

### 15. The Integer Cache Trap

```java
Integer a = 100, b = 100;
a == b;          // true  — -128..127 are cached by Integer.valueOf()
Integer c = 200, d = 200;
c == d;          // false — outside the cache, two objects
c.equals(d);     // true  — always compare wrappers with equals()
```

# Detailed Explanation

---

## What Every Class Inherits

Every class in Java extends `Object`, directly or through its ancestors. That gives every object — including arrays and instances of your own classes — a small set of methods:

```java
public class Object {
    public boolean equals(Object obj)              // reference identity by default
    public int hashCode()                          // identity-based by default
    public String toString()                       // ClassName@hex
    protected Object clone()                       // shallow copy, gated by Cloneable
    public final Class<?> getClass()               // runtime class — final
    protected void finalize()                      // deprecated Java 9, removed Java 18+
    public final void wait() / notify() / notifyAll()   // monitor methods — final
}
```

Three of them (`equals`, `hashCode`, `toString`) are meant to be overridden, one (`clone`) is best avoided, and the rest are `final`.

---

## `equals()`

### The default

```java
public boolean equals(Object obj) {
    return (this == obj);       // Object's actual implementation
}
```

Reference identity — nothing more. Two distinct objects with identical field values are not equal:

```java
class Point {
    int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
}

new Point(1, 2).equals(new Point(1, 2));   // false
```

### Overriding it

You override `equals()` to define **value equality** — "these two objects represent the same thing", even though they are two objects.

```java
class Point {
    private final int x, y;

    @Override
    public boolean equals(Object obj) {
        if (this == obj) return true;                                    // 1. fast path
        if (obj == null || getClass() != obj.getClass()) return false;   // 2. null + type
        Point p = (Point) obj;                                           // 3. safe cast
        return x == p.x && y == p.y;                                     // 4. compare fields
    }
}

new Point(1, 2).equals(new Point(1, 2));   // true
```

The four steps are the standard recipe, and each earns its place:

1. **`this == obj`** — cheap short-circuit for the common self-comparison, and the only branch that's correct for a class with expensive field comparisons.
2. **Null and type check** — `x.equals(null)` must return `false` rather than throw, and the cast in step 3 must be safe. `getClass() != obj.getClass()` is the strict form; `instanceof` is the permissive one (see the symmetry trap below).
3. **Cast** — safe because of step 2.
4. **Compare the fields that define identity** — not necessarily all of them. A cached or derived field usually shouldn't participate.

For reference fields, use `Objects.equals(a, b)` rather than `a.equals(b)`, since it handles `null` on both sides. For `double`/`float`, use `Double.compare` to get `NaN` and `±0.0` right.

### The contract

`equals()` must be:

- **Reflexive** — `x.equals(x)` is `true`.
- **Symmetric** — `x.equals(y)` and `y.equals(x)` agree.
- **Transitive** — `x.equals(y)` and `y.equals(z)` imply `x.equals(z)`.
- **Consistent** — repeated calls return the same result while the objects don't change.
- **Null-safe** — `x.equals(null)` is `false`, never an exception.

These aren't academic. Collections assume all five, and a violation shows up as an object that can't be found in a `HashSet` or a `List.contains()` that returns the wrong answer.

---

## `hashCode()`

### The default

Returns an int derived from the object's identity — historically the memory address, actually an implementation detail of the JVM (often a per-object random value stored in the header).

```java
new Point(1, 2).hashCode();   // 366712642
new Point(1, 2).hashCode();   // 1829164700  — different objects, different hashes
```

### Why you override it

Hash-based collections use `hashCode()` to choose a **bucket**, then use `equals()` only among the entries already in that bucket. That two-stage lookup is what makes `HashMap` O(1) — but it means a wrong hash sends the lookup to the wrong bucket, where `equals()` is never even consulted.

```java
@Override
public int hashCode() {
    return Objects.hash(x, y);      // the standard idiom
}
```

Roughly what `Objects.hash` does internally:

```java
@Override
public int hashCode() {
    int result = 17;
    result = 31 * result + x;
    result = 31 * result + y;
    return result;
}
```

**Why 31?** Two reasons. It's an odd **prime**, so multiplying preserves more information when the int overflows — an even multiplier would shift bits off the end and lose them systematically. And `31 * i` is optimised by the JVM into `(i << 5) - i`, a shift and a subtract, which is cheaper than a multiply on older hardware.

On a hot path, note that `Objects.hash(...)` allocates a varargs array and autoboxes primitives; the manual form avoids both. For ordinary code the readability wins.

---

## The `equals`/`hashCode` Contract

The formal rules:

1. **If `x.equals(y)` is `true`, then `x.hashCode() == y.hashCode()` must be `true`.**
2. **The reverse is not required.** Equal hash codes with unequal objects is a **collision** — legal, expected, and handled by the collection.
3. If you override `equals()` and not `hashCode()`, you inherit `Object`'s identity-based hash, and rule 1 breaks immediately.

### What breaks, concretely

```java
class Point {
    int x, y;

    @Override
    public boolean equals(Object obj) {          // overridden
        if (!(obj instanceof Point p)) return false;
        return x == p.x && y == p.y;
    }
    // hashCode() NOT overridden
}
```

```java
Set<Point> set = new HashSet<>();
set.add(new Point(1, 2));
set.contains(new Point(1, 2));   // ❌ false
```

```text
add(Point(1,2))       hash = 366712642  → bucket 7   [Point(1,2)]
contains(Point(1,2))  hash = 1829164700 → bucket 23  [ ] → empty → false
                                                       ↑
                                          equals() is never called
```

The object is "equal" by your own definition and can never be found. Worse, it fails **silently** — no exception, just a lookup that always misses, and a `HashMap` that grows without ever hitting a key. This is why every IDE generates both methods together, and why `record` generates both for you.

The rule: **override `equals()` and `hashCode()` together, always, from the same set of fields.**

> 💡 **Interview**: What happens if you override `equals()` but not `hashCode()`? → Equal objects get different hash codes, so hash-based collections route them to different buckets. `HashSet.contains()` and `HashMap.get()` return misses for objects that are logically present — silently, with no error.

### A related trap: mutable keys

```java
Set<Point> set = new HashSet<>();
Point p = new Point(1, 2);
set.add(p);          // hashed into bucket for (1,2)
p.x = 99;            // the key mutated — hash is now different
set.contains(p);     // false — the object is in the set but hashes elsewhere
```

Keys in hash collections should be **immutable**, or at least have their hash-relevant fields frozen after insertion. This is one of the strongest practical arguments for making value types immutable.

## The Symmetry Trap

The choice between `getClass()` and `instanceof` in `equals()` isn't style — it decides whether symmetry survives subclassing.

```java
class Point {
    int x, y;
    @Override public boolean equals(Object o) {
        if (!(o instanceof Point p)) return false;      // permissive
        return x == p.x && y == p.y;
    }
}

class ColorPoint extends Point {
    String color;
    @Override public boolean equals(Object o) {
        if (!(o instanceof ColorPoint cp)) return false;  // stricter
        return super.equals(o) && color.equals(cp.color);
    }
}
```

```java
Point p = new Point(1, 2);
ColorPoint cp = new ColorPoint(1, 2, "red");

p.equals(cp);   // true  — cp IS a Point, coordinates match, Point doesn't know about colour
cp.equals(p);   // false — p is not a ColorPoint
```

Symmetry is violated, and the consequences are real: `list.contains(x)` can depend on which object the list holds, and `HashSet` behaviour becomes order-dependent.

Using `getClass()` restores symmetry:

```java
if (obj == null || getClass() != obj.getClass()) return false;
```

Now a `Point` is never equal to a `ColorPoint` in either direction. That is consistent, but it also means a `ColorPoint` can never be equal to a plain `Point` with the same coordinates — which some would call a Liskov violation in the other direction.

There is no fully satisfying resolution; this is a known limitation of value equality under inheritance. The practical answers:

- **`getClass()`** when the class may be subclassed with added value fields.
- **`instanceof`** when the class is `final`, or subclasses add no value state — this is what `record`s and `AbstractList` do.
- **Composition instead of inheritance** for value types: give `ColorPoint` a `Point` field rather than extending it.

## `toString()`

The default is `ClassName@hexHashCode`:

```java
System.out.println(new Point(1, 2));   // Point@1b6d3586
```

Overriding it is the highest value-per-line change you can make to a domain class:

```java
@Override
public String toString() {
    return "Point{x=" + x + ", y=" + y + "}";
}
```

It is called implicitly in more places than people expect: `System.out.println(obj)`, any string concatenation `"txn: " + payment`, and inside collections — printing a `List` calls `toString()` on every element. Log statements go through it constantly, which is exactly when you need it and exactly when `Payment@4a3b7c` tells you nothing.

Practical notes: override it on every entity/DTO/value class; keep it single-line and cheap since it appears in logs; and **never** include secrets — card numbers, tokens, passwords — because a `toString()` on a request object ends up in log aggregation. `record`s generate a sensible one automatically, and Lombok's `@ToString(exclude = "...")` covers the rest.

---

## `clone()`

```java
protected native Object clone() throws CloneNotSupportedException;
```

A `protected` native shallow copy that throws `CloneNotSupportedException` unless the class implements the `Cloneable` marker. Shallow by default, it bypasses constructors entirely and can't deep-copy `final` fields.

The short version: prefer copy constructors or static factories. The long version is [[6. Cloning And Object Copying]].

## `getClass()`

Returns the **runtime** class of the object, as a `Class<?>`. It reflects what the object actually is, never the reference type, and it is `final` so no class can lie about its own type.

```java
Animal a = new Dog();
a.getClass();                    // class Dog
a.getClass().getName();          // "com.example.Dog"  — fully qualified
a.getClass().getSimpleName();    // "Dog"
```

Where it shows up:

- **Reflection** — inspecting fields, methods and annotations at runtime. This is the foundation of Spring's DI and AOP, Jackson's JSON mapping, and Hibernate's ORM.
- **Exact type checks in `equals()`** — as above.
- **Loggers** — `LoggerFactory.getLogger(TransactionService.class)`, so log lines carry their origin.
- **Type-based dispatch** — a `Map<Class<?>, Handler>` lookup instead of an `instanceof` chain.

### `getClass()` vs `instanceof`

```java
Object obj = new Dog();

obj.getClass() == Dog.class;      // true  — exact type
obj.getClass() == Animal.class;   // false — getClass() ignores inheritance entirely
obj instanceof Animal;            // true  — instanceof walks the hierarchy
obj instanceof Dog;               // true
```

`getClass()` asks "what exactly is this?"; `instanceof` asks "can this be used as a...?". Use `instanceof` for polymorphic behaviour, `getClass()` when exact identity matters.

One caveat for Spring codebases: a bean wrapped in a CGLIB proxy reports `getClass()` as `TransactionService$$EnhancerBySpringCGLIB$$...`, not `TransactionService`. Code that compares `getClass()` against an expected class breaks on proxied beans, while `instanceof` still works.

## `==` vs `equals()`

| | `==` | `.equals()` |
| --- | --- | --- |
| Compares | References for objects; values for primitives | Whatever the class defines |
| Can be overridden | No — an operator with fixed behaviour | Yes |
| Objects, default | Reference identity | Reference identity (inherited) |
| Objects, overridden (`String`, wrappers, records) | **Still reference identity** | Value equality |
| Primitives | Value comparison | N/A — primitives have no methods |

The essential point: `==` **never** changes behaviour. No matter how a class defines equality, `==` compares references. All the surprises come from the JVM sometimes reusing references behind your back.

### The String pool

```java
String s1 = "hello";
String s2 = "hello";
String s3 = new String("hello");

s1 == s2;         // true  — both refer to the same pooled literal
s1 == s3;         // false — new String() forces a distinct heap object
s1.equals(s3);    // true  — String compares characters
```

String literals are automatically **interned**: the JVM keeps a pool (in the heap since Java 7) and hands out the same reference for identical literals. `new String("hello")` explicitly bypasses it.

```java
String s4 = s3.intern();
s1 == s4;         // true — intern() returns the pooled reference
```

This is also why `==` on strings *appears* to work in small test programs and then fails in production, where strings arrive from a database, a request body, or `StringBuilder` — none of which are interned.

### The Integer cache

```java
Integer a = 100, b = 100;
a == b;           // true  — cached

Integer c = 200, d = 200;
c == d;           // false — outside the cache
c.equals(d);      // true
```

Autoboxing goes through `Integer.valueOf()`, which caches instances for **−128 to 127** (the upper bound is tunable via `-XX:AutoBoxCacheMax`). Inside that range you get the same object back; outside it, a new one each time. `Byte`, `Short`, `Long`, `Character` (0–127) and `Boolean` cache similarly; `Float` and `Double` never do.

The same trap in its most dangerous form:

```java
Long amountPaise = payment.getAmount();      // Long
if (amountPaise == 50000L) { ... }           // ⚠ unboxes — fine
if (amountPaise == otherAmount) { ... }      // ❌ reference comparison, silently wrong above 127
```

**The rule to state in an interview**: *"`==` for primitives, `.equals()` for objects — including wrappers and Strings — because `==` compares references, and pooling and caching make that look correct in small cases while failing on real data."*
