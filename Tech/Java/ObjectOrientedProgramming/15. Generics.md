# Generics

---

## Short Notes

---

### 1. The Problem They Solve

```java
Box box = new Box();          // pre-generics: holds Object
box.set(123);
String s = (String) box.get();   // compiles, ClassCastException at runtime
```

- Two problems: **no compile-time type checking**, and **manual casts everywhere**
- Generics fix both — wrong type is a compile error, and the cast disappears

---

### 2. Generic Classes

```java
class Box<T> {
    private T value;
    void set(T value) { this.value = value; }
    T get() { return value; }
}

Box<String> box = new Box<>();
box.set(123);        // ❌ compile error
String s = box.get(); // ✅ no cast
```

- Conventions: `T` type, `E` element, `K`/`V` key/value, `R` return, `N` number

---

### 3. Multiple Type Parameters

```java
class Pair<K, V> {
    private final K key;
    private final V value;
}

Pair<String, Integer> p = new Pair<>("age", 25);
```

- `<>` on the right is the **diamond operator** — the compiler infers the arguments

---

### 4. Type Erasure

- Generics exist **only at compile time**; the JVM sees raw types
- `Pair<String,Integer>.getClass()` → `class Pair`
- Compiler inserts the casts it already proved safe
- Backward compatibility with pre-Java-5 code was the reason

---

### 5. What Erasure Forbids

- `new T()` — the runtime doesn't know what `T` is
- `T[] arr = new T[10]` — no generic array creation
- `obj instanceof List<String>` — only the raw `List` can be tested
- Overloads differing only in type argument — identical after erasure

---

### 6. Generic Methods

```java
static <T> T getFirst(List<T> list) { return list.get(0); }
static <K, V> Map<K, V> singletonMap(K key, V value) { ... }
```

- The `<T>` goes **before the return type**
- Has its own type parameter, independent of the class — the class needn't be generic
- Inferred fresh per call site; explicit witness `Utils.<String>getFirst(...)` is rarely needed

---

### 7. Bounded Types — `extends`

```java
class NumberBox<T extends Number> {
    double asDouble() { return value.doubleValue(); }   // Number's methods available
}
```

- Without a bound, `T` is treated as `Object` — no useful methods
- `extends` here means "or implements", for both classes and interfaces

---

### 8. Multiple Bounds

```java
<T extends Number & Comparable<T> & Payable>
```

- At most **one class**, and it must come first; any number of interfaces after
- Common idiom: `<T extends Comparable<T>>` — how `Collections.max` is declared

---

### 9. Generics Are Invariant

```java
List<String> names = ...;
printList(names);            // ❌ if printList takes List<Object>
```

- `List<String>` is **not** a subtype of `List<Object>`, even though `String` is a subtype of `Object`
- Deliberate — it's what makes the compiler catch what array covariance defers to runtime
- Wildcards are the controlled escape hatch

---

### 10. Unbounded Wildcard — `?`

```java
static void print(List<?> list) {
    for (Object o : list) System.out.println(o);
}
```

- Accepts a list of any type; elements readable only as `Object`
- **Cannot add** anything except `null`
- Use for type-independent work: `size()`, `isEmpty()`, printing

---

### 11. Upper Bounded — `? extends T`

```java
static double sum(List<? extends Number> list) {
    for (Number n : list) ...       // ✅ safe to read as Number
}
```

- **Producer** — you read out of it
- Cannot add (except `null`): the real type might be `List<Integer>` or `List<Double>`
- Accepts `List<Integer>`, `List<Double>`, `List<Number>`

---

### 12. Lower Bounded — `? super T`

```java
static void addInts(List<? super Integer> list) {
    list.add(10);                    // ✅ safe to write an Integer
}
```

- **Consumer** — you write into it
- Accepts `List<Integer>`, `List<Number>`, `List<Object>`
- Reads come back only as `Object`

---

### 13. PECS

> **Producer Extends, Consumer Super**

| Need | Use |
| --- | --- |
| Only read out | `? extends T` |
| Only write in | `? super T` |
| Both, type-safely | plain `T` |
| Neither — just `size()` etc. | `?` |

```java
static <T> void copy(List<? super T> dest, List<? extends T> src)
```

---

### 14. Why Invariance — The Array Contrast

```java
Object[] arr = new String[3];   // ✅ arrays are COVARIANT
arr[0] = 100;                   // compiles → ArrayStoreException at runtime
```

- Array covariance defers the error to runtime — a known design flaw
- Generic invariance moves it to compile time
- Wildcards restore the flexibility without the runtime risk

---

### 15. Summary Table

| Concept | Syntax | Purpose |
| --- | --- | --- |
| Generic class | `class Box<T>` | Type-safe container |
| Generic method | `static <T> T m(...)` | Type-safe, class-independent |
| Bounded type | `<T extends Number>` | Restrict T, unlock its methods |
| Unbounded wildcard | `List<?>` | Any type, read as `Object` |
| Upper bounded | `List<? extends T>` | Producer — read as `T`, no adds |
| Lower bounded | `List<? super T>` | Consumer — add `T`, read as `Object` |

# Detailed Explanation

---

## The Problem Generics Solve

### Before Java 5

```java
class Box {
    private Object value;
    void set(Object value) { this.value = value; }
    Object get() { return value; }
}
```

```java
Box box = new Box();
box.set("Hello");
box.set(123);                        // no complaint — Box accepts anything

String s = (String) box.get();       // a cast, every single time

Box box2 = new Box();
box2.set(123);
String s2 = (String) box2.get();     // compiles fine → ClassCastException at runtime
```

Two distinct problems. There's **no compile-time type checking** — a container that holds `Object` accepts anything, so a type mistake survives compilation. And there's **manual casting at every read**, which is noise and a runtime failure point.

### After

```java
class Box<T> {
    private T value;
    void set(T value) { this.value = value; }
    T get() { return value; }
}
```

```java
Box<String> box = new Box<>();
box.set("Hello");
box.set(123);        // ❌ incompatible types: int cannot be converted to String
String s = box.get();  // ✅ no cast — the compiler already knows
```

The error moved from runtime to compile time, and the cast vanished. The cast still happens in the bytecode — the compiler inserts it — but it's guaranteed safe because the compiler verified the type at every insertion point.

---

## Generic Classes

A class parameterised by one or more type parameters.

```java
class Pair<K, V> {
    private final K key;
    private final V value;

    Pair(K key, V value) { this.key = key; this.value = value; }

    K getKey()   { return key; }
    V getValue() { return value; }
}
```

```java
Pair<String, Integer> p1 = new Pair<>("age", 25);
Pair<String, List<String>> p2 = new Pair<>("skills", List.of("Java", "Spring"));
```

The `<>` on the right is the **diamond operator** (Java 7+) — the compiler infers the type arguments from the declaration, so you don't repeat them.

Naming conventions, which the JDK follows consistently: `T` for a general type, `E` for an element in a collection, `K`/`V` for key and value, `R` for a return type, `N` for a number.

### A wrapper you'll actually write

```java
class ApiResponse<T> {
    private final int statusCode;
    private final T data;
    private final String errorMessage;

    ApiResponse(int statusCode, T data) {
        this.statusCode = statusCode;
        this.data = data;
        this.errorMessage = null;
    }

    T getData() { return data; }
}
```

```java
ApiResponse<TransactionDetails> txn      = new ApiResponse<>(200, details);
ApiResponse<List<Payment>>      payments = new ApiResponse<>(200, paymentList);
```

One wrapper structure, many payload types, full type safety at every endpoint. This is the single most common generic class in a Spring Boot codebase.

---

## Type Erasure

```java
Pair<String, Integer> p = new Pair<>("age", 25);
System.out.println(p.getClass());     // class Pair — not Pair<String, Integer>
```

**Generics are a compile-time construct.** After type checking, the compiler *erases* the type arguments: `Pair<K,V>` becomes plain `Pair` in the bytecode, unbounded parameters become `Object`, bounded ones become their bound, and casts are inserted wherever needed.

```text
source                          bytecode (after erasure)
──────                          ────────────────────────
class Box<T> { T get(); }       class Box { Object get(); }
class N<T extends Number>       class N   { Number ...   }
String s = box.get();           String s = (String) box.get();   ← compiler-inserted cast
```

The reason is **backward compatibility**: Java 5 had to let generic and pre-generic code interoperate in the same JVM, so generics had to compile down to what the existing JVM already understood. (Contrast C#, which reifies generics in the runtime, at the cost of a breaking change.)

### What erasure forbids

**No `new T()`** — the runtime has no idea what `T` is:

```java
class Box<T> {
    T create() { return new T(); }   // ❌ type parameter T cannot be instantiated directly
}
// workaround: pass a factory
class Box<T> {
    T create(Supplier<T> factory) { return factory.get(); }
}
```

**No generic array creation:**

```java
T[] arr = new T[10];                       // ❌
T[] arr = (T[]) new Object[10];            // ⚠ the standard workaround, with an unchecked warning
```

This is exactly what `ArrayList` does internally.

**No parameterised `instanceof`:**

```java
if (obj instanceof List<String>) { }   // ❌ illegal generic type for instanceof
if (obj instanceof List<?>)      { }   // ✅ only the raw shape is testable
```

**No overloading on type arguments** — both erase to the same signature:

```java
void process(List<String> l)  { }
void process(List<Integer> l) { }   // ❌ "have the same erasure"
```

**No static field of a type parameter** — there's one class object shared across all parameterisations, so a `static T` would have no single meaning.

> 💡 **Interview**: Why can't you write `new T()` in a generic class? → Type erasure. `T` doesn't exist at runtime, so the JVM has no constructor to call. You pass a `Supplier<T>` or a `Class<T>` instead.

## Generic Methods

A method with its **own** type parameter, declared just before the return type. The enclosing class doesn't have to be generic.

```java
class Utils {
    static <T> void printArray(T[] array) {
        for (T item : array) System.out.println(item);
    }

    static <T> T getFirst(List<T> list) {
        return list.get(0);
    }

    static <K, V> Map<K, V> singletonMap(K key, V value) {
        Map<K, V> map = new HashMap<>();
        map.put(key, value);
        return map;
    }
}
```

```java
Utils.printArray(new Integer[]{1, 2, 3});        // T inferred as Integer
Utils.printArray(new String[]{"Umesh", "Priya"}); // T inferred as String — same method

Map<String, Integer> m = Utils.singletonMap("age", 25);   // K and V both inferred
```

The type parameter is scoped to a single call and inferred fresh each time, from the arguments or the expected return type. You can supply it explicitly with a **type witness**, though it's rarely needed:

```java
List<String> empty = Collections.<String>emptyList();
```

The usual reason to need one is when inference has nothing to work with — an empty collection or a `null` argument.

---

## Bounded Types

A bound restricts what a type parameter can be, which in turn tells the compiler what methods are available on it.

```java
class NumberBox<T extends Number> {
    private final T value;
    NumberBox(T value) { this.value = value; }

    double asDouble() {
        return value.doubleValue();     // ✅ the compiler knows T is at least a Number
    }
}
```

```java
new NumberBox<Integer>(10);     // ✅
new NumberBox<Double>(5.5);     // ✅
new NumberBox<String>("x");     // ❌ String is not within its bound
```

Without the bound, `T` erases to `Object` and `value.doubleValue()` won't compile — the compiler has no guarantee the method exists. The bound is a promise: *whatever `T` turns out to be, it will have at least `Number`'s API.*

Note that `extends` covers interfaces too — `<T extends Comparable<T>>` is a bound on an interface, written with `extends`, not `implements`.

### Multiple bounds

```java
interface Payable { long getPaymentPaise(); }

class Payroll<T extends Number & Comparable<T> & Payable> { ... }
```

At most **one class**, and it must be listed first; any number of interfaces after, separated by `&`.

### The classic bounded method

```java
static <T extends Comparable<T>> T max(List<T> list) {
    T max = list.get(0);
    for (T item : list) {
        if (item.compareTo(max) > 0) max = item;    // compareTo available because of the bound
    }
    return max;
}

Integer biggest = max(List.of(3, 7, 2, 9));
```

`<T extends Comparable<T>>` is a **recursive bound** — `T` bounded by an interface parameterised on `T` itself. It reads as "a type comparable to its own kind", and it's how `Collections.max` is declared (with a slightly looser `<? super T>` on the `Comparable`, so subclasses of a comparable type still work).

## Why Generics Are Invariant

```java
static void printList(List<Object> list) {
    for (Object o : list) System.out.println(o);
}

List<String> names = List.of("Umesh", "Priya");
printList(names);      // ❌ incompatible types: List<String> cannot be converted to List<Object>
```

`String` is a subtype of `Object`, but **`List<String>` is not a subtype of `List<Object>`.** Generic types are **invariant**: two parameterisations of the same generic type are unrelated, regardless of how their arguments relate.

That looks like a limitation until you see what the alternative costs. Arrays *are* covariant:

```java
Object[] objArray = new String[3];   // ✅ allowed — arrays are covariant
objArray[0] = 100;                   // compiles fine
                                     // ❌ ArrayStoreException at RUNTIME
```

The array is really a `String[]`, so storing an `Integer` is invalid — but the compiler can't see it, and the JVM has to carry a runtime type check on every array store to catch it. Array covariance is a widely acknowledged design flaw in Java.

Generics were deliberately made invariant to avoid it. If `List<String>` were assignable to `List<Object>`, then `objList.add(100)` would compile and corrupt the list — and unlike arrays, erasure means there'd be no runtime check to catch it. Invariance moves the whole class of error to compile time.

Wildcards are the **controlled escape hatch**: they let a method accept a range of related parameterisations, while restricting the operations to the ones that stay safe.

## Wildcards

### Unbounded — `?`

```java
static void printList(List<?> list) {
    for (Object o : list) System.out.println(o);
    System.out.println(list.size());
}

printList(List.of("a", "b"));      // ✅
printList(List.of(1, 2, 3));       // ✅
printList(List.of(true, false));   // ✅
```

`List<?>` means "a list of some specific unknown type". You can read elements as `Object` — that's all that's guaranteed — and call type-independent methods.

You **cannot add** anything except `null`:

```java
List<?> list = new ArrayList<String>();
list.add("hello");    // ❌ the compiler doesn't know this is a List<String>
list.add(null);       // ✅ null is a valid value of every reference type
```

Use it when the element type genuinely doesn't matter: printing, counting, checking emptiness.

### Upper bounded — `? extends T`

```java
static double sumAll(List<? extends Number> list) {
    double sum = 0;
    for (Number n : list) {          // ✅ every element is at least a Number
        sum += n.doubleValue();
    }
    return sum;
}

sumAll(List.of(1, 2, 3));       // List<Integer> ✅
sumAll(List.of(1.5, 2.5));      // List<Double>  ✅
sumAll(List.of("a", "b"));      // ❌ String is not a Number
```

"Some unknown type that is `T` or a subtype." Reading is safe — whatever the actual element type, it's assignable to `T`.

Writing is not:

```java
List<? extends Number> list = new ArrayList<Integer>();
list.add(10);      // ❌ might actually be a List<Double>
list.add(10.5);    // ❌ might actually be a List<Integer>
Number n = list.get(0);   // ✅
```

The compiler knows the list has *one* specific element type; it just doesn't know which. Since no value is safe for every possibility, all additions are rejected.

### Lower bounded — `? super T`

```java
static void addNumbers(List<? super Integer> list) {
    list.add(10);      // ✅ any list that holds Integer-or-broader can take an Integer
    list.add(20);
}

addNumbers(new ArrayList<Integer>());   // ✅
addNumbers(new ArrayList<Number>());    // ✅
addNumbers(new ArrayList<Object>());    // ✅
```

"Some unknown type that is `T` or a supertype." Writing a `T` is safe — whatever the actual type is, a `T` fits in it.

Reading is limited:

```java
List<? super Integer> list = new ArrayList<Number>();
list.add(10);              // ✅
Object o = list.get(0);    // ✅ only Object is guaranteed
Integer i = list.get(0);   // ❌ the list could be List<Number> or List<Object>
```

## PECS

> **Producer Extends, Consumer Super.**

Ask what the parameter does *from the method's point of view*:

| The parameter... | Use | Because |
| --- | --- | --- |
| **produces** values you read out | `? extends T` | every element is at least a `T` |
| **consumes** values you write in | `? super T` | it can hold a `T` or anything broader |
| does both, type-safely | plain `T` | no wildcard can allow both |
| neither — just `size()`, `isEmpty()` | `?` | the element type is irrelevant |

### The JDK example

```java
public static <T> void copy(List<? super T> dest, List<? extends T> src) {
    for (int i = 0; i < src.size(); i++) {
        dest.set(i, src.get(i));      // read from src, write to dest
    }
}
```

`src` is a producer — only read from → `? extends T`.
`dest` is a consumer — only written to → `? super T`.

```java
List<Integer> ints = List.of(1, 2, 3);
List<Number> numbers = new ArrayList<>(List.of(0, 0, 0));
Collections.copy(numbers, ints);      // dest: List<Number> ⊇ Integer ✅   src: List<Integer> ✅
```

The same pattern is everywhere in the modern APIs once you look:

```java
Stream<R> map(Function<? super T, ? extends R> mapper);   // consumes T, produces R
void forEach(Consumer<? super T> action);                 // consumes T
Optional<T> or(Supplier<? extends Optional<? extends T>> supplier);   // produces
```

The practical value of PECS is at your own API boundaries: declaring a parameter as `List<? extends Payment>` instead of `List<Payment>` lets callers pass a `List<UpiPayment>`, which they otherwise couldn't.

## Summary Table

| Concept | Syntax | Purpose |
| --- | --- | --- |
| Generic class | `class Box<T>` | Type-safe container for any type |
| Generic method | `static <T> T method(...)` | Type-safe, independent of class generics |
| Bounded type | `<T extends Number>` | Restrict `T`, and unlock its methods |
| Multiple bounds | `<T extends A & B>` | One class first, then interfaces |
| Unbounded wildcard | `List<?>` | Any type; read as `Object`, no adds |
| Upper bounded | `List<? extends T>` | Producer — read as `T`, no adds |
| Lower bounded | `List<? super T>` | Consumer — add `T`, read as `Object` |

**The summary line**: *"Generics give compile-time type safety and remove manual casts, implemented by erasure so pre-generic code still interoperates. Because generics are invariant — deliberately, to avoid the runtime failures array covariance allows — wildcards are the escape hatch: `? extends` when I only read (producer), `? super` when I only write (consumer). That's PECS."*
