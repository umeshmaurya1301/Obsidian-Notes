# OOP Fundamentals

---

## Short Notes

---

### 1. What OOP Is

- Model a system as **objects** = state (fields) + behaviour (methods) bundled together
- Opposite of procedural: data and the functions on it live in the same unit
- Goal: **contain change** — localise it so one edit doesn't ripple across the codebase
- Java is class-based: every object is an instance of a class; every class implicitly extends `Object`

---

### 2. The Four Pillars

```text
Abstraction    → expose WHAT, hide HOW        (design / contract)
Encapsulation  → protect the state            (implementation / data hiding)
Inheritance    → reuse via is-a               (hierarchy)
Polymorphism   → one name, many behaviours    (dispatch)
```

- Abstraction + Encapsulation = hide complexity
- Inheritance + Polymorphism = extend and vary behaviour

---

### 3. Abstraction

- Expose **what** an object does, hide **how** it does it
- Caller codes against a contract, not an implementation
- Car analogy: steering wheel and brake exposed, combustion hidden
- Payoff: swap the implementation without touching any caller

---

### 4. Achieving Abstraction in Java

- `abstract class` → partial abstraction (can hold state + concrete methods)
- `interface` → pure contract (Java 8+ also allows `default` / `static` bodies)
- An abstract class **cannot be instantiated** — only subclassed
- A class with even one `abstract` method **must** be declared `abstract`

---

### 5. Encapsulation

- Bundle data + the methods that operate on it into one class
- Fields `private`, controlled access through methods that validate
- Protects **invariants** — `balance` can never be set negative directly
- Lets the internal representation change without breaking callers

> Blind getters/setters on every field is not encapsulation — it's a public field with extra steps.

---

### 6. Abstraction vs Encapsulation

| Aspect | Abstraction | Encapsulation |
| ------ | ----------- | ------------- |
| Concern | Design — what to expose | Implementation — how to protect |
| Hides | Complexity / logic | Data / state |
| Mechanism | `abstract` class, `interface` | Access modifiers, accessors |
| Question answered | "What can this do?" | "Who can touch this?" |

---

### 7. Inheritance

- Subclass acquires fields + methods of a superclass → **is-a** relationship
- `class Manager extends Employee` → `Manager` **is-a** `Employee`
- Enables reuse and is the mechanism runtime polymorphism rides on
- Overused it creates rigid hierarchies → prefer composition when is-a is shaky

---

### 8. Inheritance Rules in Java

- **Single inheritance** for classes (one `extends`), multiple types via `implements`
- **Constructors are not inherited**; `super(...)` invokes the parent's
- `private` members are not accessible in the child (present in memory, not in scope)
- No `extends` written → implicitly `extends Object`

---

### 9. Polymorphism

- "Many forms" — the same call site produces different behaviour
- **Compile-time** (overloading) → resolved by the compiler, static binding
- **Runtime** (overriding) → resolved by the JVM, dynamic binding
- Runtime polymorphism is the one interviewers mean by default

---

### 10. Compile-Time Polymorphism (Overloading)

- Same method name, **different parameter list** (count / type / order)
- Resolved at compile time from the static types of the arguments
- **Return type alone cannot overload** — `int f(long)` vs `long f(long)` won't compile
- Can occur in the same class or across parent–child

---

### 11. Runtime Polymorphism (Overriding)

- Subclass replaces a parent's instance method with its own implementation
- Chosen at runtime by the **actual object type**, not the reference type
- `PaymentProcessor p = new UpiProcessor(); p.process(x)` → UPI version runs
- Also called dynamic dispatch / virtual method invocation

---

### 12. Overriding Rules

- Same signature (name + parameter list) exactly
- Return type same or **covariant** (a subtype)
- Access modifier **cannot narrow** (`public` → `protected` is illegal)
- Checked exceptions: same, narrower, or fewer — never broader
- `private`, `static`, `final` methods cannot be overridden
- `static` redefinition is **hiding**, not overriding

---

### 13. Overloading vs Overriding

| Aspect | Overloading | Overriding |
| ------ | ----------- | ---------- |
| Binding | Compile-time (static) | Runtime (dynamic) |
| Where | Same class (usually) | Parent → child |
| Signature | Must differ | Must match |
| Return type | Free | Same or covariant |
| Access modifier | Free | Cannot narrow |
| `@Override` | Not applicable | Recommended |

---

### 14. Reference Type vs Object Type

- `Shape s = new Circle();` → reference type `Shape`, object type `Circle`
- **Compiler** checks the reference type → only `Shape`'s members are callable
- **JVM** dispatches instance methods on the object type → `Circle`'s body runs
- Fields and `static` methods bind to the **reference type** — classic trap

---

### SDE-2 Interview Priority

**Must Know**: Four pillars with a real example each, Abstraction vs Encapsulation, Overloading vs Overriding, Overriding rules, Reference type vs object type, Abstract class vs interface

**Nice To Know**: Covariant return types, Exception narrowing on override, Why constructors aren't inherited, Overload resolution order

**Advanced**: Overload resolution phases, LSP violations from careless inheritance, Fragile base class problem

# Detailed Explanation

---

## What OOP Is

Object-oriented programming models a system as a set of collaborating **objects**, each owning its own state and exposing behaviour that acts on that state. The procedural alternative keeps data in structs and logic in free functions — every function that touches the data must be trusted to maintain its rules, and no single place owns them.

The real value is not "code reuse", the answer people give by reflex. It is **containment of change**. If the rules of a wallet balance live inside `Wallet`, changing them means editing one class. If they live in twelve services that each do `wallet.balance -= amount`, the change becomes a manual audit of the whole codebase.

```text
Procedural                     Object-Oriented
──────────                     ───────────────
data:   WalletRow              class Wallet {
logic:  debit(row, amt)          private long balance;
        credit(row, amt)         void debit(long amt) { ... }
        validate(row)            void credit(long amt) { ... }
                               }
        ↑ rules scattered        ↑ rules owned by the type
```

In Java every object is an instance of a class, and every class sits under `java.lang.Object` — so `equals()`, `hashCode()`, `toString()` and `getClass()` are available on absolutely everything.

---

## Abstraction

Abstraction is a **design-time** decision: what does this thing promise to do, and what do I refuse to tell you about it? The caller programs against that promise.

```java
abstract class PaymentProcessor {
    // the contract: "I can move money" — nothing about how
    abstract PaymentResult process(Payment payment);
}

class UpiProcessor extends PaymentProcessor {
    @Override
    PaymentResult process(Payment payment) {
        // VPA resolution, NPCI handshake, switch routing — all invisible to the caller
        return switchClient.route(payment);
    }
}

class CardProcessor extends PaymentProcessor {
    @Override
    PaymentResult process(Payment payment) {
        return acquirer.authorize(payment);   // entirely different mechanism
    }
}
```

The calling code never changes:

```java
PaymentResult r = processor.process(payment);   // UPI? card? wallet? irrelevant here
```

Adding a new rail means adding a class, not editing the caller. That is the payoff, and it is the Open/Closed Principle in miniature.

### Abstract class vs interface — the short version

- `abstract class` — partial abstraction. Can hold fields, constructors and concrete methods. Use it when subclasses genuinely share **state and implementation**.
- `interface` — a pure contract. Use it when defining a **capability** that otherwise unrelated types can offer.

A class containing any `abstract` method must itself be declared `abstract`, and an abstract class can never be instantiated directly — `new PaymentProcessor()` is a compile error. It can still have a constructor, which runs via `super()` when a concrete subclass is created.

> 💡 **Interview**: Can an abstract class have a constructor? → Yes. It can't be instantiated directly, but the constructor still runs through `super()` when a concrete subclass is created — it exists to initialise the inherited state.

---

## Encapsulation

Encapsulation is the **implementation-time** counterpart: bundle the state with the code allowed to touch it, and make direct access impossible.

```java
class Wallet {
    private long balancePaise;              // unreachable from outside
    private final String walletId;

    Wallet(String walletId, long openingBalance) {
        if (openingBalance < 0) throw new IllegalArgumentException("negative opening balance");
        this.walletId = walletId;
        this.balancePaise = openingBalance;
    }

    long getBalancePaise() { return balancePaise; }     // read-only exposure

    void credit(long amountPaise) {
        if (amountPaise <= 0) throw new IllegalArgumentException("credit must be positive");
        balancePaise += amountPaise;
    }

    void debit(long amountPaise) {
        if (amountPaise <= 0) throw new IllegalArgumentException("debit must be positive");
        if (amountPaise > balancePaise) throw new InsufficientFundsException(walletId);
        balancePaise -= amountPaise;        // invariant balance >= 0 can never break
    }
}
```

```java
wallet.balancePaise = -5000;   // ❌ compile error — the field is private
wallet.debit(5000);            // ✅ goes through the rule
```

Note there is deliberately **no `setBalance()`**. A setter would hand back exactly the power the private field took away. Encapsulation means exposing *operations* (`credit`, `debit`), not *fields*. A class where every private field has a matching public getter and setter is a data bag with ceremony — it protects nothing.

The second payoff is freedom to change. If `balancePaise` later becomes a value derived from a ledger table, only `Wallet` changes; every caller still calls `getBalancePaise()`.

---

## Abstraction vs Encapsulation

These get conflated constantly, so keep the split sharp:

| | Abstraction | Encapsulation |
| --- | --- | --- |
| When | Design time | Implementation time |
| Hides | Complexity — the *how* | Data — the *state* |
| Achieved by | `abstract`, `interface` | `private`, `protected`, accessors |
| Failure looks like | Callers doing `instanceof` on every subtype | Callers mutating fields and corrupting invariants |

One line to remember: **abstraction hides the logic from the caller; encapsulation hides the data from everyone.**

## Inheritance

Inheritance makes a subclass acquire the members of a superclass, establishing an **is-a** relationship.

```java
class Employee {
    protected String name;
    protected long baseSalary;

    void printPayslip() {
        System.out.println(name + " earns " + totalCompensation());
    }

    long totalCompensation() { return baseSalary; }
}

class Manager extends Employee {
    private long bonus;

    @Override
    long totalCompensation() {
        return baseSalary + bonus;      // reuses the inherited field
    }
}
```

`Manager` is-a `Employee`: it inherits `name`, `baseSalary` and `printPayslip()`, and specialises `totalCompensation()`. Notice `printPayslip()` — written once in the parent — now prints the right number for a `Manager` without being touched. That is inheritance and polymorphism working together.

### The Java-specific rules

- **Single inheritance for classes.** `class C extends A, B` is a compile error. Multiple inheritance of *type* comes from `implements`.
- **Constructors are not inherited.** They are not members. A subclass declares its own and delegates upward with `super(...)`.
- **`private` members are not accessible** in the subclass. The bytes exist in the object's layout, but the name is not in scope.
- **Implicit `extends Object`** when no superclass is named.

### The caution

Inheritance is the tightest coupling Java offers — the subclass depends on the parent's *implementation*, not just its interface, so a change in the parent can silently break every descendant (the fragile base class problem). Use it when the is-a relationship is genuinely permanent and the subtype is substitutable for the parent everywhere (Liskov). Otherwise, compose.

```java
class Stack extends ArrayList<String> { }   // ❌ a Stack is not an ArrayList — leaks add(int, E)

class Stack {                                // ✅ composition: expose only what you mean to
    private final List<String> items = new ArrayList<>();
}
```

## Polymorphism

"Many forms": the same call expression produces different behaviour depending on context. Java has two distinct mechanisms, resolved at two different times.

### Compile-time polymorphism — overloading

Same name, different parameter list. The **compiler** picks the target from the static types of the arguments.

```java
class SettlementCalculator {
    long fee(long amount)                     { return amount / 100; }
    long fee(long amount, int bps)            { return amount * bps / 10_000; }
    long fee(long amount, int bps, long cap)  { return Math.min(fee(amount, bps), cap); }
}
```

Rules and traps:

- The parameter list must differ in **count, type or order**. Changing only the return type is a compile error:

```java
int  fee(long amount) { ... }
long fee(long amount) { ... }   // ❌ "method fee(long) is already defined"
```

- Overloads may be spread across a class and its parent — a subclass method with a *different* signature overloads rather than overrides. This is exactly why `@Override` is worth writing: it turns an accidental overload into a compile error.
- Resolution prefers an exact match, then widening, then autoboxing, then varargs — so `f(int)` beats `f(long)` beats `f(Integer)` beats `f(int...)`.

### Runtime polymorphism — overriding

A subclass supplies its own body for an inherited instance method, and the **JVM** picks the body from the actual object.

```java
abstract class Shape { abstract double area(); }

class Circle extends Shape {
    private final double radius;
    Circle(double radius) { this.radius = radius; }
    @Override double area() { return Math.PI * radius * radius; }
}

class Square extends Shape {
    private final double side;
    Square(double side) { this.side = side; }
    @Override double area() { return side * side; }
}
```

```java
List<Shape> shapes = List.of(new Circle(2), new Square(3));
double total = shapes.stream().mapToDouble(Shape::area).sum();
// each element dispatches to its own area() at runtime
```

This is what "program to an interface" buys: the loop never grows an `if/else` chain when a new shape appears.

## Overriding Rules

A method only overrides if **all** of these hold:

1. **Identical signature** — same name, same parameter types in the same order.
2. **Return type** identical or **covariant** (a subtype of the parent's return type). Legal since Java 5.
3. **Access modifier cannot be narrowed.** Widening is fine: `protected` → `public` is legal, `public` → `protected` is not.
4. **Checked exceptions cannot be broadened.** The override may declare the same checked exception, a subclass of it, fewer, or none. Unchecked exceptions are unrestricted.
5. **Not `private`, `static` or `final`.** A `private` parent method isn't visible, so a same-named child method is simply a new, unrelated method. A `static` one is *hidden*. A `final` one is locked.
6. **Constructors are never overridden** — they aren't inherited.

```java
class BaseProcessor {
    protected Number settle(Payment p) throws IOException { return 0L; }
}

class UpiProcessor extends BaseProcessor {
    @Override
    public Long settle(Payment p) throws FileNotFoundException {   // ✅ all three relaxations at once:
        return 1L;                                                 //    wider access, covariant return,
    }                                                              //    narrower checked exception
}

class Broken extends BaseProcessor {
    @Override
    protected Number settle(Payment p) throws Exception { return 0L; }  // ❌ broader checked exception
}
```

### Covariant return types

```java
class Animal {
    Animal reproduce() { return new Animal(); }
}
class Dog extends Animal {
    @Override
    Dog reproduce() { return new Dog(); }    // narrowed to Dog — legal
}
```

```java
Dog puppy = new Dog().reproduce();   // ✅ no cast needed
```

Without covariance the caller would have to downcast every time. This is why `clone()` overrides and fluent builder methods can return the concrete type instead of the base one. The rule is one-directional: narrow the return type, never widen it.

> 💡 **Interview**: Can an overriding method throw a broader checked exception? → No. Callers hold a parent-typed reference and only handle the parent's declared exceptions; a broader one would let an unhandled checked exception escape, breaking the compiler's guarantee.

## Reference Type vs Object Type

Every reference has two types, and they answer two different questions.

```java
Shape s = new Circle(2);
//    ↑ reference type      ↑ object type
```

- The **compiler** works with the reference type. It decides what you are *allowed* to call: only members declared on `Shape`.
- The **JVM** works with the object type. For instance methods it looks up the body in the actual object's class at runtime.

```java
class Shape { void draw() { System.out.println("shape"); } }
class Circle extends Shape {
    @Override void draw() { System.out.println("circle"); }
    double getRadius() { return 2; }
}

Shape s = new Circle();
s.draw();        // "circle"  → dispatched on the object type
s.getRadius();   // ❌ compile error → checked against the reference type
```

The critical exception: **fields and `static` methods bind to the reference type**. They are not dispatched virtually at all.

```java
class Parent { String label = "parent"; static String tag() { return "parent-tag"; } }
class Child extends Parent { String label = "child"; static String tag() { return "child-tag"; } }

Parent p = new Child();
System.out.println(p.label);            // "parent"     ← field access is statically bound
System.out.println(p.tag());            // "parent-tag" ← static method is statically bound
System.out.println(((Child) p).label);  // "child"      ← different reference type, different field
```

The rule to memorise: **instance methods bind to the object; fields and statics bind to the reference.** The mechanism behind this — the virtual method table — is covered in the binding note.
