# Polymorphism Deep Dive

---

## Short Notes

---

### 1. The Four Moving Parts

```text
Overloading  → compile time, parameter list      → static binding
Overriding   → runtime, actual object            → dynamic binding
Upcasting    → widen the reference (implicit)    → restricts what you can call
Downcasting  → narrow the reference (explicit)   → risks ClassCastException
```

- Everything below is one of these four, or the machinery underneath them

---

### 2. Overloading vs Overriding (Recap)

| | Overloading | Overriding |
| --- | --- | --- |
| What changes | Parameter list | Method body |
| Signature | Must differ | Must match |
| Binding | Compile time | Runtime |
| Relationship | Same class (usually) | Parent–child |

---

### 3. Static vs Dynamic Binding (Recap)

- **Static**: overloads, `static`, `private`, `final` methods, **and all field access**
- **Dynamic**: overridden **instance methods only**
- Full mechanism in [[3. Static And Dynamic Binding]]

```java
Parent p = new Child();
p.instanceMethod();   // Child's  — dynamic
p.staticMethod();     // Parent's — static
p.field;              // Parent's — static
```

---

### 4. Dynamic Method Dispatch

- The JVM resolves an overridden call using the object's **actual class**, at call time
- Walks to the **most derived** override, however deep the chain
- `Animal a = new Puppy()` → `a.sound()` runs `Puppy`'s, not `Dog`'s, not `Animal`'s
- Mechanism: object header → class → **vtable** slot → jump

---

### 5. Why It Matters

- One line of code, N behaviours: `for (Shape s : shapes) s.area();`
- New subtype = new class, zero edits to the loop
- This is what "program to an abstraction" actually buys
- Underpins Spring beans, `Comparator`, exception hierarchies, the whole Collections API

---

### 6. Upcasting

- Subclass reference → superclass reference; **implicit and always safe**
- `Animal a = new Dog();` — no cast needed, a `Dog` **is-a** `Animal`
- **Restricts** the compile-time API to the parent's members — `a.bark()` won't compile
- Does **not** change the object; overridden methods still dispatch to `Dog`

---

### 7. Downcasting

- Superclass reference → subclass reference; **explicit cast required**
- `Dog d = (Dog) a;` — compiler only checks the types are related
- Wrong actual type → **`ClassCastException` at runtime**, not compile time
- Always guard with `instanceof` first

---

### 8. `instanceof`

- Runtime type check, returns `boolean`, never throws
- `null instanceof Anything` → **`false`**, no NPE
- Checks the whole hierarchy, interfaces included
- Unrelated types → **compile error**, not `false`

---

### 9. Pattern Matching (Java 16+)

```java
if (a instanceof Dog d) { d.bark(); }   // check + cast + bind, one step
```

- Removes the redundant cast line
- `d` is scoped to where the check is known true — including `if (!(a instanceof Dog d)) return;`
- Extends to `switch` patterns and record deconstruction in later versions

---

### 10. Heavy `instanceof` Is a Smell

- A chain of `instanceof` branches usually means a missing override
- Replace with a polymorphic method on the type itself
- Legitimate uses: `equals()`, framework/library boundaries, sealed-type exhaustion

---

### 11. How It Fits Together

1. Write against the general type — **upcasting** happens implicitly
2. Overridden calls resolve by **dynamic dispatch** through the vtable
3. Overloads, statics, privates, finals and fields resolve by **static binding**
4. Need a subtype-only member → **`instanceof`** guard, then **downcast**

---

### SDE-2 Interview Priority

**Must Know**: Dynamic method dispatch, Upcasting vs downcasting, `ClassCastException`, `instanceof` including the `null` rule, Overloading vs overriding, What binds statically

**Nice To Know**: Pattern matching for `instanceof`, vtable mechanics, `instanceof` compile error for unrelated types

**Advanced**: `getClass()` vs `instanceof` in `equals()`, Sealed types and exhaustive switch, Replacing `instanceof` chains with polymorphism

# Detailed Explanation

---

## Overloading, Overriding, and Binding — The Recap

Two mechanisms, resolved at two different times.

```java
// Overloading — compile time, chosen by argument types
long fee(long amount) { ... }
long fee(long amount, int bps) { ... }

// Overriding — runtime, chosen by the actual object
class Animal { void sound() { System.out.println("..."); } }
class Dog extends Animal { @Override void sound() { System.out.println("Bark"); } }
```

| | Overloading | Overriding |
| --- | --- | --- |
| What varies | The parameter list | The implementation |
| Signature | Must differ | Must match exactly |
| Binding | Compile time (static) | Runtime (dynamic) |
| Relationship | Same class, usually | Parent–child |

And the binding rule that governs everything:

- **Static binding** — resolved by the compiler from the **reference type**. Applies to overloaded methods, `static` methods, `private` methods, `final` methods, and **all field access, including instance fields**.
- **Dynamic binding** — resolved by the JVM from the **actual object type**. Applies to overridden **instance methods** and nothing else.

```java
Parent p = new Child();
p.instanceMethod();             // Child's version  — dynamic binding
p.staticMethod();               // Parent's version — static binding
System.out.println(p.field);    // Parent's field   — static binding
```

The mechanism is worked through in [[3. Static And Dynamic Binding]]; this note picks up where that leaves off.

## Dynamic Method Dispatch

This is the actual machinery of runtime polymorphism, and it is worth knowing past "it calls the overridden method".

```java
class Animal {
    void sound() { System.out.println("Some sound"); }
}
class Dog extends Animal {
    @Override void sound() { System.out.println("Bark"); }
}
class Puppy extends Dog {
    @Override void sound() { System.out.println("Yip"); }
}
```

```java
Animal a = new Puppy();   // reference type Animal, object type Puppy
a.sound();                // "Yip"
```

Three classes declare `sound()`. The reference is typed `Animal`. The JVM still runs `Puppy`'s version, because dispatch starts from the **actual object**, not from the reference and not from the middle of the chain. It resolves to the **most derived** override.

### The vtable

```text
Animal vtable            Dog vtable               Puppy vtable
┌───────────────────┐    ┌───────────────────┐    ┌───────────────────┐
│ [0] sound → A.s   │    │ [0] sound → D.s   │    │ [0] sound → P.s   │
└───────────────────┘    └───────────────────┘    └───────────────────┘
                                    ▲
        Puppy object ──header──▶ Puppy class ─────┘
```

- Every class has a **virtual method table** — an array of method pointers, one slot per overridable method, laid out so a subclass's slots align with its parent's.
- Every object header holds a pointer to its class (and thus to the shared vtable) — not a copy of the table.
- An override **replaces the pointer** in the inherited slot. No override → the slot still points at the parent's implementation.
- At `a.sound()`, the JVM ignores `a`'s compile-time type entirely: it reads the vtable pointer from the object, indexes the `sound()` slot, and jumps.

The slot *index* is fixed at compile time; only the *contents* vary. That's why virtual dispatch is a constant-time indirection rather than a search.

`static`, `private` and `final` methods have no vtable slot to dispatch through, which is exactly why they can't be overridden — the call address is baked in at compile time.

### Why it matters practically

```java
List<Shape> shapes = List.of(new Circle(5), new Square(4), new Triangle(3, 6));
for (Shape s : shapes) {
    System.out.println(s.area());     // one call site, three implementations
}
```

You write `s.area()` once. The JVM picks `Circle.area()`, `Square.area()` or `Triangle.area()` per element, based on what is actually there. Adding a `Hexagon` means adding a class — the loop is untouched. Without dispatch this loop is an `if/else` chain that every new shape must edit, which is the Open/Closed Principle being violated one branch at a time.

Every extensible Java framework rests on this: Spring injecting an implementation behind an interface, `Collections.sort` calling your `Comparator`, `catch (IOException e)` matching any subtype.

## Upcasting

Converting a subclass reference to a superclass reference type. **Implicit and always safe** — a `Dog` *is-a* `Animal` by definition, so no cast is needed and it can never fail.

```java
class Animal { void eat() { System.out.println("Eating"); } }
class Dog extends Animal { void bark() { System.out.println("Barking"); } }

Dog d = new Dog();
Animal a = d;        // upcasting — implicit

a.eat();             // ✅ Animal declares eat()
a.bark();            // ❌ compile error — Animal has no bark(), even though the object is a Dog
```

The key insight: **upcasting doesn't change the object.** There is still exactly one `Dog` on the heap. What changes is the **compile-time view** — the set of members you're allowed to name through that reference. Dynamic dispatch is unaffected, so if `Dog` overrode `eat()`, `a.eat()` would still run `Dog`'s version.

```text
Heap:  ┌────────────┐
       │ Dog object │  ← unchanged
       └────────────┘
         ▲        ▲
    Dog d │        │ Animal a     ← two views of one object, different visible APIs
```

Why you would do it deliberately:

```java
void feed(Animal a) { a.eat(); }    // works for every Animal subtype
feed(new Dog());
feed(new Cat());
```

- **Polymorphic APIs** — accept the general type so the method works with any subtype, present or future.
- **Restricting access** — hand callers only the general contract so they can't depend on subtype-specific methods you may remove.
- It happens implicitly all the time: every `Circle` added to a `List<Shape>` is upcast on the way in.

---

## Downcasting

Converting a superclass reference back to a subclass reference type. **Explicit, and inherently risky.**

```java
Animal a = new Dog();     // upcast — safe
Dog d = (Dog) a;          // downcast — explicit cast required
d.bark();                 // now visible
```

The compiler only verifies that `Animal` and `Dog` are related in the hierarchy, so the cast is *plausible*. It cannot know what the object actually is:

```java
Animal a = new Cat();
Dog d = (Dog) a;          // compiles fine
                          // ❌ ClassCastException at runtime — the object is a Cat
```

That is the whole hazard: the failure moves from compile time to runtime, which is the wrong direction. Guard it:

```java
for (Animal a : animals) {
    if (a instanceof Dog) {      // check first
        Dog d = (Dog) a;
        d.bark();
    }
}
```

You need downcasting when you hold a general-typed reference but need a member only the subtype declares. In practice, needing it often signals that the behaviour belongs on the base type as an overridable method instead.

> 💡 **Interview**: Why does `(Dog) someAnimal` compile but throw at runtime? → The compiler only checks that the two types are related, so the cast is possible in principle; the actual runtime type is unknown until execution, and `ClassCastException` is the check finally happening.

## `instanceof`

A runtime type test returning `true`/`false`.

```java
Animal a = new Dog();
if (a instanceof Dog) {
    System.out.println("a is a Dog");
}
```

The nuances that get tested:

**It never throws on `null`.**

```java
Animal a = null;
System.out.println(a instanceof Dog);   // false — no NullPointerException
```

This is deliberate and useful: `x instanceof Dog` is a complete null-safe guard, so an explicit `x != null &&` in front of it is redundant.

**It checks the entire hierarchy, interfaces included.**

```java
class Animal { }
class Dog extends Animal implements Serializable { }

Dog d = new Dog();
d instanceof Dog;           // true
d instanceof Animal;        // true — walks up the superclass chain
d instanceof Serializable;  // true — interfaces too
d instanceof Object;        // true — always
```

**Impossible checks are a compile error, not `false`.**

```java
String s = "abc";
if (s instanceof Dog) { }   // ❌ compile error — inconvertible types
```

If the declared types are unrelated, the compiler knows the answer can never be `true` and rejects the code. This only applies when it can prove it — with an `Object` reference, any check compiles.

## Pattern Matching for `instanceof`

The pre-Java-16 idiom always repeated the type:

```java
if (a instanceof Dog) {
    Dog d = (Dog) a;        // the compiler already knew this — pure ceremony
    d.bark();
}
```

Java 16 folds the check, the cast and the binding into one:

```java
if (a instanceof Dog d) {   // d is bound only where the check is true
    d.bark();
}
```

The binding follows flow scoping, so it also works inverted — which is how guard clauses are usually written:

```java
if (!(a instanceof Dog d)) return;
d.bark();                            // d is in scope here, provably a Dog
```

and it composes with `&&`:

```java
if (a instanceof Dog d && d.isVaccinated()) { ... }   // ✅ d usable in the same condition
if (a instanceof Dog d || d.isVaccinated()) { ... }   // ❌ d not definitely assigned here
```

Later versions extend the same idea to `switch` and to record deconstruction:

```java
String describe(Object o) {
    return switch (o) {
        case Payment p when p.amountPaise() > 100_000_00 -> "high value";
        case Payment p                                   -> "payment " + p.txnId();
        case Refund(var txnId, var amount)               -> "refund of " + amount;
        default                                          -> "unknown";
    };
}
```

## When `instanceof` Is a Smell

A chain of type tests is almost always a missing override:

```java
// ❌ every new type edits this method
long fee(Payment p) {
    if (p instanceof UpiPayment)       return 0;
    else if (p instanceof CardPayment) return p.amount() * 30 / 10_000;
    else if (p instanceof NetBanking)  return 500;
    throw new IllegalArgumentException();
}
```

```java
// ✅ every new type adds a class and edits nothing
abstract class Payment { abstract long fee(); }
class UpiPayment  extends Payment { long fee() { return 0; } }
class CardPayment extends Payment { long fee() { return amount * 30 / 10_000; } }
```

The polymorphic version cannot forget a case and cannot throw at runtime for an unhandled type — the compiler enforces that every subclass implements `fee()`.

Legitimate uses remain:

- **`equals()`** — you are handed an `Object` and must check the type.
- **Framework and library boundaries** — deserialization, reflection, adapting third-party types you can't modify.
- **Sealed hierarchies** — with `sealed` types the compiler knows every permitted subtype, so a pattern `switch` is checked for exhaustiveness and needs no `default`. That is type-driven dispatch with the compiler's guarantee behind it, which is a different thing from an ad-hoc `instanceof` chain.

---

## How It All Connects

1. You write code against a general type. **Upcasting** happens implicitly wherever a subtype flows in.
2. Calls to overridden instance methods resolve by **dynamic method dispatch** — the JVM reads the object's vtable and jumps to the most derived override.
3. Overloads, `static`, `private`, `final` methods and **all field access** resolve by **static binding**, from the reference type, at compile time.
4. When you genuinely need a member only the subtype has, you check with **`instanceof`** (ideally with a pattern binding) and **downcast** — accepting that this step is where `ClassCastException` lives.

Step 4 is the escape hatch. The better the design, the less you need it.
