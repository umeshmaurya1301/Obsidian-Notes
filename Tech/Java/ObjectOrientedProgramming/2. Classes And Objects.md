# Classes And Objects

---

## Short Notes

---

### 1. Class vs Object

- **Class** = blueprint: structure (fields) + behaviour (methods)
- **Object** = runtime instance, lives in the **Heap**, has its own copy of instance fields
- Class itself occupies no heap space — metadata sits in **Metaspace**
- One class → many objects, each with independent state

---

### 2. Constructors

- Special method that initialises a new object's state
- **Same name as the class**, no return type — not even `void`
- Runs after memory allocation and default initialisation, before the reference is handed back
- Not inherited, not overridden — but can be overloaded

---

### 3. Default Constructor

- Compiler inserts a no-arg constructor **only if you write none**
- The inserted one just calls `super()`
- Write any constructor → the free one disappears

```java
class Wallet { }        // compiler adds: Wallet() { super(); }
```

---

### 4. Parameterized Constructor

- Takes arguments to initialise fields at creation time
- The place to enforce invariants — reject bad state before the object exists
- Enables `final` fields (must be assigned exactly once, in every constructor path)

---

### 5. Constructor Chaining — `this()`

- One constructor calls another **in the same class** to avoid duplicated init
- `this()` must be the **first statement**
- `this()` and `super()` cannot both appear in one constructor
- Chain ends at the constructor that does the real work

---

### 6. `this` Keyword

- Reference to the **current object instance**
- Uses: disambiguate field vs parameter, `this()` chaining, pass self as argument, `return this` for fluent APIs
- Not available in `static` context — no instance exists

---

### 7. Static vs Instance Variables

| | Static | Instance |
| --- | --- | --- |
| Belongs to | The class | Each object |
| Copies | One, shared | One per object |
| Storage | Metaspace (class object in heap) | Heap, inside the object |
| Access | `ClassName.field` | `object.field` |
| Lifetime | Class load → class unload | While the object is reachable |

---

### 8. Static vs Instance Methods

- **Static**: no `this`, callable as `ClassName.method()`, can only touch static members directly
- **Instance**: needs an object, can touch both static and instance members
- Static methods use **static binding** → they don't participate in runtime polymorphism
- Redefining a static method in a subclass is **hiding**, not overriding

---

### 9. Static Blocks

- `static { ... }` runs **once**, when the class is initialised
- Fires before `main()`, before any object creation, before any static member is first used
- Used for computed static state that a single initialiser expression can't build
- Multiple blocks run top-to-bottom in source order

---

### 10. Instance Initialization Blocks

- `{ ... }` (no `static`) runs on **every** object creation
- Runs after `super()`, before the constructor **body**
- Shared setup across all constructor overloads
- Rarely used in practice — constructor chaining is usually clearer

---

### 11. Initialization Order (Single Class)

```text
1. static fields + static blocks   (once, at class initialisation, source order)
2. instance fields + init blocks   (every new, source order)
3. constructor body                (every new, last)
```

---

### 12. Initialization Order (With Inheritance)

```text
Parent static  →  Child static            (once, parent first)
Parent instance init  →  Parent ctor body
Child  instance init  →  Child  ctor body
```

- `super()` is implicit and runs first → the parent is fully built before the child starts
- **Trap**: a parent constructor calling an overridable method sees the child's *uninitialised* fields

---

### 13. Object Creation Steps (`new`)

1. Class loaded + initialised if not already (statics run here)
2. Heap memory allocated
3. Fields set to **defaults** — `0`, `false`, `null`
4. `super()` chain runs to `Object`
5. Instance blocks + field initialisers
6. Constructor body
7. Reference assigned to the variable

---

### SDE-2 Interview Priority

**Must Know**: Class vs object, Constructor rules, `this()` vs `super()`, Static vs instance members, Full initialisation order with inheritance, Object creation steps

**Nice To Know**: Instance init blocks, Static block failure → `ExceptionInInitializerError`, Why `final` fields must be assigned in every constructor path

**Advanced**: Calling an overridable method from a constructor, Class initialisation triggers, `NoClassDefFoundError` after a failed static init

# Detailed Explanation

---

## Class vs Object

A **class** is a blueprint — it declares what fields an instance will carry and what methods it will respond to. An **object** is one concrete instance of that blueprint, allocated on the heap with its own copy of every instance field.

```java
class Wallet {
    String walletId;
    long balancePaise;
}

Wallet w1 = new Wallet();   // object 1 — its own memory
Wallet w2 = new Wallet();   // object 2 — separate memory
w1.walletId = "W-100";
w2.walletId = "W-200";      // w1 is untouched
```

```text
Stack                    Heap
─────                    ────
w1 ──────────────────▶  ┌───────────────────┐
                        │ Wallet            │
                        │ walletId "W-100"  │
                        │ balance   0       │
                        └───────────────────┘
w2 ──────────────────▶  ┌───────────────────┐
                        │ Wallet            │
                        │ walletId "W-200"  │
                        │ balance   0       │
                        └───────────────────┘

Metaspace: class Wallet  ← field/method metadata, bytecode, static fields (one copy)
```

The class itself is not duplicated per object. Its metadata lives once in Metaspace, and every object carries only a pointer to it in its header plus its own field values.

---

## Constructors

A constructor initialises a newly allocated object. It shares the class's name and declares no return type — writing one turns it into an ordinary method, which is a classic silent bug:

```java
class Wallet {
    Wallet() { }        // ✅ constructor
    void Wallet() { }   // ❌ just a method that happens to be named Wallet — never called by `new`
}
```

Constructors are **not members**: they are not inherited, cannot be overridden, and cannot be `static`, `final` or `abstract`. They *can* be overloaded, and they *can* be `private` (the basis of singletons and static factories).

### Default constructor

If a class declares no constructor at all, the compiler inserts a no-arg one whose entire body is `super()`.

```java
class Wallet { }
// compiler generates:  Wallet() { super(); }
```

The moment you write **any** constructor, that free one is gone:

```java
class Wallet {
    Wallet(String id) { ... }
}

new Wallet();   // ❌ compile error — no no-arg constructor exists any more
```

This bites hardest with frameworks (JPA, Jackson) that reflectively require a no-arg constructor: adding a parameterized one silently breaks deserialization until you add the no-arg back.

### Parameterized constructor

This is where invariants belong. An object should never exist in an invalid state, so validate before assignment:

```java
class Wallet {
    private final String walletId;      // final → must be assigned in every ctor path
    private long balancePaise;

    Wallet(String walletId, long openingBalance) {
        if (walletId == null || walletId.isBlank())
            throw new IllegalArgumentException("walletId required");
        if (openingBalance < 0)
            throw new IllegalArgumentException("negative opening balance");
        this.walletId = walletId;
        this.balancePaise = openingBalance;
    }
}
```

If the constructor throws, the half-built object is unreachable and becomes garbage — the caller never gets a reference to a broken `Wallet`.

### Constructor chaining with `this()`

`this(...)` calls another constructor of the **same class**, so initialisation logic is written once:

```java
class Wallet {
    private final String walletId;
    private final String currency;
    private long balancePaise;

    Wallet(String walletId) {
        this(walletId, "INR", 0);          // must be the FIRST statement
    }

    Wallet(String walletId, String currency) {
        this(walletId, currency, 0);
    }

    Wallet(String walletId, String currency, long openingBalance) {   // the real work happens here
        this.walletId = walletId;
        this.currency = currency;
        this.balancePaise = openingBalance;
    }
}
```

Rules:

- `this()` must be the **first statement** — nothing may run before the delegated constructor.
- A constructor may contain `this()` **or** `super()`, never both, since both demand the first slot. Delegating with `this()` means the *chained* constructor is the one that calls `super()`.
- Recursive chaining (`A → B → A`) is a compile error.

---

## `this` Keyword

`this` is an implicit reference to the object whose method is currently executing.

```java
class Wallet {
    private String walletId;
    private long balancePaise;

    Wallet(String walletId) {
        this.walletId = walletId;       // 1. disambiguate field from parameter
    }

    Wallet() {
        this("W-DEFAULT");              // 2. constructor chaining
    }

    Wallet credit(long amount) {
        this.balancePaise += amount;
        return this;                    // 3. fluent / builder-style chaining
    }

    void audit(AuditLog log) {
        log.record(this);               // 4. pass the current object along
    }
}
```

```java
wallet.credit(100).credit(200).credit(300);   // enabled by `return this`
```

`this` does not exist in a `static` context — there is no instance — which is exactly why a static method cannot touch instance fields directly.

## Static vs Instance Members

### Variables

A `static` field belongs to the class: one copy, shared by every instance and by code that has no instance at all.

```java
class TransactionCounter {
    static long totalProcessed = 0;   // one copy for the whole JVM (per classloader)
    final long sequenceNumber;        // one copy per object

    TransactionCounter() {
        totalProcessed++;
        sequenceNumber = totalProcessed;
    }
}

TransactionCounter t1 = new TransactionCounter();   // totalProcessed = 1, t1.sequenceNumber = 1
TransactionCounter t2 = new TransactionCounter();   // totalProcessed = 2, t2.sequenceNumber = 2
// t1.totalProcessed and t2.totalProcessed both read 2 — it is shared
```

| | Static Variable | Instance Variable |
| --- | --- | --- |
| Belongs to | The class | Each object |
| Copies in memory | One | One per object |
| Where | The class object / Metaspace | Heap, inside the object |
| Accessed via | `ClassName.field` | `object.field` |
| Lifetime | Class initialisation → class unload | As long as the object is reachable |
| Thread safety | Shared → needs synchronisation | Per-object → safer by default |

That last row matters in production. A mutable `static` field is global state shared by every request thread; the counter above is not thread-safe and would need `AtomicLong`.

### Methods

```java
class FeeCalculator {
    static long flatFee(long amount) { return amount / 100; }   // no object needed
}
FeeCalculator.flatFee(5000);        // called on the class

class Wallet {
    private long balancePaise;
    void credit(long amount) { balancePaise += amount; }        // needs an object
}
new Wallet().credit(500);
```

- A static method has no `this`, so it cannot read instance fields or call instance methods without being handed an object.
- An instance method can freely read static members.
- Static methods are resolved by **static binding** on the reference type, so they sit entirely outside runtime polymorphism — the subject of the next note.

---

## Static Blocks

A `static { }` block runs **once**, when the class is initialised — before `main()`, before any instance is created, before any static member is first read. It exists for static state that a single initialiser expression cannot build.

```java
class RouteConfig {
    static final Map<String, String> BANK_TO_HANDLE;

    static {
        Map<String, String> m = new HashMap<>();
        m.put("HDFC", "@hdfcbank");
        m.put("ICICI", "@icici");
        BANK_TO_HANDLE = Collections.unmodifiableMap(m);
        System.out.println("RouteConfig initialised");
    }
}
```

Multiple static blocks and static field initialisers execute **in source order**, interleaved:

```java
class Order {
    static int a = 1;
    static { a = 2; }
    static int b = a + 1;   // b = 3 — the block already ran
}
```

Class initialisation is triggered by the first `new`, the first access to a static member (except a compile-time constant), or a reflective `Class.forName()`. It is guaranteed by the JVM to happen exactly once and to be thread-safe — which is what makes the holder-class singleton idiom work.

If a static block throws, the JVM wraps it in `ExceptionInInitializerError`, marks the class as erroneous, and every later attempt to use it fails with `NoClassDefFoundError` — a confusing production symptom whose real cause is buried in the first stack trace.

## Instance Initialization Blocks

A bare `{ }` block runs on **every** object creation, after `super()` completes and before the constructor body.

```java
class Wallet {
    private long balancePaise;
    private final Instant createdAt;

    {   // instance init block — runs before every constructor body
        createdAt = Instant.now();
        System.out.println("instance block");
    }

    Wallet() { System.out.println("no-arg constructor"); }
    Wallet(long opening) { balancePaise = opening; System.out.println("parameterized constructor"); }
}
```

```text
new Wallet(500);
→ instance block
→ parameterized constructor
```

It runs regardless of which overload is called, which is its one genuine advantage. In everyday code, constructor chaining expresses the same thing more explicitly, so instance blocks show up mainly in anonymous classes, where no constructor can be declared:

```java
List<String> handles = new ArrayList<>() {{ add("@upi"); add("@ybl"); }};   // double-brace init
// works, but holds a hidden reference to the enclosing instance — avoid in long-lived objects
```

## Initialization Order

### Within a single class

1. **Static fields and static blocks** — once, at class initialisation, in source order.
2. **Instance fields and instance blocks** — on every `new`, in source order.
3. **Constructor body** — last.

### With inheritance

```java
class Parent {
    static { System.out.println("Parent static block"); }
    { System.out.println("Parent instance block"); }
    Parent() { System.out.println("Parent constructor"); }
}

class Child extends Parent {
    static { System.out.println("Child static block"); }
    { System.out.println("Child instance block"); }
    Child() { System.out.println("Child constructor"); }
}

new Child();
```

```text
Parent static block      ← class init, parent first, once per JVM
Child static block
Parent instance block    ← super() runs to completion first
Parent constructor
Child instance block
Child constructor
```

**Why**: initialising `Child` requires `Parent` to be initialised first, so the static blocks run parent-down, once. Then for each `new`, `Child()`'s implicit `super()` runs the parent's instance blocks and constructor body to completion before control returns to `Child()`'s own instance blocks and body. The invariant is simple — **a parent is always fully constructed before the child begins**.

### The constructor-calls-overridable-method trap

That invariant has a sharp edge. The parent constructor runs while the child's fields are still at their defaults:

```java
class Processor {
    Processor() {
        init();                     // ⚠ calling an overridable method from a constructor
    }
    void init() { }
}

class UpiProcessor extends Processor {
    private final String handle = "@upi";     // not assigned yet when Processor() runs

    @Override
    void init() {
        System.out.println("handle = " + handle);   // prints "handle = null"
    }
}

new UpiProcessor();   // handle = null
```

The override runs (dynamic dispatch is already active), but `handle` has not been initialised — field initialisers run *after* `super()` returns. Worse, a `final` field appears to change value mid-life. Rule: **never call an overridable method from a constructor.** Make such methods `private`, `static` or `final`, or move the work to a factory method that runs after construction.

> 💡 **Interview**: Why does a `final` field read as `null` inside a method called from the superclass constructor? → Because `super()` completes before the subclass's field initialisers run, so the override executes against default-valued fields.

## Object Creation Steps

What `new Wallet("W-1", 500)` actually does:

```text
1. Resolve + load class          → Wallet loaded, verified, prepared
2. Initialise class (if first)   → static fields + static blocks run, once
3. Allocate heap memory          → object header + space for all instance fields
4. Default-initialise fields     → 0 / 0L / false / ' ' / null
5. Run super() chain up to Object
6. Instance field initialisers + instance blocks, in source order
7. Constructor body
8. Return the reference          → assigned to the stack variable
```

Step 4 is why an instance field is readable before you assign it, while a **local** variable is not — locals get no default initialisation and the compiler rejects reads of them.

```java
class Wallet {
    long balance;                    // defaults to 0 — legal to read immediately
    void f() {
        long fee;
        System.out.println(fee);     // ❌ "variable fee might not have been initialized"
    }
}
```

If the constructor throws at step 7, the object was already allocated but is unreachable, so it is simply collected. This is why validating in the constructor is safe: a caller can never obtain a reference to a partially built object — unless the constructor leaked `this` somewhere before finishing.
