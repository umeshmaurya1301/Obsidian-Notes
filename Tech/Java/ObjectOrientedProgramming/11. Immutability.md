# Immutability

---

## Short Notes

---

### 1. What Immutable Means

- State **cannot change after construction** — every field fixed for the object's lifetime
- No setters, no mutating methods, ever
- Operations that look like mutation **return a new object**
- The variable can be reassigned; the **object** never changes

---

### 2. The Five-Rule Checklist

1. Declare the class `final` — no subclass can add mutable behaviour
2. All fields `private final`
3. No setters — constructor in, getters out
4. Mutable field types → **defensive copy on the way out**
5. Mutable constructor arguments → **defensive copy on the way in**

---

### 3. Canonical Immutable Class

```java
public final class Money {
    private final long amountPaise;
    private final String currency;

    public Money(long amountPaise, String currency) { ... }

    public Money add(Money other) {          // returns a NEW Money
        return new Money(amountPaise + other.amountPaise, currency);
    }
}
```

- `m1.add(m2)` leaves `m1` untouched — the result is a third object

---

### 4. The Mutable-Field Trap

```java
this.skills = skills;          // ❌ stores the caller's reference
public List<String> getSkills() { return skills; }   // ❌ leaks it back out
```

- `final` fields + no setters is **not** enough
- The caller mutates their list → your "immutable" object changed
- Leaks in **both** directions: constructor in, getter out

---

### 5. Defensive Copying

```java
this.skills = List.copyOf(skills);                  // copy IN
public List<String> getSkills() { return skills; }  // safe — already unmodifiable
```

- `List.copyOf` / `new ArrayList<>(...)` on the way in
- `List.copyOf` / `Collections.unmodifiableList` on the way out
- Arrays: `array.clone()`. `Date`: `new Date(d.getTime())`
- Unneeded if the field type is itself immutable

---

### 6. Why Immutability Matters

- **Thread safety for free** — no locks, no races, share freely across threads
- **Safe hash keys** — `hashCode()` can never change, so the object never gets lost in a bucket
- **No defensive copying by callers** — handing one out is always safe
- **Simpler reasoning** — behaviour fully determined by construction arguments

---

### 7. Immutable Types in the JDK

- `String`, all wrapper classes, `BigDecimal`, `BigInteger`
- `java.time`: `LocalDate`, `LocalDateTime`, `Instant`, `Duration`
- `List.of` / `Map.of` / `List.copyOf` results
- **`record`** (Java 16+) — immutable by default

---

### 8. Why `String` Is Immutable — Five Reasons

1. **String pool** — literals are shared; mutation would corrupt every user
2. **Security** — validated paths, URLs, credentials can't change after the check (TOCTOU)
3. **Thread safety** — free sharing, no synchronization
4. **`hashCode()` caching** — computed once, cached; makes `String` keys fast
5. **Class loading** — `Class.forName(name)` relies on the name not changing mid-operation

---

### 9. How `String` Enforces It

```java
public final class String {        // final — no subclass
    private final byte[] value;    // final reference (char[] before Java 9)
    // no method ever writes into value
}
```

- `substring()`, `concat()`, `toUpperCase()`, `replace()` all return **new** Strings
- `s.toUpperCase();` alone does nothing — you must reassign

---

### 10. `StringBuilder` Exists Because of This

```java
String r = "";
for (int i = 0; i < 1000; i++) r += i;   // ❌ new String each iteration — O(n²)

StringBuilder sb = new StringBuilder();
for (int i = 0; i < 1000; i++) sb.append(i);   // ✅ one mutable buffer
```

- `StringBuilder` (unsynchronized) / `StringBuffer` (synchronized, legacy)

---

### 11. Wrapper Classes Are Immutable

- `Integer`, `Long`, `Double`, `Float`, `Boolean`, `Character`, `Byte`, `Short`
- No method mutates an existing wrapper's internal value
- `x = x + 5` → unbox, add, **box into a new object**, reassign
- `System.identityHashCode(x)` changes — proof it's a different object

---

### 12. Why Wrapper Immutability Is Required

- The **Integer cache** (−128..127) shares objects — only safe because they can't change
- Safe as `HashMap` keys — hash never shifts
- Thread-safe sharing with no synchronization

---

### 13. The Mutability Test

> Does this class have **any** method that changes an existing object's fields without creating a new object?

| Class | Mutating method? | Verdict |
| --- | --- | --- |
| `String` | No | ✅ Immutable |
| `Integer` | No | ✅ Immutable |
| `ArrayList` | `add`, `remove`, `set` | ❌ Mutable |
| `StringBuilder` | `append` | ❌ Mutable (deliberately) |

---

### 14. Immutability Dissolves the Copy Problem

- Shallow vs deep copy only matters because nested objects can be **mutated**
- If everything is immutable, a shallow copy is as safe as a deep one
- Best copy strategy is to make copying unnecessary
- Copying mechanics: [[6. Cloning And Object Copying]]

# Detailed Explanation

---

## What Immutability Means

An immutable object's state is fixed at construction. There is no method anywhere on the class that changes an existing object's fields — every operation that appears to modify it produces a **new** object instead.

The distinction that trips people up: the *variable* can be reassigned; the *object* never changes.

```java
Money m = new Money(100_00, "INR");
m = m.add(new Money(50_00, "INR"));   // m now points to a different object
                                      // the original Money(100_00) is unchanged, just unreferenced
```

---

## Building a Truly Immutable Class

```java
public final class Money {                          // 1. final class
    private final long amountPaise;                 // 2. private final fields
    private final String currency;

    public Money(long amountPaise, String currency) {   // 3. state set only in the constructor
        if (currency == null) throw new IllegalArgumentException("currency required");
        this.amountPaise = amountPaise;
        this.currency = currency;
    }

    public long getAmountPaise() { return amountPaise; }    // getters only, no setters
    public String getCurrency()  { return currency; }

    public Money add(Money other) {                         // "mutation" returns a new object
        if (!currency.equals(other.currency))
            throw new IllegalArgumentException("currency mismatch");
        return new Money(amountPaise + other.amountPaise, currency);
    }
}
```

```java
Money m1 = new Money(100_00, "INR");
Money m2 = m1.add(new Money(50_00, "INR"));

m1.getAmountPaise();   // 10000 — untouched
m2.getAmountPaise();   // 15000 — a new object
```

### The five rules

1. **Class is `final`.** Otherwise a subclass can override methods to break invariants or add mutable state, and a caller holding a `Money` reference can't tell the difference. (The alternative is a private constructor plus static factories, which achieves the same by making subclassing impossible.)
2. **Fields are `private final`.** `private` blocks direct access; `final` blocks reassignment and, importantly, guarantees safe publication across threads.
3. **No setters.** State is set once, in the constructor. Every "modifier" returns a new instance.
4. **Defensive copy on the way out** for any mutable field type.
5. **Defensive copy on the way in** for any mutable constructor argument.

Rules 4 and 5 are the ones people skip, and they're the ones that matter.

---

## The Mutable-Field Trap

```java
public final class Employee {
    private final String name;
    private final List<String> skills;

    public Employee(String name, List<String> skills) {
        this.name = name;
        this.skills = skills;              // ❌ stores the caller's reference
    }

    public List<String> getSkills() {
        return skills;                     // ❌ hands the internal list back out
    }
}
```

Every immutability box is ticked — `final` class, `private final` fields, no setters — and the class is still mutable, in two directions:

```java
List<String> skills = new ArrayList<>(List.of("Java", "Spring"));
Employee e = new Employee("Umesh", skills);

skills.add("Kafka");              // ← mutated through the caller's still-live reference
e.getSkills().add("Redis");       // ← mutated through the getter
```

```text
        caller's list
             │
             ▼
  ┌────────────────────┐
  │ ArrayList          │  ← ONE list, three ways to reach it
  └────────────────────┘
             ▲        ▲
             │        │
    Employee.skills   getSkills() caller
```

`final` protects the **reference**, not the object it points at. `this.skills` can never be reassigned; the list it names can be emptied, reordered and refilled by anyone.

### Defensive copying — the fix

```java
public final class Employee {
    private final String name;
    private final List<String> skills;

    public Employee(String name, List<String> skills) {
        this.name = name;
        this.skills = List.copyOf(skills);      // ✅ copy IN — caller's later edits don't reach us
    }

    public List<String> getSkills() {
        return skills;                          // ✅ already an unmodifiable copy
    }
}
```

The idioms by type:

| Field type | Copy in | Copy out |
| --- | --- | --- |
| `List` / `Set` / `Map` | `List.copyOf(x)` or `new ArrayList<>(x)` | `List.copyOf(x)` or `Collections.unmodifiableList(x)` |
| Array | `x.clone()` | `x.clone()` |
| `Date` (legacy) | `new Date(x.getTime())` | `new Date(x.getTime())` |
| `String`, wrappers, `LocalDate`, `BigDecimal` | nothing needed | nothing needed |

Two things to note. `Collections.unmodifiableList(list)` returns a **view** — if you keep a mutable reference to the backing list, you can still change what the view shows, so it isn't a substitute for copying on the way in. And `List.copyOf` is shallow: it copies the list but not the elements, which is exactly right when the elements are immutable and insufficient when they aren't.

> 💡 **Interview**: A class has a `final` class declaration, all `private final` fields and no setters. Is it immutable? → Not necessarily. If any field is a mutable type and the constructor stores or the getter returns the reference directly, callers can mutate the internal state. `final` protects the reference, not the object.

---

## Why Immutability Matters

**Thread safety with no synchronization.** An object whose state can't change has no race conditions to guard. Multiple threads can read it concurrently with no locks, no `volatile`, no `synchronized`. In a Kafka-consumer-heavy service where the same config or reference-data object is read by many threads, this removes an entire class of bug rather than managing it. The JMM strengthens this: `final` fields written in a constructor are guaranteed visible to any thread that sees the object, so an immutable object is **safely published** even through a data race.

**Safe hash keys.** `hashCode()` derives from field values. Mutate a key after inserting it into a `HashMap` and the object hashes to a different bucket — it's still in the map, and it can never be found again.

```java
Set<Point> set = new HashSet<>();
Point p = new Point(1, 2);
set.add(p);
p.x = 99;              // only possible if Point is mutable
set.contains(p);       // false — the object is in the set but hashes elsewhere
```

Immutable keys make this impossible by construction, which is why `String` and the wrappers are the standard key types.

**Callers need no defensive copies.** Handing out an immutable object is always safe — nobody can corrupt your state through it, so you can return internal references freely.

**Simpler reasoning and testing.** An immutable object's behaviour is entirely determined by its constructor arguments. There is no temporal dimension, no "what state is it in by now", no need to reason about call ordering.

### Immutable types in the JDK

`String`; every wrapper class; `BigDecimal` and `BigInteger`; the whole `java.time` package (`LocalDate`, `Instant`, `Duration`); the collections returned by `List.of`, `Map.of`, `List.copyOf`; and `record`s, which are immutable by default:

```java
public record Money(long amountPaise, String currency) { }
// implicitly final, fields implicitly private final, no setters, equals/hashCode/toString generated
```

A `record` still needs defensive copying if a component is a mutable type — the compiler makes the *reference* final, nothing more. That's what a compact constructor is for:

```java
public record Payment(String txnId, List<LedgerEntry> entries) {
    public Payment {                             // compact constructor
        entries = List.copyOf(entries);          // defensive copy before assignment
    }
}
```

## Why `String` Is Immutable

Asked in nearly every Java interview, and there are five distinct reasons — knowing all of them is what separates a good answer from a memorised one.

### 1. The String pool

The JVM keeps a pool of string literals (in the heap since Java 7) and hands out the same object for identical literals:

```java
String s1 = "hello";
String s2 = "hello";     // the SAME object — not a copy
s1 == s2;                // true
```

This sharing is only safe because `String` can't change. If a hypothetical `s1.setChar(0, 'H')` existed, it would silently rewrite `s2` — and every other literal `"hello"` anywhere in the program, including inside the JDK. Immutability is the precondition for interning, not a side effect of it.

### 2. Security

Strings carry the parameters that security decisions are made on — file paths, JDBC URLs, credentials, class names:

```java
void connectToDatabase(String url) {
    validate(url);                          // check happens here
    DriverManager.getConnection(url);       // use happens here
}
```

If `String` were mutable, a caller holding a reference to `url` could change it **between** the check and the use — a classic **time-of-check to time-of-use (TOCTOU)** vulnerability. Immutability makes the validated value permanently trustworthy.

### 3. Thread safety

No state changes, so no synchronization is needed to share a `String` across threads. Given how universally strings are passed around, having to lock them would be crippling.

### 4. `hashCode()` caching

```java
public final class String {
    private int hash;                // cached

    public int hashCode() {
        int h = hash;
        if (h == 0 && !value.isEmpty()) {
            h = computeHash();
            hash = h;                // computed once, reused forever
        }
        return h;
    }
}
```

Because the characters can't change, the hash can be computed once and cached. `String` is by far the most common `HashMap` key type in Java, so this makes essentially every map lookup in every Java program cheaper. A mutable `String` would have to recompute the hash on every call.

### 5. Class loading and reflection

```java
Class.forName("java.util.ArrayList");
```

Class names travel as `String`s through the classloader and the security manager. A mutable name could be altered after a security check and before the load — the same TOCTOU problem, at the JVM's core.

### How it's enforced

```java
public final class String {          // final — no subclass can add mutation
    private final byte[] value;      // final reference (char[] before Java 9's compact strings)
    // no method in the class ever writes into value
}
```

All three conditions matter, and the third is the one you have to take on trust from the implementation: `substring()`, `concat()`, `toUpperCase()`, `replace()`, `trim()` all **construct and return new `String` objects**.

```java
String s = "hello";
s.concat(" world");
System.out.println(s);   // "hello" — the result was discarded

s = s.concat(" world");
System.out.println(s);   // "hello world"
```

Forgetting to reassign is the standard beginner trap: `s.toUpperCase();` on its own is a no-op that the compiler happily accepts.

### Which is why `StringBuilder` exists

Because every `String` operation allocates, building a string by repeated concatenation is quadratic:

```java
String result = "";
for (int i = 0; i < 1000; i++) {
    result += i;                     // ❌ a new String, and a full char copy, every iteration
}
```

```java
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 1000; i++) {
    sb.append(i);                    // ✅ mutates one internal buffer
}
String result = sb.toString();
```

`StringBuilder` is the deliberately mutable counterpart, and `StringBuffer` is its synchronized, legacy sibling — use `StringBuilder` unless a single builder is genuinely shared across threads. (A single-expression `"a" + b + "c"` is already compiled into a builder, so only loops and repeated concatenation need this treatment.)

## Wrapper Classes Are Immutable

The wrappers are the object forms of the primitives:

| Primitive | Wrapper | | Primitive | Wrapper |
| --- | --- | --- | --- | --- |
| `int` | `Integer` | | `boolean` | `Boolean` |
| `long` | `Long` | | `char` | `Character` |
| `double` | `Double` | | `byte` | `Byte` |
| `float` | `Float` | | `short` | `Short` |

They exist because primitives aren't objects — they can't be `null`, can't go in a `List<int>`, and have no methods. And like `String`, every one of them is immutable.

### The proof

```java
Integer x = 10;
System.out.println(System.identityHashCode(x));   // 366712642

x = x + 5;
System.out.println(x);                            // 15
System.out.println(System.identityHashCode(x));   // 1829164700 — a DIFFERENT object
```

What `x = x + 5` actually does:

1. **Unbox** `x` to the primitive `int` 10.
2. Add 5, giving the primitive 15.
3. **Box** 15 via `Integer.valueOf(15)` — a *new* `Integer` object (or a cached one).
4. Reassign `x` to point at it.

The original `Integer` holding 10 was never touched. `identityHashCode` reflects object identity rather than value, so its change is direct evidence that `x` now names a different object.

### The aliasing demonstration

```java
Integer a = 100;
Integer b = a;        // b points at the same object

a = a + 1;            // new Integer(101); a repointed

a;                    // 101
b;                    // 100 — unchanged
a == b;               // false
```

```text
Before:  a ──┐
             ├──▶ [Integer 100]
         b ──┘

After a = a + 1:
         a ──▶ [Integer 101]   ← brand new
         b ──▶ [Integer 100]   ← original, untouched
```

Contrast with a genuinely mutable type:

```java
List<Integer> list1 = new ArrayList<>(List.of(1, 2, 3));
List<Integer> list2 = list1;     // same object

list1.add(4);                    // mutates in place — no new object

list1;   // [1, 2, 3, 4]
list2;   // [1, 2, 3, 4]  ← changed too, because it IS the same object
```

With `List`, a method changes the object both references see. With `Integer`, no method changes the object at all — arithmetic only produces new ones.

### Why they had to be immutable

The **Integer cache** depends on it. `Integer.valueOf()` returns shared, pre-created objects for −128..127:

```java
Integer a = 100, b = 100;
a == b;      // true — the same cached object
```

If `Integer` were mutable, two unrelated parts of a program could both hold the cached `100`, and one calling `a.setValue(50)` would change the other's value — and every future autoboxing of 100 anywhere in the JVM. The cache is only possible because the objects can't change.

The same argument covers the other two benefits: an immutable `Integer` key's hash never shifts, so it can't get lost in a `HashMap`; and threads can share one freely without synchronization.

### The mutability test for any class

> Does this class have **any** method that changes an existing object's internal fields without creating a new object?

- `Integer` — no. Arithmetic produces new objects. ✅ Immutable
- `String` — no. `substring`, `concat`, `replace` all return new instances. ✅ Immutable
- `ArrayList` — yes. `add`, `remove`, `set` write into the backing array. ❌ Mutable
- `StringBuilder` — yes. `append` writes into its buffer. ❌ Mutable, on purpose

## Immutability Dissolves the Copying Problem

Shallow versus deep copying is only a question because nested objects can be **mutated**. Remove mutation and the distinction evaporates: a shallow copy of an immutable object graph behaves identically to a deep copy, because sharing a reference to something that can never change is harmless.

```java
final class Address {
    private final String city;
    Address(String city) { this.city = city; }
    public String getCity() { return city; }
}

final class Employee {
    private final String name;
    private final Address address;      // shared on a shallow copy — and that's fine
}
```

With a mutable `Address`, cloning `Employee` shallowly leaves both copies pointing at one `Address`, and a write through either corrupts the other. With an immutable `Address`, there is no write. The bug can't be written.

This is the strongest practical argument for immutable value types: it doesn't make copying easier, it makes copying **unnecessary**. Where mutation is genuinely required, prefer explicit copy constructors over `Cloneable` — see [[6. Cloning And Object Copying]].

**The line for an interview**: *"I make value types immutable wherever reasonable, because it removes the shallow-vs-deep copy question entirely — sharing a reference to an immutable object is always safe. Where I do need mutable state and copying, I use an explicit copy constructor rather than `Cloneable`, since `clone()` is shallow by default and bypasses constructor validation."*
