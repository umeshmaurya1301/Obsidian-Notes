# Access Control And Encapsulation

---

## Short Notes

---

### 1. The Four Access Levels

| Modifier | Same Class | Same Package | Subclass (other pkg) | World |
| --- | :---: | :---: | :---: | :---: |
| `private` | ✅ | ❌ | ❌ | ❌ |
| default (none) | ✅ | ✅ | ❌ | ❌ |
| `protected` | ✅ | ✅ | ✅ (own inherited ref only) | ❌ |
| `public` | ✅ | ✅ | ✅ | ✅ |

> Memorise this table — it is the single most-tested thing in this topic.

---

### 2. `private`

- Visible **only inside the same class** — not to subclasses, even in the same file
- Private members **are** in the object's memory, just not in the child's scope
- Therefore private methods **cannot be overridden** — the child can't see them
- Use: internal state, helper methods, the backbone of encapsulation

---

### 3. The Private "Override" Trap

```java
class Parent { private void greet() { print("Parent"); }
               void callGreet() { greet(); } }
class Child extends Parent { private void greet() { print("Child"); } }

new Child().callGreet();   // "Parent" — not an override, two unrelated methods
```

- Looks like overriding, binds statically, resolves inside `Parent` only

---

### 4. Default (Package-Private)

- No modifier written → visible **within the same package only**
- Not visible to subclasses in other packages
- A package-private **class** cannot even be imported from outside
- Use: implementation classes that collaborate inside one module

---

### 5. `protected`

- Package-private **plus** subclasses in other packages
- Designed for extension: framework base classes expose hooks to subclasses
- Wider than default, narrower than public
- Carries a restriction most people miss (next)

---

### 6. The `protected` Cross-Package Restriction

- A subclass in another package may touch a `protected` member **only through its own type**
- `this.balance` ✅ | `otherAccountRef.balance` ❌ (compile error)
- Prevents a subclass from poking at arbitrary instances of its parent
- Inside the **same package**, no such restriction applies

---

### 7. `public`

- Visible everywhere — the deliberate API surface
- Fields should rarely be `public`: no validation, no future-proofing
- Methods that form the external contract are `public`; their backing fields `private`

---

### 8. Top-Level vs Member Visibility

- **Top-level class**: only `public` or default — `private`/`protected` are compile errors
- **Members and nested classes**: all four modifiers allowed
- One `public` top-level type per file, and the file must be named after it

---

### 9. Getters and Setters

- Controlled access to private fields — encapsulation in practice
- Buys: validation, read-only fields, computed values, side effects, future-proofing
- **Not every field needs both** — getter-only is the common, safer default
- A getter+setter on every field is a public field with extra steps

---

### 10. Defensive Copies

- A getter returning a mutable field hands out a writable reference to internal state
- `return new ArrayList<>(entries);` or `List.copyOf(entries)` instead
- Same on the way in: copy constructor arguments before storing them
- Immutable field types (`record`, `String`) remove the need entirely

---

### 11. Interface Methods Must Be `public`

```java
interface Drivable { void drive(); }
class Car implements Drivable {
    void drive() { }          // ❌ "attempting to assign weaker access privileges"
    public void drive() { }   // ✅
}
```

- Interface methods are implicitly `public abstract`; overriding can't narrow access

---

### 12. The Standard Design Pattern

```java
public interface PaymentProcessor { void process(Payment p); }   // public contract

class DefaultPaymentProcessor implements PaymentProcessor {      // package-private impl
    private final ValidationEngine validator;                    // private state
    public void process(Payment p) { ... }                       // must be public
}
```

- Consumers depend on the abstraction; the implementation can be swapped freely

---

# Detailed Explanation

---

## The Four Access Levels

Java has exactly four visibility levels, applying to classes, fields, methods and constructors:

| Modifier | Same Class | Same Package | Subclass, different package | Non-subclass, different package |
| --- | :---: | :---: | :---: | :---: |
| `private` | ✅ | ❌ | ❌ | ❌ |
| default (no modifier) | ✅ | ✅ | ❌ | ❌ |
| `protected` | ✅ | ✅ | ✅ | ❌ |
| `public` | ✅ | ✅ | ✅ | ✅ |

Read it as four widening rings:

```text
private   → the class
(default) → the package
protected → the package + the subclass hierarchy
public    → everything
```

The one that surprises people is that `protected` is **wider** than default, not narrower — it adds cross-package subclasses on top of package access, it doesn't trade one for the other.

The design principle behind all of it: **start at `private` and widen only when forced.** Every level you expose is a promise you now have to keep, because anything visible outside your class becomes API that someone will depend on.

---

## `private`

Visible only inside the declaring class — not to subclasses, not even to a subclass in the same file.

```java
class Account {
    private long balancePaise;

    private void logTransaction(String msg) {         // internal helper
        System.out.println("LOG: " + msg);
    }

    public void deposit(long amount) {
        balancePaise += amount;
        logTransaction("Deposited " + amount);        // ✅ same class
    }
}

class SavingsAccount extends Account {
    void show() {
        System.out.println(balancePaise);   // ❌ compile error — invisible to the subclass
    }
}
```

The nuance worth stating precisely: private members **are inherited into the object's memory** — a `SavingsAccount` object physically contains `balancePaise`, and `deposit()` operates on it — but the *name* is not in scope in the subclass. The state exists; the access does not.

### Why private methods can't be overridden

```java
class Parent {
    private void greet() { System.out.println("Parent greet"); }
    void callGreet() { greet(); }
}

class Child extends Parent {
    private void greet() { System.out.println("Child greet"); }   // NOT an override
}

new Child().callGreet();   // "Parent greet"
```

`Child.greet()` is a completely separate method that happens to share a name. Overriding requires the parent's method to be **visible** to the subclass, and a private one never is — so there is nothing to override, no vtable slot to replace, and the call inside `callGreet()` is bound statically to `Parent.greet()` at compile time.

This is why `@Override` on the child's `greet()` is a compile error, and why the JIT can freely inline private methods.

**Use for**: all mutable state, helper methods, anything you might want to change next month without a migration.

## Default (Package-Private)

No modifier at all. Visible within the same package, and nowhere else — not to subclasses in other packages, not to anyone.

```java
// com/bank/Account.java
package com.bank;

class Account {              // package-private class
    long balancePaise;       // package-private field
    void audit() { }         // package-private method
}
```

```java
// com/bank/Bank.java
package com.bank;

class Bank {
    void test() {
        Account a = new Account();
        a.balancePaise = 100;    // ✅ same package
    }
}
```

```java
// com/external/Client.java
package com.external;

import com.bank.Account;        // ❌ Account is not public — can't even be imported
```

This is the most under-used modifier in ordinary Java code and the most used in good library code. It defines a **module boundary inside a package**: several classes collaborate closely, and only one or two of them are `public`. Consumers see the small surface; the rest can be refactored, renamed or deleted without breaking anyone.

Caveat: package-private is not a security boundary. Anyone can declare a class in your package and reach in — which is what JPMS modules (Java 9+) exist to fix properly.

---

## `protected`

Package-private access, **plus** access from subclasses in other packages.

```java
// com/bank/Account.java
package com.bank;

public class Account {
    protected long balancePaise;
    protected void applyInterest() { balancePaise = balancePaise * 105 / 100; }
}
```

```java
// com/external/SavingsAccount.java
package com.external;
import com.bank.Account;

public class SavingsAccount extends Account {
    void show() {
        balancePaise += 10;    // ✅ inherited protected field
        applyInterest();       // ✅ inherited protected method
    }
}
```

### The cross-package restriction

Here is the rule almost everyone misses. A subclass in a **different package** may access a `protected` member only **through a reference of its own type** (or a subtype) — never through a parent-typed reference, and never on some other instance of the parent.

```java
package com.external;

public class SavingsAccount extends Account {
    void test(Account other, SavingsAccount sibling) {
        this.balancePaise += 10;      // ✅ own inherited member
        sibling.balancePaise += 10;   // ✅ reference is SavingsAccount
        other.balancePaise += 10;     // ❌ compile error — 'other' is typed Account
    }
}
```

**Why**: the intent of `protected` is "you may work with the state you inherited", not "you may reach into any instance of my class". Without this rule, declaring one subclass in any package would grant full access to every `Account` object everywhere, and `protected` would be indistinguishable from `public`.

Inside the **same package** there is no such restriction — package access already covers it, so `other.balancePaise` compiles fine there.

**Use for**: designed extension points. A framework base class exposes `protected` hooks for subclasses to call or override, while keeping them out of the public API. If you mark something `protected`, you are committing to it as API for every subclass, forever — document it accordingly.

> 💡 **Interview**: Is `protected` wider or narrower than default? → Wider. `protected` is package access **plus** cross-package subclasses; it never removes package access.

---

## `public`

Visible from anywhere, with no restrictions. This is your deliberate API surface: service methods, public contracts, constructors meant to be called.

```java
package com.bank;

public class Account {
    public void deposit(long amount) { ... }
}
```

The standing rule for fields: **fields should almost never be `public`.** A public field means no validation, no way to add logging or invalidation later, no way to change the internal representation, and no way to make it read-only. The methods that form the intended API are `public`; the fields behind them are `private`.

The exceptions are genuine constants — `public static final` — and `record` components, where the accessor is public but the underlying field is private and final.

---

## Top-Level vs Member Visibility

**Top-level classes** (not nested) may be only `public` or **default**:

```java
public class Account { }      // ✅ visible everywhere
class InternalHelper { }      // ✅ visible within this package
private class X { }           // ❌ compile error at top level
protected class Y { }         // ❌ compile error at top level
```

`private` and `protected` are meaningless at the top level — there is no enclosing class to be private *to*, and no inheritance relationship to be protected *within*. Nested classes have both, so they may use all four.

A file may contain at most one `public` top-level type, and the file must be named after it.

**Members** — fields, methods, constructors and nested classes — may use all four modifiers.

## Getters and Setters

The standard mechanism for controlled access to private state:

```java
class Account {
    private long balancePaise;

    public long getBalancePaise() { return balancePaise; }

    public void setBalancePaise(long balancePaise) {
        if (balancePaise < 0) throw new IllegalArgumentException("balance cannot be negative");
        this.balancePaise = balancePaise;
    }
}
```

What this buys over a public field:

**Validation.** A setter can reject invalid values; a field assignment cannot.

**Read-only fields.** Provide a getter and no setter, and the field is immutable from outside:

```java
class Employee {
    private final String employeeId;
    Employee(String id) { this.employeeId = id; }
    public String getEmployeeId() { return employeeId; }   // no setter — fixed at construction
}
```

**Future-proofing.** The internal representation can change while the signature stays put:

```java
public long getBalancePaise() {
    return ledger.computeBalance(walletId);   // was a stored field, now derived — callers unaffected
}
```

**Computed properties.** A getter need not return a stored field at all:

```java
public int getAge() {
    return Period.between(dateOfBirth, LocalDate.now()).getYears();
}
```

**Side effects.** Audit logging, event publication, cache invalidation on write.

### The important qualification

**Not every field needs both.** Decide per field: getter only (the common, safer default), both, or — rarely — setter only, as with a password field you accept but never hand back.

And the thing worth saying out loud in an interview: a class with a getter and setter for every private field has **not** achieved encapsulation. It has a public field with two extra methods. Real encapsulation exposes *operations* that maintain invariants:

```java
// ❌ the invariant lives at every call site
wallet.setBalancePaise(wallet.getBalancePaise() - 500);

// ✅ the invariant lives in one place
wallet.debit(500);   // throws if insufficient, if negative, if the wallet is frozen
```

### Defensive copies

A getter that returns a mutable field leaks the internal state it was meant to protect:

```java
class Payment {
    private final List<LedgerEntry> entries = new ArrayList<>();

    public List<LedgerEntry> getEntries() { return entries; }   // ❌ caller can mutate internals
}

payment.getEntries().clear();   // the private field is now empty
```

```java
public List<LedgerEntry> getEntries() { return List.copyOf(entries); }   // ✅ unmodifiable snapshot
```

The same applies on the way in — copy a mutable constructor argument before storing it, or the caller retains a handle to your state. Arrays, `Date`, and mutable collections are the usual culprits; immutable types (`record`, `String`, `LocalDate`) make the problem disappear.

## Interface Methods Must Be Implemented `public`

Interface methods are implicitly `public abstract`. Overriding cannot narrow access, so the implementation must be `public`:

```java
interface Drivable { void drive(); }

class Car implements Drivable {
    void drive() { }          // ❌ "attempting to assign weaker access privileges; was public"
    public void drive() { }   // ✅
}
```

This is not a special rule for interfaces — it is overriding rule #3 from [[4. Inheritance]] applied to a method that was already `public`. It catches people because the `public` in the interface is invisible.

## The Standard Design Pattern

Putting the modifiers together as they are actually used in a well-structured service:

```java
package com.card91.switchcore;

public interface PaymentProcessor {              // public — the contract consumers see
    PaymentResult process(Payment payment);
}

class DefaultPaymentProcessor implements PaymentProcessor {   // package-private — hidden impl
    private final ValidationEngine validator;                 // private — pure internal state
    private final SwitchClient switchClient;

    DefaultPaymentProcessor(ValidationEngine v, SwitchClient s) {   // package-private ctor
        this.validator = v;
        this.switchClient = s;
    }

    protected void logAudit(String msg) { }      // protected — an extension hook, if intended

    @Override
    public PaymentResult process(Payment payment) {   // public — required by the interface
        validator.validate(payment);
        return switchClient.route(payment);
    }
}

public final class ProcessorFactory {            // public — the only way in
    public static PaymentProcessor create(Config c) {
        return new DefaultPaymentProcessor(new ValidationEngine(c), new SwitchClient(c));
    }
}
```

Consumers outside the package can name exactly two types: the interface and the factory. `DefaultPaymentProcessor` can be renamed, split, replaced with a routing decorator, or swapped for a different implementation entirely — none of it is visible outside, so none of it breaks anyone. This is the same shape as a Spring service where the interface is what gets injected and the `@Service` class is an implementation detail.

Three rules that fall out of it:

1. **The interface is the API.** Everything else defaults to package-private.
2. **`protected` is a commitment.** Only expose a hook you intend to support for every future subclass.
3. **Nothing mutable is more visible than `private`.**
