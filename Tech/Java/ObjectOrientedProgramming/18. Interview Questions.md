## Short Notes

### 1. Abstraction vs Encapsulation

The single most confused pair, and the most common opener.

- **Abstraction** = design concern → expose *what*, hide *how*. Achieved with `interface` / `abstract class`.
- **Encapsulation** = implementation concern → hide *state*, protect invariants. Achieved with access modifiers + validating accessors.
- They're orthogonal: an `interface` is abstraction with no state to encapsulate; a `private` field with a checked setter is encapsulation with no abstraction.

> [!example] One-liner
> *"Abstraction hides complexity from the caller; encapsulation hides data inside the class. One is about the contract, the other about who's allowed to touch the fields."*

→ [[1. OOP Fundamentals]], [[8. Access Control And Encapsulation]]

### 2. Interface vs Abstract Class — and which do you pick?

The most frequently asked comparison question in OOP interviews. Everyone can recite the table; the **"when"** is the discriminator.

| Aspect | Abstract Class | Interface |
| ------ | -------------- | --------- |
| Relationship | **is-a** | **can-do** / capability |
| State | Can hold instance fields | Only `public static final` constants |
| Constructors | Yes | No |
| Multiple inheritance | No | Yes |
| Members | Any access modifier | `public` (+ `private` helpers since 9) |
| Since Java 8/9 | — | `default`, `static`, `private` methods |

**Pick an abstract class when** related types share ~80% of the implementation *and state* — `Vehicle` holding `brand`/`model` for `Car`, `Bike`, `Truck`.
**Pick an interface when** unrelated types need to be substitutable for one capability — `PaymentMethod.processPayment()` implemented by `UpiPayment`, `CardPayment`, `NetBanking`.

> [!example] One-liner
> *"Abstract class when I'm sharing state and a partial implementation up a real is-a hierarchy; interface when I only need a contract multiple unrelated types can satisfy. In practice I default to the interface and only pull up an abstract class when duplicated code forces it."*

**Follow-up trap — "Java 8 gave interfaces bodies, so is the abstract class dead?"**
No. Interfaces still can't hold **instance state** or run a **constructor**, so anything with invariants to initialise stays an abstract class.

→ [[5. Interfaces And Abstraction]]

### 3. Overloading vs Overriding

| | Overloading | Overriding |
| --- | ----------- | ---------- |
| Polymorphism | Compile-time (static) | Runtime (dynamic) |
| Resolved by | Reference type, at compile time | Object type, at runtime |
| Signature | Must **differ** (params) | Must **match** |
| Return type | Can differ freely | Same or **covariant** |
| Access | Anything | Cannot be **more restrictive** |
| Exceptions | Anything | No **broader checked** exception |
| Static methods | Can be overloaded | **Hidden**, not overridden |

**Overriding rules worth stating unprompted:** same signature, covariant return allowed, access can only widen, checked exceptions can only narrow, `private` / `static` / `final` methods cannot be overridden.

> [!warning] The classic trick
> ```java
> void log(Object o) { }
> void log(String s) { }
> log(null);   // → log(String), the MOST SPECIFIC applicable overload
> ```
> Add `log(Integer i)` and the same call becomes **ambiguous** — a compile error.

→ [[7. Polymorphism Deep Dive]]

### 4. Static vs Dynamic Binding

- **Static binding** — resolved by the compiler from the *reference* type: `private`, `static`, `final`, overloaded methods, and all fields.
- **Dynamic binding** — resolved by the JVM from the *actual object*: overridden instance methods, dispatched through the vtable.

> [!warning] Fields are never polymorphic
> ```java
> class A { String name = "A"; String who() { return "A"; } }
> class B extends A { String name = "B"; String who() { return "B"; } }
>
> A ref = new B();
> ref.name;    // "A"  → field access is static binding
> ref.who();   // "B"  → method call is dynamic binding
> ```

**"Can static methods be overridden?"** → No. A static method in a subclass with the same signature **hides** it. Calls bind to the reference type, so `A ref = new B(); ref.staticM()` runs `A`'s version.

→ [[3. Static And Dynamic Binding]]

### 5. Why no multiple inheritance of classes? The Diamond Problem

- If `D extends B, C` and both override `A.m()`, the compiler can't decide which `m()` `D` inherits — plus **state** would be inherited twice.
- Java sidesteps it: single class inheritance, multiple **interface** inheritance (no state to duplicate).
- Java 8 `default` methods reintroduced a *behaviour* diamond, so the language added a rule: if two interfaces give conflicting defaults, the class **must** override and disambiguate.

```java
class D implements B, C {
    public void m() { B.super.m(); }   // forced, explicit
}
```

**Resolution priority:** class wins over interface → more specific interface wins over less specific → otherwise you must override.

→ [[4. Inheritance]]

### 6. `equals()` and `hashCode()` — the contract

Asked everywhere because it exposes shallow vs deep understanding in one question: override one without the other and the code **compiles cleanly and fails silently** in exactly the collections everything depends on.

**Contract:**
1. `a.equals(b)` ⟹ `a.hashCode() == b.hashCode()`
2. Equal hash codes do **not** imply equality (collisions are legal)
3. `equals` must be reflexive, symmetric, transitive, consistent, and `x.equals(null) == false`

```java
@Override public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Txn t)) return false;       // instanceof handles null + type
    return amount == t.amount && txnId.equals(t.txnId);
}
@Override public int hashCode() { return Objects.hash(txnId, amount); }
```

**"What breaks if I override only `equals`?"**
Two equal objects land in different buckets → `HashMap.get()` returns `null` for a key you just put, `HashSet` holds duplicates.
**"Only `hashCode`?"** → same bucket, then `equals` says "different" → still a lookup miss.

> [!warning] Mutable keys
> Mutate a field used in `hashCode()` after inserting into a `HashMap` and the entry is **unreachable** — wrong bucket, and it leaks. This is the real reason key types should be immutable.

**`==` vs `equals()`** → `==` compares references (or primitive values); `equals` compares state, *if* overridden — `Object.equals` is just `==`.

→ [[9. The Object Class]]

### 7. Immutability — "write an immutable class"

A near-guaranteed whiteboard ask. Five rules:

1. Class `final` (or all constructors `private` + static factory) — no subclass can add mutability
2. All fields `private final`
3. No setters, no method that mutates state
4. **Defensive copy on the way in** — copy mutable constructor args
5. **Defensive copy on the way out** — never return the internal mutable reference

```java
public final class Settlement {
    private final String batchId;
    private final List<Txn> txns;

    public Settlement(String batchId, List<Txn> txns) {
        this.batchId = batchId;
        this.txns = List.copyOf(txns);            // in
    }
    public List<Txn> getTxns() { return txns; }   // out: already unmodifiable
}
```

**Why bother:** thread-safe with zero synchronisation, safe as a `Map` key / `Set` element, cacheable, no defensive copying by callers.
**Why `String` is immutable:** string pool sharing, safe use as a `HashMap` key with a cached `hash`, security (a class name or file path can't be mutated after a permission check), and thread safety.

> [!warning] `final` ≠ immutable
> `final List<Txn> l` stops **reassignment**, not `l.add(...)`. That's the single most common wrong answer here.

→ [[11. Immutability]]

### 8. Shallow vs Deep Copy

- **Shallow** — copies the fields; reference fields still point at the *same* nested objects. `Object.clone()` is shallow.
- **Deep** — recursively copies the nested objects too; the copies are fully independent.
- Ways to deep copy: manual copy constructor (preferred), `clone()` overridden to clone nested fields, or a serialization round-trip (slow, fragile).

**"What's wrong with `Cloneable`?"** — it's a **marker interface** with no `clone()` method, `clone()` is `protected` on `Object`, it bypasses constructors, and it doesn't play well with `final` fields. Effective Java's advice: prefer a **copy constructor** or static factory.

→ [[6. Cloning And Object Copying]]

### 9. Association vs Aggregation vs Composition

| | Association | Aggregation | Composition |
| --- | ----------- | ----------- | ----------- |
| Relation | "uses-a" | "has-a", weak | "has-a", strong / **part-of** |
| Lifecycle | Independent | Independent | Child **dies with** parent |
| Ownership | None | Shared | Exclusive |
| Example | `Merchant` ↔ `AcquiringBank` | `Wallet` has `Card`s (card outlives wallet) | `Order` has `OrderLine`s |
| UML | plain line | hollow diamond | filled diamond |

> [!example] One-liner
> *"Composition is a part-of relationship where the part can't exist without the whole — delete the Order and the OrderLines are meaningless. Aggregation is a has-a where both sides live independently."*

→ [[10. Object Relationships]]

### 10. Composition over Inheritance — and when to avoid inheritance

**Inheritance is the wrong tool when:**
- The relationship isn't genuinely **is-a** (`Stack extends Vector` — a stack is not a vector; it inherits `get(i)` and `insertElementAt`, breaking its own invariant)
- You're inheriting only to **reuse code**
- The superclass isn't designed for extension — overriding one method can break another that self-calls it (fragile base class)
- Behaviour varies along **more than one axis** → class explosion

**Composition wins because:** you can swap behaviour at runtime, you depend only on the delegate's public API, and it isn't limited to one parent.

> [!example] One-liner
> *"Inheritance couples me to the superclass's implementation, not just its interface — a change there can silently break my subclass. I use inheritance only for a true is-a with a class designed for extension, and delegate otherwise."*

**LSP framing of the same point:** a subclass must be substitutable for its parent. `Square extends Rectangle` breaks `setWidth`/`setHeight` expectations; `Penguin extends Bird` breaks `fly()`. The **hierarchy** is wrong, not the code.

→ [[10. Object Relationships]], [[12. SOLID And Design Principles]]

### 11. SOLID — say the principle, then the violation

Interviewers grade the **example**, not the acronym.

| | Principle | Tell it's violated | Fix |
| --- | --------- | ------------------ | --- |
| **S** | One reason to change | Class does parsing + DB + email | Split by axis of change |
| **O** | Open to extend, closed to modify | `switch` on a type enum grows every release | Interface + polymorphic strategies |
| **L** | Subtypes substitutable | Override throws / weakens behaviour | Fix the hierarchy, prefer composition |
| **I** | No fat interfaces | `UnsupportedOperationException` stubs | Split into role interfaces |
| **D** | Depend on abstractions | `new MySqlRepo()` inside a service | Inject the interface |

> [!info] DIP ≠ DI
> DIP is the *direction of the dependency arrow* (high-level policy owns the abstraction). DI is just one way to supply the implementation.

The point of all five: **high cohesion, low coupling**.

→ [[12. SOLID And Design Principles]]

### 12. Object creation and initialization order

A favourite "predict the output" question.

```text
1. Static fields + static blocks    → once, at class load, PARENT first
2. Instance fields + init blocks    → PARENT first, per object
3. Constructor body                 → PARENT first, per object
```

- A constructor's implicit first statement is `super()` — so the parent is fully built before the child's fields are assigned.
- `this(...)` and `super(...)` are mutually exclusive and must be the **first** statement.

> [!warning] The trap
> Calling an **overridable method from a constructor** runs the *subclass* override before the subclass's fields are initialised — it sees `null` / `0`.

**"Can a constructor be overridden / be `final` / be `static`?"** → No to all three. Constructors aren't inherited, so overriding doesn't apply.

→ [[2. Classes And Objects]], [[17. Object Lifecycle]]

### 13. Keyword rapid-fire

- **`final`** — variable: assign once; method: can't override; class: can't extend. Does **not** mean immutable.
- **`static`** — belongs to the class, not the instance; can't use `this`; can't be overridden (only hidden); initialised once at class load.
- **`this`** — current instance; `this(...)` chains constructors.
- **`super`** — parent's members; `super(...)` calls the parent constructor; `Iface.super.m()` disambiguates defaults.
- **`instanceof`** — safe downcast guard; pattern matching (Java 16+) folds the cast in: `if (o instanceof Txn t)`.
- **Upcast** — implicit, always safe. **Downcast** — explicit, `ClassCastException` at runtime if wrong.

→ [[13. Special Classes And Modifiers]]

### 14. Static nested vs inner class

- **Static nested** — no reference to the outer instance; instantiate as `Outer.Nested n = new Outer.Nested()`. Use for a helper logically scoped to the outer class (`Map.Entry`, a `Builder`).
- **Inner (non-static)** — holds an implicit `Outer.this` reference; needs `outer.new Inner()`. **Leak risk**: a long-lived inner instance keeps the whole outer object alive.
- **Anonymous / local** — one-off implementations; largely replaced by lambdas for functional interfaces.

> [!example] One-liner
> *"Default to static nested. Make it non-static only if it genuinely needs the enclosing instance — otherwise you've added a hidden reference and a memory-leak path."*

→ [[14. Nested Classes]]

### 15. Scenario questions — how to structure the answer

These dominate SDE-2 rounds. The pattern the panel wants: **identify the axis of change → put an interface on it → inject implementations.**

**"Refactor this `if/else` payment chain"**
```java
// before: violates OCP — every new rail edits this method
if (type == UPI) { ... } else if (type == CARD) { ... }

// after
interface PaymentRail { boolean supports(RailType t); Receipt charge(Txn t); }
// Spring injects List<PaymentRail>; adding NetBanking adds a class, edits nothing
```

**"Design X using OOP" (banking, ride-sharing, parking lot)** — name the entities, state which relationships are composition vs association, put interfaces on the varying behaviour (pricing, matching, payment), and mention one pattern with a reason (Strategy for pricing, Factory for creating rails, Observer for notifications). Don't lead with patterns.

**"How does encapsulation improve security?"** — invariants can't be bypassed (no negative `balance`), the representation can change without breaking callers, and sensitive state is unreachable or immutable once validated.

**"Thread-safe Singleton"** — enum singleton, or a `static final` holder class; mention double-checked locking needs `volatile`, and that a singleton is usually better expressed as a DI-scoped bean.

→ [[12. SOLID And Design Principles]]

## SDE-2 Interview Priority Checklist

### Must Know (100%)

- Abstraction vs encapsulation, in one sentence each, without mixing them up
- Interface vs abstract class **plus the "when I'd pick which"** with a real example
- Overloading vs overriding + the full overriding rules
- Static vs dynamic binding, and that **fields are never polymorphic**
- `equals`/`hashCode` contract, what breaks in `HashMap` either way, the mutable-key bug
- Writing an immutable class from memory, defensive copies both directions
- Composition over inheritance, with a concrete "inheritance was wrong here" story
- All five SOLID principles as violation → fix
- Initialization order, and the overridable-method-in-constructor trap

### Nice To Know

- Diamond problem with Java 8 defaults + `Interface.super.m()` resolution rules
- Association vs aggregation vs composition with the UML diamonds
- `Cloneable` being a broken design; copy constructor as the answer
- Static nested vs inner class and the leak path
- Why `String` is immutable (pool, cached hash, security, thread safety)

### Advanced

- LSP stated formally: weaken preconditions, strengthen postconditions, preserve invariants
- The fragile base class problem / self-use in a superclass
- Most-specific overload resolution and `null` ambiguity
- Refactoring a type-switch into injected strategies so even the wiring stops changing
