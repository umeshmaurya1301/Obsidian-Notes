# Static And Dynamic Binding

---

## Short Notes

---

### 1. What Binding Means

- **Binding** = connecting a method call to the actual method body that runs
- **Static (early) binding**: decided by the **compiler**, from the **reference type**
- **Dynamic (late) binding**: decided by the **JVM**, from the **actual object type**
- The whole of runtime polymorphism is one sentence: instance methods are dynamically bound

---

### 2. What Binds Which Way

| Member | Binding | Resolved by |
| ------ | ------- | ----------- |
| Instance method | Dynamic | Object type |
| `static` method | Static | Reference type |
| `private` method | Static | Reference type (not inherited) |
| `final` method | Static-ish (devirtualised) | Object type, but no override possible |
| Field (static or not) | Static | Reference type |
| Constructor | Static | Exact class |

> One line: **instance methods bind to the object; everything else binds to the reference.**

---

### 3. The Classic Trap

```java
Parent p = new Child();
p.instanceMethod();   // Child's → object type wins
p.staticMethod();     // Parent's → reference type wins
p.field;              // Parent's → reference type wins
```

- Same reference, three different resolution rules
- The compiler already froze the static call into the bytecode; the JVM never reconsiders it

---

### 4. Method Hiding vs Overriding

| | Overriding | Hiding |
| --- | --- | --- |
| Applies to | Instance methods | `static` methods |
| Resolved by | Object type (runtime) | Reference type (compile time) |
| Parent version reachable | `super.m()` | `Parent.m()` |
| `@Override` legal | Yes | No — compile error |
| Polymorphic | Yes | No |

---

### 5. Field Hiding

- A child field with the same name **hides**, never overrides, the parent's
- Both fields exist in the object simultaneously — the reference type picks which one you read
- `super.field` and a cast reach the other one
- Never shadow a parent field intentionally; it is a bug factory

---

### 6. Why Statics Can't Be Polymorphic

- Instance methods are dispatched through the class's **virtual method table (vtable)**
- Each object header points to its class → the JVM looks up the override at call time
- `static` methods have **no vtable entry** — they belong to the class, not to any object
- No object → nothing to dispatch on → the compiler emits a fixed target

---

### 7. Bytecode View

| Instruction | Used for | Dispatch |
| ----------- | -------- | -------- |
| `invokestatic` | `static` methods | None — fixed target |
| `invokespecial` | Constructors, `private`, `super.m()` | None — fixed target |
| `invokevirtual` | Normal instance methods | vtable on the object's class |
| `invokeinterface` | Interface-typed calls | itable lookup |
| `invokedynamic` | Lambdas, method refs | Bootstrapped call site |

---

### 8. Practical Rules

- Always call a static method as `ClassName.method()`, never through an instance reference
- Never redeclare a parent's `static` method in a child unless you mean to hide it
- Never shadow a parent field
- Mark methods `final` when overriding would break your invariants — it also helps the JIT inline

---

### SDE-2 Interview Priority

**Must Know**: Static vs dynamic binding, What the reference type vs object type controls, Method hiding vs overriding, Field hiding, Why statics aren't polymorphic

**Nice To Know**: vtable mechanism, `invokevirtual` vs `invokestatic`, Why `private` methods bind statically

**Advanced**: itable for interface dispatch, JIT devirtualisation and monomorphic inline caches, `invokedynamic` for lambdas

# Detailed Explanation

---

## What Binding Means

Binding is the act of connecting a method **call** to the method **body** that will actually execute. The only question that matters is *when* that connection is made.

- **Static binding** (early binding) — the compiler makes the decision and writes a fixed target into the bytecode. It uses the **reference type**: the declared type of the variable.
- **Dynamic binding** (late binding) — the compiler only records a name and descriptor; the JVM resolves the real body at call time using the **actual object type**.

```java
Shape s = new Circle();
//    ↑ reference type    ↑ object type
```

Runtime polymorphism exists solely because instance method calls are dynamically bound. Everything else in Java — fields, statics, constructors, private methods — is statically bound, and that asymmetry is where the interview traps live.

---

## The Classic Trap

```java
class Parent {
    String label = "parent-field";

    static void staticMethod() {
        System.out.println("Parent static method");
    }

    void instanceMethod() {
        System.out.println("Parent instance method");
    }
}

class Child extends Parent {
    String label = "child-field";

    static void staticMethod() {          // hiding, NOT overriding
        System.out.println("Child static method");
    }

    @Override
    void instanceMethod() {
        System.out.println("Child instance method");
    }
}
```

```java
Parent p = new Child();          // reference type = Parent, object type = Child

p.instanceMethod();   // "Child instance method"  ← object type wins
p.staticMethod();     // "Parent static method"   ← reference type wins
System.out.println(p.label);     // "parent-field"  ← reference type wins
```

One reference, three different rules.

- `p.instanceMethod()` is compiled to `invokevirtual Parent.instanceMethod()`. At runtime the JVM follows `p`'s object header to the `Child` class, finds `Child.instanceMethod()` in its virtual method table, and calls that. This is genuine polymorphism — the whole point of overriding.
- `p.staticMethod()` is compiled to `invokestatic Parent.staticMethod()`. The compiler saw that `p` is declared `Parent`, resolved the target on the spot, and baked it in. The JVM never even looks at what object `p` points to. (The compiler also emits a warning: *static method should be qualified by type name*.)
- `p.label` is a `getfield` on the `Parent` slot. Field access is never virtual.

---

## Method Hiding vs Overriding

When a subclass declares a `static` method with the same signature as a parent's `static` method, that is **method hiding**, not overriding. `Child.staticMethod()` does not replace `Parent.staticMethod()` polymorphically; it is a separate method that merely shadows the parent's when reached through a `Child`-typed reference.

```java
Child c = new Child();
c.staticMethod();        // "Child static method"   — reference type is Child

Parent.staticMethod();   // "Parent static method"  ← how you should always write it
Child.staticMethod();    // "Child static method"
```

The clean proof that hiding is not overriding: `@Override` on a hiding static method is a **compile error** — *"method does not override or implement a method from a supertype"*. The annotation is the compiler's way of telling you the virtual mechanism was never involved.

| | Overriding | Hiding |
| --- | --- | --- |
| Applies to | Instance methods | `static` methods |
| Resolution | Runtime, object type | Compile time, reference type |
| Reach the parent's | `super.m()` | `Parent.m()` |
| `@Override` | Legal, recommended | Compile error |
| Participates in polymorphism | Yes | No |

The related rules: a `static` method cannot hide an instance method (or vice versa) — that combination is a compile error outright, because the two dispatch mechanisms are incompatible.

**Practical rule:** always call static methods as `ClassName.method()`. `instance.staticMethod()` is legal but reads like polymorphism while behaving nothing like it.

---

## Field Hiding

The same asymmetry applies to fields, and it surprises people more, because fields are not `static` here — they are ordinary instance fields, and they *still* bind statically.

```java
class Parent { String label = "parent-field"; }
class Child extends Parent { String label = "child-field"; }

Parent p = new Child();
Child  c = new Child();

System.out.println(p.label);            // "parent-field"
System.out.println(c.label);            // "child-field"
System.out.println(((Parent) c).label); // "parent-field"  ← same object, different reference type
```

Both fields genuinely exist inside the single `Child` object — the child's declaration does not replace the parent's slot, it adds a second one:

```text
Child object on heap
┌──────────────────────────────┐
│ header → Child class         │
│ Parent.label = "parent-field"│  ← reached via a Parent-typed reference
│ Child.label  = "child-field" │  ← reached via a Child-typed reference
└──────────────────────────────┘
```

Inside `Child`'s own methods, `label` means the child's and `super.label` means the parent's.

```java
class Child extends Parent {
    String label = "child-field";
    void show() {
        System.out.println(label);        // "child-field"
        System.out.println(super.label);  // "parent-field"
    }
}
```

Fields are never polymorphic. Shadowing a parent field is virtually always a bug: two pieces of state that look like one, with which one you get depending on the static type at the call site. Rename, or use the parent's field.

---

## Why Statics Can't Be Polymorphic — The Mechanism

Every object's header carries a pointer to its class metadata, and each class holds a **virtual method table (vtable)**: an array of pointers, one slot per virtual method, laid out so a subclass's slots line up with its parent's. An override simply replaces the pointer in the inherited slot.

```text
Parent vtable                  Child vtable
┌──────────────────────────┐   ┌──────────────────────────┐
│ [0] instanceMethod → P.im│   │ [0] instanceMethod → C.im│  ← same slot, overwritten
└──────────────────────────┘   │ [1] childOnly      → C.co│
                               └──────────────────────────┘

Child object ──header──▶ Child class ──▶ Child vtable
```

Dispatching `p.instanceMethod()` is then a constant-time indirection: follow the object's class pointer, read slot 0, jump. The compiler does not need to know the object's real type; the slot index is fixed at compile time and the *content* of that slot is what varies.

`static` methods have **no vtable slot at all**. They belong to the class, not to any object, so there is no object to look up a table on. The compiler emits a direct call, exactly like calling a free function. Nothing about that decision can change at runtime.

The same reasoning explains the other statically bound cases:

- **`private` methods** are not inherited, so no subclass can occupy their slot — nothing to dispatch. Compiled as `invokespecial`.
- **Constructors** are tied to one exact class by definition. Also `invokespecial`.
- **`super.m()`** deliberately bypasses dispatch to reach a specific implementation, which is why it too is `invokespecial` — otherwise `super.m()` inside an override would recurse forever.
- **`final` methods** cannot be overridden, so their slot content is known to be constant; the JIT devirtualises and usually inlines them.

---

## Bytecode View

Compiling the trap and running `javap -c` makes the whole thing concrete:

```text
p.instanceMethod();   →  invokevirtual  Parent.instanceMethod:()V
p.staticMethod();     →  invokestatic   Parent.staticMethod:()V
p.label;              →  getfield       Parent.label:Ljava/lang/String;
```

`invokevirtual` names `Parent.instanceMethod` too — but for a *virtual* call that name is only a starting point for the lookup, and the JVM resolves it against the receiver's actual class. For `invokestatic` and `getfield`, the named target *is* the answer.

| Instruction | Emitted for | Dispatch |
| ----------- | ----------- | -------- |
| `invokestatic` | `static` methods | None — fixed |
| `invokespecial` | Constructors, `private` methods, `super.m()` | None — fixed |
| `invokevirtual` | Normal instance methods | vtable on the receiver's class |
| `invokeinterface` | Calls through an interface type | itable lookup (slightly costlier) |
| `invokedynamic` | Lambdas, method references | Call site linked once by a bootstrap method |

> 💡 **Interview**: Why does `p.staticMethod()` print the parent's version when `p` holds a `Child`? → Because static methods are bound at compile time from the reference type and compiled to `invokestatic` with a fixed target; they have no vtable entry, so the JVM never consults the actual object.

---

## Practical Rules

1. **Call statics on the class**: `PaymentValidator.isValid(x)`, never `validator.isValid(x)`.
2. **Don't redeclare a parent's static method** in a subclass unless hiding is genuinely intended — it looks like an override to every reader.
3. **Never shadow a parent field.** Rename one of them.
4. **Mark methods `final`** when an override would break the class's invariants. It documents intent and lets the JIT devirtualise and inline.
5. **Remember the one-liner**: *instance methods bind to the object; fields, statics, privates and constructors bind to the reference.*
