# JVM Memory

---

## Short Notes

---

### 1. JVM Runtime Memory Structure

```text
JVM
├── Heap (Shared)
├── Metaspace (Shared)
└── Per Thread
    ├── Stack
    ├── PC Register
    └── Native Method Stack
```

- **Shared** across threads: Heap, Metaspace
- **Per-thread**: Stack, PC Register, Native Method Stack

---

### 2. Heap Memory

- Stores **objects** and **arrays**
- Largest memory area, shared by all threads
- Managed by Garbage Collector
- Reference variable → Stack, actual object → Heap

---

### 3. Stack Memory

- One stack per thread
- Stores method frames, local variables, primitive values, object references
- Uses Push/Pop — no GC needed, very fast
- `StackOverflowError` on infinite recursion

---

### 4. Metaspace

- Replaced PermGen from Java 8+
- Stores **class metadata** (class name, fields, methods, annotations, bytecode metadata)
- `new User()` → Heap | `class User` → Metaspace
- `OutOfMemoryError: Metaspace` possible with heavy dynamic class loading

---

### 5. PC Register

- One per thread, tracks **currently executing bytecode instruction**
- Needed for thread context switching

---

### 6. Native Method Stack

- Stores frames for **native method** execution (C/C++/OS calls)
- Examples: `Thread.start()`, File I/O, Socket operations

---

### 7. Heap vs Stack

| Feature   | Stack            | Heap           |
| --------- | ---------------- | -------------- |
| Scope     | Thread-specific  | Shared         |
| Speed     | Fast (Push/Pop)  | Slower         |
| Cleanup   | Auto (frame pop) | GC             |
| Stores    | Frames, locals   | Objects, arrays|
| Size      | Small            | Large          |

---

### 8. Stack Frame & Method Call Stack

- Each method call → **stack frame** (local vars, params, execution state)
- Frames form a **LIFO call stack**
- Frame destroyed on method exit — no GC needed

---

### 9. Local vs Instance Variables

| Local Variable (Stack)     | Instance Variable (Heap) |
| -------------------------- | ------------------------ |
| Declared inside method     | Declared inside class    |
| Lives during method only   | Lives with object        |

---

### 10. Primitive vs Reference Types

- **Primitive**: value stored directly on stack
- **Reference**: stack stores address, heap stores object
- `u2 = u1` → both point to **same** object

---

### 11. Pass-by-Value

- Java is **always pass-by-value**
- For objects, the **reference** is copied (not the object)

---

### 12. Object Creation Lifecycle (`new`)

1. Class Loading → Metaspace
2. Memory Allocation → Heap
3. Default Initialization → `null`, `0`, `false`
4. Constructor Execution
5. Reference Assignment → Stack

---

### 13. Object Layout

```text
Object Header → HashCode, Lock info, GC age, Class pointer
Instance Data → Your fields
Padding       → Memory alignment
```

---

### 14. Object References & Null

- Reference = address pointing to heap object
- `null` → points to nothing → `NullPointerException` on access
- No references → GC eligible

---

### 15. Object Destruction

- No manual `delete` — automatic GC
- Unreachable from GC Roots → eligible for collection
- `finalize()` deprecated

---

### 16. Heap Organization (Generational)

```text
Heap
├── Young Generation
│   ├── Eden        ← new objects
│   ├── Survivor S0 ← survivors after Minor GC
│   └── Survivor S1 ← alternates with S0
└── Old Generation  ← long-lived promoted objects
```

- **Weak Generational Hypothesis**: most objects die young

---

### 17. Eden, Survivors & Minor GC

- New objects → Eden
- Eden full → Minor GC → survivors to S0/S1, age incremented
- Two Survivor spaces for copy-collection

---

### 18. Object Promotion

- `age >= threshold` (~15) → promoted to Old Generation
- Old Gen: larger, less frequent, more expensive to clean

---

### 19. Large Object Allocation

- Very large objects skip Eden → **directly to Old Gen** (pretenuring)

---

### 20. Reachability Analysis

- Java does **not** use reference counting
- GC asks: "Can I reach this object from a GC Root?"
- Reachable → keep | Unreachable → collect
- Handles circular references correctly

---

### 21. GC Roots

Starting points for reachability traversal:
- Thread stack variables
- Static variables
- Active threads
- JNI references

---

### 22. Minor GC vs Major GC vs Full GC

| Type     | Scope            | Speed     | Frequency |
| -------- | ---------------- | --------- | --------- |
| Minor GC | Young Gen only   | Fast      | Frequent  |
| Major GC | Old Gen          | Expensive | Less      |
| Full GC  | Entire heap      | Slowest   | Rare      |

- Full GC triggers: Old Gen full, `System.gc()`, metadata pressure

---

### 23. Stop-The-World (STW)

- GC pauses all application threads for safe memory management
- 50ms → acceptable | 10s → production outage
- Modern collectors minimize STW

---

### 24. G1 GC (Default)

- Heap divided into many small **regions** (not contiguous Young/Old)
- Prioritizes regions with most garbage → "Garbage First"
- `-XX:MaxGCPauseMillis=200` for predictable pauses

---

### 25. ZGC & Shenandoah

- **ZGC**: ultra-low latency (<1ms), huge heaps (128GB–1TB)
- **Shenandoah**: low pause, concurrent, pause independent of heap size

---

### 26. Off-Heap Memory

- `ByteBuffer.allocateDirect()` → native memory, outside heap
- Less GC pressure, better I/O performance
- Used by Kafka, Netty, NIO, gRPC
- Risk: `OutOfMemoryError: Direct buffer memory`

---

### 27. Native Memory

- JVM process uses more than just heap: Metaspace, thread stacks, direct buffers, JIT code cache
- `-Xmx4g` ≠ 4GB process — actual usage can be much higher

---

### 28. Monitoring Tools

| Tool         | Purpose                          |
| ------------ | -------------------------------- |
| `jmap`       | Heap dump generation & stats     |
| `jstack`     | Thread dump capture              |
| `jstat`      | GC statistics monitoring         |
| `jcmd`       | Modern all-in-one JVM diagnostic |
| VisualVM     | GUI monitoring & profiling       |
| Eclipse MAT  | Heap dump analysis (Dominator Tree, Retained Heap) |

---

### 29. Memory Leaks in Java

Common causes:
- Static collections growing unbounded
- ThreadLocal not cleared in thread pools
- Listeners not deregistered
- Cache without eviction
- ExecutorService not shut down

---

### 30. Advanced Topics

- **TLAB**: Thread Local Allocation Buffer — each thread gets a slice of Eden, no locking needed
- **Escape Analysis**: JIT optimizes objects that never escape method scope
- **Safepoints**: JVM stops threads at method calls, loop back edges, exception paths
- **Generational Hypothesis**: most objects die young, few live long — GC design basis

---

### 31. Class Loading Process

- Before creating any object, JVM must **load the class**
- Three phases: **Loading → Linking → Initialization**
- Loading: find `.class` file, load bytecode, store metadata in Metaspace
- Linking: Verification → Preparation (static defaults) → Resolution (symbolic → actual refs)
- Initialization: execute static initializers and `static {}` blocks

---

### 32. Class Loader Types

- **Bootstrap** → core Java (`String`, `Object`, `ArrayList`)
- **Platform** → JDK modules (`java.sql`, `java.xml`) — called Extension Loader in Java 8
- **Application** → your classes (`User`, `OrderService`)
- **Parent Delegation Model**: child asks parent first → security (can't replace core classes)

---

### 33. Runtime Constant Pool

- Every loaded class has a Runtime Constant Pool in Metaspace
- Contains: string literals, method references, field references, numeric constants

---

### 34. String Constant Pool

- JVM maintains a pool of **unique String literals** in Heap
- `"hello"` used twice → same object reused
- `a == b` is `true` for two string literals with same value

---

### 35. Metaspace vs PermGen

| Feature     | PermGen (≤ Java 7)       | Metaspace (Java 8+)     |
| ----------- | ------------------------ | ----------------------- |
| Location    | Heap-related             | Native memory           |
| Sizing      | Fixed (`-XX:MaxPermSize`)| Dynamic (auto-grows)    |
| OOM Error   | `PermGen space`          | `Metaspace`             |

---

### 36. String Pool Interning

- Literals automatically interned: `"hello"` → pooled
- Explicit: `new String("hello").intern()` → returns pooled version
- Purpose: memory savings

---

### 37. String Literal vs `new String()`

- `String a = "hello"` → **1 object** (pool only)
- `String b = new String("hello")` → **2 objects** (pool + heap)
- `a == b` → `false` | `a.equals(b)` → `true`

---

### 38. StringBuilder Memory Behavior

- Strings are immutable → `s + "B"` creates new object each time
- `StringBuilder` uses mutable internal `char[]` buffer
- One buffer instead of many objects → less GC pressure

---

### 39. String Concatenation Internals

- Java 8: `a + b` → `new StringBuilder().append(a).append(b).toString()`
- Java 9+: `invokedynamic` + `StringConcatFactory` (more optimized)
- Compile-time: `"A" + "B"` → `"AB"` (constant folding)

---

### 40. Why Strings Are Immutable

| Reason              | Explanation                                        |
| ------------------- | -------------------------------------------------- |
| String Pool safety  | Shared pool objects can't be corrupted              |
| Security            | Passwords, URLs, paths can't be altered after creation |
| Thread safety       | Read-only → no synchronization needed               |
| HashMap key safety  | `hashCode()` never changes                          |
| Hash code caching   | Computed once, cached in `private int hash`          |
| JVM optimizations   | Pooling, constant folding, safe sharing              |

---

### 41. Heap OutOfMemoryError

- Heap exhausted — JVM can't allocate new object
- Causes: memory leaks, huge caches, large file reads
- `java.lang.OutOfMemoryError: Java heap space`

---

### 42. GC Overhead Limit Exceeded

- GC running continuously but recovering almost no memory
- Heap ~99.9% full, GC frees tiny amount, fills immediately, repeats
- `java.lang.OutOfMemoryError: GC overhead limit exceeded`

---

### 43. Direct Buffer Memory OOM

- Off-heap `ByteBuffer.allocateDirect()` exhausted
- Common in Kafka, Netty, NIO
- `java.lang.OutOfMemoryError: Direct buffer memory`

---

### 44. OOM & Error Quick Comparison

| Error                        | Memory Area       | Typical Cause             |
| ---------------------------- | ----------------- | ------------------------- |
| `Java heap space`            | Heap              | Too many objects / leak   |
| `StackOverflowError`         | Stack             | Infinite recursion        |
| `GC overhead limit exceeded` | Heap              | GC thrashing              |
| `Direct buffer memory`       | Native (off-heap) | Too many direct buffers   |
| `Metaspace`                  | Metaspace         | Too many loaded classes   |

---

### 45. Reference Strengths

```text
Strong → Soft → Weak → Phantom    (strongest to weakest)
```

| Type    | GC Behavior                        | Use Case                      |
| ------- | ---------------------------------- | ----------------------------- |
| Strong  | Never collected while referenced   | Default (`User u = new User()`)|
| Soft    | Collected under memory pressure    | Memory-sensitive caches       |
| Weak    | Collected at next GC cycle         | Metadata/reflection caches    |
| Phantom | `get()` always null; notification  | Post-mortem cleanup           |

---

### 46. WeakHashMap

- Keys stored via **weak references**
- Key unreachable → entry auto-removed by GC
- Normal HashMap: key survives even after `key = null` → potential leak
- Use cases: metadata caches, reflection caches, ClassLoader-sensitive frameworks

---

### 47. SoftHashMap

- **Not in the JDK** — no `SoftHashMap<K,V>`
- Historical: `Map<K, SoftReference<V>>` pattern
- Today: use Caffeine, Ehcache, Redis with TTL/LRU eviction

---

### 48. GC & Strong References in Spring Boot

- **Local HashMap in method**: method returns → frame removed → GC collects
- **API request**: Tomcat thread frame destroyed after response → GC eligible
- **Singleton bean cache**: `AppContext → Bean → Map → Objects` → alive forever (intentional)
- **Memory leak**: `static List` that only adds, never removes → `OutOfMemoryError`

> HashMap ≠ memory leak. Local HashMaps are fine — problems occur only with long-lived structures.

# Detailed Explanation

---

## JVM Runtime Memory Structure

When a Java program runs, the JVM creates several memory regions.

```text
JVM
├── Heap (Shared)
├── Metaspace (Shared)
├── Thread-1
│   ├── Stack
│   ├── PC Register
│   └── Native Method Stack
├── Thread-2
│   ├── Stack
│   ├── PC Register
│   └── Native Method Stack
└── ...
```

**Shared by all threads**: Heap and Metaspace hold data that any thread can access.

**Per-thread**: Each thread gets its own Stack, PC Register, and Native Method Stack.

> 💡 **Interview**: Which memory areas are thread-specific? → Stack, PC Register, Native Method Stack.

---

## Heap Memory

The Heap is where **all objects** live. When you write `new User()`, the object is allocated in Heap and a reference is stored on Stack.

```text
Stack                  Heap
user ——————→       User Object
```

Multiple references can point to the same object:

```java
User u1 = new User();
User u2 = u1;   // both point to same heap object
```

**Key characteristics:**
- Largest memory area, shared across all threads
- Managed by Garbage Collector
- All object creation happens here

---

## Stack Memory

Every thread has its own Stack. It stores **stack frames** — one per method call.

```java
public static void main(String[] args) {
    int x = 10;
    User user = new User();
}
```

```text
main frame
-----------
x = 10          ← primitive value stored directly
user = 0x123    ← reference to heap object
```

### Stack Frames and the Call Stack

Each method invocation pushes a frame. Returning pops it. This LIFO structure is the **method call stack**.

```text
methodB frame   ← top (currently executing)
--------------
methodA frame
--------------
main frame
```

Frame removed automatically on method return — no GC needed.

**Why is Stack fast?** Only Push/Pop operations, no GC overhead.

### StackOverflowError

Infinite recursion keeps pushing frames until stack space is exhausted:

```java
void recurse() {
    recurse();  // never terminates → StackOverflowError
}
```

---

## Metaspace

Replaced **PermGen** from Java 8. Stores **class metadata** — class name, fields, methods, annotations, bytecode metadata.

**Important distinction:**
- `new User()` → object goes to **Heap**
- `class User { ... }` → metadata goes to **Metaspace**

Lives in **native memory** (not bounded by JVM heap). Excessive dynamic class loading (Spring proxies, CGLIB, ByteBuddy) can cause `OutOfMemoryError: Metaspace`.

---

## PC Register

Each thread has a PC Register tracking the **address of the currently executing bytecode instruction**. Essential for thread context switching — tells JVM where a thread left off.

---

## Native Method Stack

Stores frames for native method executions (C, C++, OS calls) via the `native` keyword. Common native calls: `Thread.start()`, File I/O, Socket ops, `System.currentTimeMillis()`.

---

## Heap vs Stack — Deep Comparison

| Aspect          | Stack                           | Heap                              |
| --------------- | ------------------------------- | --------------------------------- |
| Thread safety   | Thread-specific (no sharing)    | Shared (needs synchronization)    |
| Speed           | Very fast (Push/Pop)            | Slower (allocation + GC)          |
| Cleanup         | Automatic on method return      | Garbage Collector                 |
| Content         | Frames, local vars, references  | Objects, arrays, instance vars    |
| Size            | Small (configurable via `-Xss`) | Large (configurable via `-Xmx`)   |
| Error on full   | `StackOverflowError`            | `OutOfMemoryError`                |

---

## Local Variables vs Instance Variables

**Local variables** — declared inside a method, stored on **Stack**, destroyed on method return.

**Instance variables** — declared inside a class, stored in **Heap** as part of the object, live as long as the object exists.

```java
class User {
    int age;                // instance variable → Heap
    
    void process() {
        int amount = 100;   // local variable → Stack
    }
}
```

---

## Primitive vs Reference Types

**Primitives** (`int`, `double`, `boolean`) store the **actual value** directly on the stack.

**Reference types** (`User`, `String`, arrays) store a **pointer** on the stack pointing to the heap object.

```java
User u1 = new User();
User u2 = u1;           // copies reference, not object
u2.name = "John";       // modifies same object — u1.name is also "John"
```

---

## Pass-by-Value in Java

**Java is always pass-by-value.**

- **Primitives**: value copied → changes don't affect caller
- **Objects**: reference copied → both point to same object, but reassigning the parameter doesn't affect caller

```java
void update(User user) {
    user.name = "John";     // ✅ modifies original object
    user = new User();      // ❌ only reassigns local copy
}
```

---

## Object Creation Lifecycle

When `new User("Umesh")` executes:

1. **Class Loading** — load class into Metaspace if not already loaded
2. **Memory Allocation** — allocate space in Heap
3. **Default Initialization** — fields set to defaults (`null`, `0`, `false`)
4. **Constructor Execution** — run constructor logic
5. **Reference Assignment** — reference stored in Stack frame

---

## Object Layout

Every Java object in memory has three parts:

```text
+------------------+
| Object Header    |   ← HashCode, Lock/monitor info, GC age, Class pointer
+------------------+
| Instance Data    |   ← Your declared fields
+------------------+
| Padding          |   ← For CPU memory alignment
+------------------+
```

---

## Object References, Null, and Destruction

**Reference** = address-like value pointing to a heap object. Stored on Stack (if local) or Heap (if field inside another object).

**Null**: `user = null` → no object behind it → `NullPointerException` on access.

**Destruction**: No manual `delete`. When unreachable from GC Roots → GC eligible. `finalize()` is deprecated.

---

## Heap Organization (Generational Model)

Based on the **Weak Generational Hypothesis**: most objects die young.

```text
Heap
├── Young Generation
│   ├── Eden          ← all new objects allocated here
│   ├── Survivor S0   ← survivors after Minor GC
│   └── Survivor S1   ← alternates with S0
└── Old Generation    ← long-lived promoted objects
```

### Eden Space

All new objects created in Eden. When full → **Minor GC**: dead objects removed, survivors copied to Survivor space with `age = 1`.

### Survivor Spaces (S0 & S1)

Two spaces for efficient copy-collection. After each Minor GC, live objects alternate between S0/S1, age incremented.

### Object Promotion

When `age >= threshold` (~15) → **promoted to Old Generation**. Old Gen: larger, less frequent collection, more expensive.

### Large Object Allocation

Very large objects (e.g., `new byte[50_000_000]`) may go **directly to Old Generation** (pretenuring) to avoid costly copying.

---

## Class Loading Process

When you write `new User()`, JVM must load the `User` class before creating the object. Class loading has three phases.

### Phase 1: Loading

JVM locates `User.class` and loads its bytecode. Class metadata goes into **Metaspace**.

### Phase 2: Linking

**Verification** — JVM validates the bytecode. No invalid instructions, no corrupted class file.

**Preparation** — Memory allocated for static variables with **default values only**:

```java
static int count = 10;
// At Preparation stage: count = 0 (default)
```

**Resolution** — Symbolic references resolved into actual memory references.

### Phase 3: Initialization

Static initializers execute. Static variables get **actual values**:

```java
static int count = 10;
// After Initialization: count = 10
```

---

## Class Loader Hierarchy

JVM uses a hierarchy with **Parent Delegation Model**.

```text
Bootstrap ClassLoader        → core Java (String, Object, ArrayList)
        ↓
Platform ClassLoader         → JDK modules (java.sql, java.xml)
        ↓
Application ClassLoader      → your classes (User, OrderService)
```

When loading `new User()`: Application asks Platform → Platform asks Bootstrap → Bootstrap can't find `User` → delegates back → Application loads it.

**Why delegation?** Security. You cannot replace `java.lang.String` with your own implementation.

---

## Runtime Constant Pool

Every loaded class has a **Runtime Constant Pool** in Metaspace — the runtime representation of compile-time constants.

Contains: string literals, method references, field references, class references, numeric constants.

---

## String Constant Pool

The String Pool stores **unique String literal objects** to avoid duplicates.

```java
String a = "hello";
String b = "hello";
```

Both point to the **same** pooled object:

```text
a ----\
       \
        ---> "hello"   (single object in pool)
       /
b ----/
```

```java
System.out.println(a == b);  // true — same pooled object
```

The String Pool moved from PermGen to the **main Heap** in Java 7.

---

## Metaspace vs PermGen

**Before Java 8**: class metadata lived in **PermGen** — fixed size, manual tuning:

```bash
-XX:MaxPermSize=256m
```

If exceeded: `OutOfMemoryError: PermGen space`.

**Java 8+**: replaced with **Metaspace** using native memory, dynamic growth. Less tuning needed.

| Aspect         | PermGen (≤ Java 7)         | Metaspace (Java 8+)       |
| -------------- | -------------------------- | ------------------------- |
| Location       | Inside JVM heap area       | Native (OS) memory        |
| Size           | Fixed, manually configured | Dynamic, auto-grows       |
| OOM Error      | `PermGen space`            | `Metaspace`               |
| Configuration  | `-XX:MaxPermSize`          | `-XX:MaxMetaspaceSize`    |

### Metaspace OOM

Still possible. Heavy dynamic class generation (Spring AOP, CGLIB, ByteBuddy, Hibernate proxies) can load thousands of classes. If never unloaded:

```java
java.lang.OutOfMemoryError: Metaspace
```

---

## String Pool Interning

String **literals** are automatically interned:

```java
String a = "hello";   // interned automatically
String b = "hello";   // returns same pooled object
```

For heap-created strings, **explicitly intern**:

```java
String a = new String("hello");
String b = a.intern();            // returns the pooled "hello"

System.out.println(b == "hello"); // true — both point to pool
```

---

## String Literal vs `new String()`

### Literal

```java
String a = "hello";
```

One object in the String Pool. `a` references the pooled object.

### `new String()`

```java
String b = new String("hello");
```

**Two objects**: `"hello"` in pool (may already exist) + a new String on Heap.

```java
String a = "hello";
String b = new String("hello");

System.out.println(a == b);       // false — different objects
System.out.println(a.equals(b));  // true  — same content
```

> 💡 **Interview**: `==` compares references. `equals()` compares content.

---

## StringBuilder Memory Behavior

Strings are **immutable**. Every concatenation creates a new object:

```java
String s = "A";
s = s + "B";   // creates new "AB", old "A" becomes garbage
s = s + "C";   // creates new "ABC", old "AB" becomes garbage
```

**StringBuilder** uses a single mutable `char[]` buffer:

```java
StringBuilder sb = new StringBuilder();
sb.append("A").append("B").append("C");
String result = sb.toString();  // "ABC"
```

One buffer, one final String. Much less GC pressure.

---

## String Concatenation Internals

**Java 8**: compiler converts `a + b` into `new StringBuilder().append(a).append(b).toString()`.

**Compile-time constant folding**: `"Hello" + "World"` → `"HelloWorld"` at compile time.

**Java 9+**: `invokedynamic` + `StringConcatFactory` for more efficient runtime concatenation.

---

## Why Strings Are Immutable

One of the most common Java interview questions.

### 1. String Pool Would Break

Both `a` and `b` point to the same pooled `"hello"`. If mutable, modifying through `a` would silently change what `b` sees.

### 2. Security

Java uses Strings for passwords, file paths, URLs, class names. Mutable strings would allow changing paths after validation but before use.

### 3. Thread Safety

Immutable String can be read by 100 threads simultaneously without synchronization.

### 4. HashMap Key Safety

If key string mutated after insertion, the hash changes, entry is in wrong bucket, lookups fail silently.

### 5. Hash Code Caching

String caches `hashCode` in `private int hash`. Only safe because value never changes.

> 💡 **Interview**: Strings are immutable to enable String Pooling, improve security, ensure thread safety, allow hashCode caching, and support JVM optimizations.

## Memory Errors — Detailed

### Heap OutOfMemoryError

JVM cannot allocate memory for a new object because the heap is exhausted.

```java
List<Object> list = new ArrayList<>();
while (true) { list.add(new Object()); }
// → java.lang.OutOfMemoryError: Java heap space
```

**Common causes:** memory leak (static collection), huge cache (millions of entries), large file read (`Files.readAllBytes`).

### StackOverflowError

Thread stack exhausted — too many frames (usually infinite recursion).

### GC Overhead Limit Exceeded

GC runs **continuously** but recovers **almost no memory**. Heap ~99.9% full, GC frees tiny fraction, fills immediately, repeats.

### Direct Buffer Memory OOM

Off-heap `ByteBuffer.allocateDirect()` exhausted. Common in Kafka, Netty, NIO.

### Metaspace OOM

Dynamic proxy generation (Spring AOP, CGLIB, ByteBuddy, Hibernate) or class loader leaks.

## Reference Types — Detailed

### Strong References

Default reference. As long as a strong reference chain exists from a GC Root, GC **cannot** collect.

```java
User user = new User();
System.gc();   // object survives — strong reference exists
```

### Soft References

`SoftReference<T>`: JVM keeps object alive while memory is sufficient. Under pressure, GC reclaims it.

```java
SoftReference<Image> ref = new SoftReference<>(loadImage());
Image img = ref.get();   // may return null if GC reclaimed
```

**Use case**: memory-sensitive caches. **Rarely used today** — prefer Caffeine/Redis for deterministic eviction.

### Weak References

`WeakReference<T>`: collected at **next GC cycle** regardless of memory.

```java
WeakReference<User> ref = new WeakReference<>(new User());
System.gc();
ref.get();   // likely null
```

**Use case**: metadata caches, reflection caches.

### Phantom References

`PhantomReference<T>` + `ReferenceQueue<T>`: `ref.get()` **always** returns `null`. Purpose: notification **before memory reclamation completes** — used for native resource cleanup.

---

## WeakHashMap — Detailed

In normal `HashMap`, the map holds a **strong reference** to keys. Even after `key = null` externally, the key survives — potential leak.

`WeakHashMap` stores keys using **weak references**:

```java
Map<Key, Value> map = new WeakHashMap<>();
Key key = new Key();
map.put(key, "data");

key = null;      // no more strong references
System.gc();     // key collected → entry auto-removed
```

**Use cases:** metadata caches, reflection caches, ClassLoader-sensitive caches (Tomcat, Jetty), Spring internals.

---

## GC & Strong References in Spring Boot

GC determines collectibility by **reachability from GC Roots**, not by reference type alone.

### Local Variables in Methods

```java
public void process() {
    Map<String, User> map = new HashMap<>();
    map.put("1", new User());
}
// method returns → frame removed → map + users unreachable → GC collects
```

### API Request Processing

```java
@GetMapping("/users")
public UserResponse getUsers() {
    List<User> users = repository.findAll();
    return convert(users);
}
// request ends → Tomcat thread frame destroyed → GC eligible
```

This is why Spring Boot handles millions of requests without memory growing.

### Singleton Bean Cache (Intentional Retention)

```java
@Service
public class UserCache {
    private Map<Long, User> cache = new HashMap<>();
}
```

Path: `GC Root → ApplicationContext → UserCache → HashMap → Users`. Reachable for app lifetime — not a leak, intentional retention.

### Actual Memory Leak

```java
private static final List<User> users = new ArrayList<>();
public void process(User user) { users.add(user); }  // grows forever → OOM
```

> 💡 **Interview**: HashMap ≠ memory leak. Local HashMaps are fine. Problems occur only when long-lived structures (static fields, singleton caches) hold references indefinitely.

---

## Reachability Analysis

Java does **not** use reference counting. Instead it asks: "Can I reach this object from a GC Root?"

This handles circular references correctly:

```java
A a = new A();
B b = new B();
a.b = b;
b.a = a;
a = null;
b = null;
// A ↔ B reference each other, but unreachable from GC Roots → both collected
```

---

## GC Roots

GC starts traversal from special "known live" starting points:

1. **Thread stack variables** — local variables in active methods
2. **Static variables** — `static User user = new User()`
3. **Active threads** — running threads themselves
4. **JNI references** — native code references

```text
GC Root → User → Order    // both survive
GC Root    (no path)       // both collected
```

---

## Minor GC

Most frequent GC, works on **Young Generation only**.

```text
Before:  Eden [A B C D E]     (A,C,E dead | B,D alive)
After:   S0 [B(age=1) D(age=1)]
```

Fast because most objects die young.

---

## Major GC

Works on **Old Generation**. Less frequent, more expensive — must inspect large object graphs (caches, singletons, long-lived objects).

---

## Full GC

Most expensive. Scans entire heap (Young + Old + sometimes Metaspace).

Triggers: Old Gen full, `System.gc()`, metadata pressure.

```text
Full GC (Allocation Failure)
```

Avoid in production.

---

## Stop-The-World (STW)

GC pauses **all application threads** for safe memory management. Threads must be at safepoints before pausing.

- 50ms pause → users won't notice
- 10s pause → production outage

Why pause? GC needs consistent object graph — mutations during scan would cause inconsistency.

---

## G1 GC (Garbage First)

Default collector in modern JVMs. Divides heap into many small **regions** instead of contiguous Young/Old.

```text
[R][R][R][R][R]
[R][R][R][R][R]    ← each R = Eden/Survivor/Old region
[R][R][R][R][R]
```

Tracks garbage % per region → cleans most-garbage regions first ("Garbage First").

```bash
-XX:MaxGCPauseMillis=200    # target pause time (not guaranteed)
```

Good for 2GB–32GB heaps. Balances throughput, latency, and memory usage.

---

## ZGC

Ultra-low latency collector for **huge heaps** (128GB–1TB).

- Pauses: < 1ms to a few ms
- Most work happens concurrently
- Use cases: trading systems, databases, massive backends

---

## Shenandoah

Red Hat collector. Similar philosophy to ZGC: low pause, concurrent work, pause time independent of heap size.

---

## GC Tuning Basics

```bash
-Xms2g -Xmx2g              # heap size (initial & max)
-Xlog:gc*                   # GC logging
-XX:MaxGCPauseMillis=200    # G1 pause goal
-XX:MaxMetaspaceSize=512m   # Metaspace limit
```

Monitor: GC frequency, pause time, heap utilization, Old Gen growth.

---

## The Entire GC Flow

```text
new User()
    ↓
Eden
    ↓ Minor GC (survives)
S0 (age=1)
    ↓ Minor GC
S1 (age=2)
    ↓ ... many GCs
Old Generation
    ↓ user = null (unreachable)
Reachability Analysis → no path from GC Root
    ↓
GC Reclaims Memory
```

## Off-Heap Memory: Direct ByteBuffer

Normally objects go to Heap. But Java can allocate memory outside the heap:

```java
ByteBuffer buffer = ByteBuffer.allocateDirect(1024);
```

This memory comes from **native memory**, not Java Heap.

### Why?

Without DirectBuffer (extra copy):
```text
Disk → OS Buffer → Heap Buffer → Application
```

With DirectBuffer (less copying):
```text
Disk → OS Buffer → Direct Buffer → Application
```

**Used by**: Kafka, Netty, NIO, gRPC, database drivers — anywhere high-throughput I/O matters.

### Memory layout

```text
Heap:          DirectByteBuffer object (small wrapper, few bytes)
                    ↓
Native Memory: actual 1024 bytes of data
```

---

## Native Memory (Beyond Heap)

A Java process consumes much more than just heap:

```text
Heap         4 GB
Metaspace    500 MB
Stacks       300 MB       ← ~1MB per thread × thread count
DirectBuf    1 GB
─────────────────────
Total        5.8 GB       ← -Xmx4g does NOT mean 4GB process
```

> 💡 **Interview**: Can JVM OOM even when heap has free space? → Yes, native memory can be exhausted independently.

---

## Off-Heap vs Heap

| Heap              | Off-Heap              |
| ----------------- | --------------------- |
| Managed by GC     | Outside GC            |
| Easier to use     | More complex          |
| Object allocation | Buffers / native data |
| GC overhead       | Less GC pressure      |
| Subject to `-Xmx` | Not subject to `-Xmx` |

---

## Why Kafka & Netty Use Off-Heap

### Problem: GC Nightmare

1000 clients × 10MB each = 10GB+ of heap objects. GC must scan all of them → long pauses.

### Kafka

Uses NIO ByteBuffers for producer/consumer buffers. Data flows `Network → DirectBuffer → Disk` with less copying. Also uses **zero-copy** (`sendfile`): `Disk → Kernel Buffer → Socket` — no heap involvement at all.

### Netty

Handles millions of connections. 100K connections × 64KB buffer = 6.4GB. Instead of heap buffers, uses `PooledDirectByteBuffer` — GC only sees small wrapper objects.

### Tradeoffs

- ✅ Less GC pressure, better I/O, larger buffers possible
- ❌ Harder memory management (native memory leaks possible)
- ❌ Harder debugging (`jmap` doesn't help — need `jcmd VM.native_memory`)

---

## Who Frees Off-Heap Memory?

The **OS does NOT garbage collect** off-heap allocations. The JVM handles it:

```text
allocateDirect()
    ↓
Native Memory Allocated
    ↓
Wrapper Object Created (in Heap)
    ↓
Wrapper Becomes Unreachable
    ↓
GC Detects Wrapper Dead
    ↓
Cleaner Runs (since Java 9, replaces finalize)
    ↓
Native Memory Released (conceptually: free(nativeAddress))
```

### Direct Buffer OOM

If you allocate native memory faster than GC cleans wrappers:

```java
while(true) {
    ByteBuffer.allocateDirect(100_000_000);  // rapid allocation
}
```

Result: `OutOfMemoryError: Direct buffer memory` even though heap looks fine.

### OS Reclaims When?

Only when entire Java process dies — OS reclaims all process memory (heap, metaspace, direct buffers, stacks).

### OS-Dependent?

JVM abstracts OS differences. Linux: `malloc()`/`mmap()`. Windows: `VirtualAlloc()`. From Java code, `ByteBuffer.allocateDirect()` works the same everywhere.

## Monitoring & Troubleshooting

### Heap Dump

Snapshot of all heap objects and references at a specific moment. Used for memory leak analysis and OOM debugging.

```bash
jmap -dump:live,file=heap.hprof <pid>
# or
jcmd <pid> GC.heap_dump heap.hprof
```

### Thread Dump

Snapshot of all JVM threads — shows running, blocked, waiting threads, locks, and stack traces. Used for deadlocks, high CPU, hung applications.

```bash
jstack <pid>
# or
jcmd <pid> Thread.print
```

> Heap Dump = Memory Analysis | Thread Dump = Thread Analysis

### jmap

Memory analysis tool:
```bash
jmap -heap <pid>                           # heap info
jmap -dump:live,file=heap.hprof <pid>      # heap dump
```

### jstack

Thread dump tool:
```bash
jstack <pid>     # all thread stack traces
```

Useful for deadlocks, blocked threads, high CPU.

### jstat

GC statistics without creating dumps:
```bash
jstat -gc <pid>
```

Shows Eden usage, Old Gen usage, GC count (`YGC`, `FGC`), GC time.

### jcmd

Modern JVM Swiss Army Knife (Oracle-recommended):
```bash
jcmd <pid> GC.heap_info       # heap info
jcmd <pid> Thread.print       # thread dump
jcmd <pid> GC.heap_dump f.hprof  # heap dump
jcmd <pid> VM.native_memory   # native memory tracking
```

### VisualVM

GUI tool for CPU usage, memory usage, threads, heap dumps, profiling — useful for local debugging without command line.

### Eclipse MAT (Memory Analyzer Tool)

Most important heap dump analysis tool. Opens `.hprof` files and answers: What's consuming memory? Where's the leak?

**Key features:**
- **Dominator Tree** — shows largest memory retainers
- **Retained Heap** — "if I remove this object, how much memory freed?"

**Real production flow:**
```text
OutOfMemoryError → Generate Heap Dump → Open in MAT → Check Dominator Tree → Find Largest Retained Objects → Identify Leak
```

## Memory Leaks in Java

Java has GC, but leaks still happen when objects remain **reachable** but are no longer needed:

```java
static List<User> users = new ArrayList<>();    // grows forever
ThreadLocal not cleared in thread pools
ExecutorService not shut down
Cache without eviction policy
Listener not deregistered
```

---

## ThreadLocal Memory Leak

Extremely common interview question:

```java
private static final ThreadLocal<User> ctx = new ThreadLocal<>();
```

In thread pools (Spring Boot, Tomcat):

```text
Thread survives (reused by pool)
    ↓
ThreadLocal value survives
    ↓
Memory leak
```

Always call `ctx.remove()` in a `finally` block.

---

## Escape Analysis

JIT compiler optimization. If an object **never escapes** the method scope:

```java
public int sum() {
    User u = new User();    // never returned or stored elsewhere
    return u.getAge();
}
```

JIT may: skip heap allocation entirely, allocate on stack, or eliminate the object.

---

## TLAB (Thread Local Allocation Buffer)

If many threads create objects simultaneously, do they all lock the heap? **No.**

Each thread gets a **TLAB** — a small slice of Eden. Most allocations happen inside the thread's TLAB without any locking.

```text
new Object()
    ↓
TLAB available? → yes → Allocate (no lock, very cheap)
```

---

## Safepoints

How does JVM stop all threads for GC (STW)?

Threads can only be paused at **safepoints** — specific points in code:
- Method calls
- Loop back edges
- Exception paths

JVM sets a flag → each thread checks at its next safepoint → stops.

---

## Generational Hypothesis

Formal statement:

> Most objects die young. Few objects live long.

The entire GC design (Young Gen, Old Gen, Minor GC, promotion) is built around this observation.

---

## Card Tables / Remembered Sets (G1 Level)

**Problem**: Old Gen object references a Young Gen object. How does Minor GC (which only scans Young Gen) know about this?

**Solution**: Card tables / remembered sets track cross-generation references so Minor GC doesn't miss them.
