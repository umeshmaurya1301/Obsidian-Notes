Fetching answers one question:

> **When should Hibernate load related objects from the database?**

Get it wrong and you either load the whole database into memory, or you fire 500 queries for one page. This is the second most important topic after transactions.

> [!info] Where this fits
> You know how relationships are mapped ([[7. Relationships]]). Now: *when* does Hibernate actually go and get the other side?

> [!info] The through-line of this note
> Two choices, one famous bug, three fixes, one exception.
>
> 1. **EAGER or LAZY** (§2–§3) — but they are not symmetric options. An EAGER mapping fires on *every* query of that entity forever and **cannot be turned off per query**; a LAZY mapping can always be **upgraded** per query. That asymmetry is the whole argument for LAZY as the default.
> 2. LAZY works by handing you a **proxy** (§4) instead of the data — a runtime subclass for entities, a wrapper collection for `@OneToMany`. This is the same mechanism behind two rules you already met: entities can't be `final`, and `getId()` doesn't hit the database.
> 3. Touch that proxy inside a loop and you get **N+1** (§5) — and the crucial correction: **EAGER doesn't fix it, it guarantees it earlier.** The fix isn't *when* you load, it's *how* — you need a **join**.
> 4. Three fixes, each right in different circumstances: **`JOIN FETCH`** (§6), **`@EntityGraph`** (§7), **`@BatchSize`** (§8).
> 5. Touch the proxy after the session closed instead, and you get **`LazyInitializationException`** (§10) — whose correct fix is neither EAGER nor OSIV.
>
> One line to anchor everything: **map everything LAZY, then fetch eagerly per query when you know you need it.**

## Short Notes

---

### 1. What Is Fetching?

```text
Merchant → Transactions → Refunds → Settlements
```

You load a Merchant. Should Transactions also load? Refunds? Settlements?

- That decision is **fetching**, and there are exactly two answers: **LAZY** and **EAGER**

---

### 2. EAGER Fetching

```java
@ManyToOne(fetch = FetchType.EAGER)
private Merchant merchant;
```

```java
Transaction txn = repository.findById(101L).get();
// → SELECT Transaction
// → SELECT Merchant        …even if you never touch it
```

- Eager associations **compound**: Transaction → Merchant → BankAccount → Address = one `findById` becomes four queries

> ⭐ **EAGER is a global decision made at mapping time.** It loads on **every** query of that entity, in every use case, forever. You **cannot turn it off per query** — but you *can* turn LAZY on per query. That asymmetry is why LAZY is the correct default and EAGER is a trap

---

### 3. LAZY Fetching

```java
@OneToMany(mappedBy = "merchant", fetch = FetchType.LAZY)
private List<Transaction> transactions;
```

```java
Merchant merchant = repository.findById(1L).get();   // loads Merchant only
merchant.getTransactions();                          // NOW: SELECT ... WHERE merchant_id = 1
```

- **LAZY = "load later"**
- Why it matters: `Merchant → 50,000 Transactions → each with Refunds and Ledger Entries` — loading that immediately is catastrophic

---

### 4. Proxy Objects

If the data isn't loaded, what's in the field? A **proxy**.

| Kind | What it is | Triggered by |
|---|---|---|
| **Collection proxy** | `PersistentBag` / `PersistentSet` replaces your `ArrayList` | `size()`, `iterator()`, `get()` |
| **Entity proxy** | A runtime-generated **subclass** of your entity | any getter except the id |

```java
Merchant m = txn.getMerchant();   // proxy — no SQL yet
m.getId();                        // still no SQL! the id is already known
m.getName();                      // NOW the SELECT fires
```

- ⭐ **The proxy is a subclass** — which is exactly why entities and their getters must not be `final`, or lazy loading silently breaks ([[6. Entity Mapping]] §1)
- Inspect without triggering: `Hibernate.isInitialized(...)` · force load: `Hibernate.initialize(...)`

---

### 5. The N+1 Problem ⭐

```java
List<Merchant> merchants = repo.findAll();     // 1 query
for (Merchant m : merchants) m.getTransactions();   // N queries
```

```text
SELECT merchants                     (1)
SELECT transactions of Acme          (1)
SELECT transactions of Bharat Foods  (1)
SELECT transactions of Chennai Cabs  (1)
                                  = 1 + N
```

- Invisible with 3 merchants. With **500 on a dashboard it's 501 queries**, and p99 goes 40 ms → 6 seconds

> 🚨 **EAGER does not fix N+1 — it guarantees it.** Marking it EAGER just fires the N queries *during* `findAll()` instead of later in the loop. **Same count.** The fix is not *when* you load, it's *how* — you need a **join**

- ⚠️ It happens with `@ManyToOne` too — every `t.getMerchant().getName()` in a loop is its own SELECT

---

### 6. Fix 1 — Fetch Join

```java
@Query("SELECT m FROM Merchant m JOIN FETCH m.transactions WHERE m.status = :status")
List<Merchant> findAllWithTransactions(@Param("status") Status status);
```

- ⚠️ **Plain `JOIN` filters but leaves the association lazy.** Only **`JOIN FETCH`** populates it and cures N+1

**Three gotchas:**

| Gotcha | Detail |
|---|---|
| **Duplicates** | 3 merchants × 4 transactions = 12 rows → the same 3 objects repeated. Use `DISTINCT` (de-duplicates **in memory**; automatic in Hibernate 6) |
| **Pagination breaks** | `HHH000104: firstResult/maxResults specified with collection fetch; applying in memory` — Hibernate loads the **entire** result set and paginates in RAM. OOM risk |
| **One collection only** | Two `JOIN FETCH`es on two collections = cartesian product (`MultipleBagFetchException` for `List`s) |

---

### 7. Fix 2 — `@EntityGraph`

Declarative instead of JPQL — and it works on **derived query methods**, so you keep Spring Data's generated queries and only change the fetch plan:

```java
@EntityGraph(attributePaths = {"transactions"})
List<Merchant> findAll();

@EntityGraph(attributePaths = {"transactions", "transactions.refunds"})   // nested
```

Named graph on the entity:

```java
@NamedEntityGraph(name = "Merchant.withTransactions",
                  attributeNodes = @NamedAttributeNode("transactions"))
```

- ⚠️ Produces a `LEFT JOIN FETCH` under the hood — **the same pagination caveat applies**

---

### 8. Fix 3 — Batch Fetching

Don't eliminate the extra queries — **collapse** them.

```java
@OneToMany(mappedBy = "merchant")
@BatchSize(size = 50)
private List<Transaction> transactions;
```

```sql
SELECT * FROM transaction WHERE merchant_id IN (1,2,3,...,50);
```

```text
Before:  1 + 500 queries
After:   1 + 10  queries
```

- Globally: `spring.jpa.properties.hibernate.default_batch_fetch_size: 50`

> **When to use which**
> - **`JOIN FETCH`** — you know exactly what you need, no pagination. Fastest
> - **`@EntityGraph`** — same thing, declarative, keeps derived queries
> - **`@BatchSize`** — pagination involved, multiple collections, or a global safety net. **Nearly free insurance**

---

### 9. Default Fetch Types — must remember

| Relationship | Default |
|---|---|
| `@ManyToOne` | **EAGER** |
| `@OneToOne` | **EAGER** |
| `@OneToMany` | LAZY |
| `@ManyToMany` | LAZY |

```java
@ManyToOne(fetch = FetchType.LAZY)     // override the bad default
@JoinColumn(name = "merchant_id")
private Merchant merchant;
```

- **Prefer `LAZY` wherever practical**, and fetch explicitly when you know you need it

---

### 10. `LazyInitializationException` ⭐

```java
Merchant m = repository.findById(1L).get();
session.close();          // or: the @Transactional method returned
m.getTransactions();      // 💥 could not initialize proxy - no Session
```

```text
┌─────────────────────────┐
│ findById() → Merchant   │   proxy created, session alive
└─────────────────────────┘
        session closed
              ↓
   getTransactions()  →  no session  →  💥
```

- **Where it bites in Spring**: the entity is loaded in a `@Transactional` service, returned to the controller, and **Jackson serialises it** — touching every getter *after* the transaction closed

**Fixes, best to worst:**

| # | Fix | Verdict |
|---|---|---|
| 1 | `JOIN FETCH` / `@EntityGraph` in the query | ✅ Explicit and efficient |
| 2 | **Map to a DTO inside the transaction** | ✅ The right architectural answer — never let entities escape the service layer |
| 3 | `Hibernate.initialize(...)` | ⚠️ Works, but it's N+1 by hand |
| 4 | **Open Session In View** | ❌ Hides N+1 in serialisation and holds a DB connection for the whole response |
| 5 | Make everything EAGER | ❌ Trades one exception for a permanent app-wide performance problem |

- Spring Boot enables OSIV **by default** and warns in the logs → set `spring.jpa.open-in-view: false`

# Detailed Explanation

---

## What Is Fetching?

Suppose:

```text
Merchant
   ↓
Transactions
   ↓
Refunds
   ↓
Settlements
```

You load a Merchant.

Should Transactions also be loaded? Should Refunds? Should Settlements?

This is what Fetching decides. Two types:

```text
LAZY
EAGER
```

Note that this question has no universally correct answer — it depends on what the *caller* is about to do. That's the tension that runs through the whole note: fetching is a **per-use-case** decision, but `FetchType` is declared **once, on the mapping**.

---

## EAGER Fetching

Load everything immediately.

```java
@ManyToOne(fetch = FetchType.EAGER)
private Merchant merchant;
```

Suppose:

```java
Transaction txn = repository.findById(101L).get();
```

Hibernate executes:

```text
SELECT Transaction
      ↓
SELECT Merchant
```

Even if you never use the Merchant.

Everything comes immediately:

```text
Transaction
    ↓
Merchant
    ↓
BankAccount
    ↓
Address
```

Everything loaded — one `findById` becomes four queries (or one giant join).

> [!warning] EAGER is a global decision made at mapping time
> An `EAGER` association is loaded on **every** query of that entity, in every use case, forever. You cannot turn it off per-query — but you *can* turn LAZY on per-query. That asymmetry is why LAZY is the correct default and EAGER is a trap.

Sit with that asymmetry, because it settles the whole debate. The two options are not mirror images:

```text
Mapped EAGER  →  every query pays, no query can opt out
Mapped LAZY   →  no query pays, any query can opt in (JOIN FETCH / @EntityGraph)
```

A mistake in the LAZY direction is recoverable per call site. A mistake in the EAGER direction requires changing the mapping — and thereby every other use case.

---

## LAZY Fetching

Load only what is needed.

```java
@OneToMany(mappedBy = "merchant", fetch = FetchType.LAZY)
private List<Transaction> transactions;
```

Now:

```java
Merchant merchant = repository.findById(1L).get();
```

Hibernate loads:

```text
Merchant
```

only. Transactions? Not yet.

Later:

```java
merchant.getTransactions();
```

Now Hibernate executes:

```sql
SELECT * FROM transaction WHERE merchant_id = 1
```

Lazy means:

```text
Load Later
```

### Why lazy?

Suppose:

```text
Merchant
   ↓
50,000 Transactions
   ↓
Each Transaction → Refunds, Ledger Entries
   ↓
Settlements
```

Loading everything immediately would be catastrophic. Lazy loads only what you actually access.

---

## Proxy Objects

If Transactions are not loaded, what does Hibernate keep in the field?

A **Proxy**.

```text
Merchant
    ↓
Transactions Proxy
```

The proxy knows:

> "If someone accesses me, I'll load the real data."

Two flavours:

**Collection proxy** — `PersistentBag` / `PersistentSet` replaces your `ArrayList`. Calling `size()`, `iterator()` or `get()` triggers the SELECT.

**Entity proxy** — for `@ManyToOne(fetch = LAZY)`, Hibernate generates a **subclass** of your entity at runtime. Every getter is overridden to first initialise, then delegate.

```java
Merchant m = txn.getMerchant();   // proxy — no SQL yet
m.getId();                        // still no SQL! id is already known
m.getName();                      // NOW the SELECT fires
```

The `getId()` case is a favourite interview question and worth understanding rather than memorising: the proxy was *created from* the foreign key value, so the id is the one thing it already knows. Everything else requires the row.

That's also a real optimisation — `txn.getMerchant().getId()` never touches the database, so you can build a response containing merchant ids without loading a single merchant.

> [!tip] Why proxies need a non-final class
> The proxy is a **subclass**. That's why entities must not be `final` and why getters must not be `final` — otherwise the proxy can't override them and lazy loading silently breaks.

Check initialisation without triggering it:

```java
Hibernate.isInitialized(merchant.getTransactions());
Hibernate.initialize(merchant.getTransactions());   // force load
```

---

## The N+1 Problem

One of the most common interview questions.

Suppose you fetch all merchants.

```sql
SELECT * FROM merchant;
```

Result:

```text
Acme Retail
Bharat Foods
Chennai Cabs
```

Three merchants. Later:

```java
for (Merchant m : merchants) {
    m.getTransactions();
}
```

Hibernate executes:

```text
SELECT Merchants                       (1 query)
      ↓
SELECT Transactions of Acme            (1)
      ↓
SELECT Transactions of Bharat Foods    (1)
      ↓
SELECT Transactions of Chennai Cabs    (1)
```

Total:

```text
1 + N queries
```

Hence: **N+1 Problem**.

With 3 merchants it's invisible. With 500 merchants on a dashboard it's 501 queries, and your p99 goes from 40 ms to 6 seconds.

Note *why* it survives to production: it scales with **data volume**, not with code paths. It passes review, passes tests against a seeded database of five rows, and degrades gradually as real data arrives — so by the time it's a problem, nobody associates it with the change that introduced it.

> [!warning] EAGER does not fix N+1 — it guarantees it
> A common misconception. Marking the association EAGER just means the N extra queries fire *during* `findAll()` instead of later in the loop. Same count. The fix is not *when* you load, it's *how* — you need a **join**.

### It happens with `@ManyToOne` too

```java
List<Transaction> txns = txnRepository.findAll();   // 1 query
for (Transaction t : txns) {
    t.getMerchant().getName();                       // N queries
}
```

Every `Transaction` row with a distinct `merchant_id` triggers its own SELECT. This direction is the one people forget, because they associate N+1 with collections — but it's arguably worse here, since `@ManyToOne` is EAGER by default and so it happens without anyone writing a loop at all.

---

## Fix 1 — Fetch Join

Instead of multiple queries, write one:

```java
@Query("""
    SELECT m
    FROM Merchant m
    JOIN FETCH m.transactions
    WHERE m.status = :status
    """)
List<Merchant> findAllWithTransactions(@Param("status") Status status);
```

Hibernate executes a **single JOIN query**. Everything comes together.

> [!note] `JOIN` vs `JOIN FETCH`
> Plain `JOIN` filters — the association is still lazy afterwards. `JOIN FETCH` filters **and** populates the association. Only `JOIN FETCH` cures N+1.
>
> This catches people out precisely because the plain `JOIN` version *works* — it returns the right merchants. It just leaves you with the same N+1 the moment you touch the collection.

### Three gotchas

**Duplicates.** A join multiplies parent rows by child rows. Three merchants with 4 transactions each returns 12 rows → 12 `Merchant` references (the same 3 objects repeated).

```java
SELECT DISTINCT m FROM Merchant m JOIN FETCH m.transactions
```

`DISTINCT` here de-duplicates in **memory**, not in SQL (Hibernate 6 does this automatically).

**Pagination breaks.** `JOIN FETCH` + `setMaxResults()` produces:

```text
HHH000104: firstResult/maxResults specified with collection fetch; applying in memory
```

Hibernate loads **the entire result set** into memory and paginates there. On a large table this is an OOM waiting to happen.

The reason is unavoidable rather than a Hibernate limitation: after the join, one merchant occupies several rows, so a SQL `LIMIT 10` would slice a merchant's transactions in half and hand you a half-loaded entity. Hibernate refuses to do that, so it loads everything and paginates the *objects*. Fix: fetch ids with a paged query, then fetch entities by those ids — or use `@BatchSize` instead.

**You can only fetch one collection.** Two `JOIN FETCH`es on two collections gives a cartesian product (`MultipleBagFetchException` for `List`s). Use `Set`, or two queries, or `@BatchSize`.

---

## Fix 2 — `@EntityGraph`

Instead of writing JPQL, tell Hibernate declaratively:

```text
When fetching Merchant, also fetch Transactions.
```

```java
@EntityGraph(attributePaths = {"transactions"})
List<Merchant> findAll();
```

Cleaner for many use cases — and it works on **derived query methods**, so you keep Spring Data's generated queries and just change the fetch plan. That's its real advantage over `JOIN FETCH`: you don't have to abandon `findByStatusAndCreatedAtAfter(...)` and hand-write JPQL just to change how much it loads.

Nested paths work too:

```java
@EntityGraph(attributePaths = {"transactions", "transactions.refunds"})
```

Named graph on the entity:

```java
@Entity
@NamedEntityGraph(
    name = "Merchant.withTransactions",
    attributeNodes = @NamedAttributeNode("transactions"))
public class Merchant { }
```

```java
@EntityGraph("Merchant.withTransactions")
Optional<Merchant> findById(Long id);
```

An entity graph produces a `LEFT JOIN FETCH` under the hood — so the same pagination caveat applies. It is a different *syntax*, not a different *mechanism*.

---

## Fix 3 — Batch Fetching

Instead of eliminating the extra queries, **collapse them**.

```java
@Entity
public class Merchant {

    @OneToMany(mappedBy = "merchant")
    @BatchSize(size = 50)
    private List<Transaction> transactions;
}
```

Now when the loop touches the first merchant's transactions, Hibernate loads **50 merchants' transactions at once**:

```sql
SELECT * FROM transaction WHERE merchant_id IN (1,2,3,...,50);
```

```text
Before:  1 + 500 queries
After:   1 + 10  queries
```

Or globally:

```yaml
spring.jpa.properties.hibernate.default_batch_fetch_size: 50
```

The conceptual difference from the other two fixes: `JOIN FETCH` and `@EntityGraph` **prevent** the extra queries, while `@BatchSize` **accepts** them and makes them cheap. That's why it survives pagination — it never joins, so there's no row multiplication to confuse `LIMIT`.

> [!tip] When to use which
> - **`JOIN FETCH`** — you know exactly what you need, no pagination. Fastest.
> - **`@EntityGraph`** — same thing but declarative, keeps derived queries.
> - **`@BatchSize` / `default_batch_fetch_size`** — pagination involved, multiple collections, or you want a safety net across the whole app. Set it globally; it's nearly free insurance.

The global setting deserves emphasis: it costs nothing when unused, and it silently converts the worst N+1s you haven't found yet into something an order of magnitude cheaper. It's the highest value-per-character line in a Spring Boot `application.yml`.

| Relationship | Default |
|---|---|
| `@ManyToOne` | **EAGER** |
| `@OneToOne` | **EAGER** |
| `@OneToMany` | LAZY |
| `@ManyToMany` | LAZY |

A common recommendation in production systems is to **prefer `LAZY` wherever practical**, especially for large object graphs, and explicitly fetch related data only when you know you'll need it.


## `LazyInitializationException`

Another classic interview question.

```java
Merchant m = repository.findById(1L).get();

session.close();          // or: the @Transactional method returned

m.getTransactions();      // 💥
```

Hibernate throws:

```text
LazyInitializationException: could not initialize proxy - no Session
```

**Why?**

Because the Transactions were never loaded, and the Session (Persistence Context) has already been closed. Without an active Session, Hibernate cannot execute the additional SQL required to load them.

```text
Transaction boundary
┌─────────────────────────┐
│ findById() → Merchant   │   proxy created, session alive
└─────────────────────────┘
        session closed
              ↓
   getTransactions()  →  no session  →  💥
```

Read that as the intersection of two facts you already know: proxies need a session to initialise (§4), and the persistence context is transaction-scoped ([[5. Persistence Context]] §3). The exception isn't a new concept — it's what happens when those two meet.

### Where it bites in Spring

The entity is loaded in a `@Transactional` service method, returned to the controller, and Jackson serialises it — touching every getter, including the lazy ones, *after* the transaction closed.

This is why it so often appears to be "a Jackson problem" or "a controller problem": the stack trace points at serialisation, but the mistake was letting a managed entity outlive its transaction.

### Fixes — from best to worst

**1. Fetch what you need, in the query.** `JOIN FETCH` or `@EntityGraph`. Explicit and efficient.

**2. Map to a DTO inside the transaction.** The right architectural answer — never let entities escape the service layer.

```java
@Transactional(readOnly = true)
public MerchantDto get(Long id) {
    Merchant m = repo.findByIdWithTransactions(id);
    return MerchantDto.from(m);          // touched while the session is open
}
```

This fix is worth more than it looks. It doesn't just prevent the exception — it makes the exception *impossible*, because nothing lazy ever crosses the boundary. It also decouples your API contract from your schema, so a mapping change stops being a breaking API change.

**3. `Hibernate.initialize(...)`** inside the transaction. Works, but it's the N+1 problem by hand.

**4. Enable Open Session In View.** It "fixes" the exception by keeping the session open for the whole HTTP request — and quietly reintroduces N+1 queries during JSON serialisation while holding a DB connection for the entire response. Spring Boot enables it **by default** and warns about it in the logs. Turn it off:

```yaml
spring.jpa.open-in-view: false
```

Full discussion in [[14. Performance Tuning]].

**5. Making everything EAGER.** The bad solution — it trades one exception for a permanent performance problem across the whole application.

Notice that fixes 4 and 5 are both attempts to make the *symptom* go away, and both do so by making every request slower forever. Fixes 1 and 2 address the actual mistake: not deciding what you needed before the transaction ended.

> 💡 **Interview**: why does `LazyInitializationException` happen, and how do you fix it? → A proxy was touched after the persistence context closed — usually during JSON serialisation in the controller. Fix it by fetching what you need in the query (`JOIN FETCH`/`@EntityGraph`) and mapping to a **DTO inside the transaction**. Not by enabling OSIV, and not by making the association EAGER.

## ❓ Interview Questions

### Q1. What is FetchType?

It determines **when** related entities are loaded from the database — immediately with the parent (EAGER) or on first access (LAZY).

### Q2. Difference between LAZY and EAGER?

- **LAZY:** load related entities only when accessed.
- **EAGER:** load related entities immediately with the parent entity.

EAGER is a permanent mapping-level decision; LAZY can be overridden per query with `JOIN FETCH` or `@EntityGraph`.

### Q3. What is the N+1 problem?

One query loads N parent entities, then one additional query fires per parent to load its association — `1 + N` queries instead of one. It appears whenever a lazy association is touched in a loop (and equally with EAGER, just earlier).

### Q4. How do you solve the N+1 problem?

- `JOIN FETCH` in JPQL
- `@EntityGraph` on the repository method
- Batch fetching (`@BatchSize` / `default_batch_fetch_size`)
- Or a projection/DTO query that doesn't load the association at all

### Q5. Why does `LazyInitializationException` occur?

The association was never initialised, and the persistence context that could load it is already closed. Without a Session there is no way to issue the extra SELECT.

### Q6. What is a proxy?

A runtime-generated subclass (for entities) or a wrapper collection (for `@OneToMany`) that stands in for unloaded data and triggers a SELECT on first real access. This is why entities must not be `final`.

### Q7. Does calling `getId()` on a lazy proxy hit the database?

No. The identifier is already known, so the proxy answers it without initialising. Any other getter triggers the load.

### Q8. Why does pagination break with `JOIN FETCH`?

The join returns parent rows multiplied by child rows, so SQL-level `LIMIT` would cut a parent's children in half. Hibernate therefore loads everything and paginates in memory — a warning in the logs and an OOM risk. Use `@BatchSize`, or paginate ids first.

### Q9. Should you disable Open Session In View?

Yes, in production. It hides N+1 queries in the serialisation layer and holds a database connection for the entire HTTP response. Fetch explicitly and map to DTOs instead.

---

> [!tip] ⚡ Quick Recall
> - **LAZY = load later. EAGER = load now.** Defaults: `@ManyToOne` / `@OneToOne` are **EAGER**; collections are LAZY. Override the `-ToOne` ones to LAZY.
> - EAGER can't be undone per query; LAZY can be overridden per query. That's why LAZY is the right default.
> - Unloaded data is a **proxy** — a runtime subclass (entities) or `PersistentBag`/`PersistentSet` (collections). `getId()` doesn't initialise it; any other getter does.
> - **N+1** = 1 query for parents + 1 per parent for the association. EAGER doesn't fix it, it just moves it earlier.
> - Fixes: **`JOIN FETCH`** (fastest, no pagination) · **`@EntityGraph`** (declarative, keeps derived queries) · **`@BatchSize` / `default_batch_fetch_size`** (works with pagination, great global safety net).
> - `JOIN FETCH` caveats: duplicate parents (use `DISTINCT`), **pagination happens in memory**, only one collection at a time.
> - **`LazyInitializationException`** = touched a proxy after the session/transaction closed. Real fix = fetch it in the query and map to a **DTO inside the transaction**. Not EAGER, not OSIV.
> - Set `spring.jpa.open-in-view: false`.
