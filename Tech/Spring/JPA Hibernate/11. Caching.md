> **Caching = storing frequently used data in memory to avoid expensive database calls.**

There are **three** caches in Hibernate, and only one of them is switched on for you.

```text
Application
     ↓
First Level Cache      (mandatory, per Session)
     ↓
Second Level Cache     (optional, shared)
     ↓
Database
```

> [!info] Where this fits
> Worth learning at **interview level**, not framework-internals level. You need to answer confidently *what* each cache is, *when* to use it, and *why you usually don't*. Previous: [[10. Transactions]].

## 1. Why caching at all?

Imagine this code:

```java
Wallet wallet = entityManager.find(Wallet.class, 1L);
```

Hibernate executes

```sql
SELECT * FROM wallet WHERE id = 1;
```

One second later your code does the same call again.

Should Hibernate ask the database again?

**Probably not.** The data is already in memory.

### Think of your kitchen

You're cooking. You need salt.

**Without cache** — every time you need salt:

```text
Kitchen → walk to grocery store → buy salt → come back
```

Ridiculous.

**With cache** — you buy salt once and keep it on the shelf:

```text
Kitchen shelf → take salt
```

The kitchen shelf is your cache.

### Why database access is expensive

Reading from RAM takes **nanoseconds**.

Reading from a database involves:

```text
Application
    ↓
Network
    ↓
Database Server
    ↓
SQL Parsing
    ↓
Execution Plan
    ↓
Disk / Memory Lookup
    ↓
Network
    ↓
Application
```

Even if the database keeps the page in its own buffer pool, there's still network round trip plus SQL parsing and planning. Memory inside your application is much faster.

## 2. First Level Cache ⭐⭐⭐⭐⭐

The one every interviewer expects you to know.

Every `Session` / `EntityManager` has its own cache:

```text
Session
   ↓
Persistence Context
```

**Persistence Context *is* the First Level Cache.**

### Example

```java
Wallet w1 = entityManager.find(Wallet.class, 1L);
```

Hibernate executes

```sql
SELECT * FROM wallet WHERE id = 1;
```

Wallet is stored in the Persistence Context. Again:

```java
Wallet w2 = entityManager.find(Wallet.class, 1L);
```

Hibernate checks the Persistence Context → found → returns the object. **No SQL.**

```java
System.out.println(w1 == w2);   // true
```

Both references point to the **same Java object**.

### Properties

- **Automatic** — you cannot turn it off
- **Mandatory** — always present
- **Per Session / EntityManager** — never shared
- Stores the actual **managed Java object**

### Lifetime

```text
Session Open
     ↓
Cache Exists
     ↓
Session Close
     ↓
Cache Gone
```

Close the `EntityManager` and query again → the cache is empty, Hibernate must go back to the database.

In Spring this means the L1 cache lives **for one transaction**. Two service calls = two transactions = two caches = two queries.

### It is not only about speed

Hibernate also needs the object in memory to **track changes**:

```java
Wallet wallet = entityManager.find(Wallet.class, 1L);
wallet.setBalance(new BigDecimal("90000"));
```

Because the object is in the persistence context, dirty checking can compare it against the snapshot at flush and generate the `UPDATE` → [[8. Dirty Checking and Flush]].

So the Persistence Context serves **two purposes**:

1. **Caching** — avoiding repeated queries for the same entity.
2. **State management** — enabling dirty checking and automatic updates.

> [!warning] The L1 cache only works for `find()` / `getReference()`
> A **JPQL query always hits the database**, even if the entity is already cached. The result rows are then reconciled with the persistence context (so you get the same object identity back), but the SQL is executed regardless. `find()` by id is the only cache-first path.

## 3. Second Level Cache ⭐⭐⭐

Suppose two users.

```text
User A → Session A → Wallet(1)
User B → Session B → Wallet(1)
```

The First Level Cache cannot help — it belongs to one Session only. Both sessions hit the database.

The Second Level Cache is **shared across sessions**, and lives in the `SessionFactory`:

```text
Session A
    ↓
Second Level Cache
    ↓
Database
```

Later:

```text
Session B
    ↓
Second Level Cache
    ↓
Wallet returned      ← no SQL
```

### It is NOT automatic

Unlike L1, the second-level cache is **off by default**. You must:

1. Choose a cache provider
2. Configure Hibernate to use it
3. Decide **which entities** should be cached

```java
@Entity
@Cacheable
@org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
public class Currency { ... }
```

```yaml
spring.jpa.properties.hibernate.cache.use_second_level_cache: true
spring.jpa.properties.hibernate.cache.region.factory_class: jcache
```

Providers: **Ehcache**, **Infinispan**, **Hazelcast**, **Caffeine** (and Redis via integration).

### Why isn't it automatic?

Imagine:

```text
wallet
id | balance
1  | 1000
```

User A changes the balance to **900**. If another node reads from a stale cache, it still sees **1000**.

That's dangerous. So Hibernate asks:

> "Developer, you decide what is safe to cache."

### Rule of thumb

Cache entities that change **rarely**:

✅ Country
✅ Currency
✅ State
✅ Product Category
✅ MCC codes, bank IFSC master, scheme config

Don't cache frequently changing data:

❌ Wallet balance
❌ Transactions
❌ Payments
❌ Settlements

> [!warning] The clustering trap
> The second-level cache is per **JVM** unless the provider is distributed. Run three pods behind a load balancer with a local Ehcache and each pod has its own copy — an update on pod A leaves pods B and C stale until eviction. Either use a distributed provider (Infinispan/Hazelcast in cluster mode) or only cache genuinely immutable reference data.

### What is actually stored?

Not the entity object — a **dehydrated** array of its state, keyed by id. Hibernate rebuilds a fresh entity instance per session from it. That's why the second-level cache is safe to share across threads while the first-level cache is not.

## 4. Cache concurrency strategies

When you enable L2 you must pick how it handles concurrent writes:

| Strategy | Use for | Behaviour |
|---|---|---|
| `READ_ONLY` | Never-updated reference data (currencies, countries) | Fastest. Modifying throws an exception. |
| `NONSTRICT_READ_WRITE` | Rarely updated, stale reads acceptable | Invalidates **after** commit — brief staleness window |
| `READ_WRITE` | Updated data needing consistency | Uses soft locks; safe but slower |
| `TRANSACTIONAL` | JTA environments only | Full transactional cache |

Default choice for reference data: `READ_ONLY`. If it can change at all: `READ_WRITE`.

## 5. Query Cache ⭐⭐

Normally Hibernate caches **entities**. The Query Cache stores the **result of a query**.

```sql
SELECT * FROM merchant WHERE category = 'GROCERY'
```

Instead of caching each merchant individually, Hibernate can cache the entire result list — actually the **list of ids**, then resolves each id through the second-level cache.

> [!warning] Query Cache requires the Second Level Cache
> Since it only stores ids, without L2 enabled for that entity each cache hit turns into N `SELECT`s by id. Enabling the query cache alone can make things **slower**.

It is also **optional**, and used even less often than L2.

### Why don't people enable it everywhere?

Imagine:

```sql
SELECT * FROM transaction WHERE status = 'PENDING';
```

A new transaction is inserted. The cached result is immediately stale, so Hibernate must invalidate it. For frequently changing tables the invalidation overhead outweighs the benefit.

Reserve it for:

✅ Product catalogues
✅ Countries, categories
✅ Static reports

Not for:

❌ Orders
❌ Payments
❌ Transactions

> [!tip] Interview answer
> *"Should I enable Query Cache?"*
> **"Only after identifying a repeated, read-heavy query whose underlying data changes infrequently — and only with the second-level cache enabled for those entities. I wouldn't enable it by default."**
> That demonstrates practical thinking.

## 6. How Redis relates

This is where many people get confused.

**Redis and Hibernate's Second-Level Cache are related, but not the same thing.**

Think of Redis as a **memory server**. It can store objects, JSON, strings, counters, sessions — anything.

Hibernate simply needs **some place** to store cached entities. That place could be Ehcache, Infinispan, Hazelcast — or Redis through an integration.

**Without Redis**

```text
Hibernate → Ehcache → memory inside the JVM
```

**With Redis**

```text
Hibernate → Redis → memory on the Redis server
```

### Why use Redis instead of JVM memory?

Three application servers:

```text
Server A     Server B     Server C
```

Each has its own memory. Server A caches `Wallet(1)`; servers B and C don't know about it.

With Redis:

```text
Server A ─┐
Server B ─┼─→ Redis
Server C ─┘
```

Everyone shares the same cache. That's why Redis is popular in distributed systems.

### The important interview point

Many companies **do not** use Redis as Hibernate's second-level cache. They use Redis **directly in the service layer**:

```java
Merchant m = redis.get(merchantId);

if (m == null) {
    m = repository.findById(merchantId).orElseThrow();
    redis.set(merchantId, m, Duration.ofMinutes(10));
}
```

This gives explicit control over keys, TTLs, and invalidation, which Hibernate's cache hides.

So if an interviewer asks *"Do you use Redis?"*, they usually mean **application-level caching** (`@Cacheable` / `RedisTemplate`), not Hibernate's second-level cache.

### Why do we need app caching if the DB has a buffer pool?

They cache at **different layers**:

- **Database cache** stores **pages/blocks** to avoid disk I/O. SQL must still be sent, parsed, planned, executed.
- **Hibernate L1** stores **managed Java objects** within one unit of work.
- **Hibernate L2** stores **entity state** across sessions in one JVM (or cluster).
- **Redis / application cache** stores **application-ready data** (DTOs, JSON) that can be returned without contacting the database at all.

They complement each other rather than replacing one another.

## 7. Who handles what

An excellent interview summary — memorise this table.

| Problem | Who handles it? |
|---|---|
| Connection management | HikariCP / DataSource |
| Object ↔ Table mapping | Hibernate |
| SQL execution | JDBC |
| First-Level Cache | Hibernate (always) |
| Second-Level Cache | Hibernate + cache provider (opt-in) |
| Distributed cache | Redis (optional) |
| Dirty reads | Database isolation level |
| Non-repeatable reads | Database isolation level |
| Phantom reads | Database isolation level |
| Lost updates | Database locking and/or Hibernate optimistic locking (`@Version`) |

Note what Hibernate does **not** do: it does not implement isolation. See [[10. Transactions]] and [[12. Locking]].

## ❓ Interview Questions

### Q1. Difference between First and Second Level Cache?

| First Level | Second Level |
|---|---|
| Per Session / EntityManager | Shared across Sessions |
| Mandatory, always enabled | Optional, must be configured |
| *Is* the Persistence Context | External cache provider |
| Stores the managed object | Stores dehydrated entity state |
| Dies with the Session | Lives in the SessionFactory |

### Q2. Why is the Persistence Context called the First Level Cache?

Because every entity loaded into an `EntityManager`/`Session` is kept in memory there. Requesting the same entity again during that Session returns the managed instance instead of executing another query.

### Q3. Is the Second Level Cache automatic?

No. You must enable it, pick a provider, and annotate the specific entities you want cached — because Hibernate cannot know which of your data is safe to serve stale.

### Q4. Which entities would you cache?

Slow-changing reference data — currencies, countries, MCC codes, scheme configuration. Never balances, transactions or settlements.

### Q5. Does a JPQL query use the First Level Cache?

No. A JPQL query always executes SQL. The returned rows are then reconciled against the persistence context so object identity is preserved, but the database is hit. Only `find()`/`getReference()` by id can be served from L1.

### Q6. What is the Query Cache and should you enable it?

It caches the **ids** returned by a query. It requires the second-level cache to be useful, and it must be invalidated whenever the underlying table changes — so it only pays off for repeated queries over rarely-changing data.

### Q7. Is Redis the same as the Second Level Cache?

No. Redis is a storage engine that *can* back Hibernate's L2 through an integration, but in most real systems it's used directly as an application-level cache in the service layer, which gives explicit control over keys, TTL and invalidation.

### Q8. What are cache concurrency strategies?

`READ_ONLY`, `NONSTRICT_READ_WRITE`, `READ_WRITE`, `TRANSACTIONAL` — they define how the L2 cache handles concurrent modification. Use `READ_ONLY` for immutable reference data, `READ_WRITE` when the data can change.

---

> [!tip] ⚡ Quick Recall
> - Three caches: **L1 (Persistence Context)** → **L2 (SessionFactory-wide)** → **Query Cache**. Only L1 is automatic.
> - **L1 = Persistence Context.** Per Session, mandatory, can't be disabled, dies with the Session/transaction. `find()` twice = one query, `w1 == w2`.
> - **JPQL bypasses L1** — always hits the database. Only `find()` by id is cache-first.
> - L1 also powers **dirty checking**, not just speed.
> - **L2 is opt-in**: provider + `@Cacheable` + `@Cache(usage=…)`. Shared across sessions; stores dehydrated state, not objects.
> - Cache only **slow-changing reference data** (currency, country, MCC). Never balances or transactions.
> - L2 is **per JVM** unless the provider is clustered → stale reads across pods.
> - **Query Cache** caches ids, needs L2, and invalidates on every table write. Rarely worth it.
> - **Redis** ≠ L2. Usually used directly in the service layer for explicit control.
> - Hibernate handles **lost updates** (`@Version`); the **database** handles dirty/non-repeatable/phantom reads.
