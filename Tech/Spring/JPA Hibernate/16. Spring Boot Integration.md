You have never written an `EntityManagerFactory` by hand, never picked a dialect, never created a `DataSource`. Spring Boot did all of it from a handful of properties. This note is about **what it actually configured for you**, and which knobs matter in production — especially the connection pool.

## 1. What auto-configuration actually creates

You write this:

```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/payments
    username: app
    password: secret
```

Spring Boot sees a JDBC driver and `spring-boot-starter-data-jpa` on the classpath and builds the whole stack:

```text
DataSourceAutoConfiguration
    ↓  creates
HikariDataSource

HibernateJpaAutoConfiguration
    ↓  creates
LocalContainerEntityManagerFactoryBean
    ↓  which builds
EntityManagerFactory  (Hibernate SessionFactory under the hood)

JpaTransactionManager   ← for @Transactional

JpaRepositoriesAutoConfiguration
    ↓  scans @Entity + Repository interfaces, generates proxies
```

So the four beans you never wrote:

| Bean | What it does |
|---|---|
| `DataSource` (Hikari) | hands out pooled JDBC connections |
| `EntityManagerFactory` | the Hibernate `SessionFactory`, built once at startup |
| `PlatformTransactionManager` | makes `@Transactional` work — see [[10. Transactions]] |
| Repository proxies | implement your `interface XRepository extends JpaRepository` — see [[13. Spring Data JPA]] |

**Entity scanning** starts at the package of your `@SpringBootApplication` class and goes down. Put an `@Entity` outside that tree and Hibernate simply won't see it — the classic "Not a managed type" error. Fix with `@EntityScan(basePackages = "...")`.

## 2. DataSource configuration

```yaml
spring:
  datasource:
    url: jdbc:postgresql://db:5432/payments
    username: ${DB_USER}
    password: ${DB_PASSWORD}
    driver-class-name: org.postgresql.Driver   # usually inferred from the URL
    hikari:
      pool-name: payments-pool
```

If you declare your own `@Bean DataSource`, Boot backs off entirely and uses yours (that's how you set up a read/write routing `DataSource` or multiple databases).

## 3. HikariCP — the connection pool

### The problem

Your application needs to read a wallet:

```java
Wallet wallet = walletRepository.findById(1L).get();
```

Eventually Hibernate needs a JDBC `Connection`. How does it get one?

Without a pool, every request would do:

```text
HTTP Request
    ↓
Create database connection
    ↓
Execute SQL
    ↓
Close connection
```

### Why is this bad?

Creating a database connection is **expensive**. Behind that one call:

1. A TCP connection is established.
2. SSL/TLS handshake (if enabled).
3. Authentication (username/password).
4. The database allocates server-side resources (on Postgres, it **forks a process**).
5. The JDBC driver initialises the connection.

That's anywhere from a few milliseconds to much longer.

Now imagine 1000 requests per second:

```text
1000 requests
    ↓
1000 new database connections
    ↓
1000 authentication handshakes
    ↓
1000 connection closures
```

The database spends most of its time creating and destroying connections rather than answering queries.

### The solution: a connection pool

Create a set of reusable connections up front.

```text
Database
   ↑
   │  10 connections
   ↓
HikariCP Pool
   ↓
Application
```

When a request arrives:

```text
Request
    ↓
Borrow connection
    ↓
Execute SQL
    ↓
Return connection
```

Notice: the connection is **returned**, not closed.

> [!example] Real-life analogy
> **Without a pool:** every employee buys a new laptop every morning and throws it away in the evening. Absurdly expensive.
> **With a pool:** the company owns 20 laptops. Employees borrow one, work, and return it.
> That's exactly what a connection pool does.

### Where HikariCP sits

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Hibernate
    ↓
HikariCP
    ↓
JDBC Driver
    ↓
Database
```

Hibernate does **not** create database connections. It asks the configured `DataSource` — HikariCP by default in Spring Boot — for one.

### How many connections exist?

```properties
spring.datasource.hikari.maximum-pool-size=10
```

Hikari creates **up to 10** connections.

If 8 requests arrive simultaneously:

```text
Request 1 → Connection 1
Request 2 → Connection 2
...
Request 8 → Connection 8
```

Two connections stay idle.

### What if all connections are busy?

Pool size 10, and 11 requests arrive. The first 10 borrow. Request 11 waits.

```text
Request 11
    ↓
Waiting...
```

When one finishes:

```text
Connection returned
    ↓
Request 11 gets a connection
```

### What if it waits too long?

```properties
spring.datasource.hikari.connection-timeout=30000
```

Wait up to 30 seconds. If no connection becomes available:

```text
SQLTransientConnectionException:
  payments-pool - Connection is not available, request timed out after 30000ms
```

This exact message is the single most common production JPA error. Its causes are in [[18. Production Problems]].

## 4. Pool tuning properties

### `maximumPoolSize`

```properties
spring.datasource.hikari.maximum-pool-size=20
```

The maximum number of database connections. **Not** the number of users — it is the maximum number of **simultaneous database operations**.

### `minimumIdle`

```properties
spring.datasource.hikari.minimum-idle=5
```

Keep at least five idle connections ready, even when nobody is using the application — because creating one later, on the critical path of a request, is expensive.

> [!tip] Hikari's own advice: set `minimumIdle == maximumPoolSize`
> A fixed-size pool gives the most predictable latency. Elastic pools shed connections during a quiet period and then pay the reconnect cost exactly when traffic returns.

### `idleTimeout`

```properties
spring.datasource.hikari.idle-timeout=600000
```

If a connection sits unused for that long, Hikari closes it — down to `minimumIdle`. Avoids wasting database resources. (No effect if `minimumIdle == maximumPoolSize`.)

### `maxLifetime`

One of the most important settings.

Suppose the database (or a firewall, or a load balancer) kills connections after **30 minutes**. If Hikari keeps handing out a dead connection, every query fails.

```properties
spring.datasource.hikari.max-lifetime=1500000   # 25 minutes
```

Hikari retires the connection **before** the database does.

### Why must `maxLifetime` be less than the DB timeout?

```text
Database: kills connections after 30 minutes
Hikari:   still thinks the connection is alive
    ↓
Borrow connection
    ↓
Dead connection
    ↓
Exception
```

Therefore, always:

```text
Hikari maxLifetime  <  Database / firewall timeout
```

Rule of thumb: a few seconds to a minute below the shortest timeout anywhere in the network path.

### Summary

| Property | Default | Means |
|---|---|---|
| `maximum-pool-size` | 10 | max simultaneous DB operations |
| `minimum-idle` | = max | idle connections kept warm |
| `connection-timeout` | 30 s | how long a thread waits for a connection |
| `idle-timeout` | 10 min | when an excess idle connection is closed |
| `max-lifetime` | 30 min | retire a connection before the DB does |
| `leak-detection-threshold` | 0 (off) | warn if a connection is held this long |
| `validation-timeout` | 5 s | how long a liveness check may take |

## 5. Pool sizing — the counter-intuitive part

> [!warning] Don't blindly increase the pool size
> A common misconception: *more connections = better performance.* Not necessarily.

Suppose your database efficiently handles about 40 concurrent connections. If you configure:

```properties
maximum-pool-size=500
```

then:

- The application opens far more connections.
- The database spends more time context-switching and managing them.
- **Overall throughput actually decreases** — and latency gets worse for everyone.

A database with 8 cores can only truly do ~8 things at once. Every connection beyond that is a queue, and an in-application queue (threads waiting on Hikari) is cheaper and more observable than an in-database one.

Choose the pool size based on:

- Database capacity (and its own `max_connections`)
- CPU cores
- Typical concurrent workload
- Query execution time

A widely-used starting formula:

```text
pool size ≈ (core_count × 2) + effective_spindle_count
```

For a modern SSD-backed 8-core database, that's roughly **17–20**. Start small, measure, and only raise it if the *wait time* metric says threads are queueing while the DB is idle.

> [!warning] Multiply by your instance count
> 10 pods × `maximum-pool-size=50` = **500** connections to one database. Postgres' default `max_connections` is 100. Size the pool per-instance with the total in mind, or put PgBouncer in front.

### Keep transactions short

Bad:

```java
@Transactional
public void processPayout() {
    bankClient.initiate(...);   // 10 seconds of external API calls
    payoutRepository.save(p);   // database update
}
```

The connection is held for the entire transaction — 10 seconds of a pooled resource spent waiting on someone else's server. With a pool of 20, just 20 concurrent payouts stall your whole application.

Better: do the external work **first**, then open a short transaction only for the database operations.

### Monitor the pool

Spring Boot Actuator exposes Hikari metrics automatically:

- `hikaricp.connections.active`
- `hikaricp.connections.idle`
- `hikaricp.connections.pending` ← **threads waiting** — the alert that matters
- `hikaricp.connections.acquire` ← acquisition time
- `hikaricp.connections.usage` ← how long connections are held

`pending > 0` sustained means the pool is your bottleneck. `usage` climbing means transactions are getting longer.

### Final mental model

```text
HTTP Request
    ↓
Spring Boot
    ↓
Repository
    ↓
Hibernate
    ↓
HikariCP ──── Borrow connection
    ↓
JDBC Driver
    ↓
Database
    ↓
SQL executes
    ↓
Connection returned to HikariCP
    ↓
Ready for the next request
```

## 6. Leak detection

Suppose a developer forgets to return a connection:

```java
Connection connection = dataSource.getConnection();
// forgot to close
```

The pool slowly bleeds out:

```text
10 → 9 → 8 → ... → 0
```

Now every request waits. This is a **connection leak**.

Hikari can catch it:

```properties
spring.datasource.hikari.leak-detection-threshold=2000
```

If a connection is held longer than 2 seconds, Hikari logs a warning **with the stack trace of whoever borrowed it** — which points straight at the offending method.

Set it in staging/production to something a bit above your slowest legitimate transaction (e.g. 5–10 s). It costs almost nothing and has probably saved more production incidents than any other Hikari setting.

### Why is HikariCP so popular?

Before it, people used **Apache DBCP**, **C3P0**, **Tomcat JDBC Pool**. HikariCP became the Spring Boot default because it is:

- Very fast (a tiny, highly optimised codebase — bytecode-level tuning)
- Lightweight
- Reliable
- Excellent under high concurrency

## 7. Hibernate dialect

The dialect tells Hibernate **which SQL flavour to generate** — pagination syntax (`LIMIT` vs `FETCH FIRST` vs `ROWNUM`), identity/sequence support, column types for DDL, function names.

```yaml
spring:
  jpa:
    database-platform: org.hibernate.dialect.PostgreSQLDialect
```

**You usually don't need to set it.** Hibernate 6 detects the dialect from the JDBC connection metadata at startup. Set it explicitly only when you must pin a specific version's behaviour, or when you're building the `EntityManagerFactory` without a live connection.

> [!warning] Testing on H2, running on Postgres
> Different dialects, different generated SQL, different constraint semantics. A test suite that passes on H2 proves very little about production. Use **Testcontainers** with the real database image.

## 8. `ddl-auto`

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
```

| Value | What Hibernate does at startup |
|---|---|
| `none` | nothing |
| `validate` | compare entities to the schema, **fail fast** on mismatch |
| `update` | add missing tables/columns (never drops, never alters types) |
| `create` | drop and recreate the schema |
| `create-drop` | `create`, plus drop on shutdown |

> [!warning] Never use `update` or `create` in production
> - `update` **never drops or alters** — so it silently accumulates dead columns, and a type change is simply ignored. Your schema drifts from your entities with no record of how it got there.
> - `create` / `create-drop` **destroy your data**.
>
> The production answer is: **`validate`**, with schema changes owned by **Flyway** or **Liquibase** as versioned, reviewed, rollback-able migrations. `validate` then acts as a startup assertion that the migration and the code agree.

Sane defaults: `create-drop` in tests, `validate` everywhere else.

## 9. SQL logging

The most useful thing you can turn on in development.

```yaml
spring:
  jpa:
    show-sql: false          # ← don't use this one; it goes to System.out unformatted
logging:
  level:
    org.hibernate.SQL: DEBUG                          # the statements
    org.hibernate.orm.jdbc.bind: TRACE                # the bound parameters (Hibernate 6)
    org.hibernate.stat: DEBUG                         # per-session statistics
```

```yaml
spring:
  jpa:
    properties:
      hibernate:
        format_sql: true
        generate_statistics: true
```

`generate_statistics` prints a summary per session — **query count**, time spent, cache hits. This is how you catch an N+1 without reading a wall of SQL ([[14. Performance Tuning]]).

For real production-grade query logging with timings, use **p6spy** or **datasource-proxy**, which log the *actual* SQL with parameters inlined and execution time attached.

> [!warning] Never enable parameter binding logs in production
> `org.hibernate.orm.jdbc.bind: TRACE` prints every bound value — card numbers, phone numbers, tokens — into your log aggregator. That's a PII/PCI incident. Dev and local only.

## 10. Naming strategy

Why does `LedgerEntry.createdAt` map to a column called `created_at` without you saying so?

Because of the **implicit naming strategy** and **physical naming strategy**:

```text
Java name  →  [ImplicitNamingStrategy]  →  logical name  →  [PhysicalNamingStrategy]  →  actual column
createdAt                                   createdAt                                     created_at
```

Spring Boot's default physical strategy is `CamelCaseToUnderscoresNamingStrategy`:

- `LedgerEntry` → `ledger_entry`
- `createdAt` → `created_at`
- `merchantId` → `merchant_id`
- An `@ManyToOne Merchant merchant` → join column `merchant_id`

Override globally:

```yaml
spring:
  jpa:
    hibernate:
      naming:
        physical-strategy: org.hibernate.boot.model.naming.PhysicalNamingStrategyStandardImpl
```

(That one keeps the name as-is — which is what you want if your legacy schema uses `CreatedAt` or `CREATEDAT`.)

Or override per field with `@Column(name = "...")` / `@Table(name = "...")` — always wins.

> [!tip] Let the strategy do the work
> Annotating every single field with `@Column(name = ...)` is noise if the default already produces the right name. Reserve explicit names for the columns that genuinely differ from the convention (legacy tables, reserved words like `order` or `transaction`).

## ❓ Interview Questions

### Q1. Why do we need a connection pool?

Creating a database connection is expensive — TCP handshake, TLS, authentication, server-side resource allocation. A pool creates them once and reuses them, cutting per-request latency and load on the database.

### Q2. Does every request get a new connection?

No. It **borrows** one from the pool and **returns** it when the transaction or operation completes. `connection.close()` on a pooled connection returns it to the pool rather than closing the socket.

### Q3. What happens if the pool is exhausted?

New requests block waiting for a connection. If they wait longer than `connectionTimeout` (default 30 s), Hikari throws `SQLTransientConnectionException`.

### Q4. What if a developer forgets to close a connection?

The pool leaks connections until it's empty and every request hangs. `leakDetectionThreshold` logs a warning with the borrower's stack trace so you can find the culprit.

### Q5. How do you size a connection pool?

From database capacity and cores, not from expected user count — roughly `(cores × 2) + spindles`, then measured. Oversizing hurts: the database context-switches more and throughput drops. Multiply by your number of application instances to check the total against the DB's `max_connections`.

### Q6. Why must `maxLifetime` be shorter than the database timeout?

So Hikari retires a connection before the database or a network device silently kills it. Otherwise the pool hands out a dead connection and the request fails.

### Q7. What does `ddl-auto` do, and what should it be in production?

It controls schema generation at startup. In production: **`validate`** — the schema is owned by Flyway/Liquibase migrations, and `validate` asserts the code and schema agree. `update` causes silent schema drift; `create` destroys data.

### Q8. What is the Hibernate dialect and do you need to set it?

It determines the SQL flavour Hibernate generates. With Hibernate 6 it's auto-detected from connection metadata, so you normally don't set it.

### Q9. Why is a column named `created_at` when the field is `createdAt`?

Spring Boot's default physical naming strategy, `CamelCaseToUnderscoresNamingStrategy`, converts camelCase to snake_case. `@Column(name = ...)` overrides it.

### Q10. Where does HikariCP sit in the stack?

Between Hibernate and the JDBC driver. Hibernate never opens connections itself — it asks the `DataSource`, which is a `HikariDataSource` by default in Spring Boot.

> [!tip] ⚡ Quick Recall
> - Boot auto-configures four things you never wrote: **HikariDataSource**, **EntityManagerFactory**, **JpaTransactionManager**, **repository proxies**. Entity scanning starts at the `@SpringBootApplication` package.
> - **Connection creation is expensive** (TCP + TLS + auth + server resources). A pool borrows and **returns**, never closes.
> - Stack: `Controller → Service → Repository → Hibernate → HikariCP → JDBC driver → Database`.
> - Pool exhausted → threads wait → after `connectionTimeout` (30 s) → **`SQLTransientConnectionException`**.
> - **`maxLifetime` < database/firewall timeout**, always. Otherwise you hand out dead connections.
> - **Bigger pool ≠ faster.** `(cores × 2) + spindles`, then measure. Multiply by pod count vs `max_connections`.
> - **Keep transactions short** — no HTTP calls inside `@Transactional`; the connection is held the whole time.
> - **`leak-detection-threshold`** logs the stack trace of whoever held a connection too long. Turn it on.
> - Monitor `hikaricp.connections.pending` — sustained > 0 means the pool is the bottleneck.
> - **`ddl-auto: validate`** in production; Flyway/Liquibase own the schema. Never `update` or `create`.
> - **Dialect** is auto-detected in Hibernate 6. Test against the real DB (Testcontainers), not H2.
> - SQL logging: `org.hibernate.SQL=DEBUG` + `format_sql` + `generate_statistics`. **Never** log bound parameters in production — PII.
> - Naming: `CamelCaseToUnderscoresNamingStrategy` → `createdAt` becomes `created_at`.
>
> | Property | Sane production value |
> |---|---|
> | `maximum-pool-size` | 10–20 per instance, measured |
> | `minimum-idle` | = maximum-pool-size |
> | `connection-timeout` | 3000–10000 ms (fail fast) |
> | `max-lifetime` | < DB timeout (e.g. 25 min) |
> | `leak-detection-threshold` | 5000–10000 ms |
> | `ddl-auto` | `validate` |
