Everything up to here has been *what Hibernate does*. This note is *how it does it* — the machinery behind `persist()`, the reason a lazy field is a proxy, why dirty checking works without you calling `update()`, and what the action queue is actually doing at flush time.

> [!info] Where this fits
> Senior-level material. You don't need it to write correct code, but it's what turns "Hibernate does X" into "Hibernate does X **because**" — and it's where SDE-2/SDE-3 interviews go when they want to see depth. Previous: [[16. Spring Boot Integration]]. Next: [[18. Production Problems]].

## 1. What happens at startup — bootstrap

Everything expensive happens once, at boot.

```text
Metadata sources (@Entity classes, orm.xml)
      ↓
MetadataSources  →  MetadataBuilder  →  Metadata
      ↓  (validate mappings, resolve types, detect dialect)
SessionFactoryBuilder
      ↓
SessionFactory   ← immutable, thread-safe, one per application
```

During this phase Hibernate:

- **Scans and parses** every `@Entity`, building an internal model of tables, columns and associations.
- **Resolves types** — Java type ↔ JDBC type, including your `AttributeConverter`s ([[15. Advanced Hibernate]]).
- **Detects the dialect** from connection metadata.
- **Pre-generates SQL** — the INSERT, UPDATE, DELETE and select-by-id statements for every entity, as reusable templates.
- **Builds the `EntityPersister`** for each entity and a `CollectionPersister` for each collection.
- **Creates proxy classes** for entities eligible for lazy loading.

> [!tip] Why `SessionFactory` is expensive and `Session` is cheap
> This is the whole answer to "why one `SessionFactory` per application". All the parsing, validation and SQL generation is done **once** here. Creating a `Session` afterwards is just allocating a few maps and grabbing a connection lazily — which is why opening a Session per request costs nothing. See [[4. Hibernate]].

The `EntityPersister` is the key object: for `Wallet`, it holds the table name, the column list, the pre-built SQL strings, the id generator, and the getters/setters needed to read and write field values. Every operation on a `Wallet` goes through it.

## 2. Inside the `SessionFactory` and the `Session`

```text
SessionFactory                              (thread-safe, shared)
├── Map<EntityName, EntityPersister>        ← metadata + pre-built SQL
├── Map<Role, CollectionPersister>
├── QueryPlanCache                          ← parsed JPQL → SQL plans
├── Second-Level Cache region handles       ← see 11. Caching
├── Statistics
└── ConnectionProvider (→ HikariCP)

Session / EntityManager                     (NOT thread-safe, one per transaction)
├── PersistenceContext (StatefulPersistenceContext)
├── ActionQueue
├── JdbcCoordinator      ← owns the JDBC Connection + batching
├── TransactionCoordinator
├── EventListenerGroups  (shared from the factory)
└── LoadQueryInfluencers ← enabled filters, entity graphs, fetch profiles
```

Two things stand out:

- The **`QueryPlanCache`** is why a JPQL string is parsed once and reused. It's also why *string-concatenated* queries are a slow leak — every distinct string is a new plan. Always use `:parameters`.
- The **`JdbcCoordinator`** is why the Session, not the transaction, owns batching and statement reuse.

## 3. Persistence context internals

The persistence context ([[5. Persistence Context]]) is not one map. It's several, and knowing which is which explains most of its behaviour.

```java
class StatefulPersistenceContext {
    Map<EntityKey, Object>       entitiesByKey;      // (entityName, id) → entity instance
    Map<Object, EntityEntry>     entityEntries;      // entity → its metadata + snapshot
    Map<EntityKey, Object>       proxiesByKey;       // uninitialised proxies
    Map<CollectionKey, PersistentCollection> collectionsByKey;
    // ...
}
```

The `EntityEntry` is where the interesting state lives:

| Field | Purpose |
|---|---|
| `id` | primary key |
| `status` | MANAGED / DELETED / GONE / READ_ONLY |
| `loadedState` | **the hydrated snapshot** — a `Object[]` of field values as loaded from the DB |
| `version` | for optimistic locking ([[12. Locking]]) |
| `persister` | which `EntityPersister` handles it |
| `lockMode` | current lock mode |

Now several earlier facts fall out for free:

- **`entitiesByKey` keyed by `(entityName, id)`** → this *is* the first-level cache, and it's why `find()` twice returns the **same object reference** (`==` is true).
- **`loadedState`** → this *is* the snapshot dirty checking compares against.
- **Memory cost** → each managed entity costs the object **plus** its snapshot array. That's why loading 100,000 entities in one transaction is roughly double the memory you'd expect, and why `em.clear()` matters in batch loops ([[14. Performance Tuning]]).

### Hydration

When a row comes back from a `ResultSet`, Hibernate doesn't build the entity in one step:

```text
ResultSet row
    ↓  hydrate: read raw column values into an Object[]
loadedState  (the snapshot)
    ↓  instantiate the entity (no-arg constructor, via reflection)
    ↓  resolve: convert raw values → Java types, replace FKs with proxies
    ↓  inject values into the fields
    ↓  add to entitiesByKey + entityEntries
managed entity
```

Two consequences worth remembering:

- The entity is **added to the persistence context before its fields are fully populated** — that's how Hibernate handles circular references without infinite recursion.
- Your entity's **no-arg constructor is required** because Hibernate instantiates the object itself and then sets fields directly; it never calls your business constructor.

## 4. Proxy generation

A lazy `@ManyToOne` doesn't give you the entity. It gives you a **proxy** — a runtime-generated subclass.

```text
class Transaction {
    @ManyToOne(fetch = LAZY)
    Merchant merchant;      // actually a Merchant$HibernateProxy
}
```

Hibernate (via **ByteBuddy**, which replaced Javassist/CGLIB) generates at startup:

```java
class Merchant$HibernateProxy extends Merchant implements HibernateProxy {

    private LazyInitializer initializer;   // holds: entityName, id, session, target

    @Override
    public String getName() {
        return initializer.getImplementation().getName();   // triggers the SELECT
    }
}
```

Every method is overridden to first ask the `LazyInitializer` for the real object, loading it if needed. `getId()` is the exception — the id is already known, so it's answered without a query.

This single design decision explains a whole cluster of behaviours:

| Behaviour | Because the proxy is a generated subclass |
|---|---|
| Entities can't be `final` | you can't subclass a final class |
| Lazy fields can't have `final` methods | they can't be overridden |
| A no-arg constructor is required | the proxy's constructor calls `super()` |
| `entity.getClass()` returns `Merchant$HibernateProxy` | so `getClass() != getClass()` in `equals` — use `instanceof` ([[6. Entity Mapping]]) |
| `getReference()` is free | it returns the proxy without any SQL ([[9. Fetching]]) |
| `LazyInitializationException` | the `LazyInitializer`'s session reference is closed |
| `instanceof` on subclasses can be wrong | a proxy of the base type isn't an instance of the concrete subclass |

Collections are different — a lazy `List<Transaction>` isn't a subclass proxy but a **`PersistentBag`** (or `PersistentSet`, `PersistentList`, `PersistentMap`), a wrapper implementing `java.util.List` that loads on first access and *also* tracks structural changes for dirty checking.

```java
Hibernate.isInitialized(merchant);   // has the proxy been resolved?
Hibernate.initialize(merchant);      // force it, inside the session
Hibernate.unproxy(merchant);         // get the real object out
```

## 5. Dirty checking internals

You never call `update()`. So how does Hibernate know?

```text
At load:      loadedState = ["Zomato", ACTIVE, 5000]     ← stored in EntityEntry
Your code:    merchant.setName("Zomato Ltd");
At flush:     current    = ["Zomato Ltd", ACTIVE, 5000]
              compare field by field, using each property's Type.isDirty()
              → index 0 differs
              → schedule EntityUpdateAction
```

Key points ([[8. Dirty Checking and Flush]] covers the behaviour; this is the mechanism):

- Hibernate **does not intercept your setter**. Nothing happens at `setName()` time. The comparison happens at flush.
- The comparison is **field by field**, using the mapped `Type` for each property — which is why an `AttributeConverter`'d field compares on the *converted* value, and why a mutable `Date` or a `byte[]` compares by content.
- Cost is **O(managed entities × fields)** on **every flush**. With auto-flush before every query, a transaction holding 50,000 entities and running 20 queries is doing an enormous amount of comparison work.
- The generated UPDATE contains **all columns** by default — because the SQL was pre-built at startup and can be reused/batched. `@DynamicUpdate` opts into building the SQL per-flush from the diff.

## 6. Bytecode enhancement

The default mechanism has two costs: the snapshot memory, and full-object comparison. **Bytecode enhancement** removes both by rewriting your entity classes at build time.

```xml
<plugin>
  <groupId>org.hibernate.orm.tooling</groupId>
  <artifactId>hibernate-enhance-maven-plugin</artifactId>
  <configuration>
    <enableDirtyTracking>true</enableDirtyTracking>
    <enableLazyInitialization>true</enableLazyInitialization>
    <enableAssociationManagement>true</enableAssociationManagement>
  </configuration>
</plugin>
```

What each one changes:

| Feature | Effect |
|---|---|
| **Dirty tracking** | setters are rewritten to record "field N changed" in a `$$_hibernate_tracker`. Flush reads the tracker instead of diffing — **no snapshot comparison** |
| **Lazy initialization** | enables **attribute-level laziness**: a single `@Lob` column or `@Basic(fetch = LAZY)` field can be left unloaded. Without enhancement, `@Basic(fetch = LAZY)` is silently ignored |
| **Association management** | automatically keeps both sides of a bidirectional relationship in sync, so you don't need the helper method from [[7. Relationships]] |

Enhancement also enables `@LazyToOne(NO_PROXY)` — a lazy `@ManyToOne` that loads on first field access rather than being a proxy from the start.

> [!warning] Enhancement is a real trade-off
> It rewrites your class files, which complicates debugging, can surprise tools that reflect over your entities, and changes lazy-loading behaviour in ways your existing code may not expect. Most teams never enable it. Reach for it when you have profiler evidence that dirty checking or a large `@Lob` is genuinely your bottleneck — not by default.

## 7. Reflection and property access

Hibernate has to read and write your entity's fields. Two modes:

- **Field access** — chosen when `@Id` is on a **field**. Hibernate uses `Field.setAccessible(true)` and reads/writes directly, **bypassing your getters and setters**.
- **Property access** — chosen when `@Id` is on a **getter**. Hibernate calls the getter/setter.

The `@Id` placement decides it **for the entire class**, and you cannot mix within one entity hierarchy (short of `@Access` overrides).

Practical consequences:

- With field access, logic in your setter (validation, normalisation, side effects) **never runs** when Hibernate loads a row. Don't rely on it.
- With property access, your getter runs during flush's dirty check — a getter with side effects or lazy initialisation logic will misbehave.
- **Field access is the sane default.** Put `@Id` on the field.

Raw reflection is slow, so Hibernate wraps each getter/setter in a generated **`PropertyAccess`** implementation (and with bytecode enhancement, replaces it with direct field access entirely).

## 8. The Action Queue

At flush, Hibernate doesn't just fire statements in the order you wrote your code. It sorts them.

```java
class ActionQueue {
    List<OrphanRemovalAction>            orphanRemovals;
    ExecutableList<EntityInsertAction>   insertions;
    ExecutableList<EntityUpdateAction>   updates;
    ExecutableList<CollectionRemoveAction> collectionRemovals;
    ExecutableList<CollectionUpdateAction> collectionUpdates;
    ExecutableList<CollectionRecreateAction> collectionCreations;
    ExecutableList<EntityDeleteAction>   deletions;
}
```

Execution order at flush:

```text
1. OrphanRemoval
2. Inserts            (topologically sorted by FK dependency)
3. Updates
4. Collection removals
5. Collection updates
6. Collection recreations
7. Deletes            ← always last
```

Within inserts, Hibernate performs a **topological sort** on foreign-key dependencies, so a `Merchant` is always inserted before the `Transaction` that references it — regardless of the order you called `persist()`.

> [!warning] Deletes are last — the classic constraint violation
> ```java
> walletRepo.delete(oldWallet);          // unique (customer_id, currency)
> walletRepo.save(new Wallet(cust, INR));
> ```
> You wrote delete-then-insert. Hibernate executes **insert-then-delete** → unique constraint violation. Fix with an explicit `flush()` between them, or reorder the operations. Full discussion in [[8. Dirty Checking and Flush]].

The action queue is also where **JDBC batching** is assembled: consecutive actions using the same pre-built SQL string are batched together — which is why `hibernate.order_inserts=true` improves batching ([[14. Performance Tuning]]).

## 9. SQL generation

Hibernate generates SQL at two different times.

**At startup — static SQL, per entity persister:**

```sql
INSERT INTO wallet (balance, currency, customer_id, version, id) VALUES (?,?,?,?,?)
UPDATE wallet SET balance=?, currency=?, customer_id=?, version=? WHERE id=? AND version=?
DELETE FROM wallet WHERE id=? AND version=?
SELECT ... FROM wallet WHERE id=?
```

These are cached strings — reused for every operation, which is what makes batching possible and why the default UPDATE includes every column.

**At query time — JPQL/HQL translation:**

```text
JPQL string
    ↓  ANTLR parser → semantic model (SQM — Semantic Query Model, Hibernate 6)
    ↓  SQM → SQL AST
    ↓  dialect-specific rendering
SQL string  +  parameter binders  +  result-set mappers
    ↓
cached in QueryPlanCache, keyed by the query string
```

Criteria queries skip the parser and build the SQM tree directly — which is why they're compile-time safe but also why they *don't* benefit from the plan cache in the same way (Hibernate 6 caches on a structural key).

Native queries skip translation entirely; Hibernate only binds parameters and maps the result set.

## 10. Event listeners

Every operation in Hibernate is an **event**, dispatched to a listener chain. This is the extension point the whole framework is built on.

```text
session.persist(entity)
    ↓
PersistEvent
    ↓
DefaultPersistEventListener
    ↓
cascade to associations → ActionQueue.addAction(EntityInsertAction)
```

Some of the ~40 event types:

| Event | Fired by |
|---|---|
| `PersistEvent` | `persist()` |
| `MergeEvent` | `merge()` |
| `DeleteEvent` | `remove()` |
| `LoadEvent` | `find()`, `getReference()` |
| `FlushEvent` / `FlushEntityEvent` | flush |
| `DirtyCheckEvent` | dirty checking |
| `PreInsertEvent` / `PostInsertEvent` | around the INSERT |
| `PreUpdateEvent` / `PostUpdateEvent` | around the UPDATE |
| `PreLoadEvent` / `PostLoadEvent` | around hydration |

You can register your own:

```java
@Component
public class LedgerAuditListener implements PostInsertEventListener {

    @Override
    public void onPostInsert(PostInsertEvent event) {
        if (event.getEntity() instanceof LedgerEntry entry) {
            auditPublisher.record(entry);
        }
    }

    @Override
    public boolean requiresPostCommitHandling(EntityPersister persister) {
        return true;    // fire after commit, not just after the INSERT
    }
}
```

This is exactly the mechanism behind **Envers** and **Spring Data auditing** — both are just registered listeners ([[15. Advanced Hibernate]]).

> [!warning] Don't use the EntityManager inside a listener
> You are inside the flush. Loading or persisting from a `PreUpdate`/`PostInsert` listener can reorder the action queue, recurse, or `ConcurrentModificationException`. Publish a Spring event with `@TransactionalEventListener(phase = AFTER_COMMIT)` instead — see [[11. Transaction Boundaries]].

## ❓ Interview Questions

### Q1. Why is `SessionFactory` expensive and `Session` cheap?

The factory does all the one-time work at bootstrap: parsing mappings, resolving types, detecting the dialect, pre-generating SQL, building persisters and proxy classes. A Session just allocates a persistence context, an action queue and a JDBC coordinator — and it acquires a connection lazily.

### Q2. How does Hibernate implement lazy loading?

For entities, it generates a **subclass proxy** with ByteBuddy whose methods delegate to a `LazyInitializer` that loads the real object on first access (except `getId()`). For collections, it substitutes a `PersistentBag`/`PersistentSet` wrapper that loads on first access. Attribute-level laziness requires bytecode enhancement.

### Q3. Why can't an entity be `final`?

Because Hibernate creates a lazy proxy by **subclassing** it. A final class can't be subclassed, so lazy loading (and `getReference()`) would be impossible.

### Q4. How does dirty checking actually work?

At load, Hibernate stores a hydrated snapshot (`loadedState`, an `Object[]`) in the `EntityEntry`. At flush, it compares the entity's current field values against that snapshot property by property using each mapped `Type`, and schedules an update for whatever differs. It does **not** intercept setters.

### Q5. What's the cost of dirty checking, and how do you avoid it?

O(entities × fields) at every flush, plus double memory for the snapshots. Avoid with `@Transactional(readOnly = true)`, by keeping the persistence context small (`clear()` in batch loops), by using DTO projections, or by enabling **bytecode enhancement** with dirty tracking so setters record changes directly.

### Q6. What is bytecode enhancement?

A build-time rewrite of entity classes that adds change-tracking to setters (removing snapshot comparison), enables attribute-level lazy loading, and can auto-manage bidirectional associations. It's a trade-off — it complicates debugging and changes lazy semantics, so enable it only with profiler evidence.

### Q7. What is the Action Queue?

The Session's ordered buffer of pending operations. At flush it executes orphan removals, then inserts (topologically sorted by FK), updates, collection operations, and **deletes last** — regardless of the order you called the methods. It's also where JDBC batches are assembled.

### Q8. Why did my delete-then-insert cause a unique constraint violation?

Because deletes always execute **after** inserts in the action queue. Call `flush()` between the two operations, or restructure the code.

### Q9. Field access vs property access — how does Hibernate decide?

By where `@Id` is placed: on a field → field access via reflection (bypassing your getters/setters); on a getter → property access via the accessor methods. It applies to the whole class. Field access is the usual choice.

### Q10. How does a JPQL string become SQL?

An ANTLR parser builds a Semantic Query Model, which is transformed into a SQL AST and rendered by the dialect into a SQL string plus parameter binders and result mappers. The plan is cached in the `QueryPlanCache`, keyed by the query string — which is why you must use bind parameters rather than concatenating values.

### Q11. How would you hook custom logic into Hibernate's lifecycle?

Register an event listener (`PostInsertEventListener`, `PreUpdateEventListener`, …) — the same mechanism Envers and Spring Data auditing use. For anything involving the EntityManager, prefer a Spring `@TransactionalEventListener(AFTER_COMMIT)` instead of running inside the flush.

> [!tip] ⚡ Quick Recall
> - **Bootstrap** does everything expensive once: parse mappings → resolve types → detect dialect → pre-generate SQL → build `EntityPersister`s and proxy classes. Hence one `SessionFactory`, many cheap `Session`s.
> - **Session** owns: `PersistenceContext` · `ActionQueue` · `JdbcCoordinator` · `TransactionCoordinator`. **SessionFactory** owns: persisters · `QueryPlanCache` · L2 cache · statistics.
> - **Persistence context** = `entitiesByKey` (the L1 cache, keyed by entityName+id → same reference, `==` works) + `entityEntries` (holding `loadedState`, the **snapshot**).
> - **Proxies** are ByteBuddy-generated **subclasses** delegating to a `LazyInitializer`. Explains: no `final` entities, no-arg constructor required, `getClass()` weirdness, free `getReference()`, `LazyInitializationException`. Collections use `PersistentBag`/`PersistentSet` instead.
> - **Dirty checking** = compare current fields against `loadedState` at flush, per property `Type`. Setters are **not** intercepted. Cost: O(entities × fields) per flush + double memory.
> - **Bytecode enhancement** replaces snapshot diffing with setter-level change tracking, enables attribute-level laziness and association management — at the cost of debuggability. Not a default.
> - **Access type** is decided by `@Id` placement: field (reflection, bypasses accessors) vs property (calls getters/setters).
> - **Action Queue order**: orphan removals → inserts (FK-topologically sorted) → updates → collection ops → **deletes last**. Source of the delete-then-insert constraint violation.
> - **SQL generation**: static per-entity SQL at startup (enables batching, full-column UPDATE); JPQL → ANTLR → SQM → SQL AST → dialect, cached in `QueryPlanCache` by query string.
> - **Everything is an event** — `PersistEvent`, `FlushEvent`, `PostInsertEvent`… Envers and Spring Data auditing are just listeners. Don't touch the EntityManager inside one.
>
> | Observable behaviour | Internal cause |
> |---|---|
> | Entities can't be `final` | proxy = generated subclass |
> | `find()` twice → same object | `entitiesByKey` map |
> | No `update()` call needed | `loadedState` snapshot diff |
> | UPDATE sets every column | SQL pre-built at startup |
> | Delete runs after insert | action queue ordering |
> | `LazyInitializationException` | `LazyInitializer` has a closed session |
