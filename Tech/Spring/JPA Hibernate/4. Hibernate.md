**Hibernate** is an ORM framework and a JPA provider. It is the engine that converts Java objects into SQL and SQL results back into Java objects, executing everything through JDBC.

> [!info] Where this fits
> Up until now:
> - **JDBC** → standard API to talk to databases
> - **ORM** → technique of mapping Objects ↔ Tables
> - **JPA** → specification defining how an ORM should behave
>
> Now comes the implementation. Previous: [[3. JPA]].

## 1. What is Hibernate?

Hibernate is:

- An ORM Framework
- A JPA Provider
- A library that converts Java Objects into SQL and SQL results into Java Objects

So when you write:

```java
entityManager.persist(wallet);
```

Hibernate eventually generates:

```sql
INSERT INTO wallet(user_id, balance) VALUES (?, ?)
```

And executes it through JDBC.

## 2. The biggest misconception

Many developers think:

```text

```

Wrong.

Actual flow:

```text
Your Code
      │

      │
JPA Interfaces
      │
Hibernate
      │
JDBC
      │
Oracle Driver
      │
Database
```

Hibernate is the component doing the heavy lifting.

## 4. Let's build it from scratch — why does Session exist?

This is the point where almost everyone gets confused, because tutorials introduce `EntityManager`, `Session`, `PersistenceContext`, `SessionFactory` separately. In reality they are all solving **one problem**.

### Step 1: Imagine there is no JPA or Hibernate

Using JDBC:

```java
Connection con = DriverManager.getConnection(...);

PreparedStatement ps = con.prepareStatement(
    "INSERT INTO wallet(user_id, balance) VALUES (?, ?)");

ps.setLong(1, 101L);
ps.setBigDecimal(2, new BigDecimal("5000"));

ps.executeUpdate();
con.close();
```

Everything is manual. Tomorrow you want to update — again manual.

### Step 2: Hibernate says

*"What if developers work with Java objects instead?"*

Instead of this

```sql
UPDATE wallet SET balance = 90000 WHERE id = 1;
```

You simply write

```java
wallet.setBalance(new BigDecimal("90000"));
```

Question:

**Who will remember that this wallet changed?**

Someone has to.

That "someone" is the **Session** (or `EntityManager` in JPA).

### Step 3: Think of Session as a manager

Imagine a company. There are employees. Someone has to keep track of them.

```text
Office Manager
      ↓
 Employee A
 Employee B
 Employee C
```

The manager knows who entered, who left, who got promoted, who changed salary.

Hibernate's Session is exactly this manager.

### Session manages Java objects

```java
Wallet wallet = session.get(Wallet.class, 1L);
```

Now Session knows

```text
Session
   ↓
Wallet(id=1)
```

If you do

```java
wallet.setBalance(new BigDecimal("90000"));
```

Session immediately notices

```text
Wallet Changed
```

Later

```java
transaction.commit();
```

Session says

> "Wallet changed."

Generate

```sql
UPDATE wallet SET balance = 90000 WHERE id = 1;
```

You never wrote SQL.

### Where does Session store these objects?

Inside something called the **Persistence Context**.

Think of it as Session's notebook.

```text
Manager   →   Notebook   →   Wallet
                            Transaction
                            Merchant

Manager           = Session
Notebook          = Persistence Context
Items listed      = Managed Entities
```

```text
Session
│
├── Wallet(id=1)
├── Transaction(id=5)
└── Merchant(id=10)
```

That's the whole idea. Full detail in [[5. Persistence Context]].

## 5. SessionFactory

Who creates Sessions?

**SessionFactory.**

```text
SessionFactory
    creates
     Session
```

Exactly like

```text
ConnectionPool
    creates
   Connection
```

Only one SessionFactory is usually created for the entire application, because it is expensive. It contains:

- Database configuration
- Metadata
- Entity mappings
- Cache configuration
- SQL generation strategy

```text
SessionFactory
│
├── Session 1
├── Session 2
└── Session 3
```

JPA's equivalent is `EntityManagerFactory`:

```text
JPA                      Hibernate
EntityManagerFactory  →  SessionFactory
        ↓                     ↓
   EntityManager           Session
```

## 6. Session

This is the heart of Hibernate.

Everything happens through Session. You can:

- Save
- Update
- Delete
- Find
- Execute Query
- Manage Transactions

```java
Session session = sessionFactory.openSession();

Wallet wallet = session.get(Wallet.class, 1L);
```

Session represents **one conversation with the database**.

Usually:

```text
One HTTP request  →  One Session
```

## 7. Session vs EntityManager

This is asked in almost every interview.

JPA provides

```java
EntityManager
```

Hibernate provides

```java
Session
```

Remember: JPA is only a specification. It says *"every ORM should provide a manager"* and calls it `EntityManager`. Hibernate already had its own manager called `Session`, so Hibernate simply said:

> Fine. My Session will implement EntityManager.

```text
EntityManager (JPA Interface)
        ▲
        │
   Session (Hibernate)
```

Just like

```java
List<String> list = new ArrayList<>();
```

`List` → interface, `ArrayList` → implementation. Exactly the same.

You can unwrap to reach Hibernate-only features:

```java
Session session = entityManager.unwrap(Session.class);
```

### Why have both?

Because Java wanted standardisation.

Suppose tomorrow you switch to EclipseLink. Your code

```java
entityManager.persist(wallet);
```

still works. Only the implementation changes.

> [!tip] The single most important sentence
> Don't think of `EntityManager` and `Session` as two different things.
> **`EntityManager` = the standard interface defined by JPA. `Session` = Hibernate's implementation of it.**

## 8. Session lifecycle

```java
Session session = sessionFactory.openSession();
```

Now:

```text
Session Created
      ↓
Persistence Context Created
      ↓
Objects become Managed
      ↓
Transaction
      ↓
Flush
      ↓
Commit
      ↓
Close Session
```

Very important:

When Session closes, **managed objects become detached**.

That single fact causes `LazyInitializationException` → [[9. Fetching]].

## 9. Persistence Context (Hibernate view)

Every Session has one Persistence Context.

```text
Session
   ↓
Persistence Context
   ↓
Wallet(id=1)
Transaction(id=2)
Merchant(id=5)
```

Hibernate stores every loaded entity here.

Suppose

```java
Wallet wallet = session.get(Wallet.class, 1L);
```

Hibernate checks the Persistence Context first.

If already loaded → **no SQL**.

Otherwise → SQL is executed.

This is the **First Level Cache**.

## 10. Dirty Checking

One of Hibernate's greatest features.

```java
Wallet wallet = session.get(Wallet.class, 1L);

wallet.setBalance(new BigDecimal("90000"));
```

Notice: no update query. You didn't call

```java
session.update(wallet);
```

Yet Hibernate executes

```sql
UPDATE wallet SET balance = 90000 WHERE id = 1;
```

How? **Dirty Checking.**

### How it works

When the entity is loaded, Hibernate stores a snapshot:

```text
Original Snapshot
balance = 50000
```

After modification:

```text
Current Object
balance = 90000
```

Before commit, Hibernate compares them, finds a difference, and generates the `UPDATE`. Automatically.

Deep dive in [[8. Dirty Checking and Flush]].

## 11. Flush

This confuses many developers.

**Flush does NOT mean Commit.**

Flush means

> Synchronize Persistence Context with Database.

```java
wallet.setBalance(new BigDecimal("100000"));

session.flush();
```

Hibernate executes

```sql
UPDATE wallet ...
```

But the transaction is still open. You can still rollback.

Commit means the database permanently saves the transaction.

```text
Flush   →  Send SQL
Commit  →  Make changes permanent
```

## 13. Proxy objects

Suppose

```java
Wallet wallet = session.getReference(Wallet.class, 1L);
```

Does Hibernate immediately hit the database?

No.

Instead a **Proxy Object** is returned.

```text
Fake Wallet
     ↓
Real Wallet loaded later
```

Proxy delays database access until you touch a real field.

## 14. Lazy Loading

Suppose

```text
Merchant  →  Settlements
```

Do we need settlements immediately?

No.

So Hibernate loads only Merchant. Settlements remain unloaded.

```text
Merchant
    ↓
Settlements (Not Loaded)
```

Later

```java
merchant.getSettlements();
```

**NOW** Hibernate executes SQL.

This is Lazy Loading.

### Without lazy

```text
Merchant
    ↓
SELECT Merchant
SELECT Settlements
SELECT Transactions
SELECT Payouts
```

Everything loaded immediately. Wasteful.

### With lazy

```text
Merchant Loaded
Settlements Not Loaded
Transactions Not Loaded
```

Load only when needed.

---

## 15. Eager Loading

The opposite. Everything is loaded immediately.

```text
Merchant
    ↓
Settlements
    ↓
Transactions
    ↓
Payouts
```

Good for small data. Dangerous for huge relationships.

## 16. Fetch Types

JPA defines

```java
FetchType.LAZY
FetchType.EAGER
```

Hibernate implements them.

```java
@OneToMany(fetch = FetchType.LAZY)
```

Meaning: don't load immediately.

## 17. Cascade

Suppose

```text
Merchant  →  BankAccount
```

You save Merchant. Should BankAccount also save?

Maybe yes.

Without cascade:

```java
session.save(merchant);
session.save(bankAccount);
```

With cascade:

```java
session.save(merchant);
```

Hibernate automatically saves BankAccount.

Cascade types:

```text
PERSIST
MERGE
REMOVE
REFRESH
DETACH
ALL
```

Compared to plain JDBC, Hibernate provides:

- Automatic object mapping
- Dirty checking
- Caching
- Relationship management
- Transactions
- Lazy loading
- JPQL
- Database independence
- Reduced boilerplate

## ❓ Interview Questions

### Q1. What is Hibernate?

An ORM framework and JPA provider that maps Java objects to relational tables and uses JDBC internally to execute SQL.

### Q2. Is Hibernate the same as JPA?

No. JPA is a specification; Hibernate is an implementation of it (plus extra features of its own).

### Q3. What is a Session?

Hibernate's primary interface for interacting with the database. It manages entity lifecycle, the persistence context, transactions and CRUD. It represents a single unit of work.

### Q4. What is SessionFactory?

A thread-safe factory that creates `Session` objects. Created once at startup because it is expensive to initialise (it holds all mappings and metadata).

### Q5. Session vs EntityManager?

- `EntityManager` is the standard JPA interface.
- `Session` is Hibernate's native interface and implementation.
- In a Hibernate-backed application the `EntityManager` *is* backed by a `Session`; reach it via `entityManager.unwrap(Session.class)`.

### Q6. SessionFactory vs EntityManagerFactory?

Same relationship one level up: `EntityManagerFactory` is the JPA interface, `SessionFactory` is Hibernate's. Both are thread-safe, expensive, created once.

### Q7. What is Dirty Checking?

Hibernate's mechanism for automatically detecting changes to managed entities. At flush time it compares the current state with the original snapshot and generates `UPDATE` statements only where something changed.

### Q8. What is Flush?

`flush()` synchronises the in-memory persistence context with the database by executing pending SQL. It does **not** commit — changes can still be rolled back until `commit()`.

### Q9. Why is Lazy Loading useful?

It delays fetching related data until actually accessed, avoiding unnecessary queries and huge object graphs.

### Q10. `session.get()` vs `session.load()` / `getReference()`?

`get()` hits the database immediately and returns `null` if the row doesn't exist. `load()`/`getReference()` returns a **proxy** without a query; the query happens on first field access, and a missing row throws `EntityNotFoundException` at that point.

---

> [!tip] ⚡ Quick Recall
> - Hibernate = **ORM framework + JPA provider**. It generates the SQL and runs it over JDBC.
> - **Everything goes through the Session.** Session = the manager, Persistence Context = its notebook.
> - `SessionFactory` : `Session` :: `EntityManagerFactory` : `EntityManager`. Factory is expensive + thread-safe; Session is cheap + single-threaded.
> - `EntityManager` is the interface, `Session` is Hibernate's implementation — `entityManager.unwrap(Session.class)`.
> - One Session = one Persistence Context = one First Level Cache. **Close the Session → all entities become detached.**
> - **Flush ≠ Commit.** Flush sends SQL; commit makes it permanent.
> - Dirty checking = snapshot comparison at flush → automatic `UPDATE`, no `update()` call needed.
> - `getReference()` returns a **proxy**; the DB is hit only when a field is touched.
> - Lazy = load later (default for collections), Eager = load now (default for `@ManyToOne`).
