**Hibernate** is an ORM framework and a JPA provider. It is the engine that converts Java objects into SQL and SQL results back into Java objects, executing everything through JDBC.

> [!info] Where this fits
> Up until now:
> - **JDBC** → standard API to talk to databases
> - **ORM** → technique of mapping Objects ↔ Tables
> - **JPA** → specification defining how an ORM should behave
>
> Now comes the implementation. Previous: [[3. JPA]].

> [!info] The through-line of this note
> Everything here follows from one question, asked once and answered by one object.
>
> 1. Hibernate's promise is that you write `wallet.setBalance(...)` instead of an `UPDATE` (§1–§2). But that immediately raises a question: **who remembers that this wallet changed?**
> 2. Somebody has to track every loaded object and what happened to it. That somebody is the **`Session`** (§3) — and its notebook is the **Persistence Context** (§8). Every other feature in this note is that notebook being useful.
> 3. Around it: **`SessionFactory`** creates sessions (§4), the `Session` is one conversation with the database (§5), and it is simply Hibernate's implementation of JPA's `EntityManager` (§6). Its **lifecycle** (§7) determines when your entities stop being managed — which is where `LazyInitializationException` comes from.
> 4. Now the notebook pays off: it makes reads free (**first-level cache**, §8), makes `UPDATE` automatic (**dirty checking**, §9), lets Hibernate choose *when* to send SQL (**flush**, §10), and can be extended across sessions (**L2 cache**, §11).
> 5. And because it holds objects rather than rows, it can hand you a **placeholder** instead of data — **proxies**, which is the entire mechanism behind **lazy loading** (§12) and **cascade** (§13).
>
> One line to anchor everything: **the `Session` is a manager, the Persistence Context is its notebook, and every Hibernate feature is something you can do once you have that notebook.**

### 3. Why `Session` Exists ⭐

```java
wallet.setBalance(new BigDecimal("90000"));
```

```text
Items listed = Managed Entities
```

- On `commit()`, the Session says *"wallet changed"* and generates the `UPDATE`. **You never wrote SQL**

```text
SessionFactory ──creates──► Session        (like ConnectionPool → Connection)
```

- **Thread-safe** and shared

|---|---|
| `EntityManagerFactory` | `SessionFactory` |
| `EntityManager` | `Session` |

- The **heart of Hibernate** — save, update, delete, find, query, manage transactions

### 7. Session Lifecycle

```text
Session created
      ↓
Persistence Context created
      ↓
Objects become MANAGED
      ↓
Transaction → Flush → Commit
      ↓
Session closed
```

- ⭐ **When the Session closes, managed objects become DETACHED**
- ⚠️ That single fact is the cause of **`LazyInitializationException`** ([[9. Fetching]])
- A detached object is still a normal Java object — it just has nobody watching it any more

---

### 8. Persistence Context and the First Level Cache

- **Every Session has exactly one Persistence Context**, holding every entity it has loaded

```java
Wallet wallet = session.get(Wallet.class, 1L);
```

- Hibernate checks the Persistence Context **first**:
  - Already there → **no SQL at all**
  - Not there → execute SQL, then store it
- ⭐ This *is* the **First Level Cache** — it isn't a separate feature, it's a side effect of the notebook existing
- Always on, cannot be disabled, scoped to one Session

---

### 9. Dirty Checking

```java
Wallet wallet = session.get(Wallet.class, 1L);
wallet.setBalance(new BigDecimal("90000"));    // no session.update() call
// → UPDATE wallet SET balance = 90000 WHERE id = 1
```

- On load, Hibernate stores a **snapshot** of the entity's state
- Before flush it **compares current state against the snapshot**, and generates `UPDATE` only for what changed

```text
Snapshot: balance = 50000        Current: balance = 90000     → differs → UPDATE
```

- ⚠️ Cost: the snapshot doubles the memory per managed entity, and the comparison is per-entity per-flush — which is why a persistence context holding 100,000 entities is a performance problem
- Deep dive in [[8. Dirty Checking and Flush]]

---

### 10. Flush ≠ Commit ⭐

> **Flush** = synchronise the Persistence Context with the database (send the SQL).
> **Commit** = make those changes permanent.

```text
Flush   →  SQL is sent, transaction still open, rollback still possible
Commit  →  changes become permanent and visible to others
```

- `session.flush()` executes the pending `UPDATE`, but **you can still roll back**
- Hibernate also flushes automatically — before a query that might be affected, and at commit
- Confusing these two is one of the most common JPA misunderstandings

---

### 11. Caching — L1 and L2

| | **First Level Cache** | **Second Level Cache** |
|---|---|---|
| Lives in | The **Session** | The **SessionFactory** |
| Scope | One session / one request | **Shared across sessions** |
| Enabled | **Always**, cannot be turned off | **Optional**, must be configured |

- L1 is the Persistence Context itself (§8)
- L2 needs a provider (Ehcache, Hazelcast, Infinispan) and is where Redis-vs-L2 confusion usually starts
- Full treatment in [[11. Caching]]

---

### 12. Proxies, Lazy and Eager Loading

```java
Wallet wallet = session.getReference(Wallet.class, 1L);   // NO database hit
```

- Returns a **proxy** — a fake `Wallet` subclass that holds only the id
- The real query fires **on first access to a real field**

```text
Fake Wallet (proxy) ──touch a field──► SELECT ... ──► Real Wallet
```

- ⭐ **Proxies are the mechanism behind lazy loading**, not a separate feature

| | **LAZY** | **EAGER** |
|---|---|---|
| Loads related data | Only when accessed | Immediately, with the parent |
| Good for | Large / rarely-used relations | Small, always-needed data |
| Risk | `LazyInitializationException` after the session closes | Loads the world; N+1 |

```java
@OneToMany(fetch = FetchType.LAZY)
```

- Defaults and the **N+1 problem** → [[9. Fetching]]

### 13. Cascade

> You save a `Merchant`. Should its `BankAccount` be saved too?

```java
session.save(merchant);      // with cascade → BankAccount saved automatically
```

- Without cascade you save each entity explicitly
- Cascade types: `PERSIST` · `MERGE` · `REMOVE` · `REFRESH` · `DETACH` · `ALL`
- ⚠️ `ALL` includes `REMOVE` — deleting the parent deletes children. Rarely what you want on a shared reference
- Detail in [[7. Relationships]]

```text
Spring Data JPA → EntityManager → Hibernate Session → Persistence Context
```

```text
        JPA (Specification)          Hibernate (Implementation)
```

**What it gave you over raw JDBC**: automatic object mapping · dirty checking · caching · relationship management · transactions · lazy loading · JPQL · database independence · far less boilerplate.

## Why `Session` Exists — Building It From Scratch

This is the point where almost everyone gets confused, because tutorials introduce `EntityManager`, `Session`, `PersistenceContext` and `SessionFactory` separately, as four things to memorise. In reality they are all solving **one problem**.

### Step 1 — imagine there is no JPA or Hibernate

Using JDBC:

```java
Connection con = DriverManager.getConnection(...);

PreparedStatement ps = con.prepareStatement(
    "INSERT INTO wallet(user_id, balance) VALUES (?, ?)");

ps.setLong(1, 101L);
ps.setBigDecimal(2, new BigDecimal("5000"));

ps.executeUpdate();
con.close();
```

Everything is manual. Tomorrow you want to update — manual again.

### Step 2 — Hibernate's pitch

*"What if developers worked with Java objects instead?"*

Instead of this:

```sql
UPDATE wallet SET balance = 90000 WHERE id = 1;
```

you simply write:

```java
wallet.setBalance(new BigDecimal("90000"));
```

Which raises the question the entire framework is built to answer:

> **Who will remember that this wallet changed?**

Someone has to. A plain Java object has no idea it came from a database, and no idea anyone cares that its field moved. That "someone" is the **`Session`** (or `EntityManager` in JPA).

### Step 3 — think of Session as a manager

Imagine a company with employees. Someone has to keep track of them.

```text
Office Manager
      ↓
 Employee A
 Employee B
 Employee C
```

The manager knows who entered, who left, who got promoted, who changed salary.

Hibernate's `Session` is exactly this manager.

### Session manages Java objects

```java
Wallet wallet = session.get(Wallet.class, 1L);
```

Now the Session knows:

```text
Session
   ↓
Wallet(id=1)
```

If you do:

```java
wallet.setBalance(new BigDecimal("90000"));
```

the Session notices:

```text
Wallet Changed
```

Later:

```java
transaction.commit();
```

The Session says *"wallet changed"* and generates:

```sql
UPDATE wallet SET balance = 90000 WHERE id = 1;
```

**You never wrote SQL.**

### Where does Session store these objects?

Inside the **Persistence Context** — think of it as the Session's notebook.

```text
Manager   →   Notebook   →   Wallet
                             Transaction
                             Merchant

Manager           = Session
Notebook          = Persistence Context
Items listed      = Managed Entities
```

```text
Session
│
├── Wallet(id=1)
├── Transaction(id=5)
└── Merchant(id=10)
```

That's the whole idea. Hold onto it, because the rest of this note is just *"what else can you do once you have that notebook?"* — caching, dirty checking, flush ordering, lazy loading. Every one of them is a consequence. Full detail in [[5. Persistence Context]].

## `SessionFactory`

Who creates Sessions? **`SessionFactory`.**

```text
SessionFactory
    creates
     Session
```

Exactly like:

```text
ConnectionPool
    creates
   Connection
```

Only one `SessionFactory` is usually created for the entire application, because it is expensive. It contains:

- Database configuration
- Metadata
- Entity mappings
- Cache configuration
- SQL generation strategy

```text
SessionFactory
│
├── Session 1
├── Session 2
└── Session 3
```

That list is exactly *why* it's expensive: at startup Hibernate reads every entity class, resolves every mapping and relationship, and pre-generates SQL. You pay that once, at boot, so each session costs almost nothing.

JPA's equivalent is `EntityManagerFactory`:

```text
JPA                      Hibernate
EntityManagerFactory  →  SessionFactory
        ↓                     ↓
   EntityManager           Session
```

## `Session`

This is the heart of Hibernate. Everything happens through the Session. You can save, update, delete, find, execute queries and manage transactions.

```java
Session session = sessionFactory.openSession();
Wallet wallet = session.get(Wallet.class, 1L);
```

A Session represents **one conversation with the database**. Usually:

```text
One HTTP request  →  One Session
```

That scoping matters more than it looks. The Session is cheap, single-threaded and short-lived by design — because its notebook grows as you load entities, and a long-lived session is a memory leak with dirty checking attached.

## `Session` vs `EntityManager`

This is asked in almost every interview.

JPA provides `EntityManager`. Hibernate provides `Session`.

Remember: JPA is only a specification. It says *"every ORM should provide a manager"* and calls it `EntityManager`. Hibernate already had its own manager called `Session` — it predates the spec — so Hibernate simply said:

> Fine. My `Session` will implement `EntityManager`.

```text
EntityManager (JPA Interface)
        ▲
        │
   Session (Hibernate)
```

Just like:

```java
List<String> list = new ArrayList<>();
```

`List` → interface, `ArrayList` → implementation. Exactly the same relationship.

You can unwrap to reach Hibernate-only features:

```java
Session session = entityManager.unwrap(Session.class);
```

### Why have both?

Because Java wanted standardisation. Suppose tomorrow you switch to EclipseLink. Your code:

```java
entityManager.persist(wallet);
```

still works. Only the implementation changes.

> [!tip] The single most important sentence
> Don't think of `EntityManager` and `Session` as two different things.
> **`EntityManager` = the standard interface defined by JPA. `Session` = Hibernate's implementation of it.**

## Session Lifecycle

```java
Session session = sessionFactory.openSession();
```

Now:

```text
Session Created
      ↓
Persistence Context Created
      ↓
Objects become Managed
      ↓
Transaction
      ↓
Flush
      ↓
Commit
      ↓
Close Session
```

Very important:

**When the Session closes, managed objects become detached.**

> [!warning] This single fact causes `LazyInitializationException`
> A detached entity is still a perfectly normal Java object — you can read its loaded fields all day. What it no longer has is a Session behind it. So if one of its fields is an unloaded **proxy** (§12), touching it has nobody to ask, and Hibernate throws.
>
> That's why the exception always seems to happen "in the controller" or "in the JSON serializer" — those run *after* the transaction ended and the session closed. Full treatment in [[9. Fetching]].

## Persistence Context and the First Level Cache

Every Session has one Persistence Context.

```text
Session
   ↓
Persistence Context
   ↓
Wallet(id=1)
Transaction(id=2)
Merchant(id=5)
```

Hibernate stores every loaded entity here. Suppose:

```java
Wallet wallet = session.get(Wallet.class, 1L);
```

Hibernate checks the Persistence Context first:

- Already loaded → **no SQL**
- Otherwise → SQL is executed, and the result is stored

This is the **First Level Cache**.

Worth being precise about what just happened: nobody *built* a cache. The notebook exists because §3 required something to track managed objects, and once you have a map from id → object, looking in it before querying is free. The first-level cache is a **consequence** of the persistence context, not a feature bolted onto it — which is also why it can't be disabled.

A direct consequence, and a common interview question: calling `find()` twice for the same id inside one transaction fires **one** query, and returns the **same object instance** both times.

## Dirty Checking

One of Hibernate's greatest features.

```java
Wallet wallet = session.get(Wallet.class, 1L);

wallet.setBalance(new BigDecimal("90000"));
```

Notice: no update query. You didn't call:

```java
session.update(wallet);
```

Yet Hibernate executes:

```sql
UPDATE wallet SET balance = 90000 WHERE id = 1;
```

How? **Dirty Checking.**

### How it works

When the entity is loaded, Hibernate stores a **snapshot** of its state:

```text
Original Snapshot
balance = 50000
```

After modification:

```text
Current Object
balance = 90000
```

Before commit, Hibernate compares them, finds a difference, and generates the `UPDATE`. Automatically.

> [!warning] The snapshot is not free
> Every managed entity costs roughly **double** the memory — the object plus its snapshot — and every flush walks every managed entity comparing fields. That's fine for the twenty entities in a normal request, and it's why a batch job that loads 100,000 entities into one persistence context grinds to a halt.
>
> The fix (`clear()` periodically, or a stateless session) is in [[14. Performance Tuning]]. The reason is here.

Deep dive in [[8. Dirty Checking and Flush]].

## Flush ≠ Commit

This confuses many developers.

**Flush does NOT mean Commit.**

Flush means:

> Synchronize the Persistence Context with the database.

```java
wallet.setBalance(new BigDecimal("100000"));

session.flush();
```

Hibernate executes:

```sql
UPDATE wallet ...
```

But the transaction is still open. **You can still roll back.**

Commit means the database permanently saves the transaction.

```text
Flush   →  Send SQL      (still inside the transaction, still reversible)
Commit  →  Make permanent (visible to everyone else)
```

Two things follow that people trip over:

- **Hibernate flushes on its own.** Before executing a query whose results might be affected by pending changes, and at commit time. So SQL can appear in your logs at a moment you didn't ask for.
- **Flushed ≠ visible.** Another transaction still cannot see your flushed rows — they're uncommitted, and every isolation level above Read Uncommitted hides them ([[10. Transactions]]).

## Caching — L1 and L2

Hibernate has multiple caches, and mixing them up is a common interview stumble.

| | **First Level Cache** | **Second Level Cache** |
|---|---|---|
| Lives in | The `Session` | The `SessionFactory` |
| Scope | One session / one unit of work | **Shared across sessions** |
| Enabled | **Always**, cannot be disabled | **Optional**, must be configured |
| Is | The Persistence Context itself | A separate provider (Ehcache, Hazelcast, Infinispan) |

```text
Session
   ↓
Wallet 1
Wallet 2
```

The L1 cache dies with the session; the L2 cache survives it and serves every session in the application. Full treatment — including where Redis actually fits, which is usually *not* as an L2 provider — in [[11. Caching]].

## Proxies, Lazy and Eager Loading

### Proxy objects

Suppose:

```java
Wallet wallet = session.getReference(Wallet.class, 1L);
```

Does Hibernate immediately hit the database? **No.** Instead a **proxy object** is returned:

```text
Fake Wallet
     ↓
Real Wallet loaded later
```

The proxy is a generated subclass of your entity holding only the id. It delays database access until you touch a real field.

This is worth understanding as the *mechanism*, because lazy loading, `LazyInitializationException` and "why can't entities be `final`?" are all the same fact seen from different angles — Hibernate has to be able to subclass your entity to build the proxy ([[17. Hibernate Internals]]).

### Lazy loading

Suppose:

```text
Merchant  →  Settlements
```

Do we need the settlements immediately? No. So Hibernate loads only the `Merchant`; the settlements stay unloaded:

```text
Merchant
    ↓
Settlements (Not Loaded)
```

Later:

```java
merchant.getSettlements();
```

**Now** Hibernate executes the SQL. That's lazy loading.

**Without lazy:**

```text
Merchant
    ↓
SELECT Merchant
SELECT Settlements
SELECT Transactions
SELECT Payouts
```

Everything loaded immediately. Wasteful.

**With lazy:**

```text
Merchant Loaded
Settlements Not Loaded
Transactions Not Loaded
```

Load only when needed.

### Eager loading

The opposite — everything is loaded immediately:

```text
Merchant → Settlements → Transactions → Payouts
```

Good for small data. Dangerous for huge relationships, because "load the merchant" quietly becomes "load a third of the database."

### Fetch types

JPA defines the two, Hibernate implements them:

```java
@OneToMany(fetch = FetchType.LAZY)
```

Defaults and the N+1 problem → [[9. Fetching]].

> 💡 **Interview**: `get()` vs `getReference()`/`load()`? → `get()` hits the database immediately and returns `null` if the row is missing. `getReference()` returns a **proxy** with no query at all; the query fires on first field access, and a missing row throws `EntityNotFoundException` at *that* point, not at the call.

## Cascade

Suppose:

```text
Merchant  →  BankAccount
```

You save the `Merchant`. Should the `BankAccount` also be saved? Maybe yes.

Without cascade:

```java
session.save(merchant);
session.save(bankAccount);
```

With cascade:

```java
session.save(merchant);   // Hibernate saves BankAccount too
```

Cascade types:

```text
PERSIST   MERGE   REMOVE   REFRESH   DETACH   ALL
```

> [!warning] `ALL` includes `REMOVE`
> `cascade = CascadeType.ALL` on a relationship means deleting the parent deletes the children. That's correct for a genuinely owned child (an order and its line items) and dangerous for anything shared or referenced elsewhere — a merchant and its bank account may well outlive each other. Pick the specific cascade types you mean.

## ❓ Interview Questions

### Q1. What is Hibernate?

An ORM framework and JPA provider that maps Java objects to relational tables and uses JDBC internally to execute SQL.

### Q2. Is Hibernate the same as JPA?

No. JPA is a specification; Hibernate is an implementation of it (plus extra features of its own).

### Q3. What is a Session?

Hibernate's primary interface for interacting with the database. It manages entity lifecycle, the persistence context, transactions and CRUD. It represents a single unit of work.

### Q4. What is SessionFactory?

A thread-safe factory that creates `Session` objects. Created once at startup because it is expensive to initialise (it holds all mappings and metadata).

### Q5. Session vs EntityManager?

- `EntityManager` is the standard JPA interface.
- `Session` is Hibernate's native interface and implementation.
- In a Hibernate-backed application the `EntityManager` *is* backed by a `Session`; reach it via `entityManager.unwrap(Session.class)`.

### Q6. SessionFactory vs EntityManagerFactory?

Same relationship one level up: `EntityManagerFactory` is the JPA interface, `SessionFactory` is Hibernate's. Both are thread-safe, expensive, created once.

### Q7. What is Dirty Checking?

Hibernate's mechanism for automatically detecting changes to managed entities. At flush time it compares the current state with the original snapshot and generates `UPDATE` statements only where something changed.

### Q8. What is Flush?

`flush()` synchronises the in-memory persistence context with the database by executing pending SQL. It does **not** commit — changes can still be rolled back until `commit()`.

### Q9. Why is Lazy Loading useful?

It delays fetching related data until actually accessed, avoiding unnecessary queries and huge object graphs.

### Q10. `session.get()` vs `session.load()` / `getReference()`?

`get()` hits the database immediately and returns `null` if the row doesn't exist. `load()`/`getReference()` returns a **proxy** without a query; the query happens on first field access, and a missing row throws `EntityNotFoundException` at that point.

---

> [!tip] ⚡ Quick Recall
> - Hibernate = **ORM framework + JPA provider**. It generates the SQL and runs it over JDBC.
> - **Everything goes through the Session.** Session = the manager, Persistence Context = its notebook.
> - `SessionFactory` : `Session` :: `EntityManagerFactory` : `EntityManager`. Factory is expensive + thread-safe; Session is cheap + single-threaded.
> - `EntityManager` is the interface, `Session` is Hibernate's implementation — `entityManager.unwrap(Session.class)`.
> - One Session = one Persistence Context = one First Level Cache. **Close the Session → all entities become detached.**
> - **Flush ≠ Commit.** Flush sends SQL; commit makes it permanent.
> - Dirty checking = snapshot comparison at flush → automatic `UPDATE`, no `update()` call needed.
> - `getReference()` returns a **proxy**; the DB is hit only when a field is touched.
> - Lazy = load later (default for collections), Eager = load now (default for `@ManyToOne`).
