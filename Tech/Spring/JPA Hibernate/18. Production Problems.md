## 1. Connection pool exhaustion

```text
Pool size = 10
```

Ten requests arrive:

```text
Request 1  → Connection 1
...
Request 10 → Connection 10
```

Everything is fine.

Now request 11 arrives. No connection is available.

```text
Request 11
    ↓
Waiting...
```

After `connectionTimeout`:

```text
SQLTransientConnectionException:
  HikariPool-1 - Connection is not available, request timed out after 30000ms
```

This is *the* production JPA error. Note what it looks like from outside: **every endpoint** gets slow at once, including ones that don't touch the failing table. The pool is a shared resource, so one bad query poisons the entire application.

### Why does it happen?

**Reason 1 — long-running transactions**

```java
@Transactional
public void process() {
    callExternalApi();       // 15 seconds
    repository.save(...);
}
```

The database connection is held **during the external API call**, even though the database isn't being used at all.

Better:

```java
public void process() {
    var result = callExternalApi();   // outside the transaction
    save(result);                     // short transaction
}

@Transactional
public void save(Result r) {
    repository.save(...);
}
```

Hold the connection only when you actually need it.

**Reason 2 — pool too small for the traffic**

```text
Pool = 10
Traffic = 500 concurrent users
```

If each request needs the DB for 50 ms, a pool of 10 supports ~200 req/s. Beyond that, queueing is inevitable. Little's Law is your friend here: `concurrency = throughput × latency`.

**Reason 3 — connection leak**

A developer forgets to return a connection (raw `dataSource.getConnection()`, or an unclosed `Stream<T>` from a repository).

```text
10 → 9 → 8 → ... → 0
```

Turn on `leak-detection-threshold` and Hikari logs the stack trace of the borrower ([[16. Spring Boot Integration]]).

**Reason 4 — the database itself is slow.** If queries that took 5 ms now take 5 s, your effective pool capacity dropped by 1000×. The pool is the symptom; the query is the disease.

### How do you diagnose it?

- Check **Hikari metrics** — `active`, `idle`, `pending`.
- Look for **waiting threads** (`hikaricp.connections.pending > 0`).
- Look for **long transactions** (`hikaricp.connections.usage` climbing).
- Look for **leaked connections** (leak detection warnings).
- Check **slow SQL** — the DB's own slow query log, `pg_stat_activity`.
- Take a **thread dump** — if 10 threads are parked in `HikariPool.getConnection`, that's your answer; if they're all in the same JDBC call, that's your query.

## 2. Long-running transactions

```java
@Transactional
public void placeOrder() {
    updateInventory();
    sendEmail();
    callPaymentGateway();
    uploadInvoice();
}
```

Suppose the payment gateway takes **30 seconds**. The entire transaction stays open for 30 seconds.

Problems:

- **Connection occupied** the whole time
- **Locks held** the whole time — every row you touched is blocked for others
- **Other users wait**
- On Postgres, the transaction also blocks **vacuum**, so dead tuples accumulate and the table bloats

Better ordering:

```text
Payment (external)
    ↓
Email (async / after commit)
    ↓
[ Transaction starts ]
    ↓
Inventory update
    ↓
[ Transaction commits ]
```

**Only database work belongs inside the transaction.**

> [!warning] The rule that catches most of these
> **No network call inside `@Transactional`.** Not an HTTP call, not a Kafka produce, not an S3 upload, not an email. If you need to do something external after a database change, publish it with `@TransactionalEventListener(phase = AFTER_COMMIT)` or use the **outbox pattern** — see [[11. Transaction Boundaries]].

## 3. Deadlocks

Very famous interview question.

**User A** locks Account A. **User B** locks Account B.

Now A wants Account B, and B wants Account A:

```text
A
↓
Waiting for B
↑
↓
B
Waiting for A
```

Nobody can proceed. **Deadlock.**

The database detects it (Postgres after `deadlock_timeout`, ~1 s) and **kills one transaction**. Hibernate/Spring surfaces:

```text
DeadlockLoserDataAccessException
```

(or a translated exception depending on the database.)

### Prevention

**Always lock resources in the same order.**

Instead of:

```text
A → B
B → A
```

always:

```text
Lower id  →  Higher id
```

```java
// wallet-to-wallet transfer
Long first  = Math.min(fromWalletId, toWalletId);
Long second = Math.max(fromWalletId, toWalletId);

walletRepo.lockById(first);
walletRepo.lockById(second);
```

Simple. Very effective.

Also:

- Keep transactions **short** — a lock you hold for 5 ms rarely deadlocks
- Touch rows in a **deterministic order** even when you're not locking explicitly (a batch UPDATE with `ORDER BY id`)
- **Retry the loser** — a deadlock is a transient failure by definition
- Add the **right indexes** — without one, a `WHERE` may lock far more rows than you think

Lock mechanics in [[12. Locking]] and [[9. Database Concurrency]].

## 4. Retry mechanism

Two users update the same wallet. One gets:

```text
OptimisticLockException
```

Instead of failing:

```text
Read again
    ↓
Update again
    ↓
Commit
```

Usually retry **3 times**, then fail. Spring Retry is the standard tool.

```java
@Retryable(
    retryFor = { ObjectOptimisticLockingFailureException.class,
                 DeadlockLoserDataAccessException.class,
                 CannotAcquireLockException.class },
    maxAttempts = 3,
    backoff = @Backoff(delay = 50, multiplier = 2, random = true))
@Transactional
public void debit(Long walletId, BigDecimal amount) { ... }
```

### What should NOT be retried?

**Validation errors.**

```text
Age < 18
```

Retrying 100 times — still invalid. You've just turned a fast failure into a slow one.

**Retry only:**

- Deadlocks
- Temporary database failures
- Network timeouts
- Optimistic locking conflicts

> [!warning] Three rules that make retries safe
> 1. **Retry outside the transaction.** The retry must open a **new** transaction and **re-read** the entity — retrying with the same stale object fails identically. `@Retryable` on the `@Transactional` method (invoked through the proxy) gives you this.
> 2. **Make the operation idempotent.** A retried debit must not debit twice. Key it on a client-supplied idempotency key.
> 3. **Use jittered backoff.** Without `random = true`, all conflicting requests retry at the same instant and collide again.

## 5. Read replicas

Suppose one database:

```text
Master

Read
Read
Read
Write
Read
Read
```

The master becomes overloaded.

Solution:

```text
Master
   ↓
Replica 1
Replica 2
Replica 3
```

```text
Writes  →  Master
Reads   →  Replica
```

In Spring, this is usually an `AbstractRoutingDataSource`:

```text
Repository
    ↓
Routing DataSource
    ↓
Master  or  Replica
```

and the routing key is typically `TransactionSynchronizationManager.isCurrentTransactionReadOnly()` — which is exactly why `@Transactional(readOnly = true)` matters beyond Hibernate's flush optimisation ([[14. Performance Tuning]]).

### The problem: replication lag

```text
Master  → balance = 900
Replica → still 1000
```

for a few milliseconds (or seconds under load). Eventually synchronised.

This produces the most confusing class of bug in the book: **write, then immediately read your own write, and see the old value.** A user tops up their wallet, the UI refreshes, and shows the old balance.

Mitigations:

- **Read-your-own-writes** → route a read to the master when it immediately follows a write in the same user session
- Return the new state **from the write response** instead of re-fetching
- Accept staleness explicitly for genuinely read-only views (reports, dashboards, transaction history)
- Never route **balance checks that gate a debit** to a replica

### Why don't we write to replicas?

Because replication is generally **one-way**: replicas receive changes from the primary. Writing to a replica breaks consistency (and is usually physically rejected) unless you're running a specialised multi-primary architecture — which brings conflict resolution problems of its own.

## 6. Partitioning vs sharding

### Partitioning

One database. One logical table. Split internally.

```text
transaction
    ↓
2024
2025
2026
```

Still **one database**. The DB engine routes queries to the right partition; a query with no partition key still works (it just scans them all).

Benefits: faster queries when the partition key is in the `WHERE`, and — the big one — you can **drop an entire old partition instantly** instead of running a `DELETE` over 200 million rows.

### Sharding

Multiple databases.

```text
Shard 1 → Customers A–M
Shard 2 → Customers N–Z
```

Different servers. Much larger scale.

The cost: **cross-shard queries and cross-shard transactions become your problem, not the database's.** No joins across shards, no single `ORDER BY` over everything, no ACID transaction spanning two shards. Rebalancing is a project.

### Easy interview answer

```text
Partitioning  →  inside one database
Sharding      →  across multiple databases
```

Rule of thumb: **partition when the table is too big; shard when the database is too busy.** Exhaust indexing, caching, read replicas and partitioning first — sharding is the last resort.

## 7. Optimistic lock failure

Already covered mechanically in [[12. Locking]]. Here is the real production flow:

```text
User A
    ↓
Version 5
    ↓
Save
    ↓
Version 6
```

User B is still on **version 5**. Their save fails.

The correct API behaviour:

```text
409 Conflict
    ↓
Frontend reloads the current state
    ↓
User re-applies their change and retries
```

Two distinct strategies, and knowing which to use is the point:

| Situation | Handling |
|---|---|
| Machine-driven, safely repeatable (debit a wallet) | **retry automatically** with backoff |
| Human-driven edit (merchant config form) | **return 409**, let the user see the current state and decide |

Never auto-retry a human's edit — you'd silently overwrite whatever the other person just did, which is the lost update you were trying to prevent.

## 8. Detached entity problems

```text
Transaction ends
    ↓
Entity leaves the persistence context
```

The entity becomes:

```text
Detached
```

Now:

```java
wallet.setBalance(newBalance);
```

Does the database change?

**No.** Hibernate isn't tracking it anymore.

You need:

```java
entityManager.merge(wallet);
```

Now it's managed again — well, a **copy** of it is.

```text
Managed  → Hibernate tracks changes
Detached → Hibernate ignores changes
```

### The three detached-entity bugs you will actually hit

**1. `merge()` returns a different object.**

```java
Wallet merged = em.merge(detachedWallet);
merged.setBalance(...);       // ✅ this is tracked
detachedWallet.setBalance(...); // ❌ this is not
```

Always use the **return value**.

**2. `merge()` on an entity with a null id inserts a new row.** Passing a detached object with an id that no longer exists (or was never set) silently creates a duplicate instead of updating. In a payments system that's a duplicate ledger entry.

**3. `LazyInitializationException` on a detached entity.** The proxy's session is gone. Fix it by fetching what you need before the transaction ends ([[9. Fetching]]).

And the pattern that avoids all three: **don't pass entities across transaction boundaries.** Take a DTO from the web layer, load the entity fresh inside the transaction, apply the changes, let dirty checking do the UPDATE. No `merge()` at all.

Lifecycle detail in [[5. Persistence Context]].

## 9. Soft delete

Instead of:

```sql
DELETE FROM merchant WHERE id = 42;
```

add a flag:

```text
merchant
  id
  name
  is_deleted
```

Delete becomes:

```sql
UPDATE merchant SET is_deleted = true WHERE id = 42;
```

Advantages:

- **Recovery** — undo an accidental delete
- **Audit** — regulators and reconciliation need the history
- **History** — foreign keys from old transactions still resolve

In a payments system this isn't a nice-to-have. You are usually **legally required** not to destroy records.

Implementation with `@SQLDelete` + `@SQLRestriction`, and the traps (unique constraints, native queries, `find()` by id) are in [[15. Advanced Hibernate]].

## 10. Bulk operations

Need to update **500,000 rows**.

Bad:

```java
for (Transaction t : list) {
    t.setStatus(SETTLED);
}
```

Hibernate loads **500,000 objects** — plus 500,000 snapshot arrays ([[17. Hibernate Internals]]). Huge memory, then a very slow flush.

Instead:

```sql
UPDATE transaction SET status = 'SETTLED' WHERE batch_id = ?
```

```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("UPDATE Transaction t SET t.status = 'SETTLED' WHERE t.batchId = :b")
int settleBatch(@Param("b") Long batchId);
```

One SQL statement. Orders of magnitude faster.

### But — bulk SQL bypasses the persistence context

```text
Hibernate cache
    ↓
Outdated
```

The entities already loaded in memory (and in the second-level cache) still hold the old values. You need `clear()` or `refresh()` after a bulk update if managed entities might now be stale — hence `clearAutomatically = true`.

It also **skips**:

- Dirty checking and lifecycle callbacks (`@PreUpdate`, auditing)
- **Optimistic locking** — `@Version` is not incremented unless you do it in the statement
- **Cascades** — a bulk DELETE will hit foreign key constraints that a cascaded `remove()` would have handled

> [!tip] Two valid strategies, pick deliberately
> **Bulk JPQL/native** when the change is uniform and doesn't need per-row logic. **Chunked entity processing** — load 500 rows, modify, `flush()`, `clear()`, commit, repeat — when you need business logic, events or auditing per row. Chunking also keeps each transaction short, which fixes problems 1 and 2 in this note at the same time.

## 11. Monitoring & debugging

You cannot fix what you can't see. Four things to watch:

### Slow queries

One query taking **5 seconds** — investigate. Enable the database's slow query log (`log_min_duration_statement` on Postgres) and alert on p99 query time, not average.

### Connection pool

Monitor:

- Active connections
- Idle connections
- **Waiting threads** ← the leading indicator

`pending > 0` sustained means the pool is your bottleneck.

### Hibernate statistics

```properties
spring.jpa.properties.hibernate.generate_statistics=true
```

Tells you:

- Number of SQL queries (per session — this is how you spot N+1)
- Cache hit ratio
- Entity loads
- Collection loads

### SQL logging

Enable during debugging. **Never leave verbose SQL logging on in high-volume production** without considering the performance and log-volume impact — and never log **bound parameters** in production at all, because that writes card numbers and PII into your log aggregator.

### And the two that actually find the bug

- **APM / distributed tracing** (query count and time per endpoint) — this is what turns "the app is slow" into "this endpoint issues 340 queries".
- **Thread dumps** when requests are stuck. Where the threads are parked tells you immediately whether it's the pool, the DB, or an external call.

## 12. Common production mistakes

| # | Mistake | Why it's bad |
|---|---|---|
| 1 | Everything `EAGER` | loads the whole object graph on every query, can't be opted out of |
| 2 | Returning entities from REST | lazy loading during serialization, leaks the internal model |
| 3 | A 30-minute transaction | holds a connection and locks, blocks vacuum |
| 4 | `findAll()` on 20 million rows | `OutOfMemoryError`. Use pagination |
| 5 | DB call inside a loop (`for (u : list) repo.findById(...)`) | N+1 again. Use `findAllById` / a join |
| 6 | Not batching inserts | 10,000 round trips instead of 200 |
| 7 | Pool size 500 for 4 CPUs | context-switching kills throughput |
| 8 | No index on a foreign key | every join and cascade delete becomes a table scan |
| 9 | `ddl-auto: update` in production | silent schema drift, no migration history |
| 10 | Never reading the generated SQL | every problem above is visible in the log |

## 🎯 Real interview scenarios

### Scenario 1 — "Production suddenly becomes slow. Where will you look?"

A structured answer beats a lucky guess:

1. **Application CPU and memory** — GC pressure? A memory leak?
2. **HikariCP metrics** — active vs waiting connections. Waiting > 0 → pool or DB.
3. **Slow SQL logs** — did a query plan change? Did a table cross a size threshold?
4. **Database CPU and locks** — blocked queries, deadlocks, `pg_stat_activity`.
5. **Thread dumps** if requests are stuck — where are they parked?
6. **External dependencies** — Redis, Kafka, downstream APIs. Slow dependency + transaction = pool exhaustion.

The point isn't the list — it's showing you narrow from symptom to layer to cause, and that you know **what recently changed** is always question zero.

### Scenario 2 — "Payment succeeded but the balance didn't update"

Possible reasons:

- The transaction **rolled back** (and the exception was swallowed, or `UnexpectedRollbackException` after a nested failure)
- Read from a **lagging replica**
- **Async processing delay** — the write is queued, not done
- **Optimistic locking conflict** that failed silently
- **Message queue delay** or a lost message
- The update happened in a **different transaction that rolled back** afterwards

This is the scenario where the outbox pattern earns its keep ([[11. Transaction Boundaries]]).

### Scenario 3 — "Database CPU is at 100%"

Possible causes:

- **Missing indexes**
- **N+1 problem** — thousands of tiny queries
- **Full table scans**
- **Too many concurrent connections** (oversized pool)
- Poorly optimised SQL, or a plan that flipped after statistics changed

### Scenario 4 — "The application throws `LazyInitializationException`"

Fix with:

- Fetch join
- DTO projection
- `@EntityGraph`

**Don't simply switch everything to `EAGER`.** That's the answer that ends the interview.

### Scenario 5 — "Hikari connection timeout"

Possible causes:

- Pool exhausted
- Long transactions (external calls inside `@Transactional`)
- Slow queries
- Connection leak
- Database overloaded or unavailable

Note the shape of the reasoning: the timeout is never the root cause, it's the queue backing up behind one.

## 🧠 The senior-level mental model

By now you should be able to visualise the complete request flow:

```text
HTTP Request
       │
       ▼
Controller
       │
       ▼
Service
       │
       ▼
@Transactional
       │
       ▼
Spring Data JPA
       │
       ▼
EntityManager
       │
       ▼
Persistence Context
       │
       ▼
Hibernate
       │
       ▼
HikariCP
       │
       ▼
JDBC Driver
       │
       ▼
Database
```

At each layer, ask yourself:

| Layer | The question |
|---|---|
| **Controller** | Am I exposing entities or DTOs? |
| **Service** | Is the transaction scoped correctly? Any network calls inside it? |
| **Persistence Context** | Are my entities managed or detached? How many am I holding? |
| **Hibernate** | Am I causing N+1? Am I fetching efficiently? |
| **HikariCP** | Do I have enough connections? Are they held too long? |
| **Database** | Are my queries indexed? Am I hitting locks or deadlocks? |

## ❓ Interview Questions

### Q1. How do you diagnose connection pool exhaustion?

Hikari metrics (active/idle/**pending**), then long transactions, leaked connections (leak detection stack traces), and slow SQL. A thread dump tells you whether threads are parked waiting for a connection or inside a JDBC call. The timeout is always a symptom — find what's holding connections.

### Q2. Why should external API calls never be inside `@Transactional`?

Because the database connection and every row lock are held for the whole call. A 30-second gateway call with a pool of 20 means 20 concurrent requests stall the entire application. Do external work outside the transaction, or use `@TransactionalEventListener(AFTER_COMMIT)` / the outbox pattern.

### Q3. How do you prevent deadlocks?

Acquire locks in a consistent global order (e.g. ascending primary key), keep transactions short, index the columns you filter on so you don't lock more rows than needed, set a lock timeout, and retry the loser.

### Q4. What should and shouldn't be retried?

Retry transient failures: deadlocks, lock acquisition failures, optimistic lock conflicts, network timeouts. Never retry deterministic failures like validation errors or constraint violations from bad data. Retries must open a new transaction, re-read state, use jittered backoff, and be idempotent.

### Q5. How do read replicas work in a Spring application, and what breaks?

An `AbstractRoutingDataSource` routes based on `@Transactional(readOnly = true)`. What breaks is **read-your-own-writes**: replication lag means a read right after a write can return stale data. Route consistency-critical reads to the primary.

### Q6. Why can't you write to a read replica?

Replication is one-way — replicas apply changes from the primary. Writing directly would create divergent state that replication would overwrite or conflict with, unless you run a multi-primary system with explicit conflict resolution.

### Q7. Partitioning vs sharding?

Partitioning splits one table inside one database — transparent to the application, great for time-series data and instant old-data drops. Sharding splits data across separate databases — huge scale, but you lose cross-shard joins and transactions. Partition when the table is too big; shard when the database is too busy.

### Q8. A user reports "payment succeeded but balance not updated". How do you investigate?

Check whether the transaction actually committed (rollback swallowed by a catch, or `UnexpectedRollbackException`), whether the read went to a lagging replica, whether the update is async and still queued, and whether an optimistic lock conflict failed silently. Then fix the class of bug, not the row.

### Q9. Why is a bulk `@Modifying` update risky?

It bypasses the persistence context (stale in-memory entities and stale L2 cache), skips lifecycle callbacks and auditing, doesn't increment `@Version`, and doesn't cascade. Use `clearAutomatically`/`flushAutomatically`, or process in chunks when per-row logic matters.

### Q10. Production is slow. Walk me through your investigation.

App CPU/memory → Hikari pending connections → slow SQL log → DB CPU and lock waits → thread dumps → external dependencies. And in parallel: **what changed recently** — a deploy, a data volume threshold, a traffic shift, a query plan flip.

> [!tip] ⚡ Quick Recall
> - **Pool exhaustion** → `SQLTransientConnectionException` after `connectionTimeout`. Causes: long transactions · pool too small · connection leak · slow DB. Diagnose with Hikari `pending`, leak detection, slow SQL, thread dumps. Every endpoint slows at once.
> - **No network calls inside `@Transactional`.** The connection and the locks are held the whole time.
> - **Deadlock** = circular lock wait; the DB kills one → `DeadlockLoserDataAccessException`. Prevent by **locking in a consistent order** (ascending id) + short transactions + retry the loser.
> - **Retry** deadlocks, lock timeouts, optimistic conflicts, network timeouts. **Never** retry validation errors. Retries need: new transaction · re-read · jittered backoff · idempotency.
> - **Read replicas**: writes → primary, reads → replica, routed by `readOnly = true`. The trap is **replication lag / read-your-own-writes**. Never write to a replica.
> - **Partitioning** = inside one DB (drop old partitions instantly). **Sharding** = across DBs (no cross-shard joins or transactions). Partition when the table is too big; shard when the DB is too busy.
> - **Optimistic failure**: machine-driven work → auto-retry; human edit → **409 Conflict**, reload, let the user decide.
> - **Detached entities**: changes are ignored; `merge()` returns a **different** object; `merge()` with a bad id **inserts**. Best fix: don't pass entities across transaction boundaries — load fresh inside.
> - **Soft delete** for recovery/audit/history — usually a legal requirement in payments.
> - **Bulk ops**: one `@Modifying` UPDATE beats 500k loaded entities, but it bypasses the persistence context, callbacks, `@Version` and cascades. Otherwise chunk with `flush()` + `clear()`.
> - **Monitor**: slow queries · pool active/idle/**pending** · Hibernate statistics (query count = N+1 detector) · APM traces. Never log bound parameters in production.
> - **Request flow**: `Controller → Service → @Transactional → Spring Data JPA → EntityManager → Persistence Context → Hibernate → HikariCP → JDBC → Database`. Ask the right question at each layer.
>
> | Symptom | First place to look |
> |---|---|
> | All endpoints slow | pool exhaustion → what's holding connections |
> | One endpoint slow | N+1 / missing index |
> | Intermittent 500s under load | deadlocks / optimistic conflicts |
> | Stale data after a write | replica lag |
> | `OutOfMemoryError` | unbounded query / huge persistence context |
> | Changes silently lost | detached entity, or a rolled-back transaction |
