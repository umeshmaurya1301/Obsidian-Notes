**JPA (Java Persistence API)** is a Java **specification** — a set of interfaces and rules — that defines how an ORM framework should behave. It is *not* an implementation, *not* a framework, and *not* Hibernate.

> [!info] Where this fits
> This is the most misunderstood topic in the Java ecosystem. People say *"I'm using JPA"* or *"JPA is Hibernate"* — both are wrong. After this note the relationship between **JPA**, **Hibernate** and **Spring Data JPA** should be permanently clear. Previous: [[2. ORM Basics]].

## 1. Before JPA

Suppose ORM exists.

Different companies started creating ORM frameworks:

- Hibernate
- EclipseLink
- OpenJPA
- TopLink

Each had its own API.

**Hibernate**

```java
Session session = sessionFactory.openSession();

session.save(wallet);
```

**Another ORM**

```java
orm.insert(wallet);
```

**Another ORM**

```java
database.persist(wallet);
```

Every framework had different APIs.

If your company switched ORM frameworks, you had to rewrite your application.

Exactly the same problem JDBC solved for databases happened again for ORM frameworks.

---

## 2. Java's solution

Java said:

> Instead of every ORM inventing its own API, let's define one standard.

That standard is **JPA** — *Java Persistence API*.

Notice the last word:

**API**

Not framework.

Not implementation.

> [!note] Naming trivia
> Since Jakarta EE 9, the package moved from `javax.persistence` to `jakarta.persistence` and the spec is formally *Jakarta Persistence*. Spring Boot 3.x uses `jakarta.*`. Everyone still says "JPA" in interviews.

---

## 3. Think of JPA like an interface

Suppose Java defines

```java
public interface PaymentService {
    void pay();
}
```

This interface contains no implementation.

Someone has to implement it.

Likewise, JPA defines interfaces like

```java
EntityManager
EntityManagerFactory
Query
EntityTransaction
```

But JPA doesn't implement them.

Someone else does.

---

## 4. Who implements JPA?

ORM frameworks:

- Hibernate ✅
- EclipseLink
- OpenJPA

These are called **JPA Providers**.

```text
          JPA Specification
          (Interfaces / API)
                 ▲
                 │
    ----------------------------
    │            │             │
Hibernate   EclipseLink    OpenJPA
```

JPA says

> "There should be an EntityManager."

Hibernate says

> "I'll implement it."

## 5. The biggest interview questions

### Is JPA an ORM?

No. JPA is **not** an ORM framework. It is a **specification** defining how ORM frameworks should behave.

### Is Hibernate JPA?

No. Hibernate is a JPA **implementation (provider)**. It is also an ORM framework.

### Is Hibernate bigger than JPA?

Yes. Hibernate supports everything in JPA **plus** many Hibernate-specific features (`@SQLDelete`, `@Filter`, Envers, `@BatchSize`, natural IDs...).

## 6. Where Spring Boot fits

When you write

```java
public interface WalletRepository
        extends JpaRepository<Wallet, Long> {
}
```

People think Spring Boot talks directly to the database.

Not true.

Actual flow:

```text
Your Code
      │
      ▼
Spring Data JPA
      │
      ▼
JPA Interfaces
      │
      ▼
Hibernate
      │
      ▼
JDBC
      │
      ▼
Oracle Driver
      │
      ▼
Database
```

Everything eventually reaches JDBC.

## 7. What is persistence?

Persistence simply means:

> Saving the state of an object so it survives after the application stops.

Without persistence

```java
Wallet w = new Wallet();
```

Application closes. Wallet disappears.

With persistence

```java
entityManager.persist(wallet);
```

Wallet is stored in the database.

Tomorrow you restart the application. The wallet still exists.

That's persistence.

## 8. Entity

An **Entity** is simply a Java object that maps to a database table.

```java
@Entity
@Table(name = "wallet")
public class Wallet {

    @Id
    private Long id;

    private Long userId;

    private BigDecimal balance;

}
```

This class represents

```text
WALLET

ID
USER_ID
BALANCE
```

```text
One object  ↓  One row
```

Full annotation reference in [[6. Entity Mapping]].

## 9. Persistence Unit

An interview topic many people skip.

A Persistence Unit defines:

- Which database to connect to
- Which entities exist
- Which JPA provider to use
- Configuration

Earlier (without Spring Boot), this lived in `persistence.xml`:

```xml
<persistence-unit name="paymentsPU">
    <provider>org.hibernate.jpa.HibernatePersistenceProvider</provider>
    <class>com.card91.Wallet</class>
    <class>com.card91.Transaction</class>
</persistence-unit>
```

In Spring Boot, all of this is configured automatically from `application.yml`, so you rarely see `persistence.xml`. See [[16. Spring Boot Integration]].

## 10. EntityManagerFactory

Creating an `EntityManager` is expensive.

So JPA provides an `EntityManagerFactory`.

Think of it as a machine that creates `EntityManager` instances.

```text
EntityManagerFactory
        │
      creates
        ▼
   EntityManager
```

Only one factory is usually created per application. It is **thread-safe** and holds all entity metadata, mappings and configuration.

---

## 11. EntityManager

This is the heart of JPA.

Everything revolves around it.

It is responsible for:

- Persisting entities
- Finding entities
- Removing entities
- Updating entities
- Managing the persistence context
- Creating queries

Common methods:

```java
persist()
find()
merge()
remove()
flush()
clear()
detach()
refresh()
getReference()
createQuery()
```

Each one is covered in detail in [[5. Persistence Context]].

> [!warning] Not thread-safe
> `EntityManagerFactory` is thread-safe and shared. `EntityManager` is **not** — it belongs to one thread / one unit of work. Spring injects a thread-bound proxy so `@PersistenceContext EntityManager em` is safe to hold as a field.

---

## 12. Persistence Context (introduction)

Think of it as a temporary workspace managed by the `EntityManager`.

```text
Database
    ↓
EntityManager
    ↓
Persistence Context
    ↓
Java Objects
```

Every entity loaded by the `EntityManager` is stored here while it's being managed.

An entire note is dedicated to it — [[5. Persistence Context]] — because it's central to understanding JPA.

## 13. CRUD

### Create

```java
Wallet wallet = new Wallet();
wallet.setUserId(101L);

entityManager.persist(wallet);
```

Generated SQL

```sql
INSERT INTO wallet(...) VALUES (...)
```

### Read

```java
Wallet wallet = entityManager.find(Wallet.class, 1L);
```

Generated SQL

```sql
SELECT * FROM wallet WHERE id = 1
```

### Update

```java
wallet.setBalance(new BigDecimal("100000"));
```

Notice: **no update query**.

Hibernate detects the change (Dirty Checking).

Later

```sql
UPDATE wallet SET balance = 100000 WHERE id = 1
```

is generated automatically → [[8. Dirty Checking and Flush]].

### Delete

```java
entityManager.remove(wallet);
```

Generated SQL

```sql
DELETE FROM wallet WHERE id = 1
```

## 14. JPQL

JPQL = **Java Persistence Query Language**.

Instead of writing SQL against tables, you write queries against **entities**.

SQL

```sql
SELECT * FROM wallet
```

JPQL

```java
SELECT w FROM Wallet w
```

Notice you use

```text
Wallet          ← Java class name
```

not

```text
wallet          ← table name
```

And field names, not column names:

```java
SELECT w FROM Wallet w WHERE w.userId = :userId
```

even though the column is `user_id`.

You're querying Java entities. Hibernate converts JPQL into SQL for the current dialect.

```java
List<Wallet> wallets = entityManager
    .createQuery("SELECT w FROM Wallet w WHERE w.balance > :min", Wallet.class)
    .setParameter("min", new BigDecimal("1000"))
    .getResultList();
```

---

## 15. Native SQL

Sometimes JPQL isn't enough — window functions, CTEs, vendor-specific hints.

You can write normal SQL:

```java
entityManager.createNativeQuery(
    "SELECT * FROM wallet WHERE balance > 1000", Wallet.class);
```

Hibernate sends it directly to the database.

Trade-off: you lose database portability and JPQL's entity awareness.

---

## 16. Named Queries

A query defined once on the entity and referenced by name — parsed and validated at **startup**, not at first call.

```java
@Entity
@NamedQuery(
    name = "Wallet.findByUser",
    query = "SELECT w FROM Wallet w WHERE w.userId = :userId")
public class Wallet { ... }
```

```java
entityManager.createNamedQuery("Wallet.findByUser", Wallet.class)
             .setParameter("userId", 101L)
             .getResultList();
```

Benefit: a typo fails the application boot instead of a production request.

---

## 17. Criteria API

Instead of strings, you build queries using Java objects.

```java
CriteriaBuilder cb = entityManager.getCriteriaBuilder();
CriteriaQuery<Wallet> cq = cb.createQuery(Wallet.class);
Root<Wallet> root = cq.from(Wallet.class);

cq.select(root)
  .where(cb.gt(root.get("balance"), new BigDecimal("1000")));

List<Wallet> result = entityManager.createQuery(cq).getResultList();
```

Advantages:

- Type-safe
- Dynamic query building
- No string concatenation

You'll see it in applications with **complex search filters** — where the user may filter by any combination of merchant, status, date range and amount. In Spring Data JPA this is wrapped more pleasantly as **Specifications** → [[13. Spring Data JPA]].

## ⚠️ Common Misconceptions

❌ **"JPA stores data in the database."**
No. Hibernate (or another provider) performs the actual work.

❌ **"JPA talks to Oracle."**
No. Hibernate uses JDBC, which uses the Oracle driver.

❌ **"JPA is Hibernate."**
No. Hibernate implements the JPA specification.

❌ **"Spring Data JPA is a JPA provider."**
No. It is a convenience layer *above* JPA that generates repository implementations. Hibernate is still the provider underneath.

## ❓ Interview Questions

### Q1. What is JPA?

JPA (Java Persistence API) is a Java specification that defines standard APIs and interfaces for object-relational mapping and persistence. It is not an implementation.

### Q2. Is JPA a framework?

No. JPA is a specification (API), not a framework.

### Q3. What is a JPA Provider?

An ORM framework that implements the JPA specification — Hibernate, EclipseLink, OpenJPA.

### Q4. What is the difference between JPA and Hibernate?

- **JPA** defines *what* APIs and behaviour an ORM framework should provide.
- **Hibernate** implements those APIs and also offers additional features beyond the specification.

### Q5. What is an Entity?

A Java class annotated with `@Entity` that represents a table in the database. Each entity object typically corresponds to a row in that table.

### Q6. What is EntityManager?

The primary JPA interface responsible for entity lifecycle operations — persist, find, merge, remove — and for managing the persistence context.

### Q7. Why do we need EntityManagerFactory?

Creating an `EntityManager` is relatively expensive. `EntityManagerFactory` is a thread-safe factory that creates them and is typically created once for the application's lifetime.

### Q8. JPQL vs Native SQL?

JPQL is written against entity names and field names and is translated by the provider into dialect-specific SQL, so it stays portable and entity-aware. Native SQL is raw database SQL — full power and vendor features, but no portability and no automatic entity semantics.

### Q9. Why is JPA an interface / specification rather than an implementation?

So that application code compiles against a standard API and the ORM implementation can be swapped (Hibernate → EclipseLink) without rewriting business code — the same reason JDBC is an interface over database drivers.

### Q10. What is a Persistence Unit?

A named configuration that groups the entities, the JPA provider, the datasource and the provider properties. Declared in `persistence.xml` classically; auto-configured by Spring Boot in practice.

---

> [!tip] ⚡ Quick Recall
> - **JPA = specification (interfaces). Hibernate = implementation (provider).** `JPA : Hibernate :: List : ArrayList`.
> - JPA exists because every ORM had its own API — the same standardisation problem JDBC solved for drivers.
> - Hibernate ⊃ JPA — it implements the spec **and** adds extra features.
> - `EntityManagerFactory` → thread-safe, one per app. `EntityManager` → **not** thread-safe, one per unit of work.
> - `EntityManager` owns the **Persistence Context**, the in-memory workspace of managed entities.
> - Update needs **no** `update()` call — dirty checking generates it.
> - **JPQL** queries entities/fields (`Wallet`, `w.userId`); **native SQL** queries tables/columns (`wallet`, `user_id`); **Criteria API** builds queries type-safely for dynamic filters.
> - Spring Data JPA is *not* a provider — it sits above JPA; Hibernate still does the work.
>
> | JPA | Hibernate |
> |---|---|
> | `EntityManagerFactory` | `SessionFactory` |
> | `EntityManager` | `Session` |
> | Persistence Context | Persistence Context |
> | `EntityTransaction` | `Transaction` |
