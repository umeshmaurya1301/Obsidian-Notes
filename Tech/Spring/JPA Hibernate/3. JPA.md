**JPA (Java Persistence API)** is a Java **specification** — a set of interfaces and rules — that defines how an ORM framework should behave. It is *not* an implementation, *not* a framework, and *not* Hibernate.

> [!info] Where this fits
> This is the most misunderstood topic in the Java ecosystem. People say *"I'm using JPA"* or *"JPA is Hibernate"* — both are wrong. After this note the relationship between **JPA**, **Hibernate** and **Spring Data JPA** should be permanently clear. Previous: [[2. ORM Basics]].

> [!info] The through-line of this note
> The same standardisation story as JDBC, one layer up.
>
> 1. ORM frameworks arrived — Hibernate, EclipseLink, OpenJPA, TopLink — and **each invented its own API** (§1). Switch framework, rewrite the application. That is *exactly* the problem JDBC solved for database drivers, happening again one level higher.
> 2. So Java standardised the API instead of the implementation (§2). JPA defines `EntityManager` and friends; **providers** implement them (§3). `JPA : Hibernate :: List : ArrayList`.
> 3. That one idea answers every "what's the difference between…" question in this space (§4) — including where Spring Data JPA actually sits, which is *above* JPA, not beside it.
> 4. Then the vocabulary the spec gives you: **persistence** and the **entity** (§5), the **persistence unit** (§6), the **factory / manager** pair (§7), and the **persistence context** they manage (§8).
> 5. Finally what you actually type: **CRUD** (§9) — where update needs no update call — and the four ways to query: **JPQL** (§10), **native SQL and named queries** (§11), and the **Criteria API** (§12).
>
> One line to anchor everything: **JPA says what should exist; Hibernate decides how it works.**

## Short Notes

---

### 1. Before JPA — Every ORM Had Its Own API

Once ORM existed, everyone built one — and none of them agreed:

```java
session.save(wallet);        // Hibernate
orm.insert(wallet);          // another ORM
database.persist(wallet);    // another ORM
```

- Switch ORM framework → **rewrite the application**
- ⭐ This is **exactly the problem JDBC solved for databases**, recurring one layer up ([[1. JDBC Fundamentals]] §1)
- Same problem shape ⇒ same solution shape: standardise the **API**, not the implementation

---

### 2. JPA — a Specification, Not a Framework

> Instead of every ORM inventing its own API, Java defines one standard.

- Note the last word: **A-P-I**. Not framework, not implementation
- JPA defines interfaces and *no* behaviour:

```java
EntityManager   EntityManagerFactory   Query   EntityTransaction
```

- Same as declaring `interface PaymentService { void pay(); }` — somebody else has to implement it
- 📝 Since Jakarta EE 9 the package is `jakarta.persistence` (was `javax.persistence`) and the spec is formally *Jakarta Persistence*. Spring Boot 3.x uses `jakarta.*`; everyone still says "JPA"

---

### 3. JPA Providers — Who Implements It

```text
          JPA Specification
          (Interfaces / API)
                 ▲
    ┌────────────┼────────────┐
Hibernate   EclipseLink   OpenJPA
```

- JPA says *"there should be an `EntityManager`"* → Hibernate says *"I'll implement it"*
- These implementations are called **JPA providers**
- ⭐ Exactly the `List` / `ArrayList` relationship — and that's the analogy to give in an interview

---

### 4. JPA vs Hibernate vs Spring Data JPA ⭐

| Question | Answer |
|---|---|
| Is JPA an ORM? | **No** — it's a *specification* defining how ORM frameworks should behave |
| Is Hibernate JPA? | **No** — Hibernate is a JPA *provider*, and also an ORM framework |
| Is Hibernate bigger than JPA? | **Yes** — all of JPA **plus** `@SQLDelete`, `@Filter`, Envers, `@BatchSize`, natural IDs… |
| Is Spring Data JPA a provider? | **No** — it sits *above* JPA and generates repository implementations. Hibernate still does the work |

```text
Your Code → Spring Data JPA → JPA Interfaces → Hibernate → JDBC → Driver → Database
```

- Writing `interface WalletRepository extends JpaRepository<Wallet, Long>` does **not** mean Spring talks to the database
- **Everything eventually reaches JDBC** — every fact from [[1. JDBC Fundamentals]] still applies underneath

### 5. Persistence and the Entity

> **Persistence** = saving an object's state so it survives after the application stops.

- Without it: `new Wallet()` → app closes → gone. With `entityManager.persist(wallet)` → still there tomorrow
- An **Entity** is a Java class mapped to a table; one object ↔ one row

```java
@Entity
@Table(name = "wallet")
public class Wallet {
    @Id private Long id;
    private Long userId;
    private BigDecimal balance;
}
```

- Full annotation reference in [[6. Entity Mapping]]

---

### 6. Persistence Unit

A named configuration bundle. Defines **which database**, **which entities**, **which provider**, and the provider properties.

```xml
<persistence-unit name="paymentsPU">
    <provider>org.hibernate.jpa.HibernatePersistenceProvider</provider>
    <class>com.card91.Wallet</class>
</persistence-unit>
```

- Classically lived in `persistence.xml`
- In **Spring Boot it's auto-configured** from `application.yml`, which is why you rarely see the file ([[16. Spring Boot Integration]])
- Frequently skipped in revision, and occasionally asked

---

### 7. `EntityManagerFactory` vs `EntityManager`

```text
EntityManagerFactory  ──creates──►  EntityManager
```

| | `EntityManagerFactory` | `EntityManager` |
|---|---|---|
| Cost to create | **Expensive** | Cheap |
| Count | One per application | One per unit of work |
| Thread-safe | ✅ **Yes** — shared | ❌ **No** |
| Holds | Entity metadata, mappings, config | The persistence context |

- `EntityManager` is the **heart of JPA**: `persist` · `find` · `merge` · `remove` · `flush` · `clear` · `detach` · `refresh` · `getReference` · `createQuery`
- ⚠️ `EntityManager` is **not thread-safe** — Spring injects a **thread-bound proxy**, which is why `@PersistenceContext EntityManager em` is safe as a field

---

### 8. Persistence Context — Introduction

```text
Database → EntityManager → Persistence Context → Java Objects
```

- A **temporary workspace** managed by the `EntityManager`
- Every entity the `EntityManager` loads lives here while it is **managed**
- It's the reason dirty checking, the first-level cache and `LazyInitializationException` all exist
- Full treatment in [[5. Persistence Context]] — it's the single most important note in this course

---

### 9. CRUD with JPA

| Operation | Code | Generated SQL |
|---|---|---|
| **Create** | `entityManager.persist(wallet)` | `INSERT INTO wallet(...)` |
| **Read** | `entityManager.find(Wallet.class, 1L)` | `SELECT * FROM wallet WHERE id = 1` |
| **Update** | `wallet.setBalance(...)` — **no update call** | `UPDATE wallet SET balance = ...` |
| **Delete** | `entityManager.remove(wallet)` | `DELETE FROM wallet WHERE id = 1` |

- ⭐ **Update is the surprising one**: there is no `update()` method. You mutate a managed object and Hibernate detects the change — **dirty checking** ([[8. Dirty Checking and Flush]])

---

### 10. JPQL

**Java Persistence Query Language** — queries against **entities**, not tables.

```sql
SELECT * FROM wallet          -- SQL:  table name
```
```java
SELECT w FROM Wallet w        // JPQL: Java CLASS name
```

- Field names, not column names: `w.userId` even though the column is `user_id`
- Hibernate translates JPQL into SQL **for the current dialect** → portability survives

```java
entityManager.createQuery("SELECT w FROM Wallet w WHERE w.balance > :min", Wallet.class)
             .setParameter("min", new BigDecimal("1000"))
             .getResultList();
```

---

### 11. Native SQL and Named Queries

**Native SQL** — when JPQL isn't enough (window functions, CTEs, vendor hints):

```java
entityManager.createNativeQuery("SELECT * FROM wallet WHERE balance > 1000", Wallet.class);
```

- ⚠️ Trade-off: you lose **portability** and JPQL's **entity awareness**

**Named queries** — defined once on the entity, referenced by name:

```java
@NamedQuery(name = "Wallet.findByUser",
            query = "SELECT w FROM Wallet w WHERE w.userId = :userId")
```

- ⭐ Parsed and validated at **startup**, not at first call → a typo **fails the boot**, not a production request

---

### 12. Criteria API

Build queries from Java objects instead of strings:

```java
CriteriaBuilder cb  = entityManager.getCriteriaBuilder();
CriteriaQuery<Wallet> cq = cb.createQuery(Wallet.class);
Root<Wallet> root   = cq.from(Wallet.class);
cq.select(root).where(cb.gt(root.get("balance"), new BigDecimal("1000")));
```

- **Type-safe** · **dynamic** · no string concatenation
- The real use case: **complex search filters** — merchant × status × date range × amount, any combination
- Spring Data JPA wraps this more pleasantly as **Specifications** ([[13. Spring Data JPA]])

### 13. The Complete Picture and Common Misconceptions

```text
Wallet Object → EntityManager.persist() → Hibernate → JDBC → Oracle Driver → Database
```

| ❌ Misconception | ✅ Reality |
|---|---|
| "JPA stores data in the database" | The **provider** (Hibernate) does the work |
| "JPA talks to Oracle" | Hibernate → JDBC → Oracle driver |
| "JPA is Hibernate" | Hibernate **implements** JPA |
| "Spring Data JPA is a provider" | It's a layer **above** JPA; Hibernate is still the provider |

| JPA | Hibernate |
|---|---|
| `EntityManagerFactory` | `SessionFactory` |
| `EntityManager` | `Session` |
| Persistence Context | Persistence Context |
| `EntityTransaction` | `Transaction` |

# Detailed Explanation

---

## Before JPA — Every ORM Had Its Own API

Suppose ORM exists. Different companies started creating ORM frameworks — Hibernate, EclipseLink, OpenJPA, TopLink. Each had its own API.

**Hibernate:**

```java
Session session = sessionFactory.openSession();
session.save(wallet);
```

**Another ORM:**

```java
orm.insert(wallet);
```

**Another ORM:**

```java
database.persist(wallet);
```

Every framework had different APIs. If your company switched ORM frameworks, you had to **rewrite your application**.

Stop and notice what happened here: this is *exactly* the problem JDBC solved for databases ([[1. JDBC Fundamentals]] §1), recurring one layer higher. Before JDBC, coupling your code to Oracle meant rewriting to move to Postgres. Before JPA, coupling your code to Hibernate meant rewriting to move to EclipseLink.

Same problem shape, so the same solution shape applies: **standardise the API, let vendors compete on the implementation.**

---

## JPA — a Specification, Not a Framework

Java said:

> Instead of every ORM inventing its own API, let's define one standard.

That standard is **JPA** — *Java Persistence API*. Notice the last word:

**API.** Not framework. Not implementation.

> [!note] Naming trivia
> Since Jakarta EE 9, the package moved from `javax.persistence` to `jakarta.persistence` and the spec is formally *Jakarta Persistence*. Spring Boot 3.x uses `jakarta.*`. Everyone still says "JPA" in interviews.

### Think of JPA like an interface

Suppose Java defines:

```java
public interface PaymentService {
    void pay();
}
```

This interface contains no implementation. Someone has to implement it.

Likewise, JPA defines interfaces:

```java
EntityManager
EntityManagerFactory
Query
EntityTransaction
```

But JPA doesn't implement them. Someone else does.

This is worth sitting with, because it's the source of every misconception in §13: **you cannot run an application on JPA alone.** Put only the JPA jar on your classpath and nothing persists — there's no code there to do it. The specification is a contract, and a contract does no work.

---

## JPA Providers — Who Implements It

ORM frameworks implement the spec:

- Hibernate ✅
- EclipseLink
- OpenJPA

These are called **JPA Providers**.

```text
          JPA Specification
          (Interfaces / API)
                 ▲
                 │
    ----------------------------
    │            │             │
Hibernate   EclipseLink    OpenJPA
```

JPA says:

> "There should be an `EntityManager`."

Hibernate says:

> "I'll implement it."

### The analogy to use in an interview

Java defines `List` — only an interface. Who implements it? `ArrayList`, `LinkedList`, `Vector`.

```text
List                    JPA
 ▲                       ▲
 │                       │
ArrayList             Hibernate
LinkedList            EclipseLink
```

You write `List<String> list = new ArrayList<>()` and your code depends on the interface. Same idea, same benefit: swap the implementation without touching business logic.

---

## JPA vs Hibernate vs Spring Data JPA

The three questions that get asked constantly, and one that separates people who've only used Spring Boot.

### Is JPA an ORM?

**No.** JPA is not an ORM framework. It is a **specification** defining how ORM frameworks should behave.

### Is Hibernate JPA?

**No.** Hibernate is a JPA **implementation (provider)**. It is also an ORM framework in its own right — it predates JPA and had its own API (`Session`, `SessionFactory`) before the spec existed.

### Is Hibernate bigger than JPA?

**Yes.** Hibernate supports everything in JPA **plus** many Hibernate-specific features: `@SQLDelete`, `@Filter`, Envers, `@BatchSize`, natural IDs, and more.

That superset is a real trade-off, not just trivia: the moment you use a Hibernate-only feature, you've given up the portability that was the entire point of coding against the spec. Usually worth it — but know that you're spending something.

### Where Spring Boot fits

When you write:

```java
public interface WalletRepository extends JpaRepository<Wallet, Long> { }
```

people think Spring Boot talks directly to the database. Not true. The actual flow:

```text
Your Code
      │
      ▼
Spring Data JPA        ← generates the repository implementation
      │
      ▼
JPA Interfaces         ← the specification
      │
      ▼
Hibernate              ← the provider, doing the actual work
      │
      ▼
JDBC
      │
      ▼
Oracle Driver
      │
      ▼
Database
```

Everything eventually reaches JDBC.

> 💡 **Interview**: what's the difference between JPA, Hibernate and Spring Data JPA? → JPA is the **specification**, Hibernate is the **provider** that implements it, and Spring Data JPA is a **convenience layer above** JPA that generates repository implementations for you. Only one of the three actually talks to the database, and it isn't the one in the question people expect.

## Persistence and the Entity

### What is persistence?

Persistence simply means:

> Saving the state of an object so it survives after the application stops.

Without persistence:

```java
Wallet w = new Wallet();
```

The application closes. The wallet disappears — it only ever existed in heap memory.

With persistence:

```java
entityManager.persist(wallet);
```

The wallet is stored in the database. Tomorrow you restart the application and it's still there.

### Entity

An **Entity** is simply a Java object that maps to a database table.

```java
@Entity
@Table(name = "wallet")
public class Wallet {

    @Id
    private Long id;

    private Long userId;

    private BigDecimal balance;
}
```

This class represents:

```text
WALLET
  ID
  USER_ID
  BALANCE
```

```text
One object  ↓  One row
```

Full annotation reference in [[6. Entity Mapping]].

---

## Persistence Unit

An interview topic many people skip. A Persistence Unit defines:

- Which database to connect to
- Which entities exist
- Which JPA provider to use
- Configuration

Earlier (without Spring Boot), this lived in `persistence.xml`:

```xml
<persistence-unit name="paymentsPU">
    <provider>org.hibernate.jpa.HibernatePersistenceProvider</provider>
    <class>com.card91.Wallet</class>
    <class>com.card91.Transaction</class>
</persistence-unit>
```

In Spring Boot, all of this is configured automatically from `application.yml`, so you rarely see `persistence.xml`. See [[16. Spring Boot Integration]].

That auto-configuration is convenient and slightly costly: because you never write the persistence unit, it's easy not to realise there *is* one — and then "how does Spring Boot know which entities exist?" becomes a question you can't answer. (It scans for `@Entity` and builds the unit for you.)

## `EntityManagerFactory` and `EntityManager`

### `EntityManagerFactory`

Creating an `EntityManager` is expensive, so JPA provides a factory. Think of it as a machine that produces `EntityManager` instances:

```text
EntityManagerFactory
        │
      creates
        ▼
   EntityManager
```

Only one factory is usually created per application. It is **thread-safe** and holds all entity metadata, mappings and configuration — which is precisely why building it is expensive, and why you build it once.

### `EntityManager`

This is the heart of JPA. Everything revolves around it. It is responsible for:

- Persisting entities
- Finding entities
- Removing entities
- Updating entities
- Managing the persistence context
- Creating queries

Common methods:

```java
persist()   find()      merge()     remove()
flush()     clear()     detach()    refresh()
getReference()          createQuery()
```

Each one is covered in detail in [[5. Persistence Context]].

> [!warning] Not thread-safe
> `EntityManagerFactory` is thread-safe and shared. `EntityManager` is **not** — it belongs to one thread / one unit of work. Spring injects a thread-bound proxy so `@PersistenceContext EntityManager em` is safe to hold as a field.
>
> The reason follows from what it *is*: an `EntityManager` owns a persistence context full of mutable managed entities, plus a database connection. Sharing that across threads would mean sharing a mutable identity map and a transaction — which is the whole shared-mutable-state problem, in the worst possible place.

---

## Persistence Context — Introduction

Think of it as a temporary workspace managed by the `EntityManager`.

```text
Database
    ↓
EntityManager
    ↓
Persistence Context
    ↓
Java Objects
```

Every entity loaded by the `EntityManager` is stored here while it's being **managed**.

An entire note is dedicated to it — [[5. Persistence Context]] — because it's central to understanding JPA. Almost every behaviour that surprises people traces back to it: why an update needs no `update()` call, why calling `find()` twice fires one query, and why touching a lazy field outside a transaction throws.

## CRUD with JPA

### Create

```java
Wallet wallet = new Wallet();
wallet.setUserId(101L);

entityManager.persist(wallet);
```

```sql
INSERT INTO wallet(...) VALUES (...)
```

### Read

```java
Wallet wallet = entityManager.find(Wallet.class, 1L);
```

```sql
SELECT * FROM wallet WHERE id = 1
```

### Update

```java
wallet.setBalance(new BigDecimal("100000"));
```

Notice: **no update query, and no `update()` method call.**

Hibernate detects the change (Dirty Checking) and later generates:

```sql
UPDATE wallet SET balance = 100000 WHERE id = 1
```

automatically → [[8. Dirty Checking and Flush]].

This is the first genuinely non-obvious JPA behaviour. In JDBC, an `UPDATE` happens because you wrote one. Here it happens because the object changed and the persistence context noticed — which is powerful, and also why an accidental setter inside a transaction can write to the database without any visible save call.

### Delete

```java
entityManager.remove(wallet);
```

```sql
DELETE FROM wallet WHERE id = 1
```

## JPQL

JPQL = **Java Persistence Query Language**. Instead of writing SQL against tables, you write queries against **entities**.

SQL:

```sql
SELECT * FROM wallet
```

JPQL:

```java
SELECT w FROM Wallet w
```

Notice you use:

```text
Wallet          ← Java class name
```

not:

```text
wallet          ← table name
```

And field names, not column names:

```java
SELECT w FROM Wallet w WHERE w.userId = :userId
```

even though the column is `user_id`.

You're querying Java entities. Hibernate converts JPQL into SQL for the current dialect — which is what preserves the database independence the whole stack promised. Write `LIMIT` in native SQL and you've picked a database; write JPQL with `setMaxResults` and Hibernate emits `LIMIT`, `ROWNUM` or `FETCH FIRST` as appropriate.

```java
List<Wallet> wallets = entityManager
    .createQuery("SELECT w FROM Wallet w WHERE w.balance > :min", Wallet.class)
    .setParameter("min", new BigDecimal("1000"))
    .getResultList();
```

## Native SQL and Named Queries

### Native SQL

Sometimes JPQL isn't enough — window functions, CTEs, vendor-specific hints. You can write normal SQL:

```java
entityManager.createNativeQuery(
    "SELECT * FROM wallet WHERE balance > 1000", Wallet.class);
```

Hibernate sends it directly to the database.

Trade-off: you lose database portability and JPQL's entity awareness. This is the 10% escape hatch from [[2. ORM Basics]] §8 — legitimate and necessary, but each use is a small deliberate surrender of the abstraction.

### Named Queries

A query defined once on the entity and referenced by name — parsed and validated at **startup**, not at first call.

```java
@Entity
@NamedQuery(
    name = "Wallet.findByUser",
    query = "SELECT w FROM Wallet w WHERE w.userId = :userId")
public class Wallet { ... }
```

```java
entityManager.createNamedQuery("Wallet.findByUser", Wallet.class)
             .setParameter("userId", 101L)
             .getResultList();
```

The benefit is worth stating plainly: **a typo fails the application boot instead of a production request.** An inline `createQuery` string with a misspelled field name is a runtime failure on whichever code path happens to run it — possibly the rare one, possibly at 3 a.m.

---

## Criteria API

Instead of strings, you build queries using Java objects.

```java
CriteriaBuilder cb = entityManager.getCriteriaBuilder();
CriteriaQuery<Wallet> cq = cb.createQuery(Wallet.class);
Root<Wallet> root = cq.from(Wallet.class);

cq.select(root)
  .where(cb.gt(root.get("balance"), new BigDecimal("1000")));

List<Wallet> result = entityManager.createQuery(cq).getResultList();
```

Advantages:

- Type-safe
- Dynamic query building
- No string concatenation

You'll see it in applications with **complex search filters** — where the user may filter by any combination of merchant, status, date range and amount. That's the case it genuinely wins: building that with string concatenation means a tangle of `if` statements appending ` AND ...`, which is both unreadable and an injection risk if anyone gets careless.

For everything else it's verbose enough that most teams avoid it. In Spring Data JPA it's wrapped more pleasantly as **Specifications** → [[13. Spring Data JPA]].

## The Complete Picture and Common Misconceptions

```text
Wallet Object
      │
EntityManager.persist()
      │
  Hibernate
      │
    JDBC
      │
Oracle Driver
      │
Oracle Database
```

This is the flow every time you save an entity.

### ⚠️ Common misconceptions

❌ **"JPA stores data in the database."**
No. Hibernate (or another provider) performs the actual work.

❌ **"JPA talks to Oracle."**
No. Hibernate uses JDBC, which uses the Oracle driver.

❌ **"JPA is Hibernate."**
No. Hibernate implements the JPA specification.

❌ **"Spring Data JPA is a JPA provider."**
No. It is a convenience layer *above* JPA that generates repository implementations. Hibernate is still the provider underneath.

Every one of these collapses into the same correction: **JPA is a contract; contracts don't execute.** If you can hold that sentence, you can answer all four without memorising them.

### The vocabulary mapping

Hibernate predates JPA, so it has its own name for each concept as well as the standard one. Both appear in real codebases:

| JPA | Hibernate |
|---|---|
| `EntityManagerFactory` | `SessionFactory` |
| `EntityManager` | `Session` |
| Persistence Context | Persistence Context |
| `EntityTransaction` | `Transaction` |

That table is the bridge into the next note → [[4. Hibernate]].

## ❓ Interview Questions

### Q1. What is JPA?

JPA (Java Persistence API) is a Java specification that defines standard APIs and interfaces for object-relational mapping and persistence. It is not an implementation.

### Q2. Is JPA a framework?

No. JPA is a specification (API), not a framework.

### Q3. What is a JPA Provider?

An ORM framework that implements the JPA specification — Hibernate, EclipseLink, OpenJPA.

### Q4. What is the difference between JPA and Hibernate?

- **JPA** defines *what* APIs and behaviour an ORM framework should provide.
- **Hibernate** implements those APIs and also offers additional features beyond the specification.

### Q5. What is an Entity?

A Java class annotated with `@Entity` that represents a table in the database. Each entity object typically corresponds to a row in that table.

### Q6. What is EntityManager?

The primary JPA interface responsible for entity lifecycle operations — persist, find, merge, remove — and for managing the persistence context.

### Q7. Why do we need EntityManagerFactory?

Creating an `EntityManager` is relatively expensive. `EntityManagerFactory` is a thread-safe factory that creates them and is typically created once for the application's lifetime.

### Q8. JPQL vs Native SQL?

JPQL is written against entity names and field names and is translated by the provider into dialect-specific SQL, so it stays portable and entity-aware. Native SQL is raw database SQL — full power and vendor features, but no portability and no automatic entity semantics.

### Q9. Why is JPA an interface / specification rather than an implementation?

So that application code compiles against a standard API and the ORM implementation can be swapped (Hibernate → EclipseLink) without rewriting business code — the same reason JDBC is an interface over database drivers.

### Q10. What is a Persistence Unit?

A named configuration that groups the entities, the JPA provider, the datasource and the provider properties. Declared in `persistence.xml` classically; auto-configured by Spring Boot in practice.

> [!tip] ⚡ Quick Recall
> - **JPA = specification (interfaces). Hibernate = implementation (provider).** `JPA : Hibernate :: List : ArrayList`.

> - Hibernate ⊃ JPA — it implements the spec **and** adds extra features.
> - `EntityManagerFactory` → thread-safe, one per app. `EntityManager` → **not** thread-safe, one per unit of work.

> - **JPQL** queries entities/fields (`Wallet`, `w.userId`); **native SQL** queries tables/columns (`wallet`, `user_id`); **Criteria API** builds queries type-safely for dynamic filters.
> - Spring Data JPA is *not* a provider — it sits above JPA; Hibernate still does the work.
>
> | JPA | Hibernate |

> | Persistence Context | Persistence Context |
> | `EntityTransaction` | `Transaction` |
