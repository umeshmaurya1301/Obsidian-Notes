Everything so far assumed one entity maps to one table with a simple numeric key. Real systems break that assumption constantly — a `Transaction` that has three subtypes, a row keyed by two columns, a "deleted" record that must never actually be deleted, a column that must be encrypted at rest. This note covers the tools for those cases.

> [!info] Where this fits
> These are the ⭐⭐⭐ topics — not asked in every interview, but they come up fast in any real codebase, and knowing them is what makes you look like you've shipped something. Builds on [[6. Entity Mapping]]. Previous: [[14. Performance Tuning]]. Next: [[16. Spring Boot Integration]].

## 1. Inheritance mapping

Java has inheritance. Relational databases do not. Hibernate offers four ways to bridge that gap.

The domain: every payment instrument is a `PaymentMethod`, but a `Card` has a masked PAN and expiry, a `UpiHandle` has a VPA, a `NetBanking` has a bank code.

```java
public abstract class PaymentMethod {
    Long id;
    String label;
}
```

### Strategy 1 — `SINGLE_TABLE` (default)

All subclasses in one table, distinguished by a **discriminator column**.

```java
@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "method_type")
public abstract class PaymentMethod {
    @Id @GeneratedValue
    private Long id;
    private String label;
}

@Entity
@DiscriminatorValue("CARD")
public class Card extends PaymentMethod {
    private String maskedPan;
    private YearMonth expiry;
}

@Entity
@DiscriminatorValue("UPI")
public class UpiHandle extends PaymentMethod {
    private String vpa;
}
```

Table:

```text
payment_method
| id | method_type | label | masked_pan | expiry | vpa |
|----|-------------|-------|------------|--------|-----|
| 1  | CARD        | HDFC  | 4111**1111 | 2028-04| NULL|
| 2  | UPI         | GPay  | NULL       | NULL   | u@ok|
```

**Fastest** — no joins, polymorphic queries are a single SELECT.
**Cost** — every subclass column must be **nullable**, so the database can't enforce `NOT NULL` on `vpa` even though a UPI handle must have one. Wide, sparse tables.

### Strategy 2 — `JOINED`

One table per class, linked by primary key.

```java
@Entity
@Inheritance(strategy = InheritanceType.JOINED)
public abstract class PaymentMethod { ... }
```

```text
payment_method (id, label)
card          (id → FK, masked_pan, expiry)
upi_handle    (id → FK, vpa)
```

**Most normalised** — real `NOT NULL` constraints, no wasted space.
**Cost** — every read of a `Card` is a **join**; polymorphic queries join *every* subclass table.

### Strategy 3 — `TABLE_PER_CLASS`

Each concrete class gets a full standalone table with all inherited columns duplicated.

**Cost** — polymorphic queries become a `UNION ALL` across all tables, and `GenerationType.IDENTITY` can't be used (ids must be unique across tables). Rarely the right call.

### Strategy 4 — `@MappedSuperclass`

Not really inheritance mapping — just field reuse. No polymorphic queries, no table for the parent. Covered in [[6. Entity Mapping]]; this is what you want for `BaseAuditEntity`.

### Comparison

| Strategy | Tables | Joins | Nullable columns | Polymorphic query |
|---|---|---|---|---|
| `SINGLE_TABLE` | 1 | none | many (forced) | single SELECT — **fastest** |
| `JOINED` | 1 per class | yes | none | join across subclasses |
| `TABLE_PER_CLASS` | 1 per concrete class | none | none | `UNION ALL` — **slowest** |
| `@MappedSuperclass` | 1 per concrete class | none | none | not supported |

> [!tip] Which to pick
> **`SINGLE_TABLE`** when subclasses differ by only a few columns and you query polymorphically (the common case). **`JOINED`** when subclasses have many distinct columns and data integrity matters more than read speed. Avoid `TABLE_PER_CLASS` unless you never query the parent type.

## 2. Composite keys

Sometimes the natural key is two columns. A `DailyMerchantBalance` is keyed by `(merchant_id, business_date)`.

### Option A — `@Embeddable` + `@EmbeddedId`

```java
@Embeddable
public class BalanceId implements Serializable {
    private Long merchantId;
    private LocalDate businessDate;
    // equals + hashCode are MANDATORY
}

@Entity
public class DailyMerchantBalance {
    @EmbeddedId
    private BalanceId id;

    private BigDecimal closingBalance;
}
```

Query with `findById(new BalanceId(42L, date))`.

### Option B — `@IdClass`

```java
public class BalanceId implements Serializable {
    private Long merchantId;
    private LocalDate businessDate;
}

@Entity
@IdClass(BalanceId.class)
public class DailyMerchantBalance {
    @Id private Long merchantId;
    @Id private LocalDate businessDate;

    private BigDecimal closingBalance;
}
```

The fields live on the entity itself; the ID class exists only for lookups.

| | `@EmbeddedId` | `@IdClass` |
|---|---|---|
| Key fields live | in a separate object | on the entity |
| Access | `entity.getId().getMerchantId()` | `entity.getMerchantId()` |
| JPQL | `WHERE b.id.merchantId = :m` | `WHERE b.merchantId = :m` |
| Preferred | ✅ more object-oriented | when you want flat field access |

> [!warning] The ID class must be `Serializable` with correct `equals`/`hashCode`
> Hibernate uses the key object in a `HashMap` inside the persistence context. Get `equals`/`hashCode` wrong and `find()` silently returns a second copy, or your first-level cache stops working. Also make it **immutable** — mutating an id after persist corrupts the persistence context.

And a practical note: composite keys make relationships painful (`@MapsId`, multi-column `@JoinColumn`s). Many teams add a surrogate `@Id` and put a **unique constraint** on the natural pair instead. That's usually the better trade.

## 3. Soft delete

In payments you almost never physically delete a row — audit, reconciliation and regulators all want the history.

The pattern: a `deleted` flag.

```java
@Entity
@SQLDelete(sql = "UPDATE merchant SET deleted = true WHERE id = ?")
@SQLRestriction("deleted = false")     // Hibernate 6.3+; was @Where(clause = "...")
public class Merchant {
    @Id @GeneratedValue
    private Long id;

    private String name;

    private boolean deleted = false;
}
```

- `@SQLDelete` — `repository.delete(m)` now issues an UPDATE instead of a DELETE.
- `@SQLRestriction` — every SELECT Hibernate generates for this entity silently gains `AND deleted = false`.

Now `findAll()` returns only live merchants, and `delete()` hides rather than destroys.

> [!warning] Soft delete has sharp edges
> - **Native queries bypass it entirely.** `@SQLRestriction` is applied by Hibernate's SQL generator, not by the database — write native SQL and you'll see deleted rows.
> - **Unique constraints break.** Delete `vpa = 'u@ok'` and you still can't insert it again — the old row is still there. Fix with a partial index (`CREATE UNIQUE INDEX ... WHERE deleted = false`) or by including `deleted` in the constraint.
> - **You cannot query deleted rows** through that entity at all. If you need an admin view, use a native query or a second entity mapped to the same table without the restriction.
> - **Cascade doesn't cascade the soft delete** unless the child is also annotated.

A common alternative: `deleted_at TIMESTAMP NULL` instead of a boolean — you get *when* for free.

## 4. Hibernate filters

Soft delete via `@SQLRestriction` is **always on**. A **filter** is a restriction you can switch on and off per Session.

```java
@Entity
@FilterDef(name = "activeOnly", parameters = @ParamDef(name = "flag", type = Boolean.class))
@Filter(name = "activeOnly", condition = "deleted = :flag")
public class Merchant { ... }
```

Enable it for the current Session:

```java
Session session = entityManager.unwrap(Session.class);
session.enableFilter("activeOnly").setParameter("flag", false);
```

Use it when the restriction is **conditional** — an admin endpoint that must see everything, versus a customer endpoint that must not.

> [!warning] Filters do not apply to `find()` / `getReference()`
> They are applied to **queries**, not to direct primary-key loads. `em.find(Merchant.class, 7L)` will happily return a filtered-out row. Same caveat applies to `@SQLRestriction`'s reliability guarantees — never treat either as a security boundary.

## 5. Multi-tenancy

One application, many customers, and tenant A must never see tenant B's data. Hibernate supports three models:

| Model | Isolation | How Hibernate does it |
|---|---|---|
| **Database per tenant** | strongest | `MultiTenantConnectionProvider` returns a different `DataSource` per tenant |
| **Schema per tenant** | strong | same DB, `SET SCHEMA` / different schema per connection |
| **Discriminator column** | weakest | a `tenant_id` column + a Hibernate filter on every entity |

Two pieces you must supply:

```java
// 1. Who is the current tenant? (usually from a ThreadLocal set by a servlet filter / JWT claim)
@Component
public class TenantResolver implements CurrentTenantIdentifierResolver<String> {
    public String resolveCurrentTenantIdentifier() { return TenantContext.get(); }
    public boolean validateExistingCurrentSessions() { return true; }
}

// 2. Which connection does that tenant use?
@Component
public class TenantConnectionProvider implements MultiTenantConnectionProvider<String> { ... }
```

```properties
spring.jpa.properties.hibernate.multiTenancy=SCHEMA
```

> [!warning] The killer detail: connection pools and the second-level cache
> With database-per-tenant you need a pool **per tenant** — 200 tenants × 10 connections is 2000 connections. And the L2 cache is keyed by entity + id, **not** by tenant, unless the provider is tenant-aware. Getting this wrong leaks one tenant's data to another. See [[11. Caching]].

For most SaaS backends, **discriminator column + filter** is the pragmatic default; database-per-tenant is for regulated/enterprise contracts.

## 6. Auditing (Spring Data)

Who created this row, and when? You do not want to set that by hand in 40 services.

```java
@Configuration
@EnableJpaAuditing
public class AuditConfig {
    @Bean
    AuditorAware<String> auditorProvider() {
        return () -> Optional.ofNullable(SecurityContextHolder.getContext())
                             .map(c -> c.getAuthentication())
                             .map(Authentication::getName);
    }
}
```

```java
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseEntity {

    @CreatedDate
    @Column(updatable = false)
    private Instant createdAt;

    @LastModifiedDate
    private Instant updatedAt;

    @CreatedBy
    @Column(updatable = false)
    private String createdBy;

    @LastModifiedBy
    private String updatedBy;
}
```

Extend `BaseEntity` and the four fields populate themselves on insert and update.

Under the hood this is a **JPA entity listener** — the same mechanism as `@PrePersist` / `@PreUpdate`, which you can also use directly:

```java
@PrePersist
void onCreate() { this.createdAt = Instant.now(); }
```

Lifecycle callbacks: `@PrePersist`, `@PostPersist`, `@PreUpdate`, `@PostUpdate`, `@PreRemove`, `@PostRemove`, `@PostLoad`.

> [!warning] Don't call the EntityManager inside a lifecycle callback
> You are inside Hibernate's flush. Loading or saving another entity from `@PreUpdate` can corrupt the flush order or recurse. Publish an event and handle it after commit instead — see [[11. Transaction Boundaries]].

## 7. Envers — full row history

Auditing gives you *who and when*. **Hibernate Envers** gives you *every version of the row*.

```xml
<dependency>
  <groupId>org.hibernate.orm</groupId>
  <artifactId>hibernate-envers</artifactId>
</dependency>
```

```java
@Entity
@Audited
public class Merchant {
    @Id @GeneratedValue private Long id;
    private String name;
    @NotAudited private String cachedLogoUrl;   // exclude noisy fields
}
```

Envers creates:

```text
merchant_AUD   (id, REV, REVTYPE, name)     ← one row per change
REVINFO        (REV, REVTSTMP)              ← revision number + timestamp
```

`REVTYPE`: 0 = ADD, 1 = MOD, 2 = DEL.

Query the past:

```java
AuditReader reader = AuditReaderFactory.get(entityManager);

// what did merchant 42 look like at revision 7?
Merchant old = reader.find(Merchant.class, 42L, 7);

// every revision of merchant 42
List<Number> revisions = reader.getRevisions(Merchant.class, 42L);
```

**Cost:** every write becomes two writes, and the `_AUD` tables grow without bound. Audit only the entities that genuinely need a legal/forensic trail — in a payments system that's typically merchant config, KYC status and limits, **not** the transaction table (which is already immutable and append-only by design).

## 8. Attribute converters

Map a Java type the database doesn't understand — or transform a value on the way in and out.

```java
@Converter
public class MoneyConverter implements AttributeConverter<Money, BigDecimal> {

    @Override
    public BigDecimal convertToDatabaseColumn(Money money) {
        return money == null ? null : money.amount();
    }

    @Override
    public Money convertToEntityAttribute(BigDecimal value) {
        return value == null ? null : new Money(value, INR);
    }
}
```

```java
@Convert(converter = MoneyConverter.class)
private Money amount;
```

The genuinely useful payments case — **column-level encryption**:

```java
@Converter
public class EncryptedStringConverter implements AttributeConverter<String, String> {
    public String convertToDatabaseColumn(String plain)  { return crypto.encrypt(plain); }
    public String convertToEntityAttribute(String cipher){ return crypto.decrypt(cipher); }
}

@Entity
public class Customer {
    @Convert(converter = EncryptedStringConverter.class)
    private String panNumber;     // encrypted at rest, plain in Java
}
```

Add `@Converter(autoApply = true)` to apply it to **every** field of that type without annotating each one.

> [!warning] You cannot query on a converted column meaningfully
> `WHERE panNumber = :pan` compares the *encrypted* form — which works only for deterministic encryption, and never for `LIKE` or range queries. If you need lookup, store a separate hashed/blind-index column.

Converters also can't be used on `@Id`, `@Version`, or relationship fields.

## 9. Custom types

When `AttributeConverter` isn't enough — you need **one Java field to span multiple columns**, or you need control over the JDBC binding itself — you write a custom `UserType`.

```java
public class PostgresJsonbType implements UserType<JsonNode> { ... }
```

```java
@Type(PostgresJsonbType.class)
@Column(columnDefinition = "jsonb")
private JsonNode gatewayResponse;   // raw PSP payload, queryable in Postgres
```

In practice you rarely write one from scratch — the `hypersistence-utils` library ships production-quality types for `jsonb`, arrays, `INET`, intervals and more. Hibernate 6 also natively supports `@JdbcTypeCode(SqlTypes.JSON)` for JSON columns, which covers most needs.

| Need | Use |
|---|---|
| One field ↔ one column, type conversion | `AttributeConverter` ✅ |
| One field ↔ many columns | `@Embeddable` or `UserType` |
| DB-specific type (jsonb, array, hstore) | `@JdbcTypeCode(SqlTypes.JSON)` or a library `UserType` |

## ❓ Interview Questions

### Q1. What are the JPA inheritance strategies?

`SINGLE_TABLE` (one table, discriminator column — fastest, forces nullable columns), `JOINED` (one table per class, joined by PK — normalised but requires joins), `TABLE_PER_CLASS` (full table per concrete class — `UNION` on polymorphic queries), and `@MappedSuperclass` (field reuse only, no polymorphism).

### Q2. `@EmbeddedId` vs `@IdClass`?

`@EmbeddedId` puts the key fields in a separate embeddable object accessed as `entity.getId().getX()`. `@IdClass` keeps the fields flat on the entity and uses the ID class only for lookups. Both require a `Serializable` class with correct `equals`/`hashCode`.

### Q3. How do you implement soft delete?

`@SQLDelete` rewrites the DELETE as an UPDATE setting a flag, and `@SQLRestriction` (formerly `@Where`) appends the flag check to every generated SELECT. Watch out for native queries bypassing it and unique constraints colliding with hidden rows.

### Q4. `@SQLRestriction` vs `@Filter`?

`@SQLRestriction` is static and always applied. `@Filter` is enabled per-Session with parameters, so you can turn it on for user requests and off for admin ones. Neither applies to `em.find()` by primary key.

### Q5. How does Hibernate support multi-tenancy?

Database-per-tenant, schema-per-tenant, or a discriminator column. The first two need a `MultiTenantConnectionProvider` plus a `CurrentTenantIdentifierResolver`; the third is a `tenant_id` column plus a filter. Watch connection pool sizing and second-level cache keying.

### Q6. How does Spring Data auditing work?

`@EnableJpaAuditing` registers `AuditingEntityListener`, a JPA entity listener that populates `@CreatedDate`, `@LastModifiedDate`, `@CreatedBy` and `@LastModifiedBy` on persist and update. `AuditorAware` supplies the current user.

### Q7. What is Envers and when would you use it?

Hibernate's versioning module — it writes a row to a `_AUD` table on every change, letting you reconstruct any past state. Use it for entities needing a legal/forensic trail; avoid it on high-write tables because it doubles writes and grows unbounded.

### Q8. `AttributeConverter` vs `UserType`?

`AttributeConverter` maps one field to one column — simple, portable, ideal for value objects, enums with custom codes, and encryption. `UserType` is Hibernate-specific and needed when one field spans multiple columns or you need control of the JDBC binding.

### Q9. How would you encrypt a column with JPA?

An `AttributeConverter` that encrypts in `convertToDatabaseColumn` and decrypts in `convertToEntityAttribute` — transparent to all your code. The catch: you can no longer query or index the plaintext, so add a blind-index column if you need lookups.

---

> [!tip] ⚡ Quick Recall
> - **Inheritance**: `SINGLE_TABLE` (default, fast, nullable columns) · `JOINED` (normalised, joins) · `TABLE_PER_CLASS` (UNION, avoid) · `@MappedSuperclass` (reuse only).
> - **Composite keys**: `@EmbeddedId` (preferred) or `@IdClass`. Key class must be `Serializable`, immutable, with `equals`/`hashCode`. Often better: surrogate id + unique constraint.
> - **Soft delete** = `@SQLDelete` (DELETE → UPDATE) + `@SQLRestriction` (auto `AND deleted = false`). Breaks unique constraints; native SQL bypasses it.
> - **`@Filter`** = the same idea but toggleable per Session. Neither applies to `find()` by id.
> - **Multi-tenancy**: DB-per-tenant / schema-per-tenant (`MultiTenantConnectionProvider` + `CurrentTenantIdentifierResolver`) or discriminator column. Mind pool sizing and L2 cache keys.
> - **Auditing**: `@EnableJpaAuditing` + `AuditingEntityListener` on a `@MappedSuperclass` → `@CreatedDate` / `@LastModifiedDate` / `@CreatedBy` / `@LastModifiedBy`.
> - **Envers** `@Audited` → `_AUD` + `REVINFO` tables, full row history via `AuditReader`. Doubles writes — use selectively.
> - **`AttributeConverter`** = 1 field ↔ 1 column (value objects, encryption). **`UserType`** = multi-column or DB-specific types (jsonb).
>
> | Problem | Tool |
> |---|---|
> | Subtypes in the DB | `@Inheritance` |
> | Two-column key | `@EmbeddedId` |
> | Never really delete | `@SQLDelete` + `@SQLRestriction` |
> | Conditional restriction | `@Filter` |
> | Who changed this? | Spring Data auditing |
> | What did it look like last month? | Envers |
> | Encrypt a column | `AttributeConverter` |
