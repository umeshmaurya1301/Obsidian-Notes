**ORM (Object-Relational Mapping)** is a *technique* for mapping Java objects to database tables and database rows back to Java objects, so you work with objects instead of hand-writing SQL and hand-mapping results.

> [!info] Where this fits
> Most people think the story is `JDBC → JPA → Hibernate`. The real story is:
> ```text
> Problem → JDBC → Problems with JDBC → Need for ORM → JPA Specification → Hibernate
> ```
> So before touching JPA or Hibernate, understand **why ORM was invented**. Previous note: [[1. JDBC Fundamentals]].

## 1. Let's start with a simple example

Suppose you have a table:

```text
wallet

+----+---------+---------+----------+
| id | user_id | balance | currency |
+----+---------+---------+----------+
| 1  | 101     | 5000.00 | INR      |
+----+---------+---------+----------+
```

In Java you create

```java
class Wallet {

    private Long id;

    private Long userId;

    private BigDecimal balance;

    private String currency;

}
```

Notice something?

You now have **two different worlds.**

### Java World

Everything is an Object.

```java
Wallet wallet = new Wallet();
```

### Database World

Everything is Rows and Columns.

```text
+----+---------+---------+----------+
| id | user_id | balance | currency |
+----+---------+---------+----------+
```

Java understands Objects.

Database understands Tables.

These are completely different representations.

---

## 2. The problem

Suppose you want to insert a wallet.

In Java you have

```java
Wallet w = new Wallet();

w.setUserId(101L);

w.setBalance(new BigDecimal("5000.00"));
```

Can Oracle store this Java object?

No.

Oracle has no idea what a Java object is.

It only understands SQL.

So someone has to convert

```text
Wallet Object
```

into

```sql
INSERT INTO wallet(...)
```

Similarly, when Oracle returns

```text
id = 1
user_id = 101
balance = 5000.00
```

someone has to create

```java
Wallet w = new Wallet();
```

This conversion is the entire purpose of ORM.

---

## 3. What does ORM stand for?

**Object Relational Mapping**

Break it down:

```text
Object
   ↓
Relational Table
   ↓
Mapping
```

Meaning:

> Mapping Java Objects to Database Tables and vice versa.

Visual:

```text
Java Object

  Wallet
    │
    │ Mapping
    ▼
Database Table

  wallet
```

## 4. Without ORM

Suppose you want to insert one wallet.

You'll write

```java
Connection con = ...;

PreparedStatement ps = con.prepareStatement(
    "INSERT INTO wallet(user_id, balance, currency) VALUES (?,?,?)");

ps.setLong(1, w.getUserId());
ps.setBigDecimal(2, w.getBalance());
ps.setString(3, w.getCurrency());

ps.executeUpdate();
```

Now retrieve.

```java
ResultSet rs = ps.executeQuery();

Wallet w = new Wallet();

w.setId(rs.getLong("id"));
w.setUserId(rs.getLong("user_id"));
w.setBalance(rs.getBigDecimal("balance"));
w.setCurrency(rs.getString("currency"));
```

Notice how much mapping you're writing manually.

Every table.

Every column.

Every query.

Every time.

This gets repetitive very quickly.

### Imagine 200 tables

Suppose your project has

- Customer
- Merchant
- Account
- Card
- Wallet
- Transaction
- Settlement
- Ledger Entry
- Refund
- Notification

Now imagine writing this mapping manually for all of them.

Thousands of lines.

Most of it is repetitive.

And when someone adds a column, you hunt down every query that touches that table.

---

## 5. ORM automates this

Instead of writing

```java
PreparedStatement
ResultSet
setString()
setLong()
getString()
getBigDecimal()
```

You simply write

```java
Wallet w = new Wallet();

w.setUserId(101L);
w.setBalance(new BigDecimal("5000.00"));

entityManager.persist(w);
```

ORM generates

```sql
INSERT INTO wallet(user_id, balance, currency)
VALUES (101, 5000.00, 'INR');
```

automatically.

### Reading data

Instead of

```java
ResultSet rs
Wallet w
w.setId(...)
w.setBalance(...)
```

You simply write

```java
Wallet w = entityManager.find(Wallet.class, 1L);
```

ORM generates

```sql
SELECT * FROM wallet WHERE id = 1;
```

Then creates the `Wallet` object for you.

Java Objects
      │

      │

```text

      │
      ▼

      │

```

## 7. Object-Relational Impedance Mismatch

This scary interview term simply means:

> Objects and relational databases represent data differently.

Let's see why.

### Objects have inheritance

```text
PaymentInstrument
       ↓
     Card
       ↓
   CreditCard
```

Does SQL have inheritance?

No.

### Objects have references

```java
Customer customer;

customer.getAddress();
```

Database has

```text
customer_id
```

instead of Java references.

### Objects have collections

```java
List<Transaction> transactions;
```

Database has multiple rows.

### Objects support encapsulation

```java
private BigDecimal balance;
```

Database has columns. No encapsulation.

### Objects support polymorphism

Database doesn't.

---

Everything is different.

Hence: **Object-Relational Impedance Mismatch**.

### Example

Java

```java
Customer customer = new Customer();

customer.setName("Umesh");
```

Database

```text
customer

+----+-------+
| id | name  |
+----+-------+
```

ORM maps

```text
customer.name
      ↓
   name column
```

Simple.

### Relationships

Suppose

```java
class Customer {
    List<Transaction> transactions;
}
```

Database has

```text
CUSTOMER
TRANSACTION
```

ORM knows

```text
Customer.transactions
        ↓
   Foreign Key
        ↓
   customer_id
```

Automatically. No manual coding. (Details in [[7. Relationships]].)

## 8. Advantages of ORM

**Less boilerplate** — no manual `ResultSet` mapping.

**Cleaner code** — instead of SQL everywhere, you work with Java objects.

**Productivity** — development becomes much faster.

**Database independence** — Oracle → Postgres with minimal code changes.

**Relationships become easy** — instead of writing joins you simply write

```java
customer.getTransactions();
```

**Built-in caching** — ORM frameworks provide caching → [[11. Caching]].

**Transaction management** — much easier → [[10. Transactions]].

**Dirty checking** — no manual `UPDATE` queries → [[8. Dirty Checking and Flush]].

---

## 9. Disadvantages

ORM is not magic.

Sometimes SQL is better. Examples:

- Huge reports
- Analytics
- Complex joins
- Millions of records
- Bulk updates
- Performance tuning

Native SQL can outperform ORM in such cases.

Add to that:

- **A learning curve** — persistence context, flush, lazy loading, cascade. Getting them wrong causes subtle production bugs.
- **Hidden SQL** — a single `getOrders()` can silently fire 500 queries → the N+1 problem in [[9. Fetching]].
- **Less direct control** over the exact SQL executed.

> [!warning] The senior-engineer position
> Use ORM for the 90% (CRUD, object graphs, transactional writes). Drop to native SQL/JDBC for the 10% (bulk operations, reports, complex analytical joins). Knowing *when to stop using the ORM* is the mark of experience.

## 10. JDBC vs ORM

| Feature | JDBC | ORM |
|---|---|---|
| SQL writing | Manual | Automatic (mostly) |
| Mapping | Manual | Automatic |
| Productivity | Lower | Higher |
| Learning curve | Easier | Higher |
| Performance control | Full | Less direct |
| Relationships | Manual | Automatic |
| Boilerplate | High | Low |
| Caching | None | Built-in |
| Change tracking | Manual | Automatic (dirty checking) |
| Database independence | Good | Good |

## 11. The important realization

Many beginners think ORM **replaces** JDBC.

Wrong.

ORM **uses JDBC internally**.

The flow is:

```text
Your Code
    ↓
Hibernate
    ↓
JDBC
    ↓
Oracle Driver
    ↓
Database
```

Hibernate never directly communicates with Oracle.

Eventually, everything becomes JDBC calls.

### Real example

You write

```java
walletRepository.save(wallet);
```

Hibernate converts it to

```sql
INSERT INTO wallet ...
```

Then internally

```java
PreparedStatement ps = connection.prepareStatement(...);
ps.executeUpdate();
```

Exactly like you would've written using JDBC.

Hibernate just generates it for you.

## ❓ Interview Questions

### Q1. What is ORM?

ORM (Object-Relational Mapping) is a technique that maps Java objects to relational database tables and database rows back to Java objects, allowing developers to work with objects instead of manually writing SQL and mapping results.

### Q2. Why do we need ORM?

To reduce repetitive JDBC code, automate object-to-table mapping, improve developer productivity, simplify relationship handling, and let developers focus on business logic rather than persistence code.

### Q3. Does ORM replace JDBC?

No. ORM frameworks like Hibernate use JDBC internally to communicate with the database. JDBC remains the underlying mechanism.

### Q4. What is Object-Relational Impedance Mismatch?

It refers to the differences between object-oriented concepts (objects, inheritance, references, collections, polymorphism, encapsulation) and relational concepts (tables, rows, foreign keys), which makes direct mapping non-trivial.

### Q5. When would you prefer JDBC over ORM?

When you need fine-grained control over SQL — complex reporting queries, bulk operations, performance-critical paths, or database-specific features where ORM abstractions add unnecessary overhead.

### Q6. Is ORM a tool or a technique?

A technique/concept. Hibernate, EclipseLink and OpenJPA are *frameworks* that implement the technique.

---

> [!tip] ⚡ Quick Recall
> - **ORM = technique**, not a tool. Hibernate is a *framework* implementing it.
> - It exists because Java thinks in **objects** and databases think in **rows** — the *Object-Relational Impedance Mismatch* (inheritance, references, collections, polymorphism, encapsulation have no SQL equivalent).
> - Without ORM you hand-write parameter binding and `ResultSet` mapping for every column of every table, forever.
> - ORM gives: less boilerplate, automatic mapping, easy relationships, caching, dirty checking, DB independence.
> - ORM costs: learning curve, hidden SQL (N+1), less direct control. Use native SQL for bulk/reporting.
> - **ORM does not replace JDBC — it sits on top of it.** `save()` still ends as a `PreparedStatement`.
>
> Next question this raises: *who performs the mapping?* → **ORM** is a technique, **JPA** is the specification, **Hibernate** is the implementation.
