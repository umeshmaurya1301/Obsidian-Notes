A **transaction** is a unit of work that either fully happens or fully doesn't. In Spring you get it by writing `@Transactional` — one annotation hiding a great deal of machinery.

> [!info] Where this fits
> This note is the **JPA/Spring view**: what `@Transactional` does, propagation, isolation, rollback rules, and how transactions relate to the persistence context.

## 1. ACID — quick refresher

| Property | Meaning | Payments example |
|---|---|---|
| **A**tomicity | All or nothing | Debit wallet + credit merchant — never one alone |
| **C**onsistency | Constraints hold before and after | Balance never goes negative |
| **I**solation | Concurrent transactions don't corrupt each other | Two refunds on the same txn don't both succeed |
| **D**urability | Committed data survives a crash | Settlement written before the ack is sent |

Isolation is the one that generates interview questions, because it's the one you can trade away for performance. Full treatment of anomalies (dirty read, non-repeatable read, phantom read, lost update) in [[9. Database Concurrency]].

## 2. What `@Transactional` actually does

```java
@Transactional
public void transfer(Long from, Long to, BigDecimal amount) {
    debit(from, amount);
    credit(to, amount);
}
```

Spring wraps the method in a proxy that runs, roughly, the raw JDBC you saw in [[1. JDBC Fundamentals]]:

```text
proxy.transfer()
      ↓
  connection = dataSource.getConnection()
  connection.setAutoCommit(false)
  bind connection + EntityManager to the thread
      ↓
  ┌──────────────────────────────┐
  │  your method body runs       │
  └──────────────────────────────┘
      ↓
  no exception  →  flush → commit()
  exception     →  rollback()
      ↓
  close EntityManager, return connection to the pool
```

Three consequences worth internalising:

1. **A connection is held for the entire method.** Anything slow inside a transaction — an HTTP call, an S3 upload, a `Thread.sleep` — occupies a pool connection for that whole duration. This is the #1 cause of pool exhaustion → [[18. Production Problems]].
2. **It's a proxy.** Only calls that come *through* the proxy are transactional (see section 9).
3. **The persistence context lives and dies with it.**

## 3. Transaction ↔ Persistence Context

By default in Spring, the persistence context is **transaction-scoped**:

```text
@Transactional starts
        ↓
EntityManager created  →  Persistence Context created
        ↓
   entities become MANAGED  (dirty checking active)
        ↓
@Transactional ends
        ↓
flush → commit → EntityManager closed
        ↓
   all entities become DETACHED
```

This single fact explains a family of behaviours:

- Dirty checking only works **inside** the transaction. Modify an entity outside one and nothing is saved.
- Entities returned from a `@Transactional` service method are **detached** in the controller — hence `LazyInitializationException` → [[9. Fetching]].
- The first-level cache is per transaction, so the same `findById` twice in one method is one query, but across two methods (two transactions) it's two.

> [!warning] No transaction, no update
> ```java
> public void updateBalance(Long id) {          // no @Transactional
>     Wallet w = repo.findById(id).get();
>     w.setBalance(newBalance);                 // no UPDATE ever runs
> }
> ```
> `findById` runs in its own tiny transaction (Spring Data repositories are `@Transactional(readOnly=true)` internally) and the entity is detached the moment it returns. The setter changes a detached object. Nothing happens, no error.

## 4. Rollback rules

This surprises almost everyone:

> By default, Spring rolls back on **`RuntimeException`** and **`Error`** — **not** on checked exceptions.

```java
@Transactional
public void settle() throws IOException {
    ledgerRepo.save(entry);
    throw new IOException("boom");     // ⚠️ COMMITS the save
}
```

Fix it explicitly:

```java
@Transactional(rollbackFor = Exception.class)
```

Or the reverse — commit even on a runtime exception:

```java
@Transactional(noRollbackFor = InsufficientBalanceException.class)
```

### Catching an exception does not cancel the rollback

```java
@Transactional
public void outer() {
    try {
        inner();                       // @Transactional, throws
    } catch (Exception e) {
        log.warn("ignored", e);        // you swallowed it...
    }
    repo.save(something);
}
// → UnexpectedRollbackException at commit
```

When an inner transactional method fails, the transaction is marked **rollback-only**. Swallowing the exception doesn't unmark it — Spring throws `UnexpectedRollbackException` when the outer one tries to commit.

To genuinely isolate the failure, the inner method needs `Propagation.REQUIRES_NEW`.

More scenarios in [[11. Transaction Boundaries]].

## 5. Propagation

What happens when a transactional method calls another transactional method?

| Propagation | Existing transaction | No transaction |
|---|---|---|
| **`REQUIRED`** (default) | Join it | Start a new one |
| **`REQUIRES_NEW`** | **Suspend** it, start a new independent one | Start a new one |
| `SUPPORTS` | Join it | Run non-transactionally |
| `NOT_SUPPORTED` | Suspend it, run non-transactionally | Run non-transactionally |
| `MANDATORY` | Join it | **Throw** |
| `NEVER` | **Throw** | Run non-transactionally |
| `NESTED` | Savepoint inside the current transaction | Start a new one |

### The two you must know

**`REQUIRED`** — the default. Everything joins one physical transaction, so one failure rolls back the lot. That's usually what you want for a business operation.

**`REQUIRES_NEW`** — a genuinely separate transaction with its **own database connection**.

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void writeAuditLog(String event) {
    auditRepo.save(new Audit(event));      // survives even if the caller rolls back
}
```

Use it for audit trails, failure records, and outbox rows that must persist regardless of the business outcome.

> [!warning] `REQUIRES_NEW` consumes two connections at once
> The outer transaction's connection is **held (suspended, not released)** while the inner one borrows a second. A loop calling a `REQUIRES_NEW` method can deadlock the pool: every thread holds one connection and waits for a second that no one will free. See [[18. Production Problems]].

### `NESTED` vs `REQUIRES_NEW`

`NESTED` uses a **JDBC savepoint** inside the same transaction and the same connection. The inner part can roll back to the savepoint while the outer continues — but if the **outer** rolls back, the inner goes with it. `REQUIRES_NEW` is fully independent. `NESTED` also needs a driver/`DataSource` that supports savepoints and does **not** work with JTA.

## 6. Isolation

```java
@Transactional(isolation = Isolation.REPEATABLE_READ)
```

| Level | Dirty read | Non-repeatable read | Phantom read |
|---|---|---|---|
| `READ_UNCOMMITTED` | ✅ possible | ✅ | ✅ |
| `READ_COMMITTED` | ❌ | ✅ | ✅ |
| `REPEATABLE_READ` | ❌ | ❌ | ✅ (❌ in MySQL InnoDB) |
| `SERIALIZABLE` | ❌ | ❌ | ❌ |
| `DEFAULT` | whatever the database uses | | |

Defaults: **PostgreSQL / Oracle / SQL Server → READ_COMMITTED. MySQL InnoDB → REPEATABLE_READ.**

> [!note] Hibernate does not implement isolation
> This is a favourite senior-level question. Hibernate **delegates isolation entirely to the database** — it just calls `connection.setTransactionIsolation(...)`. What Hibernate provides on top is *application-level* repeatable reads within a persistence context (the first-level cache returns the same object) and *application-level* concurrency control via `@Version` → [[12. Locking]].

Raising the isolation level is rarely the right fix for a concurrency bug — locking is usually cheaper and more precise. The anomaly-by-anomaly breakdown is in [[9. Database Concurrency]].

## 7. readOnly

```java
@Transactional(readOnly = true)
public List<TxnDto> search(SearchRequest request) { ... }
```

Three things happen:

1. **Hibernate sets `FlushMode.MANUAL`** — no automatic flush, so **dirty checking is skipped entirely**. On a query returning 10,000 entities this is a large saving.
2. **No snapshots are retained** for dirty checking → lower memory.
3. The hint is passed to the JDBC driver and, with a routing `DataSource`, can send the query to a **read replica**.

> [!warning] `readOnly = true` does not make writes fail
> With most setups a modification simply... doesn't happen. No exception, no update. That silence is the danger — a bug looks like "the save didn't work" rather than an error.

Rule: put `readOnly = true` on every query/service method that doesn't write. It's free performance.

## 8. Timeout

```java
@Transactional(timeout = 5)      // seconds
```

Sets the JDBC statement query timeout. A transaction that overruns is rolled back with `TransactionTimedOutException`.

Worth setting on anything user-facing: it converts "one slow query holds a connection and a row lock for 4 minutes" into a fast, contained failure.

## 9. Self-invocation — the classic trap

```java
@Service
public class SettlementService {

    public void processAll(List<Long> ids) {
        for (Long id : ids) {
            process(id);              // 🚨 internal call — NOT transactional
        }
    }

    @Transactional
    public void process(Long id) { ... }
}
```

`@Transactional` works through a **proxy**. An internal `this.process(id)` call never leaves the object, so the proxy is bypassed and **no transaction is started**. No error — it just silently doesn't work.

Same reason `@Transactional` is ignored on `private`, `protected`, `static` and `final` methods (with the default CGLIB proxying, a `final` class or method cannot be overridden at all).

### Fixes

**1. Move the method to another bean** (the clean answer):

```java
@Service
class SettlementProcessor {
    @Transactional
    public void process(Long id) { ... }
}
```

**2. Self-inject the proxy:**

```java
@Autowired @Lazy
private SettlementService self;

public void processAll(List<Long> ids) {
    ids.forEach(self::process);       // goes through the proxy ✅
}
```

**3. `TransactionTemplate`** — programmatic, no proxy involved:

```java
transactionTemplate.execute(status -> { ... });
```

## ❓ Interview Questions

### Q1. Why is `@Transactional` needed?

It defines the unit of work — Spring turns off auto-commit, binds one connection and one persistence context to the thread, and commits or rolls back around your method. Without it, each statement auto-commits, and JPA dirty checking never runs because the entity is detached immediately.

### Q2. What is the default rollback behaviour?

Rollback on unchecked exceptions (`RuntimeException`) and `Error`; **commit** on checked exceptions. Override with `rollbackFor` / `noRollbackFor`.

### Q3. `REQUIRED` vs `REQUIRES_NEW`?

`REQUIRED` joins an existing transaction (one commit, one rollback for everything). `REQUIRES_NEW` suspends the caller's transaction and runs in a fully independent one with its own connection — it commits or rolls back on its own. Note it holds two connections simultaneously.

### Q4. What is `NESTED` propagation?

A savepoint within the current transaction, on the same connection. The inner work can roll back independently, but an outer rollback still discards it.

### Q5. Why didn't my `@Transactional` method start a transaction?

Almost always **self-invocation** — it was called from another method of the same class, bypassing the Spring proxy. Also possible: the method is `private`/`final`, or the class isn't a Spring bean.

### Q6. I caught the exception, so why did it still roll back?

The inner transaction marked the transaction **rollback-only**. Swallowing the exception doesn't clear that flag, so commit fails with `UnexpectedRollbackException`. Use `REQUIRES_NEW` if the inner failure should truly be isolated.

### Q7. What does `readOnly = true` actually do?

Sets Hibernate's flush mode to MANUAL (skipping dirty checking and snapshot retention), hints the JDBC driver, and can route to a read replica. It does not enforce read-only at the database level.

### Q8. Does Hibernate implement isolation levels?

No. It delegates to the database via `connection.setTransactionIsolation()`. Hibernate adds *application-level* guarantees: the persistence context's repeatable reads and `@Version` optimistic locking.

### Q9. How long should a transaction be?

As short as possible. Never hold one across a network call to another service — the connection and any row locks are held for the entire round trip. Do the remote call before or after, and use the outbox pattern to stay consistent → [[11. Transaction Boundaries]].

### Q10. Where should `@Transactional` go — controller, service, or repository?

**Service layer.** That's where a business unit of work is defined. Repositories already have their own transactions for single operations; controllers should not hold database transactions across request handling.

---

> [!tip] ⚡ Quick Recall
> - `@Transactional` = `setAutoCommit(false)` + bind connection & `EntityManager` to the thread + commit/rollback. A **connection is held for the whole method** — never make network calls inside one.
> - **Persistence context is transaction-scoped.** No transaction → entity is detached → dirty checking never runs → your update silently disappears.
> - Rollback on **unchecked** exceptions only. Checked exceptions **commit** unless you set `rollbackFor`.
> - Catching an inner transactional exception doesn't stop the rollback → `UnexpectedRollbackException`.
> - **`REQUIRED`** (default) joins; **`REQUIRES_NEW`** suspends and uses a **second connection**; **`NESTED`** is a savepoint on the same connection.
> - Isolation is the **database's** job — Hibernate just forwards it. MySQL defaults to REPEATABLE_READ, Postgres/Oracle to READ_COMMITTED.
> - **`readOnly = true`** → flush mode MANUAL, no dirty checking, replica routing. Free win on every read path. It does **not** block writes; they just vanish.
> - **Self-invocation bypasses the proxy** — `this.method()` is not transactional. Also fails on `private`/`final`/`static` methods.
> - Put `@Transactional` on the **service** layer, and set a `timeout`.
