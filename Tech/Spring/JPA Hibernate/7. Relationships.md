Relationships are how JPA turns **foreign keys** into **object references**. This is the most frequently asked topic in Spring Boot interviews, and the one where most production bugs are born.

> [!info] The one example used throughout
> ```text
> Merchant
>     |
>     | 1
>     |
>     | *
> Transaction
> ```
> One merchant has many transactions. Understand these four annotations with **one** example instead of memorising definitions. Previous: [[6. Entity Mapping]].

> [!info] The through-line of this note
> One question answers almost everything here: **where does the foreign key live?**
>
> 1. There are four relationship annotations, but only one FK per relationship (§1). `@ManyToOne` **holds** it; `@OneToMany(mappedBy=…)` merely **reads the same column** from the other side. No new column is ever created for the inverse.
> 2. Two of the four have a default that will hurt you — `@ManyToOne` and `@OneToOne` are **EAGER** (§2).
> 3. `@JoinColumn` names that FK column (§3); `mappedBy` says *"I'm not the one who owns it"* (§4). And the consequence people get bitten by daily: **only the owning side's changes are written**, so adding to a collection persists nothing.
> 4. Whether to map the reverse side at all is a real design decision (§5) — an unbounded collection you never asked for is an `OutOfMemoryError` waiting for a big merchant.
> 5. `@ManyToMany` looks elegant and fails the moment the link table needs an attribute (§6) — promote it to an entity.
> 6. Then the two operations that reach across the relationship: **cascade** (§7) and **orphanRemoval** (§8), which sound similar and delete different things.
>
> One line to anchor everything: **the collection keeps your object graph correct; the owning side is what reaches the database.**

## Short Notes

---

### 1. The Four Relationship Types

Everything reduces to: **where does the foreign key live?**

**`@ManyToOne`** — the workhorse. FK lives on the **many** side:

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "merchant_id")
private Merchant merchant;
```

```text
transaction:  | id | amount | merchant_id |     ← the FK is HERE
```

**`@OneToMany`** — the reverse *view*. Creates **no new column**; reads the same FK:

```java
@OneToMany(mappedBy = "merchant")
private List<Transaction> transactions = new ArrayList<>();
```

**`@OneToOne`** — FK on whichever side you choose, usually the optional / less-loaded one.

**`@ManyToMany`** — creates a third table automatically:

```text
merchant_scheme:  | merchant_id | scheme_id |
```

> ⭐ **If you only ever use `@ManyToOne`** and never map the reverse collection, your application is simpler, faster and harder to break. Load "transactions of a merchant" with a **query**, not `merchant.getTransactions()`

---

### 2. Default Fetch Types ⭐ — memorise this

| Relationship | Default |
|---|---|
| `@ManyToOne` | **EAGER** |
| `@OneToOne` | **EAGER** |
| `@OneToMany` | LAZY |
| `@ManyToMany` | LAZY |

- ⚠️ The two `-ToOne` defaults are widely considered a **design mistake** — always override:

```java
@ManyToOne(fetch = FetchType.LAZY)
```

- ⚠️ **`@OneToOne` lazy doesn't work on the inverse side** — Hibernate can't know whether the row exists without querying, so it can't return a proxy and issues the `SELECT` anyway. Put the FK on the side you actually load, or use **`@MapsId`**
- Why this matters → [[9. Fetching]]

---

### 3. `@JoinColumn`

> **Which database column is the foreign key?**

```java
@ManyToOne
@JoinColumn(name = "merchant_id")
private Merchant merchant;
```

```text
transaction.merchant  →  merchant_id column
```

- **Interview definition**: specifies the foreign key column used to establish the relationship between two entities
- Useful extras: `nullable = false`, `foreignKey = @ForeignKey(name = "fk_txn_merchant")`

---

### 4. `mappedBy` and the Owning Side ⭐

Both classes point at each other, but the database has **one** FK. So who owns it?

```java
class Merchant   { @OneToMany(mappedBy = "merchant") List<Transaction> transactions; }
class Transaction{ @ManyToOne @JoinColumn(name="merchant_id") Merchant merchant; }
```

- `mappedBy = "merchant"` refers to the **field name in `Transaction`**
- ⚠️ **Omit `mappedBy` and Hibernate creates a join table** for the `@OneToMany` — so you get a FK *and* a redundant link table

> **The rule**: the side with **`@JoinColumn` is the OWNING side**. The side with **`mappedBy` is the INVERSE side**.

⭐ **Only the owning side's changes are written to the database:**

```java
merchant.getTransactions().add(txn);   // ❌ inverse side → NO SQL, FK stays null
txn.setMerchant(merchant);             // ✅ owning side → UPDATE transaction SET merchant_id = ?
```

> **Always write a helper on the parent** — set **both** sides:
> ```java
> public void addTransaction(Transaction txn) {
>     transactions.add(txn);      // keeps the in-memory graph correct
>     txn.setMerchant(this);      // sets the FK — the part that persists
> }
> ```

---

### 5. Unidirectional vs Bidirectional

| | Unidirectional `@ManyToOne` | Bidirectional |
|---|---|---|
| Navigation | child → parent only | both directions |
| Extra columns | none | none |
| Risk | **none** | forgetting to sync both sides; loading a huge collection |

- ⚠️ **Don't map a collection you never use.** `merchant.getTransactions()` on a merchant with 4 million transactions tries to load 4 million rows
- If a collection can grow **unbounded**, do not map it — paginate:

```java
Page<Transaction> page = txnRepository.findByMerchantId(merchantId, PageRequest.of(0, 50));
```

---

### 6. `@JoinTable` and Why `@ManyToMany` Is Discouraged

The join table can only hold **two columns**. Real link tables always grow attributes:

```text
merchant_scheme:  | merchant_id | scheme_id | enabled_at | mdr_bps |
                                              ↑ nowhere to live in @ManyToMany
```

Other problems:

- Removing one element can make Hibernate **delete all rows** for that owner and reinsert the rest (`List` without `@OrderColumn`)
- No id, no audit columns, no soft-delete flag
- Cascade behaviour is easy to get catastrophically wrong

✅ **The fix — model the join table as an entity**, two `@ManyToOne`s instead of one `@ManyToMany`:

```java
@Entity class MerchantScheme {
    @EmbeddedId MerchantSchemeId id;
    @ManyToOne @MapsId("merchantId") Merchant merchant;
    @ManyToOne @MapsId("schemeId")   Scheme scheme;
    Instant enabledAt;  Integer mdrBps;      // ← now they have a home
}
```

- If you *must* use `@ManyToMany`: use **`Set`, not `List`** — it avoids the delete-all-and-reinsert behaviour

---

### 7. Cascade

> Save the parent — should the children be saved too?

| Type | Propagates |
|---|---|
| `PERSIST` | `persist()` → children inserted |
| `MERGE` | `merge()` → children merged |
| `REMOVE` | `remove()` → children deleted |
| `REFRESH` | `refresh()` → children reloaded |
| `DETACH` | `detach()` → children detached |
| `ALL` | all of the above |

- Without cascade, only the parent is saved (and you get `TransientObjectException` if the relationship is required)

> 🚨 **`CascadeType.ALL` on `@ManyToOne` is almost always wrong**
> ```java
> @ManyToOne(cascade = CascadeType.ALL)   // deleting ONE transaction deletes the MERCHANT
> private Merchant merchant;              // …and cascades to all its other transactions
> ```
> **Cascade flows parent → child, never child → parent.** On `@ManyToOne`, use `PERSIST`/`MERGE` at most — usually nothing

---

### 8. `orphanRemoval` vs Cascade REMOVE ⭐

```java
merchant.getTransactions().remove(txn2);
```

| Without `orphanRemoval` | With `orphanRemoval = true` |
|---|---|
| Transaction survives; only the FK is nulled | `DELETE FROM transaction WHERE id = 2` |

**The distinction interviewers love:**

```text
Cascade REMOVE                  orphanRemoval
--------------                  -------------
Delete Parent                   Parent EXISTS
      ↓                              ↓
Delete Children                 Remove child from collection
                                     ↓
                                Delete Child
```

| | `CascadeType.REMOVE` | `orphanRemoval = true` |
|---|---|---|
| Trigger | **Parent is deleted** | **Child removed from the collection** |
| Parent survives? | No | **Yes** |
| Implies the other? | No | **Yes** — also deletes children with the parent |

- ✅ Use for true **parent-child composition**: Order → OrderLine, Settlement → SettlementEntry
- ❌ **Never** for a shared reference

---

### 9. Quick Summary of the Four Annotations

| Annotation | Purpose |
|---|---|
| `@JoinColumn` | Specifies the foreign key column |
| `mappedBy` | Says "I don't own the relationship" |
| `cascade` | Propagates operations to child entities |
| `orphanRemoval` | Deletes a child when removed from the parent's collection |

# Detailed Explanation

## The Four Relationship Types

Everything reduces to one question: **where does the foreign key live?** Hold that and the four annotations stop being four separate things to remember.

### `@ManyToOne` — the most important one

Many transactions belong to one merchant. The FK lives on the **many** side.

```java
@Entity
public class Transaction {

    @Id
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "merchant_id")
    private Merchant merchant;
}
```

```text
transaction

+-----+--------+-------------+
| id  | amount | merchant_id |
+-----+--------+-------------+
| 101 | 500    | 1           |
| 102 | 900    | 1           |
+-----+--------+-------------+
```

> [!tip] `@ManyToOne` is the workhorse
> If you only ever use `@ManyToOne` and never map the reverse collection, your application will be simpler, faster and harder to break. Load "transactions of a merchant" with a query instead of `merchant.getTransactions()`.
>
> This isn't minimalism for its own sake — §4's null-FK bug and §5's unbounded-collection problem are both *only possible* on the inverse side. Not mapping it removes two whole categories of failure.

### `@OneToMany` — the reverse view

```java
@Entity
public class Merchant {

    @Id
    private Long id;

    @OneToMany(mappedBy = "merchant")
    private List<Transaction> transactions = new ArrayList<>();
}
```

No new column is created. It reads the **same** `merchant_id` FK from the other side. This is the point people miss: `@OneToMany` is a *view* of data that lives elsewhere, not a mapping of its own.

### `@OneToOne`

One merchant has one bank account.

```java
@Entity
public class Merchant {

    @OneToOne
    @JoinColumn(name = "bank_account_id")
    private BankAccount bankAccount;
}
```

FK goes on whichever side you choose — usually the one that is optional or less frequently loaded.

> [!warning] `@OneToOne` is EAGER by default, and lazy doesn't work on the inverse side
> On the *non-owning* side Hibernate cannot know whether the row exists without querying, so it cannot return a proxy — it issues a SELECT anyway. Prefer putting the FK on the side you actually load, or use `@MapsId` to share the primary key.
>
> The reason is worth understanding: a proxy has to be *something*, and `null` is a legitimate value for an optional one-to-one. Hibernate can't hand you a proxy and later discover the answer was "there is no row" — so it checks up front.

### `@ManyToMany`

Many merchants use many payment schemes.

```java
@Entity
public class Merchant {

    @ManyToMany
    @JoinTable(
        name = "merchant_scheme",
        joinColumns = @JoinColumn(name = "merchant_id"),
        inverseJoinColumns = @JoinColumn(name = "scheme_id"))
    private Set<Scheme> schemes = new HashSet<>();
}
```

A third table is created automatically:

```text
merchant_scheme

+-------------+-----------+
| merchant_id | scheme_id |
+-------------+-----------+
```

## Default Fetch Types

| Relationship | Default |
|---|---|
| `@ManyToOne` | **EAGER** |
| `@OneToOne` | **EAGER** |
| `@OneToMany` | LAZY |
| `@ManyToMany` | LAZY |

The two `-ToOne` defaults are considered a design mistake. Override them:

```java
@ManyToOne(fetch = FetchType.LAZY)
```

Why they're a mistake: an eager `@ManyToOne` means every load of the child drags the parent along, and eager associations **compound**. Load a `Transaction` that eagerly fetches `Merchant`, which eagerly fetches `BankAccount`, and one `findById` becomes three queries — before anyone has asked for anything. Worse, eager fetching cannot be turned off per query, while lazy can always be *upgraded* with a `JOIN FETCH`.

The rule that follows: **map everything LAZY and fetch eagerly per query when you need it.** Full treatment → [[9. Fetching]].

## `@JoinColumn`

### What problem does it solve?

Suppose you have two tables.

**merchant**

| id | name |
|---|---|
| 1 | Acme Retail |

**transaction**

| id | amount | merchant_id |
|---|---|---|
| 101 | 500 | 1 |
| 102 | 900 | 1 |

Question: **how does Transaction know which Merchant it belongs to?**

Answer: through the foreign key.

```text
merchant_id
```

In JPA, we tell Hibernate this using `@JoinColumn`.

```java
@Entity
class Transaction {

    @Id
    Long id;

    BigDecimal amount;

    @ManyToOne
    @JoinColumn(name = "merchant_id")
    Merchant merchant;
}
```

Hibernate understands:

```text
transaction.merchant
        ↓
   merchant_id column
```

So `@JoinColumn` simply tells Hibernate:

> **Which database column is the foreign key?**

### Interview definition

`@JoinColumn` specifies the foreign key column used to establish the relationship between two entities.

Useful extras:

```java
@JoinColumn(
    name = "merchant_id",
    nullable = false,
    foreignKey = @ForeignKey(name = "fk_txn_merchant"))
```

## `mappedBy` and the Owning Side

This is probably the most confusing annotation, so let's understand *why* it exists.

Suppose you write:

```java
class Merchant {
    @OneToMany
    List<Transaction> transactions;
}
```

and:

```java
class Transaction {
    @ManyToOne
    Merchant merchant;
}
```

Question: **who owns the relationship?**

Both classes point to each other. Hibernate gets confused. Should it create `merchant_id`, or another mapping table?

Left alone, it actually creates a **join table** for the `@OneToMany` — so you end up with both a FK *and* a redundant link table. A classic surprise, and one you'll spot immediately once you know to look for a table nobody designed.

The root of the confusion is a genuine asymmetry: **Java models the relationship twice** (a field on each side), but **the database models it once** (one FK column). Something has to say which Java mapping corresponds to that one column.

To remove the ambiguity, one side is chosen as the **Owner**. The other side simply says *"I'm just referring to that relationship."* That's what `mappedBy` means.

```java
class Merchant {

    @OneToMany(mappedBy = "merchant")
    List<Transaction> transactions;
}
```

Notice:

```text
mappedBy = "merchant"
```

This refers to the field:

```java
Merchant merchant;
```

inside `Transaction` — a **field name**, not a column name. Meaning:

```text
Transaction owns the relationship
Merchant only references it
```

```text
Merchant
transactions
      ▲
      │ mappedBy
Transaction
merchant
```

### The rule

The side having `@JoinColumn` is the **Owning Side**.
The side having `mappedBy` is the **Inverse Side**.

Interviewers love this.

### Why the owning side matters in practice

**Only the owning side's changes are written to the database.**

```java
merchant.getTransactions().add(txn);   // inverse side → NO SQL, FK stays null
```

```java
txn.setMerchant(merchant);             // owning side → UPDATE transaction SET merchant_id = ?
```

This is the bug people hit constantly: they add to the collection, commit, and the foreign key is still `null`. And like most JPA bugs, it's silent — the `add()` succeeded, the collection contains the object, the transaction committed. Only the database disagrees.

> [!tip] Always write a helper method on the parent
> ```java
> public void addTransaction(Transaction txn) {
>     transactions.add(txn);      // keeps the in-memory graph correct
>     txn.setMerchant(this);      // sets the FK — the part that persists
> }
> ```
> Set **both** sides. The collection keeps your Java object graph consistent; the owning side is what actually hits the database.
>
> Skipping the collection half isn't harmless either: within the same transaction, `merchant.getTransactions()` would not contain the new transaction, because the collection was already loaded and Hibernate won't re-query it.

## Unidirectional vs Bidirectional

**Unidirectional** — only one side knows about the other.

```java
class Transaction {
    @ManyToOne @JoinColumn(name = "merchant_id")
    Merchant merchant;
}
// Merchant has no transactions field
```

**Bidirectional** — both sides map the relationship, joined by `mappedBy`.

```java
class Merchant {
    @OneToMany(mappedBy = "merchant")
    List<Transaction> transactions;
}
```

| | Unidirectional `@ManyToOne` | Bidirectional |
|---|---|---|
| Navigation | child → parent only | both directions |
| Extra columns | none | none |
| Risk | none | forgetting to sync both sides; accidentally loading a huge collection |

> [!warning] Don't map a collection you never use
> `merchant.getTransactions()` on a merchant with 4 million transactions will try to load 4 million rows into memory. If a collection can grow unbounded, **do not map it** — query it with pagination instead:
> ```java
> Page<Transaction> page =
>     txnRepository.findByMerchantId(merchantId, PageRequest.of(0, 50));
> ```

Note the asymmetry in that risk column. The bidirectional mapping adds **no** capability the query couldn't provide, and adds two failure modes. That's why "unidirectional unless proven otherwise" is a defensible default rather than laziness — and it's a good answer to give when asked which you prefer.

## `@JoinTable` and Why `@ManyToMany` Is Discouraged

`@ManyToMany` looks elegant and turns painful the moment reality arrives.

The join table can only ever hold two columns. But real link tables always grow attributes:

```text
merchant_scheme

+-------------+-----------+------------+---------+
| merchant_id | scheme_id | enabled_at | mdr_bps |
+-------------+-----------+------------+---------+
```

`mdr_bps` and `enabled_at` have nowhere to live in a `@ManyToMany`.

And notice *when* this bites: not on day one, but on the day someone asks for a per-merchant rate. At that point the mapping has to change, every query against it has to change, and you're doing schema surgery on a live table.

Other problems:

- Removing one element can make Hibernate **delete all rows** for that owner and reinsert the remaining ones (`List` semantics without an `@OrderColumn`).
- No way to add an id, audit columns, or a soft-delete flag.
- Cascade behaviour is easy to get catastrophically wrong.

### The fix: model the join table as an entity

```java
@Entity
public class MerchantScheme {

    @EmbeddedId
    private MerchantSchemeId id;

    @ManyToOne @MapsId("merchantId")
    private Merchant merchant;

    @ManyToOne @MapsId("schemeId")
    private Scheme scheme;

    private Instant enabledAt;
    private Integer mdrBps;
}
```

Two `@ManyToOne`s instead of one `@ManyToMany`. Now the link row is a first-class citizen — it can carry attributes, be audited, be queried directly, and be soft-deleted.

> [!tip] If you *must* use `@ManyToMany`
> Use `Set`, not `List` — it avoids the delete-all-and-reinsert behaviour.

## Cascade

Imagine:

```java
Merchant merchant = new Merchant();

Transaction txn = new Transaction();

merchant.getTransactions().add(txn);
```

Now:

```java
entityManager.persist(merchant);
```

Question: should Transaction also be saved?

**Without cascade** — only Merchant is saved. Transaction is ignored (and you get a `TransientObjectException` if the relationship is required).

**With cascade:**

```java
@OneToMany(mappedBy = "merchant", cascade = CascadeType.PERSIST)
```

Hibernate automatically does:

```text
INSERT Merchant
     ↓
INSERT Transaction
```

You save one object. Hibernate saves the entire graph.

### Cascade types

| Type | Propagates |
|---|---|
| `PERSIST` | `persist()` → children inserted |
| `MERGE` | `merge()` → children merged |
| `REMOVE` | `remove()` → children deleted |
| `REFRESH` | `refresh()` → children reloaded |
| `DETACH` | `detach()` → children detached |
| `ALL` | all of the above |

Most commonly used: `CascadeType.ALL` or `CascadeType.PERSIST`.

> [!warning] `CascadeType.ALL` on `@ManyToOne` is almost always wrong
> ```java
> @ManyToOne(cascade = CascadeType.ALL)   // 🚨
> private Merchant merchant;
> ```
> Deleting **one transaction** now deletes the **merchant** — and cascades on to every other transaction of that merchant. Cascade flows parent → child, never child → parent.

Cascade on `@ManyToOne` should be `PERSIST`/`MERGE` at most, and usually nothing at all.

The general principle: cascade expresses **ownership**, and a child does not own its parent. Ask "if I delete this object, should the other one cease to exist?" — for a transaction and its merchant the answer is obviously no, and that's your answer about cascade.

## `orphanRemoval` vs Cascade REMOVE

This is different from cascade, and the difference is a reliable interview question.

Imagine the database has:

```text
Merchant
   ↓
Transaction 1
Transaction 2
Transaction 3
```

Now:

```java
merchant.getTransactions().remove(txn2);
```

Question: should txn2 remain in the database?

**Without orphanRemoval** — the Transaction still exists. Only the relationship changes (FK set to null).

**With orphanRemoval:**

```java
@OneToMany(mappedBy = "merchant", orphanRemoval = true)
```

Hibernate executes:

```sql
DELETE FROM transaction WHERE id = 2;
```

The Transaction is deleted.

Think of it like:

```text
Parent
   ↓
Children

If a child is removed from the parent's collection
   ↓
Delete the child
```

### The difference — huge interview favourite

```text
Cascade REMOVE                  orphanRemoval
--------------                  -------------
Delete Parent                   Parent Exists
      ↓                              ↓
Delete Children                 Remove Child from collection
                                     ↓
                                Delete Child
```

| | `CascadeType.REMOVE` | `orphanRemoval = true` |
|---|---|---|
| Trigger | Parent is deleted | Child is removed from the collection |
| Parent survives? | No | Yes |
| Implies the other? | No | Yes — it also deletes children when the parent is deleted |

The cleanest way to hold them apart: **cascade REMOVE is about the parent's death; orphanRemoval is about the child's disinheritance.**

Use `orphanRemoval` for true **parent-child composition** (Order → OrderLine, Settlement → SettlementEntry) where a child has no meaning on its own. Never use it for a shared reference — removing a `Scheme` from one merchant's collection should not delete the scheme every other merchant uses.

> 💡 **Interview**: I added a child to the parent's collection and committed, but the FK is null — why? → You modified the **inverse** side. Hibernate only writes the **owning** side, so you must also call `child.setParent(parent)`. Use a helper method on the parent that sets both.

| Annotation | Purpose |
|---|---|
| `@JoinColumn` | Specifies the foreign key column |
| `mappedBy` | Says "I don't own the relationship" |
| `cascade` | Propagates operations to child entities |
| `orphanRemoval` | Deletes a child when it is removed from the parent's collection |

## ❓ Interview Questions

### Q1. Why `mappedBy`?

Because a bidirectional relationship is mapped twice in Java but is only **one** foreign key in the database. `mappedBy` tells Hibernate which side owns that FK so it doesn't create a second mapping (typically a redundant join table).

### Q2. What is the owning side?

The side that holds the foreign key — the one with `@JoinColumn`. Only changes made through the owning side are persisted. The inverse side (`mappedBy`) is read-only from the database's point of view.

### Q3. Why is `@ManyToMany` often discouraged?

The join table can hold nothing but the two FKs, so it cannot carry attributes (rate, enabled date, audit columns) that real link tables always need. It also has awkward delete-and-reinsert semantics with `List`. Prefer modelling the join table as its own entity with two `@ManyToOne`s.

### Q4. Difference between `CascadeType.REMOVE` and `orphanRemoval`?

`CascadeType.REMOVE` deletes children when the **parent** is deleted. `orphanRemoval` deletes a child when it is **removed from the parent's collection**, with the parent still alive. `orphanRemoval = true` also implies remove-cascade behaviour.

### Q5. I added to the collection and committed, but the FK is null. Why?

You modified the **inverse** side. Hibernate only writes the owning side. Call `child.setParent(parent)` as well.

### Q6. What are the default fetch types?

`@ManyToOne` and `@OneToOne` are **EAGER**; `@OneToMany` and `@ManyToMany` are **LAZY**. Override the `-ToOne` ones to LAZY in practice.

### Q7. Unidirectional vs bidirectional — which do you prefer?

Unidirectional `@ManyToOne` wherever possible. It's simpler, has no synchronisation bug, and avoids accidentally loading unbounded collections. Add the `@OneToMany` only when the collection is small and genuinely useful.

### Q8. What is `@MapsId`?

It makes a child share its parent's primary key (typical for `@OneToOne`), removing a redundant column and making the lazy proxy work correctly.

> [!tip] ⚡ Quick Recall
> - Everything comes down to **where the FK lives**. `@ManyToOne` holds it; `@OneToMany(mappedBy=…)` just reads it.
> - **Owning side = has `@JoinColumn`. Inverse side = has `mappedBy`.** Only the owning side is persisted — always set **both** sides via a helper method.
> - Defaults: `@ManyToOne` / `@OneToOne` → **EAGER** (override to LAZY); `@OneToMany` / `@ManyToMany` → LAZY.
> - Don't map collections that can grow unbounded — paginate with a query instead.
> - Avoid `@ManyToMany`; promote the join table to an entity with two `@ManyToOne`s so it can carry attributes. If unavoidable, use `Set`.
> - **`CascadeType.ALL` on `@ManyToOne` deletes the parent.** Cascade flows parent → child only.
> - **Cascade REMOVE** = parent deleted → children deleted. **orphanRemoval** = child removed from collection → child deleted, parent alive.
>
> | Annotation | One-line meaning |
> |---|---|
> | `@JoinColumn` | which column is the FK |
> | `mappedBy` | I don't own this relationship |
> | `cascade` | propagate operations to children |
> | `orphanRemoval` | delete child when unlinked |
