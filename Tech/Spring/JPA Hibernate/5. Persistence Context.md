The **Persistence Context** is the in-memory workspace where the `EntityManager` / `Session` keeps every entity it is currently managing. It is also the First Level Cache.

> [!info] Why this comes before Entity Mapping
> If there is **one topic** that separates an average Java developer from a good backend engineer, it's this one. Almost every advanced Hibernate feature depends on it:
> ✅ Dirty Checking · ✅ First Level Cache · ✅ Flush · ✅ Merge · ✅ Persist · ✅ Remove · ✅ Lazy Loading · ✅ Transactions
>
> Understand this and the rest of Hibernate becomes much easier — which is why we cover it *before* annotations and relationships. Previous: [[4. Hibernate]].

> [!info] The through-line of this note
> One box in memory, and everything that follows from putting objects in it.
>
> 1. Hibernate needs somewhere to keep the entities it's tracking (§1). That box is the Persistence Context, and it exists so a second `find()` for the same row doesn't re-query and doesn't produce a second object (§2).
> 2. It's owned by **one** `EntityManager`/`Session` and dies with it (§3) — which is why "the transaction ended" and "my entity stopped working" are the same sentence.
> 3. Being *in* the box or not is the entity's **state** (§4): `NEW → MANAGED → DETACHED / REMOVED`. **Only MANAGED entities are tracked**, and almost every JPA surprise is an entity being in a state you didn't expect.
> 4. The API is just the set of transitions between those states — `persist` (§5), `find` (§6), `merge` (§7), `remove` (§8), `detach`/`clear`/`refresh` (§9).
> 5. And two headline features fall out of the box existing at all: the **first-level cache** (§10) and **dirty checking** (§11), which is why neither can be turned off.
>
> One line to anchor everything: **managed means Hibernate is watching; detached means it isn't, and your setters go nowhere.**

### 1. What the Persistence Context Is

> Official: a collection of managed entity instances associated with an `EntityManager` (or Hibernate `Session`).

- A box in RAM holding every entity Hibernate is currently managing

### 2. Why It Exists

```java
entityManager.find(Wallet.class, 1L);   // 1st call
entityManager.find(Wallet.class, 1L);   // 2nd call
```

| Without a Persistence Context | With one |
|---|---|
| Database queried **again** ❌ | Returns the existing managed object |
| A **second object** created ❌ | **No SQL**, same instance |

- ⭐ **The whiteboard model**: you don't write every intermediate step into the final notebook — you work on a whiteboard and copy the answer over once

```text
Database  ◄── Flush/Commit ──  Persistence Context  ──►  Java Objects
```

- Changes happen **in memory first**; the database is updated later

---

### 3. Where It Lives — One Session, One Context

```text
EntityManager        Session
      │                 │
      ▼                 ▼
Persistence Context   Persistence Context
```

- **One Session = one Persistence Context.** It lives for the Session's lifetime unless cleared
- ⭐ When the Session closes, the context is destroyed and **all managed entities become detached**
- Dirty checking, lazy loading, flush and the L1 cache **only work while an entity is managed inside an active context**
- In Spring it is **transaction-scoped** — created when `@Transactional` starts, closed when it ends ([[10. Transactions]])

---

### 4. Entity Lifecycle — the Four States ⭐

```text
          NEW
           │
      persist()
           ▼
        MANAGED
      /     |     \
detach() remove() close()
   ▼         ▼        ▼
DETACHED   REMOVED  DETACHED
```

| State | In DB? | Tracked? | Setters trigger SQL? |
|---|---|---|---|
| **NEW** (Transient) | ❌ | ❌ | ❌ |
| **MANAGED** (Persistent) | maybe | ✅ | ✅ |
| **DETACHED** | ✅ | ❌ | ❌ |
| **REMOVED** | until flush | ✅ | → `DELETE` |

- **Only MANAGED entities get dirty checking.** This is the foundation of everything else
- ⚠️ Setting a field on a **detached** entity does **nothing** — no SQL, no error, no warning

---

### 5. `persist()`

```java
Wallet wallet = new Wallet();     // NEW
entityManager.persist(wallet);    // MANAGED
transaction.commit();             // INSERT INTO wallet ...
```

- ⚠️ **`persist()` may not INSERT immediately.** With `GenerationType.IDENTITY` Hibernate **must** insert straight away to obtain the generated id
- With `SEQUENCE` it fetches the next value and can **defer** the INSERT to flush time — which is what makes **batching possible** ([[6. Entity Mapping]])

---

### 6. `find()`

```java
Wallet wallet = entityManager.find(Wallet.class, 1L);
```

```text
1. Check Persistence Context
2. Found?  → return it            (no SQL)
3. Not found? → execute SELECT
4. Store in Persistence Context
5. Return entity
```

- The check happens **before** any SQL is considered — this is §10 in action

---

### 7. `merge()` ⭐

The most misunderstood method in JPA.

```java
Wallet managed = entityManager.merge(detachedWallet);
```

Hibernate: finds or loads a **managed** instance with that id → copies the detached object's values into it → **returns the managed instance**.

- ⭐ **`merge()` does NOT make your object managed again**

```text
Detached Object → merge → NEW Managed Object (a different instance)
```

> ⚠️ **The classic bug**
> ```java
> entityManager.merge(wallet);     // return value ignored!
> wallet.setBalance(newBalance);   // still detached → no UPDATE
> ```
> **Always assign the result.**

| `persist()` | `merge()` |
|---|---|
| Makes a **new** entity managed | Copies a **detached** entity's state into a managed one |
| Returns `void` — same object becomes managed | Returns a **different** managed instance |
| Throws if an entity with that id exists | Issues a `SELECT` then `UPDATE` |

---

### 8. `remove()`

```java
entityManager.remove(wallet);      // MANAGED → REMOVED
// at flush:  DELETE FROM wallet WHERE id = 1
```

- ⚠️ The entity must be **managed** — calling `remove()` on a detached object throws `IllegalArgumentException`
- Merge first, then remove

---

### 9. `detach()`, `clear()`, `refresh()`

| Method | Effect |
|---|---|
| `detach(e)` | **One** entity: MANAGED → DETACHED. Hibernate forgets it |
| `clear()` | **All** entities detached; the context becomes empty |
| `refresh(e)` | **Reloads from the DB**, discarding unsaved in-memory changes |

```java
// DB: balance = 70000    Memory: balance = 90000
entityManager.refresh(wallet);    // memory becomes 70000 — local changes lost
```

- ⭐ `flush()` + `clear()` every N rows is **the** batch-insert trick, so memory doesn't blow up ([[14. Performance Tuning]])

---

### 10. First Level Cache ⭐

**The Persistence Context *is* the First Level Cache** — it isn't a separate feature.

- **Automatic** · **mandatory** (cannot be disabled) · **per Session/EntityManager**

```java
Wallet w1 = entityManager.find(Wallet.class, 1L);
Wallet w2 = entityManager.find(Wallet.class, 1L);

System.out.println(w1 == w2);   // true — same object, not just equal
```

- Only **one** SQL statement executes
- ⭐ **Guaranteed identity**: within one context, one database row maps to exactly **one** Java object
- That identity guarantee is *why* `==` works and *why dirty checking is possible at all*
- More cache levels in [[11. Caching]]

### 11. Dirty Checking

```java
Wallet wallet = entityManager.find(Wallet.class, 1L);
wallet.setBalance(new BigDecimal("90000"));    // no update call
transaction.commit();
```

```text

balance = 50000    vs    balance = 90000    → differs → UPDATE
```

```text

       → Dirty Checking → UPDATE generated → Commit
```

- Works **only** for MANAGED entities — which is §4 restated

# Detailed Explanation

## What the Persistence Context Is

The official definition:

> A Persistence Context is a collection of managed entity instances associated with an EntityManager (or Hibernate Session).

That's correct — but not very intuitive. A better mental model:

> **Persistence Context is Hibernate's in-memory workspace.**

Imagine it as a box in RAM where Hibernate keeps track of all the entities it is currently managing.

```text
          Database
              ▲
              │
        SQL Queries
              ▲
              │
      EntityManager / Session
              │
              ▼
      -------------------------
      | Persistence Context   |
      |-----------------------|
      | Wallet(id=1)          |
      | Transaction(id=5)     |
      | Merchant(id=10)       |
      -------------------------
              │
              ▼
       Your Java Code
```

---

## Why It Exists

Suppose you execute:

```java
Wallet wallet = entityManager.find(Wallet.class, 1L);
```

Hibernate loads the row:

```text
WALLET

ID | USER_ID | BALANCE
----------------------
1  | 101     | 50000
```

and creates a `Wallet` object.

Now imagine you call:

```java
entityManager.find(Wallet.class, 1L);
```

again.

**Without** a Persistence Context:

- Database queried again ❌
- A **new object** created ❌

**With** a Persistence Context, Hibernate simply returns the existing managed object. No SQL, much faster — and, just as importantly, only one `Wallet` object exists for that row. That second point turns out to matter more than the performance one: if two objects represented row 1, and you changed a field on each, Hibernate would have no way to decide what the row should become.

### Think of it like a whiteboard

Imagine you're solving maths problems. You don't write every intermediate step directly into the final notebook. Instead you use a whiteboard — make changes, erase, rewrite — and finally copy the answer over.

The Persistence Context works the same way:

```text
Database
     ▲
     │
 Flush/Commit
     │
Persistence Context
     │
     ▼
Java Objects
```

Changes happen in memory first. The database is updated later, in one go, at a moment Hibernate chooses.

---

## Where It Lives — One Session, One Context

Each `EntityManager` owns exactly one Persistence Context.

```text
EntityManager        Session
      │                 │
      ▼                 ▼
Persistence Context   Persistence Context
```

So: **One Session = One Persistence Context.**

> [!note] The precise version
> More accurately: a `Session` **owns** a Persistence Context, which lives for the lifetime of that Session unless explicitly cleared. When the Session closes, its Persistence Context is destroyed and all managed entities become detached.
>
> This matters because **Dirty Checking, Lazy Loading, Flush and the First-Level Cache only work while an entity is managed inside an active Persistence Context.**

In Spring, the persistence context is normally bound to the **transaction** — it starts when `@Transactional` begins and closes when the transaction ends. See [[10. Transactions]].

That single sentence explains a surprising amount of day-to-day behaviour: entities returned from a `@Transactional` service method arrive in the controller **already detached**, so changing them there does nothing, and touching an unloaded lazy field there throws.

---

## Entity Lifecycle — the Four States

Every entity exists in one of four states.

```text
          NEW
           │
      persist()
           │
           ▼
        MANAGED
      /     |     \
detach() remove() close()
   │         │        │
   ▼         ▼        ▼
DETACHED   REMOVED  DETACHED
```

These states are **the foundation** of JPA/Hibernate. Almost every confusing behaviour in this course is an entity being in a state you didn't expect.

### State 1: New (Transient)

```java
Wallet wallet = new Wallet();
wallet.setUserId(101L);
```

Is it in the database? No.
Is Hibernate tracking it? No.
In the Persistence Context? No.

State: `NEW`. It's an ordinary Java object with no relationship to persistence at all.

### State 2: Managed (Persistent)

```java
entityManager.persist(wallet);
```

Hibernate starts managing the object.

```text
Persistence Context
Wallet(id=1)
```

Now Hibernate knows every field, every change, the original values and the current values.

This is a **Managed Entity**. **Only managed entities get dirty checking.**

### State 3: Detached

```java
entityManager.close();
```

or:

```java
entityManager.detach(wallet);
```

The `Wallet` object still exists in Java — you can read it, pass it around, serialise it. But Hibernate no longer tracks it.

```text
Wallet — Not inside Persistence Context
```

Changes won't be saved automatically:

```java
wallet.setBalance(new BigDecimal("100000"));
```

Nothing happens. No SQL. Because the object is detached.

> [!warning] Detached failures are silent
> This is the important part: there is **no exception**. The setter succeeds, the object holds the new value, the method returns normally, and the database is unchanged. Every other JPA mistake announces itself; this one doesn't. It's the single most common cause of "my update didn't save."

### State 4: Removed

```java
entityManager.remove(wallet);
```

Hibernate marks the entity for deletion. At flush/commit:

```sql
DELETE FROM wallet WHERE id = 1;
```

State: `REMOVED`. Note that it is still managed until the flush happens — the deletion is *scheduled*, not executed.

---

## `persist()`

```java
Wallet wallet = new Wallet();     // NEW
```

Call:

```java
entityManager.persist(wallet);    // MANAGED
```

Later:

```java
transaction.commit();
```

Hibernate executes:

```sql
INSERT INTO wallet ...
```

> [!note] persist() may not INSERT immediately
> With `GenerationType.IDENTITY` Hibernate **must** insert straight away to obtain the generated id — the database assigns it, so there's no way to know it without asking. With `SEQUENCE` it can fetch the next value up front and defer the INSERT to flush time.
>
> That difference is not academic: deferring is what allows Hibernate to **batch** inserts. An `IDENTITY` id generator quietly disables JDBC batching for that entity, which is a real and frequently-missed performance cliff. See [[6. Entity Mapping]] and [[14. Performance Tuning]].

---

## `find()`

```java
Wallet wallet = entityManager.find(Wallet.class, 1L);
```

Steps:

1. Check the Persistence Context.
2. If found → return it.
3. Otherwise → execute SQL.
4. Store in the Persistence Context.
5. Return the entity.

```text
find()                     find()
  ↓                          ↓
Persistence Context?      Persistence Context?
  ↓                          ↓
 Yes                        No
  ↓                          ↓
Return Object             SELECT ...
                             ↓
 No SQL                    Store
                             ↓
                          Return
```

## `merge()`

This confuses almost everyone, and it's worth slowing down for.

Suppose:

```java
entityManager.close();
```

The `Wallet` becomes detached. Then:

```java
wallet.setBalance(new BigDecimal("90000"));
```

Hibernate doesn't know. Now:

```java
entityManager.merge(wallet);
```

Hibernate:

- Finds or loads a **managed** instance with that id
- Copies the detached object's values into that managed instance
- **Returns** the managed instance

**Important:** `merge()` does **not** make the same object managed again.

```text
Detached Object
      ↓
    Merge
      ↓
New Managed Object          ← a different instance
```

```java
Wallet managed = entityManager.merge(detachedWallet);
```

Continue using `managed`, **not** `detachedWallet`.

The reason it works this way follows from §2's identity guarantee: the context may **already** hold a managed instance for that id. Hibernate can't have two objects for one row, and it can't discard the one it's already tracking — so it copies your values into the one it owns and hands that back.

> [!warning] The classic bug
> ```java
> entityManager.merge(wallet);        // return value ignored!
> wallet.setBalance(newBalance);      // still detached → no UPDATE
> ```
> Always assign the result.

### `persist()` vs `merge()`

| `persist()` | `merge()` |
|---|---|
| Makes a **new** entity managed | Copies state of a **detached** entity into a managed one |
| Used for new entities | Used for detached entities |
| Returns `void` — same object becomes managed | Returns a **different** managed instance |
| Throws if entity already exists with that id | Issues a SELECT then UPDATE |

Note the last row's cost: `merge()` generally needs a `SELECT` first, because Hibernate must load the current row before it can copy your values onto it. Merging in a loop is therefore a hidden N+1.

---

## `remove()`

```java
entityManager.remove(wallet);
```

Hibernate marks it for deletion. SQL is executed during flush.

The entity must be **managed** — calling `remove()` on a detached object throws `IllegalArgumentException`. Merge first, then remove.

## `detach()`, `clear()`, `refresh()`

### `detach()`

```java
entityManager.detach(wallet);
```

```text
Managed  →  Detached
```

Hibernate forgets the object. Useful when processing a huge list and you don't want the persistence context to grow unbounded.

### `clear()`

Suppose the Persistence Context contains:

```text
Wallet
Transaction
Merchant
Settlement
```

Call:

```java
entityManager.clear();
```

Everything becomes detached. The Persistence Context becomes empty.

This is the standard trick in a **batch insert loop** — flush + clear every N rows so memory doesn't blow up → [[14. Performance Tuning]]. Note both halves are needed: `flush()` sends the pending SQL, `clear()` releases the objects and their snapshots.

### `refresh()`

Suppose the database says:

```text
balance = 70000
```

and memory says:

```text
balance = 90000
```

Call:

```java
entityManager.refresh(wallet);
```

Hibernate reloads from the database. Memory becomes:

```text
balance = 70000
```

**Local changes are discarded** — this is a destructive operation, not a merge. Use it when you know the database is more trustworthy than your in-memory copy (after a trigger fired, or a concurrent update you want to observe).

## First Level Cache

The Persistence Context **is** the First Level Cache. It is:

- Automatic
- Mandatory (cannot be disabled)
- Per Session / EntityManager

```java
Wallet w1 = entityManager.find(Wallet.class, 1L);
Wallet w2 = entityManager.find(Wallet.class, 1L);
```

Only **one** SQL statement executes. Why? The second call returns the same managed object.

```java
System.out.println(w1 == w2);   // true
```

Same Java object — not just equal, **identical**.

> [!info] Guaranteed identity
> Within one persistence context, one database row maps to exactly **one** Java object. This is why `==` works and why dirty checking is possible at all.

That last clause is the payoff. Dirty checking compares an object against its snapshot — which only makes sense if there is exactly one object per row. The cache isn't a performance feature that happens to give identity; **identity is the requirement**, and the cache is what you get for free once you have it.

More cache levels in [[11. Caching]].

## Dirty Checking

```java
Wallet wallet = entityManager.find(Wallet.class, 1L);

wallet.setBalance(new BigDecimal("90000"));
```

No update query written by you.

At commit, Hibernate compares:

```text
Original Snapshot        Current Object
balance = 50000    vs    balance = 90000
```

Difference? Yes. Generate:

```sql
UPDATE wallet SET balance = 90000 WHERE id = 1;
```

Automatically.

### Complete flow

```java
Wallet wallet = entityManager.find(Wallet.class, 1L);

wallet.setBalance(new BigDecimal("100000"));

transaction.commit();
```

Internally:

```text
SELECT wallet
      ↓
Persistence Context
      ↓
Snapshot Created
      ↓
Balance Changed
      ↓
Dirty Checking
      ↓
UPDATE Generated
      ↓
Commit
```

Deep dive → [[8. Dirty Checking and Flush]].

## Common Mistakes

**Mistake 1** — Thinking every `find()` executes SQL.
Wrong. The Persistence Context is checked first.

**Mistake 2** — Thinking `merge()` attaches the same object.
Wrong. It returns a *different* managed instance.

**Mistake 3** — Thinking `flush()` commits.
Wrong. `flush()` sends SQL; `commit()` makes it permanent.

**Mistake 4** — Modifying detached entities and expecting automatic updates.
Hibernate isn't tracking them anymore.

**Mistake 5** — Loading 500,000 rows in one persistence context.
Every entity stays referenced until the context closes → `OutOfMemoryError`. Flush + clear periodically.

> 💡 **Interview**: my service updated the entity and the change didn't persist — why? → The entity was **detached**. Either it was loaded outside the transaction, or the transaction ended before the setter ran. Detached setters fail silently: no SQL, no exception. Reload inside the transaction, or `merge()` and use the returned instance.

Notice that mistakes 1, 2 and 4 are all the same misunderstanding wearing different clothes — not knowing which state an entity is in. If you can answer *"is this object managed right now?"* at every line, none of them can happen to you.

## ❓ Interview Questions

### Q1. What is Persistence Context?

An in-memory collection of managed entities associated with an `EntityManager` / `Session`. It tracks entity state, acts as the first-level cache, and synchronises changes with the database.

### Q2. What are the entity lifecycle states?

- **New (Transient):** created in Java, not managed, not in the database.
- **Managed (Persistent):** tracked by the Persistence Context.
- **Detached:** exists but is no longer tracked.
- **Removed:** marked for deletion, deleted at flush/commit.

### Q3. Why is the Persistence Context called the First Level Cache?

Because it stores managed entities within a single `EntityManager`/`Session`. Repeated lookups for the same entity return the cached instance without another SQL query.

### Q4. Difference between `persist()` and `merge()`?

See the table in the `merge()` section — `persist` makes a new entity managed; `merge` copies a detached entity's state into a managed instance and **returns** it.

### Q5. What does `clear()` do?

Removes **all** managed entities from the Persistence Context, making them detached.

### Q6. What does `refresh()` do?

Reloads the entity's state from the database, discarding unsaved in-memory changes.

### Q7. What is the scope of the Persistence Context in Spring?

By default it is **transaction-scoped** — created when `@Transactional` starts, closed when it ends. That's why entities returned from a service method are detached in the controller (unless OSIV is on → [[14. Performance Tuning]]).

### Q8. Two `find()` calls for the same id in one transaction — how many queries?

One. The second returns the cached managed instance, and `w1 == w2` is `true`.

> [!tip] ⚡ Quick Recall
> - Persistence Context = **Hibernate's in-memory workspace** = the **First Level Cache**. One per `EntityManager`/`Session`.
> - Four states: **NEW → MANAGED → DETACHED / REMOVED**. Only **MANAGED** entities are tracked.
> - Closing the Session/transaction detaches everything.
> - `persist()` = new → managed. `merge()` = detached → **new** managed copy (**use the return value**). `remove()` = mark for delete. `detach()` = forget one. `clear()` = forget all. `refresh()` = reload from DB, discard local changes.
> - Same row, same context → **same Java object** (`==` is true), one SQL query.
> - Changes go to memory first; SQL happens at **flush**, permanence at **commit**.
> - Detached entity + setter = **nothing happens**. This is the #1 source of "my update didn't save".
>
> | Method | State transition |
> |---|---|
> | `persist()` | NEW → MANAGED |
> | `merge()` | DETACHED → (new) MANAGED |
> | `remove()` | MANAGED → REMOVED |
> | `detach()` | MANAGED → DETACHED |
> | `clear()` | all MANAGED → DETACHED |
> | `close()` | all MANAGED → DETACHED |
