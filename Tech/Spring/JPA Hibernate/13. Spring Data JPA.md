**Spring Data JPA** removes the repository boilerplate. You declare an interface; Spring generates the implementation at runtime. This is the most practical module — you use it in almost every Spring Boot project.

> [!info] Where this fits
> Spring Data JPA **does not replace Hibernate.** It sits on top of JPA/Hibernate and provides a simpler programming model:
> ```text
> Application → Spring Data JPA → JPA (EntityManager) → Hibernate → JDBC → Database
> ```
> Previous: [[12. Locking]].

## 1. Why was Spring Data JPA created?

Before it, you wrote a lot of boilerplate.

Plain JPA:

```java
EntityManager em = ...;

Wallet wallet = em.find(Wallet.class, 1L);
```

To find all wallets:

```java
TypedQuery<Wallet> query =
    em.createQuery("SELECT w FROM Wallet w", Wallet.class);

return query.getResultList();
```

For every entity, you'd write a DAO with the same shape — find, findAll, save, delete, count.

Spring Data JPA says:

> "I'll generate this for you."

## 2. The repository hierarchy

```text
Repository                       (marker interface)
     ↑
CrudRepository                   save, findById, findAll, delete, count, existsById
     ↑
PagingAndSortingRepository       findAll(Pageable), findAll(Sort)
     ↑
JpaRepository                    flush, saveAndFlush, deleteInBatch, getReferenceById
```

You'll extend `JpaRepository` most often:

```java
public interface WalletRepository extends JpaRepository<Wallet, Long> {
}
```

The first type is the **entity**. The second is the **id type**.

### What you get for free

Without writing any implementation:

```java
save(wallet);
saveAll(list);
findById(id);          // returns Optional<Wallet>
findAll();
findAllById(ids);
deleteById(id);
delete(wallet);
count();
existsById(id);
```

Plus, from `JpaRepository`:

```java
flush();
saveAndFlush(wallet);
deleteAllInBatch();
getReferenceById(id);  // lazy proxy — no query until you touch it
```

> [!note] `JpaRepository` vs `CrudRepository`
> `JpaRepository` extends `CrudRepository` (via `PagingAndSortingRepository`) and adds JPA-specific features: pagination, sorting, batch deletes and flush control. It also returns `List` instead of `Iterable`, which is more convenient.

## 3. How does Spring generate these methods?

You only write the interface. Spring creates a **proxy** implementation at startup:

```text
Your Interface
      ↓
Spring generates a proxy (backed by SimpleJpaRepository)
      ↓
Uses EntityManager internally
```

At boot, `@EnableJpaRepositories` (auto-configured by Spring Boot) scans for interfaces extending `Repository`, parses every method name, validates every `@Query`, and registers a proxy bean for each.

> [!tip] Errors surface at startup, not at runtime
> A malformed derived method name or an invalid JPQL string fails the application context. That's a feature — you find out at deploy time, not at 2 a.m.

## 4. Derived query methods

One of Spring Data JPA's most popular features.

Suppose your entity has:

```java
class Transaction {
    String status;
    BigDecimal amount;
    Long merchantId;
    Instant createdAt;
}
```

You can write:

```java
List<Transaction> findByStatus(String status);
```

Spring automatically generates:

```sql
SELECT * FROM transaction WHERE status = ?
```

No SQL or JPQL needed. The **method name is parsed** to build the query.

### More examples

```java
findByMerchantId(Long merchantId);

findByAmountGreaterThan(BigDecimal amount);

findByStatusContaining(String keyword);

findByMerchantIdAndStatus(Long merchantId, String status);

findByMerchantIdOrStatus(Long merchantId, String status);

findByCreatedAtBetween(Instant start, Instant end);

findByStatusIn(List<String> statuses);

findByMerchantIdOrderByCreatedAtDesc(Long merchantId);

findTop10ByStatusOrderByAmountDesc(String status);

countByStatus(String status);

existsByReferenceId(String referenceId);
```

### Keyword reference

| Keyword | SQL |
|---|---|
| `And` / `Or` | `AND` / `OR` |
| `Between` | `BETWEEN ? AND ?` |
| `LessThan` / `GreaterThan` | `<` / `>` |
| `IsNull` / `IsNotNull` | `IS NULL` / `IS NOT NULL` |
| `Like` / `Containing` / `StartingWith` | `LIKE` |
| `In` / `NotIn` | `IN (…)` |
| `OrderBy…Asc/Desc` | `ORDER BY` |
| `Distinct` | `SELECT DISTINCT` |
| `First` / `Top<N>` | `LIMIT` |
| `IgnoreCase` | `UPPER(x) = UPPER(?)` |

> [!warning] The readability cliff
> ```java
> findByMerchantIdAndStatusAndAmountGreaterThanAndCreatedAtBetweenOrderByCreatedAtDesc(...)
> ```
> Once a method name reaches this length, switch to `@Query` or a `Specification`. Three conditions is roughly the limit.

## 5. @Query

Sometimes method names become long or the query is complex.

```java
@Query("""
    SELECT t
    FROM Transaction t
    WHERE t.merchant.id = :merchantId
      AND t.status = :status
    """)
List<Transaction> findForMerchant(@Param("merchantId") Long merchantId,
                                  @Param("status") String status);
```

Now you're writing JPQL explicitly — against **entity names and field names**, not tables and columns.

### Native query

Sometimes you need database-specific SQL:

```java
@Query(value = """
        SELECT * FROM transaction
        WHERE merchant_id = :merchantId
          AND created_at >= NOW() - INTERVAL '1 day'
        """,
       nativeQuery = true)
List<Transaction> findRecentNative(@Param("merchantId") Long merchantId);
```

Use it when:

- Database-specific features are required (window functions, CTEs, hints)
- Complex SQL performs better than JPQL
- Existing SQL needs to be reused

Trade-off: no portability, no compile-time/startup validation of entity fields.

> [!note] Native queries need explicit `countQuery` for pagination
> ```java
> @Query(value = "SELECT * FROM txn WHERE …",
>        countQuery = "SELECT count(*) FROM txn WHERE …",
>        nativeQuery = true)
> Page<Transaction> search(Pageable pageable);
> ```
> Spring can derive the count query for JPQL, but not reliably for native SQL.

## 6. Modifying queries

A `@Query` that writes needs two extra annotations:

```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Transactional
@Query("UPDATE Transaction t SET t.status = :status WHERE t.id IN :ids")
int markStatus(@Param("ids") List<Long> ids, @Param("status") String status);
```

> [!warning] Bulk updates bypass the persistence context
> A bulk `UPDATE`/`DELETE` goes straight to the database. Hibernate does **not** know about it, so entities already in the persistence context keep their **old values**, and the second-level cache is stale.
>
> That's what `clearAutomatically = true` (clear L1 after) and `flushAutomatically = true` (flush pending changes before) are for. Bulk operations also skip cascade, `@Version` and lifecycle callbacks — use them deliberately.

## 7. Paging and sorting

Suppose there are

```text
1,000,000 transactions
```

Never do:

```java
findAll();
```

Instead:

```java
Page<Transaction> findByMerchantId(Long merchantId, Pageable pageable);
```

Usage:

```java
Page<Transaction> page = repo.findByMerchantId(
    merchantId,
    PageRequest.of(0, 20, Sort.by("createdAt").descending()));

page.getContent();          // the 20 rows
page.getTotalElements();    // total count (extra COUNT query)
page.getTotalPages();
```

SQL generated:

```sql
SELECT … LIMIT 20 OFFSET 0
```

(or the equivalent for your dialect).

### Sorting

```java
findAll(Sort.by("amount"));
findAll(Sort.by("amount").descending());
findAll(Sort.by(Sort.Order.desc("createdAt"), Sort.Order.asc("id")));
```

### Page vs Slice vs List

| Return type | Extra COUNT query? | Use when |
|---|---|---|
| `Page<T>` | **Yes** | You need total pages / total count |
| `Slice<T>` | No | Infinite scroll — you only need "is there a next page" |
| `List<T>` | No | You just want a limited chunk |

> [!warning] Deep offsets are slow
> `OFFSET 500000` makes the database scan and discard half a million rows. For large tables use **keyset pagination** instead:
> ```java
> @Query("SELECT t FROM Transaction t WHERE t.id < :lastSeenId ORDER BY t.id DESC")
> List<Transaction> nextPage(@Param("lastSeenId") Long lastSeenId, Pageable limit);
> ```
> Also recall that **`Pageable` + `JOIN FETCH` paginates in memory** → [[9. Fetching]].

## 8. Specifications

Suppose your search screen has optional filters:

- Merchant
- Status
- Amount range
- Date range

With derived query methods you'd end up writing every combination:

```text
findByMerchantId
findByStatus
findByMerchantIdAndStatus
findByStatusAndAmountBetween
findByMerchantIdAndStatusAndAmountBetween
...
```

Combinatorial explosion. Instead, build the query dynamically with **Specifications** — reusable conditions that Spring combines at runtime (a friendly wrapper over the Criteria API from [[3. JPA]]).

```java
public interface TransactionRepository
        extends JpaRepository<Transaction, Long>,
                JpaSpecificationExecutor<Transaction> { }
```

```java
public class TxnSpecs {

    public static Specification<Transaction> hasStatus(String status) {
        return (root, query, cb) ->
            status == null ? null : cb.equal(root.get("status"), status);
    }

    public static Specification<Transaction> amountAtLeast(BigDecimal min) {
        return (root, query, cb) ->
            min == null ? null : cb.greaterThanOrEqualTo(root.get("amount"), min);
    }
}
```

```java
Specification<Transaction> spec = Specification
        .where(TxnSpecs.hasStatus(req.getStatus()))
        .and(TxnSpecs.amountAtLeast(req.getMinAmount()));

Page<Transaction> result = repo.findAll(spec, pageable);
```

Returning `null` from a spec means "no condition" — that's how optional filters drop out cleanly.

For interviews, understanding the **purpose** is usually enough: *dynamic, optional, composable filters without a method-name explosion.*

## 9. Projections and DTOs

Suppose your table has 20 columns. Your API only needs two.

Don't fetch the whole entity — fetch only what you need.

### Interface projection (closed)

```java
public interface TxnSummary {
    String getReferenceId();
    BigDecimal getAmount();
}
```

```java
List<TxnSummary> findByMerchantId(Long merchantId);
```

Spring generates `SELECT t.reference_id, t.amount …` — only the required columns.

### Nested projection

```java
public interface TxnSummary {
    String getReferenceId();
    MerchantView getMerchant();

    interface MerchantView { String getName(); }
}
```

### DTO / constructor projection

```java
public record TxnDto(String referenceId, BigDecimal amount, String merchantName) {}
```

```java
@Query("""
    SELECT new com.card91.dto.TxnDto(t.referenceId, t.amount, m.name)
    FROM Transaction t JOIN t.merchant m
    WHERE m.id = :merchantId
    """)
List<TxnDto> findSummaries(@Param("merchantId") Long merchantId);
```

Note the **fully qualified class name** — a common source of runtime errors.

### Why this matters more than it looks

Projections don't just select fewer columns. They return objects that are **not managed entities**, which means:

- No snapshot, no dirty checking → far less memory and CPU
- No lazy proxies → no `LazyInitializationException` in the controller
- Nothing accidentally written back on flush

> [!tip] The rule
> **Read paths → projections/DTOs. Write paths → entities.** Combine with `@Transactional(readOnly = true)` and most of your performance problems disappear before they start.

## 10. save() vs saveAndFlush()

A common interview question.

### save()

```java
repository.save(transaction);
```

The entity becomes managed. Hibernate decides **when** to send the SQL — typically at flush/commit.

Internally it is `persist()` if the entity is new, `merge()` otherwise → [[8. Dirty Checking and Flush]].

### saveAndFlush()

```java
repository.saveAndFlush(transaction);
```

Hibernate immediately flushes pending SQL to the database. The transaction is still open — this is **not** a commit.

Use it when subsequent code in the same transaction depends on the SQL having been executed: reading back with a native query, catching a constraint violation here, or needing the generated id before an external call.

> [!note] You often don't need `save()` at all
> ```java
> @Transactional
> public void markSettled(Long id) {
>     Transaction t = repo.findById(id).orElseThrow();
>     t.setStatus("SETTLED");        // dirty checking handles the UPDATE
> }
> ```
> The entity is managed; the update happens at commit. Calling `save()` here is harmless but redundant.

## ❓ Interview Questions

### Q1. What is Spring Data JPA?

A Spring project that reduces boilerplate by generating repository implementations at runtime on top of JPA.

### Q2. Does Spring Data JPA replace Hibernate?

No. The stack is `Spring Data JPA → JPA → Hibernate → JDBC → Database`. It's a convenience layer, not a provider.

### Q3. Difference between `CrudRepository` and `JpaRepository`?

`JpaRepository` extends `CrudRepository` (through `PagingAndSortingRepository`) and adds JPA-specific features — pagination, sorting, batch deletes, `flush()`/`saveAndFlush()`, `getReferenceById()` — and returns `List` rather than `Iterable`.

### Q4. How does Spring implement a repository interface?

At startup it scans for interfaces extending `Repository`, parses method names, validates queries, and registers a **proxy bean** backed by `SimpleJpaRepository`, which delegates to the `EntityManager`.

### Q5. When should you use `@Query`?

When a derived method name becomes hard to read, when you need joins/aggregations, or when you need native SQL for database-specific features.

### Q6. When should you use Specifications?

When search filters are dynamic and optional, so you can compose conditions at runtime instead of writing dozens of method-name permutations.

### Q7. `save()` vs `saveAndFlush()`?

`save()` makes the entity managed and lets Hibernate flush later (usually at commit). `saveAndFlush()` forces the SQL to be executed immediately. Neither commits.

### Q8. What is a projection and why use it?

An interface or DTO that selects a subset of columns. It returns unmanaged objects — fewer columns fetched, no dirty checking, no lazy proxies escaping the transaction.

### Q9. What does `@Modifying` do, and what's the catch?

It marks a `@Query` as an `UPDATE`/`DELETE`. The catch is that bulk statements bypass the persistence context — entities in memory go stale and cascades/`@Version`/callbacks are skipped. Use `clearAutomatically` and `flushAutomatically`.

### Q10. `Page` vs `Slice`?

`Page` issues an extra `COUNT` query to give total elements/pages. `Slice` only knows whether a next page exists — cheaper, ideal for infinite scroll.

---

> [!tip] ⚡ Quick Recall
> - Spring Data JPA generates a **proxy implementation** of your interface at startup. It does **not** replace Hibernate.
> - Hierarchy: `Repository` → `CrudRepository` → `PagingAndSortingRepository` → **`JpaRepository`** (adds flush, batch, `getReferenceById`).
> - **Derived queries** are parsed from the method name. Past ~3 conditions, switch to `@Query` or a `Specification`.
> - `@Query` = JPQL (entities/fields). `nativeQuery = true` = raw SQL (needs an explicit `countQuery` for paging).
> - `@Modifying` bulk updates **bypass the persistence context** — stale entities, no cascade, no `@Version`. Use `clearAutomatically`/`flushAutomatically`.
> - `Pageable` + `Sort` for paging; **`Page` costs a COUNT query, `Slice` doesn't**. Deep `OFFSET` is slow → keyset pagination.
> - **Specifications** = composable, optional filters (Criteria API made usable). Return `null` for "no condition".
> - **Projections/DTOs** for read paths: fewer columns, unmanaged objects, no dirty checking, no `LazyInitializationException`.
> - `save()` → SQL at flush/commit. `saveAndFlush()` → SQL now. Neither commits. Inside a transaction, a managed entity needs **no** `save()` at all.
