**Dirty Checking** is how Hibernate generates `UPDATE` statements you never wrote. **Flush** is the moment it decides to send them. Neither of them is `commit`.

> [!info] Where this fits
> We touched both in [[4. Hibernate]] and [[5. Persistence Context]]. This note goes deep — the snapshot mechanism, the flush lifecycle, flush modes, and the `save()` / `persist()` / `merge()` / `update()` family that interviewers love.

> [!info] The through-line of this note
> Hibernate writes SQL you never asked for. This note is *how it decides what*, and *when it sends it*.
>
> 1. **How it knows something changed**: it doesn't watch your setters. It keeps a **snapshot** at load time (§1) and **compares field by field** later (§2). That single design choice explains the cost (O(managed entities) per flush), why `readOnly = true` is fast, and why the default `UPDATE` touches every column.
> 2. **When it sends the SQL**: at **flush** — which is *not* commit (§3). Flush sends SQL and takes locks; commit makes it permanent. Hibernate flushes on its own at commit and before an overlapping query (§4), and you can change that with **flush modes** (§5).
> 3. **In what order**: not yours. The **action queue** runs INSERT → UPDATE → DELETE (§6), which is why a delete-then-insert on the same key blows up.
> 4. Then the four methods people confuse: `save()` vs `persist()` (§7), `merge()` vs `update()` (§8), `save()` vs `saveAndFlush()` (§9). Each pair has one JPA-standard member and one you should usually avoid.
>
> One line to anchor everything: **snapshot at load, compare at flush, send at flush, commit at the boundary.**

### 1. The Snapshot Mechanism

```java
Wallet wallet = entityManager.find(Wallet.class, 1L);
```

Hibernate does **two** things:

```text
Entity:    Wallet@3f2a  { balance = 50000, status = ACTIVE }
Snapshot:  Object[]     [ 50000, ACTIVE ]        ← a plain array of loaded values
```

- Two copies of the same data, **deliberately**

```java
wallet.setBalance(new BigDecimal("90000"));   // nothing happens. No SQL. Not even noticed
```

- ⭐ **Hibernate does not intercept your setter.** A managed entity is a plain object — `setBalance()` just assigns a field. There is no listener
- It finds out **later**, by comparison (unless bytecode enhancement is on → [[17. Hibernate Internals]])

### 2. Dirty Checking Internals ⭐

At flush, Hibernate walks **every managed entity** and compares field by field:

```text
current   →  [ 90000, ACTIVE ]
snapshot  →  [ 50000, ACTIVE ]
                 ↑ different  →  DIRTY  →  UPDATE
```

**The cost** — this runs over every managed entity at every flush:

```text
1,000 entities × 3 flushes = 3,000 full-state comparisons
```

- ⚠️ That's why loading 50,000 entities is slow **even if you modify one**
- **Mitigations**: `@Transactional(readOnly = true)` (sets `FlushMode.MANUAL`, skips dirty checking entirely) · `clear()`/`detach()` in batch loops → [[14. Performance Tuning]]

**By default Hibernate updates ALL columns:**

```sql
UPDATE wallet SET user_id=?, balance=?, currency=?, status=?, updated_at=? WHERE id=?
```

- **Why?** So the SQL string is **identical every time** → `PreparedStatement` plan caching + JDBC batching
- `@DynamicUpdate` generates only changed columns — ⚠️ but each combination is a **different SQL string**, defeating caching and batching. Use for wide tables/lobs, not by default

---

### 3. What Flush Actually Does ⭐

> **Flush** = synchronise the persistence context with the database (send the SQL).
> **Commit** = make those changes permanent and release locks.

```java
wallet.setBalance(new BigDecimal("100000"));
entityManager.flush();     // UPDATE sent · transaction still open · rollback still possible
transaction.commit();      // now permanent
```

- Between the two, changes are visible **to your transaction only**
- ⭐ **Row locks taken by the UPDATE are held from flush until commit** — flushing early lengthens lock hold time

**Why flush early on purpose:**

- You need a **generated id now** (an outbox row, an external call)
- You want a **constraint violation to surface here** so you can catch it
- You're batching and want to control memory (`flush()` then `clear()`)

---

### 4. When Hibernate Flushes Automatically

You rarely call `flush()` yourself. Hibernate does it at three points:

| # | Trigger | Note |
|---|---|---|
| 1 | **Before transaction commit** | Always. The main one |
| 2 | **Before a JPQL/HQL/Criteria query** | Only if the query touches tables with pending changes — **query-space overlap checking** |
| 3 | **Explicit `flush()`** | Yours |

- Rule 2 exists so your own uncommitted change is visible to your own query — a **"read your writes"** guarantee
- ⚠️ **`find()` does NOT trigger a flush** — it checks the persistence context first, so there's nothing to synchronise
- ⚠️ A **native query** gets no automatic query-space analysis unless you declare its synchronized entity classes — a genuine source of **stale reads**

### 5. Flush Modes

| Mode | Behaviour |
|---|---|
| `AUTO` | **Default.** Flush before commit and before overlapping queries |
| `COMMIT` | Flush only at commit. Queries may not see your pending changes |
| `ALWAYS` *(Hibernate)* | Flush before **every** query. Safe, slow |
| `MANUAL` *(Hibernate)* | Never flush automatically |

- ⭐ **`@Transactional(readOnly = true)` sets `MANUAL`** — which is exactly why an accidental modification inside a read-only transaction **silently does nothing** rather than throwing

### 6. SQL Ordering and the Action Queue ⭐

Hibernate does **not** execute SQL in the order you wrote the Java. At flush:

```text
1. OrphanRemovalAction
2. EntityInsertAction        (all INSERTs)
3. EntityUpdateAction        (all UPDATEs)
4. CollectionRemoveAction
5. CollectionUpdateAction
6. CollectionRecreateAction
7. EntityDeleteAction        (all DELETEs)
```

- The ordering enables **batching** (all INSERTs of one type together) but produces a famous surprise:

```java
walletRepository.delete(oldWallet);        // queued as DELETE
walletRepository.save(newWalletSameKey);   // queued as INSERT
// At flush: INSERT runs FIRST → unique constraint violation 💥
```

```java
walletRepository.delete(oldWallet);
walletRepository.flush();                  // ✅ force the DELETE now
walletRepository.save(newWalletSameKey);
```

- More in [[17. Hibernate Internals]]

### 7. `save()` vs `persist()`

| | `persist()` (JPA) | `save()` (Hibernate) |
|---|---|---|
| Return type | `void` | the generated **identifier** |
| Requires a transaction | Yes — `TransactionRequiredException` outside | Historically works outside one |
| Timing of the INSERT | **Can be deferred** to flush (with `SEQUENCE`) | **Must execute immediately** to return the id |
| On a **detached** entity | Throws `EntityExistsException` | Creates a **new row with a new id** 😬 |
| Standard? | ✅ JPA | ❌ Hibernate-only |

- ⭐ **Use `persist()`.** `save()`'s "return the id immediately" contract is what forces an eager INSERT and **defeats batching**

**What Spring Data's `save()` actually does:**

```java
if (entityInformation.isNew(entity)) { em.persist(entity); return entity; }
else                                 { return em.merge(entity); }
```

> ⚠️ **The hidden SELECT** — if you set the id yourself (natural keys, client UUIDs), Spring Data thinks the entity is *not* new and calls `merge()`, which issues a **SELECT before every INSERT**. On a bulk load that doubles your query count. Fix with `Persistable<ID>`:
> ```java
> @Override public boolean isNew() { return createdAt == null; }
> ```

### 8. `merge()` vs `update()`

Both deal with **detached** entities.

| | `merge()` | `update()` |
|---|---|---|
| Standard | ✅ JPA | ❌ Hibernate |
| Returns | a **new** managed instance | `void` — the same object becomes managed |
| SELECT first | Yes (unless already in context) | No |
| Duplicate instance in context | Handled fine | **`NonUniqueObjectException`** |
| UPDATE issued | Only if actually dirty | **Always** |

- ⭐ **Use `merge()`, and always use its return value:**

```java
Wallet managed = em.merge(detached);   // ✅
em.merge(detached);                    // ❌ changes to `detached` still go nowhere
```

repository.save(wallet);           // managed now; SQL at the next flush (usually commit)
repository.saveAndFlush(wallet);   // save() + immediate flush() → SQL sent NOW

  - read it back with a **native query** in the same transaction
  - make a **constraint violation catchable** here
  - need the **generated id** before calling an external service

# Detailed Explanation

---

## The Snapshot Mechanism

Suppose:

```java
Wallet wallet = entityManager.find(Wallet.class, 1L);
```

Hibernate does **two** things:

1. Creates the `Wallet` object you get back.
2. Stores a **hydrated snapshot** — a plain `Object[]` of the loaded column values.

```text
Persistence Context

  Entity:    Wallet@3f2a  { balance = 50000, status = ACTIVE }
  Snapshot:  Object[]     [ 50000, ACTIVE ]
```

Two copies of the same data, deliberately.

Now you change something:

```java
wallet.setBalance(new BigDecimal("90000"));
```

Nothing happens. No SQL. Hibernate hasn't even noticed yet.

> [!note] Hibernate does not intercept your setter
> A plain entity is a plain object — `setBalance()` just assigns a field. There is no listener. Hibernate finds out **later**, by comparison. (Unless bytecode enhancement is enabled, which *does* instrument setters → [[17. Hibernate Internals]].)

This is worth sitting with, because almost every surprising behaviour in this note follows from it. Hibernate chose **comparison** over **interception**, which buys it entities that are ordinary POJOs — no special base class, no proxy required for a loaded entity, no cost at assignment time. What it pays is a full scan at flush time, and that trade shows up as §2's cost.

---

## Dirty Checking Internals

At flush time, Hibernate walks **every managed entity** in the persistence context and compares field by field:

```text
For each managed entity:

    current state  →  [ 90000, ACTIVE ]
    snapshot       →  [ 50000, ACTIVE ]
                          ↑
                     different!

    → entity is DIRTY
    → generate UPDATE for the changed property
```

```sql
UPDATE wallet SET balance = 90000 WHERE id = 1;
```

Automatically. You wrote no SQL and called no `update()`.

### The cost

This comparison runs over **every** managed entity at **every** flush.

```text
1,000 entities in the persistence context
        ×
   3 flushes in the transaction
        =
3,000 full-state comparisons
```

That's why loading 50,000 entities into one persistence context is slow even if you only modify one of them. Note the shape of that cost: it scales with **how much you loaded**, not with **how much you changed** — which is deeply counter-intuitive when you're profiling a method that "only updates one row."

Two mitigations:

- **`@Transactional(readOnly = true)`** — Hibernate sets `FlushMode.MANUAL` and skips dirty checking entirely for read paths.
- **`clear()` / `detach()`** — shrink the context in batch loops → [[14. Performance Tuning]].

### By default Hibernate updates ALL columns

```sql
UPDATE wallet
SET user_id = ?, balance = ?, currency = ?, status = ?, updated_at = ?
WHERE id = ?
```

Even though only `balance` changed.

Why? So the SQL string is **identical every time** and the `PreparedStatement` plan can be cached and batched. Hibernate is optimising for the many-rows case at the cost of looking wasteful on one row.

To change it:

```java
@Entity
@DynamicUpdate          // generate SQL with only the changed columns
public class Wallet { }
```

> [!warning] `@DynamicUpdate` is not a free win
> Each distinct combination of changed fields produces a different SQL string, defeating statement caching and batching. Use it when a table is wide, has lobs, or when you're fighting lost updates on disjoint columns — not by default.

That last case is worth naming: if two transactions each change a *different* column of the same row, full-column updates make them overwrite each other, while `@DynamicUpdate` lets both survive. That's a genuine correctness use, distinct from the performance argument.

---

## What Flush Actually Does

**Flush ≠ Commit.** The single most common misunderstanding.

> **Flush** = synchronise the persistence context with the database (send the SQL).
> **Commit** = make those changes permanent and release locks.

```java
wallet.setBalance(new BigDecimal("100000"));

entityManager.flush();       // UPDATE is sent to the DB
                             // transaction still open
                             // you can still rollback
transaction.commit();        // now it is permanent
```

```text
Flush   →  Send SQL
Commit  →  Make changes permanent
```

Between the two, the changes are visible **to your transaction only** (and to any other transaction at READ UNCOMMITTED, which you should never use). The row locks taken by the UPDATE are held from flush until commit.

That last sentence has a practical edge: **flushing early makes you hold locks longer.** In a hot-row workload, an eager `saveAndFlush()` at the top of a long method is a throughput problem, because every other transaction touching that row now waits for the rest of your method to finish.

> [!tip] Why flush early on purpose
> Calling `flush()` mid-transaction is useful when:
> - You need a generated id **now** (for an outbox row or an external call).
> - You want a constraint violation to surface here rather than at commit, so you can catch it.
> - You're batching and want to control memory (`flush()` then `clear()`).

---

## When Hibernate Flushes Automatically

You rarely call `flush()` yourself. Hibernate does it at three points:

**1. Before transaction commit.** Always. This is the main one.

**2. Before executing a JPQL/HQL/Criteria query** — if the query touches tables with pending changes.

```java
wallet.setBalance(new BigDecimal("90000"));   // pending, in memory only

// Hibernate flushes here, so the query sees the new balance
List<Wallet> rich = em.createQuery(
    "SELECT w FROM Wallet w WHERE w.balance > 80000", Wallet.class)
    .getResultList();
```

This is called **query-space overlap checking**. Without it, your own uncommitted change would be invisible to your own query — a "read your writes" violation.

**3. When you call `flush()` explicitly.**

> [!warning] `find()` does NOT trigger a flush
> `em.find()` goes to the persistence context first, so there's nothing to synchronise. Only **queries** (JPQL/native/Criteria) trigger auto-flush. And a **native query** does *not* get automatic query-space analysis unless you declare its synchronized entity classes — a genuine source of stale reads.

The native-query gap is the one that reaches production. Hibernate can parse JPQL and see which entities it touches; it cannot parse arbitrary SQL to work out that `SELECT * FROM wallet` overlaps your pending `Wallet` change. So the native query runs against a database that hasn't received your update yet, and returns the old value with no warning at all.

---

## Flush Modes

```java
entityManager.setFlushMode(FlushModeType.COMMIT);
```

| Mode | Behaviour |
|---|---|
| `AUTO` | **Default.** Flush before commit and before overlapping queries. |
| `COMMIT` | Flush only at commit. Queries may not see your pending changes. |

Hibernate's native `FlushMode` adds two more:

| Mode | Behaviour |
|---|---|
| `ALWAYS` | Flush before **every** query, overlap or not. Safe, slow. |
| `MANUAL` | Never flush automatically. Nothing is written unless you call `flush()`. |

`@Transactional(readOnly = true)` sets **`MANUAL`** under the hood — which is exactly why an accidental modification inside a read-only transaction silently does nothing rather than throwing.

That's a double-edged default worth knowing in both directions. It's the reason read-only transactions are fast (no dirty-check scan at all), and the reason a setter that strayed into a read method produces no error, no SQL, and a bug report about data that "doesn't save."

---

## SQL Ordering and the Action Queue

Hibernate does **not** execute SQL in the order you wrote the Java code. It queues actions and, at flush, executes them in a fixed order:

```text
1. OrphanRemovalAction
2. EntityInsertAction        (all INSERTs)
3. EntityUpdateAction        (all UPDATEs)
4. CollectionRemoveAction
5. CollectionUpdateAction
6. CollectionRecreateAction
7. EntityDeleteAction        (all DELETEs)
```

This ordering enables batching (all INSERTs of the same type go in one batch) but produces a famous surprise:

```java
walletRepository.delete(oldWallet);        // queued as DELETE
walletRepository.save(newWalletSameKey);   // queued as INSERT

// At flush: INSERT runs FIRST → unique constraint violation
```

The fix is an explicit `flush()` between them:

```java
walletRepository.delete(oldWallet);
walletRepository.flush();                  // force the DELETE now
walletRepository.save(newWalletSameKey);
```

Note the general lesson, which outlives this specific bug: **the order of your Java statements carries no information about the order of your SQL.** Any time correctness depends on statement A reaching the database before statement B, you must force it with a flush — Hibernate will not infer it.

More on the action queue in [[17. Hibernate Internals]].

---

## `save()` vs `persist()`

`persist()` is JPA. `save()` is Hibernate's own (and what Spring Data's `save()` delegates to for new entities).

| | `persist()` (JPA) | `save()` (Hibernate) |
|---|---|---|
| Return type | `void` | the generated identifier |
| Requires a transaction | Yes — throws `TransactionRequiredException` outside one | Historically works outside a transaction |
| Timing of the INSERT | Can be deferred to flush (with `SEQUENCE`) | Must execute immediately to return the id |
| On a **detached** entity | Throws `EntityExistsException` | Creates a **new row** with a new id 😬 |
| Standard? | ✅ JPA standard | ❌ Hibernate-specific |

**Use `persist()`.** `save()`'s "return the id immediately" contract is what forces an eager INSERT and defeats batching.

Look at the return-type row and the timing row together — they're the same fact. A method that promises to hand you the id **cannot** defer the insert, because the id doesn't exist until the insert happens. The API shape dictates the performance characteristic. (Same reasoning as `GenerationType.IDENTITY` in [[6. Entity Mapping]] §4.)

### What Spring Data's `save()` actually does

```java
public <S extends T> S save(S entity) {
    if (entityInformation.isNew(entity)) {
        em.persist(entity);
        return entity;
    } else {
        return em.merge(entity);
    }
}
```

It is **`persist` or `merge`**, decided by whether the id is `null` (or by `Persistable.isNew()`).

> [!warning] The hidden SELECT
> If you set the id yourself (natural keys, client-generated UUIDs), Spring Data thinks the entity is *not* new and calls `merge()` — which issues a **SELECT before every INSERT**. On a bulk load that doubles your query count. Fix by implementing `Persistable<ID>`:
> ```java
> @Override public boolean isNew() { return createdAt == null; }
> ```

## `merge()` vs `update()`

Both deal with **detached** entities.

```java
// Detached — came from a previous transaction / a DTO / a cache
Wallet detached = ...;
detached.setBalance(new BigDecimal("90000"));
```

### `merge()` — JPA standard

```java
Wallet managed = entityManager.merge(detached);
```

- Looks for a managed instance with that id; loads it (SELECT) if absent.
- Copies the detached object's state into it.
- **Returns the managed instance.** `detached` stays detached.
- Safe if a managed copy already exists in the context.

### `update()` — Hibernate only

```java
session.update(detached);      // reattaches THIS object
```

- Makes the *given* object managed again. No SELECT, no copy.
- Always schedules an `UPDATE`, even if nothing changed.
- **Throws `NonUniqueObjectException`** if a different instance with the same id is already in the persistence context.

| | `merge()` | `update()` |
|---|---|---|
| Standard | ✅ JPA | ❌ Hibernate |
| Returns | a **new** managed instance | `void` (same object becomes managed) |
| SELECT first | Yes (unless already in context) | No |
| Duplicate instance in context | Handled fine | `NonUniqueObjectException` |
| UPDATE issued | Only if actually dirty | Always |

The `NonUniqueObjectException` row is the decisive one. It exists because of the identity guarantee from [[5. Persistence Context]] §10 — one row, one object. `update()` demands that *your* instance become the managed one, which is impossible if the context already holds a different instance for that id. `merge()` sidesteps the conflict entirely by copying into whichever instance is already there.

**Use `merge()`.** And always use its return value:

```java
Wallet managed = em.merge(detached);   // ✅
em.merge(detached);                    // ❌ changes to `detached` still go nowhere
```

## `save()` vs `saveAndFlush()`

```java
repository.save(wallet);           // entity becomes managed; SQL at flush time
repository.saveAndFlush(wallet);   // save() + immediate flush() → SQL sent now
```

`save()` does **not** guarantee the SQL has been executed. It becomes managed, and the INSERT/UPDATE happens whenever the next flush occurs — usually at commit.

Use `saveAndFlush()` when you need the write to hit the database *before* the transaction ends:

- You need to read it back with a native query in the same transaction.
- You want a constraint violation to be catchable here.
- You need the generated id before calling an external service.

But don't reach for it reflexively. Per §3, flushing early extends how long you hold row locks, and it forfeits Hibernate's ability to batch this statement with later ones.

Neither one commits. Only the transaction boundary commits → [[10. Transactions]].

> 💡 **Interview**: I deleted a row and inserted one with the same key in the same transaction, and got a unique constraint violation — why? → Hibernate's **action queue** executes all INSERTs before all DELETEs at flush, regardless of your statement order. Force the ordering with an explicit `flush()` between them.

## ❓ Interview Questions

### Q1. How does Hibernate know an entity has changed?

At load time it keeps a **snapshot** of the entity's state. At flush time it compares the entity's current state against that snapshot field by field; any difference produces an `UPDATE`. This is dirty checking.

### Q2. Is dirty checking triggered by the setter?

No. A managed entity is an ordinary object — the setter just assigns a field. Detection happens **later**, at flush, by comparison. (Bytecode enhancement can instrument setters to make this cheaper.)

### Q3. What is flush? Does it commit?

Flush synchronises the persistence context with the database by executing pending SQL. It does **not** commit — the transaction stays open and can still be rolled back. Locks acquired at flush are held until commit.

### Q4. When does Hibernate flush automatically?

Before transaction commit, and before a JPQL/Criteria query whose query space overlaps pending changes. `find()` never triggers a flush.

### Q5. What are the flush modes?

`AUTO` (default — before commit and overlapping queries) and `COMMIT` (only at commit). Hibernate adds `ALWAYS` and `MANUAL`. `@Transactional(readOnly = true)` uses `MANUAL`.

### Q6. Why does Hibernate update all columns instead of just the changed one?

So the generated SQL string is stable, allowing `PreparedStatement` caching and JDBC batching. `@DynamicUpdate` changes this at the cost of both.

### Q7. `save()` vs `persist()`?

`persist()` is the JPA standard, returns `void`, requires a transaction, and can defer the INSERT to flush (enabling batching). `save()` is Hibernate-specific, returns the identifier, and therefore must insert immediately.

### Q8. `merge()` vs `update()`?

`merge()` (JPA) copies a detached entity's state into a managed instance and **returns that instance**. `update()` (Hibernate) reattaches the given object itself and throws `NonUniqueObjectException` if another instance with the same id is already managed.

### Q9. `save()` vs `saveAndFlush()`?

`save()` makes the entity managed; the SQL runs at the next flush (usually commit). `saveAndFlush()` forces the SQL immediately. Neither commits.

### Q10. Why did my DELETE-then-INSERT fail with a unique constraint violation?

Hibernate's action queue executes all INSERTs **before** all DELETEs at flush. Force ordering with an explicit `flush()` between the two operations.

> [!tip] ⚡ Quick Recall
> - Hibernate keeps a **snapshot** at load; at flush it **compares field by field** and generates UPDATEs. Setters are not intercepted.
> - Dirty checking costs O(managed entities) per flush → use **`readOnly = true`** for reads, `clear()` in batch loops.
> - Default UPDATE touches **all columns** (stable SQL → caching + batching). `@DynamicUpdate` changes that, at a cost.
> - **Flush = send SQL. Commit = make it permanent.** Rollback is still possible after flush.
> - Auto-flush happens: before **commit**, and before an overlapping **JPQL query**. Never on `find()`.
> - Flush modes: `AUTO` (default), `COMMIT`, `ALWAYS`, `MANUAL` (what `readOnly` uses).
> - Action queue order: **INSERT → UPDATE → DELETE**, not your code order.
> - `persist()` (JPA, void, batchable) > `save()` (Hibernate, returns id, immediate insert).
> - `merge()` returns a **new** managed instance — assign it. `update()` reattaches the same object and can throw `NonUniqueObjectException`.
> - Spring Data `save()` = `persist()` if id is null, else `merge()` (which costs a SELECT).
