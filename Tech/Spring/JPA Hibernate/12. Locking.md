Locking is how you stop two concurrent transactions from silently overwriting each other. JPA gives you two strategies: **optimistic** (detect the conflict) and **pessimistic** (prevent it).

> [!info] Where this fits
> This is the **JPA-level** view — `@Version`, `LockModeType`, `OptimisticLockException`, and when to pick which. The database theory behind it (lock types, isolation anomalies, deadlock mechanics, `SELECT ... FOR UPDATE` semantics) is already covered in depth at [[9. Database Concurrency]]. Previous: [[11. Caching]].

## 1. The Lost Update problem

Imagine the database:

```text
wallet
balance = 1000
```

Two users open the same wallet simultaneously.

```text
User A                    User B
```

**User A** reads `1000`.
**User B** reads `1000`.

Now **User A** withdraws `100`. Balance becomes:

```text
900
```

**User B** withdraws `200` — based on the old balance of `1000`. The database becomes:

```text
800
```

Wrong.

The correct answer should be:

```text
700
```

`1000 - 100 - 200 = 700`. A's update was **lost**.

This is the **Lost Update Problem**, and it is exactly the class of bug that costs real money in a payments system.

Hibernate provides two solutions.

---

## 2. Optimistic Locking ⭐⭐⭐⭐⭐

The most commonly used.

Instead of locking rows, Hibernate checks:

> "Did someone modify this row while I was working?"

It uses a **version column**.

```text
wallet
| id | balance | version |
|----|---------|---------|
| 1  | 1000    | 1       |
```

```java
@Entity
public class Wallet {

    @Id
    private Long id;

    private BigDecimal balance;

    @Version
    private Integer version;
}
```

### How it plays out

**User A** reads → `version = 1`
**User B** reads → `version = 1`

**User A** updates. The database becomes:

```text
| balance | version |
| 900     | 2       |
```

Now **User B** tries. Hibernate executes:

```sql
UPDATE wallet
SET balance = 800,
    version = 2
WHERE id = 1
  AND version = 1;
```

Does version 1 still exist?

No.

Update count:

```text
0
```

Hibernate sees the affected-row count is 0 and throws

```text
OptimisticLockException
```

(In Spring Data you'll usually see the wrapped `ObjectOptimisticLockingFailureException`.)

The application retries. **No data loss.**

### Why "optimistic"?

Because Hibernate assumes

> Conflicts are rare.

No row is locked. Everyone works freely. The conflict is checked only at update time.

### Notes on `@Version`

- Types allowed: `int`, `Integer`, `long`, `Long`, `short`, `Short`, `Timestamp`/`Instant`.
- Hibernate increments it **for you** — never set it manually.
- It is added to the `WHERE` clause of **every** UPDATE and DELETE of that entity.
- It works across **detached** entities too: load in request 1, edit in the browser, save in request 2 — a stale version is still caught. This is the classic "two admins editing the same merchant config" case.
- One version column protects the **whole row**, so two users editing genuinely unrelated columns will still conflict.

> [!tip] Optimistic locking is nearly free
> No locks, no waiting, one extra small column. Add `@Version` to any entity that can be updated concurrently — it turns a silent data corruption into a loud, retryable exception.

## 3. Pessimistic Locking ⭐⭐⭐⭐

Here Hibernate says

> Nobody touches this row until I'm done.

Imagine an ATM.

**User A** starts a transaction. Hibernate executes:

```sql
SELECT ... FOR UPDATE
```

The database locks the row.

Now **User B** must wait — until

```text
Commit  or  Rollback
```

Then User B proceeds.

```text
User A
   ↓
Row Locked
   ↓
User B Waiting
   ↓
Commit
   ↓
User B Continues
```

### In code

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT w FROM Wallet w WHERE w.id = :id")
Optional<Wallet> findByIdForUpdate(@Param("id") Long id);
```

or

```java
Wallet w = entityManager.find(Wallet.class, id, LockModeType.PESSIMISTIC_WRITE);
```

With a timeout so you fail fast instead of hanging:

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
Optional<Wallet> findByIdForUpdate(@Param("id") Long id);
```

### Why "pessimistic"?

Because Hibernate assumes

> Conflicts are likely.

So it locks immediately.

> [!warning] The lock is held until commit
> Everything you do after acquiring the lock — including any HTTP call to a bank or PSP — extends the time every other request on that row is blocked. **Never** make a network call while holding a pessimistic lock. Keep the locked section to: read, compute, write, commit.

## 4. Lock modes

| `LockModeType` | Meaning |
|---|---|
| `OPTIMISTIC` | Verify the version hasn't changed at commit (even for rows you only **read**) |
| `OPTIMISTIC_FORCE_INCREMENT` | Bump the version even if the entity wasn't modified — used to lock a parent when a child changes |
| `PESSIMISTIC_READ` | Shared lock — others can read, not write |
| `PESSIMISTIC_WRITE` | Exclusive lock (`SELECT … FOR UPDATE`) — the common one |
| `PESSIMISTIC_FORCE_INCREMENT` | Exclusive lock **and** version bump |
| `NONE` | Default |

`OPTIMISTIC_FORCE_INCREMENT` has a real payments use: adding a `LedgerEntry` doesn't modify the `Settlement` row, but you want two concurrent additions to conflict — bumping the parent's version enforces that.

---

## 5. Which one is better?

Usually:

```text
Optimistic Locking
```

Reasons:

- Better concurrency
- Better performance
- No waiting
- Most web applications use it

Use **pessimistic** locking when:

- Banking / core ledger updates
- Stock trading
- Inventory management
- Seat booking

— where simultaneous updates on the same row are **common** and waiting is preferable to repeatedly failing and retrying.

### The deciding question

> How often will two transactions actually touch the same row at the same time?

**Rarely** → optimistic. A retry every now and then is cheaper than locking every request.
**Often** → pessimistic. Constant optimistic failures mean you're doing the work twice, three times, ten times.

Concrete payments split:
- Merchant profile, KYC record, config → **optimistic**
- Hot wallet balance during a flash sale, seat/inventory reservation → **pessimistic**

### Comparison

| Optimistic | Pessimistic |
|---|---|
| No DB lock | Locks the DB row |
| Uses `@Version` | Uses `SELECT ... FOR UPDATE` |
| Better performance | Lower concurrency |
| Conflict detected at update time | Conflict prevented immediately |
| Fails → you retry | Waits → you may time out |
| Works across detached entities / HTTP requests | Only within one transaction |
| Default choice for most applications | Use when conflicts are frequent |

## 6. Handling the failure

An `OptimisticLockException` is **not a bug** — it is the mechanism working. Your job is to retry.

```java
@Retryable(
    retryFor = ObjectOptimisticLockingFailureException.class,
    maxAttempts = 3,
    backoff = @Backoff(delay = 50, multiplier = 2, random = true))
@Transactional
public void debit(Long walletId, BigDecimal amount) {
    Wallet w = walletRepo.findById(walletId).orElseThrow();
    w.setBalance(w.getBalance().subtract(amount));
}
```

> [!warning] Retry outside the transaction, and re-read the entity
> The retry must start a **new** transaction and **reload** the entity. Retrying with the same stale in-memory object just fails again with the same version. `@Retryable` on the `@Transactional` method (called through a proxy) gives you this. The full treatment of safe retries is in [[11. Transaction Boundaries]].

Also make the operation **idempotent** — a retried debit must not debit twice. Key it on a client-supplied idempotency key.

## 7. Deadlocks

Two transactions each holding a lock the other needs:

```text
Txn A: locks wallet 1 → wants wallet 2
Txn B: locks wallet 2 → wants wallet 1
        ↓
    Deadlock
```

The database detects it and kills one of them (`DeadlockLoserDataAccessException`).

**Prevention: always acquire locks in a consistent order.**

```java
// Always lock the lower id first, regardless of transfer direction
Long first  = Math.min(fromId, toId);
Long second = Math.max(fromId, toId);

lock(first);
lock(second);
```

Also: keep transactions short, and never lock more rows than you need. Deep dive in [[9. Database Concurrency]] and [[18. Production Problems]].

## ❓ Interview Questions

### Q1. What is `@Version`?

It marks a version field used for optimistic locking. Hibernate increments it on every successful update and adds `AND version = ?` to the UPDATE, so a concurrent modification is detected when the affected-row count comes back as 0.

### Q2. What is the Lost Update problem?

Two transactions read the same row, both compute from that value, and both write — the second overwrites the first, whose change is silently lost.

### Q3. Why is optimistic locking preferred?

Because most applications have far more reads than conflicting writes. It allows fully concurrent access with no locks or waiting, and only fails when an actual conflict occurs.

### Q4. When would you choose pessimistic locking?

When concurrent updates on the same row are common and consistency is critical — banking transactions, inventory reservation, seat booking — where waiting is cheaper than repeatedly retrying.

### Q5. Optimistic vs Pessimistic — the one-line difference?

Optimistic **detects** conflicts at write time using a version column. Pessimistic **prevents** them by locking the row at read time.

### Q6. What happens when optimistic locking fails?

Hibernate throws `OptimisticLockException` (Spring: `ObjectOptimisticLockingFailureException`) and the transaction rolls back. The application should retry in a **new** transaction with a **freshly loaded** entity, with backoff and idempotency.

### Q7. Does optimistic locking work for detached entities?

Yes — that's one of its strengths. The version travels with the detached object, so an edit spanning two HTTP requests still detects a concurrent change on `merge()`.

### Q8. `PESSIMISTIC_READ` vs `PESSIMISTIC_WRITE`?

`PESSIMISTIC_READ` takes a shared lock — others may read but not write. `PESSIMISTIC_WRITE` takes an exclusive lock (`SELECT … FOR UPDATE`) — others may neither write nor take a conflicting lock.

### Q9. How do you avoid deadlocks?

Acquire locks in a consistent global order (e.g. ascending primary key), keep transactions short, set a lock timeout, and retry the loser.

---

> [!tip] ⚡ Quick Recall
> - **Lost update** = two transactions read the same value, both write, one change vanishes. Both locking strategies exist to stop this.
> - **Optimistic** — `@Version` column. Hibernate adds `AND version = ?` to the UPDATE; 0 rows affected → `OptimisticLockException`. No locks, no waiting. **Default choice.**
> - **Pessimistic** — `SELECT … FOR UPDATE` via `LockModeType.PESSIMISTIC_WRITE`. Locks the row until commit. Use when conflicts are frequent (balances, inventory, seats).
> - Deciding question: *how often do two transactions hit the same row?* Rarely → optimistic. Often → pessimistic.
> - `@Version` also protects **detached** entities across HTTP requests. One version guards the **whole row**.
> - Never hold a pessimistic lock across a network call. Always set a lock timeout.
> - An optimistic failure is **normal** — retry in a **new transaction** with a **re-read** entity, with backoff + idempotency.
> - Deadlocks: acquire locks in a **consistent order** (e.g. ascending id).
>
> | | Optimistic | Pessimistic |
> |---|---|---|
> | Mechanism | `@Version` | `SELECT … FOR UPDATE` |
> | Cost | retry on conflict | waiting / timeouts |
> | Assumes | conflicts rare | conflicts likely |
