## 1. The N+1 problem (deep dive)

This is probably the **most asked Hibernate performance question**.

Suppose:

```text
merchant

1 -> Zomato
2 -> Swiggy
3 -> Blinkit
```

Each merchant has transactions.

```java
List<Merchant> merchants = merchantRepository.findAll();
```

Hibernate executes:

```sql
SELECT * FROM merchant;
```

One query. Fine.

Now you write:

```java
for (Merchant m : merchants) {
    System.out.println(m.getTransactions().size());
}
```

What happens?

For Zomato:

```sql
SELECT * FROM transaction WHERE merchant_id = 1;
```

For Swiggy:

```sql
SELECT * FROM transaction WHERE merchant_id = 2;
```

For Blinkit:

```sql
SELECT * FROM transaction WHERE merchant_id = 3;
```

Total:

```text
1 query  +  3 queries
```

If there are:

```text
100 merchants
```

Hibernate executes:

```text
1  +  100  =  101 SQL queries
```

This is the:

```text
N+1 Problem
```

### Why does it happen?

Because of:

```java
@OneToMany(fetch = FetchType.LAZY)
```

Every time you touch `merchant.getTransactions()`, Hibernate has to go get them — and it does so **one parent at a time**, because that's all a lazy proxy knows how to do.

> [!warning] N+1 is not a LAZY problem
> Making it `EAGER` does **not** fix it. With `EAGER` on a `@OneToMany`, `findAll()` still issues 1 + N queries — you've just moved them earlier and removed your ability to opt out. The fix is always *how you fetch*, never *what the annotation says*.

### Solution 1 — Fetch join

```java
@Query("""
    SELECT m
    FROM Merchant m
    JOIN FETCH m.transactions
    """)
List<Merchant> findAllWithTransactions();
```

Now Hibernate executes:

```sql
SELECT m.*, t.*
FROM merchant m
JOIN transaction t ON t.merchant_id = m.id
```

One query.

### Solution 2 — EntityGraph

```java
@EntityGraph(attributePaths = "transactions")
List<Merchant> findAll();
```

Spring fetches the collection for you — declaratively, no JPQL.

### Solution 3 — Batch fetching

Hibernate groups the lazy loads instead of eliminating them.

Instead of:

```text
100 queries
```

it executes:

```text
5 queries
```

using:

```properties
hibernate.default_batch_fetch_size=20
```

Very useful — it is a **global safety net** that costs you nothing and turns a catastrophic N+1 into a mildly inefficient N/20+1. Turn it on in every project.

### Solution 4 — DTO projection

If you only need a count or a few columns, don't load the entities at all:

```java
@Query("""
    SELECT new com.card91.dto.MerchantVolume(m.name, COUNT(t), SUM(t.amount))
    FROM Merchant m JOIN m.transactions t
    GROUP BY m.name
    """)
List<MerchantVolume> volumePerMerchant();
```

One query, no persistence context, no proxies.

### How do you *identify* N+1?

- Enable SQL logging (`spring.jpa.show-sql=true`, or better, a formatted logger).
- Look for **many near-identical SELECTs differing only in the id**.
- Use **Hibernate statistics** (`spring.jpa.properties.hibernate.generate_statistics=true`) — it prints the query count per session.
- Use **p6spy** or **datasource-proxy** to log real SQL with timings.
- Best of all: **assert on query count in an integration test** so a regression fails the build.

Full treatment of fetch strategies in [[9. Fetching]].

## 2. Batch insert

Suppose:

```java
for (int i = 0; i < 10000; i++) {
    ledgerRepository.save(entry);
}
```

Without batching, Hibernate sends:

```text
INSERT
INSERT
INSERT
INSERT
...
10000 times
```

Each one is a separate network round trip. If your DB is 1 ms away, that's 10 seconds of pure waiting.

### Enable batching

```properties
spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true
spring.jpa.properties.hibernate.order_updates=true
```

Now Hibernate groups:

```text
50 INSERTs
    ↓
One network round trip
```

Then another 50. Much faster.

> [!warning] `GenerationType.IDENTITY` disables batch inserts
> With `IDENTITY`, Hibernate must execute each INSERT immediately to learn the generated id — so it can never build a batch. If you are bulk-inserting, use `SEQUENCE` with a healthy `allocationSize`. This is the single most common reason "I set batch_size and nothing changed". See [[6. Entity Mapping]].

### And flush + clear as you go

```java
for (int i = 0; i < entries.size(); i++) {
    em.persist(entries.get(i));
    if (i % 50 == 0) {
        em.flush();
        em.clear();   // release the entities from the persistence context
    }
}
```

Without `clear()`, the persistence context holds all 10,000 entities plus their snapshots, and dirty checking walks the whole lot on every flush. Memory grows, and each flush gets slower than the last.

## 3. Batch update

Same idea. Instead of:

```text
UPDATE
UPDATE
UPDATE
```

Hibernate groups them, again via:

```properties
hibernate.jdbc.batch_size=50
```

For a *uniform* mass update, though, skip the entities entirely:

```java
@Modifying
@Query("UPDATE Transaction t SET t.status = 'EXPIRED' WHERE t.createdAt < :cutoff")
int expireOlderThan(@Param("cutoff") Instant cutoff);
```

One UPDATE statement for a million rows, versus a million entities loaded into memory. (Remember it bypasses the persistence context — see [[13. Spring Data JPA]].)

## 4. JDBC batching — who actually does it?

People often ask:

> Is batching done by Hibernate or by JDBC?

Answer: **both**.

```text
Application
    ↓
Hibernate    ← groups statements into a batch
    ↓
JDBC Batch   ← addBatch() / executeBatch()
    ↓
Database
```

Hibernate **prepares** the batches; the JDBC driver **sends** them efficiently in one round trip. Neither alone is enough — this is why `hibernate.jdbc.batch_size` is a Hibernate setting that has no effect unless the driver supports batching (on PostgreSQL you also want `reWriteBatchedInserts=true` on the JDBC URL to get true multi-row INSERTs).

The raw JDBC mechanics are in [[1. JDBC Fundamentals]].

## 5. `LazyInitializationException`

One of the most common production bugs.

```java
Merchant merchant = repository.findById(1L).get();
```

Transaction ends. Session closes.

Now:

```java
merchant.getTransactions();
```

Boom.

```text
LazyInitializationException: could not initialize proxy - no Session
```

Why? The transactions were never loaded. Hibernate needs to run SQL to get them. The Session is already closed.

```text
No Session
    ↓
No SQL
    ↓
Exception
```

### The bad "fix"

Many beginners do:

```java
@OneToMany(fetch = FetchType.EAGER)
```

Problem solved? **No.** Now everything loads every time, on every query, whether you need it or not. You have traded a loud exception for a silent, permanent slowdown.

### The correct fixes

- **Fetch join** — ask for the data in the query
- **`@EntityGraph`** — same, declaratively
- **DTO projection** — don't return entities at all
- **Do the work inside the transaction** — initialise what you need in the service layer

Ranked list with examples in [[9. Fetching]].

## 6. Open Session In View (OSIV)

Very common Spring Boot interview topic.

**Without OSIV:**

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Transaction ends
    ↓
Session closed
```

The controller cannot touch lazy objects.

**With OSIV:**

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Session still open
    ↓
JSON serialization
    ↓
Session closed
```

Lazy loading still works during serialization.

Spring Boot enables it **by default** (`spring.jpa.open-in-view=true`) and logs a warning at startup about it.

### Why do many companies disable OSIV?

Imagine the controller returns an entity and Jackson serializes it.

Jackson touches `transaction.getMerchant()` → Hibernate silently executes SQL.
It touches `merchant.getSettlementAccount()` → another SQL.
It touches `settlementAccount.getBank()` → another SQL.

Suddenly JSON serialization generates:

```text
100 SQL queries
```

without anyone noticing. The queries happen **outside** the transaction, one connection held open for the whole request, in a layer where nobody is looking at performance. This can severely hurt throughput, and it means your connection pool is held hostage by how fast the client reads the response.

> [!warning] Turn it off, then fix what breaks
> ```yaml
> spring:
>   jpa:
>     open-in-view: false
> ```
> Things will start throwing `LazyInitializationException`. That is the point — each one is a place where you were doing an invisible query in the web layer. Fix each with a fetch join or a DTO.

### The balanced interview answer

> It's convenient for simple applications, but many production systems disable it to prevent hidden database access in the web layer, to release the connection at the end of the service method rather than the end of the HTTP response, and to force all required data to be fetched explicitly inside the service layer.

## 7. Read-only transactions

```java
@Transactional(readOnly = true)
public List<TransactionDto> recentTransactions(Long merchantId) { ... }
```

Benefits:

- **Expresses intent clearly** — a reader knows nothing is written here.
- **Hibernate sets `FlushMode.MANUAL`** — no automatic flush, and no dirty-check snapshot comparison at the end. On a query returning thousands of entities, that's real CPU saved.
- **Some databases and drivers optimise it** — and with a replica setup, a routing `DataSource` can send read-only transactions to a **read replica**.

Use it on every API that only reads. Details of the mechanism in [[10. Transactions]].

> [!warning] `readOnly = true` is not a security guarantee
> Hibernate skips the flush, so your changes are quietly *dropped* rather than *rejected* — unless the database itself enforces read-only. Don't rely on it to prevent writes; rely on it to avoid the cost of checking for them.

## 8. When should you use native SQL?

Normally, use `@Query` with JPQL — it's portable and it returns managed entities.

Use **native SQL** when you need:

- Database-specific features (`ON CONFLICT`, `RETURNING`, hints)
- **Window functions** (`ROW_NUMBER()`, `LAG`, running balances)
- **CTEs** (`WITH ranked AS (...)`)
- Complex reporting / analytics aggregations
- A hand-tuned plan that the JPQL translation can't produce

```sql
WITH ranked AS (
    SELECT merchant_id, amount,
           ROW_NUMBER() OVER (PARTITION BY merchant_id ORDER BY amount DESC) AS rn
    FROM transaction
)
SELECT * FROM ranked WHERE rn <= 3;
```

JPQL simply cannot express this. Don't fight it — drop to native SQL, map to a DTO/projection, and move on.

The trade-off: you lose portability, and native queries **do not update the persistence context**, so combine them with the same care as `@Modifying`.

## 9. Common production mistakes

### Mistake 1 — Changing everything to `FetchType.EAGER`

Fixing a `LazyInitializationException` by making relationships eager. Every query now drags the whole object graph. Wrong fix, permanent cost.

### Mistake 2 — Calling `findAll()` on a huge table

```java
List<Transaction> all = txnRepository.findAll();   // 10 million rows
```

Straight to `OutOfMemoryError`. Use **pagination** — or better, **keyset pagination** for deep pages ([[13. Spring Data JPA]]). For genuine bulk processing, stream with a scroll/`Stream<T>` and `clear()` periodically.

### Mistake 3 — Returning entities directly from REST APIs

Return **DTOs** instead:

- Avoids exposing the internal model (and accidental breaking changes when you rename a column)
- Avoids lazy loading during serialization
- Reduces payload size
- Prevents `@JsonIgnore` whack-a-mole with bidirectional relationships

### Mistake 4 — Running huge transactions

A transaction open for 5 minutes holds a connection for 5 minutes, holds locks for 5 minutes, and bloats the persistence context. Break work into smaller batches, each its own transaction. See [[18. Production Problems]].

### Mistake 5 — Saving one row at a time without batching

`hibernate.jdbc.batch_size` plus a `SEQUENCE` generator turns a 10-second import into a sub-second one.

### Mistake 6 — Never looking at the SQL

The single highest-ROI habit: turn on SQL logging in dev and **actually read** what your code produces. Almost every problem in this note is obvious the moment you see the statements.

## ❓ Interview Questions

### Q1. What is the N+1 problem?

One query loads N parent entities, then an additional query is executed for each parent to load its related data — `1 + N` queries where one or two would do.

### Q2. How do you solve it?

`JOIN FETCH`, `@EntityGraph`, batch fetching (`default_batch_fetch_size`), or a DTO projection — chosen based on whether you need the entities at all and whether you're paginating.

### Q3. Why shouldn't everything be EAGER?

Because it loads data you didn't ask for on every single query, increases memory usage, triggers extra joins or extra queries, and — critically — cannot be turned off at the call site. LAZY can always be upgraded per-query; EAGER cannot be downgraded.

### Q4. Why use `@Transactional(readOnly = true)`?

It signals intent, puts Hibernate in manual flush mode so it skips dirty-check and flush overhead, and allows database/driver optimisations including routing to a read replica.

### Q5. Why do many companies disable OSIV?

To avoid hidden lazy-loading queries in controllers and during JSON serialization, to release the DB connection when the service method ends rather than when the HTTP response finishes, and to make all data access explicit and therefore optimisable.

### Q6. Is batching done by Hibernate or JDBC?

Both. Hibernate groups statements into a batch; the JDBC driver transmits the batch in one round trip. `hibernate.jdbc.batch_size` controls the grouping.

### Q7. You set `batch_size=50` and nothing changed. Why?

Most likely `GenerationType.IDENTITY` — Hibernate must execute each INSERT immediately to get the generated key, so batching is silently disabled. Switch to `SEQUENCE`.

### Q8. How do you detect performance problems in a JPA application?

SQL logging plus `hibernate.generate_statistics`, p6spy/datasource-proxy for real SQL with timings, APM traces for query counts per request, and query-count assertions in integration tests to catch regressions.

### Q9. When would you drop to native SQL?

Window functions, CTEs, database-specific syntax, or complex reporting that JPQL can't express — mapped to a DTO rather than an entity.

> [!tip] ⚡ Quick Recall
> - **N+1** = 1 query for parents + N queries for their collections. Caused by lazy access in a loop; **not** fixed by EAGER.
> - Fixes, in order of preference: **`JOIN FETCH`** → **`@EntityGraph`** → **`@BatchSize` / `default_batch_fetch_size`** → **DTO projection**.
> - Always set `hibernate.default_batch_fetch_size` — free global safety net.
> - **Batch insert**: `hibernate.jdbc.batch_size=50` + `order_inserts` + `flush()`/`clear()` every N. **`IDENTITY` disables batching** — use `SEQUENCE`.
> - Batching is **Hibernate + JDBC together**: Hibernate groups, the driver transmits.
> - **`LazyInitializationException`** = touched a lazy proxy after the Session closed. Fix by fetching correctly, never by going EAGER.
> - **OSIV** keeps the Session open through JSON serialization. Convenient, but hides queries in the web layer and holds a connection for the whole request → most production systems set `open-in-view: false`.
> - **`readOnly = true`** → manual flush, no dirty-check cost, replica routing. Not a write guard.
> - **Native SQL** for window functions, CTEs, DB-specific features. Map to DTOs.
> - Production mistakes: EAGER everywhere · unbounded `findAll()` · entities in REST responses · long transactions · unbatched saves · never reading the generated SQL.
>
> | Symptom | Likely cause | Fix |
> |---|---|---|
> | Many identical SELECTs | N+1 | `JOIN FETCH` / `@EntityGraph` |
> | Bulk insert is slow | no batching or `IDENTITY` | `batch_size` + `SEQUENCE` |
> | `LazyInitializationException` | proxy touched after commit | fetch join / DTO |
> | Queries appear in the controller | OSIV on | `open-in-view: false` |
> | `OutOfMemoryError` on export | unbounded `findAll()` | pagination / streaming + `clear()` |
