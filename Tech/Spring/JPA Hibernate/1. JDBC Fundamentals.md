**JDBC (Java Database Connectivity)** is a standard Java **API** — a set of interfaces and classes — that lets a Java application connect to a relational database, execute SQL, and read results, without knowing which database it is talking to.

> [!info] Where this fits
> This is the bottom of the stack. Everything above it — Hibernate, JPA, Spring Data JPA — eventually turns into JDBC calls. See [[0. JPA Roadmap]] for the full map.

> [!info] The through-line of this note
> One problem, solved by one idea, with consequences that fill the rest of the course.
>
> 1. **Java cannot talk to a database.** Every vendor speaks its own wire protocol (§1), and hard-coding one means rewriting the app to switch (§1).
> 2. So Java defined an **API instead of an implementation** (§2): *"every vendor must implement my interfaces."* The vendor's implementation is the **driver** (§3), and your code only ever touches the interface (§4–§5). That's the whole design.
> 3. On top of that sit the four things you actually use: the **connection lifecycle** (§6), **statements** (§7), the **`ResultSet` cursor** (§8), and **transactions** (§9).
> 4. Two performance facts that everything above JDBC inherits: **batching** collapses round trips (§10), and **pooling** exists because opening a connection costs more than most queries (§11).
> 5. And then the punchline: JDBC works, but writing an application in it is miserable (§12) — every limitation in that list is a feature of ORM.
>
> One line to anchor everything: **JDBC is the *what*; the driver is the *how*.**

## Short Notes

---

### 1. Before JDBC — Every Database Speaks Differently

- Java has **no built-in knowledge** of Oracle, MySQL, PostgreSQL or SQL Server
- Each speaks its own wire protocol — Oracle Network Protocol, MySQL Wire Protocol, Postgres Protocol. **They are not the same**
- Without a translator, `SELECT * FROM wallet;` simply cannot be sent

```java
Database db = new OracleDatabase();      // ❌ migrate to Postgres → rewrite the app
```

- What Java wanted: *"I don't care which database you're using."*

---

### 2. JDBC — One Standard API

- Java's move was to define an **API, not an implementation**: *every vendor must implement my interfaces*
- ⭐ **Analogy**: chargers used to be per-vendor; USB Type-C standardised the interface and each device implements it. JDBC is USB Type-C for databases
- Your code compiles against `Connection`, `Statement`, `PreparedStatement`, `ResultSet` — never against anything Oracle-specific

---

### 3. The JDBC Driver

- The vendor's **implementation** of those interfaces, shipped as a plain JAR

| Database | Driver JAR |
|---|---|
| Oracle | `ojdbc11.jar` |
| PostgreSQL | `postgresql.jar` |
| MySQL | `mysql-connector-j.jar` |

- Add the dependency and Java suddenly knows how to talk to that database — **no application code changes**
- The driver translates JDBC calls into the database's native protocol

---

### 4. Architecture and Flow

```text
Your Java Code
       │
       ▼
JDBC API (Interfaces)
       │
       ▼
Database Driver          ← the only database-specific piece
       │
       ▼
Database
```

- `DriverManager.getConnection(url, user, pass)` hands back an `OracleConnection` **behind the `Connection` interface**
- Exactly the same idea as `List<String> list = new ArrayList<>()` — program to the interface, get an implementation
- Your application **never talks to Oracle directly**

---

### 5. JDBC Is an API, Not Software

- Common interview trap: *"is JDBC a framework?"* → **No. It is an API** — a set of interfaces and classes
- `Connection` · `Statement` · `PreparedStatement` · `CallableStatement` · `ResultSet` · `DriverManager` · `SQLException`
- **JDBC ships no ability to talk to any database.** The driver supplies that

---

### 6. Connection Lifecycle

```text
1. Load / discover driver     (automatic since JDBC 4.0)
2. Open Connection            DriverManager.getConnection(...)
3. Create Statement           con.prepareStatement(sql)
4. Execute                    ps.executeQuery() / executeUpdate()
5. Process ResultSet          rs.next(), rs.getX(...)
6. Close everything           rs, ps, con   (reverse order)
```

- ⚠️ `Connection`, `Statement` and `ResultSet` are **OS/network resources** — a leak is not usefully garbage collected
- A leaked connection stays checked out of the pool until a timeout kills it → **the #1 cause of pool exhaustion** ([[18. Production Problems]])
- **Always `try-with-resources`** — it closes in reverse order for you

---

### 7. `Statement` vs `PreparedStatement` vs `CallableStatement`

| | `Statement` | `PreparedStatement` | `CallableStatement` |
|---|---|---|---|
| Parameters | No | Yes (`?`) | Yes + OUT params |
| Precompiled | No | Yes | Yes |
| SQL injection safe | ❌ | ✅ | ✅ |
| Plan reuse | ❌ | ✅ | ✅ |
| Use for | DDL, one-off admin SQL | **99% of application queries** | Stored procedures |

- `Statement` re-parses and re-plans the SQL **every single execution**
- ⚠️ String concatenation into a `Statement` is **SQL injection** — `' OR '1'='1` returns every wallet in the system
- ⭐ `PreparedStatement` sends the **structure once**; only values travel afterwards, so a parameter can never be parsed as SQL
- **Hibernate uses `PreparedStatement` exclusively** — that's why the SQL logs show `?` and not values

---

### 8. `ResultSet` — a Cursor, Not a List

- **Not** rows in memory — a **cursor** pointing at the result on the database side

```text
        ┌──────────────────────────┐
cursor →│ id=1  user=101  bal=500  │
        │ id=2  user=102  bal=900  │
        └──────────────────────────┘
```

- The cursor starts **before** the first row — you must call `next()` once before reading
- **Forward-only** by default (`TYPE_FORWARD_ONLY`); closes when its `Statement` closes
- ⚠️ **Fetch size** (`ps.setFetchSize(500)`) controls rows per network round trip. Default is often **10** — a killer on a million-row settlement file

---

### 9. Transactions in Raw JDBC

- ⚠️ **Auto-commit is ON by default** — every statement commits immediately

```java
// auto-commit = true
debitSender();      // committed
// crash here → money vanished
creditReceiver();
```

- Group them with `setAutoCommit(false)` → `commit()` / `rollback()` → restore before returning to the pool
- `con.setTransactionIsolation(...)` sets the isolation level; `con.setSavepoint(...)` allows partial rollback
- ⭐ **This is exactly what `@Transactional` automates** ([[10. Transactions]])

---

### 10. Batch Processing

- 10,000 individual inserts = **10,000 network round trips**
- `addBatch()` buffers; `executeBatch()` sends the buffer as **one** round trip

```java
ps.addBatch();
if (++count % 1000 == 0) ps.executeBatch();   // one round trip per 1000
```

- `executeBatch()` returns `int[]` of update counts; failure gives a `BatchUpdateException` telling you how many succeeded
- ⚠️ **Hibernate can batch too — but only if you configure it**: `spring.jpa.properties.hibernate.jdbc.batch_size` ([[14. Performance Tuning]])

---

### 11. Connection Pooling

- Opening a connection = TCP handshake → authentication → session setup → **50–100 ms**. Your query takes 2 ms
- So keep a **pool** of open connections and borrow one per request
- ⭐ `con.close()` on a **pooled** connection means **"give it back"**, not "tear it down"
- Spring Boot ships **HikariCP** as the default ([[16. Spring Boot Integration]])

---

### 12. Limitations of JDBC — Why ORM Exists

| # | Limitation | The pain |
|---|---|---|
| 1 | **Boilerplate** | Connection, statement, binding, mapping, closing — every query |
| 2 | **Manual object mapping** | `w.setId(rs.getLong("id"))` … for every column, every table, forever |
| 3 | **SQL scattered as strings** | No compile-time checking; a column typo surfaces in production |
| 4 | **Relationships are manual** | You write the join and assemble the object graph yourself |
| 5 | **No change tracking** | You must remember what changed and hand-write the `UPDATE` |
| 6 | **No caching** | Ask for the same row three times, pay three times |
| 7 | **Vendor SQL leaks in** | `ROWNUM` (Oracle) vs `LIMIT` (Postgres/MySQL) |

> Every row in this table is a feature of ORM → [[2. ORM Basics]].

# Detailed Explanation

---

## Before JDBC — Every Database Speaks Differently

Suppose you wrote a Java application, and you have an Oracle database. How does Java send this SQL?

```sql
SELECT * FROM wallet;
```

The answer is: **it can't.** Java has no built-in knowledge of Oracle, MySQL, PostgreSQL, or SQL Server. Each database speaks its own protocol:

```text
Oracle      → Oracle Network Protocol
MySQL       → MySQL Wire Protocol
PostgreSQL  → Postgres Protocol
```

They are **not** the same. You know English, someone else knows Japanese — without a translator, communication is impossible. Exactly that problem existed.

### The design problem

Suppose Java had solved this the obvious way, with a class per database:

```java
Database db = new OracleDatabase();
```

Tomorrow you migrate to PostgreSQL:

```java
Database db = new PostgreSQLDatabase();
```

The **entire application changes** — every place that touched the database. That coupling is the real problem, not the protocol difference. What Java wanted was:

> "I don't care which database you're using."

---

## JDBC — One Standard API

Java's answer was to define **an API rather than an implementation**. Instead of Java learning Oracle's language, Java said:

> Every database vendor must implement **my** API.

### The analogy worth remembering

Suppose every phone charger were different — Apple, Samsung, OnePlus, Google, each with its own connector. Terrible for everyone. **USB Type-C** solved it by standardising the *interface*: every manufacturer implements the same connector, and any cable works with any phone.

JDBC is USB Type-C for databases. The interface is fixed and public; each vendor provides its own implementation behind it.

The consequence is the one that matters: your application code compiles against interfaces that will never change when the database does.

---

## The JDBC Driver

Java only knows interfaces:

```java
Connection
Statement
PreparedStatement
ResultSet
```

So who implements them? Oracle does. MySQL does. PostgreSQL does. That implementation is the **JDBC Driver** — simply a Java library (a JAR) supplied by the database vendor.

| Database | Driver JAR |
|---|---|
| Oracle | `ojdbc11.jar` |
| PostgreSQL | `postgresql.jar` |
| MySQL | `mysql-connector-j.jar` |

Add the dependency and Java now knows how to talk to that database. Note what *didn't* change: your code. Swapping databases is a dependency change and a connection-URL change, not a rewrite. That was the entire goal from §1.

---

## Architecture and Flow

```text
Your Java Code
       │
       ▼
JDBC API (Interfaces)
       │
       ▼
Database Driver
       │
       ▼
Database
```

Notice something: **your application never talks directly to Oracle.** It talks to JDBC, and the driver handles the rest.

### The real example

You write:

```java
Connection con = DriverManager.getConnection(url, user, password);
```

You never write:

```java
OracleConnection connection = ...        // ❌ this would defeat the whole design
```

Why? Because your code depends only on the JDBC interface. The Oracle driver returns *an implementation of* `Connection`. It's the same pattern you already use every day:

```java
List<String> list = new ArrayList<>();   // declared as the interface
```

### What happens internally

```java
PreparedStatement ps = con.prepareStatement("SELECT * FROM wallet WHERE id = ?");
```

```text
Java Application
        │
        ▼
PreparedStatement Interface      ← your code stops here
        │
        ▼
OraclePreparedStatement          ← the driver's class
        │
        ▼
Oracle Network Packet
        │
        ▼
Oracle Database
```

The interface keeps your code database-independent. The driver does the database-specific work. That split is the single idea this whole note rests on.

---

## JDBC Is an API, Not Software

This is a common interview question, and many people get it wrong: they think JDBC is software that connects to databases.

It is not. JDBC is an **API** — a set of interfaces and classes:

```java
Connection
Statement
PreparedStatement
CallableStatement
ResultSet
DriverManager
SQLException
```

Ship an application with JDBC and no driver, and it cannot reach a single database. The API defines *what* operations exist; the driver defines *how* they happen for one specific database.

> 💡 **Interview**: is JDBC a framework? → No. It's an API — interfaces and classes. The implementation is the vendor's JDBC driver.

---

## Connection Lifecycle

Every raw JDBC operation follows the same six steps.

```text
1. Load / discover driver     (automatic since JDBC 4.0)
        ↓
2. Open Connection            DriverManager.getConnection(...)
        ↓
3. Create Statement           con.prepareStatement(sql)
        ↓
4. Execute                    ps.executeQuery() / executeUpdate()
        ↓
5. Process ResultSet          rs.next(), rs.getX(...)
        ↓
6. Close everything           rs, ps, con   (reverse order)
```

Full example — crediting a wallet:

```java
String sql = "UPDATE wallet SET balance = balance + ? WHERE id = ?";

try (Connection con = DriverManager.getConnection(url, user, pass);
     PreparedStatement ps = con.prepareStatement(sql)) {

    ps.setBigDecimal(1, new BigDecimal("500.00"));
    ps.setLong(2, 1L);

    int updated = ps.executeUpdate();
}
```

> [!warning] Always close
> `Connection`, `Statement` and `ResultSet` are OS/network resources. A leaked connection is not garbage collected in a useful way — it stays checked out of the pool until a timeout kills it. `try-with-resources` closes them automatically, in reverse order.
>
> This is the number one cause of the pool exhaustion incident described in [[18. Production Problems]].

---

## `Statement` vs `PreparedStatement` vs `CallableStatement`

Three interfaces, three jobs.

### `Statement` — plain, no parameters

```java
Statement st = con.createStatement();
ResultSet rs = st.executeQuery("SELECT * FROM wallet");
```

The SQL string is sent, parsed and planned **every single time**.

And if you build it by concatenation:

```java
// NEVER do this
st.executeQuery("SELECT * FROM wallet WHERE user_id = '" + input + "'");
```

If `input` is:

```text
' OR '1'='1
```

the query becomes:

```sql
SELECT * FROM wallet WHERE user_id = '' OR '1'='1'
```

Every wallet in the system is returned. That is **SQL injection** — and note the mechanism: the attacker's value was *parsed as SQL*, because the database received one flat string and had no way to know which parts were data.

### `PreparedStatement` — precompiled, parameterised

```java
PreparedStatement ps = con.prepareStatement("SELECT * FROM wallet WHERE user_id = ?");
ps.setString(1, input);
ResultSet rs = ps.executeQuery();
```

The `?` is a **bind parameter**. The SQL *structure* is sent to the database once and compiled; only values travel afterwards.

Two benefits, and they come from the same mechanism:

1. **Safe** — the statement was already compiled before the value arrived, so the value can never change the statement's meaning. It is always data, never SQL.
2. **Fast** — the database reuses the cached execution plan instead of re-parsing.

> [!example] Hibernate always uses PreparedStatement
> Every SQL statement Hibernate generates is a `PreparedStatement` with `?` placeholders. That's why you see `?` in the SQL logs instead of real values. See [[16. Spring Boot Integration]] for how to log the bound values.

### `CallableStatement` — stored procedures

```java
CallableStatement cs = con.prepareCall("{ call settle_merchant(?, ?) }");
cs.setLong(1, merchantId);
cs.registerOutParameter(2, Types.NUMERIC);
cs.execute();

BigDecimal settledAmount = cs.getBigDecimal(2);
```

Used when business logic lives inside the database — common in older banking and payment cores.

### Comparison

| | `Statement` | `PreparedStatement` | `CallableStatement` |
|---|---|---|---|
| Parameters | No | Yes (`?`) | Yes + OUT params |
| Precompiled | No | Yes | Yes |
| SQL injection safe | ❌ | ✅ | ✅ |
| Plan reuse | ❌ | ✅ | ✅ |
| Use for | DDL, one-off admin SQL | 99% of application queries | Stored procedures |

---

## `ResultSet` — a Cursor, Not a List

A `ResultSet` is **not** a list of rows sitting in memory. It is a **cursor** pointing at the result on the database side.

```text
        ┌──────────────────────────┐
cursor →│ id=1  user=101  bal=500  │
        │ id=2  user=102  bal=900  │
        │ id=3  user=103  bal=120  │
        └──────────────────────────┘
```

You walk it forward:

```java
ResultSet rs = ps.executeQuery();

while (rs.next()) {
    long id = rs.getLong("id");
    BigDecimal balance = rs.getBigDecimal("balance");
}
```

`rs.next()` returns `false` when there are no more rows.

Key points for interviews:

- The cursor starts **before** the first row — you must call `next()` once before reading.
- It is **forward-only** by default (`TYPE_FORWARD_ONLY`).
- It closes when its `Statement` closes.
- **Fetch size** (`ps.setFetchSize(500)`) controls how many rows the driver pulls over the network per round trip. Default is often 10 — a killer when reading a million-row settlement file.

> [!warning] Reading a huge table
> `SELECT * FROM txn` on 10 million rows with the default fetch size means a network round trip every 10 rows. Set the fetch size, or stream. This is the same problem discussed in [[14. Performance Tuning]].

## Transactions in Raw JDBC

By default, JDBC is in **auto-commit** mode: every statement commits immediately.

That is wrong for a transfer:

```java
// auto-commit = true
debitSender();   // committed
// crash here → money vanished
creditReceiver();
```

You must group them:

```java
Connection con = dataSource.getConnection();
try {
    con.setAutoCommit(false);        // transaction starts

    debit(con, senderWalletId, amount);
    credit(con, receiverWalletId, amount);

    con.commit();                    // both, or neither
} catch (SQLException e) {
    con.rollback();
    throw e;
} finally {
    con.setAutoCommit(true);         // restore before returning to pool
    con.close();
}
```

Note the `finally` block: on a **pooled** connection, leaving auto-commit off would hand the next borrower a connection in an unexpected state. Restoring it is not optional.

You can also set the isolation level:

```java
con.setTransactionIsolation(Connection.TRANSACTION_READ_COMMITTED);
```

And use savepoints for partial rollback:

```java
Savepoint sp = con.setSavepoint("afterDebit");
con.rollback(sp);
```

> [!info] This is what `@Transactional` automates
> Spring's `@Transactional` does exactly this — `setAutoCommit(false)`, commit on success, rollback on exception — around your method. Everything you'll learn about propagation and rollback rules in [[10. Transactions]] is bookkeeping on top of these five calls.

## Batch Processing

Suppose you insert 10,000 ledger entries one at a time.

```text
INSERT → network → DB
INSERT → network → DB
INSERT → network → DB
... 10,000 times
```

10,000 network round trips. Painfully slow — and note that the *database* work was never the bottleneck; the latency was.

With batching:

```java
String sql = "INSERT INTO ledger_entry(txn_id, account, amount) VALUES (?,?,?)";

try (PreparedStatement ps = con.prepareStatement(sql)) {
    for (LedgerEntry e : entries) {
        ps.setString(1, e.getTxnId());
        ps.setString(2, e.getAccount());
        ps.setBigDecimal(3, e.getAmount());
        ps.addBatch();                       // buffer it

        if (++count % 1000 == 0) {
            ps.executeBatch();               // one round trip per 1000
        }
    }
    ps.executeBatch();                       // leftovers
}
```

```text
1000 INSERTs → one network round trip
```

Orders of magnitude faster.

`executeBatch()` returns an `int[]` of update counts. On failure you get a `BatchUpdateException`, which tells you how many statements succeeded — important, because a partially-applied batch is a real state you have to handle.

> [!info] Hibernate does this too
> Hibernate can batch its generated INSERTs, but **only if you configure it** — `spring.jpa.properties.hibernate.jdbc.batch_size`. Out of the box it doesn't, which surprises people profiling a slow bulk import. See [[14. Performance Tuning]].

## Connection Pooling

Opening a database connection is **expensive**:

```text
TCP handshake
    ↓
Authentication
    ↓
Session setup on DB server
    ↓
(finally) run your query
    ↓
Tear everything down
```

This can take 50–100 ms. Your actual query takes 2 ms. Paying the setup cost per request means spending 98% of your time on overhead.

So we don't open a connection per request. We keep a **pool** of already-open connections and borrow one:

```text
Request → borrow from pool → use → return to pool
```

Nothing is closed; `con.close()` on a pooled connection means **"give it back"**. This is worth stating explicitly because the method name actively misleads — and it's why a missing `close()` is a *leak* rather than a merely untidy omission: the connection is never returned, and the pool slowly starves.

Spring Boot ships **HikariCP** as the default pool. Full details — sizing, `maxLifetime`, leak detection, pool exhaustion — are in [[16. Spring Boot Integration]].

## Limitations of JDBC — Why ORM Exists

JDBC works, but writing an entire application in it hurts. These aren't nitpicks; each one is the direct motivation for a feature you'll meet later in the course.

**1. Enormous boilerplate.** Every query needs connection handling, statement creation, parameter binding, result mapping, and resource closing.

**2. Manual object mapping.** You write this for every table, every column, forever:

```java
Wallet w = new Wallet();
w.setId(rs.getLong("id"));
w.setUserId(rs.getLong("user_id"));
w.setBalance(rs.getBigDecimal("balance"));
w.setCurrency(rs.getString("currency"));
```

**3. SQL is scattered as strings.** No compile-time checking. A typo in a column name is found at runtime, in production.

**4. Relationships are manual.** `wallet.getTransactions()` doesn't exist — you write the join and assemble the object graph yourself.

**5. No change tracking.** You must remember which fields changed and hand-write the `UPDATE`.

**6. No caching.** Ask for the same row three times, pay for three queries.

**7. Database-specific SQL leaks in.** `ROWNUM` (Oracle) vs `LIMIT` (Postgres/MySQL) — portability breaks the moment you write real queries, which quietly undoes the very independence JDBC gave you in §2.

These limitations are exactly what **ORM** was invented to solve → [[2. ORM Basics]].

## ❓ Interview Questions

### Q1. What is JDBC?

JDBC (Java Database Connectivity) is a standard Java API that provides interfaces and classes to connect Java applications with relational databases, execute SQL statements, and process results in a database-independent way.

### Q2. Is JDBC a framework?

No. It is an API.

### Q3. Who implements JDBC?

Database vendors — Oracle, MySQL, PostgreSQL, Microsoft SQL Server. Each provides its own JDBC driver implementing the JDBC interfaces.

### Q4. What is a JDBC Driver?

A Java library supplied by a database vendor that implements the JDBC API and translates JDBC calls into the database's native communication protocol.

### Q5. Why do we need JDBC?

Without JDBC, Java applications would need custom code for every database protocol. JDBC provides a standard abstraction, allowing the same application code to work with different databases by changing only the driver and connection configuration.

### Q6. Statement vs PreparedStatement?

`Statement` sends a complete SQL string that is parsed and planned on every execution and is vulnerable to SQL injection when built by concatenation. `PreparedStatement` sends the SQL once with `?` placeholders — it is precompiled (plan reuse) and injection-safe because parameters are never parsed as SQL.

### Q7. Does `PreparedStatement` prevent SQL injection? How?

Yes. The SQL structure is compiled before parameters are supplied, so a parameter value can never change the meaning of the statement — it is always treated as data, never as SQL.

### Q8. What is auto-commit?

The default JDBC mode where every statement is committed immediately. To make several statements atomic you call `setAutoCommit(false)`, then `commit()` or `rollback()`.

### Q9. Why do we need a connection pool?

Because opening a physical connection (TCP + authentication + session setup) costs tens of milliseconds, far more than most queries. A pool keeps connections open and hands them out, so a request pays only the borrow cost.

### Q10. How does JPA relate to JDBC?

JPA/Hibernate sits above JDBC. `userRepository.save(user)` becomes Hibernate-generated SQL, executed through a JDBC `PreparedStatement`, sent by the vendor driver:

```text
Spring Data JPA → Hibernate → JDBC → Driver → Database
```

---

> [!tip] ⚡ Quick Recall
> - **JDBC = API (interfaces)**, **Driver = vendor implementation**. JDBC is not software and not a framework.
> - Flow: `Your code → JDBC API → Driver → Database`. Your code never touches Oracle directly.
> - `DriverManager.getConnection()` returns an `OracleConnection` behind the `Connection` interface — same idea as `List list = new ArrayList<>()`.
> - **PreparedStatement for everything.** Precompiled + injection-safe. Hibernate uses it exclusively.
> - `ResultSet` is a **forward-only cursor**, not a list. Tune `setFetchSize()` for big reads.
> - Auto-commit is **on** by default — turn it off for multi-statement units of work.
> - `addBatch()` + `executeBatch()` collapses N round trips into one.
> - Pooling exists because opening connections is expensive; `close()` on a pooled connection = return it.
> - JDBC's pain — boilerplate, manual mapping, no change tracking, no cache — is the reason ORM exists.
>
> | Layer | Role |
> |---|---|
> | JDBC API | *What* operations are possible |
> | JDBC Driver | *How* they are performed for one database |
> | Database | Executes the SQL |
