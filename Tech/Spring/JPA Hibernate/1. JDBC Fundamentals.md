**JDBC (Java Database Connectivity)** is a standard Java **API** — a set of interfaces and classes — that lets a Java application connect to a relational database, execute SQL, and read results, without knowing which database it is talking to.

> [!info] Where this fits
> This is the bottom of the stack. Everything above it — Hibernate, JPA, Spring Data JPA — eventually turns into JDBC calls. See [[0. JPA Roadmap]] for the full map.

## 1. Before JDBC existed

Suppose you wrote a Java application.

```text
Java Application
```

And you have an Oracle database.

```text
Oracle Database
```

Question:

**How does Java send this SQL?**

```sql
SELECT * FROM wallet;
```

The answer is...

It **can't**.

Java has no built-in knowledge of:

- Oracle
- MySQL
- PostgreSQL
- SQL Server

Each database speaks its own protocol.

Imagine this analogy.

You know English.

Someone else knows Japanese.

Without a translator, communication is impossible.

Exactly the same problem existed.

---

## 2. Every database speaks differently

Oracle internally understands

```text
Oracle Network Protocol
```

MySQL understands

```text
MySQL Wire Protocol
```

PostgreSQL understands

```text
Postgres Protocol
```

They are NOT the same.

So Java cannot directly communicate with them.

### The design problem

Imagine Java tried this:

```java
Database db = new OracleDatabase();
```

Tomorrow you migrate to PostgreSQL.

Now you need

```java
Database db = new PostgreSQLDatabase();
```

Entire application changes.

Bad design.

Java wanted:

> "I don't care which database you're using."

---

## 3. Java needed one standard API

Java introduced **JDBC** — *Java Database Connectivity*.

Think of JDBC as

```text
A common language between Java and databases.
```

Instead of learning Oracle's language, Java says:

> Every database vendor must implement MY API.

### Analogy

Suppose every mobile charger were different.

```text
Apple Charger
Samsung Charger
OnePlus Charger
Google Charger
```

It would be terrible.

USB Type-C solved that. Every phone supports one interface.

JDBC is like USB Type-C. Every database provides its own implementation behind the scenes.

---

## 4. Who actually talks to the database?

Java only knows interfaces:

```java
Connection
Statement
PreparedStatement
ResultSet
```

Who implements them?

Oracle does. MySQL does. PostgreSQL does.

This implementation is called the **JDBC Driver**.

### Database Driver

A driver is simply a Java library (JAR) provided by the database vendor.

| Database | Driver JAR |
|---|---|
| Oracle | `ojdbc11.jar` |
| PostgreSQL | `postgresql.jar` |
| MySQL | `mysql-connector-j.jar` |

When you add this dependency, Java now knows how to talk to that database.

## 5. Visual architecture

```text
Your Java Code
       │
       ▼
JDBC API (Interfaces)
       │
       ▼
Database Driver
       │
       ▼
Database
```

Notice something.

Your application never talks directly to Oracle.

It talks to JDBC. The driver handles the rest.

### Real example

You write

```java
Connection con =
    DriverManager.getConnection(url, user, password);
```

You never write

```java
OracleConnection connection = ...
```

Why?

Because Java only depends on the JDBC interface. The Oracle driver returns an implementation of `Connection`.

### What happens internally

Suppose you execute

```java
PreparedStatement ps =
    con.prepareStatement("SELECT * FROM wallet WHERE id = ?");
```

Internally:

```text
Java Application
        │
        ▼
PreparedStatement Interface
        │
        ▼
OraclePreparedStatement
        │
        ▼
Oracle Network Packet
        │
        ▼
Oracle Database
```

The interface keeps your code database-independent.

The driver does the database-specific work.

```java

Statement
PreparedStatement
CallableStatement
ResultSet
DriverManager
SQLException
```

The implementation is provided by the database driver.

## 7. Connection lifecycle

Every raw JDBC operation follows the same six steps.

```text
1. Load / discover driver     (automatic since JDBC 4.0)
        ↓
2. Open Connection            DriverManager.getConnection(...)
        ↓
3. Create Statement           con.prepareStatement(sql)
        ↓
4. Execute                    ps.executeQuery() / executeUpdate()
        ↓
5. Process ResultSet          rs.next(), rs.getX(...)
        ↓
6. Close everything           rs, ps, con   (reverse order)
```

Full example — crediting a wallet:

```java
String sql = "UPDATE wallet SET balance = balance + ? WHERE id = ?";

try (Connection con = DriverManager.getConnection(url, user, pass);
     PreparedStatement ps = con.prepareStatement(sql)) {

    ps.setBigDecimal(1, new BigDecimal("500.00"));
    ps.setLong(2, 1L);

    int updated = ps.executeUpdate();
}
```

> [!warning] Always close
> `Connection`, `Statement` and `ResultSet` are OS/network resources. A leaked connection is not garbage collected in a useful way — it stays checked out of the pool until a timeout kills it. `try-with-resources` closes them automatically, in reverse order.
>
> This is the number one cause of the pool exhaustion incident described in [[18. Production Problems]].

## 8. Statement vs PreparedStatement vs CallableStatement

Three interfaces, three jobs.

### Statement — plain, no parameters

```java
Statement st = con.createStatement();
ResultSet rs = st.executeQuery("SELECT * FROM wallet");
```

The SQL string is sent, parsed and planned **every single time**.

If you build it by concatenation:

```java
// NEVER do this
st.executeQuery("SELECT * FROM wallet WHERE user_id = '" + input + "'");
```

If `input` is

```text
' OR '1'='1
```

the query becomes

```sql
SELECT * FROM wallet WHERE user_id = '' OR '1'='1'
```

Every wallet in the system is returned.

That is **SQL Injection**.

### PreparedStatement — precompiled, parameterised

```java
PreparedStatement ps =
    con.prepareStatement("SELECT * FROM wallet WHERE user_id = ?");

ps.setString(1, input);
ResultSet rs = ps.executeQuery();
```

The `?` is a **bind parameter**. The SQL structure is sent to the database once and compiled; only values travel afterwards.

Two benefits:

1. **Safe** — the value is never parsed as SQL. Injection is impossible.
2. **Fast** — the database reuses the cached execution plan.

> [!example] Hibernate always uses PreparedStatement
> Every SQL statement Hibernate generates is a `PreparedStatement` with `?` placeholders. That's why you see `?` in the SQL logs instead of real values. See [[16. Spring Boot Integration]] for how to log the bound values.

### CallableStatement — stored procedures

```java
CallableStatement cs = con.prepareCall("{ call settle_merchant(?, ?) }");
cs.setLong(1, merchantId);
cs.registerOutParameter(2, Types.NUMERIC);
cs.execute();

BigDecimal settledAmount = cs.getBigDecimal(2);
```

Used when business logic lives inside the database (common in older banking/payment cores).

### Comparison

| | Statement | PreparedStatement | CallableStatement |
|---|---|---|---|
| Parameters | No | Yes (`?`) | Yes + OUT params |
| Precompiled | No | Yes | Yes |
| SQL injection safe | ❌ | ✅ | ✅ |
| Plan reuse | ❌ | ✅ | ✅ |
| Use for | DDL, one-off admin SQL | 99% of application queries | Stored procedures |

## 9. ResultSet

A `ResultSet` is **not** a list of rows sitting in memory.

It is a **cursor** pointing at the result on the database side.

```text
        ┌──────────────────────────┐
cursor →│ id=1  user=101  bal=500  │
        │ id=2  user=102  bal=900  │
        │ id=3  user=103  bal=120  │
        └──────────────────────────┘
```

You walk it forward:

```java
ResultSet rs = ps.executeQuery();

while (rs.next()) {
    long id = rs.getLong("id");
    BigDecimal balance = rs.getBigDecimal("balance");
}
```

`rs.next()` returns `false` when there are no more rows.

Key points for interviews:

- The cursor starts **before** the first row — you must call `next()` once before reading.
- It is **forward-only** by default (`TYPE_FORWARD_ONLY`).
- It closes when its `Statement` closes.
- **Fetch size** (`ps.setFetchSize(500)`) controls how many rows the driver pulls over the network per round trip. Default is often 10 — a killer when reading a million-row settlement file.

> [!warning] Reading a huge table
> `SELECT * FROM txn` on 10 million rows with the default fetch size means a network round trip every 10 rows. Set the fetch size, or stream. This is the same problem discussed in [[14. Performance Tuning]].

## 10. Transactions in raw JDBC

By default, JDBC is in **auto-commit** mode: every statement commits immediately.

That is wrong for a transfer:

```java
// auto-commit = true
debitSender();   // committed
// crash here → money vanished
creditReceiver();
```

You must group them:

```java
Connection con = dataSource.getConnection();
try {
    con.setAutoCommit(false);        // transaction starts

    debit(con, senderWalletId, amount);
    credit(con, receiverWalletId, amount);

    con.commit();                    // both, or neither
} catch (SQLException e) {
    con.rollback();
    throw e;
} finally {
    con.setAutoCommit(true);         // restore before returning to pool
    con.close();
}
```

You can also set the isolation level:

```java
con.setTransactionIsolation(Connection.TRANSACTION_READ_COMMITTED);
```

And use savepoints for partial rollback:

```java
Savepoint sp = con.setSavepoint("afterDebit");
con.rollback(sp);
```

> [!info] This is what `@Transactional` automates
> Spring's `@Transactional` does exactly this — `setAutoCommit(false)`, commit on success, rollback on exception — around your method. See [[10. Transactions]].

## 11. Batch processing

Suppose you insert 10,000 ledger entries one at a time.

```text
INSERT → network → DB
INSERT → network → DB
INSERT → network → DB
... 10,000 times
```

10,000 network round trips. Painfully slow.

With batching:

```java
String sql = "INSERT INTO ledger_entry(txn_id, account, amount) VALUES (?,?,?)";

try (PreparedStatement ps = con.prepareStatement(sql)) {
    for (LedgerEntry e : entries) {
        ps.setString(1, e.getTxnId());
        ps.setString(2, e.getAccount());
        ps.setBigDecimal(3, e.getAmount());
        ps.addBatch();                       // buffer it

        if (++count % 1000 == 0) {
            ps.executeBatch();               // one round trip per 1000
        }
    }
    ps.executeBatch();                       // leftovers
}
```

```text
1000 INSERTs → one network round trip
```

Orders of magnitude faster.

`executeBatch()` returns an `int[]` of update counts. On failure you get a `BatchUpdateException` which tells you how many statements succeeded.

> [!info] Hibernate does this too
> Hibernate can batch its generated INSERTs, but **only if you configure it** — `spring.jpa.properties.hibernate.jdbc.batch_size`. See [[14. Performance Tuning]].

## 12. Connection pooling

Opening a database connection is **expensive**:

```text
TCP handshake
    ↓
Authentication
    ↓
Session setup on DB server
    ↓
(finally) run your query
    ↓
Tear everything down
```

This can take 50–100 ms. Your actual query takes 2 ms.

So we don't open a connection per request. We keep a **pool** of already-open connections and borrow one:

```text
Request → borrow from pool → use → return to pool
```

Nothing is closed; `con.close()` on a pooled connection means "give it back".

Spring Boot ships **HikariCP** as the default pool. Full details — sizing, `maxLifetime`, leak detection, pool exhaustion — are in [[16. Spring Boot Integration]].

## 13. Limitations of JDBC

JDBC works, but writing an application entirely in it hurts.

**1. Enormous boilerplate.** Every query needs connection handling, statement creation, parameter binding, result mapping, resource closing.

**2. Manual object mapping.** You write this for every table, every column, forever:

```java
Wallet w = new Wallet();
w.setId(rs.getLong("id"));
w.setUserId(rs.getLong("user_id"));
w.setBalance(rs.getBigDecimal("balance"));
w.setCurrency(rs.getString("currency"));
```

**3. SQL is scattered as strings.** No compile-time checking. A typo in a column name is found at runtime, in production.

**4. Relationships are manual.** `wallet.getTransactions()` doesn't exist — you write the join and assemble the object graph yourself.

**5. No change tracking.** You must remember which fields changed and hand-write the `UPDATE`.

**6. No caching.** Ask for the same row three times, pay for three queries.

**7. Database-specific SQL leaks in.** `ROWNUM` (Oracle) vs `LIMIT` (Postgres/MySQL) — portability breaks the moment you write real queries.

These limitations are exactly what **ORM** was invented to solve → [[2. ORM Basics]].

## ❓ Interview Questions

### Q1. What is JDBC?

JDBC (Java Database Connectivity) is a standard Java API that provides interfaces and classes to connect Java applications with relational databases, execute SQL statements, and process results in a database-independent way.

### Q2. Is JDBC a framework?

No. It is an API.

### Q3. Who implements JDBC?

Database vendors — Oracle, MySQL, PostgreSQL, Microsoft SQL Server. Each provides its own JDBC driver implementing the JDBC interfaces.

### Q4. What is a JDBC Driver?

A Java library supplied by a database vendor that implements the JDBC API and translates JDBC calls into the database's native communication protocol.

### Q5. Why do we need JDBC?

Without JDBC, Java applications would need custom code for every database protocol. JDBC provides a standard abstraction, allowing the same application code to work with different databases by changing only the driver and connection configuration.

### Q6. Statement vs PreparedStatement?

`Statement` sends a complete SQL string that is parsed and planned on every execution and is vulnerable to SQL injection when built by concatenation. `PreparedStatement` sends the SQL once with `?` placeholders — it is precompiled (plan reuse) and injection-safe because parameters are never parsed as SQL.

### Q7. Does `PreparedStatement` prevent SQL injection? How?

Yes. The SQL structure is compiled before parameters are supplied, so a parameter value can never change the meaning of the statement — it is always treated as data, never as SQL.

### Q8. What is auto-commit?

The default JDBC mode where every statement is committed immediately. To make several statements atomic you call `setAutoCommit(false)`, then `commit()` or `rollback()`.

### Q9. Why do we need a connection pool?

Because opening a physical connection (TCP + authentication + session setup) costs tens of milliseconds, far more than most queries. A pool keeps connections open and hands them out, so a request pays only the borrow cost.

### Q10. How does JPA relate to JDBC?

JPA/Hibernate sits above JDBC. `userRepository.save(user)` becomes Hibernate-generated SQL, executed through a JDBC `PreparedStatement`, sent by the vendor driver:

```text
Spring Data JPA → Hibernate → JDBC → Driver → Database
```

---

> [!tip] ⚡ Quick Recall
> - **JDBC = API (interfaces)**, **Driver = vendor implementation**. JDBC is not software and not a framework.
> - Flow: `Your code → JDBC API → Driver → Database`. Your code never touches Oracle directly.
> - `DriverManager.getConnection()` returns an `OracleConnection` behind the `Connection` interface — same idea as `List list = new ArrayList<>()`.
> - **PreparedStatement for everything.** Precompiled + injection-safe. Hibernate uses it exclusively.
> - `ResultSet` is a **forward-only cursor**, not a list. Tune `setFetchSize()` for big reads.
> - Auto-commit is **on** by default — turn it off for multi-statement units of work.
> - `addBatch()` + `executeBatch()` collapses N round trips into one.
> - Pooling exists because opening connections is expensive; `close()` on a pooled connection = return it.
> - JDBC's pain — boilerplate, manual mapping, no change tracking, no cache — is the reason ORM exists.
>
> | Layer | Role |
> |---|---|
> | JDBC API | *What* operations are possible |
> | JDBC Driver | *How* they are performed for one database |
> | Database | Executes the SQL |
