**Entity mapping** is how you tell Hibernate which Java class is which table, which field is which column, and how the primary key is produced. This is the part you touch every single day.

> [!info] Where this fits
> You now know *how* Hibernate manages objects ([[5. Persistence Context]]). This note is *how you describe* those objects. Relationships between entities get their own note → [[7. Relationships]].

> [!info] The through-line of this note
> Annotations look like a list to memorise. They aren't — they're answers to four questions.
>
> 1. **"Which class, which table?"** → `@Entity` and `@Table` (§1–§2). And the rules an entity must obey (no-arg constructor, not `final`) aren't arbitrary — they exist because Hibernate **instantiates reflectively and subclasses for proxies**.
> 2. **"How is a row identified?"** → `@Id` is mandatory because the persistence context from [[5. Persistence Context]] is a map keyed by *(type, id)*. `@GeneratedValue` (§3–§4) is where the biggest hidden performance decision lives: **`IDENTITY` silently disables batch inserts.**
> 3. **"Which field, which column, and how is it stored?"** → `@Column`, `@Transient`, `@Enumerated`, `@Temporal`, `@Lob` (§5–§9). One of these has a default that will corrupt your data: **`@Enumerated` defaults to ORDINAL.**
> 4. **"What if the shape doesn't line up?"** → `@Embeddable` for many columns as one concept, `@MappedSuperclass` for shared fields, `@Converter` for a type the database doesn't have (§10–§12).
> 5. Then the one nobody prepares for and everyone gets asked: **`equals`/`hashCode` on an entity** (§13), which is hard precisely because the id is null before persist and assigned after.
>
> One line to anchor everything: **the annotations describe the mapping; the persistence context is what uses it.**

## Short Notes

---

### 1. `@Entity` and the Rules

```java
@Entity
public class Wallet {
    @Id private Long id;
    private BigDecimal balance;
}
```

- At startup Hibernate scans for `@Entity`, reads every field, and builds the metadata it uses to generate SQL forever after
- Without it, `persist()` throws `IllegalArgumentException: Unknown entity`

| Rule | Why |
|---|---|
| **No-arg constructor** (at least `protected`) | Hibernate instantiates reflectively when reading a `ResultSet` |
| Must have an **`@Id`** | The persistence context can't key it otherwise |
| Must **not be `final`** | Hibernate **subclasses it** to create lazy proxies |
| Fields/getters not `final` | Same reason — proxies override them |

> ⚠️ **Lombok trap**: `@Data` generates `equals`/`hashCode` over **all** fields — including lazy collections. Touching them triggers loading and can blow up inside a `HashSet`. Use `@Getter @Setter` and write them by hand (§13)

---

### 2. `@Table`

- **Optional** — defaults to the class name. `@Entity` is **not** optional

```java
@Table(name = "wallet_master", schema = "payments",
       uniqueConstraints = @UniqueConstraint(columnNames = {"user_id", "currency"}),
       indexes = @Index(name = "idx_wallet_user", columnList = "user_id"))
```

- ⚠️ `uniqueConstraints` and `indexes` are read **only by schema generation** (`ddl-auto`)
- If Flyway/Liquibase manages your schema — as it should in production — they are **documentation only**

---

### 3. `@Id` — Why It's Mandatory

The persistence context is a `Map` keyed by *(entity type, id)*:

```text
(Wallet, 1)  →  Wallet@3f2a
(Wallet, 2)  →  Wallet@8b1c
```

Without an id Hibernate cannot:

- tell whether two objects are the same row
- guarantee **one row = one Java object**
- build `WHERE id = ?` for `UPDATE` / `DELETE`
- look anything up in the first-level cache

> ⭐ **Use wrapper types, not primitives.** `Long`, not `long` — a `null` id means "new, not yet persisted"; a primitive defaults to `0` and Hibernate can't distinguish "new" from "id is genuinely 0"

- **Composite keys**: `@EmbeddedId` (preferred) or `@IdClass`; the embeddable **must** implement `equals`/`hashCode` → [[15. Advanced Hibernate]]

---

### 4. `@GeneratedValue` — the Four Strategies ⭐

| Strategy | How | Verdict |
|---|---|---|
| **`IDENTITY`** | DB auto-increment (`AUTO_INCREMENT`, `SERIAL`) | ⚠️ **Kills batch inserts** |
| **`SEQUENCE`** | DB sequence object, fetched **before** insert | ✅ Best on Oracle/Postgres — allows batching |
| **`TABLE`** | A counter table | ❌ Slow — row locks, contention point |
| **`AUTO`** | Provider chooses | Explicit is better |

> ⚠️ **`IDENTITY` kills batch inserts.** Hibernate must know the id the moment you call `persist()`, and only the DB can supply it — so it **executes the INSERT immediately** and JDBC batching is silently disabled. On thousands of rows: 2 seconds vs 4 minutes

```java
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "wallet_seq")
@SequenceGenerator(name = "wallet_seq", sequenceName = "wallet_sequence", allocationSize = 50)
```

- `allocationSize = 50` → Hibernate grabs 50 ids in one round trip and hands them out from memory
- ⚠️ **`allocationSize` must match the sequence's `INCREMENT BY`**, or you get duplicate key errors

| Database | Recommended |
|---|---|
| Oracle / PostgreSQL | `SEQUENCE` |
| MySQL / MariaDB | `IDENTITY` (no sequence objects) |
| SQL Server | `IDENTITY` or `SEQUENCE` |

- **UUID keys**: generate before hitting the DB (distributed systems, idempotency). Cost: 16 bytes vs 8, and random UUIDv4 **fragments B-tree indexes** — prefer time-ordered UUIDv7/ULID

---

### 5. `@Column`

| Attribute | Meaning |
|---|---|
| `name` | Column name (default: field name via naming strategy) |
| `nullable` | Adds `NOT NULL` **in generated DDL only** |
| `length` | Varchar length (default 255) |
| `precision` / `scale` | `BigDecimal` — total digits / decimal places |
| `insertable = false` | Exclude from generated INSERTs |
| `updatable = false` | Exclude from UPDATEs — **perfect for `created_at`** |

- ⚠️ **`nullable = false` is not validation** — it only affects DDL. For runtime validation use `@NotNull` (Bean Validation). Under Flyway it does nothing at all
- 💰 Money fields: always `BigDecimal` with explicit `precision`/`scale`. **Never `double`**

---

### 6. `@Transient`

| | JPA `@Transient` | Java `transient` keyword |
|---|---|---|
| Package | `jakarta.persistence` | Java language keyword |
| Excludes from | **Persistence** | **Java serialization** |
| Does the other still apply? | Field is still serialized | Field is still persisted |

- Two unrelated mechanisms that share a name. **Classic interview trap**

---

### 7. `@Enumerated` ⭐

```java
@Enumerated(EnumType.ORDINAL)   // ← also the DEFAULT if you omit the annotation
```

- Stores the **position**: `INITIATED`=0, `SUCCESS`=1, `FAILED`=2
- ⚠️ Insert a new constant in the middle → **every existing row shifts meaning**. Historical `SUCCESS` rows silently become `PENDING`. In a payments ledger that's a catastrophe

```java
@Enumerated(EnumType.STRING)
@Column(length = 20)
private TxnStatus status;
```

- Stores `'SUCCESS'` — readable in SQL, reorder-safe, refactor-safe
- Cost: more bytes, and renaming a constant breaks rows — but that's a migration you'd **notice**, unlike ORDINAL's silent corruption

> ⭐ **Always `EnumType.STRING`.** The default being ORDINAL is one of JPA's worst defaults

---

### 8. `@Temporal` and Modern Date/Time

- **Legacy only** — needed for `java.util.Date` / `Calendar`
- **Java 8+ types need no annotation** (JPA 2.2+ maps them natively):

```java
private LocalDate     settlementDate;   // DATE
private LocalDateTime createdAt;        // TIMESTAMP
private Instant       processedAt;      // TIMESTAMP (UTC)
private OffsetDateTime capturedAt;      // TIMESTAMP WITH TIME ZONE
```

- 💰 For payments store `Instant` or `OffsetDateTime` — **never a naive `LocalDateTime`**, or you lose the timezone on a settlement cutoff

---

### 9. `@Lob`

```java
@Lob private String rawIsoMessage;   // CLOB
@Lob private byte[] chequeScan;      // BLOB
```

- ⚠️ **Lobs are eagerly loaded by default** — every `findById` drags a 2 MB payload over the network
- Fix: put lobs in a **separate entity**, or `@Basic(fetch = LAZY)` (which needs bytecode enhancement to actually work → [[17. Hibernate Internals]])

---

### 10. `@Embeddable` / `@Embedded`

Several columns forming **one concept**, but not their own table:

```java
@Embeddable class Money { BigDecimal amount; String currency; }

@Entity class Transaction { @Id Long id; @Embedded Money amount; }
```

```text
transaction:  | id | amount | currency |     ← two Java objects, ONE row
```

- The embeddable has **no id and no lifecycle** — it lives and dies with its owner
- Reuse it twice → `@AttributeOverrides` to rename the columns

| `@Embedded` | `@OneToOne` |
|---|---|
| **Same** table | **Separate** tables + FK |
| No `@Id`, no identity | Has its own `@Id` |
| Cannot be queried alone | Can be loaded/queried independently |
| Lifecycle tied to owner | Independent lifecycle |
| Value object (Money, Address) | Real entity (BankAccount, KycDocument) |

> **Rule of thumb**: no meaning without its parent, and nobody queries it alone → `@Embeddable`

---

### 11. `@MappedSuperclass`

Share fields across entities **without** a table for the parent:

```java
@MappedSuperclass
public abstract class Auditable {
    @Column(updatable = false) private Instant createdAt;
    private Instant updatedAt;
}
```

- Both `wallet` and `transaction` get `created_at` / `updated_at`
- ⭐ There is **no `auditable` table**, and you **cannot** write `SELECT a FROM Auditable a`
- That's the difference from `@Inheritance`, which *is* polymorphic and queryable → [[15. Advanced Hibernate]]
- Pair with `@EntityListeners(AuditingEntityListener.class)` + `@CreatedDate`/`@LastModifiedDate` + `@EnableJpaAuditing`

---

### 12. `@Converter` — Custom Type Mapping

When the Java type and the column type don't line up:

```java
@Converter(autoApply = true)
public class MoneyConverter implements AttributeConverter<Money, BigDecimal> {
    public BigDecimal convertToDatabaseColumn(Money m) { ... }
    public Money      convertToEntityAttribute(BigDecimal v) { ... }
}
```

- Common real use: **encrypting a card number or VPA at rest**

```java
@Convert(converter = EncryptedStringConverter.class)
private String cardNumber;
```

- ⚠️ **Converted columns can't be indexed usefully** — you can no longer do `WHERE card_number = ?` efficiently. Store a **deterministic hash** alongside for lookups

---

### 13. `equals()` and `hashCode()` for Entities ⭐

**The problem**: an entity's `id` is `null` before persist and assigned after. If `hashCode()` uses the id, an entity put into a `HashSet` while transient becomes **unfindable** once persisted — its bucket changed.

```java
// ✅ Best: a business key
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Transaction that)) return false;      // instanceof, NOT getClass()
    return referenceId != null && referenceId.equals(that.referenceId);
}
public int hashCode() { return Objects.hash(referenceId); }  // stable, never null
```

```java
// ✅ No natural key? Keep hashCode CONSTANT so it survives id assignment
public int hashCode() { return getClass().hashCode(); }
```

- ⭐ Use **`instanceof`, not `getClass() ==`** — a lazy **proxy is a subclass**, so `getClass()` comparison fails for proxies

# Detailed Explanation

---

## `@Entity` and the Rules

```java
@Entity
public class Wallet {

    @Id
    private Long id;

    private BigDecimal balance;
}
```

`@Entity` tells Hibernate:

> This class is not an ordinary POJO. It maps to a table, and I want you to manage its lifecycle.

At startup Hibernate scans for `@Entity`, reads every field, and builds the metadata it will use to generate SQL forever after.

### The rules an entity must follow

| Rule | Why |
|---|---|
| Must have a **no-arg constructor** (at least `protected`) | Hibernate instantiates entities reflectively when reading a `ResultSet` |
| Must have an **`@Id`** | Without identity, the persistence context can't key it |
| Must **not be `final`** | Hibernate subclasses it to create lazy proxies |
| Fields/getters must not be `final` | Same reason — proxies override them |
| Should be a top-level class, not an `enum`/`interface` | Spec requirement |

These aren't arbitrary ceremony. Read the "why" column and you'll notice both rules trace back to mechanisms from [[4. Hibernate]]: Hibernate builds objects by reflection (so it needs a constructor it can call with no arguments) and builds lazy proxies by **subclassing your class** (so it can't be `final`). If you can state that, you've answered the question properly rather than reciting a checklist.

> [!warning] Kotlin/Lombok trap
> `@Data` generates `equals`/`hashCode` over **all** fields — including lazy collections. Touching them triggers loading and can blow up in a `HashSet`. Use `@Getter @Setter` and write `equals`/`hashCode` by hand (see §13).

Without `@Entity`, Hibernate ignores the class entirely and `persist()` throws `IllegalArgumentException: Unknown entity`.

---

## `@Table`

By default the table name = the class name.

```java
@Entity                 // → table "Wallet"
public class Wallet { }
```

Override it when the DB naming differs:

```java
@Entity
@Table(
    name = "wallet_master",
    schema = "payments",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_wallet_user_currency",
        columnNames = {"user_id", "currency"}),
    indexes = @Index(name = "idx_wallet_user", columnList = "user_id")
)
public class Wallet { }
```

`@Table` is **optional**. `@Entity` is not.

> [!note] Constraints here are only used by schema generation
> `uniqueConstraints` and `indexes` are read by `ddl-auto` when Hibernate creates the schema. If your schema is managed by Flyway/Liquibase (it should be in production), they are documentation only — the real constraint lives in the migration script.
>
> This trips people up in review: someone adds a `@UniqueConstraint`, the tests pass against an H2 schema Hibernate generated, and production has no such constraint at all.

---

## `@Id` — Why It's Mandatory

Every entity **must** have an identifier.

Reason: the Persistence Context is a `Map` keyed by *(entity type, id)*.

```text
Persistence Context
   (Wallet, 1)  →  Wallet@3f2a
   (Wallet, 2)  →  Wallet@8b1c
```

Without an id Hibernate cannot:

- tell whether two objects are the same row
- guarantee one row = one Java object
- build the `WHERE id = ?` for UPDATE / DELETE
- look anything up in the first-level cache

That's why `@Id` is not optional. It isn't a database requirement Hibernate is passing along — it's a requirement of the persistence context from [[5. Persistence Context]] §10. Every guarantee that note makes depends on being able to key the map.

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

> [!tip] Use wrapper types, not primitives
> `Long`, not `long`. A `null` id means "new, not yet persisted". A primitive `long` defaults to `0`, and Hibernate can't distinguish "new" from "id is genuinely 0".

### Composite keys

Two annotations do this — `@EmbeddedId` (preferred) and `@IdClass`.

```java
@Embeddable
public class SettlementId implements Serializable {
    private Long merchantId;
    private LocalDate settlementDate;
    // equals + hashCode are MANDATORY
}

@Entity
public class Settlement {
    @EmbeddedId
    private SettlementId id;
}
```

The `equals`/`hashCode` requirement isn't stylistic — the id **is** the map key, so without them the persistence context cannot find anything.

More in [[15. Advanced Hibernate]].

---

## `@GeneratedValue` — the Four Strategies

```java
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE)
private Long id;
```

### IDENTITY

Uses the database's auto-increment column (`AUTO_INCREMENT` in MySQL, `IDENTITY` in SQL Server, `SERIAL` in Postgres).

```sql
INSERT INTO wallet(balance) VALUES (5000);   -- DB assigns id
```

> [!warning] IDENTITY kills batch inserts
> Hibernate must know the id the moment you call `persist()`, and only the database can supply it. So it **executes the INSERT immediately** and cannot queue statements — JDBC batching is silently disabled. If you insert thousands of rows, this is the difference between 2 seconds and 4 minutes. See [[14. Performance Tuning]].
>
> This is the single highest-value fact in this note, because it is invisible: nothing errors, nothing warns, and the code looks identical to the fast version. You only find it by watching the SQL log or the clock.

### SEQUENCE

Uses a database sequence object. Default and best on Oracle and PostgreSQL.

```java
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "wallet_seq")
@SequenceGenerator(name = "wallet_seq", sequenceName = "wallet_sequence",
                   allocationSize = 50)
private Long id;
```

Hibernate asks the sequence for a value **before** inserting, so it can defer and batch the INSERTs.

`allocationSize = 50` means Hibernate grabs a block of 50 ids in one round trip and hands them out from memory — 50× fewer sequence calls.

> [!warning] allocationSize must match the sequence INCREMENT BY
> If the DB sequence increments by 1 but Hibernate thinks it has a block of 50, you get duplicate key errors. Either set `allocationSize = 1` or create the sequence with `INCREMENT BY 50`.

### TABLE

Simulates a sequence using a separate table of counters. Portable but **slow** — it needs row locks on the counter table and becomes a contention point. Avoid.

### AUTO

Lets the provider choose. On Hibernate 6 this usually means `SEQUENCE` (with a shared `hibernate_sequence` if you don't name one). Explicit is better than implicit — pick the real strategy.

### Which to use?

| Database | Recommended |
|---|---|
| Oracle | `SEQUENCE` |
| PostgreSQL | `SEQUENCE` |
| MySQL / MariaDB | `IDENTITY` (MySQL has no sequence objects) |
| SQL Server | `IDENTITY` or `SEQUENCE` |

### UUID keys

```java
@Id
@GeneratedValue
private UUID id;
```

Useful when the id must be generated **before** hitting the DB (distributed systems, idempotency keys). Cost: 16 bytes instead of 8, and random UUIDv4 fragments B-tree indexes badly — every insert lands at a random point in the index instead of appending at the end. Prefer time-ordered UUIDv7/ULID for high-insert tables.

## `@Column`

```java
@Column(
    name = "wallet_balance",
    nullable = false,
    precision = 19,
    scale = 4,
    updatable = true,
    insertable = true
)
private BigDecimal balance;
```

| Attribute | Meaning |
|---|---|
| `name` | Column name (default: field name, camelCase → snake_case via naming strategy) |
| `nullable` | Adds `NOT NULL` in generated DDL; **does not validate at runtime** |
| `length` | Varchar length (default 255) |
| `precision` / `scale` | For `BigDecimal` — total digits / decimal places |
| `unique` | Unique constraint in generated DDL |
| `insertable = false` | Exclude the column from generated INSERTs |
| `updatable = false` | Exclude from UPDATEs — perfect for `created_at` |

> [!warning] nullable = false is not validation
> It only affects DDL generation. For actual runtime validation use `@NotNull` from Bean Validation. If your schema is managed by Flyway, `nullable = false` does nothing at all.

Money fields: always `BigDecimal` with explicit `precision`/`scale`. Never `double` — binary floating point cannot represent `0.10` exactly, and a ledger that is off by fractions of a paisa per row will fail reconciliation.

## `@Transient`

Marks a field Hibernate should ignore — no column, not persisted.

```java
@Transient
private BigDecimal balanceInUsd;   // computed at runtime
```

### `@Transient` vs Java's `transient`

| | JPA `@Transient` | Java `transient` keyword |
|---|---|---|
| Package | `jakarta.persistence` | Java language keyword |
| Affects | **Persistence** — skipped by Hibernate | **Java serialization** — skipped by `ObjectOutputStream` |
| Other one still applies? | Field is still serialized | Field is still persisted |

They are unrelated mechanisms that happen to share a name. Classic interview trap.

## `@Enumerated`

```java
public enum TxnStatus { INITIATED, SUCCESS, FAILED, REVERSED }
```

### ORDINAL (the default — dangerous)

```java
@Enumerated(EnumType.ORDINAL)   // also the default if you omit the annotation
private TxnStatus status;
```

Stores the **position**: `INITIATED`=0, `SUCCESS`=1, `FAILED`=2, `REVERSED`=3.

Now someone inserts a new constant:

```java
public enum TxnStatus { INITIATED, PENDING, SUCCESS, FAILED, REVERSED }
```

Every existing row shifts meaning. Historical `SUCCESS` transactions silently become `PENDING`. In a payments ledger that is a catastrophe.

Note *how* it fails: the code change is a one-line addition that looks completely safe, passes review, passes tests written against fresh data, and corrupts every historical row the moment it deploys. Nothing throws.

### STRING (always use this)

```java
@Enumerated(EnumType.STRING)
@Column(length = 20)
private TxnStatus status;
```

Stores `'SUCCESS'`. Readable in SQL, reorder-safe, refactor-safe.

Cost: more bytes, and renaming a constant breaks existing rows (a migration you'd notice, unlike ORDINAL's silent corruption).

> [!tip] Rule
> **Always `@Enumerated(EnumType.STRING)`.** The default being ORDINAL is one of JPA's worst defaults.

---

## `@Temporal` and Modern Date/Time

Legacy — needed only for `java.util.Date` / `Calendar`:

```java
@Temporal(TemporalType.TIMESTAMP)
private Date createdAt;
```

Modern (Java 8+) — **no annotation needed**, JPA 2.2+ maps these natively:

```java
private LocalDate settlementDate;       // DATE
private LocalDateTime createdAt;        // TIMESTAMP
private Instant processedAt;            // TIMESTAMP (UTC)
private OffsetDateTime capturedAt;      // TIMESTAMP WITH TIME ZONE
```

For payments, store `Instant` or `OffsetDateTime` — never a naive `LocalDateTime`, or you will lose the timezone on a settlement cutoff. A `LocalDateTime` of `2026-03-31 23:55` is ambiguous the moment two services in different regions read it, and settlement windows are precisely where that ambiguity costs money.

---

## `@Lob`

For large objects.

```java
@Lob
private String rawIsoMessage;    // CLOB

@Lob
private byte[] chequeScan;       // BLOB
```

> [!warning] Lobs are eagerly loaded by default
> A `@Lob` column is fetched with the entity, so every `findById` drags a 2 MB payload over the network. Either put lobs in a separate entity, or use `@Basic(fetch = FetchType.LAZY)` (which requires bytecode enhancement to actually work → [[17. Hibernate Internals]]).
>
> The separate-entity approach is usually the better answer, because it works without any enhancement configuration and makes the cost visible in the model rather than hidden in a build plugin.

---

## `@Embeddable` / `@Embedded`

Sometimes several columns form one concept but not their own table.

```java
@Embeddable
public class Money {

    @Column(name = "amount", precision = 19, scale = 4)
    private BigDecimal amount;

    @Column(name = "currency", length = 3)
    private String currency;
}
```

```java
@Entity
public class Transaction {

    @Id
    private Long id;

    @Embedded
    private Money amount;
}
```

One table:

```text
transaction

+----+--------+----------+
| id | amount | currency |
+----+--------+----------+
```

Two Java objects, **one** row. The embeddable has **no id and no lifecycle of its own** — it lives and dies with its owner.

The design win is worth naming: an amount and its currency should never be separable, and modelling them as two loose fields on the entity invites exactly that bug. `Money` as an embeddable makes "amount without currency" unrepresentable.

Reusing the same embeddable twice needs column overrides:

```java
@Embedded
@AttributeOverrides({
    @AttributeOverride(name = "amount", column = @Column(name = "fee_amount")),
    @AttributeOverride(name = "currency", column = @Column(name = "fee_currency"))
})
private Money fee;
```

### `@Embedded` vs `@OneToOne`

| `@Embedded` | `@OneToOne` |
|---|---|
| **Same** table | **Separate** tables + FK |
| No `@Id`, no independent identity | Has its own `@Id` |
| Cannot be queried on its own | Can be loaded/queried independently |
| Lifecycle tied to owner | Independent lifecycle (cascade optional) |
| Value object (Money, Address) | Real entity (BankAccount, KycDocument) |

Rule of thumb: if it has no meaning without its parent and no one ever queries it alone → `@Embeddable`.

---

## `@MappedSuperclass`

Shares fields across entities **without** creating a table for the parent.

```java
@MappedSuperclass
public abstract class Auditable {

    @Column(updatable = false)
    private Instant createdAt;

    private Instant updatedAt;

    private String createdBy;
}
```

```java
@Entity
public class Wallet extends Auditable { ... }

@Entity
public class Transaction extends Auditable { ... }
```

Both `wallet` and `transaction` tables get `created_at`, `updated_at`, `created_by`. There is **no** `auditable` table, and you **cannot** write `SELECT a FROM Auditable a`.

That last point is the difference from `@Inheritance`, which *is* polymorphic and queryable → [[15. Advanced Hibernate]]. Choose `@MappedSuperclass` when the shared fields are **incidental** (audit columns) and `@Inheritance` when the parent is a real business concept you'd want to query across (`PaymentInstrument`).

Pair it with Spring Data auditing:

```java
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class Auditable {
    @CreatedDate  @Column(updatable = false) private Instant createdAt;
    @LastModifiedDate                        private Instant updatedAt;
}
```

plus `@EnableJpaAuditing` on a config class.

## `@Converter` — Custom Type Mapping

When the Java type and the column type don't line up, write a converter.

```java
@Converter(autoApply = true)
public class MoneyConverter implements AttributeConverter<Money, BigDecimal> {

    @Override
    public BigDecimal convertToDatabaseColumn(Money money) {
        return money == null ? null : money.getAmount();
    }

    @Override
    public Money convertToEntityAttribute(BigDecimal value) {
        return value == null ? null : new Money(value, "INR");
    }
}
```

Common real use: encrypting a card number or a VPA at rest.

```java
@Convert(converter = EncryptedStringConverter.class)
private String cardNumber;
```

> [!warning] Converted columns can't be indexed usefully
> If you encrypt a column you can no longer do `WHERE card_number = ?` efficiently — the stored value is ciphertext, so an index on it can only match ciphertext. Store a deterministic hash alongside for lookups, and index that.

## `equals()` and `hashCode()` for Entities

An underrated interview question.

The problem: an entity's `id` is `null` before persist and assigned after. If `hashCode()` depends on the id, an entity put into a `HashSet` while transient becomes **unfindable** once persisted — its bucket changed.

Concretely: you add a new `Transaction` to `order.getTransactions()` (a `HashSet`), then flush. The id goes from `null` to `42`, the hash changes, and `set.contains(txn)` now returns `false` for an object that is *in* the set. Nothing throws; the collection is simply, quietly wrong.

Safe approach — use a **business key**:

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Transaction that)) return false;
    return referenceId != null && referenceId.equals(that.referenceId);
}

@Override
public int hashCode() {
    return Objects.hash(referenceId);     // stable, never null
}
```

If there is no natural key, use the id but keep `hashCode()` constant:

```java
@Override
public int hashCode() {
    return getClass().hashCode();   // constant → survives id assignment
}
```

A constant hash code sounds wrong — it degrades a `HashSet` to a linked list — but entity collections are small, and correctness beats bucket distribution here.

Also note `instanceof` (not `getClass() ==`) — a lazy **proxy** is a subclass, so `getClass()` comparison fails for proxies. This is the same proxy mechanism from [[4. Hibernate]] §12 showing up in a place nobody expects it.

> 💡 **Interview**: how do you write `equals`/`hashCode` for a JPA entity? → Prefer a business key. If you must use the id, keep `hashCode()` constant so it survives the transient→persistent transition, and compare with `instanceof` so lazy proxies still match.

## ❓ Interview Questions

### Q1. Why `@Entity`?

It marks a class as a persistent type so Hibernate builds mapping metadata for it and manages its lifecycle. Without it Hibernate does not know the class exists.

### Q2. Why is `@Id` mandatory?

The persistence context is keyed by entity type + identifier. Without an id, Hibernate cannot guarantee one-row-one-object, cannot cache, and cannot generate `WHERE` clauses for UPDATE/DELETE.

### Q3. Which `GenerationType` for Oracle vs MySQL?

- **Oracle** → `SEQUENCE` (Oracle has real sequences; it also allows Hibernate to batch inserts).
- **MySQL** → `IDENTITY` (auto-increment; MySQL has no sequence objects).

Note the trade-off: `IDENTITY` forces an immediate INSERT per `persist()` and disables JDBC batching.

### Q4. Difference between `@Transient` and Java's `transient`?

`@Transient` (JPA) excludes a field from **persistence**. `transient` (Java keyword) excludes it from **serialization**. Neither implies the other.

### Q5. `@Embedded` vs `@OneToOne`?

`@Embedded` inlines a value object's columns into the **same** table with no identity of its own. `@OneToOne` is a relationship between two independent entities in **separate** tables joined by a foreign key.

### Q6. Why is `EnumType.ORDINAL` dangerous?

It stores the enum's position. Inserting or reordering a constant silently changes the meaning of every existing row. Use `EnumType.STRING`.

### Q7. What is `@MappedSuperclass` and how does it differ from `@Inheritance`?

`@MappedSuperclass` shares mapped fields with subclasses but is **not** an entity — no table, not queryable, not polymorphic. `@Inheritance` makes a real entity hierarchy that can be queried polymorphically.

### Q8. Why must an entity have a no-arg constructor and not be final?

Hibernate instantiates entities reflectively and creates **proxy subclasses** for lazy loading. A `final` class cannot be subclassed; a missing no-arg constructor cannot be instantiated.

### Q9. How would you map an encrypted column?

An `AttributeConverter` (`@Convert`) that encrypts on write and decrypts on read — transparent to the rest of the application.

> [!tip] ⚡ Quick Recall
> - `@Entity` is mandatory; `@Table` is optional. Entity needs a **no-arg constructor**, an **`@Id`**, and must **not be final** (proxies subclass it).
> - `@Id` is mandatory because the persistence context is a map keyed by *(type, id)*. Use `Long`, not `long`.
> - **`IDENTITY`** → DB auto-increment, forces immediate INSERT, **kills batching**. **`SEQUENCE`** → best on Oracle/Postgres, allows batching, tune `allocationSize`. **`TABLE`** → portable but slow. **`AUTO`** → provider decides.
> - `@Column(updatable = false)` for `created_at`. `nullable = false` affects **DDL only**, not runtime validation.
> - **`@Enumerated(EnumType.STRING)` always** — ORDINAL silently corrupts data when the enum changes.
> - `@Transient` = skip persistence. `transient` = skip Java serialization. Unrelated.
> - `@Embeddable` = value object inlined into the **same table**, no identity. `@OneToOne` = separate table + FK + own identity.
> - `@MappedSuperclass` = share columns, **no table, not queryable**.
> - `LocalDate` / `Instant` need no `@Temporal`. `@Lob` is eager by default.
> - `equals`/`hashCode`: use a business key, or a constant `hashCode`; use `instanceof` so proxies still match.
