Authentication answered *"who are you?"*. Authorization answers *"what are you allowed to do?"* — and it's where senior interviews spend most of their time, because the interesting cases (ownership, fine-grained permissions, 401 vs 403) all live here.

> [!info] 🧭 Summary
> - **Authentication first, authorization second.** Authorization can only work once `SecurityContextHolder` holds an `Authentication`.
> - Two levels: **URL-based** (`authorizeHttpRequests`, enforced by `AuthorizationFilter`) and **method-based** (`@PreAuthorize`, enforced by an AOP proxy).
> - Rules are evaluated **top to bottom, first match wins** → put the **most specific matcher first**, `anyRequest()` last.
> - `permitAll()` = no login needed · `authenticated()` = any logged-in user · `hasRole("ADMIN")` = a specific role · `denyAll()` = nobody.
> - **`hasRole("ADMIN")` is literally `hasAuthority("ROLE_ADMIN")`** — Spring prepends the `ROLE_` prefix. `hasAuthority(...)` does an exact string match with no transformation.
> - Internally Spring has **no concept of "role"** — a role is just an authority whose name starts with `ROLE_`.
> - Convention: **roles** for coarse-grained identity (`ADMIN`, `MANAGER`), **authorities** for fine-grained permissions (`DELETE_USERS`, `READ_REPORTS`).
> - `@EnableMethodSecurity` unlocks **`@PreAuthorize`** (before, most common), **`@PostAuthorize`** (after, filters the return value), `@Secured` / `@RolesAllowed` (older, no SpEL).
> - SpEL gives you **ABAC**: `@PreAuthorize("#id == authentication.principal.id")` — "you may only read your own data".
> - **401 = not authenticated** (no/invalid credentials). **403 = authenticated but not permitted.**
>

## 1. Authentication vs authorization

```text
User: Umesh
Role: ADMIN

Authentication  ->  "Who is this user?"                  ->  Umesh
Authorization   ->  "Can Umesh access /admin/users?"     ->  yes (ADMIN)
```

Order is forced by the filter chain:

```text
Request
   |
Authentication Filter        writes the Authentication
   |
SecurityContextHolder
   |
AuthorizationFilter          reads it and decides
   |
Controller
```

Spring must know *who* you are before it can ask *what* you may do. Get this order wrong (see [[1. Filters and SecurityFilterChain]]) and everything is a 403.

## 2. URL-based authorization

The everyday form:

```java
@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {

    http.authorizeHttpRequests(auth -> auth

            .requestMatchers("/public/**", "/login").permitAll()

            .requestMatchers("/admin/**").hasRole("ADMIN")

            .requestMatchers(HttpMethod.DELETE, "/api/users/**").hasAuthority("DELETE_USERS")

            .requestMatchers("/reports/**").hasAnyRole("ADMIN", "MANAGER")

            .anyRequest().authenticated()
    );

    return http.build();
}
```

`AuthorizationFilter` reads the current authorities:

```text
Authentication
    |
    +--> Principal    = umesh
    +--> Authorities  = [ROLE_USER]

Request:  GET /admin/users
Required: ROLE_ADMIN
Actual:   ROLE_USER
Result:   403 Forbidden        (the controller never runs)
```

### The matchers

| Rule | Meaning |
|---|---|
| `permitAll()` | No authentication required at all — anonymous users included |
| `authenticated()` | Any logged-in user; role is irrelevant |
| `hasRole("ADMIN")` | Must have `ROLE_ADMIN` |
| `hasAnyRole("ADMIN", "MANAGER")` | Either role |
| `hasAuthority("DELETE_USERS")` | Exact authority string |
| `hasAnyAuthority(...)` | Any of them |
| `denyAll()` | Nobody, ever — useful to shut off a path explicitly |
| `anonymous()` | *Only* not-logged-in users (e.g. a signup page) |
| `access(...)` | Full `AuthorizationManager` / SpEL for anything else |

> [!warning] Order matters — first match wins
> ```java
> .requestMatchers("/**").authenticated()          // matches EVERYTHING
> .requestMatchers("/public/**").permitAll()       // never reached
> ```
> Rules are evaluated top to bottom and the first matching one decides. Always go **most specific → least specific**, with `anyRequest()` last. In Spring Security 6 a request matching *no* rule throws an error at startup rather than being silently permitted — an improvement, but don't rely on it.

> [!tip] Don't secure by URL alone
> URL rules are easy to bypass through a different entry point (a scheduled job, a message consumer, a second controller mapped to the same service). Defence in depth = URL rules **plus** method security on the service layer.

## 3. `hasRole()` vs `hasAuthority()` — the technical difference

The most misunderstood pair in Spring Security.

### `hasAuthority()` — exact match

```java
.hasAuthority("ROLE_ADMIN")     // checks the authority string "ROLE_ADMIN"
.hasAuthority("READ_REPORTS")   // checks the authority string "READ_REPORTS"
```

No transformation. The string you write is the string Spring looks for.

### `hasRole()` — a convenience wrapper

```java
.hasRole("ADMIN")
```

is internally:

```java
hasAuthority("ROLE_" + "ADMIN")   // -> "ROLE_ADMIN"
```

Spring **prepends `ROLE_`** for you. That's the entire difference.

### The four cases

Suppose the user's authorities are `[ROLE_ADMIN, READ_REPORTS, WRITE_REPORTS]`:

| Expression | Spring actually checks | Result |
|---|---|---|
| `hasRole("ADMIN")` | `ROLE_ADMIN` | ✅ allowed |
| `hasAuthority("ROLE_ADMIN")` | `ROLE_ADMIN` | ✅ allowed (identical to the above) |
| `hasAuthority("READ_REPORTS")` | `READ_REPORTS` | ✅ allowed |
| `hasRole("READ_REPORTS")` | `ROLE_READ_REPORTS` | ❌ **denied** — that authority doesn't exist |

> [!warning] Two failure modes to remember
> - **Double prefix:** storing the authority as `ROLE_ADMIN` *and* writing `hasRole("ROLE_ADMIN")` → Spring checks `ROLE_ROLE_ADMIN` → always denied. `hasRole` takes the role **without** the prefix.
> - **Missing prefix:** storing plain `ADMIN` in the DB and writing `hasRole("ADMIN")` → Spring checks `ROLE_ADMIN`, you have `ADMIN` → denied. Either store the prefix or add it when building authorities.

### The key insight

**Spring Security does not distinguish roles from authorities.** Internally there is one flat `Collection<GrantedAuthority>` of strings. `ROLE_ADMIN` is just an authority whose name happens to start with `ROLE_`. The only special behaviour anywhere is `hasRole()` adding the prefix.

So these two lines are **exactly equivalent**:

```java
.hasRole("ADMIN")
.hasAuthority("ROLE_ADMIN")
```

### When to use which

| | Use for | Examples |
|---|---|---|
| **Roles** | Coarse-grained identity — *who you are* | `ADMIN`, `USER`, `MANAGER`, `SUPPORT` |
| **Authorities** | Fine-grained permissions — *what you may do* | `READ_REPORTS`, `WRITE_REPORTS`, `DELETE_USERS`, `EXPORT_LEDGER` |

The common enterprise pattern is both at once — roles map to permission sets:

```text
Admin user     ->  ROLE_ADMIN   + READ_REPORTS, WRITE_REPORTS, DELETE_USERS
Manager user   ->  ROLE_MANAGER + READ_REPORTS, WRITE_REPORTS
Support user   ->  ROLE_SUPPORT + READ_REPORTS
```

```java
.requestMatchers("/admin/**").hasRole("ADMIN")                    // section-level
.requestMatchers(HttpMethod.DELETE, "/api/users/**")
        .hasAuthority("DELETE_USERS")                             // operation-level
```

Why this beats roles alone: when a new "Auditor" role needs report access, you grant it `READ_REPORTS` instead of hunting through the codebase for every `hasAnyRole("ADMIN","MANAGER")` and adding one more name.

## 4. Where authorities come from

From `UserDetails`:

```java
@Override
public Collection<? extends GrantedAuthority> getAuthorities() {
    return Stream.concat(
            user.getRoles().stream()
                .map(r -> new SimpleGrantedAuthority("ROLE_" + r.getName())),
            user.getRoles().stream()
                .flatMap(r -> r.getPermissions().stream())
                .map(p -> new SimpleGrantedAuthority(p.getName()))
    ).toList();
}
```

They land in the `Authentication` at login:

```text
Authentication
     |
     +--> Principal     CustomUserDetails
     |
     +--> Authorities   ROLE_ADMIN
                        READ_REPORTS
                        DELETE_USERS
```

and `AuthorizationFilter` reads exactly that collection.

For an OAuth2 resource server they come from the token instead — JWT scopes become `SCOPE_read`, `SCOPE_write` by default, and a `JwtAuthenticationConverter` maps custom claims (like Keycloak's `realm_access.roles`) into `ROLE_*`. See [[8. OAuth2 and OpenID Connect]].

> [!warning] Authorities are a snapshot
> They're captured at login and live for the whole session or token lifetime. Revoke an admin's role in the database and — with a JWT — they stay admin until the token expires. This is *the* argument for short access-token lifetimes ([[9. Refresh Tokens and Token Security]]).

## 5. Method-level authorization

URL rules aren't always enough:

```text
GET /users/1
GET /users/2
```

Both hit the same handler, so no URL pattern can distinguish them:

```java
@GetMapping("/users/{id}")
public User get(@PathVariable Long id) { ... }
```

But user A must not read user B's data. That's what method security is for.

### Enable it

```java
@Configuration
@EnableMethodSecurity      // prePostEnabled = true by default
public class MethodSecurityConfig { }
```

Without this annotation, `@PreAuthorize` is **silently ignored** — a genuinely dangerous failure mode, and a favourite interview trap.

### `@PreAuthorize` — checked before the method runs

```java
@PreAuthorize("hasRole('ADMIN')")
public List<User> getAllUsers() { ... }

@PreAuthorize("hasAnyRole('ADMIN','MANAGER')")
public Report getReport() { ... }

@PreAuthorize("hasAuthority('DELETE_USERS')")
public void deleteUser(Long id) { ... }
```

```text
Request -> Controller -> @PreAuthorize check -> method executes
                              |
                         fail -> AccessDeniedException -> 403
```

The method body never runs on failure — nothing is loaded, nothing is mutated.

### SpEL and ABAC — "only your own data"

```java
@PreAuthorize("#id == authentication.principal.id")
public User getProfile(@PathVariable Long id) { ... }
```

```text
principal.id = 5

GET /users/5   ->  5 == 5   ->  allowed
GET /users/6   ->  5 != 6   ->  403
```

Combine with a role escape hatch:

```java
@PreAuthorize("hasRole('ADMIN') or #id == authentication.principal.id")
public User getProfile(Long id) { ... }
```

This is **ABAC** (Attribute-Based Access Control) — the decision depends on *attributes of the request and the resource*, not just the user's role. Extremely common in real systems: "a merchant may only see their own settlements".

Useful SpEL handles inside the expression:

| Expression | Meaning |
|---|---|
| `#paramName` | A method argument |
| `authentication` | The current `Authentication` object |
| `authentication.principal` | Your `UserDetails` |
| `principal` | Shorthand for the same |
| `returnObject` | The return value (**`@PostAuthorize` only**) |
| `@beanName.method(...)` | Call any Spring bean — the cleanest way to keep complex rules out of the annotation |

That last one is what you want for anything non-trivial:

```java
@PreAuthorize("@orderSecurity.canView(#orderId, authentication)")
public Order getOrder(Long orderId) { ... }
```

### `@PostAuthorize` — checked after the method runs

```java
@PostAuthorize("returnObject.owner == authentication.name")
public Document getDocument(Long id) { ... }
```

The method executes, *then* Spring inspects the returned object and throws `AccessDeniedException` if the rule fails.

Use it when ownership can only be known after loading the entity. Two caveats: the work is already done (wasted, and any side effects already happened), and inside a transaction the changes still get rolled back only if the exception propagates — so prefer `@PreAuthorize` with a bean call where you can.

`@PreFilter` / `@PostFilter` are the collection variants — they strip disallowed elements from a `Collection` argument or return value. Convenient, but they filter **in memory after loading everything**; for large result sets, filter in the query instead.

### `@Secured` and `@RolesAllowed`

```java
@Secured("ROLE_ADMIN")            // Spring's older annotation
@RolesAllowed("ADMIN")            // the JSR-250 standard equivalent
public void deleteUser() { ... }
```

Both work, neither supports SpEL. `@Secured` needs the full `ROLE_` prefix; `@RolesAllowed` needs `securedEnabled`/`jsr250Enabled` on `@EnableMethodSecurity`. Modern code uses `@PreAuthorize` for everything.

> [!warning] Method security is AOP — the same traps as `@Transactional`
> - **Self-invocation doesn't work.** Calling `this.securedMethod()` from within the same bean bypasses the proxy, so no check runs. Call it through another bean.
> - **`private`, `static` and `final` methods can't be proxied** — annotations on them do nothing.
> - Prefer annotating the **service layer**, not the controller: services are reachable from schedulers and listeners too.

## 6. 401 vs 403

Constantly asked, constantly confused.

| Status | Name | Actually means | Cause |
|---|---|---|---|
| **401** | Unauthorized | **Not authenticated** (misnamed in the spec) | No token, expired token, bad credentials, no session |
| **403** | Forbidden | **Authenticated but not permitted** | `ROLE_USER` calling an `ROLE_ADMIN` endpoint |

```text
No JWT at all         ->  401   "I don't know who you are"
Valid JWT, wrong role ->  403   "I know who you are, and no"
```

Produced by `ExceptionTranslationFilter`:

```text
AuthenticationException  ->  AuthenticationEntryPoint  ->  401 (or a login redirect)
AccessDeniedException    ->  AccessDeniedHandler       ->  403
```

For a JSON API, override both so clients get a body rather than an HTML page:

```java
http.exceptionHandling(ex -> ex
        .authenticationEntryPoint((req, res, e) ->
                res.sendError(HttpStatus.UNAUTHORIZED.value(), "Unauthenticated"))
        .accessDeniedHandler((req, res, e) ->
                res.sendError(HttpStatus.FORBIDDEN.value(), "Forbidden")));
```

> [!tip] The security-conscious variant
> Some APIs deliberately return **404** instead of 403 for resources you don't own, so an attacker can't confirm that order `#8231` exists. Worth mentioning in an interview — it shows you think about information leakage, not just status codes.

## 7. RBAC vs ABAC

| | RBAC | ABAC |
|---|---|---|
| Decision based on | The user's **role** | **Attributes** of user, resource and context |
| Example | `hasRole('ADMIN')` | `#order.merchantId == principal.merchantId` |
| Spring support | `hasRole`, `hasAuthority`, URL rules | `@PreAuthorize` SpEL, custom `AuthorizationManager` |
| Strength | Simple, auditable, easy to reason about | Expresses ownership and context |
| Weakness | Role explosion (`ADMIN_SOUTH_REGION_READONLY`) | Rules scattered and harder to audit |

Real systems use both: RBAC to reach the module, ABAC to reach the row.

```java
// RBAC — can you use the settlements module at all?
.requestMatchers("/settlements/**").hasRole("MERCHANT")

// ABAC — is this settlement yours?
@PreAuthorize("@settlementSecurity.belongsToCaller(#settlementId, authentication)")
public Settlement get(Long settlementId) { ... }
```

For very complex policy (hundreds of rules, external policy authors), the industry answer is an external policy engine — OPA/Rego, Cerbos, or XACML — with Spring calling out to it from a custom `AuthorizationManager`. Worth naming; rarely needed at the scale most services operate.

## 8. Custom `AuthorizationManager`

The extension point behind everything above, if you need programmatic control:

```java
@Component
public class TenantAuthorizationManager
        implements AuthorizationManager<RequestAuthorizationContext> {

    @Override
    public AuthorizationDecision check(Supplier<Authentication> auth,
                                       RequestAuthorizationContext ctx) {
        String tenant = ctx.getRequest().getHeader("X-Tenant-Id");
        var user = (CustomUserDetails) auth.get().getPrincipal();
        return new AuthorizationDecision(user.getTenantId().equals(tenant));
    }
}
```

```java
.requestMatchers("/api/**").access(tenantAuthorizationManager)
```

`AuthorizationManager` replaced the old `AccessDecisionManager` / voter model in Spring Security 6 — mentioning that swap is a cheap way to show you're current.

## ❓ Interview Questions

### Q1. Authentication vs authorization?

Authentication establishes identity ("who are you"); authorization decides permissions ("what may you do"). Authentication runs first and populates `SecurityContextHolder`; authorization reads it.

### Q2. Technical difference between `hasRole()` and `hasAuthority()`?

`hasRole("ADMIN")` is a wrapper that checks `hasAuthority("ROLE_ADMIN")` — it prepends `ROLE_`. `hasAuthority()` matches the exact string. Internally there's only one flat authority collection; "role" is just a naming convention.

### Q3. Does Spring Security distinguish roles from authorities?

No. Both are `GrantedAuthority` strings in one collection. Only `hasRole()`'s automatic prefix treats them differently.

### Q4. `permitAll()` vs `authenticated()` vs `anonymous()`?

`permitAll()` — anyone including anonymous. `authenticated()` — any logged-in user. `anonymous()` — *only* users who are **not** logged in.

### Q5. When do you need method security instead of URL rules?

When the URL can't express the rule — ownership checks (`/users/{id}`), rules depending on method arguments or the return value, or protecting a service reachable from non-HTTP entry points.

### Q6. `@PreAuthorize` vs `@PostAuthorize`?

`@PreAuthorize` evaluates before the method runs (preferred — no wasted work, no side effects). `@PostAuthorize` evaluates after and can inspect `returnObject`, for ownership only knowable post-load.

### Q7. Why is my `@PreAuthorize` being ignored?

Missing `@EnableMethodSecurity`; or self-invocation bypassing the AOP proxy; or the method is `private`/`static`/`final`.

### Q8. 401 vs 403?

401 = not authenticated (missing/invalid credentials). 403 = authenticated but lacking permission. `ExceptionTranslationFilter` maps `AuthenticationException` → 401 and `AccessDeniedException` → 403.

### Q9. How do you implement "a user can only see their own orders"?

ABAC via SpEL: `@PreAuthorize("#userId == authentication.principal.id or hasRole('ADMIN')")`, or delegate to a bean — `@PreAuthorize("@orderSecurity.canView(#orderId, authentication)")`. Enforce it in the service layer, and scope the query by owner as a second line of defence.

### Q10. Where do authorities come from in a JWT setup?

From the token's claims. `JwtAuthenticationConverter` maps `scope`/`scp` to `SCOPE_*` by default; configure it to map custom claims (e.g. `realm_access.roles`) to `ROLE_*`.

> [!tip] ⚡ Quick Recall
> - Authentication writes the context; authorization reads it. **Always in that order.**
> - Two levels: **URL** (`authorizeHttpRequests` → `AuthorizationFilter`) and **method** (`@PreAuthorize` → AOP proxy).
> - Rules are **first match wins** — specific first, `anyRequest()` last.
> - **`hasRole("ADMIN")` ≡ `hasAuthority("ROLE_ADMIN")`.** `hasRole` adds the prefix; `hasAuthority` doesn't.
> - Never write `hasRole("ROLE_ADMIN")` → checks `ROLE_ROLE_ADMIN` → always denied.
> - Roles = coarse (`ADMIN`), authorities = fine (`DELETE_USERS`). Same collection underneath.
> - `@EnableMethodSecurity` or `@PreAuthorize` is **silently ignored**.
> - `@PreAuthorize` before (preferred) · `@PostAuthorize` after (`returnObject`) · `@Secured`/`@RolesAllowed` older, no SpEL.
> - SpEL: `#arg`, `authentication`, `principal`, `returnObject`, `@bean.method(...)`.
> - Method security is AOP → **self-invocation and private methods bypass it**.
> - **401 = who are you? · 403 = I know you, and no.**
> - RBAC to the module, ABAC to the row. `AuthorizationManager` replaced `AccessDecisionManager`.
