Authentication filters *write* here; authorization, `@PreAuthorize` and your service code all *read* from here. One object, one line of code, and most of Spring Security revolves around it.

> [!info] 🧭 Summary
> - Chain of containers: **`SecurityContextHolder` → `SecurityContext` → `Authentication`**.
> - `SecurityContextHolder` stores the context in a **`ThreadLocal`** by default — each request thread sees only its own user. That's why it's safe in a multi-user server.
> - The one line to memorise: `SecurityContextHolder.getContext().getAuthentication()`.
> - **`Authentication`** has four parts: **Principal** (who), **Credentials** (proof, usually nulled after login), **Authorities** (what you can do), **`isAuthenticated()`** (verified?).
> - **Principal** = the identity — after login it's normally your `UserDetails` implementation, so cast it to reach `getId()`, `getEmail()`, etc.
> - Before login: `principal="umesh"`, `credentials="secret123"`, `authorities=[]`, `authenticated=false`. After: `principal=UserDetails`, `credentials=null`, `authorities=[ROLE_ADMIN]`, `authenticated=true`.
> - Prefer **`@AuthenticationPrincipal`** in controllers over reaching into the holder manually.
> - **`ThreadLocal` doesn't cross threads** — `@Async`, `CompletableFuture` and thread pools lose the context. Fix with `DelegatingSecurityContext*` wrappers or `MODE_INHERITABLETHREADLOCAL`.
> - Spring Security 6 makes context persistence **explicit**: `SecurityContextHolderFilter` only *reads*; a custom login must call `securityContextRepository.saveContext(...)` to put it in the session.
>

## 1. The three containers

```text
SecurityContextHolder        static accessor, backed by a ThreadLocal
        |
        v
SecurityContext              a holder with one field
        |
        v
Authentication               the actual user information
        |
        +--> Principal        WHO are you?
        +--> Credentials      HOW did you prove it?
        +--> Authorities      WHAT can you do?
        +--> Authenticated    ARE you verified?
```

For a logged-in admin:

```text
SecurityContext
    |
    v
Authentication
    |
    +--> Principal      CustomUserDetails(umesh@gmail.com)
    +--> Credentials    null
    +--> Authorities    [ROLE_ADMIN]
    +--> Authenticated  true
```

## 2. Why a holder at all?

You're deep inside `OrderService.placeOrder()` and you need the current user — for an audit column, an ownership check, a ledger entry. You do **not** want to thread a `User` parameter through twenty method signatures.

```java
Authentication auth = SecurityContextHolder.getContext().getAuthentication();
```

Spring gives you the current authenticated user **from anywhere in the request**, without changing a single method signature. It's an ambient-context pattern — the same idea as `@Transactional`'s thread-bound `EntityManager`.

---

## 3. Where it's stored — `ThreadLocal`

An interview favourite. By default `SecurityContextHolder` uses `MODE_THREADLOCAL`:

```text
Thread 1  (Request A)
   |
   +--> SecurityContext --> Authentication(User A)

Thread 2  (Request B)
   |
   +--> SecurityContext --> Authentication(User B)
```

Each request is handled by one thread, and each thread has its own copy. User A can never see User B's authentication.

### The three strategies

| Mode | Behaviour |
|---|---|
| **`MODE_THREADLOCAL`** | Default. Context is per-thread, not inherited by child threads. |
| `MODE_INHERITABLETHREADLOCAL` | Child threads inherit the parent's context. Useful with `@Async`, but dangerous with **pooled** threads — a pooled thread keeps whatever it inherited. |
| `MODE_GLOBAL` | One context for the whole JVM. Standalone/desktop apps only. |

> [!warning] The cleanup that must happen
> If the thread returns to Tomcat's pool still holding a `SecurityContext`, the next request on that thread starts as the previous user — a catastrophic cross-user leak. `SecurityContextHolderFilter` **clears the context in a `finally` block** at the end of every request. If you ever set the context outside the filter chain (a scheduled job, a message listener), you own the `SecurityContextHolder.clearContext()` call.

## 4. The `Authentication` object

```java
public interface Authentication extends Principal, Serializable {

    Object getPrincipal();

    Object getCredentials();

    Collection<? extends GrantedAuthority> getAuthorities();

    boolean isAuthenticated();

    Object getDetails();
}
```

### Principal — *who*

The identity of the authenticated party.

```text
Principal --> "umesh@gmail.com"       (a String, before authentication)
Principal --> CustomUserDetails        (your object, after authentication)
Principal --> Jwt                      (in an OAuth2 resource server)
```

`getPrincipal()` returns `Object`, so you cast:

```java
Authentication auth = SecurityContextHolder.getContext().getAuthentication();
CustomUserDetails user = (CustomUserDetails) auth.getPrincipal();

user.getId();
user.getEmail();
```

This is why it's worth exposing `getId()` on your `UserDetails` implementation — you'll want the primary key constantly.

> [!warning] Cast defensively
> For an anonymous request the principal is the **String** `"anonymousUser"`, not a `UserDetails`. An unguarded cast throws `ClassCastException` on any endpoint reachable without login.

### Credentials — *how you proved it*

Usually the password.

```text
Before authentication:   credentials = "secret123"
After  authentication:   credentials = null
```

Spring **erases credentials** on the authenticated token (`ProviderManager` has `eraseCredentialsAfterAuthentication = true` by default) so the password isn't sitting in memory, in a session, or in a log line for the rest of the request.

### Authorities — *what you can do*

```java
Collection<? extends GrantedAuthority> getAuthorities();
```

```java
List.of(
    new SimpleGrantedAuthority("ROLE_ADMIN"),
    new SimpleGrantedAuthority("READ_REPORTS")
);
```

Roles and fine-grained permissions live in the *same* collection — Spring makes no structural distinction between them. See [[6. Authorization]].

### `isAuthenticated()` — *are you verified*

`false` on a login attempt, `true` after a provider validated it. Note the anonymous token also reports `true` — anonymity is a legitimate authenticated state of "nobody".

### `getDetails()` — the extra bit people forget

Set by the filter, typically a `WebAuthenticationDetails` holding the **remote IP address and session id**. Useful for audit logs and IP-based rules.

## 5. Lifecycle: before and after login

**Before** — built by the filter from the request:

```java
new UsernamePasswordAuthenticationToken("umesh", "secret123");
```

```text
Principal     = "umesh"          (a String)
Credentials   = "secret123"
Authorities   = []
Authenticated = false
```

**After** — built by the provider:

```java
new UsernamePasswordAuthenticationToken(userDetails, null, authorities);
```

```text
Principal     = CustomUserDetails
Credentials   = null
Authorities   = [ROLE_ADMIN]
Authenticated = true
```

Side by side:

| | Before | After |
|---|---|---|
| Principal | `"umesh"` (String) | `UserDetails` |
| Credentials | `"secret123"` | `null` |
| Authorities | empty | `[ROLE_ADMIN]` |
| Authenticated | `false` | `true` |

The same class, `UsernamePasswordAuthenticationToken`, plays both roles — which constructor was used is the difference.

## 6. How the context gets populated

Take a JWT request:

```text
Authorization: Bearer eyJhb...
```

```java
// inside JwtAuthenticationFilter
var auth = new UsernamePasswordAuthenticationToken(user, null, user.getAuthorities());
auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));

SecurityContextHolder.getContext().setAuthentication(auth);
```

From this point the whole request knows who the user is:

```text
Request
   |
JwtAuthenticationFilter        validate token, build Authentication
   |
SecurityContextHolder          setAuthentication(...)
   |
AuthorizationFilter            reads it -> hasRole("ADMIN")?
   |
Controller                     @AuthenticationPrincipal
   |
Service                        getContext().getAuthentication()
```

> [!tip] The Spring Security 6 way to set it
> Create a fresh context instead of mutating the existing one — this matters when concurrent requests share a session:
> ```java
> SecurityContext context = SecurityContextHolder.createEmptyContext();
> context.setAuthentication(auth);
> SecurityContextHolder.setContext(context);
> ```

## 7. Reading the current user

### In a controller — the clean way

```java
@GetMapping("/me")
public UserDto me(@AuthenticationPrincipal CustomUserDetails user) {
    return userService.toDto(user.getId());
}
```

`@AuthenticationPrincipal` injects `authentication.getPrincipal()` directly. It's testable, null-safe by convention, and it keeps the static holder out of your controllers. You can also inject the `Authentication` itself as a method parameter, or a `java.security.Principal`.

### Anywhere else — the holder

```java
Authentication auth = SecurityContextHolder.getContext().getAuthentication();

String username = auth.getName();                     // principal's name
var authorities = auth.getAuthorities();              // roles + permissions
Object principal = auth.getPrincipal();               // your UserDetails
```

A small helper is worth having:

```java
@Component
public class CurrentUser {

    public Optional<CustomUserDetails> get() {
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();
        if (auth == null || !auth.isAuthenticated()
                || auth instanceof AnonymousAuthenticationToken) {
            return Optional.empty();
        }
        return Optional.of((CustomUserDetails) auth.getPrincipal());
    }
}
```

That three-part guard (`null` / `!isAuthenticated()` / `AnonymousAuthenticationToken`) is the correct "is anyone actually logged in?" check.

### In JPA auditing

```java
@Bean
public AuditorAware<String> auditorAware() {
    return () -> Optional.ofNullable(SecurityContextHolder.getContext().getAuthentication())
                         .filter(Authentication::isAuthenticated)
                         .map(Authentication::getName);
}
```

Now `@CreatedBy` / `@LastModifiedBy` fill themselves. A very common real-world use.

## 8. Where the context does **not** follow you

`ThreadLocal` is per-thread, and plenty of things run on a different thread:

| Situation | Context available? |
|---|---|
| Controller / service in the request thread | ✅ Yes |
| `@Async` method | ❌ No — new thread |
| `CompletableFuture.supplyAsync(...)` | ❌ No — pool thread |
| `@Scheduled` job | ❌ No — never had a request |
| Kafka / RabbitMQ listener | ❌ No |
| Spring MVC async (`Callable`, `DeferredResult`) | ✅ Yes — Spring propagates it |
| A new `Thread` you started | ❌ No (unless `INHERITABLETHREADLOCAL`) |

Fixes:

```java
// 1. Wrap the executor — propagates the context to pooled threads
@Bean
public Executor taskExecutor(ThreadPoolTaskExecutor delegate) {
    return new DelegatingSecurityContextExecutor(delegate);
}

// 2. Or set the strategy globally (careful with pooled threads)
SecurityContextHolder.setStrategyName(SecurityContextHolder.MODE_INHERITABLETHREADLOCAL);

// 3. Or hand it over manually
SecurityContext context = SecurityContextHolder.getContext();
executor.submit(() -> {
    SecurityContextHolder.setContext(context);
    try { doWork(); } finally { SecurityContextHolder.clearContext(); }
});
```

For a background job there *is* no user — either pass the identity explicitly as a parameter, or authenticate the job as a service principal. Don't fake a user in the holder and forget to clear it.

> [!warning] Reactive applications
> In WebFlux there is no thread affinity at all. `SecurityContextHolder` is useless there; the context lives in the **Reactor Context** and you read it with `ReactiveSecurityContextHolder.getContext()`.

## 9. `SecurityContextRepository` — how it survives between requests

For a **stateful** (session-based) app, the context must be reloaded on every request. That's `SecurityContextRepository`, usually `HttpSessionSecurityContextRepository`:

```text
Request 1 (login)   -> context created -> SAVED into HttpSession
Request 2           -> SecurityContextHolderFilter LOADS it from the session
                    -> ... request runs ...
                    -> context CLEARED from the ThreadLocal at the end
```

For a **stateless** JWT app the repository is a no-op (`NullSecurityContextRepository`): every request re-authenticates from the token and nothing is stored server-side.

> [!warning] Spring Security 6 breaking change
> `SecurityContextPersistenceFilter` was replaced by **`SecurityContextHolderFilter`**, which **only reads** — it no longer auto-saves the context at the end of the request. If you write a **custom login endpoint** and expect a session, you must save explicitly:
> ```java
> SecurityContext context = SecurityContextHolder.createEmptyContext();
> context.setAuthentication(auth);
> SecurityContextHolder.setContext(context);
> securityContextRepository.saveContext(context, request, response);   // <- required now
> ```
> Symptom if you skip it: login "succeeds" but the very next request is anonymous. Built-in filters like `UsernamePasswordAuthenticationFilter` already do this for you.

## ❓ Interview Questions

### Q1. What is `SecurityContextHolder` and where does it store data?

A static accessor for the current `SecurityContext`, backed by a **`ThreadLocal`** by default, so each request thread has its own authentication data.

### Q2. What does the `Authentication` object contain?

Principal (who), credentials (proof, usually erased after login), authorities (permissions), an `isAuthenticated` flag, and `details` (IP, session id).

### Q3. What is the principal?

The identity of the authenticated party — a `String` username before authentication, your `UserDetails` implementation after, or a `Jwt` in a resource server.

### Q4. Why are credentials `null` after authentication?

Spring erases them so the password isn't retained in memory, the session, or logs. `ProviderManager.eraseCredentialsAfterAuthentication` is `true` by default.

### Q5. Is `SecurityContextHolder` thread-safe across requests?

Yes — `ThreadLocal` isolates each request thread, and the context is cleared in a `finally` block at the end of the request so pooled threads don't leak a previous user.

### Q6. Why is the context missing in an `@Async` method, and how do you fix it?

It's thread-bound and `@Async` runs on a different thread. Wrap the executor in `DelegatingSecurityContextExecutor` (or use `DelegatingSecurityContextRunnable`/`Callable`); `MODE_INHERITABLETHREADLOCAL` works for plain child threads but is risky with pools.

### Q7. How do you get the current user in a controller?

`@AuthenticationPrincipal CustomUserDetails user` as a method parameter — cleaner and more testable than the static holder.

### Q8. How does the context survive across requests in a session-based app?

`SecurityContextRepository` (`HttpSessionSecurityContextRepository`) stores it in the `HttpSession`; `SecurityContextHolderFilter` loads it at the start of each request. In stateless JWT apps nothing is stored — every request re-authenticates.

### Q9. `getAuthentication()` is non-null — is the user logged in?

Not necessarily. `AnonymousAuthenticationFilter` installs an `AnonymousAuthenticationToken` whose `isAuthenticated()` is even `true`. Check `!(auth instanceof AnonymousAuthenticationToken)` as well.

> [!tip] ⚡ Quick Recall
> - `SecurityContextHolder` → `SecurityContext` → `Authentication`. **`ThreadLocal`** by default.
> - The one line: `SecurityContextHolder.getContext().getAuthentication()`.
> - `Authentication` = **Principal** (who) + **Credentials** (proof, nulled) + **Authorities** (what) + **authenticated** flag + **details** (IP/session).
> - Before login: String principal, real credentials, no authorities, `false`. After: `UserDetails`, `null`, authorities, `true`.
> - Cast the principal defensively — anonymous requests hold the String `"anonymousUser"`.
> - "Logged in" = non-null **and** `isAuthenticated()` **and** not `AnonymousAuthenticationToken`.
> - Context is **cleared at the end of every request** — otherwise pooled threads leak users.
> - Lost on `@Async`/executors/`@Scheduled`/listeners → `DelegatingSecurityContextExecutor`.
> - Controllers: prefer **`@AuthenticationPrincipal`**.
> - Spring Security 6: `SecurityContextHolderFilter` only **reads** — a custom login must call `securityContextRepository.saveContext(...)`.
> - WebFlux: `ReactiveSecurityContextHolder`, not the ThreadLocal one.
