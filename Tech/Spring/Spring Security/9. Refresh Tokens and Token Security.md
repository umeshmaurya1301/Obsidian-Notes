A stolen access token is a nuisance for fifteen minutes. A stolen refresh token is months of access. That asymmetry is why refresh tokens get their own note.

> [!info] 🧭 Summary
> - The **Authorization Server owns the refresh token** — it issues, stores, rotates and revokes it. Your **Resource Server never sees one**.
> - **Access token** = short (5–60 min), sent to every API. **Refresh token** = long (days–months), sent **only** to the auth server's token endpoint.
> - Why the split: short access tokens shrink the damage window, while the refresh token keeps the user from logging in every 15 minutes.
> - Refresh tokens are the more dangerous credential — whoever holds one can mint **new access tokens indefinitely**, until it expires or is revoked.
> - Access is **not** actually forever. Four brakes: **expiry**, **user revokes consent**, **logout / admin revocation**, and **rotation with reuse detection**.
> - **Refresh Token Rotation** — each use returns a *new* refresh token and invalidates the old one. Replaying an old token signals theft, and the whole token family is killed.
> - Storage: **`HttpOnly` `Secure` `SameSite` cookie**, scoped to the token endpoint. **Never `localStorage`** — XSS reads it instantly.
> - Mental model: access token = **a visitor pass**; refresh token = **the authority to issue yourself new visitor passes**.
>

## 1. Who controls the refresh token?

The **Authorization Server**: Keycloak, Google, Okta, Auth0, Azure AD. It decides lifetimes, stores the token (or a hash of it) server-side, and can invalidate it at any moment.

```text
Browser / Mobile
    |  refresh token  ->  ONLY to the Authorization Server's /token endpoint
    v
Authorization Server
    |
    +--> new access token
    |
    v
Browser  --- access token --->  API Gateway  --->  Microservices
                                  (these NEVER see the refresh token)
```

Your Spring Boot resource server is on the right-hand side. It validates access tokens and nothing else — which is exactly why `oauth2ResourceServer()` has no refresh configuration at all.

---

## 2. Why refresh tokens are the sensitive credential

```text
Access token   =  1 hour
Refresh token  =  90 days
```

Normal operation:

```text
Access token expires
    |
Client sends the refresh token
    |
Authorization Server
    |
New access token          (user never re-enters a password)
```

Stolen refresh token:

```text
Attacker
    |
Refresh token
    |
Authorization Server
    |
Unlimited new access tokens — potentially for months
```

The attacker doesn't need the password, doesn't trip MFA, and every token they mint looks perfectly legitimate to your API. Hence the rule: **short access tokens do not protect you if the refresh token is exposed.**

---

## 3. Can a provider keep access forever?

Not in a well-configured system. The auth server sets the lifetimes, and there are four independent brakes.

### Brake 1 — Refresh token expiry

The default control.

```text
Access token:   15 minutes
Refresh token:  30 days
```

After 30 days the refresh is denied and the user logs in again. Two dials matter here:

- **Absolute lifetime** — hard cap from issuance ("90 days, no matter what").
- **Idle / sliding lifetime** — expires after N days of *no use* ("30 days idle"), while active users are refreshed continuously.

Most providers apply both: sliding for convenience, absolute as the backstop.

### Brake 2 — The user revokes consent

```text
Google Account -> Security -> Third-party apps -> Remove "Travel App"
```

Google invalidates **all** access and refresh tokens issued to that client for that user. The next refresh fails. This is the promise OAuth2 was built to deliver, and the reason "just take the password" was never acceptable.

### Brake 3 — Logout / admin revocation

Depending on the provider:

- **Token revocation endpoint** (RFC 7009) — the client explicitly kills the refresh token at logout.
- **Back-channel / front-channel logout (OIDC)** — the auth server notifies clients that the session ended.
- **Admin action** — disable the user in Keycloak and every session and refresh token for them dies.

> [!warning] Logging out is a two-sided job
> Deleting the tokens in the browser is *not* logout — a stolen copy still works. A real logout calls the revocation endpoint (or the OIDC end-session endpoint) so the auth server forgets the grant.

### Brake 4 — Rotation with reuse detection

The strongest one. Next section.

---

## 4. Refresh Token Rotation

Instead of one long-lived refresh token reused forever:

```text
Use Refresh Token A
      |
      v
New access token
New Refresh Token B          <- returned to the client
      |
Invalidate A                 <- A is now dead
```

Every refresh gives you a fresh token and burns the old one. Refresh tokens become **single-use**.

### Reuse detection — the clever part

If token **A** is ever presented again *after* it was already exchanged, exactly one of two things is true: either the legitimate client replayed it, or someone stole it. Either way the auth server can't tell which party is which — so it assumes theft and **revokes the entire token family**:

```text
Attacker steals A, but the real user refreshes first:
    real user:  A -> B    (A now invalid)
    attacker:   A -> ??   REUSE DETECTED
                          -> revoke A, B and every descendant
                          -> both parties must log in again

Attacker refreshes first:
    attacker:   A -> B'
    real user:  A -> ??   REUSE DETECTED
                          -> same outcome, theft surfaced within minutes
```

The stolen token stops being useful the moment either side refreshes, and — importantly — the theft becomes **visible**, which a non-rotating scheme never achieves. This is the OAuth 2.0 Security BCP recommendation for public clients (SPAs, mobile), and Keycloak, Auth0 and Okta all support it.

> [!warning] Rotation needs a little care in the client
> Two tabs refreshing simultaneously, or a network failure after the server rotated but before the client stored the new token, can trip false reuse detection. Real implementations use a short grace window (a few seconds where the previous token still works) and serialise refreshes on the client — one in-flight refresh, other requests queue behind it.

---

## 5. Where to store tokens on the client

| Storage | XSS | CSRF | Verdict |
|---|---|---|---|
| `localStorage` / `sessionStorage` | ❌ any injected script reads it | ✅ | **Never** for refresh tokens |
| **`HttpOnly` `Secure` cookie** | ✅ invisible to JS | ⚠️ auto-sent → needs `SameSite` + CSRF token | **The recommendation** for refresh tokens |
| In-memory JS variable | ✅ gone on reload | ✅ | Good for the **access** token |

The common strong pattern for a browser SPA:

```text
Access token   ->  in memory (lost on refresh, re-obtained silently)
Refresh token  ->  HttpOnly; Secure; SameSite=Strict cookie
                   scoped with Path=/auth/token so it's sent ONLY to the token endpoint
```

That `Path` scoping matters: it means the refresh token isn't attached to every API call, so it isn't sitting in the logs of a dozen services.

For **mobile**, use the platform secure storage (Keychain / Android Keystore), plus PKCE. For a **confidential backend client**, tokens stay server-side and the browser only ever holds a session cookie — the simplest secure arrangement, and often the right one.

---

## 6. Refresh tokens in microservices

```text
Browser
    |  refresh token  ->  Authorization Server only
    |  access token   ->  API Gateway -> services
    v
```

Rules that follow:

- Microservices **receive access tokens only**. If a service has a refresh token, something is wrong with the architecture.
- Don't blindly forward a user's access token through every hop — a downstream service then wields the user's full authority. Use **Client Credentials** for service-to-service work, or **token exchange** (RFC 8693) for a narrowed on-behalf-of token.
- Keep access tokens short so a leaked one in a log or trace has a short blast radius.

The **BFF (Backend-for-Frontend)** pattern is the current best practice for browser apps: the browser holds only a session cookie, the BFF holds the tokens server-side and attaches them to downstream calls. No token ever touches JavaScript, which removes the whole XSS token-theft class.

---

## 7. Long-lived access: the `offline_access` case

Some apps must act when the user isn't present — a calendar sync running overnight, a nightly reconciliation job. Requesting the `offline_access` scope (or the provider equivalent) yields a refresh token intended for exactly that.

```text
Calendar Sync App
    |
Refresh token (offline)
    |
Authorization Server -> access token -> Calendar API      (user is asleep)
```

Still not "forever":

- The user can revoke consent at any time.
- The provider can expire or invalidate the token.
- Suspicious usage (new IP, new geography, impossible travel) can trigger revocation.
- Some providers expire refresh tokens for apps in testing mode after days.

Treat these tokens as the most sensitive secret your system holds: encrypted at rest, access-audited, and re-consent requested when refresh finally fails.

---

## 8. The senior-level summary

The main OAuth risk is **refresh token theft**, not access token theft:

```text
Access token   ->  short-lived   ->  limited damage
Refresh token  ->  long-lived    ->  sustained, invisible access
```

A well-run system combines:

```text
Short access tokens (5-15 min)
        +
Refresh token rotation with reuse detection
        +
HttpOnly / Secure / SameSite storage, path-scoped
        +
Revocation support (logout, admin, consent withdrawal)
        +
Absolute + idle lifetime caps
        +
Anomaly detection on refresh (IP / device / geography)
```

> [!tip] Mental model
> **Access token = a temporary visitor pass. Refresh token = the authority to issue yourself new visitor passes.**
> Losing a pass is annoying for an hour. Losing the badge printer is a breach.

## ❓ Interview Questions

### Q1. Who issues and controls the refresh token?

The Authorization Server. It sets lifetimes, stores it, rotates it and can revoke it. Resource servers never see it.

### Q2. Why not just issue a long-lived access token?

Access tokens are sent to every API, appear in logs and traces, and are validated offline — so they can't be revoked before expiry. Keeping them short limits the damage; the refresh token carries the long-lived trust and is exposed far less often.

### Q3. What is refresh token rotation and what does it buy you?

Each refresh returns a new refresh token and invalidates the old one. Replaying an old token means theft, so the server revokes the whole token family — turning silent long-term compromise into a detectable, self-limiting event.

### Q4. Can a third party keep access forever?

No, if configured properly: absolute and idle expiry, user consent revocation, logout/admin revocation, and rotation with reuse detection all cut it off.

### Q5. Where should a browser app store tokens?

Refresh token in an `HttpOnly` `Secure` `SameSite` cookie scoped to the token endpoint; access token in memory. Never a refresh token in `localStorage`. Better still, use a BFF so the browser holds no tokens at all.

### Q6. Do microservices need refresh tokens?

No — they only validate access tokens. Service-to-service calls use the Client Credentials grant or token exchange, not the user's refresh token.

### Q7. How do you implement real logout with tokens?

Call the auth server's revocation / end-session endpoint so the refresh token and session are killed server-side, clear the client copies, and — where instant API cut-off is required — add the access token's `jti` to a short-TTL denylist.

### Q8. What is `offline_access`?

A scope requesting a refresh token usable while the user is absent, for background jobs. Still revocable and expirable; treat it as a high-value secret.

> - **Authorization Server owns refresh tokens.** Resource servers never see them.
> - Access = **short**, sent everywhere. Refresh = **long**, sent **only** to the token endpoint.

> - Four brakes: **expiry** (absolute + idle), **consent revocation**, **logout/admin revocation**, **rotation with reuse detection**.
> - **Rotation**: single-use refresh tokens; a replay revokes the **entire family** — theft becomes visible.

> - Microservices get access tokens only; use **Client Credentials** / **token exchange** for service-to-service.
> - Deleting client-side tokens is **not** logout — revoke server-side.
