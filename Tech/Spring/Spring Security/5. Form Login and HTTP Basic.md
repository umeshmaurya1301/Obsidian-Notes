The two classic ways a request becomes an authenticated user. Both feel dated next to JWT — and both are worth understanding precisely, because JWT changes only the *first* filter and leaves the rest of the pipeline identical.

> [!info] 🧭 Summary
> - **Form login** — browser posts `username` + `password` to `POST /login`; handled by **`UsernamePasswordAuthenticationFilter`**.
> - **HTTP Basic** — client sends `Authorization: Basic base64(user:pass)` on **every** request; handled by **`BasicAuthenticationFilter`**.
> - **Everything after `AuthenticationManager` is identical** between them. Only the *entry filter* differs — which is exactly why swapping in a JWT filter later is easy.
> - Form login is **stateful**: on success Spring creates an `HttpSession`, returns `Set-Cookie: JSESSIONID=...`, and later requests are recognised by that cookie.
> - HTTP Basic is **stateless in spirit** (credentials on every request) but Spring will still create a session unless you set `SessionCreationPolicy.STATELESS`.
> - **Base64 is encoding, not encryption.** Anyone can decode it. HTTP Basic is only acceptable over **HTTPS**.
> - Session-based auth needs **CSRF protection**; token-based auth generally doesn't (see [[10. CSRF, CORS and Session Management]]).
> - Session fixation protection (`changeSessionId`) is on by default — the session id is rotated at login.
> - Practise both, then switch the entry filter to JWT and watch the rest of the pipeline stay untouched.
>

## 1. Form login

The traditional server-rendered web app flow.

```text
GET /login

   Username: ______
   Password: ______
   [ Login ]
```

The browser submits:

```text
POST /login
Content-Type: application/x-www-form-urlencoded

username=umesh&password=secret123
```

### Configuration

```java
@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {

    http
        .authorizeHttpRequests(auth -> auth
                .requestMatchers("/login", "/css/**").permitAll()
                .anyRequest().authenticated())
        .formLogin(form -> form
                .loginPage("/login")                 // your own page (optional)
                .defaultSuccessUrl("/dashboard", true)
                .failureUrl("/login?error"))
        .logout(logout -> logout
                .logoutSuccessUrl("/login?logout"));

    return http.build();
}
```

With a bare `.formLogin(Customizer.withDefaults())` Spring generates a login page for you at `/login` — handy for demos, replaced in any real app.

### Step by step

```text
POST /login
     |
     v
UsernamePasswordAuthenticationFilter        (listens ONLY on POST /login)
     |
  1. extract username=umesh, password=secret123
  2. build UsernamePasswordAuthenticationToken (authenticated = false)
  3. authenticationManager.authenticate(token)
     |
     v
ProviderManager -> DaoAuthenticationProvider
     |
  4. userDetailsService.loadUserByUsername("umesh")
  5. UserDetails { umesh, $2a$10$..., ROLE_ADMIN }
  6. passwordEncoder.matches("secret123", hash)  -> true
     |
     v
  7. authenticated token created
  8. SecurityContextHolder.getContext().setAuthentication(auth)
  9. context SAVED to HttpSession
     |
     v
  Redirect to /dashboard
```

Steps 3–7 are exactly [[2. Authentication Pipeline]].

### The success and failure hooks

Worth knowing by name — they're where "issue a JWT on login" or "record the login attempt" goes:

| Hook | Purpose |
|---|---|
| `AuthenticationSuccessHandler` | Where to redirect / what JSON to return on success |
| `AuthenticationFailureHandler` | Error page or `401` body on failure |
| `LogoutSuccessHandler` | What happens after logout |
| `AuthenticationEntryPoint` | What to do when an **anonymous** user hits a protected URL (redirect to login, or return 401 for an API) |

For a JSON API you almost always replace the first two, since the defaults redirect instead of returning a body.

## 2. What happens after login — the session

The question that follows form login in every interview: **how does Spring remember the user?**

On success Spring creates an `HttpSession` and stores the `SecurityContext` in it:

```text
Response:
Set-Cookie: JSESSIONID=A1B2C3...; HttpOnly; Path=/
```

The next request carries the cookie:

```text
GET /orders
Cookie: JSESSIONID=A1B2C3...
```

and the flow is:

```text
SecurityContextHolderFilter
     |
  read JSESSIONID -> find HttpSession -> load SecurityContext
     |
  SecurityContextHolder.setContext(...)
     |
  ... request runs, user is "logged in" ...
     |
  clear the ThreadLocal at the end
```

This is **stateful authentication** — the server holds the session; the cookie is just a pointer to it.

### Stateful vs stateless

| | Session (form login) | Token (JWT) |
|---|---|---|
| Server state | `HttpSession` per user | none |
| Client sends | `JSESSIONID` cookie | `Authorization: Bearer ...` |
| Scaling out | needs sticky sessions or a shared store (Spring Session + Redis) | any instance can serve any request |
| Logout | invalidate the session — **instant** | token stays valid until expiry → needs a denylist |
| CSRF | **vulnerable** — cookies are sent automatically | not by default (header isn't automatic) |
| Mobile / third-party clients | awkward | natural |

Neither is "better". Sessions give you instant revocation and simplicity; tokens give you horizontal scale and cross-client reach. Server-rendered app → session. Public API / microservices / mobile → token.

> [!tip] Spring Session
> "Sessions don't scale" is only true of *in-memory* sessions. **Spring Session** externalises them to Redis or JDBC, so any instance can serve any request and you keep instant revocation. A perfectly respectable architecture — and a good answer when an interviewer assumes JWT is the only option.

## 3. HTTP Basic

Common for simple APIs, internal services, and actuator endpoints.

```java
@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {

    http
        .authorizeHttpRequests(auth -> auth.anyRequest().authenticated())
        .httpBasic(Customizer.withDefaults())
        .csrf(csrf -> csrf.disable())
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS));

    return http.build();
}
```

The client sends credentials on **every** request:

```text
Authorization: Basic dW1lc2g6c2VjcmV0MTIz
```

which is simply:

```text
Base64("umesh:secret123")
```

### Base64 is not encryption

The most important point about HTTP Basic:

```java
new String(Base64.getDecoder().decode("dW1lc2g6c2VjcmV0MTIz"));
// umesh:secret123
```

No key, no secret, instant. Base64 exists to make binary safe for headers, nothing more.

> [!warning] HTTPS is mandatory
> Over plain HTTP, HTTP Basic hands the password to anyone on the network path — and it does so on **every single request**, so a single captured request is enough. Also note the browser's built-in Basic auth dialog has no real logout, which is why it's unsuitable for user-facing apps.

### The flow

```text
Authorization: Basic ...
     |
     v
BasicAuthenticationFilter
     |
  1. read the Authorization header
  2. Base64-decode -> umesh:secret123
  3. build UsernamePasswordAuthenticationToken
  4. authenticationManager.authenticate(token)
     |
     v
  ... identical to form login from here ...
```

> [!warning] The cost of "every request"
> Basic auth re-runs `loadUserByUsername` **and** BCrypt `matches()` on every single request. At cost 12 that's ~200 ms of CPU per call. For chatty APIs, authenticate once and issue a token instead.

## 4. Side by side

| | Form Login | HTTP Basic |
|---|---|---|
| Credentials arrive in | `POST /login` body | `Authorization` header |
| Filter | `UsernamePasswordAuthenticationFilter` | `BasicAuthenticationFilter` |
| Frequency | once, then a session | **every request** |
| Session created | yes | avoidable (`STATELESS`) |
| Logout | `POST /logout`, session invalidated | no real logout |
| Browser UX | your own HTML page | native popup dialog |
| CSRF needed | **yes** | no (if stateless) |
| Suits | server-rendered web apps | internal APIs, actuator, curl/scripts |

**Everything after `AuthenticationManager` is identical.** That's the whole lesson of this note.

## 5. Logout

```java
http.logout(logout -> logout
        .logoutUrl("/logout")
        .logoutSuccessUrl("/login?logout")
        .invalidateHttpSession(true)
        .deleteCookies("JSESSIONID")
        .clearAuthentication(true));
```

`LogoutFilter` intercepts the request, runs the configured `LogoutHandler`s, and never reaches a controller.

> [!warning] Logout must be a POST
> With CSRF protection enabled (the default), `GET /logout` returns 405. That's deliberate — a `GET` logout can be triggered by any `<img src="/logout">` on a hostile page. Use a form with the CSRF token.

## 6. Session security settings you should know

```java
http.sessionManagement(session -> session
        .sessionCreationPolicy(SessionCreationPolicy.IF_REQUIRED)
        .sessionFixation(fixation -> fixation.changeSessionId())   // default
        .maximumSessions(1)
        .maxSessionsPreventsLogin(false)
        .expiredUrl("/login?expired"));
```

- **Session fixation protection** — an attacker who plants a known session id in your browser *before* login would otherwise share your authenticated session. Spring rotates the id at login (`changeSessionId()`). On by default; don't turn it off.
- **`maximumSessions(1)`** — concurrent session control ("logged in elsewhere, you were signed out").
- **`SessionCreationPolicy`** — `ALWAYS`, `IF_REQUIRED` (default), `NEVER`, **`STATELESS`** (never create *or* use one — the right setting for JWT APIs).

Cookie hardening belongs here too:

```properties
server.servlet.session.cookie.http-only=true
server.servlet.session.cookie.secure=true
server.servlet.session.cookie.same-site=lax
server.servlet.session.timeout=30m
```

## 7. Why learn these if everything uses JWT?

Because JWT changes **one filter**:

```text
UsernamePasswordAuthenticationFilter        <- form login
BasicAuthenticationFilter                   <- HTTP basic
JwtAuthenticationFilter                     <- your custom filter
                    |
                    v
        everything below is unchanged:
                AuthenticationManager
                AuthenticationProvider
                UserDetailsService
                PasswordEncoder
                SecurityContextHolder
                AuthorizationFilter
```

JWT isn't a different security model — it's a different way to arrive at the same `Authentication` object.

> [!example] Build this once
> A tiny project pays for itself here:
> `User` entity → `UserRepository` → `CustomUserDetails implements UserDetails` → `CustomUserDetailsService implements UserDetailsService` → `BCryptPasswordEncoder` bean → `SecurityConfig` with `.formLogin()`.
> Then change one line to `.httpBasic()` and confirm nothing else needs to move. Then add a JWT filter and confirm the same. That's the whole architecture, felt rather than memorised.

## ❓ Interview Questions

### Q1. What happens when a user submits the login form?

`UsernamePasswordAuthenticationFilter` intercepts `POST /login`, builds an unauthenticated token, calls `AuthenticationManager` → `DaoAuthenticationProvider` → `UserDetailsService` + `PasswordEncoder`; on success the authenticated token goes into `SecurityContextHolder` and is saved to the session.

### Q2. How does Spring remember the user across requests in form login?

An `HttpSession` holds the `SecurityContext`; the browser holds a `JSESSIONID` cookie pointing to it. `SecurityContextHolderFilter` reloads the context on each request.

### Q3. Is HTTP Basic secure?

Only over HTTPS. Base64 is encoding, not encryption — the credentials are trivially decodable, and they're sent on every request.

### Q4. Difference between form login and HTTP Basic?

Where the credentials come from and which filter reads them. Form login: request body, once, then session. Basic: `Authorization` header, on every request. The pipeline after `AuthenticationManager` is identical.

### Q5. Stateful vs stateless authentication — trade-offs?

Sessions: server state, instant revocation, needs sticky sessions or a shared store, CSRF-exposed. Tokens: no server state, scales horizontally, valid until expiry (revocation needs a denylist), CSRF-safe when sent in a header.

### Q6. What is session fixation and how does Spring prevent it?

An attacker fixes a known session id in the victim's browser before login and then reuses it. Spring rotates the session id on successful authentication (`changeSessionId()`), enabled by default.

### Q7. Why must logout be a POST?

CSRF protection covers state-changing methods; a `GET /logout` could be triggered by an image tag on a malicious page.

### Q8. How do you make a form-login app return JSON instead of redirects?

Replace `AuthenticationSuccessHandler` / `AuthenticationFailureHandler`, and set an `AuthenticationEntryPoint` that returns 401 instead of redirecting to `/login`.

> [!tip] ⚡ Quick Recall
> - Form login → `POST /login` body → **`UsernamePasswordAuthenticationFilter`**.
> - HTTP Basic → `Authorization: Basic base64(user:pass)` → **`BasicAuthenticationFilter`**, **every request**.
> - **Only the entry filter differs**; `AuthenticationManager` onwards is identical. JWT slots into the same place.
> - Form login is **stateful**: `HttpSession` + `JSESSIONID` cookie. `SecurityContextHolderFilter` reloads it per request.
> - **Base64 ≠ encryption.** Basic auth demands HTTPS.
> - Session ⇒ **CSRF protection**; header token ⇒ not needed.
> - `SessionCreationPolicy.STATELESS` for token APIs; session fixation protection on by default.
> - Logout is a **POST**; `LogoutFilter` handles it, no controller involved.
> - Customise responses via `AuthenticationSuccessHandler` / `FailureHandler` / `AuthenticationEntryPoint`.
