Most backend engineers never build Google, Keycloak or Auth0. They build APIs that must **trust tokens somebody else issued**. That is exactly what an OAuth2 Resource Server is, and it's the single most common way Spring Security appears in a microservice.

> [!info] 🧭 Summary
> - A **Resource Server** is an API that protects resources and accepts **access tokens** — `/orders`, `/payments`, `/customers`. It authenticates nobody.
> - Division of labour: **Authorization Server authenticates users and issues tokens. Resource Server only verifies tokens.**
> - Config is two lines: `.oauth2ResourceServer(o -> o.jwt(...))` plus an `issuer-uri` property. No `UserDetailsService`, no `PasswordEncoder`, no login page.
> - **`BearerTokenAuthenticationFilter`** pulls the token out of `Authorization: Bearer <token>` and hands it to the JWT machinery.
> - Four validations: **signature**, **expiry (`exp`)**, **issuer (`iss`)**, and optionally **audience (`aud`)**.
> - Signature verification uses **JWK / JWKS** — the auth server publishes public keys at `/.well-known/jwks.json`; the resource server downloads and caches them. Private key signs, public key verifies (RSA/ECDSA), so the API never holds a secret.
> - `issuer-uri` triggers **OIDC discovery**: Spring fetches `/.well-known/openid-configuration` and learns the JWKS endpoint for you.
> - The resulting `Authentication` is a **`JwtAuthenticationToken`** whose principal is a **`Jwt`**, not a `UserDetails`.
> - **`scope` claim → `SCOPE_*` authorities** automatically. Custom claims like Keycloak's `realm_access.roles` need a **`JwtAuthenticationConverter`** to become `ROLE_*`.
> - In microservices **every service is a resource server**: validates the token, builds `Authentication`, checks authorization. No service stores passwords or performs login.
>

## 1. What a Resource Server actually is

An API that (a) protects resources and (b) accepts access tokens. Nothing more.

```text
GET /orders
GET /payments
GET /customers
```

These hold business data. They need to know *who* is calling and *what they may do* — but they don't need to find that out themselves.

```text
Frontend
    |
    | 1. Login (username / password / MFA)
    v
Keycloak                      <- Authorization Server
    |
    | 2. Access Token
    v
Frontend
    |
    | 3. Authorization: Bearer <token>
    v
Order Service                 <- Resource Server
```

| Question | Answer |
|---|---|
| Who authenticated the user? | Keycloak |
| Who issued the token? | Keycloak |
| Who **verifies** the token? | Order Service |
| Who serves the business data? | Order Service |

## 2. Why the API doesn't authenticate again

The beginner question: *why doesn't Order Service call `UserDetailsService`?*

Because **authentication already happened**. The token is a signed statement of its outcome:

```json
{
  "sub": "umesh",
  "roles": ["ADMIN"]
}
```

Re-checking a password here would mean the Order Service holds password hashes — which is exactly the architecture OAuth2 exists to eliminate. The resource server only has to answer four questions:

```text
1. Is the token genuine?     (signature)
2. Is it still valid?        (exp)
3. Do I trust who issued it? (iss)
4. Is the user permitted?    (scopes / roles)
```

> [!tip] The one sentence
> **Authorization Server authenticates users. Resource Server trusts tokens.** Almost every resource-server design question falls out of that.

## 3. Configuration

```java
@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/actuator/health").permitAll()
            .requestMatchers("/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated()
        )
        .oauth2ResourceServer(oauth -> oauth.jwt(Customizer.withDefaults()))
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .csrf(csrf -> csrf.disable());   // safe: auth rides on a header, not a cookie

    return http.build();
}
```

```properties
spring.security.oauth2.resourceserver.jwt.issuer-uri=https://auth.company.com/realms/payments
```

That property does a lot of work. On startup Spring calls:

```text
https://auth.company.com/realms/payments/.well-known/openid-configuration
```

and learns the token endpoint, the **JWKS URI**, and the expected issuer. If you'd rather skip discovery, point straight at the keys:

```properties
spring.security.oauth2.resourceserver.jwt.jwk-set-uri=https://auth.company.com/realms/payments/protocol/openid-connect/certs
```

> [!warning] `issuer-uri` is validated, not just used
> Spring checks that the `iss` claim in every token **equals** the configured issuer. A token from a different realm — even one signed by the same Keycloak instance — is rejected. That's your tenant boundary.

## 4. Request flow

```text
GET /orders
Authorization: Bearer eyJhbGciOi...

Request
   |
BearerTokenAuthenticationFilter     <- extract token from the header
   |
JwtDecoder                          <- signature, exp, iss, aud
   |
JwtAuthenticationConverter          <- claims -> authorities
   |
JwtAuthenticationToken
   |
SecurityContextHolder
   |
AuthorizationFilter                 <- hasRole / hasAuthority
   |
DispatcherServlet -> Controller
```

Compare with the classic form-login pipeline from [[2. Authentication Pipeline]]:

```text
Traditional                          Resource Server
-----------                          ---------------
UsernamePasswordAuthenticationFilter BearerTokenAuthenticationFilter
AuthenticationManager                JwtDecoder (validate)
UserDetailsService (load user)       -- nothing, the token IS the user
PasswordEncoder (verify password)    -- nothing, the signature is the proof
```

Far fewer moving parts, because the expensive work happened elsewhere.

## 5. `BearerTokenAuthenticationFilter`

Its job is small and precise:

```text
Authorization: Bearer abc.xyz.123
                      ^^^^^^^^^^^
                      extract this
```

- Reads the `Authorization` header (also supports form/query parameters, disabled by default and best left that way — tokens in URLs end up in logs).
- Strips the `Bearer ` prefix.
- Wraps the string in a `BearerTokenAuthenticationToken` and passes it to the `AuthenticationManager`.
- **No header → no authentication attempt.** The filter chain simply continues, and the request later fails at `AuthorizationFilter` with a 401.

On failure it delegates to `BearerTokenAuthenticationEntryPoint`, which produces the RFC 6750 response:

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token",
                  error_description="Jwt expired at 2026-08-27T10:04:00Z"
```

That `error_description` is the first thing to read when debugging — it names the exact failed validation.

## 6. What gets validated, and how

### Signature — the JWK story

The resource server must prove the token really came from the auth server. Modern setups use **asymmetric** crypto:

```text
Authorization Server            Resource Server
   Private Key  --sign-->  JWT  --verify-->  Public Key
```

The public keys are published as a **JWK Set**:

```text
https://auth.company.com/.well-known/jwks.json
```

```json
{
  "keys": [
    {
      "kty": "RSA",
      "kid": "a1b2c3",
      "use": "sig",
      "alg": "RS256",
      "n": "0vx7ag...",
      "e": "AQAB"
    }
  ]
}
```

The JWT header names which key signed it:

```json
{ "alg": "RS256", "kid": "a1b2c3" }
```

Spring's `NimbusJwtDecoder` fetches the JWK set, caches it, matches on `kid`, and verifies. When the auth server rotates keys it publishes the new one alongside the old; the decoder refetches on an unknown `kid`, so **rotation needs no redeploy**.

> [!tip] Why public-key verification is the whole point
> The Order Service can verify tokens **without holding any secret**. Compromising it yields no ability to mint tokens. With a shared HMAC secret (`HS256`), every service that can verify can also forge — which is why HS256 is fine for a monolith and wrong for microservices.

### The other three

```json
{
  "sub": "umesh",
  "exp": 1780000000,
  "iss": "https://auth.company.com",
  "aud": "order-service",
  "scope": "orders.read orders.write"
}
```

| Claim | Check | Failure |
|---|---|---|
| `exp` | now < exp (with ~60s clock skew) | `Jwt expired at ...` |
| `iss` | equals configured issuer | `The iss claim is not valid` |
| `aud` | contains this API's id (**opt-in**) | `The aud claim is not valid` |
| `nbf` | now ≥ not-before | `Jwt used before ...` |

Audience validation is **not on by default** — add it when several APIs share one issuer:

```java
@Bean
JwtDecoder jwtDecoder(OAuth2ResourceServerProperties props) {
    NimbusJwtDecoder decoder = JwtDecoders.fromIssuerLocation(props.getJwt().getIssuerUri());
    decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
        JwtValidators.createDefaultWithIssuer(props.getJwt().getIssuerUri()),
        new JwtClaimValidator<List<String>>("aud", aud -> aud != null && aud.contains("order-service"))
    ));
    return decoder;
}
```

Without it, a token minted for `marketing-service` is happily accepted by `payment-service`. That is a real privilege-escalation path in a shared-realm estate.

## 7. The `Authentication` you get

```text
JwtAuthenticationToken
   |
   +--> Principal    = Jwt         (not UserDetails!)
   +--> Credentials  = the raw token
   +--> Authorities  = SCOPE_orders.read, SCOPE_orders.write
   +--> Authenticated = true
```

Reading it in a controller:

```java
@GetMapping("/profile")
public Map<String, Object> profile(@AuthenticationPrincipal Jwt jwt) {
    return Map.of(
        "userId", jwt.getSubject(),            // "sub"
        "email",  jwt.getClaimAsString("email"),
        "roles",  jwt.getClaimAsStringList("roles"),
        "expiry", jwt.getExpiresAt()
    );
}
```

The verbose equivalent, if you need the whole `Authentication`:

```java
@GetMapping("/profile")
public String profile(Authentication auth) {
    Jwt jwt = (Jwt) auth.getPrincipal();
    return jwt.getSubject();
}
```

> [!warning] `getPrincipal()` returns `Jwt`, not `String`
> Code written against form login that does `(UserDetails) auth.getPrincipal()` will throw `ClassCastException` the moment it runs behind a resource server. Prefer `auth.getName()` (which is `sub`) in shared code.

## 8. Scope mapping — the automatic part

OAuth2 tokens carry scopes:

```json
{ "scope": "orders.read orders.write" }
```

Spring splits on whitespace and prefixes each with `SCOPE_`:

```text
orders.read   ->  SCOPE_orders.read
orders.write  ->  SCOPE_orders.write
```

So both of these work out of the box:

```java
.requestMatchers(HttpMethod.GET, "/orders/**").hasAuthority("SCOPE_orders.read")
```

```java
@PreAuthorize("hasAuthority('SCOPE_orders.write')")
public Order create(OrderRequest req) { ... }
```

It also reads the `scp` claim (Azure AD, Okta) if `scope` is absent.

> [!warning] There is no `hasScope()`
> Use `hasAuthority("SCOPE_x")`. And **`hasRole("orders.read")` will not work** — that becomes `ROLE_orders.read`, which no token produces.

## 9. Role mapping — the part you must configure

Keycloak doesn't put roles in `scope`. It nests them:

```json
{
  "realm_access": { "roles": ["ADMIN", "USER"] },
  "resource_access": {
    "order-service": { "roles": ["ORDER_APPROVER"] }
  }
}
```

Spring has no idea this claim means "roles" — you must say so:

```java
@Bean
JwtAuthenticationConverter jwtAuthenticationConverter() {
    JwtAuthenticationConverter converter = new JwtAuthenticationConverter();
    converter.setJwtGrantedAuthoritiesConverter(jwt -> {
        // keep the scopes Spring would have given us
        Collection<GrantedAuthority> authorities =
            new JwtGrantedAuthoritiesConverter().convert(jwt);

        Map<String, Object> realmAccess = jwt.getClaim("realm_access");
        if (realmAccess != null) {
            List<String> roles = (List<String>) realmAccess.getOrDefault("roles", List.of());
            roles.stream()
                 .map(r -> new SimpleGrantedAuthority("ROLE_" + r))
                 .forEach(authorities::add);
        }
        return authorities;
    });
    return converter;
}
```

```text
realm_access.roles: ["ADMIN"]
        |
        v
ROLE_ADMIN          -> hasRole("ADMIN") now works
```

End to end:

```text
Token: { "sub": "umesh", "realm_access": { "roles": ["ADMIN"] } }
GET /admin/users
Config: .requestMatchers("/admin/**").hasRole("ADMIN")

JWT validated -> JwtAuthenticationToken created
              -> ROLE_ADMIN present
              -> Access granted
```

> [!warning] The `ROLE_` prefix trap, again
> Add the prefix **in the converter**, never in the check. If your claim already contains `"ROLE_ADMIN"`, don't prefix again or you get `ROLE_ROLE_ADMIN` and a silent 403. See [[6. Authorization]] §4.

## 10. Opaque tokens

Not every auth server issues JWTs. Some issue random strings that carry no information:

```properties
spring.security.oauth2.resourceserver.opaquetoken.introspection-uri=https://auth.company.com/introspect
spring.security.oauth2.resourceserver.opaquetoken.client-id=order-service
spring.security.oauth2.resourceserver.opaquetoken.client-secret=...
```

```java
.oauth2ResourceServer(oauth -> oauth.opaqueToken(Customizer.withDefaults()))
```

| | JWT | Opaque + introspection |
|---|---|---|
| Validation | local, offline | network call per request |
| Latency | ~0 | one round trip (cache it) |
| Revocation | not until expiry | **immediate** |
| Auth server load | none | every request |
| Principal | `Jwt` | `OAuth2AuthenticatedPrincipal` |

The usual compromise: JWTs with short expiry for internal APIs; introspection where instant revocation is non-negotiable (payment authorisation, admin consoles).

## 11. Resource servers in a real microservice estate

```text
                 Keycloak
                     |
              Access Token
                     |
                     v
                API Gateway
                     |
       +-------------+-------------+
       |             |             |
Order Service  Payment Service  Customer Service
```

Every service is a resource server. Every service:

- validates the token (signature, exp, iss, aud),
- builds its own `Authentication`,
- runs its own authorization rules.

And **no service** stores passwords, renders a login page, or sees a refresh token ([[9. Refresh Tokens and Token Security]]).

Consequences worth stating in an interview:

- **Trust is transitive only through the token.** Don't add a `X-User-Id` header at the gateway and trust it downstream — anything that can reach the service can forge it. Validate the JWT in each service, even behind a gateway.
- **Don't forward the user's token blindly** for service-to-service work. Use the **Client Credentials** grant, or **token exchange** (RFC 8693) for a narrowed on-behalf-of token.
- **Cache the JWK set** (Spring does) but allow refetch on unknown `kid`, so key rotation is a non-event.

## ❓ Interview Questions

### Q1. What is an OAuth2 Resource Server?

An API that protects resources and accepts access tokens. It validates the token and enforces authorization, but never authenticates the user — that already happened at the Authorization Server.

### Q2. Which filter processes Bearer tokens?

`BearerTokenAuthenticationFilter`. It extracts the token from the `Authorization` header and hands it to the JWT decoding/authentication machinery.

### Q3. What `Authentication` implementation is created?

`JwtAuthenticationToken`, whose principal is a `Jwt` object holding all the claims — not a `UserDetails`.

### Q4. Does a resource server use `UserDetailsService`?

Normally no. The token already represents an authenticated user. You'd only add one to enrich the token identity with local data (internal roles, an account id), and even then it isn't part of authentication.

### Q5. What is JWK / JWKS?

A JSON format for public keys. The Authorization Server publishes its signing keys at a JWKS endpoint; the resource server downloads them and verifies JWT signatures with the public key while the private key never leaves the auth server. The `kid` header selects the key, which is what makes rotation seamless.

### Q6. What does `issuer-uri` do?

Points Spring at the provider's OIDC discovery document (`/.well-known/openid-configuration`). Spring learns the JWKS endpoint and other metadata from it, and validates that every token's `iss` claim matches.

### Q7. How do Keycloak roles become Spring authorities?

They don't, by default — Keycloak nests them in `realm_access.roles`. You register a `JwtAuthenticationConverter` with a custom `JwtGrantedAuthoritiesConverter` that reads that claim and maps each role to `ROLE_<name>`.

### Q8. What's the difference between validating a JWT and introspecting an opaque token?

JWT validation is local and offline (signature + claims), so it's fast but can't be revoked before expiry. Introspection calls the auth server on every request, so it reflects revocation instantly at the cost of latency and coupling.

### Q9. Why do you disable CSRF on a resource server?

Because authentication rides on the `Authorization` header, which the browser never attaches automatically. A malicious site cannot make the browser send it. See [[16. CSRF Deep Dive]].

### Q10. Should each microservice validate the token, or just the gateway?

Each service. Gateway-only validation means anything that reaches a service internally — a misconfigured route, a compromised pod, a debugging port — bypasses security entirely. JWT validation is cheap and local; do it everywhere.

> [!tip] ⚡ Quick Recall
> - Resource Server = **an API that validates access tokens**. It authenticates nobody.
> - `.oauth2ResourceServer(o -> o.jwt())` + `issuer-uri`. No `UserDetailsService`, no `PasswordEncoder`, no login page.
> - **`BearerTokenAuthenticationFilter`** extracts the token → `JwtDecoder` validates → **`JwtAuthenticationToken`** in `SecurityContextHolder`.
> - Validate: **signature · exp · iss · (aud)**. Turn on `aud` when several APIs share an issuer.
> - **JWKS** = public keys at `/.well-known/jwks.json`; `kid` picks the key; private signs, public verifies → the API holds no secret and rotation needs no redeploy.
> - `scope` claim → **`SCOPE_*`** automatically. Custom role claims need a **`JwtAuthenticationConverter`** → `ROLE_*`.
> - Principal is a **`Jwt`** — `@AuthenticationPrincipal Jwt jwt`, `jwt.getClaimAsString("email")`.
> - **Opaque tokens** = introspection call per request; slower but instantly revocable.
> - Every microservice is a resource server; **never trust a gateway-injected header** instead of the token.
> - **Authorization Server authenticates users. Resource Server trusts tokens.**
