OIDC is the topic that makes OAuth2 Login suddenly click. Everyone learns "OAuth2 = Login with Google" — but that is not what OAuth2 was designed for, and the gap between what OAuth2 actually specifies and what login needs is exactly the gap OIDC fills.

> [!info] 🧭 Summary
> - **OAuth2 is an authorization framework.** It answers *"can this application access this resource?"* It never defined a standard way to answer *"who is the user?"*
> - **OIDC is an identity layer on top of OAuth2.** OAuth2 = authorization · OIDC = authentication + identity.
> - The concrete addition is the **ID Token**: a JWT describing *who authenticated*, issued alongside the access token.
> - **Access token = boarding pass** (what you may access, sent to APIs). **ID token = passport** (who you are, consumed by your own app). Never send an ID token to an API as a bearer credential.
> - Standard claims: **`sub`** (stable unique user id), `email`, `email_verified`, `name`, `picture`, plus `iss`, `aud`, `exp`, `nonce`.
> - **`scope=openid` is mandatory** — it's the switch that turns an OAuth2 request into an OIDC request. Add `profile` and `email` for the usual claims.
> - **Discovery**: `/.well-known/openid-configuration` publishes every endpoint (authorize, token, JWKS, UserInfo), so `issuer-uri` is all Spring needs.
> - ID token validation: **signature, `iss`, `aud` (= your `client_id`), `exp`, and `nonce`** (replay protection, OIDC's own addition).
> - In Spring, `.oauth2Login()` **auto-upgrades to OIDC** when the provider supports it and `openid` is requested — the principal becomes **`OidcUser`** instead of `OAuth2User`.
> - Why OIDC won: before it, every provider invented its own identity endpoint and claim names. OIDC standardised the token, the claims, the UserInfo endpoint and discovery.
>

## 1. The problem with OAuth2

OAuth2 was designed for **delegated access**:

```text
Travel App
    |  "may I read this user's calendar?"
    v
Google Calendar
User grants: calendar.read
```

It solves **authorization** beautifully. But suppose your application only wants:

```text
Who is this user?
  email
  name
  profile picture
```

OAuth2 has no answer. It gives you an access token — an opaque permission to call *something*. Which endpoint returns the user? What is the field called? OAuth2 doesn't say.

The historical result:

```text
Google    ->  /oauth2/v1/userinfo   with field "id"
Facebook  ->  /me?fields=...        with field "id"
Microsoft ->  /me (Graph)           with field "id"
GitHub    ->  /user                 with field "login"
```

Every integration was bespoke. Worse, some apps used the *access token itself* as proof of login — a genuine vulnerability, because an access token says nothing about who obtained it or which app it was issued to. (This is the "confused deputy" problem: an attacker's app can take a token a user granted it and present it to your app as evidence of login.)

---

## 2. What OIDC adds

```text
OAuth2  =  Authorization
OIDC    =  Authentication + Identity   (built ON TOP of OAuth2)
```

Concretely, the token endpoint now returns one extra thing:

```text
OAuth2               OIDC
------               ----
access_token         access_token
                     id_token          <- the new part
refresh_token        refresh_token
```

Plus four standardisations that matter as much as the token itself:

1. **ID Token** — a JWT with a defined shape.
2. **Standard claims** — `sub`, `email`, `name`, `picture` mean the same everywhere.
3. **UserInfo endpoint** — one well-known place to fetch more claims.
4. **Discovery** — `/.well-known/openid-configuration`.

---

## 3. The ID token

```json
{
  "iss": "https://accounts.google.com",
  "sub": "123456789",
  "aud": "1234.apps.googleusercontent.com",
  "exp": 1780000000,
  "iat": 1779996400,
  "nonce": "n-0S6_WzA2Mj",
  "email": "umesh@gmail.com",
  "email_verified": true,
  "name": "Umesh Maurya",
  "picture": "https://lh3.googleusercontent.com/..."
}
```

It answers exactly one question: **who authenticated, when, at which provider, and for which application.**

It's a normal JWT ([[7. JWT Authentication]]) — header, payload, signature — signed with the provider's private key and verifiable against the same JWKS the resource server uses.

---

## 4. Access token vs ID token

The single most-mixed-up pair in this whole area.

| | Access Token | ID Token |
|---|---|---|
| Answers | *what may this app access?* | *who is the user?* |
| Audience (`aud`) | the **API** (`order-service`) | **your client** (`client_id`) |
| Sent to | resource servers, as `Authorization: Bearer` | **nobody** — consumed by your app |
| Format | JWT **or opaque** | always a JWT |
| Contains identity? | not guaranteed | that's its entire job |
| Lifetime | minutes | minutes (used once, at login) |

```text
ID Token       =  Passport         "who are you?"
Access Token   =  Boarding Pass    "what are you allowed to board?"
```

> [!warning] Never use an ID token as an API credential
> Its `aud` is your client id, not the API's. A resource server that accepts it is skipping the audience check ([[11. OAuth2 Resource Server]] §6) and will accept ID tokens minted for *any* client of that issuer. The reverse mistake — treating an access token as proof of identity — is the vulnerability OIDC was created to close. **ID token in, access token out.**

## 5. The OIDC flow

Structurally the Authorization Code Flow from [[12. OAuth2 Login and SSO]], with `openid` in the scope and one extra parameter.

```text
Step 1  App redirects
        GET https://accounts.google.com/o/oauth2/v2/auth
            ?client_id=...
            &redirect_uri=https://myapp.com/login/oauth2/code/google
            &response_type=code
            &scope=openid%20profile%20email     <- openid = "I want OIDC"
            &state=xyz
            &nonce=n-0S6_WzA2Mj                 <- OIDC addition

Step 2  User authenticates  (email, password, MFA)

Step 3  Google redirects back with ?code=...&state=xyz

Step 4  Backend exchanges the code
        -> { access_token, id_token, refresh_token, expires_in }

Step 5  Spring VALIDATES the id_token
            signature   (JWKS)
            iss         == expected issuer
            aud         == our client_id
            exp         not expired
            nonce       == the one we sent

Step 6  Spring builds OAuth2AuthenticationToken with an OidcUser principal
        -> SecurityContextHolder
```

### `nonce` vs `state`

Both are random, both are anti-replay, and they are constantly confused:

| | `state` | `nonce` |
|---|---|---|
| Defined by | OAuth2 | OIDC |
| Travels in | the redirect URL, echoed back | the **ID token claim** |
| Protects against | CSRF on the callback — code injection | **replay of a stolen ID token** |
| Checked against | the value stored in the session | the value stored in the session |

`state` proves *this callback belongs to the login I started*. `nonce` proves *this ID token was minted for the login I started*, not replayed from an earlier one.

## 6. Scopes

```text
openid     MANDATORY. Turns an OAuth2 request into an OIDC request.
           Without it there is no id_token, full stop.
           Gives: sub

profile    name, family_name, given_name, picture, locale, updated_at
email      email, email_verified
address    address
phone      phone_number, phone_number_verified
```

```properties
spring.security.oauth2.client.registration.google.scope=openid,profile,email
```

> [!warning] Missing `openid` is the classic OIDC bug
> No `openid` scope → no `id_token` → Spring silently stays on the plain OAuth2 path → your principal is an `OAuth2User`, not an `OidcUser`, and a `(OidcUser) auth.getPrincipal()` cast blows up at runtime. If `getIdToken()` isn't available, check the scope first.

Providers may also return claims via the **UserInfo endpoint** rather than stuffing everything into the ID token — keeping the token small. Spring calls UserInfo automatically when a `user-info-uri` is configured and merges the claims.

## 7. Discovery

Before OIDC you configured four endpoints by hand and re-configured them whenever the provider changed. Now:

```text
GET https://auth.company.com/realms/payments/.well-known/openid-configuration
```

```json
{
  "issuer": "https://auth.company.com/realms/payments",
  "authorization_endpoint": ".../protocol/openid-connect/auth",
  "token_endpoint": ".../protocol/openid-connect/token",
  "userinfo_endpoint": ".../protocol/openid-connect/userinfo",
  "jwks_uri": ".../protocol/openid-connect/certs",
  "end_session_endpoint": ".../protocol/openid-connect/logout",
  "scopes_supported": ["openid", "profile", "email", "roles"],
  "response_types_supported": ["code", "id_token", "code id_token"],
  "id_token_signing_alg_values_supported": ["RS256"]
}
```

Which is why one property is enough on both sides:

```properties
# client (OAuth2 Login)
spring.security.oauth2.client.provider.keycloak.issuer-uri=https://auth.company.com/realms/payments

# resource server
spring.security.oauth2.resourceserver.jwt.issuer-uri=https://auth.company.com/realms/payments
```

Google, Okta, Azure AD, Auth0 and Keycloak all publish this document, and it's the reason swapping providers is a config change rather than a rewrite.

## 8. OIDC in Spring Security

`.oauth2Login()` upgrades itself when the provider is OIDC-capable and `openid` was requested. The visible difference is the principal type.

```java
@GetMapping("/me")
public Map<String, Object> me(@AuthenticationPrincipal OidcUser user) {
    return Map.of(
        "id",       user.getSubject(),              // sub
        "email",    user.getEmail(),                // typed accessor
        "verified", user.getEmailVerified(),
        "name",     user.getFullName(),
        "claims",   user.getClaims(),               // everything
        "idToken",  user.getIdToken().getTokenValue()
    );
}
```

| | `OAuth2User` | `OidcUser` |
|---|---|---|
| Source | UserInfo endpoint only | ID token (+ UserInfo) |
| Access | `getAttribute("email")` | `getEmail()`, `getFullName()`, … |
| Extra | — | `getIdToken()`, `getClaims()`, `getUserInfo()` |

`OidcUser` **extends** `OAuth2User`, so code written against the latter keeps working.

### RP-Initiated Logout

OIDC also standardises logout, which plain OAuth2 never did:

```java
@Bean
SecurityFilterChain chain(HttpSecurity http, ClientRegistrationRepository repo) throws Exception {
    var handler = new OidcClientInitiatedLogoutSuccessHandler(repo);
    handler.setPostLogoutRedirectUri("{baseUrl}/");

    http.oauth2Login(Customizer.withDefaults())
        .logout(l -> l.logoutSuccessHandler(handler));
    return http.build();
}
```

Without this, `/logout` kills only your application's session — the user clicks "login" again and is silently signed straight back in, because the **IdP session is still alive**. That surprises everyone once.

## 9. OAuth2 vs OIDC, side by side

| Feature | OAuth2 | OIDC |
|---|---|---|
| Authorization | ✅ | ✅ (inherits it) |
| Authentication | ❌ not specified | ✅ |
| Access token | ✅ | ✅ |
| ID token | ❌ | ✅ |
| Standardised user identity | ❌ | ✅ |
| UserInfo endpoint | ❌ | ✅ |
| Discovery document | ❌ | ✅ |
| Standard logout | ❌ | ✅ |
| Login / SSO | not the design goal | the primary use case |

## 10. Why enterprises run OIDC for SSO

```text
Employee
   |  username + password + MFA, once
   v
Okta  (Identity Provider)
   |
   +--> ID Token     "this is umesh@company.com"
   +--> Access Token "may call the HR API"
   |
   +--> Jira · Confluence · HR Portal · Spring Boot apps
```

Every application trusts Okta. Every application learns *who the user is* from the ID token, in the same format, without ever handling a password. Add an app and it inherits MFA, device policy and offboarding for free — that is the whole business case.

## ❓ Interview Questions

### Q1. What is the difference between OAuth2 and OpenID Connect?

*(The answer interviewers are listening for.)* OAuth2 is an authorization framework that lets a client obtain delegated access to protected resources. OpenID Connect is an identity layer built on top of OAuth2: it adds the ID token, standardised user claims, a UserInfo endpoint and discovery, so applications can know *who* the user is and implement SSO. **OAuth2 answers "what can this application access?"; OIDC answers "who is the user?"**

### Q2. Access token vs ID token?

The access token is a credential for calling APIs — its audience is the resource server, and it may be opaque. The ID token is a JWT describing the authentication event — its audience is your client id, and it's consumed by your application, never forwarded to an API. Passport vs boarding pass.

### Q3. What does the `openid` scope do?

It's what makes the request an OIDC request. Without it the provider returns no `id_token` and you're doing plain OAuth2.

### Q4. Which claims does an ID token carry, and which matter for validation?

`iss`, `sub`, `aud`, `exp`, `iat`, `nonce` are the security-relevant ones; `email`, `email_verified`, `name`, `picture` are the identity ones. Validation checks signature, `iss`, `aud` == your `client_id`, `exp`, and `nonce`.

### Q5. `state` vs `nonce`?

`state` is OAuth2's CSRF protection on the callback — a random value echoed in the redirect and matched against the session. `nonce` is OIDC's replay protection for the ID token — sent in the authorization request and required to appear as a claim in the returned ID token.

### Q6. Why key your local user on `sub` rather than email?

`sub` is a stable, unique, provider-scoped identifier. Emails change, get reassigned when someone leaves a company, and are not guaranteed unique across providers. Match on `sub`; store email for display.

### Q7. What is the discovery document?

`/.well-known/openid-configuration` — JSON published by the provider listing the issuer, all endpoints, the JWKS URI and supported algorithms. It's why `issuer-uri` alone configures both a client and a resource server in Spring.

### Q8. `OidcUser` vs `OAuth2User` in Spring?

`OidcUser` extends `OAuth2User` and additionally exposes the ID token and typed claim accessors (`getEmail()`, `getFullName()`, `getIdToken()`). Spring produces it automatically when the provider is OIDC-capable and `openid` was requested.

### Q9. Why doesn't `/logout` really log the user out with SSO?

It clears only your application's session. The IdP session survives, so the next login is silent. Real logout uses RP-initiated logout — redirect to the provider's `end_session_endpoint` — wired in Spring via `OidcClientInitiatedLogoutSuccessHandler`.

### Q10. Why was OIDC needed if everyone was already "logging in with OAuth2"?

Because they were doing it non-interoperably and, in some cases, insecurely — treating an access token as proof of identity, which it isn't (it says nothing about who obtained it or for which app). OIDC gave the ecosystem one audience-bound identity token and one set of claim names.
