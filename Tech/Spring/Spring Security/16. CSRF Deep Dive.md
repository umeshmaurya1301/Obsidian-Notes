CSRF becomes easy once you've internalised what CORS does *not* do. CORS stops another site **reading** your data. CSRF is about another site making the victim's browser **do** something — where reading the response is irrelevant, so CORS never fires.

> [!info] 🧭 Summary
> - **CSRF = Cross-Site Request Forgery.** A malicious page causes the victim's browser to send an authenticated, state-changing request to a site the victim is logged into.
> - It works because **the browser attaches cookies automatically** based on the *destination*, not the *origin* of the request.
> - The attacker **never reads the response** — they only need the action (transfer, email change, password change, delete) to succeed. That's why CORS doesn't stop it.
> - Defence = **synchronizer token**: a random per-session value the server issues and requires on every state-changing request. The attacker can't guess it, and SOP stops them reading it.
> - The asymmetry that makes it work: the attacker can't read the session cookie **or** the CSRF token — but the browser **auto-sends the cookie** and **does not auto-send the token**.
> - `HttpOnly` on the session cookie means even the site's own JavaScript can't read it — closing the XSS-steals-cookie path.
> - **JWT in an `Authorization` header is not CSRF-vulnerable** — the browser never attaches that header, so `csrf.disable()` is correct there.
> - **JWT in a cookie *is* CSRF-vulnerable** — it's auto-sent exactly like `JSESSIONID`. Cookie storage needs CSRF protection and/or `SameSite`.
> - Spring enables CSRF **by default**, on `POST/PUT/PATCH/DELETE` only — which is why `GET` must never change state.
> - For SPAs use `CookieCsrfTokenRepository.withHttpOnlyFalse()` so JS can read the token and echo it in `X-XSRF-TOKEN`; add `SameSite=Lax` as a second, independent layer.
> - One-liner: **CORS prevents unauthorized reading of responses; CSRF protection prevents unauthorized execution of authenticated actions.**
>

## 1. What CORS does not prevent

You're logged into your bank:

```text
https://bank.com
Cookie: JSESSIONID=abc123
```

You visit `https://evil.com`, which serves:

```html
<form action="https://bank.com/transfer" method="POST">
  <input name="amount" value="10000">
  <input name="to" value="attacker">
</form>
<script>document.forms[0].submit();</script>
```

The browser sends:

```text
POST /transfer HTTP/1.1
Host: bank.com
Cookie: JSESSIONID=abc123          <- attached automatically
Content-Type: application/x-www-form-urlencoded

amount=10000&to=attacker
```

From the bank's side everything looks perfect: valid session, authenticated user, well-formed POST. **The transfer succeeds.**

The user never intended it. The attacker forged a request that the browser signed with the victim's identity.

```text
Cross-Site  ->  the request originated from another site
Request     ->  the browser sent it
Forgery     ->  it appears to come from the user, who never asked for it
```

---

## 2. Why CORS doesn't help

The instinctive objection: *shouldn't CORS block this?*

No — and the reason is the whole point of [[15. CORS Deep Dive]] §5:

```text
CORS blocks READING the response.
CSRF only needs the ACTION to happen.
```

The attacker doesn't care what the bank returns. They want:

```text
Transfer ₹10,000
Change the account email        <- then "forgot password" to themselves
Change the password
Delete the account
Add an API key
```

If the action succeeds, they've won. Response confidentiality is irrelevant.

Worse: a plain HTML `<form>` submission isn't even subject to CORS in the first place — it's a top-level navigation, the same mechanism that has existed since 1995. No preflight, no `Origin` check the browser enforces on the *server's* behalf.

---

## 3. The defence: a synchronizer token

The bank needs something in the request that **only a real page from bank.com could have known**.

When rendering the form:

```html
<form action="/transfer" method="POST">
  <input type="hidden" name="_csrf" value="7xK92LmP-a4c9-4e1a-9d2f">
  <input name="amount">
</form>
```

A legitimate submission carries both:

```text
POST /transfer
Cookie: JSESSIONID=abc123
_csrf=7xK92LmP-a4c9-4e1a-9d2f
```

The server checks **both**:

```text
Valid session?     yes
Valid CSRF token for THIS session?  yes
   -> execute

CSRF token missing or wrong
   -> 403 Forbidden
```

The forged request from `evil.com` has the cookie but no token → rejected.

```text
WITHOUT protection            WITH protection
------------------            ---------------
logged into bank              logged into bank
visits evil.com               visits evil.com
evil.com submits form         evil.com submits form
browser sends cookie          browser sends cookie
bank executes transfer  ✗     no CSRF token -> 403  ✓
```

---

## 4. Why the attacker can't send the token

The key question — *if the browser sends the JSESSIONID for them, why not the token too?*

### What the attacker **can** do

Create a form targeting `bank.com` and submit it. The browser attaches `bank.com` cookies because the **request is going to bank.com**:

```text
Attacker: "browser, send this request to bank.com"
Browser:  "fine — and I'll attach all bank.com cookies, as always"
```

### What the attacker **cannot** do

```js
document.cookie   // on evil.com -> only evil.com's cookies
```

Same-Origin Policy forbids `evil.com` from reading `bank.com`'s cookies. **The attacker never learns the value `abc123`** — they simply don't need to, because the browser supplies it.

### And the token?

```html
<input type="hidden" name="_csrf" value="X7kP91Qz">
```
or
```json
{ "csrfToken": "X7kP91Qz" }
```

To obtain it the attacker would have to **read a page from bank.com**:

```js
fetch("https://bank.com/profile").then(r => r.text())   // blocked by CORS
```

The request may be sent, but the browser refuses to expose the body — so the token can't be extracted. **This is where CORS earns its keep**, protecting the secret that protects the action.

### The asymmetry, stated plainly

| | Session cookie | CSRF token |
|---|---|---|
| Can `evil.com` read it? | ❌ no | ❌ no |
| Does the browser send it automatically? | ✅ **yes** | ❌ **no** |
| Does the attacker need to know it? | no | **yes** |
| Result | forgeable | not forgeable |

**Both are unreadable; only one is auto-sent.** That single difference is the entire mechanism.

> [!tip] The office analogy
> **Session cookie = your badge.** You carry it; the door reads it automatically. An attacker can trick you into walking to a door.
> **CSRF token = today's spoken password.** The guard asks for both. You have the badge automatically, but the attacker can't make you say a password they don't know.

---

## 5. `HttpOnly` — the other half

```text
Set-Cookie: JSESSIONID=abc123; HttpOnly; Secure; SameSite=Lax
```

`HttpOnly` means **even bank.com's own JavaScript** cannot read it:

```js
document.cookie   // JSESSIONID is absent
```

That closes the XSS path: an injected script on bank.com can't exfiltrate the session id. So in a modern app:

```text
evil.com cannot read JSESSIONID          (SOP)
evil.com cannot read the CSRF token      (SOP + CORS)
injected script cannot read JSESSIONID   (HttpOnly)
browser DOES auto-send JSESSIONID
browser does NOT auto-send the CSRF token
```

> [!warning] XSS defeats CSRF protection entirely
> A script running **on your origin** can fetch a page, read the token, and submit the request — it's same-origin, so nothing blocks it. CSRF defence assumes you don't have XSS. That's why CSP ([[17. HTTP Security Headers]]) matters just as much.

---

## 6. Why JWT APIs disable CSRF

```js
fetch("/transfer", {
  method: "POST",
  headers: { Authorization: "Bearer eyJhbGciOi..." }
});
```

The browser **never attaches `Authorization` automatically**. JavaScript must add it explicitly, and `evil.com` doesn't have the token to add. So the classic CSRF attack has nothing to ride on:

```text
evil.com submits a form to your API
   -> no Authorization header
   -> 401, before any business logic
```

Hence the ubiquitous:

```java
http.csrf(csrf -> csrf.disable());
```

which is **correct** — provided authentication really rides on a header and not a cookie.

---

## 7. JWT in a cookie — the case people get wrong

Two ways to hold a JWT in a browser, with opposite CSRF properties.

### Option 1 — memory / `localStorage`, sent as a header

```js
localStorage.setItem("token", jwt);

fetch("/api/orders", { headers: { Authorization: `Bearer ${token}` } });
```

- **CSRF risk: very low** — nothing is auto-attached.
- **XSS risk: high** — any injected script reads `localStorage` instantly. In-memory (React state) is meaningfully better: it dies on reload and isn't sitting in a persistent store.

### Option 2 — JWT in a cookie

```text
Set-Cookie: jwt=eyJhbGciOi...; HttpOnly; Secure; SameSite=Lax
```

Every request now carries it automatically:

```text
Cookie: jwt=eyJhbGciOi...
```

which is behaviourally **identical to `JSESSIONID`**:

- **CSRF risk: real.** `evil.com` can trigger `POST /transfer` and the browser attaches the JWT.
- **XSS risk: low** — `HttpOnly` keeps it away from scripts.

> [!warning] "We use JWT, so we don't need CSRF protection" is false
> It's true only for **header-based** JWT. Put the JWT in a cookie and you've re-created exactly the condition CSRF exploits: an automatically-attached credential. You then need CSRF tokens and/or `SameSite`, the same as a session app.

```text
                     auto-sent?   CSRF risk   XSS risk
Authorization header    no          low        high (localStorage)
Cookie (JWT or session) YES         HIGH       low  (HttpOnly)
```

---

## 8. `SameSite` — the browser-level layer

```text
Set-Cookie: JSESSIONID=abc; HttpOnly; Secure; SameSite=Lax
```

| Value | Cookie sent on a cross-site request? |
|---|---|
| `Strict` | never — even following a normal link from another site |
| `Lax` | only on **top-level GET navigations** (clicking a link). Not on cross-site POST, not on `fetch`, not in iframes |
| `None` | always — **requires `Secure`** |

`Lax` is the modern browser default, and it kills the classic form-POST CSRF outright. It is **not** a replacement for tokens:

- Older browsers ignore it.
- `SameSite=None` is required for genuine cross-site setups (an SSO iframe, a widget) and reopens the hole.
- `Lax` still permits cross-site **GET** — harmless only if `GET` never changes state.

Defence in depth: **CSRF token + `SameSite=Lax` + `Secure` + `HttpOnly`**.

## 9. Spring Security specifics

CSRF protection is **on by default**, applied to `POST`, `PUT`, `PATCH`, `DELETE` — and deliberately **not** to `GET`, `HEAD`, `OPTIONS`, `TRACE`.

> [!warning] That's why `GET` must never change state
> `@GetMapping("/users/delete")` bypasses CSRF protection entirely, and is trivially triggered by `<img src="https://app.com/users/delete?id=5">`. Safe methods must be safe.

### Server-rendered apps (Thymeleaf)

Nothing to do — the Thymeleaf integration injects the hidden `_csrf` field into every `<form>` automatically.

### SPA + cookie-based session

```java
@Bean
SecurityFilterChain chain(HttpSecurity http) throws Exception {
    http.csrf(csrf -> csrf
        .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
        .csrfTokenRequestHandler(new CsrfTokenRequestAttributeHandler())
        .ignoringRequestMatchers("/api/webhooks/**")     // machine callers, no cookies
    );
    return http.build();
}
```

```text
Server -> Set-Cookie: XSRF-TOKEN=abc123          (readable by JS: withHttpOnlyFalse)
JS     -> reads it, echoes it back
Client -> X-XSRF-TOKEN: abc123
```

Axios does this automatically; `fetch` needs it by hand. This works because of the same asymmetry: the cookie is auto-sent, but **only same-origin JavaScript can read it and copy it into the header** — `evil.com` can trigger the cookie but cannot read it to build the header.

> [!warning] Spring Security 6 changed the default token handling
> `CsrfTokenRequestAttributeHandler` (opt-in) restores eager token loading; the new `XorCsrfTokenRequestAttributeHandler` default BREACH-protects the token but is lazier, and the classic symptom is a 403 on the first POST after login because the token cookie was never issued. Add an endpoint that touches `CsrfToken` on load if your SPA needs it up front.

### When disabling is right

| Setup | CSRF protection |
|---|---|
| Session cookie auth (server-rendered or SPA) | **required** |
| JWT/OAuth2 in `Authorization` header, stateless | not needed — disable |
| JWT in a cookie | **required** |
| Machine-to-machine API (no browser, no cookies) | not needed |
| Public read-only GET API | not applicable |

The test is one question: **does the browser attach the credential automatically?** If yes, you need CSRF protection.

## 10. What cookies actually contain

Cookies are just `key=value` pairs. Two authentication styles:

### Session identifier

```text
Set-Cookie: JSESSIONID=abc123xyz
```

The cookie holds **only a pointer**. The server keeps the real data:

```text
abc123xyz  ->  { userId: 42, roles: [ADMIN], loginTime: ... }   in Redis / DB / memory
```

Stateful: revocation is instant (delete the entry), but you need shared session storage across instances.

### The JWT itself

```text
Set-Cookie: jwt=eyJhbGciOi...
```

The cookie holds **the whole token** and its claims:

```json
{ "sub": "42", "email": "umesh@example.com", "role": "USER", "exp": 1790000000 }
```

Stateless: the server just verifies the signature — but revocation is hard ([[9. Refresh Tokens and Token Security]]), and cookies cap around 4KB, which a fat token can approach.

### Everything else

```text
_ga=GA1.2...        analytics
theme=dark          preferences
lang=en             locale
cartId=12345        shopping cart
```

Which is why "cookies are for sessions" is wrong — cookies are a **transport**, and the security properties come from the flags (`HttpOnly`, `Secure`, `SameSite`, `Path`, `Domain`), not from the name.

### Why the header is usually preferred in Spring APIs

```text
Authorization: Bearer <JWT>      not      Cookie: jwt=<JWT>
```

- Stateless and CDN/proxy friendly.
- Works identically for SPAs, mobile apps and server-to-server callers — mobile has no cookie jar to speak of.
- Sidesteps CSRF entirely.
- No `SameSite`/domain juggling across subdomains.

The counter-argument is real though: header storage means the token lives in JS-reachable memory, so **XSS** becomes the dominant risk. The strongest browser answer remains the **BFF** ([[9. Refresh Tokens and Token Security]] §6): a same-origin session cookie to the frontend, tokens held server-side.

## ❓ Interview Questions

### Q1. What is CSRF?

An attack where a malicious site causes a victim's browser to send an authenticated, state-changing request to another site the victim is logged into. It exploits the fact that browsers attach cookies based on the request's destination, regardless of which page initiated it.

### Q2. Why doesn't CORS prevent CSRF?

Because the attacker never reads the response. CORS restricts *reading* cross-origin responses; CSRF only needs the *action* to execute. A plain HTML form POST isn't even subject to CORS.

### Q3. How does the synchronizer token defeat it?

The server issues a random per-session token and requires it on every state-changing request. The attacker can't guess it and can't read it — reading it would mean reading a page from your origin, which SOP and CORS prevent. The forged request arrives with the cookie but no token, and is rejected with 403.

### Q4. If the browser sends the session cookie for the attacker, why not the token?

Because the browser only auto-attaches **cookies**. The CSRF token has to be placed in the body or a custom header by the page's own JavaScript. The attacker can read neither value — but only one is delivered for them automatically.

### Q5. When can you safely disable CSRF protection?

When the credential is not attached automatically by the browser — i.e. a stateless API authenticated by `Authorization: Bearer`. If authentication rides on any cookie (session or JWT), disabling it is a real vulnerability.

### Q6. Is a JWT-based app automatically CSRF-safe?

No. Only if the JWT travels in a header. Stored in a cookie it is auto-sent exactly like `JSESSIONID`, and CSRF protection or `SameSite` is required.

### Q7. What does `SameSite` do, and is it enough on its own?

It tells the browser whether to attach a cookie on cross-site requests: `Strict` never, `Lax` only on top-level GET navigations, `None` always. `Lax` (now the default) blocks classic form-POST CSRF, but it's a second layer — older browsers ignore it, `None` is sometimes required, and cross-site GET still passes.

### Q8. Why does Spring skip CSRF checks on GET?

Safe methods are defined not to change state. If a `GET` mutates data it's already broken, and it's trivially triggered from an `<img>` tag.

### Q9. How do you make CSRF work with a React SPA?

`CookieCsrfTokenRepository.withHttpOnlyFalse()` so the token goes out in a readable `XSRF-TOKEN` cookie; the SPA reads it and echoes it as `X-XSRF-TOKEN`. Safe because only same-origin JS can read the cookie.

### Q10. Does CSRF protection survive XSS?

No. A script on your own origin can read the token and submit a valid request. CSRF defence assumes no XSS, which is why CSP and output encoding are part of the same story.

### Q11. What's in a session cookie versus a JWT cookie?

`JSESSIONID` holds an opaque pointer to server-side session state (stateful, instantly revocable). A JWT cookie holds the claims themselves (stateless, revocation is hard, ~4KB limit).

### Q12. One line separating CORS and CSRF?

**CORS prevents unauthorized reading of responses; CSRF protection prevents unauthorized execution of authenticated actions.**

---

> [!tip] ⚡ Quick Recall
> - **CSRF** = a malicious site makes the victim's browser perform an **authenticated action**.
> - Root cause: **cookies are attached automatically by destination**, not by who initiated the request.
> - CORS can't help — the attacker **never reads the response**, and a form POST isn't CORS-governed.
> - Defence = **synchronizer token**: unguessable, unreadable (SOP + CORS), **not auto-sent**.
> - The asymmetry: attacker can read **neither** cookie nor token; browser auto-sends **only the cookie**.
> - **`HttpOnly`** hides the cookie from JS (anti-XSS); **`Secure`** = HTTPS only; **`SameSite=Lax`** blocks cross-site POST.
> - **JWT in a header → no CSRF risk** (`csrf.disable()` is fine). **JWT in a cookie → full CSRF risk.**
> - Spring: CSRF **on by default**, `POST/PUT/PATCH/DELETE` only → **`GET` must never change state**.
> - SPA: `CookieCsrfTokenRepository.withHttpOnlyFalse()` → `XSRF-TOKEN` cookie → `X-XSRF-TOKEN` header.
> - **XSS defeats CSRF protection** — same-origin script can read the token. CSP matters.
> - Cookie contents: `JSESSIONID` = pointer to server state · `jwt=` = the claims themselves.
> - **CORS = reading. CSRF = doing.**
