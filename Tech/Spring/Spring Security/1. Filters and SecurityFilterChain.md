Everything in Spring Security is built on **servlet filters**. Before a request ever reaches your `@RestController`, it walks through an ordered chain of filters — and every feature you will meet later (form login, JWT, OAuth2, method security) is either a filter, or something a filter populated.

> [!info] 🧭 Summary
> - A **filter** runs *before* `DispatcherServlet`. Security must decide "who are you / are you allowed" before controller code executes.
> - A **`SecurityFilterChain`** = an **ordered list of security filters** + a matcher saying which requests it applies to.
> - Wiring: `Request → DelegatingFilterProxy → FilterChainProxy → SecurityFilterChain → DispatcherServlet → Controller`.
> - Each filter either **continues** (`chain.doFilter(...)`) or **stops** the request (401/403/redirect). If it stops, the controller never runs.
> - Key built-ins: `SecurityContextHolderFilter` (load context) → `LogoutFilter` → `UsernamePasswordAuthenticationFilter` (form login) / `BearerTokenAuthenticationFilter` (JWT) → `AnonymousAuthenticationFilter` → `ExceptionTranslationFilter` (maps exceptions to 401/403) → `AuthorizationFilter` (last, enforces the rules).
> - **Order is everything.** Authentication filters *write* to `SecurityContextHolder`; authorization filters *read* it. Reverse them and every request is a 403.
> - Custom filters (e.g. JWT) are inserted with `addFilterBefore(myFilter, UsernamePasswordAuthenticationFilter.class)` and extend **`OncePerRequestFilter`**.
> - You can register **multiple chains** with `securityMatcher(...)` + `@Order(...)`. Only the **first matching chain** runs — never both.
>
> Next: [[2. Authentication Pipeline]] — what happens *inside* an authentication filter.

## 1. What is a filter?

A filter is a Servlet-spec component (`jakarta.servlet.Filter`) that executes **before the request reaches `DispatcherServlet`**.

Without Spring Security:

```text
Request
   |
   v
Tomcat
   |
   v
DispatcherServlet
   |
   v
Controller
```

With Spring Security:

```text
Request
   |
   v
Tomcat
   |
   v
Security Filters      <-- the chain
   |
   v
DispatcherServlet
   |
   v
Controller
```

Every incoming request passes through a chain of filters, because security concerns have to be settled **before** the controller executes:

- Is the user authenticated?
- Is the JWT valid?
- Does the user have permission?
- Is this request CSRF-safe?
- Is the session expired?

### Why filters and not interceptors or AOP?

A classic interview question. All three can intercept a request, but they sit at different depths:

| Mechanism | Runs | Sees | Used for |
|---|---|---|---|
| **Filter** (Servlet) | Before `DispatcherServlet` | Raw `HttpServletRequest`/`Response` | **Security**, logging, CORS, compression |
| **HandlerInterceptor** (Spring MVC) | After handler mapping, before controller | The resolved handler method | MVC concerns, per-handler timing |
| **AOP / `@Around`** | Around the bean method | Method args, return value | Method security, `@Transactional` |

Security uses filters because a rejected request should never touch Spring MVC at all — and because filters also cover non-MVC endpoints (static resources, actuator, other servlets).

## 2. What is a `SecurityFilterChain`?

Just this:

```text
Filter1 -> Filter2 -> Filter3 -> Filter4
```

You declare one as a bean:

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {

    http
        .authorizeHttpRequests(auth -> auth
                .anyRequest().authenticated()
        )
        .httpBasic(Customizer.withDefaults());

    return http.build();
}
```

`http.build()` assembles a `SecurityFilterChain` containing ~15 filters, in a fixed, well-defined order. You never list them yourself — the DSL methods you call (`.formLogin()`, `.httpBasic()`, `.oauth2ResourceServer()`) decide which filters get added.

> [!note] Spring Security 6 note
> `WebSecurityConfigurerAdapter` is **removed**. The component-based style above (a `SecurityFilterChain` `@Bean`) is the only supported way now. Likewise `authorizeRequests()` → **`authorizeHttpRequests()`** and `antMatchers()` → **`requestMatchers()`**.

## 3. How the chain is actually plugged into Tomcat

The three-layer wiring interviewers like to hear:

```text
Request
  |
  v
DelegatingFilterProxy        <- a plain Servlet filter registered with Tomcat
  |                             (bridges the Servlet world into the Spring context)
  v
FilterChainProxy             <- a Spring bean named springSecurityFilterChain
  |                             holds ALL SecurityFilterChains, picks the matching one
  v
SecurityFilterChain          <- the ordered list of security filters
  |
  v
DispatcherServlet
  |
  v
Controller
```

- **`DelegatingFilterProxy`** — Tomcat starts before the Spring context exists, so it registers this thin proxy which later delegates to a Spring bean. It is the bridge between the servlet container and the `ApplicationContext`.
- **`FilterChainProxy`** — the real entry point. It holds every `SecurityFilterChain` you declared, walks them **in order**, and runs the **first one whose matcher matches**.
- **`SecurityFilterChain`** — the actual filters for this request.

---

## 4. What a filter can do

Every filter gets:

```java
doFilter(request, response, chain)
```

and has exactly two choices.

**Continue** — pass the request down the chain:

```java
chain.doFilter(request, response);
```

**Stop** — end the request here:

```java
response.sendError(401);
```

If a filter stops the chain:

```text
Request
   |
Filter A
   |
Filter B  --> 401
```

The controller never executes. That is the entire enforcement model.

## 5. The important built-in filters

You don't need to memorise all of them. Learn the **responsibility** of these seven.

| # | Filter | Responsibility |
|---|---|---|
| 1 | `SecurityContextHolderFilter` | Loads the `SecurityContext` for this request (from session, if any) and **clears it at the end** |
| 2 | `LogoutFilter` | Watches for `POST /logout`, invalidates the session, clears the context |
| 3 | `UsernamePasswordAuthenticationFilter` | **Form login** — reads `username`/`password` from `POST /login` |
| 4 | `BearerTokenAuthenticationFilter` | **JWT / OAuth2** — reads `Authorization: Bearer ...` |
| 5 | `AnonymousAuthenticationFilter` | If nobody authenticated, installs an `AnonymousAuthenticationToken` |
| 6 | `ExceptionTranslationFilter` | Catches security exceptions and turns them into 401 / 403 / redirect |
| 7 | `AuthorizationFilter` | **Last** — enforces `hasRole`, `authenticated()`, `permitAll()` |

### `SecurityContextHolderFilter`

One of the earliest filters. It creates or loads the `SecurityContext` — the per-request holder for the `Authentication` object.

```text
SecurityContextHolder  ->  SecurityContext  ->  Authentication
```

Think **thread-local storage for security information**. Full detail in [[4. SecurityContext, Authentication and Principal]].

### `UsernamePasswordAuthenticationFilter`

Listens specifically for `POST /login`:

```text
username=umesh
password=secret123
```

It reads the credentials, builds an **unauthenticated** `UsernamePasswordAuthenticationToken`, and calls:

```java
authenticationManager.authenticate(token);
```

Success → `SecurityContext` populated. Failure → 401.

### `BearerTokenAuthenticationFilter`

For token-based APIs:

```text
Authorization: Bearer eyJhb...
```

Extracts the JWT → validates it → builds an `Authentication` → stores it in the `SecurityContext`. After this filter, `SecurityContextHolder.getContext()` knows the user. No session involved.

### `AnonymousAuthenticationFilter`

If no login happened, `getAuthentication()` would return `null` and every downstream check would need a null guard. Instead Spring installs:

```java
new AnonymousAuthenticationToken(key, "anonymousUser", ROLE_ANONYMOUS)
```

So authorization logic stays uniform: there is *always* an `Authentication`, it's just anonymous.

> [!warning] Consequence
> `getAuthentication() != null` does **not** mean "logged in". Check `isAuthenticated()` **and** that the token isn't an `AnonymousAuthenticationToken`.

### `AuthorizationFilter`

The last filter before MVC. It reads the `Authentication` out of the context and evaluates your rules:

```java
.requestMatchers("/admin/**").hasRole("ADMIN")
```

```text
Request → JWT filter → Authentication created → AuthorizationFilter → allowed?
                                                                       |
                                                                  no → 403
```

### `ExceptionTranslationFilter`

Sits *above* `AuthorizationFilter` in the chain so it can catch what that filter throws:

| Exception | Becomes |
|---|---|
| `AuthenticationException` | **401 Unauthorized** (or a redirect to the login page) |
| `AccessDeniedException` | **403 Forbidden** |

Without it you'd see raw stack traces / 500s instead of proper HTTP semantics. It is also what invokes your `AuthenticationEntryPoint` and `AccessDeniedHandler`.

## 6. Filter order — and why it is critical

Spring maintains a fixed order internally (the real chain is longer than this):

```text
1. SecurityContextHolderFilter
2. LogoutFilter
3. UsernamePasswordAuthenticationFilter
4. BearerTokenAuthenticationFilter
5. AnonymousAuthenticationFilter
6. ExceptionTranslationFilter
7. AuthorizationFilter
```

**Bad order:**

```text
AuthorizationFilter
     |
JWT Filter
```

Authorization runs before anyone has authenticated → the context is empty → **403 on every request**.

**Correct order:**

```text
JWT Filter
    |
AuthorizationFilter
```

The rule to remember:

> **Authentication filters *write* to `SecurityContextHolder`. Authorization filters *read* from it. Writers must run first.**

> [!tip] Debugging the chain
> Set `logging.level.org.springframework.security=DEBUG`. On startup Spring prints the full ordered filter list for each chain — the fastest way to confirm your custom filter landed where you think it did.

## 7. Writing a custom filter (the JWT case)

The most common real-world and interview scenario.

```java
@RequiredArgsConstructor
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    private final JwtService jwtService;
    private final UserDetailsService userDetailsService;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {

        String header = request.getHeader("Authorization");

        if (header == null || !header.startsWith("Bearer ")) {
            chain.doFilter(request, response);   // not our concern — move on
            return;
        }

        String token = header.substring(7);

        if (jwtService.isValid(token)
                && SecurityContextHolder.getContext().getAuthentication() == null) {

            UserDetails user = userDetailsService.loadUserByUsername(jwtService.subject(token));

            var auth = new UsernamePasswordAuthenticationToken(
                    user, null, user.getAuthorities());
            auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));

            SecurityContextHolder.getContext().setAuthentication(auth);
        }

        chain.doFilter(request, response);
    }
}
```

Register it:

```java
http.addFilterBefore(jwtAuthenticationFilter,
                     UsernamePasswordAuthenticationFilter.class);
```

Meaning:

```text
JwtAuthenticationFilter
      |
UsernamePasswordAuthenticationFilter
      |
      ... rest of chain
```

### Why `OncePerRequestFilter`?

A plain `Filter` can run **more than once per request** — a `RequestDispatcher` forward, include, or error dispatch re-enters the filter chain. `OncePerRequestFilter` sets a request attribute so `doFilterInternal` runs exactly once. For anything that mutates the `SecurityContext`, that guarantee matters.

### Why *before* `UsernamePasswordAuthenticationFilter`?

Two reasons:

1. **Ordering** — the user must be authenticated before `AuthorizationFilter` runs. Any position before it works; `UsernamePasswordAuthenticationFilter` is a convenient, stable landmark early in the chain.
2. **Convention** — most APIs don't use form login at all, so that slot is free.

> [!warning] Three classic custom-filter bugs
> - **Not calling `chain.doFilter(...)`** on the pass-through path → the request silently dies.
> - **Overwriting an existing `Authentication`** → always check `getAuthentication() == null` first.
> - **Annotating the filter `@Component` in a Spring Boot app** → Boot may *also* auto-register it as a plain servlet filter for **every** URL, outside the security chain. Either don't use `@Component`, or register a `FilterRegistrationBean` with `setEnabled(false)`.

## 8. Multiple `SecurityFilterChain`s

You can declare several chains for different URL spaces:

```java
@Bean
@Order(1)
SecurityFilterChain apiChain(HttpSecurity http) throws Exception {
    http.securityMatcher("/api/**")
        .csrf(csrf -> csrf.disable())
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));
    return http.build();
}

@Bean
@Order(2)
SecurityFilterChain adminChain(HttpSecurity http) throws Exception {
    http.securityMatcher("/admin/**")
        .authorizeHttpRequests(a -> a.anyRequest().hasRole("ADMIN"))
        .formLogin(Customizer.withDefaults());
    return http.build();
}
```

```text
GET /api/users    -> matches chain 1 (stateless JWT)
GET /admin/users  -> matches chain 2 (form login + session)
```

> [!warning] Only ONE chain runs
> `FilterChainProxy` picks the **first** matching chain and stops. Chains do not compose. A common bug: a broad chain with no `securityMatcher` (so it matches everything) placed at `@Order(1)` — it swallows every request and the later chains never fire. Put the **most specific matcher first** and leave the catch-all chain last.

## ❓ Interview Questions

### Q1. What is a `SecurityFilterChain`?

An ordered list of servlet filters plus a `RequestMatcher` deciding which requests it applies to. Every HTTP request passes through it before reaching `DispatcherServlet`.

### Q2. Walk me through what happens between Tomcat and my controller.

`DelegatingFilterProxy` (registered with the container) → `FilterChainProxy` (Spring bean) → picks the first matching `SecurityFilterChain` → runs its filters in order → `DispatcherServlet` → controller.

### Q3. Why does filter order matter?

Authentication filters populate `SecurityContextHolder`; `AuthorizationFilter` reads it. If authorization runs first, the context is empty and every request is denied with 403.

### Q4. How do you add a JWT filter, and why *before* `UsernamePasswordAuthenticationFilter`?

`http.addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)` — so the user is authenticated before `AuthorizationFilter` evaluates the rules. Form login isn't used in a token API anyway.

### Q5. Difference between a filter, a `HandlerInterceptor`, and AOP method security?

Filter = servlet level, sees the raw request, runs before Spring MVC. Interceptor = Spring MVC level, sees the resolved handler. Method security = AOP proxy around the bean method, sees arguments and return value. Spring Security uses filters for URL rules and AOP for `@PreAuthorize`.

### Q6. Why `OncePerRequestFilter` instead of `Filter`?

Because forwards, includes and error dispatches re-enter the filter chain; `OncePerRequestFilter` guarantees the logic runs exactly once per request.

### Q7. What does `ExceptionTranslationFilter` do?

Converts `AuthenticationException` → 401 (or a login redirect) and `AccessDeniedException` → 403, delegating to the configured `AuthenticationEntryPoint` / `AccessDeniedHandler`.

### Q8. If I declare two `SecurityFilterChain` beans, do both run?

No. `FilterChainProxy` runs only the first chain whose matcher matches. Order them with `@Order`, most specific first.

> [!tip] ⚡ Quick Recall
> - Filters run **before** `DispatcherServlet` — security decides before the controller exists.
> - `DelegatingFilterProxy → FilterChainProxy → SecurityFilterChain → filters → DispatcherServlet`.
> - A filter either calls `chain.doFilter(...)` (continue) or ends the response (stop).
> - Authentication filters **write** the context; `AuthorizationFilter` **reads** it. Writers first.
> - `SecurityContextHolderFilter` first, `AuthorizationFilter` last, `ExceptionTranslationFilter` just above it.
> - `AnonymousAuthenticationFilter` means `getAuthentication()` is rarely `null` — check for `AnonymousAuthenticationToken`.
> - Custom filter = `extends OncePerRequestFilter` + `addFilterBefore(..., UsernamePasswordAuthenticationFilter.class)`.
> - Multiple chains: `securityMatcher` + `@Order`; **only the first match runs**.
> - Debug with `logging.level.org.springframework.security=DEBUG` to print the real chain.
