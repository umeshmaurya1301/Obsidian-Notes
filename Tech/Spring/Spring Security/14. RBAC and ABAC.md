Every system starts with roles and eventually outgrows them. The moment someone asks *"can User A see User B's order?"*, roles have nothing to say — both are `ROLE_CUSTOMER`. That question is where senior authorization design begins.

> [!info] 🧭 Summary
> - **RBAC** = Role-Based Access Control. Permissions attach to **roles**; users get roles. `User → Role → Permissions`.
> - **ABAC** = Attribute-Based Access Control. Access depends on **attributes** of the user, the resource, and the environment — evaluated as a rule.
> - RBAC's hard limit: it **cannot express ownership**. Two users with `ROLE_CUSTOMER` are indistinguishable to it, so "you may only see *your own* order" is unanswerable.
> - ABAC answers it: `@PreAuthorize("#order.userId == authentication.principal.id")`.
> - Attribute sources: **user** (id, department, branch, tenant) · **resource** (ownerId, department, status, amount) · **environment** (time, IP, location).
> - In Spring, ABAC is **SpEL inside `@PreAuthorize`**. Useful variables: `authentication`, `principal`, `#methodParameter`, `returnObject` (in `@PostAuthorize`), `hasRole()`, `hasAuthority()`.
> - Most real systems use **both**: RBAC for the coarse gate, ABAC for the fine one — `hasRole('MANAGER') and #branchId == authentication.principal.branchId`.
> - Rule of thumb: **RBAC gets you 70–80%**; ABAC handles ownership, department, branch, tenant and business-rule checks that roles can't express.
> - RBAC is simpler, auditable and easy to explain to non-engineers. ABAC is more flexible but harder to reason about, test and audit — "who can access this document?" stops having a listable answer.
> - Beyond a handful of rules, move logic out of annotations into a **`PermissionEvaluator`** or a custom **`AuthorizationManager`**, so policy is testable code rather than strings.
>

## 1. The problem

You have users, admins, managers, support agents. Someone must decide **who can access what**. That's authorization ([[6. Authorization]]), and there is more than one model for expressing it. The two that matter:

```text
RBAC  =  Role-Based Access Control
ABAC  =  Attribute-Based Access Control
```

---

## 2. RBAC

> Permissions are assigned to roles. Users are assigned roles.

```text
ADMIN
   +--> CREATE_USER
   +--> DELETE_USER
   +--> VIEW_REPORT

MANAGER
   +--> VIEW_REPORT
   +--> APPROVE_ORDER

USER
   +--> VIEW_PROFILE
```

```text
Umesh --> ADMIN
John  --> USER
```

The decision is a two-hop lookup:

```text
User  ->  Role  ->  Permissions  ->  Allow / Deny
```

### In Spring

```java
.requestMatchers("/admin/**").hasRole("ADMIN")
```

```java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) { ... }
```

```text
GET /admin/users

authorities = [ROLE_ADMIN]  ->  allowed
authorities = [ROLE_USER]   ->  403
```

### Why RBAC is everywhere

- Easy to understand, implement and **explain to auditors and non-engineers**.
- Maps directly onto how organisations already think: HR, Finance, Admin, Support.
- Answerable questions: *"who can approve orders?"* → list everyone with `ROLE_MANAGER`. That listability is worth a lot at audit time.

---

## 3. Where RBAC breaks

```text
User A  ->  ROLE_USER
User B  ->  ROLE_USER

Endpoint:  GET /users/{id}

Can User A view User B's profile?
```

RBAC's answer: *both are `ROLE_USER`, so both may call `GET /users/{id}`.* It has no vocabulary for **which** `{id}`. The role says nothing about the relationship between this user and this row.

You could try to patch it with roles — `ROLE_USER_42` — and it collapses immediately: a role per user, a role per branch, a role per document. This is **role explosion**, the classic failure mode of pure RBAC in a large system.

The relationship you actually need is between the **subject** and the **object**. That's ABAC.

---

## 4. ABAC

> Access depends on attributes, not only roles.

```text
User attributes         Resource attributes      Environment
  id                      ownerId                  time
  department              department               location
  branch                  status                   ip address
  manager                 amount                   device
  tenantId                tenantId                 risk score
```

A decision is a **rule** over those attributes:

```text
ALLOW IF user.id == resource.ownerId
ALLOW IF user.department == document.department
ALLOW IF user.branch == loan.branch AND user.role == MANAGER
DENY  IF environment.time NOT IN business_hours
```

### The canonical example

```text
Rule: a user may view a document only if he owns it.

Document.ownerId = 10

logged-in user id = 10   ->  allowed
logged-in user id = 11   ->  denied
```

No roles involved at all.

---

## 5. ABAC in Spring Security

ABAC is implemented with **SpEL inside `@PreAuthorize`**. (Requires `@EnableMethodSecurity` — see [[6. Authorization]] §6.)

```java
@PreAuthorize("#id == authentication.principal.id")
public User getProfile(Long id) { ... }
```

```text
GET /users/10   with principal.id = 10   ->  allowed
GET /users/20   with principal.id = 10   ->  403
```

This is ABAC because the decision compares a **resource attribute** (`id`) with a **user attribute** (`principal.id`).

### Department example

```java
@PreAuthorize("#document.department == authentication.principal.department")
public void edit(Document document) { ... }
```

### A business rule, not a role

> Only managers may approve orders above ₹1 lakh.

```text
amount <  100000   ->  any employee
amount >= 100000   ->  manager required
```

```java
@PreAuthorize("#order.amount < 100000 or hasRole('MANAGER')")
public void approve(Order order) { ... }
```

Neither pure RBAC nor pure ABAC — a **role attribute combined with a resource attribute**. Most real rules look like this.

### The e-commerce case

```text
Order:  orderId=100, ownerId=50

user 50 -> can view
user 51 -> cannot view

...even though BOTH have ROLE_CUSTOMER.
```

```java
@PreAuthorize("#order.ownerId == authentication.principal.id or hasRole('SUPPORT')")
public Order view(Order order) { ... }
```

### Useful SpEL variables

| Expression | Meaning |
|---|---|
| `authentication` | the whole `Authentication` object |
| `principal` | shorthand for `authentication.principal` |
| `#paramName` | a method argument (needs `-parameters` compilation, or `@P("name")`) |
| `returnObject` | the return value — **`@PostAuthorize` only** |
| `hasRole('X')` / `hasAuthority('X')` | the RBAC predicates, usable in the same expression |
| `@beanName.method(...)` | call any Spring bean |

```java
@PreAuthorize("authentication.name == #email")
public User byEmail(String email) { ... }
```

> [!warning] `#param` needs parameter names at runtime
> Without `-parameters` on the compiler (Spring Boot's Maven/Gradle plugins set it by default), `#id` resolves to `null` and the expression quietly evaluates to **false** — or worse, `null == null` is **true**. Use `@P("id")` on the parameter if you can't rely on the flag, and always have a test that asserts the *denied* case.

## 6. Combining them — what production actually looks like

```java
// Step 1 — pure RBAC
@PreAuthorize("hasRole('ADMIN')")

// Step 2 — RBAC + ABAC
@PreAuthorize("hasRole('ADMIN') and #userId == authentication.principal.id")

// Step 3 — a real one
@PreAuthorize("hasRole('MANAGER') and #branchId == authentication.principal.branchId")
```

### Banking

```text
Roles:  ROLE_CUSTOMER, ROLE_BANK_EMPLOYEE, ROLE_MANAGER

RBAC:   ROLE_MANAGER may approve loans.
ABAC:   ...but only loans belonging to his own branch.

Rule:   manager.branch == loan.branch
```

```java
@PreAuthorize("hasRole('MANAGER') and #loan.branchId == authentication.principal.branchId")
public void approveLoan(Loan loan) { ... }
```

### Payments — the one that always comes up

```java
@PreAuthorize("hasAuthority('SETTLEMENT_READ') "
            + "and #merchantId == authentication.principal.merchantId")
public SettlementReport report(String merchantId, LocalDate day) { ... }
```

The authority says *this user's job involves settlements*. The attribute check says *and only for their own merchant*. Drop the second half and you have a cross-tenant data leak that no role check would ever catch.

### The typical enterprise flow

```text
Authentication
       |
       v
Authentication object
       +--> Roles              (RBAC input)
       +--> User attributes    (ABAC input: id, branch, department, tenant)
       |
       v
   RBAC check  ->  is this the right kind of user?
       +
   ABAC check  ->  is this their record?
       |
       v
   Allow / Deny
```

**RBAC filters by job function. ABAC filters by relationship.** Both, in that order.

## 7. Scaling past annotations

Long SpEL strings are unreadable, untestable and un-refactorable. Two ways out.

### `PermissionEvaluator` — `hasPermission()`

```java
@PreAuthorize("hasPermission(#orderId, 'Order', 'READ')")
public Order get(Long orderId) { ... }
```

```java
@Component
public class OrderPermissionEvaluator implements PermissionEvaluator {
    @Override
    public boolean hasPermission(Authentication auth, Serializable id,
                                 String type, Object permission) {
        if (!"Order".equals(type)) return false;
        AppUser user = (AppUser) auth.getPrincipal();
        return orderRepo.findById((Long) id)
                        .map(o -> o.getOwnerId().equals(user.getId()))
                        .orElse(false);
    }
    // + the (Authentication, Object targetDomainObject, Object permission) overload
}
```

Policy becomes ordinary Java: unit-testable, debuggable, refactorable.

### Custom `AuthorizationManager` (Spring Security 6)

```java
@Bean
AuthorizationManager<RequestAuthorizationContext> sameBranch() {
    return (auth, ctx) -> {
        String branch = ctx.getVariables().get("branchId");
        AppUser user = (AppUser) auth.get().getPrincipal();
        return new AuthorizationDecision(user.getBranchId().equals(branch));
    };
}

// .requestMatchers("/branches/{branchId}/**").access(sameBranch())
```

### Filtering collections

Authorization on a **list** is a different problem — you can't `@PostFilter` a million rows.

```java
@PostFilter("filterObject.ownerId == authentication.principal.id")
List<Order> findAll();          // fine for a page, disastrous for a table scan
```

The scalable answer is to **push the predicate into the query**:

```java
@Query("select o from Order o where o.ownerId = :#{authentication.principal.id}")
List<Order> findMine();
```

or use Hibernate filters / row-level security. Rule of thumb: **`@PreAuthorize` for single objects, a WHERE clause for collections.**

## 8. Choosing

| | RBAC | ABAC |
|---|---|---|
| Decision input | roles | arbitrary attributes |
| Flexibility | low | **high** |
| Simplicity | **high** | low |
| Auditability | "list everyone with ROLE_X" | requires policy evaluation |
| Failure mode | **role explosion** | unreadable, untestable rules |
| Handles ownership | ❌ | ✅ |
| Handles multi-tenancy | ❌ | ✅ |
| Performance | trivial | may need a DB lookup per check |

- **More flexible?** ABAC — decisions can use any attribute.
- **Simpler?** RBAC — it only needs roles.
- **Scales better in a complex enterprise?** **RBAC + ABAC together.**

> [!warning] ABAC's real cost is verification
> With RBAC you can answer "who can approve loans?" by querying role assignments. With ABAC the honest answer is "run the policy against every (user, resource) pair". Keep the *set of rules* small and the *attributes* well-defined, or authorization becomes something nobody can reason about — including your auditors.

Related models worth naming if asked: **ReBAC** (relationship-based — Google Zanzibar, `user:42 is editor of doc:9`), which fits sharing and hierarchies better than either; and **PBAC/policy engines** (OPA/Rego, Cedar) which externalise ABAC rules out of the codebase entirely.

## ❓ Interview Questions

### Q1. RBAC vs ABAC in one line each?

RBAC grants access based on the roles a user holds. ABAC grants access based on attributes of the user, the resource and the environment, evaluated as a rule.

### Q2. Give a case RBAC cannot express.

"A customer may view their own order." Every customer has `ROLE_CUSTOMER`, so the role check passes for all of them. The rule depends on `order.ownerId == user.id` — a relationship, not a role.

### Q3. How do you implement ABAC in Spring Security?

SpEL in `@PreAuthorize`, comparing method arguments or the resource to `authentication.principal`: `@PreAuthorize("#order.ownerId == authentication.principal.id")`. For anything non-trivial, move the logic into a `PermissionEvaluator` (`hasPermission(...)`) or a custom `AuthorizationManager`.

### Q4. Which is more flexible, and which is simpler?

ABAC is more flexible — decisions can use arbitrary attributes. RBAC is simpler — it only needs roles. Most enterprises combine them.

### Q5. What is role explosion?

Trying to encode fine-grained, per-resource rules as roles: `ROLE_BRANCH_BLR_MANAGER`, `ROLE_DOC_42_EDITOR`. The role count grows with your data, assignment becomes unmanageable, and the model stops being auditable — which is the signal to introduce ABAC.

### Q6. Where does the attribute data come from at check time?

The user attributes ride on the principal (from `UserDetails`, a JWT claim, or an `OidcUser`). Resource attributes come either from a method argument already loaded by the caller, or from a repository lookup inside a `PermissionEvaluator` — which is why fine-grained checks can cost a query.

### Q7. `@PreAuthorize` vs `@PostAuthorize` for ownership?

`@PreAuthorize` when the attribute is available from the arguments — it denies before the work happens. `@PostAuthorize("returnObject.ownerId == authentication.principal.id")` when you must load the object to know its owner — correct, but it runs the method (and any transaction) first, so never use it on something with side effects.

### Q8. How do you apply ownership rules to a list endpoint?

Push the predicate into the query rather than filtering after the fact. `@PostFilter` re-checks every element in memory and doesn't survive pagination or large tables.

### Q9. How does multi-tenancy fit in?

It's ABAC with one mandatory attribute: every query and every check is scoped by `tenantId` from the token. Enforce it centrally — a `WHERE tenant_id = ?` filter or row-level security — rather than trusting each `@PreAuthorize` to remember.

### Q10. So which do you use in production?

Both. RBAC as the coarse gate (does this user's job involve this operation?), ABAC as the fine one (is this their record, their branch, their tenant?). RBAC covers most requirements; ABAC covers the ones that matter most when they go wrong.

> [!tip] ⚡ Quick Recall
> - **RBAC**: `User → Role → Permissions`. `hasRole('ADMIN')`. Simple, auditable, listable.
> - **ABAC**: decision from **user + resource + environment attributes**. `#order.ownerId == authentication.principal.id`.
> - RBAC **cannot express ownership** — two `ROLE_CUSTOMER`s are identical to it. That's the entire reason ABAC exists.
> - Attribute sources: user (id, branch, department, tenant) · resource (ownerId, status, amount) · environment (time, IP).
> - Spring ABAC = **SpEL in `@PreAuthorize`**. Variables: `authentication`, `principal`, `#param`, `returnObject`.
> - Production is **RBAC + ABAC**: `hasRole('MANAGER') and #branchId == authentication.principal.branchId`.
> - **RBAC ≈ 70–80% of requirements**; ABAC handles ownership, branch, department, tenant, business rules.
> - RBAC's failure mode = **role explosion**. ABAC's = unreadable, unauditable rules.
> - Past a few rules → **`PermissionEvaluator`** / custom **`AuthorizationManager`**, so policy is testable Java.
> - Lists: **push the predicate into the query**, don't `@PostFilter`.
> - **RBAC filters by job function. ABAC filters by relationship.**
