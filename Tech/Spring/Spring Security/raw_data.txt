Phase 7 is where OAuth becomes practical for backend engineers.
Most Java backend engineers are not building Google, Keycloak, or Auth0.
Instead, they're building APIs that need to trust tokens issued by someone else.
That's exactly what an OAuth2 Resource Server does.

First: What is a Resource Server?
A Resource Server is simply:
An API that protects resources
and accepts access tokens.
Example:
GET /orders
GET /payments
GET /customers
These APIs contain protected business data.

Architecture

Why Not Authenticate Again?
A common beginner question:
Why doesn't Order Service
call UserDetailsService?
Because authentication already happened.
The token already says:
{
  "sub": "umesh",
  "roles": ["ADMIN"]
}
The Resource Server only needs to verify:
1. Token is genuine
2. Token is not expired
3. Token issuer is trusted
4. User has required permissions

First: What Problem Are We Solving?

There are multiple models.
The two most common are:

RBAC (Role-Based Access Control)
RBAC says:
Permissions are assigned to Roles.

Users get Roles.

Example:

    |
    +--> VIEW_PROFILE

Umesh
    |
    +--> ADMIN

John
    |
    +--> USER

Authorization becomes:
User
   |
Role
   |
Permissions

Spring Security RBAC
Very common.
.requestMatchers("/admin/**")
.hasRole("ADMIN")
or
@PreAuthorize("hasRole('ADMIN')")

Request:
GET /admin/users
User authorities:
ROLE_ADMIN
Allowed.

User authorities:
ROLE_USER
Denied.

Why RBAC Is Popular
Easy to understand.
Easy to implement.
Easy to explain.
Example:
HR
Finance
Admin
Support
Everybody understands roles.

RBAC Limitation
Suppose:
User A
User B
Both have:
ROLE_USER

Endpoint:
GET /users/{id}
Question:
Can User A see User B's profile?
RBAC says:
Both are ROLE_USER.
RBAC cannot differentiate.

This is where ABAC comes in.

ABAC (Attribute-Based Access Control)
ABAC says:
Access depends on attributes,
not only roles.

Attributes can come from:
User
id
department
country
manager

Resource
ownerId
department
status

Environment
time
location
ip address

Decision is based on rules.

Example
Rule:
User can view a document
only if he owns it.

Document:
ownerId = 10

Logged in user:
userId = 10
Allowed.

Logged in user:
userId = 11
Denied.

No roles involved.

ABAC in Spring Security
Example:

}

Allowed.

Request:

User:

Denied.

This is ABAC.
Because access depends on:

    id

User Attribute:
    principal.id

CORS is one of those topics that seems complicated until you understand why browsers enforce it.

Step 1: Why CORS Exists
Imagine:
Frontend:
https://amazon.com
Backend:
https://api.amazon.com
User logs into Amazon.
Now imagine the user opens another tab:
https://evil-hacker.com
Without protection, JavaScript running on evil-hacker.com could do:
fetch("https://api.amazon.com/user/bank-details")
and read the response.
That would be a disaster.
To prevent this, browsers enforce a security rule called:
Same-Origin Policy (SOP)
A webpage can only read responses from the same origin.

Step 2: What is an Origin?
Origin consists of:
Protocol + Domain + Port
Examples:
Same Origin
https://amazon.com
https://amazon.com

Different Origin (Protocol)
http://amazon.com
https://amazon.com
Different origin.

Different Origin (Domain)
https://amazon.com
https://api.amazon.com
Different origin.

Different Origin (Port)
https://amazon.com:443
https://amazon.com:8080
Different origin.

Step 3: The Problem
Modern architectures look like:
Frontend:
https://app.company.com
Backend:
https://api.company.com
Different origins.
Browser blocks response:
fetch("https://api.company.com/users")
because of SOP.
But we actually WANT frontend to access backend.
So how can backend tell browser:
"It's okay, I trust this frontend."
This is where CORS comes in.

Step 4: What is CORS?
CORS =
Cross-Origin Resource Sharing
It's a mechanism where:
Backend tells browser
which origins are allowed.

Example request:
fetch("https://api.company.com/users")
Browser sends request.
Backend responds:
Access-Control-Allow-Origin: https://app.company.com
Browser sees:
Origin matches
and allows JavaScript to read response.

Step 5: Request Flow
Frontend:
fetch("https://api.company.com/users")
Browser automatically adds:
Origin: https://app.company.com
Request:
GET /users

Origin: https://app.company.com

Backend responds:
200 OK

Access-Control-Allow-Origin: https://app.company.com
Browser checks:
Request Origin == Allowed Origin
If yes:
Response accessible
If no:
CORS Error

Step 6: Important Confusion
People think:
CORS blocks requests
Not exactly.
Backend still receives request
Browser only blocks JavaScript from reading response.
Example:
fetch(...)
Browser:
Request sent
Response received
Response hidden from JS
Hence you see:
Blocked by CORS policy
in console.

Step 7: Why Postman Works
Very common interview question.
Browser
fetch(...)
fails.
Postman
works.
Why?
Because:
CORS is enforced by browsers.
Postman is not a browser.
No Same-Origin Policy.
No CORS enforcement.
Hence:
Postman succeeds
Browser fails

Step 8: Simple Requests
Browser directly sends request if it is considered "simple".
Examples:
GET
POST
HEAD
with standard headers.
Example:
fetch("/users")
Browser directly sends request.

Step 9: Preflight Request
Suppose:
fetch("/users", {
  method: "PUT",
  headers: {
      "Authorization": "Bearer xyz"
  }
})
Now browser becomes cautious.
Before actual request it sends:
OPTIONS /users
called a
Preflight Request

Step 10: Why Preflight Exists
Browser asks backend:
Can I send a PUT request?

Can I send Authorization header?
Request:
OPTIONS /users

Origin: https://app.company.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Authorization

Backend replies:
Access-Control-Allow-Origin: https://app.company.com

Access-Control-Allow-Methods: GET,POST,PUT

Access-Control-Allow-Headers: Authorization
Browser sees:
Everything allowed
Then sends actual request.

Complete flow:
Browser
   |
OPTIONS
   |
Backend
   |
Allowed
   |
PUT Request
   |
Backend
   |
Response

Step 11: Most Important CORS Headers
Allow Origin
Access-Control-Allow-Origin
Example:
Access-Control-Allow-Origin: https://app.company.com

Allow Methods
Access-Control-Allow-Methods
Example:
Access-Control-Allow-Methods: GET,POST,PUT,DELETE

Allow Headers
Access-Control-Allow-Headers
Example:
Access-Control-Allow-Headers: Authorization,Content-Type

Allow Credentials
Access-Control-Allow-Credentials: true
Used for:
Cookies
Session Authentication

Step 12: JWT vs Cookie and CORS
This is where Spring Security developers get confused.
JWT in Authorization Header
Authorization: Bearer abc123
No cookie involved.
Backend:
Access-Control-Allow-Origin
usually enough.

Session Cookie
Browser automatically sends:
Cookie: JSESSIONID=xyz
Now backend must also return:
Access-Control-Allow-Credentials: true
and frontend must call:
fetch(url,{
   credentials:"include"
})

Step 13: Why * Can Be Dangerous
Some developers do:
Access-Control-Allow-Origin: *
Meaning:
Everyone can access.
Okay for:
Public APIs
Dangerous for:
Banking
Payments
Admin portals
Usually whitelist:
https://app.company.com
https://admin.company.com

Step 14: Spring Boot Example
@Configuration
public class CorsConfig {

    @Bean
    public WebMvcConfigurer corsConfigurer() {

        return new WebMvcConfigurer() {

            @Override
            public void addCorsMappings(
                    CorsRegistry registry) {

                registry.addMapping("/**")
                        .allowedOrigins(
                            "https://app.company.com")
                        .allowedMethods(
                            "GET","POST","PUT","DELETE")
                        .allowedHeaders("*");
            }
        };
    }
}

Step 15: Spring Security Gotcha
Many people configure CORS:
WebMvcConfigurer
but still get errors.
Why?
Because Spring Security intercepts request before MVC.
Need:
@Bean
SecurityFilterChain securityFilterChain(
        HttpSecurity http)
        throws Exception {

    http.cors(Customizer.withDefaults());

    return http.build();
}
Without this:
OPTIONS request gets blocked
Preflight fails.
Actual request never sent.

Interview-Level Summary
Think of CORS like a nightclub security check:
Frontend = Visitor
Browser = Security Guard
Backend = Club Owner
Visitor says:
I want to enter.
Security guard asks owner:
Is this origin allowed?
Backend replies:
Yes, app.company.com is allowed.
Then browser lets the frontend read the response.
Without CORS, the browser protects users from malicious websites stealing data from other sites they are logged into.
The two concepts that unlock 90% of CORS are:
Same-Origin Policy (browser security rule)
Preflight OPTIONS request (browser asking permission before risky requests)
Once these are clear, the rest of CORS becomes mostly a matter of understanding the headers.

The answer is:
"Simple" in CORS does NOT mean safe.
It means:
"This request type has existed on the web for a long time and websites have always been able to trigger it."

Before AJAX existed
Long before JavaScript fetch() and CORS, a website could already make the browser send requests to another site.
For example:
GET
<img src="https://bank.com/account">
When browser loads the image:
GET https://bank.com/account

POST

    <input name="amount" value="1000">
</form>
and auto-submit it.
Browser would send:
POST /transfer
to another website.
This was possible even 25 years ago.

So what problem was CORS solving?
Not:
Can a website send a request?
That was already possible.
Instead:
Can JavaScript READ the response?
That is the dangerous part.
Example:
Attacker site
fetch("https://bank.com/account")
If JS could read the response:
{
  "balance": 100000,
  "accountNumber": "123456"
}
then the attacker could steal it.
So browser says:
Request can be sent.
Response cannot be read unless CORS allows it.

Then why preflight for some requests?
Because some requests indicate AJAX/API behavior rather than traditional web forms.
For example:
PUT /users/123
DELETE /users/123
PATCH /users/123
Traditional HTML forms cannot generate these methods.
Similarly:
Authorization: Bearer xxx
or
X-Custom-Header: abc
are not standard browser form submissions.
When browser sees these, it thinks:
This is an advanced cross-origin API call.
Let me ask permission first.
Hence preflight.

Official definition of a Simple Request
A request is "simple" only if all conditions are satisfied.
Method
Must be one of:
GET
POST
HEAD

Headers
Only simple headers:
Accept
Accept-Language
Content-Language
Content-Type
plus a few browser-managed headers.

Content-Type
For POST, only:
application/x-www-form-urlencoded

multipart/form-data

text/plain
are simple.

This is simple:
fetch("/users", {
    method: "POST",
    headers: {
        "Content-Type":
            "application/x-www-form-urlencoded"
    }
})
No preflight.

This is NOT simple:
fetch("/users", {
    method: "POST",
    headers: {
        "Content-Type":
            "application/json"
    }
})
Surprisingly:
application/json
causes preflight.
Many developers don't realize this.

Why is GET considered simple if it can read data?
Because:
Simple request ≠ Safe request
Browser already allows websites to initiate GETs through:
<img>
<script>
<link>
<iframe>
etc.
The security protection is:
JavaScript cannot read the response
unless CORS allows it.

Great connection.
Imagine you're logged into your bank.

</script>

The transfer may succeed.
Notice:
Attacker never read the response.
So CORS is not violated.
This is why:
CORS protects response reading.
CSRF protects unwanted state-changing requests.
They solve different problems.

Mental model
CORS asks:
Can JavaScript from Origin A
read responses from Origin B?
CSRF asks:
Can Origin A trick the browser
into sending authenticated requests
to Origin B?
Different threats, different defenses.
That's why a GET or POST can be a "simple request" even though it may access or modify important resources. The browser's concern for CORS is primarily cross-origin response access, not whether the operation itself is sensitive.

Now Come to the CSRF. what is this , what problem does it solves

CSRF is much easier to understand once you understand what CORS does.

First: What CORS Does NOT Prevent
Suppose you're logged into:
https://bank.com
Your browser has:
Cookie: SESSIONID=abc123
Now you visit:
https://evil.com
The attacker creates:
<form action="https://bank.com/transfer" method="POST">
    <input name="amount" value="10000">
    <input name="to" value="attacker">
</form>

<script>
document.forms[0].submit();
</script>
What happens?
Browser sends:
POST /transfer

Cookie: SESSIONID=abc123
Notice:
The browser automatically sends the bank session cookie because the request is going to bank.com.
From the bank's perspective:
Valid session cookie
Authenticated user
POST request
So the transfer may succeed.

Where is the attack?
The user never intended to transfer money.
The attacker tricked the user's browser into making an authenticated request.
This is called:
CSRF
Cross-Site Request Forgery
Breaking it down:
Cross-Site → request originated from another site
Request → browser sends request
Forgery → request appears to come from the user even though the user didn't intend it

Why CORS Doesn't Stop This
Many people think:
"Shouldn't CORS block this?"
No.
Because the attacker doesn't need to read the response.
They only need the action to happen.
Example:
Transfer ₹10,000
Change email
Delete account
Change password
If the action succeeds, the attacker wins.
Whether they can read the response is irrelevant.

What Problem Does CSRF Solve?
CSRF protects against:
Malicious websites causing a user's browser
to perform authenticated actions on another site.
In short:
CORS protects data reading.
CSRF protects unwanted actions.

How CSRF Protection Works
The idea is:
Session cookie = sent automatically
CSRF token = cannot be guessed by attacker
When rendering a page:
Server generates:
<input type="hidden"
       name="_csrf"
       value="7xK92LmP">
The browser submits:
POST /transfer

Cookie: SESSIONID=abc123

_csrf=7xK92LmP
Server checks:
Valid session?
Valid CSRF token?
Only then executes transfer.

Why Can't Attacker Send the Token?
Attacker can create:
<form action="https://bank.com/transfer">
But they don't know:
7xK92LmP
because it's generated by the bank and tied to the user's session.
So their forged request becomes:
POST /transfer

Cookie: SESSIONID=abc123
without:
_csrf=7xK92LmP
Server rejects:
403 Forbidden

Visual Flow
Without CSRF protection:
User logged into bank
        ↓
Visits evil.com
        ↓
evil.com submits form
        ↓
Browser sends bank cookie
        ↓
Bank executes transfer

With CSRF protection:
User logged into bank
        ↓
Visits evil.com
        ↓
evil.com submits form
        ↓
Browser sends cookie
        ↓
No CSRF token
        ↓
Bank rejects request

Why JWT APIs Often Disable CSRF
Suppose frontend sends:
Authorization: Bearer eyJ...
The browser does NOT automatically attach this header.
JavaScript must explicitly add it:
fetch("/transfer", {
  headers: {
    Authorization: "Bearer eyJ..."
  }
})
Now imagine evil.com.
Can it send the token?
No.
It doesn't know the token.
Therefore classic CSRF attack doesn't work.
That's why many Spring Boot applications using JWT do:
http.csrf(csrf -> csrf.disable());

When Do You Need CSRF Protection?
Session/Cookie Authentication
Cookie: JSESSIONID=abc123
✅ Usually need CSRF protection.
Because cookies are sent automatically.

JWT in Authorization Header
Authorization: Bearer xyz
❌ Usually CSRF protection is not needed.
Because the attacker cannot automatically cause the browser to include the token.

Interview Summary
CORS
Protects:
Can evil.com READ responses from bank.com?

CSRF
Protects:
Can evil.com make the user's browser
perform actions on bank.com using the user's session?

A classic interview one-liner:
CORS prevents unauthorized reading of responses; CSRF prevents unauthorized execution of authenticated actions.
Why the evil site can not read the csrf token when they can read the JSESSION_ID

This is the key insight that makes CSRF protection work.
The short answer is:
The evil site cannot read either the JSESSIONID cookie or the CSRF token from bank.com.
The difference is that the browser automatically sends the cookie, but it does not automatically send the CSRF token.
Let's walk through it carefully.

What the attacker can do
Suppose you're logged into:
https://bank.com
Your browser stores:
JSESSIONID=abc123
Now you visit:
https://evil.com
The attacker's page can create:
<form action="https://bank.com/transfer" method="POST">
  <input name="amount" value="10000">
</form>
and submit it.
The browser automatically attaches:
Cookie: JSESSIONID=abc123
because the request is going to bank.com.

What the attacker cannot do
The attacker cannot run:
document.cookie
and see:
JSESSIONID=abc123
because that cookie belongs to bank.com.
Same-Origin Policy prevents evil.com from reading cookies of bank.com.
So the attacker does not know the session ID value.

Then how is the cookie being used?
Because the browser itself sends it.
Think of it like:
Attacker: "Send this request to bank.com"

Browser: "Okay, I see this is for bank.com.
I will attach all bank.com cookies."
The attacker benefits from the cookie being attached automatically, even though they cannot read it.

What about the CSRF token?
Suppose bank.com generates:
<input type="hidden"
       name="_csrf"
       value="X7kP91Qz">
or returns:
{
  "csrfToken": "X7kP91Qz"
}
For a valid request, bank expects:
POST /transfer

Cookie: JSESSIONID=abc123
X-CSRF-Token: X7kP91Qz

Why can't evil.com send the token?
Because the attacker doesn't know:
X7kP91Qz
To know it, they'd need to read a page from:
https://bank.com
But Same-Origin Policy and CORS prevent that.
For example:
fetch("https://bank.com/profile")
may send the request,
but the browser won't allow evil.com to read the response.
So the attacker cannot extract:
<input value="X7kP91Qz">
or
{
  "csrfToken": "X7kP91Qz"
}
from the bank's pages.

The important distinction
Session Cookie
Automatically attached by browser:
Cookie: JSESSIONID=abc123
Attacker doesn't know its value, but doesn't need to.

CSRF Token
Not automatically attached by browser.
Must be explicitly included:
X-CSRF-Token: X7kP91Qz
Attacker needs to know the value.
But browser prevents them from reading it.

Analogy
Imagine your office building.
Session cookie = employee badge
When you walk through a door:
Browser automatically presents badge
The attacker can trick you into walking to a door.

CSRF token = secret daily password
The guard asks:
Show your badge.
Tell me today's password.
You have the badge automatically.
But the attacker doesn't know today's password.
So they can force you to approach the guard, but they can't make you provide the correct password.

One more thing: HttpOnly
Most session cookies are also marked:
Set-Cookie: JSESSIONID=abc123; HttpOnly
This means:
document.cookie
cannot even read the session cookie on bank.com itself.
So in modern applications:
Evil site cannot read JSESSIONID.
Evil site cannot read CSRF token.
Browser automatically sends JSESSIONID.
Browser does not automatically send CSRF token.
That asymmetry is exactly what CSRF protection relies on.

http

Excellent question.
You have discovered the "first request problem" of HSTS.

The Problem
Suppose a user has never visited:
https://bank.com
before.
They type:
http://bank.com
Browser sends:
GET /
Host: bank.com
over plain HTTP.
At this moment:
Browser has never seen HSTS header.
So it doesn't know that HTTPS is required.

What normally happens
Server responds:
301 Moved Permanently
Location: https://bank.com
Browser then goes:
http://bank.com
      ↓
redirect
      ↓
https://bank.com
After reaching HTTPS, server sends:
Strict-Transport-Security:
max-age=31536000
Browser stores:
bank.com => HTTPS only for 1 year
Future requests are safe.

Where is the danger?
The danger exists before HSTS has been learned.
Imagine you're on public Wi-Fi.
An attacker sits between you and the server.
When you send:
http://bank.com
attacker intercepts.
Instead of forwarding:
301 -> https://bank.com
they return:
200 OK
with a fake page.
Or they modify links so you stay on HTTP.
This is the classic:
SSL Stripping Attack
The attacker prevents you from ever reaching HTTPS.

So does HSTS fail for first-time visitors?
By itself:
Yes, partially.
HSTS protects:
Second visit onward
because the browser has already learned the rule.
It cannot fully protect the very first visit.

The Solution: HSTS Preload
Modern browsers ship with a built-in list:
Chrome
Firefox
Safari
Edge
contain thousands of domains that are known to require HTTPS.
Examples:
google.com
github.com
paypal.com
are preloaded.
Browser already knows:
github.com => HTTPS only
before any request is made.

What happens then?
User types:
http://github.com
Browser checks preload list:
github.com is HSTS-preloaded
Browser immediately converts:
https://github.com
No HTTP request is ever sent.
No opportunity for SSL stripping.

Visual Comparison
Without HSTS
User
 ↓
HTTP
 ↓
Attacker can intercept

HSTS Learned Previously
User
 ↓
Browser upgrades to HTTPS
 ↓
Secure

HSTS Preload
User
 ↓
Browser already knows HTTPS only
 ↓
HTTPS immediately
No insecure first request.

Real-World Practice
For production systems:
Redirect HTTP → HTTPS.
Enable HSTS.
Submit domain to HSTS preload list.
Typical header:
Strict-Transport-Security:
max-age=31536000;
includeSubDomains;
preload
Then the domain can be added to the browser preload lists.

Interview Answer
If asked:
What happens on the very first HTTP request before HSTS is known?
Answer:
HSTS alone cannot protect the first visit because the browser has not yet learned the HSTS policy. An attacker could perform an SSL stripping attack during that initial HTTP request. To solve this, browsers maintain an HSTS preload list of domains that should always be contacted over HTTPS, eliminating the insecure first request.

how do the browsers prevent this first time http, since all the websites of the world can not be cached

Question 1:
How do browsers prevent the first-time HTTP problem if they can't preload every website?
They don't.
This is an important reality.
A browser cannot know in advance that every website on Earth requires HTTPS.
For a completely new domain:
new-startup-xyz.com
the browser has only two possibilities:
Try HTTP first.
Try HTTPS first.
Historically, browsers allowed HTTP because much of the web used HTTP.

Modern browsers have improved this
Today, browsers increasingly use HTTPS-First Mode or HTTPS-Only Mode.
For example:
User types:
example.com
Browser often tries:
https://example.com
first.
If HTTPS works:
Stay on HTTPS
If HTTPS fails:
May fall back to HTTP
(depending on browser settings).
So modern browsers reduce the risk significantly.

HSTS Preload
For important domains:
google.com
github.com
paypal.com
amazon.com
browser vendors ship a built-in list.
These domains are known beforehand to require HTTPS.
So:
http://github.com
becomes:
https://github.com
before any network request.

For unknown domains
There is no magic.
The browser cannot preload:
billions of current and future domains
So the first-visit problem still exists in theory.
The web's defense is a combination of:
HTTPS by default
HSTS
HSTS preload
HTTPS-First browser modes
rather than a perfect solution.

Question 2:
How can the first HTTP request be exploited?
Let's walk through a real attack.

Scenario
You're in an airport.
You connect to:
Free Airport WiFi
Attacker is on the same network.
You type:
http://bank.com

Normal flow
Without attacker:
Browser
   ↓ HTTP
bank.com

bank.com
   ↓
301 Redirect

https://bank.com
Everything becomes secure.

Attacker in the middle
The attacker intercepts traffic.
Instead of forwarding the redirect:
301 Location: https://bank.com
they send:
200 OK
with their own content.

What the user sees
The page may look identical:
BANK LOGIN
Username
Password
User thinks:
Looks normal
and logs in.

What attacker gets
Username
Password
immediately.
This is essentially a phishing page delivered through network interception.

SSL Stripping
A more sophisticated attack.
Suppose bank.com really supports HTTPS.
Attacker sits in the middle:
You
 ↓ HTTP
Attacker
 ↓ HTTPS
Bank
The attacker creates two connections:
Attacker ↔ Bank
HTTPS
You ↔ Attacker
HTTP
You believe you're talking to the bank.
The bank believes it's talking to you.
In reality:
You ←→ Attacker ←→ Bank

What can attacker see?
Everything sent over HTTP:
Usernames
Passwords
Session IDs
Form data
because the browser never reached HTTPS.

Why can't they do this after HSTS?
Suppose you've already visited the site once and received:
Strict-Transport-Security:
max-age=31536000
Now browser remembers:
bank.com must ALWAYS use HTTPS
Next time:
http://bank.com
is rewritten locally to:
https://bank.com
before any network traffic.
The attacker never gets an HTTP request to intercept.

Can attacker read HTTPS traffic?
Normally:
No
HTTPS uses TLS.
Without the server's private key (and other compromises), the attacker sees encrypted bytes.
They cannot read:
Passwords
JWTs
Cookies
Account data

The key takeaway
The first-visit problem exists because:
Browser has not yet learned:
"This domain requires HTTPS."
An attacker on the network can exploit that by intercepting or modifying the initial HTTP traffic, performing SSL stripping, or serving a fake page.
That's why modern security guidance is:
Use HTTPS everywhere.
Enable HSTS.
Submit to the HSTS preload list.
Rely on browsers' HTTPS-first behavior.
Those layers together make first-visit attacks much harder in practice.
