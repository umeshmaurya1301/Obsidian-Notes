This is one of the most important Spring Security topics because everything in Spring Security is built around filters.
First Understand: What is a Filter?
A filter is a component that executes before the request reaches the DispatcherServlet.
Normal Spring Boot flow:
Request
   |
   v
Tomcat
   |
   v
DispatcherServlet
   |
   v
Controller
With Spring Security:
Request
   |
   v
Tomcat
   |
   v
Security Filters
   |
   v
DispatcherServlet
   |
   v
Controller
Every incoming request passes through a chain of filters.

Why Filters?
Because security concerns need to happen before the controller executes.
Examples:
Is the user authenticated?
Is JWT valid?
Does the user have permission?
Is this request CSRF safe?
Is the session expired?
All these checks happen before your controller method runs.

What is SecurityFilterChain?
A SecurityFilterChain is simply:
Filter1
   ->
Filter2
   ->
Filter3
   ->
Filter4
Spring Security bundles many filters together into a chain.
Example:
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http)
        throws Exception {

    http
        .authorizeHttpRequests(auth -> auth
                .anyRequest().authenticated()
        )
        .httpBasic();

    return http.build();
}
When Spring sees:
http.build()
it creates a SecurityFilterChain containing many security filters.

Real Request Flow
Suppose:
GET /api/users
Request arrives:
Request
   |
   v
Filter A
   |
   v
Filter B
   |
   v
Filter C
   |
   v
Controller
Each filter decides:
doFilter(request, response, chain)
Either:
Continue
chain.doFilter(request, response);
or
Stop
response.sendError(401);
If a filter stops the chain:
Request
   |
Filter A
   |
Filter B
   |
401
Controller never executes.

How Does Spring Know Filter Order?
Every filter has a predefined order.
Internally Spring maintains:
1. SecurityContextHolderFilter
2. LogoutFilter
3. UsernamePasswordAuthenticationFilter
4. BearerTokenAuthenticationFilter
5. AnonymousAuthenticationFilter
6. ExceptionTranslationFilter
7. AuthorizationFilter
(actual chain is longer)
Order is critical.
Example:
Bad order:
AuthorizationFilter
     |
JWT Filter
Authorization runs before authentication.
Result:
403
for every request.
Correct order:
JWT Filter
    |
AuthorizationFilter
Authentication first, authorization later.

}

        jwtAuthenticationFilter,
        UsernamePasswordAuthenticationFilter.class

      |

Spring inserts your filter at the correct position.

Because:

   |

   |

   |

Most APIs don't use form login.
JWT should authenticate user before authorization checks.

Part 1: BCryptPasswordEncoder
Why do we hash passwords?
Suppose a user registers:
password = secret123
Never store:
id | email            | password
1  | umesh@gmail.com  | secret123
If the database is leaked, every password is exposed.
Instead:
id | email            | password
1  | umesh@gmail.com  | $2a$10$...
Store a hash.

What is a Hash?
A hash function converts:
secret123
into:
abcxyz123...
Properties:
One-way
You can do:
secret123
    ->
hash
But not:
hash
    ->
secret123

Same Input → Same Output
secret123
always becomes the same hash.
This creates a problem.
Suppose two users have:
password = password123
Both hashes become identical.
Attackers can exploit this using precomputed tables.

What is Salt?
A salt is a random value added before hashing.
Example:
password = secret123

salt = x7d9k2
Combined:
secret123x7d9k2
Then hashed.
Another user:
password = secret123

salt = p9m4z1
Produces a completely different hash.
So:
secret123
may generate:
$2a$10$ABC...
and
$2a$10$XYZ...
even though the original password is identical.

Why BCrypt?
Old algorithms:
MD5
SHA1
SHA256
are very fast.
Fast hashing is bad for passwords.
Attackers can try billions of passwords per second.

BCrypt is intentionally slow.
Example:
new BCryptPasswordEncoder(10);
The 10 is the cost factor.
BCrypt repeatedly hashes the password.
Higher cost:
10 -> slower
12 -> slower
14 -> even slower
This makes brute-force attacks expensive.

What's Stored in BCrypt Hash?
Example:
$2a$10$N9qo8uLOickgx2ZMRZoMye...
Contains:
Algorithm
Cost Factor
Salt
Hash
All inside one string.
That's why Spring only stores:
$2a$10$N9qo8uLOickgx2ZMRZoMye...
No separate salt column is needed.

Registration Flow
User enters:
secret123
Code:
String hash =
    passwordEncoder.encode("secret123");
Result:
$2a$10$ABCD...
Store in DB.

Login Flow
User enters:
secret123
Database:
$2a$10$ABCD...
Spring does:
passwordEncoder.matches(
    "secret123",
    "$2a$10$ABCD..."
);
Internally:
Extract salt from stored hash
Hash incoming password again
Compare results
If same:
Authentication Success

Common Interview Question
Why can't we do this?
encode(rawPassword)
    .equals(storedHash)
Because BCrypt generates a new random salt every time.
Example:
encode("secret123")
Result 1:
$2a$10$AAA...
Result 2:
$2a$10$BBB...
Different hashes.
Therefore:
matches()
must be used.

Excellent questions. These are exactly the kinds of things that help you understand how BCrypt really works.
Question 1: If salt is random, how can login work later?
You're thinking:
Registration:
Password = 1234
Salt = ABC
Hash = XYZ
Later:
Login:
Password = 1234
Salt = ???
If a different salt is used:
Salt = PQR
then:
hash(1234 + PQR)
will be different from:
hash(1234 + ABC)
So how does BCrypt know the original salt?
Answer
BCrypt stores the salt inside the hash string itself.
Example:
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
This string contains:
Algorithm = 2a
Cost = 10
Salt = N9qo8uLOickgx2ZMRZoMye
Hash = remaining part
So the database stores:
password_hash =
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
not just the hash.

During login
User enters:
1234
Spring executes:
passwordEncoder.matches(
    "1234",
    storedHash
);
Internally BCrypt:
Reads the stored hash
Extracts the original salt
Extracts the original cost factor
Re-hashes the entered password using those values
Compares the result
Conceptually:
stored hash
     |
     +--> extract salt = ABC
     +--> extract cost = 10
     |
recalculate hash(1234 + ABC)
     |
compare
So the salt is random per user, but it is not lost.

Example
Two users choose the same password:
Password = 1234
User 1:
Salt = ABC
Hash = HASH1
User 2:
Salt = XYZ
Hash = HASH2
Database:
User1 -> $2a$10$ABC...
User2 -> $2a$10$XYZ...
Both can still log in because BCrypt retrieves the correct salt from each stored hash.

Question 2: What if the cost factor changes from 10 to 12?
Suppose initially:
new BCryptPasswordEncoder(10);
User registers.
Stored hash:
$2a$10$...
Notice:
10
is embedded in the hash.
Later you deploy:
new BCryptPasswordEncoder(12);
Will old passwords stop working?
Answer: No
Because BCrypt also stores the cost factor inside the hash.
During login:
passwordEncoder.matches(
    rawPassword,
    storedHash
);
BCrypt reads:
stored hash:
$2a$10$...
      ^^
and sees:
cost = 10
Then it uses cost 10 for verification.
So old users still authenticate successfully.

Example
Database contains:
$2a$10$ABC...
Application now uses:
new BCryptPasswordEncoder(12);
User logs in.
BCrypt sees:
stored hash says cost=10
and verifies using 10.
Login succeeds.

Then how do users get upgraded to cost 12?
Very common production strategy:
Old user logs in
Stored hash:
$2a$10$...
Application target:
cost=12
After successful login:
if (passwordEncoder.upgradeEncoding(storedHash)) {
    // re-hash password with stronger settings
}
Then store:
$2a$12$...
Now the user has been migrated automatically.
No password reset needed.

Same logic for algorithm changes
Suppose you move from:
BCrypt
to
Argon2
You generally don't invalidate everyone.
Typical flow:
User logs in with BCrypt hash
Verify using BCrypt
Re-hash password with Argon2
Save new hash
This is called password hash migration.

Mental Model
Think of a BCrypt hash as:
[algorithm][cost][salt][hash]
Something like:
BCrypt | 10 | ABC123 | encrypted-result
all packed into one string.
That's why BCrypt can still verify passwords years later even if:
the salt was random
the cost factor changed
new users are using stronger settings
because the information needed to verify the old password travels with the stored hash itself.

This is one of the most misunderstood Spring Security topics.

hasAuthority()
Checks exact authority string.
Example:
.hasAuthority("ROLE_ADMIN")
Spring checks:
Authentication
      |
      +--> Authorities
              ROLE_ADMIN
Exact match.

Another example:
.hasAuthority("READ_REPORTS")
Checks:
READ_REPORTS
exactly.
No modification.

hasRole()
This is actually a convenience wrapper.
When you write:
.hasRole("ADMIN")
Spring internally converts it to:
.hasAuthority("ROLE_ADMIN")
Notice:
ROLE_
is automatically added.

Internally it behaves roughly like:
hasAuthority(
    "ROLE_" + role
);

ROLE_ADMIN

Spring checks:
ROLE_ADMIN
Result:
Allowed
Same result.

Case 3
.hasAuthority("READ_REPORTS")
Spring checks:
READ_REPORTS
Result:
Allowed

Case 4
.hasRole("READ_REPORTS")
Spring checks:
ROLE_READ_REPORTS
Result:
Denied
because your authority is:
READ_REPORTS
not:
ROLE_READ_REPORTS

Refresh Token = 90 days

   |
New Access Token

If an attacker steals the refresh token:
Attacker
    |
Refresh Token
    |
Authorization Server
    |
Unlimited New Access Tokens
Potentially for months.
That's why refresh tokens require stronger protection.

Can a Provider Keep Access Forever?
Not necessarily.
The Authorization Server decides:

Examples:

Keycloak -> configurable
Okta -> configurable
Auth0 -> configurable
Common settings:
Access Token: 15 minutes
Refresh Token: 30 days
After 30 days:
Refresh Token Expired
User must log in again.

How Is Access Revoked?
OAuth provides several mechanisms.

1. Refresh Token Expiry
Most common.
Example:
Access Token: 15 min
Refresh Token: 30 days
After 30 days:
Refresh denied
User re-authenticates.

2. User Revokes Consent
Example:
User goes to:
Google Account
  -> Security
  -> Third-party apps
and removes:
Travel App
Google invalidates:
Access Tokens
Refresh Tokens
for that application.
The next refresh request fails.

3. Logout
Depending on the provider.
Example:
Logout
   |
Invalidate Refresh Token
Future refresh attempts fail.

Modern providers often use:

Use Refresh Token A
      |
      v
Get Access Token
Get Refresh Token B
      |
Invalidate A
Now:
A = invalid
B = valid

Why?
Suppose attacker steals:

and the real user already exchanged it.
When attacker tries:
Refresh Token A
again:
Invalid Token
Provider detects possible theft.
This significantly reduces risk.

Preferred:
HttpOnly Secure Cookie
Avoid:
