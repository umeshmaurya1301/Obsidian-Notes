Don't learn OAuth2 as "some Spring Security configuration". Learn it as a **distributed authorization protocol** — the config is three lines once the protocol makes sense.

> [!info] 🧭 Summary
> - **OAuth2 = an authorization *protocol*. JWT = a token *format*.** OAuth2 often issues JWTs but doesn't have to (opaque tokens are equally valid).
> - The problem it solves: let App A access your data on Service B **without giving App A your password**, with limited scope and revocable access.
> - **Four actors**: Resource Owner (the user) · Client (the app) · Authorization Server (issues tokens) · Resource Server (holds the data, your API).
> - The flow that matters: **Authorization Code Flow** — user authenticates at the auth server, client gets a short-lived **authorization code**, then exchanges it server-side (with the client secret) for tokens. **PKCE** is now required for public clients (SPAs, mobile).
> - The code is exchanged **on the back channel** so the token never travels through the browser URL. That's the entire security argument for the extra hop.
> - **Access token** = short-lived (minutes), sent to APIs. **Refresh token** = long-lived (days/months), only ever sent to the auth server ([[9. Refresh Tokens and Token Security]]).
> - **Scopes** are what the user consented to (`calendar.read`), and Spring maps them to authorities as **`SCOPE_*`**.
> - **OAuth2 ≠ login.** **OIDC** is the identity layer on top: it adds an **`id_token`** (a JWT about *who the user is*) and the `openid` scope. "Login with Google" is OIDC.
> - Two Spring roles, often confused: **`oauth2Login()`** = *my app lets users sign in with Google*. **`oauth2ResourceServer()`** = *my API validates tokens someone else issued*. Backend services almost always want the second.
> - As a resource server you do **no login, no password check, no `UserDetailsService`** — only token validation, with the public key fetched from the issuer's **JWKS** endpoint.
>
> Previous: [[7. JWT Authentication]] · Next: [[9. Refresh Tokens and Token Security]]

## 1. Why OAuth exists

It's 2010. You're building a travel app that needs the user's Google Calendar.

The naive approach:

```text
User gives the travel app their Google password
      |
Travel app stores it
      |
Travel app logs into Google as the user
```

Everything about this is wrong:

- The app knows the user's **Google password** — and so does its database, and its logs.
- **No way to limit** access: it can read Gmail, delete Drive files, anything.
- **No way to revoke** without changing the password (which breaks every other app doing the same thing).
- **MFA is bypassed** entirely.

OAuth2's one-sentence purpose:

> **A user grants a third-party application limited, revocable access to their data without sharing their credentials.**

---

## 2. The four actors

| Actor | Who | Example |
|---|---|---|
| **Resource Owner** | The user who owns the data | Umesh |
| **Client** | The app requesting access | Travel App |
| **Authorization Server** | Authenticates the user, issues tokens | Google, Keycloak, Okta, Auth0, Cognito |
| **Resource Server** | Hosts the protected data | Google Calendar API — or **your Spring Boot API** |

```text
+----------------+
|      User      |   Resource Owner
+----------------+
        |
        v
+----------------+
|   Travel App   |   Client
+----------------+
        |
        v
+----------------+
|  Google Auth   |   Authorization Server
+----------------+
        |
        v
+----------------+
|  Calendar API  |   Resource Server
+----------------+
```

In a typical enterprise setup **you write the Resource Server** and Keycloak/Okta is the Authorization Server. Recognising which box you're in is half of OAuth2.

Clients come in two kinds, and the distinction drives the flow:

- **Confidential client** — a backend that can keep a `client_secret` (your Spring Boot server).
- **Public client** — an SPA or mobile app that *cannot* keep a secret (anything shipped to a device is readable). Public clients must use **PKCE** and never hold a client secret.

---

## 3. Authorization Code Flow

The flow behind "Login with Google/GitHub/Microsoft", and the only one you should default to.

**Step 1 — user clicks "Login with Google".** The client redirects the browser to the authorization server:

```text
GET https://accounts.google.com/o/oauth2/v2/auth
      ?response_type=code
      &client_id=travel-app
      &redirect_uri=https://travelapp.com/callback
      &scope=openid%20profile%20calendar.read
      &state=xyz789
      &code_challenge=<SHA256(verifier)>
      &code_challenge_method=S256
```

**Step 2 — the user authenticates *at Google*.** Email, password, MFA. The travel app never sees any of it — that's the point.

**Step 3 — consent screen.**

```text
Travel App wants to:
    Read your calendar
    Read your profile
[Allow]  [Deny]
```

**Step 4 — redirect back with a code.**

```text
GET https://travelapp.com/callback?code=abc123xyz&state=xyz789
```

This is **not** a token. It's a one-time value, valid for ~30–60 seconds, useless on its own.

**Step 5 — back-channel exchange** (server to server, the browser is not involved):

```text
POST https://oauth2.googleapis.com/token

grant_type=authorization_code
&code=abc123xyz
&client_id=travel-app
&client_secret=***           (confidential clients)
&code_verifier=***           (PKCE)
&redirect_uri=https://travelapp.com/callback
```

**Step 6 — tokens come back:**

```json
{
  "access_token": "eyJhb...",
  "refresh_token": "def456...",
  "id_token": "eyJhb...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "openid profile calendar.read"
}
```

**Step 7 — call the resource server:**

```text
GET https://www.googleapis.com/calendar/v3/events
Authorization: Bearer eyJhb...
```

### The whole thing

```text
User
 | click "Login with Google"
 v
Client  --------------------------->  Authorization Server
 |         redirect (front channel)          | user authenticates + consents
 |                                           |
 |  <---------- authorization code ----------+
 v
Client Backend  ---- code + secret ------->  Authorization Server
 |                  (back channel)                 |
 |  <-------------- access + refresh + id token ---+
 v
Client  ---- Authorization: Bearer ---->  Resource Server
```

### Why the extra hop? Why not return the token directly?

Because the redirect in step 4 goes **through the browser** — it lands in the URL bar, browser history, `Referer` headers and proxy logs. An authorization code sitting there is nearly harmless: it's single-use, expires in seconds, and cannot be redeemed without the client secret or PKCE verifier. An access token sitting there is a full compromise.

That's exactly why the old **Implicit flow** (token straight in the redirect fragment) is **deprecated** — SPAs now use Authorization Code + PKCE.

> [!tip] Two parameters that are pure security
> - **`state`** — a random value the client generates and checks on the callback. Defends against **CSRF on the redirect** (an attacker tricking your browser into completing *their* login).
> - **PKCE** (`code_verifier` / `code_challenge`) — the client generates a random verifier, sends its SHA-256 as the challenge, and reveals the verifier only at exchange time. So a **stolen authorization code is useless** without the verifier. Originally for mobile, now recommended for **all** clients.

### The other grant types, briefly

| Grant | Use | Status |
|---|---|---|
| **Authorization Code (+PKCE)** | Web apps, SPAs, mobile | ✅ The default |
| **Client Credentials** | Machine-to-machine, no user involved — service A calling service B | ✅ Correct for backend jobs |
| **Refresh Token** | Get a new access token | ✅ |
| Resource Owner Password | Client collects the username/password directly | ⚠️ Deprecated — defeats the purpose |
| Implicit | Token in the redirect fragment | ❌ Deprecated |
| Device Code | TVs, CLIs, input-constrained devices | ✅ Niche but real |

## 4. Scopes

OAuth doesn't just say "allowed" — it says **allowed for what**.

```text
calendar.read
calendar.write
profile.read
email.read
```

The user can consent to `calendar.read` and refuse `calendar.write`; the issued token carries only what was granted. Scopes are the mechanism behind the *limited access* promise.

In Spring, scopes become authorities with a `SCOPE_` prefix:

```text
scope: "calendar.read"   ->   authority: SCOPE_calendar.read
```

```java
.requestMatchers(HttpMethod.GET, "/calendar/**").hasAuthority("SCOPE_calendar.read")
```

> [!warning] Scopes are not roles
> A scope is *what the client app was permitted to do on the user's behalf* — a delegation limit. A role is *what the user is*. A token can carry `calendar.write` scope while the user still lacks the role to perform the action. Check both: scope for delegation, role/permission for the user's own rights.

## 5. OAuth2 vs OIDC — authorization vs identity

OAuth2 was designed for **delegated authorization** ("this app may read your calendar"). It says nothing about *who the user is*. People bolted login onto it anyway, badly and inconsistently.

**OpenID Connect (OIDC)** is the standard identity layer on top of OAuth2:

| | OAuth2 | OIDC |
|---|---|---|
| Answers | "May this app do X?" | "Who is this user?" |
| Adds | — | **`id_token`** (always a JWT), `openid` scope, `/userinfo`, discovery |
| For | API access delegation | **Login / SSO** |

The `id_token` is a JWT with identity claims, intended for the **client**, not for API calls:

```json
{
  "iss": "https://accounts.google.com",
  "sub": "10769150350006150715113082367",
  "aud": "travel-app",
  "email": "umesh@gmail.com",
  "name": "Umesh Maurya",
  "exp": 1735203600
}
```

> [!warning] Don't send the `id_token` to APIs
> `id_token` = identity, for the client. `access_token` = authorization, for resource servers. Sending the id_token as a bearer token to an API is a common and wrong pattern — its `aud` is the client, not the API.

"Login with Google" is **OIDC**, not plain OAuth2. Keycloak, Okta, Auth0 and Cognito are all OIDC providers.

## 6. Spring's two OAuth2 roles

The distinction that trips people up.

### `oauth2Login()` — *my app is the Client*

Users sign into **your** app using Google/GitHub:

```java
http.oauth2Login(Customizer.withDefaults());
```

```yaml
spring:
  security:
    oauth2:
      client:
        registration:
          google:
            client-id: ...
            client-secret: ...
            scope: openid, profile, email
```

Spring runs the whole Authorization Code + PKCE dance, then creates a session with an `OAuth2User` / `OidcUser` principal. Typical for server-rendered apps and internal tools.

### `oauth2ResourceServer()` — *my API is the Resource Server*

Someone else already authenticated the user; your API only validates the token:

```java
http.oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));
```

```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://keycloak.mycompany.com/realms/prod
```

```text
Request with Bearer token
    |
BearerTokenAuthenticationFilter
    |
Validate signature (JWKS), exp, iss, aud
    |
JwtAuthenticationConverter -> Authentication (principal = Jwt, authorities = SCOPE_*)
    |
SecurityContextHolder
    |
AuthorizationFilter -> Controller
```

Notice what's **absent**: no login page, no password check, no `UserDetailsService`, no session. Authentication already happened somewhere else; you're verifying a signed assertion about it.

That single `issuer-uri` line makes Spring fetch `/.well-known/openid-configuration`, discover the JWKS endpoint, cache the public keys, handle key rotation, and validate `iss` and `exp` — all the parts a hand-written JWT filter gets subtly wrong ([[7. JWT Authentication]]).

## 7. JWT validation via JWKS

```text
Auth Server                            Resource Server (your API)
    |                                          |
 private key signs the token                   |
    |                                          |
    |  <---- GET /.well-known/jwks.json -------+   (once, then cached)
    |  ----- { "keys": [ { "kid": "abc", "n": ..., "e": ... } ] } -->
                                               |
                                       verify signature with the
                                       public key whose kid matches
                                       the token header
```

Key points for an interview:

- The token header carries a **`kid`** so the verifier picks the right key when several are published.
- Keys are **cached** and refetched on a cache miss — that's how **rotation** works with no downtime: the auth server publishes the new key alongside the old, signs with the new, retires the old later.
- The resource server needs **no shared secret** and **cannot mint tokens** — only verify. That's the property that makes this safe across dozens of services.

### Opaque tokens

Not all access tokens are JWTs. An opaque token is a random string with no readable content, and the resource server validates it by asking the auth server:

```java
http.oauth2ResourceServer(o -> o.opaqueToken(Customizer.withDefaults()));
```

That's **token introspection** (RFC 7662): a network call per request (usually cached), in exchange for **instant revocation** — the auth server is the live source of truth. The classic trade-off again:

| | JWT | Opaque + introspection |
|---|---|---|
| Validation | Local, offline | Network call to the auth server |
| Latency | ~0 | One hop (cacheable) |
| Revocation | Only at expiry | **Immediate** |
| Auth server load | None | Per request |

## 8. Mapping claims to authorities

By default Spring maps the `scope`/`scp` claim to `SCOPE_*`. Providers like Keycloak put roles elsewhere, so you convert:

```java
@Bean
JwtAuthenticationConverter jwtAuthenticationConverter() {
    JwtGrantedAuthoritiesConverter scopes = new JwtGrantedAuthoritiesConverter();

    JwtAuthenticationConverter converter = new JwtAuthenticationConverter();
    converter.setJwtGrantedAuthoritiesConverter(jwt -> {
        Collection<GrantedAuthority> authorities = new ArrayList<>(scopes.convert(jwt));

        // Keycloak: realm_access.roles = ["admin", "user"]
        Map<String, Object> realmAccess = jwt.getClaim("realm_access");
        if (realmAccess != null) {
            ((List<String>) realmAccess.get("roles")).stream()
                    .map(r -> new SimpleGrantedAuthority("ROLE_" + r.toUpperCase()))
                    .forEach(authorities::add);
        }
        return authorities;
    });
    return converter;
}
```

Now `hasRole("ADMIN")` works exactly as in [[6. Authorization]] — the roles just arrived via a token instead of a database.

## 9. OAuth2 in microservices

```text
Frontend
    |  login (Authorization Code + PKCE)
    v
Keycloak  ---- access token (JWT, RS256) ---->  Frontend
    |
Frontend  ---- Authorization: Bearer ---->  API Gateway
                                              |
                                    validates the token once
                                              |
                        +---------------------+---------------------+
                        v                                           v
                 Order Service                              Payment Service
             (oauth2ResourceServer)                     (oauth2ResourceServer)
```

Each service:

- **does not authenticate users** — Keycloak already did;
- **verifies the token** locally against the cached JWKS;
- reads `roles`, `scopes`, tenant claims for authorization.

For service-to-service calls with no user involved, use the **Client Credentials** grant: the service gets its own token with its own identity and scopes. Don't just forward the user's token everywhere — that quietly grants downstream services the user's full authority (though token *exchange*, RFC 8693, exists for when you deliberately want a narrowed on-behalf-of token).

## ❓ Interview Questions

### Q1. OAuth2 vs JWT?

OAuth2 is an authorization protocol describing how tokens are obtained and used. JWT is a self-contained token format. OAuth2 commonly issues JWTs but can equally issue opaque tokens.

### Q2. Name the four OAuth2 roles.

Resource Owner (user), Client (app), Authorization Server (issues tokens), Resource Server (hosts protected data).

### Q3. Walk through the Authorization Code flow.

Client redirects the user to the auth server → user authenticates and consents → auth server redirects back with a short-lived code → client backend exchanges code + client secret (+ PKCE verifier) for tokens on the back channel → client calls the resource server with the access token.

### Q4. Why an authorization code instead of returning the token directly?

The redirect passes through the browser (URL bar, history, logs). A single-use, seconds-long code is nearly harmless there and can't be redeemed without the client secret or PKCE verifier. This is why Implicit flow is deprecated.

### Q5. What is PKCE and why is it needed?

`code_verifier`/`code_challenge`: the client proves at exchange time that it initiated the request, so a stolen authorization code is useless. Essential for public clients that can't hold a secret; now recommended for all.

### Q6. What does `state` protect against?

CSRF on the OAuth redirect — the client generates it, checks it on the callback, and rejects mismatches.

### Q7. OAuth2 vs OIDC?

OAuth2 = delegated authorization ("this app may read your calendar"). OIDC = an identity layer adding the `id_token`, the `openid` scope, `/userinfo` and discovery. "Login with Google" is OIDC.

### Q8. `oauth2Login()` vs `oauth2ResourceServer()`?

`oauth2Login()` makes your app the *client* — users sign in via Google/Keycloak. `oauth2ResourceServer()` makes your app the *resource server* — it only validates tokens issued elsewhere. Backend APIs use the latter.

### Q9. How does a resource server verify a JWT it didn't issue?

It fetches the issuer's public keys from the JWKS endpoint (discovered from `issuer-uri`), matches the token's `kid`, verifies the RS256 signature, and checks `exp`, `iss` and `aud`. Keys are cached and refetched on rotation.

### Q10. JWT vs opaque tokens?

JWT: local, offline validation, no auth-server load, but revocation only at expiry. Opaque: introspection call per request (cacheable), auth-server load, but instant revocation. Pick by whether revocation latency or request latency matters more.

### Q11. How do scopes become Spring authorities?

`JwtAuthenticationConverter` maps the `scope`/`scp` claim to `SCOPE_*` authorities; custom claims (e.g. Keycloak's `realm_access.roles`) are mapped to `ROLE_*` with a custom converter.

---

> [!tip] ⚡ Quick Recall
> - **OAuth2 = protocol. JWT = token format.** OAuth2 may issue JWTs *or* opaque tokens.
> - Purpose: **limited, revocable, credential-free delegation**.
> - Four actors: **Resource Owner · Client · Authorization Server · Resource Server**.
> - **Authorization Code Flow**: redirect → authenticate + consent → **code** → back-channel exchange → **access + refresh (+ id) token** → `Bearer` to the API.
> - The code goes through the browser; the **token never does**. Implicit flow is dead; **PKCE** everywhere; **`state`** stops redirect CSRF.
> - **Scopes** = what the user consented to → Spring authorities **`SCOPE_*`**. Scope ≠ role.
> - **OIDC** = OAuth2 + identity: **`id_token`**, `openid` scope. "Login with Google" is OIDC. Never send the `id_token` to APIs.
> - **`oauth2Login()`** = I'm the client. **`oauth2ResourceServer()`** = I validate someone else's tokens (no login, no password, no `UserDetailsService`).
> - `issuer-uri` → discovery → **JWKS** → cached public keys, `kid` matching, painless rotation.
> - **Client Credentials** for machine-to-machine; **introspection** when instant revocation beats latency.
