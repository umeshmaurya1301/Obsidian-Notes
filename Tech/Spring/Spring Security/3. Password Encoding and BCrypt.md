`PasswordEncoder` is two methods, but interviewers dig here because it reveals whether you understand hashing, salting and migration — or just copied a `@Bean` from a tutorial.

> [!info] 🧭 Summary
> - **Never store raw passwords.** Store a **hash**: one-way, `password → hash` is easy, `hash → password` is not.
> - Plain hashing isn't enough: the same password always gives the same hash → **rainbow tables**. Fix = **salt**, a random value mixed in before hashing, unique per user.
> - **BCrypt is deliberately slow** (unlike MD5/SHA-256, which are fast and therefore *bad* for passwords). The **cost factor** controls how slow: cost 12 ≈ 2× the work of 11.
> - A BCrypt hash is a **self-describing string**: `$2a$10$<22-char salt><31-char hash>` — algorithm, cost, salt and hash all in one column. **No separate salt column needed.**
> - That's why a random salt still works at login: `matches()` **extracts the salt and cost from the stored hash** and re-hashes with them.
> - That's also why **raising the cost doesn't break old passwords** — the old hash carries its own cost of 10 and is verified with 10.
> - `encode(raw).equals(storedHash)` is **always false** (new random salt each time). Only **`matches(raw, storedHash)`** works.
> - Upgrade old hashes silently on successful login via **`upgradeEncoding()`** — re-hash and save. Same trick migrates BCrypt → Argon2.
> - Spring Boot's default is **`DelegatingPasswordEncoder`**: hashes are prefixed `{bcrypt}`, `{argon2}`, … so multiple algorithms can coexist in one column.
>

## 1. Why hash at all?

A user registers with `secret123`. If you store:

```text
id | email            | password
1  | umesh@gmail.com  | secret123
```

then the day the database leaks — a dump, a backup on an open S3 bucket, a SQL injection — **every** password is exposed. And since people reuse passwords, you've also compromised their email and banking accounts.

Store a hash instead:

```text
id | email            | password
1  | umesh@gmail.com  | $2a$10$N9qo8uLOickgx2ZMRZoMye...
```

### What is a hash?

A one-way function:

```text
secret123  --hash-->  abcxyz123...      easy
abcxyz123  --??-->    secret123         infeasible
```

**Hashing is not encryption.** Encryption is reversible with a key; hashing is not reversible at all. That's exactly what you want for passwords — you never need to *read* a password back, only to check whether a submitted one matches.

---

## 2. The problem with plain hashing: no salt

The same input always produces the same output.

```text
User A:  password123  ->  ef92b778...
User B:  password123  ->  ef92b778...     identical!
```

Two consequences:

1. **Rainbow tables** — attackers precompute hashes for billions of common passwords. Look up `ef92b778...`, get `password123` instantly.
2. **Leak amplification** — identical hashes in the dump reveal which users share a password. Crack one, crack them all.

---

## 3. Salt

A **salt** is a random value mixed with the password before hashing.

```text
User A:   password = secret123   salt = x7d9k2   ->  hash("secret123" + "x7d9k2")  ->  $2a$10$ABC...
User B:   password = secret123   salt = p9m4z1   ->  hash("secret123" + "p9m4z1")  ->  $2a$10$XYZ...
```

Same password, **completely different hashes**. Rainbow tables are now useless — an attacker would need one table *per salt*, which is the whole point.

The salt is **not secret**. It's stored right next to the hash. Its job is to make each hash unique, not to hide anything.

---

## 4. Why BCrypt and not SHA-256?

MD5, SHA-1 and SHA-256 are designed to be **fast** — they hash gigabytes per second. That's excellent for checksums and terrible for passwords: a modern GPU can try **billions of candidate passwords per second** against a SHA-256 hash.

BCrypt is deliberately **slow**:

```java
new BCryptPasswordEncoder(10);   // 10 = cost factor (work factor)
```

The cost factor is a **base-2 exponent**: BCrypt runs 2^cost internal iterations.

| Cost | Relative work | Rough time per hash |
|---|---|---|
| 10 | 1× | ~50–100 ms |
| 12 | 4× | ~200–400 ms |
| 14 | 16× | ~1 s |

A hundred milliseconds is invisible to a user logging in once. It is devastating to an attacker trying billions of guesses — it turns a one-day crack into decades.

> [!tip] Choosing a cost
> Benchmark on **your production hardware** and pick the highest cost that keeps a login under roughly 100–250 ms. Spring's default is **10**; 12 is a common modern choice. Remember it's also a **DoS surface** — a login endpoint doing 400 ms of CPU per request needs rate limiting.

Other properties that make BCrypt suitable: it's memory-hungry enough to be awkward on GPUs, and it's been in production since 1999 with no practical break.

## 5. Anatomy of a BCrypt hash

```text
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
 |   |  |                     |
 |   |  |                     +-- hash        (31 chars)
 |   |  +------------------------ salt        (22 chars, base64)
 |   +--------------------------- cost factor (10)
 +------------------------------- algorithm version (2a)
```

Everything needed to verify a password travels **with** the hash. That single string is all you store — 60 characters.

> [!warning] Column width
> `VARCHAR(60)` minimum for BCrypt. A `VARCHAR(50)` column silently truncates the hash and **every login fails** with no obvious error. Use `VARCHAR(72)` or more to leave room for `{bcrypt}` prefixes and future algorithms.

Also worth knowing: **BCrypt ignores input beyond 72 bytes**. Don't pre-hash long passwords with a fast hash to work around it unless you know what you're doing (that has its own pitfalls).

## 6. Registration and login

**Registration**

```java
String hash = passwordEncoder.encode("secret123");
// $2a$10$ABCD...
user.setPassword(hash);
userRepository.save(user);
```

**Login**

```java
passwordEncoder.matches("secret123", storedHash);   // true / false
```

Internally `matches()` does:

```text
stored hash: $2a$10$ABC...
     |
     +--> extract algorithm = 2a
     +--> extract cost      = 10
     +--> extract salt      = ABC...
     |
recompute hash("secret123" + ABC, cost 10)
     |
compare with the stored hash portion (constant-time)
```

---

## 7. Two questions everyone asks

### Q: If the salt is random, how does login ever work?

> Registration used salt `ABC`. At login BCrypt would pick a *new* random salt `PQR`, and `hash(1234 + PQR) ≠ hash(1234 + ABC)`. So how does it know?

**Because the salt is stored inside the hash string.** The database column doesn't hold "the hash" — it holds `$2a$10$<salt><hash>`. `matches()` reads the salt straight back out and re-uses it.

```text
Registration:  encode("1234")            -> $2a$10$ABC...   (random salt ABC, stored)
Login:         matches("1234", stored)   -> reads ABC from the string, re-hashes with ABC
```

So the salt is **random per user**, but never lost. Two users with password `1234` get different stored hashes, and both log in fine, because each hash carries its own salt.

### Q: If I change the cost factor from 10 to 12, do old passwords break?

**No.** The cost factor is also embedded in the hash.

```text
Stored:  $2a$10$ABC...
                ^^
Application now configured with:  new BCryptPasswordEncoder(12)

Login -> matches() reads cost = 10 from the stored hash -> verifies using 10 -> success
```

The configured cost only affects **new** `encode()` calls. Old users keep authenticating at their original cost.

The same is true for the algorithm version (`$2a$` vs `$2b$`).

## 8. Migrating users to a stronger cost (or a new algorithm)

Since old hashes keep working, how do users ever get upgraded? On successful login, silently re-hash:

```java
public void onSuccessfulLogin(User user, String rawPassword) {
    if (passwordEncoder.upgradeEncoding(user.getPassword())) {
        user.setPassword(passwordEncoder.encode(rawPassword));   // now $2a$12$...
        userRepository.save(user);
    }
}
```

`upgradeEncoding()` returns `true` when the stored hash is weaker than the encoder's current settings. This is the **only moment** you have the raw password, so it's the only moment you can re-hash — no password reset email needed.

```text
User logs in with $2a$10$...  ->  verified with cost 10  ->  re-hashed as $2a$12$...  ->  saved
```

The same pattern migrates **algorithms**:

```text
Old hash is BCrypt  ->  verify with BCrypt  ->  re-hash with Argon2  ->  save
```

This is called **password hash migration**. Users whose accounts go dormant keep the old hash, which is why teams usually pair it with a deadline ("anyone who hasn't logged in within 12 months must reset").

---

## 9. `DelegatingPasswordEncoder` — Spring Boot's actual default

Since Spring Security 5, `PasswordEncoderFactories.createDelegatingPasswordEncoder()` is the default. It stores an **algorithm id prefix**:

```text
{bcrypt}$2a$10$N9qo8uLOickgx2ZMRZoMye...
{argon2}$argon2id$v=19$m=16384,t=2,p=1$...
{noop}plaintext
```

`matches()` reads the `{id}` prefix and routes to the right encoder; `encode()` always uses the current default. That means **one column can hold several algorithms at once** — exactly what a gradual migration needs.

> [!warning] The `IllegalArgumentException: There is no PasswordEncoder mapped for the id "null"`
> The single most common Spring Security startup error. It means the stored hash has **no `{...}` prefix** while a `DelegatingPasswordEncoder` is in use. Fixes: either define `@Bean PasswordEncoder → new BCryptPasswordEncoder()` (no prefix expected), or prefix existing hashes with `{bcrypt}`.

## 10. The encoder landscape

| Encoder | Verdict |
|---|---|
| **`BCryptPasswordEncoder`** | Excellent default. Battle-tested, self-describing hash, tunable cost. |
| **`Argon2PasswordEncoder`** | Winner of the 2015 Password Hashing Competition. **Memory-hard** — resists GPU/ASIC attacks better than BCrypt. Best choice for new systems (`argon2id`). |
| **`SCryptPasswordEncoder`** | Also memory-hard, older than Argon2. Fine, less common. |
| **`Pbkdf2PasswordEncoder`** | Slow-by-iteration, FIPS-approved. Choose when compliance demands it. |
| `NoOpPasswordEncoder` | Plain text. **Deprecated. Tests only. Never production.** |
| `MessageDigestPasswordEncoder` (MD5/SHA) | Deprecated. Fast = broken for passwords. |

The practical answer in an interview: *"BCrypt is the safe, standard choice; Argon2id is the modern preference if the platform supports it."*

---

## 11. Beyond hashing

Hashing protects passwords **after** a breach. The complete picture also needs:

- **Rate limiting / lockout** on the login endpoint — `isAccountNonLocked()` on `UserDetails` exists precisely for this.
- **HTTPS everywhere** — the password travels in plain text over the wire otherwise; the best hash in the world doesn't help.
- **Never log passwords** — check your request-logging filters and `toString()` methods.
- **Breached-password checks** (e.g. Have I Been Pwned's k-anonymity API) at registration.
- **MFA** for anything sensitive — the strongest single-factor policy still fails to a phished password.
- **Erase credentials after authentication** — Spring already nulls them on the authenticated token.

## ❓ Interview Questions

### Q1. Why can't you use `encode(raw).equals(storedHash)`?

BCrypt generates a **new random salt** on every `encode()`, so the same password produces a different string each time. Verification must use `matches()`, which extracts the original salt from the stored hash.

### Q2. Where is the salt stored?

Inside the hash string itself: `$2a$10$<22-char salt><hash>`. No separate column.

### Q3. Why is BCrypt preferred over SHA-256?

SHA-256 is fast, so brute-forcing is cheap. BCrypt is deliberately slow via a tunable cost factor, making large-scale guessing economically infeasible.

### Q4. What is the cost factor and what does increasing it do?

A base-2 exponent for the number of internal iterations. +1 doubles the work. Higher = slower to hash = slower to attack.

### Q5. If I raise the cost from 10 to 12, do existing users break?

No — the cost is embedded in each stored hash and used for that user's verification. Only new `encode()` calls use 12. Upgrade old hashes on successful login via `upgradeEncoding()`.

### Q6. How would you migrate from BCrypt to Argon2 without forcing password resets?

Use `DelegatingPasswordEncoder`. On successful login, verify with the old encoder (routed by the `{bcrypt}` prefix) and re-hash with the new default, storing `{argon2}...`. Set a cut-off date for dormant accounts.

### Q7. Hashing vs encryption for passwords?

Encryption is reversible with a key — if the key leaks, so do all passwords. Hashing is one-way; you never need to recover a password, only verify one. Always hash.

### Q8. Is the salt secret?

No. It's stored in plain sight. Its job is to make each hash unique so precomputed tables don't work, not to be confidential.

### Q9. What does `{bcrypt}` in front of a hash mean?

It's the `DelegatingPasswordEncoder` algorithm id, letting one column hold hashes from several algorithms and routing `matches()` to the right encoder.

> [!tip] ⚡ Quick Recall
> - **Hash, never store.** Hash ≠ encryption — one-way, no key.
> - Same password → same hash → rainbow tables. **Salt** (random, per user, not secret) breaks that.
> - **BCrypt = slow on purpose.** Cost factor is a power of 2; +1 = double work. Default 10, modern 12.
> - Hash format: **`$2a$10$<salt><hash>`** — algorithm + cost + salt + hash in one 60-char string.
> - `matches()` extracts the salt **and** the cost from the stored hash → random salt still verifies, and raising the cost never breaks old logins.
> - **`encode(raw).equals(hash)` is always false.** Use `matches()`.
> - Upgrade silently at login with **`upgradeEncoding()`** — the one moment you hold the raw password.
> - **`DelegatingPasswordEncoder`** + `{bcrypt}`/`{argon2}` prefixes = multi-algorithm column, painless migration.
> - `"no PasswordEncoder mapped for the id \"null\""` = missing `{...}` prefix.
> - Argon2id > BCrypt for new systems; both are fine answers. Never MD5/SHA/NoOp.
