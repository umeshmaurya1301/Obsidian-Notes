Three topics the raw notes only touched in passing, and the three most likely to be misunderstood in a code review: CSRF (an attack), CORS (a browser rule), and session hardening.

> [!info] 🧭 Summary
> - **CSRF and CORS are unrelated.** CSRF is an *attack* Spring protects you from; CORS is a *browser policy* that blocks your own frontend until you allow it. `csrf.disable()` does not fix a CORS error.
> - **CSRF** = a malicious site makes the victim's browser send an authenticated request to your app, using cookies the browser attaches **automatically**.
> - The defence is the **synchronizer token**: a random token the attacker can't read (Same-Origin Policy) must accompany every state-changing request.
> - Spring enables CSRF protection **by default** and applies it to `POST/PUT/PATCH/DELETE` — not to `GET/HEAD/OPTIONS`, which is why those must never change state.
> - **Disable CSRF only when authentication doesn't ride on cookies** — a `Bearer` token API is safe because the header isn't sent automatically. Cookie-based auth + disabled CSRF = a real vulnerability.
> - **`SameSite=Lax`** on the session cookie is a strong second layer, and the modern browser default.
> - **CORS** is enforced by the *browser*, not the server. A cross-origin `fetch` triggers a **preflight `OPTIONS`** for anything non-simple; the browser blocks the response unless the headers allow it.
> - Configure CORS through Spring Security (`http.cors()` + a `CorsConfigurationSource`) so the preflight isn't rejected by the filter chain before your MVC config sees it.
> - **`allowCredentials(true)` cannot be combined with `allowedOrigins("*")`** — use `allowedOriginPatterns` or list the origins.
> - Session hardening: **`STATELESS`** for token APIs, session-fixation protection (on by default), `maximumSessions`, and `HttpOnly`/`Secure`/`SameSite` cookies.
>

## 1. CSRF — the attack

**Cross-Site Request Forgery.** The browser attaches cookies for a domain to **every** request to that domain, no matter which page triggered it.

You're logged into your bank; the session cookie sits in the browser. You then open a malicious page:

```html
<!-- evil.com -->
<form action="https://mybank.com/transfer" method="POST" id="f">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="50000">
</form>
<script>document.getElementById('f').submit();</script>
```

```text
Browser -> POST https://mybank.com/transfer
           Cookie: JSESSIONID=...        <- attached automatically
           to=attacker&amount=50000

Bank sees a perfectly valid authenticated request. Money moves.
```

The attacker never reads your cookie or your session — the **Same-Origin Policy** prevents that. They just **cause the browser to use it**. Authentication alone can't stop this: the request *is* authentic. What's missing is proof of **intent**.

---

## 2. CSRF — the defence

### The synchronizer token pattern

The server issues a random token that the attacker **cannot read** (SOP blocks cross-origin reads of your pages and responses), and demands it back on every state-changing request:

```text
GET /transfer   ->  page contains  <input name="_csrf" value="a1b2c3...">
POST /transfer  ->  must include _csrf=a1b2c3...   (matched against the session)
```

`evil.com` can *send* a request but cannot *read* the token, so it can't construct a valid one. Request rejected with **403**.

In Thymeleaf the hidden field is added automatically for `<form th:action>`. Hand-written forms need it explicitly.

### Spring's default

CSRF protection is **on by default** and applies to state-changing methods:

```text
Protected:      POST, PUT, PATCH, DELETE
Not protected:  GET, HEAD, OPTIONS, TRACE
```

Which is precisely why **`GET` must never change state**. A `GET /deleteUser?id=5` endpoint is exploitable with one `<img src="...">` tag — no CSRF token required, because Spring doesn't protect GET.

### For a JS frontend — the cookie repository

An SPA needs to *read* the token to put it in a header, so the `HttpOnly` flag comes off that specific cookie:

```java
http.csrf(csrf -> csrf
        .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
        .csrfTokenRequestHandler(new CsrfTokenRequestAttributeHandler()));
```

```text
Server -> Set-Cookie: XSRF-TOKEN=a1b2c3   (readable by JS)
JS     -> X-XSRF-TOKEN: a1b2c3            (read from the cookie, sent as a header)
```

This still works because `evil.com` **cannot read your cookies** — only send them. Axios and Angular do this automatically. (Spring Security 6 changed the default token-loading behaviour, so the explicit `CsrfTokenRequestAttributeHandler` above is the usual fix for SPAs that broke on upgrade.)

## 3. When can you disable CSRF?

The rule, stated precisely:

> **CSRF protection is needed exactly when the browser attaches credentials automatically.**

| Auth mechanism | Sent automatically? | CSRF needed? |
|---|---|---|
| Session cookie (`JSESSIONID`) | ✅ yes | ✅ **Yes** |
| JWT in an `HttpOnly` cookie | ✅ yes | ✅ **Yes** |
| `Authorization: Bearer` header | ❌ no — JS must add it | ❌ No |
| HTTP Basic from a non-browser client | ❌ | ❌ No |

So for a token API:

```java
http.csrf(csrf -> csrf.disable())
    .sessionManagement(s -> s.sessionCreationPolicy(STATELESS));
```

is correct — an attacker's page can't add an `Authorization` header to a cross-origin request.

> [!warning] The dangerous cargo-cult
> `csrf.disable()` is pasted into thousands of tutorials as "the fix for my POST returning 403". If your app authenticates with **cookies**, that line converts a 403 into a genuine CSRF vulnerability. Disable it because you use header tokens, never because a request failed.

### `SameSite` — the second layer

```properties
server.servlet.session.cookie.same-site=lax
server.servlet.session.cookie.http-only=true
server.servlet.session.cookie.secure=true
```

| Value | Behaviour |
|---|---|
| `Strict` | Never sent on cross-site requests. Strongest; breaks inbound links into logged-in pages. |
| **`Lax`** | Sent on top-level `GET` navigations only — blocks cross-site `POST`. The modern browser default. |
| `None` | Always sent; **requires `Secure`**. Only for deliberate cross-site flows. |

`SameSite=Lax` kills the classic form-POST CSRF outright. It's defence in depth, not a replacement for tokens — older browsers, and some cross-site flows, still need them.

## 4. CORS — the other thing entirely

**Cross-Origin Resource Sharing.** Nothing to do with CSRF, despite the anagram.

By default, JavaScript on `https://app.mycompany.com` **cannot read** a response from `https://api.mycompany.com` — different origin (scheme + host + port). CORS is how the server *opts in* to being read.

```text
Origin:  https://app.mycompany.com     (frontend)
Target:  https://api.mycompany.com     (your Spring Boot API)
         -> different origin -> CORS applies
```

> [!warning] CORS is enforced by the browser, not by your server
> The request often **reaches your server and executes**; the browser then refuses to hand the response to JavaScript. Two consequences: a CORS error is not a security control on its own (curl and Postman ignore it entirely), and a failed CORS check can still have changed data server-side.

### Preflight

For anything beyond a "simple" request (custom headers like `Authorization`, methods like `PUT`/`DELETE`, JSON content types), the browser first asks permission:

```text
OPTIONS /api/orders
Origin: https://app.mycompany.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization, content-type
        |
        v
200 OK
Access-Control-Allow-Origin: https://app.mycompany.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 3600
        |
        v
then the real POST is sent
```

`Access-Control-Max-Age` caches the preflight so you're not doubling every request.

### Configuring it in Spring Security

```java
@Bean
CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("https://app.mycompany.com"));
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
    config.setAllowedHeaders(List.of("Authorization", "Content-Type"));
    config.setAllowCredentials(true);
    config.setMaxAge(3600L);

    var source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/api/**", config);
    return source;
}
```

```java
http.cors(Customizer.withDefaults());   // picks up the CorsConfigurationSource bean
```

> [!warning] Why `@CrossOrigin` alone often fails
> The security filter chain runs **before** Spring MVC. An unauthenticated preflight `OPTIONS` (browsers never send credentials on it) gets rejected with 401 by `AuthorizationFilter` before your `@CrossOrigin` annotation is ever consulted. `http.cors(...)` installs `CorsFilter` **early in the chain** so preflights are answered correctly. Configure CORS **in the security config**.

### Two rules people trip on

1. **`allowCredentials(true)` + `allowedOrigins("*")` is illegal.** The browser rejects the wildcard when credentials are involved. Use `setAllowedOriginPatterns(List.of("https://*.mycompany.com"))` or list origins explicitly.
2. **Don't allow `*` in production.** Reflecting arbitrary origins with credentials enabled is how CORS becomes an actual vulnerability.

### CSRF vs CORS side by side

| | CSRF | CORS |
|---|---|---|
| What it is | An **attack** | A **browser policy** |
| Spring's role | **Protects** you (on by default) | **Relaxes** the policy so your frontend works |
| Symptom | — | `blocked by CORS policy` in the browser console |
| Fix | CSRF token / `SameSite` / header-based auth | Allow the origin on the server |
| Relationship | **None.** Disabling CSRF never fixes a CORS error. | |

## 5. Session management

Even in a JWT world, know these — every interviewer asks how you'd scale sessions.

```java
http.sessionManagement(session -> session
        .sessionCreationPolicy(SessionCreationPolicy.IF_REQUIRED)
        .sessionFixation(fixation -> fixation.changeSessionId())
        .maximumSessions(1)
        .maxSessionsPreventsLogin(false)
        .expiredUrl("/login?expired"));
```

### `SessionCreationPolicy`

| Policy | Meaning |
|---|---|
| `ALWAYS` | Always create a session |
| **`IF_REQUIRED`** | Default — create one only when something needs it |
| `NEVER` | Don't create one, but use an existing one |
| **`STATELESS`** | Never create **or use** one — the correct setting for token APIs |

### Session fixation

The attack: the attacker obtains a session id, plants it in the victim's browser (via a link, or an XSS write), and waits for the victim to log in — now attacker and victim share one authenticated session.

The defence: **rotate the session id at login**. `changeSessionId()` is the default in Spring Security and modern Servlet containers. Don't switch it to `none`.

### Concurrent session control

```java
.maximumSessions(1)
.maxSessionsPreventsLogin(false)   // false = kick the older session out
                                   // true  = refuse the new login
```

Banking and admin consoles typically want `1`. Needs `HttpSessionEventPublisher` registered so Spring learns about session destruction.

### Cookie hardening

```properties
server.servlet.session.cookie.http-only=true    # JS can't read it -> XSS can't steal it
server.servlet.session.cookie.secure=true       # HTTPS only
server.servlet.session.cookie.same-site=lax     # blocks cross-site POST
server.servlet.session.timeout=30m
```

### Scaling sessions

"Sessions don't scale" is only true of **in-memory** sessions. Spring Session externalises them:

```java
@EnableRedisHttpSession
```

```text
Instance A   \
Instance B    >---- Redis (shared session store)
Instance C   /
```

Now any instance serves any request, sessions survive a restart, and you keep **instant revocation** — the thing JWTs give up. A perfectly modern architecture, and a good answer when an interviewer assumes JWT is the only option.

## 6. Security headers Spring adds for you

Spring Security sets several response headers by default — worth knowing you get them free:

| Header | Purpose |
|---|---|
| `X-Content-Type-Options: nosniff` | Stops MIME-type sniffing |
| `X-Frame-Options: DENY` | Clickjacking protection (frame-busting) |
| `Cache-Control: no-cache, no-store` | Keeps authenticated pages out of caches |
| `Strict-Transport-Security` | HSTS — HTTPS only (on HTTPS requests) |

Not on by default but worth adding for browser-facing apps: **Content-Security-Policy** — the single most effective mitigation against XSS, which is what makes token theft from `localStorage` possible in the first place.

```java
http.headers(headers -> headers
        .contentSecurityPolicy(csp -> csp
                .policyDirectives("default-src 'self'; frame-ancestors 'none'")));
```

> [!tip] `frameOptions` and H2 console
> The classic dev annoyance: the H2 console renders in a frame and `X-Frame-Options: DENY` blanks it. `http.headers(h -> h.frameOptions(f -> f.sameOrigin()))` — in the **dev profile only**.

## ❓ Interview Questions

### Q1. What is CSRF?

An attack where a malicious site causes the victim's browser to send an authenticated request to your application, exploiting the fact that cookies are attached automatically. The request is authentic; what's missing is the user's intent.

### Q2. How does Spring protect against it?

A synchronizer token: a random per-session value that must accompany every state-changing request. The attacker's page can send requests but can't read the token (Same-Origin Policy), so it can't forge a valid one.

### Q3. Why is CSRF protection not applied to GET?

`GET` is defined as safe and idempotent. That's also why a state-changing `GET` endpoint is a vulnerability — it's exploitable with a plain `<img>` tag.

### Q4. When is it safe to disable CSRF?

When authentication doesn't ride on automatically-attached credentials — i.e. a `Bearer` token in a header. With cookie-based auth, disabling it creates a real vulnerability.

### Q5. What is `SameSite` and how does it help?

A cookie attribute controlling whether the cookie is sent on cross-site requests. `Lax` (the modern default) blocks cross-site `POST`, neutralising classic form-based CSRF as a second layer.

### Q6. CSRF vs CORS?

CSRF is an attack Spring defends against; CORS is a browser policy you relax so your own frontend can read your API. Unrelated — `csrf.disable()` never fixes a CORS error.

### Q7. What is a CORS preflight?

An `OPTIONS` request the browser sends before a non-simple cross-origin request, asking whether the method and headers are allowed. Answered with `Access-Control-Allow-*` headers, cacheable via `Access-Control-Max-Age`.

### Q8. Why must CORS be configured in the security config?

The filter chain runs before Spring MVC; an unauthenticated preflight would be rejected with 401 before `@CrossOrigin` is consulted. `http.cors(...)` installs `CorsFilter` early enough to answer it.

### Q9. Why can't you use `allowedOrigins("*")` with credentials?

The spec forbids it — browsers reject a wildcard origin when credentials are included. Use explicit origins or `allowedOriginPatterns`.

### Q10. What is session fixation and how is it prevented?

An attacker plants a known session id before login and then shares the authenticated session. Spring rotates the session id on successful authentication (`changeSessionId()`), enabled by default.

### Q11. How do you scale sessions across instances?

Spring Session with Redis (or JDBC). Any instance can serve any request, sessions survive restarts, and you keep instant revocation — the property stateless JWTs lack.

> [!tip] ⚡ Quick Recall
> - **CSRF ≠ CORS.** CSRF = attack Spring blocks. CORS = browser policy you relax. `csrf.disable()` never fixes CORS.
> - CSRF works because **cookies are sent automatically**; the attacker can send but never **read**.
> - Defence = **synchronizer token** + `SameSite=Lax`. Spring protects `POST/PUT/PATCH/DELETE` by default, **not GET** — so never mutate state on a GET.
> - **Disable CSRF only for header-token auth.** Cookie auth + `csrf.disable()` = real vulnerability.
> - SPA: `CookieCsrfTokenRepository.withHttpOnlyFalse()` → `XSRF-TOKEN` cookie → `X-XSRF-TOKEN` header.
> - **CORS is enforced by the browser** — the request may already have executed server-side.
> - Non-simple cross-origin request ⇒ **preflight `OPTIONS`**; configure via `http.cors(...)` + `CorsConfigurationSource`, not `@CrossOrigin` alone.
> - `allowCredentials(true)` **cannot** pair with `allowedOrigins("*")`.
> - `SessionCreationPolicy.STATELESS` for token APIs; **session fixation protection on by default**; `maximumSessions(1)` for concurrent control.
> - Cookies: **`HttpOnly` + `Secure` + `SameSite`**. Scale sessions with **Spring Session + Redis** and keep instant revocation.
> - Free headers: `nosniff`, `X-Frame-Options`, HSTS, no-cache. Add **CSP** yourself.
