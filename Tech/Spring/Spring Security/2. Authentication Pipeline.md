Note 1 showed *where* authentication happens — inside a filter. This note is *what happens inside*: the five components that turn a username and password into an authenticated user.

> [!info] 🧭 Summary
> - The pipeline: **`AuthenticationManager` → `AuthenticationProvider` → `UserDetailsService` → `UserDetails` → `PasswordEncoder` → authenticated `Authentication`**.
> - **`AuthenticationManager`** — the orchestrator. One method: `authenticate(Authentication)`. It **verifies nothing itself**; it delegates. Standard implementation: **`ProviderManager`**.
> - **`AuthenticationProvider`** — where authentication actually happens. Two methods: `authenticate()` and `supports()`. `ProviderManager` asks each provider "do you support this token type?" and uses the first that says yes.
> - **`DaoAuthenticationProvider`** — the one you'll use 90% of the time. It wires `UserDetailsService` + `PasswordEncoder` together.
> - **`UserDetailsService`** — one method, `loadUserByUsername()`. It **only loads the user**. It does *not* check the password.
> - **`UserDetails`** — Spring's standard user contract (`getUsername`, `getPassword`, `getAuthorities`, `isEnabled`, ...). Your `User` entity must be adapted into it; Spring doesn't understand your entity.
> - **`PasswordEncoder`** — `encode()` at registration, `matches(raw, storedHash)` at login. **Never** `equals()`.
> - Mental model: Manager = **traffic controller**, Provider = **authenticator**, UserDetailsService = **user fetcher**, UserDetails = **standard user object**, PasswordEncoder = **password verifier**.
> - The result — an authenticated `Authentication` — is stored in `SecurityContextHolder`, and everything downstream reads it from there.
>

## 0. The whole pipeline in one picture

```text
Username + Password
        |
        v
AuthenticationManager          (orchestrator — ProviderManager)
        |
        v
AuthenticationProvider         (DaoAuthenticationProvider)
        |
        +--> UserDetailsService     loadUserByUsername()
        |            |
        |            v
        |        UserDetails        standard user object
        |
        +--> PasswordEncoder        matches(raw, hash)
        |
        v
Authenticated Authentication
        |
        v
SecurityContextHolder
```

If you can draw and narrate this, you can answer a large share of Spring Security authentication questions.

## 1. `AuthenticationManager` — the orchestrator

One method:

```java
public interface AuthenticationManager {
    Authentication authenticate(Authentication authentication) throws AuthenticationException;
}
```

When a login request arrives:

```json
{ "username": "umesh", "password": "secret" }
```

the filter builds an **unauthenticated** token:

```java
var token = new UsernamePasswordAuthenticationToken("umesh", "secret");
// principal     = umesh
// credentials   = secret
// authenticated = false
```

and hands it over:

```java
authenticationManager.authenticate(token);
```

### It does not verify passwords itself

It **delegates** to one or more `AuthenticationProvider`s:

```text
AuthenticationManager
        |
        +---- Provider A
        |
        +---- Provider B
        |
        +---- Provider C
```

> **AuthenticationManager = Team Lead. AuthenticationProvider = the engineer doing the work.**

### `ProviderManager` — the real implementation

`ProviderManager` is the `AuthenticationManager` implementation Spring actually gives you. Its algorithm:

```text
for each provider in providers:
        if provider.supports(token.getClass()):
                result = provider.authenticate(token)
                if result != null:  return result   <- first success wins
if none succeeded:
        delegate to parent AuthenticationManager (if any)
        else throw ProviderNotFoundException
```

That "list of providers" is why you can support username/password **and** an API key **and** LDAP in the same application — one provider each.

> [!tip] Getting the bean in Spring Security 6
> There is no auto-exposed `AuthenticationManager` bean any more. If you need one (e.g. in a `/login` controller that issues JWTs), expose it explicitly:
> ```java
> @Bean
> AuthenticationManager authenticationManager(AuthenticationConfiguration config) throws Exception {
>     return config.getAuthenticationManager();
> }
> ```

## 2. `AuthenticationProvider` — where authentication happens

```java
public interface AuthenticationProvider {

    Authentication authenticate(Authentication authentication) throws AuthenticationException;

    boolean supports(Class<?> authentication);
}
```

Given a username and password it must:

1. **Load** the user
2. **Validate** the password
3. **Create** an authenticated token

Input:

```text
UsernamePasswordAuthenticationToken
    principal   = umesh
    credentials = secret123
    authenticated = false
```

Output on success:

```java
new UsernamePasswordAuthenticationToken(userDetails, null, authorities);
// authenticated = true   (this 3-arg constructor sets it)
```

> [!note] Why the 3-arg constructor matters
> The **2-arg** constructor creates an *unauthenticated* token; the **3-arg** (principal, credentials, authorities) constructor marks it `authenticated = true`. That's the difference between "a login attempt" and "a logged-in user". Never call `setAuthenticated(true)` by hand on a token you built from raw request data.

### `supports()`

```java
@Override
public boolean supports(Class<?> authentication) {
    return UsernamePasswordAuthenticationToken.class.isAssignableFrom(authentication);
}
```

This is how `ProviderManager` routes: a JWT token type goes to a JWT provider, a username/password token to `DaoAuthenticationProvider`.

### `DaoAuthenticationProvider` — the common one

```text
DaoAuthenticationProvider
        |
        +--> UserDetailsService     (load the user)
        |
        +--> PasswordEncoder        (verify the password)
```

Its logic, simplified:

```text
1. userDetails = userDetailsService.loadUserByUsername(username)
2. if userDetails == null  -> throw UsernameNotFoundException
3. passwordEncoder.matches(rawPassword, userDetails.getPassword())?
        no  -> throw BadCredentialsException
4. check isEnabled / isAccountNonLocked / isAccountNonExpired / isCredentialsNonExpired
5. return an authenticated token with userDetails as the principal
```

> [!tip] Two production details worth mentioning in an interview
> - **`hideUserNotFoundExceptions`** is `true` by default: a `UsernameNotFoundException` is rethrown as `BadCredentialsException`, so the API can't be used to enumerate which emails exist.
> - **Timing-attack protection**: if the user isn't found, the provider still runs a dummy `matches()` against a throwaway hash, so "unknown user" and "wrong password" take the same time.

### Custom providers

When you need something other than username/password — API keys, OTP, an external identity service:

```java
@Component
public class ApiKeyAuthenticationProvider implements AuthenticationProvider {

    @Override
    public Authentication authenticate(Authentication authentication) {
        String key = (String) authentication.getCredentials();
        Client client = clientRepository.findByApiKey(key)
                .orElseThrow(() -> new BadCredentialsException("Invalid API key"));

        return new ApiKeyAuthenticationToken(client, null, client.getAuthorities());
    }

    @Override
    public boolean supports(Class<?> authentication) {
        return ApiKeyAuthenticationToken.class.isAssignableFrom(authentication);
    }
}
```

## 3. `UserDetailsService` — the user fetcher

Exactly one responsibility:

```java
public interface UserDetailsService {
    UserDetails loadUserByUsername(String username) throws UsernameNotFoundException;
}
```

It fetches user information from wherever it lives — database, LDAP, an external service:

```java
@Service
@RequiredArgsConstructor
public class CustomUserDetailsService implements UserDetailsService {

    private final UserRepository userRepository;

    @Override
    public UserDetails loadUserByUsername(String email) {
        User user = userRepository.findByEmail(email)
                .orElseThrow(() -> new UsernameNotFoundException("User not found: " + email));
        return new CustomUserDetails(user);
    }
}
```

> [!warning] The most common misunderstanding
> **`UserDetailsService` does NOT validate the password.** It only loads user data. Password verification is done by the **`AuthenticationProvider` + `PasswordEncoder`**. The service simply returns the stored hash as part of `UserDetails`, and someone else compares it.

The "username" parameter is just a **lookup key** — it can be an email, a phone number, a customer ID. Whatever your login form sends.

> [!tip] Roles and lazy loading
> If roles/authorities are a `@ManyToMany` on the entity, loading them lazily inside `loadUserByUsername` and then leaving the transaction gives you a `LazyInitializationException` later. Fetch them eagerly in the query (`JOIN FETCH`) or map them to `SimpleGrantedAuthority` before returning. See [[9. Fetching]] in the JPA notes.

## 4. `UserDetails` — the standard user contract

```java
public interface UserDetails extends Serializable {
    String getUsername();
    String getPassword();
    Collection<? extends GrantedAuthority> getAuthorities();
    boolean isEnabled();
    boolean isAccountNonLocked();
    boolean isAccountNonExpired();
    boolean isCredentialsNonExpired();
}
```

Your database row:

```text
id       = 1
email    = umesh@gmail.com
password = $2a$10$....
role     = ADMIN
enabled  = true
```

has to be adapted:

```java
@RequiredArgsConstructor
public class CustomUserDetails implements UserDetails {

    private final User user;

    @Override public String getUsername() { return user.getEmail(); }
    @Override public String getPassword() { return user.getPassword(); }

    @Override
    public Collection<? extends GrantedAuthority> getAuthorities() {
        return user.getRoles().stream()
                   .map(r -> new SimpleGrantedAuthority("ROLE_" + r.getName()))
                   .toList();
    }

    @Override public boolean isEnabled()               { return user.isEnabled(); }
    @Override public boolean isAccountNonLocked()      { return !user.isLocked(); }
    @Override public boolean isAccountNonExpired()     { return true; }
    @Override public boolean isCredentialsNonExpired() { return true; }

    public Long getId()    { return user.getId(); }   // handy for @PreAuthorize
    public User getUser()  { return user; }
}
```

### Why the extra class? Why not implement `UserDetails` on the entity?

Because **Spring Security doesn't understand your entity** — it understands `UserDetails`. Whether the user comes from PostgreSQL, MySQL, MongoDB or LDAP, Spring works with one shape:

```text
Entity  →  UserDetails  →  Spring Security
```

You *can* make the JPA entity implement `UserDetails` directly, and plenty of tutorials do. It's usually a bad idea: it drags security concerns into your persistence model, forces `@Transient` on the four boolean flags, and the principal you put in the `SecurityContext` becomes a detached JPA entity. Prefer the wrapper.

### The four boolean flags

| Flag | `false` throws |
|---|---|
| `isEnabled()` | `DisabledException` — account deactivated |
| `isAccountNonLocked()` | `LockedException` — too many failed logins |
| `isAccountNonExpired()` | `AccountExpiredException` — e.g. a contractor account |
| `isCredentialsNonExpired()` | `CredentialsExpiredException` — password rotation policy |

These are checked by `DaoAuthenticationProvider` **before and after** the password check. Free account-lifecycle handling if you wire them to real columns.

> [!tip] Built-in shortcut
> For prototypes: `User.withUsername("umesh").password("{bcrypt}$2a$10$...").roles("ADMIN").build()` gives you a ready-made `UserDetails`, and `InMemoryUserDetailsManager` a ready-made service. Fine for demos, never for production.

## 5. `PasswordEncoder` — the password verifier

```java
public interface PasswordEncoder {
    String encode(CharSequence rawPassword);
    boolean matches(CharSequence rawPassword, String encodedPassword);
    default boolean upgradeEncoding(String encodedPassword) { return false; }
}
```

**At registration:**

```java
user.setPassword(passwordEncoder.encode("secret123"));
// $2a$10$sdjfhjksdhf...
```

Never store `secret123`.

**At login:**

```java
passwordEncoder.matches("secret123", storedHash);   // true / false
```

### Why not just compare strings?

```java
rawPassword.equals(dbPassword)   // WRONG
```

Two reasons: the raw password must never be in the database at all, and BCrypt produces a **different hash every time** (new random salt), so even `encode(raw).equals(hash)` fails. Only `matches()` works.

Declare the bean once:

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

Full treatment — salt, cost factor, hash anatomy, migration — in [[3. Password Encoding and BCrypt]].

## 6. The complete login flow

Username `umesh`, password `secret123`:

```text
POST /login
     |
     v
UsernamePasswordAuthenticationFilter        creates unauthenticated token
     |
     v
AuthenticationManager (ProviderManager)     picks a provider via supports()
     |
     v
DaoAuthenticationProvider
     |
     +--> userDetailsService.loadUserByUsername("umesh")
     |            |
     |            v
     |        UserDetails { username, $2a$10$..., ROLE_ADMIN }
     |
     +--> passwordEncoder.matches("secret123", "$2a$10$...")  -> true
     |
     +--> check enabled / non-locked / non-expired
     |
     v
new UsernamePasswordAuthenticationToken(userDetails, null, authorities)
     authenticated = true
     |
     v
SecurityContextHolder.getContext().setAuthentication(auth)
     |
     v
AuthorizationFilter  ->  Controller
```

Notice what happens to the password: it goes in as `credentials`, and the authenticated token is built with `null` credentials. Spring **erases the password** from the object it keeps around.

## 7. Failure paths

All of these extend `AuthenticationException`, and `ExceptionTranslationFilter` turns them into **401**:

| Exception | Cause |
|---|---|
| `BadCredentialsException` | Wrong password (**and**, by default, unknown username) |
| `UsernameNotFoundException` | User not found — usually hidden behind `BadCredentials` |
| `DisabledException` | `isEnabled()` false |
| `LockedException` | `isAccountNonLocked()` false |
| `AccountExpiredException` | `isAccountNonExpired()` false |
| `CredentialsExpiredException` | `isCredentialsNonExpired()` false |
| `ProviderNotFoundException` | No provider `supports()` this token type |

> [!warning] Don't leak which one it was
> Returning "user not found" vs "wrong password" to the client is a user-enumeration vulnerability. Log the specific reason server-side; return a generic *"Invalid username or password"* to the caller.

## ❓ Interview Questions

### Q1. Explain the Spring Security authentication flow.

Filter builds an unauthenticated `Authentication` → `AuthenticationManager` (`ProviderManager`) → the first `AuthenticationProvider` that `supports()` the token → `DaoAuthenticationProvider` calls `UserDetailsService.loadUserByUsername()` → gets `UserDetails` → `PasswordEncoder.matches()` → on success returns an authenticated token → stored in `SecurityContextHolder`.

### Q2. Does `AuthenticationManager` verify the password?

No. It delegates to providers. `ProviderManager` iterates its provider list and returns the first successful result.

### Q3. Does `UserDetailsService` verify the password?

No — it only loads the user. Verification is `AuthenticationProvider` + `PasswordEncoder`.

### Q4. Why do you need `UserDetails`? Why not use the JPA entity?

Spring Security is written against the `UserDetails` contract so it works with any backing store. Implementing it on the entity is possible but couples security to persistence and puts a detached entity in the `SecurityContext`.

### Q5. When would you write a custom `AuthenticationProvider`?

When the credential isn't a username/password: API keys, OTP, LDAP, a legacy SSO service, or a second factor. Implement `authenticate()` + `supports()` and register it — `ProviderManager` will route to it.

### Q6. How do you support two login mechanisms in one app?

Register two providers on the `ProviderManager`; `supports()` on each token type decides which one runs. Alternatively, use two `SecurityFilterChain`s with different `securityMatcher`s.

### Q7. What does `supports()` do?

Tells `ProviderManager` whether this provider can handle a given `Authentication` implementation — the routing mechanism between token types and providers.

### Q8. How do you get an `AuthenticationManager` bean in Spring Security 6?

Expose it from `AuthenticationConfiguration.getAuthenticationManager()`. It is no longer auto-configured as a bean.

### Q9. What are the four boolean flags on `UserDetails` for?

Account lifecycle: enabled, non-locked, non-expired, credentials-non-expired. `DaoAuthenticationProvider` checks them and throws a specific `AuthenticationException` for each.

---

> [!tip] ⚡ Quick Recall
> - `AuthenticationManager` = **traffic controller** (`ProviderManager`, iterates providers, first success wins).
> - `AuthenticationProvider` = **authenticator** — `authenticate()` + `supports()`.
> - `DaoAuthenticationProvider` = `UserDetailsService` + `PasswordEncoder`.
> - `UserDetailsService` = **user fetcher**, `loadUserByUsername()`, **never checks the password**.
> - `UserDetails` = **standard user object** — username, password hash, authorities, 4 status flags.
> - `PasswordEncoder` = **password verifier** — `encode()` on register, `matches()` on login, never `equals()`.
> - Unauthenticated token = 2-arg constructor; authenticated token = **3-arg** constructor (principal, `null` credentials, authorities).
> - Success → `SecurityContextHolder`. Failure → `AuthenticationException` → **401**.
> - Never reveal *why* login failed to the caller.
