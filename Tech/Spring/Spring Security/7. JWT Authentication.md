The raw notes skipped this phase ("I know JWT already"), so this is a compact revision pass rather than a tutorial — the parts that get asked about, and the parts that go wrong in production.

> [!info] 🧭 Summary
> - A JWT is **`header.payload.signature`**, base64url-encoded. The payload is **readable by anyone** — signed, not encrypted. Never put secrets in it.
> - The signature proves **integrity and origin**, not confidentiality. Verify it on every request or you have no security at all.
> - JWT changes exactly **one thing** in Spring Security: the entry filter. `AuthenticationManager` onwards is unchanged ([[5. Form Login and HTTP Basic]]).
> - Config for a token API: `SessionCreationPolicy.STATELESS` + `csrf.disable()` + your filter `addFilterBefore(..., UsernamePasswordAuthenticationFilter.class)`.
> - **Stateless is the whole point and the whole problem**: no server lookup per request, but also **no instant revocation**. Logout and role changes don't take effect until expiry.
> - Mitigation: **short access tokens** (5–15 min) + a **refresh token** ([[9. Refresh Tokens and Token Security]]) + a denylist keyed on `jti` for the emergency case.
> - **HS256** (shared secret — one service issues and verifies) vs **RS256/ES256** (private key signs, public key via **JWKS** verifies — right for microservices).
> - Always validate: **signature, `exp`, `iss`, `aud`, algorithm**. Reject `alg: none` and never let the token choose its own algorithm.
> - For anything beyond a single monolith, prefer `oauth2ResourceServer().jwt()` over a hand-written filter — Spring does validation, JWKS caching and key rotation for you.
>

## 1. What a JWT actually is

```text
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiJ1bWVzaCIsInJvbGUiOiJBRE1JTiJ9 . 4pZQ8s...
     header                        payload                          signature
```

```json
// header
{ "alg": "HS256", "typ": "JWT" }

// payload (claims)
{
  "sub": "umesh@gmail.com",
  "roles": ["ROLE_ADMIN"],
  "iss": "auth.mycompany.com",
  "aud": "orders-api",
  "iat": 1735200000,
  "exp": 1735200900,
  "jti": "8f14e45f-ea01-4c3e-9a72-1b1f0d7a2c31"
}
```

```text
signature = HMACSHA256( base64url(header) + "." + base64url(payload), secret )
```

### The two facts people get wrong

1. **The payload is not encrypted.** Base64 is encoding. Paste any JWT into jwt.io and read it. No passwords, no PAN, no PII beyond what you'd put in a log line.
2. **The signature is the only thing that matters.** It proves the token was issued by someone holding the key and hasn't been altered since. If you skip verification, an attacker just edits `"roles": ["ROLE_ADMIN"]` and re-encodes.

### Standard claims worth knowing

| Claim | Meaning |
|---|---|
| `sub` | Subject — who the token is about |
| `iss` | Issuer — who minted it (**validate this**) |
| `aud` | Audience — which service it's for (**validate this**) |
| `exp` | Expiry (**validate this**) |
| `iat` | Issued at |
| `nbf` | Not valid before |
| `jti` | Unique token id — the handle for a denylist |

## 2. The two flows

**Login — once:**

```text
POST /auth/login  { username, password }
     |
AuthenticationManager  ->  DaoAuthenticationProvider  ->  UserDetailsService + PasswordEncoder
     |
  valid
     |
  sign access token (15 min) + refresh token (7 days)
     |
  200  { accessToken, refreshToken }
```

**Every subsequent request:**

```text
GET /api/orders
Authorization: Bearer eyJhb...
     |
JwtAuthenticationFilter        verify signature + exp + iss/aud
     |
  build Authentication, SecurityContextHolder.setAuthentication(...)
     |
AuthorizationFilter  ->  Controller
```

**No database hit** for authentication on the second flow — that's the appeal. (Unless you call `loadUserByUsername` in the filter, which quietly gives that benefit back; building authorities straight from the claims is what makes it truly stateless.)

## 3. Spring configuration

```java
@Bean
SecurityFilterChain api(HttpSecurity http, JwtAuthenticationFilter jwtFilter) throws Exception {

    http
        .csrf(csrf -> csrf.disable())                                   // no cookies -> no CSRF vector
        .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))     // never create/use a session
        .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/**").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
        .exceptionHandling(ex -> ex
                .authenticationEntryPoint((req, res, e) -> res.sendError(401))
                .accessDeniedHandler((req, res, e) -> res.sendError(403)))
        .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class);

    return http.build();
}
```

Three lines carry the whole design: **stateless**, **no CSRF**, **filter before the form-login slot**. The filter implementation is in [[1. Filters and SecurityFilterChain]] §7.

> [!warning] `STATELESS` is not optional
> Without it Spring still creates an `HttpSession` per request and stores the context in it — you get all the memory cost of sessions and none of the benefit, plus surprising behaviour when a client happens to hold a `JSESSIONID`.

## 4. Building authorities from claims

The stateless version — no `UserDetailsService` call at all:

```java
List<GrantedAuthority> authorities = claims.get("roles", List.class).stream()
        .map(String::valueOf)
        .map(SimpleGrantedAuthority::new)
        .toList();

var auth = new UsernamePasswordAuthenticationToken(
        claims.getSubject(), null, authorities);
```

Trade-off, stated plainly:

| Approach | Per-request DB hit | Revocation |
|---|---|---|
| Authorities from claims | none | stale until the token expires |
| `loadUserByUsername` in the filter | one | current roles, instant lock-out |

Most systems take the first and keep access tokens short. Payments and admin surfaces often take the second for sensitive endpoints only.

## 5. Signing: HS256 vs RS256

| | HS256 (HMAC) | RS256 / ES256 (asymmetric) |
|---|---|---|
| Keys | One shared secret | Private key signs, public key verifies |
| Who can mint tokens | Anyone holding the secret | Only the auth server |
| Distribution | The secret must reach every verifier — and any one of them can forge tokens | Public key published via a **JWKS endpoint**; safe to hand out |
| Fits | A single monolith issuing and verifying its own tokens | **Microservices**, third-party verifiers, OAuth2/OIDC |

For anything with more than one service, RS256 + JWKS is the correct answer — services verify without ever being able to issue.

```text
Auth Server  --private key-->  signs token
Order Service  --GET /.well-known/jwks.json-->  public key  -->  verifies
```

> [!warning] Algorithm attacks
> - **`alg: none`** — a token claiming no signature. Any library that honours it accepts forged tokens. Modern libraries reject it; make sure yours does.
> - **Algorithm confusion** — an attacker flips `RS256` to `HS256` and signs with the *public* key as the HMAC secret. Never let the incoming token decide the algorithm: pin the expected algorithm in your verifier.
> - Secrets for HS256 must be **≥ 256 bits of real randomness**, from config/vault — never a string literal in `application.yml` committed to git.

## 6. The revocation problem

Stateless means the server keeps nothing, so there is nothing to delete at logout.

```text
User clicks "Logout"  ->  client deletes the token
                      ->  but a copy in an attacker's hands still works until exp
```

Same issue for "we just fired this admin" — their token keeps its `ROLE_ADMIN` claim until expiry.

The practical answers, in order of how often they're right:

1. **Short access tokens** (5–15 min) + refresh tokens. Shrinks the window to something acceptable. Most systems stop here.
2. **A denylist** of `jti` values in Redis, TTL = the token's remaining lifetime. Costs one fast lookup per request; gives instant revocation for logout and incident response.
3. **A `tokenVersion` on the user row**, included as a claim. Bump it to invalidate every token for that user (password change, role change). Requires a user lookup per request.
4. **Stateful sessions instead.** If instant revocation is a hard requirement — banking, admin consoles — sessions plus Spring Session/Redis are a perfectly good, and often better, answer.

> [!warning] Say the trade-off out loud in interviews
> "JWTs are stateless, therefore not revocable" is the single most common follow-up. The impressive answer isn't a clever hack — it's naming the trade-off and picking deliberately: short expiry for most endpoints, a denylist where revocation actually matters.

## 7. Where to store the token on the client

| Storage | XSS | CSRF | Notes |
|---|---|---|---|
| `localStorage` | ❌ readable by any injected script | ✅ safe | Convenient, the common choice, and the one security reviewers object to |
| **`HttpOnly` `Secure` cookie** | ✅ unreadable by JS | ❌ sent automatically → needs CSRF protection | Best for browsers: `SameSite=Strict/Lax` + CSRF token |
| In-memory (JS variable) | ✅ gone on reload | ✅ | Access token in memory + refresh token in an `HttpOnly` cookie is the strongest common pattern |

There is no option that's simply "safe" — you're choosing which attack to defend against with other measures. Refresh tokens in particular belong in an `HttpOnly` cookie, never in `localStorage`.

## 8. Common mistakes

- **No expiry**, or a 30-day access token → a stolen token is a permanent account takeover.
- **Sensitive data in claims** — the payload is public.
- **Not validating `iss`/`aud`** → a token minted for a different service (or a different tenant) is accepted.
- **Not verifying at all** — reading claims with a "decode" call instead of a "parse and verify" call. Know which method your library's API gives you.
- **Huge tokens** — dozens of roles inflate every request header; some proxies cap headers at 8 KB.
- **No clock-skew tolerance** — a few seconds' leeway avoids spurious `exp` failures across machines.
- **Rolling your own crypto** instead of using `oauth2ResourceServer`.

## 9. When to use `oauth2ResourceServer()` instead

If tokens come from an identity provider (Keycloak, Auth0, Cognito, Okta), don't write a filter:

```java
http.oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));
```

```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://keycloak.mycompany.com/realms/prod
```

Spring then handles JWKS fetching and caching, key rotation, algorithm pinning, and `exp`/`iss`/`aud` validation — all the parts a hand-written filter gets subtly wrong. Details in [[8. OAuth2 and OpenID Connect]].

Write your own filter only when you *are* the authorisation server, or in a single self-contained service.

## ❓ Interview Questions

### Q1. What are the three parts of a JWT?

Header (algorithm/type), payload (claims), signature. All base64url-encoded and dot-separated.

### Q2. Is a JWT encrypted?

No — signed. The payload is readable by anyone; the signature only guarantees integrity and origin. (JWE exists for encryption but is rarely used.)

### Q3. Where does the JWT filter go in the chain and why?

Before `UsernamePasswordAuthenticationFilter` — anywhere before `AuthorizationFilter` — so the `Authentication` exists when the rules are evaluated.

### Q4. How do you log out with JWT?

You can't, purely statelessly. Delete the client copy, keep access tokens short, and add a `jti` denylist in Redis (TTL = remaining lifetime) if instant revocation is required.

### Q5. HS256 vs RS256 — which and why?

HS256 shares one secret, so every verifier can also forge tokens — acceptable only inside a single service. RS256 signs with a private key and verifies with a published public key (JWKS), which is what microservices and OAuth2 need.

### Q6. What must you validate on an incoming token?

Signature (with a **pinned** algorithm), `exp`, `iss`, `aud`, and — if you use one — the denylist. Reject `alg: none`.

### Q7. Where should the client store it?

`HttpOnly` `Secure` `SameSite` cookie plus CSRF protection, or the access token in memory with the refresh token in an `HttpOnly` cookie. `localStorage` is convenient but XSS-readable.

### Q8. A user's role is revoked — when does it take effect?

Not until the token expires, if authorities come from the claims. Fix with short expiry, a `tokenVersion` claim, or loading authorities per request.

### Q9. Why is `SessionCreationPolicy.STATELESS` needed?

Otherwise Spring still creates and uses an `HttpSession`, defeating the point and producing inconsistent behaviour between clients that hold a `JSESSIONID` and those that don't.

> [!tip] ⚡ Quick Recall
> - `header.payload.signature`, base64url. **Signed, not encrypted** — never put secrets in claims.
> - JWT replaces only the **entry filter**; the rest of the pipeline is unchanged.
> - Config trio: **`STATELESS` + `csrf.disable()` + `addFilterBefore(..., UsernamePasswordAuthenticationFilter.class)`**.
> - Validate **signature (pinned alg), `exp`, `iss`, `aud`**. Reject `alg: none`; beware algorithm confusion.
> - **HS256** = shared secret, one service. **RS256 + JWKS** = microservices.
> - Stateless ⇒ **no free revocation**. Short access tokens + refresh, `jti` denylist where it matters.
> - Authorities from claims = no DB hit but stale roles; `loadUserByUsername` = fresh but a lookup per request.
> - Client storage: `HttpOnly` cookie (+CSRF) or in-memory; `localStorage` is XSS-exposed.
> - Tokens from an IdP → use **`oauth2ResourceServer().jwt()`**, not a hand-rolled filter.
