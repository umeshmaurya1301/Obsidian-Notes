The previous note was about *receiving* a token. This one is about *getting* one — your application asking Google, Okta or Keycloak to authenticate the user on its behalf. Same OAuth2 vocabulary, opposite direction, and the source of most of the confusion between the two.

> [!info] 🧭 Summary
> - **Resource Server**: your app *receives* a token and validates it. No login screen, no redirects. **OAuth2 Login**: your app *sends the user away* to an Identity Provider and gets an identity back.
> - **SSO = Single Sign-On** — log in once at the IdP, access many applications. Okta → Jira + Confluence + Slack + your Spring app, one password.
> - Actors for "Login with Google": **Resource Owner** = user · **Client** = your Spring app · **Authorization Server** = Google · **Resource Server** = Google's UserInfo/Calendar API.
> - It's the **Authorization Code Flow**: redirect → user authenticates at Google → consent → `code` back to your redirect URI → **backend exchanges `code` + `client_secret` for tokens** → fetch user info → build `Authentication`.
> - The **authorization code is not a token** — it's a short-lived single-use ticket, useless without the client secret. That's why the redirect carries a code and not an access token.
> - `client_id` / `client_secret` identify **the application** to the provider, not the user.
> - Principal becomes **`OAuth2User`** (or **`OidcUser`** with OIDC), not `UserDetails`; the `Authentication` is an **`OAuth2AuthenticationToken`**. It still lives in `SecurityContextHolder` like everything else.
> - Two Spring filters do the work: **`OAuth2AuthorizationRequestRedirectFilter`** (`/oauth2/authorization/google` → redirect out) and **`OAuth2LoginAuthenticationFilter`** (`/login/oauth2/code/google` → handle the callback).
> - The common enterprise pattern: **external identity + internal authorization** — Google says *who* you are, your own DB says *what you may do*. Wire it with a custom `OAuth2UserService`.
> - **OAuth2 Login vs SAML**: same goal (federated SSO), different era — SAML is XML/enterprise/legacy, OIDC is JSON/modern/mobile-friendly.
>

## 1. OAuth2 Login vs Resource Server

The same protocol solving two different problems. Getting these straight is half the topic.

```text
RESOURCE SERVER  (note 11)
   User --- Bearer token ---> Your API
   Your API validates it.
   No login screen. No redirects. No client_secret.

OAUTH2 LOGIN  (this note)
   User --> Your App --> redirect --> Google --> redirect back --> Your App
   Your app never sees a password.
   Login screen belongs to Google.
```

| | Resource Server | OAuth2 Login |
|---|---|---|
| Role in OAuth2 | Resource Server | **Client** |
| Config | `.oauth2ResourceServer()` | `.oauth2Login()` |
| Input | an access token in a header | a browser user with no session |
| Output | `JwtAuthenticationToken` | `OAuth2AuthenticationToken` |
| Principal | `Jwt` | `OAuth2User` / `OidcUser` |
| Redirects? | never | central to the flow |
| Session? | usually stateless | usually a session cookie |
| Needs `client_secret`? | no | yes (confidential client) |

Large systems run **both**: a server-rendered admin portal uses `oauth2Login()`, while the APIs behind it use `oauth2ResourceServer()`.

## 2. What SSO is, and why companies want it

**Single Sign-On**: authenticate once, access many applications.

```text
Company Employee
        |
        v
   Okta Login   (password + MFA, once)
        |
        +--> Jira
        +--> Confluence
        +--> Slack
        +--> Internal HR Portal
        +--> Your Spring Boot apps
```

Without SSO, every app owns an identity:

```text
Jira password
Confluence password
Slack password
Internal app password        <- four password resets, four offboarding steps
```

With SSO there is **one identity**, which means:

- One place to enforce MFA, device trust and risk detection.
- **Offboarding is a single action** — disable the user in Okta and every application loses them at once. This is the argument that actually sells SSO to security teams.
- No application stores passwords, so no application can leak them.

## 3. The actors

Using "Login with Google":

```text
User  ---->  Spring Boot App  ---->  Google
```

| OAuth2 role | Who |
|---|---|
| **Resource Owner** | the user |
| **Client** | your Spring Boot app |
| **Authorization Server** | Google |
| **Resource Server** | Google's UserInfo API (or Calendar/Drive if you asked for that scope) |

Note the shift from the last note: **here your application is the Client, not the Resource Server.**

---

## 4. What problem this solves

Your app needs a name, an email and a picture. The alternative to delegation is building and owning:

```text
Registration          Password storage + hashing
Password reset        Email verification
MFA                   Account recovery
Breach monitoring     Credential-stuffing defence
```

All of it security-critical, none of it your product. Delegating identity to Google/Okta/Keycloak removes the entire class of "we leaked passwords" incidents, because you never had any.

## 5. The full flow, step by step

This is the Authorization Code Flow. Follow it once carefully and the rest of OAuth2 stops being mysterious.

### Step 1 — user clicks

```text
https://myapp.com   ->   [ Login with Google ]
```

The link points at Spring's own endpoint, not Google's:

```text
GET /oauth2/authorization/google
```

### Step 2 — Spring redirects to Google

```text
302 Location: https://accounts.google.com/o/oauth2/v2/auth
    ?client_id=1234.apps.googleusercontent.com
    &redirect_uri=https://myapp.com/login/oauth2/code/google
    &response_type=code
    &scope=openid%20profile%20email
    &state=xyzABC123
```

**`client_id` / `client_secret`** are issued to your *application* when you register it with the provider:

```text
client_id      ~  application username   (public)
client_secret  ~  application password   (never leaves the server)
```

**`state`** is a random value Spring generates and stores in the session. It comes back on the callback and must match — that's the CSRF defence for the login flow itself, without which an attacker could inject their own authorization code and log you into *their* account.

### Step 3 — the user authenticates at Google

Email, password, MFA, device trust, risk detection, "unusual sign-in" checks. **Your application sees none of it** and there is no moment where a Google password touches your servers.

### Step 4 — consent

```text
This app wants to:
  ✓ See your name and profile picture
  ✓ See your email address
[ Allow ]  [ Deny ]
```

The user grants exactly the scopes you asked for, and can revoke them later from their Google account — which is the promise OAuth2 was built to deliver.

### Step 5 — redirect back with a code

```text
302 https://myapp.com/login/oauth2/code/google
      ?code=4/0AY0e-g7...
      &state=xyzABC123
```

> [!warning] The authorization code is **not** a token
> It's a temporary ticket, typically valid ~30–60 seconds and **single use**. It travels through the browser — URL bar, history, referrer headers, proxy logs — which is exactly why it must be useless on its own. Without your `client_secret` it cannot be exchanged for anything.

### Step 6 — back-channel exchange

Your **server** calls Google directly. No browser involved.

```text
POST https://oauth2.googleapis.com/token
    grant_type=authorization_code
    code=4/0AY0e-g7...
    client_id=...
    client_secret=...          <- proves this is really your app
    redirect_uri=...
```

```json
{
  "access_token": "ya29.a0Af...",
  "id_token": "eyJhbGciOi...",
  "refresh_token": "1//0gF...",
  "expires_in": 3600
}
```

### Step 7 — fetch the user's details

```text
GET https://www.googleapis.com/oauth2/v3/userinfo
Authorization: Bearer ya29.a0Af...
```

```json
{
  "sub": "12345",
  "email": "umesh@gmail.com",
  "name": "Umesh",
  "picture": "https://lh3.googleusercontent.com/..."
}
```

(With OIDC much of this is already inside the `id_token` — see [[13. OpenID Connect Deep Dive]].)

### Step 8 — Spring builds the `Authentication`

```text
{ "email": "umesh@gmail.com", ... }
            |
            v
   OAuth2AuthenticationToken
            |
            v
   SecurityContextHolder
```

From here on it is **indistinguishable from form login** to the rest of your application. `@PreAuthorize`, `authorizeHttpRequests` and `SecurityContextHolder` all behave exactly as in [[4. SecurityContext, Authentication and Principal]].

## 6. Configuration

```java
@Bean
SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/", "/login**").permitAll()
            .anyRequest().authenticated()
        )
        .oauth2Login(oauth -> oauth
            .loginPage("/login")                        // optional custom page
            .defaultSuccessUrl("/dashboard", true)
            .failureUrl("/login?error")
        );
    return http.build();
}
```

```properties
spring.security.oauth2.client.registration.google.client-id=1234.apps.googleusercontent.com
spring.security.oauth2.client.registration.google.client-secret=${GOOGLE_CLIENT_SECRET}
spring.security.oauth2.client.registration.google.scope=openid,profile,email
```

Google, GitHub, Facebook and Okta have **built-in provider defaults** — endpoints, user-info URI, user-name attribute — so `client-id` + `client-secret` is genuinely enough. For anything else, spell the provider out:

```properties
spring.security.oauth2.client.provider.keycloak.issuer-uri=https://auth.company.com/realms/company
spring.security.oauth2.client.registration.keycloak.client-id=portal
spring.security.oauth2.client.registration.keycloak.client-secret=${KC_SECRET}
spring.security.oauth2.client.registration.keycloak.scope=openid,profile,email,roles
spring.security.oauth2.client.registration.keycloak.authorization-grant-type=authorization_code
```

> [!warning] The redirect URI must match **exactly**
> `http` vs `https`, trailing slash, port — any difference and the provider returns `redirect_uri_mismatch`. Register `{baseUrl}/login/oauth2/code/{registrationId}` and nothing else. Behind a load balancer you also need `server.forward-headers-strategy=framework`, or Spring builds the redirect with the internal `http://pod-ip:8080` address.

## 7. What Spring creates internally

| Component | Endpoint | Job |
|---|---|---|
| `OAuth2AuthorizationRequestRedirectFilter` | `/oauth2/authorization/{registrationId}` | build the authorization URL, save `state`, redirect out |
| `OAuth2LoginAuthenticationFilter` | `/login/oauth2/code/{registrationId}` | validate `state`, exchange the code, create the `Authentication` |
| `OAuth2AuthorizedClientRepository` | — | store the access + refresh token for later API calls |
| `DefaultOAuth2UserService` | — | call the UserInfo endpoint and build the `OAuth2User` |
| `OidcUserService` | — | the OIDC variant, producing an `OidcUser` |

Both filters sit in the chain from [[1. Filters and SecurityFilterChain]] roughly where `UsernamePasswordAuthenticationFilter` would.

## 8. `OAuth2User` — `UserDetails` for OAuth

```text
Authentication (OAuth2AuthenticationToken)
      |
      +--> Principal      = OAuth2User   (attributes map)
      +--> Authorities    = OAUTH2_USER, SCOPE_email, SCOPE_profile
      +--> Authenticated  = true
      +--> AuthorizedClientRegistrationId = "google"
```

```java
@GetMapping("/me")
public Map<String, Object> me(@AuthenticationPrincipal OAuth2User user) {
    return Map.of(
        "id",    user.getName(),                 // the "sub" attribute
        "email", user.getAttribute("email"),
        "name",  user.getAttribute("name"),
        "pic",   user.getAttribute("picture")
    );
}
```

> [!warning] `OAuth2User.getName()` is not the person's name
> It returns the configured **user-name attribute**, usually `sub` — an opaque provider id like `112345678901234567890`. For a display name use `getAttribute("name")`. Also: **GitHub doesn't return an email** unless the user made it public or you request the `user:email` scope and call the emails API.

## 9. External identity + internal authorization

The near-universal enterprise requirement. Google proves *who you are*; your database decides *what you may do*.

```text
Google login succeeds
        |
        v
umesh@gmail.com
        |
        v
Look up the internal user record
        |
        v
ROLE_ADMIN, department=FINANCE, branch=BLR
```

```java
@Bean
OAuth2UserService<OidcUserRequest, OidcUser> oidcUserService(AppUserRepository repo) {
    OidcUserService delegate = new OidcUserService();

    return request -> {
        OidcUser oidcUser = delegate.loadUser(request);
        String email = oidcUser.getEmail();

        AppUser appUser = repo.findByEmail(email)
            .orElseThrow(() -> new OAuth2AuthenticationException(
                new OAuth2Error("not_provisioned"), "No account for " + email));

        Set<GrantedAuthority> authorities = new HashSet<>(oidcUser.getAuthorities());
        appUser.getRoles().forEach(r -> authorities.add(new SimpleGrantedAuthority("ROLE_" + r)));

        return new DefaultOidcUser(authorities, oidcUser.getIdToken(), oidcUser.getUserInfo(), "sub");
    };
}
```

Two design decisions worth naming in an interview:

- **Just-in-time provisioning** — create the local user on first login instead of throwing. Convenient, but then *anyone with a Google account* can sign up; gate it on an email domain or an invitation.
- **Key the local user on `sub`, not email.** Emails get reassigned and change; `sub` is stable and unique per provider. Store both, match on `sub`.

### Calling downstream APIs afterwards

Spring keeps the tokens, so you can use them:

```java
@GetMapping("/calendar")
public String events(@RegisteredOAuth2AuthorizedClient("google") OAuth2AuthorizedClient client) {
    String token = client.getAccessToken().getTokenValue();
    // call Google Calendar with it; Spring refreshes it when expired
}
```

## 10. OAuth2 Login vs traditional login

```text
Traditional                     OAuth2 Login
-----------                     ------------
Username + password             "Login with Google"
       |                               |
UserDetailsService              OAuth2UserService
       |                               |
PasswordEncoder.matches()       (Google already verified)
       |                               |
UsernamePasswordAuthToken       OAuth2AuthenticationToken
       \_______________________________/
                    |
           SecurityContextHolder      <- identical from here on
```

Same destination, different road. Everything downstream — `@PreAuthorize`, `hasRole`, `SecurityContextHolder` — is unchanged, which is precisely why Spring Security's abstraction is worth having.

## 11. OAuth2 Login vs SAML

A standard enterprise interview question.

| | OAuth2 / OIDC | SAML 2.0 |
|---|---|---|
| Format | JSON + JWT | XML |
| Era | 2012 onwards | 2005 |
| Typical IdP | Google, GitHub, Okta, Keycloak, Azure AD | ADFS, legacy corporate SSO |
| Mobile / SPA | designed for it | painful |
| Transport | REST + redirects | XML POST bindings, signed assertions |
| Spring support | `spring-boot-starter-oauth2-client` | `spring-security-saml2-service-provider` |
| Also does authorization? | yes (access tokens, scopes) | authentication only |

Both achieve federated SSO. New systems pick OIDC; SAML persists because large enterprises already run it — and Okta/Azure AD happily speak both, which is how a modern Spring app plugs into a 2008 identity estate.

## 12. Where OIDC fits

When people say "Google OAuth login" they almost always mean **OpenID Connect**. OAuth2 alone answers *"can this app access this resource?"*; it never defined a standard way to say *who the user is*. OIDC adds the **ID token** and standard claims on top. Request the `openid` scope and Spring upgrades the flow automatically — principal becomes `OidcUser` instead of `OAuth2User`. Full treatment in [[13. OpenID Connect Deep Dive]].

## ❓ Interview Questions

### Q1. What's the difference between `oauth2Login()` and `oauth2ResourceServer()`?

`oauth2Login()` makes your app an OAuth2 **Client**: it redirects the user to an Identity Provider and turns the result into a session-backed `Authentication`. `oauth2ResourceServer()` makes your app a **Resource Server**: it validates bearer tokens on incoming API calls. One obtains identity, the other consumes it.

### Q2. Walk me through "Login with Google".

Redirect to Google with `client_id`, `redirect_uri`, `scope` and `state` → user authenticates and consents at Google → Google redirects back with an authorization `code` → your **backend** exchanges the code plus `client_secret` for tokens over a direct call → fetch/decode the user's identity → build an `OAuth2AuthenticationToken` and store it in `SecurityContextHolder`.

### Q3. Why does the redirect carry a code instead of the token?

The redirect goes through the browser, so it lands in the URL bar, history, referrer headers and proxy logs. The code is short-lived, single-use, and worthless without the `client_secret`, which only your server holds. The token itself is exchanged over a direct back-channel call the browser never sees.

### Q4. What is `state` for?

CSRF protection for the login flow. Spring generates a random value, stores it in the session, and rejects the callback if it doesn't match — preventing an attacker from injecting their own authorization code and silently logging the victim into the attacker's account.

### Q5. What is SSO and what does it buy an organisation?

One identity provider authenticates the user once; many applications trust it. It centralises MFA and risk policy, removes password storage from every application, and makes offboarding a single action.

### Q6. `OAuth2User` vs `UserDetails`?

`UserDetails` is the local model: username, password hash, authorities. `OAuth2User` is an attribute map returned by the provider with no password at all. Both end up as the principal inside an `Authentication` in `SecurityContextHolder`.

### Q7. Google authenticates the user — where do my application's roles come from?

Your own database. Override the `OAuth2UserService`/`OidcUserService`, look the user up by `sub` or email after the provider call, and merge your `ROLE_*` authorities into the returned principal. External identity, internal authorization.

### Q8. OAuth2 Login vs SAML?

Same goal, different generation. SAML is XML-based, browser-POST-driven, and entrenched in large enterprises. OIDC is JSON/JWT-based, works well for SPAs and mobile, and also carries authorization via access tokens. New builds choose OIDC.

### Q9. Which Spring filter handles the callback?

`OAuth2LoginAuthenticationFilter`, on `/login/oauth2/code/{registrationId}`. `OAuth2AuthorizationRequestRedirectFilter` handles the outbound leg at `/oauth2/authorization/{registrationId}`.

### Q10. After login, how do you call the provider's API on the user's behalf?

Spring stores the tokens in an `OAuth2AuthorizedClient`. Inject it with `@RegisteredOAuth2AuthorizedClient("google")` (or use `OAuth2AuthorizedClientManager`) and it will refresh the access token for you when it expires.

> [!tip] ⚡ Quick Recall
> - **Resource Server receives a token. OAuth2 Login goes and gets one.** Your app is the **Client** here.
> - **SSO** = login once at the IdP, access many apps; centralised MFA and one-click offboarding.
> - Actors: user = Resource Owner · your app = **Client** · Google = Authorization Server · UserInfo = Resource Server.
> - Flow: redirect (`client_id`, `redirect_uri`, `scope`, `state`) → authenticate → consent → **`code`** → **back-channel exchange with `client_secret`** → user info → `Authentication`.
> - The **code is not a token**: short-lived, single-use, useless without the secret, because the browser can see it.
> - **`state`** = CSRF protection for the login flow.
> - Filters: **`OAuth2AuthorizationRequestRedirectFilter`** out, **`OAuth2LoginAuthenticationFilter`** back.
> - Principal = **`OAuth2User`** (or **`OidcUser`**); `Authentication` = **`OAuth2AuthenticationToken`**. `getName()` returns `sub`, not a display name.
> - **External identity + internal roles**: custom `OAuth2UserService`, key on `sub`, merge your own `ROLE_*`.
> - **SAML** = XML/legacy enterprise · **OIDC** = JSON/modern. Same job.
> - `redirect_uri` must match the registration **byte for byte**.
