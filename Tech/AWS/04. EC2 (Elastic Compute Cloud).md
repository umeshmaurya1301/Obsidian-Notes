EC2 is a virtual machine running in AWS. If you know VirtualBox or VMware, EC2 is the same idea with someone else's hardware, a firewall bolted on, and an API in front. Almost every AWS architecture eventually runs code on something, and EC2 is the baseline everything else is compared against.

> [!info] 🧭 Summary
> - **EC2 = a rented VM.** You pick an **AMI** (the OS image), an **instance type** (the size), a **subnet**, a **Security Group** and a **key pair**; AWS boots it in ~30 seconds.
> - **AMI** = a golden template (OS + preinstalled software + config). Bake one, launch 100 identical servers.
> - **Instance families**: **T** = burstable/cheap, **M** = balanced, **C** = CPU-heavy, **R** = memory-heavy, **I/D** = storage, **P/G/Inf** = GPU/ML. Read `m7i.large` as *family 7, Intel, size large*.
> - **Security Group** = a stateful firewall attached to the instance. Nothing gets in until you allow a port.
> - **Storage**: **EBS** = network-attached, persistent, AZ-scoped, survives a stop/start. **Instance store** = physical disk on the host, blazing fast, **wiped when the instance stops**.
> - **Pricing**: **On-Demand** (default, flexible) → **Savings Plans / Reserved** (up to ~72% off for 1–3 yr commitment) → **Spot** (up to 90% off, can be reclaimed in 2 minutes).
> - **Scaling**: **vertical** = bigger machine (hits a ceiling, needs a restart); **horizontal** = more machines behind a load balancer (AWS's preferred answer).
> - **Never store credentials on an instance** — attach an **IAM role** via the instance profile.
>

## 1. Why EC2 exists

You're building an e-commerce backend. You need CPU, memory, disk and network. The old path was: raise a purchase order, wait six weeks for servers, rack them, and hope you guessed the capacity right.

```text
Your laptop
    |
    v
AWS Data Centre  (physical host + hypervisor)
    |
    v
Virtual Machine (EC2 instance)  <- yours in ~30 seconds, billed per second
```

You choose CPU, RAM, storage and OS; AWS creates the machine. Your Spring Boot app runs on Ubuntu on EC2 and is reachable over the internet, exactly as it would be on a physical box.

## 2. Launching an instance — the five decisions

AWS asks the same five questions every time.

### 2.1 AMI — which operating system?

**AMI = Amazon Machine Image**, a template used to create instances. It contains:

- The **OS** (Amazon Linux 2023, Ubuntu, RHEL, Windows Server)
- Any **preinstalled software**
- **Configuration** and the block-device mapping

```text
Install on one server:  Java 21 + Docker + Nginx + your app
        |
        v
    Create AMI
        |
        v
Launch 100 instances -> all identical, all ready in seconds
```

> [!intuition] AMI = a golden machine template
> Like a laptop disk image. **Baking an AMI** (with Packer or EC2 Image Builder) moves install time from *boot* to *build* — instances that take 4 minutes to configure at launch take 30 seconds if the work is already in the image. This matters enormously for Auto Scaling, where slow boots mean slow reaction to traffic.

AMIs are **Region-scoped** — copy an AMI to use it in another Region. They're backed by EBS snapshots.

### 2.2 Instance type — how powerful?

Read the name as `<family><generation><attributes>.<size>`:

```text
m7i.large
|||  |
|||  +-- size:       nano < micro < small < medium < large < xlarge < 2xlarge ...
||+----- attributes: i = Intel, a = AMD, g = AWS Graviton (ARM), d = local NVMe
|+------ generation: 7 (newer = better price/performance)
+------- family:     m = general purpose
```

You do **not** need to memorise hundreds. Know the families:

| Family | Optimised for | Use it for |
|---|---|---|
| **T** (`t3`, `t4g`) | **Burstable**, cheapest | Dev boxes, low-traffic APIs, bastions |
| **M** (`m5`, `m7i`) | **Balanced** CPU:RAM (1:4) | **Spring Boot services, microservices — the default** |
| **C** (`c6`, `c7`) | **Compute** (1:2) | Video encoding, batch crunching, game servers |
| **R** (`r6`, `r7`) | **Memory** (1:8) | Caches, in-memory analytics, big JVM heaps |
| **X / z** | Extreme memory | SAP HANA, huge in-memory DBs |
| **I / D** | Local NVMe / HDD throughput | NoSQL nodes, data warehouses |
| **P / G / Inf / Trn** | GPU / ML accelerators | Training and inference |

> [!gotcha] T-family CPU credits — a real production trap
> `t3`/`t4g` instances earn **CPU credits** while idle and spend them when busy. Run hot for long enough and you exhaust the credits, and the instance is throttled to its **baseline** (as low as 10–20% of a vCPU) — your p99 latency collapses for no visible reason. `unlimited` mode lets it keep bursting *for a surcharge*. **Never put a steady-load production service on a T instance.** Use M.

**Graviton** (`m7g`, `c7g` — AWS's ARM chips) typically gives ~20% better price/performance. Java, Go, Node and Python run on ARM without code changes; the only work is rebuilding container images for `linux/arm64`.

### 2.3 Network — VPC, subnet, public IP

Which VPC and which subnet (and therefore which AZ). Public subnet + public IP = internet-reachable; private subnet = not. See [[03. VPC & Networking Basics]].

### 2.4 Security Group — the firewall

A **stateful** firewall attached to the instance's network interface. **Default inbound = deny everything.**

```text
Spring Boot API on port 8080

Security Group: sg-app
  Inbound:
    8080  from  sg-alb          <- only the load balancer
    22    from  203.0.113.0/24  <- only the office, never 0.0.0.0/0
  Outbound:
    all                          <- default
```

Stateful means: allow the inbound request and the response is automatically permitted. You never write return rules.

> [!warning] `0.0.0.0/0` = the entire internet
> `allow 22 from 0.0.0.0/0` is the most common AWS security finding in existence. Scope SSH to a known CIDR, or skip SSH altogether and use **SSM Session Manager** — no open port, no bastion host, and every session is logged in CloudTrail.

**Interview line:** *"Is a Security Group a firewall?"* — Yes. It is AWS-managed, stateful firewall rules attached to an ENI rather than to a subnet. Compare with **NACLs**, which are stateless and subnet-level.

### 2.5 Key pair, user data, IAM role

- **Key pair** — the SSH private key. AWS keeps only the public half; lose the private key and you cannot SSH in (you can still recover via SSM or by detaching the root volume).
- **User data** — a shell script that runs **once on first boot**. Good for last-mile config; bad for heavy installs (bake an AMI instead).
- **IAM role (instance profile)** — how the instance gets AWS permissions. **This is how you avoid access keys entirely.**

```bash
#!/bin/bash
# user data — runs as root on first boot
dnf install -y java-21-amazon-corretto
aws s3 cp s3://artifacts/app.jar /opt/app.jar   # works via the instance role
systemctl start app
```

## 3. Storage — EBS vs instance store

A distinction people get wrong, and it decides whether your data survives.

| | **EBS** (Elastic Block Store) | **Instance Store** |
|---|---|---|
| What | **Network-attached** virtual disk | **Physical disk on the host machine** |
| Persistence | Survives **stop/start** and termination (if configured) | **Wiped** on stop or terminate |
| Scope | **AZ-scoped** — can't attach across AZs | Tied to that physical host |
| Performance | Very good (gp3: 3,000–16,000 IOPS) | **Fastest** — local NVMe |
| Resizable | Yes, live | No |
| Snapshots | Yes → S3 | No |
| Use for | Root volumes, databases, **anything you care about** | Scratch space, caches, temp shuffle data |

**EBS volume types worth knowing:**

| Type | Character | Use |
|---|---|---|
| **`gp3`** | General purpose SSD; IOPS/throughput set **independently of size** | **The default. Always pick gp3 over gp2.** |
| `io2` / `io2 Block Express` | Provisioned IOPS SSD, highest durability | Latency-critical databases |
| `st1` / `sc1` | Throughput/cold HDD | Big sequential logs, archives |

> [!gotcha] The stop/start surprise
> Stopping an instance and starting it again gives you a **new public IP** (unless you use an Elastic IP) and **wipes any instance-store volume**. Your EBS root volume survives. "My files disappeared after a restart" is almost always instance store — or an app writing to a container's ephemeral layer.

EBS volumes are replicated within their AZ, so a single disk failure doesn't lose data — but an **AZ** failure can. Snapshots are incremental and stored in S3, which *is* multi-AZ.

## 4. Pricing models

Same hardware, wildly different prices depending on the commitment you make.

| Model | Discount | Trade-off | Use for |
|---|---|---|---|
| **On-Demand** | — | Most expensive, zero commitment | Dev, spiky/unknown load, the default |
| **Savings Plans** | up to ~72% | Commit to $/hour for 1 or 3 years | **Steady-state production** |
| **Reserved Instances** | up to ~72% | Commit to a specific type/Region | Legacy of Savings Plans; still fine |
| **Spot Instances** | up to **90%** | AWS can reclaim with a **2-minute warning** | Stateless workers, CI runners, batch, big-data |
| **Dedicated Hosts** | premium | Physical host to yourself | Licence compliance (BYOL), regulatory |

> [!example] The realistic production mix
> Cover your steady baseline with a **Savings Plan**, absorb daily peaks with **On-Demand**, and run interruption-tolerant work (CI, batch reconciliation, video transcode) on **Spot**. A stateless service behind an ASG can safely run a share of its fleet on Spot — handle the 2-minute interruption notice by draining connections and letting the ASG replace the node.

Billing is **per second** (60-second minimum) for Linux. You are billed while an instance is *running*; a **stopped** instance costs nothing for compute but **you still pay for its EBS volumes**.

## 5. Scaling — vertical vs horizontal

### Vertical scaling (scale up)

Make the machine bigger.

```text
t3.medium  (2 vCPU,  4 GB)
     |
     v
m7i.2xlarge (8 vCPU, 32 GB)
```

- Simple — no application changes.
- **Requires a stop/start** → downtime.
- **Hits a hard ceiling** — there is a biggest instance.
- Still a **single point of failure**.

### Horizontal scaling (scale out)

Add more machines behind a load balancer.

```text
        ALB
    /    |    \
  EC2   EC2   EC2      <- add/remove freely
```

- **No ceiling** — keep adding nodes.
- **Fault tolerant** — one dies, traffic reroutes.
- Requires the app to be **stateless** (no in-memory sessions, no local file storage).

> [!intuition] Why AWS pushes horizontal
> Horizontal scaling is what makes Auto Scaling, rolling deploys and AZ redundancy possible. The price of admission is statelessness: **put sessions in ElastiCache** ([[11. ElastiCache & Caching Patterns]]) and **files in S3** ([[08. S3 (Simple Storage Service)]]) instead of on the instance. Once the instance holds nothing important, it becomes disposable — and disposable is what makes everything else work.

## 6. Placement, metadata, and the rest

- **Placement groups** — *Cluster* (same rack, lowest latency, all eggs in one basket), *Spread* (separate hardware, max resilience), *Partition* (racks isolated per partition — HDFS, Kafka, Cassandra).
- **Instance metadata** — `http://169.254.169.254/latest/meta-data/`. Gives the instance its own ID, IP, and **IAM role credentials**. **Enforce IMDSv2** (token-required) so an SSRF bug in your app can't read those credentials.
- **Elastic IP** — a static public IPv4 you own. Free while attached to a running instance, **billed when idle**. Usually unnecessary: put an ALB in front instead.
- **Status checks** — *System* (AWS's hardware/network) vs *Instance* (your OS). ASG can be told to replace an instance that fails either.

## ⚠️ Gotchas & Limits

> [!warning]
> - **T-family throttling** — credits run out under sustained load and the instance is silently capped. Don't run steady production on T.
> - **Instance store is ephemeral** — a stop wipes it. Anything you care about goes on EBS or S3.
> - **EBS is AZ-scoped** — you cannot attach a volume across AZs. Snapshot and restore.
> - **A stopped instance still bills for EBS** and for any idle Elastic IP.
> - **Public IPs change** on stop/start. Use an ALB or an EIP if the address must be stable. (Since 2024, public IPv4 addresses carry an hourly charge whether idle or not.)
> - **No credentials on the box.** Instance profile, always.
> - **Termination protection is off by default**, and the root EBS volume is set to *delete on termination* — a careless terminate destroys the data.
> - Default account limits (vCPU quotas per family) will block a big scale-out until you request an increase — find this out *before* the load test, not during.

## 🔑 Key Takeaways

- **EC2 = a VM you rent by the second.** AMI (image) + instance type (size) + subnet (where) + SG (firewall) + IAM role (permissions).
- **AMI = golden template.** Bake it, launch identical fleets fast.
- **T = burstable, M = balanced, C = CPU, R = memory.** M is the default for a Spring Boot service; avoid T for steady load.
- **EBS persists and is AZ-scoped; instance store is fast and ephemeral.** `gp3` is the sane default.
- **Pricing:** On-Demand for flexibility, Savings Plans for baseline, **Spot for interruption-tolerant work at up to 90% off**.
- **Horizontal beats vertical** — but only if the app is stateless. Sessions → Redis, files → S3.
