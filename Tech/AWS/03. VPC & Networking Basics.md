IAM is the *identity* boundary; the VPC is the *network* boundary. You don't need deep networking for a backend interview — you need to be able to draw the standard picture and explain why the database is not reachable from the internet.

> [!info] 🧭 Summary
> - A **VPC** is your own isolated virtual network inside a Region, defined by a **CIDR block** (e.g. `10.0.0.0/16`).
> - A **subnet** is a slice of that CIDR **inside exactly one AZ**. Multi-AZ = multiple subnets.
> - **Public subnet** = its route table has a route to an **Internet Gateway (IGW)**. **Private subnet** = it does not. That routing rule is the *entire* difference.
> - Private resources reach *out* to the internet via a **NAT Gateway** sitting in a public subnet (outbound only — nothing can initiate a connection inward).
> - **Security Group** = **stateful**, allow-rules-only, attached to an ENI/instance. **NACL** = **stateless**, allow *and* deny, attached to a subnet, evaluated in rule-number order.
> - Standard layout: **ALB in public subnets → app in private subnets → RDS/ElastiCache in private (DB) subnets.**
> - **VPC Endpoints** let private resources reach S3/DynamoDB without a NAT Gateway. *Gateway* endpoints (S3, DynamoDB) are free; *Interface* endpoints (PrivateLink, everything else) cost per hour.
> - SGs can reference **other SGs** — `allow 5432 from sg-app` is the idiomatic way to lock a database to its application tier.
>

## 1. What a VPC is

**VPC = Virtual Private Cloud** — a logically isolated network inside an AWS Region that you control completely: IP range, subnets, routing, gateways, firewalls.

```text
AWS Account
   |
   +-- VPC   10.0.0.0/16      (Region: ap-south-1)
         |
         +-- Public  Subnet  10.0.1.0/24   (AZ: ap-south-1a)
         +-- Public  Subnet  10.0.2.0/24   (AZ: ap-south-1b)
         +-- Private Subnet  10.0.11.0/24  (AZ: ap-south-1a)
         +-- Private Subnet  10.0.12.0/24  (AZ: ap-south-1b)
                 |
                 +-- EC2 / ECS tasks / EKS pods / RDS
```

Two accounts' VPCs are completely invisible to each other unless you deliberately connect them (peering, Transit Gateway, PrivateLink).

> [!info] Every account gets a default VPC
> AWS pre-creates a default VPC per Region with public subnets in every AZ and an IGW attached — which is why "launch an EC2 and SSH in" works immediately. **Never run production in the default VPC**: everything in it is public by default.

---

## 2. CIDR in 60 seconds

A **CIDR block** is `<network address>/<prefix length>`. The prefix says how many leading bits are fixed; the rest are yours to assign.

| CIDR | Fixed bits | Usable addresses (AWS) | Typical use |
|---|---|---|---|
| `10.0.0.0/16` | 16 | ~65,531 | A whole VPC |
| `10.0.1.0/24` | 24 | **251** | One subnet |
| `10.0.1.0/28` | 28 | 11 | A tiny subnet |
| `0.0.0.0/0` | 0 | everything | "the entire internet" |

> [!gotcha] AWS reserves 5 IPs in every subnet
> A `/24` has 256 addresses but only **251 usable**. AWS takes the network address, VPC router, DNS, a future-use address, and the broadcast address. Size subnets with headroom — you cannot resize a subnet after creation, only add new ones.

Private ranges (RFC 1918) — use these for VPCs so they never clash with public internet addresses:

```text
10.0.0.0/8         10.x.x.x        <- most common for VPCs
172.16.0.0/12      172.16–31.x.x
192.168.0.0/16     192.168.x.x     <- your home router
```

Plan the range so it doesn't overlap with your office network or another VPC you'll ever peer with. **Overlapping CIDRs make peering impossible** and are painful to undo.

## 3. Public vs private subnet — it is only routing

This is the concept people over-complicate. A subnet is "public" for exactly one reason:

```text
PUBLIC SUBNET route table          PRIVATE SUBNET route table
--------------------------         ---------------------------
10.0.0.0/16  -> local              10.0.0.0/16  -> local
0.0.0.0/0    -> igw-abc123         0.0.0.0/0    -> nat-xyz789
                  ^                                  ^
             Internet Gateway                  NAT Gateway
             (in + out)                        (OUT only)
```

- **Internet Gateway (IGW)** — attached to the VPC (one per VPC), horizontally scaled and highly available by AWS. Provides **two-way** internet reachability for resources that also have a **public IP**.
- **NAT Gateway** — lives *in a public subnet*, has an Elastic IP, and translates outbound traffic from private subnets. **Outbound only.** Nothing on the internet can open a connection to a private instance through it.

> [!intuition] Why the database goes in a private subnet
> A public subnet resource with a public IP is reachable from the entire internet, and your only defence is the Security Group. A private subnet resource has **no path in at all** — even a misconfigured SG cannot expose it. Defence in depth: fix the routing, not just the firewall.

**A resource needs all three to be internet-reachable:**

1. A **public IP** (or Elastic IP),
2. a route to an **IGW**,
3. a **Security Group + NACL** that permits the traffic.

Missing any one and it isn't reachable. "My EC2 is in a public subnet but I can't SSH" is almost always #1 or #3.

## 4. Security Groups vs NACLs

Both are firewalls; they sit at different levels and behave differently. This comparison is asked constantly.

| | **Security Group** | **Network ACL** |
|---|---|---|
| Level | **Instance / ENI** | **Subnet** |
| State | **Stateful** — return traffic auto-allowed | **Stateless** — must allow return traffic explicitly |
| Rules | **Allow only** | **Allow and Deny** |
| Evaluation | All rules evaluated; any allow wins | **Numbered order**, first match wins |
| Default | Deny all in, allow all out | Default NACL allows everything |
| Can reference | Other **Security Groups** | CIDR blocks only |

### Stateful vs stateless — the actual difference

```text
SECURITY GROUP (stateful)
  Inbound  allow 8080 from 0.0.0.0/0
  Outbound (nothing needed)
  -> request in on 8080, response out is AUTOMATICALLY allowed

NETWORK ACL (stateless)
  Inbound  allow 8080 from 0.0.0.0/0
  Outbound allow 1024-65535 to 0.0.0.0/0   <- ephemeral ports, MUST be added
  -> forget the outbound rule and every response is silently dropped
```

Forgetting **ephemeral port ranges** on a NACL is the classic "the request arrives but the client times out" bug.

### The SG idiom worth memorising

Security Groups can reference **other Security Groups** as their source. This is how you build tiers without hardcoding IPs:

```text
sg-alb    inbound: 443   from 0.0.0.0/0
sg-app    inbound: 8080  from sg-alb        <- only the load balancer
sg-db     inbound: 5432  from sg-app        <- only the app tier
```

The database is now unreachable from anywhere except the app tier, no matter how instances scale or which IPs they get.

> [!warning] `0.0.0.0/0` means the entire internet
> `allow 22 from 0.0.0.0/0` (SSH open to the world) is the single most common AWS security finding. Scope SSH to your office CIDR — or better, drop SSH entirely and use **SSM Session Manager**, which needs no open port and no bastion.

## 5. The standard three-tier layout

This is the diagram to draw when asked "how would you deploy a Spring Boot app on AWS?"

```text
                        Internet
                            |
                    [ Internet Gateway ]
                            |
    +-----------------------+------------------------+
    |  PUBLIC SUBNETS  (ap-south-1a / 1b)            |
    |     ALB          NAT Gateway                   |
    +-----------------------+------------------------+
                            |  (sg-app allows 8080 from sg-alb)
    +-----------------------+------------------------+
    |  PRIVATE APP SUBNETS  (ap-south-1a / 1b)       |
    |     EC2 / ECS tasks / EKS pods  (Spring Boot)  |
    +-----------------------+------------------------+
                            |  (sg-db allows 5432 from sg-app)
    +-----------------------+------------------------+
    |  PRIVATE DB SUBNETS   (ap-south-1a / 1b)       |
    |     RDS (Multi-AZ)      ElastiCache            |
    +------------------------------------------------+
```

Why each piece:

- **ALB public** — it's the only thing that should accept internet traffic; it terminates TLS.
- **App private** — no public IP, no inbound path from the internet; reaches out via NAT for OS updates and third-party APIs.
- **DB private** — reachable only from the app tier's SG. An RDS **DB subnet group** spans ≥2 AZs so Multi-AZ failover has somewhere to go.
- **Everything duplicated across ≥2 AZs** — lose an AZ, keep serving.

## 6. VPC Endpoints — skipping the internet entirely

By default, an app in a private subnet calling S3 goes **out through the NAT Gateway, across the public internet, and back into AWS**. That costs NAT processing fees and leaves the VPC.

A **VPC Endpoint** gives you a private path to AWS services.

| Type | Services | How it works | Cost |
|---|---|---|---|
| **Gateway Endpoint** | **S3, DynamoDB only** | A route-table entry | **Free** |
| **Interface Endpoint** (PrivateLink) | Almost everything else (SQS, KMS, Secrets Manager, ECR, STS…) | An **ENI** with a private IP in your subnet | Per-hour + per-GB |

> [!example] The easy cost win
> An app writing 500 GB/month of receipts to S3 through a NAT Gateway pays NAT data-processing charges on every byte. Adding a **Gateway Endpoint for S3** is free, removes that charge entirely, and keeps the traffic off the public internet. It is usually the first thing to fix in a VPC cost review.

## 7. Connecting VPCs and networks

Enough to recognise the names:

| Option | Use for |
|---|---|
| **VPC Peering** | One-to-one VPC link. **Not transitive** — A↔B and B↔C does *not* give A↔C. |
| **Transit Gateway** | A hub for many VPCs and on-prem links. The answer once you have more than a handful of VPCs. |
| **Site-to-Site VPN** | Encrypted tunnel to your data centre over the internet. |
| **Direct Connect** | A dedicated physical circuit to AWS — consistent latency, higher cost. |
| **PrivateLink** | Expose *one service* privately to another VPC/account without exposing the whole network. |

## ⚠️ Gotchas & Limits

> [!warning]
> - **A subnet cannot span AZs**, and its CIDR cannot be changed after creation. Plan the address space up front.
> - **NAT Gateway is AZ-scoped and not free.** One per AZ for real HA — and if the AZ holding your single NAT dies, every private subnet routed through it loses internet.
> - **NACLs are stateless.** Always add the ephemeral port range (`1024–65535`) outbound, or responses vanish.
> - **Security Groups have no deny rules.** To block a specific IP you need a NACL or WAF.
> - **Overlapping CIDRs cannot be peered.** This is the #1 regret in VPC design.
> - Deleting an IGW or detaching it silently breaks every public route in the VPC.
> - An **Elastic IP that isn't attached to a running instance is billed**, unlike one that is.

---

## 🔑 Key Takeaways

- **VPC = your private network in a Region**; **subnet = a slice of it in one AZ**.
- **Public vs private is purely a route-table question**: a route to an IGW or not.
- **NAT Gateway = outbound-only internet for private subnets.** IGW = two-way, for public subnets.
- **SG = stateful, instance-level, allow-only, can reference other SGs. NACL = stateless, subnet-level, allow + deny, ordered.**
- The default architecture is **ALB public → app private → DB private, across ≥2 AZs**.
- **Gateway Endpoints for S3/DynamoDB are free** and remove both NAT cost and internet exposure.
