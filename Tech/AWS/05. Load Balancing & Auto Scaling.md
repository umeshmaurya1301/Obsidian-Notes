One server is a single point of failure and a hard capacity ceiling. A **load balancer** removes the first problem; an **Auto Scaling Group** removes the second. Together they are the reason `ALB → ASG → EC2` appears in almost every AWS architecture diagram you will ever draw.

> [!info] 🧭 Summary
> - **ELB** (Elastic Load Balancing) is the family. **ALB** = **Application Load Balancer**, the Layer-7 (HTTP/HTTPS) one you will use 90% of the time.
> - **ALB** routes on **content** — path (`/api/*`), host (`api.example.com`), header, method, query string. **NLB** is Layer 4 (TCP/UDP), ultra-fast, static IP. **GWLB** is for security appliances. **CLB** is legacy — don't use it.
> - ALB anatomy: **Listener** (port + protocol) → **Rules** (conditions) → **Target Group** (a set of targets + a health check) → **Targets** (EC2, IPs, Lambda, containers).
> - **Health checks** are the whole point: the LB stops sending traffic to any target that fails, automatically.
> - The ALB **terminates TLS** (certificate from **ACM**, free) so your app speaks plain HTTP internally, and it injects **`X-Forwarded-For`/`-Proto`**.
> - An **ASG** keeps a fleet between **min / desired / max**, spread across AZs, and **replaces unhealthy instances automatically**.
> - Scaling policies: **Target Tracking** (keep CPU at 50% — use this), **Step**, **Scheduled**, **Predictive**.
> - ASG + ALB = self-healing and elastic — but only if the app is **stateless**.
>

## 1. What is an ALB, exactly?

**ALB = Application Load Balancer**, AWS's Layer-7 load balancer and the member of the ELB family you will meet most often.

It is a **managed, highly available reverse proxy** with one DNS name in front of many backends:

```text
                Users
                  |
     my-app-alb-1234.ap-south-1.elb.amazonaws.com
                  |
            [ ALB ]   <- lives in >= 2 public subnets, AWS scales it for you
             /  |  \
          EC2  EC2  EC2   (private subnets)
```

It does five jobs:

1. **Distributes** incoming requests across healthy targets.
2. **Health-checks** targets and removes failed ones from rotation.
3. **Terminates TLS**, so certificates live in one place.
4. **Routes by content** — different paths/hosts to different backends.
5. **Gives you one stable DNS name** while instances behind it come and go.

> [!intuition] Why "Application" load balancer
> It's Layer 7 — it *parses the HTTP request*. That's what lets it route `/api/payments/*` to one target group and `/static/*` to another. An NLB sees only TCP packets and cannot do that. The trade-off is a little latency for a lot of intelligence.

### The problem it solves

```text
Without a load balancer          With an ALB
------------------------         ---------------------------
Users -> EC2-1                   Users -> ALB -> EC2-1 / EC2-2 / EC2-3
EC2-1 dies -> outage             EC2-1 dies -> ALB routes around it
Scale = a bigger box             Scale = add another box
Traffic capped by one machine    Traffic spread across the fleet
Cert on every server             Cert on the ALB only
```

## 2. ALB anatomy — Listener → Rule → Target Group → Target

This chain is the mental model. Learn it and ALB configuration stops being mysterious.

```text
                    ALB
                     |
   +-----------------+------------------+
   |                                    |
Listener :80                      Listener :443 (HTTPS, ACM cert)
   |                                    |
redirect -> 443             +-----------+-----------+
                            |           |           |
                       Rule: path    Rule: host   Default rule
                       /api/*        admin.x.com      |
                            |           |             |
                            v           v             v
                        TG-api      TG-admin       TG-web
                            |
                    Health check: GET /actuator/health -> 200
                            |
                  +---------+---------+
                  |         |         |
               EC2:8080  EC2:8080  EC2:8080
```

| Component | What it is |
|---|---|
| **Listener** | A port + protocol the ALB accepts on (`:443 HTTPS`) |
| **Rule** | Conditions (path / host / header / method / query / source IP) → an action, evaluated in **priority order**; the **default rule** catches the rest |
| **Target Group** | A named set of targets **plus a health check and a routing algorithm** |
| **Target** | An EC2 instance, an **IP address**, a **Lambda function**, or an ECS task |

**Actions a rule can take:** forward to a target group, **redirect** (HTTP→HTTPS, free, no backend hit), **return a fixed response** (maintenance page), or **authenticate** via Cognito/OIDC before forwarding.

### Health checks — the actual mechanism

The target group pings each target on a schedule:

```text
Protocol:            HTTP
Path:                /actuator/health
Healthy threshold:   2 consecutive successes  -> back in rotation
Unhealthy threshold: 2 consecutive failures   -> removed from rotation
Interval:            30 s
Timeout:             5 s
Success codes:       200
```

A target that fails is **taken out of rotation but not terminated** — the ALB just stops sending it traffic. (Terminating it is the ASG's job; see §5.)

> [!gotcha] The health-check endpoint must be shallow
> If `/actuator/health` checks the database, a brief DB blip marks **every** instance unhealthy at once and the ALB has nowhere to send traffic — you turn a degraded dependency into a total outage. Use a **liveness** endpoint that only proves the process is up, and keep the deep dependency check on a separate readiness/ops path.

### Two settings that bite

- **Deregistration delay (connection draining)** — default **300 s**. On deregistration the ALB stops sending *new* requests but lets in-flight ones finish. 300 s makes deploys crawl; 30 s is usually right, and should exceed your longest request.
- **Idle timeout** — default **60 s**. If your backend's keep-alive timeout is *shorter* than the ALB's, the ALB reuses a connection the backend just closed and you get sporadic **502s**. Always set the app's keep-alive timeout **higher** than the ALB's idle timeout.

## 3. ALB vs NLB vs GWLB vs CLB

The comparison question. Know the first two properly.

| | **ALB** | **NLB** | **GWLB** | **CLB** (legacy) |
|---|---|---|---|---|
| Layer | **7** (HTTP/HTTPS/gRPC) | **4** (TCP/UDP/TLS) | 3 (gateway) | 4 & 7 |
| Routes on | Path, host, header, method, query | IP + port only | — | Basic |
| Latency | ~ms | **~100 µs** | — | ms |
| Throughput | Very high | **Millions of req/s** | — | Lower |
| Static IP | No (DNS name only) | **Yes** — one Elastic IP per AZ | — | No |
| Preserves source IP | Via `X-Forwarded-For` header | **Yes, natively** | Yes | Via header |
| TLS termination | Yes | Yes | No | Yes |
| Targets | EC2, IP, **Lambda**, containers | EC2, IP, ALB | Appliances | EC2 |
| WebSocket / HTTP2 / gRPC | **Yes** | (passthrough) | — | No |
| Use it for | **Web apps and REST APIs — your default** | Extreme performance, non-HTTP protocols, **when the client needs a fixed IP to whitelist** | Firewalls, IDS/IPS appliances | Nothing new |

> [!example] When you actually need an NLB
> A bank partner will only call your payment API if you give them a **fixed IP to whitelist** — an ALB's IPs rotate, so the answer is an NLB with Elastic IPs (optionally with an ALB behind it, which is a supported pattern). Also: MQTT/IoT, database proxies, game servers, or anything where sub-millisecond overhead matters.

## 4. TLS, and what the ALB adds to the request

TLS terminates at the ALB, using a certificate from **ACM** (AWS Certificate Manager) — **free for use with ALB/CloudFront, and auto-renewing**.

```text
Browser --HTTPS--> ALB --HTTP--> EC2:8080
                    ^
              TLS ends here
```

The ALB then adds headers your app must trust *carefully*:

| Header | Meaning |
|---|---|
| `X-Forwarded-For` | The **real client IP** (the ALB's own IP is the TCP source) |
| `X-Forwarded-Proto` | `https` or `http` as seen by the client |
| `X-Forwarded-Port` | The client-facing port |

```properties
# Spring Boot behind an ALB — otherwise every client looks like the ALB,
# generated links come out as http://, and redirects break.
server.forward-headers-strategy=native
```

> [!warning] Only trust `X-Forwarded-For` behind a load balancer
> Directly exposed, a client can forge it. Behind an ALB in a private subnet, the ALB overwrites/appends it, so the rightmost entries are trustworthy. This matters for rate limiting and audit logs — spoofed IPs mean your per-IP throttle is worthless.

**Sticky sessions** (a cookie pinning a user to one target) are available per target group — but they are a **workaround for a stateful app**, not a design. They break even load distribution and lose the session when the target dies. The real fix is [[11. ElastiCache & Caching Patterns|session state in Redis]].

## 5. Auto Scaling Group (ASG)

The load balancer spreads traffic. The ASG decides **how many machines exist**.

### The problem

```text
Daytime:  500 users   -> need 6 servers
Night:     50 users   -> need 1 server
```

Running 6 servers all night is money set on fire. Running 1 all day is an outage.

### What an ASG does

```text
              ALB
               |
   +-----------+-----------+
   |           |           |
  EC2         EC2         EC2
  1a          1b          1c
   \___________|___________/
               |
        Auto Scaling Group
        min = 2, desired = 3, max = 10
```

Three responsibilities:

1. **Maintain the desired count** — an instance dies, a replacement launches.
2. **Scale in/out** on demand, per policy.
3. **Spread across AZs** — it balances instances evenly, so losing an AZ loses only part of the fleet.

**Configuration:**

- **Launch template** — the blueprint (AMI, instance type, SG, IAM role, user data). *Templates supersede launch configurations, which are deprecated — always use a launch template.*
- **min / desired / max** — the floor, the current target, and the ceiling.
- **Health check type** — `EC2` (hypervisor status checks only) or **`ELB`** (the target group's health check). **Use `ELB`**: a hung JVM keeps passing EC2 status checks forever while serving nothing but 502s.
- **Health check grace period** — how long a new instance gets to boot before health checks count against it. Too short and the ASG kills instances mid-startup, forever, in a loop.

### Scaling policies

| Policy | How it works | When |
|---|---|---|
| **Target Tracking** | "Keep average CPU at 50%" — ASG does the maths | **Default choice, use this** |
| **Step Scaling** | CPU > 70% add 2; CPU > 90% add 4 | When you need graduated response |
| **Simple Scaling** | One alarm, one action, cooldown | Legacy |
| **Scheduled** | Scale to 10 at 09:00 Mon–Fri | Known patterns — market open, salary day |
| **Predictive** | ML forecasts load and pre-scales | Strong daily/weekly cycles |

Good target-tracking metrics: **`ASGAverageCPUUtilization`**, or better for a web tier, **`ALBRequestCountPerTarget`** — requests per instance tracks load far more honestly than CPU for I/O-bound Spring Boot services.

> [!gotcha] Scaling is not instant
> Alarm evaluation (~1–3 min) + instance launch + OS boot + JVM/Spring startup + health checks passing = **3–8 minutes** before a new instance takes traffic. A traffic spike will hurt before scaling helps. Mitigations: **bake a fast AMI**, scale on a *leading* indicator (request count, queue depth) rather than CPU, keep `min` above your true floor, use **warm pools** for pre-initialised instances, or move to containers where startup is seconds.

**Lifecycle hooks** pause an instance in `Pending:Wait` or `Terminating:Wait` so you can run setup, or drain connections and ship final logs before it dies.

## 6. Putting it together

The reference architecture, and the answer to *"How would you host a Spring Boot application on AWS?"*

```text
                     Internet
                        |
                   Route 53 (DNS)
                        |
                  [ ALB ]  public subnets, AZ-a + AZ-b, ACM cert
                        |  health check: /actuator/health
             +----------+----------+
             |          |          |
           EC2        EC2        EC2      private subnets
          (AZ-a)     (AZ-b)     (AZ-a)
             \__________|__________/
                        |
                Auto Scaling Group
                min 2 / desired 3 / max 10
                target tracking @ 50% CPU
                        |
                        v
             RDS PostgreSQL (Multi-AZ)  +  ElastiCache Redis
                        |
                        v
                   S3 (files)
```

What each piece buys you:

- **ALB** — one address, TLS, content routing, removes unhealthy targets.
- **ASG across AZs** — survives an instance failure *and* an AZ failure, and matches capacity to load.
- **Private subnets** — the app has no inbound path from the internet.
- **RDS Multi-AZ + Redis + S3** — because the instances must stay **stateless** for any of this to work.

> [!info] The self-healing loop
> ALB health check fails → target removed from rotation → ASG (health check type `ELB`) sees it as unhealthy → terminates it → launches a replacement from the launch template → new instance passes health checks → ALB adds it back. **Nobody was paged.** That loop is the single most valuable thing to be able to narrate in an interview.

## ⚠️ Gotchas & Limits

> [!warning]
> - **An ALB needs at least two subnets in different AZs.** It will not create otherwise.
> - **Deep health checks cause total outages** — a DB blip fails every target at once. Keep the LB's check shallow.
> - **502 from an ALB** is usually the idle-timeout mismatch (§2) or the app returning a malformed response. **503** usually means *no healthy targets at all*.
> - **ALB has no static IP.** Whitelisting requirements need an NLB.
> - **ASG health check type defaults to `EC2`**, which cannot detect an application that's up but broken. Change it to `ELB`.
> - **Too short a grace period** = an infinite launch/terminate loop. Too long = broken instances serve traffic.
> - **Sticky sessions hide statefulness**; the session still dies with the instance. Externalise it.
> - **Cross-AZ data transfer between ALB and targets is billed.** ALBs have cross-zone load balancing always on (and free); **NLBs charge for it**.
> - Scaling in can kill an instance **mid-request** — set a sensible deregistration delay and use a `Terminating:Wait` lifecycle hook.

---

## 🔑 Key Takeaways

- **ALB = Layer-7 managed reverse proxy.** One DNS name, health checks, TLS termination, content-based routing.
- The chain is **Listener → Rule → Target Group → Target**, and the **target group owns the health check**.
- **ALB for HTTP; NLB for L4 speed, non-HTTP protocols, or a static IP.** GWLB for appliances, CLB never.
- **ASG = correct number of healthy instances**, spread across AZs, self-healing. Use **`ELB` health checks** and **target tracking**.
- `ALB → ASG → EC2 → RDS` is the reference architecture; recite it.
- All of it depends on the app being **stateless** — sessions in Redis, files in S3.
