# Lectures 4–6 – AWS IAM (Identity & Access Management)

> [!info] Overview
> **IAM** controls **who** (authentication) can do **what** (authorization) on **which** AWS resources. It is a **global**, **free** service — identities are not tied to a Region. Everything in IAM reduces to four building blocks: **User, Group, Role, Policy** — identities that *do* things, and policies that *permit* things.

---

## 🎯 Key Concepts

### What is IAM
- The service that manages **access** to your AWS account and its resources.
- Two jobs: **Authentication** (prove who you are) and **Authorization** (decide what you're allowed to do).
- **Global** service — an IAM user/role works across all Regions; there's no per-Region copy.
- **Free** — no charge for IAM itself, only for the resources identities use.

### Root User vs IAM User
- The **root user** is the email you signed up with — it has **unrestricted** access and *cannot be limited by policy*.
- Best practice: **lock it away** (enable MFA, don't create access keys for it, don't use it daily). Create IAM users/roles for actual work.

### IAM Entities — the four building blocks
- **User** — a single identity for a person or an application.
- **Group** — a collection of users; a convenient way to attach permissions to many users at once.
- **Role** — an identity that is **assumed temporarily**; no permanent credentials.
- **Policy** — a **JSON document** that defines permissions; attached to the identities above.

---

## 🛠️ How It Works

### IAM User
- Identity for one person/app. Two ways a user authenticates:

| Access type | Used for | Credentials |
|---|---|---|
| **Console access** | Web sign-in (humans) | **Username + password** (+ MFA recommended) |
| **Programmatic access** | CLI / SDK / API (apps & automation) | **Access Key ID + Secret Access Key** |

- The **secret access key** is shown **only once** at creation — store it safely; if lost, rotate (create new, delete old).
- A user starts with **no permissions** — access is granted purely by attached policies.

### IAM Group
- A bucket of users; attach a policy to the group and **every member inherits** it.
- A user can belong to **multiple groups**; manage permissions by group, not per-user.
- **A group is *not* an identity** — it has no credentials and **can't be a `Principal`** (you can't "assume a group" or grant a resource to a group). Groups also **can't be nested**.

### IAM Role
- An identity with **no long-term credentials** — when *assumed*, it issues **temporary credentials** via **`STS`** (Security Token Service).
- Granted by **assuming** the role, not by logging in. Common uses:
  - **EC2 instance** needing AWS access → attach a role (via **instance profile**) instead of hard-coding keys.
  - **AWS service → service** (e.g. Lambda reading from S3).
  - **Cross-account access** — let another AWS account assume a role in yours.
  - **Federation** — external/corporate identities (SSO, web identity) get temporary access.
- **Why roles win:** no static keys to leak, credentials auto-rotate and expire.

### IAM Policy
- A **JSON** document listing permissions. Two categories by *what they attach to*:

**1. Identity-based policy** — attached to a **user / group / role** ("what can *this identity* do?").
  - **AWS-managed** (maintained by AWS), **customer-managed** (your reusable policies), or **inline** (embedded in one identity).

**2. Resource-based policy** — attached to the **resource itself** ("who can touch *this resource*?").
  - Always includes a **`Principal`** (which identity is allowed). Examples: **S3 bucket policy**, **SQS queue policy**, **KMS key policy**, Lambda resource policy.

> [!example] Policy document shape
> ```json
> {
>   "Version": "2012-10-17",
>   "Statement": [
>     {
>       "Effect": "Allow",
>       "Action": ["s3:GetObject", "s3:PutObject"],
>       "Resource": "arn:aws:s3:::my-bucket/*",
>       "Condition": { "IpAddress": { "aws:SourceIp": "10.0.0.0/16" } }
>     }
>   ]
> }
> ```
> Key fields: **`Effect`** (Allow/Deny) · **`Action`** (the API calls) · **`Resource`** (the ARN) · **`Principal`** (only in resource-based policies) · **`Condition`** (optional rules).

### How a request is evaluated
1. **Explicit `Deny`** anywhere → **denied** (always wins).
2. Else an **explicit `Allow`** → **allowed**.
3. Else → **implicit deny** (default is *no access*).

---

## ⚠️ Gotchas & Limits
> [!warning]
> - **Explicit deny always overrides allow** — a single `Deny` beats any number of `Allow`s.
> - **Default is deny** — identities start with zero permissions; nothing is allowed until a policy grants it.
> - **Don't use the root user** for everyday tasks, and **never create root access keys**. Enable **MFA** on root.
> - **Secret access key is shown once.** Lost = rotate, not recover. Never commit keys to git or bake into AMIs/code.
> - **Group ≠ identity** — can't be a `Principal`, can't be assumed, can't be nested.
> - **Prefer roles over long-lived access keys** for EC2/Lambda/cross-account — temporary creds beat static secrets.
> - IAM is **eventually consistent & global** — policy changes propagate quickly but aren't guaranteed instant.

---

## 🔑 Key Takeaways
- IAM = **authentication + authorization**, and it's **global + free**.
- Four entities: **User** (one identity) · **Group** (users + shared policy) · **Role** (temporary, assumed) · **Policy** (JSON permissions).
- User login: **console = username/password**, **programmatic = access key + secret**.
- Policies: **identity-based** (on the identity) vs **resource-based** (on the resource, needs a `Principal`).
- Evaluation: **explicit Deny → explicit Allow → implicit Deny (default)**.
- **Least privilege** + **roles over static keys** + **MFA** = the security baseline.

---

## 🎤 Interview Tips
- Lead with **least privilege**: grant only the actions/resources needed, widen later — never start broad.
- For "an EC2 instance/Lambda needs to call S3," answer **IAM role**, *not* embedding access keys — temporary `STS` credentials, auto-rotated.
- Know the **identity-based vs resource-based** distinction; the giveaway for resource-based is the **`Principal`** element (e.g. S3 bucket policy for cross-account access).
- State the **evaluation order** crisply — **explicit deny wins, default is deny** — it's a classic checkpoint question.
- Mention **IAM is global** (catches people who assume it's regional like most AWS services).
