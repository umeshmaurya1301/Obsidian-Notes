# Lecture 2 – AWS Global Infrastructure (Part 1)

> [!info] Overview
> AWS runs a worldwide network of data centers organized into a clear hierarchy so you can deploy close to users and survive failures. The building blocks, from largest to smallest footprint: **Regions** → **Availability Zones (AZs)** → **Local Zones** → **Edge Locations (PoPs)**. This part covers what each one is and when you'd reach for it.

---

## 🎯 Key Concepts

### Region
- A **geographic area** (e.g. `us-east-1` = N. Virginia, `ap-south-1` = Mumbai) containing a cluster of isolated data centers.
- Each Region is **fully independent** — isolated from other Regions for fault tolerance and data sovereignty. Data doesn't leave a Region unless you explicitly move it.
- A Region contains **multiple AZs** (typically 3+).
- **How you choose a Region:**
  - **Compliance / data residency** — laws may require data to stay in-country.
  - **Latency** — pick the Region closest to your users.
  - **Pricing** — per-service cost varies by Region.
  - **Service availability** — not every service launches in every Region at once.

### Availability Zone (AZ)
- One or more **discrete data centers** within a Region, each with redundant power, cooling, and networking.
- AZs are **physically separated** (km apart) but linked by **high-bandwidth, low-latency** private fiber — far enough to isolate disasters, close enough for synchronous replication.
- Named by appending a letter to the Region: `us-east-1a`, `us-east-1b`, `us-east-1c`.
- **Purpose: high availability.** Deploy across **multiple AZs** so one data-center failure doesn't take your app down.

### Local Zone
- An **extension of a Region** placed in a large metro/population center that isn't itself a full Region.
- Puts select compute, storage, and database services **physically closer to end users** for **single-digit-millisecond latency**.
- Attached to a **parent Region** (you opt in to enable it).
- **Use cases:** latency-sensitive workloads — real-time gaming, live video streaming, media/entertainment rendering, AR/VR.

### Edge Location (PoP — Point of Presence)
- A site that **caches content close to users**, separate from Regions/AZs — there are **far more** Edge Locations than Regions.
- Powers AWS's content-delivery and edge networking services:
  - **`CloudFront`** (CDN) — caches static/dynamic content near users.
  - **`Route 53`** (DNS), **`AWS Global Accelerator`**, **`AWS Shield`** / **`WAF`** (edge security).
- Cuts latency by serving requests from the nearest PoP instead of the origin Region.
- **Regional Edge Caches** sit between origin servers and Edge Locations to hold less-frequently-accessed content longer.

---

## 🛠️ How It Works — The Hierarchy

```
AWS Global Infrastructure
└── Region (us-east-1)           ← geographic area, independent
    ├── Availability Zone (1a)   ← 1+ isolated data centers
    ├── Availability Zone (1b)
    └── Availability Zone (1c)

Local Zone        → extends a Region into a nearby metro (low latency)
Edge Location/PoP → global cache/CDN tier (CloudFront, Route 53, etc.)
```

> [!example] Putting it together
> A user in Mumbai hits your app: a static asset is served from the **Edge Location** in Mumbai (cached by `CloudFront`), while the API runs on `EC2` spread across **AZs** `ap-south-1a/1b/1c` in the **Mumbai Region** so a single data-center outage doesn't cause downtime. If you needed sub-ms latency for a game in a city without a Region, you'd enable a **Local Zone** there.

---

## ⚠️ Gotchas & Limits
> [!warning]
> - **AZ ≠ a single data center** — an AZ can be *multiple* data centers; it's the unit of fault isolation, not a single building.
> - **AZ letters aren't fixed across accounts** — `us-east-1a` may map to a different physical AZ in another account (AWS randomizes the mapping to balance load). Use **AZ IDs** (`use1-az1`) when correlation matters.
> - **Edge Location ≠ AZ** — Edge Locations don't run your `EC2`/RDS workloads; they're a caching/CDN/DNS tier only.
> - **Not all services are global** — most are Region-scoped; deploying in one Region doesn't replicate to others automatically.
> - **Local Zones are opt-in** and offer a **subset** of services, not the full Region catalog.

---

## 🔑 Key Takeaways
- Hierarchy: **Region → AZ**, with **Local Zones** and **Edge Locations** as extensions for latency/delivery.
- **Region** = isolated geographic area; choose by compliance, latency, price, service availability.
- **AZ** = isolated data center(s) for **high availability**; always go multi-AZ for production.
- **Local Zone** = Region extension for ultra-low latency in a specific metro.
- **Edge Location (PoP)** = global cache/CDN tier behind `CloudFront`, `Route 53`, `Global Accelerator`.

---

## 🎤 Interview Tips
- "How do you make a system fault-tolerant on AWS?" → **multi-AZ** is the baseline answer; **multi-Region** for disaster recovery / global resilience.
- Be able to distinguish the tiers crisply: **Region** (geography/isolation) vs **AZ** (HA within a Region) vs **Edge** (latency/CDN). Interviewers probe whether you conflate AZs with Edge Locations.
- Tie **Region choice** to real constraints (data residency laws, user latency) — shows you think about non-functional requirements, not just architecture diagrams.
