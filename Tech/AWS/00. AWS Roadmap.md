# ☁️ AWS Roadmap

The index for these notes. Eleven notes covering the 80/20 of AWS for a backend engineer — enough to design and defend a production architecture in an SDE-2 interview, not enough to pass a Solutions Architect exam. That trade is deliberate.

> [!info] How to use this
> Read **01 → 11 in order** the first time; each note assumes the one before it. Notes **04–11** are the services you'll actually be asked about; **01–03** are the foundations that make the rest coherent. After the first pass, revise from the **🧭 Summary** callout at the top of each note (the whole note in bullets) and the **⚡ Quick Recall** table at the bottom (the night-before pass).

## 🏗️ The architecture to be able to draw

If you can draw this from memory and justify every box, you've covered most of what a backend interview asks about AWS.

```text
                          Internet
                              |
                        Route 53 (DNS)
                              |
                     [ ALB ]  public subnets, AZ-a + AZ-b
                              |  ACM cert, TLS terminates here
                              |  health check /actuator/health
              +---------------+---------------+
              |               |               |
         ECS Task        ECS Task        ECS Task     private subnets
         (AZ-a)          (AZ-b)          (AZ-a)       Fargate
              \_______________|_______________/
                              |
                    ECS Service (desired 3)
                    + Service Auto Scaling
                              |
        +---------------+-----+-------+---------------+
        |               |             |               |
   RDS PostgreSQL   ElastiCache      S3          DynamoDB
   (Multi-AZ)       Redis          files       sessions /
   + read replicas  cache+session  presigned   idempotency keys
        |
   RDS Proxy (if Lambda is in the picture)

   Event-driven side:
        S3 PUT  ->  Lambda  ->  thumbnail / CSV import
```

**Why each box exists:**

| Box | Justification |
|---|---|
| **ALB** | One stable address, TLS termination, health checks, removes dead targets |
| **≥2 AZs everywhere** | Survive a data-centre failure — the HA baseline |
| **Private subnets for app + DB** | No inbound path from the internet at all |
| **ASG / Service Auto Scaling** | Match capacity to load; replace unhealthy instances automatically |
| **RDS Multi-AZ** | Automatic failover, ~zero data loss |
| **Read replicas** | Scale reads without touching the primary |
| **ElastiCache** | Take read load off the DB; **hold sessions so servers stay stateless** |
| **S3** | Files off the instances — the other half of statelessness |
| **IAM roles** | No credentials anywhere in code or images |

## 🔁 The cross-cutting themes

Four ideas run through every note. Interviewers are really testing these, using service names as the vehicle.

> [!intuition] 1. Statelessness is the keystone
> Auto Scaling, rolling deploys, self-healing and multi-AZ all assume **an instance can vanish without consequence**. Sessions → [[11. ElastiCache & Caching Patterns|Redis]], files → [[08. S3 (Simple Storage Service)|S3]], data → [[09. RDS & Aurora|RDS]]. Every "how do I keep X on the server?" question has the same answer: don't.

> [!intuition] 2. Multi-AZ is the default unit of resilience
> ALB across AZs, ASG across AZs, RDS Multi-AZ, S3 across ≥3 AZs. When asked "how do you make it highly available?", the first answer is always **spread it across Availability Zones**.

> [!intuition] 3. Identity beats credentials
> Every "how does service A talk to service B?" answer is **an IAM role**, never an access key. Instance profile, task role, IRSA, execution role — same idea each time.

> [!intuition] 4. Availability and scalability are different problems
> Multi-AZ ≠ read replicas. A load balancer ≠ auto scaling. A cache ≠ a database. Interviewers deliberately conflate them to see whether you'll separate them.
