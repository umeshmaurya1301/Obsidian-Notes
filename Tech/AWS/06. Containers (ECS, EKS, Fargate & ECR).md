You already know Docker and Kubernetes, so this note is mostly a mapping exercise: which AWS service plays which role, and the one decision interviewers actually care about — **ECS or EKS, and why**.

> [!info] 🧭 Summary
> - **ECR** = AWS's private Docker registry ("AWS Docker Hub"). Images live here; ECS/EKS pull from it.
> - **ECS** = AWS's own container orchestrator. Proprietary, simple, deeply integrated, **free** (you pay only for the compute).
> - **EKS** = **managed Kubernetes**. AWS runs the control plane (~$0.10/hr); you get standard K8s, portability and the whole ecosystem — plus its complexity.
> - **Fargate** is **not an orchestrator — it's a launch type.** It's *serverless compute* that both ECS and EKS can run tasks/pods on, so you manage no EC2 nodes at all.
> - The real axis is **EC2 launch type vs Fargate** (do I manage nodes?) crossed with **ECS vs EKS** (whose orchestrator?).
> - ECS vocabulary: **Task Definition** (≈ pod spec) → **Task** (a running instance) → **Service** (keeps N tasks alive + registers them with an ALB) → **Cluster**.
> - Permissions: the **task execution role** pulls the image and writes logs; the **task role** is what *your code* uses. Two different roles — a classic gotcha.
> - **Choose ECS** when you're all-in on AWS and want less to operate. **Choose EKS** when you already run Kubernetes, need portability, or need the K8s ecosystem.
>

## 1. Why containers, on AWS

```text
Yesterday                     Today
--------------------------    ------------------------------------
Spring Boot -> EC2            Spring Boot -> Docker image -> ECS / EKS
Bake an AMI per release       Build an image per release
Boot time: minutes            Start time: seconds
"Works on my machine"         Same image dev -> staging -> prod
Instance = the unit           Container = the unit; instances are cattle
```

The payoff over plain EC2 + ASG: **faster deploys, denser packing** (many containers per host), **environment parity**, and **finer-grained scaling** — you scale a container, not a whole VM.

## 2. ECR — where images live

**ECR = Elastic Container Registry.** A private, IAM-authenticated Docker registry.

```text
docker build -t payments-api .
        |
        v
   ECR repository
   1234.dkr.ecr.ap-south-1.amazonaws.com/payments-api:v1.4.2
        |
        v
   ECS task / EKS pod pulls the image
```

```bash
# Auth is IAM, not a username/password — the token lasts 12 hours
aws ecr get-login-password --region ap-south-1 \
  | docker login --username AWS --password-stdin \
      1234.dkr.ecr.ap-south-1.amazonaws.com

docker push 1234.dkr.ecr.ap-south-1.amazonaws.com/payments-api:v1.4.2
```

Worth knowing:

- **Image scanning** — ECR scans pushed images for CVEs (basic scanning is free; enhanced uses Amazon Inspector).
- **Lifecycle policies** — auto-expire old images. Without one, ECR storage grows forever and you pay for a thousand dead builds.
- **Immutable tags** — turn this on. It prevents anyone re-pushing `v1.4.2` with different content, which makes rollbacks trustworthy.
- **Pull-through cache** — mirrors Docker Hub images into ECR, avoiding Docker Hub rate limits in CI.

> [!gotcha] Pulling ECR from a private subnet
> A task in a private subnet needs a route to ECR. Either a **NAT Gateway**, or — better and cheaper — **interface VPC endpoints for `ecr.api` and `ecr.dkr` plus a *gateway* endpoint for S3** (ECR stores the actual image layers in S3, so forgetting the S3 endpoint means pulls still fail).

## 3. ECS — AWS's own orchestrator

**ECS = Elastic Container Service.** AWS's proprietary orchestrator: you declare what should run, ECS keeps it running.

### The four nouns

```text
Cluster
  |
  +-- Service: payments-api   (desired count = 3, attached to a Target Group)
        |
        +-- Task  <- a running instance of a Task Definition
        +-- Task
        +-- Task
              |
              +-- Container(s)  <- your Docker image
```

| ECS noun | Kubernetes equivalent | What it is |
|---|---|---|
| **Task Definition** | Pod spec / Deployment template | JSON blueprint: image, CPU, memory, ports, env vars, secrets, log config, IAM roles. **Versioned** — every change makes a new revision. |
| **Task** | Pod | One running instance of a task definition |
| **Service** | Deployment + Service | Maintains N tasks, replaces failures, registers targets with an ALB, runs rolling deploys |
| **Cluster** | Cluster | The logical grouping |

```json
// Task definition, trimmed to the parts that matter
{
  "family": "payments-api",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "1024", "memory": "2048",
  "executionRoleArn": "arn:aws:iam::123:role/ecsTaskExecutionRole",
  "taskRoleArn":      "arn:aws:iam::123:role/payments-api-task-role",
  "containerDefinitions": [{
    "name": "app",
    "image": "1234.dkr.ecr.ap-south-1.amazonaws.com/payments-api:v1.4.2",
    "portMappings": [{ "containerPort": 8080 }],
    "secrets": [
      { "name": "DB_PASSWORD",
        "valueFrom": "arn:aws:secretsmanager:ap-south-1:123:secret:prod/db" }
    ],
    "logConfiguration": { "logDriver": "awslogs" }
  }]
}
```

> [!warning] Two IAM roles, and people constantly confuse them
> - **`executionRoleArn`** — used by the **ECS agent**, *before* your code runs: pull the image from ECR, fetch secrets, write to CloudWatch Logs.
> - **`taskRoleArn`** — used by **your application code**: read S3, query DynamoDB, publish to SQS.
>
> "Access denied pulling image" → execution role. "Access denied calling S3 from my app" → task role.

**Network mode `awsvpc`** gives each task its **own ENI and private IP**, so a task gets its own Security Group and looks exactly like an EC2 instance to the rest of the VPC. This is the mode Fargate requires and the one you should use.

## 4. Fargate — the axis people get wrong

> [!intuition] Fargate is not a competitor to ECS or EKS
> **Fargate is a *launch type* — serverless compute that ECS or EKS runs your containers on.** The question isn't "ECS vs Fargate"; it's "ECS-on-EC2 vs ECS-on-Fargate".

```text
                    Who orchestrates?
                 ECS                 EKS
             +--------------------+--------------------+
  EC2        | You manage the EC2 | You manage the     |
  launch     | container hosts.   | worker nodes.      |
  type       | Cheapest at scale, | Full control,      |
             | you patch nodes.   | DaemonSets, GPUs.  |
             +--------------------+--------------------+
  Fargate    | No servers at all. | No nodes at all.   |
             | Per-task billing.  | Per-pod billing.   |
             | THE DEFAULT.       | Fewer K8s features.|
             +--------------------+--------------------+
```

| | **EC2 launch type** | **Fargate** |
|---|---|---|
| You manage | The host instances (patching, scaling, capacity) | **Nothing** |
| Billing | Per **instance**, whether packed or idle | Per **task's vCPU + memory**, per second |
| Density | Pack many containers per host | One task = its own micro-VM |
| Start time | Fast (host already warm) | ~30–60 s (provisions a micro-VM) |
| Cost | **Cheaper at steady high utilisation** | Cheaper for spiky/low utilisation; less ops |
| Special hardware | GPUs, huge instances, custom kernels | Not available |
| Isolation | Shared kernel between tasks | **Own micro-VM per task** (stronger) |

**Default to Fargate.** Move to the EC2 launch type when you have steady, high, predictable utilisation (where bin-packing genuinely saves money), or need GPUs, DaemonSets, or privileged containers.

## 5. EKS — managed Kubernetes

**EKS = Elastic Kubernetes Service.** AWS runs the **control plane** (API server, etcd, scheduler) across multiple AZs; you run the workloads.

```text
   AWS-managed control plane   ($0.10/hr per cluster)
   api-server + etcd + scheduler, multi-AZ, patched by AWS
              |
   +----------+-----------+-------------------+
   |                      |                   |
Managed Node Groups    Fargate profiles    Karpenter
(EC2 you own)          (serverless pods)   (fast autoscaling)
```

Your existing Kubernetes knowledge transfers directly — `kubectl`, Deployments, Services, Helm all work unchanged. What's AWS-specific:

| Concern | AWS piece |
|---|---|
| Pod → IAM permissions | **IRSA** (IAM Roles for Service Accounts, via OIDC) — or the newer **EKS Pod Identity** |
| `Service type: LoadBalancer` / `Ingress` | **AWS Load Balancer Controller** → provisions an NLB / ALB |
| Pod networking | **VPC CNI** — every pod gets a **real VPC IP** |
| Persistent volumes | **EBS CSI** / **EFS CSI** drivers |
| Node autoscaling | **Cluster Autoscaler**, or **Karpenter** (faster, picks instance types itself) |
| Cluster auth | IAM identities mapped to K8s RBAC via access entries |

> [!gotcha] The VPC CNI IP-exhaustion trap
> Because every pod consumes a **real VPC IP**, subnet sizing becomes a capacity limit. A `/24` (251 usable) can be exhausted by a few dozen pods, and each instance type also caps how many ENIs/IPs it can hold. Plan **large subnets** (`/20` or bigger) for EKS, or enable prefix delegation. This surprises teams migrating from on-prem Kubernetes, where pod IPs were overlay-only.

## 6. ECS vs EKS — the decision

| | **ECS** | **EKS** |
|---|---|---|
| Orchestrator | AWS proprietary | **Standard Kubernetes** |
| Learning curve | Low — a few nouns | High — the full K8s surface |
| Control-plane cost | **Free** | ~**$73/month** per cluster |
| Portability | **AWS lock-in** | **Portable** — same manifests on GKE/AKS/on-prem |
| Ecosystem | AWS-native only | Helm, Istio, ArgoCD, Prometheus, operators |
| Ops burden | Minimal | Real — upgrades, add-ons, CRDs |
| Team needs | Any backend team | Someone who genuinely knows K8s |

> [!info] The interview answer
> "**ECS** if we're committed to AWS and want the smallest operational surface — it's free, deeply integrated with ALB/IAM/CloudWatch, and a small team can run it. **EKS** if we already have Kubernetes expertise, need multi-cloud portability, or want the CNCF ecosystem — Helm, operators, service mesh. The trade is standardisation and portability against a real increase in operational complexity, plus a control-plane bill. For a greenfield service on a small team I'd start with **ECS on Fargate**; for an org already running Kubernetes, EKS is obvious."

Say **why**, not just which. And note that **Fargate is available for both**, so "I don't want to manage servers" doesn't decide it.

## 7. The containerised reference architecture

```text
   Developer push
        |
   CI (CodeBuild / GitHub Actions)
        |  docker build + push
        v
      ECR  (payments-api:v1.4.2, scanned, immutable tag)
        |
        |  pull
        v
                    Internet
                       |
                   [ ALB ]  public subnets, ACM cert
                       |  target group: IP targets (awsvpc)
        +--------------+--------------+
        |              |              |
   ECS Task       ECS Task       ECS Task     private subnets, Fargate
   (AZ-a)         (AZ-b)         (AZ-a)
        \______________|______________/
                       |
              ECS Service (desired 3)
              + Service Auto Scaling
                       |
                       v
        RDS (Multi-AZ)   ElastiCache   S3   Secrets Manager
```

Compared with [[05. Load Balancing & Auto Scaling|the EC2 version]], the ALB, private subnets, multi-AZ spread and stateless requirement are **identical** — only the unit of deployment changed. **Service Auto Scaling** replaces the ASG and reacts in seconds rather than minutes, because there's no OS to boot.

## ⚠️ Gotchas & Limits

> [!warning]
> - **Execution role vs task role** — the single most common ECS permissions bug.
> - **Fargate has no privileged mode, no GPUs, no DaemonSets**, and limited fixed CPU/memory combinations.
> - **Fargate ephemeral storage** defaults to 20 GB (configurable to 200 GB) and is **wiped when the task stops**. Containers are stateless — files go to S3, state to RDS/Redis.
> - **EKS control plane costs even when idle.** Ten dev clusters = $730/month before a single pod runs.
> - **EKS version upgrades are your job** — AWS supports each K8s version for a limited window, then force-upgrades you.
> - **VPC CNI IP exhaustion** — size EKS subnets generously.
> - **ECR with no lifecycle policy** grows without bound.
> - `awsvpc` mode consumes an ENI per task, and **each instance type caps ENIs** — this limits task density on the EC2 launch type.
> - Set a container **health check** *and* an ALB target-group health check; they serve different purposes (restart vs. de-register).

## 🔑 Key Takeaways

- **ECR** stores images; **ECS/EKS** run them; **Fargate** is the serverless *compute* both can use.
- ECS nouns: **Task Definition → Task → Service → Cluster**. The **service** keeps N tasks alive and wires them to the ALB.
- **Two IAM roles per task**: execution (pull image, fetch secrets, logs) and task (your app's own AWS calls).
- **ECS = simple, free, AWS-locked. EKS = standard, portable, ecosystem-rich, more work + a control-plane bill.**
- **Default to Fargate**; switch to EC2 launch type for steady high utilisation, GPUs, or DaemonSets.
- The surrounding architecture (ALB, private subnets, multi-AZ, stateless) doesn't change from the EC2 world — only the deployment unit does.
