Almost every AWS question eventually becomes an IAM question. "How does your Spring Boot app read from S3?" is an IAM question. "How do you avoid leaking credentials?" is an IAM question. This note is short on JSON and long on the three ideas that matter: **identity, permission, and how AWS decides**.

> [!info] 🧭 Summary
> - **IAM User** = a long-lived *human* identity (console password + optional access keys). **IAM Group** = a bundle of users; permissions attach to the group.
> - **IAM Role** = an identity with **no permanent credentials**, *assumed* temporarily by a service, a user, or another account. STS hands back keys that expire in minutes/hours.
> - **IAM Policy** = a JSON document listing `Effect` / `Action` / `Resource` / `Condition`. Policies grant nothing until attached to a user, group or role.
> - **Roles are the answer to almost everything.** EC2 → *instance profile*. ECS task → *task role*. EKS pod → *IRSA*. Lambda → *execution role*. **Never bake access keys into code or an AMI.**
> - **Evaluation logic**: explicit **`Deny`** wins → else an explicit **`Allow`** → else **implicit deny** (default is no access).
> - **Identity-based policy** (attached to who) vs **resource-based policy** (attached to what, e.g. an S3 bucket policy). A cross-account call generally needs *both* sides to allow.
> - **Least privilege**: grant the narrowest `Action` on the narrowest `Resource`. `"Action": "*"` on `"Resource": "*"` is the classic audit finding.
> - **Root account**: use it once to set up, enable MFA, then lock it away. Never issue root access keys.
>

## 1. Why IAM exists

You have an AWS account. It has EC2 instances, an S3 bucket of customer invoices, and a production RDS database. Now five engineers and twelve services need access — but not the same access.

```text
Without IAM               With IAM
------------              --------------------------------
One root login       ->   Alice  -> read-only on prod
Shared by everyone        Bob    -> full access on staging
Full power                app-server-role -> GetObject on ONE bucket
No audit trail            CloudTrail logs every call, per identity
```

IAM answers exactly two questions on every single API call:

1. **Authentication** — who are you?
2. **Authorization** — are you allowed to do this to that?

> [!info] IAM is free and global
> IAM has no cost and is not Region-scoped. A user or role you create is usable in every Region.

## 2. The four building blocks

### IAM User — a human identity

A permanent identity with credentials:

- **Console password** — for the web UI.
- **Access key ID + secret access key** — for CLI/SDK.

```text
IAM User: umesh
  - console password (+ MFA)
  - access key AKIA...  (long-lived — the risky part)
```

> [!warning] Access keys are the number-one leak vector
> Long-lived access keys end up in Git repos, Docker images, Slack messages and Stack Overflow posts. For anything running *inside* AWS, use a **role** and no keys exist to leak.

### IAM Group — a bundle of users

Groups exist purely so you attach a policy once instead of *n* times.

```text
Group: Developers      -> policy: ReadOnlyOnStaging
  +-- umesh
  +-- alice
  +-- bob
```

Rules: a user can be in many groups; **groups cannot be nested**, and a group is not an identity — you cannot "assume" a group.

### IAM Role — the important one

An identity with **no permanent credentials**, designed to be *assumed*. When assumed, **STS** (Security Token Service) issues short-lived credentials that expire automatically.

```text
EC2 Instance
   |  (attached instance profile)
   v
Role: app-server-role
   |  policy: s3:GetObject on arn:aws:s3:::user-images/*
   v
Temporary credentials from STS  (auto-rotated, expire in ~1 hour)
   v
S3 read succeeds. No key ever stored on disk.
```

Every role has **two** policy sides — a distinction people miss:

| | What it answers |
|---|---|
| **Trust policy** (`AssumeRolePolicyDocument`) | *Who is allowed to assume this role?* (e.g. `ec2.amazonaws.com`) |
| **Permission policy** | *What can the role do once assumed?* |

**Where roles get used:**

| Caller | Mechanism |
|---|---|
| EC2 instance | **Instance profile** — credentials via IMDSv2 |
| ECS task | **Task role** (distinct from the *execution* role, which pulls the ECR image) |
| EKS pod | **IRSA** — IAM Roles for Service Accounts, via OIDC |
| Lambda function | **Execution role** |
| A user in another account | `sts:AssumeRole` — cross-account access |
| Corporate SSO user | Federation → role, no IAM user at all |

### IAM Policy — the permission document

JSON, and you do **not** need to memorise it. You need to read it.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadUserImages",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::user-images/profiles/*"
    }
  ]
}
```

| Element | Meaning |
|---|---|
| `Effect` | `Allow` or `Deny` |
| `Action` | The API calls — `s3:GetObject`, `dynamodb:Query`, `ec2:*` |
| `Resource` | The **ARN** it applies to |
| `Condition` | Optional guards — source IP, MFA present, tag match, TLS required |

**ARN anatomy** — worth being able to read aloud:

```text
arn:aws:s3:::user-images/profiles/umesh.jpg
 |   |  |  | |        |
 |   |  |  | |        +-- resource / key
 |   |  |  | +----------- bucket
 |   |  |  +------------- account id (empty for S3, it's global-namespaced)
 |   |  +---------------- region (empty for S3)
 |   +------------------- partition (aws, aws-cn, aws-us-gov)
 +----------------------- always "arn"
```

**Policy types you'll meet:**

- **AWS managed** — written by AWS (`AmazonS3ReadOnlyAccess`). Convenient, usually too broad.
- **Customer managed** — yours, reusable. The right default.
- **Inline** — embedded in one identity, dies with it. Use sparingly.

## 3. How AWS decides — evaluation logic

This is the mechanism question, and the ordering is absolute:

```text
Request: umesh wants s3:DeleteObject on arn:aws:s3:::prod-invoices/*

  1. Is there an explicit DENY anywhere?
        (SCP, permission boundary, identity policy, resource policy)
        YES -> DENY. Nothing can override this.
  2. Is there an explicit ALLOW?
        YES -> ALLOW
  3. Otherwise
        -> IMPLICIT DENY  (the default: nothing is permitted)
```

> [!intuition] The one sentence
> **Deny always wins; access is denied by default; an Allow is only needed to open a door that starts closed.**

Layers that can each contribute a deny:

| Layer | Scope |
|---|---|
| **SCP** (Service Control Policy, via Organizations) | A guardrail on the whole *account* — sets the max possible permissions |
| **Permission boundary** | The max permissions an identity may have, even if its policy grants more |
| **Identity-based policy** | Attached to a user/group/role |
| **Resource-based policy** | Attached to the resource (S3 bucket policy, SQS queue policy, KMS key policy) |

## 4. Identity-based vs resource-based policies

```text
Identity-based                     Resource-based
"umesh may read bucket X"          "bucket X may be read by umesh"
attached to the USER/ROLE          attached to the BUCKET
```

Within one account, **either one** granting access is enough. **Across accounts, you generally need both**: the caller's role must allow the action, *and* the resource policy must allow that principal.

```json
// S3 bucket policy — allows a role from ANOTHER account to read
{
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::222222222222:role/reporting-role" },
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::finance-reports/*"
}
```

Only a handful of services support resource-based policies: **S3, SQS, SNS, KMS, Lambda, Secrets Manager, ECR, API Gateway**. RDS and DynamoDB tables do **not**.

## 5. Least privilege in practice

> [!gotcha] The most common real-world failure
> An engineer debugging a permissions error attaches `AdministratorAccess` "just to unblock", and it is never removed. That role is now the account's soft underbelly.

The working method:

1. Start with **zero**.
2. Grant the specific `Action` on the specific `Resource` ARN.
3. Use **IAM Access Analyzer** / **CloudTrail** to see which permissions were actually used, and trim the rest.
4. Add `Condition` guards where cheap.

```json
// Least privilege + conditions, for a payments service writing receipts
{
  "Effect": "Allow",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::payment-receipts/${aws:PrincipalTag/tenant}/*",
  "Condition": {
    "Bool": { "aws:SecureTransport": "true" },
    "StringEquals": { "s3:x-amz-server-side-encryption": "aws:kms" }
  }
}
```

**Root account rules:** create an admin IAM user (or better, SSO), enable **MFA on root**, delete any root access keys, and use root only for the handful of tasks that require it (closing the account, changing the support plan).

## 6. The pattern you must be able to draw

The question *"How does your Spring Boot app on EC2 read from S3 without credentials?"* comes up constantly.

```text
   Spring Boot app on EC2
            |
            | 1. SDK finds no env vars / no ~/.aws/credentials
            v
   Instance Metadata Service (IMDSv2)
            |  169.254.169.254  (link-local, not routable off the host)
            v
   Instance profile -> Role: app-server-role
            |
            | 2. STS returns temporary credentials (auto-refreshed)
            v
   s3:GetObject on arn:aws:s3:::user-images/*  -> ALLOWED
```

Nothing was stored. Nothing can leak. Credentials rotate themselves.

```java
// No credentials in code — the default chain reaches IMDSv2 and finds the role.
S3Client s3 = S3Client.builder().region(Region.AP_SOUTH_1).build();

s3.getObject(GetObjectRequest.builder()
        .bucket("user-images")
        .key("profiles/umesh.jpg")
        .build());
```

> [!warning] IMDSv1 vs IMDSv2
> IMDSv1 was a plain `GET` to `169.254.169.254` — an SSRF bug in your app could read the instance's credentials. **IMDSv2 requires a session token via `PUT` first** and enforces a hop limit, which blocks that class of attack. Enforce IMDSv2 (`HttpTokens=required`) on every instance; it is the default for new launches.

## ⚠️ Gotchas & Limits

> [!warning]
> - **Explicit `Deny` cannot be overridden** — not by an admin policy, not by a resource policy. Debug "mysterious" denials by hunting for SCPs and boundaries.
> - **A policy attached to nothing does nothing.** Creating a policy is not granting it.
> - **Roles have two policies** (trust + permission). "Cannot assume role" is a *trust policy* problem; "access denied after assuming" is a *permission policy* problem.
> - **Groups are not principals** — you cannot write `"Principal": {"AWS": "...:group/Developers"}`.
> - **IAM changes are eventually consistent.** A brand-new policy can take a few seconds to take effect globally.
> - **`iam:PassRole` is the sleeper privilege.** Letting a user pass *any* role to EC2 or Lambda is effectively letting them become that role — always scope `PassRole` to specific role ARNs.
> - Don't confuse the ECS **task role** (what your container may do) with the ECS **task execution role** (what the ECS agent uses to pull the image and write logs).

## 🔑 Key Takeaways

- **User** = permanent human identity. **Role** = temporary identity assumed by services or across accounts. **Policy** = the permission document. **Group** = a convenience bundle for users.
- **Use roles for everything running inside AWS.** No access keys means nothing to leak, and rotation is automatic.
- Evaluation: **explicit Deny → explicit Allow → implicit deny**. Default is no access.
- **Identity-based vs resource-based** policies; cross-account usually needs both.
- **Least privilege**: narrowest action on the narrowest ARN, then verify with Access Analyzer.
- Root account: MFA it, no access keys, use it almost never.

## ⚡ Quick Recall

| Question | Answer |
|---|---|
| IAM User vs IAM Role? | User = permanent identity + long-lived creds; Role = assumed temporarily, STS issues short-lived creds |
| Why a role instead of access keys on EC2? | No credentials stored → nothing to leak; auto-rotated; scoped per instance |
| Policy evaluation order? | Explicit Deny > explicit Allow > implicit deny |
| Default access for a new user? | None — implicit deny |
| Least privilege? | Grant only the actions/resources actually needed |
| How does a role differ from a group? | A role is assumable and can be used by services; a group is only a container for users |
| Cross-account S3 read needs what? | Caller's identity policy **and** the bucket's resource policy |
| What issues the temporary credentials? | **STS** |
| Which service authenticates an EKS pod to IAM? | **IRSA** (IAM Roles for Service Accounts, over OIDC) |
| What is `iam:PassRole` and why care? | Lets a principal hand a role to a service — unscoped, it's privilege escalation |
