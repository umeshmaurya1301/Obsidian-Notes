This is where backend engineers who know PostgreSQL get confused. AWS says "DynamoDB" and the instinct is to look for tables, joins and a `WHERE` clause. **DynamoDB is not "AWS PostgreSQL".** It solves a different problem, and the mindset flip — *design the table around the queries, not the queries around the table* — is the whole lesson.

> [!info] 🧭 Summary
> - **DynamoDB = fully managed, serverless NoSQL key-value / document database.** Single-digit-millisecond latency at effectively any scale. Closer to Cassandra than to Postgres.
> - **Partition key (PK)** is hashed to decide **which physical partition** an item lives on. It determines data distribution — and therefore whether you scale or get a **hot partition**.
> - **Sort key (SK)** orders items *within* one partition key, enabling range queries (`begins_with`, `between`). PK + SK = **composite primary key**.
> - **`Query` is cheap; `Scan` is a disaster.** Query hits one partition; Scan reads the entire table.
> - **GSI** = a different PK/SK, its own capacity, **eventually consistent only**. **LSI** = same PK, different SK, **must be created with the table**.
> - **Reads**: **eventually consistent** (default, cheap, may be stale) vs **strongly consistent** (2× the cost, higher latency, not available on a GSI).
> - **Capacity**: **on-demand** (pay per request, zero planning) vs **provisioned** (cheaper at steady, predictable load) + auto scaling.
> - Extras that matter: **Streams** (CDC → Lambda), **TTL** (free auto-expiry), **transactions**, **DAX** (microsecond cache), 400 KB item limit.
> - **RDS for relationships, transactions and flexible queries; DynamoDB for massive scale with known access patterns.**
>
> Next: [[11. ElastiCache & Caching Patterns]] — the in-memory layer in front of both.

## 1. The mindset flip

```text
PostgreSQL                          DynamoDB
------------------------            --------------------------------
1. Design normalised tables         1. List every access pattern
2. Write whatever query you need    2. Design the key schema to serve them
3. Add an index if it's slow        3. Add a GSI for patterns keys can't serve

"What data do I have?"              "What queries will I run?"
```

In PostgreSQL you can always write a new query — it might be slow, but it works. **In DynamoDB, a query your key schema doesn't support is either impossible or a full table scan.** Getting the keys wrong is expensive to fix later, because it means a data migration.

```sql
-- PostgreSQL: flexible, ad hoc, works on day one
SELECT * FROM orders WHERE amount > 1000 ORDER BY created_at;
```

DynamoDB has no equivalent. There is no `ORDER BY` on an arbitrary column and no `WHERE` on an unindexed attribute — only "give me the items under this partition key, optionally filtered by sort key range".

## 2. Tables, items, attributes

```json
// One ITEM in the Orders table. Schemaless apart from the key attributes.
{
  "orderId":   "O-123",
  "userId":    "U-10",
  "amount":    500,
  "status":    "PAID",
  "createdAt": "2026-08-28T10:15:00Z"
}
```

- **Table** → **items** (rows) → **attributes** (columns).
- **Schemaless except the keys** — only the PK (and SK) must exist on every item; everything else varies freely per item.
- **Max item size: 400 KB.** Large blobs go in S3 with the key stored here.

---

## 3. Partition key — the single most important concept

DynamoDB spreads data over many physical partitions. **The partition key decides where each item lands.**

```text
hash(partitionKey)  ->  partition

  U-1  -> Partition-1
  U-2  -> Partition-3
  U-3  -> Partition-2
```

That's how it scales horizontally without you thinking about shards — and it's also how you can accidentally destroy performance.

### Hot partitions

```text
BAD:  PK = country          GOOD:  PK = userId
      "India"    -> 90% of traffic to ONE partition
      "Nepal"    -> idle             High cardinality -> even spread
      "Bhutan"   -> idle
```

Every partition has a throughput ceiling (**~3,000 RCU / 1,000 WCU**). Concentrate traffic on one key and you get throttling while the table as a whole sits idle.

> [!gotcha] Choosing a partition key
> Want **high cardinality** (many distinct values) and **uniform access** (no single value dominating). `userId`, `orderId`, `tenantId#userId` are good. `status`, `country`, `date` are bad — few values, wildly skewed traffic.
>
> For an unavoidably hot key, **write-shard it**: use `PK = orderId#<0-9>` with a random or hashed suffix, spreading one logical key across 10 partitions, and fan out the reads. Adaptive capacity absorbs mild skew automatically, but it won't rescue a genuinely bad key design.

---

## 4. Sort key — range queries within a partition

The partition key alone gives you "fetch one item". Adding a **sort key** gives you "fetch a *range* of items for this key, in order".

```text
PK = userId,  SK = createdAt

PK=U-100  SK=2026-01-01  { orderId: O-1, amount: 200 }
PK=U-100  SK=2026-01-02  { orderId: O-2, amount: 900 }
PK=U-100  SK=2026-01-03  { orderId: O-3, amount: 150 }
PK=U-101  SK=2026-01-01  { ... }
```

Now you can efficiently ask:

- All orders for `U-100` (partition key only)
- Orders for `U-100` in January (`SK between '2026-01-01' and '2026-01-31'`)
- The user's **most recent** order (`ScanIndexForward=false, Limit=1`)

**Items are stored physically sorted by SK within a partition**, so these are sequential reads — extremely fast.

Sort keys are also where **hierarchical modelling** happens, using `begins_with`:

```text
PK = USER#17
SK = PROFILE                        -> the profile
SK = ORDER#2026-08-01#O-1           -> orders
SK = ORDER#2026-08-15#O-2
SK = ADDRESS#home                   -> addresses

Query PK=USER#17, SK begins_with "ORDER#"  -> just the orders
Query PK=USER#17                            -> everything, in one call
```

That's the essence of **single-table design**: one query returns a whole object graph, replacing what would have been three joins in SQL.

## 5. Query vs Scan

> [!warning] The most expensive mistake in DynamoDB
> **`Scan` reads every item in the table** and then applies your filter — you are billed for everything read, not what's returned. On a 100 M-item table this is minutes of latency and a serious bill. **`Query` uses the partition key to jump straight to the right partition.**
>
> `FilterExpression` does **not** save you — filtering happens *after* the read is paid for.

```text
Query:  "PK = U-100 AND SK begins_with 'ORDER#'"   -> reads ~10 items
Scan:   "userId = U-100"                            -> reads 100,000,000 items
```

If you find yourself needing a Scan in an application path, your key schema is wrong — or you need a **GSI**.

## 6. Secondary indexes — GSI and LSI

### GSI — Global Secondary Index

Your table is keyed by `orderId`. Then the business asks for "all orders for a user". `userId` isn't the partition key, so the only option is a Scan — unless you add a GSI.

```text
Base table          PK = orderId
GSI "by-user"       PK = userId,  SK = createdAt

Get order by id      -> Query the base table
Get orders by user   -> Query the GSI
```

A GSI is a **separate, automatically-maintained copy** of the data with a different key schema. Conceptually it's `CREATE INDEX` — but with real, separate costs.

### LSI — Local Secondary Index

**Same partition key, different sort key.** Useful for an alternate ordering within a partition (e.g. orders by `amount` instead of `createdAt`).

| | **GSI** | **LSI** |
|---|---|---|
| Partition key | **Can differ** | **Must be the same** |
| When created | **Any time** | **Only at table creation — permanent** |
| Count per table | 20 (soft) | 5 |
| Capacity | **Its own** | Shares the table's |
| Consistency | **Eventually consistent only** | **Strong reads possible** |
| Size limit | None | 10 GB per partition-key value |

> [!info] Use a GSI by default
> LSIs cannot be added later, cannot be removed, and impose a 10 GB per-partition-key limit that can wedge a table permanently. GSIs are flexible and cover almost every case. Reach for an LSI only when you specifically need a **strongly consistent** alternate sort within the same partition key.

**GSI projections** decide which attributes are copied into the index: `KEYS_ONLY`, `INCLUDE` (a named subset), or `ALL`. Projecting everything makes the index a full second copy of the table — double the storage and double the write cost. Project only what the query needs.

> [!gotcha] Every write hits every index
> One `PutItem` on a table with three GSIs is **four writes** you pay for. Indexes are not free reads — they're a permanent tax on writes. Also, if a GSI is under-provisioned, **writes to the base table can be throttled**.

## 7. Consistency

The distributed-systems question. DynamoDB replicates every write across three AZs; the question is whether your read waits for all of them.

```text
WRITE  status = PAID   -> acknowledged once 2 of 3 replicas have it

Immediately read:
  Eventually consistent (default) -> might hit the lagging replica -> "PENDING"
  Strongly consistent             -> guaranteed "PAID"
```

| | **Eventually consistent** | **Strongly consistent** |
|---|---|---|
| Default | **Yes** | No — opt in per request |
| Cost | **0.5 RCU** per 4 KB | **1 RCU** per 4 KB (**2×**) |
| Latency | Lowest | Slightly higher |
| Staleness | Possible, typically < 1 s | None |
| Works on a GSI? | Yes | **No** |

Practical rule: **eventually consistent for reads that tolerate a second of staleness** (feeds, listings, recommendations, analytics); **strongly consistent for read-after-write correctness** (checking a payment status you just wrote, reading a balance before deciding).

> [!warning] GSIs are eventually consistent — always
> There is no strongly-consistent read on a GSI, and the index update happens *after* the base-table write. Never write to the base table and immediately query a GSI expecting to see it. This surprises people who think of a GSI as a SQL index.

## 8. Capacity modes and cost

You pay for **throughput**, not for servers.

- **RCU** — 1 strongly consistent read of up to **4 KB/s**, or 2 eventually consistent reads.
- **WCU** — 1 write of up to **1 KB/s**.

| Mode | How it bills | Use when |
|---|---|---|
| **On-demand** | Per request; scales instantly; zero planning | Unpredictable/spiky traffic, new features, dev. **Start here.** |
| **Provisioned** | Per RCU/WCU/hour, with auto scaling | Steady, predictable traffic — can be **significantly cheaper** |

You can switch between modes (with a cooldown). Reserved capacity gives further discounts on provisioned throughput for committed workloads.

**Throttling** (`ProvisionedThroughputExceededException`) happens when you exceed capacity — at the table level or on a single hot partition. The SDK retries with exponential backoff by default; persistent throttling means a capacity or key-design problem.

## 9. The features that come up

| Feature | What it does |
|---|---|
| **DynamoDB Streams** | An ordered change log (24 h retention) of every insert/update/delete → **triggers Lambda**. The backbone of CDC, audit trails, materialised views, and cache invalidation. |
| **TTL** | Set an epoch timestamp attribute; DynamoDB deletes expired items **free of charge** (within ~48 h). Perfect for sessions, OTPs, idempotency keys. |
| **Transactions** | `TransactWriteItems` / `TransactGetItems` — ACID across up to 100 items, even across tables. **2× the cost.** Real transactions, not eventual consistency. |
| **Conditional writes** | `attribute_not_exists(pk)` or `#version = :expected` — **optimistic locking** and the standard idempotency primitive. |
| **DAX** | A DynamoDB-native write-through cache; microsecond reads, no application changes. |
| **PITR** | Continuous backups, restore to any second in the last 35 days. Turn it on. |
| **Global Tables** | Multi-Region, multi-active replication, last-writer-wins. |
| **Adaptive capacity** | Automatically shifts throughput toward hot partitions — mitigates mild skew, not bad design. |

> [!example] Idempotency in payments, the DynamoDB way
> A conditional write is exactly the primitive you want for "process this payment only once":
> ```text
> PutItem  PK = IDEMPOTENCY#<key>
>          ConditionExpression = attribute_not_exists(PK)
>          TTL = now + 24h
> ```
> Succeeds → this is the first attempt, do the work. `ConditionalCheckFailedException` → a duplicate, return the stored result. Single-digit-millisecond, infinitely scalable, and it self-cleans via TTL. Compare that with a `SELECT ... FOR UPDATE` on a shared Postgres row, which serialises everything through one hot row.

## 10. DynamoDB vs RDS — the decision

| Choose **RDS/Aurora** when you need | Choose **DynamoDB** when you need |
|---|---|
| **JOINs, GROUP BY, window functions** | **Massive scale** — millions of req/s |
| **Multi-table ACID transactions** | **Predictable access patterns**, known up front |
| **Rich relationships** (users↔orders↔payments) | **Single-digit-ms latency** at any table size |
| **Flexible/evolving queries** — ad hoc reporting | **Zero operational overhead**, no capacity planning |
| Strong relational integrity, foreign keys | Huge, spiky, or unpredictable traffic |
| Banking, payments, ERP, inventory | Sessions, carts, leaderboards, IoT, activity feeds |

> [!example] The same system, both databases
> Building a payments platform:
> - **RDS PostgreSQL** — the **ledger**: transfers, double-entry accounting, settlement, reconciliation. Needs ACID across tables, foreign keys, and ad hoc reporting the finance team invents weekly.
> - **DynamoDB** — **idempotency keys, user sessions, device/last-seen state, notification preferences, webhook delivery status**. Enormous volume, trivially simple access patterns, no relationships.
>
> Answering "which one?" with "both, and here's the split" is a stronger answer than picking a side.

**Mental model:** *RDS = rich features, ask what data you have and query it however you like. DynamoDB = extreme scale, ask what queries you'll run and design the keys around them.*

## ⚠️ Gotchas & Limits

> [!warning]
> - **Item size max 400 KB.** Big payloads → S3, store the key.
> - **`Scan` bills for every item read**, and `FilterExpression` doesn't help — the filter runs after the read.
> - **Hot partitions throttle** even when the table looks idle. High-cardinality keys, or write-sharding.
> - **GSIs are eventually consistent, always**, and every base write costs a write per index.
> - **LSIs must be created with the table** and can never be added or removed. Prefer GSIs.
> - **A throttled GSI throttles the base table's writes.**
> - **`Query` returns max 1 MB per call** — you must paginate with `LastEvaluatedKey`.
> - **No `ORDER BY` on arbitrary attributes** — ordering only ever comes from the sort key.
> - **Transactions cost 2×** and cap at 100 items.
> - Migrating a key schema means **rewriting the data**. Model the access patterns before you create the table.
> - Attribute names count toward item size — long names on billions of items are real money.

---

## 🔑 Key Takeaways

- **DynamoDB is query-first.** Enumerate access patterns, then design the keys. Retrofitting is a migration.
- **Partition key = distribution** (avoid hot partitions); **sort key = ordering and range queries within a partition**.
- **Query, never Scan.** A Scan in a production path means the key schema is wrong.
- **GSI = different partition key, own capacity, eventually consistent. LSI = same PK, different SK, table-creation only.**
- **Eventually consistent by default; strongly consistent costs 2× and doesn't work on GSIs.**
- **On-demand to start; provisioned + auto scaling when the pattern is steady.**
- **Streams, TTL and conditional writes** are the features that show up in real designs — especially idempotency.
- **RDS for relationships and flexible queries; DynamoDB for scale with known patterns.** Most real systems use both.
