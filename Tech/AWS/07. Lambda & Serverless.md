Lambda runs your code without any server you can see, scales from zero to thousands of concurrent executions on its own, and bills per millisecond. It is superb for event-driven glue and genuinely bad for long-running stateful services — and knowing exactly where that line falls is what the interview is testing.

> [!info] 🧭 Summary
> - **Lambda = Functions as a Service.** Upload code, pick a trigger, AWS runs it. No instances, no patching, **scales to zero**.
> - You are billed on **GB-seconds** (memory × duration) + per request. Idle costs nothing.
> - **Hard limits**: **15 min** max timeout, **128 MB – 10,240 MB** memory, **512 MB – 10 GB** `/tmp`, **6 MB** sync payload / 256 KB async, 50 MB zipped deployment package (10 GB as a container image).
> - **Memory is the only performance dial** — CPU and network scale *with* it. More memory is often **cheaper** because the function finishes sooner.
> - **Cold start** = a new execution environment must be created (download code → start runtime → run init → run handler). Warm invocations skip all but the handler.
> - Java suffers most from cold starts (JVM + Spring). Fixes: **SnapStart** (snapshot after init, restore in ~ms), **provisioned concurrency**, smaller dependencies, or don't use Lambda for that workload.
> - **Concurrency** is the real scaling unit: default **1,000 per Region**, with **reserved** (guarantee/cap) and **provisioned** (pre-warmed) variants.
> - Use it for **event-driven, short, spiky** work. Avoid it for long-running APIs, stateful logic and heavy JVM monoliths.
>

## 1. What Lambda removes

```text
Traditional (EC2 / ECS)              Lambda
-------------------------            ------------------------
Provision instances                  Upload a function
Patch the OS                         (nothing)
Configure auto scaling               Automatic, per request
Pay while idle                       Pay per ms of execution
Capacity planning                    None
Deploy = rolling restart             Deploy = new version, instantly
```

```text
User uploads an image
        |
        v
      S3 (PUT event)
        |
        v
    Lambda: resize-thumbnail
        |
        v
      S3 (thumbnails/)
```

No server was provisioned, nothing ran between uploads, and you paid for ~800 ms of compute. That's the ideal Lambda shape: **event in → short work → result out**.

## 2. Execution model — and what a cold start actually is

The single most-asked Lambda question. Be precise about the phases.

```text
COLD START (first request, or after scale-out / long idle)
  1. Download code / container image          ]
  2. Start the execution environment (micro-VM)] AWS's time
  3. Start the runtime (JVM, Node, Python)     ]
  4. Run INIT code — static blocks, Spring     ] YOUR time (billed)
     context, SDK clients, DB pools            ]
  5. Run the HANDLER                            <- the actual request
  ~ 100 ms (Node/Python) to several seconds (Java + Spring)

WARM START (subsequent requests to the same environment)
  5. Run the HANDLER only
  ~ 1-10 ms overhead
```

AWS keeps an idle environment around for an unspecified period (commonly minutes) and then reclaims it. Cold starts happen when:

- The first request after idle,
- **every scale-out** — going from 10 to 100 concurrent executions means 90 cold starts,
- after every deployment (new version = all-new environments),
- after a configuration change.

### Why Java is the worst case, and what to do

JVM startup plus Spring context initialisation can push a cold start to **5–10 seconds**. The fixes, in order of preference:

| Fix | Effect | Cost |
|---|---|---|
| **SnapStart** | Snapshots the environment **after init**, then restores from it — cuts Java cold starts by up to ~90% | **Free** |
| **Provisioned concurrency** | Keeps N environments **pre-initialised and warm** | You pay for them idle |
| Trim dependencies, avoid Spring | Less to initialise | Engineering effort |
| Move init work into the handler? | **No — the opposite.** Init is *outside* the handler on purpose | — |
| Use a different runtime, or ECS | Node/Python start in ~100 ms | Rewrite / different service |

> [!intuition] Put expensive setup in `init`, not in the handler
> Anything created **outside** the handler is created once per environment and **reused across every warm invocation** — SDK clients, DB connection pools, config, parsed schemas. Anything inside the handler is rebuilt on every single request. Getting this wrong is the most common Lambda performance bug.

```java
public class ThumbnailHandler implements RequestHandler<S3Event, String> {

    // INIT scope: built once per environment, reused by every warm invocation.
    private static final S3Client S3 = S3Client.create();

    @Override
    public String handleRequest(S3Event event, Context context) {
        // HANDLER scope: runs per request. Keep it lean.
        var record = event.getRecords().get(0);
        resize(S3, record.getS3().getBucket().getName(),
                   record.getS3().getObject().getKey());
        return "ok";
    }
}
```

> [!warning] "Stateless" has an asterisk
> A warm environment **keeps its memory and `/tmp` between invocations**. Never *rely* on that for correctness (any request may hit a fresh environment) — but do be aware that **leftover state can leak between requests**. A static mutable field holding the previous caller's user context is a real security bug, not a theoretical one.

## 3. Concurrency — the real scaling model

Lambda doesn't scale by "instances"; it scales by **concurrent executions**.

```text
concurrency = requests per second x average duration in seconds

100 rps x 0.2 s  =   20 concurrent executions
100 rps x 2.0 s  =  200 concurrent executions
```

| Type | What it does |
|---|---|
| **Unreserved (default)** | Shared pool, **1,000 per Region** by default (raisable) |
| **Reserved concurrency** | Carves out a guaranteed slice for one function — **and caps it**. Use it to protect a fragile downstream (like RDS) from a Lambda stampede. |
| **Provisioned concurrency** | Keeps N environments **initialised and warm** — no cold starts, but billed while idle |

When you exceed the limit: synchronous callers get **429 `TooManyRequestsException`**; asynchronous invocations are **retried with backoff** (twice by default) and then sent to a **DLQ / on-failure destination**.

> [!gotcha] Lambda + RDS = the connection storm
> Lambda scales to hundreds of concurrent environments; **each one opens its own database connection**, and PostgreSQL falls over at a few hundred. Traditional pooling doesn't help — the pools are in separate environments.
> **Fixes:** use **RDS Proxy** (multiplexes and pools connections outside Lambda), set **reserved concurrency** as a hard cap, or use **DynamoDB**, which is HTTP-based and has no connection concept. This is a favourite senior-level interview probe.

## 4. Triggers — where invocations come from

| Source | Invocation | Typical use |
|---|---|---|
| **API Gateway / Function URL / ALB** | **Sync** | HTTP APIs |
| **S3** | **Async** | Thumbnails, CSV ingest, virus scan on upload |
| **SQS** | Poll (batch) | Queue workers |
| **SNS / EventBridge** | **Async** | Fan-out, scheduled cron (`rate(5 minutes)`) |
| **DynamoDB Streams / Kinesis** | Poll (batch, **ordered per shard**) | CDC, real-time aggregation |
| **Cognito, CloudFront, Step Functions** | Varies | Auth hooks, edge logic, orchestration |

The three modes behave very differently on failure:

- **Synchronous** — the caller sees the error. **Lambda does not retry.** Your client must.
- **Asynchronous** — Lambda **retries twice** with backoff, then sends the event to a **DLQ** or on-failure destination. **Configure one, or failures vanish silently.**
- **Poll-based (SQS/Kinesis)** — Lambda polls in batches; failures return to the queue until `maxReceiveCount`, then hit the queue's DLQ. **Use partial batch responses** so one poison message doesn't fail the other nine.

> [!warning] At-least-once means duplicates
> Async and queue-based invocations can deliver the **same event more than once**. **Make handlers idempotent** — the standard pattern is an idempotency key checked against DynamoDB (with a conditional write) before doing the work. In payments this isn't optional; a duplicate S3 event means a customer charged twice.

## 5. Lambda vs a Spring Boot service

| Use **Lambda** when | Use **ECS/EC2** when |
|---|---|
| Event-driven, triggered by S3/SQS/EventBridge | Long-running HTTP APIs |
| Short tasks (< 15 min, ideally seconds) | Requests exceed 15 min or need streaming |
| Spiky or unpredictable traffic | Steady, continuous traffic |
| Traffic drops to zero between bursts | Never idle |
| Stateless glue: thumbnails, notifications, ETL | Stateful/complex domain logic, big frameworks |
| Ops simplicity matters more than latency floor | Cold starts are unacceptable |

> [!example] Where the line falls in a payments system
> **Lambda:** settlement-file ingest from S3, webhook fan-out, expiring stale carts on a schedule, streaming ledger changes to analytics.
> **ECS/EC2:** the UPI switch itself, the order service, the payment API — continuous traffic, tight p99 latency budgets, long-lived DB connections, and rich domain logic. Running those on Lambda buys cold starts, connection storms and a 15-minute ceiling for no benefit.

**On cost:** Lambda wins decisively at low/spiky volume and **loses at sustained high volume**. A function at constant high concurrency costs far more than the equivalent Fargate task — at that point you've paid a premium for elasticity you're no longer using.

## 6. Configuration that actually matters

- **Memory (128 MB – 10,240 MB)** — the *only* performance dial. **CPU is allocated proportionally**; ~1,769 MB ≈ one full vCPU. Raising memory often **reduces total cost** because duration drops faster than the per-ms price rises. Tune it with AWS Lambda Power Tuning rather than guessing.
- **Timeout** — max **15 minutes**, default 3 seconds. Set it just above the realistic p99; a long timeout turns a hang into a large bill.
- **`/tmp`** — 512 MB by default, configurable to 10 GB. Ephemeral, and **shared across warm invocations** (so clean up after yourself).
- **Environment variables** — encrypted at rest with KMS. **Secrets belong in Secrets Manager / Parameter Store**, not in plaintext env vars.
- **Layers** — shared dependencies across functions.
- **Versions & aliases** — publish immutable versions, point an alias (`prod`) at one, and shift traffic gradually for canary deploys.
- **VPC attachment** — needed to reach RDS or ElastiCache in private subnets. Modern Lambda VPC networking no longer adds a big cold-start penalty, but a VPC-attached function **loses default internet access** — it needs a **NAT Gateway** or **VPC endpoints** to reach S3 or any public API.

## ⚠️ Gotchas & Limits

> [!warning]
> - **15-minute hard ceiling.** Longer work needs Step Functions, ECS, Batch or Fargate.
> - **6 MB synchronous payload limit** (256 KB async). Pass large data via an **S3 key**, not the payload.
> - **Cold starts** hit hardest on Java/.NET and on every scale-out. SnapStart or provisioned concurrency.
> - **Connection storms into RDS** — use RDS Proxy or reserved concurrency.
> - **At-least-once delivery → make handlers idempotent.**
> - **No DLQ configured = silently lost events** on async failures.
> - **Warm environments retain state** in memory and `/tmp` — never leak one caller's data into another's request.
> - **VPC-attached Lambdas have no internet** without a NAT Gateway or VPC endpoints.
> - **Recursive triggers burn money fast**: a function that writes to the same S3 bucket that triggers it is an infinite loop. Use separate buckets or prefix filters. (AWS now auto-detects some loops, but don't rely on it.)
> - Concurrency limits are **per Region, shared across all functions** — one runaway function can starve the rest.

## 🔑 Key Takeaways

- **Lambda = FaaS**: code + trigger, no servers, scales to zero, billed per GB-second.
- **Cold start** = creating and initialising a new execution environment. Warm invocations reuse it and run only the handler.
- **Java cold starts are the worst case** → **SnapStart** (free) or **provisioned concurrency**.
- **Init code outside the handler** is reused across invocations; handler code runs every time.
- **Concurrency (not instances) is the scaling unit** — default 1,000/Region; reserved caps and protects, provisioned pre-warms.
- **Lambda + RDS needs RDS Proxy or a concurrency cap**, or connections exhaust the database.
- Use Lambda for **event-driven, short, spiky** work; use ECS/EC2 for **long-running, steady, stateful** services.
