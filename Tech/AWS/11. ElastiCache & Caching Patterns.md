You already know Redis, so most of this note is not new technology — **ElastiCache is Redis managed by AWS**, exactly as RDS is PostgreSQL managed by AWS. The parts worth real attention are the **caching patterns** and the **distributed-lock caveats**, because that's where interviewers separate people who've read about Redis from people who've operated it.

> [!info] 🧭 Summary
> - **ElastiCache = managed Redis/Valkey (or Memcached).** Same protocol, same clients, same commands — AWS runs replication, failover, patching and backups.
> - Why: **RAM beats disk.** Postgres reads are milliseconds; Redis is sub-millisecond.
> - **Cache-aside (lazy loading)** is the default pattern: check cache → miss → query DB → populate cache → return.
> - **Always set a TTL.** No TTL means stale data forever and an eventual OOM.
> - Use cases: **caching, session storage, rate limiting, leaderboards, distributed locks, pub/sub**.
> - **Session storage in Redis is what makes app servers stateless** — the prerequisite for auto scaling.
> - **Distributed locks with `SET key val NX EX 30` are useful but not safe** in the strict sense: **lock expiry** during a slow operation and **failover before replication** both allow two holders. Redlock is debated.
> - **For money, don't rely on a Redis lock alone** — use database constraints, idempotency keys and optimistic locking.
> - Failure modes to name: **cache stampede**, **thundering herd**, **hot key**.
>

## 1. What ElastiCache is

```text
Without ElastiCache            With ElastiCache
--------------------------     -------------------------------
Launch EC2                     Create a Redis cluster
Install Redis                  (done)
Configure replication          Multi-AZ + auto-failover: on
Configure failover             (done)
Monitor memory, patch          CloudWatch + managed patching
```

```properties
# Your Spring Boot app cannot tell the difference
spring.data.redis.host=mycache.abc123.ng.0001.aps1.cache.amazonaws.com
spring.data.redis.port=6379
```

**Engine choice:**

| | **Redis / Valkey** | **Memcached** |
|---|---|---|
| Data structures | Strings, hashes, lists, **sets, sorted sets**, streams, HLL | Strings only |
| Persistence | Snapshots + AOF | **None** |
| Replication / HA | **Yes**, with automatic failover | No |
| Transactions, Lua, pub/sub | Yes | No |
| Multi-threaded | Mostly single-threaded core | **Yes** |

**Pick Redis** (or Valkey, the open-source fork AWS now pushes as the cheaper default) for essentially everything. Memcached is only interesting for a pure, simple, multi-threaded string cache. **ElastiCache Serverless** also exists — no node sizing, scales automatically, good for spiky or unknown load.

**Why in-memory at all:**

```text
PostgreSQL query   ~1-10 ms   (disk + planner + network)
Redis GET          <1 ms      (RAM + a trivial protocol)
```

That's 10–100× on the read path, and — often more importantly — **load taken off the database**, which is the expensive, hard-to-scale tier.

## 2. Use case 1 — caching

### The problem

```text
GET /products/123      ->   Spring Boot   ->   PostgreSQL
10,000 req/s                                    every single time
```

The same rarely-changing product row is read 10,000 times a second. The database burns CPU re-answering a question it just answered.

### Cache-aside (lazy loading) — the default pattern

```text
READ
  1. GET product:123 from Redis
  2. HIT  -> return it. Done.
  3. MISS -> SELECT from PostgreSQL
          -> SETEX product:123 300 <json>
          -> return it

WRITE
  1. UPDATE PostgreSQL
  2. DEL product:123        (invalidate; let the next read repopulate)
```

```java
public Product getProduct(Long id) {
    String key = "product:" + id;

    String cached = redis.opsForValue().get(key);
    if (cached != null) {
        return deserialize(cached);                       // HIT
    }

    Product p = productRepository.findById(id).orElseThrow();  // MISS
    redis.opsForValue().set(key, serialize(p), Duration.ofMinutes(5));
    return p;
}
```

**Why cache-aside wins as a default:** only requested data is cached (no wasted memory), and a cache failure degrades to slow rather than broken. Its costs: **every miss pays a DB round trip**, and cached data can go stale until the TTL expires.

### The other patterns

| Pattern | How | Trade-off |
|---|---|---|
| **Cache-aside** | App checks cache, populates on miss | **Default.** Simple, resilient; misses are slow |
| **Read-through** | Cache library fetches from the DB on miss | Cleaner app code; needs library/DAX support |
| **Write-through** | Write to cache *and* DB on every write | Cache always fresh; slower writes, caches data nobody reads |
| **Write-behind** | Write to cache, flush to DB asynchronously | Very fast writes; **risk of data loss** |

> [!warning] Always set a TTL
> A key with no expiry is stale forever and consumes memory forever. TTL is your **safety net against every invalidation bug you haven't found yet** — it bounds how wrong the cache can be. Pick it from how much staleness the use case tolerates: seconds for prices, minutes for product details, hours for reference data.
>
> Also set an **eviction policy** — `allkeys-lru` for a pure cache. The default `noeviction` makes writes *fail* when memory fills, which turns a cache into an outage.

## 3. Use case 2 — session storage

The reason this note matters to everything else in the vault.

```text
BROKEN: sessions in server memory
    ALB
   /    \
Server-1  Server-2
  ^
  User logs in here; session lives in Server-1's heap.
  Next request is balanced to Server-2 -> no session -> "logged out".
  Server-1 is replaced by the ASG      -> every user on it logged out.
```

```text
FIXED: sessions in Redis
    ALB
   /   |   \
 S-1  S-2  S-3
   \   |   /
     Redis        session:abc123 -> { userId: 17, roles: [...] }
   
  Any server can serve any request. Instances are disposable again.
```

```java
// Spring Session — externalises HttpSession with no controller changes
@EnableRedisHttpSession(maxInactiveIntervalInSeconds = 1800)
public class SessionConfig { }
```

> [!intuition] This is the keystone of horizontal scaling
> [[04. EC2 (Elastic Compute Cloud)|Auto scaling]], rolling deploys and [[05. Load Balancing & Auto Scaling|self-healing ASGs]] all assume an instance can vanish without consequence. In-memory sessions break that assumption, which is why sticky sessions are a workaround rather than a fix. **Sessions → Redis, files → S3**, and the instance holds nothing that matters.

## 4. Use cases 3–5 — rate limiting, leaderboards, pub/sub

### Rate limiting

```text
Rule: 100 requests / minute / user

INCR  ratelimit:user:123:2026-08-28T10:15
EXPIRE ... 60         (only on first increment)
> 100 ?  -> 429 Too Many Requests
```

Atomic, microsecond-fast, and shared across every application instance — which a local in-process counter can never be. For production, a **Lua script** makes the increment-and-expire atomic; sliding-window and token-bucket variants build on the same primitive.

### Leaderboards

Redis **sorted sets** were made for this:

```text
ZADD   leaderboard 4500 player:17
ZREVRANGE leaderboard 0 9 WITHSCORES   -> top 10, O(log N + M)
ZREVRANK  leaderboard player:17         -> this player's rank
```

Doing this in SQL means an `ORDER BY` over millions of rows on every page load.

### Pub/Sub

Redis can fan out messages to subscribers. Useful for cache invalidation across instances and lightweight real-time notifications — but it is **fire-and-forget with no persistence, no consumer groups, no replay**. A subscriber that's down misses the message permanently. **For anything that must not be lost, use Kafka/MSK or SQS/SNS.** (Redis **Streams** sit in between, with persistence and consumer groups.)

## 5. High availability

```text
      Primary (writes)
          |  async replication
      Replica  (reads, standby)
          |
   Primary fails -> replica promoted -> DNS repointed
```

Very similar to [[09. RDS & Aurora|RDS failover]]: **Multi-AZ with automatic failover** takes ~1–2 minutes (often less), and the endpoint stays the same.

**Cluster mode:**

| | **Cluster mode disabled** | **Cluster mode enabled** |
|---|---|---|
| Shape | 1 shard: 1 primary + up to 5 replicas | Up to 500 shards, each with replicas |
| Scaling | **Read** scaling only; data must fit one node | **Write + data** scaling via sharding |
| Client | Simple | Cluster-aware client required |
| Constraint | — | **Multi-key ops must share a hash slot** — use `{tag}` hash tags |

> [!gotcha] Replication is asynchronous
> ElastiCache replication is **async**, so a failover can lose the last few writes. That's tolerable for a cache. It is **not** tolerable if you have been treating Redis as a source of truth — and it is exactly the mechanism behind the lock caveat in §6.

## 6. Distributed locks — and why they're not what people think

The topic that separates a mid-level answer from a senior one.

### The problem

```text
Order Processor-1  ---\
                       >--- both pick up order O-123
Order Processor-2  ---/

Without a lock: the customer is charged twice.
```

### The naive Redis lock

```text
SET lock:order:123 <unique-token> NX EX 30

NX = only set if the key does not exist   -> mutual exclusion
EX = expire after 30 seconds              -> no deadlock if the holder dies
```

```java
String token = UUID.randomUUID().toString();
Boolean acquired = redis.opsForValue()
        .setIfAbsent("lock:order:123", token, Duration.ofSeconds(30));

if (Boolean.TRUE.equals(acquired)) {
    try {
        processOrder(123);
    } finally {
        // Release ONLY if we still hold it — compare-and-delete via Lua.
        // A plain DEL can delete someone else's lock after ours expired.
        redis.execute(RELEASE_SCRIPT, List.of("lock:order:123"), token);
    }
}
```

Two details that are already easy to get wrong: **the expiry is mandatory** (without it, a crashed holder deadlocks the key forever), and **release must be a compare-and-delete** (a plain `DEL` can free a lock that has since been acquired by someone else).

### The caveats that actually matter

> [!warning] Caveat 1 — lock expiry doesn't stop the work
> ```text
> t=0   Worker-1 acquires the lock, TTL 30 s
> t=30  TTL expires. Worker-1 IS STILL RUNNING — it has no idea.
> t=31  Worker-2 acquires the lock and starts the same work.
> t=40  Both write. The customer is charged twice.
> ```
> The lock expired but the *work* didn't. Redis cannot suspend your thread. Mitigations — a watchdog that renews the TTL while work proceeds, generous TTLs, **fencing tokens** — reduce the window; none of them close it.

> [!warning] Caveat 2 — failover loses the lock
> ```text
> Worker-1 acquires the lock on the PRIMARY.
> The primary crashes BEFORE async replication propagates the key.
> The replica is promoted — it has never heard of the lock.
> Worker-2 acquires the "same" lock. Two holders.
> ```
> This is inherent to asynchronous replication, not a bug you can configure away.

> [!warning] Caveat 3 — network delays and GC pauses
> A process can acquire a lock, then stall (a long GC pause, a network partition) past the TTL, and resume believing it still holds it. Distributed systems provide no way for a node to be certain it hasn't been fenced out.

### Redlock

Redis proposed the **Redlock** algorithm — acquire on a majority of N independent Redis nodes — to make this safer. There has been substantial, well-known debate in the distributed-systems community about whether it delivers the guarantees people assume, particularly under clock drift and process pauses.

**For an interview, you don't need to take a side.** You need to say: *"Redis locks are a useful coordination mechanism, but they are not equivalent to a database transaction or a consensus system like ZooKeeper/etcd. They reduce contention; they do not guarantee mutual exclusion under failure."*

### What to do for money

> [!example] Payments: don't rely on the lock for correctness
> Use the Redis lock as an **optimisation** to stop two workers duplicating effort, and make the *system* correct independently:
>
> | Mechanism | What it guarantees |
> |---|---|
> | **Idempotency key** — unique constraint on `(idempotency_key)` | A retry can never create a second charge |
> | **DB unique constraint** on `(order_id, status)` | The database refuses the duplicate outright |
> | **Optimistic locking** — `UPDATE ... WHERE version = ?` | A stale writer's update affects 0 rows and fails |
> | **`SELECT ... FOR UPDATE`** | Real mutual exclusion, enforced by the database |
> | **Transactional outbox** | Exactly-once effects across a DB write and a message publish |
>
> The Redis lock keeps ten workers from stampeding the same order. **The database constraint is what makes double-charging impossible.** Being able to draw that distinction — coordination vs. correctness — is the answer interviewers are listening for.

## 7. The failure modes to be able to name

| Problem | What happens | Fix |
|---|---|---|
| **Cache stampede / thundering herd** | A hot key expires; 10,000 concurrent requests all miss and hit the DB at once, and the DB falls over | Lock-on-miss (one requester rebuilds, others wait), **stale-while-revalidate**, **jittered TTLs** so keys don't expire in lockstep |
| **Hot key** | One key (a viral product) saturates a single shard | Client-side local cache, or replicate the key across N suffixed variants |
| **Cache penetration** | Repeated lookups for a key that doesn't exist bypass the cache every time | **Cache the negative result** with a short TTL, or a Bloom filter |
| **Big keys** | A multi-MB value blocks Redis's single-threaded core | Split the value; never `KEYS *` in production (use `SCAN`) |
| **Stale after write** | Cache invalidation missed on an update path | Invalidate on write, keep TTLs short, and use Streams/CDC-driven invalidation for critical data |
| **Memory full** | `noeviction` makes writes fail | Set `allkeys-lru` and alarm on `DatabaseMemoryUsagePercentage` |

> [!gotcha] The cache is not a database
> A cache node can be flushed, evicted or failed over at any moment. **Every value in Redis must be reconstructible from the source of truth.** If losing Redis means losing data, you have built a database without durability — the exception being deliberate use of Redis persistence, which is still weaker than RDS.

## ⚠️ Gotchas & Limits

> [!warning]
> - **No TTL = stale forever + eventual OOM.** Always expire.
> - **`noeviction` is the default** — set `allkeys-lru` for a pure cache or writes will start failing.
> - **Replication is async** — a failover can lose recent writes, including locks.
> - **Locks can expire mid-operation**; work does not stop when the key does.
> - **Redlock is contested.** Don't claim Redis gives you guaranteed mutual exclusion.
> - **Never `KEYS *` in production** — it's O(N) and blocks the single-threaded core. Use `SCAN`.
> - **Cluster mode restricts multi-key operations** to a single hash slot — use `{tag}` hash tags.
> - **ElastiCache is VPC-only.** No public endpoint, ever — it lives in a private subnet with a Security Group.
> - **Encryption in transit/at rest must be enabled at creation.**
> - **Scaling a cluster can be disruptive** and cold caches cause a load spike on the database behind them. Warm deliberately.
> - **Cross-AZ traffic between the app and the cache is billed** — and adds latency.

## 🔑 Key Takeaways

- **ElastiCache = managed Redis.** Same Redis you know; AWS owns replication, failover and patching.
- **Cache-aside is the default pattern**: check → miss → DB → populate → return. Invalidate on write, and **always set a TTL**.
- **Sessions in Redis are what make application servers stateless** — the prerequisite for auto scaling and self-healing.
- Redis is also the right tool for **rate limiting (INCR), leaderboards (sorted sets), and pub/sub** (fire-and-forget only).
- **Distributed locks are coordination, not correctness.** Expiry-during-work and failover-before-replication both permit two holders.
- **For money, the guarantee must come from the database** — idempotency keys, unique constraints, optimistic locking.
- Know the failure modes by name: **stampede, hot key, penetration, stale-after-write**.
