S3 is the single most important AWS storage service for a backend engineer. You will encounter it in almost every system, and three of its features — **presigned URLs, lifecycle policies and event notifications** — come up in interviews far more often than the rest combined.

> [!info] 🧭 Summary
> - **S3 = object storage.** A flat **bucket** holds **objects**; each object is *data + metadata + a unique key*. **Not a filesystem** — "folders" are just `/` in the key.
> - **11 nines of durability** (99.999999999%), replicated across ≥3 AZs automatically. Max object **5 TB**; max single PUT **5 GB**.
> - **Storage classes** trade retrieval cost/latency for storage cost: **Standard → Intelligent-Tiering → Standard-IA → Glacier IR → Glacier Flexible → Deep Archive**.
> - **Versioning** keeps every overwrite and turns a delete into a **delete marker** — the recovery mechanism.
> - **Lifecycle policies** automate the transitions and expiry: Standard → IA at 30 d → Glacier at 365 d → delete at 7 y.
> - **Presigned URLs** let a browser upload/download **directly to S3**, using your credentials for a limited time. Your backend never touches the bytes.
> - **Everything is private by default.** Access via IAM roles, bucket policies, or presigned URLs — never by making the bucket public.
> - **Event notifications** (PUT/DELETE → Lambda/SQS/SNS/EventBridge) are the backbone of event-driven AWS.
> - **Never store user files on EC2** — instances are disposable, and files on one instance are invisible to the others.
>

## 1. What S3 is — and what object storage means

**S3 = Simple Storage Service.** Think Google Drive or Dropbox, but built for applications: images, PDFs, videos, CSVs, logs, backups, static site assets, ML datasets.

There are three kinds of storage, and knowing which is which is a common question:

| Type | AWS service | Unit | Used by |
|---|---|---|---|
| **Block** | **EBS** | Fixed-size blocks | Operating systems, databases — a raw disk |
| **File** | **EFS / FSx** | Files in a hierarchy | Shared network drives, POSIX mounts |
| **Object** | **S3** | Object = data + metadata + key | Applications, over HTTP |

An **object** is:

```text
Key:      profiles/umesh.jpg
Data:     <the bytes>
Metadata: Content-Type: image/jpeg, size, ETag, custom x-amz-meta-* headers
Version:  (if versioning is on)
```

You interact over **HTTP APIs** (`GET`, `PUT`, `DELETE`), not a filesystem. You cannot append to an object, seek and patch a byte range, or rename — **every write replaces the whole object**.

### Buckets, keys, and the folder illusion

```text
Bucket: user-images            <- globally unique name, Region-scoped data
  |
  +-- profiles/umesh.jpg       <- these are KEYS, not paths
  +-- profiles/alice.jpg
  +-- thumbnails/umesh.jpg

s3://user-images/profiles/umesh.jpg
```

> [!intuition] S3 has no folders
> `profiles/umesh.jpg` is one flat key that happens to contain a `/`. The console *renders* a folder tree; S3 stores a flat key-value map. Consequences: "renaming a folder" means copying every object and deleting the originals, and listing is a **prefix scan** — which is why `ListObjectsV2` with a good prefix is fast and listing a bucket with millions of keys is not.

Bucket names are **globally unique across every AWS account on Earth**, DNS-compatible, and cannot be renamed.

## 2. Why not store files in the database — or on EC2?

### Not in the database

Storing a 4 MB profile picture as a `bytea` in PostgreSQL bloats the table, wrecks backup and restore times, blows out your buffer cache, and makes replication expensive.

**The pattern: bytes in S3, metadata in the database.**

```text
users
  id | name  | profile_picture_key
  17 | Umesh | profiles/17/avatar.jpg
                        |
                        v
              s3://user-images/profiles/17/avatar.jpg
```

### Not on EC2 — the interview classic

```text
Option 1: files on the instance disk
   EC2-1: image1.jpg    EC2-2: (empty)    EC2-3: (empty)
   
   - Upload lands on EC2-1
   - The next request is load-balanced to EC2-2  -> 404
   - EC2-1 is replaced by the ASG               -> file gone forever
   - Disk eventually fills                      -> outage
   - Backups are your problem
```

```text
Option 2: files in S3
   EC2-1 ---\
   EC2-2 -----> S3 (shared, durable, effectively unlimited)
   EC2-3 ---/
```

| S3 gives you | Why it matters |
|---|---|
| **11 nines durability** across ≥3 AZs | An instance or AZ dying loses nothing |
| **Shared storage** | Every instance sees every file |
| **Effectively unlimited capacity** | No disk-full outage |
| **Lifecycle management** | Automatic archival and deletion |
| **Cheaper** | Especially for large, rarely-read files |

> [!intuition] The real reason
> S3 is what makes **stateless application servers** possible. Once instances hold nothing important, they become disposable — and disposable instances are what make Auto Scaling, rolling deploys and self-healing work at all. Files on EC2 quietly break every one of those.

## 3. Storage classes

Same durability across the board (except One Zone-IA); they differ in **retrieval cost and latency**.

| Class | Access pattern | Retrieval | Use for |
|---|---|---|---|
| **Standard** | Frequent | Instant | Active files, profile images, hot data |
| **Intelligent-Tiering** | **Unknown/changing** | Instant | Auto-moves objects between tiers for a small monitoring fee — **the safe default when you can't predict** |
| **Standard-IA** | Infrequent (monthly) | Instant, **per-GB retrieval fee** | Old invoices, backups you may need |
| **One Zone-IA** | Infrequent, reproducible | Instant | **Single AZ** — cheaper, but data is lost if that AZ is lost. Only for regenerable data |
| **Glacier Instant Retrieval** | Archive, rare but instant | Instant | Medical images, compliance data occasionally read |
| **Glacier Flexible Retrieval** | Archive | **Minutes to hours** | Old backups |
| **Glacier Deep Archive** | Deep archive | **~12 hours** | 7-year regulatory retention — **cheapest storage in AWS** |

> [!gotcha] IA and Glacier have minimums
> Standard-IA and One Zone-IA bill a **minimum object size of 128 KB** and a **30-day minimum duration**; Glacier classes have 90/180-day minimums. Lifecycling millions of tiny objects into IA can cost **more** than leaving them in Standard, and early deletion is charged as if the object had stayed. Check object size distribution before writing the rule.

## 4. Versioning

Off by default. Once **enabled**, it can only be *suspended*, never removed.

```text
Without versioning              With versioning
--------------------            -----------------------------
PUT resume.pdf                  PUT resume.pdf -> version v1
PUT resume.pdf (new)            PUT resume.pdf -> version v2 (v1 retained)
  -> v1 is gone forever         GET resume.pdf -> v2 (latest)
                                GET ?versionId=v1 -> the old one
```

**Deletion behaves differently, and this is the part people miss:**

- `DELETE` on a versioned bucket **doesn't delete anything** — it writes a **delete marker** as the new latest version. `GET` returns 404, but the data is intact.
- Removing the delete marker **restores** the object. This is the "undo" for an accidental delete.
- To truly delete, you must `DELETE` a **specific `versionId`**.

**Protects against:** accidental overwrites, accidental deletes, and (with **MFA Delete** and **Object Lock**) ransomware and tampering.

> [!warning] Versioning silently multiplies your bill
> Old versions are **full objects that you pay for**, forever. A daily-overwritten 1 GB file becomes 365 GB in a year. **Always pair versioning with a lifecycle rule** that expires noncurrent versions after N days — and one for `AbortIncompleteMultipartUpload`, since failed multipart uploads leave invisible, billable parts behind.

## 5. Lifecycle policies

Rules that move or delete objects automatically based on age. This is how you stop paying Standard prices for data nobody reads.

```text
Day 0     ->  S3 Standard            (invoices being viewed daily)
Day 30    ->  Standard-IA            (rarely accessed now)
Day 365   ->  Glacier Flexible       (archive)
Year 7    ->  DELETE                 (retention period satisfied)
```

```json
{
  "Rules": [{
    "ID": "invoice-archival",
    "Status": "Enabled",
    "Filter": { "Prefix": "invoices/" },
    "Transitions": [
      { "Days": 30,  "StorageClass": "STANDARD_IA" },
      { "Days": 365, "StorageClass": "GLACIER" }
    ],
    "Expiration": { "Days": 2555 },
    "NoncurrentVersionExpiration": { "NoncurrentDays": 90 },
    "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
  }]
}
```

Rules can filter by **prefix** and by **tag**, so different data classes in one bucket can age differently.

## 6. Presigned URLs

The most important S3 concept for a backend engineer, and a frequent interview question.

### The problem

```text
Naive:  Browser --10 MB--> Spring Boot --10 MB--> S3
```

Your API server is now a file-transfer proxy: it burns bandwidth and memory on every upload, request timeouts get long, and scaling the app tier is driven by file size rather than request volume. For a 500 MB video this is untenable.

### The fix

```text
1. Browser: "I want to upload avatar.jpg"
        |
        v
2. Spring Boot: check auth, generate a presigned PUT URL (valid 10 min)
        |
        v
3. Browser --uploads DIRECTLY--> S3
        |
        v
4. Browser tells the backend "done" (or S3 fires an event notification)
        |
        v
5. Backend stores the key in PostgreSQL
```

A presigned URL is just an S3 URL with the signature, expiry and permitted operation baked into the query string. **Whoever holds it can perform that one operation, on that one key, until it expires** — no AWS credentials involved.

```java
// Generate a presigned PUT valid for 10 minutes
S3Presigner presigner = S3Presigner.create();

PutObjectPresignRequest req = PutObjectPresignRequest.builder()
        .signatureDuration(Duration.ofMinutes(10))
        .putObjectRequest(b -> b.bucket("user-images")
                                .key("profiles/17/avatar.jpg")
                                .contentType("image/jpeg"))
        .build();

String uploadUrl = presigner.presignPutObject(req).url().toString();
```

Downloads work the same way with `presignGetObject` — the bucket stays private, and each user gets a short-lived link to their own object only.

| Benefit | Why |
|---|---|
| **Backend never handles bytes** | Massive reduction in bandwidth, memory and latency |
| **Faster for the user** | Direct browser → S3, over AWS's edge network |
| **Secure** | No credentials exposed; the URL expires; scoped to one key and one operation |
| **The bucket stays private** | No public access needed to serve user content |

> [!warning] The authorisation is on *generation*, not on use
> Your backend must check "does user 17 actually own `profiles/17/avatar.jpg`?" **before** signing. Once signed, the URL works for anyone holding it — so keep expiry short (minutes), and pin `Content-Type`/`Content-Length` conditions where it matters. A presigned URL generated from an over-privileged role is an over-privileged URL.

## 7. Security — everything is private by default

```text
Internet ---X---> S3 bucket        (default: no public access)

Access is granted by exactly one of:
  - IAM identity policy      (a role/user is allowed)
  - Bucket policy            (a resource-based policy)
  - Presigned URL            (temporary, delegated)
  - ACLs                     (legacy, disabled by default — don't use)
```

The controls that matter:

- **Block Public Access** — on by default at the account and bucket level. It **overrides** any policy that would make objects public. Leave it on; serve public content via **CloudFront + Origin Access Control** instead.
- **Bucket policy** — the resource-based policy. Used for cross-account access and blanket rules (e.g. deny any request not using TLS).
- **IAM roles** — how your EC2/ECS/Lambda code gets access. No access keys anywhere.
- **Encryption** — **SSE-S3 (AES-256) is on by default for all new objects**. Use **SSE-KMS** when you need per-key access control and an audit trail of decryptions (regulated/payments data). Note KMS request costs and quotas at high throughput.

```json
// Bucket policy: refuse any non-TLS request outright
{
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::payment-receipts",
               "arn:aws:s3:::payment-receipts/*"],
  "Condition": { "Bool": { "aws:SecureTransport": "false" } }
}
```

> [!info] Public vs private buckets
> **Public** is for genuinely public web assets — and even then, front it with CloudFront. **Private** is everything else: invoices, user documents, reports, receipts. Almost every S3 data-breach headline is a bucket that was made public "temporarily".

## 8. Event notifications

S3 can publish an event when an object is created or deleted — the foundation of event-driven architecture on AWS.

```text
User uploads image        CSV dropped by a partner
        |                          |
      S3 PUT                     S3 PUT
        |                          |
   ObjectCreated event        ObjectCreated event
        |                          |
      Lambda                      SQS -> ECS worker
        |                          |
  create thumbnail          import + reconcile rows
```

**Destinations:** Lambda, SQS, SNS, or **EventBridge** (richer filtering, more targets, better for fan-out). Filter by **prefix** and **suffix** so only `uploads/*.csv` triggers your handler.

> [!warning] At-least-once, and the infinite loop
> Event delivery is **at-least-once** — your consumer **must be idempotent**. And a Lambda that writes its output back into the **same bucket and prefix** that triggered it is an infinite recursive loop that will bill you spectacularly. Write thumbnails to a **different bucket** or a prefix excluded by the filter.

## 9. Multipart upload, and the rest

- **Multipart upload** — split a large object into parts, upload them in **parallel**, retry only the failed part, then complete. **Required above 5 GB**, recommended above ~100 MB. Failed multipart uploads leave billable orphan parts — expire them with a lifecycle rule.
- **Strong consistency** — since December 2020, S3 provides **strong read-after-write consistency** for all operations, at no cost. If you read older material claiming "eventual consistency for overwrites", it is out of date.
- **Cross-Region Replication (CRR)** / **Same-Region Replication (SRR)** — async replication for DR or compliance. Requires versioning on both buckets.
- **Object Lock** — WORM (write once, read many); an object cannot be deleted before its retention date. For regulatory retention and ransomware protection.
- **Transfer Acceleration** — uploads via CloudFront edge locations for distant users.
- **S3 Select / Glacier Select** — run SQL over a single object to retrieve only matching rows.
- **Static website hosting** — S3 + CloudFront is the standard way to serve a React frontend.
- **Requester Pays**, **Access Points**, **Storage Lens** — worth recognising, not memorising.

## 10. The end-to-end pattern

```text
UPLOAD
  Browser -> POST /api/uploads/avatar        (auth check)
  Backend -> presign PUT, expires in 10 min
  Browser -> PUT directly to S3
  S3      -> ObjectCreated event -> Lambda -> thumbnail into thumbnails/
  Backend -> INSERT key into PostgreSQL

DISPLAY
  Browser -> GET /api/users/17
  Backend -> read key from PostgreSQL, presign a GET (5 min)
  Browser -> loads the image directly from S3

LIFECYCLE
  30 d -> Standard-IA    365 d -> Glacier    7 y -> deleted
```

Bytes in S3, metadata in Postgres, the backend only ever handling small JSON. That's the shape.

## ⚠️ Gotchas & Limits

> [!warning]
> - **Bucket names are globally unique and immutable.** Pick well.
> - **No folders** — renaming a prefix is a copy + delete of every object.
> - **Versioning without lifecycle rules = an unbounded bill.** Expire noncurrent versions.
> - **IA/Glacier minimums** (128 KB, 30/90/180 days) can make tiering small objects *more* expensive.
> - **Presigned URLs are bearer tokens** — authorise before signing, keep expiry short.
> - **Block Public Access overrides bucket policies.** Confusing when you *do* want public — use CloudFront + OAC instead.
> - **Event notifications are at-least-once** → idempotent consumers.
> - **Never let a triggered Lambda write back to its own trigger prefix.**
> - **Data transfer out is billed**, and `GET`/`PUT` request counts add up on chatty workloads — put CloudFront in front of hot objects.
> - **Deleting a bucket requires it to be empty**, including every old version and delete marker.
> - Read-heavy hotspots: S3 scales to 5,500 GET/s and 3,500 PUT/s **per prefix** — spread keys across prefixes for extreme throughput.

## 🔑 Key Takeaways

- **S3 = object storage**: flat bucket + key, accessed over HTTP. Not a filesystem; no appends, no renames.
- **11 nines of durability across ≥3 AZs**, and **strong read-after-write consistency**.
- **Storage classes + lifecycle policies** are how you control cost — automate the ageing, watch the minimums.
- **Versioning** protects against overwrites and deletes (delete markers), but **must** be paired with expiry rules.
- **Presigned URLs** keep file bytes out of your backend entirely — the single most useful S3 pattern in backend work.
- **Private by default**; grant via IAM roles, bucket policies or presigned URLs — never by going public.
- **Event notifications → Lambda/SQS** make S3 the trigger for event-driven pipelines.
- **Never store user files on EC2** — it breaks statelessness, and statelessness is what makes scaling work.
