You already know PostgreSQL and MySQL, so don't think of RDS as a new database. Think of it as *"PostgreSQL managed by AWS"*. The interview value is almost entirely in two topics — **Multi-AZ vs read replicas** — and in being able to say precisely which problem each one solves.

> [!info] 🧭 Summary
> - **RDS = managed relational database.** AWS runs the server, storage, patching, backups, monitoring and failover; you own schema, queries, indexes and users.
> - Engines: **PostgreSQL, MySQL, MariaDB, SQL Server, Oracle**, plus **Aurora**.
> - **Multi-AZ = high availability.** A **synchronous** standby in another AZ, **not readable**, with **automatic failover** in ~60–120 s. Solves *availability*.
> - **Read Replica = read scaling.** **Asynchronous**, **readable**, **no automatic failover**, and has **replication lag**. Solves *throughput*.
> - **They are not alternatives** — production usually runs both.
> - Failover keeps the **same endpoint**; AWS repoints DNS, so no config change is needed. This is why you never connect to an IP.
> - **Backups**: automated daily snapshot + continuous transaction logs → **point-in-time recovery** to any second within the retention window (up to 35 days).
> - **Aurora** = AWS's cloud-native MySQL/PostgreSQL-compatible engine: storage replicated **6 ways across 3 AZs**, up to **15 replicas** with ~ms lag, failover in **seconds**, auto-growing storage to 128 TiB.
> - **RDS Proxy** pools connections — the fix for Lambda/serverless connection storms.
>

## 1. What RDS actually gives you

```text
Without RDS (PostgreSQL on EC2)     With RDS
--------------------------------    ---------------------------
Launch EC2                          Create the RDS instance
Install Linux, install PostgreSQL   (done)
Configure backups                   Retention: 7 days -> done
Configure replication               Multi-AZ: yes -> done
Monitor disk, patch, tune           CloudWatch + auto minor upgrades
Handle failures at 2 a.m.           Automatic failover
```

Connecting looks exactly like any other PostgreSQL:

```properties
spring.datasource.url=jdbc:postgresql://mydb.abc123.ap-south-1.rds.amazonaws.com:5432/appdb
```

Your application cannot tell the difference between local PostgreSQL and RDS PostgreSQL. That's the point.

### What "managed" means — the split

| **AWS manages** | **You still manage** |
|---|---|
| OS + database engine patching | Schema design and migrations |
| Automated backups & snapshots | Queries, indexes, `EXPLAIN` plans |
| Monitoring & metrics | Connection pooling in the app |
| Failover infrastructure | Database users and grants |
| Hardware replacement, storage scaling | Capacity choice, parameter tuning |

> [!warning] Managed ≠ tuned
> AWS will not fix a missing index, an N+1 query, or a connection pool sized at 200 per instance. Every performance problem you had with PostgreSQL you still have — you've just outsourced the operations, not the engineering.

## 2. Multi-AZ — high availability

The most-asked RDS topic.

### The problem

An RDS instance runs in **one AZ**. Power, network or hardware failure in that AZ makes your database unavailable, and your entire application with it.

### The solution

```text
        AZ-a                          AZ-b
  +---------------+            +---------------+
  |  PRIMARY DB   | ---sync--> |  STANDBY DB   |
  |  reads+writes |            |  NOT readable |
  +---------------+            +---------------+
          ^
          |
   application (one endpoint)
```

- **Synchronous replication** — a commit is acknowledged only once it's durable on **both**. Zero data loss on failover (RPO ≈ 0).
- The standby is **not readable**. It exists purely to take over. (People assume otherwise constantly.)
- On failure, AWS **promotes the standby and repoints the endpoint's DNS** — typically **60–120 seconds**.

Failover triggers: AZ outage, primary instance failure, storage failure, instance type change, or OS patching (which is why Multi-AZ also gives you **near-zero-downtime maintenance**).

> [!info] Multi-AZ DB *cluster* — the newer option
> Classic Multi-AZ is a *DB instance* deployment with one unreadable standby. AWS also offers a **Multi-AZ DB cluster**: **two readable standbys** across three AZs with semi-synchronous replication and faster failover (~35 s). If someone challenges "the standby is never readable", that's the nuance — but for interview default, classic Multi-AZ's standby is not readable.

**Interview answer:** *"Multi-AZ provides high availability by maintaining a synchronous standby in another Availability Zone and failing over automatically during an outage."*

## 3. Read Replicas — read scaling

### The problem

```sql
SELECT * FROM orders WHERE user_id = ?
```

called millions of times a day. Your primary is saturated serving reads, and write latency suffers as a result.

### The solution

```text
              PRIMARY  (all writes)
                 |
        --- async replication ---
        |                    |
   Replica-1            Replica-2       (reads)
   (can be in           (can even be
    another AZ)          another Region)
```

- **Asynchronous** — the primary does not wait. Writes stay fast.
- Replicas are **readable**, and each has **its own endpoint**.
- Up to **5** for RDS engines (**15** for Aurora), and they can live in another Region.
- **No automatic failover** — a replica can be *manually promoted* to a standalone primary, which breaks replication.

### Replication lag — the trade-off

```text
t=0     write:  UPDATE users SET name='Umesh' WHERE id=17   -> PRIMARY
t=0+5ms read:   SELECT name FROM users WHERE id=17          -> REPLICA
        returns the OLD name.
```

Lag is typically 10 ms–1 s, but grows under heavy write load, long transactions, or a big `ALTER TABLE`. Monitor **`ReplicaLag`**.

> [!gotcha] Read-after-write is the bug you will actually ship
> A user updates their profile, is redirected, the read goes to a replica, and they see their old data — "the save didn't work". **Route reads that must be fresh to the primary.** In Spring, `@Transactional(readOnly = true)` plus a routing `DataSource` is the usual mechanism; the discipline is deciding, per use case, whether stale-by-a-second is acceptable. Analytics and dashboards: yes. Confirmation screens and balance checks after a transfer: absolutely not.

## 4. Multi-AZ vs Read Replica

Memorise this table. It is asked constantly, and mixing the two up is a red flag.

| Feature | **Multi-AZ** | **Read Replica** |
|---|---|---|
| **Purpose** | **High availability** | **Read scaling** |
| Replication | **Synchronous** | **Asynchronous** |
| Readable? | **No** (classic deployment) | **Yes** |
| Automatic failover | **Yes** | **No** (manual promotion) |
| Replication lag | None | **Possible** |
| Cross-Region | No | **Yes** |
| Data loss on failure | ~none (RPO ≈ 0) | Possible (unreplicated writes) |
| Cost | 2× instance, no extra read capacity | 1× per replica, adds read capacity |

> [!intuition] The one-liner
> **Multi-AZ is insurance. Read replicas are capacity.** Insurance you never read from; capacity you never fail over to. Production usually needs both: Multi-AZ for survival, replicas for throughput.

*"Can read replicas replace Multi-AZ?"* — **No.** A replica doesn't fail over automatically, and its async lag means promoting it can lose committed writes.

## 5. Backups and point-in-time recovery

Two distinct mechanisms:

| | **Automated backups** | **Manual snapshots** |
|---|---|---|
| Schedule | Daily, during the backup window | On demand |
| Retention | 1–**35 days** (0 disables) | **Until you delete them** |
| PITR | **Yes** | No — restores to that instant only |
| On instance deletion | Deleted (unless you take a final snapshot) | **Kept** |

### Point-in-time recovery (PITR)

```text
10:00  everything is fine
10:05  someone runs:  DELETE FROM orders;     -- no WHERE clause
10:06  panic

Daily snapshot + continuous transaction logs (every ~5 min to S3)
        |
        v
Restore to 10:04:59  ->  a NEW instance with the data intact
```

> [!warning] Restore creates a *new* instance
> PITR does not rewind your existing database — it provisions a **new** one, which takes minutes to hours depending on size, and gives you a **new endpoint**. Your recovery runbook must include cutting the application over. Practise it before you need it, and note that **restores don't carry over your parameter group, security groups or Multi-AZ setting** unless you specify them.

Snapshots are **incremental** and stored in S3. Restoring is not a fast operation on a large database — for tight RTO, rely on **Multi-AZ failover**, not on restores.

## 6. Failover, and why the endpoint matters

```text
Application connects to:
    mydb.abc123.ap-south-1.rds.amazonaws.com     <- a DNS name
NOT to:
    10.0.11.15                                    <- an IP

Primary fails
    -> AWS promotes the standby
    -> AWS updates the DNS record to the new host
    -> the application reconnects to the SAME hostname
    -> zero configuration change
```

> [!gotcha] The JVM DNS cache will bite you
> The JVM caches DNS lookups — historically **forever** when a `SecurityManager` was present. After a failover, a stale cache keeps you pointed at the dead host and connections keep failing long after AWS has recovered. Set `networkaddress.cache.ttl` to a low value (e.g. `30`), and make sure your connection pool (HikariCP) is configured to validate and evict broken connections. This is a great senior-level detail to raise unprompted.

Failover behaviour to expect: **in-flight transactions are lost** and must be retried. Applications need **connection retry with backoff** — Multi-AZ is not transparent, just fast.

## 7. Aurora — AWS's cloud-native engine

Raw notes list Aurora but never explain it, and interviewers do ask. **Aurora** is MySQL- and PostgreSQL-**compatible** (same wire protocol, drivers and SQL) but re-architected: **compute and storage are separated**.

```text
   Writer      Reader      Reader   ...  up to 15 readers
      |           |           |
      +-----------+-----------+
                  |
     SHARED DISTRIBUTED STORAGE LAYER
     6 copies across 3 AZs, self-healing, auto-grows to 128 TiB
```

Because all nodes read the **same** storage volume:

| | **RDS (standard)** | **Aurora** |
|---|---|---|
| Replicas | Up to 5, each a full copy | **Up to 15**, sharing one storage layer |
| Replica lag | 10 ms – seconds | **Typically < 10 ms** |
| Failover | 60–120 s | **Usually < 30 s, often ~10 s** |
| Storage | Provisioned in advance | **Auto-grows** in 10 GB increments |
| Durability | Multi-AZ standby | **6 copies across 3 AZs** |
| Throughput | Baseline | ~3–5× MySQL, ~2–3× PostgreSQL (AWS's figures) |
| Cost | Lower | ~20% higher per instance-hour, plus I/O |

Endpoints Aurora gives you:

- **Cluster (writer) endpoint** — always points at the current writer.
- **Reader endpoint** — load-balances across all replicas. Point read-only traffic here.
- **Custom endpoints** — subsets of instances (e.g. a large instance reserved for reporting).

Variants worth naming: **Aurora Serverless v2** (scales capacity in fine-grained increments, good for spiky or dev workloads), **Aurora Global Database** (cross-Region replication with ~1 s lag, for DR), and **Aurora Blue/Green Deployments** (a synchronised copy for near-zero-downtime major upgrades).

**When to pick Aurora:** you need more read scale, faster failover, or larger storage than RDS comfortably gives, and you're comfortable with AWS lock-in. **When to stay on RDS PostgreSQL:** cost sensitivity, an extension Aurora doesn't support, or a need to stay portable.

## 8. Connections, and the serverless problem

Relational databases have a **hard connection ceiling** — PostgreSQL allocates a backend process per connection, and a few hundred is enough to exhaust memory.

```text
30 ECS tasks x HikariCP pool of 20  =  600 connections  -> RDS falls over
500 concurrent Lambdas x 1 each     =  500 connections  -> same outcome
```

**RDS Proxy** sits between application and database, **multiplexing many client connections onto a few database connections**:

```text
Lambda / ECS  ->  RDS Proxy  ->  RDS PostgreSQL
   500 conns      pools/reuses      ~20 conns
```

It also **speeds up failover** (the proxy holds client connections open while the backend switches) and can fetch credentials from **Secrets Manager**, so no password lives in your config. For any Lambda-to-RDS architecture, RDS Proxy is close to mandatory — see [[07. Lambda & Serverless]].

Also worth knowing: **`max_connections` is set by a parameter group formula based on instance memory** — scaling up the instance is what raises it. Size your application pools deliberately; a pool of 20 per task is almost always too many.

## 9. Everything else, briefly

- **Parameter groups** — engine config (`max_connections`, `work_mem`, `shared_buffers`). Some changes need a reboot.
- **Option groups** — engine-specific add-ons.
- **DB subnet group** — the private subnets across ≥2 AZs that RDS may place instances in. Required for Multi-AZ.
- **Encryption at rest (KMS)** — must be enabled **at creation**; you cannot encrypt an existing instance in place (restore an encrypted snapshot instead). Always enable TLS in transit.
- **Storage autoscaling** — grows storage automatically before you run out. Turn it on.
- **Performance Insights** — the fastest way to find your worst query. Enable it.
- **Enhanced Monitoring**, **CloudWatch alarms** on `CPUUtilization`, `FreeableMemory`, `DatabaseConnections`, `ReplicaLag`, `FreeStorageSpace`.
- **Blue/Green deployments** — a synchronised staging copy for low-risk major-version upgrades.

## ⚠️ Gotchas & Limits

> [!warning]
> - **The Multi-AZ standby is not readable.** It is availability, not capacity.
> - **Read replicas lag.** Never serve read-after-write from a replica.
> - **Failover drops in-flight transactions.** Retry with backoff; failover is fast, not transparent.
> - **JVM DNS caching** can keep you pinned to a dead host after failover.
> - **PITR creates a new instance with a new endpoint** — and doesn't inherit your parameter/security groups.
> - **Encryption can't be added in place** — decide at creation.
> - **Connection limits scale with instance memory**, not with your ambitions. Use RDS Proxy for serverless.
> - **Deleting an instance deletes its automated backups** unless you take a final snapshot.
> - **Aurora bills for I/O** (in the standard configuration) — a very chatty workload can cost more than expected; Aurora I/O-Optimized exists for that case.
> - **Major version upgrades are not automatic** and are not reversible — use Blue/Green.
> - RDS is **not** for analytics. Big aggregations belong in Redshift or Athena, not on your OLTP primary.

## 🔑 Key Takeaways

- **RDS = managed relational DB.** AWS owns operations; you still own schema, queries and indexes.
- **Multi-AZ** = synchronous, unreadable standby, **automatic failover** → *availability*.
- **Read replicas** = asynchronous, readable, **manual promotion**, lag → *read scaling*. Production usually runs both.
- **Failover keeps the same endpoint** — always connect by DNS, and watch the JVM's DNS cache.
- **Automated backups + transaction logs → PITR** to any second within 35 days; restore creates a *new* instance.
- **Aurora** = cloud-native, 6-way replicated storage across 3 AZs, 15 low-lag replicas, sub-30 s failover, auto-growing storage.
- **RDS Proxy** solves the connection-storm problem for Lambda and large container fleets.
